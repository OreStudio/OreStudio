* Acceptance

- A matrix names every Qt reference data screen (list, detail, history, child tables) and the web screen that covers it, or states that none does, with the field and capability gaps per entity.
- An audit lists every contradiction between the Record screen standard, the Entity screen specification and UX Language, and every form layout question the standards leave open: field grouping, widget per field kind, button placement, history layout and refresh.
- The audit judges the Screen review checklist as a review instrument and says what a checkable rule needs that it lacks.
- The Qt topics are grouped and ordered for the screen pipeline, and each group names the journeys it needs.
- Findings that are work and not analysis are filed as captures.

* Decisions

- 2026-10-25: /The Qt client names the topics; the web standards rule the
  form./ A Qt screen says what a person needed to do. It does not say how the
  web screen looks. The pipeline per topic is: extract the user journeys,
  prototype to the settled standard and sign the prototype off, build with any
  server side extension, write the test scenario, test the screen, sign it
  off. A journey is judged by common sense: a CRUD variation uses the standard
  record screen, and a complex goal becomes a workflow the screen offers under
  Workflows. The journey makes sure the use cases are teased out and the work
  stays user centric; it does not map one to one onto a form.
- 2026-10-25: /One epic, four stories first./ The epic One UX language for
  every screen holds the arc in the sprint. Later topics and the other areas of
  the application join it as their own stories.
- 2026-10-25: /The Qt parity gaps are not a story of their own./ The arc was
  proposed with a fifth story that closed the parity gaps. It folds into the
  per-topic pipeline, because a gap is only known once the topic's journeys say
  what a person needs, and a screen built to close a gap without a journey is
  the Qt dialog again.
- 2026-10-25: /The checks go in before the screens change./ The harness story
  precedes the first topic story, so the first screen work proves the checks.
- 2026-10-25: /Playwright is the first harness./ Rendering checks run in a real
  browser against the environment. If it falls short the gap is recorded and
  the approach is revisited.
- 2026-10-25: /Allium for behaviour, prose for look, no OpenSpec./ The record
  screen behaviour is an Allium specification beside the prose standards.
  OpenSpec is not adopted: compass stories, tasks and captures already carry
  the change proposal workflow.

* Out of scope

  the standards, the checks and the screens.
- The screens outside reference data. They join the epic as their own stories
  once the pipeline has run on the first topic.
