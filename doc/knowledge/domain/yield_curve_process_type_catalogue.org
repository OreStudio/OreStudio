* Summary

=yield_curve_process_type= is a reference-data table that enumerates the
short-rate engines an =ir_curve_generation_config= may select. It is
declared in =ores.synthetic.api/domain/yield_curve_process_type.hpp=, it is
seeded by
=projects/ores.sql/populate/synthetic/synthetic_yield_curve_process_types_populate.sql=,
and an IR curve config's =process_type= column is a foreign key to its =code=.

* Detail

** Why it is a table

The column was once constrained by an inline check listing three strings. The
catalogue replaces that with one row per engine, so an engine is describable,
validatable as a foreign key, and orderable for display. It is scoped to
=ores.synthetic= rather than =ores.refdata=, because selecting an
=IYieldCurveProcess= engine is specific to synthetic curve generation and has
no other consumer yet. The system tenant manages the rows.

** The row

The columns are =code=, =name=, =description= and =display_order=, followed
by the audit block every entity in this schema carries. The primary key is
the tenant, the code and the valid-time window, with an exclusion constraint
that keeps two live versions of one code from overlapping. Partial unique
indexes cover the active name, the active code and the code and version pair.

** The seeded engines and their parameters

Five codes are seeded. Each one's accepted parameter names come from
=yield_curve_process_parameter_definition= and are also fixed in the mapping
layer's own expected set.

| Code                  | Parameters                                              |
|-----------------------+---------------------------------------------------------|
| VASICEK               | kappa, theta, sigma, initial_rate                        |
| COX_INGERSOLL_ROSS    | kappa, theta, sigma, initial_rate                        |
| HULL_WHITE            | kappa, theta, sigma, initial_rate                        |
| BLACK_KARASINSKI      | kappa, theta, sigma, initial_rate                        |
| TWO_FACTOR_GAUSSIAN   | kappa_x, kappa_y, theta, sigma_x, sigma_y, rho, initial_rate |

The four one-factor engines share one parameter vocabulary. The two-factor
engine adds a second mean-reversion speed, a second volatility and a
correlation, which is why =rho= carries the bounds of minus one and one in
its definition row.

** The fact the code shape does not show

Two factories exist for these engines and they disagree, so a catalogue row
is a statement about one of them and not about both.

=map_parameters_to_yield_curve_process= in
=ores.synthetic.api/src/domain/yield_curve_process_parameter_mapping.cpp=
constructs all five. It is the path the IR curve feed and the curve shape
preview handler both take, so all five engines are reachable from a config.

=ores::analytics::quant::service::process_factory::make_yield_curve_process=
constructs three of them, =vasicek=, =cox_ingersoll_ross= and =hull_white=,
and throws =std::invalid_argument= for anything else. It has no caller
anywhere in the tree. The header comment on this note's own entity, and the
comment on the create script, both name only those three engines, which
understates the seeded table.

A reader who needs to know what a curve config can actually run has to read
the mapping layer, not this table and not the create script.
