* Summary

Post-processing reads the archive the engine produced and records what it
contains. The output is a set of delimited files, one per analytic: net present
values, cashflows, curve points and whatever else the run's configuration asked
for. Post-processing parses them and loads them into tables shaped for the
queries that will read them.

It is the phase whose cost is proportional to the size of the result, and the
one where throughput is decided. Like pre-processing it has a documented
substitute: a run configured to ignore results records where the output is and
stops, so the pipeline and the workflow can be exercised without ingestion
working.

* Detail

** The steps

| Step | Reads | Produces |
|------+-------+----------|
| Fetch | object storage, by the recorded output location | the output archive |
| Unpack | the archive | one delimited file per analytic |
| Parse | each file | typed rows, in batches |
| Load | the rows | rows in the result store |
| Record | the counts | the run's result summary |

Fetch and unpack are the same for every analytic. Parse and load are per
analytic family, because the columns differ.

** The result store

The results are tabular and homogeneous, and the queries against them are
columnar: one analytic, many keys, one run. Three properties follow.

- *One narrow table per analytic family.* The columns are the analytic's own
  keys and measures. A single table keyed by analytic name and row key would be
  an entity-attribute-value layout and would cost a join for every read.
- *Provenance is separated from measures.* The run identifier, the engine
  version and the timestamps are written once per file and read rarely; keeping
  them out of the measure rows keeps the scanned relation narrow.
- *Loaded in bulk.* The ingestion path is a bulk load of a parsed file, not a
  sequence of row writes through an entity interface. The volume makes the
  difference between the two decisive.

Ownership of the store is the open question on this page. The results are the
output of a run, and reporting owns the run, so a result store in reporting is
the shortest path and has one writer. The alternative is that each analytic's
results belong to the domain that owns the underlying data — valuations to
trading, curves to market data — with =ores.ore= still supplying the parser,
because the engine's output formats are its subject. That distributes one file
across several writers.

The cost of the shortest path should be stated rather than discovered: results
landing in reporting's database make them a reporting asset, so moving them to a
domain later is a migration.

** The canonical row

Every file the engine writes is marshalled into rows of one shape before anything
loads them. The shape is the contract between the grid, the store and the screens:

| Column | Read from | Notes |
|--------+-----------+-------|
| =subject_type= | the marshal, from the file | =trade= |
| =subject_id= | =TradeId= | the engine's own identifier |
| =measure= | the file's heading | =npv=, =npv_base=, =notional=, =delta=, =gamma= |
| =currency= | =NpvCurrency=, =NotionalCurrency= | empty when the measure has none |
| =value= | the figure's column | a decimal, never formatted |
| =source= | the marshal | the file and the row it came from |

The run, its definition, its party and tenant, and =as_of= are not in the file:
they belong to the run, and the load fills them.

A file stating one measure in one row projects one row. A file stating several
measures in one row, as the sensitivity output does, widens to one row per measure.
That rule is stated per analytic in the marshal and nowhere else.

A marshal refuses rather than guesses: a file whose headings it does not know,
naming the headings it found; a row with no subject id; a figure it cannot read as
a decimal; a measure whose currency it cannot state when the measure has one. A
refusal is a run error naming the file and the heading, and it fails the
post-processing rather than writing part of a result.

The screens rely on one row per subject, measure and currency per run — a repeated
row is a fault the store's key refuses — on =value= being a decimal whose
formatting is theirs, on =measure= being open so a new analytic adds a value rather
than a column, and on a run's rows arriving together.

This refines *The result store* above: the families stay apart, and a family whose
files state several measures carries the measure as a dimension. Each is a
time-series table keyed and chunked on the run's priced date, in the form the
[[id:6F3F1A80-5B4C-4F33-ADF0-F42CDE8FF8C2][tick ingest pipeline]] gives its
hypertables.

** Where the work happens

The expensive half is reading what the engine wrote, and it belongs where the
engine is: the compute wrapper, on the worker beside it. The wrapper is the only
component that knows which analytics the package ran and what files they wrote, so
it marshals them into the canonical rows before it uploads, for the same reason the
package is prepared where the engine reads it. The reporting service's step is to
fetch, validate and load.

That split is what keeps the service scalable: a run's rows are written by a single
=COPY= inside one transaction, so many runs finishing together are many short
inserts rather than many parsers, and the work grows with the grid rather than with
the reporting service's replicas. The queue group spreads the load and the run
grant admits it.

** What a node may reach

The marshal fits because a node already holds everything it needs, and nothing
more. [[id:1805BAFC-7E43-4D9C-822F-17C3455C6E00][The job lifecycle]] has the detail;
in short, when a node claims a job it is given a work directory, an
=output_uri=, a =storage_token= and the storage HTTP base URL, and it talks to the
rest of the system over the trusted machine channel of =compute.v1.ops=:

| Reach | Why |
+-------+-----+
| the job directory | the package is extracted there and the engine writes =Output/= there |
| object storage, over HTTP with the claim's token | to upload the archive it produces |
| =compute.v1.ops= claim, heartbeat and submit | to take work and to say what happened |
| the database | not at all |
| a user session, or a user's token | not at all |

So the marshal reads and writes inside the job directory, and the canonical rows
travel in the same archive the node uploads with the same token. It adds no
access, no credential and no round trip, and it keeps the rule that a node holds
no user's authority.

** What the node does not decide

The marshal projects; it does not interpret. It knows the headings of the files the
package's analytics write, and it refuses a file it does not know rather than guess
at one. Everything a reader would call judgement -- which run this is, which party
owns it, what date it priced at, whether the rows load at all -- is decided by the
reporting service on the other side, which holds the run.

Retrieval and post-processing are two calls from the workflow because they answer
two questions: *where the output is*, and *what it says*. A transport failure and a
contract failure read differently, and the errors a person sees say which. The
pipeline keeps its six phases; [[id:38D55527-A968-41BD-8C51-FFBC184DEC5B][the
reporting note]] states the workflow's steps.

** What is not bound to ORE

The result files are delimited tables, not an ORE document. Their shape — a
header, then rows of keys and measures — is the same shape any analytic engine
produces. Binding the store to ORE's schema would tie a reporting concern to one
engine's output format for no benefit, and the parser is the only part that
needs to know the format at all.

** The substitute: ignoring results

When the run's configuration selects the substitute, the phase is not executed.
The workflow dispatches a step that records the output location on the run and
completes. Nothing is fetched, parsed or loaded.

This is what allows a run to complete while the result store is unwritten, and
it is deliberately the weakest of the substitutes: it proves that a run can
reach a terminal state and that its output exists, and it proves nothing about
the contents. Three conditions hold, as for pre-processing:

- *The output must still be recorded.* A run that ignores its results must still
  name where they are, or the work is lost the moment the archive expires.
- *The parallel phase must be indistinguishable.* Finalisation knows that the
  run completed and where the output is; it is not told whether the results were
  read.
- *The substitution must be recorded on the run.* A completed instance whose
  results were never ingested must not be mistaken for one whose results are
  queryable.

** What does not exist today

- No parsing of the engine's output at all. The archive is uploaded and
  archived; nothing reads it.
- No result store, and no model for one.
- The phase that was meant to do this is a stub that records completion without
  fetching anything, and its own comment says the work is deferred.
