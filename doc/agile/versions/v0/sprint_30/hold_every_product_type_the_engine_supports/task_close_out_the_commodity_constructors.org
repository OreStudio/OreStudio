* Notes

** From the reconcile task

ORE reads =CommodityWindowBarrierOptionData=, but the vendored XSD declares no
such element, so a writer that follows the XSD cannot write the type. That is
the likely reason the generator does not book it. See [[id:CC7CC29C-9413-4DF3-BC32-D1C8A978D295][Which trade types ORE carries and ORE Studio holds]].


** What this run found

- The planner's reason for leaving the window barrier option out was wrong. ORE reads =tradeType() + "Data"= (=windowbarrieroption.cpp=, =fromXML=), so it reads =CommodityWindowBarrierOptionData=; it is the vendored =instruments.xsd= that misspells it =CommodityWindowBarierOptionData=. The bindings generator now corrects it through =SCHEMA_ERRATA=.
- The schema states a window barrier option's strike through its strike group, as text. The first writer set it as a decimal and the bindings refused it; the recorded refusal showed it before ORE ran.
- Adding a type moves every commodity slot to another type, so all 23 commodity documents were re-recorded, and two known engine errors stopped occurring and left the known list.
- The commodity, FX and equity positions were drawn by hash. They held both directions by chance until the slots moved, when the basket option fell to one direction; they now read the turn as the other families do.
- =CommodityPairwiseVarianceSwap= and =ForwardVolatilityAgreement= are unsupported, as [[id:80315472-7360-4C53-B6F7-57F7BCE78A1C][Tag the types the engine cannot carry]] states, so they are no longer listed as awaiting a builder.

** Import proof

No ORE example states a commodity window barrier option, so its import is proven by the projection reading back the generated document, and its acceptance by the engine run on that document.
