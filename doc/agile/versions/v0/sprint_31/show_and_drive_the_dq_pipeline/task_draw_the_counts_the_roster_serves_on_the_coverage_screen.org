  draws: the bundles grouped by level in a tree on the left, the chosen bundle's
  datasets in a dense table on the right, a text filter and a state filter over
  that table, and no card beside it. A row opens the dataset's own page, which is
  [[id:F8B44A0B-844E-424D-8C12-162C4C500B4C][its own task]].
- The coverage screen reads the bundle roster and no other DQ collection, so a
  person sees the bundles by level and the members of the bundle in view from
  one operation.
- The staged column draws the number of rows the roster counts for each member,
  and the published column states its absence with a dash and not a zero.
- The readiness of a member is one of the four reasons or "metadata complete",
  and the reason is stated for a member whose artefact table staged no rows as
  well as for one that no dataset row names.
- The screen does not depend on the tenant holding the rows: a world or platform
  bundle is read where it lies, in the system tenant.

* Plan

1. Read the roster on the screen: once with no bundle, for the bundles and the
   one to open on, and once with that bundle's code, for its members and counts.
2. Draw the staged column from the member's own =staged_count= and keep the dash
   for the published count, which the provenance still owes.
3. State the readiness from the facts the roster already carries, and add the
   two it did not: whether a dataset row names the member's code and whether its
   artefact type is one the store holds. The store's discovery function already
   computed both; the operation did not state them, so it was serving the screen
   a sentence about a missing row instead of a fact about it.
4. Drop the four collection reads the screen used to make. The junction they
   read answers no rows for a shared bundle, because its generated read states a
   tenant predicate that the row level security policy does not need; that is
   [[id:276F573C-8822-46FB-AC41-531847E07AA5][its own task]] and not a reason to
   keep four requests where one answers.

* Notes

- *The arrangement changed after the first build.* The first screen was drawn as
  three stacked cards. The design that was signed off drew tables, and the area
  replaces the Qt Data Librarian, so the arrangement was reopened and signed off
  again on 2026-11-26 as a tree and a table with the dataset on its own page. This
  task carries that rework; the prototype records both arrangements.
- *The roster crashed the DQ service, and the screen said nothing.* The service
  held the registration context by reference, and registration hands it a
  temporary, so the reference dangled the moment registration returned. Every
  request to =dq.v1.ops.bundle_roster= then read a freed implementation and the
  process died with =SIGSEGV= inside =context::impl=, which the gateway saw as a
  connection drop and the screen as "Cannot reach the server". The handler holds
  the context by value now, as every generated handler does, and the state is
  recorded in the code where the member is declared.
- *The junction read is not the roster's peer.* =dataset_bundle_members.list=
  answers no members for a world or platform bundle, because its generated read
  states a tenant predicate and the membership rows live in the system tenant.
  The row level security policy admits them, so the predicate is the whole
  cause. It is [[id:276F573C-8822-46FB-AC41-531847E07AA5][its own task]].
- *A permission mismatch on the area.* The area and its card asked for any one of
  four reads; the roster asks for one, =dq::datasets:read=. Both now ask for that
  one, so a person who holds only one of the others no longer sees an area whose
  only screen refuses them.
- *The menu has no Data quality entry in the standards page.* It does now; see
  the Menu structure page's Data quality area.
- *Four reads sent together do not all arrive.* On the provisioned environment
  the screen stayed on Loading and the browser reported "Cannot reach the
  server" for two reads the DQ service never logged. The service answered the
  two bundle reads and never saw the datasets or artefact-types requests, so the
  fault is between the browser and the service and not in either. Unauthenticated
  concurrency and keep-alive reuse both pass, so it needs an authenticated read
  to show itself. The reads are serialised as a mitigation with the reason in
  the code; the gateway's HTTP session layer is where the cause lives and its
  log is full of "Session error ... end of stream" for this client across the
  whole session, before this work as well as after it.

* Result

The screen is the arrangement signed off on 2026-11-26. The bundles of every level
sit in a tree on the left, each with its dataset count; the chosen bundle's
datasets fill a dense table on the right with a text filter and a state filter
over them; and a row opens the dataset's own page, which is
[[id:F8B44A0B-844E-424D-8C12-162C4C500B4C][its own task]].

The staged column draws the count the roster serves. The published column keeps
its dash and the page names that absence, because the provenance read is still to
build. The state column draws the reason a dataset cannot publish, and the row
that is ready says so.

Read once and drawn twice: the roster is asked for the bundles, which names the
bundle to open on, and again for that bundle's members, because the staged count
costs one count per member in the service.
