* Summary

This document records how =ores.codegen= is built and how its parts
fit together: where its data lives, how templates are picked for
models, how modelines and licence headers are handled, and the
conventions it enforces. The renderer is compass-ng's =codegen= codec,
which reads this component's library; the Python generator that
rendered it before is deleted.

For /what/ the component is and /how to operate it/, see
[[id:08FBD248-257A-A474-DD43-DB08949978F1][ores.codegen]] (the component model) and the recipes it links to.

* Detail

** Main generator functions

compass-ng's =codegen= codec classifies each model by its =#+type:= line,
loads the physical-space graph from the template library, computes each
model's supported set from the facets' =#+model_types:= and the model's
=:ores.*.enabled:= overrides, resolves each output path from the archetype's
pattern, renders the Mustache template and formats C++ and TypeScript. It
writes an output only when its content differs.

** Template system

- Mustache via the =pystache= library.
- Templates live in =library/templates/=. The =.mustache= files are
  generated artefacts, tangled from the literate facet docs in the
  same directory — see the [[id:3B6B9F75-BDC9-4AE9-B16E-5A05FFC3A4B5][Codegen template library]] overview for
  the hierarchy, tangle workflow, and drift checks.
- Output is SQL, C++, or org-mode depending on the template family.

** Data files

- =library/data/licence-GPL-v3.txt= — full GPL v3 licence text used in
  generated headers.
- [[id:9340037F-54A6-44A7-9FC6-2CE739B81167][=library/data/modeline.org=]] — per-language editor modeline strings (MASD-style org hierarchy), read by the =codegen= codec.

** Model types and file naming

/This section covers the legacy JSON model path only/ — org-mode
models (the current standard; see [[id:2A2E8B6D-179D-452C-9169-04E6BB46CC07][Codegen input org-file schema
reference]]) declare their type via =#+type:= frontmatter instead of a
filename suffix, and =get_model_type()= checks that frontmatter first.
Filename-suffix detection, described below, is the fallback used only
for JSON models that carry no frontmatter.

Each legacy JSON type has a root JSON key of the same name and is
associated with one or more templates through the
[[id:D7D53D71-C9E8-43AE-AA42-E58E57CD76C8][ores physical-space graph]].

| Filename suffix       | Model type      | Root JSON key   | Primary template                             |
|-----------------------+-----------------+-----------------+----------------------------------------------|
| =*_entity.json=       | =schema=        | =entity=        | =sql_schema_table_create.mustache= (legacy)  |
| =*_domain_entity.json=| =domain_entity= | =domain_entity= | C++ templates + =sql_schema_domain_entity_create.mustache= |
| =*_junction.json=     | =junction=      | (varies)        | =sql_schema_junction_create.mustache=        |

The =*_table.json=/=*_table.org= =table= model type (root key =table=,
=sql_schema_create.mustache=) is retired — every SQL-only entity table
migrated to =domain_entity= and the type's dispatch was removed from
the generator entirely.

** Model-template mapping

The active mapping is declared in [[id:D7D53D71-C9E8-43AE-AA42-E58E57CD76C8][ores physical-space graph]], not hard-coded
in Python.  Each facet entry lists which templates apply to which model
types and the output path pattern.

*** Table schema mappings (retired)

The =*_table.json=/=*_table.org= =table= model type and its
=sql_schema_create.mustache= template are retired; every SQL-only
entity table now expresses the same shape (primary key, columns,
validation function, insert trigger, coding scheme, image id) as a
=domain_entity= model with no C++ sections, rendered via
=sql_schema_domain_entity_create.mustache=. The =codegen= codec
applies the same field normalisation to every entity — only the separate
=table= model type and its dedicated template are gone.

*** Domain entity schema mappings (=*_domain_entity.json= files)

These files drive both C++ generation and SQL for domain entities (party,
book, counterparty, etc.).  The SQL portion is handled separately from
the C++ portion.

| Template                                       | Output file                                |
|------------------------------------------------+--------------------------------------------|
| =sql_schema_domain_entity_create.mustache=     | ={component}_{entity}_create.sql=          |
| =sql_schema_notify_trigger.mustache=           | ={component}_{entity}_notify_trigger.sql=  |
| =sql_schema_artefact_create.mustache=          | =dq_{entity}_artefact_create.sql=          |
| C++ templates (via =--address ores.cpp=)        | =.hpp= / =.cpp= files                     |

*** Standard data mappings

| Model file               | Template(s)                                                              |
|--------------------------+--------------------------------------------------------------------------|
| =model.json=             | =sql_batch_execute.mustache=                                             |
| =catalogs.json=          | =sql_catalog_populate.mustache=                                          |
| =country_currency.json=  | =sql_currency_populate.mustache=, =sql_country_populate.mustache= |
| =datasets.json=          | =sql_dataset_populate.mustache=, =sql_dataset_dependency_populate.mustache= |
| =methodologies.json=     | =sql_methodology_populate.mustache=                                      |

| Template                            | Output file                              |
|-------------------------------------+------------------------------------------|
| =sql_populate_refdata.mustache=     | ={component}_{entity}_populate.sql=      |

** Addressing system

The physical-space *address* names a subtree of the [[id:D7D53D71-C9E8-43AE-AA42-E58E57CD76C8][ores physical-space
graph]] (root → technical space → facet → archetype). Every entity's
generation footprint is its supported set on that graph, narrowed by the
model's own =:ores.*.enabled:= drawer overrides. There is no separate profile
declaration to maintain — an entity's =ores.*= binding *is* its generation
footprint.

=./compass.sh generate= writes every model's footprint; =--scope <model>=
limits a run to the outputs of one model, and =--scope <template>= to the
outputs of one template.

** Component registry

Named components are declared in [[id:B3CBBDED-7CD9-423B-94D8-F5C4C0488CEA][=library/component_catalogue.org=]], in the
library that compass-ng's =codegen= codec reads. See [[id:B3CBBDED-7CD9-423B-94D8-F5C4C0488CEA][component_catalogue.org]] for
the full table (name, models_dir, entity_glob, exclude_suffix, modeling_dir).

** Features

- /Licence generation/. Generated files carry a licence header with
  editor modelines, a copyright with the current year, and the
  appropriate per-language comment formatting.
- /Multi-language comment support/. SQL and C++ use =/* ... */= with a
  =* = line prefix; Python uses ="""=, JavaScript uses =/** */=.
- /Graph-resolved output/. Each archetype's output path pattern (on
  its [[id:D7D53D71-C9E8-43AE-AA42-E58E57CD76C8][ores physical-space graph]] node) is expanded against the model's
  own fields and written project-root-relative; parent directories are
  created automatically. =--dry-run= prints the resolved paths without
  writing.
- /Overall models/. A =model.json= can orchestrate generation of
  multiple artefacts in dependency order.
- /Dynamic prefixing/. The dataset prefix on a dataset model
  prefixes every output file (for example =flags_=).
- /Automatic sibling loading/. JSON models in the same directory are
  loaded together so a template can cross-reference them.
- /Enhanced data context/. Subject-area datasets (such as
  =currencies_dataset=, =countries_dataset=) are surfaced as named
  variables to templates for direct access.

** Example model structure

From a dataset's =catalogs.json= payload:

#+begin_src json
[
    {
        "name": "Visual Assets",
        "description": "Visual media assets including country flag images.",
        "owner": "Reference Data Team"
    }
]
#+end_src

The =sql_catalog_populate.mustache= template generates SQL that:

1. Includes the enhanced licence header.
2. Sets the schema to =ores=.
3. Generates SQL calls to =metadata.upsert_dq_catalogs()=.
4. Includes summary queries.

** Extending

To add a new SQL-only entity table (the =table= model type's retired
role) for an existing component, scaffold a =domain_entity= model
(=compass add entity_org --component <name> ...=) with no =** Presentation=
section instead — see [[id:2A2E8B6D-179D-452C-9169-04E6BB46CC07][Codegen input org-file schema reference]].

To add a new facet or template:

1. Add the Mustache template to =library/templates/=.
2. Add an entry to [[id:D7D53D71-C9E8-43AE-AA42-E58E57CD76C8][ores physical-space graph]] under the relevant facet heading,
   adding a row to the templates table with =template=, =output= pattern, and optionally =model_types=.
3. A new model type needs a change to compass-ng's =codegen= codec, which
   classifies models by their =#+type:= line.

To add a new named component:

1. Add a row to [[id:B3CBBDED-7CD9-423B-94D8-F5C4C0488CEA][=library/component_catalogue.org=]] with the component's =models_dir=,
   =entity_glob=, =exclude_suffix=, and =modeling_dir=.
2. =./compass.sh generate= then covers the component's models.
