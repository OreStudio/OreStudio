The translation unit that compiles the apply fragment names no repository
itself, so the includes it needs are generated beside the fragment rather
than kept by hand: a family added to the registry then arrives with its own
header and no regeneration leaves the fragment calling a repository the unit
never declared.

The includes stay outside the namespace and outside the fragment, which is
why they travel as their own file: an include inside the fragment's namespace
would declare every repository type in that namespace.

One line per family, sorted, so two generations of the same models produce the
same bytes whatever order the modelling tree was read in.
