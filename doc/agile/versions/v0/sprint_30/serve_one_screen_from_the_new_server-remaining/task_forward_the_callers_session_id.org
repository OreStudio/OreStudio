* Goal

Make IAM's account handlers act on the caller a forwarded message speaks for:
read the delegated token when the message carries one, as the request context
already does, so a party switch, the self reads, a sign-out and a token refresh
through the C++ server act on the person signed in, as they do through the BFF.

* Acceptance

- One helper names the caller's token, the delegated one first, and every IAM
  handler that validates the caller's token reads it.
- A test proves the helper reads the delegated token, refuses a malformed one,
  and reads the Authorization token when there is no delegation.
- A party switch through the C++ server succeeds where the BFF's does, proved
  live.

* Plan

Found while proving the trade reads live on Acme. A tenant administrator lands
on the tenant's System Party, which holds no trades, and must switch to an
operating party. The BFF's switch succeeds; the C++ server's answers 401 "Your
session has ended", and IAM logs "party ... not in account's party list
(account has 0 parties)".

The first theory was the session id: IAM logged one for the BFF's request and
none for the C++ server's. The gateway now forwards it, as the BFF does, and
IAM logged it, and the switch still failed. That disproved the theory.

The cause is the token IAM reads. The BFF is the caller's own client, so the
Authorization it sends is the caller's token. The gateway sends its own token
as the Authorization and the caller's as the X-Delegated-Authorization.
=make_request_context= reads the delegated token first, but the account
handlers that validate the token themselves -- the password and email changes,
the default party, the party choice and switch, the self reads behind
=self_request_scope=, the sign-out and the refresh, and the party provisioning
step -- read the Authorization alone, so through the gateway they acted on the
HTTP server's own account, which holds no parties.

Decisions:

- =bearer_token= becomes =caller_token=, with the request context's rule: a
  delegated token names the caller when the message carries one, a delegated
  header that is not a bearer token names nobody, and otherwise the
  Authorization does. IAM's private reader in the auth handler is deleted, and
  every caller of either moves to it. A service speaking for itself sends no
  delegation, so its own calls read as before.
- It is as safe as the Authorization it replaces: the handlers validate the
  token they read as a signed JWT either way, so a delegated token names its
  holder exactly as it would in the Authorization.
- The gateway also forwards the session id the caller's token states, as the
  BFF sends its own; it did not fix the switch, and it keeps the two servers'
  requests alike.
