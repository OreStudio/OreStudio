* Plan

The notification itself already exists: =inbox.v1.ops.raise_notification=
writes the notification, its message arguments, one recipient row per person
and each person's in-application delivery, in one transaction, as the
signed-in account. The work is to reach it from a command, to name the kind,
and to point a person at their scenario.

1. *The shell surface is hand-written, and stays in the generated shape.* The
   raise takes a list of named values for its message arguments. The generator
   fills a list field from one comma-separated token, so a list of name/value
   pairs has no token form and opting the model into the shell facet fails the
   generator's own refusal of a silent gap. The unit therefore sits beside the
   generated ones and mirrors them: the same menu, the same
   positional-then-flag order, the same =__none__= token for an empty list, and
   the whole JSON answer printed. One deviation is stated in the unit: the link
   id is a flag and not a positional, because the tokenizer drops an empty
   argument and an empty link id is the normal case.
2. *One kind, three languages.* =scenario.to_run= seeds beside the inbox's own
   kinds, its message key is the server's dotted path, and the message is
   written in English, French and Portuguese so the bell renders words.
3. *One command.* =compass notify scenario <doc> --to <username@tenant>=
   resolves the doc by path or by :ID:, reads the recipient's account id from
   the database, and drives the raise through =ores.shell=, so the operation
   runs as the =--from= account and the answer is the notification's id.
4. *One suggestion.* =compass add test_scenario= prints the ready-to-run
   command for the scenario it wrote, naming the persona from the first step
   when the step states one and a placeholder when it does not.
5. *Evidence.* The scenario is raised to a real recipient and read back through
   the BFF the app itself calls.

* Notes

- The raise is reached through the hand-written shell unit. The generator has
  no token form for a list of named values, so the model stays out of the shell
  facet; the unit repeats the generated shape so a reader of one reads the
  other.
- =compass notify= takes the raising account from =ORES_SHELL_LOGIN_USERNAME=
  and =ORES_SHELL_LOGIN_PASSWORD= in =.env=, which is
  =tenant_admin@acme_corporation= here. That account raises, because raising
  asks for =inbox::notifications:write= and TenantAdmin holds the wildcard
  grant. Any other =--from= account must hold that permission.
- The response field =raised_by= carries the raiser's username, but the bell
  renders message arguments only, so the raiser is also passed as an argument.
- The kinds populate script refuses a second run over a populated database:
  its =on conflict do nothing= never fires, because the insert goes through the
  entity's insert function, which raises =already_exists= first. A fresh
  database applies the script; an existing one needs the one row inserted. This
  is older than this task and is left as it stands.
- The banner in =compass add test_scenario= still says the scenario's first step
  logs in as =tenant_admin@acme_corporation=, which the template does not state;
  the suggestion beside it names the persona or the placeholder instead.

* Result

A scenario can be handed to the person who should run it.

- The shell raises a notification through the inbox operation:
  =notification_operations raise-notification <kind_code> <link_route>
  <account_ids> [--link_id] [--argument name=value]
  [--audience_permission_code]=. It is hand-written because the operation's
  arguments are a list of name-value records and the generator's only
  container form is a list of strings; the unit mirrors the generated shape and
  states the one deviation, an empty =--link_id= being the normal case.
- The kind =scenario.to_run= (=notification.scenario.to_run=) is seeded with the
  inbox's kinds and the message in en, fr and pt.
- =compass notify scenario <doc> --to <username@tenant> [--from ...]
  [--reason ...]= resolves the doc by path or :ID:, reads the recipient from
  the database, and raises the notice with the link
  =/development/tests/<:ID:>=. The default raiser is the tenant administrator.
- =compass add test_scenario= prints the ready-to-run notify command after
  scaffolding, naming the persona from the first step where it can.
- The bell needed no change: a route with an empty link id is used as it
  stands, and a test renders the notice from its arguments.
