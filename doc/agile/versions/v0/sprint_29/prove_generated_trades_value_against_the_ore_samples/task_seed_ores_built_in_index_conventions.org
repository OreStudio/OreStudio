* Goal

Every tenant holds the Ibor and overnight index conventions ORE defines in code, each with its oresmd address, so a convention lookup answers for them.

* Acceptance

- A script mines ORE's =ored/utilities/indexparser.cpp= into seed rows of =ibor_index_convention= and =overnight_index_convention=: day count, fixing calendar, settlement days, business day convention, end of month and the oresmd address. The seed names the ORE version it was mined from.
- Population loads the seed; a provisioned tenant finds the conventions of =EUR-EURIBOR-6M= and =USD-SOFR= through =convention_lookup=.
- A tenant may override a seeded convention with its own.

* Plan

1. Give the Ibor and overnight rows of the population scripts their address,
   from =tools/ore_conventions/oresmd_index_map.tsv=, which already carries
   the ORE name of every family the codecs admit. The row's id stays the
   synthetic feeds' =(currency, family)= name: the address is the market
   identity, the id is a local catalogue name, and the lookup answers by the
   address.
2. Make the corpus-derived seed's =IborIndex= rows state the family address.
   A convention defines the family, not one tenor, and the lookup drops the
   tenor before it matches, so an address that carries one can never be found.
3. State, per row, why a family ORE has no index for carries no address
   (SEK-SWESTR, KRW-KOFR, NZD-NZONIA, INR-MIBOR: ORE has MIBOROIS, a different
   index, and no index for the other three).
4. A test of =convention_lookup= over exactly the rows population writes: it
   answers for =EUR-EURIBOR-6M= and =USD-SOFR=, and a tenant row that states
   the same address wins over the seeded one.

* Notes

- Measured while starting this task (2026-11-07), evidence in
  =evidence/index_convention_addresses.txt=. The corpus-derived seed carries
  addresses, but only for ten tenor-keyed Ibor rows, and each states the
  tenor, which the defining role cannot match. The rows for the families ORE
  defines in code (EUR-EURIBOR, USD-LIBOR, GBP-LIBOR, JPY-LIBOR, CNY-SHIBOR,
  MXN-TIIE, TWD-TAIBOR, and the overnight RFRs) carry no address at all.
- The earlier note, that the seed already held the family addresses, was
  wrong for the Ibor rows.
- ORE's index parser is not vendored: =external/ore/packages= holds binaries
  only, and =external/ore/tools/datum_catalogue= builds against a local ORE
  engine checkout we do not have. The census of ORE's names therefore comes
  from =external/ore/catalogue/index_corpus.jsonl= and from the map the
  codecs generate, not from reading =indexparser.cpp=, which the acceptance
  asks for. Say which of the two the task should require.
