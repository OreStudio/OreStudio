This page documents a [[id:31C868B9-306E-4282-BA8C-07E647021B34][task]] in the [[id:9D20C630-1504-4E5C-9110-C83D00DB03A1][Keep a secret encrypted, with its key outside the system]] story. It captures the goal, current status, acceptance, and any notes or results.

* Goal

Build =ores.vault= as a Domain composite of =api=, =core=, =service= and
=client=, and put the five operations on the bus: write, describe, resolve,
delete and rotate. A write arrives sealed to the vault's transport key. A
resolve leaves sealed to the caller's registered key, and the vault chooses that
key by the subject in the verified token rather than from the request. The key
that seals every stored row is a system credential of the unit, and it reaches
no table, no file and no variable in the tree. Every resolve records the
subject, the name, the version and the time, and no operation records a value.

Two routes in =ores.http= front the store, and both are the gateway's own: a
write, which seals the value to the vault, and a reveal, which answers a person
who holds =vault::secrets:read=. A reveal is the gateway resolving as a
registered consumer and opening the reply in its own process, so the vault gains
no operation and the bus keeps its ciphertext.

* Acceptance

- The component is scaffolded from four overviews and registered in the service registry, with its database role, NATS account and start order.
- write, describe, resolve, delete and rotate work over NATS, and only resolve
  lets a value out, sealed to the caller's registered key.
- The write route demands =vault::secrets:write= and seals the value to the
  vault's transport key before the value reaches the bus.
- The reveal route demands =vault::secrets:read=, resolves as the gateway, opens
  the reply in the gateway's process, and answers with =Cache-Control: no-store=.
  The value appears in no trace attribute, log line or error message.
- The key that seals every stored row is a system credential of the unit, and
  appears in no table, file or variable of the tree.
- Every resolve appends the subject, the name, the version and the time, and no
  operation records a value. The gateway's log names the person behind each
  reveal, and the vault never authorises on that name.

* Plan

** The order of the work

Five increments, each one ending in a tree that builds and a suite that runs, so
a mistake shows in the increment that made it.

1. *The record of each use.* A new append-only entity, =ores.vault.secret_use=,
   because a resolve has to leave a row behind before the operation that writes
   it can be honest. It follows =ores.iam.auth_event=: a codegen entity with
   =:current_state:=, so the data layer and the schema are generated and the
   record carries no versions.
2. *The keys reach the unit.* The key encryption key and the vault's transport
   private key are =LoadCredential= entries of the unit. No part of the tree
   holds a key in a variable, a table or a generated file: compass writes the
   two files at deploy into the environment's credential directory and the
   service reads them from =CREDENTIALS_DIRECTORY=, refusing to start without
   them.
3. *The five operations.* One operation model generates the protocol of
   =vault.v1.ops.write|describe|resolve|delete|rotate=; a hand-written handler
   and a composing registrar answer them, with a =custody_service= in core that
   holds the two keys and does the sealing. This is where the sealed box meets
   the database.
4. *The gateway's two routes.* =ores.http= owns the write route and the reveal
   route. The write seals in the gateway; the reveal resolves as the gateway and
   answers over the session. The gateway is therefore a consumer with a key pair
   of its own, provisioned by the same step as the vault's.
5. *The unit starts.* The application wires the NATS client, the context, the
   registrar and the heartbeat; the registry entry turns on; the exception and
   the disabled state go; the telemetry expects the service again.

** The shape of a write and a resolve

A write arrives with the value sealed to the vault's transport key. The vault
opens it with the transport private key, then seals it again under the key
encryption key with the row's tenant, name, owner and key version as additional
data, and stores one row. A resolve finds the row for the tenant and name, opens
it under the key version, looks the caller's public key up by the subject in the
verified token, seals to it, appends the use, and replies with ciphertext.

=rotate= opens and re-seals every row under a new key version in one transaction
and appends one use per row. =describe= answers the metadata and never the sealed
value. =delete= removes the row and appends the use.

* Notes

** What increments 1 and 2 settled

- The use record is =ores.vault.secret_use=, on the =current_state= route like
  =ores.iam.auth_event=: it has no versions, no audit columns and no column that
  could hold a value. A refusal appends a row as well, because the row an
  operator most wants to read is the one where somebody asked for what they did
  not own.
- The primitives now take a context and authenticate it. The sealer's context is
  the row — tenant, name, owner, key version — and the box's is the delivery —
  subject, name, version. Without it a copied ciphertext opened, which the two
  new cases prove it no longer does.
- The keys are =LoadCredential= entries: =build/keys/vault.kek= and
  =build/keys/vault.transport.key= for the vault, =gateway.transport.key= for
  the gateway. =vault_credentials.ensure()= generates whatever is missing when
  the units are written, and never replaces what exists.
- The unit generator writes the vault's unit even while the service is
  disabled; the target does not want it, so nothing starts it.

** What increment 3 and the unit settled

- The custody operations are a hand-written handler beside the generated CRUD
  registrars, because no model generates them: =write=, =describe=, =resolve=,
  =delete=, =rotate= and =public_key=, on =vault.v1.ops.*=.
- A write's sealed value is opened under the context the caller and the vault
  agree on, =vault.write|name|owner=, and stored under the row's own context.
  A resolve opens the row under the version it records and seals the value to
  the consumer the token names, under =subject|name|version=.
- Rotation needed a versioned key to mean anything: a row records the version
  that sealed it, so the deployment keeps every version it ever used, and the
  loader refuses a deployment whose stated current version it does not hold.
- The application is hand-written now. The codegen knob
  =:ores.cpp.service-app.enabled: nil= removes the whole family, so the config
  artefacts are re-enabled one by one beside it, exactly as IAM does.

** The key that reached a commit

The first version of the provisioning step committed =build/keys/vault.kek=,
because =.gitignore= named the extensions the earlier keys used (=*.pem=,
=*.key=) and this one has none. The gate's credential check reads text and a
32-byte key is not text, so nothing stopped it. The directory is now ignored as
a whole, and the lesson is a project memory:
[[id:5D19FE6D-6B62-4FD7-92D0-2960E747B5C3][Ignore a key directory, not the
extensions of its keys]].
