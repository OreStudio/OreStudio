* Plan

Phase 1 closes the grants first, because a read no person role may call is not a
read. The grants go to =Member=, the role every person account holds: the
journey's three actors all hold it, and a functional role adds nothing to a
shared screen. Each grant is one line in
=projects/ores.sql/populate/iam/iam_roles_populate.sql=, beside the section that
already classifies the same kind of read.

The latest-run read follows the codebase's own shape. The filter on
=definition_id= is the model's own =:filterable:= knob, so the filter record,
the repository condition and the TypeScript twin are generated rather than
hand-written. The latest-run read is a custom message on the run entity: one
request carrying the definition ids, one reply carrying one run per definition,
a custom repository method, and a custom handler method and subscription. The
generated files carry the paste points for all three, so nothing under
=projects/ores.reporting= is hand-edited.

Phase 2 follows the same rule as phase 1: each read is declared in the model and
carried through the paste points, so the subject, the C++ types and the
TypeScript twin come from one source. The problem count is a store aggregate and
not a page of rows. The health word is derived in the service, because the
mapping is the server's vocabulary and the states it maps are reference data a
tenant cannot read. The next fire time is the scheduler's answer, relayed on the
caller's own session, because the reporting tables record firings made and not
firings due. The owner is left open: it is a decision about what an owner is,
not a read.

** What the tests call, and what they assert

Both tests live in
=projects/ores.reporting/core/tests/service_report_instance_listing_tests.cpp=
and call the read through the service, which is the entry its NATS users reach.

- =a list of runs answers only the definitions it is asked for= writes one run
  of each of two definitions, then asks the list for the first definition and
  for both definitions. It asserts the reply holds the runs asked for, and only
  those.
- =two definitions and three runs read as two rows, each the latest run= writes
  two runs of one definition and one run of another, asks the latest-run read
  for all three definitions, and asserts the reply has two rows: the newer run
  of the first definition and the only run of the second, with no entry for the
  definition that never ran.

** Phase 1, gap by gap

- *G6, G7, G8 and G9.* Five reads are granted to =Member= in
  =projects/ores.sql/populate/iam/iam_roles_populate.sql=:
  =reporting::report_definitions:read=, =reporting::report_instances:read=,
  =reporting::report_error_events:read=, =dq::fsm_states:read= and
  =scheduler::job_instances:read=. =Member= is the role every person account
  holds, which is what reaches all three actors of the journey. No wildcard and
  no write code is granted. The classification is stated in
  [[id:3CAA394F-E84C-3434-331B-6E664F7E84D2][Role-Based Access Control]].
- *G1.* One read answers for every definition named:
  =reporting.v1.ops.get_latest_report_instances_by_definition=, declared in
  =ores.reporting.report_instance.org= under =* Messages= and carried through
  the custom paste points of the repository, the service, the handler and the
  sub-registrar. The store reduces, so the cost is one row per definition.
  Party scope is the row-level security on the table; the request names no
  party.
- *G2.* =definition_id= is =:filterable: true= on the run entity, so the list
  filter carries =definition_id= and =definition_id_one_of=, the repository
  builds the condition, and the TypeScript twin states them. The model, not a
  generated file, is the file that changed.

The shape chosen for G1 is two reads, not one join: the definitions read, then
one latest-run read keyed by the ids that read returned. Neither the definition
nor the run has to grow a composite message, and each read stays the codegen's
own artefact. The screen is one call per table, not the three reads and the BFF
reduction the specification records.

** Phase 2, gap by gap

- *G3.* =reporting.v1.ops.get_report_error_counts= answers one row per run that
  recorded a problem, carrying how many are errors and how many are warnings. A
  run with no problem has no entry, which the screen draws as no problems. The
  count is one =GROUP BY= in the store, so a run with twenty errors costs one
  row and the error rows never leave the database. The read follows the codegen
  route phase 1 used for the latest run: two declared messages in
  =ores.reporting.report_error_event.org=, a custom repository method (where the
  codebase already puts a custom read), a custom service method, a custom handler
  method and a custom subscription. The model is the file that changed; the
  generated files carry the paste points.
  The verb is =ops= because the subject gate admits eight verbs on a resource and
  a count is none of them: the count is a domain read of the run's problems, not
  a page of them.
- *G4.* =reporting.v1.ops.get_report_instance_health= answers the health word of
  each run asked for, and the state name the word came from. The word is derived
  in the reporting service, in
  =projects/ores.reporting/core/include/ores.reporting.core/service/report_health.hpp=,
  and not in a client. The mapping is stated once:

  | state                       | health word            |
  |-----------------------------+------------------------|
  | =pending=, =queued=, =running= | =running=           |
  | =completed=, no errors      | =completed clean=      |
  | =completed=, one error or more | =completed with errors= |
  | =failed=                    | =failed=               |
  | =cancelled=, =skipped=      | none yet (G12)         |

  A run that has not started has no word of its own in the screen's five, so it
  reads as =running=, the one word for in flight. =cancelled= and =skipped= map
  to no word, on purpose: G12 is the decision, it belongs to phase 3, and the
  function says so in its comment rather than borrowing a nearby word.
  The read returns the word rather than the state names for two reasons. The
  word is the server's vocabulary, and a client that mapped state names itself
  would be a second place to change when G12 is decided. And the state names are
  not the screen's to read at all: the lifecycle states are the system tenant's
  reference data, and the row-level policy on =ores_dq_fsm_states_tbl= admits
  them only to a session that states the system tenant, so a tenant session
  asking =dq.v1.fsm_states.list= for them sees nothing. The reporting service
  reads them under the system tenant, which is what its own state lookups
  already do, and answers the word. The =dq::fsm_states:read= grant G9 added
  stays, but this read no longer needs it.
- *G5.* =reporting.v1.ops.get_next_fire= answers, per definition, when the
  scheduler says the definition's job fires next, or no time when it states
  none. The read is on the definitions whose ids the caller names; the party
  scope is the session's, never a field. The reporting service reads the
  definitions to learn their =scheduler_job_id=, then relays the caller's own
  session to =scheduler.v1.ops.get_scheduler_status= once for the whole page and
  joins the status to the definitions in C++. A paused job states no next fire,
  and a definition with no job is run on demand; both answer no time, and the
  screen learns which from =scheduler_job_id= in the definition it already read.
  The join is a named unit, =plan_next_fire= in =next_fire_plan.hpp=, so it is
  tested against the same function the service calls.

** G5, the verification the gap asked for

The three facts the scheduler read rests on, each read in the tree at this
branch:

- =scheduler::job_instances:read= is granted to =Member= at
  =projects/ores.sql/populate/iam/iam_roles_populate.sql:213=, beside the four
  reporting reads phase 1 added, and the populated database answers the same
  code for =Member=.
- =scheduler.v1.ops.get_scheduler_status= is gated by that code and no other,
  at =projects/ores.scheduler/core/include/ores.scheduler.core/messaging/scheduler_status_handler.hpp:71=.
- Its reply carries =next_fire_at= per job
  (=scheduling_operations_protocol.hpp=, =job_schedule_status=), filled from the

So the read is callable by =Member= and it carries the time. It is wired through
the reporting read above, and the caller's grant is what answers the scheduler
underneath it: the reporting service adds no authority of its own and forwards
nothing it does not hold.

** G10, the owner, and the decision this task does not make

Nothing in the tree records who owns a definition. =report_definition= has no
owner column, and its nearest relation, =run_grant_id=, names a consent whose
=grantor_account_id= is nullable and is a grantor rather than an owner. The
prototype's Owner column is a fixture. No column was added, because what an
owner is has not been decided and a column on a guess would have to be migrated
away.

The question is two questions: who an owner is, and where the ownership is
recorded. The options:

1. *An owner is a person account.* A nullable =owner_account_id= on the
   definition, resolved to the account's name by the read. One person owns a
   report; the cell answers "who to ask". Cost: an account that leaves must hand
   the definitions on, and the reporting service has to read IAM to name the
   person, which it already does for tenants and run grants.
2. *An owner is a party.* The definition already carries =party_id=, so the cell
   would repeat the Party cell. It only means something if the intent is a desk
   or a team inside the party, and no table holds that today.
3. *An owner is a role.* An =owner_role_id= pointing at an IAM role. The cell
   then names a team rather than a person and changes hands without a write to
   the definition, which is cheap to keep current and weaker as an answer to
   "who do I ask".
4. *Ownership is an assignment.* A separate table of (definition, account,
   effective window), so ownership has history and more than one person can hold
   it. The most general and the most expensive: a new table, its own reads, and a
   rule for which holder the cell draws.

*Recommendation.* Option 1: a nullable =owner_account_id= on the definition.
The prototype's own words for the cell are "the person the report belongs to",
one column keeps the definition read one row, and a nullable column lets the
definitions that exist today read as "unassigned" rather than as someone else's.
The read that follows is =reporting.v1.report_definitions.list=, which already
returns the definition, with the account name resolved beside it and
=reporting::report_definitions:read= as its gate.

*The decision, recorded elsewhere.* The recommendation above is superseded. A
capture now records that ownership belongs to a *team* and not to a person —
[[id:312E7600-482B-4656-970B-63DE8C5C3CCA][A report is owned by a team, not by a person]], filed in
=doc/agile/product_backlog/inbox/=. The reason is that an individual owner
answers "who last touched this" and not "who answers for this", breaks when the
person moves, and in practice reports are run and repaired by a rota. The capture
also records what a team is as an open question, so no column can be designed
yet. *G10 must be re-scoped to a team when it is picked up:* the column names a
team, and the reads and the cell follow that answer rather than
=owner_account_id=.

Until that is settled, G10 stays open and the Owner cell has no source.
