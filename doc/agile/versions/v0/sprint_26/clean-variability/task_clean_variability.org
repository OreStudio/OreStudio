* Notes

** What the component is

=ores.variability= is a composite of =api=, =core= and =service=
([[id:8C604D55-6F20-41D2-A66A-12A767B81D07][ores.assets]] is the same shape).
=api= holds the domain type, its JSON and table I/O, the wire protocol and an
event type; =core= holds the entity, mapper, repository, service, handler and
registrar; =service= is the runnable host.

It owns one entity and one table, =ores_variability_system_settings_tbl=. The
table is bitemporal: its primary key is
=(tenant_id, party_id, name, valid_from, valid_to)= with a GiST exclusion over
the validity window. A setting is named by a dotted string such as
=system.bootstrap_mode= or =onboarding.party=, typed =boolean=, =integer=,
=string= or =json=, and scoped to a tenant and a party; =party_id= defaults to
the tenant's system party, so most settings are tenant-wide.

** The gap against the standard

The component has one defect with two faces, and it is the same finding under
M06 and P01 to P04: no wire type is modelled, and the hand-written protocol
predates the canonical grammar. Measured against
[[id:C650CBC9-FDED-4C68-981F-7902E296928E][NATS entity protocol specification]]:

- The resource segment is =settings=, not =system_settings=.
- =save= and =history= are not verbs. The closed set has =put= for the first
  and no verb for the second: an entity's versions are a sub-resource read with
  the standard verbs.
- The read type and the write type are the same type. =domain::system_setting=
  carries =tenant_id=, =party_id=, =version=, =modified_by=, =performed_by=
  and =recorded_at=, and a write sends that same struct. The specification
  makes tenancy, version and provenance server-owned and forbids them in a
  write record, precisely so that a round-tripped read cannot be used to lie.
  The handler papers over this by re-stamping the fields after decoding, which
  hides the defect from every gate.
- Responses are ={success, message}= rather than the specification's =result=,
  and a failure carries the exception text in the payload.
- The list is unpaged and unordered, and there is no =get=, =get_many=,
  =put_many=, =delete_many= or precondition.
- =clear_bootstrap_mode= and =complete_party_onboarding= are genuine domain
  operations in the common namespace. The specification reserves
  =variability.v1.ops.*= for exactly this.

** Pre-existing defects the inventory found

None of these is the clean-standard work itself. Each is a real defect the
census exposed, and each is either fixed here or filed with a reason.

*** The setting-change event has no publisher, and one subscriber listens on a subject nobody owns

=system_setting_changed_event= is declared in =api= and subscribed in
=ores.http/server/src/app/application.cpp:93-97=. Nothing in
=projects/ores.variability/*/src/= ever publishes it: there is no publisher, no
event bus and no outbound subject in the component at all. Separately,
=ores.iam/core/src/messaging/registrar.cpp:370= subscribes to the raw literal
="ores.variability.system_setting_changed"=, which is not the event's own name,
not a subject any component declares, and not the canonical event form. Its
comment says an update to =iam.token.*= takes effect without a restart; nothing
publishes, so it never fires and the reload never happens. Two subscriptions,
two different subjects, zero publishers.

*** Three components use variability as an in-process settings library

The wire protocol is only half the component's interface. In process:

| =ores.iam= | =system_settings_service::{get_int, refresh, is_bootstrap_mode_enabled, set_bootstrap_mode, is_user_signups_enabled, is_signup_requires_authorization_enabled, is_onboarding_party_complete}=, from =token_settings.cpp=, =bootstrap_mode_service.cpp=, =signup_service.cpp=, =iam_routes.cpp=, =auth_handler.hpp= and =account_operations_handler.hpp=. |

A generated stack replaces the entity, mapper, repository, service and handler.
The generated service will not carry =is_bootstrap_mode_enabled= or the other
typed accessors, because those are this component's domain logic rather than

** Decisions

*** D1. What identifies a setting on the wire

The table's identity is the composite =(tenant_id, party_id, name)=, and two of
those three columns are server-owned. So the wire key is one of:

- *(a) =name= alone*, with tenancy and party read from the authenticated
  context. This is the =ores.iam.account= precedent, where the key is the
  username and the tenant comes from the token. It needs no new column, no seed
  rewrite and no compass change. It cannot address another party's setting,
  which no caller does today.
- *(b) A new surrogate =id= uuid*, with =name= as the natural key. This is the
  =ores.assets.tag= precedent, binding =uuid-identified-lookup=. It costs a
  schema change, a data migration, an edit to every seed script, an edit to
  =compass_db.py=, and a change to the upsert function.

Recommendation: *(a)*. It is the smaller change, it matches how the settings are
actually addressed, and (b) buys nothing a current caller needs.

*** D2. The two domain operations

=clear_bootstrap_mode= clears =system.bootstrap_mode= and sets
=onboarding.tenant=; =complete_party_onboarding= sets =onboarding.party= for a
party named in the request. Two options:

- *(a) Model them as operation models under =variability.v1.ops.*=*, which is
  what P04 asks for. The party named by =complete_party_onboarding= is the
  party being onboarded, not the caller's own party, so it is a target rather
  than a claim of tenancy and it belongs in a domain operation. Record the
  reason, because the specification's server-owned rule otherwise reads as
  forbidding it.
- *(b) Re-express both as ordinary writes* of =system.bootstrap_mode= and
  =onboarding.party=. This removes two subjects and two handler methods, but it
  puts a party scope on the wire, which D1 rules out.

Recommendation: *(a)*.

*** D3. How the in-process consumers survive the generation

Three components call variability in process, not over the wire: =iam= through
nine typed accessors, =http= through =get_all()=, =refdata= through the
repository and =read_latest(ctx, name)=. A generated stack replaces the entity,
mapper, repository, service and handler, and the generated service carries
entity verbs only. It will not carry =is_bootstrap_mode_enabled=,
=is_signup_requires_authorization_enabled= or the rest, because those are this
component's domain logic, not entity operations. Three options:

- *(a) Generate the CRUD and keep a hand-written typed settings service on top
  of the generated repository.* Codegen owns the entity, the wire protocol, the
  handler, the SQL and the shell surface; the component keeps a small
  hand-written facade holding only the typed accessors its three in-process
  consumers need. This is the split the architecture pages already describe for
  =core=: repositories and a service layer. The dead accessors and the dead
  repository methods go; the nine live ones stay.
- *(b) Migrate all three consumers to the wire.* It removes the library edges,
  but =iam= reads settings during startup and inside request handlers, and a
  synchronous bus round trip on that path buys a failure mode the in-process
  call cannot have. =refdata= reaches for the repository, not even the service,
  and would have to grow a client for one setting.
- *(c) Keep the whole in-process stack hand-written and generate only the wire
  types.* This passes M06 and P01 to P04 while leaving the entity, mapper,
  repository and service as hand-written duplicates of what codegen emits for
  every other component, which is what G02 forbids.

Recommendation: *(a)*. It satisfies G02, keeps the in-process path as cheap as
it is today, and makes the surviving hand-written surface a deliberate, small
facade rather than a parallel implementation.

*** D4. The never-published change event

Two subscribers, two different subjects, no publisher. Options: publish the
event from the generated write path and point both subscribers at the canonical
subject, or delete the event and the two subscriptions. P06 asks for an event
cache that warms through the canonical list and follows the canonical event
actions, so the first is the standard-compliant answer; the second is honest if
the reload is not wanted. Recommendation: publish it, and fold the =iam=
subscription's raw literal into the canonical generated constant. The reload
the IAM comment promises has never worked, so this is a behaviour change that
needs a test.
