- The parallel steps of a run execute in different services at once.

* Plan

Every step of a provisioning run is dispatched to one subject,
=iam.v1.ops.provision_tenant_step=, served by ores.iam. That is why iam links
the synthetic and refdata cores: it compiles code for work its own data has
nothing to do with. It is also why the parallel steps of a run queue: one
service takes them.

The move is one kind at a time, because each kind drags its own dependencies:

1. State the owner of each kind once, where the definition states a step's
   subject, so the engine stores the owner with the row and every service reads
   the same table. Done here, as =step_subject_for_kind=.
2. Move a kind whose work a service already owns, end to end, and drop the
   executor and the link it needed from iam. Start with =build_calendars=: the
   work is refdata's own, the step calls a request to refdata today, and no iam
   state is involved, so it proves the dispatch with the least code moved.
3. Then =generate_trades= into ores.synthetic, which drops iam's
   =ores.synthetic.core= link and takes the longest step off iam's workers.
4. Then the marketdata kinds: the curve, forward and surface publishes, the
   surface blueprints and the subscription setup.
5. Then the reporting, dq and inbox kinds: =schedule_reports=,
   =publish_bundle= and the two approval-mode steps.

Step 3 (=generate_trades=) needed a prerequisite the plan did not foresee, and
it is served: iam answers =iam.v1.ops.enter_tenant_as_service=, which gives a
service account a session inside a tenant it serves, scoped to one of that
tenant's parties and carrying the service's own permissions. The story's
Decisions state why that session names no person. Step 2 avoided the need
because the calendar work is refdata's own data and it writes as its own
service account; =generate_trades= writes trades through requests that answer a
session, which is why a request that grants one was necessary.

Step 4 moves one kind at a time, because each brings its own machinery.
=subscribe_market_data= goes first: it reads the tenant's feeds and gives each
party a subscription and a route, all of it marketdata's own data, so it proves
a second service's step dispatch with the least code moved.

When a step moves a kind that runs *beside* another in the same run — the
surfaces beside the schedules, or the curves beside the trades — measure that
the two services work at once, which the =generate_trades= run already shows.

Each stage is its own PR, because each one moves an executor and its link, and
a stage that lands alone is a stage a run can be proved against.

* Notes

- The rest of step 4 is not the same shape as the first three kinds. Two of the
  remaining kinds read the *system* tenant's blueprints: =publish_party_curves=
  copies the system's curve blueprints and =give_party_surface_blueprints= the
  system's surface blueprints, both through an administrator session in the
  system tenant. A service session cannot read the system tenant, and by design
  it is refused there, so those two need the blueprints to reach the tenant by
  another route before they can move. That is a decision, not a port.
- Two more bring machinery rather than only requests: the forwards and surfaces
  kinds retry a request and read back what an earlier attempt did, through
  =request_retry.hpp=, which lived in iam.core. It has moved to ores.service,
  with the refusal error type it shares with iam's internal client, so a service
  that is not iam can retry a step's work; that move changes no behaviour and
  leaves no coupling behind.

* Notes

- The two blueprint-copying kinds were held by how a blueprint reaches a
  tenant, not by the steps. The story decides it: a service reads the
  installation's blueprints in the system tenant as itself, through its own
  database context, so neither step enters an administrator session and

* Result

Stage 1 is done: the dispatch names the service that owns each kind, and
ores.refdata serves the calendar step in its own process.

- =step_subject_for_kind()= states the owner of a kind once, beside the words
  and the budget the definition already keeps there, and =make_step= stores the
  owner on the step the engine persists. A kind no service serves is sent to
  ores.iam, which refuses it, so an unserved kind fails where a person can read
  it instead of waiting for nobody.
- ores.refdata serves =build_calendars= on
  =refdata.v1.ops.provision_tenant_step=, through the same =step_routes= and
  =serve_step_commands= the book-apply steps use, so the step is a durable
  consumer on refdata's own stream. It calls the calendar materialisation
