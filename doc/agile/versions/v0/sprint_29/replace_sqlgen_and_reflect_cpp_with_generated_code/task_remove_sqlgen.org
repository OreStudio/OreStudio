* Plan

Three PRs, each ending in a green build of the whole tree and every suite.

1. *Codegen: drop the sqlgen backend.* Every component is on libpq, so the
   sqlgen repository archetype, the backend switch, the
   =#+repository_backend:= lines and the sqlgen branches of the entity,
   mapper and header templates go. The sqlgen-only helpers of
   =ores.database= that only that archetype used (the sqlgen query
   templates of =bitemporal_operations=, =list_filter=, =stated_order= and
   =valid_at=) go with it.
2. *Database: run the context on libpq.* The context holds the libpq pool,
   its connection options and the session it acts for, and no sqlgen pool.
   A unit of work leases one libpq connection and holds one transaction, and
   a context bound to it runs every call on that transaction, so the bridge
   of #3961 and its overlay patch go. The raw-SQL helpers of
   =ores::database::repository= keep their signatures and run on libpq. The
   Postgres listener holds its own libpq connection. =db_timestamp= is
   reflect-cpp's =rfl::Timestamp=, which sqlgen only re-exported, so no
   entity changes.
3. *Build: drop the dependency.* vcpkg.json, the overlay port and its
   patches, =find_package= and every =sqlgen::sqlgen= link go, with the
   sqlgen text in models, diagrams and docs.
4. *Docs: describe the Postgres architecture as it now is.* Every document
   that describes how the services reach Postgres (the =ores.database=
   overview, the knowledge documents, recipes, component models and
   diagrams) names the libpq layer, the query builder, the unit of work and
   the per-transaction session settings, and nothing describes sqlgen as
   current.

* Notes

** Semantics that differ from sqlgen, signed off

The move keeps sqlgen's semantics unless they did not make sense; each
difference below was put to the user with its reason and signed off.

- *A call on a committed unit of work is refused.* Under sqlgen, the
  context of a unit of work that had committed still held its connection,
  outside any transaction, so a later call ran and committed on its own. A
  context taken from a unit of work promises one unit, and running outside it
  silently hides a caller bug. #3961 already refused it for every repository
  on libpq, with every suite green; =pq::transaction::ended()= now makes the
  refusal hold even for work that runs no statement.
- *A commit after a failed statement throws.* Under sqlgen, COMMIT on an
  aborted transaction was answered by Postgres with a rollback and no error,
  so the caller believed its writes were kept. The transaction now rolls back
  and throws, and the unit of work reports =Cannot commit the transaction=.
  The work is discarded either way; only the failure becomes visible.

run on the libpq layer; the pool retries opening under an open policy; the
codegen has one repository archetype; vcpkg.json names libpq and the sqlgen
overlay port is deleted.

- No source, CMake file, template or vcpkg file names sqlgen
  (=grep -rln sqlgen projects build/cmake CMakeLists.txt vcpkg.json= over
  code, CMake, JSON and mustache files: no match).
- The sqlgen repository facet and its backend switch are deleted.
- Models, diagrams and docs describe the libpq layer and the target state of
  the arc; only the agile history, the plans and one investigation record
  name sqlgen.
- Full build green at -j4; ctest 96/96; database recreated, 24/24 services
  running, Acme provisioning complete, no ERROR or FATAL line in the journal.
  Codegen tests: 1637 pass, and the 5 failures also fail on origin/main.

Two semantics changed, signed off by the user: a call on a committed unit of
work is refused, and a commit after a failed statement rolls back and throws.
