* What

Remove the link from =ores.inbox.core.lib= to =ores.variability.core.lib=. =approval_lifecycle::enforces_approvals= reads the approvals mode through =system_setting_repository=. Read the mode over NATS with =variability.v1.ops.get_setting= through a reader passed to the =approval_lifecycle= constructor, then remove the edge from =core_link_edges_baseline.json=.

* Why

A core may link another component's API and not its core. The =Core link edges= workflow failed on this edge, so the baseline accepts it for now.

The change is larger than a read:

- =approval_lifecycle= takes only a database context. It has about 50 production call sites in inbox, reporting, refdata, marketdata and trading, and 109 test call sites.
- =get_setting= reads in the tenant of the request token. A service token loses the override of a tenant, so the caller's identity must travel with the request.
- =get_setting= needs =variability::system_settings:read=. A caller without it is denied, and the lifecycle then enforces approvals, so an =auto_approved= installation can start to wait for approvers.
- The read happens on each raise, so the result depends on the variability service being up.
- =approval_auto_approval_tests.cpp= writes the setting directly to the database, and no variability service runs in that suite.

Acceptance needs tests for the tenant override, the denied read and an unavailable service.
