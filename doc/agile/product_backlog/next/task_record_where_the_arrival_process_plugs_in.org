* Result

* Result

Delivered in PR 2767, a documentation change to the capture itself.

The capture already named candidate arrival models but not where any of them
plugs in, because the code it was written against had a clock per producer and
so no single place to put one. It now records that the two clocks collapsed
into one =tick_clock= owning the period, the sliced stop-responsive sleep, the
publish counter and the guard, with a producer supplying only what one tick
does.

It records the seam precisely: the clock answers one question, when is the next
tick, and today computes a constant period from =ticks_per_hour=; the change is
to ask an arrival model for that instant instead, which leaves the producer's
process untouched and keeps the arrival process decoupled from the price
process, as the capture's goal requires.

It records what the current code cannot express. Intensity is a property of the
feed and not of the asset class -- a G11 pair ticks far more often than an
emerging-market pair -- so the scalar =ticks_per_hour= is too coarse and the
arrival parameters belong on the generation config beside the process
parameters. Under a regime model the state machine belongs to the arrival model
and the clock stays regime-agnostic, which is what stops that work reopening the
clock.

Two traps for the implementer are recorded: the first tick currently sleeps a
full period, which a draw-based clock must not inherit because under an arrival
model the first tick is not special; and the stop-responsive slicing must
survive, so a sleep cut short by a stop is not confused with a short
inter-arrival draw.

No code changed, so nothing is tested. The claim that the capture's listed
models remain unconfirmed by a literature review is the capture's own open
question and is left standing.
