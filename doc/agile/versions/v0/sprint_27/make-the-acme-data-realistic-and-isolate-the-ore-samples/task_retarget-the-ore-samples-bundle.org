* Acceptance

- The bundle holds only: the sample counterparty aliases, the sample netting
  agreements, sets and CSAs the aliases resolve to, the netting set aliases,
  the sample portfolio names, and the sandbox portfolio.
- Every item has a code and a description that mark it as ORE sample data.
- The sample CSAs keep ORE's terms.
- The bundle installs on every party in =acme_demo=. Agreement numbers carry a
  per-party part, so no two parties collide.
- A sample import creates its portfolio and books inside the sandbox tree.
  The ACME portfolio tree gets nothing.
- After provisioning, each party resolves all 19 ORE netting set ids and the
  portfolio names the samples use.
- The methodology, catalogue and licence describe sample data, not ACME data.

* Plan

1. Take the item list from the current bundle. Remove everything the import
   does not need.
2. Rename the codes and descriptions to mark sample data. Give agreement
   numbers a per-party part.
3. Add the sandbox portfolio. Find where an import puts its books today, and
   point it at the sandbox tree.
4. Move the bundle from one party to every party in =acme_demo=.
5. Update pgTAP. Provision ACME. Import a sample into two parties and check
   that each lands in its own sandbox.

* Notes

*Audit and design, 2026-10-10.*

- *The sandbox already exists.* Sprint 26 added the sandbox entity: an owner, an
  anchor in the official tree, visibility, and its own portfolio tree. The ORE
  import does not use it yet. A sample import still creates portfolios and
  books from the directory tree it reads.
- *Decision (user, 2026-10-10).* This task seeds data only. It opens one shared
  sample sandbox per party, anchored at the party's official top portfolio and
  owned by the publishing actor. A separate task makes the importer place its
  books in that sandbox.
- *Decision: the artefact type.* The =named_portfolios= type published sample
  names as official top-level portfolios. It is replaced by =sandbox_portfolios=,
  which writes the same names as roots of the sandbox. The names PF1 and PF2
  stay, because an import resolves them by name.
- *Decision: codes.* Agreement numbers start =ORE-SAMPLE-=, netting set codes
  start =ORE-SAMPLE-NS-=, and every description starts =ORE sample data:=. The
  per-party part the acceptance asked for is not needed: agreement numbers are
  unique per party since the party-scoping task.
- *Decision: counterparty aliases.* They stay a tenant-level opt-in
  (=ore.counterparty_aliases=). Counterparties are tenant-level, so one publish
  serves every party.
- *CSA terms.* Unchanged. They keep ORE's terms, including EUR-EONIA.

* Result

The ORE samples bundle is labelled, installed on every party, and its
portfolios are published into a sample sandbox.

- Agreement numbers start =ORE-SAMPLE-=, netting set codes start =ORE-SAMPLE-NS-=
  and each sample description starts =ORE sample data:=. The CSA terms are
  ORE's own.
- The bundle goes to Plc, UK, US and HK. Each holds 8 sample agreements, 19
  sets and 19 aliases.
- The new publish =sandbox_portfolios= replaces =named_portfolios=. It opens a
  shared sample sandbox per party and writes PF1 and PF2 as its roots. The
  owner is the publishing actor, else the tenant administrator.

*Acceptance.* Met: labelling; the CSA terms; installation on every party; the
sample portfolios outside the official tree; the methodology and dataset
descriptions say sample data.

*Not met.*

- A sample import does not yet create its portfolios and books in the sandbox.
  The importer still builds them from the directory tree it reads. The task
  "Place the ORE import in the sample sandbox" covers it.
- No import was run, so it is not shown that each party resolves the portfolio
  names inside the sandbox. The 19 netting set ids and their aliases do exist
  on every party.
- The bundle does not hold the counterparty aliases. They stay a tenant-level
  opt-in, because counterparties are tenant-level.

*Proof limits.* The sandboxes were created by a direct call of the publish
after a first provision. A clean provision through the bundle path was not
completed: the database rebuild hung on a Postgres cluster shared with other
worktrees. The first provision showed the publish ran with no actor and wrote
nothing, which led to the tenant administrator fallback. The fallback was run
by hand, not through the provisioning path.

*Known gap.* The publish handler logs only inserted, updated and skipped
counts. A =skipped_no_owner= or =skipped_no_anchor= result is silent.
