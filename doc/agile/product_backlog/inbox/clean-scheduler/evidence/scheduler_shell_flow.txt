The scheduling flow, driven from the shell
==========================================

Run at the head that adds the scheduler submenu, against the live fleet: NATS on
21205, the recreatable database, ores.iam.service for the session and
ores.scheduler.service for the loop. The service and the shell were started by
hand, with the same arguments their systemd units pass, because this session's
sandbox cannot drive the user manager.

The script, run with ores.shell --load:

    # Exercises the whole scheduling flow from the shell: create a job, watch it
    # fire, read the executions it recorded, and remove it again.
    scheduler jobs
    scheduler schedule e2e-ok "* * * * *" --action execute_sql --command "select 1" --description "shell end-to-end probe"
    scheduler jobs
    scheduler status
    scheduler watch --seconds 100
    scheduler instances --job e2e-ok --limit 5
    scheduler remove e2e-ok
    scheduler jobs

What it proves:

- scheduler schedule arms a job and the shell lists it back with its cron,
  action and command.
- The running service picks the new definition up without a restart: the loop
  reads the table again on the change event its pipeline already receives.
  Before this unit reload() had no caller, and a job scheduled while the
  service ran never fired -- the first run of this script showed exactly that,
  with the execution events arriving only for the two seeded jobs.
- scheduler watch receives the scheduler's own publication on
  scheduler.v1.job-instance-events and prints it: each event names the
  definition and the execution, and the tenant when the row has one.
- scheduler instances reads the execution back as succeeded in 0 ms.
- scheduler remove deletes by name, resolving it to the key the protocol
  addresses, and the definition is gone from the next listing.

One observation for the operations read, not fixed here: when the definition
row is gone, the execution summary's job_name carries the definition
identifier instead of a name, because the join finds nothing. The page is also
ordered by time, so a client-side --job filter sees one page; the command
says so.
