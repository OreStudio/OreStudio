#+title: ores.trading.product_schema_operations
#+description: Codegen operation model for a product's schema: the fields a screen draws to book a product, and the forms it may be booked in.
#+type: ores.codegen.operation
#+component: trading
#+subcomponent: api
#+entity_singular: product_schema_operation
#+namespace: ores::trading::messaging
#+brief: Describes a product's fields and forms, and lists the products that can be described.
#+filetags: :model:operation:trading:
#+created: 2026-11-23
#+updated: 2026-11-23

A screen that books a product, the shell that prints one and the synthetic
generator that draws one all need the same description of it: its fields, with
their kinds, whether each is required and repeats, and their words, and the
forms the product may be booked in. Trading serves it, because trading owns the
products, the scripts and their inputs.

A native product's fields are those of its trade type's element, which
=ores.ore= describes as ore parameters of the scope instrument; trading reads
them from its cache of =ores.ore='s parameters, not from =ores.ore='s tables. A
field whose value is another schema type names it through its value domain,
=record:legData= or =list:legData=, and the description carries the fields of
every type the product reaches. A script-only product, a library script no
product type twins, has its script's inputs and their codes as its fields.

Each form names the script it runs, if any, and that script's product tag, the
tag a pricing configuration assigns an engine to.

The handler stays hand-written beside this model, because an operation model
generates no service handler.
