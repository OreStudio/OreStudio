* Acceptance

* Plan

The design leaves two answers open for these twelve: move them behind a service, or
keep them as an explicit filesystem adapter with its own directory and its own risk
note. It forbids one thing either way: they must not be smuggled into the HTTP core
or dressed up as resources they are not.

The decision is to **delete them from the port's scope**, for a reason that is a
fact about the routes and not a preference. Each of the twelve reads, or writes, the
checkout the BFF itself runs in: the agile store walks =doc/agile=, the QA store
reads and writes =doc/qa=, and the work trees shell out to =git=. A deployed gateway
holds no checkout, so no service could answer them there, and a gateway that wrote a
deployment's own repository would be a risk with no product value.

The BFF already says the same thing in its own configuration, which is the strongest
evidence available: =ORES_WEB_DOC_ROOT= is optional, and unset "means the runner is
off"; the agile store is passed as =undefined= when there is no doc root and its
routes answer not-found; and the screens that call them hang off the site's existing
=developerTools= flag.

So the owner is the tooling that already reads and writes those documents: the
developer surface, not the product's API.

What this task does not do, and why. The inventory's pairing data lives in
=build/scripts/route_pairing.py=, and the compass-ng codec is what now renders the
inventory from it. That gate is being ported by another story, and a change to its
data model while it is in flight would collide with the port. Recording a deletion
there is the follow-up this task names rather than performs; until it lands, the
inventory still prints "none" against the twelve, which overstates what the port owes
by twelve routes.

* Result

The twelve file-backed routes have a decision: they are deleted from the port's
scope, and their owner is the developer tooling that already reads and writes those
documents. The reason is recorded per route, and the two facts that settle it are
that the BFF itself makes them optional, since =ORES_WEB_DOC_ROOT= unset turns the QA
runner off, and that four of them write into the checkout rather than read a tenant's
data.

The mechanical change to the pairing data is the one part left, and it is named
above with the reason it waits.
