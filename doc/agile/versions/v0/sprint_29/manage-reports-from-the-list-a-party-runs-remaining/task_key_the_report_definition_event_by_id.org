* Goal

Make one definition answerable by a key that names one row. The model declares
the definition's name as its key (=(:key_field: name)= in
=projects/ores.reporting/modeling/ores.reporting.report_definition.org=), and the
table is unique on the name within a party
(==report_definitions_name_party_id_uniq_idx== in
=projects/ores.sql/create/reporting/reporting_report_definitions_create.sql=).
The two disagree as soon as one person sees more than one party, which a tenant
administrator always does: ACME holds four definitions called =Audit Trail
Summary=, one per party.

Everything generated from the key inherits the disagreement:

- =report_definition_event.key= carries a name, so a change notification names a
  definition that four rows share, and a list can only mark all four.
- =get_report_definition_request.key= reads a name, so the generated read cannot
  name one row.
- The history read inherits the same ambiguity, and it is the worst case of the
  three: =report_definition_service::get_definition_history= takes the declared
  key, which is a name, resolves it with =read_any_by_name= and takes the newest
  row carrying it. Asked for one party's definition it can therefore answer with
  another party's versions. The history service also subscribes to no
  =reporting.v1.history.get= subject at all: the reporting registrar registers no
  history handlers, so the generic history read has no responder for this
  component.

The screens are already right: a definition is opened by its id, which is the
primary key, and the list returns it. This task is what remains for the model.

* Acceptance

- One definition is named by a key that identifies one row: either its id, or
  its name and its party together.
- The change event carries that key, so a screen that hears a change can mark the
  one row that changed.
- The generated read by key takes that key, and a name shared by two parties is
  either refused or answered per party. The history read resolves the same key,
  so a definition's versions are the versions of the row the screen opened.
- The reporting service subscribes to =reporting.v1.history.get= and registers the
  definition's history provider, as the other components' registrars do, and the
  record page's History tab is drawn again.
- The screens keep working unchanged: the reporting list and page already open a
  definition by its id (`GET /api/reporting/reports/:id`), which this task neither
  needs nor may break.
- The modelling file, the generated C++ and TypeScript, and the populate script
  agree on the key, with the codegen gate green.
