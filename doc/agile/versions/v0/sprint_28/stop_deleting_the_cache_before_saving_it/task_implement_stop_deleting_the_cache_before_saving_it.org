* Notes

** Why the delete was there

=actions/cache/save= refuses to overwrite an existing key, so the entry was
deleted immediately before the save.

** Why that is destructive

The window between the delete and a successful save has nothing in it. The
cache service fails: these very run logs carry =Failed to restore: Cache
service responded with 400= and =Failed to save: Our services aren't
available right now=. A failed save after a successful delete removes the
entry for good, and both Linux clang entries are now gone. The repository
total fell, so this was not eviction under the 10 GB cap.

** The replacement

Saves go to =sccache-<variant>-${{ github.run_id }}=, unique per run, so they
never collide and nothing has to be deleted. Restores use
=restore-keys= prefix matching and take the newest entry. Old entries age
out through the seven-day rule and LRU, which never destroys the newest.

** The floor still matters

With prefix matching the newest entry wins, so a run that failed early must
not save. The 1000 MB floor is kept, and nightly-linux.yml now has it too.
