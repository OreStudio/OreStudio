This page defines the [[id:902A5312-B3A2-4C66-8017-34F0F26658C6][workflow]]
Report execution. It runs one report definition to completion: it prepares the
engine's input, submits it to the compute grid, records what came back, and
settles the report instance. A person starts it from the shell, or the scheduler
starts it from a job, and either way it leaves a completed or failed report
instance and the engine's output archive in storage. The chain is a function of
the definition's run configuration, so a run either executes every phase or
replaces pre-processing and post-processing with prepared substitutes. A failed
step marks the instance failed; a person then reads the failure on the instance
and decides whether to trigger another run.

* Purpose

Turns a report definition into a completed report instance. When it finishes, the
instance has walked pending, running and completed, the engine's output archive
is in storage, and the run's record says where it landed. The workflow is also
what keeps reporting free of the grid's timing: submission is asynchronous, and
the engine holds the run open until the compute batch closes.

* Steps

The chain is a function of the run configuration the definition carries, so
there are two shapes. A run that executes pre-processing runs seven steps; a run
that substitutes it runs four. Steps 1 to 4 below appear only in the executing
shape, and step 6 appears in both shapes with two possible operations.

#+ATTR_HTML: :class hug-leading
| # | Operation | Produces | On failure |
|---+-----------+----------+------------|
| 1 | =gather_trades= | A stored trades object and its key. | Compensation: the instance is marked failed. |
| 2 | =gather_market_data= | A stored market data object and its key. | Compensation: the instance is marked failed. |
| 3 | =assemble_bundle= | A persisted input bundle row naming both objects. | Compensation: the instance is marked failed. |
| 4 | =prepare_ore_package= | The tarball URI the engine consumes. | Compensation: the instance is marked failed. |
| 4' | =resolve_prepared_input= | The archive the definition named, answered in the packaging phase's own result type. | Compensation: the instance is marked failed. |
| 5 | =submit_compute= | A compute batch, its workunits, and a link row the bridge watches. | Compensation: the instance is marked failed. |
| 6 | =collect_compute_results= | The engine's output, ingested. | Compensation: the instance is marked failed. |
| 6' | =ignore_compute_results= | The batch named, and its output left unread. | Compensation: the instance is marked failed. |
| 7 | =finalise= | The instance at completed, with its completion time. | Compensation: the instance is marked failed. |

Each step's command is built from the run's request and from the earlier steps'
results, which are addressed by the *name* of the step that produced them. A
builder that cannot find or read what it consumes stops the run rather than
handing the next phase an empty field.

* Failure and recovery

This workflow declares no failure policy of its own: the engine compensates the
steps that completed, in reverse. Every step compensates through
=reporting.v1.ops.fail_report=, so a compensation is not an undo. It marks the report
instance failed with the failing step's message, and each further compensation
leaves the first message in place. What a completed step produced, a stored
object or a compute batch, stays where it is; nothing deletes it.

A retry resumes from the run's persisted record of completed steps: a restart
re-dispatches every step left in progress, under its original step id. The
handlers do not yet check whether they have already run, so a re-dispatched
phase does work twice. Until they do, two facts follow. Treat a run that was
recovered as having acted more than once, and prefer triggering a fresh run over
retrying a failed one.

Two failure modes have no automatic recovery. A phase that never answers leaves
the run in progress, because there is no acknowledgement and no deadline; the run
then re-dispatches on every restart. And an unknown workflow type is logged and
dropped while the trigger has already answered =triggered=, so a mistyped type
looks like a successful trigger that produced nothing. Both are recorded on the
story below.

The engine's own failure rules are on
[[id:4F95A407-AD43-4CBD-952E-1CCACAA90080][Workflows]].

* Progress

Two reads render progress, and they answer different questions.

- The run: =workflow.v1.instances.list= and =workflow.v1.ops.get_workflow_steps=, over
  the workflow instance and its steps. The workflow instance id is created by the
  trigger and carried in the start message, so a client can follow the engine's
  view before the first step answers.
- The report: =reporting.v1.report_instances.list= and
  =reporting.v1.report_instances.get=, over the report instance. One line shows
  the definition, the instance's state, when it started, when it completed, and
  the output message.

The report instance is the read a business user follows, and it is the one that
carries the failure text. Its states are pending, queued, running, completed,
failed, skipped and cancelled, defined on
[[file:../architecture/report_definition_and_schedule.org][Report definition and schedule]].
The engine's instance states are a separate vocabulary, and the two are not the
same table.
