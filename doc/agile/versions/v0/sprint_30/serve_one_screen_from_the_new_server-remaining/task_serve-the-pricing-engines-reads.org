* Goal

Serve the pricing engines' five reads. A pricing engine configuration is three
tables in the analytics service: a header, one row for each product and one row
for each parameter. The screens never see the split, so a read answers the whole
document.

The ORE document of a configuration is one more read: the ORE service writes it
and names it, and the route hands it to the browser as a file. The vocabulary is
the last: the lookups the editor draws its controls from.

* Acceptance

- The C++ server answers =GET /api/reporting/pricing-engines=,
  =GET /api/reporting/pricing-engines/:id=,
  =GET /api/reporting/pricing-engines/:id/history=,
  =GET /api/reporting/pricing-engines/:id/ore-document= and
  =GET /api/reporting/pricing-engines/vocabulary= at the BFF's paths, with the
  BFF's member names and status codes.
- The page states each configuration's parties, its count of products and its
  count of parameters.
- One configuration states the document and the reports that bind it.
- The ORE document is answered as a file, under the name the service states, as
  =application/xml=, and an export that says it could not write one is a refusal
  that carries the service's sentence.
- The vocabulary is paired in the inventory as a route that is not an API, as
  =choices= was, because the editor calls it and the screen breaks without it.
- A test proves each route against the answer the BFF gives.
- Each route in scope names its C++ equivalent in the inventory.
- The local gate is green.

* Plan

Branch =feature/serve-the-pricing-engines-reads=.

The document read is the unit the writes task extends: the header, its products,
its parameters, its bound reports and the party names, stated as one document.
The history reads the versions of all three tables.

The ORE document joins two ids. The screen names the configuration by the id it
shows; the ORE service reads a document by the reporting configuration that the
record fills. The gateway makes that join and the screen never learns the second
id.

The vocabulary is one read of fifteen lookup collections, keyed by the names the
editor's controls use. The inventory states it as not an API and in no area, so
serving it changes no area's count. It is served because the editor calls it.
