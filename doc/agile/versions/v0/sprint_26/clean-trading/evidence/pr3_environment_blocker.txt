PR 3: the environment cannot be rebuilt from main's tree

Measured 2026-09-27 on feature/model-missing-trading-families, while
verifying the commodity family port.

Why the database was rebuilt
----------------------------
The port renames the commodity table's surrogate key from id to
instrument_id, so the live schema had to follow before the suites could
run. The sanctioned way is =./compass.sh db recreate -y -k=.

Three defects on main stop it
-----------------------------
1. Five dq population-function scripts open a leading block comment and
   never close it. psql aborts with "unterminated /* comment" at the
   first of them, part way through =setup_schema.sql=:

     projects/ores.sql/create/dq/dq_coding_schemes_population_functions_create.sql
     projects/ores.sql/create/dq/dq_badge_definitions_population_functions_create.sql
     projects/ores.sql/create/dq/dq_badge_mappings_population_functions_create.sql
     projects/ores.sql/create/dq/dq_badge_severities_population_functions_create.sql
     projects/ores.sql/create/dq/dq_code_domains_population_functions_create.sql

   Each begins with =/* -*- sql-product: postgres; ... -*-=, then a blank
   line and =-- ==== =, and the copyright block and its closing =*/= are
   missing, so the whole file is one comment. The fix is to restore the
   header the generator dropped.

2. The populate scripts use =:'storage_service_user'= and
   =:'storage_service_password'=, but compass passes only the services
   named in =projects/ores.sql/service_vars.sh=, whose =SERVICE_NAMES=
   list has no =storage=. compass fails with:

     psql:populate/iam/iam_service_account_roles_populate.sql:63:
     ERROR: syntax error at or near ":"

3. With the variable passed, the same script fails again because the
   storage service account row is never seeded:

     ERROR: Account not found: ores_merry_newton_storage_service

   So the storage service is in the environment (.env format 25) and in
   the populate scripts, and is missing from the role and account
   seeding.

Consequence
-----------
No worktree can rebuild its database from main's tree. Against the half
seeded database left by attempt three, =ores.trading.core.tests= reports
103 cases, 99 failed, across the whole suite rather than in the commodity
family: the failures are the missing seed data, not the port.

What was done about it
----------------------
The three defects were worked around locally, one at a time, to get far
enough to see the next: the five SQL headers were closed, =storage= was
added to =SERVICE_NAMES=, and the database was recreated. Attempt three
stopped at defect 3. All the workarounds were then reverted, so this
branch carries only trading work; the database is left half seeded and
needs the storage owner's fix before any DB-backed suite can pass.

What this means for the port
----------------------------
=ores.trading.api.lib=, =ores.trading.core.lib=,
=ores.trading.service.lib=, the ORE core and service libraries, the shell
application library and their test binaries all compile, and the drift
dry run reports no drift. The suites are the missing evidence, and they
are missing for an environment reason, not a code one.

Defect 4, found after the first three were worked around
--------------------------------------------------------
The populate then fails in the flags step:

    psql:populate/flags/flags_dataset_tag_populate.sql:44:
    ERROR: there is no unique or exclusion constraint matching the
    ON CONFLICT specification

    on conflict (tenant_id, dataset_id, name) do nothing
    ... in ores_dq_tags_artefact_tbl

The dq artefact table does not carry the unique constraint that clause
names. The same artefact family looks malformed elsewhere: the create
scripts emit the same index name a dozen times, each reported as
"already exists, skipping", which is why the constraint is not there to
match. This is generated SQL, and dq is not in the drift registry, so
nothing catches it.

State after four defects
------------------------
The database now reaches the schema-complete state and aborts in the
flags populate. Against it, =ores.trading.core.tests= still reports 103
cases with 99 failed, across the whole suite: the seeds the suites need
are not there. The four repairs were reverted, so this branch carries
only trading work.

The premise is what is wrong
----------------------------
Each repair revealed the next defect, and all four are in the same
component's generated SQL and its service plumbing. Rebuilding the
environment from main's tree is not a thing that works today, and
patching it defect by defect from a trading branch is not the fix. The
owners of dq and of the storage service should regenerate their SQL, and
the environment should be restorable from a snapshot so that one broken
component cannot stop every worktree's verification.

Defect 5, found after the first four were worked around
-------------------------------------------------------
The populate then advances past the flags step and fails in the
synthetic seed:

    psql:populate/synthetic/synthetic_fx_spot_configs_uniform_demo_populate.sql:55:
    ERROR: Row already exists: a create cannot replace it. State the
    version you read to replace the row, or ask for a version replace.
    CONTEXT: PL/pgSQL function ores_dq_catalogs_insert_fn()

Two seed scripts insert the same =Synthetic Market Data= catalogue row,
and the insert function refuses the second rather than skipping it, so
the seed is not re-runnable and the recreate cannot finish. This is the
fifth independent defect, and the fifth time a repair revealed the next.

The suite failures are downstream of this
-----------------------------------------
The grant step runs after the populate, so the half-seeded database also
leaves the test role without the grants the suites need. The failure that
was visible on the last attempt is exact:

    permission denied for table ores_refdata_parties_tbl

That is why the trading core suite reports 103 cases with 99 failed: not
the commodity port, and not only missing rows.

Defect 5 is fixed, and defect 6 stands behind it
------------------------------------------------
Defect 5 is fixed on its own branch and raised as PR #2232,
[fix/seed-catalog-upsert-idempotence]. The root cause was not the seeds:
=ores_dq_catalogs_upsert_fn= relied on an ON CONFLICT clause, but the
catalogs insert trigger owns the version column and refuses a version-0
create when a live row exists, and a BEFORE INSERT trigger runs before
the conflict arbiter, so the clause never fired. The helper now makes the
existence check its file's header documents, and the dead clause is gone.

Verified: the helper called twice in a row against the rebuilt database
returns quietly both times with exactly one live row, where the populate
log shows the old code raising on the second call.
=evidence/pr3_environment_blocker.txt= records the reproduction; PR #2232
carries it with the newly found defect below.

The populate then advances past the synthetic step and stops in the fpml
step, on a sixth defect of the same class but a different mechanism:

    psql:populate/fpml/fpml_populate.sql:43:
    ERROR: Row already exists: a create cannot replace it.
    CONTEXT: PL/pgSQL function ores_dq_coding_schemes_insert_fn()
    ... ores_dq_coding_schemes_publish_fn(...) line 66

=ores_dq_coding_schemes_publish_fn= publishes a dataset's rows with
version 0, and the insert trigger refuses when the natural key exists, so
a dataset whose key is already published aborts the populate. It is
generated SQL, so the fix belongs in the dq model or the publish
template. It is recorded in PR #2232 for that owner, and the environment
still cannot be rebuilt end to end until it lands with the other four.

The rebuild after the rebase, and defect 7
------------------------------------------
Measured 2026-09-27 after the rebase onto main, on
feature/model-missing-trading-families.

The database rebuild now succeeds. Defects 1 to 5 are fixed on main, and
three local workarounds carried the last three steps: =storage= was added
to =SERVICE_NAMES=, the storage service account was seeded, and the
coding-schemes publish skipped an existing live row. The populate ran to
the end and the grants were applied. The workarounds are uncommitted, so
this branch carries only trading work.

The build then failed, and not in trading:

    projects/ores.workflow/core/src/service/fsm_state_map.cpp:21:10:
    fatal error: 'ores.dq.api/messaging/fsm_protocol.hpp' file not found

dq modelled the FSM pair in =dd131c388b=, merged as PR #2216 before the
PR 2 merge. That commit deleted =fsm_protocol.hpp=, =fsm_handler.hpp= and
=fsm_service.{hpp,cpp}=, and the generated pair replaced them. The
replacement has no machine filter: the old =get_fsm_states_request=
carried a =machine_name=, the new =list_fsm_states_request= carries none,
and the new =fsm_state= carries a =machine_id= uuid instead of a name.
Two consumers still call the deleted shape:

    projects/ores.workflow/core/src/service/fsm_state_map.cpp
    projects/ores.reporting/core/src/messaging/registrar.cpp:62

The second passes the machine name =report_instance_lifecycle=. Nothing
in dq maps that name to a machine id, so the migration needs a decision
from the dq, workflow and reporting owners. No local workaround was
attempted: any replacement would invent a machine identity that the model
does not state.

Consequence: =cmake --build --preset linux-clang-debug-make= fails at the
default =all= target, so no worktree can run the full =ctest= suite from
main's tree. The build has been in this state since PR #2216, before the
PR 2 merge; only targeted builds have been green since.

The same defect stops the service start. After =compass services start=,
21 of 24 units are ready and three are not. Two of the three fail on the
deleted subject, from the binary the previous build left behind:

    ores.workflow.service: NATS request failed: no service is handling
    subject 'ores.dev.merry_newton.dq.v1.fsm-states.list'
    ores.reporting.service: the same subject and the same error

The third, =ores.storage.service=, fails before that, on its database
role:

    Failed to create connection pool: Connection to postgres failed:
    FATAL: password authentication failed for user
    "ores_merry_newton_storage_service"

The storage role is minted from the service registry, and the registry
has no storage entry, so the two local workarounds above cover the
populate and the account row but not the role. A storage service unit
exists and starts; the environment behind it does not.

What the FSM fix needs
----------------------
The machine table survives the remodelling as hand-written SQL:

    projects/ores.sql/create/dq/dq_fsm_machines_create.sql

It carries =id= and =name=, and the seed reads the id by name
(=populate/dq/dq_fsm_trade_status_populate.sql=). dq modelled only
=fsm_state= and =fsm_transition=, so the machine has no model, no
protocol and no domain type, and =list_fsm_states_request= has no
machine filter. A caller therefore cannot reach the mapping the table
still holds. The owner's choice is to model the machine, or to state a
machine filter on the state list request that joins the table.
