Four of them carry a `double` in the domain over a `numeric` column, which is
the worse of the two shapes: exact at rest and lossy in the domain. All ten
become `double precision`, and the reason is not only the rule — ORE's schema
reads each of these leaves as `xs:float`, so the binary float is the more
faithful type as well.

They convert with the same batch, so the count of columns to move is 35, not
25: 25 money to decimal, 10 continuous to float.

*The 10 need almost no mapper seam — two exceptions, and one of them is a trap.*
Every continuous column's ORE seam already assigns a `double` — `result.quantity
= static_cast<double>(d.Quantity)` at `commodity_instrument_mapper.cpp:248`,
`result.recovery_rate = static_cast<double>(*d.FixedRecoveryRate)` at
`credit_instrument_mapper.cpp:161`, and the same shape for `variance_strike`
and `conversion_ratio` in the bond, commodity, equity and curve mappers. For
those, changing the column to `double precision` makes the two agree and needs
no C++ change.

Two do not follow that pattern, because their model says `numeric` *and* their
C++ says `optional<decimal>`: `commodity_instrument_mapper.cpp:434`
(`constituent.weight`) and `equity_instrument_mapper.cpp:1354` (`row.weight`),
both `from_double(static_cast<double>(*...Weight)).value()`. When the batch
flips those columns to `double precision` **these two seams must be reverted to
a plain `static_cast<double>`**, or the build fails on a decimal assigned to a
double. They are the only two in the 10, and they are the trap: a batch that
changes the models and regenerates will build cleanly for the other eight and
break here.

*A money target with a continuous-looking source.* Separately,
`equity_instrument_mapper.cpp` fills `inst.notional` — a money column,
`numeric(38, 12)` and decimal — from ORE's `Quantity` leaf at lines 316, 383,
452, 489, 729, 1150 and 1186. ORE's `Quantity` is an `xsd::base<float>`
binding, so the lexical patch gives it the document's digits, and these seven
sites were still converting through `from_double` and throwing them away. The
lesson worth keeping: classify a seam by the **target column's role**, not by
the source leaf's name. "Quantity" sounds continuous and feeds a notional.

Note also that nothing in `ores.trading`'s models names `positiveDecimal`,
`correlationValue`, `recoveryRate`, `non_negative_decimal` or
`offPeakPowerIndexDataType_OffPeakHours_t` — the five ORE leaves that are a
plain `typedef double` rather than a binding, and so are the only floating
leaves the lexical patch does not touch. No money value travels through them,
so the patch's coverage is complete for the persisted domain even though 5 of
the 42 floating setters keep the old shape (35 `set_float` sites plus 7
`set_double`, of which 2 are bindings and these 5 are bare typedefs). Measured
by matching every `_set_` function body against the setter calls: 42 setters in
the code, 37 in `ore_numeric_leaf_setters.txt`, and the five in the difference
are exactly the typedefs.

* Plan

Convert in one batch and verify with one environment cycle. The model change
is mechanical; three things about it are not obvious and cost a build
iteration each if missed. All three were learned from the
=swap_leg_rate.value= slice.

1. The column's own generator block must change too. Every column carries a
   =#+begin_src cpp :name generator= block, and a money column's emits a bare
   literal such as =0.05=. That generates a =*_generator.cpp= assigning a
   =double= to a =decimal=, which does not compile. The spelling that works is
   =ores::utility::decimal::decimal::from_string("0.05").value()=. A scripted
   edit that changes only =:type:= and =:cpp_type:= will fail the build.
2. The ORE mappers convert across the boundary, in both directions. Taking a
   value from ORE is =from_double(v).value()=; handing one back is
   =X.to_double()=, and the ORE leaf is a =float= so it takes a further cast.
   The =ore= component's mappers are where the compile errors land, not the
   trading repositories, which the generator handles.
3. Test helpers that read a rate as a =double= need =.to_double()= as well.
   The sibling helper on the line above already does this; copy it.

Cost, measured: the slice needed three builds. Most of that is items 1 and 3,
which a script can handle; item 2 is per-family.

The inventory is not written here, on purpose.
=build/scripts/money_decimal_columns.baseline= is the authoritative list,
produced by the check from the models themselves, so it cannot drift from
them. It holds 37 money columns that are binary float: 11 in =ores.trading=,
the rest in =ores.dq=, =ores.refdata= and =ores.synthetic=, mostly CSA terms
and curve spreads. A converted column shows up in the check's output as
"fixed since the baseline was written", which is the signal to delete its
line — so the baseline shrinks as the work lands and never needs a second

* Seam shapes, learned by building

Three attempts, three different shapes. None was predicted correctly; each was
found by converting, regenerating, building, and reading the errors.

| Slice | Shape | Fix |
|-------+-------+-----|
| Bond (`bond_instrument_mapper.cpp`) | direct assignment | `from_double(...).value()` and `.to_double()` at 4 lines |
| CSA (`netting_set_mapper.cpp`) | helper pair | `number_decimal` beside `number`, `put_decimal` beside `put`, 10 call sites |
| Curve (`curve_configuration_mapper.cpp`) | helper pair | `optional_decimal` / `assign_optional_decimal`, 4 call sites |
| **FX (`fx_instrument_mapper.cpp`)** | **helper signatures** | not done: `fill_barrier` and `make_barrier` take `double`, and the call sites pass decimals, so the helpers' parameters change rather than the call sites converting |
| **Equity (`equity_instrument_mapper.cpp`)** | **helper return type** | `extract_strike`, `first_barrier_level` and `second_barrier_level` return `double`, so they lose the digits before the seam sees them. Turning the call sites into `exact_decimal(<double>)` looks correct and is not: the value is already a float by then. The three helpers must return `decimal`. |

The equity row is the one that hides best. `exact_decimal(extract_strike(...))`
reads as exact and is not, because `extract_strike` returns a `double` computed
from the binding. A conversion is only as exact as its input, and a
`double`-returning helper is a float boundary in the middle of the mapper. The
rule that catches it: when converting a seam, check where the *value* was last
text, not what the call looks like. `_Strike_t` is literally `xsd::string`
(`domain.hpp:9666`), so the text was still there and `std::stod` threw it away.

Read closely, the FX fix is narrower than "templatise everything".
`fill_barrier` already takes its lower level as a template parameter
(`template <typename Lower> ... Lower& lower`), so a decimal lower works; it
is the upper that is hard-coded to `std::optional<double>&`, and the two
assignments inside do `lower = static_cast<double>(levels.front())`. So the
change is: templatise the upper as well, convert those two assignments with
`from_double`, and change `make_barrier`'s `double level` parameter. The call
sites then need nothing.

The FX case is the one that is not a conversion. `make_barrier(const std::string&, double level)` and `fill_barrier(barrierData&, type, lower, upper)` must take the decimal types, and 19 compile errors follow from it. Expect the same shape in any family whose mapper has a helper that carries a money value across its interface.

* The lever has known gaps

`scripts/convert_money_column_to_decimal.py` now makes four edits, not three:
`:type:`, `:cpp_type:`, the generator block, and `:default_value:`. It learned
the fourth from a build, not from reading — a default of `0.0` renders as
`= 0.0` in the generated header, which a decimal cannot take.

It has also carried the same bug twice: a rewrite ending in `\s*$` consumes the
newline before `:END:` and welds the drawer closed. Fixed once in the generator
path and reintroduced in the default-value path. **Both were caught by grep,
not by any test.** Treat the lever as unverified for any edit path that has not
been exercised on a real column, and grep the model afterwards for a `:END:`
that has moved onto the previous line. The lever now checks its own output for
that shape and refuses to write.

A third bug, and the worst of the three: the generator-block search ran from
the column's heading to the next `#+begin_src cpp :name generator` **in the
whole file**, with `.` matching newlines. A column that has no generator block
therefore matched its *neighbour's*, and the lever rewrote a column nobody
named. It was caught by the mirror direction, where `commodity_instrument`'s
`variance_strike` reported a generator body of
`std::chrono::year_month_day{...}` — a date. The search now stops at the next
`** ` heading. The money direction's output is byte-identical before and after
the fix, so no already-converted column was harmed, but it was luck: the
continuous columns happened to be adjacent to a date leaf.

* The scale, scoped from the live schema

`numeric(28, 10)` rounds a document's eleventh and twelfth decimal places
away, and the corpus states them. Measured against the recreated database
rather than the models:

    select count(*) from information_schema.columns
     where table_schema='public' and data_type='numeric' and numeric_scale=10;
    --> 90 in ores_trading_*, and the rest elsewhere

That is many more than the 63 the model audit reported, because the audit read
declarations and this reads the schema the server actually carries.

The fix is a lever, not ninety edits: models declare the scale literally as
`:type: numeric(28, 10)`, so replacing that string with `numeric(28, 12)`
across `projects/**/modeling/*.org` widens every column at once, and one
regenerate plus one build and recreate proves it. The final scale is numeric(38, 12), and the route there is worth recording
because the first attempt was wrong. "Wider is free and cannot lose digits"
is false: numeric(28, 10) allows eighteen integer digits and numeric(28, 12)
allows sixteen, so widening the scale without widening the precision **narrows
the integer part**. The suite caught it — three assertions failed with
"numeric field overflow: a field with precision 28, scale 12 must round to an
absolute value less than 10^16" in repository_bond_leg_amount_repository_tests.
numeric(38, 12) gives twenty-six integer digits and twelve places, more room
than the original in both dimensions.

**Verify it against the columns.** The round trip cannot see this: the
exporter re-renders a stored decimal through ORE's `float`, whose shortest
spelling restores the document's digits, so a truncated column still exports
byte-identical text. `select value from ores_trading_bond_issue_leg_amounts_tbl
where amount_role='spread'` said `0.0099999998` while the document said
`0.00999999978` and the classifier said numeric 0.

* How the batch runs

*Dry-run first.* The two lever runs were executed against a staged copy of the
35 target models under `build/output/scratch/batch/`, with the baselines
rewritten to point into the copy, and the result checked before anything was
written to the tree. Measured on the copy: **0 money offenders, 0 continuous

says — money columns take `numeric(38, 12)`, `ores::utility::decimal::decimal`

is that the lever re-aligns the whitespace of every `:type:` and `:cpp_type:`

little larger than the semantic change and the reported change list counts

* The batch is two units, and the first one needs no recreate

The 35 columns do not split the way the rules do. Measured on the staged tree by
comparing each column's declared type before and after: **24 of the 25 money
columns already declare `numeric(38, 12)`**, so converting them changes only
`:cpp_type:` — and `cpp_type` appears in sixteen codegen templates, none of them
an SQL one. So that unit produces no SQL change, no schema-fingerprint change,
and **no recreate and no tenant rebuild**. The other 11 columns — the ten
continuous plus `rpa_instrument.protection_fee`, whose type moves the other way,
from `double precision` to `numeric(38, 12)` — do change SQL and do need the
recreate.

| Unit | Columns | Changes | Needs |
|------+---------+---------+-------|
| A | 24 money | `:cpp_type:` and json/nats C++ only | regenerate, seam fixes, build, tests |
| B | 10 continuous + `rpa_instrument.protection_fee` | SQL type | regenerate, 2 seam reverts, build, recreate, provision |

Ship A first. It carries almost all of the correctness value — every remaining
money quantity becomes exact in the domain — and it does not need the database
recreate that B does.

**But weigh the build before splitting, because the build dominates.** The
split was recommended on the recreate, and that is the smaller cost. Measured
since: `compass codegen regenerate` rewrites every file a component owns
whether or not the content changes, so it moves mtimes for all of them and
invalidates that component's whole build cache. A second unit therefore costs a
second full `trading-cpp` build — an hour or more here, against roughly half an
hour for the recreate and re-provision. So:

| Route | Builds | Recreates | Roughly |
|-------+--------+-----------+---------|
| A then B | 2 full trading builds | 1 | 2h30 |
| A and B together | 1 full trading build | 1 | 1h30 |

Unless the recreate itself is the risk being managed — it takes the services
down and rebuilds the tenant, and it cannot be rehearsed — the combined unit is
the cheaper one, and the two-unit split is worth it only when something needs
the money half on the environment before the continuous half is ready.

The reason to state this at all is that the two were planned as one unit
because the *rules* are two halves of one rule, then split because the *schema*
cares only about which columns change type, and now the *build* pulls them back
together. Each split was reasoned from a different cost, and the build is the
one that actually dominates.

* What "consistent by role" means, measured

The goal is that the same economic quantity is typed the same way in every
family. It is not, and the counterexample is `strike`, which appears across
eleven families in **three** different shapes:

| Column | Distinct (SQL, cpp) shapes | Where |
|--------+---------------------------+-------|
| `strike` | 3 | `numeric`+decimal in 6 equity families; `numeric`+`double` in `fra_instrument`, `fx_accumulator_instrument`, `fx_variance_swap_instrument`; `numeric`+`std::optional<double>` in `fx_asian_forward_instrument`, `fx_digital_option_instrument` |

So the acceptance is not "one shape per column" — optionality is a real
difference and an optional strike is legitimately `std::optional<decimal>`. It
is: **the value type is `decimal` in every family, never `double`**, and the
column is exact. That is what `check-money-decimal-columns` enforces, with the
baseline as the list of places it is not yet true.

The measurement also explains why a name-level search for the work
over-reports: `strike` is already decimal in six of its eleven families, so a
grep for the name finds files that need no change. The compiler is the reliable
oracle for which seams move, and the dry run says 11 columns change SQL type
while the other 24 change only `:cpp_type:`.

* Why the scale change is one unit, not two

Changing the model's scale changes the generated SQL, which changes the schema
fingerprint, and the fingerprint guard runs when a process starts. Two
consequences that decide how the work must be sequenced:

- The already-running services keep running, because they checked at startup
  and do not re-check. So the change does not visibly break anything.
- Every *new* process that touches the database refuses, including the test
  binaries, which print "the database was built from different SQL" and exit.

So applying the replace and the regenerate without the recreate leaves the
source coherent and the environment unverifiable — the 13 converted columns
and the digest tests can no longer be run at all. The change, the regenerate,
the build and the recreate are one unit, and it should be started only when
there is room to finish it. Around twenty minutes, services down, tenant
rebuilt.

* Two things this change exposed

**model-drift does not check column types.** While the models said
numeric(38, 12) and the generated SQL still said numeric(28, 12) — before the
regeneration reached that component — `compass check --only model-drift`
passed. It compares structure, not types, so a precision change is invisible
to it and only the build and the database suite can confirm a regeneration
finished. Do not treat model-drift as evidence that the SQL matches the
models.

**component-drift is red on any branch that regenerates, and that is not
drift.** `check_component_drift.py --component <x>` regenerates the component
and then reports a `git diff` of the working tree against the base ref, so it
fails for every generated file the branch has touched — including regenerated
ones that are correct. On an uncommitted branch the verdict is unreadable.

The question to ask instead is whether regeneration is a **no-op**, and it is
answerable in two commands: hash the component's generated tree, regenerate,
hash again. Measured for `trading-cpp` after the trade columns, the digest and
the boundary work had all landed: the tree hash is
`0ebc616cb36a395c06ed088846deaccc8bab9f287cf6c4d8f85f0289f5b98727` before and
after, and `git status` reports the same 232 paths. So the tree matches its
models, and the check's red is a statement about the branch and not about the
work.

The gap is now closed by `check-model-sql-types`
(`projects/ores.codegen/scripts/check_model_sql_types.py`, registered in
`build/scripts/local_checks.py`). It reads each model's `:tablename:` and
`* Columns` drawers, finds the SQL file that actually creates that table, and
compares the declared type with the created one. Measured on this tree: 3152
columns compared, 0 mismatches, 0 models whose table no file creates. It was
mutation-proved in both directions — a model changed to `numeric(28, 12)`
against SQL at `numeric(38, 12)`, and the reverse, each reported and each
exiting 1 — and it carries a vacuity floor so a parse that stops understanding
the models fails instead of passing, with `--min-compared` to lower that floor
only when running against a subtree.

**The tests pinned the old scale.** `repository_bond_leg_amount_repository_tests`
hard-codes ten decimal places in its probe expectations and uses an
eighteen-digit value to test the column refusing an over-wide number. Both
were correct assertions about numeric(28, 10) and both had to change with the
scale. They were not a regression to revert; they were the schema being
asserted in two places, which is what a test of a decimal column should do.

* The import is not idempotent on the book name

For anyone re-running the round trip to check this work: `ore import` names the
book after the source **filename**, and a second import of
`portfolio_roundtrip.xml` fails with "The book already exists for that id".

    ✗ Script aborted at line 4: ore import …
      [1/1] ore_import_execute: failed — The book already exists for that id.

Three times in this work a re-run was mistaken for a defect because of it.
Either stage the document under a fresh name, or delete the old book first.
It is a property of the importer, not of the decimals.
