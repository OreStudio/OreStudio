This page documents a [[id:31C868B9-306E-4282-BA8C-07E647021B34][task]] in the [[id:0781E7E1-EF38-4030-8627-13210FA75792][Refactor conventions onto families and bundles]] story. It captures the goal, current status, acceptance, and any notes or results.

* Goal

Every convention family is declared once, in its own entity, and carries only its own fields. The list of families is generated from those entities, and so is the code that writes and reads them. No type holds every family, so no translation unit has to reflect them all.

* Acceptance

- Each convention family is its own entity with its own fields, and a family's field belongs to it alone.
- One generated registry names every family, its scope, and its repository, and the hand-maintained list is gone.
- The apply code that writes the families is generated from the same registry, so adding a family needs no hand edit.
- No reflected type in refdata carries every convention family, and no translation unit instantiates one.
- =conventions_document=, =conventions_document_service= and the whole-document protocol operations no longer exist.

* Plan

The work ran in two halves, and the halves are why the task is still open.

The first half generated the family list and the per-family apply, and it is merged. Before the hand list was touched, the registry was compared with it. The two agreed on 26 families, on the same party and world scopes, and on every row the service wrote, which is what made the swap safe. The apply could not come from the registry alone, because a table of strings cannot call a typed repository, so the same generation emits a branch per family.

The second half is the deletion, and it forces its callers to move in one wave. =conventions_document= is the payload the ORE mapper builds and reverses, and the run store is the service's only production caller. Deleting it means moving the mapper pair, the run store, the diff, the legacy importer and exporter, and the export path onto the staged bundle.

* Notes
- The pin holds. Comparing the service's hand-written calls with the generated
  registry gives 26 families against 26 entries, no disagreement about which
  families are party-scoped and which are world-scoped, and no registry row the
  service never writes. =fx= is skipped and unregistered, as decided. The
  registry is therefore equivalent to the hand list before the hand list is
  deleted.
- The registry cannot replace the calls by itself. A table of strings cannot
  call =replace_party_rows(ctx, zero_convention_repository(), ...)=, because
  each family needs its own repository type. The dispatch has to be generated.
  Codegen must emit one apply function per scope from the same registry:
  party families through =replace_party_rows=, world families through
  =add_missing_world_rows=, and the skipped families collected. The service
  then calls two generated functions instead of listing 26.
- The work splits. First the generated apply functions, which delete the
  service's hand list with behaviour unchanged and the pin green. Then the
  aggregate itself, which is what forces the mapper, the run store and the BFF
  to move in one wave.

- =fx= needs no entity and no registry entry. The document carries an
  =fx_convention= that is the pair, its =currency_pair_convention=, a spot lag
  and its advance calendars. All three of those are entities
  (=currency_pair=, =currency_pair_convention=, =currency_pair_convention_calendar=),
  so the ORE FX convention is a projection of existing rows, not a store of its
  own. Drop it from the document and derive it in the boundary mapper.
- The tenor basis swap family registers as its central row plus its two parts,
  because that is what the document carried. Collapsing it to one family entry
  is a later decision, not part of this task.
- The registry started as a python renderer and is now a codegen facet with
  three archetypes, so a template change replaces a script change. The emitted
  bytes did not change when the renderer was retired.
- What the deletion still has to move, as the tree stands on 2026-10-18. The
  aggregate is declared in
  =projects/ores.refdata/modeling/ores.refdata.configuration_document_messages.org=
  and generated into =ores.refdata.api/messaging/configuration_document_protocol.hpp=.
  In refdata, =conventions_document_service= is the only service that builds
  it, and the run store is the service's only production caller. The service
  also drives the six generated bulk functions in =convention_family_apply.inc=,
  and those functions, not the per-family dispatch, are what reach the type.
  ores.ore holds the type besides, in the mapper pair, the legacy importer and
  exporter, the diff, and the service import. The tests that pin the current
  behaviour are =conventions_document_service_tests= and the conventions half of
  =run_store_database_tests=.

* Result

Not yet complete. Merged so far are the per-family entities, the generated registry, the generated per-family apply in its own translation unit, and the retirement of the python renderer. The aggregate itself is still present, so the task's headline acceptance criterion is not met.

The deletion is in progress. It needs the whole-document service gone, the mapper pair and the run store and the diff and the export on per-family values, and the type removed from the model and its protocol.
