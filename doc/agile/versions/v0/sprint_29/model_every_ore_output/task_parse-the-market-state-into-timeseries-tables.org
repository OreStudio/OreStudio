* Acceptance

- rawcube, netcube, scenario and scenario_fullSurface are catalogued as run results and land in the metric table, one row for each figure, keyed by result, file, line and heading.
- scenariostatistics and stress_scenarios are read into a scenario value hypertable in ores.marketdata with the columns result, file, line, date, scenario, factor and value, one row for each value.
- todaysmarketcalibration is read into a calibration value table in ores.marketdata with one row for each line, its text kept and its number beside it.
- A family whose figures the run configuration decides requires no figure column, so a run that simulates other curves than the sample is read whole.
- The market_state_payloads table, the payload index and the base64 writer are removed.
- A test reads each checked-in sample of these families and lands every value.

* Plan

The metric reader already reads six of the seven families, because each one
states keys, qualifiers and figures: the cubes are keyed by netting set, date
and sample with one =Value=, the sensitivity scenarios by trade and factor, and
the two scenario files by date and scenario with one figure for each factor
column. Only =todaysmarketcalibration= needs its own reader, because its values
are text as often as numbers.

1. Give each metric an identity that holds at volume. The metric table's unique
   index is party, run, family, subject, date and measure, so two factors of one
   trade, two samples of one cube or two results of one run collide. A figure is
   identified by its result, the file it came from and the line it was read
   from. Prove it with a sensitivity of two factors for one trade, red first.
2. Make the cubes and the sensitivity scenarios run results, so the
   post-processor stores them as metrics with no new reader.
3. Give marketdata a figure hypertable for =stress_scenarios= and
   =scenariostatistics=, and a calibration table, each fed by a reader.
4. Remove the payload table, the payload index and the base64 writer.

* Notes

- The red test that proved the metric key was first green for the wrong reason:
  its helper gave each metric a random party, so the two rows never shared a
  key. With one party, as a run stamps, it failed on the unique index.
- The corpus gate passed with the scenario families, but my first marketdata
  tests were refused: the catalogue generator required every column the samples
  share, so the scenario families required the sample's curves. =var= had the
  same defect for quantiles. Fixed in the generator, not the generated file.
- =stress_scenarios= states no record, so the reader made the scenario the
  subject and left the scenario column empty. A scenario or factor key now fills
  its own column even as the subject.
- The Acme reports price NPV and SA-CCR only, and ORE writes an empty
  calibration for them, so the run proves the market-state path reads and stores
  without refusal but no Acme report drives the scenario files. Those are proven
  by the reader and repository tests against the real tables.

* Result

Every market-state file a run writes is now rows a user can query, and no family
is stored as a blob. The cubes and the sensitivity scenario files are run results
in the metric table. =stress_scenarios= and =scenariostatistics= land in
=ores_marketdata_market_scenario_values_tbl=, one row for each factor of each
line, and =todaysmarketcalibration= in
=ores_marketdata_market_calibration_values_tbl=, one row for each line with its
text and, for a double, its figure. Every row of the run's figures and state is
keyed by result, file and line, which is the only key that holds when a file
states many rows with the same subject, date and heading. The payload table, the
payload index, the base64 writer and their permissions are gone. Every acceptance
bullet is met; the end-to-end proof of the scenario path is limited as the Notes
say.
