* What

The services screen shows what the installation runs as a roster: one row per
expected instance, with a state word for each — running, stopped, missing — so
a service that stops keeps its row and a service that never reports shows as
missing rather than absent
([[id:ED949529-0A80-4661-BBAC-E5DB7A6E5828][See the running services]]). The
screen needs two reads and neither exists.

The roster itself is a code-generation model.
=projects/modeling/service_registry.org= lists every service, its
=replicas=, its =enabled= flag and its startup dependencies, for the
deployment tooling to generate from. No operation serves it, so the screen
can only draw what reported, and the expected-but-absent row cannot exist.

The state beyond running hangs on the same gap. *Running* is answerable today:
a sample arrived within five minutes. *Stopped* and *missing* are not. The
thing that knows an instance was stopped is the service manager — the one
=compass services status= asks — and it serves no screen. The candidates: a
read of the registry, so the expected rows and the replica counts exist; and
either a state read or the latest sample per instance at any age, so a quiet
instance keeps its row with the age of its last report.

* Why

An operator's question is as much what is missing as what is running. A
screen drawn from samples alone answers only the second, and it fails in the
worst way: the shorter the list, the less the reader can tell. The registry
already holds the truth a screen needs — the expected services and their
replica counts — and it is one read away.
