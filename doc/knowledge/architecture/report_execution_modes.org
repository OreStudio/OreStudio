#+title: Report execution modes
#+description: The report run pipeline end to end, from the scheduler through the workflow and the compute grid and back, designed in two modes — demo, which consumes an input bundle that already exists, and full, which selects trades, resolves market data, exports ORE XML and imports the results. A single knob on the report definition selects the stages.

#+level: cross

* Summary

A report run is one pipeline whose two ends may be real or substituted. In
the middle, three stages never change: a job input is handed to the compute
grid, the grid runs the ORE engine, and the output is brought back. Around
that middle sit a preprocessing end, which produces the job input, and a
post-processing end, which consumes the output.

A single knob on the report definition — its *execution mode* — selects which
stages the run materialises. *Demo mode* substitutes the preprocessing end
with an input tarball that already exists and the post-processing end with
"record where the output landed"; it exercises the real scheduler, the real
workflow, the real grid and the real storage. *Full mode* is the target: it
selects the trades, resolves the market data, converts ORE Studio data into
the ORE input files, and converts the engine's output back into ORE Studio
data. Full mode is designed here and not yet implemented.

The design's load-bearing rule is that every stage hands the next one a
*storage URI*, never an in-memory structure. Both modes therefore produce the
same thing at the seam — a tarball whose root holds =Input/ore.xml= — and the
grid cannot tell them apart. That is what lets demo mode be a test of the real
machinery rather than of a stub.

* The pipeline in stages

A stage is a unit of work with a name, an owner and a storage-URI contract.
The list below is the target; the two modes differ only in which stages are
present.

| # | Stage | Owner | Consumes | Produces | demo | full |
|---+-------+-------+----------+----------+------+------|
| 0 | =select-trades= | ores.reporting, reading ores.trading | the definition's scope (books, portfolios, as-of date) | the run's trades | skipped | yes |
| 1 | =resolve-market-data= | ores.reporting, reading ores.marketdata | the selected trades | the curves, fixings and quotes they need | skipped | yes |
| 2 | =export-ore-inputs= | ores.ore | the trades and market data | =Input/= for the engine | skipped | yes |
| 3 | =provide-input= | mode-specific | — | one tarball URI whose root holds =Input/ore.xml= | vendored tarball | produced by stage 2 |
| 4 | =submit-job= | ores.compute | the tarball URI | a batch and its workunits | yes | yes |
| 5 | =execute= | the wrapper node and the ORE engine | package and input tarballs | =Output/=, archived to storage | yes | yes |
| 6 | =retrieve-output= | ores.reporting | the result id | the output URI, recorded on the instance | yes | yes |
| 7 | =import-results= | ores.ore | the output archive | rows in the database | skipped | yes |
| 8 | =finalise= | ores.reporting | — | the instance in a terminal state | yes | yes |

Stages 4, 5 and 6 are the *common tail*. Nothing in them knows which mode
produced the input or whether the output will be imported, and nothing in
them may learn.

** The engine package is a prerequisite, not a stage

Registering the ORE engine build — an app, an app version, and a
per-platform package with its SHA256 — is done once per environment and per
engine build, not per run. It is seeded, as
[[id:CC0A311E-7245-4694-86A1-3170023C385A][the end-to-end runbook]] does
today. A run cannot start without it, because the workunit needs an
=app_version_id= and the wrapper needs a =package_uri=.

* Two modes, one knob

** The knob

The knob is a column on the report definition, =execution_mode=, with two
values today: =demo= and =full=. It is *definition state*, not a build flag
and not a message field invented at trigger time, for three reasons:

- a run must be reproducible from the database alone, and a build flag is not
  in the database;
- the scheduler fires the trigger without an operator present, so there is
  nobody to pass a flag;
- the mode belongs to the definition the same way its cron expression and its
  concurrency policy do.

The trigger already carries the answered question: the scheduler publishes
=reporting.v1.ops.trigger_report_instance= with the definition id, and the
reporting service resolves the definition. The mode is therefore read where
the instance is created and travels to the workflow in the start message's
=request_json=, which is the one field =build_steps= already receives.

** Why a column, and not the report type

=report_type= is tempting, because it is already a foreign key on the
definition and a demo run is "a different kind of report". It is the wrong
carrier: report type is a *category of report* — risk, grid, regulatory — and
overloading it would make a demo run a different kind of report rather than
the same report run in a different way. A separate column keeps the type
axis and the mode axis independent, which is what the target needs: a full
run and a demo run of the same definition should differ in exactly one field.

** The modes as stage bindings

A mode is not a separate pipeline. It is a binding from each stage to a
provider:

| Stage | demo binding | full binding |
|-------+--------------+--------------|
| preprocess | absent; =provide-input= resolves a pre-uploaded tarball | =select-trades= → =resolve-market-data= → =export-ore-inputs= |
| provide-input | the vendored tarball | the tarball stage 2 wrote |
| common tail | unchanged | unchanged |
| post-process | absent; =retrieve-output= records the URI and stops | =import-results= |

Read that way, demo mode is full mode with its two ends unbound — which is
exactly why it is a legitimate test of the machinery and not a mock.

* The seam

Every stage boundary carries a storage URI. That is the whole contract.

- =select-trades= and =resolve-market-data= write the run's inputs where the
  next stage can find them; they do not hold them in memory across a message
  boundary, because they cannot — each stage is a separate NATS request, and
  the process may be a different one.
- =provide-input= produces *one URI* whose object is a tarball whose root
  holds =Input/ore.xml=. In demo mode the object already exists and the stage
  resolves it; in full mode the export wrote it.
- =submit-job= receives that URI and nothing else about its provenance.
- =retrieve-output= records the output URI on the instance. In demo mode the
  chain ends there; in full mode =import-results= reads that same URI.

The seam is the storage contract in
[[id:286B7167-9B8A-4937-BBA5-E9D285AFECE3][Object Storage]]: a bucket, an
opaque key and bytes. The pipeline relies on storage being able to move bytes
without understanding them, and on the key being a name that composes, not a
path storage creates.

** Consequence: the run directory is the unit of work

Because the engine's working directory is the job directory and =ore.xml= is
resolved inside it, the tarball's *layout* is part of the contract, not just
its bytes. The wrapper's manifest names =Input/ore.xml=, so any input
produced by any mode must have that shape. This is a contract between
=ores.ore=, =ores.reporting= and =ores.compute=, and it should be stated once
and asserted at the seam rather than assumed three times.

* Orchestration: the workflow is the coordinator

The pipeline crosses four services — reporting, ore, compute, and the grid
behind compute — and one of them is asynchronous and may take minutes. That is
a saga, and [[id:7F4B91E2-3D86-4A57-B92C-08E146DA7359][ores.workflow]] is
what makes it one. This is the part of the design that is easiest to leave
implicit, because the stages read like a pipeline; it is stated here because
every stage this design adds is a new participant in a coordination contract,
not just a new box.

** The shape of the coordination

- One workflow instance per report instance, started by the trigger.
- A *stage* is a participant. The engine invokes it by publishing a command on
  the stage's subject; the stage does its work and answers on
  =workflow.v1.events.step-completed=.
- The engine — not the stages — decides what runs next, persists that
  decision, and owns resumption after a crash.
- Every step carries =reporting.v1.report.fail= as its compensation subject.

** The participant contract

A step command carries three headers — step id, workflow instance id, tenant
id — which is how a stage attributes the message it receives, and its payload
is the step's =command_json=. Completion names the step and carries its
result. That is the entire interface between the coordinator and a
participant, and a new stage joins it rather than inventing a mechanism.

** What the engine gives today, and what this design needs**

| Property | Today | What the design requires |
|----------+-------+--------------------------|
| dispatch | =nats_.publish=, fire and forget: no ack, no timeout | a stage that never answers must not hang the run for ever |
| durability | the step is persisted =in_progress= *before* the publish, and recovery re-dispatches every =in_progress= step on restart | delivery is at-least-once, so every stage must be idempotent |
| completion | a completion for a step no longer =in_progress= is ignored | a stage that runs twice must be harmless, not merely mis-recorded |
| failure | compensation walks the completed steps in reverse, each publishing =fail_report= | each mode must say what its compensation undoes |
| selection | =build_steps= is re-run on every dispatch | a chain must be a pure function of =request_json=, or a resumption can materialise a different chain |

The last row is why the mode travels in the start message rather than being
read again at each dispatch: resumption must rebuild the same chain it
started with.

** Idempotency is a requirement on every stage

Because dispatch is at-least-once and there is no timeout, a stage can be
invoked more than once — after a restart, after a re-dispatch, or because a
publish was delivered twice. Every stage must therefore converge rather than
accumulate: submitting a batch twice must not create two batches, exporting
twice must overwrite the same object rather than append, and importing twice
must not double the result rows.

This is not a general plea for care. Demo mode will find it, because a restart
in the middle of a run is exactly what a smoke test should survive, and
because the modes share the tail — an idempotency defect that demo mode
exposes is one full mode would otherwise have inherited.

** Two state machines describe one run, and one must be authoritative

The workflow instance records steps; the report instance records the FSM. They
can disagree — a workflow that has failed while its instance still reads
=running= is a real outcome today, and a second mode doubles the number of
paths that reach it. The design's position is that the *report instance* stays
the user-visible truth, and the workflow's terminal transition is what drives
it, through the same FSM guard the pipeline already uses. The alternative — the
workflow as the source of truth, with the instance as a projection — is
defensible but would move the state a caller reads away from the table a
caller already reads.

** The engine gaps this design leans on

Three are already known and are prerequisites rather than details:

- an unknown workflow type is logged and dropped, while the trigger has
  already answered =triggered=, so a mis-selected chain looks like success;
- =materialised_steps_json= is written but never compared, so the guard its
  own comment claims does not exist;
- a step whose subject has no subscriber stays =in_progress= for ever and is
  re-dispatched on every restart.

None is fixed by this design, and all three are things a two-mode pipeline
will hit rather than merely risk. They are why the design tasks the
orchestration contract separately from the stages.

* Results are addressed by role, not position

The current workflow's step lambdas read earlier steps' results by index:
=submit_compute= reads =results[3]=, =collect_compute_results= reads
=results[4]=, =prepare_ore_package= reads =results[2]=, =results[0]= and
=results[1]=. A missing position yields an empty field silently.

That is already fragile with one chain. With two it becomes a defect
generator: every stage a mode adds or removes shifts the indices of every
stage after it, and the failure mode is a blank field that surfaces much later
as a domain error — or, worse, does not surface at all.

The design therefore replaces positional access with *a result addressed by
the stage's role*: a step's result is looked up by the stage that produced it.
The workflow already knows each step's name, so the map exists; what changes
is that consumers ask for "the input tarball URI" rather than "the fourth
result". This is the single change that makes two modes cheap instead of
quadratic, and it should land *before* the second mode does.

* The NATS contract

Every hop below is a NATS request unless noted. The reporting and scheduler
services authenticate with their own service tokens
([[id:3E20C1A0-7BA1-4F31-8C34-1E5F13558890][Service-to-Service Auth]]), and
the trigger demands a session.

| Subject | Publisher | Subscriber | Payload |
|---------+-----------+------------+---------|
| =reporting.v1.ops.trigger_report_instance= | ores.scheduler, on a job firing | ores.reporting | definition id, tenant, job instance id |
| =workflow.v1.start= | ores.reporting | ores.workflow | workflow type and the =request_json= carrying the mode |
| =reporting.v1.report.gather-trades= | ores.workflow, dispatching step 0 | ores.reporting | instance and definition |
| =reporting.v1.report.gather-market-data= | ores.workflow, step 1 | ores.reporting | instance and definition |
| =ore.v1.report.export-inputs= *(new)* | ores.workflow, step 2 | ores.ore | instance, and the gathered inputs |
| =reporting.v1.report.provide-input= *(new)* | ores.workflow, the input stage | ores.reporting | instance and mode; demo resolves, full passes through |
| =compute.v1.report.submit= | ores.workflow | ores.compute | instance, tenant, correlation, tarball URIs |
| =compute.v1.work.assignments.{tenant}.{platform_code}= | ores.compute | a wrapper node, by queue group | result id, workunit id, package URI and SHA256, input URI, output URI |
| =compute.v1.results.submit= | the wrapper node | ores.compute | result id, host id, output URI, outcome |
| =workflow.v1.events.step-completed= | the stage handler | ores.workflow | step index and the step's result |
| =reporting.v1.report.collect-compute-results= | ores.workflow | ores.reporting | instance and batch |
| =ore.v1.report.import-results= *(new)* | ores.workflow | ores.ore | instance and output URI |
| =reporting.v1.report.finalise= | ores.workflow | ores.reporting | instance |
| =reporting.v1.report.fail= | any stage, or compensation | ores.reporting | instance and the reason |
| =scheduler.v1.job_definitions.put= / =.delete= | ores.reporting, when reconciling | ores.scheduler | the job definition |
| =storage.v1.objects.{put,get,delete,list}= | any stage | ores.storage | bucket, key, and either bytes or a URI |
| =PUT/GET /api/v1/storage/{bucket}/{key}= *(HTTP)* | a stage with bulk bytes | ores.storage | the object |

Two properties of this table are worth stating because they are easy to lose
in implementation:

- *The grid never sees the domain.* The only thing =ores.compute= receives
  about a report is an instance id and a list of URIs. It cannot tell a demo
  run from a full one, and it must not grow the ability to.
- *The mode never reaches the wrapper.* The wrapper is mode-blind by
  construction, because the mode was resolved before the input existed.

* Distance from today

** Exists

- The whole common tail. A report triggered from the shell runs gather,
  assemble, package, submit, collect and finalise, and the instance reaches
  =completed= through the FSM guard. The grid path itself —
  =compute dispatch-batch=, assignment, wrapper, engine, result — works and is
  documented in [[id:1805BAFC-7E43-4D9C-822F-17C3455C6E00][Compute job lifecycle]].
- The scheduler's job model and its firing path, with a job instance per
  firing and a service token on the publish.
- Reporting's scheduling reconciliation: a definition owns a scheduler job
  named =report_definition.<id>=, adopted by name on every restart.
- Object storage with both interfaces, and the reporting run keys it already
  uses.
- The vendored example job input, =external/ore/packages/TA002_IR_Swap.tar.gz=,
  whose root holds =Input/ore.xml= — the object demo mode consumes.
- An ORE XML layer in =ores.ore=, in two halves that are easy to confuse.
  The *bindings* are complete: =xsdcpp= generates the whole ORE vocabulary
  from =external/ore/xsd/input.xsd=, so every document can be loaded and
  saved. The *mappers*, which turn ORE Studio's own data into those
  bindings, exist for four document kinds only — portfolio, currency config,
  calendar adjustments and conventions. The engine additionally needs
  =ore.xml=, =todaysmarket.xml=, =pricingengine.xml= and =curveconfig.xml=,
  and none of those four has a mapper.

** Missing

| What | Whose | Note |
|------+-------+------|
| =execution_mode= on the definition, and its carrier into =build_steps= | ores.reporting | the knob itself |
| Result addressing by role instead of index | ores.workflow, ores.reporting | prerequisite for a second chain |
| An input stage that resolves a pre-existing tarball | ores.reporting | the demo binding |
| A repeatable way to put the demo tarball in storage | ores.reporting, seeding | today the object is in the tree, not in a bucket |
| Mappers for =ore.xml=, =todaysmarket.xml=, =pricingengine.xml= and =curveconfig.xml= | ores.ore | the bindings can save all four; no ORE Studio to binding mapper exists for any of them |
| A package that satisfies the wrapper's contract | ores.ore | =prepare_ore_package= tars =trades.msgpack= and =market_data.msgpack=; the wrapper needs =Input/ore.xml= plus six named files |
| ORE result ingestion | ores.ore | nothing reads the engine's output at all: =npv.csv=, =flows.csv= and =curves.csv= are only ever archived, and =collect_compute_results= is a stub |
| Market data *resolution* | ores.marketdata, ores.reporting | gathering dumps every series the tenant holds; nothing derives what the selected trades need, and =oresmd_resolver= is called only from its own tests |
| An as-of trade population selector | ores.trading, ores.reporting | scope is book and portfolio only; there is no date-versioned selector, although =risk_report_config= already stores a market data date |
| A compute app version for the tenant | seeding | submit fails without one |
| The reporting-to-compute handoff | ores.compute | see below — the tail is *not* currently drivable from reporting |

** The handoff is the load-bearing gap

The common tail works when it is driven by =compute dispatch-batch= from the
shell. It does not work when it is driven from =ores.reporting=, for three
independent reasons, all of which must be fixed before demo mode can run at
all:

1. =report_submit_handler= publishes on =compute.v1.work.assignments.{tenant}=,
   where no wrapper subscribes; they subscribe to =...{tenant}.{platform_code}=;
2. it leaves =result_id=, =package_uri=, =config_uri= and =output_uri= empty;
3. =prepare_ore_package= hands over a bucket-prefixed URI, =ores/ore/...=,
   where the wrapper fetches an =/api/v1/storage/...= path.

This is why demo mode is worth building first: it forces the tail to be real
and drivable from the workflow, which is the part full mode inherits
unchanged.

* How the knob is exercised

** Demo mode proves

- the scheduler fires and the trigger arrives authenticated;
- the workflow selects a chain from the definition's own state;
- the common tail runs from a workflow step, not from an operator's shell;
- the engine actually executes and its output actually reaches storage;
- the instance records where that output is.

It deliberately does *not* prove that the trades or the market data are
right, because it does not look at them.

** Full mode proves

Everything demo mode proves, plus that ORE Studio's own data can be turned
into a run the engine accepts, and that what comes back can be read into the
database.

** The check that makes demo mode worth having

Because the mode is definition state and the seam is a URI, demo mode is
repeatable from a database recreate: seed the tarball, seed the definition
with =execution_mode = demo=, fire the schedule, assert the instance reaches
=completed= and that the output object exists. That is a check the fleet can
run on every build, which is the point of designing the knob before the
feature.

* Decisions

1. *The mode is definition state.* A column, resolved when the instance is
   created and carried in =request_json=, so a run is reproducible from the
   database and works with no operator present. It also makes =build_steps= a
   pure function of its input, which resumption requires.
2. *The mode is not the report type.* The type axis stays a category; the
   mode axis is separate, so a full run and a demo run of one definition
   differ in one field.
3. *Stages exchange storage URIs, never structures.* This is what makes the
   modes interchangeable and the grid mode-blind.
4. *ores.workflow is the coordinator, and the participant contract is stated.*
   A stage is a participant on a command and a completion event, not a link in
   a chain of direct calls. The design states that contract rather than
   leaving it implicit in the stage list.
5. *Every stage is idempotent.* Dispatch is at-least-once with no timeout, so
   convergence is a requirement on each stage, and demo mode is where it gets
   found.
6. *The report instance is the authoritative state.* The workflow drives it
   through the FSM guard; the workflow's own instance record is the
   coordinator's bookkeeping, not the answer a caller reads.
7. *Step results are addressed by role.* The change lands before the second
   mode, because two modes make positional access a defect generator.
8. *Both modes produce the same object shape* — a tarball whose root holds
   =Input/ore.xml= — and that shape is a stated contract, asserted at the
   seam.
9. *The engine package is a prerequisite, not a stage.* It is seeded per
   engine build, not per run.
10. *Full mode is designed now and built later.* No stage that demo mode
    proves may need to change to admit it.

* Open questions

- *Where the export's inputs live between stages.* Stages 0 and 1 produce
  data that stage 2 consumes. Today's gathered blobs are MsgPack under the
  reporting run keys; the export could read those, or the export could be
  given its own query. Which of the two keeps =ores.ore= free of reporting's
  storage layout is unresolved.
- *Whether =provide-input= is one stage or two.* Demo resolves a URI; full
  passes one through. It may be simpler for the demo binding to be an
  *absence* — the export stage writing the vendored object's URI — rather
  than a stage with two behaviours.
- *What a run should do when no grid is present.* The orchestration section
  states the requirement — a stage that never answers must not hang the run —
  but not the mechanism: a per-stage deadline, a retry budget, or a
  compensation on timeout. The choice belongs with the orchestration
  contract, and it decides how an environment without a grid fails.
