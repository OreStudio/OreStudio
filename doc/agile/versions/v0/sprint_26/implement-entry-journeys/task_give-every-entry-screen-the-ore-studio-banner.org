* Goal

Every door into a deployment carries the same banner. The setup screen already leads with the project's artwork; the sign-in dialog does not, and the registration door the Entry story adds must. A person arriving at a deployment for the first time sees the same product whether they are being set up, signing in or registering.

* Acceptance

- The sign-in dialog carries the banner.
- The registration door carries it on every step, not only the first.
- The banner is the artwork the setup screen and the main site already use, reached through =assets/brand.ts= rather than a second copy of the file.
- The banner does not crowd the party picker, the forced password change panel, or the refusal notices: it is above the work, and the work still reads.
- A test asserts the banner renders on both dialogs, so a future layout change cannot drop it silently.

* Plan

1. Decide where the banner belongs. The setup screen draws it per screen; a shell that draws it for every visitor is the smaller change and the one that makes "every dialog" true by construction, so try the shell first and fall back to the page if the shell cannot tell a door from a form.
2. Put it on the sign-in dialog, above the credentials form and above the party picker, because the picker replaces the form rather than following it.
3. Put it on the registration door's rail, above the step, so it stays put while the step changes.
4. Assert it in the shell's or the page's test, whichever ends up owning it.
