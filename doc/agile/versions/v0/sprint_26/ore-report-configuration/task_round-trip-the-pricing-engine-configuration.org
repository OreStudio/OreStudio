* Result

The mapper pair and both tests are written, and the corpus is proven.

** What round trips

=125= of the =125= pricing engine files in the corpus round trip through
=pricing_engine_mapper=, with no failure. The walk is the harness every other
kind uses: each file is parsed, mapped to the entities, mapped back, and
compared as a parsed document against the original, so a field the mapper drops
makes the two disagree and the first difference is named.

This was measured by linking a driver against the already-built
=libores.ore.core= and running it over =external/ore/examples=. The output was:

#+begin_src
kind=pricing engines files=125 passed=125 failures=0
#+end_src

The driver is throwaway and lives outside the tree; the committed test runs the
same walk inside Catch2.

The mapper and the two new test files also compile clean under their own
targets' recorded =flags.make= with =-Wall -Wextra -Werror=, as do the twelve
regenerated sources in =ores.analytics= and =ores.shell=. Fifteen of fifteen.

** Through the database

=pricing_engine_database_roundtrip_tests.cpp= passes. It takes the largest
document in the corpus — 80 products, 406 product parameters and 9 global
parameters — maps it, writes the configuration and its rows to PostgreSQL,
reads them back filtered to the configuration id, and compares the document
that comes out against the one that went in.

The database was rebuilt from scratch with =compass db recreate -y -k= first, so
the case ran against the regenerated schema rather than a hand-patched one. Both
=position= columns are present in the recreated database.

** Reproving it after the build

The corpus walk was first run through a hand-linked driver, because =compass
build= could not start: it wraps =cmake --build= in =systemd-run --user
--scope=, which fails with "Failed to connect to user scope bus via local
transport" while the sandbox does not expose the user manager's private socket.
That driver reported the same 125 of 125, and the committed Catch2 case now
reports it inside the suite, so the driver is no longer needed.

One trap is worth recording. Building only =ores.ore.core.tests= relinks the
analytics *libraries* but leaves the analytics *test* executables compiled
against the old struct, so =ores.analytics.core.tests= aborted with =free():
invalid pointer=. That is a stale binary and not a defect in the change: a full
=compass build= recompiles those dependents, and all six suites the change
touches pass.

** Why =position= had to be added

=34= of the 125 files write the same =Product/@type= more than once and =24=
write the same =Parameter/@name= twice within one scope, so neither field
identifies its row and neither can be sorted back into the order the document
wrote. The column follows =ores.reporting.configuration_parameter=, which
documents the same reason for the same solution.

** A corrected description

The task description claimed that no entity model existed and that the document
carried engine-to-currency and engine-to-product assignments and grid and script
settings. Both claims were wrong: the three entities already mirrored the
document element for element, and the schema has none of those settings. The
description is corrected, and the three entities were left as they were apart
from the two =position= columns.
