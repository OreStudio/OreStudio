* Goal

Curves are referenced by name from five of the analytics documents, so a curve that does not round trip breaks every document that names it.

* Acceptance

- Every curveconfig.xml in the corpus imports, exports and matches.
- A curve resolves its conventions, calendar, day counter and index by foreign key, not by string.
- The segment types are a seeded lookup, so a new segment type is a row and not a struct.

* Plan

Measured on 2026-10-03 at fe244a3331 before any change:

- 89 corpus documents have the root =CurveConfiguration=, with 22 section kinds.
  An entry carries from 2 to 30 distinct child elements, by section. Yield
  curves are the largest: 1193 entries and 10 segment kinds in use.
- The binding already holds =curveconfiguration= with a loader and saver. No
  binding work is needed.
- The binding groups a yield curve's segments by kind, one vector per kind, so
  the order of segments across kinds is lost before a mapper runs. A mapper can
  keep only the order within a kind.
- The curve tables on main (=curve_definition=, =curve_section=,
  =curve_segment=, =curve_quote=) store each entry's common settings as text
  and the rest as a semicolon and pipe encoded =extras= column. Nothing reads,
  writes or seeds them. That shape fails this task's acceptance and the
  story's (no name and value pairs, references by foreign key).
- The day counters the corpus writes do not match the seeded day count codes:
  =Actual/365 (Fixed)=, =ACT=, =Actual/360=, =ActActISDA= and =30E/360E= have
  no row, 657 values in all. The schema's =dayCounter= enum lists every
  spelling ORE accepts, about seventy.
- Curve segments name 219 distinct convention ids. Conventions are one table
  per category, each keyed by its text id, with no shared identity table.

Shape:

- A curve entry is a header row, =curve_definition= (section, =CurveId=,
  description, position), which is the one identity other documents refer to,
  plus a detail row per section family with that family's settings as typed
  columns. Nested lists (segments, quotes, volatility configurations) are child
  rows with typed columns and a position within their kind.
- An ORE enumeration becomes a seeded lookup derived from the schema by a
  script, keyed by ORE's own spelling, so a column keeps the exact spelling
  and resolves by foreign key. A day counter spelling also names its canonical
  day count code.
- A convention reference is checked against every convention table by one
  validation function, because there is no shared convention identity. An
  index reference resolves against the floating index types.

Delivery, one PR per step, each with its own check:

1. Lookups. The curve sections, the segment kinds and types, and the ORE day
   counter spellings, seeded by a script that reads the schema. Check: the
   seed counts equal the schema's enumerations.
2. Yield curves. Replace the generic columns with the header and the yield
   curve detail, segments and quotes; the mapper for the =YieldCurves=
   section. Check: every =YieldCurves= section in the corpus round trips in
   memory and through the database.
3. The other curve sections (default, equity, inflation, commodity, securities,
   FX spots, intraday power). Same check per section.
4. The volatility and correlation sections and the report configuration. Check:
   every whole document in the corpus round trips.

* Notes

Step 2, decided while building it:

- A document is a =curve_configuration= row, as today's market is a
  =todays_market_config= row, so a tenant may hold several and a report reaches
  one through its reporting configuration.
- Sixteen of the nineteen sections appear empty somewhere in the corpus, so the
  sections a document writes are rows of =curve_configuration_section=, with or
  without entries.
- =BootstrapConfig= is shared by five section types, so it is one table keyed
  to the curve entry. A row exists exactly when the element does; fourteen
  corpus yield curves write it empty.
- Every corpus =Report= on a yield curve is present and empty (121), so
  =yield_curve.has_report= holds its presence.
- A segment stores only its type; the type fixes the segment element. The
  mapper keeps the same table as the seed, and the seed test ties the seed to
  the schema.
- ORE enumerations other than the day counter and the segment type -- the ORE
  boolean, the interpolation method and variable, the extrapolation method --
  are held as the text the schema spells, and the binding refuses an unknown
  value on export. Only the two the acceptance names are lookups.
- A convention is checked by =ores_refdata_validate_convention_id_fn=, which
  looks in all twenty-four convention tables keyed by id. FX conventions are
  held per currency pair and their id is not stored, so only the id the
  conventions export writes, =BASE-QUOTE-FX-CONVENTIONS=, resolves. 600 or more
  corpus FX ids have another form; [[id:F7171FEA-3402-4B19-BCB3-02F3BFC33C1A][Keep each FX convention's ORE id]] fixes that.
- Four index names the corpus yield curves use were not seeded floating index
  types: =EUR-EONIA=, =EUR-ESTER=, =GBP-LIBOR-3M= and =USD-LIBOR-1M=. They are
  seeded now.

Step 3a, decided while building it:

- Step 3 is split by section family: 3a the equity curves, securities, FX
  spots and intraday power curves; 3b inflation; 3c default curves, whose
  nested configurations need child rows; 3d commodity.
- A calendar is an expression, not a name: =TARGET,UK= and
  =JoinHolidays(TARGET, US settlement)= are both one calendar. The schema
  lists 471 names and allows two open forms, any four-letter exchange code and
  any =CUSTOM_= name. =calendar_name= holds the 471, and
  =ores_refdata_validate_calendar_fn= splits an expression and checks each
  part against them or against the two forms. The refdata =calendar= table's
  61 codes miss most of the corpus (=XNYS=, =USD=, =weekends only=), so it is
  not the target.
- 101 corpus equity curves write an empty =Calendar= and three an empty
  =Quotes=; the empty calendar is stored as empty text and the quotes element's
  presence as =equity_curve.has_quotes=.
- =intraday_power_curve.convention= is nullable in the table because the
  generated event test cannot seed a convention; the mapper refuses to export
  an entry without one.

Step 3b, decided while building it:

- An inflation curve's settings are =inflation_curve= and its seasonality
  factors =inflation_seasonality_factor=; its quotes sit on the entry, as an
  equity curve's do. =has_quotes= and =has_seasonality= hold the presence of
  the two optional elements.
- The schema allows inflation =Segments= and no corpus document writes them.
  The mapper refuses an entry that does, rather than lose it; modelling them
  waits for a document that needs them.

Step 3c, decided while building it:

- A default curve writes its settings inline (144 corpus curves) or as a list
  of prioritised =Configurations= (189, nine with two), never both. One table,
  =default_curve_configuration=, holds both forms: an inline curve is one row
  with =is_inline= set. =default_curve= holds only the currency.
- A configuration's quotes and =BootstrapConfig= are rows of =curve_quote= and
  =curve_bootstrap_config= naming the configuration, through a new nullable
  =default_curve_configuration_id= on each.
- =Pillars= and =States= are comma lists in ORE's own text and are held as
  written. =SourceCurves= and =SwitchDates= appear in no corpus document and are
  refused, as inflation segments are.

Step 3d, decided while building it:

- A commodity curve's =BasisConfiguration= is one per curve, so its settings
  are =basis_= columns on =commodity_curve=; its =PriceSegments= are rows of
  =commodity_price_segment=. Each appears in one corpus document.
- A quote's owner can now also be a price segment, and a parent that writes
  more than one quote list names the list: =curve_quote.quote_list= is
  =BasisQuotes=, =OffPeakQuotes= or =PeakQuotes=, and null for the main
  =Quotes=. That is the fourth way a quote attaches, and step 4 should decide
  whether a single owner reference reads better than four nullable columns.

Step 4a, decided while building it:

- Step 4 is split by surface shape: 4a the flat sections (FX volatilities,
  yield volatilities, base correlations, correlations), whose entries have no
  child lists; 4b CDS and inflation cap and floor volatilities; 4c swaption and
  cap and floor volatilities; 4d equity, commodity and bond future volatilities
  and the global =ReportConfiguration=.
- Ten entry types carry the same =Report= element, so it is one table,
  =curve_report_configuration=, keyed to the entry's =curve_definition=. A row
  exists exactly when the entry writes the element. No corpus entry writes its
  own =Report=; the database test adds one to an FX volatility.
- =ParametricSmileConfiguration= on an FX volatility, and =RecoveryGrid=,
  =RecoveryProbabilities= and =QuoteTypes= on a base correlation, appear in no
  corpus document and are refused.
- The FX smile interpolation is free text in the schema, not an enumeration,
  and is held as written.

Step 4b, decided while building it:

- CDS, equity and commodity volatilities all name one or more volatility
  configurations (=Constant=, =Curve=, =StrikeSurface=, =ProxySurface= and, for
  equity and commodity, more surface kinds), each with an optional priority.
  They share one table, =curve_volatility_config=, with a =kind= column and the
  columns each kind uses. Only =StrikeSurface= is modelled now, because it is
  the only kind a corpus CDS volatility writes; steps 4c and 4d add the other
  kinds with the sections that write them.
- A CDS volatility's =Terms= are rows of =cds_volatility_term=, with their
  position. =PriceInfo=, an empty =Terms= element and the unmodelled surface
  kinds are refused.
- An inflation cap and floor volatility is flat. Its =Report= and
  =BootstrapConfig= reuse =curve_report_configuration= and
  =curve_bootstrap_config=.
- The operator asked whether these tables hold curves or curve
  configurations. They hold configurations only; the naming question waits in
  [[id:1027E041-1B39-4150-8725-3C0C78F0F1D1][Discuss the _config suffix for the curve configuration tables]].
