* Acceptance

- The setup form proposes =super_admin= and an address, and both are editable.
- The password keeps no default, because a password that ships with the product is not a password.
- A test asserts the proposed values, and the workspace typechecks, passes the format check, tests green and builds.

* Plan

One commit: two constants, their comment, and the tests that hold them.

** The username

=super_admin=, which is what the accepted prototype's first-run journey
defaulted the system administrator to (=8b0ce0a95b=, "Default the system
administrator to =super_admin="). The prototype is the design record for the
journey's content, so the default comes from there rather than from a guess.

** The address, and why not a plausible domain

=super_admin@system.ores=. Two reasons, and the second is the one that decided
it. Every other system-scope account already uses that suffix —
=compute_wrapper@system.ores=, =http@system.ores=, =ddl@system.ores= in the IAM
seeds — so the first administrator reads like the rest of the deployment. And
=.ores= is not a real top-level domain, so nothing can be delivered to an
address nobody changed; the example the request named, =localhost.com=, is a
registered domain, so a placeholder there could reach a stranger if a deployment
never changed it.

The prototype left the email empty, so proposing it goes beyond the design
record. It is the same kind of convenience as the username, and it is editable.

** The password, which gets nothing

A default password is a password that ships with the product, and this account
is the SuperAdmin of a fresh installation. The prototype left it empty too. The
form requires the policy to be met before it will submit, and the policy is the
one the server enforces.

* Notes

- *The address differs from the one the request named.* It asked for
  =super_admin@localhost.com=; the default is =super_admin@system.ores=. The two
  reasons are the convention above and the routability of =localhost.com=. It is
  one line in =SetupPage.tsx= to change.
- *The prototype left the email empty.* Defaulting only the username was the
  accepted design; defaulting the address as well is the same convenience, and
  the person can clear it.
- *A default is a value, not a word.* Neither constant belongs in the i18n
  catalogue: a catalogue carries the words, and a translator has no business
  translating an account name.

* Result

The setup form proposes =super_admin= and =super_admin@system.ores=, both
editable, and proposes no password. A person creating the administrator of an
empty installation now types one thing and clicks once.

The username comes from the accepted prototype, so the default is the design
record's rather than a choice made here. The address follows the convention
every other system-scope account uses and cannot be delivered anywhere, which is
what makes it safe to leave unchanged.

The form still refuses to submit until the password meets the policy the server
enforces, and the account it creates is the SuperAdmin the deployment needs
before it can be signed in to at all.
