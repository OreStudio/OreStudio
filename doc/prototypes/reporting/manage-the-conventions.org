* Summary

This prototype owns the whole conventions interaction of a conventions
configuration. It is a *table*, not a wizard: one row per convention kind, the
name of the convention in use, what its terms say, where the kind came from, and
one button that opens that kind alone. The step-per-kind wizard that used to be
here is gone, because twenty-six steps is not a screen a person can read.

Two prototypes that used to draw the same interaction hand the work here:

- [[file:create-a-report/][Create a report]] reads the set on its step 2 and links
  here;
- [[file:change-what-a-report-runs/][Change what a report runs]] reads the set on its
  step 1 and links here.

The conventions do not belong to a definition. A conventions configuration is a
reporting row of type =conventions= whose detail lives with =ores.refdata=, and
thirty-one definitions bind the configuration this page draws. A change here
reaches every one of their next runs.

It is throwaway. It reads no service and writes nothing. The term values and
the row counts are real rows of ACME's own convention tables; which document of
a kind the page names, the default mark and the change in progress are fixtures
and say so.

**ACME is provisioned, and the conventions arrive through a DQ publish.** The
tenant holds 10,991 convention rows across 26 tables, so every kind is bound and
no row reads *none*. 25 of the 26 kinds came from a DQ publish; =tenor= is the
one exception, with no DQ artefact table, its 4 rows copied from the system
tenant during provisioning. Every kind now holds many documents rather than one,
and no column records which of them a run reads, so the absence the screen has to
argue about is no longer *no document*: it is *no default*.

* Detail

** The screen is a table

| Column | What it holds |
|--------+---------------|
| Kind | The family's name, its code, and how many term columns its table carries. |
| The convention in use | The name derived from the terms of the first document of the kind by key, how many documents the kind holds, and whether the party owns them or the tenant does. A kind with none reads *none* and says what a run does instead. |
| What its terms say | The same terms in words, and the count of documents the kind holds. |
| Where it came from | *DQ publish* with the subject and the dataset that wrote the kind, or, for =tenor=, *copied from the system tenant* and why. |
| (one button) | *Change*, which opens that kind alone. Nothing else on the row acts. |

The table answers one question: what does this report read, kind by kind. A
person scans 26 rows and opens the one that is wrong. Nothing is chosen on the
table, so nothing is lost by looking.

** The first state is provisioned, and every kind is bound

ACME is provisioned, so the page opens on the state the database is in: **every
kind holds documents.** Tenant =5f3febb3-d42a-4b4e-a1c4-8515229ce9dd=, code
=acme_corporation=, status active, owns **10,991 rows across the 26
=ores_refdata_<kind>_conventions_tbl= tables**:

| Kind | Rows | Kind | Rows |
|------+------|------+------|
| average_ois | 25 | ibor_index | 10 |
| bma_basis_swap | 15 | inflation_swap | 110 |
| bond_yield | 25 | intraday_power_load | 10 |
| cds | 20 | ois | 260 |
| cms_spread_option | 5 | overnight_index | 23 |
| commodity_forward | 20 | swap | 1,600 |
| commodity_future | 3,950 | swap_index | 1,215 |
| cross_currency_basis | 1,035 | tenor | 4 |
| cross_currency_fix_float | 120 | tenor_basis_swap | 185 |
| currency_pair | 179 | tenor_basis_two_swap | 20 |
| deposit | 815 | zero | 190 |
| fra | 210 | zero_inflation_index | 45 |
| future | 35 | fx_option | 865 |

The five parties share the tenant, so a party-scoped kind holds a fifth of those
rows per party: deposit 163, swap 320, commodity future 790. **A party holds
2,155 documents; the tenant holds 216 more in the four kinds whose table carries
no party column.** The page states both numbers above the table.

**A new party still starts with none.** That state is reachable as
=?state=none=, and it reads:

  A new party holds no convention document. Every row below reads none, and a run
  falls back to the curated document for the kind. This is where provisioning
  starts, and this fixture draws it. The database is provisioned, so this is not
  its state.

**26 convention tables, 25 DQ publishes, one exception**

The rows did not arrive by hand. Each fact below was checked against the
database:

- **25 of the 26 kinds came from a DQ publish.** 24 of them from subject
  =refdata.v1.ops.publish_conventions_from_dq= and dataset
  =1847fe5b-e8a5-435d-9df3-2d6afc411b85=, named =ORE Instrument Conventions=;
  =currency_pair= from
  =refdata.v1.ops.publish_currency_pair_conventions_from_dq= and dataset
  =4ac03ec8-9591-489a-bc8f-5bb8573eba6b=, named =Standard Currency Pair
  Conventions=.
- The function =ores_refdata_publish_conventions_from_dq_fn= loops an array of
  **24 kinds** and dispatches each =ores_dq_<x>_conventions_artefact_tbl= into
  =ores_refdata_<x>_conventions_tbl=. The currency pair function covers the
  25th. **25 covered, 1 uncovered.**
- **=tenor= has no DQ route at all.** There is no
  =ores_dq_tenor_conventions_artefact_tbl=, so no function can copy it. Its 4
  rows were copied from the system tenant during provisioning, and every row says
  so in its own columns: reason =system.new_record=, commentary "Copied from the
  system tenant during provisioning". This is the one real exception, and the
  table gives it its own provenance mark and says why.
- A published row records the import too: reason
  =system.external_data_import=, commentary "Imported from DQ dataset: ORE
  Instrument Conventions".

The prototype states the provenance three ways: a mark per row, a card that
names the two subjects and their datasets in full, and the importing row's own
reason code on a kind's page. It does not let a reader believe that provisioned
means authored.

**A published document is a copy, so a kind holds many**

The publish copies each curated artefact row into the party's own table: one row
in, one row out. So a kind does not hold one document, it holds every document
the dataset states. The swap kind holds 320 documents for a party, commodity
future 790, swap index 243, deposit 163. A kind's page therefore names the first
document by key and says how many the kind holds, and **the absence that matters
now is not "no document" but "no default"**: nothing records which of the 320
swap documents a run reads.


** A name is derived, because no name is stored

No convention table carries a name. One carries a description:
=ores_refdata_tenor_conventions_tbl=. Every table carries an =id= text, which is
the row's key, and =tenor= and =currency_pair= carry a =code= and a =pair_code=
instead. A key is not a name. The name and the description are therefore read
off the terms, for every kind including =tenor=, so one rule names all 26:

- An **index-based** document is named by its index, such as =AED-EIBORON=.
- A **terms-based** document is named by its calendar, its convention, its day
  count and its settlement days, such as
  =AED · ModifiedFollowing · ACT/360 · 2d=.
- The **payment frequency** joins the name where the kind states one, because
  two swap rows differ only in it.
- A kind whose table carries no calendar and no day count is named by the
  identifier terms it does carry: an FX option by its FX convention, its ATM
  type, its delta type and its switch tenor, and =tenor= by the anchor it
  measures from, its resolution algorithm and its business-day rule.
- A kind that carries a fixing index leads with it, because the index is what
  tells two of its documents apart.
- A term the row leaves empty is dropped from the name and reported beside it.

**The fields differ by kind, because the tables do.** Deposit carries
=index_based, index, calendar, convention, end_of_month, day_count_fraction,
settlement_days=; swap carries =fixed_calendar, fixed_frequency,
fixed_convention, fixed_day_count_fraction, index= and states no settlement
days; FRA carries an index and nothing else; IBOR index carries no index column
at all, so its terms cannot name the index it belongs to; FX option carries no
calendar; commodity future carries 50 term columns. A single formula cannot span
them, so the rule is stated per kind and the table names the fields it read
under each name. That is the shape the created convention will have to satisfy,
and no one has decided it.

The one description column, on =tenor=, is real and the page shows it: the row
=CREDIT_CDS_IMM= states "Credit/CDS curves: tenors resolve to the first business
day following the appropriate IMM roll date, not a fixed offset from an anchor."
The page still derives a name there, so that a reader of 26 kinds reads one
rule.

The description is the same terms said in words, from one dictionary of term
names: "The AED calendar, modified following as the business-day rule, ACT/360
as its day count, settlement 2 business days after the trade." An index-based
row reads "Fixing on AED-EIBORON. It states no calendar, convention, day count
or settlement days, so the index carries them."

** A derived name does not identify a document

ACME holds **320 swap documents stating 201 distinct sets of terms**, so two
documents carry one name: =AED-SWAP= and =AED-EIBOR-3M-SWAP= state the same
TARGET, modified following, 30/360, annual swap, and the page names the second
of them because it sorts first by key. The deposit kind holds 163 documents
stating 141 sets, and its 5 bond-yield documents state one set between them.
The row key tells them apart and the name does not, so the key sits beside every
name on a kind's page. The page says this rather than presenting a derived name
as an identity it is not, and adds the consequence a report feels: a report
cannot choose its document by name.

** The page for one kind

=?kind=<code>= opens that kind alone:

- **The document in use**, at the top: the first document of the kind by key,
  with its terms, its row key, whether the party or the tenant owns it, and the
  publish that wrote it with the row's own reason code and commentary. On
  =tenor= the card also shows the description column and says why that kind has
  one. A kind with none draws a stated *none* card and says what a run does
  instead.
- **The alternatives for that kind**, read from ACME's own table, each with its
  derived name, its description and its key. Where the kind came from a DQ
  publish the page says that each document is a copy of a curated row of that
  dataset, so a document and the row it came from state the same terms.
- **Which alternative is the default.** None is modelled, and the page says
  where a real one would have to live.
- **The create route**, which leaves the report flow.

Every kind holds many documents, so every kind's page says that the model does
not say which one a run takes: the key of the table is =(tenant_id, id, party_id)=,
so many rows per party and kind are allowed, and no column orders them. The name
the page shows is the first by key, and the page calls that a fixture choice and
not a rule.

** The default: none is modelled, and here is where it would live

The only =%default%= column anywhere is =pays_at_default_time= on
=ores_refdata_cds_conventions_tbl=, which is a CDS business term and not a
default flag. With every kind now holding many documents, this is the sharpest
gap on the screen: the table can name a document and the database holds it, and
nothing records which one a run reads. The fallback a run takes when a party
holds nothing is not recorded either.

A real default would have to live in one of two places, and the page names both:

1. a **per-kind default column** on
   =ores_refdata_<kind>_conventions_tbl=, marking one row of the party's own as
   the one a run takes;
2. a **per-kind default row keyed by tenant and kind**, in its own table, naming
   a curated document where the tenant holds none. With every kind provisioned
   this second home is less about a fallback and more about a choice among the
   party's own documents.

Neither exists, and the prototype picks neither. The default mark drawn on the
swap, deposit and CDS pages is a fixture, labelled =default · fixture= wherever
it appears, so that the states "a document matching the default" and "a document
deviating from it" can be read. The comparison that decides is over the fields
the kind names itself by.

** Three readings of the alternatives

=?variant=A|B|C= changes the alternatives block and nothing else. The document in
use, the default statement and the create route are identical across the three,
so a reader compares one block.

- **A, described list.** Every alternative with its derived name, its terms in
  words, its key, and the one in use marked.
- **B, compare.** The document in use beside a candidate, field by field, with
  the fields that differ marked, and a count of them. This is for the swap kind
  of 320 documents, where a list of 320 descriptions cannot be read.
- **C, search and filter.** A search over the derived name and the description,
  and filters for the long kinds: index-based, terms-based, marked default, and
  not the one in use. The search finds a document by a term a person would say
  aloud, and it reads nothing else: no index, no ranking, no server.

** The create route is its own screen

Authoring a convention is a different job from choosing one, so it has its own
page, reached from the table or from a kind:

- the **terms in a form**, one field per term the chosen kind's table carries,
  and the form changes with the kind;
- the **kind chosen** in the same form, because the terms depend on it;
- a **reason code**, a **commentary** and a **valid from**, which are the
  bitemporal columns of the write;
- a statement of **what it writes**: the party's own row in
  =ores_refdata_<kind>_conventions_tbl=, bitemporal, carrying =modified_by=,
  =performed_by=, =change_reason_code=, =change_commentary=, =valid_from= and
  =valid_to=;
- a statement that it **leaves the report flow**: a person arrives from a report
  and does not return to it.

**What was verified about the write, and what was not.** The subject exists on
all 26 kinds, tenor included: 26 =refdata.v1.<kind>_conventions.put= subjects
declared in =projects/ores.refdata/api/include/ores.refdata.api/messaging/=
and subscribed by 26 registrars in =projects/ores.refdata/core/src/messaging/=,
each with a handler behind it, and the deposit resource also carries a shell
command and its tests. **No run of the write is recorded here**, so the page
claims that the operation exists in shape and claims nothing about whether it
works. The prototype calls no subject.

**Four kinds are tenant-scoped, not party-scoped.**
=ores_refdata_currency_pair_conventions_tbl=,
=ores_refdata_ibor_index_conventions_tbl=,
=ores_refdata_overnight_index_conventions_tbl= and
=ores_refdata_tenor_conventions_tbl= carry **no =party_id= column**, unlike the
other 22. A row there belongs to the whole tenant, so no party owns one alone.
The table marks those rows *tenant-wide*, states the tenant's count rather than
the party's, and the create route says so on those four kinds. **The publish says
the same thing in its own report:** it reports =records_skipped 33= on the second
and later parties, which is exactly the IBOR index 10 plus the overnight index 23
it will not copy per party.

** Reachable states

The bar at the foot of the page sets the fixture:

| State | What it draws |
|-------+---------------|
| =?state=provisioned= | Every kind holds documents. The database state, and the default the page opens in. |
| =?state=none= | No document anywhere: every row reads none, and a run falls back to the curated document. Where a new party starts. A fixture, and reachable on purpose. |
| =?state=change= | The provisioned set plus one document picked as the one a report should read, and not written, on swap. A fixture. |

=?kind=<code>= opens a kind, =?variant=A|B|C= the reading, =?cand=<key>= the
candidate variant B compares, =?from=create-a-report|change-what-a-report-runs=
where the back link goes, and =?seed=<key>= starts the create form from a
document the kind already holds. Every link is a plain query string, so a reload
lands where the person was.

** What the page refuses to invent

- No default marker, because none exists. The mark drawn is a fixture.
- No name column, because none exists. The name is derived on the page, and the
  page says what it read.
- No per-kind binding in the reporting model, because the model has none. The
  binding the fixture shows is labelled as a fixture.
- No operation on the create route is called, and no claim is made that the
  write works.
- No description column, because only one kind has one. The description on
  every row is the terms, said in words; the single stored description, on
  =tenor=, is shown and labelled as what it is.
- No claim that provisioned means authored. Every row's provenance is stated,
  and the one kind no publish reaches says so.

** What is fake

The tenant, the party, the per-kind row counts and the term values are real:
they are ACME's rows in =ores_dev_bright_faraday=. The fixtures are the
configuration, the thirty-one definitions that bind it, which document of a kind
the page names as in use, which alternative is the default, and the change in
progress. The table puts the two apart: a real count sits beside a fixture mark,
and the bar says which state is drawn. Nothing reads a server and nothing is written. The page labels
itself a fixture at the top, on the bar and in each card that carries an
invented value.

** Where the code lives

=doc/prototypes/reporting/manage-the-conventions/=. Three files, plain HTML, CSS
and JavaScript, no framework, no modules, no fetch, and no build step. One
function derives a name, one renders the terms in words, and every screen reads
them, so the table, the alternatives and the create form cannot disagree about
what a document is called.

** The verdict

None yet. This page is on the branch that proposes it and waits for review.

** What it does not settle

- *Which of the three readings is right.* That is the question the variants
  exist to answer, and this note does not answer it.
- *How a reporting configuration should name a document per kind.* The current
  model does not. The page states the absence and does not pick the fix.
- *Where the default should live.* Two places are named and neither is chosen.
- *What to do about the kinds whose terms cannot name their own document*: IBOR
  index carries no index column, the 5 bond-yield documents state one set of
  terms, and four kinds have no party column. A name derived from terms is
  honest about all three and silent about the fix.
- *How a run picks one document out of 320.* Provisioning answered "does a
  party hold its conventions" and left "which one does a run read" open. 26
  kinds are bound and none is chosen.
- *Whether a person should hold a document for every one of the 26 kinds before
  a report can run.* Every kind is now bound for ACME, so the question is
  answered for this tenant and not by a service: no constraint enforces
  completeness, and a new party still starts empty.
