* Result

Both journeys run as journeys of their own, on the runtime and the step library
the first run inlines, and both were walked in a headless browser.

The *New tenant* journey runs at =/tenants/new=, and it is a route rather than
a gate: the installation is already set up, so a signed-in administrator adds a
tenant beside the ones the deployment has. The rail is the same five steps the
first run inlines, from the same library, so the two journeys cannot describe a
tenant differently; what the new journey does not carry is the administrator to
create and the first sign-in, because both already happened. Two things differ
from the first run and both come from who the person is: the browser does not
hold the signed-in administrator's password, so a starting point that hands that
password to the tenant's administrator asks for one instead, and the hand-over
is the journey's end. That walk is recorded in
=evidence/new_tenant_journey_live.txt=.

The *New party* journey runs at =/parties/new= for a tenant administrator, who
is the person this journey belongs to: the session already names the tenant, so
the five steps are find the legal entity, describe the party, review, follow the
run, and the next steps. It carries both cases the product owner states, and
they converge after the first step. A legal entity the deployment holds brings
its own legal name and its LEI, which the search reads from the deployment's own
register; a party that is not one of them is named by hand and has no LEI. The
walk is recorded in =evidence/new_party_journey_live.txt= with two screenshots,
and it goes all the way through: the run finished, the party came back /active/,
the caller is joined to it, its onboarding is complete, and *Work in it now*
re-scoped the session to it. The party the register does not hold ended in the
same place with no identifier, which is what such a party looks like.

Three things had to be built before the screens could be honest. The BFF gained
=POST /api/provision-party=, which adds the party row and starts the run, and
=POST /api/session/switch-party=, because the party a person adds during a
session is not in the list the login answered with. The progress and retry reads
became =/api/workflow/:instanceId=: they were named after the tenant, and a
party's run is the same record. And the party stage now records the legal entity
the party was built from, which the browser cannot do: a party identifier is
stamped with the party its writing session acts in, and the person adding a
party works in another one, so the run writes it with a client scoped to the
party it is provisioning. The LEI field travels on =iam.v1.parties.provision=
for the same reason.

The starting point a party stage runs from is the deployment's, and neither
client names it: the profiles are the system tenant's rows, a tenant reads only
its own, and the service that holds both is the one that chooses. The shell's
=provision party= therefore names none by default, and the browser names none at
all.

The scripted end-to-end proof, the last acceptance line, is
=projects/ores.web/scripts/verify-first-run.ts=, run with =npm run
verify:first-run=. It is not a recording of a browser: it drives the browser's
own client, its own request-building and its own password rules in the journey's
order, so an answer the browser could not parse fails the walk. It refuses to
run on a deployment that is already set up, because the first run is the one
path that cannot happen twice. On a fresh database it walked the installation
from nothing to *Ready* and every check passed, which is
=evidence/first_run_journey_scripted.txt=. Its only red mark on the first run
was the script's own: it compared the tenant administrator's login principal
against the session's account name. No product code changed for it.

The party journey also does not carry the accounts picker the prototype showed.
Nothing writes the chosen associations -- the run joins the caller alone -- and a
picker whose choices went nowhere would be worse than no picker. The journey
document records it under *What is missing*, with the placement of a party under
the tenant's own party and the parent a person does not choose.
