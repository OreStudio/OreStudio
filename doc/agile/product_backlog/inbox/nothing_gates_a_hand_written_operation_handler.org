#+title: Nothing gates a hand-written operation handler
#+description: check_handler_permissions.py compares only the four components in its registry, and only their generated messaging handlers. An operation model generates no handler, so its handler is hand-written and can ship with no permission check at all: ores.scheduler's operation handlers call has_permission zero times. The HTTP server has no route-level permission hook either, and only iam_routes checks codes.

* What

The gate that keeps a handler's permission checks honest sees only part of the
tree. =check_handler_permissions.py= scans
=projects/ores.<component>/**/messaging/*_handler.hpp|.cpp= and compares the code
a handler checks against the literals in the IAM seed SQL. It runs for the four
components in its registry — =refdata=, =analytics=, =compute=, =assets= — and the
file says why: a component whose seeds are still incomplete would fail the tree
for a gap that predates the check.

Both halves of that leave a hole, because an operation model generates no
handler. The =ores.cpp.nats-handler= and =ores.cpp.service= facets do not admit
=ores.codegen.operation=, so a component that models its surface as operations —
twenty models do, and =ores.telemetry= is entirely built that way — hand-writes
its handler. And a hand-written handler is:

- outside the registry, so the gate never reads it;
- free to check nothing, which is what =ores.scheduler='s operation handlers do:
  =job_instance_handler.hpp= and =scheduler_status_handler.hpp= call
  =has_permission= zero times;
- gated by nothing else, since the generated-handler template is what emits the
  check for entity handlers, and it emits it for writes only.

The HTTP side has the mirror of the same gap: the router has an
=auth_required()= flag and no permission hook at all, so a route authenticates and
then checks nothing. The only route file in the server that checks a code is
=iam_routes.cpp=, through a hand-written =check_auth= helper; =risk=,
=variability= and =assets= all authenticate and stop there.

* Why

Authorisation is a per-operation decision, and this is the class of handler the
gate cannot see making it. The consequence is not hypothetical: an operation
handler that mutates state can be published, reviewed and merged with no check,
and the permission seeds stay consistent with a handler that never consults them,
so the gate reports green.

It matters now because storage is about to become exactly this shape. Its surface
is an operation model — the handler cannot be generated — so its permission checks
will be hand-written, and unless =storage= joins the registry the new handler
lands ungated. The same applies to every future operation-only component, which is
the direction =ores.telemetry= and =ores.scheduler= already point.

The fix is to give the gate a way to see a hand-written handler: require an
=has_permission= call in any component in the registry that owns an operation
handler, and add components to the registry as their seeds complete. The HTTP
side needs a route-level permission declaration, so the check stops depending on
each route remembering to call a helper.

** A marketdata instance, 2026-10-04

=marketdata.v1.series.export-to-storage=, served by =market_series_handler.hpp=,
checks no code, so any authenticated caller can export its tenant's whole market
data set to object storage. =ReportingService= is its only caller. The ORE
export, =marketdata.v1.export= in =ore_export_handler.hpp=, is a different
handler and is gated: it checks =marketdata::observations:read=.
[[id:0666E3FB-11E1-4595-A430-018D2FC2A1C4][Gate and seed the marketdata permissions]]
found it while mapping the callers of marketdata handlers.
