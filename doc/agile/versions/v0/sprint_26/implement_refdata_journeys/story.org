* Decisions

- *The journey documents are the specification.* The screens build from the
  five refdata journeys; where the build proves a document wrong, the
  correction goes to the document.
- *No server work is planned.* Every operation the five screens need exists,
  and the TypeScript wire package already carries all 139 refdata protocols
  and the history protocol. The work is ores.web routes, operations and
  screens. A gap the journeys record is stated on the screen, as each document
  says, unless a task chooses to close it.
- *One history panel and one change-reason form, written once.* The first
  screen builds both over =refdata.v1.history.get= and =/api/change-reasons=,
  and every later screen reuses them.
- *New routes and menu items only.* The screens add routes and menu entries in
  =AppRoutes.tsx= and =shell/areas.ts=, and touch no page another story owns,
  so they do not clash with the access and profile work in the same files.

- *One registry of record resources is the BFF's authority.* Each screen
  reads and writes through =/api/refdata/:resource=, keyed by a name the
  registry allows; a write is checked against a schema that satisfies the
  generated write type. No screen names a subject.
- *A field table drives every record form.* Text, numbers, dates, choices,
  classification and record pickers, with conditional fields, give the form,
  the details, the revert and the write from one list per entity.
- *A screen states a server gap rather than hiding it.* Where the server
  behaves differently from the journey, as with the calendar rebuild, the
  screen says so and the journey is corrected.

* Out of scope

- Journeys 5 to 9 of the refdata catalogue (parties, books, conventions,
  tenors): they are not written yet.
- The server-side gaps the journeys record, such as delete-in-use checks and
  junction end checks; they are captured separately.
- The ORE XML export of currencies, which has no server operation.
