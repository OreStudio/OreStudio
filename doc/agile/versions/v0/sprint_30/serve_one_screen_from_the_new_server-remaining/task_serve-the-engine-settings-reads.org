* Goal

The gateway answers none of the engine settings' reads. Serve the page of
settings, one setting with its groups and their parts, and its history, at the
paths and in the shapes the BFF answers.

A configuration is a central row and three parts, one for each group of
settings. A part with no row means the engine default for every setting in it,
and a setting that is null inside a row means the engine default for that
setting. The screens can therefore always say which value is in force, and these
three reads are how they say it.

* Acceptance

- The C++ server answers =GET /api/reporting/engine-settings=,
  =GET /api/reporting/engine-settings/:id= and
  =GET /api/reporting/engine-settings/:id/history= at the BFF's paths, with the
  BFF's member names and status codes.
- The page states, for each configuration, the party's name and code, the count
  of groups that hold a part, the count of groups the data states, and the
  threads the execution part holds.
- One configuration states each group with its values, and a group with no row
  states null for every value.
- A group the data states and the wiring does not name is not offered, because
  its part cannot be read or written.
- The history states the central row's versions and every part's versions in one
  list, newest first.
- A configuration that another party owns is refused, with that party's name in
  the sentence.
- A test proves each route against the answer the BFF gives.
- Each route in scope names its C++ equivalent in the inventory.
- The local gate is green.

* Plan

Branch =feature/serve-the-engine-settings-reads=.

The three reads share an =engine_settings_rows= unit beside the documentation
route: the groups, the parts of each group, the central row, the party names and
the bound reports. That unit is what the writes task extends, so the second half
of the engine settings adds to it rather than restating it.

The counts are arithmetic over the reads. No service derives them and the
gateway derives nothing a service could state.

A part's rows travel under a subject per group, and the gateway names those
subjects. That is the wiring of the service and not the model of the screen, and
it stays beside the routes for the same reason.

The router registers =/documentation= before =/{id}=. A parameter at the end of
a pattern matches anything, so a literal that follows one is never reached
unless it is registered first.
