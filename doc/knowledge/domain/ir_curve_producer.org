#+title: The IR curve producer
#+description: How one short-rate state becomes a slice of pillar ticks, and the refdata resolution a slice needs before the first tick.

* Summary

=ores::synthetic::feed::ir_curve_feed= is the producer that turns an
=ir_curve_generation_config= into a stream of curve points on NATS. It is
declared in =ores.synthetic.api/feeds/ir_curve_feed.hpp= and implemented in
=ores.synthetic.api/src/feeds/ir_curve_feed.cpp=. It implements
=ores::marketdata::domain::IFeed=, and its =kind()= returns the string
constant =ir_curve_feed_kind=, spelled ="ir_curve"=.

* Detail

** How the feed is built

=make_ir_curve_feed= is the builder the start paths share, so the auto-start
pass and an on-demand start cannot drift.

1. It resolves the config's template entries into =ir_curve_resolved_entry=
   records through =resolve()=.
2. Under ="vintage"= it overrides the stored =initial_rate= value row with a
   real observation. The anchor is the resolved deposit entry with the
   smallest tick distance to its end, chosen by =select_vintage_anchor_entry=,
   which is a separate function so the selection is unit-testable without a
   live market data client.
3. It builds the process through
   =map_parameters_to_yield_curve_process=, passing the joined definitions and
   value rows.
4. It derives the publish subject from =source_name= and the binding mode
   through =producer_subject=.

** One process step, many ticks

=start()= runs the same fixed-mode clock the FX feed uses. The period is one
hour divided by =ticks_per_hour=, slept in slices of one hundred milliseconds
so =stop()= is observed promptly, and =stop_flag_= is left alone at the top
of the loop for the same reason recorded in the FX feed.

Each pass does this.

1. It advances the process once with =next()=. The new state is read from the
   process by the pricing step and its return value is discarded.
2. It takes one timestamp for the whole batch.
3. For every resolved entry it builds one =market_tick=, each with that same
   timestamp, and publishes it on the one subject.

** How a pillar tick is named and priced

A curve is a series, as [[id:C3E053CA-0D4B-480B-9119-E11530160EC1][oresmd: ORE Studio Market Data URI]] explains. Each entry names its own pillar. The
loop builds a quote key through =ores::marketdata::core::make_pillar_quote_key=
from the config's currency, the config's index tenor and the entry's own start
tenor code, start date and end date, then turns that key into a URI through
=pillar_datum_uri=. The key is an =IR_SWAP/RATE= quote. Its =fwd_start= is the
start of the pillar, its =tenor= is the tenor of the index the curve stands for,
and its =term= is the end of the pillar. An overnight index such as SOFR has the
tenor =1D=. A term index such as EURIBOR 6M has the tenor =6M=. The series a
point lands in therefore carries the index of the curve, and a EURIBOR 6M curve
and a EURIBOR 3M curve are two series, as [[id:6EA42D11-94F4-4D3A-9A51-024EC56EFC44][Funding and Projection Curves]] requires of a projection
curve per index tenor.

The value comes from =price_ir_curve_entry= in
=ir_curve_template_resolver.cpp=. That function reads the process's
=discount_factor()= values and dispatches on the entry's =curve_role= to the
matching =curve_instrument_pricer= formula, which is a simple rate for a
deposit, an implied forward for a forward rate agreement, and a par-rate
solve for a swap. The same function serves the curve shape preview handler,
so a preview and a run cannot disagree about what a state implies.

** Identity and conflict

The feed reports the series its pillars land in through =series_uris()=: one
series for the pillars that start at spot, and one for each later start date,
such as a meeting-dated FOMC pillar. The feed builds the list once, from its
resolved entries, through =pillar_series_uri=. Two feeds conflict when their
lists share a series, because both would write points into it. The role comes
from the config and is reported by =role()=, but it plays no part in what the
feed owns: two curves of one currency and index tenor publish the
same series, whatever their index family or role, and so cannot run together. See [[id:B4729C76-4D88-4F3C-B3D3-5FC7BD62D158][The feed and its lifecycle]] for the identity, and [[id:39057B64-8F85-4882-9B66-D2D4FC7468E4][The feed controller]] for
the controller that enforces it.

** The facts the code shape does not show

The process's own time axis is fixed and does not follow the publish cadence.
The constant =ir_curve_feed_dt= is one over three hundred and sixty five, so
one model step is one calendar day whatever =ticks_per_hour= says. The
cadence decides how often a human sees a curve and the daily step decides how
far the curve's short rate has moved. The two are independent, and the same
short-rate parameters therefore describe a much slower-looking curve at a low
cadence than at a high one.

The seed is the literal =42=, passed directly to the process builder. The
curve path has no entropy draw and no seed column, unlike the FX path, which
draws from =std::random_device= and logs the result. Two curve feeds started
with the same config and the same parameter rows therefore produce the same
sequence of states.

=publish_count()= counts batches, not ticks. One unit of the counter is one
pass of the loop and therefore one tick per resolved entry. The info-level
log line says so, spelling the counter as "batch" and printing the number of
points alongside it.
