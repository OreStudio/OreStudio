* Acceptance

- A job that waited longer than the storage token lifetime runs to success when a node takes it.
- The queue has a stated bound and a stated rule for what happens to a job that waits past it.
- A person sees how long the oldest job has waited and how many wait, per tenant for the operator.
- A restart or a recreate of the database does not leave assignments that fail on replay.

* Findings

** What happened

On 2026-10-12 a soak run queued about 1000 jobs on the grid at 00:49. The grid ran them slowly. By 09:58 every job that a node took had failed in the first step, with the same message: =GET .../api/v1/storage/ores/compute/input/....tar.gz returned HTTP 401=.

Measured on the dev database that morning:

| What | Value | How |
|------+-------+-----|
| Client errors in the last 3 hours | 4276, all with HTTP 401 | the third query below. The first query shows the same message for the last 2 hours, with the object id the only difference |
| Successes among them | 0 | the same query |
| Age of those results at failure | every one more than 4 hours, counted from the result's first version and not from its failure | the second query below |
| Oldest unsent result | 9 hours 9 minutes | the second query below |
| Messages in the assignments stream | 17,520, newest 8 hours old | =nats stream ls= |

The queries, run on the dev database on 2026-10-12 with =compass sql -- -f=. The numbers describe that database and no commit.

from ores_compute_results_tbl
where valid_to = ores_utility_infinity_timestamp_fn()
  and server_state = 5 and received_at > now() - interval '2 hours'

       count(*) filter (where r.outcome = 3) as client_error,
       count(*) filter (where r.outcome = 1) as success
from ores_compute_results_tbl r join created c on c.id = r.id
where r.valid_to = ores_utility_infinity_timestamp_fn()
  and r.server_state = 5 and r.received_at > now() - interval '3 hours'
group by 1 order by 1;

The last query puts every failure in the overflow bucket, which is a wait of more than 4 hours.

** Why it happens

Three facts combine.

1. The dispatcher publishes one assignment for each result and puts a storage token in it. The token lets the node read the package and the input and write the output. The IAM handler gives the token one hour of life (=capability_lifetime= in =storage_capability_handler.hpp=).
2. The assignments live in a JetStream stream. A node takes them in order and at its own pace. A stream keeps them for seven days, and it outlives a restart of the services and a recreate of the database.
3. A node does not check the token before it starts. It downloads the input, receives HTTP 401 and reports a client error. The server treats that as the final outcome of the result. Nothing puts the result back in the queue.

So a job that waits longer than one hour is certain to fail. A failed job takes about a second, as the wrapper log shows one failure each second on one node, so the nodes look idle while the queue drains by failing.

** What the grid will meet

The grid is shared by many tenants and its capacity is fixed. Any burst of work larger than the capacity makes a queue. A report run, a stress run or a month-end batch can queue hours of work. So waiting is the normal state of work on this grid, and the design must treat it as normal.

** Options

*** Mint the token when the node takes the job

The assignment carries no token. The node asks for one when it starts a job, for exactly that job. The token then lives one hour from the start, which is longer than any one job needs. A job can wait for any time.

- For: removes the cause. The token covers the work and not the wait. A queued job holds no credential, which is safer.
- Against: a node makes one more round trip per job. The assignment needs a new call, and the wrapper changes.
- Open: how a node proves it may ask. The node holds no standing credential today.
- Direction to check: the compute service mints the token when a node claims the job, over the node's NATS identity. The NATS client certificate proves that identity. It is one certificate for the whole wrapper role and not one for each node, so it says "a wrapper" and not "this wrapper". A node-held credential that outlives the job would bring back the standing credential that option 2 is criticised for, so the token must be minted for one job and expire with it.

*** Give the token a life as long as the longest wait

- For: no protocol change.
- Against: a long-lived token for each queued job is a standing credential, and the wait has no upper bound. It only moves the cliff.

*** Refuse an expired assignment and put the result back

The node reads the expiry from the token, and the dispatcher publishes a fresh assignment for the result.

- For: small change. It repairs the damage after the fact.
- Against: it handles the failure and leaves the cause. Each expired job costs a round trip and a republish, and a long queue republishes the whole queue every hour.

*** Publish the assignment late

The dispatcher keeps a result unsent in the database and publishes its assignment only when capacity exists, for instance when a node reports idle. The stream then holds only work that a node can take soon.

- For: the queue lives in the database, where it can be counted, ordered by priority, bounded and shown. The stream stays short, and a recreate leaves nothing behind.
- Against: a larger change. The dispatcher needs a view of the idle capacity, which the node samples and the heartbeat already hold.

** Related gaps

- The task "Do not replay a compute assignment whose result is gone" in the acme report smoke test story: a recreate of the database leaves assignments that fail on replay. A queue that lives in the database removes that case.
- The reaper puts a result back in the queue when its host goes stale. It reads only the system tenant's results today.
- The grid screens show the unsent count and no age. A person cannot tell a queue of seconds from a queue of hours.

* Decisions

None yet. The recommendation, to settle in the first task: take the credential off the queue. Mint the token when a node takes the job. Keep the queue in the database, order it by priority and age, and publish an assignment only when a node can take it. Bound the queue per tenant, so one tenant's burst cannot starve the others, and state what happens to a job that waits past the bound.

The candidate rules for a job that waits past the bound, for the first task to choose from:

- Refuse the submit, so the caller learns at once and nothing waits unseen.
- Expire the job after a stated wait, mark it so a person sees why, and let the caller submit it again.
- Shed the oldest job of the tenant with the longest queue, which keeps the newest work and loses the oldest.

Refusing at submit is the plainest and the only one that never loses work a person believes is queued.
