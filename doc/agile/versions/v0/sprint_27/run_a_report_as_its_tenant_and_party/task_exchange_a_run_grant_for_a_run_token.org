* Goal

IAM serves =iam.v1.run_grants.exchange=: a step service presents its own
token, a grant id, a run id and a tenant, and receives a five-minute run
token that acts in the grant's tenant and party with the role's permissions,
after IAM re-checks the grant and its grantor, computes the permissions and
logs the issue.

* Acceptance

- A step service in the grant's audience, holding =iam::run_grants:exchange=,
  exchanges a live grant for a run token; a caller that fails any of the five
  checks is refused with the reason that names the check.
- The token carries the grantor's account id and username, the grant's tenant,
  the grant's party as its only visible party, the computed permission codes,
  the requesting service as the actor, the grant id and the run id. It expires
  five minutes after issue and opens no session.
- The permissions are the role's permissions intersected with the grantor's
  permissions in the party now. A grantor who holds none of them makes the
  exchange answer =forbidden= with the reason =grant_lapsed=.
- Each issue appends one row to the issue log.
- IAM limits exchanges per service and per tenant, so one caller cannot
  exhaust it.

* Plan

The exchange is IAM's. It needs four things the tree does not have yet, so
the work lands in this order, each unit verifiable on its own.

1. *The claims.* Add =act=, =grant_id= and =run_id= to
   =ores::security::jwt::jwt_claims=, write them in =create_token= and read
   them in =validate= and =validate_allow_expired=. Only the run token the
   exchange issues carries them; the caller's own token does not need them.
2. *The caller's service name.* The run token's =act= and =aud= name the
   requesting service. The identity is the =<Component>Service= role the
   caller's account holds, read with =authorization_service::get_account_roles=
   from =caller_account()=. It is bound to the account and stable across
   environments, so no environment-scoped user name is stored on a grant. This
   departs from the dotted =ores.reporting.service= names in the design page,
   which have no source in a token today; the reporting audience becomes the
   three service role names.
3. *The operation.* Add =exchange_run_grant_request= /=response= to
   =ores.iam.run_grant_messages.org= and regenerate the protocol. Seed
   =iam::run_grants:exchange= and assign it to =ReportingService=,
   =OreService= and =ComputeService=.
4. *The service.* =run_grant_operations_service::exchange_run_grant= makes
   the five checks in order, computes the role's permissions intersected with
   the grantor's, mints the token with the claims the design page lists,
   appends the issue-log row and answers.
5. *The issue log.* A new insert-only table modelled on
   =ores_iam_auth_events_tbl=, carrying the grant, the run, the service, the
   tenant, the party and the outcome, with its entity and repository.
6. *The limits.* An in-memory token bucket per key, in
   =ores.service/service/rate_limiter.hpp= beside =request_context.hpp=, with
   the clock injected as =partition_token_cache= injects its own. A refusal
   carries the time to the next token, so the caller backs off by exactly that
   much; the backoff itself stays in =ores.nats/service/retry.hpp=. IAM keeps
   one limiter for the calling service and one for the tenant, and answers a
   refusal as =unavailable=.

The step service's cache is the next task
([[id:FAAE99F3-0C98-4265-BFD6-4BD8A052B2F2][Cache run tokens in the step
services]]), so the exchange answers a token and the cache is not built here.
The deferred grant moments — a manual run's grant, the suspension on
=grant_lapsed=, the revoke on delete and the re-grant on a party change —
belong to this operation's callers; this task builds the exchange they call.

* Notes

- Hold until the worktree clever dijkstra lands its story "Read each tenant's
  cache partition inside its tenant", branch
  =feature/read-each-tenant-cache-partition-inside-its-tenant=. It adds IAM's
  in-process Token Exchange with delegation semantics, the =act= claim, the issue
  log and a generic =partition_token_cache= in =ores.eventing=. Build on those
  rather than a second set.

- The exchange must check that the grant's resource names the run's definition,
  =reporting.report_definition/<id>=. The definition's =run_grant_id= is a
  generated column a person can set through the generic report definition
  write, so the exchange, not the column, must tie a grant to its definition.
- Moments deferred here from the schedule task, because each needs the
  exchange or a person's token where reporting has none: a one-run grant for a
  manual trigger; suspending a definition when an exchange answers
  =grant_lapsed=; revoking a definition's grant when it is deleted; and a new
  grant when its party changes.
- Reconciliation schedules every unscheduled definition at service start as
  the service account, so its jobs carry no grant. Once runs exchange a grant,
  decide whether reconciliation re-creates jobs only for definitions that hold
  an active grant, and leaves the rest unscheduled.
