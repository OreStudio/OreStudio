* Goal

A person who provisions a tenant should not be told it is ready while its setup is still running. The provisioning run records the id of the run it creates, so the shell should follow that child run to completion before it reports success.

* Acceptance

- run_and_follow reads the last completed step's child_instance_id and follows the child run when this session can read that run's tenant
- bootstrap setup, and a provision tenant run from the system tenant, print the tenant ready only after the child run completed
- a child run in another tenant is reported, naming its instance id, and the command exits successfully without claiming the tenant is ready
- an unreadable step result fails the command; a readable result that names no child is no handoff
- the wait counts every step the instance planned, so a run is never called finished while a step it owes is missing
- the transient 'Workflow instance not found' first-poll warning is not printed as a warning
- proven by live runs as super_admin (bootstrap setup) and as tenant_admin@acme_corporation (provision tenant) on a recreated database

* Notes

The review finding about the child's tenant was confirmed live before
the fix: signed in as =tenant_admin@acme_corporation=, =workflow wait
<child instance>= printed =Workflow instance not found.= five times and
aborted with exit code 1, while the same id read as =super_admin=
reached four completed steps. That child was the one the
=empty_operational= starting point creates, which has four steps. A
child the =acme_demo= starting point creates has nine. The child run
belongs to the tenant that was created, so only the system tenant may
read it.

The wait's step count was also wrong: the engine creates a step row
when it dispatches the step, so a poll can see every visible step
complete while a later step does not exist yet. A live run declared
=✓ All 1 step(s) completed= for a two-step run and returned while the
tenant's setup was still running. The wait now counts the instance's
=step_count=.

* Result

The shell follows the run a provisioning run hands its work to when the
session can read that run. A tenant administrator's session cannot read
a run in the tenant being created, so the command names that run and
says the setup continues there, and exits successfully. bootstrap setup
runs as the system tenant and follows the acme_demo child through all
nine of its steps before it reports the tenant ready. A handoff that
names no tenant, or names something that is not a tenant id, is not
followed, and a run whose own status says completed is not waited on for
step rows the session may not read. Proven live on a recreated database
as both super_admin and tenant_admin@acme_corporation.
