* Result

*Decision: no coordinate columns. The bullet is met in the service tier, and the story
now says so.*

*What the bullet asks.* A node's coordinate tuple is queryable and joinable, not only
text inside an identity string.

*What is true.* A coordinate is a typed field of the point's URI. The codec parses it
once. =coordinate_of= reads it as a typed value, the write refuses a point whose
coordinate is not a value of the declared shape, and the shared grid places the point
at its node. A caller queries by coordinate through the typed reads: the slice read
names an axis and a component, and the evolution read names the object. The coordinate
joins to the declared shape by value, in the service. SQL cannot query it, because the
column set was removed on purpose when the URI became the only identity.

*Why no column.* No journey asks for points across series by coordinate. The one
journey that matches by coordinate does so in the client, over a candidate and its
quotes. A column would reverse a decision the component made, and it would add one
facet's coordinate to a generic time-series table. It would also give two identities
that can disagree, the cost the URI decision exists to avoid.

*What would reopen it.* A journey that needs a query across series by coordinate, for
example every five-year point of every curve. The earlier decision already names the
form: an index on a derived projection of the URI's parts, not a new table and not a
column on the points.

*Effect on the story.* The acceptance bullet is reworded to say how it is met. With the
recipe on a point's provenance done, every bullet is met and the story closes.
