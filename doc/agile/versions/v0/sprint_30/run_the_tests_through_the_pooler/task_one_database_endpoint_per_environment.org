This page documents a [[id:31C868B9-306E-4282-BA8C-07E647021B34][task]] in the [[id:CF800DC8-A36D-4DBA-B819-C98B409CD9F7][Run the tests through the pooler]] story. It captures the goal, current status, acceptance, and any notes or results.

* Goal

Every environment states one database endpoint, and no client derives anything
from the pooler. =ORES_<SVC>_SERVICE_DB_PORT= carries the endpoint:

- with no pooler, it is the port PostgreSQL listens on;
- with a pooler, it is the port the pooler listens on, and the pooler keeps
  PostgreSQL's port as its upstream.

That is one derived value, not a mode each consumer tests. A service, a test
and =ores.database='s =database_options= read the endpoint and stay ignorant of
what answers it.

** The two facts, and which one has no owner

The deployment holds two facts about the database: where PostgreSQL listens,
and where clients dial. They coincide when no pooler is in front. When one is,
the second is the pooler's port and the pooler forwards to the first. Only the
code that wires the deployment needs both; everyone else needs the endpoint.
=database_options= already models exactly that: one =port=, no pooler concept
(=projects/ores.database/include/ores.database/domain/database_options.hpp=).

Today four actors hold the first fact and disagree:

| Actor | Where it comes from | Value |
|-------+---------------------+-------|
| Service configuration and the as-service suites | =.env= =ORES_<SVC>_SERVICE_DB_PORT= | 20007 in a fresh CI environment |
| CI's PostgreSQL | =build/scripts/start_ci_postgres.sh=, the cluster default | 5432 |
| Test helpers | =PGHOST=/=PGPORT= | 5432 |
| The pooler | =build/scripts/start_ci_pooler.sh=, upstream from =PGPORT= | 6432 listening, 5432 upstream |

The fresh CI environment is generated in the pooler-on shape — the story's
*Goal* names base + 7 as the pooler's port, 20007 on a base of 20000 — but CI
runs no pooler for most suites. The as-service suites read 20007 and connect to
nothing; the other 105 suites pass because their helper reads =PGPORT=, 5432.
Nothing in the pooler is at fault: it already derives its upstream from
=PGPORT=, which is the rule this task wants everywhere.

** The rule

  endpoint = ORES_DB_POOLER_PORT when a pooler is declared, else the port PostgreSQL listens on

The environment declares it once, where the topology is known, and every client
reads the result. The only readers of the pooler keys stay in the deploy and
systemd code:

- =systemd_generate.py:597= renders the unit only when =ORES_DB_POOLER_PORT= is
  set and not =0=; =:1074= also requires =ORES_DB_POOLER_ENABLED=1=;
- =env_deploy.py:532= reads the flag to decide whether the remote host gets the
  pooler's configuration;
- =env_deploy.py:585= passes the remote =PGPORT= to the pooler's upstream.

** What CI does not prove today

CI has the pooler off for most suites and starts one only around the database
suite, which is the coverage this task keeps. The bug is the fallback: a
pooler-off environment must name PostgreSQL's port, and it names the pooler's.

* Acceptance

- With =ORES_DB_POOLER_ENABLED=0, every =ORES_<SVC>_SERVICE_DB_PORT= in a
  generated =.env= equals the port PostgreSQL listens on for that environment;
  with it =1=, every one equals =ORES_DB_POOLER_PORT= and the pooler's upstream
  stays on the PostgreSQL port.
- The continuous CI run passes =ores.refdata.core.tests=,
  =ores.inbox.core.tests= and =ores.workflow.core.tests= with the pooler off,
  and still passes the database suite through the pooler that
  =start_ci_pooler.sh= starts, so both cases stay covered.
- No C++, CMake or test file reads =ORES_DB_POOLER_ENABLED= or
  =ORES_DB_POOLER_PORT=; the readers stay in =systemd_generate.py= and
  =env_deploy.py=.
- A gate step fails when an environment's service database port is neither the
  PostgreSQL port nor the declared pooler port, so an =.env= cannot name a port
  nothing listens on again.

* Plan

Work started on 2026-11-23 and the first finding changed the size of the task:
=.compass/checks/env_format.org= already states the rule. Line 214 gives every
service ={ORES_DB_POOLER_PORT}= when =ORES_DB_POOLER_ENABLED= is 1, and line
215 gives it ={PGPORT:-5432}= when it is not; lines 216 and 217 write the
listener variables only in the pooled case. So generation derives one endpoint
and the services stay ignorant of the pooler. What no one could do was *state*
the topology: =compass env configure= had no flag for it, so every environment
took the format's default, which is a pooler, and CI generated a pooler's port
on a machine that runs none.

Three steps, in order:

1. Teach =compass env configure= the fact: =--pooler= and =--no-pooler= become
   =--var ORES_DB_POOLER_ENABLED=1/0=. One helper, =env_init._declared_vars=,
   assembles the =--var= pairs, so the new declaration sits beside the two
   that were already there (=ORES_COMPILER_CACHE=, =ORES_USE_BUSCTL=).
2. Tell each workflow the truth about its machine: the five that configure an
   environment pass =--no-pooler=, because each starts PostgreSQL directly and
   none of them runs a pooler. The pooled database step keeps its own port, so
   CI still covers both cases.
3. Prove both shapes on the pinned generator, and unit-test the declaration.

No C++, CMake or test code changed: =database_options= already carries one
port, which is the shape the rule wants.

  =ores.workflow.core.tests=. The other 105 suites passed in the same run.

  =compass env generate= writes today: base 21800, no =ORES_DB_POOLER_*= key,
  every =ORES_<SVC>_SERVICE_DB_PORT= at 5432. clever_dijkstra's pooler port is
  21607, per the story's *Goal*.
- =db_port= has no single owner. =env_init.py:530= forwards
  =ORES_DB_PORT= when =.env= already has it and passes nothing when it does

  This turned out not to matter: the choice is not arbitrary, it follows
  =ORES_DB_POOLER_ENABLED=, and that is what the task made declarable.

  =.compass/checks/env_format.org= line 209 (=kept=, default =1=) and CI never

* Result

=--no-pooler= makes the environment state the machine it runs on. On the CI
runners every service database port is now 5432, the port
=start_ci_postgres.sh= starts, so the three as-service suites connect to a
server that exists. The pooled step is untouched and still runs the database
suite through 6432, so CI covers both topologies.

| Change | Where |
|--------+-------|
| =--pooler= and =--no-pooler= on =compass env configure=, through one =--var= helper | =projects/ores.compass/src/env_init.py= |
| Four tests, including the one account that holds two roles | =projects/ores.compass/tests/test_env_init.py= |
| =--no-pooler= in the five workflows that configure an environment | =.github/workflows/continuous-linux.yml=, =nightly-linux.yml=, =nightly-macos.yml=, =nightly-windows.yml=, =site-cdash.yml= |
| =role= read as the comma-separated =roles= the seeder writes | =projects/ores.compass/src/compass_open_as.py= |

The environment format did not change: =compass/checks/env_format.org= already
derived the endpoint, so no pin bump and no format version followed. Still
open, and owned by the sibling task, is a run-time check that a declared
endpoint has a listener: a pooler that is declared and not started still shows
up as a connection refusal instead of a message that names the fix.
