* Goal

Every analytics entity renders a protocol header from its org model, and no analytics message renders as TypeScript. Bind the analytics models to the TypeScript protocol and domain facets and extend the projection until it renders, so an analytics message exists in both targets or not at all. A check proves the two targets stay in step, and the generated tree regenerates with no diff.

* Decisions

- *The analytics entities are drift-free at =origin/main=.*
  =check_component_drift.py --component analytics-cpp= regenerates the whole
  component and reports no drift, so the generated C++ protocols are a stable
  input to project from.
- *The binding mechanism is in place; the protocol facet is not.*
  =compass codegen regenerate --component analytics-cpp --address ores.ts
  --dry-run= writes four =generated/analytics/ui/*_ui.ts= modules and no
  protocol module. =ores.ts.ui= declares
  =model_types: domain_entity junction=, so an entity model binds to it today.
  =ores.ts.protocol= declares =model_types: operation= alone, so no entity
  model can reach it, whatever =:ores.*.enabled:= override the model carries.
- *TypeScript has no domain layer.* Every analytics protocol response carries a
  =std::vector<ores::analytics::domain::<entity>>= member, and
  =org_loader._ts_type= projects only =std::string=, =bool=, =int= and
  =std::uint64_t=. The entity interface must exist before the protocol
  interfaces can reference it.
- *The entity projection is shared with the IAM story.* The re-cut of
  [[id:18F49E14-F89E-4E01-B4B7-33928F3B094A][Generate every protocol message as TypeScript]] reaches the same conclusion:
  the facet needs generalising and the domain layer needs adding. Analytics is
  the smaller proof of that path, so this story carries the generalisation and
  the IAM story rebases onto it.

* Out of scope

- The other drift-free components. This story covers analytics alone.
- The C++ output. Every analytics C++ file must come out byte-identical, which
  the drift check proves.
- The hand-written protocols in other components. Analytics has none, so
  nothing needs porting to the operation model first.
