#+title: ores.trading.credit_instrument
#+description: Codegen entity model for the trading =credit_instruments= table. Drives the C++ domain class, mapper, repository, service, generator, and SQL schema generation from a single literate source.
#+type: ores.codegen.entity
#+component: trading

#+brief: The credit family header: one row per credit trade, keyed by trade_id, owning the family's facts, legs and basket.
#+entity_singular: credit_instrument
#+entity_plural: credit_instruments
#+entity_title: Credit Instrument
#+created: 2026-09-27
#+updated: 2026-10-12

One row per credit trade, the family's own header. It holds what every
product in the family states the same way: the trade it belongs to, the trade
type code, the party, the activity that wrote the version, the reference
entity, the instrument's start and maturity dates and its description. It
holds no product economics.

The header is the family's *coverage*: the =trade_type_code= check that the
routed-instrument template generates from =ores.trading.trade_type_catalogue=
lists exactly the six codes the importer writes, and the two codes with no
importer, CreditDefaultSwapOption and CBO, stay out until a mapper writes them.
It is also the family's *owner*: the delete cascade section below names every
table the family writes, so the delete rule closes the legs, the basket and
the facts with the header and the family does not outlive it.

The products' own fields stay in their fact tables, keyed by the same trade
and joined to this row by the trade id. A fact table carries no =party_id= and
no =trade_type_code=: the header is the family's party boundary and its
routing boundary.

The dates are the family's *common dates*, the one set of names for the start
and the maturity of every credit product. A risk participation agreement's
protection start and end are those dates.

** reference_entity_id_type
:PROPERTIES:
:type:     text
:cpp_type: std::string
:nullable: false
:economic: true
:END:

What kind of identifier =reference_entity_id= states: the legal entity's LEI,
or an identifier the system's own data uses.

A reference is typed rather than guessed, because a credit curve named =ACME=
in an engine document and an LEI are different things and a column that holds
either without saying which cannot be joined to anything.

The closed set is LEI and Internal. It is a check on this column rather than a
catalogue table, because the two kinds of identifier are a property of how a
reference is stated and not a list the tenant curates.

** reference_entity_id
:PROPERTIES:
:type:     text
:cpp_type: std::string
:nullable: false
:economic: true
:END:

The identifier of the reference entity the risk is on, read with
=reference_entity_id_type=.

Every credit product states one. When the type is LEI the value is the legal
entity's LEI and the soft reference below applies; when it is Internal the
value is the identifier the source states, such as an engine document's credit
curve or issuer id, and nothing is claimed about a legal entity.

Soft FK to the DQ lei_entity dataset when the type is LEI: the entity belongs
to that dataset rather than to a trading table, so the reference is recorded
rather than copied. A later change tightens it into a real foreign key once a
legal entity lives in refdata.

Resolving an internal identifier into an LEI replaces both this value and its
type together, so a trade states one identifier and never two.

The rows a credit instrument owns. Each is keyed by the instrument's own trade
id, so the delete rule closes them all with one statement per table and the
family does not outlive its header.

The legs, the strikes and the schedules are the shared shapes the bond pilot
and the rates family built; the credit family writes to them rather than
widening them.

** Pinned keys

The header copies the anchor's party and trade type, so the insert trigger
checks the copies against the anchor's current row and refuses a row that
disagrees. The anchor is a versioned table, so a database foreign key cannot
name it and the pin is a trigger check, as the =trade_id= key is. The fact and
child tables carry neither column: they reach both through this row (design
decision D3), so the header is the only row of the family that can disagree.

The insert trigger stamps =party_id= from the session, and row-level
security hides another party's anchor, so in practice the pin refuses a
disagreeing =trade_type_code=; the party column is held to the anchor as
well, so a path that bypasses the stamp cannot drift from it.

The anchor's model states that its party and trade type are fixed for the
trade's life and that a change is a cancel and rebook. The anchor's write
path does not enforce it, so an amendment that changed the trade type would
leave the header unchecked. That gap belongs to the trade model, not to this
family, and it is open.

| name   | columns                           | table                  | target_columns            | error_message                                                          |
|--------+-----------------------------------+------------------------+---------------------------+------------------------------------------------------------------------|
| anchor | trade_id, party_id, trade_type_code | ores_trading_trades_tbl | id, party_id, trade_type | Invalid trade_id: %. The party and trade type must be the trade's own. |

The tenant isolation and the party isolation policies are hand-written in
=trading_rls_policies_create.sql=, as =bond_instruments=' are: the header
carries =party_id=, so it needs the restrictive party policy beside the
tenant policy, and the generated =:rls_tenant_isolation:= form states the
tenant policy alone.

* C++

The C++ domain class nests the scaffolding columns and the columns marked
=:group: identity= below into an =instrument_identity identity;= member
(see the ores.trading.instrument_identity field-group model), the implicit
audit columns fold into an =ores::dq::domain::audit_record audit;= member
(see the ores.dq.audit_record field-group model), and the dates and the
description stay flat in between. The SQL schema, DB entity and column
lists are unaffected. The entity templates consume these annotations;
domain and repository profiles regenerate correctly.
