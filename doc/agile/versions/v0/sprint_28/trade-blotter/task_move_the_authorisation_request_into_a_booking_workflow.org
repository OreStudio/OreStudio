* Notes

** Why this task exists

Task 1 raises the request inside the trading transaction. That writes five inbox tables from the trading service. The page [[id:B2D74E96-0353-4A3D-8CE5-3FC3C30D864C][Data classifications]] says one owner holds a bundle and no transaction spans two owners. A set that crosses owners runs as steps in the workflow engine. Each step is atomic in its own owner.

Task 1 chose the in-transaction raise so that a live actual trade never exists without a request. A workflow keeps that guarantee by retry and resume, and it shows the gap as the status request pending.

** The steps

1. Book. Trading writes the trade, activity, booking and state in one =unit_of_work=. This is the existing =book_trade=, and it stays the bundle B7 of the bundle catalogue.
2. Raise. The inbox creates the approval request. Trading then writes the detail row. The step is idempotent on the trade id and version, per [[id:183361A9-31B8-4066-A13D-94CA35270F42][Idempotency in a workflow step]].
3. Announce. Operations is told.

The model to follow is =book_apply_workflow= in refdata: a definition with steps, each with a deadline, and the policy stop, so a failure leaves the run stopped for the engine's retry verb.

** Findings that shape the work

- Two bulk callers book actual trades and so now raise one request each: the synthetic population writer (=trading_trade_population_writer.cpp=, line 384) and the ORE import outside a sandbox (=ore_import_execute_handler.cpp=, line 619). One workflow run for each trade is too heavy for a seeded book of thousands. This task must batch them or raise on purpose. Task 1 did not measure this.
- Not yet checked: how long a run takes, and whether an interactive booking can wait on one.
