* Acceptance

- Each of the five signed-off prototypes has a screen, and each draws what its design note records.
- The coverage operation, the per-dataset preview, the artefact read and write, and the published-row count exist, or the screen states which is absent.
- A person who has never seen the Qt client completes every journey on a fresh database.

* Plan

1. Serve the reads the screens need from both deployments, as
   [[id:43B17B69-D1CA-4333-98BF-462AA5ECD8EF][Serve the DQ reads from both the C++ server and the BFF]]
   does: one web API module through =baseFor('dq')=, and the same paths on
   =ores.http= and on the BFF.
2. Build the operations the journeys read: the coverage operation over the three
   discovery functions, the per-dataset preview, and the published-row count.
3. Build the artefact read and write, without which the correction cannot start.
4. Build the five screens from the shared parts, in the order the journeys
   imply: coverage, publish a dataset, publish a bundle, correct one artefact,
   trace a published value.
5. Prove each journey on a fresh database, as the story's last acceptance asks.

Notes

- The prototypes are the design record: =doc/prototypes/dq/=, one folder per
  screen, each with a design note that states its states and what is fake.
- The journeys are =doc/knowledge/journeys/dq/=, and each one's * What is
  missing section names the operation that blocks it.
- The used-by question in the trace journey needs the reference to be an
  identifier or the text to be indexed, which is a trading component change and
  not a DQ screen.
