This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A tenant administrator picks an instrument family, chooses or creates its convention, authors its terms, and reviews and saves them.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want the terms ORE uses for one instrument to be the terms we actually trade
them on, so that a trade I book and a curve I bootstrap read the same
convention." The journey is done when the convention is saved, and its history
shows what changed and why.

* Actor and trigger

The actor is the person who maintains the tenant's reference data: an account
holding the =Operations= role, or a tenant administrator, acting inside their own
tenant. The trigger is a new instrument the tenant wants to trade, a term that has
moved (a fixing calendar, a day count, an index), or a curve whose bootstrap
reads the wrong convention. The journey starts at *Conventions*, or at a link
beside a convention picker on a curve or a trade, and ends when the person
leaves the convention.

A convention is a lookup that other records point at, so the person starts from
the instrument they want to trade, not from the entity name. The instrument
family decides which convention entity serves it.

The journey keeps no server state. No step waits on the server after its reply.

* Steps

The journey has six steps, one per screen. The rail shows them in this order.
The history is not a seventh step: it is the Terms step's own record view, and a
step marked final cannot be returned past.

1. *Choose the instrument.* The person opens *Conventions*. The system shows the
   convention families this tenant actually keeps, each as a card: the family
   name, one line on what instrument it serves, the whole convention entity it
   resolves to, and how many conventions it already holds. A filter narrows the
   list by family name, entity or description. The person picks a family, or
   arrives with one already chosen from a picker's link. A family with no
   convention yet opens the terms step with an empty form.
2. *Choose the convention.* The system lists the chosen family's convention
   rows: the id, a one-line summary of its terms, who modified it, when, and its
   version. The person searches by id, opens a row to edit it, or chooses *New
   <family> convention*. The search field says on screen that the filter takes
   =id_one_of= only, so it filters by id and not by a term. See /What is
   missing/.
3. *Author its terms.* The system shows every field the convention model
   carries, grouped by the leg or the part of the schedule it belongs to. Each
   field carries a badge: *from the list* when the value is a pick from another
   refdata list, and *free text* when this convention is the only place the
   value lives. The stored value is the list's code, never its label. The person
   changes the terms, or leaves the values a new convention starts from. A term
   that is a pick is not edited here: the screen links to the list that owns it.
   For the swap convention the screen groups the columns into a fixed leg and a
   floating leg, and says on screen that the grouping is the screen's, not the
   row's: the model carries no leg objects. The person opens *History* from this
   step to see the versions. The system writes nothing on this step.
4. *Review.* The system shows what will change: the convention's fields in the
   model's own order, grouped as in step 3, and a count of the fields that
   differ from the version it read. The person confirms. Nothing is written
   until they do.
5. *Save.* The person saves. The system writes the record with one request,
   =refdata.v1.<plural>.put=, carrying the change, the precondition and the
   intent. It creates with =must_not_exist= and changes with
   =must_match_version=, so a duplicate create or a concurrent edit is refused
   instead of overwritten.
6. *See the result.* The system reports that the convention is saved, with its
   new version, and says that a trade that picks this family reads these terms.
   The person can open the history, return to the list, or start again from
   another instrument.

*Refused* is a screen of its own, not a step of the walk. It holds no rail
place, because the person does not walk to it. The system shows what was
refused, that the record keeps its version and was not changed, the step that
raised it, and the way back to that step.

*History* is the Terms step's own view. The system shows every saved version
with the field-level difference from the one before, and the person can switch
version or hide the diff. A revert is not a history operation: it reads the old
version and writes its values as a new version, through the same =put= with a
new change reason.

* Four-eyes controls

A change that touches data other functions rely on needs a second person, and the
person who asks cannot decide. [[id:C5846977-529F-4E36-A9DB-EA48A7476E6F][Book types and the controls on each]] records the rule for each act of this
journey:

- A new convention, and any change to its terms: *Market Risk* decides, because a trade, a curve or a report reads these terms.

Review marks each change as needing a named function or no approval. When any
change is gated, the confirm becomes *Raise request*: the system raises one
approval request (=inbox.v1.ops.raise_approval=), shows it waiting, and leaves the
record as it was. A decider from the named function opens the request with
=inbox.v1.ops.get_approval=, reads what would change and the check, and approves or
declines with a comment (=inbox.v1.ops.decide_approval=). The request applies only when
every named function has approved, and one decline ends it. The prototype draws the
waiting, decide and declined states (=?state=waiting=, =?state=decide=, =?state=declined=); the check it draws is that every term names a value its list still holds, which =?check=lookup= makes fail.

The approval operations exist. No request kind is seeded for these acts, a request
holds no pending change, and nothing applies the change when the last decider
approves, so a screen cannot yet raise or apply a gated change. The deferred
[[id:C6D6A0C2-1A62-4C52-8DED-D431E410E89F][four-eyes authorisation framework]] is that missing piece. The deciders are Operations,
Finance and Market Risk, and the Acme dataset holds no Finance account; the task
[[id:C37EA3F0-1A82-4E42-A21B-599C6873191A][Add the missing book-control actors to Acme]] adds it.

The journey is one screen: a flat step rail on the left and the current step on
the right. The instrument family and the chosen convention stay in the header
while the person walks the steps.

The terms step is drawn in full for two families only, the *swap* convention and
the *deposit* convention. The swap convention is the worked example, because it
carries both a fixed leg and a floating leg and every field is also a pick. The
deposit convention is the simpler contrast: eight columns, most of them
optional, and every field inherited from the index when =index_based= is set.

The other 23 families are named on the picker and their rows are listed, but
their terms step is *not* drawn here and not drawn in the prototype. Each one
resolves to its own entity, and the picker says so on the card rather than
inventing a form.

The current status of every =put= is =partial= for one reason: the refusal the
journey must handle is drawn on screen but the server cannot produce it. The
generated =result= carries a =fields= vector and the assets and IAM services
fill it, but no generated refdata convention service does. A refused write
therefore arrives as a plain error with a code and a message, and the screen has
to name the offending field itself. See /What is missing/.

* What is missing

1. *The convention list cannot be searched by a term.* The filter a generated
   =list= accepts is =id_one_of= and nothing else, so the search field filters
   the page the client already holds and cannot reach a convention by an index,
   a calendar or a day count. The candidate is a term filter on the convention
   lists. Until it exists the screen says on the field that the filter takes
   =id_one_of= only, and loads the list in pages the client filters.
2. *The history has no draft version.* =refdata.v1.history.get= returns saved
   versions only. The prototype draws a *now* version that holds the values
   before the write, and says on screen that the server has no draft version, so
   a real screen shows *now* only after the write. Until a draft exists the
   history view is a post-write view.
3. *The refusal carries no field-level record.* The one refusal this journey
   must handle is a term that references a value the list no longer holds, and
   it is drawn as its own screen. But the generated =result= is a plain error:
   the =fields= vector exists in the shared protocol and the assets and IAM
   services fill it, and no generated refdata convention service does. The
   server therefore cannot name the field it refused, and the screen has to
   match the code and the message itself. The candidate is for the generated
   refdata services to report a =field_failure= per refused field. Until then
   the screen shows the plain error, as the prototype draws it.
4. *The family-to-entity mapping is the client's.* The server carries one list
   per convention entity, so nothing lets a client ask "which convention serves
   this instrument family". The mapping is the screen's. The candidate is a
   refdata list that names the family and the entity it resolves to, so the
   journey and any other client agree. The journey already writes the mapping
   out in full, in the table under /Choose the instrument/, so the rows a
   server-side list would carry are known and only the list is missing. Until
   then it is authored once, in the application.
5. *No convention field validates its term.* A convention's term columns are
   plain text, and the models declare no foreign key and no lookup check on
   them. The server therefore stores any text, and a term that references a
   value the list no longer holds is written rather than refused. The candidate
   is the same existence check the other refdata writes make. Until then the
   refusal in /Steps/ describes a check the server does not make, and the screen
   offers only codes it has read from the lists.

The tenant-administrator item this section used to carry is closed. =Operations=
now holds every convention family and the term lists their pickers read, so the
screen is reachable by the people who run reference data and not only by a tenant
administrator.

The sub-periods coupon type list this section used to carry is built:
=refdata.v1.sub_periods_coupon_types.list= exists, seeded with the two values
the swap and tenor basis swap models' own column descriptions name, so the pick
is a pick and not free text.

** The workspace note does not apply

The agreed catalogue expected this journey to wait on the workspace removal,
because the instrument conventions then bound the =workspace-scoped-lookup=
profile and a convention set would be curated per trading desk. That is stale.
Commit =d0de221445= ("Drop the workspace column from every entity") dropped the
=workspace= column, no refdata entity binds that profile, and no =workspace=
reference is left in the refdata models. All 25 conventions bind
=simple-lookup=. A convention is tenant-wide, there is no desk step to draw, and
this journey waits on nothing.
