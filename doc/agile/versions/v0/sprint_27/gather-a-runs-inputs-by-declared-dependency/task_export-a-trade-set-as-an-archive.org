* Goal

=trading.v1.ops.export_trades_to_storage= takes book ids and no date, pages
=trade_export_service::export_books=, and stores one blob for all of them: the
=export_portfolio_response=, holding the trades and their instrument batch.
[[id:3653CE61-84B8-4B77-9BBA-8D718A4B2F93][Carry the export's instruments as typed batches]] removed the opaque
=instrument_payload=, so the batch is typed and the ORE mapper can be driven
from it — which is how a run maps its portfolio today.

What the export cannot do is answer for one set. It names books and no as-of, so
one object answers for every book in the report and for whatever the database
holds now.

Export **one trade set at a time, by its batch key**, and source everything the
portfolio needs — trade headers, instruments and envelopes — into a zip whose
shape is declared. The as-of travels on the set, so the request does not
restate it.

* Acceptance

- The request names a trade set's batch key, and the as-of comes from the set.
- The archive holds everything the ORE portfolio mapper needs: each trade's
  anchor, its instrument typed and keyed by the trade id, and its envelope
  (counterparty, netting set, portfolios, additional fields).
- The archive's shape is declared — the set of members, their names, their
  encodings, and a manifest to check them against — so a reader validates
  before it maps.
- The archive is named by the batch key, so the package step can tell which
  sets have arrived and which are missing.

* Plan

*One archive per trade set, with members split by instrument type.* The trade
set is the unit the run fans out over and the unit the package counts, so the
archive is per set. Inside it, a manifest plus one member per instrument type
(and one for the headers and envelopes) is the shape that lets the mapper
stream type by type, lets a new instrument family arrive without touching the
others, and localises a mapping failure to a type rather than to a set.

The alternative — a separate archive per set per instrument type — multiplies
the object count by the number of types and makes the fan-in set's size vary
with each set's contents, which is the thing the waiting logic least wants.
This is a decision to confirm when the shape is drawn: it is recorded here
because it is the question, not because it is closed.

*Where the as-of comes from.* It is on the trade set, and every market and
trade table is bitemporal, so reading it is a =valid_at= read rather than new
machinery. Nothing in this path needs a date parameter.

*What the encoding is.* The members stay in an encoding this tree can read
without a new parser; the point of the change is the shape and the completeness
of the data, not the container's format. The manifest is what makes the shape
declared rather than inferred.
