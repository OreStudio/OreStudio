* Goal

Trade generation is a *building block*, not a seeding script. The service
receives a request carrying a configuration, generates against it, and persists
the result. Everything else is a composition of that block.

Three compositions are in view, and only the first is needed now.

Populating a provisioned system sends the request once, with a configuration
naming the size. A periodic synthetic trade feed sends the same request on a
schedule. Amending an existing population sends it in an update mode. None of
these is a separate mechanism; they differ in who sends the request and what the
configuration says.

The four sizes follow from this rather than sitting beside it. Tiny, medium,
large and extra large are named configurations of the same block, so a tiny
population is realistic because its configuration describes a small firm's book
and not because a large one was truncated.

The pattern is already established. [[id:DC252F72-1BB0-4CC8-B558-C191FFA5E826][ores.synthetic]] handles
=generate_organisation= on =synthetic.v1.organisation.generate=, and carries
feed configurations alongside per-asset-class generation configurations such as
[[id:8771702C-0BC4-4955-8D7E-DDBE2497D5B3][market data generation config]]. A trade generation configuration is the missing
sibling, and the work is to add one rather than to invent a mechanism.

The service boundary follows the same shape. =ores.synthetic= owns what to
generate and how: the configurations, the algorithms, the seed. It does not own
trades. Persisting them is =ores.trading='s work, reached downstream, so
generation gains no second path into the trade tables and the rules that govern
a trade stay in one place.

* Acceptance

- Trade generation is reachable as a request =ores.synthetic= handles, carrying
  a configuration rather than hard-coded parameters. The configuration names at
  least the book, the seed, the instrument mix and the counts.
- The configuration is a persisted entity, following the generation
  configurations =ores.synthetic= already carries, so a population can be
  reproduced from what is recorded rather than from how it was invoked.
- Trades are persisted by =ores.trading=, called downstream, not written by the
  generator. Generation introduces no second path into the trade tables.
- The seed makes a population reproducible. The same configuration yields the
  same book, which is what lets a large population be generated rather than
  committed.
- Sizes are *named presets* of the configuration, not fixed constants. The
  parameters a preset sets are the same ones a caller may supply directly, so a
  load test at an arbitrary volume is a configuration and not a code change.
- Four presets ship, named and purposed: t0 tiny, small enough for an
  integration test to assert against, through to the largest, which exists to be
  loaded at volume. Their parameters are recorded, and adding a fifth requires
  no code.
- Volume has no ceiling in the design. Whatever the presets happen to set, the
  analysis states how cost scales with the number of trades and where each
  approach breaks, rather than certifying one target figure.
- Realism is defined per size and is checkable. A tiny population is realistic
  as a small book rather than as a sample of a large one, and the analysis
  states what differs beyond count: how many asset classes, how many
  counterparties, what maturity spread a firm of that size plausibly has.
- Populating a provisioned system composes the block without a manual step: no
  hand-written XML, no separately run generator, no hand-imported file.
- The design admits the compositions not built now. A scheduled feed sending the
  same request, and an update mode that amends an existing population, are shown
  to need no change to the block. Neither is implemented here.
- The cost is measured rather than estimated, at more than one volume, so the
  shape of the curve is known and not just one point: how long generation takes
  and how long persistence takes.
- Coverage is measured against the =ores.trading= instruments: which the
  generator can populate, which it cannot, and which asset classes a realistic
  book needs that neither side carries.
- Trades land in portfolios by a rule reflecting each portfolio's owner unit and
  aggregation currency, not by round-robin.
- What ORE's TradeGenerator knows is extracted and written down: which fields a
  valid trade needs, which come from the convention, which from the curve
  config, and which the caller must supply. Whether we depend on it or
  reimplement it is a conclusion of the analysis, not its premise.

* Decisions

*Generation is a block behind a request, not a seeding script.* The same block
then serves provisioning, a periodic feed and amendment, which differ in who
sends the request and what the configuration says rather than in mechanism.

*Sizes are presets of the configuration, not constants.* A load test at an
arbitrary volume must be a configuration change and not a code change.

*The service boundary stands, and a bulk path is needed behind it.* The vector
write batches, so the boundary costs no call per trade. What the boundary writes
through is the cost: multi-row =INSERT= with the per-row trigger loads a million
swaps in 133 seconds against 14.8 by =COPY= without it.

*Suppressing the notify trigger is not worth doing.* It costs 1.5% on the
deployed schema. The synthetic benchmark's 4.2x was an artefact of measuring a
table where nothing else happened.

*Preset distributions are a labelled assumption, not a citation.* Public sources
publish notional by asset class and not trade counts, and a population is sized
in trades.

*The story pauses here.* Two defects in the trading model bound what any
population can contain, so repairing the model first is cheaper than generating
against one that is about to change. This is a sequencing choice: the story could
proceed against what the schema stores today.

* Out of scope

- Repairing the trading model. Sixteen defects were found and recorded, and one
  was fixed because it blocked the story outright. The rest belong to their own
  story.
- Extending instrument coverage. 28 of ORE's 112 trade types cannot be stored,
  and adding them is a model change rather than a generation change.
