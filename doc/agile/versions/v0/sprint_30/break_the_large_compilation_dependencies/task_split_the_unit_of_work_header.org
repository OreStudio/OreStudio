* Goal

pq/unit_of_work.hpp needs pq::transaction's definition for its body, and pq/transaction.hpp defines pq::session_context beside it, so the header cannot take the session context's declaration. This task separates the two types so it can, which takes the forward-declaration check to zero offenders.

* Plan

pq/transaction.hpp defines two types: the transaction, and the session context
it keeps a copy of. The copy is why the definition has to live beside it, and
that is why pq/unit_of_work.hpp, which only passes the context on, could not
take the declaration: the only header that defined the type was the one it
needs for the transaction.

The split:

- =pq/session_context.hpp= holds the struct, and =pq/session_context_fwd.hpp=
  its declaration. The struct carries the includes it needs, which are
  =tenant_id.hpp=, =<boost/uuid/uuid.hpp>=, =<optional>=, =<string>= and
  =<vector>=.
- =pq/transaction.hpp= includes the definition, because the member is a copy,
  and stops defining the struct. It loses the includes only the struct used.
- =pq/unit_of_work.hpp= takes =session_context_fwd.hpp= and keeps
  =transaction.hpp=: it constructs the transaction, so it needs that
  definition, but it only passes the context through.

The split moves no reach: =pq/transaction.hpp= stays the header the connection,
the statement types and the libpq-facing code take, so the radius of
=unit_of_work.hpp= is the same before and after. What it buys is that the type
has a declaration, so a header that needs the session context and not the
transaction takes the cheap header, and the forward-declaration check has no
remaining offender to explain.

The first such consumer is =context.cpp=, which builds a session context and
never opens a transaction: it took =pq/transaction.hpp= for the struct alone
and now takes =pq/session_context.hpp=, which halves what that translation
unit parses.

The check's list entry for the type points at the new pair, and the baseline,
whose only line was this offender, is empty.

* Notes

The reach numbers say what the split does not do. =transaction.hpp= and
=result.hpp= reach the same 188 objects, and =session_context.hpp= joins them,
because every object that takes the transaction takes the context with it. A
consumer that only names the context is what the new header exists for, and the
repository unit of work is not one: it holds the transaction behind a
=unique_ptr= and constructs it, so it keeps the definition.

The parse cost says what the split does do: the probe that includes only
=session_context.hpp= costs half of the one that includes =transaction.hpp=,
because the transaction's header carries the statement types and the result
type with it.

* Result

The session context is its own type in its own header. =pq/transaction.hpp=
includes the definition because it keeps a copy, =pq/unit_of_work.hpp= takes
the declaration, and =context.cpp= — the one consumer that builds a context and
never opens a transaction — takes the cheap header. The forward-declaration
check reports no offender at all, so its baseline is empty.

The split was expected to move no reach, and it did not: =transaction.hpp= and
=result.hpp= still reach 188 objects, and =session_context.hpp= joins them
because the transaction's own header includes it. The gain is parse time for a
consumer that names the context alone (1.40 s against 2.83 s for a probe), and
the structural gain that the type can now be declared at all, which is what the
next task in this family needs.

The two checks that would have caught a mistake are the ones that ran: the
header compiles alone and the tree builds clean, and the suites that read
through the pq layer pass. The rest of the tree was rebuilt for the headers, not
for behaviour; nothing here changes what any statement sends.
