#+title: Story: Save the compiler cache instead of silently dropping it
#+description: actions/cache tars the cache directory, and a tar that reads a file while sccache is still writing it exits non-zero. actions/cache reports that failure as a warning and still exits zero, so the Save step reports success while storing nothing. The debug job has therefore never stored a cache: the only linux-clang-debug entry is the legacy one built before coverage changed every compile line, so every run restores it, misses 79 per cent of its compiles, hits the 320-minute cap and saves nothing again. The prune step makes it worse, because it is gated on the cache being worth saving rather than on the save having landed, so it would delete the entry the failed save was meant to replace. * Decisions

- *The save was failing silently, and that is why the cache never warmed.*
  actions/cache archives the directory with tar. sccache's server was still
  running and still writing, so tar exited 1 with "file changed as we read it",
  and actions/cache turned that into a warning on a step that exits zero. Every
  debug run since the coverage change restored the stale entry, missed 79 per
  cent of its compiles, hit the cap and stored nothing, while the run reported
  that the save had succeeded.
- *Stop the server before archiving.* =sccache --stop-server= flushes it and
  leaves the directory still, which is what makes tar able to read it. The
  statistics step moves above it, because a stopped server reports nothing and
  those numbers are the only evidence of whether the cache is warming.
- *Prune on the entry existing, not on the step exiting zero.* The prune is what
  turns a failed save into a lost cache: it deletes the entry the save was meant
  to replace. It now asks the cache service whether the run's key is there, and
  when it is not it reports an error and deletes nothing. A step that cannot be
  trusted to say it failed must not be the gate for a delete.
- *The ceiling is left alone for now.* The debug job reported its local cache at
  3946 MB against a =max-size: 2500M=, so the working set may not fit once the
  save works. That is a capacity question for the 10 GB repository cap, and the
  next successful save measures the real size rather than guessing at it.

* Out of scope

- Raising =max-size=, and rebalancing the ceilings between the six Linux
  variants. The evidence for the right number is the size of the first cache
  that is really stored.
