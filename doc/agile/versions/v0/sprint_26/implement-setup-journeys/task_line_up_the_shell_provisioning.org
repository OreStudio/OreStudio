This page documents a [[id:31C868B9-306E-4282-BA8C-07E647021B34][task]] in the [[id:DCF3E855-AEDF-4520-97B6-815A428DB514][Implement the setup journeys in ores.web]] story. It captures the goal, current status, acceptance, and any notes or results.

* Goal

=ores.shell= and =ores.web= drive the same three journeys through the
same server-side operations, so that neither is the reference and neither
can drift.

The shell is not a bystander in this work. It already carries the three
Setup journeys as porcelain commands, and two recipes under
=doc/recipes/shell/provisioning/= run the whole sequence end to end:
=acme_system_provision.org= with =--source synthetic=, and
=how_do_i_provision_the_system_with_acme_corporation_holding_group.org=
with =--source acme=. Each creates the system administrator and a tenant,
signs out, signs in as the tenant administrator, and provisions the tenant
through the porcelain command. They are the sequences the browser is being
built to match.

Those three commands orchestrate on the client today. This task removes
that orchestration, because the accepted
[[id:94C3AE99-8642-4418-982D-92C5FD805CCB][seed profile contract]] already
decided it: "ores.web and ores.shell are thin callers. The shell's
client-side orchestration is deleted." The work moves to the server, and
both clients become callers of one contract.

  same subjects the browser calls, and hold no sequence of their own.
- The orchestration they do today — publishing bundles, waiting on
  workflows, generating a synthetic organisation, associating the
  administrator with the operational parties — happens on the server, in
  one request per stage, or is recorded as deliberately staying in the

  =how_do_i_provision_the_system_with_acme_corporation_holding_group.org=

* Plan

1. *Inventory the orchestration.* Read
   =projects/ores.shell/application/src/app/commands/provision_commands.cpp=
   and list, per command, every call it makes and every wait it performs.
   The three commands are 696 lines, and the list is the checklist for
   the rest of the task.
2. *Inventory the flags.* Each command's flags are the wizard's knobs.
   Map each to a seed-profile parameter, to a field on the generic
   request, or to nothing. The last group is the one to argue about,
   because a knob that disappears is a capability that disappears.
3. *Re-point each command* at the generic request and the two bootstrap
   subjects that survive, deleting the client-side sequence.
4. *Regenerate the recipes and scripts* that follow the commands, and add
   the Acme script to the story's end-to-end proof.
5. *Run the Acme script* against a fresh database, on the fleet, and
   record the output.

* Notes

The commands' own header says each "spans one of the GUI provisioning
wizards end-to-end". The GUI is gone, so these commands are now the only
description of what those wizards did. That makes them evidence as well as
code: the inventory in step 1 is the record of the wizard behaviour the
journeys replace, and it should not be deleted with the orchestration.

All six recipes under =doc/recipes/shell/provisioning/= are hand-written
and tangle to scripts in the shell's library. Two of them run a whole
system provisioning, and they exercise both provisioning paths that exist
today:

- =acme_system_provision.org= creates a tenant called =acme=, provisions
  it with =--source synthetic=, then adds a party and sets the default
  party.
- =how_do_i_provision_the_system_with_acme_corporation_holding_group.org=
  creates =acme_corporation=, provisions it with =--source acme=, which
  reaches the synchronous =provision-acme= handler, and publishes the
  risk-management bundle.

=--source= is a flag of the porcelain =provision tenant= and not of a
script; its permitted values are =gleif=, =synthetic= and =acme=. The
=acme= value is the one that depends on the handler the generic request
replaces, so it is the value this task has to re-point.

=doc/recipes/shell/tenant_provisioning/tenant_provisioning.org= is a
different thing: one generated recipe with a section per command in that
submenu, including one that calls =tenant_provisioning
provision-acme-tenant=. It is generated, so it regenerates when the
command changes and is never edited by hand.
