#+title: Classification of retained data
#+description: The retained data of the platform, classified by the treatment that holds each class.
#+type: knowledge
#+level: cross
#+filetags: :housekeeping:retention:storage:architecture:

* Summary

The data the platform retains divides into a small number of classes, and the
retention period or other treatment that suits a class follows from what the
data is for rather than from the table or directory that holds it. Age-based
retention suits only those classes whose worth decays with time. The classes
that dominate a footprint are commonly superseded, derived or duplicated
instead, and each of those takes a different treatment: overwriting,
recomputation or deduplication. The classification assigns a treatment to each
class, and the executor that applies it is described in
[[id:E92D8CA4-C33F-4AE2-808B-9092B100E9C5][Housekeeping of retained data]].

* Detail

** The classes

| Class | What it holds | Treatment |
|-------+---------------+-----------|
| Run outputs | report cashflows, metrics, text values | age-based retention: drop the chunks past the period |
| Versioned counters | delivery counts, per subscription | overwrite the current row, keeping no history |
| Market observations and fixings | quotes, fixings, calibration and scenario values | retention by financial as-of, never by wall clock |
| Telemetry samples and logs | service samples, grid and node samples, log lines, auth events | age-based retention over a fixed window |
| Durable stream records | the subjects a stream keeps | the stream's own limits: maximum age and maximum bytes |
| Workflow and queue records | workflow instances and steps, messages, approval requests | archive on completion, expire after a period |
| Derived reference data | calendar dates and the other tables a rule produces | recompute, or share one copy across owners |
| Artefacts | objects under the store's key prefixes | a lifecycle rule: expire by key prefix and age |
| Engine distributions | the packages a compute node caches | deduplication by digest, one copy per host, evicted by age |
| Scratch | a job's working directory | release it once its output is stored |
| Audit and validity history | the closed rows of the bitemporal tables | a stated retention policy, decided deliberately |

** Why one treatment does not serve

Age-based retention assumes that a row's worth decays with time. Three of the
classes violate that assumption in different ways, and each violation has its
own answer.

A versioned counter is not aged but superseded: every row but the latest is
already obsolete when it is written, so a retention period removes the history
long after it has cost the space. The treatment is an overwrite applied as the
value is written, which prevents the rows and costs least of any here.

Derived reference data is not aged but reproduceable. A calendar's business days
follow from its rule and its year range, so a copy per owner is a copy of a
function, and the treatment is to compute the data or share one copy rather than
to expire it.

Engine distributions and per-owner copies are not aged but duplicated. The same
package sits in the object store and again in each node's cache, often a third
time as the extracted tree. Expiring a duplicate removes one copy of several.
The treatment is deduplication: the content is addressed by its digest, so that a
second copy cannot be made, and the remaining copy is evicted by age.

** Two treatments that write nothing

Overwriting a counter and recomputing derived data hold a store without removing
anything from it. They are classified here, apart from retention, because an
operator reads them differently: a retention policy reports what it deleted, and
these report what they avoided writing. Both are subject to the same policy and
the same telemetry as the deleting treatments, and neither depends on the storage
engine's licence.

** Where the treatment is applied

Each class names the shape of its target rather than a particular table: a
time-partitioned table, an ordinary table, a key prefix, a directory, or a
transform applied as the value is written. Naming the shape keeps the
classification stable as tables are added, and it tells the executor which of its
actions applies. A new table joins an existing class by declaring it, and
inherits the treatment and the cadence already stated for that class.
