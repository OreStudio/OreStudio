It is a snapshot, not a description of the system. Whatever it concludes that the code must keep doing belongs on the page that owns the subject; cite that page from code, recipes and models, not this one.

* Context

ACME is seeded with 31 report definitions and nothing that can run them. The
run resolves a risk report config by definition id before it reads anything
else, and no seed writes one. Before we write the seed, we need to know what
each report actually reads, so we do not create a configuration that binds a
document the report never uses, or worse, claim a report is runnable when its
run would stop at a file nothing can store yet.

* Methodology

Read the 31 rows of
=projects/ores.sql/populate/reporting/reporting_report_definitions_populate.sql=,
the only report type =risk=, the four configuration types that type requires,
and the ORE run documents under =external/ore/examples=. The definitive
availability answer is the saver list and the unbound list in
=projects/ores.ore/core/tests/configuration_type_seed_tests.cpp=.

* What every risk report reads

A =risk= run reads four documents before it prices anything, and the type
records that as a hard requirement:

| Configuration type | ORE file | Bound? |
|--------------------+----------+--------|
| =pricing_engines= | =pricingengine.xml= | yes |
| =todays_market= | =todaysmarket.xml= | yes |
| =curve_configuration= | =curveconfig.xml= | yes |
| =conventions= | =conventions.xml= | yes |

Every row below needs those four. The table names only what each report needs
on top of them.

* Availability

Twelve configuration types have an ORE saver and a table. Five do not:
=simm_calibration=, =historical_return=, =basel_traffic_light=,
=reference_data= and =ibor_fallback=.

No report needs =simm_calibration=, =credit_simulation=, =reference_data= or
=ibor_fallback=. Four reports are conditional, because their natural
implementation reaches an unbound type and a cheaper implementation does not:

- Board Risk Dashboard, Stressed VaR and Intraday Risk Monitor need a
  =var= reading. A parametric VaR reads a covariance matrix, which is market
  data and not a configuration, so all three are available. A historical VaR
  reads =historical_return=, which cannot be stored yet.
- P&L Attribution needs =basel_traffic_light= only if the desk classification
  is in scope. The delta, gamma, vega and theta decomposition is a
  sensitivity report and is available.

So 27 of the 31 reports have every document available today under any
reading, and the remaining four are available if their VaR is parametric and
their attribution stops at the decomposition.

* Conclusions

A report configuration is three rows, not one. The definition binds a
configuration type to a configuration id through
=ores_reporting_report_configurations_tbl=, and the run's own settings live in
=ores_reporting_risk_report_configs_tbl=. The four Setup documents are
required by the type, so they are the same four for all 31 reports. Only the
extra analytics documents vary, and only nine reports need any.

The books the run prices come from the config's portfolio scope.
=ores_reporting_resolve_book_ids_for_config_fn= already expands a portfolio
through =ores_trading_get_book_ids_by_portfolio_fn=, so no new function is
needed. The root portfolio is the one whose =parent_portfolio_id= is null.

* Recommendations

Create configurations for the 27 unconditional reports first: bind the four
Setup documents, scope each to the party's root portfolio, and set only the
analytics flags the report names. Leave the four conditional reports until
someone decides whether their VaR is parametric, and open a separate task for
the five unbound ORE types if a historical VaR or a traffic-light
classification is wanted.
