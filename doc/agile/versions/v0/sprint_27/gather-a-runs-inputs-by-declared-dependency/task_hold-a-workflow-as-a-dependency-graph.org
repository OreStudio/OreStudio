* Goal

The chain is a =std::vector<workflow_step_def>= built in code, and the
instance stores each step's ordinal, so the only edge in the graph is the
ordinal. That is enough while every step produces exactly one artifact and the
chain is a line, and it stops being enough the moment a step gathers per trade set:
an ordinal says which step is next, not what a step is waiting for.

Persist the graph with the run — steps as vertices, artifact dependencies as
edges — and reconstruct it as a =boost::adjacency_list= to decide what is
dispatchable.

* Acceptance

- A step's dependencies are persisted with the run and read back at dispatch;
  the ordinal alone no longer decides what runs.
- The engine dispatches a step only when its declared inputs exist, whatever
  position it holds.
- A consumer of an artifact that N producers write runs only once all N have
  finished, and runs once, not N times.
- A run in progress can be resumed after a restart by reconstructing the graph
  from the database, not from the code that built the chain.

* Plan

Vertices are steps; an edge runs from the producer of an artifact to each of
its consumers. The ready set is every vertex whose incoming edges are all
satisfied, which is what the engine dispatches from in place of the ordinal.

The precedent is in this tree: =ores.dq='s =publish_service.cpp= builds a
=boost::adjacency_list= over datasets and their declared dependencies, orders
it with =boost::topological_sort=, and publishes in that order. The same shape
serves here, and a reviewer already knows how to read it.

Two things must survive the change. Compensation is a saga walk of the
satisfied prefix in reverse, so it needs a defined order from a structure that
is no longer a line; and =recover_in_progress= must rebuild the graph from the
database, which is what makes persistence the point rather than a convenience.

Where the edges are persisted is a decision to take with the schema in hand:
an edge table keeps a step's dependencies open-ended, while a =depends_on=
column on the step keeps the read simple and would have to become a list. The
edge table is the one that survives a step with two producers without a second
migration.

* Notes

*Landed so far.* The graph itself, and the engine deferring to it.

=workflow_graph= holds a run's steps as vertices and an edge from a step to
every step that reads its result, built with =boost::adjacency_list= and
queried through =in_edges=. It answers two questions: whether the chain can be
run at all, and which steps may run given what has answered.

It is rebuilt from the run's own =materialised_steps_json=, not from the
definition as it stands now, so a definition edited after a run started cannot
change what that run was waiting for. That is the persistence the task asked
for: the graph travels with the run and a restart reconstructs it from the
database.

Three chains are refused before a run exists, and each is a definition that
cannot be executed rather than a state a run can reach: a consumer of a name no
step produces; two steps with one name, because a consumer cannot say which it
reads; and a consumer of a step the engine reaches only later.

That last refusal is deliberate and worth naming. The graph derives an order
and would run a chain declared the other way round; the *engine* advances along
the declaration, so it would dispatch the consumer first and find its input had
not run. A chain the engine cannot walk is refused up front rather than left to
fail at the step that discovers it. Dispatching from the graph's own order is
what lifts the restriction.

At dispatch the engine asks the graph whether the step it is about to take is
ready, and fails the run naming the inputs it is waiting on when it is not.

*What the task still owes.* Two things, and both are the same change.

The advance loop still walks the chain by index and dispatches one step per
completion. Until it dispatches *every* ready step instead, a consumer of many
producers — the fan-in the gathering redesign needs — is refused rather than
made to wait, because nothing reconsults the graph when a producer answers.
The readiness rule is already the fan-in rule: it waits on every producer that
writes an input, proven by a test with two batch-keyed producers. What is
missing is a loop that acts on it.

* Blocked: the chain's rows cannot be inserted for another tenant

Re-pointing the engine at the two relations was built and reverted. What it
found is worth recording, because it is the next thing to fix and it is not
obvious.

The reading side works. The graph is drawn from the plan rows and their edges,
the query handler takes a step's words from the chain, and every single-tenant
run passes. What fails is *writing the chain* for a run that belongs to another
tenant, which is exactly the arrangement a deployed engine runs in: it holds
the system tenant and acts for whoever asked.

The plan step's insert is refused by its own soft-FK check:

#+begin_example
Invalid workflow_id: <id>. No active workflow instance found with this id.
#+end_example

The check is the generated one, and it is byte-for-byte the check the execution
rows already use — =where tenant_id = NEW.tenant_id and id = NEW.workflow_id
and valid_to = ores_utility_infinity_timestamp_fn()=. The execution rows insert
happily in the same run, into a table whose trigger is identical.

The evidence narrows it to the trigger's own view, and the measurements are:

- The instance row exists, is current, and its =tenant_id= is *exactly* the one
  the plan row is being written with. Checked by reading both back.
- The engine's own context, reading the same instance by the same id at the same
  moment, returns one row — with the system tenant set.
- So the row is committed and visible to the engine, and invisible to the
  trigger's identical lookup.
- Neither table forces row-level security (=relforcerowsecurity= is false), and
  both insert functions are =security definer= owned by the same role that owns
  the tables.

*What to do next.* Reproduce the lookup the way the trigger runs it — set the
role and the session tenant as the trigger has them, then run the same
statement — and read back the tenant the policy sees. The likely answers are
that the policy is evaluated under a tenant the trigger does not expect, or
that the update trigger on the instance has left the row current under a
different version. Either way the fix belongs in the policy or the check, not
in the caller, and it must not be made by weakening the check.
