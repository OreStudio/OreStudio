* Goal

Every write lands on a tenant that holds accounts, including the write whose
actor is the account written. The generated insert function validates
=modified_by= before its version management retires the actor's current row,
so the validator finds the row its rule requires. The validator's own rules do
not change. The fix lives in the three literate templates that render every
create script, and a regeneration carries it to every generated file.

* Decisions

- *The validation moves; the validator does not weaken.* The other column
  validations already run before the version management: the tenant, the
  foreign keys, the enums and the change reason. Moving =modified_by= into
  that group is the smallest change that meets the validator's rule.
  Relaxing the validator instead, for example by accepting an actor whose row
  was current at the start of the statement, would hide a real refusal for
  every other caller.
- *The fix belongs to the templates, and every generated file follows.* The
  assignment sits in 338 generated create scripts, in three shapes (domain
  entity, junction and table), and a patch of each output would drift from its
  template at the next regeneration.
- *The bootstrap branch stays.* A tenant's first account must be creatable
  before any account row is current, so the branch that passes any actor
  during bootstrap remains as it is.
- *The journey check stands on a bootstrapped deployment, and the seeds come
  last.* The BFF refuses every sign-in while =system.bootstrap_mode= is on,
  and creating the initial administrator expects a system tenant with no
  current accounts, because the insert names an actor that does not exist
  until the insert lands. The cycle is recreate, bootstrap, seed, check.
- *The moved validation changes one error precedence.* A write that is stale
  and also carries a bad =modified_by= is now refused for the actor,
  =Invalid modified_by= (23503), where it was refused for the version. The
  write was refused either way. The conflict path answers =outcome=conflict=
  with its code and the panel composes the record-changed sentence itself,
  and the open question the same run found about that message is captured at
  [[id:25870CC8-06CF-4921-8804-878F2CF62401][A version conflict carries no
  message]].

* Result

The self write lands. The three literate create templates (domain entity,
junction and table) moved the assignment
=NEW.modified_by := ores_iam_validate_account_username_fn(NEW.modified_by)=
above the version management, and the regeneration changed 321 template-owned
create scripts with no hand patch. The repository case
=write_account_with_itself_as_modified_by= writes an account and replaces it
as itself: it fails on the old order with =Invalid modified_by= (23503) and
passes on the new one. The same work found and guarded the bootstrap fallback:
a tenant whose only account is the subject empties when the retire runs, and
the validator's bootstrap branch then accepts any actor, so the case writes a
keeper account and appends a per-run identifier to the username.

The end-to-end check closes the story. On a database recreated from the
regenerated scripts, bootstrapped through the shell and seeded, the profile
journeys checker ran 67 checks and 64 passed: the member's own profile and
contact saves land, the round trip reads back, and the administrator's contact
insert lands. No failure traces to the self write. Two failures are the upload
over the message fabric's payload cap (capture [[id:820AC660-C3FC-4A45-998D-A65818FA4BB8][A profile image over the
payload cap cannot reach the validator]]). The third is the empty message on a
version conflict, which the store leaves to the panel and the checker asserts;
it is captured at [[id:25870CC8-06CF-4921-8804-878F2CF62401][A version conflict
carries no message]].

The two journey gaps that recorded the refusal close in their journey
documents, =Present myself= and =Keep my details current=. Every acceptance
item holds, and the two captures above hold the work the run leaves open.

** What

On a tenant that holds user accounts, a write whose actor is the account
written is refused. The generated insert function performs its version
management first — it retires the account's current row with =valid_to =
clock_timestamp()= — and only then assigns =NEW.modified_by :=
ores_iam_validate_account_username_fn(NEW.modified_by)=. The validator accepts
an actor only while a current row with that username exists, and the retirement
just removed the actor's own row, so the write raises =Invalid modified_by:
<username>= (=23503=). Every self write hits it: the member's own profile and
contact saves, and an administrator's write to their own account. The contact
record reaches it through the account version touch its insert performs
(=ores_iam_account_contact_informations_insert_fn= calls
=ores_iam_accounts_touch_version_fn= before its own validation).

** Why

Two of the three Profile journeys cannot land their save on any tenant that
already holds accounts: =PUT /api/me/profile= and
=PUT /api/me/contact-information= answer "The write failed.", while the
administrator's write to a colleague's record passes, because retiring the
colleague's row leaves the actor's own row current. The validator's bootstrap
branch — a tenant with no current non-service accounts passes any actor — hides
it from every unit test that seeds its own tenant. The ordering lives in the
generator, not in one generated file: the assignment appears in 338 generated
create scripts, in three template shapes, so the fix belongs to the templates
and a regeneration, not to a patch of each output. Found by the profile journeys
end-to-end run (task [[id:6CDA40DF-EBED-4F62-9804-525EEAB0282C][Build the
profile screen]], 2026-10-05).
