* Goal

Make the ORE series key shape data. The qualifier depth, the point
dimension and the default point of every series type move from a
compiled table into one a user can manage, and the reader receives that
table instead of reaching for it. Each of the eight types the corpus
carries but the table does not know gains a row, so its keys split into
one series with many points instead of many single-observation series.

* Acceptance

- The key shape of every ORE series type lives in a table, seeded
  from the corpus and managed like any other catalogue: the qualifier
  depth, the point dimension, and the point to record when a key
  carries none.
- The table holds a row for each of OI_FUTURE, SHAPE_PROFILE,
  BOND_OPTION, RATING, INDEX_CDS_TRANCHE, GENERIC-MD, CPR and FIXING.
- Every distinct key of those types decomposes into a qualifier and a
  point, so its observations share one series.
- =ores.ore.core= receives the shape table. It never reads the database
  itself, so its tests run with no database, no NATS and no pipeline.
- An empty table throws, and the message names the table and says it is
  unseeded. A row that claims a point dimension and also carries a
  default point is rejected, both in the constructor and by a table
  constraint.
- =known_series_types()= answers from the supplied rows, so no list of
  type names is compiled into the reader.
- A test asserts that the classifier's type set and the table's type
  set are equal, so the two cannot drift.
- The corpus census of distinct series is materially lower after the
  change, and the drop is recorded.

* Plan

The mechanism changed after the design discussion. The shape of an ORE
key was to stay a compiled table, with eight rows added. It becomes
managed data instead, and this task records that rescope. The outcome
does not change: the eight types must decompose properly.

** Why the shape becomes data

The shape table says how a key splits. That is ORE's grammar, so it
belongs to =ores.ore=, and nothing in the component prevents it. Every
component that owns an entity model owns a schema, and =ores.ore.core=
already links =ores.database.lib=. A compiled table also cannot serve
the case that matters: when ORE adds a type, or a user brings one of
their own, the answer must be an inserted row, not a rebuild.

** Two tables, two owners

The shape table belongs to =ores.ore=, because it describes the ORE
file format, which ORE defines and we only read. The classification
table belongs to =ores.marketdata=, because it maps a type to refdata
asset class codes, which are our taxonomy. The two facts change for
different reasons. This also means the promise "a user can add their
own types" holds only once the classification table is data too, which
is task 219. Until then a new row imports only if both tables carry it,
and the shape row without a classification row makes the classifier
throw and aborts the file. That pulls 219 into this work.

** The reader takes the table

=series_key_registry= stops being free functions over a static map and
becomes a value built from rows.

#+begin_src cpp
class ORES_ORE_CORE_EXPORT series_key_registry final {
public:
    explicit series_key_registry(std::vector<domain::series_key_shape> shapes);
    decomposed_key decompose(const std::string& key) const;
    bool has_point_dimension(const std::string& series_type) const;
    std::string default_point_for(const std::string& series_type) const;
    std::vector<std::string> known_series_types() const;

private:
    std::unordered_map<std::string, domain::series_key_shape> by_type_;
};
#+end_src

The rows are the generated =domain::series_key_shape= rather than a
second struct of four fields. The design sketched a parallel struct,
because it was not obvious that =ores.ore.core= may see the entity
type. It may: =ores.ore.core= already links =ores.ore.api.lib=, and
its generated repositories include that header to return rows. A
second struct would be a second artefact for the same table-shaped
data, which the data oriented design note rules out: the wire shape
is a codegen projection of the entity, not another type. So the
repository's rows feed the constructor with no mapping layer between
them.

=reconstruct_key= stays free. It joins strings and needs no table, so
the serializer does not change.

The constructor throws when the rows are empty, and the message names
the table. It also rejects a row that claims a point dimension and
carries a default point. A table constraint carries the same two
checks, so an illegal state cannot be stored either.

A third check was considered and declined. =qualifier_depth= is an
=integer= in the table, so a negative depth can be stored. It needs no
check, because a negative depth makes the key shorter than its type
expects, and that branch already folds the whole remainder into the
qualifier: the row degrades a key exactly as an uncatalogued type
does, and the key still reconstructs verbatim. Throwing in the
constructor would abort an import over a row the table accepts, which
is the failure this task exists to remove.

** An unknown type still folds

An empty table throws. A type with no row is a different case. Its key
folds into the qualifier and loses nothing, because the key still
reconstructs verbatim. A file carrying a type nobody catalogued must
not take an import down, because ORE adds types over time and this
corpus already carries two that ORE's own catalogue does not document.
The alarm lives in the corpus test instead, which fails whenever the
corpus carries a type with no row.

** How the rows arrive

A repository reads the table once at the start of each import, builds
the registry, and passes it down by const reference. That is one read
per batch rather than per key, and no process-wide cache to invalidate
when a row changes. The component already injects this way, since
=import_service= takes a =context=.

** The call sites are shallow

=decompose_key= has one production caller, =market_data_parser.cpp=.
=default_point_for= has two, in =import_service.cpp= and
=feed_ingest_loop.cpp=. =has_point_dimension= is used only by tests
today. The generated =market_observation.hpp= mentions
=default_point_for= in a comment and does not call it.

rest is the point.

| Type | Depth | Point dimension | Default point | Corpus evidence |

| BOND_OPTION | 1 | yes | | 154 keys, one series. Same shape as SWAPTION |

The remaining thirty-five rows are the compiled table as it stands,
with the comment above each entry as its description.

The corpus walk reported 107,947 distinct keys across 41 types in 91
files. The C++ test comment claims 107,951 across 42 in 95, so the two
disagree. The =compass test run= warning is the authority, and this
work must reconcile the count.

The two counts differ in what they count, not in what the corpus
holds. Market data lives in =*.txt= files, one =date key value= per
line. Fixings live in =fixings.csv= files headed
=#fixingDate,fixingId,fixingValue=, and every line there is also a
dated key. A walk of the market data files alone finds 39 types in 62
files; the remaining types and files come from the fixings. GENERIC-MD
is the clearest case: it appears in no market data file at all, and
only in two =fixings.csv= files. Unit 4 must therefore state which of
the two, or which union, it counts, and the test comment must say the
same. The census must run through =parse_market_data= and
=parse_fixings= rather than a hand-written line rule, so that the
count follows the reader the corpus actually feeds.

SHAPE_PROFILE and GENERIC-MD are absent from
=doc/knowledge/domain/ore_market_data_catalogue.org=. That document
also needs the per-type qualifier and point table.

A multi-facet component does not wire its root modelling directory into
CMake. =ores.trading= holds 65 entity orgs and no root
=CMakeLists.txt=; =ores.marketdata= and =ores.ore= now hold entity orgs
there on the same terms. Only single-facet components such as
=ores.database= build a component-level diagram, and
=cmake_component_modeling.mustache= has no renderer. The generated
=ores.ore.puml= and its diagram targets therefore stay uncommitted, as
=ores.marketdata='s did. Wiring the root modelling directory for
multi-facet components is a separate decision.

** Unit 1 evidence

The seed reproduces the compiled table exactly. A mechanical compare of
every =type, qualifier_depth, has_point_dimension, default_point= tuple
across =series_key_registry.cpp= and the populate script reports 35
rows matching with no mismatch and no omission, plus the eight new
types. So the thirty-five known types keep their current shape.

The entity regenerates byte-identical, and the cmake source lists are
already in step. The ore component is not in the drift registry, so its
gate stays the per-component check.

The =ores.ore.core.tests= suite needed the database lifecycle listener
in its =main.cpp=, which it never had. It is the only core facet that
touches the database and lacked one; without it no test tenant is
provisioned and the eventing test dies on an empty tenant id. With the
listener in place the suite is 521 of 521 green. It takes 501 seconds
because the timeout listener's watchdog joins on a one-second sleep per
test case, so every case costs a second; =refdata.core= pays the same
toll for its 241 cases.

The entity carries the registrars that codegen emits, and nothing calls
them. =ores.ore= has no aggregate =messaging/registrar.hpp=, unlike the
fifteen components that expose a CRUD surface. This is not a broken
convention. Every aggregate registrar is hand-written and selective:
=ores.marketdata= hand-wires =market_series= and =market_fixing= and
calls a generated sub-registrar only for =market_observation=. No
consumer needs the surface yet, because Unit 2 reads the rows in
process. Wire the registrar when a client must manage the table.

** Unit 2 evidence

=series_key_registry= is now a value. It holds the rows in an
=unordered_map= keyed by series type, and it answers =decompose=,
=has_point_dimension=, =default_point_for= and =known_series_types=
from them. The constructor throws on an empty table and on a row that
claims a point dimension and also carries a default point.

The three free functions stay, marked =@deprecated= in Doxygen only, so
every existing call site keeps working until Unit 3 deletes them. The
compiled table therefore still sits in the source, and Unit 2 changes
no behaviour that a caller can reach. That is why the rest of the tree
sees nothing from this unit.

The full seventy-three suite run did not complete, and this is a gap

** Unit 3 evidence

The migration is complete and the compiled table is gone.
=series_key_registry.cpp= loses 167 lines holding the type-to-shape map,
=series_key_registry.hpp= loses the three deprecated free functions, and
no caller can reach a compiled grammar any more.

=parse_market_data= takes the registry by const reference.
=import_service= builds one per batch from
=series_key_shape_repository{}.read_latest(ctx_)=, next to the parse
call, so a fixings-only import never pays for the read.
=feed_ingest_loop= builds one in =start()= before the subscription
exists and holds it in an =optional=; the tick path then reads it with
no lock and no database call. An empty optional leaves the point empty,
which is the answer an uncatalogued type already gets.

The tests needed a grammar with no database behind it, so
=ores.testing/series_key_shape_seed.hpp= reads
=ore_series_key_shapes_populate.sql= and builds a registry from it. It
parses the script's own text, so a test that passes here passes against
the rows the loader writes, and a row that drifts in SQL fails the test
that depends on it. =ores.testing= links =ores.ore.core.lib= to host it.

A test tenant is provisioned fresh on every run, so
=ores_iam_provision_tenant_fn= now copies =ores_ore_series_key_shapes_tbl=
into it. Without that copy the tenant's table is empty, the registry
constructor throws, and every import fails. The function was installed
into the test database with =compass db sql -u ddl -f=, because
=compass db setup= runs a bare =create database= that fails on an
existing one.

=ores.marketdata.core.tests= is green: 191 cases, no failure, 21.64
seconds, including the three corpus cases that failed before.
=ores.ore.core.tests= is green: 535 cases, no failure, 535.88 seconds.
Both counts are read back from the runs' own results files.

The corpus census now runs. It reads 107,947 distinct keys across 41
series types in 91 files out of 3,528 walked, with none unreadable.
That is the figure the Notes recorded from the manual survey, reached
this time through =parse_market_data= itself, so the survey and the
reader agree. The test comment's 107,951 across 42 in 95 does not, and
the reconciliation belongs to Unit 4.

One defect was found and fixed on the way, and it had hidden the whole
walk. =seed_shapes()= located its =values= keyword and then started the
row scan at the offset after the newline instead of after the keyword,
so the first character it read was the =v= of =values=, the guard
rejected it, and the function threw on the first iteration. Every test
that built a registry failed with =no shape rows found in ...=, which is
why the census read zero and why the ore core suite was red. The corpus
test also built the seed inside its per-file =catch=, so the throw was
swallowed once per file and an empty census looked like a corpus with no
market data rather than a seed that could not be read. The seed is built
outside that =catch= now, and the census reports files seen and files
unreadable, so a walk that reads nothing cannot print the same line as a
corpus that carries nothing.
