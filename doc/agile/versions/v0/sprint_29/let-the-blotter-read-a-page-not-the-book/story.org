* Goal

A desk opens the blotter and has its rows in well under a second, at any size the tenant has written, and its rail states how many rows sit at each node without reading the book to find out.

The screen asks two questions, and they are different questions: give me one page of rows, and give me a count at each node. Today one request answers both by reading everything.

- *The contract comes first, the projection behind it.* Two new operations carry the screen: one page of rows, keyed by the sort key and the row id, and one rail of counts. They are implemented over the summary view first, so the screen's answers are correct and measurable at the size we have, and the projection replaces the view behind the same contract when the book outgrows it. Deciding the contract before the store keeps the store replaceable.
- *The rail is counted by the store.* A count at each node is one grouped read; the client never counts rows it retrieved to draw a page.
- *Where the projection lives*: a table the trading service writes and maintains. The summary view pays four correlated subqueries per row, so neither a page nor a count can be read without them; the table answers both at any size. It is built third, because the contract does not depend on it.
- *Search* is left as the summary states it today: the identifiers and the references, concatenated into one column. A trigram index waits until a search is measured to need one.
- *Flat mode* is a filter on the same rows, not a second model: the projection carries legs and the top list filters them out.
- *History*: the blotter reads the current state only, as the summary view already states. As-of would make the projection bitemporal; nothing asks for it.

* Out of scope

- The screen's layout and interaction, except where the read model forces a change (paging, the rail's source).
- The other screens that read the summary view; they are separate stories unless they share the projection.
