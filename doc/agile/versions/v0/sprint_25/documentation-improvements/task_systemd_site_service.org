* Goal

`compass site serve` currently only runs as an ad hoc foreground/background
shell process (manually backgrounded, killed via `pkill`). Give it a
proper detached lifecycle -- `compass site start`/`compass site stop`/
`compass site status` -- so it starts/stops/reports cleanly and
doesn't leave orphaned python http.server processes behind. (Initially
framed as "add a systemd unit"; see `* Plan` for why a PID-file
lifecycle, matching the Qt client, turned out to be the right call
instead.)

* Acceptance

- `compass site start`/`compass site stop`/`compass site status`
  start/stop/report the site-preview server, replacing manual
  backgrounding (nohup/pkill).
- No orphaned `python3 -m http.server` (or emacs build) processes
  left behind after stop.
- =compass site serve= (the existing foreground command) is
  unchanged, for interactive terminal use.

* Plan

=compass_services.py='s own module docstring already documents a
precedent that changes this task's original systemd-unit framing: the
DB-driven, per-replica systemd fleet (=systemd_generate.py=,
=compass services start/stop/status=) is for *registered
service_definitions* -- and the Qt client, a single local dev-facing
process with no DB registration, deliberately opted out of that and
kept its own lightweight PID-file =_launch=/=_terminate= lifecycle
instead (see the "Qt client is unaffected" note in that docstring).

The site-preview server is architecturally the same shape as the
client -- a single, local, per-checkout dev convenience, not a fleet
member -- so it gets the client's PID-file pattern rather than a
generated systemd unit for a service that was never registered in the
DB to begin with. Implemented directly in =compass.py= (a
=_cmd_site_start/stop/status= trio next to the existing
=cmd_site=/=_lan_ip=), reusing =compass_services=' =_read_pid=/
=_pid_alive=/=_terminate= helpers rather than duplicating them.
=start= runs the same build-then-bind logic as =serve=, but spawns the
actual HTTP server as a detached child (re-execing
=compass.py site serve --port N=, stdout/stderr to a log file,
=start_new_session=True=) and writes a PID file under
=build/output/site-run/= instead of blocking the caller's terminal.

* Result

Added `compass site start`/`stop`/`status`, PID-file based (same
lifecycle pattern as `compass client start/stop`), not a generated
systemd unit -- see `* Plan` for why that's the right call given the
site server was never a DB-registered service to begin with.
Hand-verified: `start` returns immediately with URLs printed and a
live PID; `status` correctly reports running/stopped; a second
`start` while already running skips cleanly; `stop` gracefully
terminates with no orphaned process or stale PID file left behind.
`compass site serve` (foreground) is untouched.
