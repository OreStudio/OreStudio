#+title: DQ Bundle Publication Pipeline
#+description: The stages by which a staged DQ dataset becomes a published row, and at each stage which part a generator owns and which part a person writes.
#+type: knowledge
#+level: cross
#+filetags: :dq:publish:bundle:pipeline:architecture:knowledge:

* Summary

The model of publication is stated once, in
[[id:7287B58F-964C-4D42-8EC4-6C5DA53EEE2D][Reference data classification by
publication level]]: the three levels, the bundle that carries each, the tenant
that holds its rows and the caller each admits. That page also draws the path
and the sequence. This page does not restate them. It follows the same path
through the code and records, stage by stage, which part a generator owns and
which part a person writes. It is the reference to consult before adding an
artefact type, and the case for generating the one part that is still written 72
times.

* Detail

** The stages and their owners

| Stage | What it is | Who writes it |
|-------+------------+---------------|
| Registries | The bundle, its members, the artefact type, the dataset and the dependency edges | Generated: each is an entity model under =projects/ores.dq/modeling/=, so its table, repository and shell commands follow |
| Staging table | =ores_dq_<plural>_artefact_tbl=, the artefact's own store | Generated from the owning entity's model, which opts in with =:ores.sql.schema.domain_entity_artefact_create.enabled: true= |
| Staged rows | The rows a publication drains | Hand-written, per dataset; see *The staged rows* |
| The verbs | =dq.v1.ops.publish_bundle= and =dq.v1.ops.publish_datasets= | Hand-written handler over generated message types |
| The step | One workflow step per dataset, dispatched in dependency order | The workflow definition is generic; a service states its subjects in an operation model or a constants header |
| The function | =ores_<component>_publish_<plural>_from_dq_fn= | Hand-written, in all eight component trees |

** The registries

Five registries carry a publication. A *bundle* names one level and one scope,
and the level decides the tenant the run writes into. A *member* puts a dataset
in a bundle, in a display order that breaks ties, and marks whether the dataset
publishes by default: an optional member is published only when the caller names
it, so a large dataset does not arrive with every small one. An *artefact type*
names the staging table, the target table and the target subject, which is the
one value the workflow and the handler also state. A *dataset* names the run a
member stands for. A *dependency* is an edge between datasets and is what orders
the run.

The level is a property of the bundle and not of the dataset, so the direct
dataset verb has no level to check. That the two verbs therefore admit different
callers is captured as
[[id:B14DE752-043F-4EA0-A72E-ECDEB034C5F4][A dataset publish names no level,
so a tenant can publish a world dataset into itself]].

The bundle, the member junction, the artefact type and the dataset are codegen
entity models: [[id:2DC7CB2C-EF21-4E55-BB05-07F42DF5BD8B][ores.dq.dataset_bundle]]
and [[id:6D8510CF-B977-4126-9051-5BFA9DE929B3][ores.dq.artefact_type]] among them.

** The staging table

The artefact table is the artefact's own store: the entity's columns, the
=dataset_id= and =tenant_id= that provenance needs, and no key or foreign key,
because a staged row may be incomplete or may name a party the target service
does not hold yet. It is generated from the model of the entity it stages, in
the component that owns the published rows. Every artefact table in the tree is
generated: 186 files match =projects/ores.sql/create/*/*_artefact_create.sql= and
all 186 carry the generated marker.
[[id:F19A6B98-1CAD-4206-913B-A4EAAED2DEAF][From an entity model to a published
row]] states the one way, and the patterns it replaced.

** The staged rows

The rows are what a publication drains, and they are the stage codegen does not
own. Four families, each with a writer of its own:

- *FpML coding schemes.* Forty-eight populate files under
  =projects/ores.sql/populate/fpml/= fill the FpML artefact tables. The
  generator that produced them was retired, because it wrote JSON entity models
  and codegen stopped reading JSON; nothing in the tree regenerates these files,
  and they are maintained by hand. 42 of the 48 still carry a
  generated header naming one of three populate templates —
  =sql_dataset_refdata.mustache=, =sql_populate_refdata.mustache= or
  =sql_non_iso_currency_populate.mustache= — and none of the three runs for them
  any more. The other six carry no header. The migration onto the dataset
  pipeline is
  [[id:44B275EC-DC37-4961-80EF-9D79D4C186FB][Migrate FPML, crypto, flags and
  ip2country onto the org dataset pipeline]].
- *Other external sources.* GLEIF LEI, crypto exchange lists and the ISO code
  lists each have a one-off script that parses that source's native format:
  =lei_generate_metadata_sql.py=, =crypto_generate_metadata_sql.py= and
  =external/iso/iso_generate_metadata_sql.py=. The parsing is source-specific by
  nature.
- *Computed data.* What a run computes — a synthetic feed's ticks, a simulated
  path — is produced by use and never published. What is published is the
  configuration the generator reads, and a person writes that populate script,
  as =synthetic_fx_spot_configs_populate.sql= is written. The computation belongs
  to the generator; the staged configuration does not.
- *Demonstration data.* The seeder datasets generate their populate SQL from
  =projects/ores.seeder/datasets/<name>/generate_sql.py= and the JSON beside it,
  one generator per dataset, outside =compass generate=.

The populate archetypes =sql_dataset_refdata= and =sql_populate_refdata= still
exist as templates, and no dataset model consumes them yet: the tree holds no
model of type =ores.codegen.dataset=. The component operation models that do
exist generate messages and registrars, not populate rows.

** The verbs

=publish_handler=, in =ores.dq.core/messaging/publish_handler.hpp=, serves both
verbs. Each decodes its request, builds the caller's context, requires
=dq::datasets:write= and resolves its datasets to publishable entries through
=publish_service=. The two differ in how they resolve. The bundle verb reads the
bundle's level, refuses a caller the level does not admit, then takes the
bundle's members and their dependency closure. The dataset verb takes the
datasets the caller names. Both then apply the optional-member filter and start
one workflow.

The level gate is worth stating because it is what keeps the second copy from
existing: a platform or world bundle is published only by the system tenant, and
a tenant reads those rows where they lie. A tenant bundle writes into the tenant
that asked.

=publish_handler= is hand-written, and it has to be: neither verb is a CRUD verb
over an entity, so neither can be derived from an entity model. The message types
it decodes are generated from =ores.dq.publish_bundle= and
=ores.dq.publish_datasets=.

** The step

=start_publish_workflow= publishes a =start_workflow_message= of type
=bundle_publish_workflow=, carrying the resolved entries. The definition, in
=ores.dq.api/workflow/bundle_publish_workflow.hpp=, turns that request into one
=workflow_step_def= per dataset: =command_subject= is the dataset's
=target_subject=, and the payload is a =publish_from_dq_command= carrying the
dataset, the tenant, the mode and the parameters.

The order is the dependency closure's, and the bundle's display order breaks
ties, which is the order =publication_order= states. A dataset with no target
subject is dropped from the run. There is no compensation step: the publish
functions are idempotent upserts, so a failed run halts and leaves the datasets
that preceded it in place. A run writes no audit row, and the run-log table that
would hold one has no writer; that gap is captured as
[[id:5C20BEF9-13CA-48B5-8221-E83C1D6345DD][The publication run log has no
writer, so the history screen is always empty]]. What a run wrote is read from
the provenance each published row carries, which names its dataset.

** The function

Each target service subscribes its own subjects and calls a =SECURITY DEFINER=
function in its own SQL tree. The eight =*_publish_from_dq_create.sql= files hold
75 =CREATE FUNCTION= statements: the 72 publish functions
named =ores_<component>_publish_<plural>_from_dq_fn=, and three helpers the same
file defines. The 72 are spread unequally:

| Component | Publish functions | File |
|-----------+-------------------+------|
| refdata | 56 | =refdata_publish_from_dq_create.sql= |
| reporting | 5 | =reporting_publish_from_dq_create.sql= |
| marketdata | 3 | =marketdata_publish_from_dq_create.sql= |
| analytics | 2 | =analytics_publish_from_dq_create.sql= |
| iam | 2 | =iam_publish_from_dq_create.sql= |
| synthetic | 2 | =synthetic_publish_from_dq_create.sql= |
| assets | 1 | =assets_publish_from_dq_create.sql= |
| trading | 1 | =trading_publish_from_dq_create.sql= |
|-----------+-------------------+------|
| total | 72 | |

The function is the one sanctioned exception to strict service-table isolation.
It reads =ores_dq_<plural>_artefact_tbl=, which belongs to another service, at
DDL-owner privilege, and it writes only tables its own service owns. DQ itself
never holds DML on another service's tables.
[[id:98B3572E-A9F9-45F5-A4C5-3DC23F3CFF70][DQ Publish Pattern — Architecture
and Decision]] holds the rationale and the migration history behind the rule.

A service that publishes its own artefacts into its own tables needs no
cross-service read, so DQ names its six functions =ores_dq_<plural>_publish_fn=
rather than =..._from_dq_fn=. The bring-up bootstrap is one of them.

The C++ side of that stage is no longer written per entity. One
=publish_from_dq_handler= per service derives the function name from the subject
it received: =refdata.v1.ops.publish_trading_account_types_from_dq= calls
=ores_refdata_publish_trading_account_types_from_dq_fn=, and DQ's
=dq.v1.ops.publish_coding_schemes_from_dq= calls
=ores_dq_coding_schemes_publish_fn=. DQ's derivation also checks the name against
an allow-list, because a wildcard subscription would otherwise let a publisher
choose the SQL it calls.

A service states its subjects in an operation model of type
=ores.codegen.operation= — =ores.refdata.publish_operations=,
=ores.marketdata.publish_operations=, =ores.reporting.operations= and
=ores.dq.publish_from_dq= among them — and the model generates the messages, the
subjects and the subscription. The synthetic service is the exception: it keeps
its subjects in =ores.synthetic.api/domain/step_subjects.hpp=. The SQL function
stays hand-written in every case; nothing generates it.

* What a generator owns today

This is the table to read before adding an artefact type.

| Artefact | State | Verdict |
|----------+-------+---------|
| Artefact staging table | Generated from the owning entity's model | Solved |
| Target entity model and table | Generated, ordinary entity codegen | Solved, and orthogonal to publishing |
| Workflow orchestration | Generated infrastructure, generic | Solved, zero marginal cost per type |
| Handler and registrar wiring | One derived handler per service; subjects from an operation model | Solved |
| Artefact-type registration row | Hand-written insert, though =target_subject= is derivable from the subject | Mechanical |
| Bundle and membership rows | Hand-written one-line upserts | Cheap to template, low value alone |
| Publish function SQL | Hand-written, 72 near-identical bodies | The remaining gap |
| Staged rows | Hand-written for FpML and the other external sources; each demonstration dataset has its own seeder script | Separate concern, migrating |

The publish functions are structurally alike: read the artefact table, honour the
mode, upsert into one target table by natural key. The story that would generate
them is
[[id:53116563-2667-48CD-941E-8521D3E42CBC][Codegen facet: generate the DQ
publish-from-dq pattern]], which proposes a facet that generates the function for
the homogeneous part of the family from a declaration on the entity's model.

** Worked example: =report_definitions= in the =risk_management= bundle

Every file the pipeline touches for one artefact type, in pipeline order.

1. Bundle row — [[proj:projects/ores.sql/populate/dq/dq_dataset_bundle_populate.sql][~projects/ores.sql/populate/dq/dq_dataset_bundle_populate.sql~]]
   registers the =risk_management= bundle and its level.

2. Bundle membership — [[proj:projects/ores.sql/populate/dq/dq_dataset_bundle_member_populate.sql][~projects/ores.sql/populate/dq/dq_dataset_bundle_member_populate.sql~]]
   maps the =ore.report_definitions= dataset into that bundle at =display_order
   40=, after business units, portfolios and books.

3. Artefact-type registration — [[proj:projects/ores.sql/populate/dq/dq_artefact_types_populate.sql][~projects/ores.sql/populate/dq/dq_artefact_types_populate.sql~]]
   registers the type, pointing =artefact_table= at
   =dq_report_definitions_artefact_tbl=, =target_table= at
   =reporting_report_definitions_tbl=, and =target_subject= at
   =reporting.v1.ops.publish_report_definitions_from_dq=.

4. Staging declaration — the owning entity model at 7 opts in with
   =:ores.sql.schema.domain_entity_artefact_create.enabled: true=. The staging
   shape is the entity's own columns, so no artefact-columns section is needed.

5. Generated staging table — [[proj:projects/ores.sql/create/dq/dq_report_definitions_artefact_create.sql][~projects/ores.sql/create/dq/dq_report_definitions_artefact_create.sql~]]
   creates =ores_dq_report_definitions_artefact_tbl=.

6. Dataset registration and seed data — [[proj:projects/ores.sql/populate/reporting/reporting_report_definitions_populate.sql][~projects/ores.sql/populate/reporting/reporting_report_definitions_populate.sql~]]
   registers the dataset and inserts the standard ORE analytics report rows into
   the staging table. This is a setup-time write into a DQ-owned table, not a
   runtime one; [[id:98B3572E-A9F9-45F5-A4C5-3DC23F3CFF70][DQ Publish Pattern]]
   distinguishes the two.

7. Target entity model — [[proj:projects/ores.reporting/modeling/ores.reporting.report_definition.org][~projects/ores.reporting/modeling/ores.reporting.report_definition.org~]]
   is the domain type. Items 5 and 8 are both generated from it.

8. Target table — [[proj:projects/ores.sql/create/reporting/reporting_report_definitions_create.sql][~projects/ores.sql/create/reporting/reporting_report_definitions_create.sql~]]
   creates =ores_reporting_report_definitions_tbl=, the constrained, party-scoped
   table that readers query.

9. Publish function — [[proj:projects/ores.sql/create/reporting/reporting_publish_from_dq_create.sql][~projects/ores.sql/create/reporting/reporting_publish_from_dq_create.sql~]]
   defines =ores_reporting_publish_report_definitions_from_dq_fn=. It is
   hand-written, and it is the gap named above.

10. Subject — the =reporting.v1.ops.publish_report_definitions_from_dq= subject
    is declared in [[proj:projects/ores.reporting/modeling/ores.reporting.operations.org][~projects/ores.reporting/modeling/ores.reporting.operations.org~]],
    which generates the message and the subscription.

11. Derived handler — [[proj:projects/ores.reporting/core/src/messaging/publish_from_dq_handler.cpp][~projects/ores.reporting/core/src/messaging/publish_from_dq_handler.cpp~]]
    receives the command, derives the function name from the subject and calls
    it. One handler serves every reporting subject.

12. Orchestration — [[proj:projects/ores.dq/core/include/ores.dq.core/messaging/publish_handler.hpp][~projects/ores.dq/core/include/ores.dq.core/messaging/publish_handler.hpp~]]
    turns the bundle into a request and
    [[proj:projects/ores.dq/api/include/ores.dq.api/workflow/bundle_publish_workflow.hpp][~projects/ores.dq/api/include/ores.dq.api/workflow/bundle_publish_workflow.hpp~]]
    turns the request into one step per dataset, dispatching to item 3's subject.

13. The call — =report_definitions= needs no publish-time parameters, so no
    parameter page exists for it. The callers are the shell's =bundles publish
    <code>=, a seed profile's =publish_bundle= step, which tenant provisioning and
    the web's new-tenant journey drive, and the bring-up bootstrap, which
    publishes the platform and world bundles directly.
