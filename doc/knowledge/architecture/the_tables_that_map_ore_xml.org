* Summary

Eight tables touch the ORE document. Only four are mappings in the strict
sense; two are staging, and two are inventories of a screen.

| Table | Maps | Kind |
|-------+------+------|
| =ores_reporting_ore_parameters_tbl= | =(scope, subtype, name)= and an =xpath= to a domain and its text | the parameter catalogue |
| =ores_dq_ore_parameters_artefact_tbl= | the same, staged from the guide | staging |
| =ores_reporting_ore_parameter_setting_value_sets_tbl= | a parameter to its set | link |
| =ores_reporting_ore_parameter_vocabularies_tbl= | an ORE element to its set | link |
| =ores_refdata_curve_configuration_columns_tbl= | a curve column to an element and an =xpath= | element map |
| =ores_refdata_convention_kind_terms_tbl= | a convention term to =(schema, xpath)= | element map |
| =ores_reporting_engine_settings_group_settings_tbl= | a part column to its =Setup= name | screen inventory |
| =ores_analytics_pricing_pair_settings_tbl= | a pair to the settings it takes | screen inventory |

The curve columns table, the convention kind terms and the vocabularies answer
one question three ways, which is the defect the normalisation story's first task
removes. Until then, a reader that needs "which set states this leaf" asks the
vocabularies table and treats the other two as the columns that carry the
element.
