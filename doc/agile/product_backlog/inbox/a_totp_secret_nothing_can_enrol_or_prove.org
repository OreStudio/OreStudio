This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Give an account a second factor it can enrol, prove and revoke.
=ores.iam.account_credential= already carries =totp_secret=, nullable and
=:no_wire:=, and nothing in the tree reads it or writes it: there is no
enrolment, no code verification and no way to turn a factor off. The column has
been a placeholder since it was written.

Three operations, addressed where the specification puts operations that are
not entity verbs:

#+begin_example
iam.v1.ops.totp-enrol     -- generate a secret for the caller's own account
iam.v1.ops.totp-verify    -- prove a code, which is what activates it
iam.v1.ops.totp-disable   -- remove the factor, proved by a code or a password
#+end_example

* Why

A password is one thing a person knows, and it leaks. The schema anticipated the
second factor and the product has never had one, so an account that should be
protected by something it holds is protected by a secret it may have reused
elsewhere.

The credentials split has just made this tractable and is the reason to write
the idea down now rather than later. The secret lives on the entity that owns
it, is nullable so an account without a factor says so honestly, is
=:no_wire:= so it cannot leave through a record read, and keeps a version
stream of its own, so enrolling or revoking a factor leaves the account's
profile history alone. A profile write cannot reach it. Before the split the
secret was a column on the account row, and the first profile write would have
cleared it exactly as it cleared the service password hash.

What the story that takes this has to decide, and none of it is obvious:

- *How the secret reaches the person, once.* =:no_wire:= skips the member in
  both directions, so the enrolment answer cannot be the credential record. It
  travels on a purpose-built field -- the base32 secret or the =otpauth://= URI
  -- the way =save_account_request.password= already carries a plaintext
  inward. Enrolment is the one moment a credential leaves the server, and it
  should be the only one.
- *Whether an unproved secret counts.* A secret that is written and never
  proved locks out whoever mistyped it. The ordinary shape is enrol, then
  verify, then active; the version stream supports it, since the row can hold
  the secret while the account carries the fact that the factor is not yet
  proven.
- *What login takes.* =iam.v1.auth.login= takes a username and a password, and
  a second factor changes that contract. Either the request grows a code field,
  or the password step yields a partial session that can present nothing but a
  code. The second is more work and does not tell a caller whether the password
  was right before the code is asked for.
- *How the secret is held at rest.* A password is hashed because nothing needs
  it back. A TOTP secret must be recovered to check a code, so it cannot be
  hashed, and it is a bearer secret of the same strength as a password. Whether
  that is acceptable, or whether it needs encryption with a key the database
  does not hold, is a decision this capture does not make.
- *Recovery when the factor is lost,* which is the delivery problem the tree
  does not yet solve and which the capture below already names.
