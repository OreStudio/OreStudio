* Goal

A service's PostgreSQL listener keeps up with a burst of notifications. Before
this, =postgres_listener_service= paused 100 ms after every poll, even with
notifications waiting, so it read at most one socket's worth per pause: about
460 notifications a second. A bulk import fires one notification per row, so
prime_origin's corpus imports left the marketdata service's listener hours
behind. PostgreSQL held its backend in =ClientWrite= the whole time, and on the
shared server that backend stalled every other environment's =DROP DATABASE=,
twice in one day.

* Decisions

* Out of scope

- One notification per row for bulk tables. The notify triggers are generated
  per row for all 298 tables; a bulk import of 100,000 observations still
  sends 100,000 notifications and 100,000 NATS events. Captured separately.
- The event bus logging every event at INFO, which wrote 566,867 log lines in
  this incident. Captured separately.

* Result

The listener paused 100 ms after every poll, so it read at most one socket's
worth of notifications per pause. It now pauses only when a poll finds
nothing. The reproduction drains 135 times faster, and a corpus import with the
service running leaves no backend in =ClientWrite=. The per-row triggers and
the per-event logging that made the burst so large are captured.
