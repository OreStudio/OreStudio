Live run of a provisioning run that stops on its failed step and is retried to
completion, 2026-09-28, environment eager_maxwell, branch
feature/follow-the-progress-and-retry-the-failed-step.

The database and the NATS store were recreated, the fleet started on the
branch's binaries, and the initial administrator bootstrapped. The failure was
made by retiring one dataset the photo step reads, so the step fails for a
reason a person can fix; nothing else in the deployment was disturbed:

  update ores_dq_datasets_tbl set valid_to = clock_timestamp()
   where code = 'acme.acme_hk.accounts'
     and valid_to = ores_utility_infinity_timestamp_fn();
  -- UPDATE 1

The run stopped where it failed, with the error standing against the step and
every completed step kept. Nothing was rolled back: the state is failed, not
compensated, which is the stop-and-retry policy this unit landed.

The cause was then removed, and the retry asked for through the same route:

  update ores_dq_datasets_tbl set valid_to = ores_utility_infinity_timestamp_fn()
   where code = 'acme.acme_hk.accounts'
     and valid_to <> ores_utility_infinity_timestamp_fn();
  -- UPDATE 1

  POST /api/provision-tenant/ae5b2b6e-.../retry  {"stepName":""}

  {"success":true,"message":"","instanceId":"ae5b2b6e-011a-483c-8bbb-4750e5dc3773",
   "stepIndex":4,"stepName":"attach_photos"}

What this proves, against the task's acceptance:

- the read the page follows answers the run's status, its error, the step it is
  executing, and one summary per step naming the step, its state and its error;
- a step that fails stops the run, which is the policy the definition declares
  and the engine now reads;
- the retry resumes the run from the step that failed, under that step's own
  identity, clears the run's error, and leaves every completed step and its
  result alone;
- the run completes after a retry, and the browser reaches both the read and the
  retry through its own routes;
- the run belongs to the tenant that asked for it, so the person who provisioned
  the tenant is the person who can watch and resume it.

One defect this unit surfaced, captured for the component that owns it: a step
command is published fire-and-forget, so a command whose service is stopped at
that instant is lost, and the run waits for ever on a step that will never
answer. Stopping the marketdata and assets services to provoke a failure
produced exactly that — stalled runs, no error and no failed step — and only a
workflow-service restart moved them.
