* Plan

** The problem

Booking writes the trade, the activity, the booking and the state in one
SQL function, =ores_trading_book_trade_fn=. The function bypasses the
generated repositories. The task moves the four writes onto the
repositories and keeps them atomic.

** The seam

Every repository write calls =execute_write_query=, defined once in
=projects/ores.database/include/ores.database/repository/bitemporal_operations.hpp=.
The helper calls =session(ctx.connection_pool())=, begins a transaction,
writes, and commits. The read helper opens its own session in the same
way. Current-state entities are a second shape: 33 generated repositories
inline the same session/begin/commit in the template at
=cpp_domain_type_repository.cpp.mustache=, and current-state reads use the
same read helper.

** The chosen seam: a transaction bound to the context

The unit of work binds one transaction to the =context= that every
repository already takes. This is the shape sqlc uses with
=WithTx=. The service opens the boundary; the repositories join it.

- =ores::database::unit_of_work= owns one pooled session and one
  =sqlgen::Transaction=. It yields a =context= bound to that transaction.
  =commit()= ends it; the destructor rolls back when the caller forgets.
- =context= carries the transaction as an owning =rfl::Ref=, so a copy
  carries it too and no lifetime rule is needed.
- =execute_read_query=, =execute_write_query= and the current-state
  template path use the active transaction when the context carries one.
  Without one they open a session as they do today.
- Repository signatures and all 343 call sites stay.
- Reads must join, because =replace_claim= reads before it writes.
- A service sets the tenant and the party before it opens the unit of
  work. A held connection cannot change tenant inside a transaction.

** Phases

1. Unit of work in =ores.database=, as above.
2. Booking onto the repositories. =trade_operations_service::book_trade=
   opens one unit of work and writes the trade with a =must_not_exist=

3. Delete =ores_trading_book_trade_fn= and update the drop file. Rewrite

4. State the rule in =projects/modeling/system_model.org=. Add

** Decision: a transaction bound to the context

Taken 2026-10-06 with the owner. The unit of work binds one transaction to
the =context= the repositories already take. This is the sqlc =WithTx=
shape. The alternatives were an ambient thread-local transaction (rejected:
no DI framework, hidden control flow) and an explicit =unit_of_work&=
parameter on every repository (rejected: it forces every single-statement
write to open a transaction, and it changes 343 call sites).

The binding fact: =rfl::Ref= is an owning, copyable handle, so a =context=
copy carries the transaction safely. No raw pointer and no lifetime rule
are needed.

** Implementation: the unit of work

- =ores.database/repository/unit_of_work.hpp= owns one pooled session and
  one =sqlgen::Transaction=. It yields a =context= bound to that
  transaction, commits once, and rolls back on destruction.
- =context= carries the transaction as an optional owning =rfl::Ref=. A
  copy carries it, and =with_tenant= and =with_party= preserve it.
- =execute_write_op= is new. =execute_read_query=,
  =execute_write_query= and =execute_delete_query= join the context's
  transaction when it has one, and otherwise open their own session as
  before.
- The repository template's current-state path now calls
  =execute_write_op= instead of opening its own session. 21 generated
  repositories in the drift-free components under test are regenerated.
- =ores.database.tests.unit_of_work_tests= checks the binding and the
  rollback.

** Known offenders for the architectural check

Three hand-written writes still open their own session and so do not join
a unit of work:

- =ores.telemetry.database/repository/telemetry_repository.cpp=
- =ores.reporting.core/repository/report_input_bundle_repository.cpp=
- =ores.iam.core/repository/session_repository.cpp=, its
  =update_session_counters= and =end_session=.

=ores.synthetic= and =ores.scheduler= carry current-state repositories
whose generated output has pre-existing drift. This change leaves them
alone. Regenerating them would mix their drift into the booking change.

** The sqlgen read that commits the unit of work

Found 2026-10-06 while moving booking onto the repositories. sqlgen's
postgres iterator wraps every read in its own =BEGIN= and =END=, and
PostgreSQL reads =END= as =COMMIT=. A read inside a unit of work therefore
commits it. The booking service's conflict read and every repository
=apply_claim= read committed the transaction before the failing write, so
the anchor and the activity stayed while the booking failed.

=book_trade= reads inside its unit of work again, and states a
=must_not_exist= claim for each of the four writes.

The tracked overlay at =build/cmake/overlays/common/sqlgen= lists
=fix-iterator-transaction.patch=. The patch asks =PQtransactionStatus=
whether the iterator joined a transaction, and runs no =BEGIN= and no =END=
when it did. sqlgen =0.8.0#2= carries it.

Verified 2026-10-06 with sqlgen =0.8.0#2=: =ores.database.tests= passes, 138
assertions across 39 cases, including "a read inside a unit of work does not
commit it"; =ores.trading.core.tests= passes, 886 assertions across 127 cases,
with the NATS server running. The memory
[[id:9562C34E-5790-422D-8E31-774691995860][A read inside a unit of work commits it]] carries the rule.

Raised upstream as munich-data-engineering/sqlgen#140. The port's =0.8.0= is
this project's own label for the pinned commit; upstream's tags stop at
=v0.6.0= and its =CMakeLists.txt= still declares =0.6.0=. The portfile records
that the commit is the thing to track. Raised as munich-data-engineering/sqlgen#141
and closed by the owner.

* Result

Merged on 2026-10-07 as [[https://github.com/OreStudio/OreStudio/pull/2718][#2718]], on top of #2672 and #2680.

** What landed

- =ores::database::unit_of_work= binds one transaction to a =context=;
  the repository read, write and delete helpers join it when the context
  carries one and open their own session when it does not.
- =book_trade= opens one unit of work and writes the trade, the activity,
  the booking and the state through their repositories, each with a
  =must_not_exist= claim.
- =ores_trading_book_trade_fn= is deleted, and the two pgTAP files that
  called it are rewritten.
- =check_entity_table_writes.py= states the rule with a ratchet baseline,
  runs on every pull request, and records the purge and the fixtures as
  its exceptions.
- The sqlgen overlay carries =fix-iterator-transaction.patch=, which stops
  the postgres iterator from ending an enclosing transaction on a read.
  The port is =0.8.0#2=.

** What was verified

=ctest= is 93 of 94 suites and 9370 of 9371 assertions at =8ea91a2421=.
The unit of work suite passes 39 cases and 138 assertions; the booking
suite passes 127 cases and 886 assertions. Each of the 18 test targets
that crashed before this work now builds and passes.

** What is open

=ores.scheduler.api.tests= fails one case. It asserts that =0 9 1 * 1=
matches on either restricted day field, so the next match after Tuesday
2026-10-06 is Monday 2026-10-12; the engine returns Monday 2026-02-01,
which is the *and* reading. No file in this task's diff touches
=ores.scheduler=, and the test binary and the scheduler library were both
rebuilt from this tree.

The pgTAP trading suites cannot run in this environment. Every failure is
a NULL party or counterparty read from the system tenant, which carries
one party and none of the counterparties the tests index with =offset 1=.
The suites passed against the database that predates the =compass db
recreate= this verification required.
