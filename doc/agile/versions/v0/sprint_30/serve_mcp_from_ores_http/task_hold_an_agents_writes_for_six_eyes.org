* Goal

An agent's write does not apply. It raises an approval request in the existing four-eyes framework, which its person approves first; the write then needs whatever approval a person's own write would need, by someone who is neither the agent nor its person. Every agent write is held unless an approval policy rule exempts it, so the approval policy gains the condition made by an agent. A trade an agent books is approved by its person and then authorised through the existing trade authorisation, by an authoriser who is neither.

* Acceptance

- A write made with an agent's token raises an approval request and changes nothing until it is approved.
- A read made with an agent's token is not held. A write the token's permissions do not cover is refused before any approval request is raised.
- The approval queue, trade authorisation and IAM's write handlers refuse a token whose =act= names an agent, whatever permissions it carries.
- The person the agent acts for approves first, and the agent can never approve. The further approval a person's own write would need is given by someone other than the agent's person; when nobody else holds that right, the request stays pending and the review panel says it has no eligible approver.
- A trade booked by an agent, once its person approves, enters trade authorisation, and its authoriser is neither the agent's person nor the agent.
- An approval policy rule can exempt an agent write, and without a rule every agent write is held.
- The review panel shows that a request was raised by an agent, for whom.

* Plan

The four-eyes framework gates a write through typed pending tables, one per
gated entity. An agent may write any entity, so a pending table per entity is
not the hold. The gateway is: every agent write passes ores.http, and the held
change is the call itself. The person's approval replays the call, as the
person with the agent as actor, and the replay meets exactly the controls the
person's own write would: a gated entity raises its own request, decided by
others under the four-eyes rule; a trade goes live unauthorised and enters
trade authorisation. That is the six eyes.

1. Inbox: an =iam.write_by_agent= kind; a request an agent raised (its
   =acting_agent= stamp) is decided only by the person it was raised for, and
   the queue offers it to them alone.
2. The second line: the queue, trade authorisation and IAM's writes refuse a
   token whose =act= names an agent, from rules shared with IAM's withholding.
3. The hold: ores.http raises the request with the agent's token, keeps the
   call (method, path, body) as a held write, and answers 202 with the request.
4. The replay: on the request's approval ores.http claims the held write, asks
   IAM for a replay token naming the person and the agent, runs the call
   through its own routes, and marks the request failed when it does not apply.
5. Exemption: an approval policy row exempts an agent write by route.
6. The review panel shows the held call and the agent and person.
7. Trades: trade authorisation refuses the agent and the agent's person.

* Result

An LLM agent's write is held at the gateway: ores.http raises an
=iam.write_by_agent= approval request with the agent's own token, keeps the call
itself, and answers 202 with the request. Reads, POST operations that only
read, and writes a policy row exempts run as any other, and a token that can
write nothing is refused at once. The request is its person's alone to decide:
the queue offers it to them only, the decisions table refuses anyone else, only
an agent can raise the kind, and no agent can decide anything, because every
service refuses a withheld permission, decisions included, to an agent's token
and the queue refuses its decision outright. Approval replays the call through
ores.http as the person with the agent as actor, under a token IAM issues for
that held write alone, so the write meets the controls the person's own would:
a gated write raises its own request for others to decide, and a booking goes
live unauthorised for Operations. A replay the service refuses fails the
request with the service's reason. The review panel shows the agent, the call
and its outcome.
