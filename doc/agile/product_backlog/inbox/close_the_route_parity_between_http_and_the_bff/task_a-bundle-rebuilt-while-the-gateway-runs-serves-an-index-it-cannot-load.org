* Acceptance

- A bundle published under a running gateway is served whole: the index and every asset it names come from the same build.
- A test publishes a new bundle under a running server, then reads the index and one asset it names.
- An asset that is not there answers 404 that names the file, so the screen fails loudly instead of blank.

* Plan

The two halves of the answer disagreed. =file()= reads every body from disk at
request time, so the index a browser loads is whatever the build last wrote. The
manifest, though, is a snapshot taken when the server starts, and it is the only
thing a path is resolved against. A build that publishes while the server runs
therefore served the new index and refused the hashed asset it named, and the
browser showed a blank page until a restart.

The fix is the first of the two the goal offers, and the smaller one: a path the
snapshot does not hold is asked of the directory before it is refused. Nothing
is written back into the manifest, so there is no lock and no shared mutable
state across sessions: the manifest stays the one table a request is resolved
against, and a miss costs one =stat=.

Rebuilding the whole manifest when =index.html= changes was the other option,
and it is worse here: it needs a lock on the table every request reads, and it
would rescan a directory of hundreds of files because one of them changed.

The rules that keep a request inside the bundle are applied by
=bundle_manifest::read= as they are by the scan: a component that climbs out of
the root finds nothing, and a dot file is the build's own. The bundle's own
answer stays what it was: an API path is refused rather than served the shell, a
screen path still gets the shell, and a path that would leave the root is a
screen path and gets the shell, which is what its test states.

Only the =assets/= prefix takes the new path, and that is deliberate: an asset is
a file the build wrote, so its absence is a breakage worth saying, while a path
outside =assets/= is a screen and a screen is the application. A missing asset
answers the 404 the previous change put in the contract, naming the file.

* Notes

The two cases are in =projects/ores.http/core/tests/web_bundle_routes_tests.cpp=.
The first publishes under a running server, exactly as a build does: it writes a
new asset and an index that names only it, then reads the index and fetches the
asset it names, asserting the content type and the immutable cache rule as well
as the bytes. Without the change that fetch is a 404, which is the blank page.

The second fetches an asset neither the build nor the directory holds, and
asserts the 404 carries the contract's code and names the file. The refusal a
screen sees therefore says =gone-ZZZZ0000.js= rather than leaving the browser to
fail at a script tag.

The fixture's =write= was private, because nothing published after the bundle
was built; it is public now, which is what makes the case possible.

* Promoted from capture

Captured 2026-11-22 in the product backlog; promoted preserving the UUID.

** What

Make the served bundle follow the directory it is served from: when a file under
=assets/= is asked for and the startup list does not hold it, read it from the
directory and serve it, or rebuild the list when =index.html= changes.

** Why

=web_bundle_routes= takes a manifest of the web directory in its constructor and
answers every request from it, while the index is read from disk each time:

#+begin_src cpp
web_bundle_routes::web_bundle_routes(std::filesystem::path root)
    : manifest_(std::move(root)) {
    ...  // "Serving the browser bundle from ... (N files)"
}
#+end_src

So after a build the two disagree. Observed on 2026-11-22: the build finished at
15:04:41 and published =assets/index-nra1mBrk.js= at 15:03, while the gateway had
started at 15:02 with the previous manifest. The browser asked for the index, was
given the file from disk naming =index-nra1mBrk.js=, asked for it, and was
answered 404 by the same server:

#+begin_src
bad 404 http://localhost:20401/assets/index-nra1mBrk.js
script tags: /assets/index-nra1mBrk.js
#+end_src

The page is blank, with no console error beyond the failed load, so it reads as a
broken build rather than a stale one. Restarting the gateway fixes it, which is
what happened.

This bites hardest while the port runs, because a bundle rebuild is routine and
the gateway is not restarted on every one.

* Result

A bundle published under a running gateway is served whole. The index was
already read from disk on every request, so the browser followed the new build;
the manifest was not, and it refused the assets the new index named. A path the
startup scan does not hold is now read from the directory before it is refused,
so the index and every file it names come from the same build and no restart is
needed.

The manifest stays the only table a request is resolved against and is never
written back, so nothing is shared mutably across sessions and a miss costs one
=stat=. The rules that keep a request inside the bundle are applied by the read
as by the scan, and only the =assets/= prefix takes the new path: an API path is
still refused rather than served the shell, and a screen path still gets the
application.

A missing asset answers the contract's 404 and names the file, so a screen fails
loudly instead of loading a bundle that cannot work.

Proved: the two new cases, and the HTTP core suite with them. Not proved: a real
publish under the running fleet, which is a build-and-restart the local tests
imitate rather than perform.
