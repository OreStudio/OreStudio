* Goal

Make the reporting path's workunit reach a wrapper and run. The original note
listed three defects in the submit path; the run-token task moved submission
onto the compute dispatcher and closed one of them, so two remain:

- *The subject has no consumer.* The dispatcher publishes each assignment on
  =compute.v1.work.assignments.{run_tenant}.{platform}=, and every wrapper
  subscribes on its own configured tenant, the system tenant, so a tenant's
  run is published where nobody listens. The platform's wrapper fleet is the
  deployment's shared pool and must consume every tenant's work.
- *The input URI is the wrong shape.* =prepare_ore_package= answers with
  =ores/ore/packages/{instance}/ore_package.tar.gz=, a bucket and key, and the
  wrapper fetches it over the storage HTTP interface, which speaks
  =/api/v1/storage/{bucket}/{key}=. The package and output URIs the dispatcher
  sets are already paths.

* Acceptance

- A workunit submitted through the reporting path is picked up by a wrapper and executes.
- The wrapper can download the package and the input, and has somewhere to put the output.
- The subject, the URI shape and the workunit fields match what the working dispatcher produces.

* Plan

The subject fix belongs in the wrapper, not the dispatcher: the stream already
captures =assignments.>=, and the tenant segment is the routing key a tenant's
own pool will filter on later, so the shared fleet widens its consumer to
=assignments.*.{platform}= and keeps the tenant in the subject. The node's
=--tenant-id= stays its own identity for the host row and telemetry; it is no
longer a filter on the work it takes.

The URI fix belongs where the URI is built: =prepare_ore_package= builds it with
=storage_paths::make_object_path=, the same helper the compute dispatcher uses
for the package and the output.

* Notes

The live run reached the wrapper. Run =f8275ac1-1ac5-4e2e-a485-97324ef3b13e=,
tenant =51e855c0-ce99-4726-a590-7272c89cf8b1=:

- The wrapper subscribes to
  =compute.v1.work.assignments.*.x64-linux= (durable
  =compute_wrapper_shared_x64-linux=), and at 14:24:57 it took the run's
  assignment. Defect 1 is closed.
- The attempted package URL is
  =http://localhost:20600/api/v1/storage/ores/compute/packages/ORE-1.8.17.0/...=,
  the path shape storage speaks. Defect 3 is closed for the package; the input
  is built by the same helper.
- It then failed =HTTP 401=. =ores.compute.wrapper= has no storage credential
  at all: =application.cpp= passes a =constexpr= empty =storage_bearer_token=
  to every get and put. A node needs a credential before it can download, and
  the design says that credential is the per-assignment capability
  [[id:F37D960D-9687-47DC-8737-605CA38D0CF2][Storage policy]] describes, which
  the [[id:0B573887-5101-4D91-9288-38F0C0AE3E06][isolation story]] owns. This
  task waits on it rather than inventing a standing service token the policy
  would replace.

A second finding: the JetStream assignments stream survives a database
recreate. On the recreated environment the wrapper replayed assignments from
the previous one and answered =results.submit failed: Result not found= for
each, because the result rows were gone. The smoke-test story's "reproducible
from a freshly recreated database" acceptance will meet this; the stream wants
purging, or the handler wants to treat an unknown result as an expiry rather
than an error.
