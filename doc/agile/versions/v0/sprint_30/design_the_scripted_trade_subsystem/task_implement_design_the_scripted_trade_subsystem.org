project's knowledge standard, as the target state the story's later tasks build

* Plan

First survey what the pages above and the code state today, then write one page
per claim. The claims agreed with the user on 2026-11-21, each a candidate page:

- A product is booked in one of the forms it offers: its own element, a
  ScriptedTrade over a library script, or both.
- Every product has a schema of its fields and its forms, which a booking form,
  the shell, import and the generator all read.
- A scripted trade names a library script and version, or states its script
  inline; ORE accepts either.
- The script library is versioned reference data; a trade states the version it
  was booked on, and a correction to ORE's library is a version of its own.
- A script's free variables are its inputs, and the inputs of a script with no
  element of its own are that product's schema.
- A twin recipe maps a native product's terms onto its script's inputs.
- ORE's grammar is the one authority on whether a script parses: its Boost
  Spirit parser is copied into =ores.trading.scripting= with its authorship,
  kept diffable against ORE's, and shaped to ORE Studio's standards.
- A scripted trade is validated in three layers: the editor's grammar as a
  convenience, ORE's grammar on the server, and ORE's build of the trade.
- The editor's tree-sitter grammar is tested against ORE's parser on the
  library and on scripts ORE's random AST generator writes.
- The engine is given a script's text; any compiled form of it, a syntax tree,
  a computation graph or a device kernel, is a cache of one run.
- One booking API books a product in either of its forms, and a free-form
  scripted trade through the same validation.
- ores.shell has commands to parse and validate a script and to describe a
  product, and the ones that read no store need no login.
- The generator draws each product's terms against its schema and books every
  product and form through the booking API, so the path a person books on is
  the path the tests prove; ORE values each.
- The components of the subsystem and their dependency graph, with no cycle.

The gaps today's code shows, to be named on the pages: script-only products are
booked from a carrier native type's rows, not drawn against their own schema;
the script inputs are mined into the seed, not derived by a parser; no trade
states a script version; scripts whose product has an element of its own
(the accumulators, TaRF, the outperformance option, the basket and rainbow
variants) have no scripted form; nothing parses a script before ORE does.

* Notes

** The pages state only the target

On review the user asked that the pages describe only the state after the story,
not the code as it stands. The gaps the plan meant to name on the pages, a
"Divergence from the current implementation" section on each, were removed;
every gap was first checked to be an acceptance criterion of one of the story's
tasks.

** What the survey found

- The architecture lives where the rule of one component reading every ORE
  document puts it ([[id:9697F09E-441A-4B51-869E-FC59433EEA1E][One component reads every ORE document, and none of them stores XML]]): a script's text is trading's data,
  not an ORE document, so its parser belongs to =ores.trading=. ORE's parser
  needs only Boost Spirit and a few header-only QuantLib types, so the copy can
  replace those and link no QuantLib.
- =ores.analytics.quant= is the precedent for a dependency-light specialist
  sub-component consumed for what it computes; =ores.trading.scripting= takes
  that role, below =ores.trading.api=, and returns its own types so the API can
  depend on it with no cycle.
- The seed's script inputs are mined from the code by a text script that
  compass-ng now runs; the seed's header still names the retired
  =generate_script_library.py=.
- Generic Scripted Products already states ORE's side, the language and the two
  places a script may live, so the new pages link it rather than restate it.
- The catalogue's =Scripted forms= prose said a product absent from it has no
  library script in ORE; the =Library scripts= table shows several that do, so
  the prose now says so.
