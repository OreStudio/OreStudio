* Goal

The bitemporal sentinel (the =valid_to= value of current rows,
=9999-12-31 23:59:59=) must mean the same instant in every session,
regardless of the session's TimeZone setting. Today it does not:
=ores_utility_infinity_timestamp_fn()= returns a naive literal
(=utility_functions_create.sql:38=) that folds per session TimeZone,
and the function is declared =IMMUTABLE=, so the planner folds it at
plan time and can prove a partial index's predicate
(=valid_to = ores_utility_infinity_timestamp_fn()=) equivalent to the
app's own naive-literal condition -- dropping or mismatching the
=valid_to= filter when the session TimeZone shifts the fold. Demonstrated
live in an America/New_York session: a repository query returned a row
violating its own WHERE clause (=sel_match = f=), and count vs detail
disagree because the drop is plan-dependent. Observed damage: the wizard
leg's =account_service::logout= warned "Attempted to logout non-existent
account: 019fee78-…" for tenant_admin at 02:47:17/02:48:14 -- its
=read_latest(id)= (id + sentinel predicate) returned empty in a non-UTC
session -- and =ores_iam_login_info_tbl.online = 1= for that account was
left stale.

The fix has three parts: (A) the function returns the explicit UTC
instant ='9999-12-31 23:59:59+00'::timestamptz= so its fold is
TimeZone-independent; (B) every application DB session forces UTC --
audit the DQ engine, workflow, and any other connection sites missing
the forcing the pool and bitemporal repository already apply (the
app's naive literal stays, so UTC sessions are required for correct
reads); (C) verify in New York/Tokyo sessions and clear the stale
=online= flag. Migrating to ='infinity'::timestamptz= (B2) is
deliberately deferred: 395 naive-literal sites across 191 files make
it a large, independent change.

* Result

All three parts implemented and verified live (2026-08-11) on the
=ores_dev_prime_origin= DB. Fix A and B committed; fix C executed
against the live DB (function applied via =CREATE OR REPLACE= with
the committed body, then verified):

- Same instant in every session: =ores_utility_infinity_timestamp_fn()=
  renders =9999-12-31 23:59:59+00= in a UTC session,
  =9999-12-31 18:59:59-05= in =America/New_York=, and
  =10000-01-01 08:59:59+09= in =Asia/Tokyo= — epoch
  =253402300799= in all three. The naive literal still folds per
  session (NY: =9999-12-31 23:59:59-05=), but the planner can no
  longer prove it equivalent to the function's fold, so the
  partial-index predicates hold.
- Repository query (=ores_iam_accounts_tbl=, id =019fee78-…=,
  =valid_to = '9999-12-31 23:59:59'=): in the UTC session the app
  actually uses (fix B forces every session to UTC) it returns the
  tenant_admin row with =sel_match = t= and count = 1 = detail. In a
  NY/Tokyo session it returns a safe empty — the F16 wrong-row
  result (=sel_match = f=, a row violating its own WHERE) is gone.
- =EXPLAIN= in a NY session: the =valid_to= Filter is retained
  (index scan on the exclusion index, filter on the heap) — never
  dropped as F16's equivalence proof dropped it.
- Stale flag: =ores_iam_login_info_tbl.online = 1= for
  =019fee78-ea2e-714d-8693-ddd295080d7b= (left by the failed logout
  at 02:47:17/02:48:14) cleared to =0=.

Note on the acceptance wording: "the repository query returns the
current row with =sel_match = t= in NY/Tokyo sessions" holds for the
UTC sessions fix B enforces on every app connection. In stray
non-UTC sessions the naive app literal still folds away from the
sentinel, so the query correctly returns nothing — the fix removes
the wrong-row drop, not the naive literal itself (migration to
='infinity'::timestamptz= is the deferred B2 cure for stray
sessions).
