The chain a book's approval is stated by has three levels, and one function
resolves them: =ores_refdata_book_allowed_product_types_fn=. A caller that has to
know what a book permits must not read the three junction tables and resolve them
itself, because two statements of one rule drift apart. It asks this operation
instead, and the answer is the resolution's own.

The callers are the ones that choose before they write. The synthetic trade
generator is the first: it reads each book's set to choose the products it books
there, so the matrix constrains the population rather than being discovered when
a booking is refused.

The handler is hand-written beside this model, because the answer is a table
function rather than a row of an entity.

** book_product_approval

#+begin_src cpp :name comment
/**
 * @brief The product types one book permits, as the chain resolves them.
 *
 * The set is absent when the book, its desk and its party all restrict nothing,
 * because no level then names a type the catalogue does not: every type is
 * permitted. The set is empty when a level restricts and names nothing, which
 * permits none. A caller that folded the two together would read an open book
 * and a shut one alike.
 */
#+end_src
