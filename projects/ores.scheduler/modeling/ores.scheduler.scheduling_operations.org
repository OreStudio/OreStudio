The scheduler's two operational reads, both served to the scheduler monitor
view: the execution history across every job, and the live status of every job
the scheduler holds.

Both are computed views rather than stored rows, which is why they are
operations and not entity verbs. The instance list is a join: a stored
=job_instance= row carries only its definition's identifier, and the view adds
the job's own name and action type so a caller can render the row without a
second round trip. The status view is computed twice over: it folds each
definition together with its most recent instance, and it derives the next fire
time by asking the cron expression. Neither shape is a row a caller addresses by
key, so neither is derived from an entity.

The handlers that serve them stay hand-written beside this model, because the
instance read joins two repositories and the status read evaluates cron
expressions. An operation model generates no service handler.
