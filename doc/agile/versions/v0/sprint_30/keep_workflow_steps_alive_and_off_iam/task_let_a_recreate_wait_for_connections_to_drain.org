* Acceptance

- compass db recreate -k waits a bounded time for the environment's connections to close before it refuses.
- Stopping the services and recreating the database succeed back to back.

* Plan

1. Widen the drain window in =check_connections(kill=True)=, from the 10
   seconds it waits today to a bounded minute, and keep it bounded: a backend
   that never closes must still fail the recreate rather than hang it. The
   wait reports how many connections remain, so a run that waits says so.
2. Keep the refusal honest without =-k=. Terminating a backend is the
   caller's decision, so a recreate that was not told to kill still refuses at
   once, and the hint stays.
3. Move the deadline into one named constant, so the window the wait uses and
   the window the tests state are the same number.
4. Update =test_compass_db_connections.py=: its deadline case counts the kill
   rounds, so it changes with the window. Add a case that the wait reports the
   connections it is waiting for.
5. Prove it against the real environment: stop the services, then recreate
   back to back, which is the acceptance line the story recorded as failing.

* Notes

- The refusal is a 10 second wait in =check_connections=, in
  =projects/ores.compass/src/compass_db.py=. After it terminates the backends,
  it polls every half second until the count is zero or the deadline passes,
  and the deadline is short: the story recorded a recreate refusing while the
  stopped services' connections drained for about 15 seconds. The wait is
  already the right shape, so the work is its window and what it says, not its
  algorithm.
- The function is well covered: =test_compass_db_connections.py= already pins
  the kill path, the deadline path and the refusal without =-k=, through a
  stand-in for =psql=. The deadline case counts the kill rounds, which is how
  the current window was measured.
- The story's evidence names the failing shape concretely: =compass db recreate
  -k= refused while the connections of 25 stopped services drained.
