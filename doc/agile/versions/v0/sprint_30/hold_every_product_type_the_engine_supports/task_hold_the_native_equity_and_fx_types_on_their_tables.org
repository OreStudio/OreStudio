* Acceptance

- each of the five types routes to an equity or fx table (new, or an existing one
  extended), whose columns hold every scalar term the
  element states; lists, baskets and schedules are rows of child tables or of
  the shared rows (options, barriers, underlyings, schedules)
- the projection reads and writes the element from those rows, value for value,
  and a round-trip test reads ORE's or the user guide's example and writes it back
- the builder states the rows, and the generator books the element form
- the class-read entry for the type is removed: the scripted instrument table
  holds no element form of it, only the generic ScriptedTrade form where ORE's
  library carries one
- the catalogue names both forms of the type where ORE carries both
- the ORE engine test reads and builds each, with no error of the trade kind
- every fact the element states is a column or a row: nothing is held as text

* Plan

- *EquityFutureOption* is an equity option with a future expiry, so it goes on
  the equity option table with one new column, =future_expiry_date=, and a check
  that only the future option states it. The reader and writer pick the element
  by trade type.
- *CashPosition* gets =cash_position_instruments= (currency, amount) in the
  equity family, where the catalogue groups it.
- *EquityPairwiseVarianceSwap* and *FxPairwiseVarianceSwap* each get a table,
  one per family, as the single-name variance swaps do. ORE requires exactly two
  underlyings, so each member's index, strike and notional is a column pair.
  The basket terms, the pay currency, the settlement date and the optional
  accrual lag, payoff limit, cap and floor are columns. The valuation schedule
  and the lagged valuation schedule are instrument schedule rows. One header,
  =pairwise_variance_swap_projection.hpp=, reads and writes the element for
  both rows, and one header, =pairwise_variance_swap_terms.hpp=, builds the
  row for both builders.
- *FxAsianOption* gets =fx_asian_option_instruments= (index, currency,
  notional, strike, option type, position, expiry, settlement). The OptionData
  block, the Underlying block and the observation dates are the shared option,
  underlying and schedule rows, as the equity Asian option holds them.
- The four builders move from the scripted family to the equity and FX
  families and return their tables' rows. The planner books them through
  those builders. The class-read entries for all five are removed.
- The catalogue gains a list of the scripted forms: the library script that
  books a product as the generic =ScriptedTrade=. Of the five, only the
  pairwise swaps have one (=PairwiseVarianceSwap=); ORE's library holds no
  script for an equity future option, a cash position or a single-underlying
  FX Asian option.
- The models are written by a script from a column list, so the four tables
  share the forward model's identity, keys and C++ section; the hand-written
  wiring (variant, carrier, batch join, export, registrars, digest observers,
  event mappings) is applied by a second script.

* Notes

The type was first held on the scripted instrument table through the
class-read path, as parameter rows. That held every value but gave the element
no table of its own, against the story's rule that a product ORE carries in
both forms is held in both, and that the forms can be compared. ORE builds all five natively.

* Result

The five native equity and FX types are held in their own shape.
EquityFutureOption is on the equity option table with a =future_expiry_date=
column. CashPosition, EquityPairwiseVarianceSwap, FxPairwiseVarianceSwap and
FxAsianOption each have a table of their own, with every scalar term as a
column and their option, underlying and schedule blocks as shared rows. The
projection reads and writes each element from those rows, and a round-trip
test covers each type, including a new one for the FX pairwise swap. The four
builders now return their tables' rows, and the planner books them through
those builders. The class-read list shrank from 28 to 23 entries. The
generated trades of all five pass the ORE engine check, recorded twice.

The catalogue gained a list of scripted forms. It names =PairwiseVarianceSwap=
for both pairwise swaps. ORE's library has no script for the other three, so
they are held in their own form only.

Two defects were found on the way. A table base longer than 51 characters is
silently cut in SQL while the C++ keeps the full name, so the equity pairwise
model states a shorter =:tablename:=, and the defect is filed as a capture. The
pairwise scalars are free-style nodes whose value is their own text, so the
shared pairwise reader handles them that way.
