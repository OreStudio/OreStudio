#+title: Investigation: FX family data model review
#+description: The seven FX instrument models and their generated artefacts reviewed against the Regime 2 data-oriented design checklist: what holds, what does not, and which findings are recorded deferrals.
#+type: investigation

A point-in-time record of a review of the FX instrument family against
[[id:BBD43BF2-9FEE-42B0-A667-9468AF759DC2][Data-Oriented Design in ORE Studio]],
Regime 2, the persisted domain data, plus the Regime 3 projection of the one
field that carries an encoded document.

The family is the second of the instrument families reviewed with this lens.
Bonds were the pilot and were reworked to the method; the FX family was not,
so this review asks whether the tree meets the guidelines rather than whether
it was built to them.

* Context

The FX family holds 26 trade-type codes in
=ores.trading.trade_type_catalogue.org=. Sixteen of them route to one of
seven instrument tables. The seven models are flat, single-row instruments
keyed by the trade; there is no FX family header, no per-product fact table
and no shared child table, unlike the rates and bonds families.

The review was commissioned to establish, with evidence, whether that model
meets the Regime 2 checklist, and to separate a defect from a recorded
decision.

* Methodology

The family is seven entity models under =projects/ores.trading/modeling/=,
their seven tables and notify triggers under
=projects/ores.sql/create/trading/=, and 98 declared columns in total. The
generated tables carry 154 columns, the difference being the eight scaffolding
columns per table.

The Regime 2 checklist was walked per entity model for the decision checks,
and once for the invariant checks. The generated C++ was read for the
invariant surface: the domain headers, the repository entity and mapper, the
JSON and table codecs, and the eventing and protocol headers. The ORE import
and export seam was read in =projects/ores.ore/core/=, because the
*One-way numeric conversion* check is decided there and nowhere else.

The work was split three ways — the conversion seam, the model-to-generated
artefact census, and the service, wire and catalogue surfaces — and every
critical claim below was then re-checked in the main thread. No build, test
or database run: every claim is from source artefacts.

* Paths taken

- *The model and its generated artefacts.* For each of the seven models the
  column drawer was compared with the generated SQL column, the generated
  domain member and the generated repository entity member. This is the path
  that found the one type disagreement and the encoded-JSON column.
- *The ORE boundary.* =fx_instrument_mapper.cpp= was read in full, then the
  binding it reads from, then the helper it calls. This is the path that
  changed the review's conclusion: the mapper reads every money leaf through
  =exact_decimal=, which looks correct, and the value is already lossy before
  the call.
- *The service and wire surfaces.* The seven repository headers, the seven
  services, the seven protocols and the import handler were read for batch
  access and for the Regime 3 shape.
- *Withdrawn: a family-level finding on the wire projection.* The JSON codecs
  project the domain type directly, so =identity= and =audit= appear as nested
  objects. The
  [[id:BBD43BF2-9FEE-42B0-A667-9468AF759DC2][data-oriented design page]]
  already names that a codegen limitation component-wide, in *There is no
  entity*, so it is not an FX finding. It is recorded here only so the next
  review does not raise it again.

* Conclusions

** What holds

| Check | Result |
|-------+--------|
| Identity by key | PASS. All seven tables carry =primary key (tenant_id, trade_id, valid_from, valid_to)=, and the relation to the trade is the key itself, not an owning-parent link. The instrument carries no identity of its own: the trade names it. |
| Table-shaped children | PASS with one exception. Six of the seven instruments are flat single-row tables with no child record at all. The exception is =fx_accumulator_instrument.range_bounds_json=, which is finding 2. |
| Explicit variation | PASS. The family states its variation as per-type tables, not as an inheritance web: 16 catalogue codes route to seven tables, and the =trade_type_code= check on each table is generated from the single catalogue, so the sets are disjoint. The =fx_instrument_variant= in =fx_instrument_variant.hpp:34-40= is a closed variant of the same seven, and it is an in-process carrier only — it never crosses the wire. |
| Core/cold split | PASS. All seven models set =:domain_audit_group: ores.dq.audit_record=, and the generated domain type folds the audit columns into an =audit= member. |
| Exact money at rest | PASS for 21 of the 22 numeric columns. Every money column is =numeric(38, 12)= with =ores::utility::decimal::decimal=, and no money column is stored as text. The one exception is finding 3. |
| Value semantics | PASS. 0 raw pointer members, 0 destructor declarations across the 29 =fx_*.hpp= domain headers, and each type is a plain value with a key and a defaulted =operator==. |
| No shared-ownership webs | PASS. =shared_ptr=, =unique_ptr= and =weak_ptr= do not appear in any of the generated FX domain, repository, service or eventing headers. |
| Codec drift | PASS. All 14 generated codecs (seven JSON, seven table) carry the AUTO-GENERATED banner and name their mustache template. No hand-written codec stands in for a generated one. |
| Flat value messages | PASS. The export carrier is =instrument_batch= at =trade_operations_protocol.hpp:170=: one typed array per concrete entity, joined by trade id. No protocol in the family holds a =std::variant= field, and the reason a variant cannot cross the wire is recorded at =trade_operations_protocol.hpp:163-169=. |
| Batched collection access | FAIL on the read side. Batch writes, batch removals and batch history reads are used correctly; the three read loops are finding 4. |

** The enforcement gap**

=check_money_decimal_columns.py= sees none of findings 1 to 3, and each one
escapes by a different route.

- Finding 3 is in =EXCLUDED_COLUMNS= for the money direction, because a
  variance strike is volatility. The name =strike= reads as money, so the
  continuous direction skips it too.
- Finding 1 never reaches the check. The check reads the models, and the loss
  is in the ORE binding.
- Finding 2 has no money token in its name at all.

Both baselines are a single blank line, so the gate asserts nothing about this
family in either direction. =check_model_sql_types.py= passes the family,
correctly: the model and the generated table agree, and finding 3 is a
disagreement with the generated C++, which that check does not read.

** Corrections made while checking**

- The conversion seam was first recorded as passing, because the mapper calls
  =exact_decimal= at every money site. That reading is wrong. The lexical
  branch needs an =xsd::base<T>= leaf, no FX binding is one, and the call
  silently takes the =from_double= overload. The helper's name was read, not
  its behaviour.
- The nested =identity= and =audit= JSON projection was first recorded as a
  Regime 3 finding. It is not a family failure: the design page names it a
  codegen limitation for every grouped entity.
- The 19 nullable strings were first recorded as an FX defect. They are a
  component convention that predates the family.
- ="PR 4"= was first read as a bare placeholder. The soft references are a
  recorded deferral with a stated target, so finding 5 is context, not
  oversight.

** Score

Regime 2, *2 of 5*, debt *High*. The single number hides a split worth
stating, as it did for the bonds review. The structural half is a clean 5:
identity is the key, the variation is per-type tables, the core and cold parts
are split, the money is exact at rest, and every generated invariant holds.
The debt is in the conversion seam and in one column. Every FX money value
enters through a binary float, one accumulator field carries a document tree
in a text column, and one column disagrees with its domain type.

The difference from bonds is worth recording: bonds failed on six stragglers
inside a seam that was otherwise migrated. FX has no migrated site at all —
the family was never brought to the lexical-form boundary.

* Recommendations

1. *Migrate the FX money bindings first.* It is the only systemic Critical and
   it has one root cause. Add the FX money members to
   =scripts/reapply_ore_lexical_form.py=, then write the reverse with
   =set_exact=, as the credit task did. The script must grow first: it records
   that it handles =xsd::optional<float>= members only and refuses a required
   plain =float=, and most FX money members are required.
2. *Give =RangeBounds= a child table*, keyed by the instrument, and delete
   =range_bounds_json=. That closes finding 2 and the float text channel with
   it. The ORE schema requires at least one bound, so the child table also
   needs an insert rule for the empty case.
3. *Move the variance strike to =double precision=*, using the mirror mode of
   =scripts/convert_money_column_to_decimal.py=, so the column agrees with the
   continuous domain type.
4. *Close the gate.* Teach =check_money_decimal_columns.py= to see a
   continuous quantity whose name reads as money, and seed the baselines.
   Until then the family has a check that cannot see its own defects.
5. *Take the service read loops to the component, not the family* (4): it is
   7 of 7 services, so it is a service-base or codegen question.
6. *Decide the rest rather than fixing them:* the barrier discriminator (6),
   the doubled vocabularies (8, 9) and the prose exercise-style list.
7. *Correct the exact-numbers page* (10) so it stops restating a baseline it
   calls authoritative.
