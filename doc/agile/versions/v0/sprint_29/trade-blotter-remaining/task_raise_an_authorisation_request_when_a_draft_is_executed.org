* Goal

A trade can go live without passing through book_trade: Execute takes a draft to live. Raise the same request there, in the same transaction, so no live actual trade exists without one. The review of the first task named this the likeliest gap.

* Acceptance

- An actual draft executed into a real book raises one request.
- A draft that stays a draft raises none.
- A trade that already has a request raises no second one.
- A later amendment is tested not to match an older request.

* Plan

There was no Execute path in the code base: nothing took a draft live, so the
hole the task names was open through the generic state write instead. The state
machine states the transitions, and it says the shape:

| Activity | From | To |
|----------+------+----|
| =draft_capture= | none | draft |
| =execution= | draft | live |

So the unit is the operation the transition was waiting for:
=trading.v1.ops.execute_trade=, modelled beside =book_trade= and served by the
same hand-written service. It writes the activity and the state and raises the
request in one transaction, which is what makes the trade live and asking in the
same breath.

The duplicate rule the operation needs is in =raise_if_awaiting=: a trade raises
one request per moment it waits, not one per write it takes. An answered request
does not suppress the next amendment, because only a request still waiting
counts.

The generic state write can still take a draft live without a request. That is
the codegen's seam rather than this task's: a state write has no hand-written
hook to raise from, and adding one to every entity's service is a change to the
generator, not to this operation.

* Result

A draft is executed by an operation of its own, and the trade goes live and
waits for Operations in one transaction.

| Piece | Where |
|-------+-------|
| The messages | =execute_trade_request= and =execute_trade_response= in [[proj:projects/ores.trading/modeling/ores.trading.trade_operations.org][trade_operations]] |
| The service | =trade_operations_service::execute_trade= |
| The subject | =trading.v1.ops.execute_trade=, served by the hand-written operations handler |
| The duplicate rule | =operational_authorisation_service::raise_if_awaiting= |

The operation refuses a trade that is not a draft, one that moved since the
caller read it, and one that is not an actual trade. A draft that stays a draft
raises nothing, because only the execution touches the live status.

* What was not proved

The suite did not run. =origin/main= does not compile: =cb28cc941d= calls
=ores::synthetic::service::routed_code_count=, which no header declares, and
=trade_population_planner.cpp= does not build against the instrument batch it is
handed. Both are other environments' work, so the local binary could not be
linked and the cases below are compiled but not executed.

The generic state write is still a way to take a draft live with no request. The
fix is a hook in the generated service, which the codegen owns.

* Cases written

- An actual draft executed raises one request, and the summary says the trade is
  live.
- A draft that is not executed raises none.
- A second raise for a trade already waiting raises none.
- An amendment after the last request was answered raises its own.
- An execution of a trade that moved since it was read is refused.
- A trade that is not a draft cannot be executed.
