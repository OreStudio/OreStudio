The three provisioning recipes, each from its own empty installation
====================================================================

Run on 2026-09-29 in eager_maxwell, at branch feature/line-up-the-shell-provisioning
(the shell and iam service built from the working tree, commit aa4fe8dcc8 plus the
completing step's party-scope fix).

Each recipe begins with `provision system`, which refuses an installation that is
not in bootstrap mode, so each one needs its own recreate. The cycle for each:

  compass services stop
  sleep 60                       # the fleet's pools take a while to let go
  compass db recreate -y -k
  compass services start
  compass shell -l projects/ores.shell/scripts/library/provisioning/<recipe>.ores

The wait matters: a recreate started too soon after the stop aborts with active
connections, which is captured in
doc/agile/product_backlog/inbox/a_recreate_fails_while_the_pools_are_still_closing.org.

What the runs found
-------------------

The first runs of recipes 1 and 3 left their tenant reporting bootstrap mode, with
onboarding.tenant false:

  barclays         | onboarding.tenant     | false
  barclays         | system.bootstrap_mode | true

and the completing step said so:

  [4/4] complete_provisioning: completed_with_warnings
      warn: The bootstrap mode flag was not cleared: Repository error: Executing
      INSERT failed: ERROR:  Row already exists: a create cannot replace it. State
      the version you read to replace the row, or ask for a version replace.

The cause: the completing step acted as the administrator, whose party is one the
provisioning created, while the tenant's flags live under the tenant's system party.
The settings write reads the row it replaces back under the scope it writes in, so
the read found nothing, the write claimed a create, and the insert trigger refused a
row that was already there. The step now acts as the tenant's system party, and both
recipes end with the flags the checks above show, one row each and no warning. The
`empty_operational` path never showed it because its administrator's party is the
system party; the demonstration and GLEIF paths associate the administrator with the
parties they create first.

Stated honestly: this defect was on the browser's path too. A tenant provisioned
from the first run journey with the demonstration card was left reporting bootstrap
mode with its onboarding incomplete.
