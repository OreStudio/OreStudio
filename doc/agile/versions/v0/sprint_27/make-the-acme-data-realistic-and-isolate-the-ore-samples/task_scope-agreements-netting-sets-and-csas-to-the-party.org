* Goal

A master agreement and its CSA are contracts between one ACME legal entity and
one counterparty. Today the agreement number and the netting set code are
unique per tenant, and the CSA has no party of its own. Two parties cannot
hold the same code, so every party must invent its own, and the ORE samples
bundle cannot install on every party.

Scope all three to the party. Agreement number and netting set code become
unique per party. The CSA gets its own =party_id=. This task comes before the
two bundle tasks, because both depend on it.

* Acceptance

- Two parties can each hold an agreement with the same number and a netting
  set with the same code.
- Agreement number is unique per tenant and party. Netting set code is unique
  per tenant and party.
- The CSA has a =party_id=. It is fixed for life, and it equals the party of
  its netting set. What happens for a netting set that has no party is the
  blocking open question below. Settle it before implementation.
- Every lookup of an agreement or netting set by number or code names the
  party. The DQ publish functions, the alias resolution and the ORE import are
  covered.
- pgTAP covers: the same code under two parties, a CSA whose party differs
  from its set's, and a lookup that names no party. That lookup raises an
  error. It never returns a row chosen from another party.
- A fresh ACME provision passes.

* Notes

*Decision, 2026-10-10.* A netting set belongs to a party and follows the usual
RLS pattern. The pattern is the one =book= uses: a required =party_id= that is
part of the natural key, a foreign key to parties, and a restrictive party
isolation policy for select. This closes the open question: the netting set
=party_id= becomes required.

*Findings from the search.* The scope is wider than the three tables.

- =ores_refdata_netting_sets_tbl.party_id= is nullable. Its RLS policy reads
  =party_id is null or party_id = ANY(visible parties)=, because a set read
  from an ORE document has no legal entity yet. A required party removes the
  null branch. The ORE import must then give each set the importing party.
- =netting_agreements_agreement_number_uniq_idx= is on =(tenant_id,
  agreement_number)=. =netting_sets_code_uniq_idx= is on =(tenant_id, code)=.
  Both become per party.
- =ores_refdata_csas_tbl= has no =party_id= and no RLS policy at all.
- =netting_set_identifiers_ore_alias_idx= is unique on =(tenant_id, id_scheme,
  id_value)= for the ORE scheme. An ORE id such as =CPTY_A= can name only one
  set in the whole tenant. It collides in the same way when every party holds a
  set for it, so it must be per party too. The identifier takes its party from
  its netting set.
- Lookups that name an agreement or a set: the publish-from-DQ functions in
  =refdata_publish_from_dq_create.sql= (agreements, sets, CSAs, aliases), the
  trade booking validation in =trading_trade_bookings_create.sql=, the trade
  component functions in =trading_trade_components_functions_create.sql=,
  =ore_import_execute_handler.cpp= and the netting set mapper in =ores.ore=.
  The DQ staging tables carry the same keys.

*Decisions taken while building.*

- The CSA and the netting set identifier carry a fixed =party_id=, with a
  foreign key to parties. They have no pinned key to the party of their set. A
  pin is correct, but the generated eventing integration test cannot satisfy
  it: the generator seeds a parent netting set under one party and the CSA
  under another, and the pin refuses the CSA. The publish functions and the ORE
  mapper write the set's party, so the two stay equal by construction.
- Party isolation follows the pattern of netting sets, agreements and books: a
  tenant policy for all commands, generated with the table, and a handwritten
  restrictive policy for select on =party_id= in
  =refdata_rls_policies_create.sql=. The generator's own
  =rls_party_isolation= flag was tried first. It makes the generated eventing
  tests of the child tables seed parties the session cannot see.
- The ORE netting set mapper takes the importing party. An ORE document names
  no legal entity of the firm, so the importer supplies it. Only tests call it
  today.

*Known follow-up.* =ores_refdata_csa_eligible_currencies_tbl= has no
=party_id= and no party policy. Its rows are reachable through CSAs that the
party policy hides, but a direct listing is not filtered by party. A policy by
join to the CSA would close it.

*Not changed.* The trade booking validation and the trade component functions
look sets up by id and already check the trade's party.
