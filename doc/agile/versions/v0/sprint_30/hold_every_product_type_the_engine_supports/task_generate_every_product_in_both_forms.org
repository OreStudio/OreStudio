* Goal

Every product ORE carries in both forms is booked in both: once as its own element and once as a generic ScriptedTrade naming the library script with the same payoff, each through a builder, and ORE reads and builds both.

* Acceptance

- the catalogue names, for each product with two forms, the library script that carries its second form
- every generic ScriptedTrade the generator books goes through the scripted builder of the scripted builders task, and each twin's variables are a recipe held as data
- the generated population holds one trade of each such product in each form
- each pair states the same economic terms in both forms, so the two can be
  valued and compared
- the ORE engine test reads and builds both forms of each, with no error of the trade kind

* Plan

Decided with the user on 2026-11-19: each twin's variables are a recipe held in a
reference table.

- The recipe is an org table in the trade type catalogue, one row per native
  trade type and script input: the input's name, its type and shape as the
  library states them, the path of the native row value it takes, and a
  transform. A path names a part of the native trade's rows: =product.strike=
  for a column of the product row, =instrument_underlyings[underlying].name=
  for a column of the rows under a role, =instrument_options.option_type= for a
  shared row, or a constant. The =sign= transform turns =Long= or =Call= into
  =1= and =Short= or =Put= into =-1=, as the scripts read them.
- A generator turns the org table into the seed of a =script_twin_inputs=
  reference table and into a compiled-in table the trade generator reads, so the
  data has one source and the generator needs no database.
- One evaluator reads a path over the native trade's instrument batch through
  the rows' =wire_fields=, so a recipe needs no code of its own.
- The generator books each product with a scripted form twice: the native trade,
  then a generic =ScriptedTrade= built through the scripted trade builder from
  the recipe evaluated over the native trade.
- Delivered in steps: the reference table, the evaluator and the basket and
  rainbow recipes first, then the remaining products' recipes.

* Notes

** The generic barrier options and the FD variant of their script

A recipe for EquityGenericBarrierOption and FxGenericBarrierOption was written
and run, then held back. The engine run prices the =SingleAssetOptionBwd= tag
with FD, so ORE runs the =FD= variant of the library's GenericBarrierOption
script, and every twin failed there:

- With barrier monitoring dates that start after the as-of date: "RandomVariable:
  inconsistent times 0 and 0.558904 at L124 ... PAY( LongShort * BarrierRebate,
  TODAY, SettlementDate, ...) - R_V". The backward loop rolls R_V back only to
  the first monitoring date, not to today.
- With an expiry on a holiday (2029-12-02, a Sunday) before the last adjusted
  monitoring date: "AssetModel::npv(): can not roll back from t1= 4.81096 to
  t0= 4.8137".

The native trades price on the same engine, so ORE's own GenericBarrierOption
class does not run this library code as the twin states it. With the engine set
to MC for the tag, all four twins priced with no error, and each NPV equalled
its native's exactly (for example -4772.758430 EUR and 19702.508881 USD), so
the recipe itself was right. The open choice is how to book these twins under
the FD engine: correct the FD variant of the script in the library seed, roll
the twin's dates as ORE's native class does, or price the twins' tag by MC.

** The pairwise variance swaps: a derived lag and an unlimited payoff

The PairwiseVarianceSwap script reads a LaggedValuationSchedule and a positive
PayoffLimit, and the native trade states neither. ORE's own class
(=OREData/ored/portfolio/pairwisevarianceswap.cpp=) derives the lag as the
valuation schedule shifted by =1D= on =NullCalendar=, =Unadjusted=, so the twin
states that =DerivedSchedule=, unless the native states a lagged schedule of
its own. ORE's engine reads a payoff limit of zero as no limit, and the script
requires a positive one, so the twin states a limit of a million. The native
trades have no pricing engine in the engine run, so the two forms cannot be
compared by NPV; the four twins price with no error.

** The FX worst-of basket swap: a library script ORE cannot parse

ORE's library WorstOfBasketSwap script (=Examples/Products/Input/scriptlibrary.xml=,
line 792) has no semicolon after =couponAccumulation = couponAccumulation +
(1-allAssetsTriggered)=, and ORE's parser stops there: "expected
<InstructionSequence> in L17:30:0". No trade can run it. The seed states the library
as ORE ships it, and compass-ng regenerates that file, so the correction is a
populate script of its own, =trading_script_library_corrections_populate.sql=,
which writes a new version of the variant after the seed. It applies when its
text occurs once, does nothing once the code holds the replacement, and fails
the load otherwise, so a library that changes the script is reviewed.

ORE's own class runs a script of its own, not the library one, so the twin
maps the native terms onto the library's inputs:

- The script pays the initial fixed amount on SettlementDates[1] and each
  period's coupons on the dates after, and requires as many settlement dates as
  determination dates. ORE reads a listed schedule's dates once each
  (=OREData/ored/portfolio/schedule.cpp=, the =std::unique= before the Schedule
  constructor), so the initial amount cannot share the first pay date, as ORE's
  class pays it when none is stated. The twin pays it on the first period date.
- The script reads one fixing of the floating index on each fixing date. ORE's
  class compounds an overnight index over the period.
- The LOGPAY cash flow types InitialFixedAmount, FloatingLeg, FixedCouponLeg and
  EquityAmountPayoff are mined as inputs; ORE reads them by name only, so the
  twin states them as zero.

Priced alone in ORE, the twins and their natives are close: -651335.18 against
-630811.63 USD (2027 maturity, short) and 266454.13 against 264880.01 USD (2035
maturity, long). The fixing and the initial pay date above are the known
differences; Monte Carlo noise is the other.

* Result

First PR: the machinery and the first recipes. The catalogue's =Scripted twin
recipes= table states, for each product with a scripted form, where each input
of its script takes its value from in the native trade's rows. The generator
script =generate_script_twins.py= joins it with the mined script inputs, refuses
a recipe that misses or invents an input, and writes the seed of the new
=script_twin_inputs= reference table and the table the trade generator compiles
in. One evaluator reads a recipe over the native trade's rows through their
wire fields, and the FX and equity planners book each such product again as its
generic ScriptedTrade through the scripted trade builder. The equity and FX
basket and rainbow options are twinned: the twins book, export, and ORE builds
them with no error of the trade kind. The remaining products' recipes follow.
