* Goal

One page states the model the story builds for a run's failures: the phases a run
passes through, what each phase can refuse and how it says so, the three grains of
a run's market readiness, the six causes a gap can state, and the partition of the
population that follows from excluding an incomplete trade before the engine.

The page is the reference the later tasks read, so a builder of the readiness
record and a builder of the error phase do not have to re-derive either. The two
product approval matrices are decided in the story's =* Decisions= and belong to
the task that models them; this page takes the run, not the population.

* Acceptance

- The three attribution phases are named, with the pipeline phases each covers and what each refuses.
- Each grain of the readiness record states what it answers and who reads it.
- The six causes a run can state for a gap are named, each one a fact an existing read holds.
- The phase is stated beside the engine's scope, with the reason the scope stays the engine's.
- The partition of the population is stated, so an engine error means a trade whose market data was complete.
- The page states what the attribution does not establish, so a later reader does not take it for more than a classification.

* Plan

The page was written against the pages that already own its parts, so that it
extends them rather than restating them: the pipeline's six phases, the
requirement and its resolution, the error event and its engine scope, and the
chain from a fixing to a report. It states the three attribution phases on top of
those six, the six causes a gap can name, the three grains of the readiness
record, and the partition the exclusion rule produces. The lifecycle it describes
is drawn as a state diagram beside the page and rendered with PlantUML. The page
is wired into the reading order of the Report Processing structure note, and it
names the page it contradicts rather than editing a list it does not own.

* Result

[[id:DFC5F290-B8B6-4DEC-970C-D93C98FD39F8][Error Attribution in a Report Run]] states the model.

What it establishes:

- Three attribution phases — preprocessing, engine and postprocessing — each
  mapped onto the pipeline's six phases, with what each refuses in its own
  vocabulary.
- A trade's completeness, the six causes a gap can name, and the three grains at
  which a run records readiness: by address, by trade and by run.
- The exclusion rule and the partition it produces, so that an engine error is an
  error on a trade whose market data was complete.
- The reason a run with nothing complete fails in preprocessing rather than
  reporting an empty valuation.
- The separation of the phase from the engine's scope, and what the attribution
  does not establish.

The lifecycle is drawn in =report_run_trade_states.puml= and rendered to PNG, and
the page is listed in the reading order of [[id:01083101-A83A-4294-81A4-DDF3192CEB14][Report Processing]].
[[id:08C54927-C7BD-48B7-BF7B-13DC3702FF68][Report pre-processing]] still states that no resolution exists and that
the export writes every series the tenant holds; both are delivered, so the new
page names the contradiction rather than editing a list it does not own, and the
correction of that page is left to the task that owns it.
