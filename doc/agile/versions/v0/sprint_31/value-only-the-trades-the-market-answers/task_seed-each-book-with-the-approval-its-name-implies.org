* Acceptance

- Each published ACME book states the product types its name and purpose imply, and no longer takes every code the catalogue holds.
- The party's set is stated by the provision and covers every one of its books' sets, through the desks the chain gained: each desk states a set that holds every one of its books' sets.
- The affinity is one list per book, read both by the book's set and by the generator's choice of types, so the two cannot drift apart.
- Every type the generator books into a book is permitted by that book's matrix, and a check fails when one is not.
- The union of the books' sets covers the trade type population the generator books, so no generated type is left without a book that may carry it.

* Plan

The approval is data quality data and belongs beside the books it constrains.
The books are staged in =ores_dq_books_artefact_tbl=, written by the ACME
seeder's generated scripts, and published into refdata by
=ores_refdata_publish_books_from_dq_fn=. The book's approved set follows the same
path, and the gap is that it does not exist yet: the publish states
=restricts_product_types = true= on every book and then takes *every* code the
catalogue holds, so the matrix says nothing about the book, and no provision
states a party's set.

1. *The approval is a junction artefact beside the books.*
   =ores.refdata.book_product_type= gains the junction artefact facet
   (=:ores.sql.schema.junction_artefact_create.enabled: true=), which generates
   =ores_dq_book_product_types_artefact_tbl(dataset_id, tenant_id, book_id,
   product_type_code, version)= — the template's default columns, because unlike
   =party_currencies= this dataset holds many books and each row must name the
   book it approves. The row is keyed by the book's artefact id, which the books
   dataset already mints.
2. *The seeder states the affinity.* The ACME seeder generates the books and their
   approved types in one pass from the curated book data, so the cable book
   carries the FX option types, the CDS book the credit types, and the books
   together cover the population. The affinity is data in the dataset and not a
   rule in code; a book whose name states no affinity is a defect the seeder
   refuses rather than publishes open.
3. *The publish keeps the artefact id.* The publish mints a fresh uuid per book
   today and drops =a.id=, so nothing can join the artefact rows to the published
   books. It keeps the pair (artefact id, published id), writes the junction from
   the artefact rows, and removes the insert that takes every code.
4. *The party's set is the union of its books.* Parties are not DQ artefacts, so
   nothing stages their set. The provision states it after the books are
   published, as the union of the sets of that party's books, which is the
   smallest set the subset rule accepts and is not a second curation.
5. *One list, two readers.* The generator reads the published book's set to choose
   the types it books, so the affinity is stated once and cannot drift between
   the matrix and the population.

   The set is read through the chain and not through the junctions. A book's
   approval is resolved by =ores_refdata_book_allowed_product_types_fn=, and a
   generator that read the three junction tables and resolved them itself would
   be the second statement of one rule. So refdata serves the resolution:
   =refdata.v1.ops.get_book_product_approvals= answers each book of a request with
   the set it permits, or with no set at all when no level restricts. The
   operation is a hand-written handler beside a codegen operation model, because
   the answer is a table function and not a row of an entity.

   The generator asks it once per run, before it plans, and plans *per book*: a
   book's population is stated from the config's types narrowed to that book's
   set, so a book never carries a product it does not permit. A book that permits
   none of the config's types books nothing rather than widening the matrix to
   fill itself, and a type no book of the config permits is reported with that
   reason rather than as a market data gap. The plan is then checked against the
   approvals, and a trade of a product its book does not permit is refused, so a
   drift between the matrix the write path enforces and the one the planner chose
   within is loud rather than discovered at a booking.

   A population is planned per book, so the trades a config books into a book
   number from that book's own first slot. A config scoped over several books
   therefore states different trade identifiers than it did before this slice,
   which is expected: the population is a rebuild and not a migration.
6. *The seed test changes with the behaviour.*
   =refdata_book_product_types_seed_test.sql= asserts today that a published book
   takes every code. It asserts the book's own set instead, that the party's set
   covers every book, and that the union across the group covers the population.
   It also asserts the read a choosing caller asks — the books in the order the
   request named them, one row per permitted type, and a book that permits none
   answering one row that names no type — and that every code any ACME book
   dataset states is one the catalogue holds, which is what caught a book that
   named a code the catalogue had retired.
7. *The affinity covers the population the generator books.* The curated lists
   were written per family and left codes no book stated: seven equity and
   scripted products, a credit structure, an intraday power forward and a retired
   code the catalogue no longer holds. The generator books one hundred and
   nineteen codes across its eight planners, so the books' lists are widened until
   every one of the hundred and nineteen has a book that may carry it.

* Result

The provision states a matrix that is both narrower than the catalogue and
complete for the population. Every published ACME book states the products its
name and purpose imply; the desks state the union of their books and the parties
the union of their own; and the generator chooses within those sets rather than
discovering them when a booking is refused.

The generator reads one book's answer at a time and plans that book's population
against it, so a book that permits two products still holds its trades per book,
a book that permits none of the config's types books nothing, and a type no book
of the config permits is reported with the matrix as its reason rather than as a
market data gap. The plan is checked against the approvals before it leaves, and
that check was proved to fire: with the narrowing disabled it refuses the plan,
naming the book and the set it permits.

Coverage, measured on the reloaded database: the ACME books state 120 of the 121
catalogue codes, and all 119 codes the eight planners book are stated by at least
one book. The catalogue code no book states is the generic
=ForwardVolatilityAgreement=, which no planner books, because the planners book
the FX, equity and commodity agreements, which are separate codes.

A config scoped over several books now numbers each book's trades from that
book's own first slot, so the population such a config states has different trade
identifiers than before this branch. That is expected: a population is a rebuild,
not a migration, and a rebuild states the same population every time.
