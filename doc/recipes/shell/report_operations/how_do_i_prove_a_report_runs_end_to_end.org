#+title: How do I prove a report runs end to end?
#+description: Trigger a report definition, watch its instance through the lifecycle, and confirm the compute job produced analytics that came back into storage.
#+type: recipe
#+level: cross
#+filetags: :recipe:shell:report_operations:grid:end_to_end:
#+created: 2026-10-24
#+updated: 2026-10-24

The run starts in ores.reporting, gathers its trades and market data, packages
the run for ores.compute, and collects the result back. The compute side of the
same chain is the runbook [[id:CC0A311E-7245-4694-86A1-3170023C385A][Run a compute job end to end]];
this recipe drives the report above it.

* Question

How do I prove that a report definition runs through the grid and its analytics
come back?

* Answer

Preconditions: the services are up (=compass services start=), the database was
provisioned from =acme_demo= (see [[id:45B89A49-B2B8-4C1C-9BB7-09EB27E4D50C][How do I provision the system with Acme Corporation (holding group)?]]),
and that provision published the ORE engine packages. A fresh database holds no
reference data, so the trigger answers =no_run_grant= or finds no definition
until the provision has run.

1. /Pick a definition the session's party owns, and check its scope resolves to books./
   A session may only run a definition owned by the party it acts for. That
   party is the one the shell prints as =Party:= when it signs in. A definition
   owned by another party answers =no_run_grant=.

   #+begin_src sh :results verbatim
   ./compass.sh sql -- -c "select d.id, d.tenant_id, p.short_code as party, d.name,
     r.name as config,
     (select count(*) from ores_reporting_resolve_book_ids_for_config_fn(
        d.tenant_id, r.id, d.id)) as books_in_scope
   from ores_reporting_report_definitions_tbl d
   join ores_refdata_parties_tbl p
     on p.id = d.party_id and p.valid_to > now()
   join ores_reporting_report_configurations_tbl c
     on c.report_definition_id = d.id
    and c.configuration_type_code = 'risk_report_config'
    and c.valid_to > now()
   join ores_reporting_risk_report_configs_tbl r
     on r.configuration_id = c.configuration_id
    and r.tenant_id = c.tenant_id
    and r.valid_to > now()
   where d.valid_to > now()
   order by p.short_code, books_in_scope desc, d.name;"
   #+end_src

   Take a row whose =party= is the party the shell signed in as, with
   =books_in_scope= above zero. Its =id= and =tenant_id= are the two ids
   step 2 needs.

   The join runs through =report_configurations.configuration_id=, which names
   the central =ores_reporting_configurations_tbl= row. The risk configuration
   is the row whose =configuration_id= holds it. Joining on the central id
   returns no scope for every definition.

2. /Trigger the definition./ The command creates the instance and returns its id.
   Run this recipe with =compass shell -f=, which signs in from =.env= before it
   loads the file. Replace both placeholders with the definition and tenant ids
   from step 1.

#+name: report-run-end-to-end
#+begin_src ores-shell :tangle how_do_i_prove_a_report_runs_end_to_end.ores :exports none
connect $ORES_NATS_URL
report_operations trigger-report-instance <report_definition_id> <tenant_id>
exit
#+end_src

3. /Watch the instance walk the lifecycle./ It passes =pending=, =running= and
   =completed=. Each transition is a version of the instance row, so order by
   =version=.

   #+begin_src sh :results verbatim
   ./compass.sh sql -- -c "select i.version, s.name as state, i.started_at,
     i.completed_at, i.output_storage_key
   from ores_reporting_report_instances_tbl i
   left join ores_dq_fsm_states_tbl s on s.id = i.fsm_state_id
   where i.id = '<report_instance_id>'
   order by i.version;"
   #+end_src

4. /Confirm the compute job succeeded./ The batch carries the instance id as its
   external reference.

   #+begin_src sh :results verbatim
   ./compass.sh sql -- -c "select b.external_ref, b.status, r.id as result_id,
     r.outcome, r.server_state, r.duration_ms, r.error_message, r.output_uri
   from ores_compute_batches_tbl b
   join ores_compute_workunits_tbl w on w.batch_id = b.id and w.valid_to > now()
   join ores_compute_results_tbl r on r.workunit_id = w.id and r.valid_to > now()
   where b.valid_to > now() order by b.external_ref;"
   #+end_src

   Success is =status = closed=, =outcome = 1= and =server_state = 5=. A failed
   engine writes the engine's own message into =error_message= and leaves
   =outcome= at anything but 1.

5. /Download the output and read the analytics, not just the exit code./ The
   download is the step that brings the engine's bytes back; without it the
   instance records a location and nothing has been read.

#+name: report-download-output
#+begin_src ores-shell :tangle how_do_i_prove_a_report_runs_end_to_end_download.ores :exports none
connect $ORES_NATS_URL
compute download-output <result_id> build/e2e/out
exit
#+end_src

   #+begin_src sh :results verbatim
   find build/e2e/out -maxdepth 1 -type f -printf '%s %f\n'
   grep -c "Built Portfolio" build/e2e/out/log.txt
   cat build/e2e/out/runtimes.csv
   #+end_src

   The archive holds the contents of the engine's =Output/= directory, so
   =log.txt= and the reports land at the root of the download directory.
   =log.txt= states whether the portfolio built, =runtimes.csv= shows which
   analytic ran and for how long, and =pricingstats.csv= shows how many pricings
   each trade took. A trade with zero pricings under an analytic that prices is
   a gap in the reference data, not a chain failure.

* Script

=projects/ores.shell/scripts/library/report_operations/how_do_i_prove_a_report_runs_end_to_end.ores=

* Tested by

Witnessed on 2026-10-24 against a database recreated from nothing in the
=swift_curie= environment, on report definitions owned by =Acme Corporation Plc=:

| Definition            | Instance   | States                    | Result             | Analytics |
|-----------------------+------------+---------------------------+--------------------+-----------|
| Audit Trail Summary   | 97e9d3c2   | pending, running, running, completed | outcome 1, 5, closed | =PORTFOLIO_DETAILS=, 10s |
| Liquidity Coverage    | 52fc3f8d   | pending, running, running, completed | outcome 1, 5, closed | produced and collected |

Both runs left =reporting/runs/<instance>/output.tar.gz= in storage and a
compute batch whose external reference is the instance id. The engine logged
=Built Portfolio. Initial size = 8, size now 8, built 0 failed trades=, so the
package the chain builds is readable by ORE.

The failure side was tested on the same day. A package whose =Input/portfolio.xml=
was removed produced the engine's own verdict, and the result recorded it:

#+begin_example
outcome 3, The engine's analytic failed. The engine reported:
  Error in ORE analytics: Failed to run analytics PORTFOLIO_DETAILS
#+end_example

Before the fix that made this true, the same package returned outcome 1, because
ORE's bookkeeping files looked like analytics.
