This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A tenant administrator defines how a tenor code resolves under a convention, down to the date it produces on a named calendar.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want every tenor code we quote to mean one date under each convention, so
that a ladder, a curve or a swap that names 3M gets the date the desk means by
3M." The journey is done when each convention's set reads correctly and a worked
tenor resolves to a date the person can check on a named calendar.

* Actor and trigger

The actor is the tenant administrator, acting inside their own tenant. No
narrower role holds these permissions today. The trigger is a tenor the desk
reads differently, a new label, a convention whose anchor or resolution
algorithm is wrong, or a swap that refused a date. The journey starts at
*Tenors*, and ends when the person leaves the catalog. The journey keeps no
state.

The design question the screen settles is that a tenor has two halves. One half
is the code a person reads, with its display name, description and display
order. The other half is the resolution the system computes, which depends on
the convention and ends in a date on a named calendar. The journey shows both
halves at once, so a person never edits a code without seeing the date it
produces.

* Steps

1. *See the tenors.* The person opens *Tenors*. The system lists every code in
   display order: code, display name, kind, unit and multiplier, sort order and
   version. Beside each row it shows the date the tenor resolves to under the
   convention, calendar and horizon in force. The person searches the code, the
   display name or the description, and filters by kind. See /What is missing/
   for the resolution column.
2. *Open the tenor.* The person picks a row. The system shows the code and the
   resolution side by side: on the left the code a person reads, on the right
   the anchor, the offset or the schedule walk, and the date that comes out. The
   seven columns of the tenor row sit below. The person corrects a field, states
   a change reason and a commentary, and saves. See /What is missing/ for the
   two fields the wire does not carry.
3. *Set its resolution.* The person opens *Its resolution* and chooses a
   convention. The system shows the convention's default anchor (`measured_from`)
   and its resolution algorithm, then a matrix of every tenor: whether it is in
   this convention's set, the anchor it uses, the offset it walks and the date
   it resolves to. A dim row is a tenor the convention does not resolve. The
   person changes the convention's description, anchor or algorithm, or the
   membership row. See /What is missing/ for the read-only junction.
4. *Walk the schedule.* The person opens *The schedule* and picks a schedule
   axis. The system shows how the axis produces dates, then expands the axis
   into a ladder: each roll with its schedule date and the date it becomes after
   the roll rule adjusts it on the calendar. The person can change the axis, the
   roll count, the roll rule and the start of the ladder to see the expansion.
5. *Read the resolved dates.* The person opens *The resolved dates* and sets the
   tenor, the convention, the calendar, the roll rule and the horizon. The
   system walks the resolution end to end and shows every turn: the horizon, the
   anchor, the offset, each schedule step, the roll and the final date. A step
   that cannot resolve is refused with the step that refused it and the dates it
   counted.
6. *Review.* The person opens *Review*. The system repeats the whole resolution
   in one panel, with the tenor, the convention, the anchor date, the resolved
   date, the calendar, the roll rule and the change reason, and states whether
   the record resolves. Nothing is written until the person confirms.
7. *Write the tenor and the convention.* The person confirms. The system writes
   the tenor row and the convention row, each with a new version, and shows the
   new version and the resolved date. See /What is missing/ for the missing
   membership write.
8. *Check the history.* The person opens a row's history. The system shows every
   version with the field-level difference from the version before, and the
   person can revert by writing the old values as a new version. History is
   never rewritten.
9. *Leave.* The person goes back. Every picker and ladder that reads a tenor
   now resolves it under the new rules.

Two states sit off the rail. *The refusal* shows a tenor that cannot resolve,
with the step that refused it, the dates it counted and the row that owns the
fault; the record does not move. *History* is the state step 8 opens.

No step waits on the server after its reply, and the journey keeps no state.

Five coverage rows are =missing=, and they name three things the server does
not carry: an operation that resolves a tenor over the wire, a write for the
resolution junction, and a refusal message. The resolution column and the
resolved-dates step need the same missing operation, and the resolution step
and the write step need the same missing junction write.

* What is missing

1. *No operation resolves a tenor over the wire.* The resolution lives in
   =resolve_end_date=, a domain function in
   =ores.refdata.api/domain/tenor_resolution.hpp=. It takes the horizon, the
   spot date and the schedule dates, and it returns a date or throws. The list
   step's resolution column and the resolved-dates step both need an operation,
   and the prototype draws the reply one would return. The candidate is a
   =refdata.v1.tenors.resolve= request whose reply carries the anchor date, the
   date before the roll, the adjusted date, the roll rule and the calendar.
   Until then the screen cannot show a resolved date the server confirmed.
2. *=tenor_convention= has no roll-rule column.* A convention carries its
   anchor and its algorithm, and nothing that says how a resolved date is
   adjusted. The =business_day_convention_type= lookup holds the four roll rules
   the prototype draws, and no column in =tenor_convention= points at it. The
   candidate is a =business_day_convention_type= column on =tenor_convention=,
   with the same foreign key the other lookups use. Until then the roll rule is
   a choice on the screen with no row behind it, and the write cannot store it.
3. *=tenor_convention_resolutions= is read-only.* The server serves
   =refdata.v1.tenor_convention_resolutions.list=, =.get= and
   =.list_by_convention_code=, and there is no =.put= and no =.delete=. The
   resolution step can show membership and cannot change it: the anchor
   override, the SPECIAL tenor's offset and a SCHEDULE_STEP row's schedule code
   and step count all have no write. The candidate is the =.put= and =.delete=
   pair with the version check the other refdata writes make. Until then the
   screen shows the set and says it cannot change it.
4. *The refusal is a thrown exception with no message on the wire.*
   =resolve_end_date= throws =std::invalid_argument= or =std::logic_error=, and
   no operation carries either to a screen. A screen must show the step that
   refused, the dates it counted and the row that owns the fault. The prototype
   draws that payload. The candidate is a refusal message, either a failure
   reply on the resolve operation or a typed error the handler maps. Until then
   a refused resolution is a 500-class failure with nothing a person can read.
5. *The tenor write carries no change reason and no commentary.* The body of
   =refdata.v1.tenors.put= carries code, display name, description, sort order,
   kind, unit and multiplier. It carries no change reason and no commentary,
   although the row is validated by =ores_dq_validate_change_reason_fn=. The
   screen draws both fields because the journey needs them. The candidate is the
   two columns on =tenor_write=, as the other refdata writes carry them.
6. *A swap's rolls are not a refdata row.* =tenor_schedule= names the axis and
   the dates it produces, and nothing stores a ladder. The rolls a swap needs
   are computed where the swap is built. The closed-form axis is evaluated
   code-side, and an event-lookup axis reads =calendar_event= rows. The schedule
   step draws the expansion so a reviewer can see the axis working, and it is
   not a write target.
