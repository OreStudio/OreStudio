#+title: Six-eyes approval of LLM agent writes
#+description: An agent's write is held until its person approves and then until someone else gives the approval the write needs.
#+type: knowledge
#+level: cross
#+filetags: :knowledge:agents:approvals:four_eyes:
#+created: 2026-11-22
#+updated: 2026-11-22

This page states the target design. It does not describe what is built.

* Summary

An agent's write does not apply when the agent makes it. It raises an approval
request that its person approves first, and the write then needs whatever
approval the person's own write would need, given by someone who is neither the
agent nor its person. The claim of this page is that four eyes are not enough
when one pair belongs to an agent: the person who approves their agent's write
is checking the agent, and a second person is still needed to check the
person, so an agent's write passes six eyes. It is the separation of privilege
of Saltzer and Schroeder (1975), applied once more for the agent.

* Detail

** The hold

Every write made with an agent's token is held unless a rule exempts it. The
approval policy of the [[id:E21DFC83-9F3F-45BE-AD3F-48262126DFAC][Four-eyes framework]] says which acts are gated and which part
decides each; it gains one condition, /made by an agent/, so that a rule can
gate an act only when an agent makes it, or exempt it. Without a rule, an
agent's write is held. Reads are never held. A write under a read-only grant
is refused by =ores.http= before any request is raised, because the catalogue
knows that the operation writes and the token carries the grant's scope.

The request is an ordinary [[id:0FE6BDD9-EB24-4B07-8B0C-D816AAF1BEBF][Approval requests]] in the one queue of [[id:EE61043C-CBCE-44B5-85E9-A3E433FBA3EF][ores.inbox]]. Its first
part is the agent's person; its later parts are those the policy names for the
act. The agent can never decide a part. The person decides only the first.
The later parts are decided by someone else; when nobody else holds the right,
the request stays pending, and the review panel says that it has no eligible
approver. Over MCP the held write is an answer, not an error: =call_operation=
returns the request, so the agent can tell its person what waits.

** Trades

A trade already passes a second pair of eyes after it is booked: it goes live
and unauthorised, and Operations authorises it ([[id:A9E9D1EF-5879-4488-87C8-BDD914C3B502][Operational Authorisation]], [[id:E509AFFC-3924-428E-B504-96D68BF5568A][Trade booking]]). An
agent's booking uses that control rather than a second queue. The trade goes
live and unauthorised as every trade does, and its operational authorisation
request names one more part, the agent's person, before Operations. Operational
authorisation is metadata on the trade and moves no version, so the trade's
lifecycle is unchanged, and an unauthorised trade's contribution to risk and
P&L follows the same rule whoever booked it.

** What a rule cannot close

The [[id:71146F3F-B884-4E61-BA8B-A8A0731703C6][Rules for the automatic approval of requests]] close a request with no person under five stated rules. A
request an agent raised is not closed by any of them at its first part: the
point of that part is that a person looks at what the agent did, and a rule
that closes it removes the look. The later parts follow the rules exactly as
the person's own write would, so a demonstration tenant or a one-person
installation still needs the person and no one else.
