* Acceptance

- A lookup holds ux, api, ore_import and synthetic.
- The anchor refuses an origin that is not in the lookup.
- Synthetic and the ORE import state their origin. The reason code no longer marks generated data.
- The service refuses an origin that the authenticated client may not state.
- A database-backed test proves the refusal.

* Plan

1. The lookup. =ores.trading.origin_type= mirrors =entry_channel_type=: a
   closed set, =:has_tenant_id: false= because it is the same for every
   tenant, a =code= primary key and a =description=, seeded once and never
   changed at run time. Codes: =ux=, =api=, =ore_import= and =synthetic=.
   Because it is immutable the anchor references it with a foreign key and
   not a trigger check, which is the reason =entry_channel_type= already
   gives.

2. The anchor. =ores.trading.trade= gains =origin= and
   =origin_reference=. The origin is not economic. =entry_channel= is
   marked economic, but it records how a trade was executed, while origin
   records which system first wrote it down: a re-import of the same trade
   from ORE must not change its economic identity, so origin stays out of
   the digest. =origin_reference= is the reference the origin implies: the
   ORE trade id for an import, the generation config id for a synthetic
   trade, and nothing for a person at a screen.

3. The refusal. A client may state =ux= or =api=; =synthetic= and
   =ore_import= are stated only by the services that own those paths. The
   trading service refuses an origin the authenticated client may not
   state, and the refusal names the origin.

4. The callers. The synthetic writer states =synthetic= and its config id,
   and stops marking generated rows with the reason code. The ORE import
   states =ore_import= and the ORE trade id. The screens state =ux=. The
   API default is =api=.

5. Verification. A database-backed test proves the refusal for a client
   that may not state an origin. A run of the commodity population proves
   the synthetic path states its own origin, and the rows are read back.

* Result

A trade states where it came from and what that origin refers to. The lookup
holds =ux=, =api=, =ore_import= and =synthetic=; the anchor references it with
a foreign key, and the C++ type is an enum registered as a custom value type,
so an unknown code cannot be constructed on either side.

=book_trade= refuses an origin the caller may not state, before it writes
anything: a client may state =ux= or =api=, while =synthetic= and
=ore_import= belong to the services that own those paths, which the session
names in its service account. Two database-backed cases prove it.

The population writer states =synthetic= and its config id; the ORE import
states =ore_import= and the ORE trade id. The screens have no booking path
yet, so nothing states =ux=, and every other caller falls to =api=.

The change reason still marks generated data. The acceptance asked for that
to move to the origin, and origin now carries it, but the reason is read by
the digest fold to decide whether an amendment moved the external version, so
changing it would alter that logic. It is recorded here as deliberate rather
than done.
