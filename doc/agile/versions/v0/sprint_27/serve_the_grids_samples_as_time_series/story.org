* Goal

A system administrator picks last hour, day or week and reads how the grid's load, fleet, throughput and outcomes moved, and which node was busy or quiet when. Both stored sample tables already hold the data. No subject reads a range of either, so the story adds the reads, serves them through the BFF, and draws the panels the Watch the grid journey names. A week of node samples is about half a million rows for 26 nodes, so the reads bucket the rows on the server. The second half reads ORE's runtimes.csv and its memory lines in the wrapper, so each node sample can also state how long the engine ran and how much memory it peaked at.

* Acceptance

- A grid sample range read returns the samples between two times, bucketed to a width the caller asks for, so a week comes back as hundreds of points and not tens of thousands.
- A node sample range read returns one series per node over the same range and buckets, with the tasks done, failed, mean and longest duration and bytes moved.
- Both reads serve the whole installation, are gated by a permission, and say an empty range is empty and not a flat line at zero.
- The BFF serves both reads with the range presets of the other operations screens, and the grid screen draws load, fleet, throughput and outcomes on one shared time axis.
- The grid screen draws the node load heatmap and the node state ribbon from the node series, grouped by machine.
- A node sample carries the engine run time and the peak memory of its jobs, read from runtimes.csv and the memory lines, and the screen can chart them.

** What the docs already say

  specification. It names the ranges (last hour, day, week), nine panels on one
  shared time axis, and eight gaps. It marks the range reads for grid and node
  samples as missing, with no subject and no permission gate.
- The capture [[id:E7035C69-EB6E-4158-B384-825A8CDACA8A][The grid has no usage history]]
  is the core gap. The grid read answers with the newest sample alone, and
  nothing reads a range.
- The capture [[id:91EBB242-A9B2-4B09-8DFE-CC440078E4B5][Expose the telemetry stats surface]]
  is the same shape from the other side. Its four reads aggregate logs and
  sessions and not grid samples, so only the pattern carries over.
- The story [[id:84345A75-CCE4-4C6B-80EA-A5857E01730B][Account for the grid's usage]]
  owns the Usage tab, the allocation by tenant. This story does not build it.
- The message bus screen is the precedent. It reads NATS samples over a range
  with a request that carries a time range and a limit, and the BFF works out
  the window on the server.

** What is stored

On 2026-10-11 the grid samples table held 3529 rows from 2026-10-10 13:39, and
the node samples table held 36661. Both are hypertables with a 30 day retention
and a 30 second write interval. For 26 nodes that is about 75000 node rows a
day and about 525000 for a week. That is a calculation and not a measurement.
A read over a week therefore buckets the rows on the server.

** What the ORE logs offer

Measured on 60 jobs unpacked from storage, each a 20 year interest rate swap.

- Each job writes =runtimes.csv= (total, count, maximum, minimum and average per
  phase) and =pricingstats.csv= (timing per trade). The values fit microseconds.
  A total of 20000 matches the log's median PRICING analytic span of 24 ms.
  These files are structured, so they are safer to read than log text.
- The six memory lines per run show 50 to 53 MiB at the start and 61 to 66 MiB
  at the finish.
- The log timestamps give phase spans. Market data load has a median of 2 ms,
  the PRICING analytic 24 ms, and the whole log 40 ms with a maximum of 121 ms.
- The NOTICE lines also carry the quotes required, the fixings and the FX
  triangulation sizes. Those describe the portfolio and not the node's load.
- The test job is tiny, so the wrapper's own steps (download, unpack, upload)
  dominate. The engine numbers say little about node load until real portfolios
  run.

** What is missing

- A range read of grid samples, and one of node samples, each with a bucket
  width. Neither model generates a protocol.
- A permission gate on both reads.
- A node state beyond heartbeat age. The ribbon can state online and quiet, and
  lost only from the runner state.
- The grid summary counts are computed for one tenant. The ledger story fixes
  that, so the load panel states whose work it counts until then.

* Decisions

- The reads bucket on the server, and the caller asks for the width. The bucket
  is plain SQL on the epoch, so the read runs on a PostgreSQL without
  TimescaleDB. The browser never receives raw rows for a week.
- A series travels as columns on a regular time axis, not as a list of rows. The
  reply carries the start, the bucket width and the bucket count once, then one
  integer array per counter. A chart reads one column at a time, the time axis
  is implicit, and no field name or timestamp repeats per point. A =samples=
  column says how many samples each bucket held, and 0 marks a gap, so a gap is
  never read as a measured zero.
- The node series uses the same time axis. The nodes are listed once, and each
  metric is one flat array of nodes times buckets, row-major, which is the shape
  the heatmap draws.
- The engine run time and peak memory come from =runtimes.csv= and the memory
  lines in the wrapper, and not from the telemetry log rows. A structured file
  is read once per job, and a log line can change its wording.

* Out of scope

- The Usage tab, the allocation by tenant (the ledger story).
- Per-node views that open from a row.
- Control of a node, such as draining or stopping it.
- The Qt client.
