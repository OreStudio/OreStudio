#+title: The ingest loop and the one pipeline
#+description: How a tick is queued, planned against its bindings, written in a batch with one transaction for each tenant, and republished per consumer on core NATS, and where an if still stands in for a registered hook.
#+type: knowledge

* Summary

=feed_ingest_loop=, declared in
=ores.marketdata.service/app/feed_ingest_loop.hpp=, is the one path every
tick takes from the wire to the store. It holds one subscription over every
producer's ticks and handles every tick the same way, whatever its asset
class.

* Detail

** The one pipeline rule

The market data pipeline in ORE Studio is one path. A producer publishes a
=market_tick= on ="synthetic.v1.ops.tick.<source>"=. The tick names its datum
by its oresmd quote URI and its producer by its source, and it carries no
owner. The ingest loop plans the tick against the enabled bindings of that
source, writes one observation per binding, and republishes the tick on the
per consumer stream. Every other note in this cluster describes one part of
that path and links here rather than restating this rule.

** How a tick is handled

- =refresh()= reads every feed binding across all tenants through
  =feed_binding_repository= and caches the enabled ones by source name. The
  marketdata service subscribes to the =feed_binding_event= channel and
  calls =refresh()= when a binding is created, retargeted or removed, so a
  bind or an unbind changes what the loop ingests without a restart.
- =plan_tick=, in =ores.marketdata.service/src/app/tick_plan.cpp=, is pure.
  It reads the tick's URI into a datum through =oresmd_uri_codec::read=,
  writes the canonical ORE key, parses the value and builds one target per
  binding. Each target carries the binding and the republish subject from
  =market_tick_subject=. It returns a =tick_drop= instead of a plan in three
  cases, which are =unbound_source=, =unnameable_datum= and =not_a_number=.
  The loop warns once per source or per URI and drops the tick.
- The subscription only decodes a tick and puts it in a bounded queue. A worker
  thread takes every tick that has arrived and handles them as one batch. A full queue
  drops its oldest tick, because an old tick that waits while a newer one arrives is
  worse than a tick that is lost. A batch that grows as the worker falls behind shares
  the cost of its write among more ticks.
- A batch writes the rows of one tenant in one transaction, because the row-level
  security policy checks the tenant of the connection. The loop keeps the last row of
  each key in a batch, because two rows of one key in one transaction would break the
  unique index of current rows. A batch that fails is split in two until the failing
  row is alone, and the loop logs that row and goes on.
- After the commit the loop republishes each stored tick on core NATS, with no wait
  for an acknowledgement. The republish follows the commit of the batch, so the stream
  does not run ahead of the table.
- The loop keeps the id of each series after it reads the series once. The cache
  clears on =refresh()= and when a row for a series fails to store.
- Persistence creates the series on the first tick that lands in it.
  =make_feed_series= takes the identity and the classification from the
  datum and the =producer_kind= from the binding. Every later tick inserts
  an observation against the series that already exists.

** Where the one path is not yet complete

One branch in =handle_tick= is not a registered hook. After a successful
persist, the loop offers an FX spot datum to the CRM bridge under the
condition =plan->datum.type() == datum::instrument_type::fx_spot=. The
comment beside it records the reason. Currency driver pairs are FX shaped,
so only an FX spot rate is a candidate driver update. A third asset class
that wants to feed CRM would need an edit at this line, so this is the one
place where an =if= still stands in for a registration that a kind could
supply.

** Two facts the code shape does not show

- The subscription is a single wildcard over the bound prefix and not one
  subscription per source. A new producer starts being ingested through the
  existence of its binding, with no subscription change.
- A bound consumer that never ticks still appears in the status log,
  because =refresh()= keeps a stats entry per bound consumer rather than
  creating one on the first tick.
- The status log gives the lag of each source, which is the age of its newest stored
  tick when its batch committed. It also gives the depth of the queue, the number of
  ticks the queue dropped, and the size and time of the last batch. A lag of 70
  minutes shows there within the first status line.
- The observation table sends no change notification. A tick changes many times each
  second, and the live tick stream carries each new value.
