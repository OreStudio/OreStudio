* Goal

A generated trade that ORE cannot read or build fails a test that names its
type and what is wrong, so the reports only fail for market data.

* Acceptance

- A test plans a population of every trade type each planner routes, builds
  the booking request of each slot and exports its instruments as ORE XML,
  in memory, with no database or service.
- The test fails, naming the trade type, when the writer refuses a trade,
  when a trade is written with no product data, or when a generated trade
  leaves out or empties a path that every ORE sample of its type states.
- A second check runs the ORE engine on that portfolio and fails on any error
  ORE raises reading or building a trade, unless a known list, asserted
  exactly as the corpus losses are, names the type and the error.
- A run of the Acme reports after provisioning records no Trade errors, only
  market data errors; the numbers are in Measurements.

* Plan

The corpus roundtrip proves that ORE's example XML survives our model. It
says nothing about the trades the generator books, which reach XML on a path
the samples never take: planner, booking request, instrument rows, export.
That path is where the reports fail.

1. *Export a generated population in memory.* The planners state a
   population as slots (=trade_population_planner.hpp=), and
   =trading_trade_population_writer::book_request_for= builds the booking
   request of a slot without a session. Its =instrument_batch= is what the
   exporter (=ores.ore.core/xml/exporter.hpp=) takes. So the test plans one
   population per asset class, long enough to reach every code the planner
   routes (=code_count=), builds each request and exports the trades. This
   needs no database, no NATS and no ORE.
2. *Judge without ORE, in the unit suite.* Three checks, each naming the
   trade type:
   - The writer refuses no trade (the XSD's required elements).
   - No trade is a passthrough: each has its product's data node.
   - Each path every ORE sample of the type states, from
     =Example_Trades=, is stated and not empty in each generated trade of
     the type. This is the story's suggestion 4. It catches a missing
     =OptionData=, =Rates=, =RangeBounds=, =Underlyings= or =Tranche=
     without knowing ORE's rules.
   A known list of accepted gaps, asserted for equality, starts from the
   first run and can only shrink.
3. *Let ORE judge, as a tagged test.* Write the portfolio and run the ORE
   engine from the vendor package on it, with the example configuration in
   =Products/Input=. Read the structured log with the parser the reporting
   service uses, and fail on a Trade error that a read or build of the trade
   raised (=node not found=, =not recognized=, =no builder found=). A Trade
   error whose cause is a missing curve or quote is market data and is
   counted apart. This catches values ORE refuses, such as a barrier type
   of =KnockOut=, which no path check sees.
4. *Fix what the checks find*, type by type, in the generator or the
   projection, each fix taking its entry off the known list.
5. *Prove it on the reports.* Recreate, provision Acme and let the reports
   tick; record the error counts by scope before and after.

** Revised on 2026-11-06: recorded trades and trade builders

Agreed with the product owner. Steps 1 and 2 above became a recorded set:
the generated trades of each type are written to
=projects/ores.synthetic/core/tests/data/generated_trades=, one portfolio per
type, and a test fails when the generator moves until the files are written
again (=ORES_UPDATE_GENERATED_TRADES=1=). The structure checks judge those
files against known lists asserted exactly.

The first run showed the cause of most report errors: the trade
constructors let a trade be built without its product. The credit
constructors take the terms every credit product shares and return the
header alone, so a CreditDefaultSwap has no CDS row and no premium leg; a
callable swap's terms hold no call option. The fix is trade builders, one
per trade type, usable outside the generator:

1. *A builder returns the trade the system uses*, a member of
   =trade_instrument=, not loose batch rows.
2. *Economic terms in, the rest from conventions*, as ORE's own
   =TradeGenerator= does (=OREData/ored/portfolio/tradegenerator.cpp=): an
   index, a notional, a maturity and a rate give a complete swap, the day
   count, frequency, calendar, adjustment and fixing days taken from the
   index's convention. A setter overrides any of them.
3. *Required terms in the constructor, optional terms in setters.* The
   required terms of a product are the ones its ORE data class reads as
   mandatory (=getChildValue(..., true)=; 439 reads in =ored/portfolio=),
   so a forgotten term is a compile error, not an empty string.
4. *ORE's vocabularies as enums*, taken from its parsers, so a builder cannot
   state a value ORE refuses, such as a barrier type of =KnockOut=.
5. *Shared sub-builders* for the shapes ORE repeats: legs, schedules, option
   blocks, barriers, underlyings, range bounds.
6. =build()= returns =std::expected= and checks what types cannot: dates in
   order, a schedule that is not empty. The error names the term.
7. *A registry* maps each catalogued trade type to its builder; a test fails
   for a type with none, and each builder's trade must roundtrip through our
   XML unchanged.
8. The builders live in =ores.trading.api=, which links =ores.refdata.api=
   (no cycle: refdata does not link trading), and take the refdata
   convention types themselves. A small =conventions_source= interface finds
   a convention by index name; one implementation holds conventions in
   memory, for tests, the generator and the shell.

Rollout: the conventions interface and the swap leg builder, proven on Swap;
then credit, whose every type is broken; then family by family, each
removing its =construct_*= functions and =*_terms= structs, migrating its
planner and taking its entries off the known lists.

Later, out of this task: the database leg. A generated trade written to the
database and exported must give the same XML as the in-memory export; the
value differ of the corpus test compares the two. That catches a row the
export reader does not read back.

range bounds, structures) that the generator does not fill.
