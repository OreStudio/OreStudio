* Acceptance

- The run's workflow carries a =post_process_results= step after =submit_compute=, so the rows are loaded once the batch exists.
- For each result of the batch the step downloads the canonical rows the node wrote, and reads them with one reader.
- A refusal names the result, the header or the row that caused it, and loads nothing: a partial load would read as a complete one.
- Every row of every result lands in one insert for the run.
- The step answers the number of rows it loaded and a message naming the run.
- The run's log rows are written once, before the rows are loaded, so a run whose rows are refused still states what the engine said.
- Nothing in the step parses the run's archive; the rows come from the canonical file.

* Plan

The step asks the batch's workunits for their results, checks each result's
outcome, downloads each result's rows into a =read_outcome=, maps them onto
=ores.reporting.api::domain::report_result_row= with the instance's party,
definition and priced date, and inserts them once. The archive stays the run's
output and is not read here.

* Notes

- The description asks for "one reader per analytic". One reader serves every
  analytic, because the canonical file states its measures as rows rather than as
  columns; what is per analytic is the projection the node runs before upload.
  Only =npv.csv= has one today, so one analytic's rows load and 34 of the 35
  seeded analytic codes would load none. Filed as

- The step records the run's account through =record_run_logs= before it loads
  the rows, so the ordering is a property of the step rather than of the archive.

* Result

The run's workflow loads its figures after the batch is submitted. The step asks
each workunit for its results, refuses a result whose outcome is not success, and
downloads the canonical rows the node wrote for each one. One reader parses the
file; a header it does not know, a field it cannot read or a figure it cannot
parse is refused with the reason, and a refusal loads nothing.

The rows are mapped onto the run's party, definition and priced date and inserted
in one call, and the step answers the count it loaded. The run's log rows are
written first, so a run whose rows are refused still carries the engine's account.

The service no longer parses the run's archive for errors: the account comes from
the rows the node wrote, which is where the figures come from too.
