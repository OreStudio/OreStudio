* Goal

The vault has two HTTP doors — a write and a reveal — and no screen. A person
cannot list the secrets their tenant keeps, cannot see a consumer, cannot rotate or
delete either, and cannot read a value back except by hand-rolling a request. The
shell now serves all of that; the web serves none of it.

* Acceptance

- =ores.web= has a vault area: a list of the tenant's secrets, a list of its
  consumers, a write flow, a reveal that is an audited act, and a delete.
- The gateway exposes the doors those screens need, with the permission each one
  requires, and the route inventory states them.
- The screens state what the vault is and is not: a value is sealed end to end,
  and the screen shows the reveal as a recorded act rather than a copy.
- A web test covers each screen's refusal, and the gate passes.

* Plan

Not yet started. Two questions decide the shape and are worth answering before the
first screen:

- *Who seals a value a person types?* The shell takes an already-sealed value and
  the client hides it before it leaves. A browser has no X25519 in the platform it
  can rely on, so either the web gets a sealing library, or the gateway accepts the
  value over the authenticated session and seals it as the consumer it already is
  for a reveal. The second is smaller and keeps the decision where the audit is.
- *Which doors are missing?* The gateway has =POST /api/v1/vault/secrets= and
  =GET /api/v1/vault/secrets/{name}/value=. A list needs =GET /api/v1/vault/secrets=
  and =GET /api/v1/vault/consumers=, a history needs the versions door, and a
  delete needs its own, each with the permission the custody service already
  enforces.

The screens follow the vault's journey, which is designed and not built
([[id:5B2D332C-7480-40E4-A989-CC8B1D2124D5][Extract the vault's journey and
prototype its screens]]).
