* Plan

** What it stops on

The 2026-10-28 run
[[https://github.com/OreStudio/OreStudio/actions/runs/40722677906][40722677906]]
failed in =windows-clang-release-ninja= inside headers this project does not
own:

#+begin_example
vcpkg_installed/x64-windows/include/rfl/Literal.hpp:413:75: error: too few
arguments provided for function-like macro invocation
vcpkg_installed/x64-windows/include/rfl/Variant.hpp:31:69: (same)
vcpkg_installed/x64-windows/include/rfl/Generic.hpp:211:73: (same)
#+end_example

"Too few arguments provided to function-like macro invocation" is a
preprocessor complaint: a macro is invoked with fewer arguments than it
declares.

** What the macros are

The compiler says which macro, and the answer is not in rfl. The full log of the
2026-10-28 run
[[https://github.com/OreStudio/OreStudio/actions/runs/40734148623][40734148623]]
names both the definition and the expansion:

#+begin_example
rfl/Literal.hpp:413:75: error: too few arguments provided to
  function-like macro invocation
  413 | static_assert(sizeof...(fields_) <= std::numeric_limits<ValueType>::max(),
...\Windows Kits\10\include\10.0.26100.0\shared\minwindef.h:193:9: note:
  macro 'max' defined here
  193 | #define max(a,b) (((a) > (b)) ? (a) : (b))
#+end_example

=minwindef.h:197= defines =min= the same way, and that is what stops
=rfl/Generic.hpp= on =std::numeric_limits<int>::min()=. The failing macro is
=Windows.h='s =min=/=max=, and the invocation it breaks is
=std::numeric_limits<T>::max()= with no arguments.

The earlier reading of this page -- that a variadic macro relies on MSVC's
traditional leniency -- was wrong. Nothing in rfl is variadic, and the failure
reproduces with clang on Linux given the two macros and a header that has
already pulled in =<limits>=.

Include order makes it a unity-build problem. Something earlier in the unit
includes =<windows.h>=, which defines both macros after =<limits>= has already
undone them, and rfl's headers are reached afterwards through
=ores.nats/domain/wire_codec.hpp=.

** The fix

=Windows.h= defines =min= and =max= only when =NOMINMAX= is not defined, so the
root =CMakeLists.txt= defines it for every Windows target, beside the
=WIN32_LEAN_AND_MEAN= it already sets. That removes the macros at their source.
It suppresses no diagnostic, and no flag is added to make a macro expand.

Both Windows compilers can reach this: the MSVC job stopped earlier, in
=ores.database=, so it had not compiled the units that fail. The definition is
therefore not clang-specific.

** What it is not

It is not the configuration document split. The error appears in headers that
carry no project type, and the split's own failure -- C1202 in the reflected
aggregate -- has not been observed yet because MSVC stops earlier. Keep the two
apart so neither is blamed for the other.

* Result

The root =CMakeLists.txt= defines =NOMINMAX= on Windows, beside
=WIN32_LEAN_AND_MEAN=. =cmake -S . -B build/output/linux-clang-release-ninja=
configures clean; the definition sits inside =if(WIN32)=, so no Linux build
changes. No Windows job has run it yet, so the acceptance's first line is
unproven until the next nightly-windows.

The failure is also recorded where a reader looks for it rather than in this
page: [[id:5AAE6900-8488-4E22-9F31-A1B9D5320EFB][CMake setup]] now states why both
Windows definitions exist.
