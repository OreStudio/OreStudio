* Acceptance

- Established what version and change_reason_code mean for the refdata synthetic generators: version 0 is the domain default of an unpersisted in-memory fixture; version 1+ is the persisted version counter the service layer sets on create.
- Established the codegen-standard generator contract after PR #1698: version==0, change_reason_code=="system.test", matching the committed generators on main.
- Answered whether version==0 assertions mean the tests verify nothing: no — the tests call the real generators and validate real output; at capture time the stale version==1 assertions failed loudly on every CI run (mismatch means FAIL, never a silent pass).
- Verified the disposition of the fix: already merged on main — commits 90ad8693be, c113b851e, 123ca2bfa, d0458e500. No stale generator assertions remain in the repo.

* Notes

- Current state on main (2026-08-11): all ten =generators_tests.cpp= test cases assert =version == 0= and =change_reason_code == "system.test"=, including =party_identifier_generator_produces_valid_instance= and =counterparty_identifier_generator_produces_valid_instance=.
- The generators emit =version = 0= / ="system.test"= (=party_identifier_generator.cpp=, =counterparty_identifier_generator.cpp=). This is the codegen-standard boilerplate every refdata generator got in PR #1698; the domain default is =int version = 0= (never-persisted instance).
- The fix for exactly this capture's issue landed on main one day after the capture was filed: commit =90ad8693be= (2026-07-17, "[dq,refdata,history,iam] Fix build and test breakage on main") rewrote the party_status, party_id_scheme, party_identifier and counterparty_identifier expectations. =c113b851e= (2026-07-28) fixed the =party_generator_produces_valid_instance= case the same way; =123ca2bfa= / =d0458e500= fixed the contact_information pair (the capture's own reference).
- Version semantics: =ores.dq.domain.change_reason_constants= defines =synthetic_new="system.new"= (fresh synthetic fixture) and =synthetic_test_data="system.test"= (general test-only fixture); both are legitimate codes. The codegen standard chose ="system.test"=, so version==1 / "system.new" were pre-standardization leftovers in the hand-written generators' tests.
- Repo-wide sweep: no stale generator assertions remain. =version == 1= hits in ores.iam/ores.trading/ores.synthetic generator tests match generators that explicitly set =version = 1= (=tenant_generator.cpp:34=, =activity_type_generator.cpp:35=, etc.) — consistent per-component contracts, not stale expectations. The hits in ores.compute/ores.dq domain tests assign the field explicitly and assert their own value — a distinct, legitimate pattern, not generator output.
- The capture's title/body overstates the live risk: at capture time the two tests failed loudly (assertion mismatch), so the drift was caught, not hidden.
