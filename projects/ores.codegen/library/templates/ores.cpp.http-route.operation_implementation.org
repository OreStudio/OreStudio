The route table and the handler bodies behind the declarations of the sibling
=ores.cpp.http-route.operation_header= archetype. One handler per declared
message the model exposes, plus the registration that puts each route on the
router and the OpenAPI registry.

Exposure is decided before this template runs: the projection keeps only the
messages that state =:http_route: true=, so the route set here is the model's
own declared HTTP surface and a message left unexposed is simply absent from
=application.http_route.routes=.

* Mustache incantations

Three constructs carry weight here.

- ={{method}}= is the route builder the operation calls. A declared operation
  states no verb, so it is always =post=: the canonical request is the whole
  of what the route sends, and a body needs a method that carries one.
- ={{#has_fields}}= selects the handler body by whether the request declares a
  field. A message with fields parses the JSON body; a message with none
  constructs the request, so a bare status probe does not fail on an empty
  body.
- ={{#requires_session}}= emits =.auth_required()= and ={{^requires_session}}=
  emits =.auth_optional()=, so the route states exactly one of the two and the
  message's own =:auth:= property alone decides which.

*One enforcement point.* =forward()= takes the caller's token from the HTTP
request, hands it to =nats_client::with_delegation=, and sends the request on
the subject the message states. The service's generated handler validates that
token and checks the operation's permission. The gateway maps the answer,
including the error the service names, and never decides access itself.

*Addressing.* The path is the message's own NATS subject transliterated:
=iam.v1.ops.lock_account= reaches =/api/v1/iam/accounts/lock=. The subject is the
address the protocol already agreed on, so the URL cannot disagree with it, and
a message the model renames moves its route in the same commit.
