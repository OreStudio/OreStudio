* Plan

Refdata needs no code change, so the task maps and proves. Map every entity,
junction and operation model to the unit it renders, and name the models that
render none with the reason each has. Prove the two negatives: no hand-written
unit registers a refdata menu and no hand-written unit extends one. Follow the
one cross-component reader, accounts set-default-party, to the refdata request it
sends, so a read reached from another component is not mistaken for a duplicate.
Run the component's shell suite.

* Notes

The six models that render no unit divide in two. The three operations are
operations the shell was never given: =asset_class= declares a catalogue read,
=calendar_adjustment= an export read and =calendar_materialisation= a
regeneration command, and all three carry the facet off with no opt-in and no
hand-written command that sends their subjects or their requests. Nothing is
superseded by leaving them off, and giving them a command would add shell surface
rather than move it, so the finding recorded here is that three declared
operations have no shell reach.

The three curve models are
[[id:EC3B6F30-2A64-4FAB-9E5A-71A5A5645C9B][Model the ORE report configuration as entities]],
bright_faraday's work in flight, committed under =[refdata] Put the curve tables'
policies in the RLS phase=. They carry no =:profile:=, so no facet is on for
them, and the shell is not theirs to decide.

The one hand-written unit that reads refdata data is an iam command, not a
refdata one: =accounts set-default-party= resolves a party name by sending
=list_parties_request=. That is the generated =parties= read used inside another
verb, not a second command answering the same name.
