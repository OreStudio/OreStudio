* Goal

Model the two facts custody needs, in =ores.vault=, as codegen entities like
every other table: a secret a tenant keeps, sealed under a key version and bound
to the row it belongs to; and a consumer, which is the identity a token presents
and the public key the vault seals to. The secret's row holds the nonce, the
tag, the ciphertext and the version, and it never holds a plaintext. The
consumer's row holds a subject and one public key, so the vault finds a
recipient from a token and from nothing else. Both are tenant-scoped, and the
schema, the domain types, the protocol and the suites are generated from the
models.

* Acceptance

- The secret's row carries the nonce, the tag, the ciphertext, the key version and the owning consumer, and two tenants may use one name.
- The consumer's row carries the subject a token presents and its public key, and one subject has one key.
- Both are tenant-scoped under the isolation policy, and no generated wire surface carries a ciphertext or a value.

* Plan

The models come first and the tree follows, so the component had to exist before
either entity could be written. The order was: five component overviews (the
group and its four parts), the catalogue row, the component scaffold from
codegen, the two entity models, then `compass generate` for the whole tree and
the tangles for the shell and HTTP libraries.

The component's shape is what the decision settled: `api`, `client`, `core` and
`service`, with the entities at the group level where a composite keeps them.
The `client` part carries its opt-in C++ scaffold because nothing generates into
it yet; the server facade it will hold belongs to the service task, and the
scaffold line and its four files leave with that task.

* Notes

** What the two models are

`ores.vault.secret` keys on `name` and carries the `owner`, the sealed value and
the key version. `ores.vault.consumer` keys on the subject a token presents and
carries the public half. Both are on the `uuid-identified-lookup` profile with
the tenant isolation policy, and both turn on the wire codec, without which the
generated api part does not compile.

** What the codegen baseline does not carry

A new component's parts do not link what its generated code includes, so each
gap is declared in the part's overview rather than patched into the generated
CMake:

- `ores.vault.core` needs `ores.database` and `ores.history.core`. The history
  edge is a `core_link_edges/forbidden_edge` and carries an exception, as the
  fifteen cores that already link it do.
- `ores.vault.service` needs `ores.eventing.core` for its event sources.
- `ores.shell.vault`, the adapter part the entity models generate commands for,
  needs `ores.shell.api`, `ores.nats`, `cli::cli` and the vault's own api, and
  the `find_package(cli)` that names the target.

** What is left for the next task

One item, and it is the first act of [[id:26B4556D-3BC8-4ED2-A58B-B889CF17E7DB][Serve
the secrets, sealed]]: the service's generated application still holds "not yet

* Result

The vault exists and holds the two facts custody needs. =ores.vault= is a Domain
composite of =api=, =client=, =core= and =service=; =ores.vault.secret= keys on
the name and carries the owner, the sealed value and the key version, and
=ores.vault.consumer= keys on the token's subject and carries the public half.
Both are tenant-scoped, both carry the wire codec, and the tree around them is
generated: types, codecs, protocols, repositories, services, handlers, history
providers, SQL, TypeScript twins, the shell commands and the ER diagram.

What the work cost beyond the models, all of it recorded in the notes above: a
new component's parts do not link what their generated code includes, so four
links were declared in the overviews; the schema entry point had to order the new
create and drop files; the service had to be registered before it had a role,
which meant two hand-maintained IAM catalogues the registry does not generate;
and the fleet count in the compass suite moved from twenty-one to twenty-two.

What is proven: the environment database was rebuilt from this model on
2026-11-26, and the four vault suites pass against it. The relevant gate passes
in full.

What it does not do: the service's application is still the scaffold, so it
cannot report ready, and the registered service carries a =compass:except= until
the serve task replaces the application. The repository, the service and the
handler layers have no operations behind them yet, and the shell commands that
the entity models generated call operations that do not exist.
