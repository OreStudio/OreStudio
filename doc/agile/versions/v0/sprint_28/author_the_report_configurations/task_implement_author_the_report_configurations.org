* Goal

Give the user guided screens to create and edit a report configuration and every entity it holds. The screens follow the record screen standard. They link to the report definition screens when those screens use a configuration.

** Rules the prototypes follow

- Prototype rules: [[id:D913FE21-6CF6-439A-89CF-6A1928AFA094][Prototypes]]. Plain HTML, CSS and JavaScript under
  =doc/prototypes/reporting/<name>/=. No framework, no build, no backend. Copy the
  design tokens from =projects/ores.web/packages/web/src/styles.css=. Switch
  variants and states with query parameters. Write a design note beside each
  prototype. Register each prototype on =doc/prototypes/reporting/index.org=
  with its review cell at =none=.
- UX standard: [[id:2BF7F03F-6BF4-45FF-8E26-4D3B4E2D943D][Record screen standard]]. Use the shared parts it names for lists,
  paging, the record page, change reasons, history, related records, icons,
  states and feedback.
- Memory: [[id:708C2462-C1F8-455B-B091-9D9690FEEAAB][Keep journey prototypes on main]].

** Steps

1. Read the ORE report configuration investigations. List every entity a
   configuration holds and the type of each link between them.
2. Group the entities into screens. Give each screen a guided flow: choose,
   check, connect.
3. Prototype the configuration screen and one screen for each related entity.
4. Show on each screen how the configuration links to a report definition. The
   report definition screens will use a configuration later.
5. Write a design note for each prototype. Register each one on the group page.
6. Run =build/scripts/check_prototype_inventory.py=.

** Scope, settled

A configuration is one of the five types a report definition binds:
=conventions=, =pricing_engines=, =todays_market=, =curve_configuration= and
=risk_report_config=. See [[id:4E0F3F61-7C25-44B5-9C3F-2F4B7B2E9A10][Create a report prototype]].
One type at a time. Conventions run in another environment. Pricing engines go
first. The other three follow.

* Notes

- *Group.* The journeys and prototypes sit in the reporting group, not a new one,
  because a configuration is bound by a report and the group already holds Create
  a report and Change what a report runs. A group for the configurations can
  split out later if the five types crowd it.
- *Vocabulary.* The models, engines, pairs and settings come from a fixture. No
  operation returns them, and no service checks a pricing engines document when
  it is written. Each journey states the gap.
- *Link to report definitions.* Each journey names the report journey that binds
  or reads the configuration. The reach statement matches Change what a report
  runs.
