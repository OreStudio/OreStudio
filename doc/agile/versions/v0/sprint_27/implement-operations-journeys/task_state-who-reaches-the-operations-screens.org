* Goal

The documents say who reaches each operations screen, for the three
signed-in contexts the shell draws: the system administrator, a tenant
administrator and a regular user. The four installation screens stand in the
*Operations* area that the system-administration menu carries alone, and the
versions screen is offered in every mode, because its answer belongs to any
signed-in person. The group page, the five journeys, the story and the
screens task carry one model.

* Plan

One documentary pass. The model comes from the accepted record rather than
from a new decision: the four installation journeys name the system
administrator as their actor, the versions journey names any signed-in
person, and the shell carries an area per mode — a screen that belongs to
another mode is absent rather than disabled
(=projects/ores.web/packages/web/src/shell/areas.ts=). The contexts are the
three the session mode carries: *system administration*, *tenant
administration* and *application* (=sessionModeSchema= in
=@ores/wire-protocol=).

The pass edits, in one commit set:

1. The group page gains *Who reaches the screens*, a table of the three
   contexts against the area, the installation screens and the versions
   screen, and the intro paragraph points at it.
2. Each of the four installation journeys states that no other signed-in
   person reaches its screen.
3. The versions journey states that the shell offers its screen in every
   mode, because the answer belongs to every session.
4. The story's acceptance and Decisions, and the screens task's Goal and
   acceptance, carry the same contract.

The prototype was re-read as the design record (accepted at =285519db99=,
on =main= since PR #2676) before the pass. Its
variant bar switches fixture states, not roles; every screen runs in system
administration mode; and the versions panel is drawn as the *About* screen.
No control on the prototype switched actor, so the documents carry the model
and the screens task owns whatever control the build adds.

* Notes

The task answers a question from the user at the story's start: how do these
screens work for a super administrator, a tenant administrator and a regular
user? The prototype was re-read to check for actor controls. It carries none:
the variant bar switches fixture states (*Reporting*, *Nothing reported*, and
so on), every screen runs as the system administrator, and the actor stands
in prose on each screen. The documents therefore carry the model, and the
screens task owns whatever control the build adds.

The versions screen's reachability follows its audience. Its actor is any
signed-in person, the login answer that carries the builds belongs to every
session, and the four installation screens alone carry privileged data — which
is also why the build must state the versions row as unknown rather than
guessing until the login answer carries the database.

* Result

The documents now carry one access model for the three signed-in contexts.
The system administrator reaches the *Operations* area and all five screens.
A tenant administrator and a regular user reach none of the four installation
screens, which stand in an area only the system-administration menu carries,
and both reach the versions screen, which the shell offers in every mode.

The group page holds the model as a table, *Who reaches the screens*. The four
installation journeys and the versions journey state their own row of it, and
the story's acceptance and the screens task's acceptance carry the same
contract, so the build has one source.

The question that started the task assumed the prototype had actor buttons.
It has none: its variant bar switches fixture states. The access model
therefore comes from the accepted record (the journeys' actors, the session
modes and the shell's absent-not-disabled rule), not from the prototype.
