* Goal

A person never writes an oresmd URL by hand. A dialog offers the schema row of the chosen kind, one field for each row, with the codes the system already keeps as pickers, and shows the URL in the codec's own spelling before it is copied or applied. The grammar lives on the server, in the codec, so the browser cannot spell a URL the server would refuse. Any screen can call the dialog, and the IR and FX synthetic feed screens do first.

* Acceptance

- The server answers an operation that describes the oresmd schema: the kinds, the instrument and quote types, and for each row its fields, which are required, which are left out, and where each field's codes come from.
- The server answers an operation that parses a URL into its fields, or says why the codec refuses it, and an operation that composes the fields into the URL in the codec's spelling.
- A dialog in ores.web shows the accepted editor of the prototype, the composer of variant A, called as variant C calls it: it opens over a screen, loads the screen's URL, composes and validates, and Apply writes the URI back.
- The IR and FX synthetic feed screens open the dialog from their market data URI.
- A screen calls the dialog with a URL and a callback, and the dialog reimplements none of the grammar.

* Decisions

- The grammar lives on the server. The codec in =ores.marketdata= is the only writer and reader of an oresmd URL, and it is strict: it refuses an unknown, repeated or empty key, a missing required field, and any spelling but its own. The browser asks the server to describe the schema, to parse a URL and to compose one. Marco chose this over a TypeScript port or a generated twin on 2026-10-12, so the strict spelling cannot drift.
- The editor is the accepted one of the prototype at =doc/prototypes/market_data/oresmd-url-editor/=: the composer, variant A, is the editor, and the blueprint invocation, variant C, is how a screen calls it. The prototype needs no new round.
- The editor is a component that any screen calls with a URL and a callback. The IR and FX synthetic feed screens call it first. Other screens follow.
- The feed screens are in PR 3152, which is open. It names every synthetic feed by its oresmd series and draws the IR curve feeds, with the URI as a row of the Details tab. The task that opens the editor from them waits for it. The server tasks and the dialog do not.
- The schema, parse and compose operations need =marketdata::market_series:read=, the permission of the series read. They are a grammar call that changes nothing and holds no party's data, so no new permission is made. Marco decided this on 2026-10-12.

* Open questions

The first tasks do not need an answer to these.

- Does the real screen use a modal over the dialog, or an inline field? The prototype draws a modal.
- Does Apply write a changed URI back to a stored record, or does the first cut only read? A series is keyed by its URI, so changing one is not an edit of a field.
- Does the real writer encode the RFC 3986 sub-delimiters in the subject path, or keep them plain as the record's examples do?
- Is a value outside the catalogue a warning or a refusal? The codec accepts what ORE accepts, and the catalogue omits some of it.

* Out of scope

- Changing the grammar or the codec's rules.
- A managed catalogue of URLs, which is variant B of the prototype and stays a record.
- Writing a series from the editor. The editor produces a URL and a screen decides what to do with it.
