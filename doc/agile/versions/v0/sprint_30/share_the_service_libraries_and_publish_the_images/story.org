* Acceptance

- One image holds the libraries every service loads, and each service image
  builds on it, so the libraries are stored and transferred once.
- The whole hierarchy is published to GitHub Container Registry, and a host
  pulls what it does not already have.
- The web service has an image of its own and reports the release it runs, so
  the services screen does not call it an older build.
- A deploy checks that every image is present before it stops anything, and
  names every container it started, so an incomplete deploy fails.

* Decisions

- *The libraries are shared, the binaries are not.* Every service links the same
  runtime, so one image carries it and each service image adds its own binary.
- *The published tag names the release and the commit.* A host can say which
  build it runs, and a republished tag never overwrites another release.
- *A pull is preferred to a transfer.* The registry is the only distribution
  path a host needs, so a host with no checkout of its own still runs.

* Out of scope

- A rollback to an earlier published tag.

* Result

The hierarchy is ores-service-base (12 MB) to ores-service-libs (677 MB, the 76
libraries the services load, stripped) to a per-service image of a few
megabytes. Twenty-four images are published to ghcr.io/orestudio under
=0.0.30-<commit>= and =main=. The pauli environment runs twenty-one containers
pulled from there, the web service among them, and it reports release 0.0.30.
A deploy that finds an image missing stops before it stops anything, and ends
with a report of every container.
