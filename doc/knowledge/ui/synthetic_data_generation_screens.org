* Summary

The synthetic area authors and runs the market data the platform generates
rather than receives. One screen does most of the work: the *Market
Simulator*, a composite window that browses the configured feeds, starts and
stops them, and shows what a running feed is producing. The configuration
windows behind it edit one row at a time: a collection, an FX price feed, an
IR curve feed, a GMM component, and the two catalogues that give the IR curve
editor its process types and parameters.

The ores.qt implementation lives in the separate =ores.qt= checkout, under
=synthetic/=, and its menu is *Market Data > Synthetic*. The prototypes below
restate each screen as plain HTML so the layout and the arguments can be
reviewed without a session.

* The data model the screens edit

| Entity | Table | What it is |
|--------+-------+------------|
| Generation config | =ores_synthetic_market_data_generation_configs_tbl= | A named, party-scoped collection of feeds, the Collection node of the tree. |
| Folder | =ores_synthetic_folders_tbl= | A generic self-referencing hierarchy; the tree is built from real folder rows, not parsed from a name. |
| FX spot generation config | =ores_synthetic_fx_spot_generation_configs_tbl= | One FX pair feed: base/quote, process, initial price, tick clock, provenance. |
| GMM component | =ores_synthetic_gmm_components_tbl= | One Gaussian of a feed's mixture: mean, stdev, weight. |
| IR curve generation config | =ores_synthetic_ir_curve_generation_configs_tbl= | One curve feed: currency, index family, tenor, role, process, provenance. |
| IR curve template entry | =ores_synthetic_ir_curve_template_entries_tbl= | One row of the curve template ladder: start tenor, end tenor, instrument. |
| Yield curve process type | =ores_synthetic_yield_curve_process_types_tbl= | A short-rate model the IR curve editor can choose: code, name, order. |
| Process parameter definition | =ores_synthetic_process_parameter_definitions_tbl= | One parameter of one process type: name, symbol, default, range, order. |

A feed is identified by its =source_name=, which mirrors its namespace path,
for example =synthetic.themes.realistic_2026.gbpusd=. Starting or stopping a
non-leaf tree node sends one folder-scoped request and the server fans it out;
a Feed leaf or a mixed selection uses the per-feed request.

* Screens

** Market Simulator
:PROPERTIES:
:ID: A55C3FED-70A5-4C08-B4C4-39416682E886
:END:

The one-stop authoring window. A toolbar (New Collection, New FX Rate, New IR
Curve, Edit, Delete, Start, Stop, Validate Vintage, Reload), a tree of the
configured feeds on the left, and a hero header, a summary and a live chart on
the right. FX feeds show a mid-price tick chart; IR curves show recent curve
snapshots overlaid, newest bold, with the number of snapshots under a History
control. *Validate Vintage* merges each contributor's check into one summary:
for FX the availability of the named vintage, for IR the local
binding-collision check, ending "N of M item(s) pass (or don't need)
validation".

The design argument is the cascade: a node's state is running, stopped or
partial ("3 of 8 running"), and starting a collection is one request, not N
client-side calls. The prototype is at
[[file:../../prototypes/synthetic-market-simulator/][synthetic market simulator]].

** Author an FX price feed
:PROPERTIES:
:ID: BDB77AC7-2442-4127-8CA6-B925759D6ADC
:END:

The FX spot generation config editor, three tabs: *Instrument* (pair, ORE key,
source name, description, enabled), *Price behaviour* and *Provenance*. Price
behaviour chooses an engine (Geometric Brownian Motion, Ornstein-Uhlenbeck,
Gaussian Mixture), the tick clock ("New price every N s", echoed as ticks per
hour), and a Simple or Advanced mode. Simple exposes drift, volatility and —
for the mean-reverting engine — long-term mean and reversion speed with the
derived half-life. Advanced edits the raw GMM components (μ, σ, w) with the
weight sum normalised on save. Two live previews sit beside the form: the
return distribution, f(x) = Σ wᵢ·N(x; μᵢ, σᵢ), and sample price paths with a
Reseed control. Provenance chooses "Fixed" (the initial price is entered) or
"From vintage data" (browse the available vintages).

The prototype is at
[[file:../../prototypes/author-an-fx-price-feed/][author an FX price feed]].

** Author an IR curve feed
:PROPERTIES:
:ID: 6AE940F0-160F-4F14-91F0-038038F4D37A
:END:

The IR curve generation config editor, four tabs: *Instrument* (currency, index
name, tenor, role — Discount, Projection or Self-discounting — fixed leg
frequency, ORE key), *Process*, *Curve Template* and *Provenance*. Process
chooses one of the seeded short-rate models, Vasicek, Cox-Ingersoll-Ross,
Hull-White, Two-Factor Gaussian or Black-Karasinski, and renders one row per
parameter the catalogue defines for it (κ, θ, σ, r0, with symbol, default,
minimum and maximum). Two previews argue the choice: the *curve shape* the
parameters and template imply, and *sample short-rate paths*. The Curve
Template is the ordered tenor ladder the curve is bootstrapped from (DEPO,
FRA, IRS, OIS), and at least one entry is required.

The prototype is at
[[file:../../prototypes/author-an-ir-curve-feed/][author an IR curve feed]].

** Bootstrap a synthetic yield curve
:PROPERTIES:
:ID: 534255D5-39E4-42DF-AEAB-AE2CD034DA5D
:END:

The step that turns a Curve Template into a curve. The ladder is the strip of
instruments to reprice (DEPO, FRA, IRS, OIS, each with its market par rate),
the process and r0 come from the IR curve feed, and the bootstrap solves one
discount factor per pillar so every instrument reprices to par. The screen
shows the solved pillars (zero rate, discount factor, forward to the pillar,
reprice residual), the three curves the result defines (zero, discount,
instantaneous forward) and the checks that matter: the residual is a
convergence check, and the forward shape is the plausibility check, because a
curve can reprice every instrument and still be implausible. A ladder whose
interval instruments overlap is refused by the curve template validator before
the solve starts, which is why the periods must touch end to end.

The prototype is at
[[file:../../prototypes/synthetic-yield-curve-bootstrap/][synthetic yield curve bootstrap]].

** Manage synthetic collections
:PROPERTIES:
:ID: 74B498A1-8DB5-4D3B-86A2-28684269AC8A
:END:

The Generation Configs window, which edits a collection: name, description and
enabled, the feeds it owns, and its version history. In the tree these same
rows are the Collection nodes, seeded as Basic, Realistic 2026, Uniform Demo
and ORE Samples 2016. Deleting a collection deletes its feeds. The prototype
is at
[[file:../../prototypes/manage-synthetic-collections/][manage synthetic collections]].

** Manage GMM components
:PROPERTIES:
:ID: 698F2B46-BDF7-420B-8DB0-DFD2B339C5E6
:END:

The GMM Components window, the same rows the FX editor edits in Advanced mode,
browsed across every FX feed at once. Each component belongs to one feed and
carries a description, mean, stdev and weight; the weights are normalised
across a feed's components when it is saved, so the screen shows both the raw
sum the user typed and the normalised weights. The prototype is at
[[file:../../prototypes/manage-gmm-components/][manage GMM components]].

** Manage yield curve process types
:PROPERTIES:
:ID: 6513F5DF-2262-4845-8C23-A9CA7090DB5B
:END:

Two runtime-managed catalogues that together drive the IR curve editor's
Process tab: the process types (Vasicek, Cox-Ingersoll-Ross, Hull-White,
Two-Factor Gaussian, Black-Karasinski) and their parameter definitions
(parameter name, display name, symbol, short label, data type, default,
minimum, maximum, order). Because the catalogue is data, a new model needs no
code change to appear in the editor. The prototype is at
[[file:../../prototypes/manage-yield-curve-process-types/][manage yield curve process types]].

* What is missing

- The Market Simulator's tick chart and the IR curve snapshot overlay read a
  live stream. A history range, and a read as of a past instant, do not exist.
- The GMM weight sum is normalised on save but the raw values are not kept, so
  a reviewer cannot see what was typed.
- The process-type and parameter-definition catalogues are runtime-managed but
  the FX editor's engines are still a code-side list, so the two halves of the
  same idea are managed differently.
- A feed's =source_name= is the identity, not the row id, so a rename is a
  re-identification.
- No screen shows a collection's *coverage* (which asset classes, instruments
  and currencies it spans) before it is started.
