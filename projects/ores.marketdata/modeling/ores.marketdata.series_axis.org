The axes a composite market series varies over. A term structure varies over one
axis and a surface over two. Each row names one field the series' instrument type
marks as a coordinate, so the object's shape is a declared thing rather than an
inference from whatever points happen to be stored.

The rows are ordered. The =sequence= column holds the position of each axis among
the object's coordinates, so a reader walks the axes in the order the type's key
writes them and a hole in a grid is a hole rather than an absent row.

The table is a current state, not a history: the series row is already temporal
and the shape of a series is written again whenever it is built. A series with no
rows here declares no shape, and a caller that reads one gets nothing rather than
a fabricated default.

* Columns

** series_id
:PROPERTIES:
:type:        uuid
:cpp_type:    boost::uuids::uuid
:primary_key: true
:END:

The series this axis belongs to. A soft reference: the series table is temporal
and its primary key carries the validity window, so no foreign key can name a
single current row of it.

** axis_field
:PROPERTIES:
:type:        text
:cpp_type:    std::string
:primary_key: true
:END:

The oresmd field code the axis is, which is one of the coordinate fields the
series' instrument type declares. A type that declares no coordinate has no
axis row.

** party_id
:PROPERTIES:
:type:     uuid
:cpp_type: boost::uuids::uuid
:END:

The owning party, copied so a query filters without joining the series.

** sequence
:PROPERTIES:
:type:    integer
:cpp_type: int
:default: 0
:END:

The axis's position among the object's coordinates. The order the schema row
declares is the order the values are read.

*** read_latest_for_series
:PROPERTIES:
:ID: 4C1E7A93-6B25-4D08-9F31-8A5C2E7B4D16
:END:

Reads the current axes of the series @p series_ids names, in one statement
however many series are asked for.

The generated key read wants a series and an axis per row, which cannot serve a
caller that asks for every axis of a series before it knows which axes the series
has. This read filters by the series alone, so a caller that checks a batch of
points reads the shapes of those points' series and nothing else.

    const std::vector<std::string>& series_ids);
#+end_src

#+begin_src cpp :name implementation :implements F2EB1914-5E94-42CA-9C77-46BDB364BF9E
std::vector<domain::series_axis>
series_axis_repository::read_latest_for_series(context ctx,
                                               const std::vector<std::string>& series_ids) {
    if (series_ids.empty())
        return {};
    const auto tid = ctx.tenant_id().to_string();
    const auto query = sqlgen::read<std::vector<series_axis_entity>> |
                       where("tenant_id"_c == tid && "series_id"_c.in(series_ids));
    return execute_read_query<series_axis_entity, domain::series_axis>(
        ctx,
        query,
        [](const auto& entities) { return series_axis_mapper::map(entities); },
        lg(),
        "Reading series axes by series.");
}

The table is current state and carries no validity window. A rebuilt series
writes its axes again, and a history here would be a second copy of a shape the
points already imply.

** Indexes

| name   | columns             | unique | current_only | where_extra |
|--------+---------------------+--------+--------------+-------------|
| series | tenant_id, series_id | false  | false        |             |

A read starts from the series, because every query names the object whose shape
it wants before it names an axis.

* Physical space

The table is a projection the service writes and a query joins. It reaches no
client as an entity of its own, so nothing but the data layer and the SQL schema
is generated.
