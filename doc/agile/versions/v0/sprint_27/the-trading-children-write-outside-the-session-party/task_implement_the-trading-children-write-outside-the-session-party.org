* Notes

The diagnosis took three steps, each proved against the running database:

1. The test aborted dereferencing an empty optional -- =party_ctx.party_id()=
   -- because =party_scoped_writes= had gone false for these two entities.
2. Seeding a party and writing the parent with it worked, and the notification
   chain proved out, so the writes themselves were sound.
3. The CRUD round trip then failed with =already_exists=. The cause is the
   replace claim: =trade_state_repository::replace_claim= reads the current row,
   the row-level security policy hid it (the session had no visible party), the
   read came back empty, and the claim therefore said "no row exists" for a row
   that does. The insert trigger, which gives version zero the one meaning "no
   current row exists", refused it.

So the missing piece was the session party, not the seed.
