* Notes

** The decision

*Replace sqlgen with generated statements on a thin layer of our own over
libpq. Replace reflect-cpp with generated JSON and MessagePack codecs over
yyjson and msgpack-c. Do not adopt libpqxx. Build every component as a unity
build first, because it is the largest lever on build time and does not wait
for the rest.*

** The reasons

1. *Build time is the measure, and the unity build is its largest lever.* On
   =ores.dq.core=, a unity build of 16 cut compile CPU by 75%, against 45% for a
   precompiled header and about 1.4% of the total for =-O0= tests. reflect-cpp
   is about 21% of the total by the sample. The unity build does not depend on
   the replacement, and the generator is now unity-safe, so it comes first.
2. *Generated code compiles three to five times faster.* A generated codec
   unit takes 4.3 s and 195 MiB, against 13.1 s and 437 MiB for reflect-cpp. A
   libpq repository unit takes 2.0 s and 175 MiB, against 10.0 s and 410 MiB
   for sqlgen. The objects are 2.6 and 9 times smaller.
3. *sqlgen's reads cost six round trips.* Every sqlgen read goes through a
   cursor: =BEGIN=, =DECLARE=, two =FETCH=, =CLOSE= and the end of the
   transaction. A point read is 5–7 times slower than one prepared statement.
   Every repository read in the services pays this today.
4. *Batches need pipeline mode, and libpqxx does not have it.* Pipeline mode
   wrote 1,000 rows 3–5 times faster than one prepared insert per row. libpqxx
   gives the same run-time speed as libpq on the paths it has, but it lacks
   pipeline mode, it needs a clang triplet because of an ABI mismatch, and it
   compiles twice as slowly as libpq. When the generator writes the calls,
   libpqxx's nicer API gives little.
5. *Generated codecs keep the wire format.* The generated codec reproduces
   reflect-cpp's JSON and MessagePack byte for byte, in both directions. The
   move needs no protocol change. The codec work is 2–3.5 times faster, but a
   message with timestamps gains only 1.1–1.9 times, because ISO 8601
   conversion is 80–90% of its cost. That is a separate capture, [[id:EDDA9476-7971-470C-A1A0-66208C25251E][Make ISO 8601 timestamp conversion fast]].
6. *The surface is almost all generated.* Of the SQL use, 3,647 of 3,692 reads
   and 862 of 864 deletes are generated. Of the JSON use, 5,577 of 5,857 calls
   are. A template change moves most of it, and the hand-written remainder is
   small.

** The order of the move

Each step leaves the system working. Each one ends in a check that proves it.

1. *Unity build everywhere.* Rename the hand-written file-local collisions,
   turn on =UNITY_BUILD= with a batch of 16 in the component CMake template,
   and keep generated code unity-safe. Proof: the whole tree builds and the
   suites pass as a unity build, and a full build without ccache on a quiet
   machine measures the gain against the baseline of about 17.2 CPU hours.
2. *The libpq layer in =ores.database=.* RAII handles for the connection and
   the result, one =ensure= for result checks, SQLSTATE mapped to our own
   exception types, a prepared-statement registry for each connection, a
   pipeline batch, COPY, and the tenant and party settings the pool sets
   today. It is the layer the data path's typed statements run on. Proof: its
   own tests against the database, and the repository benchmark on it.
3. *Generated repositories on the layer, one component at a time.* The
   repository template emits statements, typed parameters and row decoders in
   place of sqlgen calls, behind the same repository interface. Start with
   =ores.dq=, the component measured here. Proof: each component's suites
   pass, and its reads take one round trip.
4. *Delete sqlgen.* Move the 45 hand-written reads, 7 inserts and 2 deletes,
   and drop the sqlgen entity facet and the dependency. Proof: nothing includes
   sqlgen, and the build passes.
5. *One-time codecs for the twelve types with a custom encoding.* =uuid=,
   =tenant_id=, =decimal=, =time_point=, =year_month_day= and the rest, written
   by hand once, with tests that compare their bytes to reflect-cpp's.
6. *Generated codecs, one component at a time.* Each type's JSON and
   MessagePack functions go into its own translation unit, as decided earlier
   in this story, and =ores::nats::wire_codec= calls them in place of
   reflect-cpp. Proof: for each type, a test compares the generated bytes with
   reflect-cpp's in both formats, while both exist.
7. *Delete reflect-cpp.* Move the 106 dynamic JSON uses to yyjson, the enum
   tables and schemas to the generator, and drop the dependency. Proof:
   nothing includes reflect-cpp, and the build passes.

Steps 2 to 4 and steps 5 to 7 are independent of each other, and each can
follow step 1 alone.

** What the decision does not settle

- The absolute times. The repository and codec benchmarks ran on a machine
  under heavy load, so the decision rests on ratios. They will be measured
  again on a quiet machine.
- The full-build gain of each option. The [[id:C8F67EE9-885C-4EBE-9F63-0E89A1D71B70][translation-unit cost]] task still needs the full-build
  totals after each option, on a quiet machine.
- Binary results and binary COPY. A read of 1,000 text rows takes about 4 ms on
  every client, so text is enough for the control plane. The data path may
  need binary formats for ticks; that is its own decision.

* Result

Replace both libraries with generated code: statements on a thin libpq layer
in place of sqlgen, and JSON and MessagePack codecs over yyjson and msgpack-c
in place of reflect-cpp. libpqxx is not adopted. A unity build of every
component comes first, because it is the largest lever on build time and
waits on nothing. The notes give the reasons, each from a measurement in this
story, and the order of the move in seven steps.
