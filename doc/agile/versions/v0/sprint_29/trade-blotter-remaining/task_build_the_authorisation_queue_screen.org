* Acceptance

- The queue groups deals by class and by state.
- A hold and a denial need a comment.
- A new version of a deal notifies the operator and does not lock it.

* Plan

The task asks for a prototype first, so this unit is the prototype:
[[proj:doc/prototypes/operations/operational-authorisation-queue.org][Work the authorisation queue]].
It draws the queue two ways — class and state as a rail, or as tabs over a
full-width table with the deal in a drawer — and it settles nothing about the
build until one variant is chosen.

The screen itself comes after that: an Operations screen over the approval
request of kind =trading.operational_authorisation=, the trade it names, and the
states the knowledge page sets. It reuses the inbox's request parts rather than
a second authorisation model, because a second one would be a second answer to
the same question.

* Result

The prototype and the screen are both built, and the screen is the rail variant's
content with the rail's divisions moved to buttons above the list: the class as a
segmented control and the state as toggle buttons, each carrying its figure, with
the deal opening its own page rather than a pane beside the list.

* The screen

[[proj:projects/ores.web/packages/web/src/operations/AuthorisationQueuePage.tsx][AuthorisationQueuePage]]
sits at =/operations/authorisation-queue= and is offered as a card in the
Operations area, and in Trading beside the blotter. The buttons carry the class
and the state with a figure on each; the table states the deal's reference, its
type and class, the counterparty, the book, the trade date and when it was
raised; opening a row leaves the queue for the request's own page, where the deal
is read and decided. A row is tinted and edged in its state's colour, so a queue
of forty deals reads by colour before it is read by word.

The read behind it, =GET /api/queue/authorisations=, joins each request the person
may decide to the trade it names and states the book, the counterparty, the
deal's status, its type's name from the catalogue and the version it is at now.
The class is derived from the trade type rather than the asset class, because the
queue divides by how much work a deal is: a plain swap is flow and a package is
not. The eight codes the catalogue actually holds are the flow set; a code the
catalogue does not hold reads as non-flow, which is the safe direction.

A decision carries a comment, which the page requires before any button is
enabled, and a hold additionally names a reason from the lookup. Whether a hold
is offered at all is the kind's own rule, which the row carries. A deal that
moved after its request was raised is drawn in its own group and says so on its
page, and the row stays open: nothing takes a lease on a deal. A denied request
offers no decision, because a denial cannot become an authorisation.

* What the walk proved, and what it did not

A request raised against a live bond trade was read through the route and decided
through the same call: the row arrived with the deal's own reference, book,
counterparty and class, and after =approve= it left the open queue and appeared
in the answered tail as =approved= at request version 2.

No browser was available to this session, so the screen was not drawn on a
screen: the read, the decision and the grouping are proved, the pixels are not.
The grouping it depends on is tested as a function, and the label set is tested
for parity across the three languages.

* What is not offered yet

Three things the signed-off prototype draws need data the read does not carry,
and each is recorded rather than half-drawn:

- [[id:C3830177-46FC-46A1-83A0-1660C4742E82][Finish the authorisation queue's specification]] — the expiry a deal is
  pinned by, the operational error flag, the fields an amendment changed with
  their previous values, the legs of a package, and the person and time the row
  last moved.
- [[id:8276D0CF-A711-4FED-B073-574821E13167][Page the authorisation queue and count it on the server]] — the screen
  reads a window of 250 requests and says when the store holds more, because the
  inbox does not yet answer the counts each button states.
- [[id:73921707-CE11-41AD-923D-ED5B36D7FF09][Classify a product type as flow or non-flow]] — the division is a set of
  trade type codes in the BFF today; it belongs on the trade type, configured by
  a tenant and overridden by a party.

Undoing a decision is not offered either: the design calls for an un-authorise
carrying a reason, and the inbox's four decisions do not include it, so an
authorised or denied row says so rather than drawing a button that would fail.
The two reports the knowledge page names -- time held, and what stayed overnight
-- are absent.
