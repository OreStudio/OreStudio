* Summary

Importing and exporting a party, one dataset, or a whole environment. Twelve
journeys ask for a prototype; five screens answer them, because the trigger,
the payload and the permission change a variant and the act changes a screen.
The table of the screens opens each one; the table of the journeys walks from a
journey to the state of the screen that serves it.

Each prototype is a static page under =doc/prototypes/=, opens with no build
and no session, and reads mock data only. Where a prototype carries a Gemini
review the last column opens it; none does. [[file:../index.org][Prototypes]] is
the top page and the only inventory.

* Why five screens and not twelve

A screen is a place a person acts. The journeys differ in three things that do
not make a screen: the trigger (a defect, a seed, a promotion, a feed, a
correction), the payload (a bundle, a sample tree, two market files, one
conventions file), and who may act (tenant administrator, operations user,
maintainer, support). Those are variants of the entry, and of the review, and
of the register.

The differences that do make a screen are the acts themselves, and there are
five:

1. *Name a source and a scope.* Every import journey starts here. Seven
   journeys share it because the first step is identical.
2. *Decide a staged import.* A different act and a different actor: the maker
   cannot decide. One journey names it, four pass through it.
3. *Read one attempt's outcome.* A per-family question, asked after the
   commit. Four journeys ask it of the same record.
4. *Read the party's history.* A question about all attempts, not one. No
   journey names it as its destination, and four need it. It is the one screen
   that survives without a journey of its own.
5. *Take data out.* The writing side, shared by the two export journeys and
   the two import journeys that begin with an export.

Two consolidations deserve their own line. *Reproduce a defect* and *Promote an
environment* get no screen: each is an export bundle, an entry, a review, a run
and a register row, and a sixth screen would duplicate all five. *Import as a
party-scoped user* gets no screen either: it is the permission and scope
variant of the entry, the review and the register, and giving it a screen would
hide the boundary it is about. *See what a failed family left behind* is the
run record in its failed state, and *Retry* is that record's retry plus the
register's comparison — the same data read twice, not two screens.

* Adding a prototype

Create =doc/prototypes/data_exchange/<name>/= with an =index.html=, and a
=prototype.css= and =prototype.js= when it needs them. Open the page with the
links table every prototype carries, and leave its review row at =none=. Write
the design note at =doc/prototypes/data_exchange/<name>.org=, add a row to the
table above, and link the note from the row's first cell. Add the journeys it
serves to the journey table. Stop there: the site build finds every prototype
under this tree, so no build file names it.

A review goes at =doc/prototypes/data_exchange/<name>/review/=, with an
=index.html= that lists its screens. The row names it. [[file:../index.org][Prototypes]]
states the whole method and the rules that hold for every group.
