* Plan

Branch =feature/serve-the-ore-import=.

The two routes are forwarded, not composed. The gateway states the document, the
configuration the service should write into, the name and variant of a new
configuration, whether removals are kept, and the reason. It states back what
the service answers.

This is the only write in the area that acts on a document a person did not
build through a screen, which is why it is its own task and its own PR.

* Notes

** The answer is the service's reply, unchanged

The BFF's schemas for the two answers are loose objects over the wire's own
member names -- =root_element=, =in_file_products=, =configuration_id= -- so the
route states the reply exactly as the service wrote it. Nothing is renamed and
nothing is dropped, and a =success: false= is answered rather than refused,
because the person reads the reason on the step.

** The two ids are joined here**

The screen names a configuration by the id it shows; the service reads a
document by the reporting configuration the record fills. The gateway reads the
record for that second id. A body that names no configuration is joined to an
empty one, which is the file for a configuration that does not exist yet, so a
preview of a new document needs no configuration at all.

** The size is the service's to refuse**

The service refuses a document over four mebibytes with its own sentence, so the
gateway states no size rule of its own; the BFF refused it in the schema and this
does not. The route's body limit is twice the document's, so the JSON escaping
around the file does not refuse it first: a document at the limit arrives whole
and the service states what is wrong with it.

* Result

The two import steps are served at the BFF's paths, and each answers the ORE
service's own reply, a refusal included.

- The preview hands the file over and writes nothing.
- The import hands the same file over with the removed rows the person kept and
  the reason for the write, and answers what the service saved and the rows it
  could not write.
- The gateway reads no XML, builds none and validates none.

The gateway joins the two ids the screen and the service speak: the screen names
a configuration by the id it shows, and the service reads a document by the
reporting configuration that record fills. A body that names no configuration is
joined to an empty one, which is the file for a document that does not exist yet.

The reporting part's suite passes 92 cases and 692 assertions, eight of them for
these routes, and the inventory pairs 251 of the BFF's 328 routes, reporting 43 of
44.
