* Goal

Before any of the story is built, the architecture is written as knowledge: how an agent acts for a person through ores.http, from the grant that lets it, through the token that names it, the MCP transport and catalogue it calls, to the record of what it did and the six eyes on what it changes. The notes build on what the ores.agent prototype taught and on the investigations already done, and link into the existing graph: the four-eyes framework, trade authorisation, IAM sessions and the actor claim. Each note holds one idea, follows the zettelkasten house style, and draws as UML what it describes as a structure or a process.

* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the

The architecture is a new cluster, =doc/knowledge/agents/=, written by the
procedure of [[id:E3B70401-5142-4ACC-A61F-1BBF19F8470F][Zettelkasten]]:
one structure note, [[id:47B179BF-C982-4BB1-AF4F-35E00B9D2750][LLM agents acting for a person]], and eight notes, each one idea,
with seven PlantUML diagrams beside them. It builds on the run grant (Grant
Management and Token Exchange are reused, not reinvented), the four-eyes
framework, operational authorisation, the published area map of the route
inventory, the two MCP investigations, and the prototype's own documentation.

Choices the review should settle, each stated on its note:

1. *Trades use operational authorisation as the hold.* An agent's booking goes
   live and unauthorised, as every booking does, and its operational
   authorisation request gains the agent's person as a first part before
   Operations, rather than being held in a second queue first.
2. *The record has two parts*: an acting-agent field on every entity row,
   added by the codegen, and one log of every tool call in =ores.http=, reads
   included, which is the person's activity view.
3. *No automatic approval rule closes the first part* of an agent's request;
   the later parts follow the rules as the person's own write would.
4. *The catalogue's areas are the sixteen published areas* of the route
   inventory, not path segments.
