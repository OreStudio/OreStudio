* Plan

** Settled design approach

Agreed with the user on 2026-08-09. Three design questions were
settled before any provisioning ran:

1. Step 6 vs step 7: the two-step recipe is forced by the bundle
   layout. =risk_management= carries report definitions as a
   non-optional member of a demo-org bundle, so the holding company
   (whose book/portfolio tree is hand-seeded) can receive reports only
   through a root-party republish of the whole bundle, relying on the
   publish functions' per-party idempotency guards.
2. Why not one publish for everything: a bundle publish copies dataset
   rows; it cannot create the tenant, the parties, or the IAM user
   accounts. Those are security principals instantiated by the
   provisioning workflow. The tenant must exist before any data can
   land, so "one publish" is structurally impossible; "one command" is
   the ceiling.
3. Fixture-as-data: the employees ARE data already -- per-party
   accounts datasets (=acme.<party>.accounts=) with =username= and
   =photo_key= rows; the workflow reads them and instantiates the IAM
   accounts, attaching photos by key. This principle is the
   architecture and stays.

Target shape (the review's fixes):

- One provisioning command covering the system and tenant phases,
  impersonating internally -- no relogin, no user-visible loops. The
  per-office loop already runs server-side inside =provision_acme=.
- Report definitions move to their own bundle, published for the
  holding party inside the workflow. This removes recipe step 7 and
  the two-step dance.
- Keep the per-party bundle plan, the idempotency guards, and GLEIF as
  counterparty reference data.

* Notes

** Shell leg on a fresh DB: provisioning fails (F10, F11)

Ran the current recipe as-is on a fresh database. The base bundle
workflow aborted at step 0 and =acme_lei_import= failed too, yet the
shell printed "✓ Acme Corporation holding group provisioned" and the
=risk_management= publish printed "✓ All 4 step(s) completed". The
tenant holds only its System party: 0 parties, 0 staff, 0 currencies,
0 business units/portfolios/books, 0 report definitions, 1 account
(=tenant_admin=).

- F10 (root cause, fixed): =refdata.*= datasets declare no dataset
  dependencies, so the publication-service topological sort is
  unconstrained and ran =refdata.currency_pairs= before
  =iso.currencies=; the insert trigger on =ores_refdata_currency_pairs_tbl=
  rejected EUR and aborted the whole base workflow. Main independently
  fixed the core edges in PR #1935 (declared inline in each seed
  script, merged 2026-08-09); this review adds the complementary
  edges PR #1935 does not cover -- =refdata.calendars -> calendar_types,
  iso.countries, iso.coding_schemes= (its insert validates country and
  coding-scheme codes against published iso tables),
  =refdata.currency_pair_conventions -> iso.currencies=, and
  =refdata.currency_pair_convention_calendars -> currency_calendars=
  (the seed doc's stated dependency, where #1935 declares
  =-> refdata.calendars= instead) -- in a new
  =refdata_dataset_dependency_populate.sql= wired into
  =refdata_populate.sql=. Verified live on a fresh DB: all 38 base
  members completed in dependency order, LEI import, holding group,
  offices, and step-7 publish all landed.
- F11 (recorded, not yet fixed): =provision_acme_tenant_response= is
  built with =success = true= up front; both abort paths reply with
  it, so a failed provisioning looks successful to the caller. Fix:
  reply with =success = false= on the abort paths and surface the
  failed step in the response. Same family: a bundle publish whose
  steps insert 0 rows (no root party to publish for) reports "All N
  step(s) completed" with no warning -- the publish functions no-op
  silently when party resolution finds nothing.
- F6 note: the step-7 no-op does not answer F6's question -- it
  proves nothing lands when there is no party, not whether the guards
  skip demo-org data for a real root party. Recheck after F10 fix.
- Masked historically: provisioning was only ever exercised against
  restored databases whose reference data pre-existed, so the
  ordering bug never surfaced; pre-#1929 the first-available-heuristic
  failure masked it differently.
