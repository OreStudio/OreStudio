* Goal

Every request a provisioning step makes either takes the shared default deliberately or states its own deadline. A request whose work outlives the default states a longer one, with the reason in the code beside it, so a slow calibration no longer fails against a deadline set for a read.

* Acceptance

- The audit names every request class a provisioning step makes, the work it
  does and the deadline it states, in an evidence file beside the task.
- A request whose work derives or writes a set of rows states its own deadline,
  derived from a measurement and from the step budget it must fit inside.
- A request that keeps the shared default is recorded in the audit as
  deliberate, with the bound that makes it safe.
- The deadline is stated in one place per class, not repeated as a number at
  each call site.

* Plan

- Extract every request call site in =tenant_provisioning_handler.hpp= and group
  the sites by the request they send. The inventory goes in
  =evidence/request_deadlines.org=.
- Classify each class by the work it asks for: a read or a handshake, a set of
  rows derived or written from the tenant's data, or a whole-table
  regeneration.
- State the two deadlines that differ from the shared default as private
  constants in the handler, with the measurement and the step budget that
  bound each one in the comment. Apply them at the five derive sites and the
  one bulk site.
- Make the internal client's default the platform's one default, so the same
  call cannot get a different deadline from an overload.
- Leave every other request on the shared default, and record in the audit why
  each is bounded.

* Result

The audit is at =evidence/request_deadlines.org=: every call site, grouped by
request, with the work it asks for and the deadline it states.

Two deadline classes are now stated once, as private constants in
=tenant_provisioning_handler.hpp=, and used at the five derive sites and the
one bulk site:

- =work_request_deadline=, 120 s, for a curve bootstrap, a curve publish, a
  forward set, a surface calibration and a surface publish.
- =bulk_request_deadline=, 600 s, for the calendar regeneration, replacing the
  literal the call site held.

The internal client's default is now the platform's one default,
=ores::nats::service::default_request_timeout=, rather than a second 30 s
written into its signature. A call cannot get a different deadline from an
overload.

The two failing cases are =[initial_admin_guard]= tests. They assert a
PostgreSQL sqlstate of 55000 from a database function, and they fail because
this environment's database schema is out of sync with the checkout, which
=bearings= reports and which this change does not touch. Every case that does
not read the database passes.

- On a recreated database and a full build, =ores.iam.core.tests= passes in full: 348 of 348 (2026-11-13).
