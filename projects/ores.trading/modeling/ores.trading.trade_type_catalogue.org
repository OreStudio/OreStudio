#+title: ores.trading.trade_type_catalogue
#+description: The one declaration of the trade types: their seed, which instrument table holds each, and so every instrument table's trade_type check and the export routing.
#+type: ores.codegen.trade_type_catalogue
#+component: trading
#+filetags: :model:trade_type:catalogue:trading:
#+brief: The trade types and the instrument table that holds each.
#+created: 2026-10-04
#+updated: 2026-10-08

Every trade type ORE knows, and the instrument table that holds a trade of
that type. Each instrument table used to list the codes it accepts by hand,
ten of them listed all 121, and the export handler kept its own routing in
hand-written conditions. The three disagreed: a type could be routed to a
table that refused it, or accepted by a table export never read.

This model is the single source. The trade types seed is generated from it;
each instrument model that declares =:routed_column:= gets a =trade_type=
check listing exactly the codes routed to it, so the lists are disjoint and
a trade's instrument can sit in one table only; and the C++ routing the
export handler reads is generated from it.

An empty =instrument= means no table holds the type yet: nothing imports it,
so nothing can export it. A type is routed where the ORE importer writes it.

=product_type= is the asset class the refdata taxonomy carries, not the
table the type routes to. RiskParticipationAgreement is a credit product
whose importer has always written the credit table, so it is classified
=credit= and routed there; its columns on the old =rpa_instruments= table
were never written by any mapper. InflationSwap is an inflation product
whose importer writes the rates family's tables; it stays classified
=swap= and routed to =rate_instruments= until an inflation family is
scaffolded, and the reason is recorded on the rates story.

The rates family routes every one of its codes to =rate_instruments=, the
family's header. A product's own fields live in the family's fact tables,
which the header's =* Delete cascade= names and the export carries as child
arrays; the fact tables are not routed instruments, because one trade type
resolves to one instrument table and the header is that table for the whole
family.

The =Failed= type ORE uses for a trade it could not load is deliberately
absent: it is a placeholder, not a product.

* Batch

The export carries every trade's instrument as a typed array per entity, so a
receiver joins an array to its trade by the trade id every element carries and
no element needs a tag. There is one array per routed instrument entity and one
per child table below, and a member's name is the entity's declared plural.

** Instrument types

The element type of a routed instrument's array. An instrument absent from this
table crosses as its own entity type; a row here is the exception, a family
whose document shape is a container over its rows rather than a single row.

| instrument      | cpp_type            |
|-----------------+---------------------|
| bond_instrument | bond_instrument_data |

** Children

The child tables the export carries beside the instruments, one array each. A
child's elements are keyed by the same trade id, so a reader gathers one
trade's rows from the array with no second lookup structure.

The rates family's product fact tables are here because the family routes to
its header: the header is the routed instrument and a product's own fields
are its facts. The family's legs, its leg amounts and rates, its call dates,
its strikes, its schedules and its option block are here for the same reason,
and the last three are shared shapes: the bond pilot built them and the rates
family writes to them rather than widening them, so the array is the same
shape whichever family states the rows.
