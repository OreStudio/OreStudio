* Goal

Two matrices state the products a party may trade and the products one of its books may carry, and a book's set can neither exceed nor escape its party's.

* Acceptance

- A party level matrix names the product types the party may trade.
- A book level matrix names the product types that book may carry, and a write that names a type outside the party's matrix is refused.
- A query answers the types one book may carry, resolved from both matrices.

* Plan

The book's set already exists: =ores_refdata_book_product_types_tbl= with the
=books.restricts_product_types= flag, and the booking path already reads it. The
task therefore adds the party's set and the rule that binds the two, rather than
a matrix from nothing.

1. *The party's set mirrors the book's.* A =party_product_types= junction and a
   =parties.restricts_product_types= flag, both generated from a junction model
   modelled on the book's. The flag carries the distinction the book's carries:
   no rows means every type when it is false and none when it is true. Without
   the flag every existing party would stop being able to book, which is a
   migration rather than a model.
2. *The rule is enforced where the sets meet, not in a caller.* Three triggers
   hold it: a book may not name a type its party does not permit, a party may
   not drop a type one of its books carries, and a party may not start
   restricting while a book carries a type outside the set it would state. A
   caller that skips the service cannot break the rule, and the booking path
   needs no change because the book's set can no longer exceed the party's.
3. *The resolution is SQL, and it does not read the catalogue.* Two functions
   resolve a party's set and a book's set. A null answer means every type the
   catalogue states, and an empty array means none, because the catalogue
   belongs to the trading component and the reference data must not read it.
4. *The codegen carries the stack.* The junction model generates the table, its
   notify trigger, its RLS policy, the C++ domain, repository, service, handler
   and protocol, and the wire protocol. The permission seeds are hand-written,
   as they are for every table.
