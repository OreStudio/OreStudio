* Acceptance

- repository_account_repository_tests.cpp gains a case that writes an account and then replaces it with modified_by set to the account username; the case fails on the old ordering and passes on the new.
- The SQL reproduction lands on a database built from the regenerated scripts: the self write commits, the same write with another actor commits, and an actor that names no current account is still refused with Invalid modified_by (23503).
- Each run states the commit and the database it stood on, and both results appear in the task Result.
- The write moves the version forward, and the written field reads back.

* Plan

1. Add =write_account_with_itself_as_modified_by= to
   =repository_account_repository_tests.cpp=: write a first version,
   then replace it with =modified_by= set to its own username, and
   check that the write lands, the version moves to 2, and the changed
   field reads back.
2. Run the case against the current database, whose insert function
   still validates the actor after the version management: the case
   must fail, and the failure must name =Invalid modified_by= (23503).
3. Recreate the database from the regenerated scripts
   (=compass db recreate=), so the schema carries the new order.
4. Run the case again: it must pass.
5. Run the SQL reproduction against the rebuilt database, this time
   with commits: the self write lands, the other-actor write lands, and
   the actor that names no current account is refused. Record the
   version the self write leaves and the field that reads back.
6. Record every run with its commit and its database, and close.

* Notes

- The seed script's default actor, =sysadmin=, names no account. The
  account-parties insert of the seed statement is refused once the account
  row the same statement inserted is visible, because the tenant turns
  strict part-way through the statement. Seed with the member's own name as
  =AUDIT_ACCOUNT=, as =evidence/task2_seed_on_the_new_build.txt= shows.
  This behaviour belongs to the seed script's defaults, not to the fix: the
  account-parties insert never retired the actor's row.
- A terminated tenant refuses every write, including the demonstration
  probes. The bootstrap-fallback demonstration therefore provisions its own
  scratch tenant.

* Result

=write_account_with_itself_as_modified_by= joins
=projects/ores.iam/core/tests/repository_account_repository_tests.cpp=. It
writes a first account and a keeper account, then replaces the first with
=modified_by= set to its own username. It checks that the write lands, that the
version moves to 2, and that the changed field reads back.

On the old order the case fails. The database carried the old-order function
(fingerprint =089d3deaaa9b2e12=, built from 13e8b9e1ef-dirty), and the run
reports =Invalid modified_by: claude_gleason-0-f2b4cdc7-…= (=23503=) raised at
=ores_iam_accounts_insert_fn() line 85=: 5 assertions, 1 passed, 4 failed,
exit 42 (=evidence/task2_case_on_the_old_order.txt=). The read-back shows
version 1 and the service account as =modified_by=, so only the first write
landed.

The first version of the case passed on the old order. The reason is the
validator's bootstrap branch: in a fresh suite tenant the account being written
is the only non-service account, the retire empties the tenant, and bootstrap
accepts any actor. A demonstration on a scratch tenant shows both halves on the
old-order function: the self write lands while the tenant holds one account, and
the same write is refused once a keeper account remains
(=evidence/task2_bootstrap_fallback.txt=). The case now writes a keeper account
and appends a per-run UUID to the username, so no twin from an earlier run
satisfies the validator's lookup.

The database was recreated from the regenerated scripts (=compass db recreate -y
-k=; fingerprint =082f5666a7fd2039=, built from 4b000931b1-dirty), and the test
binary was rebuilt against it. The two members were seeded
(=evidence/task2_seed_on_the_new_build.txt=); the first seed is itself a self
write, and the new order lands it.

On the new order the case passes: all tests passed, 5 assertions, exit 0
(=evidence/task2_case_on_the_new_order.txt=). The SQL reproduction with commits
(=evidence/task2_sql_reproduction_on_the_new_build.txt=) lands the self write
(version 1 to 2, the =modified_by= is =ores_web_member=, the changed
=full_name= reads back), lands the control write with =ores_web_probe= as actor
(version 3), and refuses the bogus actor with =23503 Invalid modified_by:
no_such_actor_zzz=.

Every acceptance item holds: the case fails on the old ordering and passes on
the new, the SQL reproduction lands the self write and the other-actor write and
still refuses an actor that names no current account, every run states its
commit and its database, and the write moves the version forward with the
written field reading back.
