* Decisions

- The decisions live as data, not as filled cells. The 408 rows hold 177 distinct notes and
  32 KB of note text repeats across siblings, so a rule states a family's reason once and a
  new route in that family inherits it. The cost is 106 rules that decide exactly one route.
- The line between a resource and a composed view is the number of collections the answer
  weaves. One collection with its keys resolved is a resource. Two or more woven into one
  answer are a view.
- The area list is the published namespace, and the owner column names the component that
  must answer each view after the port, which is not always the module answering it today.
- A view keeps the route a screen calls until the cutover, so the test for it is the same
  request against either server. Moving it to the published namespace is a versioned change
  of its own, and doing it in the port would force every like-for-like test to compare two
  different URLs.
- The gate counts the registrations each server declares and compares them with the table,
  because a scanner that reads one line at a time silently dropped six routes on its first
  run and the gate could not see them either.

- The inventory is generated from what each server registers, not typed, and
  a gate compares it with the tree. A classification applied to a list that can go
  stale is a classification of a tree that no longer exists.
- The tool never writes a =Kind=, =Area= or =Note= cell. It keeps what it finds, so a
  regeneration cannot overwrite a decision, and the deciding stays with a person.

* Result

The four-way rule is applied to every route the two servers answer, 408 of them, and the
published area list is the design section 11.2 list plus nine areas the routes needed. The
tables a reviewer reads are the inventory, its area map and its composed views, and the gate
keeps all three honest.
