* Result

Five accounts, one per narrower person role, were created in Acme with
=evidence/walk_setup.mjs=, and =evidence/walk_roles.py= signed in as each role
and both administrators and called the same twelve routes. The matrix is in
the story's Permission matrix section. Every refusal matches the role's grant,
and no role holding a permission was refused it.

The walk turned up three failures that are not refusals:

- =GET /api/change-reasons= answered 502 for every role, because the BFF sent
  the request without its =order= field and the server's decoder requires
  every field. Fixed here: the request is the generated type, and a test pins
  its body; removing the field fails the test. It now answers 200 for every
  role.
- SuperAdmin's lock of an Acme account answers success but changes nothing,
  because row-level security keeps the system session out of the tenant's
  rows. Captured.
- Reading a session that still has to choose a party answers 500. Captured.

This task also carries the three review follow-ups from #2565, recorded in the
Review table. ctest passes the service, security and iam suites. The web
service logs to the journal already: its unit sets no redirection and the BFF
logs JSON to stdout; the file =ores.web.service.0.log= under the log directory
is left over from an earlier run and nothing writes it now.
