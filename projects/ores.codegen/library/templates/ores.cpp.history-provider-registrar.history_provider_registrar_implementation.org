Per-entity history-provider registrar implementation. Defines
=register_<entity>_history_provider()= which registers the entity's
history provider under the =product.component.entity_singular= key.
The provider body constructs the entity's service from the scoped
context, reads the entity's version history through the service, and
renders each version through the presentation mapper, via
=ores::history::service::build_entity_history_versions()=. An entity whose
rows the system tenant holds (=system_tenant_validation=), such as the
pricing engine vocabulary, is read in the system tenant: the caller's
tenant holds none of those rows, so a read there answers an empty history
for a row the caller may read.

The provider is registered with the permission a caller needs to read
the history: the entity's own read code, =<component>::<entity_plural>:read=.
A history holds every version of the rows the entity's reads serve, so it
needs the same code, and the dispatcher refuses a caller who does not hold
it. The history subject is never on the allow-list of
[[id:804C7048-DBBF-4B39-8737-BFB4949884C4][Authorised reads]], so a history
is guarded even when some of the entity's reads are open.

Each entity's registrar includes only that entity's service and
mapper headers, so a compile failure in one entity's provider cannot
block the rest of the service.

A compound-key entity emits a registrar with an empty body. Its rows
have no single-string id on the =history_provider= interface, so
nothing can be registered until a composite-key representation
exists. The direct service call carries the full key.

An entity whose declared key is shared by the rows of other scopes, such as a
contact type held by every party, is read by the row's own id
(=history_by_row_id=). The entity id is then the row's =id=, not the declared
key, so the history of one party's contact is never another party's.

Model inputs consumed by this template:

- =entity_singular= (Flags) — the service class, mapper function, and
  file names.
- =entity_singular_short= (C++ =** Repository= drawer) — the service
  method's =get_<short>_history= spelling, so irregular entities come
  out right (=get_type_history=, =get_centre_history=).
- =entity_plural= (Flags) — the read code's resource name.
- =product= and =component= (Flags) — the =entity_type= key prefix,
  composed identically to the notify_trigger SQL facet's =entity_name=.

The =product=, =component=, and =entity_singular= composition mirrors
the SQL create trigger verbatim, so the server-side provider key and
the row-change side of the history pipeline can never drift out of
sync.
