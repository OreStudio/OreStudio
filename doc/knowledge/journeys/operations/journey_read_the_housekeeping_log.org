This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A system administrator reads what each housekeeping sweep did: the policy it applied, what it freed, and why a run failed or was skipped.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want to know what housekeeping has actually done, and what it says about the
stores it did nothing for." The journey is done when the administrator has
read the runs of a sweep — when each ran, the policy it applied, what it
removed, whether it failed and why — or has established that no sweep has run
in the window asked for.

* Actor and trigger

The system administrator: an account holding the =SuperAdmin= role and acting
from the system tenant. The log belongs to *Operations*, where the other logs
of the installation are read, so the person who reads the telemetry logs reads
this one the same way.

The trigger is a claim that needs proving: a store that is still large after
its period passed, an audit that asks whether the policy is being applied, a
sweep that failed, or a policy the platform reports as skipped. It is also the
screen a person opens the morning after changing a period, to see the first run
under it.

Through a run's job the journey reaches the sweep's own instance, and through
the policy it reaches the store, so the log is the bridge between "what the
installation said it would do" and "what it did".

* Steps

1. *Open the runs log.* The administrator opens *Housekeeping* in *Operations*
   and chooses *Runs*. The system shows one row per policy per sweep: when it
   ran, which policy, which target, the outcome, what it freed and the detail
   the sweep recorded.
2. *Start on a window.* The screen opens on the last day, because the sweep
   runs daily and the question is usually about last night. The window is a
   range with an inclusive start and an exclusive end, so adjacent windows
   tile without repeating a run.
3. *Read the outcome first.* Each row's outcome is one of four the server
   states, and the screen does not invent a fifth: *applied*, the action ran;
   *skipped*, the sweep does not perform this action and says so; *failed*, the
   action was attempted and raised; *dry*, the sweep was asked to report only.
   A skipped row is the one that matters most, because the policy looks
   enabled and the store is not being bounded.
4. *Read what it freed.* Each row states the count the sweep removed and its
   detail line. A run that freed nothing is not an error: a store whose oldest
   data is younger than its period has nothing to remove, and the screen says
   that in words rather than showing a zero that looks like a failure.
5. *Narrow to one store.* The log filters by policy, by target and by outcome.
   Arriving from a store's detail filters to that store, so the question "what
   has housekeeping done for this store" is one click from the store.
6. *Follow a run to its job.* Each sweep is a job the scheduler fires, so a row
   links to the job instance that produced it: when it was triggered, when it
   started and finished, its duration and the error the scheduler recorded.
   That is the difference between "the sweep failed" and "the sweep was never
   fired".
7. *Follow a failure to its lines.* When a run failed, the detail carries the
   server's message and the time, so the telemetry logs answer the rest, in
   [[id:57C4B9A6-DA79-403E-984E-50D2561352B3][Read the telemetry logs]],
   filtered to the scheduler's component and that instant.
8. *Nothing has run.* A window with no runs is one of three findings: the
   sweep is disabled, its schedule is in the future, or the job never fired.
   The screen says which, from the sweep's schedule and its last instance, and
   links to where each is fixed.

* What is missing

- *A read of the runs.* The table =ores_scheduler_retention_runs_tbl= is
  written by the sweep and read by nothing over the wire; PR #5126 adds the
  entity and protocol. Until it merges, this journey cannot be built, and the
  honest screen is the one that says the log is not readable yet.
- *Bytes, not counts.* A run records how many rows or chunks it removed.
  "Freed 4 chunks" is not a size, and the person asking is asking about bytes.
  A size per run needs the size read that
  [[id:F7C1E75E-9F08-437B-80C0-7D50B945CA52][See what the system keeps]] also
  needs, measured before and after the action.
- *The window's paging.* The log is a store that only grows by one row per
  policy per sweep, so a plain window read with a total is enough; there is no
  reason to build paging beyond that, and the screen must not imply more
  history than the store keeps.
