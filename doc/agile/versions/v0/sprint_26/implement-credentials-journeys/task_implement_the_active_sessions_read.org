* Goal

Make =iam.v1.sessions.active= answer the sessions that have not ended.
=session_operations_handler::active= replies ={.success = true}= with no rows,
so the audit screen's active list is empty by construction and the browser route
in front of it can only report "not available".

* Acceptance

- =session_repository::read_active= answers the tenant's sessions whose
  =end_time= is empty, and none that have ended.
- =session_service::active_sessions= carries it to the handler.
- =active= fills the response with those rows and reports failure when the
  store fails, rather than answering success with nothing.
- The operation checks =iam::sessions:read=, as the derived CRUD reads of the
  same resource do.
- A repository case states what the read includes and leaves out.
- The component builds and =ores.iam.core.tests= passes.
- The live subject answers rows, checked through the browser's own route.

* Plan

1. Add the read to the repository: one row per open session, in key order,
   inside the tenant.
2. Add the service method over it.
3. Fill the handler's response and guard the operation, verifying the request
   context first, which the two operations in that handler did not do before.
4. Add a repository case for the read: an open session comes back, an ended one
   does not.
5. Build, run the suite, restart the fleet, and read the subject through
   =GET /api/sessions/active=.

* Notes

- *A session is open while its =end_time= is empty.* The store states that as an
  empty string rather than a null, because the column is =text not null default
  ''=, so the read filters on the empty string and not on =is null=.
- *The operations in that handler verified nothing before.* =active= and
  =samples= replied with success without proving the caller or checking a
  permission, because they predate the guard machinery the derived CRUD handler
  uses. =active= now proves its request context and checks =iam::sessions:read=;
  =samples= is left as it was and is not part of this task.
- *=samples= cannot be implemented yet.* Nothing writes
  =ores_iam_session_samples_tbl=: the only references to it in the component are
  the protocol and this handler's stub. A read over a table nothing fills would
  answer an empty list for ever and look like a working read, so the writer
  comes first. Recorded rather than guessed at.
- *The first administrator had to be created to read the subject live.* The
  database was recreated earlier in this story, so the deployment was in
  bootstrap mode; =POST /api/bootstrap/administrator= created it and the session
  cookie followed.

* Result

=session_repository::read_active=, which filters on the empty end time inside
the tenant; =session_service::active_sessions= carries it to the handler; and

=iam::sessions:read=, which neither operation in that handler did before.

Verification: =ores.iam.core.tests= passes whole, =427 assertions in 166 test
cases=, including a new repository case that writes one open session and one
ended session and asserts what =read_active= includes and leaves out. Live: the
fleet was restarted onto the new library, the first administrator was created,
and =GET /api/sessions/active= answered the open rows with an empty =endTime= on
each, while =GET /api/sessions?limit=2= answered two rows of eight.
