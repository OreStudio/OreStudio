* Goal

Store the engine settings of a report as a named configuration: a central row and three parts, a configuration type, a binding slot, and the seed that replaces the run settings columns.

* Acceptance

- The central table and the three part tables exist, generated from models.
- A write to a part bumps the central version in the same transaction.
- A report definition binds an engine settings configuration in its own slot.
- The ACME seed holds the engine settings configurations in place of the twenty run settings columns.

* Plan

Reference entities, chosen so the knobs are the standard ones. The central row follows =risk_report_config= in the same
component and binds the profile =uuid-identified-lookup=. Each part follows =book= and binds the profile
=fk-scoped-child=, with =parent_entity_singular= set and the foreign key to the central row flagged
=bump_parent_version=. The central row sets =generate_touch_function=, as =convention= and =portfolio= do. The drift check
(=projects/ores.codegen/scripts/check_model_drift.py=) passes.

1. Four models under =projects/ores.reporting/modeling/=: =engine_settings= and the parts =engine_settings_fixings=,
   =engine_settings_building= and =engine_settings_execution=. Every setting column is nullable. A null means the
   engine default, and a missing part row means the default for the whole group.
2. Generate the SQL, the domain, entity, mapper, repository and generator, and the TypeScript twins.
3. Wire the new scripts into the create and drop lists and the tenant reset list.
4. Seed the configuration type =engine_settings=. A report type does not require it, because absent settings mean the defaults.
5. Add the publish function, the artefact type row, the operation and its subject, so a dataset can stage a document.
6. Test the publish with pgTAP.
7. Seed the ACME engine settings and bind them in the report definitions. This is the next task.
8. Messaging, service and screens are not generated here. They come with the screens task.
