* Goal

No trades-to-ORE-portfolio exporter exists. =trade_mapper= and the instrument
mappers walk the import direction only, so =prepare_ore_package= copies
trading's blob into the tarball under a name ORE never opens, and the engine
stops at "Pricing: Build Portfolio" with "Failed to run analytics
PRICING,XVA".

=ores.ore= owns the ORE schema and the mappers, so the reverse walk belongs
there: read a trade set's archive, rebuild the mapper's input types, map them,
render the portfolio XML, and upload it as the run's portfolio input.

* Acceptance

- The mapper walks from a stored trade to the ORE portfolio element it
  describes, for every instrument type the archive can carry.
- The rendered portfolio is what ORE reads at the file its run document names
  as =portfolioFile=, and the engine proceeds past "Build Portfolio".
- A trade the mapper cannot express fails the step and names the trade, rather
  than producing a portfolio that is quietly missing it.
- The output is one portfolio per trade set, uploaded as a declared artifact
  the package step can wait on, named by the batch key.

* Plan

=save_data(const portfolio&)= already exists, and every mapper's forward
function already exists because the import path uses it. The work is the
reverse direction, and the decision to take first is whether to add a reverse
to each mapper or to build the portfolio by walking the archive directly
against =trade_mapper='s element constructors. The mappers already know both
spellings of each element, so a reverse beside each forward keeps the two
halves of one mapping in one file; a separate builder would be a second place
that knows the same correspondence.

The step must not emit a partial portfolio. ORE treats a portfolio that parses
as the truth of what to price, so a trade that cannot be mapped has to stop
the run: a silent omission is a report that prices a portfolio nobody asked
for.
