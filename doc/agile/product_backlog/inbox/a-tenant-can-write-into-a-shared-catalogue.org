#+description: The model forbids a tenant holding a write path into a table that carries a shared row, but the permissions still grant one: a tenant that writes a row of its own shadows the shared row in every read, and no check refuses it.

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

The reference data model permits exactly one copy of a shared row, and states
that a tenant must hold no write path into a table that carries one. The
permissions do not yet enforce that: a tenant's role grants, for example,
=refdata::calendars:write=, so a tenant administrator can add a calendar of its
own. A row of the tenant's own shadows the shared row of the same code in every
read, which is the divergence the model exists to prevent.

The gap is on every catalogue that took the shared-reference read: the
vocabularies first, and now the world catalogue beside them.

* Why

The read side of the model is in place and tested: a tenant reads the platform's
and the world's rows where they lie. A write path that recreates a second copy
by hand leaves the class of defect open by another route, and it is invisible in
the publication pipeline because no dataset is involved.
