* Result

The writing party comes from the token. A write lands in the caller's
party, and a caller that names no party cannot write.

Every link was confirmed, not re-derived. The file and line of each is in
=evidence/party_from_token_probe.txt=.

- The =party_id= claim lives at =ores.security/jwt/jwt_claims.hpp=:140 and
  is read at =jwt_authenticator.cpp=:208. It is minted from the account's
  own membership: at login (=auth_handler.hpp=:830=), and at a party switch
  (=account_operations_handler.hpp=:1245=), which refuses a party the
  account is not a member of. It is never taken from a request body.
- The claim becomes the request context at
  =ores.service/src/service/request_context.cpp=:77=.
- The context becomes =app.current_party_id= on every acquire
  (=tenant_aware_pool.hpp=:264=, and =bitemporal_operations.cpp=:182= for a
  raw connection). The pool writes the empty string when the context has no
  party, so a pooled connection cannot hand this context the last user's
  party.
- The setting becomes the row in 24 trading create scripts, for example
  =trading_bond_instruments_create.sql=:109=.
- The wire cannot state it. =bond_instrument_write= carries =trade_id=,
  =trade_type_code=, =trade_activity_id=, =issue_id= and =notional= only.

Proved against the running system. Logged in as
=tenant_admin@acme_corporation=, whose token names Acme Corporation Plc, a
=bond_instruments set= stored =party_id ddb2008f…=. All 32 bond instruments
carry the party their trade carries, 8 per party over 4 parties. A probe row
that stated ACMCOR under a session naming ACCOUK was stored as ACCOUK. A
session with =app.current_party_id= empty had its insert refused, with
=ERROR: invalid input syntax for type uuid: ""= at
=ores_trading_bond_instruments_insert_fn= line 9.

*Not met, and worth a task of its own.* The refusal is incidental.
=require_party= (=handler_helpers.hpp=:283=) states exactly this rule, and
no trading handler calls it. =grep -rn require_party projects/ores.trading/=
returns 0. =make_request_context= admits a party-less token at tenant scope,
and the write then dies on a cast of the empty setting. Nothing is
defaulted, so the acceptance holds, but the failure does not name its cause.
Its ten call sites sit in configuration-document handlers in three files, in
analytics, refdata and reporting.

*Noted.* Party and tenant are separate. This task covers party only. The
capture about a system-tenant caller re-parenting another tenant's run is
about =tenant_id=, which the session owns, and it is filed elsewhere.
