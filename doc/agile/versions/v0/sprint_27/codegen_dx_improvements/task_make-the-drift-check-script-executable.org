* Acceptance

- The literal path command runs to the check's own verdict:
  =projects/ores.codegen/scripts/check_component_drift.py --component compute-cpp=.
- =git ls-files -s= records mode 100755 for the script.

* Plan

Two changes, because the script had two independent reasons to refuse a
literal execution.

*The mode.* =chmod +x= and stage. Git records the mode, so the bit cannot
go missing without a commit that says so.

*The interpreter.* The shebang names =#!/usr/bin/env python3=, the system
interpreter, and the script imports codegen-module dependencies that only
the sibling virtualenv carries. So the script now tests whether it can
import =pystache=, and re-execs under =projects/ores.codegen/venv/bin/python=
when it cannot and that virtualenv exists.

The test is =sys.prefix=, not the executable path. The first attempt
compared =Path(sys.executable).resolve()= against the virtualenv's
=bin/python= and never fired: a virtualenv's interpreter is a symlink chain
back to the system one, so both paths resolve to the same file and the
guard concluded there was nothing to do. The prefix is the property that
actually differs, and it distinguishes the two environments without
resolving anything.

A virtualenv whose own interpreter lacks =pystache= terminates instead of
looping: the second pass finds =sys.prefix= equal to the virtualenv
directory and falls through to the import error.

* Result

The documented command runs as written. =check_component_drift.py= is mode
100755, and it re-execs under the codegen virtualenv when the interpreter it
was started with cannot import =pystache=.

Verified by running the literal path command, not by reasoning about it:

#+begin_example
projects/ores.codegen/scripts/check_component_drift.py --component compute-cpp
#+end_example

It regenerated =compute-cpp= across every address and reported exactly one
drifted file, the script's own uncommitted edit. The earlier failure was a
=ModuleNotFoundError= for =pystache= raised before the script read a single
argument; that error is gone.

The first version of the interpreter guard did not work and its own debug
output said so. =Path(sys.executable).resolve()= and
=Path(.../venv/bin/python).resolve()= both resolved to =/usr/bin/python3.14=,
because the virtualenv's interpreter is a symlink chain to the system one, so
the inequality the guard tested was false and the re-exec never ran. Keying
the guard on =sys.prefix= fixed it.

No gate was added to keep the execute bit. Git tracks the mode as part of the
blob entry, so the bit can only change in a commit that shows the mode change,
and there is no executable-bit lint in the tree to extend. The "if a gate can,
keep it" clause in the acceptance was written before that was established;
recording it as unnecessary is honest, but it is a gap the task text implied
would be closed and was not.

The guard's first version was wrong twice, and review found both defects.

It ran at module level, so any process that imported this module on an
interpreter without =pystache= had its process replaced by a fresh
=check_component_drift.py= carrying the importer's arguments; running
=render_component_draft.py --help= printed this script's usage instead. And
its condition could not come true under a directory holding a =bin/python=
that is not a virtualenv: that interpreter keeps the system prefix, the
inequality stays true, and the exec loops with no output at all, which is the
silent hang this task set out to remove. The guard now runs only under
=__main__=, requires =pyvenv.cfg=, and sets a sentinel on the way in.

=codegen-drift.yml= and =codegen-sweep.yml= call =python3 projects/ores.codegen/scripts/check_component_drift.py=,
and both install the codegen requirements into the runner's interpreter before
they do. The import therefore succeeds on a runner, the guard never fires, and
neither workflow was ever broken by the absent checkout virtualenv. They are
unaffected by this change rather than repaired by it. The re-exec exists for a
bare local =python3=, which has no requirements installed and no virtualenv to
find them in.
