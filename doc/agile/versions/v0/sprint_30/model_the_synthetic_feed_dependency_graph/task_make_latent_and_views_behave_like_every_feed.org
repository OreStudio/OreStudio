This page documents a [[id:31C868B9-306E-4282-BA8C-07E647021B34][task]] in the [[id:8DE041AE-95E6-40CE-9B62-2CE3BA77838A][Model the synthetic feeds as a dependency graph: upstreams, latent surfaces and vendor views]] story. It captures the goal, current status, acceptance, and any notes or results.

* Goal

The latent provider becomes, for all intents and purposes, a simulated source
like =bloomberg-a=: a catalogue source =latent-a= with its own runner and its
own market data adapter. It runs the latent vol surfaces as feeds, says why
each starts and stops, publishes each surface's clean quotes under its own
names (useful for debugging a vendor's noise against the truth), and shows on
every screen exactly as Bloomberg does: the source card with Serving, the feeds
it serves and Stop source; the dashboard state, Start and Stop; a feed's
running flag. The vendor views stop creating the surfaces they read: a view
reads a surface =latent-a= runs, and is starved when it does not run.

* Why the issues kept coming

Every provider but Latent is a chain: a catalogue source (=bloomberg-a=), a
runner in the synthetic service that runs the provider's feeds on demand, and a
market data adapter whose heartbeat says Serving or Stopped. Every screen and
verb reads that chain. Latent had no chain. The feed graph design defined a
latent surface as "published by no vendor", with no source, so a surface ran
only as a side effect of the vendor views: the first view to hold it built and
started it (=shared_surfaces::attach=), the last to release it stopped it. Each
fix after that added a "no source" branch to one screen (=ProviderNodeControl=,
=source === undefined= in the dashboard and the Provider tab, the latent
node's own rules), and each new screen found the gap again: no Start or Stop,
no state, no start messages in a latent surface's log, no running flag. The
fix is to give Latent the chain and delete the branches, not to add a fifth.

The owner decided on 2026-11-23:

- *Demand.* =latent-a= runs a surface while a demanded vendor view reads it
  (the demand passes up the graph edge from view to surface), and also while
  the market data service demands the surface's own quotes. Nothing runs that
  no one reads.
- *State.* =latent-a= announces a market data adapter and heartbeats like
  =bloomberg-a=, so the dashboard's state code serves it unchanged. With its
  own quotes, the adapter serves real ids.

* Acceptance

- The market data catalogue holds =latent-a= for provider =latent=, system kind, visible to the system tenant only.
- The synthetic service builds a runner and an adapter for =latent-a= as for every source; its offers are the latent surfaces.
- =latent-a= runs a surface while a running vendor view reads it, or while the market data service demands its quotes; its runner's journal says which view or which demand started it, and why it stopped.
- A vendor view reads a surface =latent-a= runs; it never builds or starts one. With its surface stopped, the view is starved in the graph and publishes nothing.
- =latent-a= publishes each running surface's clean points as quotes under its own names, and the market data service stores them like any vendor's.
- The dashboard and the Provider tab show Latent exactly as Bloomberg: the source card (Serving, feeds served, Stop source), the state, Start and Stop. =ProviderNodeControl= and every =source === undefined= branch are gone.
- A view's page opens through ores.http and the BFF, with its provider and whether it runs.
- Live: stopping =latent-a= stops every latent surface and starves every view, with reasons in each log; starting it brings them back; a latent surface's page shows it running and its log shows why.

** Phase 0. The view key read (independent; land it first)

The view page fails ("expected string, received undefined" for
=provider_code= and =running=) because no server reads a view with its
provider and run, as =feedRecordSchema= in
=ores.web/packages/web/src/api/client.ts= requires.

1. =ores.http/synthetic/src/routes/synthetic/feed_key_routes.cpp=: add
   =handle_fx_vol_view=, a =feed_key_read<messaging::list_fx_vol_views_request,
   messaging::fx_vol_views_filter>(req, session, "fx-vol-views",
   &messaging::list_fx_vol_views_response::fx_vol_views)=, declare it in
   =feed_key_routes.hpp=, and register
   =GET /api/synthetic/fx-vol-views/key/{key}= like the vol route (catalogue
   id =web_get_synthetic_fx_vol_views_key_key=, subject =fx_vol_views=). A view
   has =config_id= and =source_name=, so =feed_key_read= works unchanged.
   Check that the generic record route for =fx-vol-views= does not shadow it:
   the other three kinds register theirs the same way.
2. =ores.web/packages/bff/src/synthetic.ts=: add ='fx-vol-views'= to
   =FEED_KEYS=. The =:resource/key/:key= read then adds the provider and the
   run, and the ticks read accepts the view.
3. Tests: an ores.http route test beside the existing feed key tests, and a
   BFF test like the =fx-vol-surface-feeds= key tests in =synthetic.test.ts=.
4. Regenerate (=./compass.sh generate=) for the route inventory; build; run
   =ctest -R http= and the BFF tests. Live: a view page opens.

** Phase 1. The catalogue source and the notation

1. =ores.sql/populate/marketdata/marketdata_catalogue_populate.sql= installs
   =bloomberg-a= (line about 123: code, provider, session =synthetic-local=,
   mode =real_time=, ...). Add =latent-a= for provider =latent= the same way,
   and grant it to the system party as the file does for the others. Check the
   other places =git grep bloomberg-a= names (IAM seed profiles, stopped feed
   nodes) and add =latent-a= where a simulated source must be listed.
2. Row security: the =latent= provider is system kind and hidden from tenants
   (=rls_shared_read_condition: kind <> 'system'=). Make sure the =latent-a=
   source and its adapter status follow the provider: invisible to tenants,
   visible to the system tenant.
3. A notation for =latent=: =simulator_offers.hpp= skips a provider with no
   =vendor::notation_of(provider_code)=. Add a latent notation whose external
   id of a point is the scheme name of the surface plus the point (find
   =notation_of= in =ores.synthetic/api= and follow how a vendor's vol point ids
   are formed). These are the ids =latent-a='s adapter announces and serves.
4. Check: recreate the database; =latent-a= is in the catalogue; the system
   tenant sees it, Acme does not.

** Phase 2. =latent-a= runs the latent surfaces

Today: =app/application.cpp= builds one =simulated_adapter= (a
=generator_runner= plus a =simulator_adapter=) per catalogue source with
session =synthetic-local= (the loop at about line 116). The offers come from
=system_generator_offers= in =simulator_offers.hpp=, which offers a vol surface
to each VENDOR source, as a =basic_shared_surface_hold= that attaches to
=shared_surfaces= (=shared_surfaces.hpp=).

1. =latent-a= gets built by the same loop once it is in the catalogue. Its
   offers: in =system_generator_offers=, when =provider_code= is =latent=,
   offer each enabled latent surface as an ordinary feed whose generator is the
   surface itself (=fx_vol_surface_feed= from =ores.synthetic.api/feeds=, made
   as =shared_surfaces= makes it today), with the surface's =source_name=
   (=synthetic.latent.fx.fx_vol_surface.<pair>=) as its run name. The runner
   then starts, stops, names, journals and lists it like any feed; no new run
   machinery.
2. The surface publishes its clean points: give the surface the latent
   notation's targets so each tick goes out under =latent-a='s ingress
   subjects, as a vendor view's points do under its vendor's.
3. Check: a service test like =simulator_adapter_tests.cpp= (the runner journal
   test is the model) that =latent-a='s runner, given a demand for a latent
   point id, starts the surface and says why.

** Phase 3. Views read a running surface

1. Replace the lazy part of =basic_shared_surfaces=: =attach= no longer takes
   =make=, never builds and never starts; =detach= never stops. Keep it as the
   registry of running surfaces: =latent-a='s runner registers a surface when
   its run starts (the runner's =started_hook= or the generator's =start=) and
   withdraws it when the run stops. A hold whose surface is not registered
   waits: it attaches when the surface registers, and publishes nothing until
   then. Attaching to a surface and its later withdrawal must be safe under the
   registry's lock; a withdrawn surface detaches its holds.
2. =basic_shared_surface_hold= keeps its role (a view's generator) without
   =make_=. Its =publish_count= is zero while its surface does not run.
3. Remove what only served the lazy start: =hold_effect=,
   =effect_of_releasing= and the =held_surfaces= / =surfaces_only_held_here=
   fields of =simulated_source= (=ores.synthetic.api/messaging/feed_config_protocol.hpp=),
   their codec, and the source card's "surfaces only held here" effect
   (=stopEffects= in =ores.web/packages/web/src/marketdata/synthetic/sourceStrip.tsx=,
   its translations in en, pt and fr). Stopping =bloomberg-a= no longer stops
   a surface: only =latent-a= does.
4. Check: the shared surface tests, rewritten for register, wait, attach and
   withdraw; a test that a hold whose surface never registers publishes
   nothing and does not throw.

** Phase 4. Demand passes from a view to its surface

A view is demanded by the market data service through its vendor's adapter.
Its surface must then run.

1. In the fleet (=generator_fleet.hpp=), keep the set of latent surfaces the
   running views read, by view name: a vendor runner that starts a view adds
   (surface, view) to it, one that stops it removes it. Hand the set to
   =latent-a='s runner as a second demand, beside the market data demand its
   adapter receives. The runner runs the union.
2. =generator_runner::apply= takes the demand as ids. Add an internal demand
   input (a =set_derived_demand(std::map<surface, std::set<view>>)= that
   re-applies, the way =reapply()= does) rather than faking market data ids,
   so the journal can say why: "Started: demanded by
   synthetic.bloomberg.fx.fx_option.audusd (bloomberg-a)" and "Stopped: no view
   reads it and the market data service does not demand it."
3. Order at start-up: a view may start before its surface; Phase 3's waiting
   hold covers it. Guard against a cycle: a surface's demand comes only from
   views, and a view's only from market data, so none exists; keep it that way
   (no surface demands a view).
4. Check: a fleet test that starting a demanded Bloomberg view starts its
   surface on =latent-a= with the view named in the journal, and dropping the
   view's demand stops the surface when no other view reads it.

** Phase 5. The graph

1. =feed_graph.hpp= =build_feed_graph=: give each latent node a =source= edge to
   =latent-a=, as an upstream has to its provider's source. A stopped
   =latent-a= then starves every latent surface and, down the existing edges,
   every view, through =derive_states= unchanged.
2. Remove what compensated for the missing source: the latent rules that exist
   only because a latent node had no source (read =node_kind::latent= uses).
   Keep the kind as a label, and keep =without_provider(graph,
   latent_provider)= in =simulated_source_handler.hpp=: that hides the system
   provider from tenants, a different matter.
3. Update the graph tests (=service/tests/feed_graph_tests.cpp=): a latent node
   has a source edge; stopping =latent-a= starves its surfaces and their views.

** Phase 6. The screens

1. =ores.web/packages/web/src/marketdata/synthetic/DashboardTab.tsx=: delete

2. =ProviderTab.tsx=: delete its =ProviderNodeControl= branch (about line 164).
3. =feedNode.tsx=: delete =ProviderNodeControl= and =StopNodeDialog= uses that

4. =providers.ts= =SYSTEM_PROVIDERS= and =useHiddenProviders= stay: hiding

5. Tests: the dashboard and Provider tab tests show Latent with its source

6. Check: =npx vitest run= in =packages/web= and =packages/bff=; publish with

** Phase 7. Documents

1. =doc/knowledge/architecture/synthetic_feed_graph.org=: the node table's

** Phase 8. Proof

Recreate the database (=compass-devops-recreate-db=), start the services,
provision Acme (=compass-devops-run-environment=), then as the system tenant:

- The dashboard shows Latent like Bloomberg: source card =latent-a=, Serving,
  14 feeds served, Stop source; Start and Stop.
- A latent surface's page shows it running; its Messages tab says it started,
  demanded by a named view.
- Stop =latent-a=: every latent surface stops and every view is starved, each
  log says why; Bloomberg's own spots and curves keep running.
- Start =latent-a=: the surfaces and views come back.
- The Quotes board shows =latent='s clean quotes beside a vendor's noisy ones
  for the same pair.
- A view's page opens.
- As Acme, Latent and =latent-a= are not visible.
