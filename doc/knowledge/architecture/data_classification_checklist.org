* Summary

This page is the form a modeller fills in before writing a model, a
message or a table. It is short on purpose. The classification is the
decision; the pattern, the table and the wire follow from it.

A modeller classifies first, then uses the sanctioned pattern for the
classification. A pattern never chooses the classification. This order is
the whole point of the page: almost every bad shape in this codebase was
a pattern applied to data whose classification was never asked for.

A set that fits no classification is a finding to report. It is not a
shape to invent.

* Detail

** How to use it

Fill in the checklist before writing the model. Step 2 sets the
classification; step 6 then reads the sanctioned pattern from
[[id:B2D74E96-0353-4A3D-8CE5-3FC3C30D864C][Data classifications]]. The
classification selects the pattern, so a step 6 answer that contradicts a
step 2 answer means step 2 was wrong.

Fill it in before a shape is committed to a file. The checklist is also
the review artefact: a reviewer checks the classification and the
invariant, and does not audit the field count.

** The checklist

1. *Name the data and its operation.* What is the set, which caller
   receives it, and what operation is it? One sentence. If the set has no
   named caller, it has no classification yet.

2. *Classify the data.* Pick one: Entity, List, Family, Bundle,
   Artefact. One classification per message. If two answers both look
   right, write two messages rather than one shape that does both. The
   definitions are in
   [[id:B2D74E96-0353-4A3D-8CE5-3FC3C30D864C][Data classifications]].

3. *Name the invariant, or record that there is none.* Write one
   sentence of the form "X must hold at instant T". If the sentence needs
   a file, a screen, a workflow step or a boundary format to be true,
   there is no invariant: write "none" and say why.

4. *Count the owners.* How many services write rows in this set? Name the
   owner of each kind. The answer is "one" or "several", and it is never
   "the coordinator".

5. *Choose the classification from the rule.* No cross-type invariant:
   Entity, List, or split the set. Invariant and one owner: Family.
   Invariant and several owners: Bundle. A file at the boundary: Artefact,
   and classify separately what it converts into. A file's contents are
   never an invariant.

6. *Name the sanctioned pattern and the generated artefact that carries
   it.* Entity: the entity or composite pattern, and its generated type
   and verbs. List: the list verbs and the paged reply. Family:
   =ores.codegen.family=, =<family>_item= and =<family>_write=. Bundle:
   the manifest and the per-owner part message. Artefact: the mapping
   layer and the object-storage key. If no pattern carries it, stop and
   report the gap. Do not compose a flag combination that no facet
   consumes.

7. *State the atomicity scope.* The row; per element; one owner and one
   transaction; per owner; or none. Name what commits in which
   transaction, and what a failure halfway leaves behind.

8. *State the consistency point if the set claims to be a view of the
   world.* Give the =as_of= instant or snapshot the set was taken at, and
   the rule that rejects a stale one. A set that claims to be one view of
   the world without one instant is a set of rows that may disagree.

9. *State what is forbidden here.* Name the anti-pattern the
   classification replaces, plus any local rule a reviewer must enforce.
   An Entity forbids the nested aggregate. A List forbids a cross-element
   invariant. A Family forbids the hand-written restatement and the field
   group that fakes it. A Bundle forbids the archive field and the union
   of typed arrays. An Artefact forbids the document tree as the model.

10. *Record the finding if no classification fits.* Name the set, the
    invariant you could not find, the owners you could not line up, and
    the classification you believe is missing. Stop there. Do not invent a
    shape; an invented classification is a second type system, and the
    generator cannot check it.

** Worked examples

*** A list of currencies

- Classification: *List*.
- Invariant: none. The caller wants every active currency, and no
  currency constrains another.
- Owners: one, refdata.
- Pattern: the list verbs, paged, with the total.
- Atomicity: per element.
- Forbidden: a wrapper aggregate so the list can be saved whole; a
  client-side join.

*** A tenor basis swap convention

- Classification: *Family*.
- Invariant: the central convention row and its parts must describe the
  same convention at one instant, and a convention fills exactly one of
  the two forms.
- Owners: one, refdata.
- Pattern: =ores.codegen.family=, =tenor_basis_swap_convention_item= and
  =tenor_basis_swap_convention_write=, and the four derived verbs.
- Atomicity: one owner, one transaction over the central row and the part
  that the write names.
- Forbidden: a hand-written family struct; a field group that nests the
  parts.

*** An environment export

- Classification: *Bundle*.
- Invariant: every kind must describe the environment at one instant, or
  the restored environment mixes two systems.
- Owners: several. Each component writes its own kinds.
- Pattern: a content-addressed artefact with a manifest, and one
  part-reference message per owner.
- Atomicity: per owner. Global atomicity is not available.
- Consistency point: the =as_of= instant in the manifest.
- Forbidden: a struct with one typed array per kind; a tar or zip field
  in a message.
- Transport: [[id:0BA30CC1-18C8-48CC-8243-8912880F8DEC][Transporting a
  bundle]].

*** An ORE conventions file

- Classification: the file is an *Artefact*. What it converts into is 27
  *Families* and their *Lists*.
- Invariant: none across the families. A zero convention and a CDS
  convention never constrain each other; the file lists them because the
  format lists them.
- Owners: one, refdata, for every family.
- Pattern: a mapping layer from the XML to per-family family messages.
  The file, if kept, is an object-storage artefact with a key.
- Atomicity: per family write. A conversion that must be all-or-nothing
  is a bundle, because it spans the families.
- Forbidden: one struct with 27 typed arrays. The format's element list
  is not a type. The test that refuses it is in
  [[id:B2D74E96-0353-4A3D-8CE5-3FC3C30D864C][Data classifications]],
  section "The anti-type".

** Signs the checklist was skipped

- A struct named after a file, a screen or a workflow step. The name
  records where the list of kinds came from, not what constrains them.
- One struct with several arrays of unrelated concrete types.
- A member list that grows whenever the format gains an element.
- "The document must be stored in one transaction", said without naming
  an owner or an instant.
- A compile error used to justify a shape. A compile error is a technical
  problem; see
  [[id:B2D74E96-0353-4A3D-8CE5-3FC3C30D864C][Data classifications]],
  section "Compilation errors do not reclassify data".
