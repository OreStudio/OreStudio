* Goal

=marketdata.v1.ops.export_market_data_to_storage= takes no set and no date.
Its own documentation states the stance: an ORE market file "is a snapshot of
everything a run needs, not a slice of one series, and an export that could
name a subset would produce a file that does not reproduce anything". That was
true of a whole-tenant run. A run that gathers per trade set needs the export
narrowed to the requirements that set resolves and read at the set's as-of, so
two runs of one set on different dates read different rows.

* Acceptance

- The request names a trade set, and the as-of comes from the set.
- The export writes only the series that set's resolution requires.
- The rows are read as of the set's date, not as of now.
- A requirement that no series answers fails the step and names the missing
  data, because ORE cannot price a curve whose quotes are quietly absent.
- The market and fixings bodies remain what ORE parses, as they are today.

* Plan

The serializer already exists and is proven: =ore_export_service::write_all=
walks the series, observations and fixings and renders the files ORE reads.
What changes is the selection it walks and the date it reads at, so this task
is mostly about the resolution task's output reaching it.

The wiring, in three units that each build and test on its own:

1. *The export names its requirements.* =export_market_data_to_storage_request=
   gains =requirements=, the oresmd addresses the run needs. The handler reads
   =ores_marketdata_requirement_coverage_fn= once for the whole list; a
   requirement no series answers fails the export and is named, and the
   answering addresses narrow the export. The narrowing lives in
   =series_to_export=, beside the choice between the party's own series and the
   world's fixing, so a required fixing is still written from the system tenant.
2. *Trading answers what a set needs.* =trading.v1.ops.
   resolve_market_data_requirements= takes trade ids and the as-of and returns
   the distinct addresses =ores_trading_market_references_fn= reads from their
   instrument rows. Trading owns the trades, so the resolution stays in the
   service that can read them, and a legal address never leaves the database.
3. *The run passes the set through.* =gather_market_data_request= gains
   =trade_ids=, the workflow hands it the manifest =gather_trades= wrote, and
   the step calls the trading verb before it calls the export. An empty set
   keeps the whole-tenant gather a caller that names no set asks for.

The documented stance above has to be reversed deliberately rather than
quietly: the comment argues that a subset does not reproduce anything, and the
answer is that the *resolution* is what makes a subset reproducible — the set
is derived from the trade set's own members at a stated date, not chosen by a
caller who might choose badly. When the stance changes, that reasoning belongs
in the same comment.

Fixings are read the same way and stay a separate file, because the engine
reads them from one of its own.

* Result

A run now gathers the market data its own trades need. The gather step hands the
trade set to trading, trading answers the distinct oresmd addresses its
instrument rows hold, and the export writes the series that answer them and
refuses the ones the market does not hold, naming them.

The pieces, each with its own test or measurement:

- =export_market_data_to_storage_request.requirements=, read once through
  =ores_marketdata_requirement_coverage_fn=. An address with no series fails the
  export and is named; the answering addresses narrow the export in
  =series_to_export=, beside the choice between the party's own series and the
  world's fixing, so a required fixing is still written from the system tenant.
- =trading.v1.ops.resolve_market_data_requirements=, backed by
  =ores_trading_market_references_fn=, so the resolution stays in the service
  that owns the trades.
- =gather_market_data_request.trade_ids=, fed by the manifest =gather_trades=
  wrote, so the run states its set rather than a caller choosing one.

Measured on the acme_demo provision of 2026-11-21: 467 trades resolved to 98
requirements, and the export refused the 93 the market does not hold, all of
them commodity fixings and credit curves. That refusal is the acceptance; the
data gap belongs to "Prove a run on generated trades and market data".

Read on the way there: the as-of is the run's business date, and reading the
trades at that day's first instant resolved nothing on a population booked
during the day. The set is read at the close of the day it names, which is the
rule the market coverage read already applied.

What is not proven live: a narrowed export that succeeds end to end, because
this population's requirements are 93 of 98 missing. The selection is pinned by
the unit test, and the success path is what the next task's run shows.
