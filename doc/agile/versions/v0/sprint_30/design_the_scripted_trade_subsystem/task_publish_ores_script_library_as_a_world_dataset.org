* Goal

ORE's script library arrives as a world dataset whose methodology extracts, corrects, parses and derives the inputs of every script with ORE Studio's parser; a tenant's own script is parsed when it is published; and a scripted trade records the version of the script it was booked on, or its inline text, so it revalues on the payoff it was booked with.

* Acceptance

- the library is a dataset of the Open Source Risk Engine catalogue
- the generator is =external/ore/tools/generate_script_library.py=, which reads only =external/ore/examples/Products/Input/scriptlibrary.xml= and writes the dataset's populate files
- it replaces the =script_library_seed= step of =compass generate= as the only generator of the library's rows, so =trading_script_library_populate.sql= and its include in =populate_trading.sql= go
- the corrections are a data file beside the generator, each naming its script and variant, the text it replaces, its replacement and the reason; the file is their only list
- =external/ore/methodology.txt= gains a numbered step before its final commit step that states exactly how to reproduce the staged rows from a clean checkout: the ORE commit, the build of =ores.shell= the generator calls, the command, the files read and written, the corrections, the verification and the commit; following it on a fresh checkout reproduces the committed files byte for byte
- its rows are staged in the artefact tables of the script, variant, input, result and calibration entities, which opt in through their models, whose descriptions then state that the rows are derived by the dataset's methodology
- the trading service's publish function writes the staged rows into the system tenant, and the dataset is a member of the =world= bundle
- a check in the build job, after =ores.shell= is built, runs the generator and verifies its output equals the committed files
- the populate scripts that load the library and correct it today are retired; the corrections are steps of the methodology, under the same exactly-once rule
- the shell's =script parse=, =script check=, =script inputs= and =script print= run with no session and no server, and =script check= prints each diagnostic as FILE:LINE:COLUMN: severity: message [code] and exits with a non-zero status on any error
- the generator parses every script with =script check= and fails on a script that does not parse, with its line and column
- the staged inputs are those =script inputs= derives, which corrects Accumulator02's ObservationPeriodEndDates from a Number list to an Event list, and a test verifies they equal inputs_of for every script
- a republished dataset writes a new version only of the scripts whose rows changed
- a tenant's script is parsed when the tenant publishes it and refused with the same diagnostics; a name the world library holds draws a warning, and the tenant's script is the one its bookings resolve the name to
- a scripted trade records its library script's name, holding tenant and version, or its inline text and a hash of it
- a run writes the library from the versions its trades name

* Plan

Seven PRs, each ending in a check. The fourth step of the first plan, a trade
records its script's version and a run writes the library from those versions,
is three: a version must first name a whole script, which the rows did not.

1. The shell's =script= menu, which needs no session: =parse=, =check=,
   =inputs= and =print=, a local unit of =ores.shell.trading= linking
   =ores.trading.scripting=. The generator runs them through the shell's batch
   mode, =ores.shell --load=, which exits non-zero when a command fails.
2. The dataset: the generator and its corrections file in =external/ore/tools/=,
   the methodology step, the staging tables of the seven script entities, the
   SQL publish function, the artefact type and the =world= bundle membership,
   and the build job's reproduction check; the =script_library_seed= output and
   the corrections populate script are retired, and the twin recipes' populate
   runs after the bring-up publish.
3. The trading service's publish-from-DQ handler, so the dataset can be
   republished over the bus as well as at bring-up.
4. A script version names the whole script: every row beneath a script carries
   the version of its script row, and the state of any version reads back.
5. A scripted trade records its script's name, holding tenant and version, or
   its inline text and a hash.
6. A run writes the library from the versions its trades name.
7. A tenant publishes its own script through the trading service, which parses
   it and warns on a name the world library holds.

* Notes

** What the fifth PR found

The pin is set by a trigger on the scripted instruments table rather than by
the booking service, because three paths write the table: booking, the import
of an ORE portfolio and the generators. The trigger fires after the generated
insert trigger, as Postgres fires a table's triggers in name order; by then the
generated trigger has validated the tenant and closed the trade's current row,
so an amendment's previous pin is read from the trade's latest row.

A name no library holds is recorded with no version rather than refused. The
generators name =Autocallable=, which ORE's library does not hold, and the run,
which needs the script, is where its absence is an error.

** What the fourth PR found

A trade could not have recorded a version that meant anything. A change to a
script wrote its script row and its child rows as new versions, but each row's
version counts that row's own writes, so the numbers did not line up, and the
insert triggers stamp =valid_from= with =clock_timestamp()= while the publish
closed rows at =current_timestamp=, so no instant separated one version from
the next. Every child row now carries =script_version=, the version the script
row was given in the same publish, and the published state function reads any
version by that number.

The column is not staged: the six models declare their staging bodies in
=* Artefact columns=, listing the columns they had, so the staging tables are
unchanged. A column option that leaves one column out of the default staging
projection would be shorter, but the codegen that =compass-ng= runs is its own
binary, so the option belongs there.

** What the third PR found

The trading service had no handler for =trading.v1.ops.publish_script_library_from_dq=,
so a bundle publish over the bus could not publish the dataset: its step
reached no subscriber. The bring-up publish runs in SQL and did not need one.

The handler copies the analytics one, with the subject plan that refuses a
function name which is not a plain identifier, and its test. It is the ninth
copy of the same handler; the copies differ in their function-name rule, their
guard and their decode. The capture
[[id:AE3F5C64-0007-4C54-BEF9-D6ECFFDC0238][One publish-from-DQ handler for every service]]
records them and the move of one copy into a shared library, which needs a
decision on where the command and result types live, so it is not part of
this task.

** What the second PR found

- The staging template wrote only the first column of a composite primary key,
  so every staged script table lost its purpose or sequence number; it now
  writes every key column, as the live table's template does. No existing
  staged entity has a composite key, so nothing else changed.
- Against the seed it retires, the generator differs where it should: the two
  corrected scripts, each the seed's code with its correction applied;
  Accumulator02's ObservationPeriodEndDates, now a list of Events; and five
  script descriptions the seed took from section headings
  (=RAINBOW OPTIONS -->=, the copyright line), now each script's own first line.
  Every other row of the seven tables is equal.
- Input descriptions sit under =Input Data:= or =Inputs:=, and an entry may
  separate its name with a tab or wrap onto deeper lines, so an entry is read
  as a name and its text, and the first entry of a name is kept.
- The twin recipes became no dataset: they are platform data ORE Studio
  authors, which a populate script writes, and they need the scripts only to
  exist. They run after the bring-up publish, as the tenor convention
  resolutions already do.
- Every publish-from-DQ function writes another service's live tables outside
  its repository, and each is excused for =entity_writes/sql_writer=; the
  library's is excused the same way.

** What the first PR found

- The shell runs a script offline with =--load=: with no server, the
  auto-connect fails, the commands run, and a command that marks a failure ends
  the batch with exit status 1. The generator relies on that contract.
- The shell already has a =script_commands= class, for =load=, so the payoff
  script unit is =payoff_script_commands=; the menu is still =script=.
- A REQUIRE rule comes back as the condition on one line, and inputs come in
  the order =inputs_of= derives them, which is the order the store holds.
- The twin recipes (=trading_script_twin_inputs_populate.sql=) are a populate
  script whose trigger requires the script to exist. Once the scripts arrive by
  the =world= publish, which runs after the populate scripts, the recipes cannot
  be written by a populate script; the second PR has to order them after the
  publish.


The world bundle is published in SQL at bring-up, before any service runs, so the parsing and derivation are steps of the generator rather than of the publish function.

* Result

In progress: the first four of seven PRs are in. The fourth makes a script
version name the whole script: every row beneath a script carries the version
of its script row, so any version reads back exactly. The third gives the trading
service a handler for the script library's publish step, so a bundle
published over the bus publishes the library as the bring-up does. The second publishes ORE's
script library as the =ore.script_library= world dataset: a generator in
=external/ore/tools/= extracts, corrects, parses and derives every script with
the shell, and the bring-up publishes the staged rows, writing a new version
only of a script that changed. In the first, the shell's =script= menu parses,
checks and lists the inputs of a payoff script with no session and no server,
and a batch run with =--load= exits non-zero when a command fails, which is the
contract the library's generator calls it under.
