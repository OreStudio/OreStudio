* Result

Done. =provision_tenant_workflow= declares the system-scoped step kinds plus
=start_tenant_setup=, and =tenant_setup_workflow= declares the remaining kinds
plus =complete_provisioning=. The new step's executor reads the run's own request
from =arguments_json=, mints an instance id and publishes the child's start
message for the new tenant, with a token minted for that tenant's administrator,
so the child is owned by the tenant it sets up and the plan is never stored twice.

Both runs were exercised over HTTP against a running fleet on a recreated
database: the system run completed in two steps and left the tenant
=bootstrapping=; the tenant run completed in four and left it =active=, with the
tenant's =onboarding.tenant= flag turning true so the gate released its
administrator.

The workflow engine itself did not change: a step already carries its own subject
and payload, and the step executor already mints its own token, so one run
starting another is a step kind rather than an engine feature.
