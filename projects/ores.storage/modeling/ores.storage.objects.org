#+title: ores.storage.objects
#+description: Codegen operation model for object storage: put, get, delete and list over a bucket and an opaque key, the surface both the NATS service and the HTTP routes serve.
#+type: ores.codegen.operation
#+component: storage
#+subcomponent: api
#+entity_singular: objects
#+namespace: ores::storage::messaging
#+brief: Object storage operations.
#+filetags: :model:operation:storage:
#+created: 2026-09-26
#+updated: 2026-09-26

Object storage has no entity: an object is a bucket, an opaque key and a byte
string, and the store never parses any of the three. That is why the surface is
an operation model rather than an entity model, and why the messages below carry
no tenancy and no server-owned field.

Four operations are modelled. There is deliberately no =exists= operation: the
protocol has no such verb, and existence is a read, so =get= reports absence in
its own reply and the HTTP projection answers =HEAD= without a body. There is no
=counter= either, because a count is a property of a list.

The bucket is the caller's concern. Storage holds no bucket name, no registry
and no allow-list, so the bucket arrives as part of the request and the server
validates it as a key segment rather than checking it against a list.

The handler that serves these operations stays hand-written beside this model,
because an operation model generates no service handler. It authenticates the
caller, checks the operation's permission code, and calls =ores.storage.core=.

#+begin_src cpp :name comment
/**
 * @brief Writes one object, replacing whatever was at the key.
 *
 * A put carries the whole object: there is no append and no partial write, so
 * an object is either the old value or the new one. The content travels in the
 * message only when it is small enough to; the bulk path is HTTP, and the two
 * leave the same object at the same bucket and key.
 */
#+end_src
