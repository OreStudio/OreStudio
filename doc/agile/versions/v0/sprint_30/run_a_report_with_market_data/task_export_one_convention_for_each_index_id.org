* Acceptance

- The curated set holds no id under both IborIndex and OvernightIndex, and the generator refuses one that does.
- A run's conventions.xml holds one convention for each id.
- The GBP OIS convention resolves in ORE on a run of the generated trades.

* Plan

Found by the prototype of the market configuration task: a run's package was
amended by hand and run on the vendored ORE 1.8.17.0, and the GBP discount
curve failed with "Convention 'GBP-OIS-CONVENTIONS' not found" although the
package's =conventions.xml= held it.

1. State the rule where the gate checks the table: =propose.py --check=
   refuses an id that more than one row names, whatever the kinds. Run it on
   the current table first, so the check is seen to fail.
2. Keep one row for each of the six ids: an overnight rate keeps its
   OvernightIndex, an IBOR family its IborIndex, because the swap and basis
   conventions name the tenored IBOR indices.
3. Record why in =propose_decisions.tsv= and the methodology, and
   regenerate the seed.
4. Run the generated trades on a recreated database and read whether the
   OIS conventions resolve.

* Notes

The cause: ORE holds every convention in one map keyed by id and refuses the
second of two with one id (the log reads "Convention already exists for id
GBP-SONIA"). It keeps the first it reads, the IborIndex, so the OIS
convention =GBP-OIS-CONVENTIONS=, which names =GBP-SONIA=, builds its index
from an IBOR convention, fails, and is then reported as not found. Every
trade discounted in GBP, USD, JPY or CAD failed at its discount curve,
before any index or quote mattered.

Removing the stray IborIndex from the package by hand turned the GBP OIS
error count from 31 to 0, and ORE built a trade where it had built none.

The IborIndex rows of the four overnight rates were mined from ORE's
=indexparser.cpp=, where the ids name the term rates. ORE parses a term rate
such as =GBP-SONIA-3M= without a convention, so dropping them loses nothing.
