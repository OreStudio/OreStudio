* Goal

The detail view of a feed draws its oresmd URI as a link to the series with an Inspect button. The list column of the same name is plain text, so the reference behaves two ways. Draw the column with the same component, without three queries for each row.

* Acceptance

- The list column links to the series when a page can open it, and is plain text otherwise.
- A grid of many feeds does not make a parse request for each row.

* Plan

The premise is stale. The per-kind feed list screens, with the =oresmd URI= column
of the FX list, went with commit 246921bba9 on 2026-10-13, when Synthetic became one
screen with a feed tree. The only feed list now is the feed tree table in
=marketdata/synthetic/FeedTreeTab.tsx=, which has no such column, and the IR list
never had one. The column is therefore added to the feed tree and drawn with the
rule the record page uses.

1. The rule that decides where a URL points moves into =oresmd/identity.ts= as
   =seriesTargetOf=: the Evolution page for a series with an axis, the series page
   for one with no axis, and nowhere for a refusal, a fixing or a series the party
   does not have. The record page and the list both call it.
2. =OresmdUrlResolved= draws a URL with an already-decided target and the Inspect
   button. =OresmdUrl= decides its own target and hands it to the same drawing, so
   the record page and a row of the list look and behave the same.
3. The list decides the target of every row on the page in one read, not one read a
   row: =oresmd/useSeriesTargets.ts= asks the codec about the URIs of the page
   together, through one new route (=POST /api/oresmd/parse-many=) that forwards
   each URI to the server's existing parse subject. The party's series list is
   already one read, and the schema is one read kept for the session.
4. A test covers the rule over its five outcomes, and a test covers the read: one
   call for a page of URIs, none a row, and a set larger than one call split into
   the sets the codec's limit carries.
