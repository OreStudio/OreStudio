* Summary

This prototype draws the change of one product row as the Record screen standard draws an amend: the record page, the dialog with a change reason, the stale-version refusal and the History tab with Revert. The configuration is shared and under model risk control, so an approved configuration never changes in place. On an approved configuration the dialog *proposes* a new version, and the version in force stays in force until the sign-off completes. On a draft the dialog changes the row in place. The one dialog adds three things the standard leaves open: the *reach*, the *difference* and the *choice of what to do with the change*.

The page answers to the journey [[id:D998F36A-9716-48E7-BC70-BC4813115591][Change how a product is priced]]. It is throwaway: it reads no service, writes nothing to one, and states which parts of the interaction no operation supports. It follows the [[id:2BF7F03F-6BF4-45FF-8E26-4D3B4E2D943D][Record screen standard]] and the rules in [[file:../index.org][Prototypes]]: plain HTML, CSS and JavaScript, no framework, no build and no backend, with the design tokens of =projects/ores.web/packages/web/src/styles.css=.

* Detail

** The question the screen answers

"The desk says my Bermudan swaption price is off, so I want to price it another way, and I want to know what else that moves." A product row belongs to a configuration that several reports bind. A change to it is a change to all of them, and a person who owns one report may not own the others. The dialog says so before anything is typed: nothing changes now, and the change reaches the next run of each report once it is approved. It shows the difference as the history will draw it, and offers a draft copy for a person who only wants to test.

** States and switches

- =?status=approved|draft=: an approved configuration takes a proposal, and a draft changes in place with no choice.
- =?bound=0|1|4=: how many reports bind the configuration. With none the dialog says the change reaches no run once it is approved. With one or four, it names them.
- =?pending=1=: a proposal is already open, and the dialog says that a second proposal sits on the same version and one of them must be rebased.
- =?conflict=1=: the first submit is refused as a stale version, with Reload, as the standard says for a 409.
- =?config=c1|c2&open=<product type>= opens the dialog on a product.
- Changing the model marks the engine for review. A pair not known to work is marked, never refused.
- A setting the new pair does not take is shown as *will be dropped* with a *Drop* tick, and a setting the pair usually needs is shown as *usually needed* with an *Add* tick. Nothing is dropped or added until the person ticks it.

** What to do with the change

*Propose a new version* writes a proposal. Version N stays in force. Version N+1 waits for the roles model risk names, and the person who proposes cannot sign it off. *Try it in a draft copy* copies the whole configuration with the change, asks for a name, and saves it as a draft. No report is rebound, and no official report can bind a draft. The earlier design rebound one report to the copy. That made a second unofficial configuration in the pricing of an official report, which model risk exists to stop, so the prototype no longer offers it. No operation makes a copy, and the prototype states that.

** What is fake

Every value. The reports are names, because no read lists the reports that bind a configuration. The usual pair and the settings are the same fixture as the authoring prototype. A submit writes a proposal to the page's memory, marks the product with *change proposed*, and the History tab then shows the proposal at the top, not as a version in force. A change to a draft writes a new version. The page cannot say which version of a configuration a run used, because no operation returns it, and it says so in the reach.

** Where the code lives

=doc/prototypes/reporting/change-how-a-product-is-priced/index.html=. One file, plain HTML, CSS and JavaScript, with the style and the script inline, no modules, no fetch and no build step.

** What it argues

- The History tab draws the shared timeline as the [[id:BD492939-118E-4B55-AE5B-300F7A1C3B41][Entity screen specification]] draws it: an event chart split by kind, a rail grouped by day with the time in the left gutter, one header line for each entry, the note on its own line, a collapsed detail, the current-version emblem and the *Hide system activity* toggle. The prototype does not draw batches of entries that are one act, and the toggle is always on, because the fixture has no reader without the account permission.
- The reach, the difference and the choice of what to do with the change belong inside one dialog, because the change is one write.
- An approved version never changes in place. The default is a proposal, and the page says what stays in force.
- A copy is a draft that no official report can bind.
- Nothing is dropped or added by the pair change until the person ticks it.

** The verdict

None yet. This page is on the branch that proposes it and waits for review.

** What it does not settle

- Whether a copy should be a server operation. The page writes one request and states that none exists.
- Whether the history of a configuration should show a change to one product as the change of a row. The document write moves the version of the whole document.
