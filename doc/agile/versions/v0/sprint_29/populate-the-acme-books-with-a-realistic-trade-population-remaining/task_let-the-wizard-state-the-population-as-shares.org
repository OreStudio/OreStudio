* Acceptance

- The run normalises the shares it is given, so a mix that does not sum to a hundred is a mix it scales rather than one it refuses.
- The wizard renders the population parameters as one section rather than eight loose fields, and it says what the shares come to.
- A class that cannot hold its codes is refused with the smallest total that would, and the wizard shows that before the run starts.

* Plan

Three layers, landed one at a time so each is verifiable.

1. The arithmetic: the shares are shares. A run scales the mix it is given to
   the total it states, by the largest-remainder rule, so a mix of ninety-seven
   is the same book as a mix of a hundred and the operator is not asked to do
   arithmetic the server can do. This layer changes the refusal the previous
   task shipped and is the one this branch lands.
2. The form: the population parameters are one section rather than eight loose
   fields, and the section states what the shares come to as they are typed.
   The grouping is derived by the wire protocol from the parameter's name, so
   one place decides it and the screen does not sniff strings itself. Moving the
   group into the profile's parameter rows is the follow-up: it is a column on a
   generated entity, and regenerating that entity sweeps the convention-family
   drift this repository already carries.
3. The preview: a read that runs the same arithmetic and returns the trades per
   class, the floor each class must clear and the per-book counts, so a refusal
   arrives while the operator is typing rather than when the run starts. It
   belongs beside the run, in the provisioning handler, because that is where
   the config rows and their books already are.

Presets belong with layer 2: named pairs of a total and a mix that are known to
hold, starting with the weights page's own thousand, because the floors mean a
free total and an untouched mix is the one combination that fails.

* Result

The first layer is done and the other two are not.

The run now normalises the shares it is given: a mix that does not sum to a
hundred is scaled to the total the operator states, by the largest-remainder
rule, so the classes together state exactly the total. A mix of ninety-nine is
not the mix of a hundred — the class whose share dropped takes 24 of 99 rather
than 25 of 100 — so what the run promises is proportion, within the one-trade
rounding each config is counted in, and the test states exactly that.

Two mistakes remain refusals, because they are not arithmetic: a mix that names
no share at all, and a mix that names a class the run records no config for. A
class whose share cannot hold its codes is refused with the smallest total that
would, and that refusal now scales with the shares the operator stated rather
than with a percentage.

Measured: the knob suite is 8 cases and 51 assertions, and iam.core is green at
1190 assertions in 316 cases.

Still to come, and recorded in the plan: the form's population section with its
presets, and the preview read that runs this arithmetic before the run starts.
