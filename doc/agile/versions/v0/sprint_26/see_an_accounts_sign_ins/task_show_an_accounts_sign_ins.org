* Acceptance

- iam.v1.sessions.list filters by account and states a start-time order, generated from the model.
- A person's page shows the account's type, sign-in state and sessions.
- A tenant's People tab opens an account the same way, the system tenant's included.

* Plan

- Mark the session's =account_id= filterable and its =start_time= sortable in
  the model; the list contract generates the filter and the stated order, so
  no hand-written read is added. No SQL changes.
- One read composes an account's sign-ins: the account, its login record and
  a page of its sessions, newest first. The BFF serves it for the session's own
  tenant and inside any tenant, the system tenant read as the session.
- One panel draws it, on a person's page and on a new tenant account page
  opened from the tenant's People tab, which gains a kind column.

* Result

An administrator opens an account and reads its sign-ins.

- *Server.* =iam.v1.sessions.list= takes an account filter and a stated order;
  a repository test proves it reads one account's sessions, newest first.
- *BFF.* =GET /api/accounts/:username/sign-ins= and
  =GET /api/tenants/:code/accounts/:username/sign-ins= answer the account, its
  sign-in state and a page of its sessions.
- *Web.* The panel shows the kind of account (person or service), the last
  sign-in, failed attempts, lock and password state, and the sessions with
  start, end, client, address, country and traffic. A tenant administrator sees
  it on a person's page; the system administrator opens any account from a
  tenant's *People* tab, where a *Kind* column marks service accounts, and the
  system tenant's platform services are read there.

Tests: iam core 209 (one new) on a recreated database; BFF 153 (two new), web
249 (two new), protocol 70. A session's end is still not recorded, which the
panel states.
