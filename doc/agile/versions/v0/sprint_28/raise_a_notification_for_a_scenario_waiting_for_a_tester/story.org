* Decisions

- Closed at sprint 28 close with its 1 done tasks. The 1 open tasks and the original acceptance moved to [[id:C76D7295-D2DB-4329-A1AC-9D5F7EE31E51][Raise a notification for a scenario waiting for a tester — the remaining work]] in the product backlog inbox.
These come from what the code does today. They hold unless an answer under Open questions changes them.

- The inbox raises a notification for a kind and a permission audience. A raise resolves the audience, at that moment, to the people of the tenant who hold the permission, so a tester role is a permission and nothing more. A kind of notification is data: a seed row, with a code prefixed by the component that raises it. The story adds a kind and a permission, and no new mechanism.
- The BFF holds no permission rules of its own. The server checks the permission a call names. So the Development routes need a permission in the permission catalogue and a role that holds it, and the BFF asks for it.
- A scenario waiting for a tester is a fact about files, and nothing in the files can raise an event. Something must notice it and raise it. The first cut notices it inside the BFF, which already reads the scenario docs, and raises through the inbox service.

* Open questions

- *Who raises it, and when?* The BFF can scan the scenario docs when someone lists them, or on a timer. A scan on a list raises nothing until somebody opens the tab, which defeats a notification. A timer needs a tenant to raise for and a session or service identity to raise as. Which does the story take?
- *Does the module run in production?* A deployed BFF has no work tree, so it has no scenario docs to scan or to write results into. If the answer is no, the notification is a development-environment feature and the permission can say so. If the answer is yes, scenarios and results need a store other than files, which is a story of its own.
- *What does once for each scenario mean?* The notification needs a key so that a rescan does not raise it again. A scenario that is reopened after a retest could raise again or not.
- *Is an assignment in this story?* The capture asks for one. An assignment names a tester for a scenario and the notification goes to that one person. Without it the notification goes to every holder of the permission.
