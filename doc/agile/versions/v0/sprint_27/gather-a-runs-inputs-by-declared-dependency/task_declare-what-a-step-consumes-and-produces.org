* Goal

A step carries an ordinal and nothing else: the engine dispatches step /n+1/
when step /n/ succeeds, and no part of the system states what a step reads or
what it leaves behind. A consumer therefore discovers a missing input when it
runs and fails, which is why a run still gathering and a run that is broken
look the same from outside.

Give a step a declared set of input artifacts and output artifacts, and make
the engine consult that declaration before it dispatches.

* Acceptance

- A step definition names the artifacts it consumes and the artifacts it
  produces.
- The engine refuses to dispatch a step whose declared inputs do not all
  exist, and names the ones that are missing.
- An artifact's state is readable per run: missing, in progress, or present.
- A step that declares no inputs is dispatchable, so the declaration is not a
  tax on work that has none.

* Plan

The declaration belongs beside the step definition the registry already holds,
because that is where a step's identity and command subject live. The graph
task persists it per run; this task is the vocabulary.

An artifact is named by a key the storage plan already builds —
=reporting/runs/{instance}/...=. Reusing that namespace means the declaration
and the object cannot drift, and no second registry of names appears.

An artifact's state is *derived*, never stored twice: present means the object
exists and its producing step reached success, in progress means its producer
is running, and missing means neither. A stored state column beside the
objects would be a second truth that a crash could disagree with; the
principle that makes the run recoverable is that the objects are the record.
