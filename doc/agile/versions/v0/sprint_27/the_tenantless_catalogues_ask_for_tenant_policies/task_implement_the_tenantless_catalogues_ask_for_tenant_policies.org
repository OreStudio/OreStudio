* Acceptance

- No generated create script reads a column its table does not have.
- The generator refuses a policy flag the entity cannot support.

* Plan

Found by recreating the database, which had not been possible since these
models changed. The template emits the tenant policy from
=sql.rls_tenant_isolation= and the party policy from =sql.rls_party_isolation=,
and each policy reads one column of its own name. Nothing tied either flag to
the column existing:

- =a2dcf034fa= and =2b7301ceca= gave =booking_nature_type=,
  =counterparty_scope_type= and =entry_channel_type= =:has_tenant_id: false= --
  their prose says the set is the same for every tenant -- but left
  =:rls_tenant_isolation: true=. The generated create scripts then read a
  =tenant_id= column the tables do not have.
- =e37b84a81b= gave =structure_member= =:rls_party_isolation: true= on the
  premise that it "had party_id with no restrictive policy". Both halves are
  wrong: =178610c4e8= had already removed the column, and the hand-written
  =trading_rls_policies_create.sql= already gives the table a restrictive party
  policy through =ores_trading_structure_party_fn=. The generated policy reads
  =party_id=, so the schema cannot load.

Drop the four flags and regenerate. Then add the two rules to
=validate_rls_isolation=, beside the three it already carries, so the same
mistake fails when the model is read rather than when the schema is loaded.

The party rule applies to a domain entity only. A junction's =party_id= comes
from one of its sides and is not in =columns= at all, so a rule stated over the
declared columns would fail the ninety junction and entity models that are
correct today.

* Notes

The scan that found these parses each generated create script's table columns
and then looks for =tenant_id=, =party_id= or =counterparty_id= in the rest of
the file. It is deliberately narrow: =trade_bookings= and =iam_sessions= are
reported by it and are sound, because the first's references are qualified on
the trades, books and netting sets it joins and the second's is a comment. A
rule that read the policies instead of the file text would not have those false
positives, and would also catch a policy that reads any other missing column.
