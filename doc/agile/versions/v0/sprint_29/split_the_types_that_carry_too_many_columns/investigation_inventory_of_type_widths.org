A point-in-time record, written while the story that commissioned it was open, of an [[id:A7F8D9E2-3C4B-4A5D-B67C-8E9F0A1B2C3D][investigation]] into Every generated persisted type's member and column count, the blocks that repeat across the wide ones, and a verdict for each type over twenty members..

It is a snapshot, not a description of the system. Whatever it concludes that the code must keep doing belongs on the page that owns the subject; cite that page from code, recipes and models, not this one.

* Context

The MSVC job of the Windows nightly stopped on C1202 on 2026-10-29, in
=std::tuple_cat= over one =column_binding= per persisted column of a generated
entity with 47 bindings. Nothing in that failure involves reflection, and it is
not the configuration document an earlier task was watching. The compiler is
reporting the shape of the model.

This page asks the question the failure raises: which persisted types hold more
than one component, and what should each become? It answers with numbers a
reader can reproduce and a verdict per type.

* Methodology

The models are the authority, not the generated headers. One script,
=build/scripts/inventory_entity_columns.py=, reads every
=projects/*/modeling/*.org= of type =ores.codegen.entity= and counts, per type,
the columns it declares, the nullable ones, the ones folded into a =:group:=,
the members its domain struct therefore carries, and the rows of its =* Parts=
table. Its output is committed beside this page as =evidence/entity_columns.tsv=.

#+begin_src sh :results verbatim
python3 build/scripts/inventory_entity_columns.py \
  > doc/agile/versions/v0/sprint_29/split_the_types_that_carry_too_many_columns/evidence/entity_columns.tsv
#+end_src

The generated query builder binds the scaffold's own columns on top of the
model's, so a binding count is the column count plus eight, measured on
=cap_floor_volatility_config= (39 columns, 47 bindings: =tenant_id=, =version=,
=modified_by=, =change_reason_code=, =change_commentary=, =performed_by=,
=valid_from=, =valid_to=). That is the number MSVC reported.

The criteria are the ones the model states: a type holds one component when its
fields share one invariant that holds at one instant and one key identifies
them; a block that is present only when a flag is set, or only for one value of
a discriminator, or only for one direction of a pair, is a different component.
The reasons in the table name the flag or the discriminator that was read.

The threshold is twenty members. It is where the tail starts, not a limit the
model states: the median type carries 6 members, and 24 of 457 carry 20 or more.

A verdict outside refdata is a reading of that model from outside its component.
The numbers hold, and their owners confirm the verdict before anyone acts on it.


* Paths taken

- Counting from the generated headers. The first run counted every =bind(= in a
  generated entity and reported 60 for =commodity_future_convention=. That
  number was right, but it cannot be attributed: it mixes the model's columns
  with the scaffold's and says nothing about which block a column belongs to.
  The model is the authority, so the script reads the model and the scaffold's
  eight columns are stated as a constant.
- Counting every =**= heading under any section. The second run counted the
  =* Artefact columns= block as columns of the same type, and read
  =ir_curve_generation_config= as 44 columns when it has 21. A section heading
  is not a column, and a section with a space in its name defeated the first
  pattern. Recorded here because the inflated numbers looked plausible.
- Splitting the configuration document's protocol. Set aside: the failure is in
  a repository's column list, not in a message. See
  [[id:2750EACD-6C84-485D-B32A-E41D2785F0DF][the task that looked there]].
- Composing the document from field groups. Set aside: =rfl::Flatten= hoists the
  group's names into the parent's literal, so it lowers nothing, and the document
  is not the failing type anyway.

* Conclusions

457 persisted types. Their member counts, by bucket:

| Members | Types |
|---------+-------|
| 1-5     | 196   |
| 6-9     | 141   |
| 10-14   | 69    |
| 15-19   | 27    |
| 20-24   | 11    |
| 25-29   | 7     |
| 30+     | 6     |

The median is 6 and the widest is 57, so this is a tail of 24 types rather than
a model that is wrong everywhere. Of the 24, 17 should split,
6 should group, and 1 should keep.

Three shapes repeat, and each one names its own split:

- *A flag and its block.* =has_proxy_config= with seven proxy columns,
  =has_basis_configuration= with ten basis columns, =has_quotes= with three.
  The block's fields are meaningless unless the flag is set, so the flag and the
  block are one invariant, and a row that does not have them carries nulls it
  can never use.
- *A discriminator and its columns.* =segment_type= with twenty element columns,
  =kind= with one column per surface, =default_curve_type= with one column per
  construction. The row is a union of kinds written as nullable columns.
- *A pair of directions.* =flat_*= and =spread_*= in the cross-currency basis
  convention, the fixed and floating legs of the fix-float convention. Each arm
  has its own terms and its own invariant.

The conventions family already solved the second shape: a central row, one part
per kind, and only the central row carries the kind. That is the pattern the
split task should follow, and it is what
[[id:B607E5B7-190F-4D38-B515-8A7B27FB6B47][The atomised entity: a central row
and its parts]] states.

** Corrected after reading the ORE schema

Two verdicts in the table above are wrong, and the schema is why. The ratio of
nullable columns that ranked them measures the schema's optional children, not a
union:

- =fx_volatility_config= -- =fxVolatility= in =curveconfig.xsd= is one =xs:all=
  with a mandatory =Dimension= and optional smile fields. There is no element per
  dimension, so dimension is a value of one component, not a discriminator
  between components. Verdict: =keep=, at most =group=.
- =inflation_cap_floor_volatility_config= -- =inflationCapFloorVolatility= is
  likewise one =xs:all= with a mandatory =Type= and optional strike lists.
  Verdict: =keep=, at most =group=.

=curve_volatility_config= keeps its =split= verdict, and the split is larger than
the table suggested: =VolatilityConfig= is an =xs:all= of up to seven kinds, each
its own type with its own priority. See
[[id:8C947D0F-E4AB-41C0-BA1A-C5AFE23A48E9][the task]] for the shape.

The rule to record on [[id:BBD43BF2-9FEE-42B0-A667-9468AF759DC2][Data-Oriented
Design in ORE Studio]]: a new model is checked for a =has_*= flag followed by its
block, a discriminator followed by one column per value, and a pair of
per-direction columns. Any of the three is a split, and the check belongs in
codegen so a model that has one fails review with a reason rather than a review
comment.

Ownership: 17 types span refdata, trading, marketdata, dq and
synthetic. The refdata ones are one environment's; the trading, marketdata and
dq ones belong to whoever holds those components, so the split task takes the
refdata list first and hands the rest over rather than editing another
environment's component.
