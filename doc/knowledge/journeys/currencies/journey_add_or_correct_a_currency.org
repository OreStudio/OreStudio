This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A reference data administrator adds a currency or corrects one, with its countries, calendars and desk groups on one screen.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want this currency to be right everywhere it is used: its codes and symbol,
how its amounts round, the countries that issue it, the calendars that settle
it, and the desk groups it sits in." The journey is done when the currency
reads correctly on one screen and its history shows why it changed.

* Actor and trigger

The actor is the person who keeps the tenant's reference data: an account with
the =TenantAdmin= role, which holds every permission, or one with the
=Operations= role, which holds the currency permissions. Both act inside their
own tenant. The trigger is a new currency the desk must book, a redenomination,
or a wrong value found in a run or a report. The journey starts at the currency
list, or at a link from any screen that shows a currency code, and ends when the
person leaves the currency.

* Steps

1. *Find the currency.* The person opens *Currencies*. The system lists the
   tenant's currencies: code, name, symbol, market tier and monetary nature.
   The person filters by code or name, or chooses *Add currency*.
2. *Read the currency.* The person selects a row. The system shows one screen
   with four panels: the currency itself, its countries, its calendars, and its
   desk groups. Each panel reads with its own operation, so a slow panel does
   not hold the others.
3. *Correct the currency.* The person edits the currency panel: the ISO codes,
   name, symbol, fraction symbol and fractions per unit; the rounding type and
   precision; the format; the monetary nature and market tier; the ORE currency
   type, spot days, day basis and base precedence. Rounding type, monetary
   nature and market tier are pickers over their lists, not free text and not a
   button that opens another screen. The person states a change reason, and the
   system writes the currency with =must_match_version=, so a concurrent edit is
   refused instead of lost.
4. *Set the countries.* The person adds or removes the countries that issue the
   currency. The system writes or deletes one =currency_country= row each time.
   The rows keep no history, so the panel is a plain list.
5. *Set the calendars.* The person adds or removes the holiday calendars used
   for the currency's spot and settlement dates. The system writes or deletes
   one =currency_calendar= row each time. A calendar name links to
   [[id:4C3A8F3E-655F-4DB8-9F94-A25EBA9C4E8A][Keep a holiday calendar right]].
6. *Set the desk groups.* The person adds the currency to a desk group, such as
   G11 or Scandies, or removes it. The system writes or deletes one
   =currency_currency_group= row.
7. *Check the history.* The person opens the *History* panel. The system reads
   every version of the currency with the generic history request, and shows
   who changed it, when, and the field-level difference from the version
   before. The person can open one version read-only.
8. *Revert a change.* The person chooses *Revert to this version* on an older
   version. The system writes the old values as a new version, with the change
   reason the person states. History is never rewritten.
9. *Exchange with ORE.* The person exports the tenant's currencies as an ORE
   =currencyconfig.xml=, or imports one. See /What is missing/.
10. *Leave.* The person goes back to the list. Every screen that reads the
    currency now reads the corrected values.

No step waits on the server after its reply. The journey keeps no state of its
own: a refused write leaves the panel as it was, and the person can try again.

* Screens and wireframes

One screen. The currency panel sits above the three lists it owns, because the
countries, calendars and groups mean nothing without the currency they belong
to. The history is a panel on the same screen, not a separate dialog.

The generic history request is the one =ores.history= defines: the subject is
derived from the entity type, and the reply carries every version's full field
render and the field-level diff from the version before. The per-entity
=refdata.v1.currencies_versions.list= and =.get= also exist and return the raw
rows; the screen needs the diff, so it uses the generic request. The currency
list filter also accepts =as_of=, which a later screen can use to show the list
as it stood on a date.

* What is missing

1. *No server export of currencies as ORE XML.* The Qt client wrote
   =currencyconfig.xml= itself, with =ore::xml::exporter::export_currency_config=
   linked into the desktop binary. A browser cannot do that. The candidate is a
   =refdata.v1.currencies.export= operation that returns the document, in the
   shape of =refdata.v1.calendar_adjustments.export=. Until it exists, the screen
   offers no export.
2. *Import is a whole ORE bundle, not one file.* =ore.v1.ore.import.execute=
   imports an ORE directory, and its planner reads the currency configuration as
   one part of it. The candidate is to let the import take a currency
   configuration on its own. Until then, the screen links to the ORE import
   instead of offering its own.
3. *The =Operations= role cannot fill its own pickers.* It holds read, write and
   delete on currencies and the three junctions, but no read on countries,
   calendars, currency groups, rounding types, monetary natures or market tiers.
   An =Operations= member can change a currency but cannot see the values it
   must pick from. The candidate is to grant those reads to =Operations=, or to
   introduce a reference data role. Until then, only a tenant administrator can
   run this journey end to end.
4. *Reverting is a client convention, not an operation.* There is no revert
   subject; the screen writes the old values with =put=. This is enough, and it
   keeps history append-only. The seeded change reasons have no code for a
   revert. The candidate is =common.revert=. Until it exists, the screen uses
   =common.rectification= and puts the reverted version in the commentary.
