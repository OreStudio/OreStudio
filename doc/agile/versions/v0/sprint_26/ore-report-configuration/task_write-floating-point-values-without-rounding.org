* Plan

Found by the curve configuration database round trip: a yield curve tolerance
of =1e-12= was written to the database and read back as =0=.

The cause is upstream. sqlgen's =Parser<T>::write= in
=include/sqlgen/parsing/Parser_default.hpp= turns every value with no
reflection method and no enum type into text with =std::to_string=. For a
float or a double that is =printf("%f")=: six decimal places, so =1e-12= is
written as =0.000000= and =0.0123456789= as =0.012346=. The read side,
=std::stod=, is exact; only the write loses digits. The latest upstream commit
that touches the file, =816ca6adec=, still does this.

The fix is a patch on the overlay port, which pins sqlgen at =47e5711=: floats
are written with =std::to_chars=, the shortest text that reads back as the same
value. The port version is bumped so a cached build of the old port is not
reused.

Proof: a repository test writes three doubles through a generated repository
and reads them back. Run against the unpatched port it fails all three cases;
with the patch it passes them.

* Result

- The sqlgen overlay port carries =fix-floating-point-precision.patch=, which
  writes floats with =std::to_chars= instead of =std::to_string=. The port
  version is bumped to 1 so a cached build is not reused.
- =repository_floating_point_precision_tests.cpp= writes =1e-12=,
  =0.0123456789= and =123456789.123456789= through a generated repository. It
  failed all three against the unpatched port and passes all three with the
  patch.
- Build clean after a reconfigure; ctest 89/89 with services up.
- The same defect exists in upstream sqlgen at =816ca6adec=; the patch is
  written against the upstream file so it can be offered there.
