* Acceptance

- Every refdata resource named by a generated handler has its read, write and delete permission seeded.
- The pre-existing gap closes for calendars, calendar_events, tenor_conventions and the nine junction resources.
- The roles that held the parent entity's write permission keep the equivalent access.
- A database recreated from the seed script grants the permissions, and the refdata suites pass against it.

* Plan

The generated handlers check =refdata::<resource>:write= and =:delete=,
and the seed script covered only some of the resources. A comparison of
the 137 permission strings the refdata handlers name against the 79
seeded gave 138 missing rows across roughly 50 resources, most of them
pre-existing: =calendars=, =calendar_events= and =tenor_conventions=
among them, plus the nine junction resources the coverage work added.

Add the missing read/write/delete rows in the same style as the existing
ones, and give the Operations role the four currency-derived junction
resources, so the calendar assignment it previously reached through
=refdata::currencies:write= works again. The party-derived junctions
stay with the roles that manage parties.

* Notes

The gap was measured, not guessed: the required set is every
=has_permission= string in the generated refdata handlers, and the
seeded set is every =refdata::= literal in the populate script. The
comparison is reproducible in one command and is the check a future
resource should be added through.

The recreate surfaced an environment flake: the first run failed in
=setup_schema.sql='s grant block with =tuple concurrently updated=, a
Postgres catalog conflict, after the populate step had already
succeeded. The second run completed clean.

* Result

Every refdata resource a generated handler names now has its read, write
and delete permission seeded: 138 rows were missing and are added, taking
the refdata permission set from 79 to 217. The pre-existing gap closes
for calendars, calendar_events, tenor_conventions, book_purpose_types,
the CRM resources, the convention resources and the rest, and the nine
junction resources are covered with them.

The Operations role gains the four currency-derived junctions
(currency_calendars, currency_countries, currency_currency_groups and
currency_pair_convention_calendars), so the calendar assignment it used
to reach through =refdata::currencies:write= works again. The
party-derived junctions stay with the roles that manage parties.

Verified against a database recreated from scratch: the seed applies,
the permission set is 217 and the Operations role holds 17 grants, and
the four refdata suites pass against it.
