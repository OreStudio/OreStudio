* Acceptance

- A line number is unique inside a request. The derived model declares the request and line number as a natural key, so the unique index is generated.
- The policy names the columns of the entity. A line selects its parts from the columns it changes.
- The preview runs the real service write for each line inside one transaction it never commits, with a savepoint per line. It returns the refusals the service gives, publishes no event and sends no notification.
- The preview refuses a line whose base version is not the live version.
- The raise writes the request, its parts and its lines in one transaction, and refuses a request that no policy row gates.
- A test refuses a line for an unknown request.
- A test shows a preview that leaves the live table and the pending table unchanged.

* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

- The apply (workflow, apply_failed, retry) moves to the task "Apply an approved request". This task stops at a request that holds typed lines and its parts.
- A line holds no part. A put can change columns that two parts decide, so the request's parts are the union the policy gives for all its lines. The =part_code= column leaves the derived model.
- The policy field names become the columns of the entity (book_status, rates_centre_code, is_sweepable, owner_unit_id, parent_portfolio_id). The two rows for columns the book does not have are removed.
- A database function returns the parts for an entity type, an operation and a list of changed columns.
- The preview and the raise are a service in refdata, because only refdata knows the book columns and the book service. A kind =refdata.book_change= is seeded for the requests.
- The preview needs no new transaction support. =unit_of_work= holds one transaction and drops it on destruction. A savepoint per line is =execute_raw_command=. A rolled-back transaction discards the notifications the write queued.
- A "no line on a decided request" guard is not added in the database. The raise creates the request and its lines together, and it is the only writer.

* Notes

- The preview needs no new transaction support. =unit_of_work= holds one transaction and rolls it back when it is destroyed. The raw command helper opens its own connection, so the savepoints run on the transaction's own connection instead.
- A write that fails inside a transaction aborts it until the savepoint rolls back. The test with a refused line followed by a good line shows the next line is still checked.
- The service lives in =ores.refdata.service=, not =ores.refdata.core=. =ores.inbox.core= links =ores.iam.core=, which links =ores.refdata.core=, so core cannot link the inbox.
- The telling of the deciders moved out of the approval handler into =approval_announcer=, so any component that raises a request tells its deciders the same way.
- The policy now names the book's columns. Five rows changed name and the two rows for columns the book lacks (allowed currencies and products) are gone, so the policy has 30 rows. The earlier count of 32 was right for the earlier names.
- The column list that compares a line with the live book is written by hand. A column the policy does not name cannot gate a change, so a missed column only matters when the policy names it.
- The raise and the preview are not yet reachable from outside the process. The next task, "Expose the book raise and preview", adds the typed operations.

* Result

A maker can propose changes to books as typed lines. The preview and the raise are a service, =book_proposal_service=. They are not yet offered over NATS.

- The preview runs the real book service for each line in a transaction it never commits, with a savepoint per line. It returns each line's refusal and the parts the policy names. The live table and the pending table are unchanged afterwards.
- The raise previews, refuses when any line is refused or no policy row gates the changes, then writes the request, its parts and its lines in one transaction. It tells the deciders of the open parts after the commit.
- The pending line has no part. The request holds the parts, as the union the policy gives for the columns all its lines change.
- A line number is unique inside a request. The derived model declares the request and line number as a natural key, and the generator emits the unique index.
- The policy names the book's columns. The kind =refdata.book_change= and the function =ores_inbox_policy_parts_fn= are new.

Evidence: ten new =[book_proposal]= cases pass (30 assertions) on a recreated database. They cover a valid new book and its three parts, a preview that writes nothing, a refused line followed by a good line, a stale version, a one-column change naming one part, a raise that writes the request, parts and line, a refused line that raises nothing, a change no policy row gates, a duplicate line number, and a line for an unknown request. The generated =book_change= test and the 20 =[approval]= cases still pass. The cmake source, populate reference, handler permission, test case reachability, pasted block symbol and derived-model checks pass.

The ER diagram check on main failed for the parts and policies tables of the earlier task, which had no row-level security. This task adds a tenant policy to both. A tenant reads its own rows and the system tenant's, and writes only its own. The pending book lines also gain the party and sandbox policies the book has. The ER diagrams are regenerated, and the strict parse and the diagram check pass.

Not done here: the NATS operations, the apply and the screens. They are the next tasks.
