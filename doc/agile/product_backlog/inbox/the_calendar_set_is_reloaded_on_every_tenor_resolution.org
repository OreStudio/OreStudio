#+title: The calendar set is reloaded and rebuilt on every tenor resolution
#+description: load_calendar reads every materialised day of a calendar (about 9,900 rows, 2024 to 2050) and rebuilds the CSR holiday set on each resolve request; the arithmetic is already data-oriented and allocation-free, so the query is the bottleneck.
#+type: capture

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

The calendars should be loaded into the process once and asked in memory, and today
they are not: every tenor resolution re-reads the calendar from the database and
rebuilds the in-memory set.

There is no network hop in the arithmetic. NATS carries the =resolve_tenor=
request, and the answer is computed in =ores.refdata.core= by
=tenor_resolution_engine= against a =business_day_calendar_set= that is built
inside the call. The cost is that =load_calendar= reads the whole materialised
calendar each time: =calendar_date_repository::read_latest_by_calendar= selects
every live row of the calendar ordered by date, and the default materialisation
window is =year_start(today - 2y)= to =year_end(2050)=, which is one row per
calendar day -- about =9,900= rows, of which about =3,100= are closed. Then
=build_calendar_set= sorts and uniques them and packs them. The FX forward ladder
does the same in =fx_forward_ladder_plan.cpp=. So the cost of a resolution is a
table scan and a rebuild, not a calculation.

* Why

The size says it should be a cache, not a query. Packed, the whole thing is tiny:

| Item | Size |
|------+------|
| Closed days per calendar, as the set holds them (=year_month_day= each) | about 3,100 dates, about 12 KB |
| The CSR index and weekend masks per calendar | tens of bytes |
| Thirty calendars, all packed | about 370 KB |

A few hundred kilobytes is not a cache with an eviction policy, it is data that
belongs in one immutable object for the life of the process. The type is already
shaped for it -- =business_day_calendar_set= holds many calendars at once, with
=calendar_count=, per-calendar CSR offsets and a =calendar_index= on every query,
and =from_rows= takes every calendar's rows in one flat span. What is missing is a
loader that builds it once and a reader that keeps it.

Two ways to build it, and the second is the better one:

- *From the materialised table.* Read every live =calendar_dates= row for the
  tenant, ordered by (calendar_code, date), about 300,000 rows for thirty
  calendars, and pack them. One read at start-up, none after.
- *From the rules.* The materialised table is itself a cache of
  =calendar_rule_engine::instantiate_holidays_batch= over =calendar_rule= and
  =calendar_exception= rows, which are a few dozen rows per calendar. Running that
  engine at start-up, once per calendar over the same window, gives the same set
  from hundreds of rows instead of hundreds of thousands, and needs no dependency
  on the table being fresh. The catch is that the materialiser also resolves
  =base_calendar_code= chains, which the loader would have to take over.

The one real decision is invalidation: a calendar edited while the service runs. A
version stamp read cheaply -- the maximum =modified_at= over the rule and exception
rows, or a generation column -- lets the loader rebuild on change without a restart;
an event subscription is the alternative, and it is the pattern the eventing
component already provides.

The arithmetic itself is already right and needs no work. =business_day_calendar_set=
holds holidays in one flat sorted array with per-calendar offsets, weekend masks as
=bitset<7>=, and answers by binary search inside one calendar's slice, =noexcept=
and allocating nothing. =calendar_arithmetic::add_period= is pure date arithmetic
and consults no calendar at all. =calendar_arithmetic::adjust= and =advance= walk
one day at a time over that set, which is a handful of lookups per date and is what
an in-memory set makes cheap.

The surface arc adds nothing to this load: an FX surface's value date is a tenor
added to a spot date by =calendar_arithmetic::add_period=. But if a later stage
decides that value date should be a business day, it must be adjusted against this
in-memory set and never by asking a service.

Two smaller findings belong with the same work:

- *A silent unknown-calendar answer.* =business_day_calendar_set::is_business_day=
  returns =true= for a =calendar_index= the set was not built with, because both
  guards fail and the function falls through. =calendar_arithmetic::adjust= and
  =advance= throw =std::out_of_range= for the same index, so the two layers
  disagree, and the tolerant one answers "every day is a business day" -- the same
  failure =calendar_not_materialised= exists to prevent at the service boundary.
  It is also =noexcept=, so it cannot report the mistake.
- *=from_rows= trusts its caller.* It requires rows sorted by (calendar, date) and
  duplicate-free, and verifies neither; a mis-sorted input makes every binary
  search wrong without an error. One pass over the rows at build time would catch
  it, and a loader that reads from the database should not be the thing that
  discovers the order.
