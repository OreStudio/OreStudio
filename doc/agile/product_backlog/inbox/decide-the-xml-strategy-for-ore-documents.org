#+description: Decide the XML strategy for ORE documents, and consider replacing the generated binding rather than extending it.

The bond review found that a money value cannot be recovered exactly from the ORE binding wherever the schema declares a bare numeric element. The cause is structural, not a bug: the bindings are generated by xsdcpp, a sibling checkout at /home/marco/Vault/Development/xsdcpp that is not vendored, not in vcpkg.json, not in CMake and not on PATH, and whose pin this repository records only in a knowledge page. xsdcpp maps xs:float to a bare float (Generator.cpp:405-406), so an element like StrikeData/Value loses the document's digits at parse. An element like Notional keeps them only because it carries a startDate attribute, which forces xsdcpp to build a class, and that class happens to derive from xsd::base<float>.

Three routes were considered and none was taken:
- Keep the lexical form on every numeric leaf by changing xsdcpp. The machinery already exists: domain_xsd.hpp carries a hand-patch (reapplied by scripts/reapply_ore_lexical_form.py) giving xsd::base<T> a lexical string for floating-point T, with implicit conversions to T. The generator change is small, but the parser half in domain.cpp is not, and regeneration is currently blocked by unexplained drift: a run today adds other_elements to trade and changes componentSubTrade, which the committed bindings deliberately removed.
- Roll our own XML layer and retire xsdcpp, which is what the user leans towards.
- Leave it and record the limitation.

What an analysis should settle: how much of the 122,000 generated binding lines is actually used; whether the export path needs the same fidelity as the import path; what ORE's own schema guarantees, given it types the same money concept as xs:string in one product and xs:float in another (ContractNotional in bondFutureData against bondFutureOptionData); and what the drift on trade and componentSubTrade actually is, since it blocks any regeneration either way.
