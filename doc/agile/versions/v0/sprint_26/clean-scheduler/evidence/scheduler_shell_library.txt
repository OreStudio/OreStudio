The scheduler scripts in the shell's library
==========================================

Each command of the scheduler submenu has a recipe at
doc/recipes/shell/scheduler/scheduler.org, and the recipe tangles into one
runnable script under projects/ores.shell/scripts/library/scheduler/:

    scheduler-instances.ores
    scheduler-jobs.ores
    scheduler-remove.ores
    scheduler-schedule.ores
    scheduler-status.ores
    scheduler-watch.ores

Every script below was run through ores.shell --load against the live fleet
(NATS, the database, ores.iam.service for the session and
ores.scheduler.service for the loop), in this order:

What the run shows:

- schedule creates the definition the recipe documents, paused because the
  example says --inactive, and jobs lists it back with its cron, action and
  command.
- status reads it back as paused with no next firing, which is what a paused
  definition is.
- instances reads the executions the loop has recorded.
- remove deletes it by the name the script shows, and the next jobs run is
  empty again.
- watch subscribes and prints what arrives.

Two defects in the committed tree that this unit found, both outside the
scheduler component:

1. The library was incomplete. The tangle writes 1202 scripts and git held
   1085: 12 recipe groups' scripts had never been committed, so a person
   reading the library on a clean checkout would not find them. This unit
   commits its own six and records the rest; the inventory check gates
   doc/recipes/shell/shell.org and nothing gates the library itself.
2. doc/recipes/shell/shell.org carried six merge-conflict markers -- two
   =======, two ======= and two >>>>>>> lines left by an unresolved merge
   that was committed. This unit removed them and regenerated the file, so
   it is consistent with the recipes again.
