* Goal

The five [[id:5E970C7F-68EA-42BF-B73E-997C4A003762][Operations]] journeys run in
=ores.web= against the real server:

- [[id:ED949529-0A80-4661-BBAC-E5DB7A6E5828][See the running services]] —
  every service the installation expects, with its instance count, its state
  and its version; rows never disappear.
- [[id:7B820710-161C-4926-B5AA-5EF2772A3652][Watch the compute grid]] — the
  host and work summary, one row per node, and the compute wrappers that
  report for those nodes.
- [[id:EE26E58C-F389-4E82-BF96-EC5324F9F795][Watch the message bus]] — the
  server's vitals and one row per stream: messages, bytes and consumers over
  time.
- [[id:57C4B9A6-DA79-403E-984E-50D2561352B3][Read the telemetry logs]] —
  the lines behind a symptom, found by time, level, source, component, tag or
  session.
- [[id:C3D59907-9D6A-448C-9A61-9E750755BBFB][Check the versions and the
  database]] — the client build, the server build, and the database
  fingerprint.

This is the ninth group of
[[id:961BE2F3-3FE2-4140-BB18-EBDC89DF0913][Implement the user journeys in ores.web]].
It reuses the journey runtime the Setup group landed and adds no journey
entity.

This group starts where no other group does: its design is already settled.
The five journeys were written and walked against a clickable prototype in
sprint 26, and the user accepted the walk on 2026-10-04
([[id:BFE393CC-15F5-4A35-BFF6-A5CFB817F0A7][Prototype the operations
journeys]]; branch =prototype/operations-journeys= at =285519db99=, kept as
the design record and never merged). The walk also found five data-model
linkages between the accepted screens and the models, and they sit as captures
in the product backlog's inbox. This story closes them and builds the screens
from the accepted design.

* Acceptance

- The five journeys run in =ores.web= against the real server, on the journey
  runtime the Setup group landed, and no journey entity is added.
- The five data-model linkages are closed or explicitly deferred, and each
  capture leaves the inbox with its task's evidence.
- The whole grid is read, not the session tenant's slice, under the permission
  the journey records, and the shell's grid stats command follows the same
  read.
- The services roster keeps every expected instance with its state word —
  running, stopped or missing — and the heartbeat carries its host, so a
  wrapper's row can name its node and an instance's row its host.
- The login answer carries the database row, so the versions panel adds no
  request.
- Every gap the five journeys record is either closed with its evidence or
  stated on the screen, and every Related journeys entry is a link on the
  screen.
- The Operations area carries the five screens, the system-administration
  menu carries the Operations entry and no other menu does, and every screen
  carries the footer with both builds. The four installation screens carry
  "Back to operations" navigation and stand in the area alone; the versions
  screen is offered in every mode, so a tenant administrator and a regular
  user reach it and no other operations screen.

* Decisions

- *The accepted design is the build's input.* The five journeys were written
  and walked against a clickable prototype in sprint 26, and the user accepted
  the walk on 2026-10-04. The prototype branch is the design record; this
  build ports its screens onto the journey runtime rather than merging them,
  and each task re-checks its own claims against the tree as it works.
- *The data-model linkages are the story's first tasks.* The walk found five
  linkages between the accepted screens and the models, and each one sits in
  the inbox as a capture. They are the story's first tasks, so the build sizes
  from them instead of finding them mid-screen.
- *The grid belongs to the installation.* The grid reads drop the session
  tenant's filter, and the stored tenant id stays on the sample as
  attribution. The read grows the permission the journey records, so the whole
  grid and who may see it stay two separate decisions.
- *The heartbeat carries one new field, not a new entity.* A host id on the
  service heartbeat answers both questions the record found — which node runs
  a wrapper, and which host runs an instance — and the publishing process
  already holds the id.
- *The database rides the login answer.* The versions panel needs no read of
  its own: the login answer states the deployment's build already, and it
  gains the database row beside it. The row's audience is the server build's
  audience.
- *The roster keeps every expected row.* A services screen drawn from samples
  alone fails worst when the list is short: the operator cannot tell what is
  missing. The screen draws the installation's expected services and their
  replicas, and the read that serves them is the roster task.
- *The estate's state is a small subset of the old controller.* Heartbeats
  tell only whether an instance went quiet. The roster also needs what should
  run, which the registry gives through a generated expected-services table,
  and what each instance said about itself: every process announces =started=
  and a graceful =stopped= through the shared service lifecycle, and telemetry
  stores the events and raises a =service_restarted= notification to the super
  administrators. Supervision stays systemd's, as it would be Kubernetes';
  the decommissioned controller's =pid=, stderr and restart policy are not
  brought back. Settled with the operator on 2026-10-06
  ([[id:6585F9F0-881B-46FC-B247-37E5E6252FDF][Record service starts and stops]],
  [[id:2F054957-1C41-4E98-B89E-6DE3D16924F7][Notify super administrators of service restarts]]).
- *Both clients reach one operation.* Where the shell carries an operations
  journey today — the grid stats command and its recipe — it follows the same
  subject when the read changes. Where it carries none, this story records
  that rather than inventing a shell surface.
- *A journey a person cannot reach from a screen is not finished.* Each
  journey's Related journeys list is links on the screen; a screen that omits
  them has not implemented the journey.
- *The Operations area is offered in system administration alone.* The four
  installation journeys' actor is the super administrator acting from the
  system tenant, so the system-administration menu carries the Operations
  entry and no other menu does: a tenant administrator and a regular user
  reach none of the four screens. The versions screen is the exception. Its
  actor is any signed-in person, so the shell offers it in every mode, beside
  the footer. The accepted walk ran the prototype in that mode.
- *The screens follow the accepted contracts.* The
  [[id:166B2D77-6D04-47D5-A651-5431E1F2E082][UX language]], the
  [[id:6743F6E3-578C-4E4B-9DD6-D5A0DF6734C8][UI design principles]] and the
  [[id:CDE625E2-96AE-4644-9921-282339925F3E][TypeScript Clean Standard]] bind
  the work.
- *A cross-sprint group closes DONE and gets a successor.* The programme's
  rule applies here: if the group does not close in sprint 26, what lands is
  recorded and the rest continues in a successor story.
