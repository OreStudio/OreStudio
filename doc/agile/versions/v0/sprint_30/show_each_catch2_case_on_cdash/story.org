* Goal

CDash shows each Catch2 test case's status, time and failure text, so a
failed suite names the case that failed and a slow suite names the slow
case. The product owner cares about what CDash shows, not how ctest
registers the tests. So the suites still run as one ctest test and one
process each. Only the Test.xml that CTest.cmake submits changes.

* Acceptance

- After =ctest_test=, CTest.cmake turns each suite entry in Test.xml into
  one entry per case, named =<suite>.<case>=, with the case's status, time,
  failure text and the suite's labels.
- A suite entry stays as it is when its results cannot account for it: no
  results file, a file older than the run, a file cut short by a crash, or
  a failed suite whose cases all passed.
- The suites run as before: no extra process, and no extra test tenant.
- The memcheck run and local =ctest= are unchanged.
- CDash groups the cases by component: each test is labelled with its
  component, and every submission declares the components as subprojects.

* Decisions

- *Change the submitted Test.xml, not the registration.* The capture
  proposed =catch_discover_tests=, one process per case, as compass did.
  For ORE that costs too much. The tree has about 36,280 cases, and 75 of
  the 104 suites provision a test tenant in each process. One provisioning
  took 4.2 s, so one process per case would spend about 42 hours on tenants
  in each run. Process start alone costs about 80 ms per case. The product
  owner wants the cases on CDash, and the results are already in each
  suite's Catch2 XML. So none of the capture's traps applies: the tenant
  per run, the memcheck time, the results file, and case names that start
  with =-= or hold test-spec characters.
- *Never hide a failure.* A suite entry is replaced only when its results
  account for the suite's status.
- *Without Python, submit the suite entries.* CTest.cmake warns and
  submits as before.

* Out of scope

- Local =ctest= and =ctest -R= by case name. Each suite stays one test.
- The memcheck results, which CDash reads from a different part.

** What

Register every Catch2 test case as its own CTest test with
=catch_discover_tests=, so CDash shows each case's result and time. Today each
of the 105 suites makes one =add_test= call, so a CDash entry covers a whole
suite. compass did this in [[https://github.com/MASD-Project/compass/pull/86][compass PR #86]] with one helper in
=projects/CMakeLists.txt=:

#+begin_src cmake
include(Catch)
function(compass_add_catch2_tests suite target)
    if(COMPASS_TEST_FILTER)
        set(spec TEST_SPEC ${COMPASS_TEST_FILTER})
    endif()
    catch_discover_tests(${target}
        ${spec}
        TEST_PREFIX "${suite}."
        WORKING_DIRECTORY ${CMAKE_RUNTIME_OUTPUT_DIRECTORY}
        DISCOVERY_MODE PRE_TEST)
endfunction()
#+end_src

=ORES_CATCH2_ARGS= goes in through =EXTRA_ARGS=, and the memcheck filter
=~[long_running]= through =TEST_SPEC=. =PRE_TEST= discovers the cases when ctest
runs, so a build never runs a test binary.

** Why

The product owner asked for it. A failed suite on CDash names no test case,
and a slow suite does not show which case is slow. On compass the change took
CDash from 15 entries per build to 1228 test cases (Continuous Linux run
44363298398).

** Traps to check first

Measured on main at 43cdfbab7e on 2026-11-18. A story starts by deciding each.

- *The database tenant per run.* =database_lifecycle_listener= provisions a test
  tenant in =testRunStarting= and terminates it in =testRunEnded=. One process
  per case makes that about 35,000 provisions per run instead of about 105.
  Before it provisions, it closes the synthetic rows that an aborted earlier run
  left. Under =ctest -j=, two cases of one suite run at once, so one case can
  close the rows of a sibling that is still running. Run the database suites
  under =ctest -j= before the switch, or keep whole-suite registration for them.
- *Memcheck.* compass measured about 1.4 s of valgrind start-up per case. At
  that rate, ORE's about 35,157 test cases need about 13.7 hours. This is an
  estimate from compass's number, not a measurement. Keep whole-suite
  registration under =WITH_MEMCHECK=, as compass suggests if the run is too slow.
- *The results XML.* Each suite writes =test-results-<suite>.xml=, which
  =ATTACHED_FILES_ON_FAIL= attaches and =compass test= reads to report the
  failures. One process per case overwrites that file on every case. Decide
  where the results go, and update =compass test= and
  =compass-code-investigate-test-failure= to match.
- *Test case names that begin with =-=.* ctest passes a case's name to the
  binary, and Catch2 reads a leading =-= as an option. compass had three such
  names. One of them printed help and passed without running. ORE has none
  today (=grep -rnE '(TEST_CASE|SCENARIO)\(\s*"-'= over =projects=). A check
  should keep it that way.
- *Names with Catch2 test spec characters.* A name with a comma, a bracket or
  =*= changes meaning when ctest passes it back as a test spec. Check that each
  discovered case runs exactly one case.
- *Local cost.* compass's ctest went from 4.5 to 5.3 s to 6.2 s. ORE has about
  30 times as many cases, and each process starts logging and the database
  listener. Measure =compass test run= before and after.
