#+title: Where new data goes
#+description: A new kind of data lands at exactly one level, and the level names the tenant it lives in, the bundle that publishes it and the write path that may touch it.
#+type: knowledge
#+level: cross
#+filetags: :knowledge:architecture:dq:publishing:data:
#+created: 2026-11-14
#+updated: 2026-11-14

* Summary

Every row the platform holds has one owner: the installation, the world, or a
tenant. The owner is the row's *level*, and the level decides the three things
a developer asks about new data — the tenant the rows live in, the bundle that
publishes them, and the write path that may touch the table. Installation and
world rows live once, in the system tenant, and no tenant holds a copy; a
tenant reads them where they lie. A tenant row lives in that tenant, and a
party-scoped row names its party. This page answers "where does this new data
go", and it names the page that owns each part rather than restating it.

* Detail

** The question, and its four answers

Ask in order and stop at the first yes. The answer is the level, and the level
decides everything that follows.

1. *Does the platform define these values so that it can function?* The
   *installation* level. A coding scheme, a template image, a provider, an
   adapter or an ORE parameter has one correct set, and the platform is its
   author.
2. *Does the platform adopt them from an outside source?* The *world* level.
   ISO currencies and countries, the FpML vocabularies, the GLEIF records and
   the QuantLib calendars are adopted, and the source is recorded on the
   dataset.
3. *Does one tenant own them?* The *tenant* level. Its parties, conventions,
   books, portfolios and badges are that tenant's, and no other tenant reads
   them.
4. *Otherwise the rows are produced by use*, which is a trade, an activity or a
   measurement. Nothing is published, and the write path that produces them is
   the only delivery.

The first two questions are the tier questions of
[[id:78E47817-A984-4325-AA73-B8B87C56BC3B][The data tiers]], asked from the
publishing side rather than from substitutability. The third is the tenant
ownership of
[[id:5A5D6490-AF64-4AAF-8B3D-48EF3EDAF3D2][Tenant ownership and the information flow]].

** Where the answer puts the rows

The level and the scope name the bundle, and the bundle names the tenant it
writes into. One table carries the whole map.

| Bundle | Level | Scope | Writes into | Published | The values it carries |
|--------+-------+-------+-------------+-----------+-----------------------|
| =system_core= | Installation | Installation | The system tenant | At database bring-up | The coding schemes, the template images, the provider, adapter and supplier catalogues, the system tenant's feeds, the ORE parameter documentation, the FX vol surface blueprints |
| =world= | World | World | The system tenant | At database bring-up | ISO and FpML vocabularies, calendars and their exceptions and events, currency pairs and their conventions, currencies, commodities, equity underlyings |
| =tenant_defaults= | Tenant | Tenant-wide | The tenant | When the tenant is created | The badges and badge mappings, the code domains, the value domains and the parameter values a tenant starts with |
| =party_essentials= | Tenant | Party | The party's tenant | When the party is onboarded | The party's instrument conventions and its CRM topology |
| =party_reporting= | Tenant | Party | The party's tenant | When the party is onboarded | The party's report definitions |
| =ore_samples= | Tenant | Party | The party's tenant | When the party is onboarded | The ORE samples: netting agreements, netting sets, CSAs, aliases, portfolios |
| =risk_management= | Tenant | Party | The party's tenant | When the party is onboarded | The business units, portfolios and books, and the ORE report definitions, of a party that runs reports |
| =crm_topology= | Tenant | Party | The party's tenant | When the party is onboarded | The CRM topology on its own |
| =lei_hierarchy= | Tenant | Tenant-wide | The tenant | When the tenant asks for it | The GLEIF hierarchy imported as the tenant's parties, and the staging datasets it reads |
| =crypto= | World | World | The system tenant | When the installation asks for it | The cryptocurrency slice, published beside the currencies |

A bundle carries one level and one scope, and the two decide its target tenant
and its parameters. A dataset is a member of one bundle and no more; the
datasets a bundle reaches through a dependency edge are not members. A bundle
is a run, not a transaction: each step commits its own function call, and a
step that fails stops the run without undoing the steps before it. The
guarantee a bundle does and does not give is
[[id:BA57E2D2-553B-4A06-9295-E792D1E29487][The bundle and package catalogue]]'s
subject, at B14.

Two consequences a developer must carry:

- A tenant never holds a copy of an installation row or a world row. It reads
  the system tenant's rows through the shared-reference policy, and an entity
  whose rows a tenant reads declares =:system_tenant_visible:= on its model.
  [[id:0EAAEDFD-7954-4649-A463-9EE377B023F7][Data read across tenants]] holds
  the mechanism and the checklist for a new shared table.
- A record and the row made from it can sit at different levels, and the GLEIF
  import is the case that proves it. The LEI record is a world fact. The party
  a tenant creates from that record is the tenant's own row. The dataset that
  writes parties is therefore a tenant dataset, whatever it reads.

The deployment's own registers — the services roster, the hosts, the grid and
node samples, the telemetry logs — sit at the installation level and are
published by nobody. A service writes them as it observes them, no bundle
carries them, and no tenant reads them. A reader looking for the dataset that
publishes one is looking for something the model does not have.

** The writer

The level names the write path, and the choice is not free.

- A table that a person manages — previews it, re-publishes it, versions it —
  is written by a *publish function*, and the rows arrive as a dataset.
- A fixed vocabulary the platform ships is written by a *populate script*, and
  every tenant reads its rows through the shared-reference read.
- A table has one mechanism that writes it. If a publish function writes it, no
  populate script inserts into it, and the reverse. One function may serve two
  datasets that fill one table, as the FpML and ORE asset-class datasets do;
  each row still has one dataset.
- A row a populate script writes is the installation's own. It is not a
  published row, though every tenant reads it.

Three moves are therefore always wrong, whatever the feature asks for. Do not
insert into a table a publish function writes. Do not publish an installation
row or a world row into a tenant. Do not add a dataset to a second bundle.

** The path a publication takes

#+caption: The path: from a bundle request to a published row.
#+attr_html: :width 100%
[[proj:doc/knowledge/architecture/where_new_data_goes_components.png]]

The publish function is the only thing that writes a published row, and it has
two callers: the bundle publication at runtime, and the bootstrap at database
bring-up. The function reads the dataset's artefact rows, which live in the
system tenant, and writes the owning tables in the target tenant. It is
idempotent, and it returns the four counts — inserted, updated, skipped,
deleted — that a caller reads.
[[id:F19A6B98-1CAD-4206-913B-A4EAAED2DEAF][DQ artefacts]] owns the function's
contract, the artefact table, the artefact type and the steps that add one.

#+caption: One bundle publish: dependency order, one function per dataset.
#+attr_html: :width 100%
[[proj:doc/knowledge/architecture/where_new_data_goes_publish_sequence.png]]

The order is the dependency closure's, not the display order of the bundle
members. A dataset with no target subject is dropped from the run.

** Provenance

The row's audit tail is the one every reference-data entity carries, which
[[id:A19D2750-D97D-09A4-BD2B-5218D9654E56][Data quality]] states and this page
does not repeat. Publication adds one thing to it: the commentary names the
dataset, as =Imported from DQ dataset: <name>=, and the reason code is
=system.external_data_import=.

The chain runs from the row to the dataset by that name, from the dataset row
to its artefact rows by the dataset id, and from the artefact type to the
publish function, the target table and the subject. The name and not the id is
what a published row records, so a rename breaks the chain and a database
recreate does not.

** Reproducibility

A database recreate produces the schema, the system tenant, the staged
artefacts and the published installation and world catalogues, and it produces
them from the tree alone. A test therefore starts on a database that holds the
calendars, the currencies, the conventions, the commodities and the
underlyings, with no tenant provisioned and no trade booked. How to run one is
[[id:4342B077-85EA-4C6A-9BDF-D38560C80B37][How do I recreate the
database?]]'s subject.

Three things a recreate does not reproduce. The dataset id, which
=ores_dq_datasets_upsert_fn= mints with =gen_random_uuid()= against the
natural key of name, subject area and domain. The publication history, which
no table holds. The row versions, which return to 1 because a recreate writes
every row once.

An operator proves a catalogue with the two checks the tree has.
=ores_dq_bundle_datasets_list_fn= and =ores_dq_bundle_preview_fn= say whether
a bundle is complete: every member has a dataset, a subject, and no member is
missing. A re-run of the bundle then says whether the catalogue matches, and a
correct one returns =skipped= for every row.

Bringing a database up stops at the system tenant. An operator continues by
creating a tenant, publishing =tenant_defaults= into it, and onboarding each
party with =party_essentials=. Market data and trades follow, and neither is
published.
