* Goal

oresmd should be able to *express* an identifier for every one of the
49 ORE quote types [[id:F9AE7F54-D995-476A-BA24-93698BF5029D][the market
data catalogue]] documents -- not just project a URI into a working ORE
key string, which is a separate, narrower concern this story does not
require of every family (see =* Out of scope=). Representation
completeness is the goal; XML/conversion coverage is tracked
separately (e.g. the [[id:A202712C-9CFD-48DC-9014-40BA5A9408C6][ORE
curve-config/market-data XML round-trip task]] this story was split off
from, which stays scoped to =YieldCurve= plus whatever asset classes
oresmd already represents).

* Decisions

- *Representation and conversion are separate concerns*: this story's
  acceptance is "oresmd can express an identifier for every catalogued
  type", not "every type has working XML import/export" -- the latter
  is per-domain-model conversion work tracked wherever that domain
  model actually lives (e.g. =ir_curve_generation_config=/=ir_curve_feed=
  for IR yield curves), and most catalogued types have no ORES domain
  model behind them at all yet. Confusing the two led to this story's
  own split-off from an XML-round-trip task that was never meant to
  carry this scope.
- *Volatility surfaces get one shared sub-schema, not eight
  independent ones*: every vol sub-family (swaption, cap/floor, FX/equity/commodity/bond
  option, inflation cap/floor, credit index option) shares the same
  underlying shape -- a strike/moneyness dimension, an expiry/tenor
  dimension, and a model-subtype (=RATE_LNVOL=/=RATE_NVOL=/=RATE_SLNVOL=/=SHIFT=/=PRICE=)
  -- so the schema design happens once, in its own task, rather than
  being rediscovered independently per sub-family.

* Out of scope

- Full =curveconfig.xml=/=todaysmarket.xml=/market-data-quote-string
  *conversion* code for every family -- tracked, where it belongs, in
  the [[id:A202712C-9CFD-48DC-9014-40BA5A9408C6][ORE curve-config/market-data
  XML round-trip task]] (scoped to =YieldCurve= for now) and future
  tasks once each family's own ORES domain model exists.
- Building the ORES domain models each new asset class's real data
  would live in (e.g. an actual inflation curve entity, a correlation
  matrix entity) -- this story only extends oresmd's *identifier*
  representation, not the persisted domain models those identifiers
  would eventually back.
