* Plan

The BFF's session holds more than the C++ session store keeps: the login's
outcome (active, or waiting on a party), the parties offered, the tenant's name
and whether it is setting up, the session mode, the version and database, the
password-reset flag and the access lifetime. The session record grows to hold
them, and the existing sign-in in =auth_session_routes= is the starting point.
The credential policy limits the sign-in, as it does the generic one; the BFF
answered a throttled sign-in with 401, and the C++ server answers 429.

The BFF's client also renewed the token when it expired. The C++ gateway does
not, so a browser session would end at thirty minutes; that is
[[id:7D194F8C-6352-4F0B-AA9B-D1D8E716A7AC][Renew a browser session's token]], and the switch to the C++ server waits for it.

** What was built

- =session_record= gains =view=, the browser's session as JSON, which the store
  keeps and never reads, so =ores.http.api= names nothing of IAM. The store
  gains =update=, which changes a record under its lock and slides its expiry.
- =browser_session= in the IAM part is the session the browser reads, a codec
  struct in the BFF's field order, with =session_of= from a login answer and
  =party_choice_json= for a login that waits on a party.
- =browser_session_routes= in the IAM part, registered by the application beside
  =auth_session_routes=: =POST /api/session= (open, credential policy) checks
  bootstrap mode, signs in, opens a record and sets the cookie, answering the
  session or the party choice; =GET /api/session= reads the record, refuses a
  login that waits on a party, and releases the tenant setup rail once the
  tenant's run is complete; =DELETE /api/session= ends the IAM session best
  effort, closes the record and clears the cookie; =POST /api/session/party= and
  =POST /api/session/switch-party= need a session, so the CSRF guard covers
  them, exchange the token and update the record; the switch reads the tenant's
  parties through =tenant_parties=, now shared with provisioning.
- =POST /api/account/password= moved here from =account_door_routes=, so it
  clears the session's reset flag after a change, as the BFF did.
- ores.web sends =X-Ores-Request= on every request. The C++ server refuses a
  cookie write without it; the BFF ignores it, so the browser works with both.

* Result

The C++ server answers the browser's session routes at the BFF's addresses and
in its shapes: sign in, read the session, sign out, choose a party and switch
party, and a password change clears the session's reset flag. The browser
marks its requests so the C++ server accepts its cookie writes. Tests compare
the login answers and the session view exactly, prove the session read and
sign-out against a real store, the refusals before any forward, and which
routes need a session.
