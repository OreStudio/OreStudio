* Plan

Decisions:

- *Owner and place.* The inventory names ores.assets the owner, so the view
  lives in =image_screen_routes= in =ores.http.assets=. It reads four reference
  data lists, so the assets part links =ores.refdata.api=; both apis are public
  links, because the view's model in the header holds their types.
- *Schema.* =image_map= is a model of four code-to-image maps and the
  placeholder, written by the codec. =image_map_of= is a pure function of the
  five reads: a calendar uses its own image or its country's, a business centre
  its country's, and the placeholder is the image coded =xx=, as the BFF built
  it. A missing placeholder is null.
- *Cache policy.* Fresh for five minutes, as the BFF kept it and the inventory
  states. Every screen reads the map, so revalidating it would cost five reads a
  screen; a flag changes rarely, and a stale flag for a few minutes is cosmetic.
  This is the one view so far whose caller's own writes can change it and that
  is still kept fresh; the trade-off is stated on the route.

* Result

The image map is served by ores.http at the BFF's address, a published model
built from four reference data lists and one image search, fresh for five
minutes with an =ETag=. A test proves each fallback, the placeholder and the
answer's shape.

Proved live on a freshly provisioned Acme deployment: the map answers 200
with 170 currencies, 250 countries, 61 calendars and the placeholder, byte for
byte the BFF's answer (22,039 bytes each), with =private, max-age=300= and an
=ETag=; the same tag answers 304 with no body; no session answers 401.

Component audit: the task touched ores.http (the assets part), which now links
=ores.refdata.api=. The view lives in the image screens' unit; =validate_docs.sh=
is run before the pull request.
