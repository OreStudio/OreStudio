* Notes

- The finding that changes the shape of the work: =iam.v1.auth.signup= serves through =account_setup_service=, which reads neither =system.user_signups= nor =system.signup_requires_authorization=, while the service that does read them is never constructed. The deployment's switch is therefore advisory, and a deployment with self-registration turned off still accepts registrations over NATS and over the HTTP gateway.
- The second finding: the sign-up handler never parses a hostname, so it writes with the IAM service's own context, which defaults to the system tenant. The browser has no tenant to offer it, because the BFF does not resolve one from the address.

* Result

The investigation is [[id:9700E01F-B582-4984-AF2F-81E2BA880544][Analyse the sign-up process end to end]]. It confirms six of the journey document's seven gaps and corrects the fifth, which describes the authorisation refusal of a service nothing calls.

Two findings move the work beyond the screen. Self-registration is open on every deployment regardless of =system.user_signups=, because the live path checks nothing; and a registration that names no hostname creates its account in the system tenant, because the handler writes with its own context and the browser has no tenant to send. Neither is fixable on the sign-up screen.

The record ends with the six decisions the target state must settle — the policy read, the default tenant, the default party, the waiting state, the default role and the kill switch — and with three prerequisites that are not choices: the live path must read the flags, the response must carry an error code, and the BFF must expose a rate-limited route.
