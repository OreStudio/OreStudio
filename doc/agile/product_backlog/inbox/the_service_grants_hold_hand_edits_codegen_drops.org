#+title: The service grants file holds hand edits that regeneration drops
#+description: iam_service_db_grants_create.sql is generated from the service registry, but main's copy holds grants added by hand that the template and registry do not state; regenerating it revokes them.

* What

=projects/ores.sql/create/iam/iam_service_db_grants_create.sql= is generated
by the =ores.sql.service= codegen address from
=projects/modeling/service_registry.org=. Regenerating it on 2026-11-21, to add
=ores.orgmode.service=, removed lines main's copy holds that neither the
template nor the registry states:

- the loop in =_ores_grant_dml_fn= that grants each component's views to the
  service that owns its tables;
- the approvals-mode grants on =ores_variability_system_settings_= for the
  inbox, refdata, reporting, trading and marketdata services;
- marketdata's grants on the inbox notification tables, and the comments that
  explain its approval-decision grant.

So they were added to the generated file by hand. The next registry change that
regenerates the file will silently revoke them, as it would have here. Move
each into the template or the registry (=Select prefixes=, =DML prefixes=), and
make the codegen drift check cover this file so a hand edit is refused.

* Why

A service that loses a grant fails at run time, not at build or test time, and
only on the path that needs it.
