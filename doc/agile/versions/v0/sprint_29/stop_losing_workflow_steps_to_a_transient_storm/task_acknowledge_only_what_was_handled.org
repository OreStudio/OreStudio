* Result

* What was actually wrong

=client.cpp:239= states it plainly: "JetStream subscriptions auto-ack by
default (ManualAck is false)". Returning from the handler is the
acknowledgement, and =on_msg= catches every exception and returns, so a
handler that throws acknowledges the message it failed on.

It is worse than an unused guarantee. =on_msg= destroys the =natsMsg= *before*
calling the handler:

#+begin_src cpp
message m = extract_message(msg);
natsMsg_Destroy(msg);
msg = nullptr;
cl->handler(std::move(m));
#+end_src

So by the time a handler could decide it had done enough work, there is no
message handle left to acknowledge. Manual acknowledgement cannot be added
without changing that order, which is why this is a task rather than a flag.

* Design

The acknowledgement becomes an RAII guard owned by the client, so the default
is right and forgetting it is impossible.

- =on_msg= keeps the =natsMsg= alive, builds the guard from it, calls the
  handler, and lets the guard settle on the way out of every path, including
  the catch blocks.
- The guard acknowledges in its destructor unless the handler settled it
  otherwise. A handler that wants a redelivery calls =fail()=, which naks so
  the server redelivers at once rather than after the ack wait.
- A handler that throws leaves the guard unsettled, and the catch block naks
  it. That is the case the auto-ack gets wrong today.
- The guard reaches the handler either as a member of =ores::nats::message= or
  as a second handler parameter. Whichever is chosen has to be uniform, because
  every JetStream handler is written against it.

This belongs with the redelivery bound. A =nak= retries immediately, so with
=max_deliver= unlimited a message that always fails becomes a hot loop; the
experiment that proved redelivery was exactly that loop until it was stopped.
