* What this measures

Two axes, because they answer different questions.

- *Time* is what a caller waits for. It is noisy on a shared machine and it is
  recorded anyway, because a change that doubles the time is worth seeing.
- *Cache and instruction counts* are why the time moved. They come from
  =cachegrind=, which simulates the caches, so the same binary on the same
  input produces the same numbers on every run. That is what makes a committed
  history worth diffing.

Three modes, so the cost of the document model can be separated from the cost
of scanning.

| Mode | What it does |
|------+--------------|
| =scan= | reads the events and keeps nothing |
| =tape= | builds the transient document model |
| =pugi= | builds a pugixml DOM, the baseline the model is judged against |

* Running it

#+begin_src sh
./benchmarks/xml/run.sh              # measure and append to history.tsv
./benchmarks/xml/run.sh --no-record  # measure and print, leave the history alone
./benchmarks/xml/compare.py <older-commit> [<newer-commit>]
#+end_src

=run.sh= builds the benchmark from the product sources with the build tree's
own flags, so it needs a configured tree but no CMake target. It is not part
of =ctest= and not part of any check: it takes minutes and it is not a pass or
fail. Run it when the XML layer changes, and record the result.

=history.tsv= is long-form: one row per case, metric, commit, date and
compiler. Appending is safe, and =compare.py= prints the delta between any two
commits that appear in it.

* Cache tooling, and what works here

|=cachegrind=| simulates the L1 instruction, L1 data and last-level caches and
counts instructions. It needs no privileges, it is deterministic, and it is the
only one of the two options that works unprivileged on this machine. It is
roughly fifty times slower than a native run, which is why =inputs.tsv= pins a
small repeat count.

|=perf= is installed but =/proc/sys/kernel/perf_event_paranoid= is 3, so
unprivileged processes cannot read hardware cache counters. Real counters need
=sudo sysctl kernel.perf_event_paranoid=1=, and even then the counts move
between runs. Use cachegrind for the committed history and treat =perf= as a
tool for a one-off look.

Neither measures what the hardware actually did. Cachegrind's numbers are a
simulation of a stated cache configuration, printed in its header. They are
comparable across builds of the same machine, and not comparable across
machines.

* A benchmarking framework

None of the three is required for the cache axis: cachegrind does that, and no
C++ framework reports cache misses.

For the time axis there are three sensible choices.

| Option | Cost | Reach for it when |
|--------+------+-------------------|
| Google Benchmark 1.9.5 | a vcpkg dependency; the port is vendored, the source is not cached | the suite grows and you want percentiles, counters, and a JSON baseline |
| nanobench 4.6.0 | one header, MIT, also vendored as a port | you want low-overhead microbenchmarks and HTML or CSV out |
| Catch2 =BENCHMARK= | already a dependency | the case is trivial and you want it beside the tests |

This directory does not use any of them yet, and the reason is cost rather
than taste. Adding a dependency means a =vcpkg install= against a build tree
that is currently hours behind, and the measurement this file exists to take
works without it. The hand-rolled loop is the "best of five" statistic, which
is the one number that matters when the machine is shared. When the build tree
is current, Google Benchmark is the right home for the time axis: it is the
one that records a baseline file a script can diff, which is the property this
directory is built around.

* The first measurement, and what it changed

The suite was first run at =fcea424d5a=, twenty repeats of one 478 KB
portfolio and two of the 6.3 MB calendar file.

| Input | Mode | ns/parse | Instructions | D1 misses | LL misses |
|-------+------+----------+--------------+-----------+-----------|
| portfolio | scan | 1,403,333 | 666,521,544 | 340,837 | 27,406 |
| portfolio | tape | 1,454,835 | 760,586,768 | 1,826,670 | 67,914 |
| portfolio | pugi | 849,544 | 219,824,078 | 1,579,176 | 54,063 |
| large | scan | 19,174,893 | 863,970,232 | 559,566 | 234,056 |
| large | tape | 26,526,143 | 954,532,643 | 2,626,251 | 2,315,099 |
| large | pugi | 14,952,829 | 468,502,687 | 1,813,791 | 1,549,571 |

Two readings, both uncomfortable.

*The tape is the cache cost.* Building it multiplies first-level data misses
by 5.4 on the portfolio and last-level misses by 9.9 on the 6.3 MB file. A
token is twenty bytes, so the 478 KB document becomes a 721 KB tape and the
6.3 MB document becomes a 15.9 MB tape. The scan-only column is the floor, and
it is far below both trees. This qualifies the claim that the generated DOM is
the expensive artefact: it is expensive relative to scanning, and so is the
tape.

*The scanner executed three times pugixml's instructions* on the same
document, 666 M against 220 M. A callgrind profile put forty percent of the
parse in one place: the =normalise= pre-scan, a byte-at-a-time loop over every
text and attribute value that almost always found nothing to do. A second
tenth went to =memcmp= on the tag path, which compared up to five prefixes for
every element.

* What the first measurement changed

The scanner took two changes, both measured before and after.

- The pre-scan is now a few memchr-backed =find()= calls.
- The second character after =<= decides which prefix is worth comparing,
  which keeps the common tag path free of =memcmp=.

The same suite at =e82a0a827f=:

| Input | Mode | ns/parse | Instructions | Change in instructions |
|-------+------+----------+--------------+------------------------|
| portfolio | scan | 620,464 | 343,284,249 | -48% |
| portfolio | tape | 740,802 | 410,789,892 | -46% |
| portfolio | pugi | 903,024 | 219,824,068 | unchanged |
| large | scan | 11,790,666 | 649,136,390 | -25% |
| large | tape | 18,089,642 | 718,883,057 | -25% |
| large | pugi | 14,405,819 | 468,502,757 | unchanged |

Wall time on the portfolio fell from 1.40 ms to 0.62 ms per parse, and the
scanner is now 1.6 times pugixml's instructions rather than three. The tape
still costs four times the first-level misses of scanning alone, which is what
building a model costs and is why the entity path will stream rather than
build one.

The corpus did not move: 1,623 documents read, 1,623 round tripped, 1,623
validating, 26 unit cases green.

* What to run when

- A change to the scanner, the document model or the writer: the whole suite.
- A change to a codec table: the case that covers its family.
- A change that only touches the orchestration around the codec: nothing here.
