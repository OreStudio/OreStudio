This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: An empty installation is brought to life: the system administrator, the first tenant and the first sign-in.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"Get me from an empty installation to a system I can work in." The person
creates the system administrator, then the first tenant with its parties and
its administrator, then signs that administrator in. The journey is done when
the installation leaves bootstrap mode and the last screen reads *Ready*.

* Actor and trigger

Two actors share one path. The first steps are open to anyone who reaches the
installation: while [[id:8AEB87D6-0CE2-1434-E71B-60BEAE20ADF0][system bootstrap]]
is not complete, the system is in bootstrap mode, nobody can sign in, and the
*Setup* page is the only page. From the first sign-in onward the actor is the
tenant administrator: an account of type =user=, signed in, inside the first
tenant. The trigger is a browser pointed at a new installation. The journey
ends at *Ready*, when the installation stops being in bootstrap mode.

This is one of the three journeys that carry server-side state. The tenant
work runs on the server, it takes minutes, and it can fail half way. The state
lives in =ores.workflow=, so the person can close the page and come back, and
the shell can drive the same steps. Every other group in this corpus describes
a journey that keeps no such state. The order is fixed: first run is the only
journey that can happen on an empty database.

* Steps

1. *Welcome.* The system shows the splash, "Welcome to ORE Studio", one
   sentence, and three unnumbered stage cards: create the administrator,
   create the first tenant, sign in. The person chooses *Get started*. No
   server call happens here.
2. *Create the administrator.* The person enters a username (default
   =super_admin=), an email and a password. The password field applies the
   shared policy. The system runs [[id:8AEB87D6-0CE2-1434-E71B-60BEAE20ADF0][system bootstrap]]:
   it creates the system administrator and nothing else. No tenant is created
   at this step, and nobody can sign in yet.
3. *Choose a starting point.* The new tenant steps now run inline, as rail
   steps 2 to 6. The person picks a
   [[id:8AEB87D6-0CE2-1434-E71B-60BEAE20ADF0][seed profile]]: /Empty
   operational/ or /ACME demo/. Each card shows a tagline, three bullets and
   its counts. The ACME card also shows the ACME logo. Nothing is created yet.
4. *Describe the tenant.* For /Empty operational/ the person enters the root
   LEI and the counterparty set, and sets the administrator's password. For
   /ACME demo/ the profile fills in the code, name, hostname and administrator
   username and email; the details show as a summary behind *Change settings*,
   and the tenant administrator reuses the system administrator's password. No
   forced password change follows for ACME, and one does for /Empty
   operational/.
5. *Review.* The person reads one summary: starting point, tenant name and
   code, administrator, and the profile's parameters. The screen states how
   many steps the profile runs. Nothing is created until the person confirms.
6. *Provisioning.* The person confirms, and the system starts the
   [[id:8AEB87D6-0CE2-1434-E71B-60BEAE20ADF0][provision]] workflow for the
   first tenant. The rail lists one line per workflow step, and each line reads
   pending, running, done or failed. *This is the step that carries the state.*
   The person can leave the page. A failed step stops the instance, the tenant
   stays /bootstrapping/, and a retry resumes from the failed step; the
   completed steps are kept.
7. *Hand off.* The tenant is ready. The person chooses *Continue as tenant
   admin*, which signs out, signs in as the tenant administrator and opens
   their first sign-in, or *Hand off to someone else*, which signs out and
   shows the username to pass on. The web keeps the administrator's password in
   memory only until this point; it is never written to storage.
8. *First sign-in.* The tenant administrator sets a password only they know
   when the profile forces a change, and chooses the party to start in when
   they work in more than one. This is
   [[id:8AEB87D6-0CE2-1434-E71B-60BEAE20ADF0][onboard]]: a person's first use
   of a tenant that already exists.
9. *Ready.* The system confirms the installation. The person goes home, or to
   the Tenants page to create another tenant.

One flat step rail. The new tenant steps are written once, as a library of
step definitions, and first run expands them inline. The person sees the
Welcome screen first, and then one rail of eight steps, never a journey inside
a journey. Steps that change server state are final: there is no Back past
them.

* Prototype

Accepted by the user on 2026-09-22. The prototype is on a throwaway branch and
is not merged; the branch is kept as the record.

- Branch :: =prototype/first-run-journey=
- Route :: =/setup=
- Source :: =projects/ores.web/packages/web/src/pages/prototype/newTenantJourney/= on =prototype/first-run-journey= only; the path does not exist on =main=
- Design record :: [[id:DA4BE50C-B2EC-4C6D-8DAA-9EB06D33B003][Task: Prototype the first run journey]]

The prototype settled three things. Journeys are data: one page renders an
ordered list of step definitions, so first run reuses the new tenant steps
rather than copying them. Every deployment is multi-tenant, so first run never
asks about tenancy. And ACME asks for nothing, in first run and in the new
tenant journey alike.

=iam.v1.bootstrap.status= and =iam.v1.bootstrap.create-admin= are declared in
[[id:4B98E2D0-8FE3-4321-8CFD-90A4C13422EA][ores.iam.bootstrap_messages]] and
need no session, because the system is in bootstrap mode. The account and
tenant subjects need a session. =workflow.v1.instances.steps= is not in the
generated web protocol: the generator emits no =workflow= package for the
browser, so the BFF adds a route for it.

=iam.v1.bootstrap.provision-tenant= still exists and needs no session, because
bootstrap mode is still on. It takes no seed profile, runs synchronously and
returns no instance id. The accepted contract retires it and replaces it with
=iam.v1.tenants.provision= for every tenant, the first one included.

=iam.v1.tenants.provision-acme= still exists and needs a session. It runs the
whole provisioning server-side through internal actor impersonation. It is
ACME-only, it takes no seed profile, and it returns all its steps at the end, so
it streams no progress. The accepted contract retires it too. The generic
profile-driven request =iam.v1.tenants.provision= does not exist yet.

* What is missing

Three things this journey names are not in the system, and none of them stops
a person on the path it takes:

- the provision request has no field for reusing the creating administrator's
  password, so a profile that wants the hand-over is a profile the request
  cannot state;
- the *Operational* card's LEI import has no staged GLEIF data to read on a
  fresh installation, which is
  [[id:F6C38DC8-5DEB-4EC1-ABD0-FDBB517E174B][captured in the inbox]];
- the engine's change event carries an =entity_change_event= that no one
  schema can read for every entity, so the page follows the progress read
  instead, which
  [[id:767A3138-2D4C-4330-8281-DBCFEACF244D][its capture]] owns.

Everything else the journey reaches for exists, and the list below is the
record of what each part turned out to be.

1. *The journey's state is a workflow instance.* A journey is a definition and
   not a server-side object, so no journey entity was added anywhere. The
   run's state is a workflow instance in =ores.workflow=, and the page follows
   it through the progress read. Only the server-side run resumes: the rail
   position is memory, so a reload leaves the journey at the sign-in screen,
   and the steps a person takes around the run do not survive it.
2. *The starting points are data.* =ores.iam= owns the profile, its parameter
   schema and the step-kind catalogue, and the reads =iam.v1.seed_profiles.list=
   and =.get= answer them. *Operational* and *ACME demo* are rows, so a third
   profile is a row and a new step kind is code. The page builds each card and
   its form from the row, and holds no profile of its own.
3. *One provision request serves every tenant.* =iam.v1.tenants.provision=
   takes the profile code and its parameters and returns the instance id of the
   run it starts, the first tenant included. The two verbs it replaces stay
   reachable until the shell moves to it.
4. *Progress is read, not pushed.* The page asks the progress read again while
   the run is open and renders the rail from the answer: the run's state, the
   step it is executing, and one line per step. The engine's
   =workflow_instance_changed= event is not the progress contract: its payload
   is an =entity_change_event= that no one schema can read for every entity.
5. *A retry resumes a stopped run.* =workflow.v1.instances.retry= re-dispatches
   the step a run stopped on and leaves the completed steps and their results
   alone. Discard stays a separate administrator action,
   =iam.v1.system.reset-tenant=, because the contract keeps completed work.
6. *The forced change fires.* The profile's =force_password_change= reaches the
   account the provisioner creates, and the login answer carries the account
   record's flag, so the *Operational* profile's administrator is answered with
   =passwordResetRequired: true= at first sign-in and sets a password only they
   know. The profile's other hand-over choice, reusing the creating
   administrator's password, is read for the *ACME demo* card; a request field
   for it does not exist.
7. *The policy is read, not copied.* The validator states its rules once as a
   record and enforces that record, and a read answers with it before anybody
   has signed in. Every password field in the journey is built from that
   answer, so a deployment that tightens a rule tightens the screen.

What remains is the rest of the plan: the *New tenant* and *New party*
journeys, the shell's move to the same contract, and the proof of all three
journeys on a fresh installation. One gap is already found and captured: the
*Operational* card's own LEI import does not complete on a fresh installation,
because the derived GLEIF dataset is not staged for the new tenant. The
journey behaves as designed there — the rail shows the failed step, the retry
is offered, and the tenant stays in =bootstrapping=.
