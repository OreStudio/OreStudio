* Goal

A person reading a curve learns how it was made, in the same words the fixings screen uses: the curve's own series says IR_CURVE_BOOTSTRAP and names the blueprint that bootstrapped it, and a computed term fixing says IR_TERM_FIXING, because compounding a term rate from an overnight curve is not a bootstrap. Each derivation kind names one kind of config, so an id resolves to one table.

* Acceptance

- A curve's output series states its derivation when the curve is created, not on its first republish.
- The published curve record says how the curve was made, by the blueprint's name rather than its id.
- The three computed term indices are labelled with a kind that names their computation, and no kind resolves to two tables.

* Plan

1. *The kind.* The catalogue gains =IR_TERM_FIXING=, and the three computed
   term indices are relabelled with it. =IR_CURVE_BOOTSTRAP= stays what it says:
   a curve bootstrapped from an instrument grid, whose config id resolves to a
   refdata blueprint.
2. *The stamp.* A layout script stamps every seeded blueprint's output series
   =IR_CURVE_BOOTSTRAP= with its config and version once the blueprints exist, so
   a fresh installation states the derivation before anything republishes. The
   republish service keeps stamping an unclaimed series as the fallback for a
   blueprint created later.
3. *The record.* =published_curve_set= gains =derivation_kind= and
   =derivation_config_name=; the reader joins the output series and the blueprint;
   the record page prints "How it was made" beside the curve configuration.
4. *Proof.* A pgTAP suite asserts the two invariants a kind implies — every
   =IR_CURVE_BOOTSTRAP= id resolves to a blueprint, every =IR_TERM_FIXING= id to a
   generation config — and that a seeded curve states its derivation before any
   republish. The reader's own test asserts the record carries the kind and the
   blueprint's name; the record page's test asserts the line.

* Result

A curve now says how it was made, in the words a person reads rather than by an
id. The published curve record carries the derivation: the kind is
=IR_CURVE_BOOTSTRAP= and the blueprint's name travels beside it, so the Details
tab reads "How it was made: ir curve bootstrap, built by USD-SOFR-FOMC" where it
used to show only a bare uuid labelled *Curve configuration*. A curve no
derivation produced says *observed*, because that is a fact about the curve and
not the absence of one. The kind follows the blueprint the record names rather
than the series' own claim, so the two cannot disagree: a series that is not yet
stamped, under a record that names a blueprint, still states how the curve was
made.

For the seeded curves, the derivation is stated when the curve is created. A
layout script stamps every seeded blueprint's output series with the kind, the
config and its version once the blueprints exist, so a fresh installation states
it before anything republishes: 38 of 38 on the database the gate rebuilt, and
none left reading observed. A blueprint created later in the application is
stamped by the republish service on its first republish, and
[[id:CC8358E9-DC1F-4983-ADF8-CA6938918884][the gap that leaves]] is captured. The
record reports such a curve correctly in the meantime, because it reads the
builder from the publish row.

The record's fields are grouped into a =curve_derivation= message rather than
left flat, which keeps =published_curve_set= inside its field ceiling, and the
grouping replaced =bootstrap_config_id=, so the =v1= subject changed shape. The
rule that =v1= changes only for a breaking shape change permits it, because a
field was removed rather than renamed in place, and the provisioning handlers
read the same value from its new home.

The kind became its own. =IR_TERM_FIXING= joins the catalogue, and the three
computed term indices carry it, because compounding a term rate from an overnight
curve is not bootstrapping a curve from an instrument grid. That also repairs the
half of the previous task this exposed: an =IR_CURVE_BOOTSTRAP= config id
resolves to a refdata blueprint, and the three fixing series had pointed at a
synthetic generation config under the same kind, so one kind named two tables. A
pgTAP suite asserts both halves — every =IR_CURVE_BOOTSTRAP= id resolves to a
blueprint, every =IR_TERM_FIXING= id to a generation config — and that a seeded
curve states its derivation before any republish.

What this does not do: the analytics and evolution screens, which draw a curve's
points, say nothing about how the points were made. Each point already carries
that in =observation_lineage=, which distinguishes a derived point from one keyed
by hand, and that is a read and a surface of its own rather than a line on the
record. It is not part of this task's ask, and the record is where a person meets
the curve.
