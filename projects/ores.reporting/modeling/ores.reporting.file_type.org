#+title: ores.reporting.file_type
#+description: Codegen entity model for the reporting =file_type= table. The kinds of file in the ORE universe and the well known name of each.
#+type: ores.codegen.entity
#+component: reporting
#+filetags: :model:entity:reporting:
#+brief: A kind of file in the ORE universe and its well known name.
#+entity_singular: file_type
#+entity_plural: file_types
#+entity_title: File Type
#+created: 2026-10-12
#+updated: 2026-10-12

Reference data naming the files an ORE run reads and writes. A file type is one
parameter of the run document that carries a file name: a Setup parameter such as
conventionsFile, or the parameter of an analytic such as the outputFileName of npv.
The table gives each its well known name, so a configuration never repeats a file
name and the export looks the name up when it writes a file.

The names come from the shipped ORE samples. Each is the most common name the samples
give the file, and sample_count out of sample_total records how many use it.
Names that embed a date are set aside, because a date is a value of the run.

A name may be a pattern with a key, for example portfolio_{{BOOK_ID}}.xml, for a file
that a run splits. The table can hold the pattern. Splitting is a later task.

The table lists names and patterns. It does not hold the content of a file.

** direction
:PROPERTIES:
:type:     text
:cpp_type: std::string
:nullable: false
:END:

Whether ORE Studio reads the file or ORE writes it: input or output. An input is a file ORE Studio reads and parses into the entities of its configuration type when it imports a run, and writes back from those entities when it exports one. An output is a file ORE writes when the run executes, which ORE Studio names but does not parse. A file that one analytic writes and another reads is an output of the writer and an input of the reader.

#+begin_src cpp :name generator
std::string("input")
#+end_src

** format
:PROPERTIES:
:type:     text
:cpp_type: std::string
:nullable: false
:END:

The format of the file: xml, csv, csv_gz for a compressed csv, txt, dat for a binary file, or json. An xml file is validated against the XSD in xsd_file. A csv file has a header line and its columns are named by the guide or by the report that writes it.

#+begin_src cpp :name generator
std::string("csv")
#+end_src

** xsd_file
:PROPERTIES:
:type:     text
:cpp_type: std::optional<std::string>
:nullable: true
:END:

For an xml file, the XSD of ORE that declares its root element, for example nettingsetdefinitions.xsd for netting.xml. Nothing for a file that is not xml, or an xml file that ORE publishes no schema for.

:PROPERTIES:
:type:     text
:cpp_type: std::string
:nullable: false
:END:

What the file is: input_document, data_file, output_file or intermediate_file. An intermediate file is one analytic writes and another reads.

#+end_src

:PROPERTIES:

:nullable: true

The configuration type whose entities fill the document, or nothing when no configuration type describes it yet.

** name_pattern
:PROPERTIES:
:type:     text
:cpp_type: std::string
:nullable: false
:END:

The well known name of the file, or a pattern when a run may split the file by a key. A pattern writes the key between double braces, for example portfolio_{{BOOK_ID}}.xml. The key is upper case letters, digits and underscores.

#+end_src

** is_default
:PROPERTIES:
:type:     boolean
:cpp_type: bool
:nullable: false
:default:  false
:default_value: false
:END:

Whether a run of the analytic names this file unless the configuration says otherwise. The seed sets it for a file that at least half of the samples that run the analytic name. A Setup file type is never a default, because the definition's bindings decide which documents the run names.

#+end_src

** produced_by_file_type_code
:PROPERTIES:
:type:     text
:cpp_type: std::optional<std::string>
:nullable: true
:END:

For an intermediate file, the file type of the analytic that writes it. The reader takes the name of the writer, so two analytics that share a file read one name.

** sample_count
:PROPERTIES:
:type:     integer
:cpp_type: int
:nullable: false
:END:

How many of the ORE samples that name this file give it this name. It is zero when the name comes from the official ORE user guide and no sample uses it.

:PROPERTIES:
:type:     integer
:cpp_type: int
:nullable: false
:END:

:PROPERTIES:
:type:     text
:cpp_type: std::string
:nullable: false
:END:

What the file is for, in detail: what it holds, what the analytic does with it, who writes it and who reads it, and how a run names it. A reader who has never seen an ORE run can tell from it why the file is there.

** Checks

Domain constraints beyond the standard temporal, natural-key and nil-uuid
checks the template emits on its own.

| expression |
|------------|
| "ore_parameter" <> '' |
| "direction" in ('input', 'output') |
| ("direction" = 'output') = ("kind" = 'output_file') |
| "format" in ('xml', 'csv', 'csv_gz', 'txt', 'dat', 'json') |
| "xsd_file" is null or "format" = 'xml' |
| "kind" in ('input_document', 'data_file', 'output_file', 'intermediate_file') |
| "name_pattern" ~ '^[A-Za-z0-9_.-]*(\{\{[A-Z][A-Z0-9_]*\}\}[A-Za-z0-9_.-]*)*$' |
| "sample_count" >= 0 and "sample_count" <= "sample_total" |

** Indexes

The analytic and the ORE parameter say which file a type is, so a second row for the
same pair would name the file twice. The Setup block has no analytic, and a null does
not make two rows differ in a unique index, so the Setup parameters and the analytic
parameters each have an index of their own.

| name             | columns                                    | unique | current_only | where_extra                    |
|------------------+--------------------------------------------+--------+--------------+--------------------------------|
| setup_parameter  | tenant_id, ore_parameter                   | true   | true         | analytic_type_code is null     |
| analytic_parameter | tenant_id, analytic_type_code, ore_parameter | true | true         | analytic_type_code is not null |
