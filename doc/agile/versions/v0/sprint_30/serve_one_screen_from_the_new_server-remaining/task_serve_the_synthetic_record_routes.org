* Plan

Extend the record route generator from the reference data PR, rather than
write a second one. The synthetic registry differs from the reference data one
in five ways, and each becomes a model declaration:

- =#+web_area:= names the address the resource is served under, so the three
  reference data lookups the synthetic screens read (tenors, instrument codes
  and payment frequencies) answer under =/api/synthetic= with =refdata::=
  permissions.
- =#+web_writes: many= switches the write and the removal to the BFF's batch
  bodies: =changes= through the put-many subject, answered with the rows as
  written, and =removals= through the remove subject for one row or the
  remove-many subject, unconditional, for many.
- =#+web_parent_filter:= names the filter member a parent's rows are read by,
  where the BFF read a parent through the list filter and not a list-by
  request.
- =#+web_read_only_because:= states the sentence the catalogue shows for a
  resource no screen writes, and =#+web_system_owned: true= marks a catalogue
  every tenant shares, which only a system tenant session writes.
- The catalogue entry takes the request, so the synthetic catalogue states
  whether this session may write each resource.

The two feed resources read one row with its collection's provider, whether it
runs and where its run started. That is a composed view, so their key read is
hand-written and the generator does not register one for them.

* Result

The C++ server answers the six synthetic record routes and the catalogue for
the 16 resources of the BFF's registry: 13 synthetic units and the three
reference data lookups, which stay in the refdata part and answer under
=/api/synthetic=. The two feed key reads are hand-written composed views. The
generated tests check the refusals, the read-only rules and the accepted pages
of every unit. The work also fixed a defect PR #4560 shipped: a filtered
junction page wrote through an emptied filter.
