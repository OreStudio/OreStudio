#+title: The tick ingest pipeline: freshness first
#+description: Proposal for an ingest pipeline that keeps the newest tick, drops what is stale, and holds tens of thousands of ticks per second: lanes, latest-value conflation, batched writes and a bounded ring. It compares the design with the tickerplant, conflated feeds and time-series stores.
#+type: knowledge
#+level: cross
#+filetags: :marketdata:ingest:ticks:performance:architecture:proposal:
#+created: 2026-10-20
#+updated: 2026-10-20

* Summary

This note proposes an ingest pipeline for market ticks. It is a proposal. The
code does not work this way today.

The pipeline puts freshness first. A tick that arrives late, while a newer tick
waits, is worse than a tick that is lost. So the pipeline keeps the newest tick
of each datum, it drops ticks that are too old, and it never lets a consumer wait
for the store. Work is split into lanes. Each lane has one writer thread, a bounded
ring buffer, and a batch write to the store. The design follows the LMAX Disruptor
where that helps, and it sets the rest aside.

The target is tens of thousands of ticks each second, across every asset class and
instrument. The present loop writes about 150 rows each second.

* Detail

** The requirements

1. *Freshness over completeness.* A stale tick is worse than a missing tick. A tick
   that the queue loses is bad. A tick that the pipeline processes late, while
   newer ticks wait behind it, is worse.
2. *Volume.* The pipeline holds tens of thousands of ticks each second, once every
   asset class and instrument ticks.
3. *The live view does not wait for the store.* A chart reads the newest value at
   once, whatever the database does.
4. *Overload is visible.* A lag of seconds shows on a gauge. A lag of 70 minutes
   cannot pass unseen.
5. *A fault stays in its lane.* A slow or failing write for one series does not
   stop the others.
6. *No change signal for each row.* A time series does not announce each new row. The
   live stream is the signal.

** Why the present path cannot meet them

[[id:00D63182-C7FF-4AC9-8A83-9A5D984B2876][The ingest loop]] handles each tick on
one thread, in arrival order. For each binding of the tick, it reads the series,
inserts two observations, and publishes to JetStream. Each insert is a commit. The
publish waits for an acknowledgement. The rule that the republish follows the stored
row ties the live view to the speed of the database.

The queue sits inside the NATS client. It has no age limit, and it serves the oldest
tick first. When the loop falls behind, it spends its time on old ticks while newer
ticks wait. This is the behaviour that requirement 1 forbids.

Measurements on one environment (release build, one server shared by five
environments, a burst of 4,000 ticks) show the limit.

#+ATTR_HTML: :class hug-leading
| Configuration | Rows written each second |
|---------------+--------------------------|
| As built: synchronous commit on, one NOTIFY for each row | 143 |
| Synchronous commit off for the marketdata role | 166 |
| Synchronous commit off, and the NOTIFY function empty | 210 |

Three facts come from the samples.

- Exactly one database session of the marketdata service is active. The work is
  serial.
- With the commit sync removed, 41 percent of the samples of that session wait on a
  database-wide lock, 34 percent run on the CPU, and 24 percent wait for the
  service. The lock is the one that a transaction takes at commit after it calls
  =NOTIFY=. PostgreSQL takes it so that notifications enter the queue in commit
  order. The row trigger =ores_marketdata_market_observations_notify_trg= calls
  =pg_notify= for every row.
- The blockers of that lock were the marketdata sessions of two other environments
  on the same server. The lock is shared across databases, so ingests that share
  one server slow each other.

A commit sync is also slow on this disk. One =fdatasync= takes about 4.3 ms.

The demand is small today. One environment receives 13 ticks each second. Each tick
reaches 4.6 bindings on average, and each binding stores two rows. That is about 120
rows each second against a ceiling of about 150. At 30,000 ticks each second the
same fan-out is about 280,000 rows each second.

** The proposal

The pipeline has five stages. A receive stage decodes ticks and routes each one to a
lane. A bounded ring buffer in each lane holds the ticks. A lane worker takes
everything that has arrived and does two things with it. It publishes the newest
value of each datum to live consumers, and it writes the batch to the store in one
transaction.

*** Receive

The NATS callback does three things and no input or output. It decodes the tick, it
checks the age of the tick, and it writes the tick into the ring of its lane. A
lane is chosen by a hash of the datum key. A tick of one datum always reaches the
same lane, so the order of one series holds without a lock.

*** The ring buffer

Each lane owns one ring buffer of fixed size. The slots are allocated once, and the
ring is a power of two in size. A sequence number marks each slot, in the style of
the Disruptor. The receiver claims the next slot and publishes it. The lane worker
reads up to the newest published slot.

The ring never blocks the receiver. When the ring is full, the receiver overwrites the
oldest slot and adds one to a counter of dropped ticks. The newest tick always
wins. A starting size is 65,536 slots for each lane. At 10,000 ticks each second in
one lane, the ring holds about six seconds.

*** The age gate

Every tick has an age: the time now minus the =observation_time= of the tick. The
receiver drops a tick that is older than the limit of its class, and it counts the
drop. The lane worker checks again when it takes the tick from the ring. A starting
limit is 5 seconds for a live tick. The limit is a setting for each asset class.

The gate changes the order of service in one more way. A lane that is behind takes
the newest ticks first and drops the old ones. It does not work through the old
ticks.

*** Conflation and the live path

A lane worker keeps the newest tick of each datum in the batch it took. It publishes
those ticks to the live consumers on the party subjects. The publish uses core NATS
and waits for no acknowledgement. The live path ends here, and it never waits for the
store.

A consumer that joins late needs the last value. A JetStream stream with a limit of
one message for each subject holds it. The lane worker publishes to that stream
without waiting for the acknowledgement of each message.

*** Batched persistence

The same cycle writes every tick that passed the age gate in one transaction, with a
multi-row insert or a =COPY=. One commit now covers hundreds or thousands of rows.
The cost of the commit is shared by all of them.

- The series identity of each key comes from a cache in memory. A binding event
  clears the cache. A series that does not exist yet is created on a slow path,
  outside the batch.
- The shape check and the manual point check run once for the batch.
- A batch that fails is split in two and tried again. The split continues until it
  isolates the row that the database refuses. The lane drops that row, counts it, and
  logs it.
- The size of a batch has a cap. A starting value is 5,000 rows.

*** The overload states

A lane measures its lag from the oldest tick that it processes. The lag selects
one of three states.

#+caption: The overload states of a lane. The live path stays fresh in every state. Only the history in the store gets thinner.
#+attr_html: :width 100%
[[proj:doc/knowledge/architecture/tick_ingest_overload_states.png]]

- *Live.* The lag is small. The lane writes every tick.
- *Catching up.* The lag is above the first limit. The lane writes only the newest
  tick of each series for each second. The shape of the history stays, and the
  volume falls.
- *Shedding.* The lag is above the second limit. The lane drops every tick older
  than the age limit and counts each drop.

The lane goes back one state when the lag falls below half of the limit. The gap
stops the lane from flipping between two states. Starting values are 5 seconds for
the first limit and 30 seconds for the second. Tuning by measurement sets the final
values.

*** Observability

Each lane reports these values to the status log and to telemetry.

- The depth of the ring and the age of its oldest slot.
- The lag from the tick time to the commit, and from the tick time to the live
  publish.
- The size of each batch and the time of each commit.
- The ticks dropped, by reason: the ring was full, the tick was too old, the series
  was thinned, or the database refused the row.

An alert fires when the lag is above the first limit for longer than a set time.
The lag of 70 minutes that started this work would have fired it within seconds.

** What changes in the store

- *No notification at all.* The observation table has a row trigger that calls
  =pg_notify=. The code generator adds it to a table by default. The pattern behind
  it, in [[id:81AB065B-E6EB-4CC2-BB18-F3FD2652EC47][the PostgreSQL architecture note]],
  is a signal that an entity changed, so that a client marks its copy stale and
  reloads it. That fits a table that changes now and then. It does not fit a time
  series. The series changes many times each second, and no client can reload at that
  rate. The live path already carries each new value to the consumers that need it.
  So the trigger goes away, and so does the event mapping that republishes it.
  The model of the table sets the =ores.sql.schema.notify_trigger= knob to false.
  Three other marketdata tables already do this. Without the trigger, a commit never
  takes the notification lock, and the ingests of other databases on the same
  server no longer wait for it.
- *The second row for each tick.* The ingest stores each tick twice, once at its own
  time and once under the previous business day. At scale this doubles the writes.
  It is an open question whether a snapshot job should build that row instead.
- *One row for each party.* A tick is stored once for each binding. The cost grows
  with the number of parties that consume a source. It is an open question whether
  the store should keep one row for each source and let parties read it through a
  view.
- *Indexes.* The table has seven indexes and a trigger that closes the previous
  current point. Each index costs a write. A measurement with a batch decides
  which of them the hot path needs.

** What the first consumer needs: Hedgr

Hedgr is the new desktop client. Its plan, =docs/plans/market-eventing.md= in the
Hedgr repository, shows how a real consumer reads the pipeline.

- *Live values come from the party tick stream.* Hedgr subscribes once for each
  session to =marketdata.v1.ops.market_tick.<tenant>.<party>.>=. This is the subject
  that the ingest loop publishes to after it stores a row. Hedgr has no
  subscription to any observation change event. That confirms that the database
  notification serves no client here.
- *Hedgr waits for the store without knowing it.* The subject carries a tick only
  after the ingest has stored it. When the ingest fell behind, the chart showed ticks
  that were 70 minutes old, and nothing in Hedgr was at fault. The live path of
  this proposal removes that coupling.
- *Hedgr measures freshness itself.* It judges the age of a tick from the
  =observation_time= of the tick, and it draws that age beside the verdict. This is
  the right measure. It is also the acceptance measure for the pipeline: the age of
  a tick as the client sees it, at the 99th percentile.
- *Hedgr already conflates.* It buckets ticks into 1 second, 1 minute and 1 hour
  levels on the NATS thread, and it passes closed buckets to the frame loop through a
  fixed ring. A chart needs at most one point for each second. A lane could therefore
  conflate the live path for such a consumer to one tick for each datum in every
  100 milliseconds and lose nothing the chart shows. That cuts the fan-out from tens of
  thousands of ticks each second to a few for each datum. The conflation interval
  becomes a setting for each class of consumer.
- *The subject is scoped to a party.* The live publish must still go to one subject
  for each binding. Its cost is small compared with a commit, because core NATS
  carries it without an acknowledgement. The cost grows with the number of parties
  that watch a source.
- *Hedgr seeds a chart from the store.* On open, on reconnect and on a manual
  refresh it asks for the newest 2,000 points of a series. A window of recent ticks
  held in each lane would serve this read from memory. This is one more reason to
  keep such a window.
- *One difference needs a decision.* The ring of Hedgr drops the newest bucket when
  it is full. The freshness rule says to overwrite the oldest. The two rules differ
  only when the frame loop stalls, but they should agree.

** How tick systems are built in practice

Tick processing is an old problem, and the industry has settled on a small number of
shapes. This section lists them. The sources are linked where this session read
them. Claims that come from a vendor are marked as such.

*** The tickerplant, the real-time store and the history store

The shape that many trading firms use comes from kdb+. A feed handler captures the
raw feed. A tickerplant receives each update, writes it to a log file, and publishes
it to subscribers. A real-time database subscribes, holds the current day in memory,
and answers intraday queries. At the end of the day it writes its data to a
historical database that is partitioned by date. The
[[https://code.kx.com/q/architecture/][KX architecture guide]] and the
[[https://code.kx.com/q/kb/kdb-tick/][kdb+tick page]] describe the parts. The log is
the recovery source: a restarted real-time database replays it.

Two details matter here. First, the tickerplant can run in zero-latency mode or
publish in batches on a timer. The KX guidance says that a subscriber that only plots
graphs needs an update every few seconds, so a chained tickerplant serves slow
subscribers. That is conflation by another name. Second, the split between a
real-time tier in memory and a history tier on disk is the norm. A chart of the
last few minutes reads memory. It does not query the history store.

*** Conflated feeds

Exchanges and vendors sell the same idea as a product. The CME MDP 3.0 conflated
feed sends only the most recent update of each instrument, which cuts the bandwidth
and the work of the consumer. See the
[[https://b2bits.atlassian.net/wiki/spaces/B2BITS/pages/286294017/Java+TCP+Handler+for+CME+MDP+3.0+Conflated+Feed][description of a handler for it]].
A patent that came up in the same search notes the limit: some data conflates well,
such as the current price, and some does not, such as a trade cancellation.
This pipeline carries observed values, so it can conflate them. A trade or an event
needs a lane that does not conflate.

Chronicle sells a ring buffer in two forms: one that delivers every message in order,
and one that conflates to the newest value for a reader that wants only that. It
claims under 200 nanoseconds at the 99.9th percentile for the conflating form. That
is a vendor figure on one machine, so treat it as indicative. See the
[[https://chronicle.software/ring-buffer][Chronicle page]].

*** In-process hand-off

Low-latency trading systems pass messages between threads on a ring buffer. The LMAX
Disruptor, Aeron with its ring-buffer adaptors, and Chronicle Queue are the common
tools. They exist for nanosecond hand-off. This pipeline needs a millisecond commit, so
it takes the pattern and not the tools.

*** Time-series databases

A database that is built for ticks ingests in batches and makes the commit interval an
explicit setting.

- *QuestDB* writes through a write-ahead log and takes data over its line protocol.
  Its out-of-order handling holds rows in memory and commits after a lag. The
  [[https://questdb.com/docs/guides/out-of-order-commit-lag][commit lag guide]]
  calls the setting a trade between throughput and the time until data is readable.
  A forum answer in the same results says the cost sits mostly in the commit and not
  in the number of rows. The lane cycle makes the same trade, and it sets the lag
  from the measured lag of the lane.
- *ClickHouse* wants
  [[https://clickhouse.com/docs/concepts/best-practices/selecting-an-insert-strategy.md][inserts of 10,000 to 100,000 rows]],
  about one each second. When clients cannot batch, its
  [[https://clickhouse.com/docs/concepts/features/operations/insert/asyncinserts][asynchronous inserts]]
  batch in the server and accept a loss on a crash.
- *TimescaleDB* groups rows by chunk and writes each chunk in one transaction. It
  recommends =COPY= for bulk loads. See the
  [[https://www.tigerdata.com/docs/build/data-management/write-data/insert][insert documentation]].

All three say one thing: never commit once for each tick.

*** Streams with a compacted topic

Kafka offers log compaction, which keeps the last record of each key. A common
design puts ticks on a Kafka topic and loads a column store from it, for example
through the ClickHouse Kafka table engine and a materialized view. It fits a system
that must replay. It adds a broker, and a consumer that falls behind reads old
records first, which is the behaviour this pipeline avoids.

*** The last value for a late joiner

A consumer that starts late needs the current value at once. The kdb+ real-time
database serves it from memory. A compacted topic serves it as the last record of a
key. A JetStream stream with one message for each subject serves it here. A lane could
serve it from its own memory instead, which removes the stream.

** Where the proposal follows practice and where it departs

It follows practice in these points.

- It has a receive stage, a fan-out to live consumers, and a store writer, which is the
  tickerplant, the real-time store and the history writer in the kdb+ shape.
- A lane that conflates for its live consumers is a chained tickerplant.
- Writes to the store are batched with an explicit commit interval, as in QuestDB,
  ClickHouse and TimescaleDB.
- The store has no change signal for each row, because none of these systems has one.

It departs from practice in two points, and both follow from the requirements.

- *No replay log.* A tickerplant logs every tick so that a restart can replay it.
  This pipeline keeps no log, because a replayed tick is a stale tick. A restart
  resumes at the newest tick.
- *Age-based shedding.* A tickerplant keeps every tick and lets a slow subscriber
  fall behind. This pipeline drops old ticks and keeps the newest.

One idea from practice is not yet in the design. A real-time tier in memory would hold
the recent ticks of each datum, for example the last few minutes, in the lane. A chart
would seed itself from that window, and a late joiner would read the last value from
it. The history store would then serve only older data. This is the largest open
choice, and it is listed below.

** Prior art

- *The LMAX Disruptor* (Thompson, Farley and others, 2011). A ring buffer with
  slots allocated once, sequence numbers, one writer for each ring, and a consumer
  that takes every available event as a batch. It avoids locks and queue
  contention. This pipeline takes four ideas from it: the bounded ring, the
  pre-allocated slots, the single writer, and batching without a timer. It does not
  take the library, the busy-spin wait strategies or the graph of consumers. The
  cost here is milliseconds for a commit and not nanoseconds for a hand-off, so a
  plain mutex and a condition variable are enough for the receive side.
- *The single writer principle* (Martin Thompson, "Mechanical Sympathy"). One thread
  owns each piece of mutable state. The lane follows it: one writer owns the ring
  and the connection of its lane.
- *Reactive libraries.* Reactive Streams libraries name the same drop-the-old idea
  =onBackpressureLatest=. A consumer that cannot keep up gets the newest item and not
  the oldest.

** Options set aside

- *A durable JetStream consumer as the buffer.* It makes the backlog visible, and it
  loses nothing at a restart. It also replays old ticks in order, and requirement 1
  forbids that. It fits data that must not be lost, such as trades. It does not
  fit a perishable tick.
- *Back-pressure that blocks the producer.* It protects every tick and makes the
  newest tick wait for the oldest. It breaks requirement 1.
- *A GPU.* The work waits for commits and locks and does little arithmetic. A GPU
  has nothing to speed up on this path.
- *A column store for the history now.* A column store takes more than a million
  rows each second. It is a large change, and a batched write to the present store
  may be enough. Measure first. The decision belongs to step 3 below.

** Delivery in three steps

Each step ends with a measurement. The test tool is the tick injector, which sends
a burst of ticks at a chosen rate and times the drain.

1. *Remove the per-row costs. No new structure.* Drop the notification trigger of the
   observation table, add a series cache and a multi-row insert, and stop waiting for
   acknowledgements on the live publish. Add the lag gauge. Acceptance: the burst drain rate is at least ten
   times the rate of today, and the lag gauge shows the lag of a loaded system.
2. *Lanes, the ring, the age gate and the overload states.* Acceptance: a burst of
   ten times the sustained rate leaves no backlog after the burst ends. The lag of
   the live path stays below the age limit at all times.
3. *Scale out.* Several lanes, each with its own connection. Tune the indexes and
   chunks. Decide on a column store for history. Acceptance: 30,000 ticks each second
   for ten minutes, with the lag of the store below 1 second at the 99th percentile.

** Open questions

- Does a stream that can carry a tick that the store dropped cause a problem for any
  consumer? This note accepts it. The stream is the live view, and the table is the
  record of what the pipeline wrote.
- What is the age limit for each asset class? Interest rate curves tick slowly,
  and FX spot ticks fast.
- Should the CRM bridge read from the conflated live path and not from the store path?
- Is the second row for each tick worth its cost at scale?
- Should the ring of Hedgr overwrite its oldest bucket when it is full, to follow the
  freshness rule?
- Should each lane keep a window of recent ticks in memory, as the real-time database
  of a kdb+ system does, so that charts and late joiners never read the store?
- Does any client need to learn that a series changed? If so, the signal belongs on
  the live tick stream, at most once each second for each series. A database
  notification is not the way.
- How many lanes does one server need, and how many connections can the database
  give them?
