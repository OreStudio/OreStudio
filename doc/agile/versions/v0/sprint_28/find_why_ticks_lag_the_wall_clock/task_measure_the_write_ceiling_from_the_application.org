* Result

The ingest can reach the target with a different writer and a different table. It cannot
with the writer and the table of today.

- The writer of today, =market_observation_repository::insert=, gives about 2,300 rows each
  second at any batch size above 5,000. =COPY= through =libpq= into a scratch copy of the same
  table with its insert trigger gives about 10,500, so the writer is a factor of about five.
  The same =COPY= without the trigger gives 46,000 to 54,000, so the trigger is another factor
  of about five. The append-only table gives about 185,000. The batch writer should use =COPY=
  and the trigger must go. PostgreSQL refuses =COPY FROM= on a table with row-level security,
  so =COPY= cannot write the table as built.
- A transaction of fewer than 1,000 rows loses most of that. A batch split across 100
  tenants gives transactions of 500 rows, and the rate falls to 63,000 on the append-only
  table and 16,000 on the observation shape. A row for each source keeps one large transaction.
- A table with 100 million rows in 61 chunks costs 6 to 25 percent of the rate of an empty
  table, from single runs. A row takes 178 bytes with its index, against 986 for the observation shape.
- Compression cannot be measured here. The server runs the Apache build of TimescaleDB that
  Debian packages, which refuses =compress_chunk=. The test did not try the policy jobs or
  =drop_chunks=. The retention plan needs two paths: policies on the Community edition, and a
  scheduled =drop_chunks= with bars on the Apache build. The deployment edition is a decision
  for the owner.

The benchmark is a hidden test, =repository_market_write_ceiling_tests.cpp= in the marketdata
core tests. It runs only when its tag is named, and it drops its scratch schema at the end.

Open: the row-level security policy on the append-only table, a real mix of series, and a disk
that is not shared.
