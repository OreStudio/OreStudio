This page documents a [[id:699A8D45-B67E-4D3E-9206-24FA17C51ADA][story]] in [[id:AC79A686-FBE5-49DE-AA4C-2C59250C3A93][Sprint 27]]. It captures the goal, current status, acceptance criteria, and the tasks that compose it.

* Goal

A read checks its read permission, unless the security documentation
allow-lists it by subject, with the reason it is open. A member then reads only
what a role they hold lets them read. Today the reverse is true: codegen makes a
read need authentication alone unless its model opts in, so almost every read
answers any signed-in member.

The story closes the gap and keeps it closed:

1. State the rule and the allow-list in
   [[id:804C7048-DBBF-4B39-8737-BFB4949884C4][Authorised reads]].
2. Guard the personal data in IAM at once, with the opt-in the models already
   have.
3. Make codegen guard every read by default. A model opts out only by naming
   its allow-list entry.
4. Seed the =:read= codes each person role and each service role uses, so that
   guarding a read does not lock anybody out of their work.
5. Add a check that fails when a read is open and not allow-listed.

* Root cause

=projects/ores.codegen/src/codegen/org_loader.py= decides which operations a
generated handler guards. A write names its =:write= or =:delete= code. A read
names none unless its model sets =:guard_reads: true=; the loader states this
as policy: "Without the flag a read needs authentication alone, which is the
estate's default." Four models set the flag. The =:read= codes are seeded for
most resources, so the permission exists and nothing checks it.

* Decisions

1. *Allowed means written down.* A read may answer every signed-in member only
   when [[id:804C7048-DBBF-4B39-8737-BFB4949884C4][Authorised reads]] lists its
   subject and the reason. Decided 2026-10-06.
2. *Personal data first.* Contact information, account parties and role
   requests are guarded with the opt-in that already exists, before the
   default changes, because they are the exposure that matters most.
3. *The default and the seeds ship together.* Guarding every read by default
   without the =:read= codes the roles use would lock members out of screens
   they use today, so the codegen task and the seed task land in one pull
   request.
4. *Explicit codes, composed through a Member role; no read wildcards.* A
   wildcard such as =refdata::*:read= grants resources that do not exist yet,
   so a sensitive entity added later would be readable by every person role
   without anybody deciding it. Reads are granted one code at a time, and the
   reads every person needs are held by one stored role, =Member=, that every
   person account holds. Job roles add only their own codes. A person without
   Member sees empty screens, which fails closed. Decided 2026-10-06.
5. *Classify a read before granting it.* Vocabulary (currencies, calendars,
   day counts, the status and type lookups) may go in Member. A business fact
   (parties, counterparties, books, business units) or personal data goes only
   to the job roles that need it. Decided 2026-10-06.
6. *History is exactly as open as the entity.* A history provider registers
   with its entity's read code, and the history dispatcher checks it, so the
   per-component history subject is no side door.

** What

Every read must check its read permission, unless the security documentation
allow-lists the read by subject, with the reason it is open. Today most
generated read handlers check no permission, so any signed-in member reads the
entity. The fix has three parts:

1. State the rule and the allow-list in
   [[id:804C7048-DBBF-4B39-8737-BFB4949884C4][Authorised reads]].
2. Make codegen emit the read check by default, so a model must opt out to be
   open, and an opt-out names its allow-list entry.
3. Add a check that fails when a handler serves a read with no permission check
   and no allow-list entry, in the shape of =check_handler_permissions.py=.

** Why

Found live on 2026-10-06. =ashley.moore@acme_corporation=, who holds only
Viewer, ran =account_contact_informations list= and read 57 records. Each
record holds a street address, a postal code, a city, an email and a phone.

In =ores.iam=, 13 of the 17 handlers that serve reads check no read
permission. Only =account=, =login_info=, =session= and =tenant= check one.
The writes are guarded: puts and deletes check =:write= and =:delete=, and the
account party writes check =iam::accounts:update=. The =:read= codes are
already seeded in =iam_permissions_populate.sql=, so the check is missing, not
the permission.

| Open read | Exposure |
|-----------+----------|
| =account_contact_informations= | High: personal data |
| =account_parties= | Medium: who works in which party |
| =role_grant_requests=, =role_grant_request_roles= | Low to medium: who asked for which role (added by PR #2673) |
| =roles=, =permissions= | Low; =iam.v1.roles.permissions= and =iam.v1.roles.mine= are allow-listed, the lists are not |
| =account_statuses=, =account_types=, =tenant_statuses=, =tenant_types=, =seed_profiles=, =seed_profile_parameters=, =seed_profile_steps= | Low: lookups and configuration |

The same default holds in every component; see * Measurements.
