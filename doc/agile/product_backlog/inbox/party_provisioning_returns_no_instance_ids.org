#+title: Party provisioning returns no workflow instance ids
#+description: workflow.v1.parties.provision declares workflow_instance_ids in its response and the handler never fills the vector, so a caller cannot follow the workflow it just started.
#+type: capture
#+level: cross
#+filetags: :workflow:provisioning:defect:
#+created: 2026-09-27
#+updated: 2026-09-27

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

=workflow.v1.parties.provision= answers with a
=provision_parties_response= that declares =party_ids= and
=workflow_instance_ids=. The handler fills =party_ids= only. It publishes
one =start_workflow_message= per party and never learns the instance id the
engine creates, so =workflow_instance_ids= is always empty and the field's
own doc comment, "use these IDs to query status", is not true.

The fix is small, because the start message already takes the id. The
engine reuses a caller-provided =instance_id= when the request carries one,
and treats a repeated start as the same run. So the handler can generate
the id per party, put it in =start_msg.instance_id=, and push the same id
into =resp.workflow_instance_ids=.

* Why

A caller cannot follow the provisioning it just started. The journey's
progress step needs an instance id to read =workflow.v1.instances.steps=,
and the shell has to wait for the instance it started. The
[[id:9AB6C90E-5338-435A-9559-4E426D612EB6][New party]] journey records
this as a gap: the progress read exists, but the request does not hand
over the id to read with.

The correlation id is not a substitute. The instance carries one, but no
list filter is known to match on it, so a caller cannot find its run
without the id the response was supposed to carry.
