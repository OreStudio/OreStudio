#+title: A first schedule
#+description: A first schedule end to end: a job definition with a cron expression, the firing it produces, and the notification its action publishes.
#+type: knowledge
#+level: cross
#+filetags: :knowledge:architecture:scheduling:
#+created: 2026-09-28
#+updated: 2026-09-28

The smallest useful schedule has three parts: a name, a cron expression,
and an action. This page follows one such job from registration to
notification, and it uses no other component: the job publishes a message
every minute on a subject with no subscriber. The pages after it describe
each part in detail; this page describes the whole path first.

* Detail

** The three parts of a job

A job definition stores a name, a cron expression, an action type and its
payload. The name is unique within the tenant. The cron expression
defines when the job runs. The action defines what the firing performs
and holds the payload it needs. The definition also stores the tenant and
party the job runs for, and an active flag.

The example job is the smallest job with an observable effect.

| part            | the example's value                     |
|-----------------+-----------------------------------------|
| job name        | =example.heartbeat=                     |
| expression      | =* * * * *=, every minute               |
| action type     | =nats_publish=, a published message     |
| action payload  | the subject =example.heartbeat.tick=    |
| active          | yes                                     |
| tenant          | the tenant that registered it           |
| party           | none                                    |

** Registration

Registration writes the job definition through
=scheduler.v1.job_definitions.put=. The name is the natural key, so
registering the same name again updates that job instead of inserting a
second one, and a caller can register repeatedly without creating
duplicate schedules. An inactive job keeps its row and its execution
history, and a job may have no tenant, which is how the system's jobs are
stored. [[id:74597EAF-C5EB-4750-87D2-9B1DF46FEBED][The job
definition]] defines the write path, the precondition every write
carries, and the versions a write creates.

No execution has happened yet. The job runs at the next occurrence its
expression defines, not at the moment of registration.

** The firing and the notification

The job's next occurrence arrives, the loop wakes, and the job is due.

The scheduler writes the firing, then publishes the message on
=example.heartbeat.tick=. No component subscribes to that subject, so the
scheduler reads no reply and the firing completes when the publish
returns. The message is the notification, and the subscriber may be a
console, another component, or a tool written for the test. The scheduler
neither knows nor records which it is.

** The record the example produces

The firing was written before the publish, so a publish that failed would
still have a row with its error. The execution list shows the firing with
the job's name and action type; the live status shows the expression, the
active flag, the state of the last firing and the time of the next
occurrence. The firing record is the only state the example produces, and
it is how the example is verified when nothing was subscribed to the
subject.

** Why the example needs no other component

The publish succeeds whether or not a subscriber exists, so no receiver
has to be running for the firing to complete. That is why this is the
first example: the scheduler can be understood on its own. A reader does
not need any other component before reading the pages that follow.

Two cases are outside the example, and both belong to the boundary with
other components rather than to scheduling. The first is work that
outlives one action, which the job can start but not execute. The second
is an action whose result must be known, which turns the publish into a
request. Neither changes the expression, the firing or the record; only
the reach of the action differs.
