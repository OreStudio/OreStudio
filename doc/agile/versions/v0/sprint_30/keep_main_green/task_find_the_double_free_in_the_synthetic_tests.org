* Notes

What is known, so the next session starts where this one stopped.

The gcc release nightly aborts in =ores.synthetic.service.tests= with
=free(): double free detected in tcache 2=, inside
=feed_config_calibrate_writes_only_with_the_write_permissions=
(=feed_config_handler_tests.cpp=). It did the same on 25 and 26 November, so it
is deterministic under gcc.

Clang cannot reproduce it: fifteen runs of =[feed_config_handler]=, three runs
of =[feed_config_handler],[integration]=, the single case, and the single case
under valgrind with the service fleet up all pass. The live market-data service
is not the difference, because the case is clean with it answering.

The tree to work in is =build/output/linux-gcc-release-ninja=, built by the
gcc preset. Run the suite with the environment loaded:

#+begin_src sh
set -a && . ./.env && set +a
build/output/linux-gcc-release-ninja/publish/bin/ores.synthetic.service.tests
#+end_src

Then, in order: run it whole, since the corruption may be planted by an
earlier case; run it under valgrind with the project suppressions, which
reports an invalid free with a stack even where glibc only reports the
double free; and if valgrind is still quiet, take the abort's backtrace from
a core or from =catchsegv=.

A glibc double free inside a process is not caused by another process, so
the answer is in this binary, and the repair belongs in the handler or the
client it calls, not in the test.
