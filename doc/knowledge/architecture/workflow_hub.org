#+title: Workflows
#+description: Structure note for the workflow cluster: the definition that declares the steps, the step protocol, the instance and step states, failure and retry, idempotency, waiting and deadlines, and how provisioning is described as a plan of operations.
#+type: knowledge
#+level: cross
#+filetags: :knowledge:architecture:workflow:structure_note:
#+created: 2026-09-28
#+updated: 2026-09-28

A workflow is how this platform does work that outlives a request: the caller is
answered with an instance id, and a service drives an ordered list of steps,
recording each one's outcome. The state lives with the platform and any client
can read it, which is why a journey can be closed and reopened and why the
browser and the shell can drive the same run. Read the cluster in the order
below: how a definition declares its steps, the contract a step must honour,
the states a run moves through, what happens when a step fails, how a step
avoids doing its work twice, and how a step waits for work that takes minutes.
The last note is the one most readers came for: how tenant provisioning is
described as a plan of operations.

* Reading order

** The pages for individual workflows

[[id:645A06C7-D9D5-4ED1-969B-B6366D122BC9][Workflow pages]] — the inventory of
the per-workflow pages, under
[[proj:doc/knowledge/workflows][=doc/knowledge/workflows/=]]. Each one is the durable
contract for one named process: its purpose, participants, messages, steps,
failure policy and progress read. Read a page there when the question is /what
does this workflow do/; read the notes below when the question is /how does the
engine run any workflow at all/.

** The definition that declares the steps

[[id:FF8BAB73-9A76-4B23-87F5-59D1BE1A2877][The workflow definition]] —
start here. What a definition declares, where it lives, how one is added or
changed, and what protects a run that is already in progress: the step list is
resolved once at start and persisted, so a deployment cannot reshape a run.
Read it before adding a workflow or changing the steps of one.

** The protocol a step honours

[[id:247E1FE4-A00C-42D1-A6BA-831BC22C8078][The step protocol]] —
start here. What a caller sends, what a definition declares, how a step is
dispatched, what a handler reports to complete it, and what a later step may
read from the steps before it. Everything else in the cluster follows from this
protocol, so the identifiers a step carries and the completion it reports are
worth slowing down on.

[[id:D0CD9449-ED47-4651-9381-FDD726773EA7][The life of a step]] — the same protocol as
a sequence diagram and a flowchart, from the caller's request to the finished
run.

** The states a run moves through

[[id:2C59492F-B715-4195-8FC7-761CE5515449][The workflow instance and step states]] —
the machine a run and its steps must honour: the states, which are initial and
which terminal, and what each transition means. Read it before changing either
machine, because a state carries a promise to every reader of a run.

** When a step fails

[[id:353DC9B3-65BC-4801-B6D8-08ADD2647F24][Failure, compensation and retry]] — the
failure policy as the definition's own choice, with stop-and-retry as
provisioning's: what a stopped run leaves behind, what a retry resumes from, and
why the steps that completed are kept.

[[id:183361A9-31B8-4066-A13D-94CA35270F42][Idempotency in a workflow step]] — why a step
can be re-published at all, and the two forms of safety a step may rely on: an
identity that makes a repeat the same step, and a write that converges on
repetition.

** How a run starts at a stated time

[[id:DFC57D4F-9AB2-4428-BDEC-BF44D106A75D][Scheduler]]. Read it when the question is
where a run comes from at a stated time. The structure note for the

[[id:13105F27-9C05-495E-B9A0-2EFC9B5AC811][Scheduling and workflows]]. Read it
