#+title: A primary-key column never takes its default
#+description: The domain template emits a primary-key column as 'type name;' with no initialiser, while every other column carries the ':default_value:' guard. So the one column where an unset value is most likely, and most damaging, is the one that cannot default: a missed assignment reads an indeterminate int instead of failing a constraint. Found while giving a new key column a default of zero.

* What

Carry the =:default_value:= guard into the primary-key branch of the domain
template, so a key column can state an initialiser like every other column can.

* Why

=cpp_domain_type_class.hpp.mustache= emits the two shapes differently:

#+begin_src text
{{#primary_key.columns}}
    {{{cpp_type}}} {{column}};                                       <- no initialiser
{{/primary_key.columns}}
{{#natural_keys}}
    {{{cpp_type}}} {{column}}{{#default_value}} = {{{default_value}}}{{/default_value}};
{{/natural_keys}}
#+end_src

So =:default_value: 0= on a primary-key column is silently ignored. Every
precedent that works — =credit_simulation_config.seed=, =bond_formula_based_leg_data.fixing_days=
— is a non-key column.

The consequence is the opposite of what a key needs. An ordinal in a composite
key is the field a writer is most likely to forget, because it is metadata about
the row rather than data from the document; with no initialiser the forgotten
value is an indeterminate =int=, so the failure is undefined rather than the
constraint's refusal.

Found while giving =instrument_strikes.sequence_number= a default of zero. The
model gained the property, regeneration ignored it, and the member stayed bare.
Changing this affects every generated key in every component, so it wants its
own unit and a regeneration sweep.
