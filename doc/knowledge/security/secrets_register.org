* Summary

This page lists every secret the workspace holds today, the component that
consumes it, and whether it moves to =ores.vault=, in which phase. The rule
that decides an entry is stated in [[id:F9F1A2BA-94C2-4DAA-8689-F0871AA56801][Secret
Custody in the Vault]]: a value that ORE must present to another party is
custody, and a value that ORE only compares is not. Of the twenty-nine
secret-bearing values in the environment file, twenty-four move to the vault,
two belong to the test suite, one is a person's demonstration login that should
not be shared at all, and two are development keys that become per-checkout files. No
vendor credential is set in this environment; the class is registered so that
the first one has a home.

* Detail

** How to read an entry

| Field | Meaning |
|-------+---------|
| What | The value, and the name it is known by today |
| Today | Where it is written, and how it is made |
| Consumer | The component that must hold it, and when |
| Decision | Vault, out of scope, or delete, with the reason |
| Phase | The migration phase that acts on it |

The phases are cumulative, and each one ends in a state the tree can run in.

** E1. The database role passwords

| What | Twenty-five values: eighteen service passwords, the tick writer's, four administrative role passwords and two for the test suite |
| Today | The environment file, through the =secret= kind of [[proj:compass/checks/env_format.org][the environment format]], which makes a random value once and keeps it |
| Consumer | Each service at start, to open its connection pool; the administrative roles through compass; the test suite through its own two |
| Decision | Sixteen move to the vault, and each service resolves its own at start. Two do not: the vault's, because it would have to answer its own request, and IAM's, because IAM has to exist before the vault does — those two are placed as credential files. The tick writer's, the four administrative ones and the gateway's stay in the file, because they are the deployment's own accounts and no service resolves for them. The two test passwords stay: a test fixture must create its own database without a service in front of it, and the value protects nothing that outlives the run |
| Phase | 2, done |

** E2. The IAM signing key

| What | =ORES_IAM_SERVICE_JWT_PRIVATE_KEY=, the RSA private key IAM signs tokens with |
| Today | The environment file, through the =file= kind, which puts a file's lines on one quoted line; the file is =build/keys/iam-rsa-private.pem= |
| Consumer | =ores.iam.service=, which mints a token for every sign-in and every service-to-service call; the public half is published and is not a secret |
| Decision | A credential file, and the reason is the boot order rather than a preference. A signing key is the textbook recoverable secret — a copy of it forges every token in the deployment — so the vault is where it belongs. But IAM cannot ask: the vault fetches the keys that verify tokens from IAM before it subscribes, so IAM starts first, and a process that has not started cannot resolve. IAM's signing key therefore keeps the file it has today — =build/keys/iam-rsa-private.pem=, which the unit re-exports at start, so the value never enters the environment file. The public half stays published, which is what lets every other service verify a token without asking IAM |
| Phase | 2, closed as an exception |

** E3. The vendor source credentials

| What | =ORES_MARKETDATA_<VENDOR>_API_KEY=, =_USER= and =_PASSWORD=, the credentials ORE presents to a public market data source |
| Today | The environment file, through the =carried= kind, which keeps every matching variable the file already has. *This environment sets none of them*; the class exists and is empty |
| Consumer | The market data adapters, at the moment they open a session with the vendor: runtime, and on demand rather than at start |
| Decision | The vault, when a source is first configured. These are the API keys the workspace is most likely to acquire next, and the reason the register states the class before it has a member |
| Phase | 3 |

** E4. The provider client secrets

| What | The client secret of each identity provider a tenant enables, starting with the Google client |
| Today | Nowhere. The value was removed from the environment file on 2026-11-26 rather than kept until a store existed, so the Google token exchange cannot succeed until this entry is populated |
| Consumer | The gateway's external sign-in routes, at the token exchange, which is runtime: a person signs in at any time, so the value cannot be read once at start |
| Decision | The vault, and it is the first customer. It is the only entry a third party can revoke, and the only one whose loss is visible to a person outside the deployment. It waits on the token exchange itself, which the external-identity story builds: the =client_secret_ref= column already names a lookup, and it names a vault entry once the exchange asks for one. The gateway's own bootstrap is settled by [[id:5FADF948-4520-41D3-B4F0-BE4873C06AF0][secure introduction]] like every other consumer's |
| Phase | 1, waiting |

** E5. The development TLS keys

| What | =ORES_NATS_TLS_KEY=, the shared client key, and =ORES_SHELL_NATS_TLS_KEY=, the shell's copy of it |
| Today | The environment file *names* the key's path, not its value: ={nats_tls_key}= is a path, and the key itself is a per-checkout file under =build/keys/nats= with mode 0600. The earlier state this row described, a private key written into the file, no longer exists |
| Consumer | The shell, and a worktree that runs a client without a staged certificate. A deployed service does *not* use them: it presents its own leaf, issued per service and rotated every ninety days ([[id:18D8CB4F-E926-49E8-83C3-7C8418861B33][NATS certificates]]) |
| Decision | Out of vault custody, and out of the environment file. A TLS library reads a key from a file, and a leaf rotates on a schedule the certificate tool owns. Done: the shell presents its own leaf, =ores.shell.crt=, beside every service's, and the file carries the mode the deployed leaves carry |
| Phase | 3 — done |

** E6. The demonstration login

| What | =ORES_SHELL_LOGIN_PASSWORD=, the well-known password of the seeded =tenant_admin= account |
| Today | The environment file, through the =value= kind, whose own row states that the value is "well known, not a secret" |
| Consumer | =compass shell=, which offered it as a default, and =compass notify=, which raised as that account |
| Decision | Delete from the shared file. It is a person's credential, it is the same for every checkout, and a shared default is the habit the vault exists to end. A developer keeps it in their own configuration or types it |
| Phase | 0 — done, environment format version 38 |

** E7. The verify-only credentials

| What | The password hashes in the account credential table, and the =SHA-256= hash of each agent key's secret |
| Today | IAM's tables. The agent key stores only the hash of 256 random bits, and the key itself is shown once and never written |
| Consumer | IAM, which compares an offered value with the stored one |
| Decision | Out of scope, permanently. Recovery is neither possible nor wanted, and custody of a value ORE must never hand back would be custody without a purpose |
| Phase | — |

** E8. The vault's own bootstrap material

| What | The key encryption key, the vault's transport key pair, and the transport key pair of each consumer |
| Today | Nothing exists yet. The entry is here so that the register accounts for the secrets the migration creates, and not only the ones it removes |
| Consumer | The vault's unit, and each consumer's unit, through a system credential |
| Decision | Out of scope by necessity: a vault cannot hold the key that opens it, and a consumer must reach its own key before it can speak to the vault. These are provisioned as system credentials by the deployment, and a copy of one is as good as the holder it was issued to |
| Phase | 1 |

** The phases

*Phase 0 — remove what is not a secret.* E6 leaves the environment file.
Nothing else changes, and nothing depends on it. Done on 2026-11-27 as
environment format version 38: the generator no longer writes the password,
=compass shell= and =compass notify= read it from the process environment, and
the username stays because it is not a secret.

*Phase 1 — the vault, and its first customer.* The component exists with its two
entities, five operations and the sealed delivery of [[id:4F28F755-7DA1-4EDD-9983-256622B6088A][Sealed
Delivery of a Secret to Its Consumer]]. E4 moves: the gateway resolves a
provider's client secret at the token exchange, and the provider's registry row
carries a reference where it used to carry the name of an environment
variable. The vault's own database password and NATS credential come from its
credential files, because it is the one process that cannot ask itself.

*Phase 2 — the service credentials.* E1 and E2 move. This is the phase that
changes how the environment file is generated: a =secret= row stops writing a
value into the file and names the vault entry instead, and the deployment gains
two =LoadCredential= entries per unit — the consumer's own private key, and the
vault's transport public key the answer is sealed to. The second is needed
because the read that publishes that key requires the session the exchange
exists to make possible, and a public key is not a secret, so placing it costs
one more entry and saves a call the workload cannot make. Each service resolves
its database password before it opens a pool.

As of environment format version 39 this is done: the file names each service's
vault entry and carries no value for it, and =compass vault provision= invents
each password, sets it on the role, sets the hash IAM signs the service in with,
writes the verifier the pooler authenticates it with, and stores the value in the
vault — one act, so the four cannot disagree.

Two processes keep a credential file instead of a name, and the reason is the
boot order rather than a preference. The vault cannot answer its own request.
IAM cannot be asked before the vault either, because the vault fetches the keys
that verify tokens from IAM before it subscribes, so IAM has to exist before the
vault does and the vault has to exist before the services that resolve. The
order is therefore IAM, then the vault, then everything else, and IAM's password
stays a file for as long as that order holds. IAM's own signing key follows the
same reasoning.

*Phase 3 — the vendor credentials and the development artefacts.* E3 and E5.
E5 is done: the key is a per-checkout file and the file names its path.
E3 joins when a source is configured, resolving on demand rather than at start.
E5 becomes a file per checkout with the mode the deployed leaves already carry.

The order of a cold start follows the phases and does not change between them:
the database first, then the vault with its own credentials, then the services
that resolve at start, then the services that resolve on demand. A service
resolving at start does it by
[[id:4D069D1A-EADA-407B-89B4-92F2375C0836][Secure Introduction]], which is what
lets it reach the vault before it holds a token.

** What the migration cannot do

A vault cannot resolve its own secrets, so its own credentials stay files, and
so does anything a library insists on reading from a path. That is an exception
with a boundary, not a gap.

A lost key encryption key loses every secret it protected. The ciphertext stays
in the database and stays unreadable, which is the correct behaviour and an
operational requirement at once: the key needs a backup that is not stored
beside the database it protects, and the procedure that restores it needs
writing before the first secret is written rather than after.
