This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A system administrator keeps the installation's market data feeds running: the bindings it holds, whether each source is running and when it last ticked, and how to start or stop one.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want every market data feed this installation runs to be up, and to know the
moment one goes quiet." The journey is done when each feed binding is shown
with its source, the series its ticks land in, whether it is enabled, whether
the feed is running and when it last ticked, and the operator has started or
stopped what needed it.

* Actor and trigger

The actor is the system administrator: an account with the =SuperAdmin= role,
acting from the system tenant in system administration mode, as the
[[id:5E970C7F-68EA-42BF-B73E-997C4A003762][Operations journeys]] group sets
out. Changing a binding needs =marketdata::feed_bindings:write= or
=marketdata::feed_bindings:delete=; starting and stopping a feed needs the
synthetic and market data permissions the producer services hold. The trigger
is a service restart, a feed the desk says is silent, a new source to bring up,
or a routine check. The journey starts at *Operations*, then *Market data
feeds*, and ends when the operator leaves the screen.

Two facts shape the screen. A binding is stored and versioned; the running set
is live and not stored. And a binding names a producer source, not a series:
the series a source writes is resolved per tick from the datum's =oresmd_uri=.
The screen must therefore join a stored row to a live set, and infer the series
from what has been written; see /What is missing/.

* Steps

1. *List the feed bindings.* The person opens *Operations* and then *Market
   data feeds*. The system lists the bindings the installation holds: the
   source name, the owning party, the workspace, whether it is enabled, and the
   row's version and who last changed it.
2. *Read one binding.* The person selects a row. The system shows the binding's
   fields and its versions, so the person can see when it was enabled or
   disabled, and by whom.
3. *Read the feed behind the source.* The person opens the producer
   configuration whose =source_name= matches the binding. The system shows the
   generation config: the source name, the folder it sits under, the enabled
   and auto-start flags, the tick rate, and, for an IR curve, the currency,
   index family and tenor. Today only the FX configurations list; see /What is
   missing/.
4. *Read whether the source is running.* The person asks the installation which
   feeds are running. The system lists the running source names, every kind.
   This is the live set the producer factory holds, not the stored bindings.
5. *Read the last tick.* The person reads when each source last ticked. The
   ingest loop counts the ticks and remembers the last one per binding, but only
   in memory, and no read exposes them; see /What is missing/.
6. *Start a feed.* The person chooses *Start*, on one binding or on a folder
   subtree. The system resolves the folder subtree, starts every feed under it,
   of every kind, and reports the counts: started, already running and skipped,
   with a per-kind breakdown. The subject exists; the web client does not call
   it today; see /What is missing/.
7. *Stop a feed.* The person chooses *Stop*, on one binding or on a folder
   subtree. The system stops every running feed under it and reports how many
   stopped, by kind.
8. *Enable or disable a binding.* The person changes the enabled flag and states
   a change reason. The system writes the binding against the version it read.
   Disabling suspends ingestion without deleting the binding; it does not stop
   the producer, so the running set and the binding can disagree.
9. *See a feed that has gone quiet.* The person sorts the rows by last tick and
   reads the ones that have not ticked within the interval their tick rate
   implies. The screen needs the last-tick read from step 5 and the tick rate
   from step 3; see /What is missing/.
10. *Leave.* The person goes back to the *Operations* area.

Start and stop act on the running service, not on stored rows, and the running
set is not stored, so the effect is visible in the reply and a later visit
re-reads it from the service.

* Screens and wireframes

One screen. The binding table and its summary sit at the top, the selected
binding and the producer behind it sit in the middle, the folder control with
its start and stop buttons sits under them, and the binding's versions sit at
the bottom, so the person reads what is held, then what is behind it, then what
can be done to it.

The binding and the producer configurations are versioned, so each has a
history. The running set is not an entity: it lives in the producer factory and
in the ingest loop, and it is gone after a restart. The series is the one
identity a tick carries, so the screen reads the series from the observations
rather than from the binding.

The list of running sources is =synthetic.v1.feed_configs.list=, which returns
the running =source_name= values of every kind. The one-feed start and stop are
keyed by a config id, which the server resolves to the config's =source_name=;
the folder start and stop take a folder id and resolve the whole subtree
server-side. The last-tick read does not exist; the ingest loop keeps its
counters in memory and writes them to the status log once a minute; see
/What is missing/.

* What is missing

1. *No last-tick read.* The ingest loop keeps a tick count and the last tick
   time per binding in memory, and the status log writes them once a minute,
   but no subject returns them, and nothing stores them. The candidate is a read
   over the ingest loop's statistics, or a stored last-observation time per
   binding. Until then the screen shows whether a source is running, and it
   takes the newest observation of the series the source writes as the nearest
   thing to a last tick; it cannot answer for a source directly.
2. *No stored source-to-series mapping.* A feed binding names a source, a party
   and a workspace; it does not name the series its ticks land in, because the
   series is resolved per tick from the datum's =oresmd_uri=. The row cannot say
   which series a source writes without reading the observations. The candidate
   is a series reference on the binding, or a read that resolves a source to the
   series it has written. Until then the screen shows the series of the source's
   most recent observations and says the mapping is inferred.
3. *The IR producer configurations cannot be listed.*
   =synthetic.v1.fx_spot_generation_configs= has list, get and put, but
   =synthetic.v1.ir_curve_generation_configs= has only get and put, and its key
   is a config id, so the IR feeds cannot be enumerated. The candidate is a list
   subject for the IR generation configs. Until then the IR rows appear only
   when the screen already knows a config id, and the folder tree stands in for
   the enumeration.
4. *Start and stop are shell-only, and carry no permission of their own.* The
   subjects exist and the shell reaches them, through =synthetic start
   folder|feed=, =synthetic stop folder|feed= and =synthetic list feeds=, but
   no web operation calls them. The permission catalogue names permissions for
   the producer configs and the feed bindings and none for the start and stop
   subjects, so what gates them is not stated. The candidate is the web
   operation and a permission for each act. Until then the screen is read-only
   and points the operator at the shell.
5. *No silence threshold and no alert.* Nothing states how long a feed may be
   quiet, and nothing raises a notification when it goes quiet. The producer
   configs carry a tick rate, =ticks_per_hour=, but nothing compares it with a
   last tick. The candidate is a threshold on the binding or the config, and a
   notification kind for a quiet feed. Until then the screen sorts by last tick
   and the person judges.
6. *No feed status history.* A binding has versions, so a change to the enabled
   flag is recorded, but nothing records when a feed started, stopped or went
   quiet, so the operator cannot read a feed's uptime. The candidate is a
   start-and-stop event with an actor and a time, or a status sample. Until then
   the screen shows the current state only.
7. *Enabled and running are different things.* A binding's enabled flag governs
   ingestion; the producer runs or not independently, and the running set is not
   stored. No read returns a binding's running state, so the screen joins the
   stored binding to the live running set on the source name string, and the two
   can disagree. The candidate is a single stored field that says a feed is up,
   or a read that returns both together. Until then the screen shows both and
   says what each one means.
