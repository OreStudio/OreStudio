* Acceptance

- The single-instant read answers on the same object definition as the slice read
  and the evolution read.
- The three reads agree on the object and on its nodes.
- A test shows the three answers for one object are consistent.

* Plan

1. Move the node grid out of the evolution reader into =series_grid= beside the
   shape, so every read that returns nodes takes them from one place. The slice
   reader takes =coordinate_of= from there too.
2. Add =service::series_snapshot_reader=. It resolves the typed identity, reads
   the shape, builds the grid and places each as-of point at its node.
3. Change =get_curve_snapshot_request= to carry the typed identity and the
   response to carry the axes, the nodes, a value and a record time per node,
   and the staleness figures. The header and its TypeScript twin generate from
   =ores.marketdata.operations.org=, so the change is made in the model.
4. Make =curve_snapshot_handler= a thin wrapper, as the evolution handler is.
5. Test the reader, including a test that the snapshot and the evolution agree.

Decision: the snapshot keeps the as-of read. It carries the latest value of a
node forward from before the instant, and the evolution states only what an
instant states. The three reads agree on the object and on its nodes. They do
not agree on a value the evolution holds as a hole, and that difference is the
meaning of the two reads, not drift.

* Result

The single-instant read now answers on the object definition the slice and the
evolution reads use.

- =get_curve_snapshot_request= takes the typed identity, not an =oresmd_uri=.
  The response states the axis names and the declared nodes once, then one value
  and one record time per node, with the staleness figures as before.
- =series_grid= in =series_shape= builds the nodes and places a point at its
  node. The snapshot and the evolution both use it, so they cannot disagree about
  the nodes. The slice reader shares =coordinate_of=.
- =series_snapshot_reader= holds the read, and =curve_snapshot_handler= is a thin
  wrapper, as the evolution handler is.
- An object that declares no axis is refused, as it is for the other two reads.
- The header and its TypeScript twin are regenerated from the operations model.

A test shows that a snapshot and an evolution for one object give the same axes
and nodes, and the same value wherever the evolution states one. The snapshot
may hold a value where the evolution holds a hole, because it carries the latest
value forward and the evolution states only what an instant states.
