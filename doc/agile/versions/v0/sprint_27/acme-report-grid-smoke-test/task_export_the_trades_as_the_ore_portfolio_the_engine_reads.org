* Relationship to the redesign

This task is the near-term unblock: it maps the trades blob the run gathers
*today* so ORE proceeds past "Build Portfolio". The shape of that blob is
about to change — [[id:004B0E88-1BB6-4323-A579-EEB56C29BA3F][Gather a run's inputs by declared dependency]] replaces the
one export with a trade set's archive at an as-of, and gives the mapping its own
task there ([[id:18FFC5F4-6DEB-4E7F-B0C5-ECC359ED5A82][Map a book's archive into the ORE portfolio]]).

Whichever lands first, the same thing is built underneath both: the reverse of
=trade_mapper= and of the instrument mappers. Build that once. If the redesign
lands first, this task dissolves into it and should be abandoned rather than
carried.

* Acceptance

- The run's portfolio input is ORE-readable, placed at the path the run document
  names, exactly as the market data and the fixings now are.
- The engine proceeds past =Pricing: Build Portfolio= rather than failing with
  =Failed to run analytics PRICING,XVA=.
- Every trade the run gathered appears in the portfolio, carrying the instruments
  and envelopes the engine needs to price it.
- The reverse walk lives beside the forward one, so adding an instrument to the
  import mapper without its export counterpart fails a test rather than losing a
  trade silently. That is the property worth having: the two directions are one
  fact about one schema, and nothing today makes them move together.

* Plan

The chain today, and where it breaks. =gather_trades= asks
=trading.v1.ops.export_trades_to_storage= for the run's trades, which writes a
gzipped msgpack of =trade_export_item= rows. =prepare_ore_package= then downloads
that blob and writes it at a hardcoded =trades.msgpack=, so nothing ever puts a
portfolio where the run document says one is.

Two halves, and only the second is small.

*1. Placement.* =run_store.hpp= already declares =run_data_files::portfolio=, the
path the run document names, and =report_package_handler.cpp= already writes the
market data and the fixings at their declared paths. The trade branch is the odd
one out: it writes =trades.msgpack=. It changes to write the portfolio body at
=places.portfolio=, and to fail loudly when the run document names no portfolio,
as it already does for the fixings.

*2. The export mapper.* The gathered rows are =domain::trade_export_item=, which
carries instruments as an opaque payload with no shape a mapper can walk. So the
export walk is:

1. read the gathered rows and rebuild the types the import side's =trade_mapper=
   and instrument mappers take as input;
2. map them, producing an =ores::ore::domain::portfolio=;
3. render it with =save_data(const portfolio&)= from =domain.hpp= -- the same
   renderer the importer's inverse uses, so the XML matches what ORE expects by
   construction rather than by our transcription of the schema;
4. upload the rendered body as the run's portfolio input.

Where it lives: =ores.ore= owns the ORE schema and its mappers, so the export
walk belongs beside =trade_mapper= in =ores.ore.core/domain/=, not in the
reporting handler that calls it. The reporting chain asks for the portfolio; it
does not know how one is built.

*Risk.* The redesign (=18FFC5F4=) needs the same reverse walk against a trade
set's archive instead of the run's one blob. Building it once, as a function of
the rows rather than of where they came from, is what lets both callers share it
-- and is the reason this task does not special-case the current blob's shape.
