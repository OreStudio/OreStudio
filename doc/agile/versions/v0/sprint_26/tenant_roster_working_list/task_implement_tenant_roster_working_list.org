* Acceptance

- The roster searches over code, name and hostname, and pages with a total.
- The roster filters by tenant type and by status, and the See the tenants journey and its wireframe record both filters.
- Each row carries an actions menu: open the tenant, resume setup when its run is unfinished, and the retire or reset journey.
- Opening a tenant shows its details, its provisioning run and its parties, from a journey document written first.
- Every new behaviour is proved by a test, and each screen was read against the running deployment.

* Plan

1. *Search function.* =ores_iam_tenants_search_fn(search, type, status,
   limit, offset)= over the current tenant rows, excluding the system tenant,
   matching code, name and hostname with =ilike=, ordered by code, with the
   total from a window count.
2. *Operation model.* =ores.iam.tenant_roster_messages=, entity singular
   =tenant_roster= (the =tenants= shell menu belongs to the generated entity
   unit): =search_tenants_request= and =search_tenants_response=. The filters
   are in the request now, so the filters task adds a screen and no protocol.
3. *Handler.* A hand-written =tenant_roster_handler= that checks
   =iam::tenants:read= and calls the function, registered in iam's aggregate
   registrar, with a test.
4. *BFF.* =/api/tenants= reads through the search, passes =search=, =offset=
   and =limit=, and stops filtering the system tenant itself.
5. *Screen.* A search box that searches as the person types after a pause,
   previous and next paging, and the "Showing a-b of n" footer.
6. *Records.* A dated correction on
   [[id:18E4CA0F-0668-46F2-97D3-A5EF58522928][Show the tenants a deployment holds]].

* Result

- *The server searches.* =ores_iam_tenants_search_fn= answers one page of the
  tenants that match a search over code, name and hostname, a type filter and a
  status filter, in code order, each row carrying the total. It leaves the
  system tenant out, so the BFF no longer does. Four tests drive it; with the
  system rule removed from the function, the system-tenant test fails and the
  other three pass (checked).
- *The wire is generated.* =iam.v1.tenants.search= is declared in
  =ores.iam.tenant_roster_messages=, so its C++ header, its TypeScript twin, the
  =tenant_roster search= shell command and its recipe are generated. The
  handler checks =iam::tenants:read=. The filters are in the request already, so
  the filters task adds a screen and no protocol.
- *The BFF and the screen.* =/api/tenants= passes =search=, =offset= and
  =limit= through and refuses a page that is not a whole number. The roster has
  a search box that asks after a pause, previous and next paging that keeps the
  last page on screen, and a "Showing a-b of n tenants" footer; an empty
  deployment shows no search box, and a search with no match says so.
- *Checked live.* Through the BFF: no search answers 26 tenants, =cd_tenant_1=
  six, =GROUP= with a page of two at offset two the second page of four, and
  =system= none. The generated shell command answers on the fleet. The rendered
  page was not opened in a browser; its behaviour is covered by the web tests.
- *Recorded.* The task that built the roster carries a dated correction for the
  journey items its acceptance left out.
