#+title: The store never canonicalises the business day convention
#+description: ores.refdata.core's curve-configuration round trip asserts that the store keeps one code per business day convention, and nothing does it: stored_business_day_convention has one caller in the tree, the test. Also as_stored turns an absent convention into an empty string, which the round trip then reports as a lost value.

#+level: cross

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

The store keeps whichever business day convention spelling a document states,
so the same adjustment reaches the table as =F=, =Following= or =FOLLOWING=,
while =ores.refdata.core='s curve-configuration round trip expects one code.

* Why

=bc083d5498= states the invariant — "the mapping layer converts the stated
spelling to the code before a row is written, so the table holds one
representation" — and adds =stored_business_day_convention=, but never wires it
into the write path. Its only caller is the round-trip test, which therefore
asserts behaviour nothing implements.

Two assertions fail on =origin/main= and on branches that hold no codec work:

- =Example_63 ... CapFloorVolatilities.CapFloorVolatility[1]:
  BusinessDayConvention was lost=
- =Input/curveconfig.xml ... InflationCapFloorVolatilities
  .InflationCapFloorVolatility[0]: BusinessDayConvention: 'ModifiedFollowing'
  became 'MF'=

Both come from the test's own expectation, =as_stored= in
=curve_configuration_database_roundtrip_tests.cpp=:

1. It assigns the helper's =std::string= into an =std::optional<std::string>=
   member. For a row that states no convention the helper answers ="",= so the
   expectation gains an empty convention where the document states none. The
   store gives none back, and the comparison reads that as a lost value. Keeping
   the empty optional instead makes the case pass, which was verified by
   rebuilding the test that way.
2. It canonicalises a spelling the store never canonicalises. The document says
   =MF=, =as_stored= maps it to =ModifiedFollowing=, the database holds =MF=.
   The SQL value guard
   (=refdata_curve_configuration_columns_validate_create.sql=) only refuses a
   value outside the set; it never rewrites one.

* What to decide

Either the mapping layer canonicalises, which is what its commit says it does,
or the round trip stops expecting it and states that the table may hold every
spelling a document uses. The first keeps the invariant the SQL guard and the
grouped queries rely on; the second is honest about today's behaviour.
