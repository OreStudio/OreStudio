* Goal

Destroying an =ores::nats::service::subscription= must not return while the
dispatch thread is inside the handler that subscription carries. Once it does
return, the owner is free to destroy everything the handler reaches.

* Acceptance

- =~subscription= and move assignment drain, wait for that drain to complete,
  and only then free the closure and destroy the NATS subscription. The wait is
  bounded at 30s, the budget cnats itself uses for a drain.
- =subscription::drain()= keeps its promise: it returns after in-flight
  deliveries have been processed.
- =client::drain()= waits for the connection's closed callback instead of
  returning as soon as the drain was requested.
- A regression test holds a handler inside a delivery and asserts that
  destroying the subscription does not return until the handler is released.
- A fleet start and stop leaves 0 failed units.
- ctest passes.

* Plan

=subscription= destroyed the cnats subscription through an asynchronous drain:
it registered =natsSubscription_SetOnCompleteCB=, called
=natsSubscription_Drain=, and returned. The closure the handler runs through
was freed later, from the dispatch thread, which made destruction look safe to
the caller. It is not: the closure calls into the owner's state, and the owner
treats "the handle is gone" as "nothing will call me again".

=service_lifecycle::announce_ready_and_drain= owns that order. It calls
=nats.drain()=, logs "Shutdown complete", and returns; the coroutine's frame then
destroys the subscription vector, the event bus and the service state. The
marketdata ingest loop was destroyed in that window while a tick was in
=handle_tick=, and the dispatch thread walked into a freed rate engine.

Two changes, both at the seam the promise was made on:

1. =drain_and_release= replaces the async helpers. It drains, calls
   =natsSubscription_WaitForDrainCompletion=, then frees the closure and
   destroys the subscription. =~subscription= and move assignment both use it,
   and =subscription::drain()= waits the same way.
2. =client::drain()= registers a closed callback through
   =natsOptions_SetClosedCB= and waits on it, because =natsConnection_Drain=
   only starts the drain. The latch lives in =client::impl= so it outlives the
   connection, and every connect clears it.

No call site creates a subscription per request: =request_sync= uses
=natsConnection_RequestMsg=, so a blocking destruction touches only teardown and
subscriber churn, not the request path.

* Notes

The crash is intermittent: it needs a delivery in flight at the moment the
owner is destroyed. Two short start/stop cycles did not reproduce it, before or
after the fix, so the evidence for the defect is the recorded core dump and the
ordering above, not a repeatable trigger. What the fix changes is the ordering,
which is checkable by reading the two functions.

Two gates report this change while it is uncommitted, and neither report is
about the code: =format= wants clang-format on the edited files, and
=component-drift= fails on any =git diff= at all, because it regenerates the
components and reads the working tree's diff as drift. Both pass on a committed
tree.

A closed connection counts as drained. The first version of the wait treated
the =NATS_CONNECTION_CLOSED= that a teardown drain returns as a failure, so the
marketdata service leaked every subscription and logged an error at each stop,
and the fleet run showed it. Closing a connection joins its dispatch threads,
so nothing can be running once it answers that way.

The regression test is =service_subscription_lifetime_tests.cpp=. It holds a
handler inside a delivery and destroys the subscription from another thread, so
the assertion is the old behaviour's outcome: before the fix the destroyer
returned immediately and the check would see it done. The test was never run
against the old code, because relinking every dependent of =libores.nats= takes
about forty minutes in this shared checkout.

* Result

Destroying a subscription now waits for the handler it carries, and the wait is
bounded: 30s for the drain, twice that for the wait, and a drain that does not
finish leaks the closure and the subscription rather than handing a running
handler a dangling pointer. A closed connection counts as drained.

=service_subscription_lifetime_tests.cpp= holds the behaviour: it keeps a
handler inside a delivery, destroys the subscription from another thread, and
asserts the destroyer has not returned while the handler still holds.

Verified on this tree: the nats, iam-service and marketdata-service suites pass,
and a fleet start and stop leaves 23 units stopped with none failed and no drain
error in the marketdata journal. The full rebuild of every dependent of
=libores.nats= was not run here; it takes about three hours in this checkout's
shared build queue.
