  =.env=, and =..._MAX= is sixteen.

* Notes

** 2026-11-22 — not run, and why

Its preconditions are not met in the environment this was attempted from:

- =.env= is an older format than the checkout expects, so every command that
  reads it refuses until =compass env configure= runs.
- The database is out of sync with the checkout's schema, so a tenant would
  have to be recreated before a provisioning run could succeed.

So the precondition — "a provisioned tenant whose parties have market data, and
no step failed" — cannot be established without readying the environment.

Run =compass env configure=, then =compass db recreate -y -k=, then the
provisioning script this scenario names, then read the journal as Step 3 says.

** 2026-11-22 — attempted on a recreated database, blocked before any lane runs

The environment was readied: =.env= regenerated to version 36, the database
recreated (schema in sync, `312c42fd39e9be4a`), the fleet started, and the
pool states =MIN= 2 and =MAX= 16 as the precondition requires.

The provisioning this scenario names failed at its first step, so no publish
step and no lane was reached:

#+begin_src text
system_provision: failed — The step's progress stood still for 20m 17s, past
its budget of 20m (subject iam.v1.ops.provision_tenant_step). The iam service
was still reporting when the command was published, so the command reached a
service that did not finish the step.
#+end_src

The journal shows no acquisition failure in the iam log, so this is not yet
evidence one way or the other about the pool. It has to be understood before
the scenario can run: a fresh database and a freshly started fleet cannot
provision the system inside the step's budget.

Next: start the fleet, wait for every unit to report healthy, then rerun this
scenario's Step 2 and watch =pg_stat_activity= while it runs.

** 2026-11-22 — passed, on a rebuilt tree

The two attempts above shared one cause, and it was not the pool. Every
executable in the tree was older than the libraries it loads: =ores.shell= and
=ores.dq.service= were linked on 21 November at 14:57, and the libraries those
binaries call were rebuilt on 22 November. A full =compass build= relinked 691
targets, and the faults went with the skew. Three symptoms, one cause:

- =ores.dq.service= took the =system_core= request, died in the copy its own
  decoder made of it, and left the publishing step with a transport timeout. The
  core dump names the frame: =publish_bundle_request::publish_bundle_request=
  copying a string whose data pointer was =0x5c=.
- A shell command against the same subject reported =std::bad_alloc= before any
  reply arrived. After the relink the same command reaches =dq= and reads the
  refusal the handler states.
- =system_provision= reported no progress for 20m 17s after that death, because
  the step holds its phase record still while it waits on a run that cannot
  finish.

The run after the rebuild: =.env= at version 36, the database recreated
(5m 07s), the fleet started with 24 of 25 units (the official provider adapter
stays down without its vendor tokens), then the provisioning script.

- =system_provision= completed, publishing =system_core=.
- =publish_party_curves= completed in 11m 41s, =publish_party_forwards= in 45s,
  =publish_party_surfaces= in 0.13s.
- =complete_provisioning= marked the tenant active at 18:00:39.
- =journalctl --user -u ores.marketdata.service-merry_newton --since "-90 min"=
  holds no =No connection came free= line, and neither does the service's log
  file. The pool of two that this scenario indicts recorded nothing.

Four steps ended with warnings, and none of them is the pool: one staff photo
the account insert cannot see although it sits live in the system tenant, 72
party curves deferred behind funding curves that have published nothing, and the
four surfaces no party holds a blueprint for. The first is captured in the inbox.
