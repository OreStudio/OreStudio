* Goal

Ticket type: grilling (human in the loop).

The booking screen shows a version and an audit trail. The rule the story
follows comes from the source document: any change to a component increments
the version of the structure itself. Authorisation is the one exception — it
cannot change the version, or the loop never ends.

The machinery already exists. =ores.history= dispatches on an entity type to
one generic history dialog, and Temporal Composite Entity Versioning already
states that a child write bumps the parent's version in the same transaction.

Decide what the screen shows, at which level, and how a component change
reads in the structure's history.

* Acceptance

- The screen states which version of the structure it shows.
- The screen states what changed to produce that version.
- A component change reads in the structure's history as one structure
  version, not as a loose component edit.
- An authorisation change is visibly outside the version count.
- The decision states what the generic history dialog shows unchanged, and
  what needs new work.
- The decision is recorded in the story's =* Decisions=.
