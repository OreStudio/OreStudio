* What the Windows job says first

The task's premise is that the MSVC build fails on C1202 in the reflected
aggregate. On 2026-10-28 it does not: the nightly run
[[https://github.com/OreStudio/OreStudio/actions/runs/40643890504][40643890504]]
contains no C1202 at all, because the build stops earlier:

#+begin_example
real_environment_provider.cpp(28): error C2220: the following warning is
treated as an error
clang-cl: error: 'getenv' is deprecated [-Wdeprecated-declarations]
#+end_example

That is a unity-build effect: the file defined _CRT_SECURE_NO_WARNINGS, which
arrives after the CRT has already been included by an earlier file in the same
unity unit, so it suppressed nothing. Fixed by reading the environment with
_dupenv_s on Windows and dropping the define.

The same sweep found the rule broken in four test files, eighteen calls in all,
one of which suppressed the warning with the same macro and one of which used
=setenv=, =unsetenv= and =tzset= with no platform guard at all -- a Windows
build break waiting behind this one. They read through =ores.platform= now, and
the timezone calls have a portable shim. No warning is suppressed anywhere in
the tree; the only native =getenv= left is the provider's own POSIX branch,
which is where the project's memory says it belongs.

The consequence for this task is an order, not a change of goal: the C1202
cannot be observed, let alone measured, until the build gets past the errors in
front of it. The Windows job also reports =nats-server did not become ready
within 30s=, which is its own problem and does not stop the compile.

* What the split actually is

The measurement first. The document holds **33 typed vectors** plus its
configuration object, in one reflected struct: a literal of 34 names. The
sprint 28 investigation measured the unit as **Mode 1, context accumulation**,
not a single literal that is too wide: the same 24-name
=tenor_basis_swap_convention= literal built in a unit of 12 headers and failed
in a unit of 103. See
[[id:1B13CDFF-BDA0-4D2E-8E05-ECB3EC3B9259][Why the configuration document
protocol unit is wide]].

That reading decides the remedy, and it rules out two candidates:

- A file split alone does not lower accumulation, and under a unity build it
  cannot even separate the files: every source of the component lands in the
  same unit.
- =rfl::Flatten= is not a decomposition fix either. It adds the flattened
  struct's names to the parent's literal, recursively, so a wide parent stays
  wide, and it is a JSON-shape decision, never a compile fix. See
  [[id:BBD43BF2-9FEE-42B0-A667-9468AF759DC2][Data-Oriented Design in ORE
  Studio]]. An earlier version of this section said otherwise, on the authority
  of the field-group template's header comment; the template was wrong and is
  corrected in the same change as this page.

What the investigation recommended, and what already happened. It recommended
one operation model per document family, so each unit's encode graph reaches one
document. The conventions half is gone: =ebcf187bca= deleted the conventions
aggregate and the whole-document service, so this protocol now carries one
document of 33 element types where it carried two and 58. Half the accumulation
the investigation measured left the unit by deleting a document, not by
splitting a file.

What remains is 33 element types in one unit, and whether that is over MSVC's
ceiling is not known: C1202 has never been reached, because the Windows job
stops earlier every time. The next step is evidence, not code.
