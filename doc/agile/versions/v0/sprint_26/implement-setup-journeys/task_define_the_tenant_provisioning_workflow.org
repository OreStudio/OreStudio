* Plan

Step 7 makes the instance id step 6 answers with name a run that
exists and finishes. The reconnaissance that decided the shape:

*What the engine actually requires.* The engine publishes a step
command fire-and-forget and waits for nothing
(=workflow_engine.cpp=, =publish_command=). A run advances only when the
handler on the far end publishes a =step_completed_event= echoing the
=X-Workflow-Step-Id= header the engine set. There is no step timeout, no
per-step retry, and no completion hook on a definition: a run finishes
only by running its declared steps out, so the last step is an ordinary
step. An engine step sent to a subject that never reports completion
hangs the run for ever. A step is sent with three headers only —
=X-Workflow-Step-Id=, =X-Workflow-Instance-Id= and =X-Tenant-Id= — and
never with the caller's token, so a step handler runs as the service.

=build_steps= is called at start *and again on every advance*, always
with the same three strings, so the list it returns must be the same
list every time; nothing else is passed to it, and in particular no
completed step's result. A later step's =build_command= does see the
earlier results, addressed by step name; only steps that reported a
non-empty result are visible, and step names must therefore be unique.

*Which subjects can be a step today.* Only the leaves that call
=workflow_step_context::from_message= report completion: the
=publish_from_dq= publisher in each component that owns one (=dq=,
=refdata=, =marketdata=, =assets=, =synthetic=, =reporting=, =iam=),
plus =refdata.v1.parties.put=, =iam.v1.accounts.*= and
=iam.v1.account_parties.*=. The composite verbs are
*not* step-compatible: =dq.v1.bundles.publish= and
=workflow.v1.parties.provision= start nested runs and answer the
caller, and never emit a completion event, so dispatching a step
straight at them would hang the run.

*The design this forces.* ores.iam owns a step executor per step kind.
The definition dispatches each step to an iam subject that carries the
kind and its arguments; the iam handler does the kind's work by calling
the composite verbs request/reply — which is what =provision_acme= does
today, including its waits — and then reports completion through
=workflow_step_context=. Where the work is a nested run, the handler
follows that run to its end through the workflow query subject before it
reports, so a step completes only when its data is really in place. No
other component changes, and the work that =provision_acme= already does
is lifted rather than rewritten, so step 12 can delete it.

The step kinds are the catalogue in code, which this task creates: a
kind the definition does not know is refused when the run starts rather
than silently skipped.

*The split.* The six kinds are not one task's worth. This task lands the
definition, the run lifecycle, and the three kinds the Operational
profile declares — =publish_bundle=, =import_lei_hierarchy= and
=provision_party= — because they are the production path and the path
the shell's =provision tenant= takes. The three kinds only the ACME demo
declares — =load_staff=, =attach_photos= and =start_market_feeds= — are
the next task, which is added to the story beside this one. A profile
that declares a kind this task has not built is refused when its run
starts, so the browser's card for it cannot half-provision a tenant.

*Acceptance, read against that split.* The third and fourth bullets
above are met for the kinds this task lands: the tenant leaves
=bootstrapping= and holds the data its profile ordered for the
Operational card, and the demos those bullets describe for the ACME card
arrive with the three remaining kinds.

* The shape, decided with the plan's owner

The ACME demo path lands first. The six executors are lifted from
=provision_acme=, so the demo card provisions end to end against data
that exists and no other component changes. Two decisions follow from
that and from the reconnaissance:

- *A kind reads what it acts on from its own arguments.* The lift would
  otherwise leave ACME's names in code — =Acme Corporation Plc=,
  uk/us/hk, =acme_group=, =acme_lei_import= — and the story already
  decided the seed profile is data. So =publish_bundle= takes the bundle
  codes to publish, =import_lei_hierarchy= the bundle that carries the
  hierarchy and the root LEI (or the root LEI alone, from the request's
  parameters, when the form supplied it), =provision_party= the party
  bundles with the name each holds, and the three demo kinds the bundles
  and keys their work needs. Each refuses, naming the field, when the
  argument is absent. The ACME rows grow those arguments in ores.iam's
  own seed script; the Operational rows keep what they have.
- *A profile whose kinds cannot be honoured is refused before the run
  starts, naming the kind.* This is what keeps the ACME-shaped interim
  from publishing demo data into a production tenant: the Operational
  card needs =party_essentials= and a bundle carrying a generic LEI
  import, neither of which exists, and it is refused until they do. Those
  two bundles are DQ/seeder data and become their own task with that
  component's owner.

The plumbing the executors need lands first: the run's request and every
step command carry the tenant administrator's account id, because the
engine sends a step without the caller's token and the handler has to
mint its own.

* Result

Pull request #2330 delivered the reconnaissance and the target-state
documentation this task produced: the investigation that decided the
provisioning architecture; the workflow engine cluster and the
per-workflow pages, under the new workflow document type, including the
tenant provisioning page this definition has to satisfy; the scheduler
cluster; and the capture of the scheduler's fixed minute wake.

The definition, its registration and the step executor followed, and the
acceptance is met on the live deployment. A run of the Operational
profile completes: four steps in the profile's order, each reporting
completion; the tenant leaves bootstrap mode; and it holds two parties
with thirty-one report definitions each. The runs are recorded beside
this task: =evidence/provision_tenant_run_live.txt= is the run that
stopped in =provision_party=, and
=evidence/provision_tenant_run_completed.txt= is the run that finished.

Two gaps were closed to get there. The Operational profile ordered two
bundles that did not exist, so =lei_hierarchy= and =party_essentials=
were added as DQ populate data. And the report definition's natural key
was tenant-wide while its publication guard and its row-level policy are
per party, so the key is now the party's; that one model line is what let
=provision_party= publish for the second party.

What this task does not land: the three step kinds only the ACME card
declares — =load_staff=, =attach_photos= and =start_market_feeds= — which
are the story's next task. A profile that orders them is refused before
its tenant exists, which is the behaviour the story asked for.
