* Notes

- *The scheduler record's G08 claim is wrong and was corrected here.*
  =task_clean_scheduler.org= says iam and compute "keep one
  =ores.<component>.hpp= in the core module and no api header". iam keeps
  four: core, api, client and service. compute is simply missing api,
  client and wrapper, and scheduler is missing its own api header. The
  rule G08 states is one per module, and 94 headers across the tree
  follow it. The workspace component had none of its three.
- *The header the diagrams read is the core one.*
  =plantuml_class_diagram_conventions.org= sources a namespace's note
  from =<namespace>.hpp=, and G08 says the outermost one is the
  description the diagram conventions read. So
  =core/include/ores.workspace.core/ores.workspace.core.hpp= carries the
  sentence that describes the whole component, and the api and service
  headers describe their own modules.
- *An invariant that a replace and a delete share a first step cannot
  live in that step.* Both close the current version row; only a
  replace follows it with the next version. A check inside the insert
  trigger therefore cannot tell them apart. The guard is a deferred
  constraint trigger instead: it fires for the Live row and asks, at the
  end of the transaction, whether that row still has a current version.
  A replace leaves one and passes; an archive or a delete leaves none
  and raises. Proved live: the delete raises, the replace inserts and
  leaves version 2 current.
- *The ER refresh is not a workspace change, and the numbers say so.*
  132 hunks, +1362/-232, and exactly one added line names a workspace
  table. The rest is a month of accumulated drift from about twenty
  other entities. It is committed separately so it can be split off; the
  durable fix is the check mode, which is what stops it recurring.
- *A check against a stamped artefact can never pass.* The first cut of
  the ER check compared byte for byte, and the template writes
  =' Generated: {{generated_at}}=, so every run reported one line
  differing. The check now blanks that line on both sides and says why,
  and two regression tests pin it: a different stamp passes, and a
  changed body still fails.
- *Two of the twenty warnings were not RLS warnings at all.* The iam
  seed-profile tables carry =tenant_id= but are =:system_scope:=, so the
  column is always the system tenant and belongs in neither the primary
  key nor the exclusion constraint. Those got the =TENANT_002/003=
  entries the tenants table already had, with the same reason.
