* Goal

Every leaf of curveconfig.xsd that ORE reads is documented once, in the ORE parameter contract, keyed by curveconfig.xsd and its XPath, with the value set its values belong to. The extraction is a script, so the next ORE release is a rerun and not a hand edit.

* Acceptance

- An extractor reads the ORE source and records every curve section, its entry element and each leaf ORE reads, with the source file and line of each fact, and names any block it cannot resolve.
- Every extracted leaf that the guide or a curation describes has an ore_parameter row keyed by curveconfig.xsd and its XPath, with label, description, format, default and release where the source gives them.
- The generator's check mode passes and reports the coverage counts, and the counts are recorded on the task with the command and the commit.
- The [[id:852207A6-6785-43E6-A5D6-2D5C2C374101][ORE element and leaf screen standard]] defines /Parameter/ broadly enough for this kind, since the story decided a curve configuration's leaf is a parameter.
- No screen or web change is made by this task.

The value set each leaf's values belong to is the next task,
[[id:52535EEC-CB9C-4ECF-A9EB-C2F186B2677D][Give the curve configuration leaves their value sets]]. This task was
scaffolded with that work inside it, which was wrong for two reasons: the derive
needs the parse function behind each leaf, which the extractor does not yet
record, and the conventions precedent carried it as a task of its own so that a
documented leaf and a controlled leaf are judged separately.

* Plan

1. Build =extract_curve_terms.py= beside =extract_convention_terms.py=. It takes
   =--ore=, else =ORES_ORE_ENGINE=, else the default the guide extractor uses.
   It reads =OREData/ored/configuration/curveconfigurations.cpp= for the
   document root and the section skeleton, then each family parser for the
   leaves, with the same =XMLUtils::checkNode=, =getChildValue= and =parse*=
   regexes the conventions extractor uses. It writes =curve_terms.json= with the
   source file and line behind each fact.
2. Turn the terms into contract rows: =schema_name = curveconfig.xsd=, and the
   XPath from the section, the entry element and the leaf path.
3. Give every row a value set: a closed list from the parser where ORE maps one,
   a catalogue where the value belongs to refdata — a currency, a calendar, a
   day counter, an index.
4. Add a check mode and record the coverage counts on this task.
5. Widen the /Parameter/ definition in the [[id:852207A6-6785-43E6-A5D6-2D5C2C374101][ORE element and leaf screen standard]]
   so it covers a curve configuration's leaf and not only a product's or the
   document's global parameters. The story decided the word; this task makes the
   page say it.

* Notes

- *The extractor has a close precedent.* =extract_convention_terms.py= records
  for each term its member, name, path, read call, parse function, mandatory and
  conditional flags, the source file and line, and the guide line of its text.
  The curve extractor records the same facts, so the two datasets are read the
  same way and a later reader compares them without a translation.
- *The guide is the prose and the source is the structure*, as they were for the
  conventions. =Docs/UserGuide/parameterisation/curveconfig.tex= and its
  =curve_configurations/*.tex= sub-sections give the text; the parser files give
  the reads.
- *A word collision to fix.* The refdata entity docstrings call these leaves
  *settings*: =yield_curve_config= says "The settings of one ORE yield curve
  entry", and =curve_definition= says "the settings every section shares". The
  engine run settings own that word, so those docstrings contradict the decision
  this story makes. The implement task corrects them, when the metadata moves
  into data.
- *=curve_section= is the authority* on the sections and their entry elements.
  The extractor must agree with it. A disagreement is a finding, not a silent
  rename.
- *The contract id derives from =schema_name= and =XPath=*
  (=ore_parameter_seed.py=), so the schema must be right on the first write. The
  pricing rows still carry =ore.xsd=, and their correction is separate work.
- *The extractor reads five parser idioms*, because the curve document is not
  written the way the conventions document is. A leaf is a direct
  =getChildValue=; a child node whose value is read with =getNodeValue=; a
  child node whose own children are read; a member that parses a block, whose
  type names the class; and a dispatch on the child's node name, where the block
  holds alternatives (=Segments= holds =Direct=, =Simple= and the rest). A
  derived config may also inherit =fromXML= from a base class, which parses the
  same node, so its leaves belong to the derived entry too.
- *The same leaf is read in more than one branch.* A commodity curve reads
  =DayCounter= once for its piecewise form and once for its direct form. Both
  are one leaf of the document, so the extractor writes one term and marks it
  conditional. Five leaves are conditional this way.
- *Eight blocks stay unresolved*, each recorded with the source line that reads
  it: =RecoveryGrid=, =BootstrapConfig= under =CommodityCurve=, =Configurations=,
  =TimeExtrapolation=, =ParametricSmileConfiguration=, =Segments= under
  =InflationCurve=, and the two volatility entries whose parser is inherited.
  Each is a gap the next pass closes or records a reason for; none is silently
  dropped.

* Result

The extractor reads the ORE source and writes =curve_terms.json=: 19 sections,
434 leaves, 5 of them conditional, each with the source file and line of its
read, and 8 blocks it cannot resolve, named with the line that reads them.

The guide supplies prose for 235 of the leaves, attributed to the section it
describes, and =curve_parameter_rows.py= turns those into contract rows keyed by
=curveconfig.xsd= and the leaf's XPath. The generated seed carries 235 curve rows
and 2,260 rows in all, and the generator reports the 199 leaves that still have
no text.

The leaf standard now defines /Parameter/ to cover a curve configuration, which
the story decided and this task owed.

What this task did not do, and says so: the value set each leaf's values belong
to is [[id:52535EEC-CB9C-4ECF-A9EB-C2F186B2677D][a task of its own]], because it needs the parse function behind each leaf.
