* Goal

An installation ships with every store it keeps already bounded. The store
catalogue states a default retention policy for each store that can take one — a
quarter for report output, a month for delivery counters, a week for job inputs, a
day for scratch — and provisioning creates the policy, so nobody has to notice
the absence before the store starts growing. A store without a policy then means
one of two things, and both are worth a person's attention: the store's bound
cannot be expressed as an age, or somebody removed the default.

* Acceptance

- The store catalogue states, for each store, whether it carries a policy and the default period and action when it does
- Provisioning creates the policy for every store that states one, in the tenant that owns the store, and a second provision leaves exactly one policy per store
- The default period follows the kind of data: run output a quarter, counters a month, job inputs a week, scratch a day
- The policy rows are delivered as platform data like the sweep itself, so a default changes without a schema rebuild
- A store whose bound cannot be expressed as an age (the calendar dates) states that, rather than carrying a default that does nothing

* Plan

- The catalogue states the default; the shipped policies are derived from it, so
  one statement of a period serves both and the two cannot drift. The policy
  dataset's artefact rows become a =select= over the catalogue's artefact rows
  rather than a hand-written list, and the catalogue stages first so the rows
  exist when the derivation runs.
- A policy needs to name the store it came from, so =retention_policy= gains
  =store_code=. That is also what makes one policy per store checkable: the
  publish creates a policy only where no current policy already names the store,
  so a changed default never applies an older period beside a person's choice.
- The policy's own vocabulary had to grow to match the catalogue. It refused
  =release_directory= and a =directory= target, which is exactly what the node
  scratch default asks for; the checks and the model now state both.

* Result

An installation ships with every store the catalogue can bound already bound.
Eight policies are derived from the ten catalogue rows: the two stores that take
none are the package cache, bounded by its content keying, and the calendar
dates, whose bound is a range rather than an age.

The derivation is one statement: the policy artefact rows are a select over the
catalogue's artefact rows, where the bound is a policy. A new store therefore
arrives with its policy, a default changes in one place, and the policy code
names the store and the period so an operator reads it without a join.

Two things were found by doing it. The policy needed to name its store, or a
second default for the same store could apply an older period beside the first;
=store_code= is the fix, and the publish now skips a store that already holds a
policy under another code. And the policy's own checks refused the node scratch
default, because =release_directory= and a =directory= target were not in its
vocabulary even though the sweep's task names them: the catalogue found a gap in
the model it was meant to serve.
