* What

Let an entity model state that a table belongs to the installation, and generate it. The model would say three things.

- The table is a mutable current-state table with a key of its own, so it has no validity window and no version.
- Its policy admits a session of the system tenant alone, written =tenant_id = current and tenant_id = system=. That admits no tenant's rows to anyone else, so the RLS guard does not flag it.
- Its writes are atomic statements that the repository holds by hand, such as a claim that takes one row with =for update skip locked=.

From that the codegen would produce the table and its drop script, the policy, the domain type and the repository base with the plain reads and writes.

* Why

The work ledger is the queue of the compute grid. A queue that serves every tenant cannot be a query over every tenant's results, because no policy lets the system tenant read another tenant's work. The ledger is the installation's, with one entry for each result, holding ids, times and counts, and the service reads it as the system tenant.

The entity templates offer the current-state shape that the grid samples use, and the shared-reference policy that admits the system tenant's rows to every session. They offer no policy that admits the system tenant alone, so the ledger is hand-written: its create and drop scripts, its repository and its tests. Every installation-owned scheduling table that follows will want the same shape, and a hand-written one drifts from the conventions the generated tables keep.
