* Goal

Every journey in the [[id:D602E114-F896-42CA-893A-841AD6FC3221][User Journeys]] catalogue runs in =ores.web=, against the real
server. The catalogue holds 21 journeys in eight topic groups. This
story orders the groups. Each group has its own story, and each of
those carries its own completion.

This is the third pass of the sprint 26 mission. The first pass put
every component on the [[id:7B477025-132E-4B20-80B4-D8C9420880B8][Component Clean Standard]]. The second
extracts the journeys and is
[[id:28844DEF-E9AD-45B9-A6E0-CFF51CA1A064][still in flight]]. The journeys are design documents and they do not
change here. This pass builds from them.

The first group writes the journey runtime, and every later group uses
it. The runtime is the reason this is a programme and not one long
story: a journey is an ordered list of steps, one page renders the
list, and the work of the second group is then the steps alone.

Setup is first for two reasons. It is the only group that runs on an
empty installation, so it is the only one that can be demonstrated from
nothing. And First run expands the new tenant steps inline, so the
Setup story lands the shared step library that every later group reads.

Entry is second although First run ends in a sign-in. The sign-in
itself already works through =POST /api/session=; what the Entry story
adds is the screen, self-registration, and the failure paths.

* Decisions

- *One story per group, and the catalogue's grouping is the
  implementation grouping.* Journeys are grouped by the topic a
  designer looks them up under, never by component. A component is an
  implementation concept and it moves; what a person is trying to do
  does not.
- *The runtime is written once.* A journey is an ordered list of step
  definitions. One page renders the flat rail from that same list, so
  the rail cannot drift from the steps. The first group settles the
  contract; a later group that needs it changed records why rather than
  forking it.
- *The build targets the accepted contracts.* Both sprint 25 decisions
  are recorded in the prototype tasks and both are the target:
  [[id:DDCB8562-405D-4D16-8C82-0144CBAB3612][the bootstrap workflow catalogue]] and
  [[id:94C3AE99-8642-4418-982D-92C5FD805CCB][the seed profile contract]]. The build
  does not add a client path to a subject the design has retired.
  =iam.v1.bootstrap.provision-tenant= and =iam.v1.tenants.provision-acme=
  are used only until the generic request replaces them, and no new
  code depends on them.
- *The journey is not server-side; its state is.* The state is a
  [[id:FDF3C079-4E18-4DB7-911F-7691AD1F5665][workflow instance]], which already carries
  the kind, the current step, the request, the result and the error. No
  journey entity is added. [[id:3361CF92-89B0-481E-9E51-ACE2FEEF2FAA][Journey execution]]
  records the reasoning and supersedes the sprint 25 plan for a
  =/journey/= entity.
- *The extraction story owns the journey documents.* The build does not
  rewrite them. Where the build proves a journey document wrong, the
  correction goes to that document and is recorded in the story that
  found it.
- *The prototype branches are the design record and are ported, not
  merged.* They predate the removal of the generated screens, so they
  still carry the entity framework. The reduction commit =e47043269f=
  names what went and why.
- *A cross-sprint story closes DONE and gets a successor.* The
  catalogue needs more than one sprint, so a group that does not close
  in sprint 26 closes with what landed and continues in a successor
  story.
- *=ores.web= has its own standard.* The
  [[id:7B477025-132E-4B20-80B4-D8C9420880B8][Component Clean Standard]] is
  written around SQL, a repository, a service and a generated registrar,
  and the TypeScript packages have none of those. The
  [[id:CDE625E2-96AE-4644-9921-282339925F3E][TypeScript Clean Standard]]
  is its sibling: the same shape, one item per convention, and every item
  naming the check that proves it. It is written before the first line of
  journey code, because a convention recorded afterwards is a convention
  nobody followed.
- *Every journey has two clients.* =ores.web= and =ores.shell= run the
  same server-side operation for each stage, so a journey is implemented
  once on the server and reached from both. The shell already carries
  several journeys as porcelain commands, and the recipes under
  =doc/recipes/shell/provisioning/= run the whole Setup sequence end to
  end, one per provisioning path. A group's story therefore carries the
  shell side of its journeys in the same group, and a group that lines up
  only the browser has moved the disagreement rather than removed it.
- *A client's orchestration moves to the server, it is not duplicated.*
  Where the shell drives several calls in sequence today, the accepted
  contracts put that sequence in one request. Both clients then call the
  same subject and neither owns the order.
