* Goal

ORE Studio supports every trade ORE supports. For every product type ORE
carries:

- the data model holds every fact the trade states as a column or a row, never
  as JSON or a list in text; a first pass may carry defects such as too many
  columns, which later refactoring fixes;
- a builder books it from typed terms, and a term a builder is not given does
  not compile;
- the generator books Acme trades of it through the builder, in each form ORE
  reads it in: its own element, and, where ORE's library holds a script with the
  same payoff, a generic =ScriptedTrade= naming that script;
- the XML we write is accepted by ORE: the trade test framework (the recorded
  generated trades, the ORE engine test, the sample-paths check and the content
  roundtrip) reads and builds every generated trade, with no error the trade
  causes.

Every script in ORE's library is generated as a generic =ScriptedTrade=. A trade
type ORE cannot carry is tagged unsupported in the catalogue with its reason,
and a person sees it. When the story is done, nothing on how a trade is
represented is left to do: later work refactors for performance and
data-oriented design, and prices the trades.

* Acceptance

- the catalogue states every ORE trade type with its support status, its form or
  forms and its instrument table; an unsupported type is tagged with its reason
  and ORE's evidence, and nothing can route, book, import or generate it
- every supported type has a data model of its own, with no JSON and no list
  held as text: the tables its facts need, the checks those tables state, and
  the relationship rows the shape requires
- every supported type has a projection reader and writer, so a document imports
  into rows and exports as the element ORE reads, value for value
- every supported type has a builder, and every generic =ScriptedTrade= is built
  by one scripted builder that checks its variables against its script's inputs
- the generator books every supported type through its builder; a product ORE
  carries in two forms is booked in both; every script in ORE's library is
  booked as a generic =ScriptedTrade=
- the ORE engine test reads and builds every generated trade; its known list
  holds only lines of the market data or engine configuration kind, each with
  its reason, and a test fails when a line of the trade kind appears
- the old =construct_*= functions and =*_terms= structs are gone
- a check fails when the catalogue and ORE's trade builders drift apart, and a
  test fails when a type is added without a route, a builder and a generator
- every defect the trade representation captures named is fixed with a test, or
  shown fixed with evidence, and the tests are shown to catch defects by a
  property-based roundtrip and a mutation run
- the coverage, each type's measured level and the unsupported types are visible
  on the catalogue's own page, and a scripted trade is edited on a screen of its
  own

* Decisions

- A product's facts are modelled once, in the shape its terms demand, whether or
  not ORE reads the product through a script. Where ORE carries it as a
  =ScriptedTrade= subclass, its element is a fixed schema the projection writes
  member by member, as it already does for =DoubleDigitalOption=; where ORE
  carries it natively, the element is written natively. The catalogue records
  which form each type takes.
- Where ORE's script library holds a script with the same payoff as a product's
  own element, the product has two forms, and the generator books both, so each
  is tested. The generic form is a =ScriptedTrade= naming the library script.
- Both forms are held, each in its own shape, so the two implementations can be
  compared. A product's element form sits on a table of its own, with its terms
  as columns and its lists and schedules as rows; the scripted instrument table
  holds only the generic =ScriptedTrade= form. The class-read path first held
  twenty-eight element forms as parameter rows of the scripted table, eight of them
  products ORE builds natively. That held every value but gave no element a
  table, so the "Hold ... on their tables" tasks move each element to one, and
  "Compare the two forms of each product" values each twin pair and compares
  them.
- A trade type the engine cannot carry stays in the catalogue, tagged
  unsupported with its reason and the evidence from ORE's source, rather than
  leaving it. A person sees it on the coverage page; nothing can book, import or
  generate it under that type; and a check fails when a later ORE release
  registers it. At ORE 1.8.17.0 (=3d75a6908=), the engine the tests run, there are two, and the registrations are the same at the later =c3ffbae78=:
  =CommodityPairwiseVarianceSwap=, for which ORE has only the equity and FX
  classes, and the bare =ForwardVolatilityAgreement=, which ORE replaced in
  release 1.123.0 (merge =3477d435d=) with its FX, equity and commodity types.
  Neither product is lost: ORE carries both as a generic =ScriptedTrade= over the
  library scripts =PairwiseVarianceSwap= and =ForwardVolatilityAgreement=, and
  the script tasks generate them that way.
- "Accepted by ORE" is what the trade test framework measures: the ORE engine
  test reads and builds every recorded trade with the configuration of ORE's
  Products example. A build error for want of market data or an engine
  configuration is not the trade's fault and stays on the known list, tagged
  with its kind; every other error is a defect this story fixes. Pricing is the
  valuation story's work.
- ORE's script library is reference data: a script with its code, NPV and
  results, and its inputs as rows with a type, a shape and a value rule. A script
  is ORE's code, fixed, so it is not generated from a template; what varies per
  trade is its variables, and those are a recipe held as data. One scripted
  builder serves every library script. ORE has no builder of its own to reuse:
  its parser yields the script's free variables, and the library's comments
  describe them, so the inputs are mined, not typed.
- A scripted trade is edited on a typed form drawn from its script's inputs, not
  as free text. An inline custom script is an advanced mode with a code editor.
- The open representation tasks of [[id:47DEDD3C-082E-46A9-BD01-67DFAB9CFFA5][Make the generated trades value correctly in ORE]]
  moved here on 2026-11-15; that story keeps the market data and valuation work.

  this one: its content roundtrip and audit are done, the ORE contract is the
  engine test, and its measured levels are the coverage page.
- Every open capture on trade representation was swept on 2026-11-15: 22 were

  discarded as fixed, duplicated or superseded, each with its reason. A capture

* Out of scope

- Market data, pricing engine configuration and valuation. They stay on
  [[id:47DEDD3C-082E-46A9-BD01-67DFAB9CFFA5][Make the generated trades value correctly in ORE]].
- Refactoring the data model for performance or a stricter data-oriented design,
  such as splitting a type that carries too many columns. That follows this
  story.
