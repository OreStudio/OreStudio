This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A reference data administrator picks one of the short code lists that classify reference data and keeps its rows correct.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want the codes that classify our reference data to hold exactly the values we
use, with names people understand, in the order they expect." The journey is
done when the chosen list reads correctly and its history shows why it changed.

* Actor and trigger

The actor is the tenant administrator: an account with the =TenantAdmin= role,
acting inside their own tenant. No narrower role holds these permissions today.
The trigger is a value a picker does not offer, a wrong or unclear name, or a
code the tenant no longer uses. The journey starts at *Classifications*, or at a
"correct this list" link beside any picker that reads one of these lists, and
ends when the person leaves the list.

These lists have no goal of their own, so a plain list with its edit form is the
right screen, as in [[id:D730532F-4D1B-4344-B723-4F9F006B8041][Tune the tenant]]. The difference is scale: there are 28
lists, so the person first chooses which one.

* Steps

1. *Choose the list.* The person opens *Classifications*. The system shows the
   lists grouped by topic: currencies, calendars, parties, books and
   portfolios, products and ORE codes, tenors, and market data. The person
   picks one, or arrives with one already chosen from a picker's link.
2. *Read the list.* The system lists the rows: the code, the name, the
   description and the display order. Five lists carry only a code and a
   description, and one of those carries an order too; the columns follow the
   list.
3. *Add a row.* The person enters a new code, its name, description and order,
   states a change reason, and saves. The system writes it with
   =must_not_exist=, so a duplicate code is refused instead of overwritten.
4. *Correct a row.* The person changes the name, description or order. The code
   is the key and does not change. The system writes it with
   =must_match_version=.
5. *Reorder.* The person moves rows. The system writes each moved row's new
   order.
6. *Remove a row.* The person removes a code the tenant no longer uses. The
   system closes the row; it stays in the history. See /What is missing/ for
   codes still in use.
7. *Check the history.* The person opens a row's history. The system shows every
   version with the field-level difference from the one before, and the person
   can revert to an older version, which the system writes as a new version.
8. *Leave.* The person goes back. Every picker that reads the list offers the
   values it now holds.

No step waits on the server after its reply, and the journey keeps no state.

* What is missing

1. *Removing a code still in use is not refused.* A delete closes the row
   without checking who refers to it. A currency that uses a removed rounding
   type keeps the code, and its next save fails, because the currency's
   validator checks that the code exists. The same holds for every list a
   record points at. The candidate is an in-use check on delete that names the
   records still using the code. Until it exists, the screen warns before every
   removal that records may still use the code.
2. *Lists ORE defines are editable like any other.* =day_counter=,
   =calendar_name=, =floating_index_type=, =leg_type= and
   =business_day_convention_type= hold spellings an ORE document must write
   exactly. Changing or removing one can produce a document ORE rejects.
   Calendars mark this with =is_editable=; these lists have no such marker. The
   candidate is the same marker on the ORE vocabularies. Until then the screen
   shows these lists read-only, and says why.
3. *Order is not unique.* =display_order= is a free integer, so two rows may
   share it and the list order is then undefined. The candidate is a unique
   index per list, or a stated tie-break by code.
4. *Only a tenant administrator can run this journey.* No role below
   =TenantAdmin= holds these permissions.
