* Acceptance

- market_series and feed_binding carry oresmd_uri, and it is the natural key for a series and for a feed binding.
- import_service writes the URI for every market-data key and every fixing index name, and writes no row that has an identifier without one. from_index_name has production call sites at last.
- The corpus import round-trips: every fixing row in external/ore/examples creates a series, with the skipped-name warning count at zero and the de-duplication count unchanged.
- series_type, metric, qualifier, ore_key and the import classification table are deleted, and every consumer reads the URI.
- The FOMC segment's instruments carry ORE identities: the raw grid is one series per pillar, named by the shape of the instrument the feed simulates -- the spot-starting pillar spelled as the swap it is, so no pillar needs a new spelling -- and the republish curve carries ORE's DISCOUNT key.

* Scope, measured before the column

Read at =00c9cdd711= on the merged trunk. Nothing here is a claim about the
abandoned branch; the two write paths are the code as it stands.

**Neither import path stores an identity today.**

- *Market data.* =import_service.cpp='s =canonical_key()= already computes the
  identifier: it calls =from_ore_key()=, projects it back with =to_quote_key()=, and
  returns the canonical spelling and the registry's decomposition of it. The
  identifier itself is **discarded**. The series is found or created on
  =(series_type, metric, qualifier)=, and the observation keeps the file's own text
  in =obs.key=, because the rows above hold the canonical spelling rather than it.
- *Fixings.* The series is created as
  =find_or_create_series("FIXING", "RATE", f.qualifier)=, where the qualifier **is**
  the index name. =from_index_name()= has no production call site at all: zero
  outside the projections and their tests. A fixing series therefore has no
  identifier to store, and the index name is the whole of its identity.

**Both identity-bearing tables are known, and the blast radius is measured.**
=market_series= keys on the triple; =feed_binding= keys on =ore_key= and
=source_name=. 63 files across =ores.marketdata=, =ores.synthetic=, =ores.shell= and
=ores.ore= name =qualifier=, which is the set the deletion has to carry. The value
the new column needs is in hand on the market-data path and one call away on the
fixing path, so this task is the cutover and its consumers rather than a new
projection.

* What the deletion has to carry, counted

Counted at =ce3c6f32bd= on this branch, with member-access and column patterns
rather than the bare word, because =metric= alone matches 481 files and most of
them are somebody else's metric:

| What | Count | Pattern |
|------+-------+---------|
| C++ files reaching a series' =qualifier= | 21 | =\.qualifier\b= |
| C++ files reaching a series' =series_type= or =metric= | 32 | =\.(series_type\|metric)\b=, in the three components that hold series |
| SQL files naming the ="qualifier"= column | 2 | the market series create and populate scripts |

| Org documents naming =qualifier= | 80 | models, recipes and manuals |

The organs split by component: =ores.marketdata= 33, =ores.synthetic= 16,
=ores.ore= 12, then two in the shell and one each in =ores.trading= and
=ores.testing=. The deletion is therefore a cross-component change, which is why
the plan kept it as its own acceptance rather than folding it into the column's.

**=feed_binding='s column is deferred, and the reason is structural.** The plan
gives the binding an =oresmd_uri= beside its =ore_key=, and the column was added and
regenerated: =ores_marketdata_feed_bindings_tbl= took it and the entity's layers
followed. It was then taken back out, because nothing can write it today. The row is
assembled by the generated service -- =feed_binding_service.cpp= carries the
AUTO-GENERATED banner -- and the service template has no per-column derivation hook;
the =#+begin_src cpp :name generator= blocks a model can declare feed the test-data
generators under =api/src/generators/=, not a real write. Every other writer is a
generated shell command. So the binding's identity arrives with the unit that
replaces =ore_key=, where the same code that supplies the key today supplies the URI;
until then the column would be null in every row, which is worse than absent. The
natural key stays =ore_key= and =source_name= meanwhile.

**The identity the writers derived named a datum, not a series.** The column sits on
the series row, and the value came from a key that names one datum: =IR_SWAP/RATE/
USD/0D/1D/5Y= is the 5Y point of the =USD/0D/1D= series. The import projected the
file's whole key, so a series row's identity carried whichever point arrived first,
and two databases built from the same files in a different order would disagree about
the identity of one series. The ingest loop projected the triple alone, which names no
class whose key is longer than the triple, so a swap, curve or future series got no
identity at all from a live tick. =oresmd_parser::to_series_uri()= projects the
identifier with its point, and a volatility surface with it, dropped; both writers
call it, and the ingest loop builds the datum's full key -- the triple plus the tick's
point -- before falling back to the triple. No row changes shape: the series and its
points were already separate rows.

**The deletion needs no backfill, and the fallback is what says so.** The plan
records a hard cutover with no backfill, which only works because this schema is
applied by recreation rather than by migration: a database is built from the create
scripts, so it holds no series written before the identity column. The triple
fallback exists for a database that does have one, and it is the thing the deletion
removes -- at which point a series with no identity is unreachable, which is why the
create scripts and the writers have to agree before the columns go.

**The curve snapshot requests name the series by the triple, and the identity move
was taken back.** Making them carry the identity is two hand edits, because neither
the protocol header nor the handler is generated, and the edit was made and then
reverted before the merge: a request carrying only an identity cannot reach a row
that has none, and this path must read the FOMC grid, which no projection can name.
So the handler's two lookups are the production readers left on the triple **alone**;
the import's and the ingest loop's calls ask by identity first and fall back to the
triple. The move waits for the rows to have identities. The path is verified by the
compiler and the suites and by nothing else: it has no sender anywhere in the tree
and no case exercises it, which is worth knowing before the cutover leans on it.

**Not every series row in the table can be given an identity, and the constraint
says so.** Read on the live database at =ca23d34ef2=: of 5,864 series rows, **4,431**
carry a series type the ORE key grammar knows, and **1,433 across 28 types do not**.
Re-read at =3632865c32=, after the generator had been run again: of 5,971 rows,
**4,569** are nameable -- by =from_ore_key()=, or by =from_index_name()= for the 188
=FIXING= rows, which the quote grammar has no type for -- and **1,402 are not**. All
but two of the unnameable set is test-data generator output: =CD-0= to =CD-25=, 1,400
rows, whose =series_type=, =metric= and =qualifier= are all the same string and whose
subclass cycles through the list the model's generated generator draws from.

The remaining **two rows are the FOMC segment**, both seeded by
=marketdata_market_series_fomc_populate.sql=, and both production: they carry the
fixed uuids the FOMC bootstrap config references as its =source_series_id= and its
=output_series_id=.

- =RATES / YIELD / 'USD/SOFR-FOMC'=, the raw grid "the identity the ingest loop
  resolves the ir_curve_feed's ticks by". =RATES= and =YIELD= are not ORE series
  types, so =from_ore_key()= cannot name it.
- =YieldCurve / DISCOUNT / 'USD/SOFR-FOMC'=, the curve the republish service writes
  into. =YieldCurve= names a curve in ORE's curve configuration rather than a market
  data type, so the grammar carries it in neither direction.

This task's first reading called the second row generator output and so counted one
production row. It is the republish seed, and there are two.

**The instrument set is ORE's, and the corpus spells it.** The raw grid's ticks are
simulated quotes for meeting-dated OIS, and its pillars pair FOMC meeting dates:
=SPOT= to =1F=, then =1F= to =2F=, through =8F= to =1Y=. ORE carries the same
instrument class elsewhere in the corpus: =external/ore/examples= spells a
meeting-dated OIS as =IR_SWAP/RATE/GBP/20220922/1D/20221103= -- a start date, the
overnight index tenor, an end date -- and the live table holds 58 series whose settle
segment is =20220922=. The curve row is nameable in the same vocabulary:
=DISCOUNT/RATE/CCY/CURVE/TENOR= is how the corpus carries a discount curve's points
(the =USD-DUMMY= curve), and =DISCOUNT= is already an oresmd class. So the invented
=RATES/YIELD= vocabulary is not what the instrument class needs.

**Decided: the feed publishes the grid as the instruments it simulates, and the
bootstrap reads them per pillar.** The synthetic feed resolves each entry's start and
end tenor to dates already, because the schedule needs them, so the ORE key is a
projection of what the feed holds. The grid stops being one series with a point per
entry and becomes one series per instrument, which is how ORE models a curve's input;
the bootstrap's own pillars carry the start tenor, the end tenor and the role, so its
input is derived from the config rather than referenced by one =source_series_id=.
The republish output keeps its one-series-per-curve shape and takes ORE's =DISCOUNT=
key, with the pillar as the observation's point. The alternatives, recorded for the
reader who asks why they were not taken:

- oresmd grows a namespace for internally derived series. Rejected: it would make the
  identity space admit whatever the system invents, which is what the grammar exists
  to refuse, and the grid's instruments turn out to be ORE's after all.
- the derived series keep the triple and the URI stays the key for observed rows
  only. Rejected: two keys in one table, which defeats the point of the cutover.

**The shape decides the identity, and it closes the deposit pillar's open question.**
Every pillar's quote is an ORE swap key: =IR_SWAP/RATE/CCY/<start>/1D/<end>=, which the
corpus spells for the same instrument class as =IR_SWAP/RATE/GBP/20220922/1D/20221103=
(=external/ore/examples=, 58 series in the live table whose settle segment is
=20220922=). The start slot holds =0D= for the pillar that starts at spot and a meeting
date for the rest, =1D= is the overnight index tenor every dated OIS quote in the corpus
carries, and the end date is last. One series per pillar -- the key without its end date
-- and the end date is the observation's point. ORE's money-market family has no dated
point, so the spot-starting pillar is spelled as the swap it is rather than as a
deposit; the dated spelling the unit left open is therefore closed, and no pillar needs
a new spelling.

The curve the republish service writes keeps the corpus's discount shape,
=DISCOUNT/RATE/CCY/CURVE/TENOR= (=DISCOUNT/RATE/USD/USD-DUMMY/1D= in
=external/ore/examples=). There the curve is the series and the =TENOR= is the
coordinate, which is the slot the corpus's =1D= fills: the series' key is
=DISCOUNT/RATE/CCY/CURVE= and the maturity is the observation's point. That is also why
the =DISCOUNT= family appears in the defect below -- the projection has to drop a
maturity the identifier holds in =tenor= -- rather than because the shape is wrong.

Both shapes are pinned by a case -- the spot-starting pillar, a dated pillar and the
curve -- so the grammar is proved before the feed and the seed are written against it.
The case also pins the negative: two pillars are two series, and the curve's maturities
are one.

**The curve's half of the seed carries its identity now.** The FOMC seed row the
republish service writes into reads =DISCOUNT / RATE / 'USD/USD-SOFR-FOMC'= with
=oresmd://ir/usd?curve_id=USD-SOFR-FOMC&type=quote&metric=rate&quote=discount=, so the
triple and the identity agree and neither is an invented vocabulary. Nothing else had
to move: the republish service and the bootstrap reach that row by the fixed uuid the
config names, and the pillars stay the observations' points. The raw grid's half waits
for the re-key, because its identity only exists once the feed publishes one series per
pillar.

**The bootstrap reads its tenor convention off the grid series, so the re-key has to
give it somewhere else to look.** =curve_republish_service.cpp='s
=tenor_convention_code_for()= returns =RATES_SPOT_FOMC= for a source qualifier ending in
=-FOMC= and =RATES_SPOT_FORWARD= otherwise, =build_refdata_context()= throws when the
series is missing, and that convention decides which tenor resolutions the pillar dates
come from. The grid's qualifier is =USD/SOFR-FOMC= today, which is what the rule
matches; the per-pillar qualifiers the re-key writes (=USD/20260128/1D=) match nothing,
so the convention would silently become =RATES_SPOT_FORWARD= and the FOMC pillars would
resolve as ordinary spot-starting instruments. The unit is therefore two parts: the
bootstrap config names its own tenor convention -- a column seeded to =RATES_SPOT_FOMC=
for the FOMC config and =RATES_SPOT_FORWARD= for the rest -- and then the feed and the
bootstrap move to the per-pillar identities. The first part stands alone and is where
the unit starts, and it deletes =tenor_convention_code_for()= and its throw path rather
than keeping them as a fallback: a fallback would leave the coupling between a series'
spelling and the convention its pillars resolve under.

**The two configs still disagree on the roles, and identity is no longer what exposes
it.** The synthetic config's FOMC entries are a =DEPO=, seven =FRA=s and an =IRS=; the
bootstrap config's nine pillars are a =DEPOSIT= and eight =SWAP=s. Because the shape
decides the key, a pillar's role no longer reaches its identity and the vocabularies do
not need reconciling for one. The disagreement is a pricing question -- whether the
feed's FRA path and the bootstrap's single-period swap path agree on the same pillar --
and the FOMC unit answers it on its own terms. The column stays nullable until the feed
and the seed agree, and the identity is what a row gets *if it has one*: the constraint
would not catch the generator output anyway, since random text satisfies a not null
column. What the generator writes is now a generic index name -- the one oresmd URI
that names a series with a name and nothing else -- rather than the default faker noun,
so the rows it produces carry an identity the grammar reads.

**Two IR families keep their coordinate where the projection did not look, and the
rest do not.** The decomposition splits a datum key into the series and the point, and
=to_series_uri()= was written to drop the identifier's =point= and its surface. That is
the whole of the coordinate for the swap, money-market, FRA, vol and commodity families
-- the MM series =CHF/2D= carries its maturities in =point=, the FRA series =EUR/3M=
likewise -- but not for two IR families:

- a =DISCOUNT= curve's maturity is the identifier's =tenor=, because the series is the
  currency and the curve: =DISCOUNT/RATE/EUR/EUR= carries =1D= through =35Y= as points;
- a future's coordinate is its =contract_code= and its =tenor=, because the series is
  the currency and the contract month: =MM_FUTURE/PRICE/EUR/2024-04= carries
  =XICE:FEI/3M= as its point.

So those two families' series identities carried one observation's coordinate while the
rest were right. The triple fallback keeps a row reachable and stops duplicates, so
nothing broke; what was wrong was the value stored. At =94e2d8645d= the live table held
36 =DISCOUNT= series and 70 in the two future families.

**The fix is in the projection, and the survey is a test.** Which fields hold the
coordinate is a fact about each family, so =to_series_uri()= now clears the discount
tenor and the future's contract code and tenor as well. A case walks one two-point pair
per family -- MM, FRA, swap, swaption, commodity forward, discount and future -- and
asserts that the two points project to one identity with no point in it, so a family
that regresses fails the case rather than the cutover. The earlier reading of this
defect named the no-index families too, which the case disproves: their coordinate is
the =point=, and 232 of their series were never affected. The series-level inverse this
record first asked for is not needed, because the identifier already holds every field
the series needs.

* Plan

The additive half is delivered (#2358), the identity is a series rather than a datum
for every family (#2362, #2364), the FOMC shapes are pinned (#2365), the curve's seed
row carries its identity (#2366), the generator writes one (#2368), the config names
the tenor convention its pillars resolve under (#2370) and the currency they are
quoted in (#2375), and the feed keys every pillar as the OIS quote it simulates
(#2373) while the bootstrap reads those keys per pillar (#2384); the raw grid those
ticks used to land in is gone from the seed and from the config that named it. What
is left is the cutover the task takes its name from.

**The re-key, in four steps.** Each step ends green on its own.

1. *The feed keys each pillar.* =ir_curve_resolved_entry= gains the entry's
   =start_date= and =end_date= strings, which =resolve()= already computes for the
   year fraction. A pillar is spot-starting when its =start_tenor_code= is =SPOT= --
   the config's own first entry -- and meeting-dated otherwise, and that one rule
   lives in a single builder both sides call rather than being written twice.
   =ir_curve_feed= publishes one tick per entry with =series_type="IR_SWAP"=,
   =metric="RATE"=, =qualifier= =<CCY>/<start>= (the start slot holding =0D= for the
   spot-starting pillar and the start date for the rest), =1D= as the index tenor, and
   =point_id= the entry's end date. The ingest loop already derives the series identity
   from a tick's full key, so the series appear with their ORE identities and nothing
   else in the pipeline moves. =ores.synthetic= is where this step's test belongs: a
   tick per pillar carrying the shape above.
2. *The bootstrap reads its own pillars.* =curve_republish_service= stops reading one
   =source_series_id= and reads, per pillar, the series the key above projects to:
   resolve the pillar's start and end tenor codes to dates through =refctx=, call the
   same builder, which takes the currency the config names (#2375). Then the reader finds
   the series by identity and takes its observation. The rate map is
   keyed by the pillar's =end_tenor_code=, which is what =resolve_bootstrap_pillars()=
   already matches on, so its contract does not change. The fallback and the lineage
   are in the note below, which also records what this step's proof is and what it is
   not.
3. *The seed stops seeding the grid, and the column goes with it.* Delivered:
   =marketdata_market_series_fomc_populate.sql= seeds the curve row alone, and the
   bootstrap config's =source_series_id= left the model, so the domain, protocol,
   entity, mapper, history field mapper, generator, service, shell command, recipe,
   TypeScript twins and create script are regenerated and a migration drops the
   column with the check that kept it apart from =output_series_id=. The reader's grid
   fallback went with the column, because the config no longer names a grid to fall
   back to. The lineage's column of the same name stays.
4. *The constraints and the deletion.* Started: =oresmd_uri= is not null and is the
   natural key with =party_id=, and the triple no longer keys the row (see the
   identity note below). What is left of this step is =series_type=, =metric=,
   =qualifier=, =ore_key= and the import classification table going, with the
   census's 21 + 32 C++ files, 4 SQL files, 2 TypeScript twins and 80 org documents
   as the checklist. The triple readers and their fallbacks go last, because they are
   what keeps a half-migrated database reachable in the meantime.

**The identity is the key, and what that costs.** =market_series.oresmd_uri= is not
null, non-empty, and unique with =party_id=; the registry's three columns no longer key
the row. Two writers had to change with it, because both could previously store a row
with no identity at all: the import drops a market-data key or an index name the
grammar cannot name, and the ingest loop drops a tick whose key it cannot name, each
reporting what it dropped. The corpus names every key it carries -- 485606 of 485606
instrument keys and 156 of 156 index names -- so no corpus row is dropped. What this
loses is a key the registry accepts and the grammar does not, such as the short
=IR_SWAP/RATE/EUR/2D/1D= the import used to store with no point: a row no reader could
find once the identity keys the catalog is a row that should not be written, and the
unit that pinned it now pins the drop. The generator's rows cannot collide on the
identity, because the party is generated per row and the party is part of the key --
which is the answer to the review question that asked whether its counter was enough.

**Step two, delivered.** The reader stands on four things, and all four exist now.

- The key builder sits in =ores.marketdata.core=, as a hand-written source
  (=oresmd/pillar_quote_key.cpp=) beside the parser and the projections it goes through,
  registered with =regenerate_cmake_component_files.py --component ores.marketdata.core=.
  It returns the pillar's ORE key and, beside it, the series identity that key projects
  to, so the feed's writer and the bootstrap's reader cannot disagree about the spelling.
  The feed's own copy is gone: =ir_curve_feed= calls the shared builder.
  =ores.synthetic.api= links =ores.marketdata.core.lib=
  (=projects/ores.synthetic/api/src/CMakeLists.txt=), and the =reachability= gate is green
  on this tree with that link in it.
- The currency exists now: the config names it (#2375), and the reader takes it from
  there rather than from a series' spelling.
- The dates exist now: =resolve_tenor_date()= turns a pillar's start and end tenor codes
  into calendar dates, which is the path the discount curve's own points already take.
- The fallback arrived with the reader and went with the column it read (step three): a
  pillar whose series is absent, or whose series carries no quote at the point the read
  derived, now gets no rate at all, and =resolve_bootstrap_pillars()= fails loudly on
  it. The plan said =curve_republish_resolver_fomc_tests= seeds the grid and would prove
  that path. It does not, and the correction stands: the case is a unit test of
  =resolve_bootstrap_pillars()= that hands the resolver an in-memory rate map, so it never
  reads a series at all. The reader's own path is proved by four database-backed cases
  instead -- a pillar read from its own series, one with no series, one whose series has
  no quote at its point, and the lineage the mixture pins -- added when the review asked
  for them.

The lineage follows the reader: it lists the series each pillar was taken from, so a
curve's provenance names its quotes rather than the grid they used to land in. A
PROJECTION config names its discount curve's own output series there too -- the row the
discount points are read from -- where the earlier form named that curve's *config* id,
which is not a series.

The one thing the plan does not do is keep two writers: the feed either publishes the
grid's key or the pillars' keys, never both. The fallback above is a *reader*
tolerance, so a database written before step one is still readable after step three,
which is the same reason the identity lookups fall back to the triple.

* Result

The additive half of the identity cutover is delivered. =market_series= carries
=oresmd_uri=, and both writers of series rows supply it: the import, from
=from_ore_key()= for a market-data key and from =from_index_name()= for a fixing's
index name -- the latter's first production call site -- and the ingest loop, which
derives it from the =ore_key= it already builds. The repository reads by identity
through =read_latest_by_uri=, declared in the model beside the triple reader, and
the import's and the ingest loop's lookups ask by identity first and by the triple
after it, for a row written before the column existed.

Nothing is deleted. The triple still keys the row, so a series with no identity is
still reachable and the component cannot be stranded by this change. Measured on the
rebuilt tree: 1782 assertions in 400 cases, including a case that imports one key
from each space and reads the series back by its identity and by its triple, both
agreeing. Component drift is clean for =marketdata= at all eight addresses,
including the entity that gained the column.

**A second unit, on the same column, made the identity name a series rather than a
datum.** The import projected the file's whole key and the ingest loop projected the
triple alone, so a series' identity carried whichever of its points arrived first and
a swap series got none from a live tick at all. =to_series_uri()= projects the
identifier with its point dropped, both writers call it, and the ingest loop builds
the datum's full key before falling back to the triple. Two IR families kept their
coordinate where that projection did not look -- a discount curve's maturity and a
future's contract code and tenor -- and it now drops those too, with a case walking one
two-point pair per family and three pairs that must stay apart, which is what guards
the drop against over-clearing. Measured on the rebuilt tree: 1839 assertions in 403
cases.

**A third unit put the grid's pillars on their own identities.** The builder that spells
a pillar as the OIS quote the feed simulates moved into =ores.marketdata.core=, beside
the parser its identity goes through, and the bootstrap reads each pillar's observation
from the series that key names, scoped to the config's party. The lineage names the
series each pillar was read from, in place of the grid they used to land in. Measured on
the rebuilt tree: 1865 assertions in 408 cases, and 178 in 27 for the service, including
the reader's database-backed cases. The plan's claim that the resolver's FOMC case seeds
the grid was wrong and is corrected in place; the reader's path it was said to prove has
cases of its own, added after the review.

**A fourth unit dropped the grid and the column that named it.** The FOMC seed writes the
curve row alone, and =source_series_id= left the config's model, taking the reader's grid
fallback with it: a pillar whose series is absent, or carries no quote at the point the
read derived, now gets no rate and the bootstrap fails loudly on it. The removal
regenerated the config's addresses -- domain, protocol, entity, mapper, history field
mapper, generator, service, shell command, recipe and the TypeScript twins -- and a
migration drops the column, with its check, from a database created before the change.
Measured on the rebuilt tree: 176 assertions in 28 service cases, 4284 in 1518
shell-refdata cases, and 588 in 81 refdata-api cases, with the ER diagram regenerated.

**A fifth unit made the identity the key.** =oresmd_uri= is not null, non-empty and
unique with =party_id=, and the registry's three columns no longer key the row; a
migration backfills a row that has none from its own uuid and takes the triple's unique
index with it. The import and the ingest loop each stop storing a row they have no
identity for: the import drops a market-data key or an index name the grammar cannot
name, and the loop drops a tick whose key it cannot name, both reporting what went. The
corpus names every key it carries, so no corpus row is dropped, and the one case that
pinned a short key's empty point now pins the drop instead. Measured on the rebuilt
tree: 1879 assertions in 412 core cases, 176 in 28 service cases, 144 in 51
shell-marketdata cases and 71 in 14 marketdata-api cases.

Three measurements taken here changed the plan rather than the code, and each is
recorded with its number:

- the =feed_binding= column cannot be written, because its only writer is a generated
  service with no derivation hook and a model's generator block feeds test data;
- the column cannot be made =not null= yet, because the FOMC bootstrap seeds a series
  under the synthetic pipeline's own vocabulary, which no projection can name -- the
  replacement is the instruments' own ORE keys, decided above;
- =marketdata= is one modelling pass short of =COMPONENTS_UNDER_TEST=, because seven
  hand-written protocol headers carry no TypeScript twin and a twin is generated from
  an operation model. Listing the component was tried and reverted, and the modelling
  pattern to follow is read off =ores.variability.operations=.

What the deletion still owes is recorded where it belongs: the internal series'
identity, a backfill or a recreated database, the unique index on the identity, and
the behaviour that a write omitting the identity clears it until the column is
=not null=.
