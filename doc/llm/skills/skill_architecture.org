* Summary

This document is the hub of the /compass skill framework/. The objective of the
framework is to define an ontology of core domain concepts and their associated
operational processes. Together these establish the computational primitives
required for humans and [[id:0D919421-2B73-4322-9F79-9FDA38A67EA1][large language models]] to operate agent harnesses
autonomously or semi-autonomously. The framework rests on academic foundations,
principally [[id:74C5D8A2-F781-4E23-A6FC-2921AD5879AD][Cybernetics]] and [[id:BA0E3273-DC4B-7CD4-447B-06227B7D09A8][MASD]], and on empirical foundations drawn from
[[id:4ACD003D-5CEB-4D2E-BE10-BA77D1043FB8][skill collections]] published by other developers. We have attributed provenance
as fully as we can; report any citation we have missed.

The hub introduces the principal concepts and links to the spoke pages that
treat each in detail. It defines the key concepts of the framework, describes
the entry points into the model, and closes with an index of the pages that
compose it.

* Detail

** Key Concepts

A skill in agent tooling is "a document that an assistant loads to perform a
/kind/ of work" (/c.f./ [[id:4ACD003D-5CEB-4D2E-BE10-BA77D1043FB8][Agent skills]]). The compass framework refines that
general notion: a [[id:87D41A08-0B37-41CE-8483-B59B36BA87FA][skill]] is one /action/ applied to one /typed target/. Compass
represents a skill as a document type, one of many defined by the [[id:8B29A8D8-E004-4E87-B81D-ABEAF68F2B98][documentation
ontology]]; that same ontology supplies the types the targets are drawn from. The
framework also builds on ideas taken from [[https://flaviocopes.com/pstack/][pstack]] and from open-source tooling
such as [[https://karthinks.com/software/fifteen-ways-to-use-embark/][Emacs' embark]], both analysed as prior art and in places adopted
/verbatim/.

That analysis yielded a small and consistent action model composed of three
concepts.

- *[[id:F5CB5A45-6557-410B-9E4F-542957561A16][Planes]]*. Artefacts are classified by the relation an agent bears to them:
  the agent /loads/ grounding, /cites/ a stance, /sequences/ a method,
  /executes/ an action, /declares/ a specification, and /convenes/ a
  deliberation. The [[id:F5CB5A45-6557-410B-9E4F-542957561A16][planes]] document treats the taxonomy and its rationale.
- *[[id:3018B7FE-2DF7-49E5-A57F-A75C02C4D498][Dispatching]]*. Operations are registered against a target's /type/ rather
  than against the command that produced the target. Applicable verbs are
  therefore computed rather than remembered, which removes the combinatorial
  growth to which a hand-written catalogue is prone.
- *[[id:5365DE9F-E3F9-4B5F-ACC1-B347B5FCE2A9][Functions]]*. Actors declare a function, whose [[id:926B916E-A57E-498E-99AB-720B583C0362][cybernetic level]] determines the
  relevant subset of the catalogue. The filter is a default at most levels: an
  agent sees a smaller catalogue but may reach outside it on request. At the
  audit level alone the filter is a constraint rather than a default, since an
  auditor that can be persuaded to modify what it observes is not an auditor.

The framework applies these concepts to carry a /unit of work/, most often a
[[id:31C868B9-306E-4282-BA8C-07E647021B34][task]], from an unverified beginning to a verified end. A [[id:E8311826-9900-4932-AFFB-A8AF663414DF][method]] governs the
passage, and its phases are determined as the work proceeds rather than fixed in
advance. Each phase cites the principles that govern its judgement and calls the
actions that operate on the relevant artefacts, preferring [[id:D8CB6EED-1F6A-4EE5-840B-2FE28DE17911][generated]] structure
wherever generation is possible. The extent to which the work must climb the
[[id:DEE49C55-1626-470D-BB0F-D58A11D35769][verification]] ladder follows from what it changed. An agent may be configured and
[[id:54AD5986-34A0-4B19-9F20-D9A024225036][left running]] against a checkable finish condition.

** Entry Points

The composition model is independent of any particular way of using it. Three
entry points are supported, and none is privileged over the others.

The first is to *invoke an action*, where both the operation and its target are
already known. The second is to *dispatch on a target* with =compass-act=, where
the target is known and the operation is not. The third is to *enter the mode*
with =compass-helm=, which declares a function, matches the work to a method,
and routes to the other two as the method's phases fire.

The mode is a convenience over methods rather than a precondition for them: a
method may be invoked directly, as may an action. Separating the three in this
way allows each to be exercised and tested on its own.

** Terminology

The framework uses a fixed vocabulary. The [[id:47341FC6-B8FB-499E-AAE0-F4EE0ABFDA05][glossary]] is the register of record;
the table below fixes usage within the framework and names the terms it retires.

#+ATTR_HTML: :class hug-leading
| Concept                          | Term      | Retired synonyms                     |
|----------------------------------+-----------+--------------------------------------|
| A unit of work an agent executes | task      | ticket, issue, unit, slice           |
| A body of related tasks          | story     | epic, spec, map                      |
| A recorded idea, not yet work    | capture   | backlog item, inbox item             |
| The approach to a kind of work   | method    | playbook, flow                       |
| The sticky posture for a session | mode      | stance skill, style, persona         |
| A rule that is cited, not run    | principle | rule, guideline                      |
| A durable fact about the domain  | knowledge | research note, doc, ADR              |
| Intended behaviour, checkable    | spec      | never used for a story plan          |
| The role a session adopts        | function  | persona, agent type, role            |
| Any LLM process doing work       | agent     | bot, assistant                       |
| The agent a human talks to       | session   | main agent, parent, the LLM          |
| An agent spawned by another      | delegate  | subagent, worker, child agent        |
| The typed thing acted upon       | target    | object, candidate, entity            |
| The operation applied to it      | action    | command, verb, skill                 |

Three terms admit a misreading and are worth stating negatively. /Spec/ denotes
an Allium specification and nothing else; a story's plan is a *plan*. /Persona/
denotes a Council member and nothing else; the role a session adopts is a
*function*. /Agent/ is the general term for any process of this kind and
therefore names no role: the level designated S1 is called Agent, but it is a
function, adopted by a session or a delegate.
