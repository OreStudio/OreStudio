* Acceptance

- The specification validates with the Allium tooling.
- Each obligation names the rule identifier it encodes.
- The propagate skill lists the tests the specification requires, and the third story takes that list.

* Plan

Take the behaviour rules the audit named: the stale rule, the edit in progress,
the stale write, the reasons that follow the change, create, delete, revert,
links against parts and the access rule. Model the domain they move: the
record and its versions, the change news, the screen and the dialog with its
state machine. Write one rule or invariant per behaviour, each naming the
identifiers it encodes, in the house style of the existing specs. The look
stays out. The Allium CLI is not installed, so the test obligations are derived
by hand from the test generation taxonomy, one row per construct, as evidence
beside the task for the harness story.

* Result

=doc/llm/specs/record-screen-behaviour.allium= states the record screen's
behaviour in 25 rules, 9 invariants and 2 surfaces,
citing 42 rule identifiers. The Allium CLI is not installed in this
environment, so the specification is unvalidated by a tool and its test
obligations, 44 of them, are derived by hand in
=evidence/record_screen_test_obligations.org= for the harness story. Fifteen
need a second browser or account, two a controllable clock, and one is an open
question for the owner: whether Refresh after a write returns to the first
page always or only when the sort could move the record.
