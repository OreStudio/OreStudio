* Acceptance

- The ORE service answers a request for one configuration with the ORE XML text, built from the stored configuration, products and parameters, read through analytics' own messages ([[*What the specification changed][What the specification changed]]).
- The XML is a valid PricingEngines document: each product names its type, model and engine, and each parameter sits under its model or engine node with its name and value.
- The BFF serves =GET /api/reporting/pricing-engines/:id/ore-document=, and the configuration page has an Export button that saves the file the server names.
- ores.shell has a command that exports one configuration to a file or to standard output, and a test proves the output.
- A test compares the export of one configuration with the XML ORE would read, character for character, and a round-trip test reads the export back with the projection that writes it.
- The export refuses a configuration that does not exist or that the session's party cannot see, naming the reason.

* Plan

** The shape

The document is the one ORE reads, at =Examples/ORE-API/Input/pricingengine.xml= in the ORE source:

#+begin_src xml
<?xml version="1.0"?>
<PricingEngines>
  <Product type="Swap">
    <Model>DiscountedCashflows</Model>
    <ModelParameters/>
    <Engine>DiscountingSwapEngine</Engine>
    <EngineParameters/>
  </Product>
  <GlobalParameters>
    <Parameter name="ContinueOnCalibrationError">true</Parameter>
  </GlobalParameters>
</PricingEngines>
#+end_src

The products come first, in their stored position. Each carries =Model=, =ModelParameters=, =Engine= and =EngineParameters= in that order, and an empty section is a self-closing element. The global parameters are one =GlobalParameters= block after the products. A parameter is =<Parameter name="...">value</Parameter>=, the value escaped, and a section's parameters follow their stored position. The model and engine are the pair the configuration holds; a product with neither cannot be exported.

** The server operation

The analytics service owns the document, so the operation lives beside the save: a =export_pricing_engines_document_request= carrying the configuration id, and a response carrying either the XML text or the reason it was refused. One handler reads the configuration, its products and its parameters, checks the party, and writes the document with pugixml, so the escaping and the self-closing sections are the library's and not string concatenation. It refuses an id the party cannot see and an id that does not exist, and it names the reason in the reply.

The BFF adds =GET /api/reporting/pricing-engines/:id/export=, which asks the service and answers =application/xml= with a =Content-Disposition: attachment= whose filename is the configuration's name. The screen's Export button calls it; the button is not a client-side generator, because the XML is the service's answer and ORE's format is not the screen's to own.

** The shell command

=ores.shell= gets =pricing_engines export <id> [--file <path>]=. It sends the same request and writes the text to the file, or to standard output when no file is named, so a person can pipe it into ORE. Its test asserts the text, the refusal of an unknown id, and the file written.

** The tests

- A golden test exports a seeded configuration and compares the document with the XML ORE reads for the same configuration, structure and values, with attribute order stated by the test rather than by the writer.
- A round-trip test parses the export with pugixml and asserts every product, model, engine and parameter against the stored rows.
- A refusal test asserts the message for an id that does not exist and for one the party cannot see.
- The shell test asserts the command's text and its file.

** The order

1. The analytics request, handler and writer, with the golden and round-trip tests at the service.
2. The BFF route, with a test that the content type and the filename are the configuration's.
3. The screen button, checked in the browser with Playwright by downloading the file.
4. The shell command and its test.

The export is read-only: it writes no row and records no history.

* What the specification changed

The plan above predates the [[id:2BF7F03F-6BF4-45FF-8E26-4D3B4E2D943D][Record screen standard]]'s Import and Export section and the [[id:E69C008D-7092-4855-98EC-47A75F422F61][Configuration screen standard]]'s Export section, which were written after it. The build follows the specification. Where the two differ:

| The plan said | The specification says, and the build does |
|---------------+--------------------------------------------|
| The operation lives in the analytics service | Every =ore.v1.ops.*= operation lives in the ORE component (RS-ORE-06), so =ore.v1.ops.export_pricing_engines= is served by =ores.ore.service=, which reads the configuration through analytics' messages under the caller's delegated session |
| =export_pricing_engines_document_request= | The verb-first name =export_pricing_engines_request= (RS-ORE-06) |
| The request carries the configuration id | It carries the *reporting configuration* the record fills, which is what analytics finds a document by. The BFF and the shell join the id the screen shows to it |
| The BFF route is =/api/reporting/pricing-engines/:id/export= | The spec's shape is =GET /api/<kind>/ore-document= (RS-ORE-06), with the id the screen names |
| The file is named after the configuration | The name is the =name_pattern= of the file type row whose =configuration_type_code= is =pricing_engines= (RS-ORE-01): =pricingengine.xml=. The configuration's own name is not a file name |
| A golden file beside the test | An exact-string test of the whole document, and a round trip through =pricing_engine_projection= |
| The handler checks the party itself | Analytics refuses a configuration the session's party cannot see, in its own words, and the handler answers those words |

Two further points, neither a defect:

- The run parameter that =configuration_type.run_parameter= records may override the name for a run. The export is a screen and shell action on a configuration, not a run, so it writes the table's name pattern as it stands.
- The projection's =write= states the schema-driven emitter, and this exporter states pugixml. The two differ on one point: an empty =GlobalParameters= is written by the exporter, because the specification says an empty section is an empty element, and left out by the emitter, because an absent block maps to the same rows. Both documents ORE reads.

* Notes

- Nothing here generates XML in the browser. The screen holds the document, but the format is ORE's and the service is the one place that knows how the stored rows map onto it.
- The value is written exactly as stored. The value set check already guards what a value may be, so the writer does not reformat numbers, dates or booleans.
- =GlobalParameters= is a root-level block in ORE's format, not a child of a product.
- The ORE source's example file at =Examples/MarketRisk/Input/Correlation/pricingengine.xml= is the reference for the shape. There is no golden file: the test states the whole document as a string, so a change to the shape fails it where a golden file could be regenerated without a reader noticing.

The click itself was not driven through a browser.

The name came from =ores_reporting_file_types_tbl= (row =setup.pricingEnginesFile=, configuration type =pricing_engines=, kind =input_document=, direction =input=, name pattern =pricingengine.xml=).
