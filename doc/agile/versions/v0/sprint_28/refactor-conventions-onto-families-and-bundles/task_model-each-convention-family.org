This page documents a [[id:31C868B9-306E-4282-BA8C-07E647021B34][task]] in the [[id:0781E7E1-EF38-4030-8627-13210FA75792][Refactor conventions onto families and bundles]] story. It captures the goal, current status, acceptance, and any notes or results.

* Goal

Every convention family is declared once, in its own entity, and carries only its own fields. The list of families is generated from those entities, and so is the code that writes and reads them. No type holds every family, so no translation unit has to reflect them all.

* Acceptance

- Each convention family is its own entity with its own fields, and a family's field belongs to it alone.
- One generated registry names every family, its scope, and its repository, and the hand-maintained list is gone.
- The apply code that writes the families is generated from the same registry, so adding a family needs no hand edit.
- No reflected type in refdata carries every convention family, and no translation unit instantiates one.
- =conventions_document=, =conventions_document_service= and the whole-document protocol operations no longer exist.

* Plan

The work ran in two halves, and the halves are why the task is still open.

The first half generated the family list and the per-family apply, and it is merged. Before the hand list was touched, the registry was compared with it. The two agreed on 26 families, on the same party and world scopes, and on every row the service wrote, which is what made the swap safe. The apply could not come from the registry alone, because a table of strings cannot call a typed repository, so the same generation emits a branch per family.

The second half is the deletion, and it forces its callers to move in one wave. =conventions_document= is the payload the ORE mapper builds and reverses, and the run store is the service's only production caller. Deleting it means moving the whole-document service, the six generated apply and read functions, the mapper pair, the legacy importer and exporter, the diff, the service import and the run store onto the bundle.

** The shape the deletion builds towards

Chosen on 2026-10-18 from three designs scored against this task. The scored designs and the synthesis are in [[file:evidence/the-package-design.md][the-package-design.md]].

A family is a registry key and one payload per row, where a payload is that row serialised as its own generated type. Nothing else identifies a family.

=refdata::service::conventions_bundle= holds rows of ={ family, sequence, payload }=, and no member is a family's value type. It arrives hand-written in the first step, because the shape is still moving, and moves into generation when the per-family units land. =conventions_bundle_service::apply(bundle)= is the only writer and ::read(party) the only reader. Neither opens a unit of work, so the commit passes its transaction and the run store passes its own.

The two tenor basis swap obligations become the prologue and epilogue of =apply=, in the caller's transaction. The prologue resolves the identity after stamping, because the identity is the party, the kind and the name, and the mapper cannot state the party. The epilogue closes the omitted leg form after the writes. The writer decides the write order for the shared family: it writes the central row and then its two part families in code, so the foreign key that a part carries to its central row holds whatever order the bundle is in.

=ores::ore::domain::conventions_package= belongs to ores.ore. It holds one bundle and the FX projection, which is a projection of three entities, is never stored, and never crosses the boundary. =split_conventions= and =join_conventions= replace =conventions_mapper::map= and =reverse=.

Both directions are generated one family per translation unit, with a dispatch unit that includes only declarations, so no unit reflects two families. A =convention_family_key= enumeration is generated from the registry with a =static_assert= tying it to the table. A codegen gate holds a translation unit to one reflected family, so the aggregate cannot come back quietly.

The plan is five steps.
1. Pin today's behaviour. Tests only, with byte equality on exported files and canonical row facts, so every later step is judged against them.
2. The refdata write side and read side. The bundle, the per-family units, the obligations, and the commit on top of them.
3. The ores.ore boundary. The package and the generated bindings, with both callers moved and a declared bridge through the transition.
4. Delete the aggregate, the service, the six bulk functions and the model section, retiring the bridge.
5. The translation-unit gate, and the measurements this task records.

Step 3 arrived in one change. The package, its two directions, the tests that compare it with the document and the move of both production callers all came together, so the new shape had callers from the first commit. The bridge is the mapper pair itself: =map= and =reverse= still turn a document into the rows the legacy file importer and exporter, the diff and the tests work in, and step 4 removes them with the type.

* Notes
- Step 1 is merged: the export of all seventy-two corpus files is pinned by
  digest, and the rows an example import writes are pinned by reading the
  tables directly.
- Step 2's write side is merged. =conventions_bundle_service= applies a bundle
  of family payloads in the caller's transaction, the two tenor basis swap
  obligations now live in =conventions_identity= and are called by both write
  paths. The writer gives the shared family its own order, and the commit
  sorts its staged rows into registry order so the rows and the reported
  outcomes do not depend on the order the stages landed in. The staged path
  gains the obligations it lacked, which is a behaviour change and the one this
  step declares.
- The registry does not yet say which families are one bundle. The bundle
  service names the three tenor basis swap families by hand, and the commit
  sorts by the registry's alphabetical order. A registry field that states the
  dependency order would remove the hand list and make the ordering rule
  explicit.
- The run store has no unit of work, so it applies a bundle without one and
  the import is still not atomic. The bundle service takes the caller's
  transaction, so the fix is the run store opening one, not a change in the
  service.
- Step 2's read side is merged. The generated fragment now carries
  =read_family_payloads=, one branch per family, and
  =conventions_bundle_service::read= assembles every family the session sees
  into one bundle of payloads. The shared convention family is narrowed to the
  kind this bundle covers, because that one table carries every kind. A test
  proves the bundle read carries the same rows as the document read, which is
  the bridge the next step removes.
- Step 3 is in review as #3562. =ores::ore::domain::conventions_package= holds
  one bundle and the FX projection, and =split_conventions= and
  =join_conventions= are the two directions over it. The package is now what
  crosses the boundary: the run store and the run configuration operations both
  read into it and write from it, and neither of them assembles a document any
  more. The run configuration operations lost the whole-document reflection that
  turned a document into generic JSON and back; per-row =rfl::json= remains,
  because a payload is a row.
- An import now applies one row at a time: =apply_staged_family= decodes one
  payload and writes it, and the row helpers read the family's table on every
  call. The document path read a family once and wrote its rows together, so a
  family of many rows costs a read per row where it used to cost one. That is
  the shape the staging path already had, and the fix is the per-family apply
  the next two steps write: one call per family carrying its rows.
- The FX convention is the only part of the package that does not enter the
  bundle, and that is what the projection means. It comes back on the export
  only when the same package is joined, which is why the store never returns
  one: the three entities it is a projection of are the store, and the read
  does not assemble them.
- The per-family translation units are not generated yet, so the staged apply
  and the payload read each compile one branch per family in a single unit.
- The pin holds. Comparing the service's hand-written calls with the generated
  registry gives 26 families against 26 entries, no disagreement about which
  families are party-scoped and which are world-scoped, and no registry row the
  service never writes. =fx= is skipped and unregistered, as decided. The
  registry is therefore equivalent to the hand list before the hand list is
  deleted.
- The registry cannot replace the calls by itself. A table of strings cannot
  call =replace_party_rows(ctx, zero_convention_repository(), ...)=, because
  each family needs its own repository type. The dispatch has to be generated.
  Codegen must emit one apply function per scope from the same registry:
  party families through =replace_party_rows=, world families through
  =add_missing_world_rows=, and the skipped families collected. The service
  then calls two generated functions instead of listing 26.
- The work splits. First the generated apply functions, which delete the
  service's hand list with behaviour unchanged and the pin green. Then the
  aggregate itself, which is what forces the mapper, the run store and the BFF
  to move in one wave.

- =fx= needs no entity and no registry entry. The document carries an
  =fx_convention= that is the pair, its =currency_pair_convention=, a spot lag
  and its advance calendars. All three of those are entities
  (=currency_pair=, =currency_pair_convention=, =currency_pair_convention_calendar=),
  so the ORE FX convention is a projection of existing rows, not a store of its
  own. Drop it from the document and derive it in the boundary mapper.
- The tenor basis swap family registers as its central row plus its two parts,
  because that is what the document carried. Collapsing it to one family entry
  is a later decision, not part of this task.
- The registry started as a python renderer and is now a codegen facet with
  three archetypes, so a template change replaces a script change. The emitted
  bytes did not change when the renderer was retired.
- What the deletion still has to move, as the tree stands on 2026-10-18. The
  aggregate is declared in
  =projects/ores.refdata/modeling/ores.refdata.configuration_document_messages.org=
  and generated into =ores.refdata.api/messaging/configuration_document_protocol.hpp=.
  In refdata, =conventions_document_service= is the only service that builds
  it, and the run store is the service's only production caller. The service
  also drives the six generated bulk functions in =convention_family_apply.inc=,
  and those functions, not the per-family dispatch, are what reach the type.
  ores.ore holds the type besides, in the mapper pair, the legacy importer and
  exporter, the diff, and the service import. The tests that pin the current
  behaviour are =conventions_document_service_tests= and the conventions half of
  =run_store_database_tests=.

- Two modelling comments still repeat claims this task's record no longer makes.
  =bundle_import.hpp= and =ores.refdata.bundle_import.org= describe a sweep
  that marks stale imports expired, and a failed commit that marks an import
  failed, and nothing performs either.

* Result

Not yet complete. Merged so far are the per-family entities, the generated registry, the generated per-family apply in its own translation unit, and the generated per-family read. The ORE boundary package is in review as #3562. The aggregate itself is still present, so the task's headline acceptance criterion is not met.

The boundary is what step 3 changes, and it changes it in the direction the deletion needs. The two run import paths no longer move conventions through the document: the run store and the run configuration operations each split a file into a package and apply its bundle, and each joins the bundle the read returns. What still names the type is the legacy file importer and exporter in ores.ore, =conventions_difference=, the whole-document service in refdata, and the tests that compare the package with the document. Those are step 4's work, and they go with the type rather than before it, because a comparison against the old shape is what proved the new one.
