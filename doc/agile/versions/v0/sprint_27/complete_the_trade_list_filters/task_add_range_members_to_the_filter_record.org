* Result

A filterable column that holds a date or a timestamp now has a =_from= and a =_to= member in the filter record. The generator derives them in =filter_members=, the one list the record, the repository condition and the service guard all read, so the three cannot disagree.

*The rule, as built.*

- Both members carry text on the wire, in the form =as_of= takes: a date, or a UTC timestamp.
- On a date column the bound is the date. On a timestamp column a date means the start of that day for =_from= and its last microsecond for =_to=, in UTC. A UTC timestamp is the bound itself.
- Both bounds are inclusive, an absent bound sets none, and a null column never matches.
- A bound that is neither, or a date that is not on the calendar, is refused by the service with the new outcome code =filter_range_invalid=, which names the member and the text. The repository throws =std::invalid_argument= for the same input, as it does for an unsortable field.

*What it needed.* A new outcome code in the outcome catalogue. =at_least= and =at_most= beside the other conditions. =range_bound= in its own header, used by the service to validate and by the repository to build the condition. =filter_value= overloads for a date and a timestamp, so the equals and one-of members of such a column compile.

*Found.* =parse_as_of= accepts a date that is not on the calendar, such as 30 February, because the time library normalises it. A range bound checks the calendar itself. The same leniency still holds for =as_of=, which this task did not change.

*Proved on.* The booking's =trade_date= and =execution_timestamp=, now filterable. The trade summary reads them.
