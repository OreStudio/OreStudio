This page documents a [[id:31C868B9-306E-4282-BA8C-07E647021B34][task]] in the [[id:4AD7DD1A-3E8C-4B97-BC38-149A66F59250][Carry one hundred thousand feeds on the data path — the remaining work]] story. It captures the goal, current status, acceptance, and any notes or results.

* Goal

Every service reaches postgres through pgbouncer, and every query a service
runs goes through its context's pool: a repository, a statement or a raw-SQL
helper. Two changes make this so.

- The raw-SQL helpers (=execute_raw_*= and =execute_parameterized_*= in
  =bitemporal_operations.cpp=) stop opening a connection per call. They lease
  a connection from the context's pool through =database::transact=, so a call
  on a context bound to a unit of work runs on that unit of work's
  transaction, and the tenant, party and actor settings are
  transaction-local, as they are for every other query.
- pgbouncer runs in transaction pooling mode as a systemd unit of each
  environment, beside nats-server, and the services connect to it.

The first change delivers [[id:964B4B51-C5C7-4339-AC51-593CE49CFB07][Run every hand-written query on a pooled connection]], and this task
closes it. The first change comes before the second: transaction pooling hands a server
connection to another client at each commit, so the session-level settings
the raw helpers set today would leak to that client.

* Plan

** Why bother, in numbers

One PostgreSQL server carries six development databases and =max_connections =
1500=. A fleet holds its connections for life: the pool opens every connection
when it is made (=pq/pool.hpp=), and the default size is 2
(=database_configuration.cpp=, =db-pool-size=, with no =ORES_*_DB_POOL_SIZE= in
=.env=). Measured with =pg_stat_activity= while the fleets were idle:

| Database | Connections | Idle |
|----------+-------------+------|
| ores_dev_clever_dijkstra | 38 | 38 |
| ores_dev_festive_dijkstra | 37 | 37 |
| ores_dev_bright_faraday | 13 | 12 |

Thirty-eight idle server connections for one environment that is doing nothing,
at two a service, and ten environments on one instance is four hundred. In
transaction mode the same fleet keeps a handful of server connections and
multiplexes a request at a time onto them; the cap becomes pgbouncer's
=default_pool_size= and =max_db_connections= rather than a sum of per-service
sizes nobody can see.

** Decision 1: prepared statements, which is the real blocker

The repositories run *named* prepared statements. =detail::prepared(sql)= keeps a
per-process cache of =fixed_statement=s named =ores_q_N=, the transaction
pipeline sends =PQsendPrepare= for a name the client connection has not prepared
(=pq/transaction.cpp=, =connection::is_prepared=), and hand-written SQL is sent
unnamed. A name lives on a *server* connection; transaction pooling hands a
different server connection to the next transaction, so a name the client
believes is prepared may not exist, and worse, a name is owned by whichever
client prepared it on a connection both clients share.

Two ways out, and this is the decision to take before the unit is written:

1. *Let pgbouncer track the statements.* pgbouncer 1.21 and later implement
   prepared-statement support for transaction pooling: the client's
   =Prepare= and =Bind= are followed by pgbouncer, which re-prepares on the
   server connection that actually serves the transaction. It needs
   =max_prepared_statements= set to a non-zero value, and it costs memory per
   client and a small protocol overhead. The distro offers 1.26.1.
   Nothing in our code changes, which is most of its appeal.
2. *Send repository statements unnamed too*, as hand-written SQL already does.
   Then no name exists to be lost, and any pgbouncer version works. The cost is
   that PostgreSQL parses and plans every execution, which the named cache was
   there to avoid, and the benchmark that would say whether that cost is real has
   not been run.

Recommendation: 1, with 2 as the fallback if an environment cannot carry a
current pgbouncer, and with the measurement that decides it written into the
task that does it, not assumed.

** Decision 2: the listener does not go through the pooler

=postgres_listener_service= issues =LISTEN= and =NOTIFY= on its own dedicated
connection, not one from the pool (=postgres_listener_service.cpp=,
=connect_utc=), and the event source sits on it. A =LISTEN= belongs to a session,
so transaction pooling would subscribe a server connection that is handed to
somebody else on the next commit, and the notifications would arrive nowhere or
everywhere. The listener therefore keeps a direct connection to PostgreSQL: the
services' options name the pooler's port, and the listener's name PostgreSQL's.
=pgbouncer= can also serve a second database entry in session mode for it, but a
direct connection is one setting and no second pool.

The administrative paths the task already names - =compass db recreate=, the
schema restore - connect directly for the same reason.

** Decision 3: pool sizes become client limits, so they are sized with the pooler

This is why the pool-sizing task under
[[id:A4D0E305-CEF6-4684-ABBA-0D09657479F1][Keep workflow steps alive while they
work, and off iam]] has to be taken with this one rather than before it. Today
=db-pool-size= is simultaneously the service's concurrency and its share of the
server's =max_connections=, because a pooled connection *is* a server
connection. Behind a transaction pooler the two separate:

- the service's =db-pool-size= is how many statements it may have in flight;
- pgbouncer's =default_pool_size= and =max_db_connections= are the server's
  budget, per database and per environment.

So the lanes a step runs (four, in the surfaces and curves and forwards steps)
and the step workers a service runs (two, =provisioning_step_registrar.cpp=)
argue for a *larger* client pool than two, while the server connection count is
capped and shared. Sizing the pool before the pooler lands would size it to the
wrong constraint, which is why that task is waiting on this one.

** What to build

1. The compatibility decision above, with its evidence.
2. A pgbouncer unit per environment: =compass systemd generate= emits it, it
   joins =ores-<env>.target=, starts before every service unit, and its
   configuration lives under =build/config/= with its port in the environment's
   =.env=. Transaction mode, =max_prepared_statements= per decision 1, and a
   =default_pool_size= / =max_db_connections= that states the server's budget.
3. The services' connection options name the pooler's port; the listener's and
   the administrative paths' name PostgreSQL's.
4. The proof: =pg_stat_activity= shows the fleet's connections arriving from
   pgbouncer and the count of them dropping to the cap; a full build, ctest and
   fleet start; Acme provisioning completing; no ERROR or FATAL in the journal.

* Notes

Target state: [[id:42930B6A-544A-4F7E-ACF4-9ABC60F2B408][The environments share the database through a transaction pooler]]. Its caps,
its list of what connects directly and its prepared-statement rule are this
task's specification.

Points to settle in the plan:

- One pgbouncer for the machine or one for each environment. The target doc
  caps server connections for each environment's database and for the
  instance; one pgbouncer in front of the shared instance enforces both. A
  unit for each environment fits =ores-<env>.target= and keeps environments
  independent, but then the instance cap is only the sum of the environment
  caps. Bring the choice to the user with the numbers.

- LISTEN needs a session that stays on one server connection, which
  transaction pooling does not give. The =postgres_listener_service= keeps a
  direct connection to postgres.
- Our libpq layer prepares statements. pgbouncer keeps protocol-level
  prepared statements across transaction pooling only from version 1.21, with
  =max_prepared_statements= above zero. Check the packaged version and set it.
- pgbouncer bounds the server connections. Size =default_pool_size= against
  the fleet (24 services, each with its own pool) and postgres's
  =max_connections=; see the max-connections recipe.
- =database_options= and =context_factory= read the port from the
  environment; decide whether pgbouncer's port replaces =ORES_DB_PORT= for the
  services or sits beside it.
- The unit follows =render_nats_unit= in
  =projects/ores.compass/src/systemd_generate.py=, with tests in
  =test_systemd_generate.py=; =compass env status= and the smoke check should
  report it.
