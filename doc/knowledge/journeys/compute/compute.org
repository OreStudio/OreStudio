*This page is a proposal under review. The activity inventory is complete; the
journey list at the end is the set proposed to write and prototype. Nothing
here is an accepted journey yet.*

* Overview

The compute grid is not one screen. It is a set of things a person wants to
find out and do, and the [[id:5E970C7F-68EA-42BF-B73E-997C4A003762][Operations journeys]]
give exactly one of them a journey: the fleet survey. Everything about the
*work* the grid does — how much is in flight, how busy it is, where the time
goes, why a job failed, what is about to arrive, what capacity it needs, and
what a tenant's own users are running — has no journey at all.

This page states the activities, measures what is missing, and proposes the
journeys that would cover them. It is the input to prototyping them.

* The activities

Each activity is something a person wants to know or do, stated as the person
would state it. The actor is named, because the same question asked by the
super administrator and by a tenant administrator is a different journey over
different rows.

** The super administrator

| Activity | What it answers |
|----------+-----------------|
| Survey the fleet | How many nodes do I have, and are they all reporting? |
| Read the load | How many jobs is the grid working on, and how busy is it? |
| Watch the load over time | Where are the spikes, and is the grid getting faster or slower? |
| Follow one job | Where is this job, what has it cost, and where is its time going? |
| Reproduce a failed job | Give me everything about this job on this node so I can run it here. |
| Pull a node's logs | What did this node say while it was failing? |
| Plan the capacity | What can the grid take, what does a job need, and what is about to arrive? |
| Know what is coming | Which jobs are scheduled to kick in soon? |
| Keep the grid running | Drain a node for maintenance, requeue stuck work, stop a runaway. |
| Keep what the grid can run | Which apps and versions may it execute, and where do their packages come from? |
| Set the concurrency | How many of a thing may run at once? |

** The tenant administrator

| Activity | What it answers |
|----------+-----------------|
| Watch my jobs | What are my users running right now? |
| Read my queue | What of mine is waiting, running and done? |
| Reproduce my job | Give me the details of my job so I can run it myself. |
| See my share | How much of the grid is my tenant using? |
| Act on my jobs | Cancel, re-run or prioritise my own work. |

** Any signed-in person

| Activity | What it answers |
|----------+-----------------|
| Follow my own job | Where did the job I submitted get to? |

* What exists today: one journey of twelve

| Activity | Journey today |
|----------+---------------|
| Survey the fleet | [[id:7B820710-161C-4926-B5AA-5EF2772A3652][Watch the compute grid]] — the summary, the node table and the wrappers |
| Read the load | None. The grid journey states the counters; nothing covers how much work is in flight and how busy the grid is |
| Watch the load over time | None — [[id:E7035C69-EB6E-4158-B384-825A8CDACA8A][The grid has no usage history]] |
| Follow one job | None |
| Reproduce a failed job | None |
| Pull a node's logs | None. [[id:57C4B9A6-DA79-403E-984E-50D2561352B3][Read the telemetry logs]] searches the installation's logs; it does not pull one node's |
| Plan the capacity | None |
| Know what is coming | None |
| Keep the grid running | None |
| Keep what the grid can run | None |
| Set the concurrency | None |
| Watch my jobs, read my queue, reproduce, see my share, act | None — [[id:77DA388B-FC5A-41AE-B88C-4BF34C82D7C9][A tenant cannot list its own jobs]] |
| Follow my own job | None |

Eleven of the twelve have no journey.

** The legacy surface agrees.** The retired =ores.qt/compute= client carried
=HostMdiWindow=, =BatchMdiWindow=, =WorkunitMdiWindow=, =ResultMdiWindow=,
=QueueMonitorMdiWindow=, =QueueChartWindow=, =ComputeConsoleWindow=,
=ComputeDashboardMdiWindow=, =ConcurrencyPolicyController=, =AppMdiWindow=,
=AppVersionMdiWindow=, =TransferProgressDelegate= and the =Report*= family.
Not one of them has a journey behind it. The legacy client is not the target —
the journeys are — but its breadth measures what is missing.

* The journeys proposed

Super administrator, in the compute group:

1. *Watch the compute grid* — the fleet, the nodes and the wrappers. Exists;
   it needs the whole-grid read and the failure fields before it is true.
2. *Read the grid's load* — how much work is in flight, how busy the nodes
   are, the throughput, and how that moved over the last day and week.
3. *Follow a job* — one job end to end: its state, its node, its timings, its
   inputs and outputs, and where its time went.
4. *Reproduce a failed job* — everything about a job on a node, and that
   node's own logs, so it can be run again locally.
5. *Plan the grid's capacity* — what the nodes have, what a job needs, and
   what is scheduled to kick in soon.
6. *Keep what the grid runs* — the apps, their versions and their packages,
   and how many of a thing may run at once.
7. *Keep the grid running* — drain, requeue and stop. Control rather than
   observation, and the one proposal I would defer.

Tenant administrator:

8. *Watch my tenant's jobs* — what my users are running, waiting on and
   failing.
9. *Reproduce one of my own jobs* — the same detail as the administrator's,
   narrowed to my own work.

* Open questions

- *Where does control end?* Reading is the Operations area's mode today.
  Draining a node and requeuing work are not reads, and they may belong with
  the scheduler journeys rather than here.
- *Jobs versus the scheduler.* "What is scheduled to kick in soon" is the
  scheduler's question, answered by =ores.scheduler=; the grid's is what those
  arrivals will do to the load. The two journeys must not both own it.
- *Jobs versus reports.* A report run submits a batch of workunits; the
  [[id:1805BAFC-7E43-4D9C-822F-17C3455C6E00][Compute job lifecycle]] is the
  flow between them. Each journey must say which end it starts from.
- *The tenant's own rows.* The tenant journeys are ordinary tenant-scoped
  reads; the installation's fleet is not
  ([[id:5A5D6490-AF64-4AAF-8B3D-48EF3EDAF3D2][Tenant ownership and the information flow]]).
  They are two actors over two ownership classes, not one screen with a
  filter.
