* Goal

A member asks for a role and an administrator answers. The role request is the
first approval kind: IAM records which roles a request asks for, raises it in
the inbox as the person, and grants the roles once the request is approved.

* Acceptance

- The role grant request and its roles are codegen models with keys and
  foreign keys, the request keyed by the inbox request it details.
- Asking refuses an unknown role, a role already held and a role already
  waiting, and leaves no request behind when its record fails.
- An approved request's roles are granted once, as the approver, with the
  request as the grant's reason, including approvals made while IAM was down.
- The whole flow runs live: a member asks, the administrator approves from the
  queue, the role is granted, and both are told.

* Plan

| Fork | Chosen | Rejected, and why |
|------+--------+-------------------|
| How a request reaches the inbox | One IAM operation raises it with the person's token, then writes its detail, and withdraws it if the detail fails | The browser calling the inbox and IAM separately: two calls, and an orphan request when the second fails |
| How an approval is applied | IAM reconciles approved, ungranted roles at start and on each request change | The inbox calling IAM: the record never writes another component's data; acting on the event alone: the event carries no tenant, and a missed one would lose a grant |
| How IAM reads the inbox | Two security-definer functions owned by IAM | A select grant on the inbox's tables for IAM's role |

- Model the two IAM tables with codegen; the request's key is the inbox
  request's id.
- Write the ask operation as an operation model with a hand-written handler.
- Write the reconcile as a SQL function and a small applier the service runs.
- Switch on shell commands for the role request and approval operations, so a
  script drives the flow live.

* Result

A member asks for roles with =iam.v1.role-requests.ask=, and an approved
request's roles are granted by IAM. Proved live on a freshly recreated and
bootstrapped system with the scripts in =evidence/=: =ashley.moore= asked for
Trading; asking again and asking for a role the account holds were refused as
=already_asked= and =already_held=; =tenant_admin= read the request in the
queue and approved it, and a second decision was refused; IAM granted Trading
as =tenant_admin= with =access.role_change= and "Approved request <id>"; the
administrator was told the request waited, and Ashley that it was approved;
the reconciliation then had nothing left to grant.

Two tests drive the reconciliation against the database: an approved role is
granted once, and a role already held is not granted again. The live run found
one defect, fixed: approvals in a test tenant that had since been removed
would have failed every run, so the reconciliation reads only tenants that
still exist and are not terminated.

Review round 1 found that a role taken away after the grant would be granted
again on the next reconcile. Each request role now records =applied_at=, and
the reconciliation reads only rows not yet applied. A third test grants,
takes the role away and reconciles, and nothing is granted again. The live
flow was rerun on a fresh build: Trading was granted once and marked applied;
the administrator then took it away with =authorization revoke-role=; IAM was
restarted, its start-up reconcile read no rows, and Trading stayed removed.
