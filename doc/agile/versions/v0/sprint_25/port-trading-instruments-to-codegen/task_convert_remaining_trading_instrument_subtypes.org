* Notes

** Follow-up: entire equity_* instrument family missing from drop_trading.sql

Flagged during PR #1874 review: =projects/ores.sql/drop/trading/drop_trading.sql=
has zero =\ir= references to any =trading_equity_*_instruments_drop.sql=
file -- not =equity_position= (the PR #1857 pilot), nor
=equity_forward=/=equity_variance_swap= (this task's entities 3-4), nor
any of the still-hand-crafted equity variants. These =_drop.sql= files
exist on disk but are unreachable dead code: a full =drop.sql= run
leaves every equity instrument table, trigger, and function fully
intact. Pre-existing (predates the pilot), not something to patch
piecemeal per converted entity -- needs a dedicated small cleanup task
wiring up the whole equity_* family in =drop_trading.sql= at once,
mirroring the FX/rates/bond blocks' pattern.

** Composite/leg-bearing entities need a template feature, not just a model

Attempted =composite_instrument= first (after the pilot) since it's
the smallest remaining domain struct (49 lines). Regeneration failed
to build: the hand-crafted =composite_instrument_handler.hpp=
messaging dispatcher calls custom service methods
(=save_composite_instrument(data, legs)=,
=remove_composite_instrument=, =get_legs=/=get_legs_batch=) that
manage the parent + =composite_leg= child relationship
transactionally -- genuine custom logic no codegen service template
currently reproduces. The =Custom repository methods= org heading
exists in the model schema but isn't actually consumed by any
template today (confirmed by grep), so this isn't a quick fix.

=fra_instrument= has the identical pattern with =swap_leg= (custom
=get_swap_legs=/=get_swap_legs_batch=/save-with-legs methods hand-
patched onto its "generated" service file) -- and because
=fra_instrument.org= is permanently blocked from regeneration by task
836BB4CE, this drift has never actually been caught or verified. Any
entity with a *_leg child table (composite_instrument, and
presumably every swap-leg-bearing swap/swaption entity) shares this
gap.

Decision: defer composite_instrument/composite_leg and any other
leg-bearing entities to a follow-up once the service template gains
a genuine paste-block/custom-method extension mechanism (or the
custom methods are otherwise formalised) -- don't force a hand-patch
that would just recreate the same silent-drift problem fra_instrument
already has. Picking flat, single-table instruments first instead.

Also discovered along the way: the shared
=ores.trading.instrument_identity= field-group struct hardcodes the
=instrument_id= field name, so it only fits entities whose primary key
column is literally named =instrument_id= (as in the pilot). Entities
like =composite_instrument= whose PK column is =id= don't fit that
group and would need either a rename (bigger blast radius, changes
the DB column) or to stay flat with no identity grouping (fine --
small entities don't need the C1202 nesting anyway).

** bond/commodity/credit/scripted: blocked by codegen domain-template gaps (2026-08-09)

The Next candidate =bond_instrument= turns out to be anything but flat
-- it is the *most* nested entity in the family. Its hand-crafted
domain decomposes into =instrument_identity= + =bond_terms=
(=security_id=, issuer, currency, face_value, coupon_rate,
=coupon_frequency_code=, =day_count_code=, issue_date, maturity_date)
+ =bond_features= (settlement_days, call_date, conversion_ratio,
=security_id=/=future_expiry_date/=trs_return_type/=trs_funding_leg_code=
-- several *non-persisted* members with no SQL column) + =bond_option=
(option_type, option_expiry_date, option_strike, ascot_option_type --
all non-persisted) + description + audit, per the MSVC C1202
rfl-complexity decomposition (PRs #1047/#1071/#1075/#1083/#1085).
=commodity_instrument= (commodity_terms/commodity_option/
commodity_pricing/commodity_exotic) and =credit_instrument=
(credit_terms/credit_schedule/credit_index/credit_option/credit_tranche)
share the shape; all three also have PK column =id=, not
=instrument_id=.

The codegen domain template supports exactly one shape: the fixed
=instrument_identity= group + flat columns + the fixed audit group. It
has no mechanism for arbitrary nested sub-structs, nor for
non-persisted members, so zero-diff regeneration of the domain class is
impossible for any of the three -- and the alternative (a generated
flat domain) would break every consumer of =bond_terms=/
=bond_features=/=bond_option= (and their commodity/credit equivalents):
persistence tests, the ores.ore XML round-trip mappers, and the Qt
forms. =scripted_instrument= is flat but its PK column is =id=: the
mapper template emits =r.identity.{{column_name}}= keyed on the model
column name while the =instrument_identity= field-group hardcodes the
=instrument_id= field name, so an =id=-named column cannot map into the
group (the hand-crafted mapper bridges the gap by hand:
=r.identity.instrument_id = v.id=). The two options the instrument_
identity note lists are both non-zero-diff here: renaming the DB column
changes =create.sql=, and dropping the identity group changes the
domain shape and its consumers.

Decision: defer all four to a follow-up once the codegen domain
template gains nested-group support (beyond the fixed identity/audit
groups) and a column-name-to-group-field mapping -- the same class of
deferral as composite/fra/swap-legs above, and the same reasoning:
don't force a hand-patch or a shape change that would recreate the
silent-drift problem this task exists to eliminate. The task is
complete at 15/19; the remaining four are feature-gated, not
effort-gated.
