#+title: How do I provision the deployment's secrets into the vault?
#+description: Run compass vault provision once per environment: it writes one consumer and one password per database service, sealed by the vault, before any service holds a token.
#+type: recipe
#+level: cross
#+filetags: :vault:secrets:deployment:recipe:
#+created: 2026-11-27
#+updated: 2026-11-27

See [[id:5FADF948-4520-41D3-B4F0-BE4873C06AF0][Secure Introduction of a Workload to
the Vault]] for why a value has to be written before any service holds a token,
and [[id:DBF20EC5-63BB-4DE5-957C-5322DE0E487F][Secrets Register]] for which
credentials this moves and when.

* Question

How do I put each service's database password into the vault, with the key the
service will answer a challenge with, before the fleet starts?

* Answer

#+begin_src sh :results verbatim
./compass.sh vault provision --dry-run    # what it would write, values masked
./compass.sh vault provision              # write it
#+end_src

It writes one consumer and one password per database service, reading the
passwords the environment file already holds, so nothing has to be generated and
no role changes. It skips the vault. Run it again whenever a service is added or
a password changes: a value written twice becomes a new version of the same
secret rather than a second secret.

The order matters. The vault must be running, because it is the process that
seals the values; generate the units and start it first:

#+begin_src sh :results verbatim
./compass.sh services start ores.vault.service
./compass.sh vault provision
#+end_src

* What it writes

Two things per database service, both under =build/keys=:

- =<psql_var>.vault.key= — the private half of the service's key pair, mode 0600,
  which the unit reads at start once services resolve their passwords.
- =<psql_var>.vault.pub= — the public half, registered with the vault as the
  consumer's key.

And two rows in the vault's *system* tenant, because a database password
protects a role the deployment owns and not any one tenant: a consumer named by
the service account, and =db.<psql_var>.password= owned by that account.

* Script

=projects/ores.compass/src/vault_provision.py= builds the document and hands it
to =ores.vault.service --provision -== on standard input, so no file of
plaintext passwords exists at any point. The verb and its document are described
in [[id:5FADF948-4520-41D3-B4F0-BE4873C06AF0][Secure Introduction of a Workload to
the Vault]].

* Tested by

=sprojects/ores.compass/tests/test_vault_provision.py= holds the document's
shape: one consumer and one secret per database service, the vault skipped, a
service the environment file omits skipped and named, and a key pair generated
once and kept. The vault's own side is held by
=sprojects/ores.vault.service/tests/provisioning_tests.cpp= and by an integration
case in =ores.vault.core.tests=.

Manual: =./compass.sh vault provision --dry-run= prints the document with each
value replaced by its length, so a run can be inspected before it writes.
