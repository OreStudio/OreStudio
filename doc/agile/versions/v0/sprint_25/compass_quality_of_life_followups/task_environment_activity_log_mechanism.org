* Goal

Give =compass bearings= a way to tell a checkout "you need to perform
these manual setup steps" after pulling a change that can't be
auto-applied by =compass env configure= (root-owned systemd
drop-ins, one-time local migrations, ...). Motivated directly by
today's WS-5 root-half systemd step (protect the interactive session
via a root-owned =user-1000.slice.d/= drop-in): every other
environment in the fleet needs to run it, and until now there was no
mechanism to tell them so beyond an ad hoc chat message.

* Acceptance

- A new =doc/knowledge/architecture/environment_activity_log.org=
  carries a machine-parsed table of activities, each linking to the
  recipe with its actual steps — sibling of the existing =.env=
  format version log, not merged into it (see the doc's own
  =* Detail= for why).
- =ORES_ENV_VERSION= bumped (new =.env= var =ORES_ENV_ACTIVITY=);
  =compass env configure= writes it, *preserving* an existing value
  across regenerations (unlike =ORES_ENV_VERSION=, which always
  stamps latest) — a manual/privileged activity can't be safely
  auto-reapplied on every =configure=.
- =compass env activity= (bare: list outstanding; =new <title>
  <recipe-id>=: record one; =ack <N>=: acknowledge one for this
  checkout).
- =compass bearings= surfaces every activity newer than the
  checkout's =ORES_ENV_ACTIVITY=, each with its recipe link and the
  =ack= command to run afterwards.
- The WS-5 root-half step registered as the log's first real entry
  (activity 1), with a proper recipe
  ([[id:0E135A6C-F705-4C07-A5FA-CCE65FA138FF][How do I protect the interactive session at the root level?]]).
- Verified live end-to-end: fresh =.env= regeneration stamps
  =ORES_ENV_ACTIVITY= correctly; a simulated stale checkout
  (=ORES_ENV_ACTIVITY=0=) shows the correct =bearings= warning;
  =ack= rejects an out-of-range number.

* Plan

1. New module =env_activity.py=, mirroring =env_init.py='s
   =current_version=/=new_version= parsing shape
   (=_parse_activity_rows=, =current_activity=, =new_activity=) plus
   the two things unique to activities: =checkout_activity= (reads
   =ORES_ENV_ACTIVITY= from =.env=) and =ack= (writes it back,
   deliberately not auto-bumped by =configure=).
2. Wire =compass env activity [new|ack]= into =cmd_env= in
   =compass.py=, same dispatch shape as the existing =version=
   subcommand.
3. =env_init.py='s =.env= writer: reuse =existing.get("ORES_ENV_ACTIVITY")=
   if present (like a reused secret), else stamp
   =env_activity.current_activity()= — a genuinely fresh checkout
   starts "caught up", not demanded to perform every historical
   activity.
4. =compass bearings=: new section next to the existing =.env is
   stale= check, reusing the same yellow-warning style.
5. Record the =.env= schema change itself via
   =compass env version new= (version 20) — this addition is exactly
   the kind of change that mechanism exists for.
6. Author the WS-5 root-half recipe
   (=doc/recipes/compass/how_do_i_protect_the_interactive_session_at_the_root_level.org=)
   and register it as activity 1 via =compass env activity new=, to
   both give the fleet a real first entry and validate the mechanism
   end-to-end.

* Result

Shipped the full mechanism in one PR: new =env_activity.py= module
(mirroring =env_init.py='s version-log parsing shape),
=compass env activity [new|ack]=, a =compass bearings= section, the
=.env= schema bump (=ORES_ENV_VERSION= 20, new =ORES_ENV_ACTIVITY=
var), and the WS-5 root-half recipe registered as activity 1 — this
checkout's own =.env= now reports "activity 1 (log highest: 1),
nothing outstanding" after acknowledging the root step performed
earlier today. Verified live: fresh regeneration stamps the var
correctly; a simulated stale checkout (=ORES_ENV_ACTIVITY=0=) makes
=bearings= print the expected warning with a working recipe link;
=ack= rejects an out-of-range activity number.
