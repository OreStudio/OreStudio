* Notes

- *What makes a path wrong.* The contract keys a leaf by an XPath and every
  reader resolves it against the document. A path that no document holds
  describes a leaf that cannot be drawn and cannot be guarded: the store and the
  page both do nothing with it, without an error.
- *Five paths fail today*, found by walking the published artefact through
  `curveconfig.xsd` from `CurveConfiguration`, where a path may only continue
  through a complex type:
  - `/CurveConfiguration/FXVolatilities/FXVolatility/ParametricSmileConfiguration/Parameters/Dimension`
  - `/CurveConfiguration/FXVolatilities/FXVolatility/ParametricSmileConfiguration/Calibration/Dimension`
  - `/CurveConfiguration/SwaptionVolatilities/SwaptionVolatility/ParametricSmileConfiguration/Parameters/Dimension`
  - `/CurveConfiguration/SwaptionVolatilities/SwaptionVolatility/ParametricSmileConfiguration/Calibration/Dimension`
  - `/CurveConfiguration/YieldVolatilities/YieldVolatility/Interpolation`
- *The four smile paths are one cause.* `ParametricSmileConfiguration::fromXML`
  reads its three blocks into the same variable name, `n`, and the extractor
  keys the block's parser by that variable, so the last call wins and every
  block is walked as `ResidualCorrection`, whose single read is `Dimension`. The
  real `Parameters` block holds repeated `Parameter` nodes and the real
  `Calibration` block holds three leaves, so the sibling attribution wants the
  call that follows the block's own read, bounded by the next block. A repeated
  child is a collection the extractor does not model yet, which is why the
  `Parameters` block may end up recorded as unresolved rather than wrong.
- *`Interpolation` is the schema's gap, not the code's.*
  `genericyieldvolcurveconfig.cpp:236` reads `Interpolation` for a yield
  volatility, and `yieldVolatility` in `curveconfig.xsd` declares no such
  element. The path is real, so the check needs the statement that the ORE code
  reads it, with that source line, rather than an exemption a reader cannot
  verify.
