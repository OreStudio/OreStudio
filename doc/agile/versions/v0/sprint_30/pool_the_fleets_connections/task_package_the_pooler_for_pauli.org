* Goal

pauli runs the pooler as a podman container beside the fleet, pulled from the
same registry as the services, and every service on pauli reaches PostgreSQL
through it. A deploy of pauli starts the pooler before the services that need it
and reports it like any other container.

* Acceptance

- A =pgbouncer= image is built from a Dockerfile in =docker/=, on the smallest
  base that carries it (Alpine, whose package is 1.24 or later and past the
  prepared-statement floor), and published to the registry under the same tagging
  scheme as the service images: =0.0.30-<commit>= and =main=.
- Its configuration is generated from the environment, the same file the unit
  would use, mounted read-only into the container.
- =compass env deploy pauli= deploys the pooler with the fleet, ordered before the
  services, and its report names it as it names nats and the services.
- The services on pauli connect to the pooler; the listener and the
  administrative paths do not.
- pauli's =pg_stat_activity= shows the fleet arriving from the pooler, and the
  count of server connections settling to the cap.
- A deploy that finds the pooler image missing stops before it stops anything, as
  the service images already do.
- The deployment recipe records the pooler beside nats, so a person bringing up a
  host knows it exists and why.

* Plan

=env_deploy.py= already deploys three kinds of container - the fleet's
service-runtime images, =localhost/ores-nats=, and the compute and web images -
and marks them (=IMAGE_NATS= at line 68, the NATS configuration staged from
=build/config/nats-<label>.conf=, the ordering at lines 378-393). The pooler is a
fourth: an =IMAGE_PGBOUNCER=, its configuration staged beside NATS's, and the same
start ordering and missing-image guard.

The image follows =docker/nats.Dockerfile= in intent and not in base: NATS is a
static Go binary and gets =scratch=, while =pgbouncer= links libevent, OpenSSL and
c-ares, so the smallest honest base is =alpine:3.22= with =apk add
--no-install-recommends pgbouncer=, about 410 KiB installed. Nothing of ours is
linked into it, so musl is safe.

The recipe to update is the deployment runbook for the remote host
(=doc/recipes/compass/how-do-i-deploy-the-service-runtime-to-a-remote-wsl-host.org=),
which lists what a deploy starts.

* Notes

** Written, 2026-11-21

- =docker/pgbouncer.Dockerfile=: =alpine:3.22=, =apk add pgbouncer=, no
  configuration baked in. Alpine's package is 1.24 or later, past the
  prepared-statement floor; Debian 12's 1.18 is below it.
- =start_ci_pooler.sh print-config <port> <dir>= writes the container's shape:
  it listens on the interface the pod gives it, reaches the database on the host
  that runs the pod (=host.containers.internal=), and logs to stderr rather than
  to a file inside the image.
- =image_build.py= builds and tags =ores-pgbouncer= beside =ores-nats=, and
  =env_deploy.py= transfers it with the other standalone images and stages its
  configuration under =build/config/pooler/= on the remote.

** Not written, and why

The pooler is not yet a container of the pod: =docker/run-pod.sh= starts the
service runtime and the NATS sidecar, and the pooler is a third. Nor is it
published to the registry, nor named in the deployment recipe.

** Built, run and published, 2026-11-21

The build needs podman's runtime state under =/run/user=, which the workspace
sandbox denies, so it ran with wider permissions. Running it found three faults
that reading the file could not:

- Alpine's package ships no =pgbouncer= user, and pgbouncer refuses to run as
  root, so the image creates the user its entrypoint drops to.
- The container expects =pgbouncer.ini=, which the generator did not write, and
  its auth file must name the mount point rather than the directory it was
  written to, because pgbouncer reads it after dropping privileges.
- The mounted directory is read-only, so a pidfile inside it is a file it cannot
  write, and the container shape carries none.

Proof: =podman run= of the image answered =select 'pooled from the container'=
against this environment's database, and its log shows the server connection
with TLS established.

Published as =ghcr.io/orestudio/ores-pgbouncer=, tags =main= and
=0.0.30-07672ec35a1e=, digest =sha256:114f50e6...=, and made public. Verified
without credentials: an anonymous pull token fetches the manifest of =main= with
HTTP 200, which is what a host with no login on it will do.

What is left is the deploy path, and it is not the one this batch first assumed.
=docker/run-pod.sh= is historical: =env_deploy.py= says it is the sequence that
deployed to Newton in sprint 24, and pauli is deployed through the **quadlet**
units =systemd_generate.py= renders (=cmd_quadlet= and =cmd_quadlet_deploy=, the
latter with =--host= for a remote). So the pooler needs a quadlet unit beside
the NATS one, not a line in =run-pod.sh=.

pauli is reachable from this checkout (podman 5.8.6) but has no
=~/ores-deploy= yet, so it has never been deployed from here. A first deploy is
therefore the increment after the quadlet unit, not something to bolt onto it.
