#+title: ores.trading.trade_type_catalogue
#+description: The one declaration of the trade types: their seed, which instrument table holds each, and so every instrument table's trade_type check and the export routing.
#+type: ores.codegen.trade_type_catalogue
#+component: trading
#+filetags: :model:trade_type:catalogue:trading:
#+brief: The trade types and the instrument table that holds each.
#+created: 2026-10-04
#+updated: 2026-10-08

Every trade type ORE knows, and the instrument table that holds a trade of
that type. Each instrument table used to list the codes it accepts by hand,
ten of them listed all 121, and the export handler kept its own routing in
hand-written conditions. The three disagreed: a type could be routed to a
table that refused it, or accepted by a table export never read.

This model is the single source. The trade types seed is generated from it;
each instrument model that declares =:routed_column:= gets a =trade_type=
check listing exactly the codes routed to it, so the lists are disjoint and
a trade's instrument can sit in one table only; and the C++ routing the
export handler reads is generated from it.

An empty =instrument= means no table holds the type yet: nothing imports it,
so nothing can export it. A type is routed where the ORE importer writes it.

=markets= names the markets a type references, the first of them the market
the catalogue groups the type under, marked with a trailing =!=. A type that
names no market is one whose market is decided per trade: every container and
every scripted trade. =family= is the contract shape the type shares with types
in other markets, and =construction= says whether the type is built natively,
by script or as a container.

A type is routed where the ORE importer writes it. RiskParticipationAgreement
is a credit product whose importer has always written the credit table. The
table that was meant to hold its facts was never written by any mapper, and it
is retired. InflationSwap references inflation first and interest rates second,
and its importer writes the rates family's tables, so it is routed to
=rate_instruments= until an inflation family is scaffolded, and the reason is
recorded on the rates story.

The rates family routes every one of its codes to =rate_instruments=, the
family's header. A product's own fields live in the family's fact tables,
which the header's =* Delete cascade= names and the export carries as child
arrays; the fact tables are not routed instruments, because one trade type
resolves to one instrument table and the header is that table for the whole
family.

The =Failed= type ORE uses for a trade it could not load is deliberately
absent: it is a placeholder, not a product.

* Descriptions

The description a person reads before booking a type, and the source it comes
from. One row per code, in the same order as the trade types above.

The prose says what the product is, in one sentence, and names no model, no
engine and no pair: a reader who has never booked the type can tell from this
line whether it is the one they want, and the page it is read on names the code.

The source is the document the description was written from, and the reference
is the file inside it. Where ORE documents a product under a chapter that covers
several types, the chapter is named and the description says which of them this
is.

* Common dates

The dates a deal grid reads across families. Each product used to state them
under its own name, so the blotter could not read one date column across a
family (finding R9). A family maps its own columns onto these names by
declaring =:common_date: <name>= on them; the view for the family is
generated from those declarations, so a later family adds its mapping on its
models and edits no view. A name that no family owns names the entity and
column that hold it for every family instead.

A mapped column must sit in a table keyed by the trade alone. A date a family
does not state reads as null, and so does a shared date whose table has no row
for the trade, as a trade with no booking has no trade date.

| name          | description                                              | shared_entity | shared_column |
|---------------+----------------------------------------------------------+---------------+---------------|
| trade_date    | The date the trade was agreed.                           | trade_booking | trade_date    |
| start_date    | The date the instrument starts, or its underlying starts. |               |               |
| expiry_date   | The date an option expires.                              |               |               |
| maturity_date | The date the instrument ends, an end date included.      |               |               |

* Digest

A trade's economic digest folds the digests of the rows that make up its
instrument. This section declares which rows those are, so the code that reads
them is generated and a family cannot gain or lose a component without the
model saying so.

** Shared components

The entities whose rows for the trade are part of every instrument's economic
shape, whatever table the trade type routes to: the legs and their amounts,
rates and amortizations, the forwards, the strikes, and the option, schedule
and date blocks. The bond pilot built these shapes and the other families
write to them, so one reader serves the whole catalogue. =reader= is the
function that reads an entity's rows by trade id.

The option's exercise prices are an economic table that is not listed here:
the digest has never read them. Listing them is a change to what the digest
covers, so it is a decision of its own and not a side effect of declaring the
shape.
