* What moves, measured

=ensure_issue= writes a =put_bond_issue_composite_request=: one =bond_issue= row
(issue id, security id, issuer, face value, issue date, settlement days,
calendar, sub type, price type, curve) plus one leg, one notional amount and one
fixed rate. It runs before the trade is booked, because the instrument points at
an issue that must already exist.

So this slice moves about sixty lines from the writer to the planner and gives
the batch the rows the request already holds. It is not a rename: the leg, the
amount and the rate are part of the security, and the planner has to state them
with the issue's own identifiers.

* Why it is its own task

The instrument flip kept =terms= precisely because this coupling exists, and the
planner's tests caught it. Moving the security is the step that lets
=bond_terms= leave the plan, so it is the step that starts deleting the bag.

The bond security states its rows. The planner builds the issue with its leg, its
notional and its coupon, its rate and its schedule rule, and puts them in the
batch beside the instrument; the writer packs them into the composite write,
stamps every row and sends. It decides nothing about the issue now: the terms
were drawn where the security was drawn.

The bag is deleted. `trade_terms` and the slot's `terms` member are gone, every
family's planner keeps its own drawing struct, and the writer's dispatch has no
bag arm left. That was the story's endgame: the slot states rows, and one
structure describes each family's drawing rather than what a slot carries.

The population is unchanged: 24 bond instrument rows, 16 issues with a leg, a
rate, a schedule and a notional-plus-coupon pair each, no instrument without its
issue, and 127 trades in total.

One number moved and the record should say so. An earlier run on the same
population counted 18 issue rows where this one counts 16. The issue table is
versioned and that count includes every version, so a re-written issue adds a
row; the current run holds sixteen securities, sixteen live issues and no
orphan instrument, and no test or provisioning step depends on the version
count. It is noted rather than explained because the earlier database is gone.

The task document reached this branch late: the story listed the row, but the
doc itself was never merged from its scaffold branch, so the table held a row
with no link until this PR brought the doc with it.
