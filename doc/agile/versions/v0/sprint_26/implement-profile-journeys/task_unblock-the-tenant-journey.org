* Acceptance

- A screen inside the signed-in shell is bounded and centred at the width the
  wide public shell already uses, so a banner fills the same column in both.
- The details step of *New tenant* offers a password of its own for a starting
  point that inherits the creating administrator's password, because this
  journey holds no such password.
- The details step moves on once the password and its confirmation are typed,
  and stays put until then.
- First run keeps the offer, because it does hold the creating password.
- The offer of a password that cannot be handed over is not drawn.
- The tests that recorded the broken state as correct are corrected, and one
  asserts each half of the rule.
- Both defects were read in a browser against the running deployment.

* Plan

1. *The layout is the shell's, not the journey's.* The banner is already sized
   correctly and states no height, so the defect is the column it is given.
   The bound goes on the signed-in shell, where every screen gets it, and it is
   the public shell's own number so the two agree.
2. *The password rule, not the screen.* Whether a profile may hand the creating
   administrator's password on is a fact about whether the journey holds one,
   so the proposal is dropped where it is built, and the form stops offering a
   choice that cannot be kept.
3. *Correct the test that agreed with the defect.* The old test asserted that
   the broken state was correct. It now asserts both halves of the rule: a
   journey holding no password asks for one, and first run, which holds the
   creating password, keeps the offer.
4. *Read it in a browser.* Both defects are about what a screen draws, so both
   are read against the running deployment, not only in a test.

* Result

Both defects are fixed, and both were read in a browser against the running
deployment.

- *The banner is bounded.* The image was never the defect: it states its ratio
  and no height. The column it was given was. The public shell has always
  capped and centred its screen at =max-w-[1100px]= and the signed-in shell did
  not, so the same journey drew a wall once somebody had signed in. The
  signed-in shell now uses the public shell's own bound, and every screen gets
  it. On a 1600px display the banner draws 794px wide, as it does before a
  sign-in, instead of filling the window.

- *The details step can be left.* A starting point may offer to hand the
  creating administrator's password to the tenant's administrator, and the
  standalone *New tenant* journey holds no such password: nobody signed in as
  the account that creates the tenant. The offer stood anyway, which hid the
  password field and left Continue disabled with no way forward that a person
  could see. The proposal is now dropped where the details are built, when the
  journey holds nothing to hand over, and the form asks for a password of the
  tenant's own. First run is unchanged, because it does hold the creating
  password.

- *The test that agreed with the defect is corrected.* The old test asserted
  that a demonstration profile with an unheld password leaves the step disabled,
  which was the defect written down as the rule. It now asserts both halves: a
  journey holding no password asks for one and moves on once it is typed, and a
  journey holding one keeps the offer and moves on without asking.

Proved live: the harness signs in, opens *New tenant*, chooses the starting
point that inherits the password, moves to the details step, confirms the
password and its confirmation are asked for, types them, and confirms the step
then moves on. Screenshot in =evidence/tenant_details.png=; harness in
=evidence/tenant_journey_check.js=.

What this task does not do. The bound is one number shared by the two shells,
so a screen that wants a different width changes both. The details step still
opens as a summary that must be expanded to reach the settings, which is a
separate question about how much a person should have to read before typing.
