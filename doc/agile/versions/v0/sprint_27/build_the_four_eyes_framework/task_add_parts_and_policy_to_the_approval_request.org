* Acceptance

- A request needs an approval from every one of its parts, and one refusal ends it.
- A part with an earlier place in the order cannot be answered before it.
- The person who asked never decides, and one person answers a part once.
- The policy says which acts are gated and which part decides each, as data the system tenant holds.

* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

- Model three tables in codegen: =approval_part= (code, decider permission, answer order), =approval_policy= (entity type, operation, optional field, part) and =approval_request_part= (the parts one request needs).
- Add a nullable =part_code= to =approval_decision=, so a decision names the part it answers.
- Make the decide function count by part when a request has part rows, and keep the old count when it has none.
- Let the handler check the permission the named part carries, and tell the deciders whose turn it is.
- Seed the four parts and the policy rows from the controls note.

* Result

A request can now name parts. Each part is a function whose approval the request needs. A decision names the part it answers.

- Three new tables, generated from models: =approval_part=, =approval_policy= and =approval_request_part=. =approval_decision= gains =part_code=.
- The decide function approves a request when every part has approved. One refusal refuses it. A part answers only after every part of an earlier answer order has approved. Parts of the same order answer in either order. A request with no part rows keeps the old count.
- The handler checks the permission of the part the decider names. It tells the holders of the parts whose turn it is, on raise and after each approval.
- The system tenant holds four parts (Controller first, then Finance, Market Risk and Operations together) and 33 policy rows from the controls note. A permission code per part is seeded.
- The raise and decide protocol carry =part_codes= and =part_code=, in the model and in the TypeScript client.

Evidence: =ores.inbox.core.tests [approval]= passes, 17 cases and 63 assertions, against a freshly recreated database. Four of the cases are new and cover order, parallel parts, naming a part and a part refusal. The populate, handler permission, paste block and test case reachability checks pass. The web typecheck and format check pass.
