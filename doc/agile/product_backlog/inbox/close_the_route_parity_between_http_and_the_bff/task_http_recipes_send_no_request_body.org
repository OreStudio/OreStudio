* Goal

The recipes under =projects/ores.http/scripts/library/= are tangled from the
=ores.doc.http-recipe= facet, and its template =http_recipe.org.mustache=
emits only a method line, an =Accept= header, an optional =Authorization=
header and the status assertion. It emits no body and no =Content-Type=, so a
write arrives empty.

Replaying the =tags= group against the running gateway gives 4 =PASSED= and 6
=FAILED=, every failure reading =actual value is <400>=: =add=, =set=,
=get-many=, =put-many=, =delete= and =delete-many=.

The path sentinel is wrong for HTTP as well. =_sentinel_for_field= falls back
to the shell absent token =__none__= for =std::string= and for every unmapped
type, so the token is written straight into request URLs, as in
=DELETE /api/v1/assets/tags/__none__=.

* Acceptance

- Every generated write recipe emits the body its route takes.
- The harness replays the corpus, and every recipe that asserts a 200 reaches its handler.
- A check fails when a generated recipe has no body, so the corpus cannot drift back.

* Plan

The fault is one stage upstream of this repository, and that decides the plan.

=doc/recipes/http/<plural>/<singular>.org= is rendered by compass-ng's
=codegen= codec from the entity models, and the Hurl files are then tangled
from it by compass-ng's =http_recipe_library= codec. The endpoint data those
templates read carries the method, the path, the subject and the session flag,
and nothing about the request, so a body has nowhere to come from here: any
edit to a recipe document is overwritten by the next =compass generate=, and
the check would fail on it besides.

So the work is two changes, in this order.

1. *compass-ng.* The codec supplies, per endpoint, the body as JSON built from
   the request message the route names, an HTTP-appropriate path sentinel in
   place of the shell's =__none__=, and the query parameters a route requires
   instead of a body. A new check codec, =http_recipe_bodies=, reports a
   generated recipe that sends neither. The specification is the handover
   beside this task.
2. *This repository*, once a release carrying it is installed: the template
   renders =Content-Type= and the body when the endpoint states one, =reason=
   and =commentary= in the query for a delete, =compass_ng.pin= names the new
   release, =.compass.org= enables the check with its page under
   =compass/checks/=, and the 54 recipe documents and their Hurl files are
   regenerated.

Two things the measurements below corrected in the original capture: the
corpus is far larger than it said, and a =DELETE= takes no body at all — its
intent travels as query parameters, which is why those six recipes answer 400
even with a body.

* Notes

The capture's numbers were read before the corpus grew, and one of its facts
was wrong. The truth as measured on 2026-11-25:

- The corpus is 453 Hurl files, not 82. 280 of them use =POST=, =PUT= or
  =DELETE=, and every one of those sends no body and no =Content-Type=.
- =DELETE= is not a body-carrying method in this gateway. The generated route
  registers =.no_body()= and takes the change intent as query parameters,
  =reason= and =commentary=, both required, so a DELETE recipe answers 400
  until it states them in the URL. That is the sixth of the six failing =tags=
  recipes, and it is why a body alone does not fix this task.
- The body of a write is the request message the route names, read as JSON by
  the generated codec into a default-constructed struct, so an absent member
  keeps its default. A body of ={} =, or one whose nested written rows are ={}=,
  therefore reaches the handler; it is the empty *body* that is refused.

The handover for the compass agent is
=evidence/compass_handover_send_the_request_body.md=. It states the data
contract the template will consume — =has_body=, =body=, =content_type=,
=has_query=, =query= — the sentinel rule, the check codec, and how to prove the
result.

** What

The 82 recipes under =projects/ores.http/scripts/library/= are tangled from
the =ores.doc.http-recipe= facet, and its template
=http_recipe.org.mustache= emits only a method line, an =Accept= header, an
optional =Authorization= header and the status assertion. It emits no body
and no =Content-Type=, so a write arrives empty.

57 of the 82 use a body-carrying method — 45 =POST=, 6 =PUT=, 6 =DELETE= —
and none carries a body. Replaying the =tags= group against the running
gateway gives 4 =PASSED= and 6 =FAILED=, every failure reading
=actual value is <400>=: =add=, =set=, =get-many=, =put-many=, =delete= and
=delete-many=.

The path sentinel is wrong for HTTP as well. =_sentinel_for_field= falls back
to the shell absent token =__none__= for =std::string= and for every unmapped
type, so 17 recipes write that token straight into the request URL, as in
=DELETE /api/v1/assets/tags/__none__=.

** Why

A recipe exists to prove the wiring between the route and the handler, and an
endpoint that answers 400 proves the opposite of what its recipe asserts. The
57 recipes are therefore worse than absent: each reports a pass-shaped
document that cannot pass. The fault is at the source, in one template and one
builder, so one fix corrects all of them.

The typed inputs the fix needs already exist for the shell surface: the
=entity_shell_plan= =keys=, =writes= and =put_writes= commands, and the
per-field sentinels. Their values are shell tokens rather than JSON, so the
facet needs a JSON-typed sentinel and a body block per write endpoint. A
regression test should assert that a write recipe carries a body.

Found while closing the ores.http clean-up. The =Generate literate HTTP
recipes= story is marked DONE on an acceptance line — every tangled Hurl file
runs against the live gateway unchanged — that these 57 recipes do not meet.
