* Plan

*One family at a time, each complete.* A family moves reader, writer and
mapper in one change, so no family ever has two live implementations. Calendar
adjustments went first because it is the smallest and proves the shape every
later migration reuses: its mapper is deleted, not retyped, and the projection
that survives sits at the boundary beside the reading and the writing it
serves. Currency config followed and needed two more codec helpers, because a
currency's rounding type is an enumeration: the record holds an index and a
projection speaks the schema's spelling.

*The codec grew the vocabulary a projection needs.* A projection receives the
record the generated table describes and states which of its members it fills,
because the writer writes only the fields whose presence bit is set. Four small
functions join the codec: =find_field=, =find_child_type=, =is_present= and
=mark_present=. A projection names a member the way the document does, so it
does not repeat the schema or hardcode bit numbers. Because the lookup accepts
an element or an attribute, the generator now refuses a type that spells both
the same, so the ambiguity cannot arise silently.

*A date list is two rows.* The element that holds the dates and the =Date= row
inside the record it points at are both rows, so a projection states both. The
first attempt set only the outer one, and the dates vanished from the writing:
the family's own round-trip test caught it before the change left the branch.

*The importer reads text as well as files*, so an export can be imported again
without a temporary file, which is what the family's round-trip test does.

*The netting set mapper had no reader.* The ore-side mapper turned a
netting set document into =mapped_netting_sets=, and only its own tests
called it; the live netting set mapper is the refdata one on the database
side. So the family needed no projection at all: its table was already
written and proved, and the mappers and suites that duplicated it are gone.

*Pricing engines moved as a projection, not a mapper.* The family maps a
document into analytics product and parameter rows, which is work no table
can carry, so the class survives as =pricing_engine_projection= with the
codec record as its input. It also owns reading and writing, so its two
callers in the run store and the run configuration service ask it for a
document rather than binding one themselves.

*Two families share one projection helper.* Currency config followed calendar
adjustments, and its review found the table lookup copy-pasted in the importer
and the exporter, and the writer's error message still naming the calendar
table for a currency field. Both live in =src/xml/projection.hpp= now, beside
the rule that a projection states every row it fills and throws when the
schema no longer has it.

need the generator extended first.

deleted: the projection into the five analytics tables is the work.

* Notes

- *A rename now fails instead of writing nothing.* =mark_present= reports a
  name the table does not have, and the projection throws rather than emitting
  a document missing the field.
- *The netting set family has a table and no reader.* Its XML mapper was
  reached only by its own tests, so the mapper and those tests are gone and the
  family is covered by the binding, writing and round-trip suites that walk the
  corpus. A sprint-26 story records netting sets as reading and writing through
  the refdata store; that store is live, but the ORE XML path into it never had
  a caller, and this change makes that explicit.
- *The reading is stricter than xsdcpp.* The binder refuses an element or an
  attribute the schema does not name, and the importer throws. That is the
  codec's policy on a family with no =xs:any=, and it is the behaviour the
  tables were chosen for; a document ORE tolerates but the schema does not
  describe is a document to look at, not to import quietly.
- *The boundary still throws.* =import_calendar_adjustments_text= and the
  exporter report a malformed document with =std::runtime_error=, like every
  sibling in the importer and exporter. Converting the whole boundary to
  =std::expected= is one change for all families, not one per family.
