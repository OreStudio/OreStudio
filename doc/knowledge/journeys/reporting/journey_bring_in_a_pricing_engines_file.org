This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A market-risk owner or tenant administrator brings in an ORE pricing engine configuration file, reads what it holds against what the party already has, and saves it as a new draft or as a proposal for a new version of a configuration.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I have the ORE =pricingengine.xml= my quants use. I want it in ORE Studio, and I
want to know what it changes before it does." Most pricing configurations start
life as an ORE file; the project holds about seventy variants. The person should
not retype a file. The journey is done when the file's products and settings are
saved, and the person has read what the file holds, what it adds to or changes in
a configuration the party already has, and what it holds that the system cannot
read. A file never becomes an official configuration directly. A new file is saved
as a draft. A file put into an approved configuration is a proposal for a new
version, and it waits for sign-off. A file put into a draft changes the draft in
place.

* Actor and trigger

A market-risk owner or a tenant administrator runs this journey, inside their own
tenant, for their own party.

The trigger is a file from a quant, from an ORE example, or from another
installation, or a change to a configuration the quants maintain in a file. The
journey starts from *Workflows* on the list in
[[id:386DD47E-DA9E-4EA7-B925-852048EE47B7][See the pricing engine configurations a party holds]],
or from step 1 of
[[id:0D39E4B7-75FD-480A-A996-2234BCC7BCC8][Author a pricing engine configuration]],
and ends on the saved configuration's page.

This is a workflow with its own address and several steps, not a dialog, because
it reads a file, compares and then writes. It is not a data exchange of a whole
party. That is covered by the data exchange journeys.

* Steps

1. *Choose the file.* The person chooses a file or pastes its text. The screen
   accepts =<PricingEngines>= documents. A file of another kind is refused with
   the root element it found.
2. *Read what the file holds.* The screen parses the file and states, before
   anything is written: the count of =Product= elements, the count of distinct
   models and engines, the count of model and engine parameters, and the global
   parameters. The products are listed in file order with their type, model and
   engine.
3. *Read what the system does not know.* Three lists, each only when not empty:
   - *Product types the system has no code for.* A =Product type= that is not in
     the pricing engine type vocabulary. Each is shown with the choice *Skip* or
     *Add the type first*.
   - *Elements the screen cannot read.* An element, an attribute or a parameter
     the file holds that has no column. The screen lists it and states that it is
     dropped.
   - *Duplicates.* A product type that appears twice. The screen shows both and
     asks which one to keep.
4. *Choose the target.* Two choices:
   - *Save as a new draft configuration.* The person gives a name, a description
     and a variant. The variant tag is filled from the file name when it follows the
     ORE naming, such as =pricingengine_amc.xml= giving =AMC=. No official report can
     bind a draft.
   - *Put it into a configuration the party holds.* The person chooses the
     configuration from a combo box, which shows each status. For an approved
     configuration the file is a proposal: version N+1 waits for sign-off, version N
     stays in force, and the reach panel names the reports that the change would
     reach after the sign-off, as in
     [[id:D998F36A-9716-48E7-BC70-BC4813115591][Change how a product is priced]]. For
     a draft the file changes the draft in place and reaches no run.
5. *Read the difference.* When the target is an existing configuration, a
   three-part table compares it with the file: *added* products, *changed*
   products with the model, engine or parameter that differs, and *removed*
   products, the ones the configuration has and the file does not. The removed
   list is the one that matters most and is drawn first. A new configuration has
   nothing to compare, and the step says so.
6. *Decide the removed products.* For each removed product the person chooses
   *Keep it* or *Drop it*. The default is *Keep it*, because a file that omits a
   product usually leaves it out by accident. A product kept stays in the new
   version unchanged.
7. *Review and submit.* The final step names the products that will be written, in
   order, with the counts of added, changed, kept and dropped, and the elements
   that were dropped because they cannot be read. A new draft has *Save as draft*
   and is written with the reason =system.new_record=. A draft target has *Save* and
   asks for a change reason and a commentary. An approved target has *Submit for
   sign-off*, asks for a change reason and a commentary, claims the version read, and
   states that the configuration does not change and that the person who submits
   cannot sign off.
8. *See the result.* A draft opens its page, where the History tab shows the new
   version with its diff, and the commentary names the file. A proposal opens
   [[id:41C7A1F2-8E5B-4D36-9A0C-7B2E5D1F6A93][Sign off a pricing engine change]].

* Prototype

The [[file:../../prototypes/reporting/bring-in-a-pricing-engines-file/][bring in a pricing engine configuration file prototype]] owns this journey, and
[[file:../../prototypes/reporting/bring-in-a-pricing-engines-file.org][its design note]] says what it argues, which states it can reach and what is
fake. It belongs at =doc/prototypes/reporting/bring-in-a-pricing-engines-file/=.

It must draw the five panels on the standard steps UI. It must offer three
fixture files behind =?file=|=: a clean file, a file with a product type the
system has no code for and an element the screen cannot read, and a file that
omits a product the target already has. It must offer three targets behind
=?target=new|c2|c3=: a new draft, an approved configuration and a draft. It must draw the added, changed and
removed table and the keep-or-drop choice, and the final review. It must state
that the parse is a mock and which operation would parse a file. Every value is a
fixture.

* What is missing

1. *A parse for a person's file.* The data quality publisher turns a cleared
   document into the three tables through
   =analytics.v1.ops.publish_pricing_engines_from_dq=, and the shell imports
   ORE files. Nothing takes a file a person chooses in a browser and returns a
   =pricing_engines_document=. The screen either parses in the browser, which
   makes a second parser that can drift from the server's, or a new operation
   parses on the server. The second is the answer. The
   [[id:81B5B745-A079-46E2-93CF-CD3F2738B609][XML document codec prototype]] shows
   a codec that turns an ORE document into records through generated tables, which
   is the shape the operation would take.
2. *A preview that writes nothing.* The parse must return the document without
   saving it. The publisher saves, so the screen needs the parse as its own
   request.
3. *A diff between two documents.* The difference in step 5 is the screen's own
   computation over two documents. A server diff would give the History tab and
   this step the same result.
4. *A new version of a document.* The document write replaces the rows of the
   configuration. It does not state which products were kept and which were
   dropped. The history shows the configuration as changed and the diff is
   recomputed from the versions.
5. *No home for a proposal.* A file put into an approved configuration must not
   replace the rows that a run reads. The same gap as in
   [[id:D998F36A-9716-48E7-BC70-BC4813115591][Change how a product is priced]].
6. *The unreadable elements.* ORE files hold elements the tables do not, such as
   an inline calibration block. The screen lists them and drops them. A later
   model can keep them.
7. *The write is not one transaction.* The same gap as in
   [[id:0D39E4B7-75FD-480A-A996-2234BCC7BCC8][Author a pricing engine configuration]].
