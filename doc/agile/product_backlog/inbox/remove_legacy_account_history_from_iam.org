#+title: Remove the account-specific history protocol from ores.iam
#+description: iam still serves a hand-shaped account history on iam.v1.accounts.history; the generic iam.v1.history.get now serves every IAM entity, so the account-specific protocol and its four consumers should go.
#+type: capture
#+level: cross
#+filetags: :iam:history:codegen:
#+created: 2026-09-22
#+updated: 2026-09-22

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Delete the account-specific history protocol and point its consumers at the
generic one.

The legacy path is a subject of its own, with a request keyed by the account's
name rather than by a type and an id:

#+begin_src cpp
get_account_history_request  { username }
get_account_history_response { history: account_version_history }
account_version_history      { versions: vector<account_version> }
account_version              { data, version_number, modified_by, recorded_at, change_summary }
// subscribed at "iam.v1.accounts.history"
#+end_src

The generic path is one subject per component, keyed by type and id, and it
already answers for this entity:

#+begin_src cpp
// "iam.v1.history.get"
get_entity_history_request { entity_type, entity_id }
entity_history_version     { version, modified_by, recorded_at, fields, changes }
#+end_src

* Why

Two history protocols for one component is the drift the generic service exists
to remove: a client has to know which entity's history is asked for by name and
which by id, and the answer's shape depends on which one it asked. The account
one also cannot answer for any other IAM entity, and its =change_summary= is a
prose field where the generic path carries a structured diff.

The generic providers are registered as of commit =ff44fdc4ea=, so
=iam.v1.history.get= now answers for the seven IAM entities that derive a
versions pair. Nothing needs the legacy subject to keep working.

* Open question

The generic request is keyed by =entity_id=, a uuid. The shell and HTTP surfaces
are keyed by =username=. Resolving one to the other is a step every such surface
would repeat, so decide whether it belongs in the command, in a small client
helper, or whether the generic request should also accept a natural key.
