#+title: A self write is refused on a tenant with accounts
#+description: Every write where the actor is the account written is refused with 'Invalid modified_by' on a tenant that holds user accounts: the generated insert trigger retires the account's current row as part of the version replace before it validates modified_by, and the validator accepts an actor only while a current row with that username exists. The contact record's insert reaches it too, through the account version touch. The bootstrap branch hides it from unit tests. Found by the profile journeys end-to-end run; PUT /api/me/profile and PUT /api/me/contact-information cannot land.

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

On a tenant that holds user accounts, a write whose actor is the account
written is refused. The generated insert function performs its version
management first — it retires the account's current row with =valid_to =
clock_timestamp()= — and only then assigns =NEW.modified_by :=
ores_iam_validate_account_username_fn(NEW.modified_by)=. The validator accepts
an actor only while a current row with that username exists, and the retirement
just removed the actor's own row, so the write raises =Invalid modified_by:
<username>= (=23503=). Every self write hits it: the member's own profile and
contact saves, and an administrator's write to their own account. The contact
record reaches it through the account version touch its insert performs
(=ores_iam_account_contact_informations_insert_fn= calls
=ores_iam_accounts_touch_version_fn= before its own validation).

* Why

Two of the three Profile journeys cannot land their save on any tenant that
already holds accounts: =PUT /api/me/profile= and
=PUT /api/me/contact-information= answer "The write failed.", while the
administrator's write to a colleague's record passes, because retiring the
colleague's row leaves the actor's own row current. The validator's bootstrap
branch — a tenant with no current non-service accounts passes any actor — hides
it from every unit test that seeds its own tenant. The ordering lives in the
generator, not in one generated file: the assignment appears in 345 generated
SQL files, so the fix belongs to =sql_schema_domain_entity_create.mustache= and
a regeneration, not to a patch of each output. Found by the profile journeys
end-to-end run (task [[id:6CDA40DF-EBED-4F62-9804-525EEAB0282C][Build the
profile screen]], 2026-10-05).
