* Goal

An installation that predates the shared copy loses the copies it already
holds, so every tenant reads the installation's days, and an operator can
rebuild that copy with a command rather than by restarting the service.

* Acceptance

- A tenant's rows for a calendar the installation owns are closed or removed,
  in one run per tenant, so the read resolves to the installation's copy
- An operator command rebuilds the installation's copy on demand
- The command is idempotent: a second run extends the copy and rewrites nothing
- A test shows a tenant reading the installation's days after the purge, with no
  row of its own under the calendar

* Analysis

[[id:A898881E-B0A8-4E23-B717-DB7681AB2B18][Hold the calendar dates once, in the
system tenant]] stopped new copies from being written and made the read resolve
the party's exceptions over the installation's days. It did not remove the rows
a tenant had already been given: each tenant provisioned before the change holds
its own days for every shared calendar, and `calendar_day_service` prefers the
caller's row for a date, so those rows would mask the installation's later days
rather than merely waste space.

The purge is a per-tenant act, because only a session inside a tenant may close
that tenant's rows: the table's delete policy is the own-tenant one. An operator
runs it once per tenant, or the recompute path runs it for the tenant that
triggers it.

* Plan

The rebuild command already exists: =POST /api/refdata/calendars/{code}/rebuild=
extends a calendar's days, and since the days moved to the owning level a
system-tenant session builds the installation's copy while a tenant's rebuild of
a shared calendar writes nothing. That item of the acceptance is therefore met
by the surface that was already there, and this task adds the purge beside it.

The purge is a command of its own, in the message model the materialisation
already uses (=ores.refdata.calendar_materialisation_messages=): a request that
names one calendar or none, and a response that reports the rows removed and the
calendars they came from. The service lists the calendars the caller can read,
keeps the ones it does not own, counts the caller's live rows for each, and calls
the repository's batch close. A calendar the caller owns is skipped, because its
days are the tenant's own. The handler takes the caller's context, so the table's
delete policy confines the command to the caller's tenant.

An HTTP route exposes it beside the rebuild, =POST
/api/refdata/calendars/dates/purge=, and the route inventory is regenerated.

* Result

A tenant can remove the copies of the installation's days that it was given
before the days moved, and the installation's own copy is left alone.

The command is =refdata.v1.ops.purge_calendar_date_copies=, with an HTTP route at
=POST /api/refdata/calendars/dates/purge= that takes an optional calendar code.
It reports the rows removed and the calendars they came from, skips a calendar
the caller owns, and is idempotent: a second run removes nothing. The caller's
context is the one the handler uses, so the delete policy keeps the command in
the caller's tenant.

The rebuild command the acceptance asked for already existed, as =POST
/api/refdata/calendars/{code}/rebuild=, and the owning-level rule makes it build
the installation's copy when the session is the system tenant's. It is stated in
the plan rather than added again.

Proved by a new case, =purge_removes_the_tenant_copies_of_the_installation_days=:
it builds an installation calendar, writes a stale tenant row that contradicts
it, shows the party read preferring the stale row, purges it, shows the
installation's answer returning with its own holiday untouched, and shows the
second purge removing nothing. The calendar, materialisation and tenor
resolution cases pass beside it (28 cases, 3078 assertions).
