* Acceptance

- The resolution answers the addresses of each trade, keyed by trade id, and the distinct union for a caller that only needs the set.
- A trade whose instrument rows hold no address comes back with no addresses rather than an error, and the caller can tell it apart from a trade whose addresses the market lacks.
- A test pins the per trade answer against the trades of a small set.

* Plan

The resolution is already per trade: =ores_trading_market_references_fn= returns
=trade_id=, the address and the source. What collapses it is the read above the
function, which asks for =distinct oresmd_uri= because every caller so far wanted
the union, and the message, which has one list for the whole set.

1. *The message carries both answers.* =resolve_market_data_requirements_response=
   gains =trade_requirements=: one entry per trade the request names, in the order
   it names them, each with its own distinct addresses. A trade named twice
   answers once. A trade whose rows hold no address keeps its entry with no
   addresses, which is what tells "this trade names nothing" apart from "this
   trade was not in the set" — the second is absent from the answer, the first is
   present and empty.
2. *The union is derived, not read twice.* The repository reads the per-trade rows
   once and the operation states the union from them, so the two answers cannot
   disagree about which addresses the set needs. The union stays in the response
   because a caller that only gathers market data wants the set and not the map.
3. *The fold is a plain function.* Grouping rows into a trade's addresses, seeding
   an entry for every trade asked about, is a function over rows, so a test states
   it without a database: two addresses on one trade, a trade with none, the same
   address on two trades, and a trade named twice.
4. *The SQL function does not change.* It already answers per trade and the pgTAP
   test already pins its rows; only the read above it changes.

* Result

The operation answers what each trade needs beside what the set needs. A caller
that has to say which trade lost its valuation now reads a trade's own addresses
instead of inferring them from the union, and the caller that only gathers market
data reads the same answer's union, which is now derived from the per-trade answer
rather than read beside it.

The three states a caller must tell apart are told apart by presence and emptiness
rather than by a flag: a trade the request did not name is absent from the answer,
a trade that names nothing is present with no addresses, and a trade that names
addresses the market lacks is present with addresses the market's own answer does
not hold — the last a fact about the market and not about this answer.

The SQL function did not change. It has answered per trade since it was written and
the pgTAP test already pins the row of a floating leg, the absence of one for a
fixed leg, and the fact that a trade outside the set states nothing; what changed
is the read above it and the message it fills.
