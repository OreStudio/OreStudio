* Acceptance

- The generated series projects to a stated family, or the generator refuses to make one it cannot state.
- The generated subclass and the generated URI agree, so the identity kind rule accepts them.
- A suite that writes generated series writes no identity row of kind 'unknown'.

* Plan

=generate_synthetic_market_series= is generated from =cpp_domain_type_generator.cpp.mustache=,
which gives every text column a faker word. For a series that is a lie rather than a
placeholder: the URI is the identity, so =oresmd://generic/<noun>-<n>?type=fixing-<n>=
is a series with no family at all, and the projection records it as =unknown=. The
generator was patched once before, in sprint 22, to set the asset class and the
subclass so the mapper had an enum to serialise -- a fix for the store, not for the
data.

Three seams, in order of how much they change:

- A =:generator_expr:= on the =oresmd_uri= column and on =series_subclass=, which the
  entity meta model already supports. Cheap, but the two expressions have to stay in
  step by hand, and a fixed URI collides on the series unique key unless every row
  draws a different party, which is exactly what the fixtures override.
- A codegen change so the model states a series' identity as one expression that
  yields the URI and the subclass together, which is the honest seam: the two are
  one fact.
- Stop generating series at all and have the fixtures state the URI and the subclass,
  through a helper that builds a row from a real identity. Sixty call sites, and every
  one of them becomes a fixture the guard actually exercises.

The third is the one to weigh against the second: a test that generates a series is
usually a test about something else, and an explicit row reads better than a faker
word. Whichever is chosen, the done condition is the third acceptance bullet: no
suite writes an identity row of kind =unknown=.

The first seam was taken. The generator writes an IBOR fixing, which the codec
reads and the =ir/index_fixing/ibor= shape states, so one expression is enough
for the URI and the subclass is the constant =index_fixing=. The two expressions
stay in step without a codegen change, because the subclass no longer varies.
The URI collision the plan feared does not arise: the index name carries the
row's counter, which keeps two rows of one party apart, and a random part, which
keeps a run apart from earlier runs in the tick store.

* Notes

The random part of the name is needed. A first version used the counter alone.
The counter restarts in each test process, and the tick store keys its streams by
the URI and keeps them between runs, so a second run would have read the first
run's ticks.

Three fixtures that override the generated URI were brought in line. The two zero
curve fixtures now state =yield=, the subclass of the curve their URI names. The
tick reads fixture wrote a =generic= URI and now writes an IBOR fixing named from
the series id.

Two fixtures still write =unknown= rows, both by hand rather than through the
generator:

- The identity fixture in =repository_market_series_repository_tests.cpp= writes
  a =generic= URI. A fixing URI there makes
  =two_providers_keep_two_series_for_one_item_and_party= fail, because the
  identity table's unique index for fixings leaves out the provider. That is a
  defect in the identity table, not in the fixture, and it is captured as
  [[id:3B58C44F-5E31-4A30-B185-C06A75E6451C][Two providers of one fixing collide in the identity table]].
- The FX option fixture in =service_observation_reader_tests.cpp= adds a =tag=
  field to keep each series apart, and the =fx_option= schema has no such field.
  The instrument's identity is its currency pair only, so a readable URI would
  collide across cases on the shared party.

The backfill case that writes =no_such_instrument= is unreadable on purpose.

* Result

The test generator now writes a series that is an identity: an IBOR fixing whose
name the codec reads, under the =index_fixing= subclass. Every fixture built on
it exercises the projection and the shape guard rather than the unreadable path.

All three acceptance points are met. The generated series projects to the stated
family =ir/index_fixing/ibor=. Its subclass and URI agree, so the identity kind
rule accepts them, and the fixtures that override the URI now state the matching
subclass. Across three suite runs on a recreated database, no generated series
wrote an =unknown= identity row. The rows that remain come from two hand-written
fixtures, named in Notes, and one from the deliberate unreadable case.
