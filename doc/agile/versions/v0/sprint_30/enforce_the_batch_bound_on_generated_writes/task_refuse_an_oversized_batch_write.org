* Goal

A generated put-many or delete-many of more than 1,000 elements is refused as invalid before any row is read or written, and the refusal names the bound.

* Acceptance

- The outcome catalogue holds batch_too_large, an invalid request outcome whose message names the entity and the limit.
- Every generated put-many and delete-many refuses more than 1,000 elements with it, and accepts exactly 1,000.
- A service test proves a refused put-many writes nothing and a refused delete-many removes nothing.

* Plan

- Add =batch_too_large= to the outcome catalogue as an invalid request outcome
  with the arguments entity and limit, and render it into =outcome_code.hpp=.
- In the service template, check the size of the batch at the top of every
  put-many block (entity, junction, aggregate) and every delete-many block
  (entity, junction), before any read or write, against =max_batch_size=.
- Regenerate every service.
- Replace the two marketdata service tests that put 1,001 rows to span read
  chunks: the service now refuses such a batch, and the repository tests keep
  the chunked-read cases. Add a test for exactly the bound, one for a refused
  put-many and one for a refused delete-many.

* Result

Every generated put-many, aggregate put-many and delete-many refuses a batch of
more than 1,000 elements with =batch_too_large= before it reads or writes a row.
The refusal is an invalid outcome, and its message names the entity and the
bound. A batch of exactly 1,000 is accepted. The marketdata service tests prove
the three cases: exactly the bound is answered in order, a refused put-many
writes nothing, and a refused delete-many removes nothing.
