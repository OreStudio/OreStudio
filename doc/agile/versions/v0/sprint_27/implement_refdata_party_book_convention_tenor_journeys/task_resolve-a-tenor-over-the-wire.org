* Notes

Split out of [[id:D538F972-C4A4-4BF3-A189-D0BD1755FBA4][Resolve a tenor over
the wire, and make the tenor machinery writable]]. That task built the two
things this operation depends on -- the roll rule on =tenor_convention= and the
writes on =tenor_convention_resolutions= -- and filed this one, because a new
hand-written handler with its own protocol pair, registration and permission is a
unit of its own and it could not be written before the roll rule existed to
report.

Reconnaissance at =cff0559411= (trunk).

*What to call.* =resolve_end_date= is the whole of the logic and it already
exists: =projects/ores.refdata/api/include/ores.refdata.api/domain/tenor_resolution.hpp=,
signature =resolve_end_date(const tenor&, const tenor_convention&, const
std::optional<tenor_convention_resolution>&, std::chrono::year_month_day horizon,
std::chrono::year_month_day spot, const std::optional<std::vector<std::chrono::year_month_day>>&
schedule_dates = std::nullopt)=. It is pure: everything it reads is passed in. The
handler's work is therefore loading the three rows and the two dates, calling it,
and reporting what it did. The doc comment above it names exactly which
conditions throw =std::invalid_argument= and which throw =std::logic_error=, so
the refusal payload's cases are already enumerated.

*The pattern to copy.* A custom operation is declared in the entity's model and
implemented in a named src block, not hand-edited into a generated file. In
=projects/ores.refdata/modeling/ores.refdata.party.org=:

- the =* Messages= section declares a request/response pair, with =:subject:= and
  =:response:= drawers on the request and typed =*** <field>= children on both
  (see =get_party_composite_as_of_request= and its response);
- the =** Custom NATS handler methods= section carries
  =#+begin_src cpp :name custom_handler_methods :implements B9E2F4A1-3C7D-4E8B-A5F0-2D6C1B8E3A7F=
  with the handler body.

Both the C++ protocol header and its TypeScript twin render from that one
declaration, so the client sees the new pair without a second edit. The registrar
subscribes whatever the model declares.

*The subject.* The journey names none, and the composite reads sit under
=refdata.v1.ops.*=. A =refdata.v1.ops.resolve_tenor= keeps the generated list and
get subjects for the catalog untouched and puts the operation where the other
hand-written refdata operations live; =refdata.v1.tenors.resolve= would read
better but would sit inside the generated per-entity namespace, so check which
one the subject-conformance gate expects before choosing.

*A permission is needed.* The operation is a read but it is not one of the
generated reads, and =check_handler_permissions.py= classifies by the request a
method decodes. Decide whether it takes =refdata::tenors:read= (it reads the
catalog and resolves, and writes nothing) or a permission of its own, and seed it
if it needs one.

*The refusal belongs with the operation, not before it.* The journey's second
missing row is the refusal payload, and there is nothing to carry a refusal until
the operation exists. Build them together, and prefer a failure reply on the
resolve response over mapping a typed error in the handler, because the shared
=result= already has the shape -- =outcome=, =code=, =message= and the =fields=
vector -- and the assets and IAM services already fill =fields=.

*What landed already, so do not rebuild it.* =tenor_convention= carries
=business_day_convention_type=, validated by
=ores_refdata_validate_business_day_convention_type_fn= and defaulting to
=ModifiedFollowing=, which is the roll rule the reply reports.
=tenor_convention_resolutions= takes =put=, =put_many=, =delete= and
=delete_many=, with =refdata::tenor_convention_resolutions:write= and =:delete=
seeded. The tenor write already carries its change reason: =put_tenor_request=
takes an =intent= whose =reason_code= and =commentary= the service copies onto the
row, so the journey row that said it did not was stale and has been corrected.
