* Goal

Make a durable JetStream consumer heal itself after a subject rename: when the caller names the stream, compare the stored filter and delete a consumer whose filter differs, so the subscribe recreates it against the current subject. Carry the stream name at every durable subscribe site.

* Acceptance

- js_queue_subscribe takes an optional stream name and reconciles the durable before attaching.
- The workflow engine and compute wrapper subscribes name their streams.
- A durable planted on a stale filter is replaced on the next service start and the service comes up running.

* Plan

=ensure_stream= already compares a stream's subject filter and updates it, so
the stream side of a rename heals. A durable consumer stores its own filter,
which nothing compared, so the consumer kept the old spelling and
=js_QueueSubscribe= refused to attach it.

Add the same reconcile on the consumer side, at the one place every durable
subscriber goes through:

1. =js_queue_subscribe= takes an optional trailing =stream_name=. When it is
   given, the call reads the durable's stored filter first.
2. On a mismatch it deletes the consumer, so the subscribe that follows
   recreates it against the current subject. A consumer that is absent or
   unreadable is left alone and the subscribe reports the real reason.
3. Each durable subscribe site names its stream: the workflow engine's two
   consumers and the compute wrapper's one.

Deleting the consumer discards its position, so the recreated one delivers from
its start policy again. That is at-least-once by design: a consumer whose filter
is wrong has no position worth keeping.

No unit test covers this. JetStream behaviour needs a live server, which the
unit suite does not start, and =ensure_stream='s reconcile is verified the same
way. The proof is the plant-and-heal run recorded under Notes.

* Notes

The plant-and-heal proof, run on 2026-10-07 against the festive_dijkstra fleet:

1. Stop =ores.workflow.service=.
2. Create the durable with the pre-rename filter:
   =nats consumer add ores_dev_festive_dijkstra_workflow
   workflow-engine-step-completed --filter
   ores.dev.festive.dijkstra.workflow.v1.events.step-completed --deliver all
   --ack explicit --pull --replay instant --defaults=.
3. Start =ores.workflow.service=.
4. =nats consumer info= then reports =created= at the start time and
   =Filter Subject: ores.dev.festive.dijkstra.workflow.v1.ops.step_completed=,
   with =Active Interest: Active using Queue Group ores.workflow.service=.

Before the change step 3 failed with =js_QueueSubscribe failed= and the service
exited. The same defect stranded four consumers in another environment after the
subject migration.

Discovered while verifying: =compass services logs= died with
=UnicodeDecodeError= when a service logged a binary body. Fixed here with
=errors="replace"=.

* Result

=js_queue_subscribe= reconciles the durable when the caller names its stream.
The workflow engine and the compute wrapper name theirs. A durable planted on
the pre-rename filter was replaced on the next service start and the service
came up running, so a subject rename no longer strands a consumer.

The full check suite found three failures that belong to =origin/main=, not to
this branch: =iam.v1.storage_capabilities.mint= is outside the entity protocol
and its model opts the TypeScript protocol facet out, so =subject-conformance=,
=protocol-twins= and =codegen-tests= fail on a clean trunk. They are recorded
here and need their own task: the subject wants the ops namespace, and the
TypeScript twin wants a projection for =ores::security::jwt::storage_grant=,
which today is hand-written C++ with no org model.
