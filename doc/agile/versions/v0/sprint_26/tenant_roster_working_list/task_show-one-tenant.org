* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

1. *Journey.* Write See one tenant, draw its wireframe and list it in the
   tenancy hub.
2. *Party read.* Every party read filters by the session's tenant, so a system
   administrator reads only the system tenant's parties. Declare
   =refdata.v1.parties.list-of-tenant= in an operation model in
   =ores.refdata= and generate its protocol. The handler refuses a caller
   outside the system tenant, checks =refdata::parties:read=, and reads with a
   context scoped to the named tenant. The party table's policy already lets
   the system tenant read every row, so no policy changes. Repository and
   handler tests prove the scope and the refusal.
3. *BFF.* =GET /api/tenants/:code= refuses a session outside system
   administration, reads the tenant with =iam.v1.tenants.get=, the tenant's
   runs with =workflow.v1.instances.list= filtered on the target, and the
   parties with the new read. =iam.v1.tenants.get= keys a tenant by its code,
   so the address names the code. It answers 404 for an unknown code or the
   system tenant. A party read that fails does not fail the page: the answer says the
   parties are unavailable, as the roster does for runs.
4. *Web.* A =TenantPage= at =/tenants/:code= with three panels: details with
   provenance, setup, parties. The roster's *Open* item links to it.
5. *Verify.* Web, BFF and C++ tests; a full build and ctest; a live read of a
   real tenant and of an unknown code.

* Result

A system administrator opens a tenant from the roster, by its name or the row
menu's *Open*, and reads =/tenants/:code=: the details with the row's
provenance, the setup run, and the parties with each parent by name. An
unfinished run links to its page. An unknown code, or the system tenant's,
answers that no tenant has the code. The journey
[[id:9A77690B-8190-4237-94F1-D8111F3FB0B9][See one tenant]] was written first,
with its wireframe, and the tenancy hub lists it.

=iam.v1.tenants.get= keys a tenant by its code, so the address names the code
and not the id. The parties come from a new generated read,
=refdata.v1.parties.list-of-tenant=, with a generated shell command. Its service
refuses a caller outside the system tenant and the system tenant as a target,
and reads with a context scoped to the named tenant. =GET /api/tenants/:code=
joins the three reads; a failed run or party read empties that panel and says
so.

Tests: four C++ service tests and four shell tests; 5 BFF route tests, with a
stub proof of the system tenant check; 7 web screen tests and 2 roster tests;
5 wire read tests. The full build is clean. ctest passed 87 of 89 first; the 2
failures were a database built before main added a column, and both suites
pass on a recreated database. The live read of a provisioned Acme tenant
answered its run and its 5 parties, all its own, and the system and unknown
codes answered 404.
