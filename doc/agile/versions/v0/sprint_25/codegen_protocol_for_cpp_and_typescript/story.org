* Goal

The IAM component hand-writes eleven protocol headers. Each header declares request and response structs, a NATS subject, and a response alias. ores.codegen cannot express these messages today, because the entity model covers CRUD shapes only.

This story adds an ores.codegen.operation model type. One org file holds every message of one protocol header. The C++ template renders that org into the same bytes the hand-written header holds today.

The story then adds a TypeScript target space. The same org renders TypeScript interfaces. The ores.qt UI is moving to TypeScript, and it needs every message.

* Decisions

- *The generated headers gain the AUTO-GENERATED banner.* =render_template= stamps that
  banner into every =*.hpp.mustache= output that carries =cpp_license=. Suppressing it for
  these eleven headers needs a special case in =_emits_cpp=, which costs more than the
  five banner lines it removes.
- *The org names the response on the request node.* Pairing is many-to-one:
  =switch_party_request= reuses =select_party_response=. A nested =*** request= /
  =*** response= shape cannot express that, so the request node carries a =:response:= key
  and plain structs stay flat siblings.
- *TypeScript field names stay snake_case.* The C++ member names are the rfl::json keys.
  The wire format therefore fixes the TypeScript property names, and a camelCase rename in
  the generated interfaces would break decoding.
- *The operation model type sits beside the existing model types.* =load_model= already
  dispatches on =#+type:=, so the new type needs one map entry and one loader function.

* Out of scope

- The other hand-written protocol headers in the repository. This story covers IAM alone.
- C++ behaviour changes. The port holds the bytes steady, apart from the banner.
- Qt UI code. The story generates the TypeScript the UI consumes; the UI migration is
  separate work.
- The HTTP and shell transport shapes.
