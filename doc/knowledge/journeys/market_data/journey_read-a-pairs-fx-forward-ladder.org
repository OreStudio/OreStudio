This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A trader or quant reads their party's published forward set of a pair at an as-of: outrights, discount factors, forward points and swap points, with the inputs and the approval behind them.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want my party's forward curve of this pair at this as-of, in whatever measure I need: forward rate, discount factors, forward points or swap points. I want to know what it was built from and who approved it." The journey is done when the person has read the ladder in the measure they need and can name the spot, the two curves and the approval behind it.

* Actor and trigger

The actor is the trader or the quant, and it can be anyone who reads market data for the party. The trigger is a price to check, a hedge to size, an FX option's forward to confirm, or a published curve that has just changed. The journey starts at *Market data / FX forward ladder* and ends when the person leaves the page.

The journey reads and changes nothing. A forward set is a published record of the session's party: a person raised it, another approved it, or the tenant's auto-approval closed it. So every number on the page is one somebody approved, and it reads the same after the market moves.

* Steps

1. *Open the ladder.* The person opens *Market data / FX forward ladder*. The system lists the pairs the party can read and opens the last pair the person read, as the address states.
2. *Choose the pair and the as-of.* The person picks a USD pair or a cross with a convention, and an as-of. The system answers the party's newest published set of that pair at or before the as-of.
3. *Read what it is built from.* The system states the spot, each spot observation it read (one for a USD pair, the two USD legs for a cross), the spot date, the convention version with its pip and calendars, the method, and each funding curve with the set it came from. A curve withdrawn since says so. A statement says the rates hold no cross-currency basis. Each input links to its own record.
4. *Read how it was approved.* The system states who raised the set, who decided it, the decision's comment and who published it, and links the request. A set closed by auto-approval says so and names the rule; the decision's comment names who turned the rule on.
5. *Read the ladder.* The system shows one row per tenor: near date, value date, forward rate, forward points, swap points and both discount factors. The short dates come first, and each states its own two dates.
6. *Choose the measure.* The person picks forward rate, discount factors, forward points or swap points. The chart draws that measure by tenor, and the matching column is highlighted. No new read is needed.
7. *Change the start.* The person starts the ladder from spot, today or tomorrow. The system sets the near date of the tenors after S/N, recomputes their swap points and marks those rows. The short dates keep their own dates.
8. *Read a forward-forward.* The person picks a near and a far tenor. The system states both forward rates, the swap points between them and the days. The ladder does not change.
9. *Meet a refusal.* If the party has published no set of the pair at or before the as-of, the system shows no numbers and says so.
10. *Leave.* The address holds the pair, the as-of, the start, the measure and the forward-forward tenors, so the person can send this exact view to someone else.

The owner signed off this journey and its prototype on 2026-11-09.

Placements the prototype decides:

- The page is under *Market data*, at =/market-data/fx-forwards=, beside *Published curves*.
- A curve name links to its page in *Published curves*, a spot and the convention to the pair's page, and the request to its own page.
- The chart spaces the tenors evenly and not by time.

* Prototype

A static page at =doc/prototypes/market_data/fx-forward-ladder/index.html=: mock data only, no backend, no build step and no session. It argues that one page can show all four measures of a ladder, always beside the inputs they rest on.

The start, the measure and the forward-forward need no read. The reply states each tenor's dates and forward rate, so the client computes the rest.

* What is missing

1. *A party has no set until one is published.* Provisioning will publish a set of every pair each party can build; [[id:30A638A1-D5EF-4DDF-BAB9-4121CDC1B488][Publish FX forward curves in provisioning]] records the work.
2. *The screen does not raise a publish.* A person publishes from the shell, with =fx_forward_operation publish-fx-forward=.
