--------------------------------------------------------------------------------
2. A correction the runs forced: the duplicate window
--------------------------------------------------------------------------------
The engine publishes a step command with `Nats-Msg-Id = <step id>` and the
stream carries a 2m Duplicate Window. So:

  * a copy that carries that header and is published within two minutes of the
    first is dropped by the server and never delivered;
  * the same applies to the step-completed event, so a second completion for one
    step inside two minutes never reaches the engine and the claim is never
    released.

The first two duplicate attempts were contaminated by exactly this: each
produced one delivery, not two, which is why no loser ever appeared. Both copies
of the run that counts go WITHOUT the dedup header, which is the only way to get
two stored messages for one step.

4. The loser answered busy (run_busy_path_test.sh)
--------------------------------------------------------------------------------
A fast step cannot show this: the claim is released the moment the engine writes
the step away from in_progress, so with a step that reports in under 100 ms the
live-claim window is that same 100 ms. The identity fixture declares
delay_seconds for exactly this purpose. Run started 15:35:48, one step
`hold_the_claim`, delay 8 s; a second copy of its command published at
15:35:56.310 while the claim was live.

Workflow service journal, verbatim:

  15:35:48.376246 [INFO] [ores.workflow.messaging.identity_step_handler]
    Identity step 'hold_the_claim' waiting 8s so the run can be observed.
  15:35:56.376302 [INFO] [ores.workflow.messaging.identity_step_handler]
    Identity step 'hold_the_claim' reporting completion.
  15:35:56.376597 [INFO] [ores.workflow.service.workflow_engine]

  15:35:56.393059 [INFO] [ores.service.messaging.step_command_stream]

--------------------------------------------------------------------------------
6. Kill-mid-step (run_kill_mid_step_test.sh)
--------------------------------------------------------------------------------
Stage: the identity fixture, not a reporting step. A reporting step reports in
about 80 ms, so killing it in flight is a coin flip; the fixture declares
delay_seconds so a run can be held open. The fixture's step deadline was
write_step_timeout, 120 s -- exactly the lease -- so it was raised for this run
to a fixture-local identity_step_timeout of 900 s (identity_workflow.hpp, saved
as part of this artifact). Without that the engine's deadline would fail the
step at the moment the lease ended and the run would prove the opposite.

Run d54640c6-4554-4d65-addf-14fd8d2207cd, step 1849e14b-6ba8-4f55-80fc-3ea7ad37c461,
one step hold_the_claim with delay_seconds 15.

Observed timeline:

  14:48:33.577  run started
  14:48:33.648  identity handler: "waiting 15s so the run can be observed"
  14:48:33.680  CLAIM TAKEN        ores.workflow.service/993525  attempts=1
  14:48:35.682  HOLDER SIGKILLED   (t0 + 2.0 s)
  14:48:37.929  service auto-restarted (Restart=always), pids 993525 -> 994035
  14:49:03.646  DELIVERY 2         "is held by another delivery; retrying ... in 30000ms"  (t0 + 30.0)
  14:49:33.666  DELIVERY 3         same                                                  (t0 + 60.0)
  14:50:03.685  DELIVERY 4         same                                                  (t0 + 90.0)
  14:50:33.712  TAKEOVER           handler running again under pid 994035                (t0 + 120.0)
  14:50:34.292  claim row          ores.workflow.service/994035  attempts=2
  14:50:48.713  completion reported (the re-run's own 15 s delay)
  14:50:49.261  STEP COMPLETED
  14:50:48.888  Workflow COMPLETED: type=identity_workflow steps=1

Held against the prediction: redeliveries at about 30, 60 and 90 seconds, each
finding a live lease and naking with the 30 second hold off -- exact. Takeover at
about 120 seconds, when the lease ended -- exact. No deadline failure. attempts
went 1 -> 2 across the takeover, which is the counter doing its job.

The one difference: the parent's note said completion "a little after 120". It
was 135.6, because the fixture's delay_seconds 15 applies to the re-run as well
as the first attempt, so the takeover at 120 was followed by 15 seconds of work.
That is the fixture's own delay, not one of the four numbers.

A note on the restart: the unit carries Restart=always, so the SIGKILL was
followed by an automatic restart 2.2 seconds later. That is why deliveries 2-4
had a consumer to come back to. Had the holder stayed down, the message would
have waited, and the claim would still have been taken over when it finally
returned -- the lease does not need a live consumer to expire.
