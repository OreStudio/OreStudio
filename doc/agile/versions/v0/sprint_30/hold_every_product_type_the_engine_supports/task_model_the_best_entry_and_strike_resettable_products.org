* Acceptance

- each of the four types names an instrument table that carries the terms the product states
- the projection reads and writes each element, value for value
- each type has a builder, and the catalogue routes all four
- the generator books one trade of each type through its builder, and the recorded trades hold it
- the ORE engine test reads and builds each, with no error of the trade kind
- every fact the element states is a column or a row: no list, basket or schedule is held as text

* Plan

ORE reads the four types as scripted trades over fixed elements
(=bestEntryOptionData2=, =strikeResettableOptionData2=). They route to the
scripted instrument table through the class-read path that the basket and
rainbow options use. That path already reads every element they state: scalar
leaves as parameters, one =Underlying= as an underlying row, and the
observation schedule as a product schedule. The projection needs only the four
entries in its table.

- Two builder templates, =best_entry_option_builder= and
  =strike_resettable_option_builder=, take the family (equity or FX) as a
  parameter.
- =trigger_direction= moves to =option_position.hpp=, so the commodity and
  scripted builders share it.
- The generator states the observation dates as a list, one a quarter, moved
  off weekends. ORE's FX examples state a list, and the path check compares the
  generated trades with them.

* Result

EquityBestEntryOption, FxBestEntryOption, EquityStrikeResettableOption and
FxStrikeResettableOption are held in the scripted instrument table. Each fact of
the element is a parameter, underlying or schedule row; the observation dates
are schedule date rows. The round-trip test reads ORE's two FX examples from
its AMC portfolio and writes them back. Each type has a builder, the catalogue
routes all four, and the generator books one trade of each. The ORE engine
builds the recorded trades with no error, and the recorded FX trades state
every path ORE's examples state.
