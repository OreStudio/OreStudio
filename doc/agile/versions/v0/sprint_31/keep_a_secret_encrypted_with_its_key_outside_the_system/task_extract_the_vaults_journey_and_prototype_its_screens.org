* Goal

A person keeps the secrets ORE must use, and the product has no screen for
that act. This task writes the journey that person walks and draws the screens
it needs, after HashiCorp Vault's own screens and not as a copy of them, before
anything is built. The journey is judged step by step against the record screen
standard, and the owner signs it off. The prototype then draws every state at
its own address.

* Plan

** The screens

Four screens, and each one answers one question:

| Screen    | The question it answers                                                    |
|-----------+-----------------------------------------------------------------------------|
| Secrets   | What does the installation hold, for which consumer, at which key version?   |
| Secret    | What is this secret's history, what is its value, and how is it replaced?    |
| Consumers | Which services may receive a secret, and is each one enabled?               |
| Uses      | Who asked for what, when, and at which key version?                         |

** The steps

The journey runs in one sitting. An administrator opens the secrets list and
reads what the installation holds. They write a value for a consumer. They
replace that value, and the earlier version stays in the history. They reveal
the current value, because a person who maintains a service must be able to
check what the installation holds. They rotate the key that protects every
secret, as one audited act, and no one re-enters a value. They register a
consumer with its public key, or disable one. They open the uses screen and read
who asked for what.

Two refusals sit in the journey, because a screen is judged by what it refuses:
a person who holds no write permission, and a consumer that asks for a secret
it does not own.

** What comes from HashiCorp Vault

| Vault screen          | What this journey takes from it                                             |
|-----------------------+-----------------------------------------------------------------------------|
| Secrets engine (KV)   | A secret has versions and metadata, and the list marks the current version   |
| Secret detail         | The value is masked, one control reveals it, and the reveal is a request kept |
| Policies and tokens   | A client's own record says what it may do, which here is the consumer row    |
| Audit devices         | Every request is recorded, which here is the uses screen                     |
| Seal and key rotation | The protecting key is an object with a version and a last rotated time       |

** What the journey refuses, and why

- A lease and a dynamic credential end by themselves. ORE's secrets are
  configuration and outlive any run.
- An unseal ceremony splits a key among holders. This vault's key never enters
  the process as a share.
- A reveal that nobody records, or a value on a screen without the read. The
  value is masked until the person asks, the ask demands
  =vault::secrets:read=, and the act is recorded twice: the vault records the
  gateway's resolve and the gateway records the person. The bus still carries
  ciphertext, so the record is the price of the reveal. Read
  [[id:4F28F755-7DA1-4EDD-9983-256622B6088A][Sealed Delivery of a Secret to Its
  Consumer]].

** The order

The journey comes first and stops for the owner's sign-off, because a prototype
drawn over an unjudged journey hides its gaps. The prototype follows, and it
settles the placements the journey leaves open: how a version list marks the
current version, the words for a secret that no consumer has read, where a
refusal sits, and how a masked value invites a reveal and what the screen says
about the record it leaves.

** The area

The menu structure has no secrets area. This task decides whether the screens
join Operations, which holds the installation's own life, or take an area of
their own, and it amends the menu structure page in the same change.
