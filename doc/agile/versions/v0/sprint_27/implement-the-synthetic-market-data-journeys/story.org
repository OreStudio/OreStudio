* Decisions

The remainder is carried in [[id:B34E795E-6075-4738-8453-E8266A80D134][Build the synthetic collection and model catalogue journeys]].

- *One table, generic routes.* The BFF serves the synthetic resources from
  one table (=bff/src/synthetic.ts=) over =/api/synthetic/:resource=, not a
  route set per screen. The nine generated resources share one CRUD shape,
  so a screen adds no BFF code to read or write them.
- *A save is one =put_many=.* The server checks every row's version and
  writes the set in one statement, so a mixture or a ladder lands whole or
  not at all. A batch removal is unconditional, because =delete_many=
  refuses versions.
- *Read one row by its one-of filter, not by =get=.* A definition's =get=
  takes =parameter_name=, which several process types share.
- *Shared catalogues are written from the system tenant only.* The process
  types and the definitions live in the system tenant. The definitions are
  read only until their key names the process type, and the process types
  are writable from a system session alone.
- *Feed screens follow one standard.* The FX price feed screen is the shape
  of every feed screen, recorded in the
  [[id:303D85B2-0039-4B1C-83BD-BB866BC0AEE1][Feed screen standard]]: the list
  is the run dashboard; the process is edited as one set in a list with a
  dialog per part, with marked unsaved changes and one Save that asks the
  reason and offers a restart.
- *The engine sits with the process, and the server converts.* The engine
  decides what a part's numbers mean, so it is chosen on the process tab, and
  a change asks the synthetic service to convert the draft
  (=convert_fx_mixture=). Quant logic that decides a written value lives on
  the server.
- *A running feed keeps its process.* A feed reads its parts when it starts,
  so a save tells the person and offers to restart the feed.
- *The shared record parts take a store.* =RecordStore= gives the record
  list, dialogs and history their routes, so a synthetic screen reuses the
  refdata parts.
