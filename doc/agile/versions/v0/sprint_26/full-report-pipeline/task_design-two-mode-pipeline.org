* Result

Delivered as [[id:259EA767-EDF7-45EF-BE4D-B1A8FA96F7BD][Report execution
modes]]. It states the stage list with an owner for each, the storage-URI seam
that makes the two modes interchangeable, the rule that step results are
addressed by role rather than index, the full NATS contract hop by hop, and
two PlantUML interaction diagrams whose rendered images were read.

The design's most useful output is not the diagram but the distance it
measured, because that is what changes the plan:

- The common tail already exists and works when the shell drives it, and does
  not exist for the workflow, for three reasons recorded in the design and
  owned by the ACME smoke-test story.
- The ORE conversion is much less complete than "we have an XML layer"
  suggests. The bindings cover the whole ORE vocabulary, but the ORE Studio to
  binding mappers cover four document kinds — portfolio, currency config,
  calendar adjustments and conventions — and none of the four configuration
  documents the engine needs.
- =prepare_ore_package= ships =trades.msgpack= and =market_data.msgpack=,
  where the wrapper's contract is =Input/ore.xml= plus six named files, so the
  step's name and the workflow's own description run ahead of its code.
- Nothing reads the engine's output at all, and gathering is a blanket tenant
  dump rather than a resolution of what the selected trades need.

Three questions are left open on purpose rather than settled by assertion:
where the export's inputs live between stages, whether the demo input binding
is a stage or an absence, and what a run should do when no grid is present.

* Added after review: the orchestration section

A review of the first PR asked whether ores.workflow was really in the design,
given that a run coordinates four services. It was — as a participant in both
diagrams and as the publisher of every step command — but the design treated
the coordinator as given and never stated the contract with it. The document
now carries an *Orchestration* section: the participant interface, the
at-least-once dispatch that makes idempotency a requirement on every stage,
the properties the engine gives against what the design needs, the two state
machines and which is authoritative, and the three engine gaps the pipeline
leans on. The contract itself is tasked separately as *Define and enforce the
orchestration contract*.

* Added after review: making the workflow clear

A second review asked whether the document made the workflow clear, and it did
not. The orchestration section had stated the contract, but the document still
opened with a stage table that reads like a chain of direct calls, and it never
said what a workflow *is* here.

It now carries *The workflow: how the stages are run*, which states that a
workflow is a definition registered in C++ at startup rather than seeded data,
that =build_steps= is rebuilt on every dispatch and on recovery, that the chain
is therefore a pure function of the start message, and that one registered
definition serves both modes because the mode is an input to =build_steps=
rather than a type of its own. The stage table now says outright that every
stage is run by the engine and that the Owner column means who does the work,
not who calls it. A third diagram, the dispatch loop, draws the mechanism once
so the two mode diagrams can stay about the stages, and the "what the diagrams
show" section now states that no stage calls another.
