* Result

=doc/llm/memory/a_subject_rename_strands_durable_consumers.org= records it.

A rename leaves every durable consumer stored under the old filter. A durable
is keyed by name and JetStream refuses to attach one whose stored filter
differs, so each durable subscriber fails closed at startup: the service is
absent, the fleet reads 24 of 25, and the service's own log says only
=js_QueueSubscribe failed=.

The trap is that the stream reconciles and the consumer does not, so a rename
looks finished. Four consumers were stranded by the 2026-10-07 migration, the
workflow engine's two and the compute wrapper's two, and the wrapper's filter is
a wildcard, which no stream-level fix could reach.

The memory carries the check to run after a rename and names the structural fix
-- reconcile the consumer the way =ensure_stream= reconciles the stream -- which
is not done here. Another environment captured the same defect as
=a_subject_rename_leaves_durable_consumers_unable_to_attach=, not yet on main.
