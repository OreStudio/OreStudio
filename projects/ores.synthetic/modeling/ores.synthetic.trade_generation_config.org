#+brief: A named, party-scoped recipe for generating a synthetic trade population.
#+created: 2026-10-15
#+updated: 2026-10-15

A named recipe for the trades one party's books receive. It is the
population as configuration: a reviewer reads the row and the two scope
lists rather than a command.

The row names the booking party, the instrument family, the tenor and
notional bands, the as-of anchor and the seed. The book scope and the
counterparty scope are the two multi-valued field sets and live in child
tables, one row per book and one row per counterparty, the same
one-config-many-children shape =fx_spot_generation_config= uses for its
=gmm_component= rows and =ir_curve_generation_config= for its
=ir_curve_template_entry= rows.

The booking party is the row's own =party_id=. The writer sets
=app.current_party_id= to it before each trade, because the trading
insert triggers overwrite the instrument's party from session state.

The two scope lists are the child tables =trade_generation_book= and
=trade_generation_counterparty=, one row per book and one row per
counterparty. Both are edited from this configuration's detail dialog.

The population is a function of the pair (seed, as-of anchor). The seed
pins the shape of the population and not the identity of its rows. The
same pair emits the same rows; a later anchor moves the population
forward rather than repeating it. See
[[id:6E648B05-2ADB-4E03-89CB-D4670CB72FC3][Investigation: Populating ACME
with a trade population]], "What makes a seed deterministic".

** as_of_date
:PROPERTIES:
:type:        date
:cpp_type:    std::chrono::year_month_day
:nullable:    false
:filterable:  true
:END:

The as-of anchor every generated trade date is an offset from. It is an
input, never a read of the clock inside a field generator, so a
re-provision at a later anchor moves the population instead of shifting
stored rows. The population is a function of this column and =seed=
together.

std::chrono::year_month_day{std::chrono::year{2026}/1/2}
#+end_src

** seed
:PROPERTIES:
:type:          bigint
:cpp_type:      std::uint64_t
:nullable:      false
:default_value: 1
:END:

Seed for the generator's random engine. Two runs at the same (seed,
as-of) pair emit the same population, which makes a review a rebuild and
a diff. It pins the shape of the population, not the identity of rows: a
moved anchor deliberately moves the population, and a stable trade
identifier is derived from stable inputs rather than from this number
alone.

#+begin_src cpp :name generator
std::uint64_t{1}
#+end_src

** trades_per_book
:PROPERTIES:
:type:          integer
:cpp_type:      int
:nullable:      false
:default_value: 8
:END:

How many trades one book of the scope receives. The size is a property of
the population and not of the generator, so a tenant that wants a larger or
smaller book states it here rather than in code: the generator holds no
count of its own.

It is a count per book and not a total, so a configuration scoped to four
books states four times this many trades.

#+begin_src cpp :name generator
std::uint32_t{8}
#+end_src

** structures_per_book
:PROPERTIES:
:type:          integer
:cpp_type:      int
:nullable:      false
:default_value: 2
:END:

How many structures the generated trades are grouped into, per book. A
structure is a deal a customer sees, so a population that produced trades and
no structures would leave the composition screens with nothing to show: this
states how many the run groups, and the planner decides which trades go in and
in what role.

Zero states that the scope groups nothing, which is what a tenant that wants
only flat trades asks for.

It is a count per book and not a total, like the trade count beside it.

** reference_curve_id
:PROPERTIES:
:type:     text
:cpp_type: std::string
:nullable: true
:END:

The curve the population's bonds are discounted on, as the oresmd URI of
the market series that curve is. An ORE bond resolves its discount curve
by the index the trade names and the market's own forwarding decides which
curve that index is, so the trade states a curve and the market decides the
rest.

The population is kept in one currency, the first book's own, so one curve
serves every trade it emits. A population whose book keeps no currency a
curve exists for states none, and its bonds then name no curve and are
refused by the engine's builder rather than priced on a guess.

** Flags
:PROPERTIES:
:tablename: ores_synthetic_trade_generation_configs_tbl
:rls_tenant_isolation: true
:rls_party_isolation: true
:END:

Both policies are emitted into this table's own create script by the model
flags above, the shape =ores.analytics.credit_simulation_config= uses. The
sibling synthetic configs instead carry hand-written policies in
=synthetic_rls_policies_create.sql=, which they need because their policies
hop through a parent container's scope; this configuration is scoped to one
party and needs no hop.

** Checks

The bands are constrained for order and for non-negativity. The tenor
band is not: a tenor is a label, and only the refdata catalogue can say
which of two labels is longer.

| expression                                  |
|---------------------------------------------|
| "name" <> ''                                |
| "min_tenor_code" <> ''                      |
| "max_tenor_code" <> ''                      |
| "min_notional" >= 0                         |
| "max_notional" >= "min_notional"            |
| "seed" > 0                                  |
| "trades_per_book" > 0                       |
