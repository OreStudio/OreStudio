#+title: Story: Hotfix: the settings trigger is refused by the function it calls
#+description: ores_variability_system_settings_default_party_fn is an invoker-rights BEFORE INSERT trigger that calls ores_variability_resolve_system_party_fn, whose EXECUTE is revoked from PUBLIC so that only the reading roles hold it. A trigger runs with the writing role's privileges, so the moment a service writes a tenant-wide setting -- a nil party, which is what such a caller sends -- the insert is refused by the function its own trigger calls. The bootstrap is the first caller to do it, and the last step fails with permission denied.

* Decisions

- *Fix the caller, not the grant.* =ores_variability_resolve_system_party_fn= is
  definer and deliberately revoked from PUBLIC, because it takes a tenant as a
  parameter and reads across the tenant boundary. The trigger that needs it was
  the invoker. Making the trigger a definer function leaves the function's
  reach exactly as it was and lets the write land.
- *Do not widen the service roles.* Granting resolve to the services would also
  have made the insert work, and would have handed every service the ability to
  read any tenant's settings. That is the privilege the revoke exists to
  withhold.
- *The test-user grant stays.* It is now redundant for the trigger, which runs
  as its owner, but the two invoker-rights seed functions still call resolve
  directly. Removing it is a separate question about those functions.
- *Sign the bootstrap in as the system party.* A tenant-wide setting carries no
  party, and the table's party-isolation policy admits the row only when the
  resolved party is one the session may see. The trigger fix gets the write as
  far as the policy; it is the party the session is scoped to that lets it land.
  The administrator is therefore signed in as the system party, and offered no
  other: a wizard that let somebody pick a party would offer a choice whose
  wrong answer blocks the step it is there to perform.
- *End the bootstrap at the sign-in screen.* The settings being written are
  tenant-wide, so the person should not be left sitting in the system party once
  the deployment is set up. Both rails sign out as their last act and hand the
  browser the sign-in screen, where the installation's own administrator signs
  in as itself.
- *Hold the rail on the persona, not on the absent tenant.* The old gate held
  the rail whenever the deployment had no tenant of its own and had not recorded
  a finish. That reads the setup flag through a session, and the sign-out the
  rails now perform closes the session first, so the flag read back as unset and
  the rail reopened forever. The gate now holds the rail for a system
  administrator whose finish is not recorded, for a bootstrap still open, and
  for a journey this browser began. A visitor with no session is never held.
- *Leave the welcome screen alone, and offer "no tenant" among the tenants.*
  Keeping the system tenant alone is a choice about which tenant to create, so
  it is offered as the first card of the tenant choice, shaped like every other
  card, and not as a separate control on the welcome screen.

* Out of scope

- Whether =ores_variability_system_settings_set_fn= and
  =ores_variability_system_settings_upsert_fn= should be definer too. They are
  invoker-rights and call resolve directly, and they work only because every
  caller today is itself definer or the DDL owner.
- Splitting the one wizard into two — a system setup run by the super
  administrator and a tenant setup run by the tenant administrator — with the
  authentication boundary as the seam. The bootstrap now completes end to end
  with the steps it has, so the split is its own piece of work.

* Result

Done. Bootstrap's last step is accepted and the browser lands on the sign-in
screen.

Two defects sat under the one reported failure. The first was the refusal:
=ores_variability_system_settings_default_party_fn= was an invoker-rights
trigger calling a function whose EXECUTE is deliberately revoked from PUBLIC, so
a service creating a tenant-wide setting was refused by the function its own
trigger called. It is now =SECURITY DEFINER= with =search_path = public,
pg_temp=, and =resolve_system_party= is still ungranted to both service roles.
The second appeared once the first was fixed: the row then met the table's
party-isolation policy, which admits a tenant-wide setting only when the
resolved party is one the session may see. The bootstrap therefore signs in as
the system party and offers no other, and both rails sign out at the end.

Both were reproduced and then shown absent on a recreated database. The full
run was then driven over HTTP against the running fleet: the administrator was
created, the sign-in answered =mode: system-administration= scoped to =System
Party=, =POST /api/bootstrap/complete= returned ={"success":true}=, the
authenticated status read returned =onboardingComplete: true=, and the
signed-out read returned =isInBootstrapMode: false= so the browser stops at the
sign-in screen rather than the setup rail.
