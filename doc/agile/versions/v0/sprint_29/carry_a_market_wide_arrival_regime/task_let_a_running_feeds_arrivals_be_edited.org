* Result

A running feed's Arrivals tab is editable for a caller who may write the feed,
as its Process tab is. Saving a change to a running feed says the feed runs on
its old law and offers to restart it, ticked by default; the save then stops
and starts the feed. Four defects were found and fixed on the way:

- The feed pages passed =mayWrite && running !== true=, so the fields locked
  whenever the feed ran, and every synthetic feed runs.
- Save used a =btn primary= class the product does not define, so it rendered
  as bare text. It is the product's =Button= now.
- The save never re-read the feed, so the form compared against the stale row:
  after one save a person could not save back to the original value, and a
  second save would have sent the old version (inferred).
- The reason code was read through translation; it is a constant now.

Evidence: the panel tests pass (206 in marketdata/synthetic). The harness, as
the system administrator, opens a running feed's Arrivals tab, changes its
sensitivity, sees the running note with the restart ticked, saves, sees the
restarted feed run on the new value, and saves the old value back: 14 of 14
pass live. The feed the first failing run left at 1.5 was put back to 1.

Found and captured, not fixed here: a tenant administrator is offered edits
to system feeds that the server refuses with a database error
(=a_tenant_is_offered_edits_to_system_feeds=).
