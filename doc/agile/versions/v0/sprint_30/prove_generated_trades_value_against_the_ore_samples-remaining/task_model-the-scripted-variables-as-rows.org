* Plan

The three JSON columns are the shape ORE reads, so the work sits at the two
boundaries and nowhere else: the columns leave the model, the rows arrive, and
each side reads what the other writes.

1. The model. =scripted_instrument= keeps the script's name and body and gains
   =script_npv=, the variable the script's result lands in, which the schema
   requires beside an embedded body. The three JSON columns leave it.
   =scripted_parameter= already holds a variable's name, its declared type, its
   shape and its scalar value, and =scripted_parameter_value= holds a list's
   members.
2. The ORE boundary. The projection reads a =ScriptedTradeData= or a named
   product's element into parameter rows. A product ORE reads through a class of
   its own, =DoubleDigitalOption= and =PerformanceOption_01=, is read member by
   member instead: those elements state no type attribute, so the declared type
   is the kind of leaf the schema gives the member. An Underlying block is an
   =instrument_underlying= row and not a parameter, because it is an entity with
   a type, a name, a weight and a price type.
3. The planner. The synthetic planner states the rows the projection reads, and
   an index variable holds the equity's oresmd address, so the export writes the
   ORE name the address resolves to.
4. The tests. The projection's own round trips, the corpus content round trip
   over every trade of ORE's example portfolios, the planner's population, and
   the report over the provisioned book.

* Notes

- The two basket products needed no special case. =AsianBasketOptionData= and
  =AverageStrikeBasketOptionData= are free style products, which is what
  =is_named_product= tests for, so the named product's path reads them once the
  hand written branches are gone. The corpus content round trip proves it: every
  trade of ORE's example portfolios comes back value for value.
- =DoubleDigitalOption= and =PerformanceOption_01= keep the members their
  element states, not the script variables ORE derives from them
  (=LowerBound1=, =LongShort= and so on). The derivation is not invertible: a
  call and a collar differ only by a bound that is =QL_MAX_REAL=. The members are
  also what the document states, so they are what a round trip can prove.
- A generated =ScriptedTrade= still states =PutCall= as a number, which the
  =AsianBasketOption= library script cannot read: the product wants
  =AsianBasketOptionData= with an event schedule, not the generic form. The
  market data for an equity index is missing as well, so the population's
  scripted trades are the next task rather than this one; what this task proves
  is that the rows carry what the export needs.
