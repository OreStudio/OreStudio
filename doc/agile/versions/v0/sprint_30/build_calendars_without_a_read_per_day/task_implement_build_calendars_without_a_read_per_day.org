* Goal

The calendar materialiser writes a calendar's new days with a new claim for each, so the repository reads no day before the insert, and provisioning builds the calendars inside the step's 600 s.

* Acceptance

- =calendar_materialisation_service::regenerate= passes a claim for each day, so =replace_claim= runs for none.
- A fresh provisioning of Acme completes, with the time of =build_calendars= in the IAM log.
- The calendar materialisation tests pass unchanged.

* Plan

- Measure first. =pg_stat_statements= showed the per-day reads and their transactions. A set-based insert of one calendar, rolled back, gave the floor of the table: 2.66 s through the trigger, 1.03 s with the trigger off, 0.16 s with the exclusion constraint also dropped.
- Change the caller, not the generated repository. The materialiser knows the days are new, and it calls the =write(rows, claims)= overload that the repository already has. The generated per-row read in the other batch writers is a capture.

* Result
