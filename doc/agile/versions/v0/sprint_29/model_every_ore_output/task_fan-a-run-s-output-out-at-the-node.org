* Goal

A run's output reaches the components that store it one file at a time, not one
archive at a time.

The node finishes a run with the engine's output directory on its own disk. It
uploads each output file as its own compressed object, and a manifest that names
them. Reporting fetches the result files, marketdata fetches the market-state
files, and neither downloads or unpacks an archive. The archive stays as the
run's audit blob and is not the path a reader takes.

* Acceptance

- The node uploads one object per output file, under a key that names the result
  and the file, and a manifest that lists them with their families and sizes.
- The output archive is still uploaded, unchanged, as the run's audit blob.
- Reporting's post-processor fetches the result files it models, by name, and
  never unpacks an archive.
- Marketdata fetches the market-state files it models, by name, and never
  unpacks an archive.
- A file a run wrote that no family covers is named in the manifest and logged,
  not silently dropped.
- A run whose files are uploaded individually loads in bulk, and the step's cost
  is proportional to the bytes it reads and not to the size of an archive.

* Plan

A run's output reaches its readers one file at a time. The node already has the
engine's directory on disk, so it uploads each file as its own gzipped object
beside the archive, and a manifest that names them. A reader asks the manifest
which files it models and fetches those, by name.

The shape:

- Keys. =compute/output/{result_id}/{file}.gz= for each file and
  =compute/output/{result_id}/manifest.json.gz= for the manifest. The archive keeps
  its key, =compute/output/{result_id}.tar.gz=, as the run's audit blob.
- Grant. The claim already grants a put on =results_path=, the canonical result
  rows the node no longer writes. That slot becomes the output-file prefix, so
  the token still carries five grants and none of them is dead.
- Manifest. =ores.ore.core= owns it, beside the catalogue that names a file's
  family: the result id, and for each file its name, its family (empty when no
  family covers it), its bytes, its compressed bytes, its digest and its key. The
  key is in the manifest so a reader that is handed one needs no knowledge of the
  compute key layout.
- Fetching. =ores.storage.core= reads one gzipped object back as bytes. Each
  reader reads the manifest, keeps the families it models, and fetches those.
- Readers. Reporting fetches the result families. Marketdata is handed the
  manifest paths, not the archive paths, and fetches the market-state families.
  Both archive-unpacking blocks go.

A file no family covers is named in the manifest with an empty family, and the
node logs it.

The manifest is written last, so a manifest that exists names files that exist.

The order of delivery:

1. The keys and the grant, with the dead results slot removed.
2. The manifest type, its JSON form and a round-trip test.
3. The node writes the files and the manifest.
4. Reporting reads through the manifest; its archive block goes.
5. Marketdata reads through the manifest; its archive block goes.

* Result

The node uploads each file a run wrote as its own gzipped object under
=compute/output/{result_id}/=, and a gzipped manifest that names each file's
family, sizes and digest. Reporting reads the result files through the
manifest, and marketdata reads the market-state files the same way. Neither
unpacks an archive. The run's archive is still uploaded as its audit blob.

Proved end to end on a recreated database with Acme provisioned: Group
Consolidated Exposure (instance =b15ca172=) completed, the node uploaded 15
files and the manifest, reporting stored 38 metrics from 4 result files, and
marketdata stored the run's =todaysmarketcalibration= payload.
