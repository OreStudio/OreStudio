** What the environment would not let us do

=compass build= cannot run in this environment: its =systemd-run --user
--scope= wrapper fails with "Failed to connect to user scope bus". The
same targets build through =cmake --build --preset linux-clang-debug-make=
directly, and that is how V01 and V02 were measured. The two suites that
read the tables need =ORES_TEST_DB_USER= from =.env= and a live database.

The TypeScript side cannot be checked here either. =projects/ores.web= is
installed with npm, and its =node_modules= has neither =zod= nor
=@msgpack/msgpack=, so =tsc --noEmit= reports module-resolution errors for
every file rather than type errors. The eight regenerated =marketdata= .ts
files are therefore recorded as rendered-but-unchecked. The codegen suite
does cover the TypeScript rendering, at 826 passing cases after the rebase.

** One generator defect the rebase exposed

Rebasing onto =main= after the PR was raised picked up 48f4282df6, which made
the generated row-level-security policies idempotent so that re-running
=setup_schema.sql= against a populated database stops aborting on a policy
that already exists. It fixed the domain-entity archetype and missed the
junction one.

The guard was not missing from the tree, only from the generator: 02c78a7dda
had hand-added =drop policy if exists= to the checked-in junction SQL. So the
two disagreed, and regenerating this component -- whose only junction opts
into tenant isolation -- removed the guard and reintroduced the abort. The
fix is in the junction template, with a regression test that renders a
junction with =:rls_tenant_isolation:= and asserts the drop precedes the
create; removing the guard from the template makes it fail. No generated file
changes, which is the point: the checked-in SQL was already right and the
generator now agrees with it.

That same commit also fixed the =reporting= omission this PR's shell commit
originally carried. It found it independently and first, so the finding is
main's, not this PR's; only =marketdata= is added to the shell's parts here.

** Check the database before believing a red suite

=compass db status= opens with the schema version and a drift line, and PR 3
is the argument for reading it first. The restored database was a day behind
this tree. Two suites went red on it, and neither failure was in the code:

- =ores.synthetic.core.tests= failed all eight of its eventing integration
  tests, because the restored schema still held the legacy notify function
  for those tables while the committed SQL was already canonical. A single
  =select prosrc like '%entity_ids%' from pg_proc= settled it in one query.
- =ores.iam.core.tests= failed one case that writes an asset image, because
  the restored =ores_assets_images_tbl= still had =id= where the tree now
  expects =image_id=.

After =compass db recreate -y -k= all eight suites in the affected set are
green. The lesson is written up in
[[id:427D8713-4018-462B-BA4C-2EB65CC780FE][Forty generated notify triggers
still emit the retired entity_ids payload]], because the same confusion in
the other direction -- committed SQL that really is stale -- is a defect, and
the two look identical from a failing test.

** What the corpus says about oresmd

ORE's shape table defines 43 series types. oresmd declares 29 of them, so
14 are unrepresented; measured against the committed corpus at
=external/ore/examples/=, those 14 are 48.8% of the key lines. The larger
problem is the other direction: 9 of the 29 declared types still cannot
express the keys ORE actually writes.

The shape table and the oresmd models contradicted each other, and the
shape table was right. =ores_series_key_shapes_populate.sql= states every
shape correctly -- it was corrected from the corpus -- and the oresmd
models were never brought into line. FRA and IMM_FRA were declared with an
index where ORE writes =ccy/start/length=, so all 2,273 of their corpus
lines projected nothing; MM's index-less form, 94% of its lines, was
rejected for want of an index the producer never wrote. All three now
project and round-trip.

What remains needs the identifier grammar extended rather than a shape
corrected: BASIS_SWAP and the two cross-currency swaps carry two tenors
and sometimes two currencies, ZERO carries a day count, the futures carry
a contract month and an exchange, CORRELATION carries two operands on a
strike surface, and CPR has no currency at all.

Two defects fell out of the same walk, and both are closed. The IR
6-segment path discarded the settlement segment and rebuilt it as a
hardcoded ="2D"=, so the 1,338 corpus keys carrying =0D= would have been
stored as =2D= -- PR 2 added =settle= to =ir_market_data_identifier= and
stopped rewriting it, and the segment now reaches the series qualifier as
the file wrote it. =import_keeps_the_ir_swap_settlement_segment_the_file_carried=
pins that for a =0D= key and for one carrying an explicit settlement date,
which is the other thing the segment can be. The CSV tokeniser needed two
commas, so a line with exactly one aborted its whole file; PR 2 fixed that
too. What is left of the settlement question is the projection's ="2D"=
fallback, for an identifier built from something other than a key, and
there the proposed source -- refdata's per-currency spot days -- is the FX
convention rather than ORE's swap convention; see the analysis.

=projects/ores.codegen/scripts/check_oresmd_ore_coverage.py= makes the
coverage record permanent and rerunnable; =--corpus= adds the line counts.
It also enforces the test requirement: every modelled quote type carries a
projection test and a round-trip test, or a recorded reason. Seven of the
twenty-nine were one-sided when the check was written -- six with no round
trip and one with no projection -- which is how a projection that emits a
key its own inverse cannot read survives a green suite.
