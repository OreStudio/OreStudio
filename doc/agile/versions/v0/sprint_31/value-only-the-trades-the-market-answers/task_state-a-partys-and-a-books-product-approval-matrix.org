* Goal

Two matrices state the products a party may trade and the products one of its books may carry, and a book's set can neither exceed nor escape its party's.

* Acceptance

- A party level matrix names the product types the party may trade.
- A book level matrix names the product types that book may carry, and a write that names a type outside the party's matrix is refused.
- A query answers the types one book may carry, resolved from both matrices.

* Plan

The book's set already exists: =ores_refdata_book_product_types_tbl= with the
=books.restricts_product_types= flag, and the booking path already reads it. The
task therefore adds the party's set and the rule that binds the two, rather than
a matrix from nothing.

1. *The party's set mirrors the book's.* A =party_product_types= junction and a
   =parties.restricts_product_types= flag, both generated from a junction model
   modelled on the book's. The flag carries the distinction the book's carries:
   no rows means every type when it is false and none when it is true. Without
   the flag every existing party would stop being able to book, which is a
   migration rather than a model.
2. *The rule is enforced where the sets meet, not in a caller.* Three triggers
   hold it: a book may not name a type its party does not permit, a party may
   not drop a type one of its books carries, and a party may not start
   restricting while a book carries a type outside the set it would state. A
   caller that skips the service cannot break the rule, and the booking path
   needs no change because the book's set can no longer exceed the party's.
3. *The resolution is SQL, and it does not read the catalogue.* Two functions
   resolve a party's set and a book's set. A null answer means every type the
   catalogue states, and an empty array means none, because the catalogue
   belongs to the trading component and the reference data must not read it.
4. *The codegen carries the stack.* The junction model generates the table, its
   notify trigger, its RLS policy, the C++ domain, repository, service, handler
   and protocol, and the wire protocol. The permission seeds are hand-written,
   as they are for every table.

* Result

The party states the product types it permits, and a book can neither exceed
that set nor escape it.

What exists:

- =ores_refdata_party_product_types_tbl=, generated from
  [[id:84B5E325-ACE1-4B2A-B7CF-032DDD7D1366][ores.refdata.party_product_type]], with its notify trigger, its RLS
  policy, its history and its events. The party row gains
  =restricts_product_types=, on the same two-state rule as the book's.
- The whole C++ stack for the junction, and the wire protocol, which the codegen
  writes from the model: domain, codec, table, generator, repository, service,
  handler, protocol, history provider, and the shell commands and recipes.
- Two resolutions, in =refdata_product_approvals_create.sql=:
  =ores_refdata_party_allowed_product_types_fn= and
  =ores_refdata_book_allowed_product_types_fn=. A null answer means every type
  the catalogue states; an empty array means none; a party or book the caller
  cannot see resolves to none.
- The subset rule in three triggers: a book may not name a type its party does
  not permit, a party may not drop a type a book of the party carries, and a
  party may not start restricting while a book carries a type it would not
  permit.
- The permission seeds, =refdata::party_product_types:{read,write,delete}=, and
  the Trading role's read of the set its books narrow.
- A pgTAP test, =refdata_party_product_types_test.sql=, over the two resolutions
  and all three refusals.

What the change does not do:

- The booking path is unchanged, deliberately: it already reads the book's set,
  and the book's set can no longer exceed the party's, so the refusal reaches it
  without a line of code.
- A book whose party is changed after the book states its set is not
  re-checked; the rule holds on the writes it covers, and moving a book between
  parties is not one of them. The check belongs with whatever writes that move.
- No provision seeds a matrix. A party with the flag false permits everything,
  so nothing existing changes, and a demo that wants a narrow party states one.
- The web screen for either set is not built. The protocol and the shell
  commands exist; the screen belongs to the screens work.
- =refdata_party_functions_create.sql= carries column lists of its own and does
  not name the new flag. Nothing writes a party through those functions, so the
  omission cannot lose the flag, and the functions answer the questions they
  were written for.
