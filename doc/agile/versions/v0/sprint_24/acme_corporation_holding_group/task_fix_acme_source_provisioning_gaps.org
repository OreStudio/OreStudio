* Notes

Discovered while manually walking [[id:CAA32021-D905-468A-BEB4-B76A9432C218][Verify attach logo to counterparty]] against
a freshly --source acme-provisioned tenant. In order found:

1. LEI-imported parties land =status = 'Inactive'= -- the generic
   =provision party= flow activates them, =--source acme= never did.
2. =onboarding.party= was never set true per party -- login re-launches
   the Party Provisioning Wizard even for an Active party.
3. The tenant admin had no =ores_iam_account_parties_tbl= row for any
   Acme party beyond the auto-created System Party -- =accounts
   set-default-party= failed with "User is not a member of requested
   party".
4. No default party was set on the tenant admin account at all --
   login lands on the inactive System Party by default (Barclays'
   =accounts set-default-party "BARCLAYS PLC"= step has no Acme
   equivalent).

=ores_iam_acme_activate_party_fn= (new helper in
=iam_acme_provisioner_create.sql=) addresses 1-3, and a default-party
step addresses 4, using the same select-rowtype/mutate/reinsert idiom
as =ores_refdata_parties_touch_version_fn= (both parties and accounts
are append-only temporal -- a raw UPDATE would bypass versioning).
Landed as a stopgap and verified via direct SQL/shell checks (not a
full Qt login/click-through) -- decided against continuing to chase
further gaps interactively, since every fix here is exactly the
hand-rolled-SQL-duplicating-the-service-layer pattern the
internal-impersonation rework replaces wholesale. Blocking further
work on that task rather than iterating further on SQL patches.
