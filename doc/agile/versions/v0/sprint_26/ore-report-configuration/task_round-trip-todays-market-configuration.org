* Plan

The corpus census in [[file:evidence/todays_market_corpus.md][evidence/todays_market_corpus.md]]
settled the shape before any model was written. It counted 98 files, 24 optional
top-level collections, and 206 =Configuration= blocks across 88 files.

**Four tables, not twenty-four.**

The document has two shapes in it. Twenty-three collections are an ordered list
of entries, each one identifying attribute plus a reference. =Configuration= is
not a list of entries at all: it is a bundle of references into those
collections, keyed by a required =id=. So the two shapes get two tables, and the
twenty-three share the first because they are the same shape.

| Table | One row per | Holds |
|-------+-------------+-------|
| =todays_market_config= | document | name, description |
| =todays_market_configuration= | =Configuration= element | its =id=, and its position |
| =todays_market_configuration_binding= | =*Id= child | which collection, and the referenced name |
| =todays_market_entry= | collection entry | which collection, the key, the target, the position |

**The collection name is a key, not a column.**

Twenty-four collections do not become twenty-four tables, and they do not become
twenty-four nullable columns either. They become one discriminator column whose
vocabulary lives in a seeded lookup, the way =pricing_engine_type= does, so the
set is data rather than schema. The lookup also records the name of the
attribute each collection identifies its entries by, which is what lets
=currency= and =name= stay distinct without the mapper carrying a table of its
own.

**SwapIndexCurves gets a column, not a table.**

It is the only collection whose entry carries a second value, the nested
=Discounting=, and the census measured that nesting as exactly one level deep
and never more. One nullable column on =todays_market_entry= covers it. A table
of its own would trade one nullable column for a table, a join and a second
mapper path, for one collection.

**The entry table carries the key attribute's name, and two collections carry
two keys.**

Reading the entry attributes out of the schema, rather than inferring them from
the corpus, changed the entry table. The key is =name= for nineteen collections,
=currency= for =DiscountingCurves=, =pair= for the two FX collections, and the
literal string =key= for =SwaptionVolatilities= and =CapFloorVolatilities=. So
=entry_key= would hold a different attribute depending on the row and its own
name collides with one of the values it stores. The entry table therefore
carries the attribute name beside the value.

=SwaptionVolatilities= and =CapFloorVolatilities= identify by =key= *and*
=currency= together, so they need a second key column; a row keyed on one
attribute would collapse two distinct entries. Every entry type also declares an
optional =id= that no corpus file writes, which the mapper has to carry so that a
document which does write it is not silently changed.

The full table is in [[file:evidence/todays_market_corpus.md][the census]].

**Order is stored rather than recovered.**

A collection may name the same key twice, and a reference cannot be sorted back
into the order the document wrote. =position= carries it, the same column and
the same reason as =pricing_model_product=.

**What this plan deliberately does not decide.**

Whether =currency= and =name= are one concept under two spellings or two
concepts. Nothing in the corpus distinguishes them, so the mapper stores the key
as written and the lookup records which attribute a collection uses. If they
turn out to be the same thing, that becomes a merge; if they do not, nothing was
lost.

* Notes

**The description this task was scaffolded with named four things the schema
does not have.** It claimed the document carries "the calendar, the sensitivity
and report currency settings, and the ibor fallback and pricing engine binds".
=todaysmarket.xsd= contains no occurrence of =ibor=, =pricing=, =calendar= or
=sensitivit= at all:

#+begin_src sh
grep -c -i "ibor\|pricing\|calendar\|sensitivit" external/ore/xsd/todaysmarket.xsd
# → 0
#+end_src

Those four belong to the *run* document — =ore.xml= carries the Setup block with
the calendar, the currency and the sensitivity settings, and it binds the market
and pricing engine configurations by name. Today's market is what those bindings
point at. The description is corrected. This is the second scaffolded
configuration description to name constructs from a neighbouring document, so it
is worth reading the schema rather than the description before costing the unit.
