* Goal

A change event names the record that changed, on every entity in the system. The bus, the broker, the BFF and the browser carry the key. A list still goes stale once for a bulk change, and a record page goes stale only when its own record changed. The protocol, the pipeline and the screen documents state the rule.

* Acceptance

- Every generated entity event carries the key of the row that changed, and the protocol states where.
- The BFF tells a browser the keys of a change, up to a stated limit, and omits them for a bulk change.
- A record page goes stale only when its own record is among the keys, or the keys are omitted. A list behaves as before.
- The drift gate and the conformance checks pass for every component.
- The NATS entity protocol, the eventing pipeline, the Change notification page and the entity screen specification describe the rule.

* Decisions

Found in the live test of [[id:4DE7AFB9-A06A-4844-8B11-C26A05B334E8][Keep the record screens up to date]]:

- Diane changed her job title. Hazel was on her own page, and her Refresh button pulsed. Her record had not changed. The event says that the =accounts= entity changed, with a time, and names no record. The parent story chose a time and not a list, so that a bulk import makes a screen stale once.
- That choice is right for a list and wrong for a record page. A pulse for a change that is not the person's own teaches them to ignore the pulse.

What the code holds today:

- The database notification already carries =key=, the key of the row as a JSON object.
- The typed event, such as =account_event=, carries =event_id=, =action=, =version=, =occurred_at= and =correlation_id=. It does not carry the key. The key is dropped between the notification and the typed event.
- The BFF passes =component=, =entity= and =at= to the browser.

What this story proposes:

- The key travels in the payload of the typed event. The tenant and the party travel in headers because the subscriber filters on them. The key is data about the entity, and a subscriber reads it after it has decided to listen.
- The BFF passes up to a small number of keys on each message. A change with more keys than the limit omits them, which means /many/. A list ignores the keys.
- A record page declares the record it shows. It goes stale when its record is among the keys, or when the keys are omitted.

Open decisions for the product owner:

- The limit on keys in one message. The proposal is 20.
- Whether the key is the model's declared key (a username for an account) or the storage key (an id). A screen holds the declared key, so the proposal is the declared key.

* Out of scope

- A dependent screen (a book showing a country name). The Change notification page states why.
- The reporting line and role grants have no event of their own. They are in the parent story.
