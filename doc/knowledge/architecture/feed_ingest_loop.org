#+title: The ingest loop and the one pipeline
#+description: The one path every tick takes from an adapter to the stored quote series and the party stream, and how the loop keeps the newest value when the store is slow.

* Summary

The ingest loop is the one path every tick takes. An adapter publishes a tick
with a vendor id. The loop maps the id to an internal item, checks the value,
writes one observation for each party routed to the source, and delivers the
tick on each party stream. The path is the same for every adapter and every
asset class. The loop never asks whether the source is live or simulated.

The stages, in order:

1. *Receive.* One wildcard subscription covers all adapter ingress subjects.
   A new adapter needs no subscription change. See [[id:97208391-AE4B-4032-9744-8F8B228FD567][The adapter subjects]].
2. *Map.* The loop reads the tick's provider, id scheme, external id and field
   and finds the internal item. See [[id:BAE0F052-CCA6-43FB-A139-03518CE2D929][The mapping belongs to the provider and not to the source]]. A tick with no mapping is
   dropped with the reason =unmapped=, and the loop logs it once for each id.
3. *Check quality.* See [[id:98E49FCD-10E4-4DCE-9099-E728359B6D60][Quality checks run between mapping and storage and ignore the source kind]].
4. *Resolve the parties.* The loop finds every party routed to the tick's
   source for that provider. See [[id:37B27CA8-9F44-4A61-9B02-3EAABD8C3818][A party routes to exactly one source for each provider]].
5. *Store.* One observation for each party in the series
   (item, provider, party). See [[id:E4736D88-03B2-4A40-B7F4-01B06B9B9FD7][A quote series is keyed by item, provider and party]].
6. *Compose.* A composite item that uses this series is recomputed. See
   [[id:41D84AD1-0058-4135-9B9D-BDE08BE8169A][A composite attributes its use to the providers of its inputs]].
7. *Deliver and meter.* The loop delivers the tick on each party stream and
   counts the delivery for each party. See [[id:3E51B0BD-D22B-4790-821F-E2FED44D152C][Usage is recorded as events and priced later]].

** How the loop keeps the newest value

- The subscription decodes a tick and puts it in a bounded queue. A full queue
  drops its oldest tick, because an old tick that waits while a newer one
  arrives is worse than a lost tick.
- A worker thread takes every tick that has arrived and handles them as one
  batch. The worker sizes the next batch from the speed of the last one,
  between 50 and 20,000 ticks.
- A batch writes the rows of one tenant in one transaction, because
  row-level security checks the tenant of the connection. The loop keeps the
  last row of each key in a batch. A batch that fails is split in two until
  the failing row is alone, and the loop logs that row and goes on.
- The worker drops a tick older than 5 seconds and counts the drop.
- The loop delivers a tick after the commit of its batch, with no wait for an
  acknowledgement. A store that is down does not stop delivery: the loop
  delivers the ticks it cannot store, and it waits one second, then doubles the
  wait to thirty seconds, before it tries the store again.
- A shutdown stops the subscription, works through the queue for two seconds,
  and logs how many ticks it dropped.
- The loop keeps the id of each series after one read. The cache clears when
  routing changes and when a row for a series fails to store.

** What the loop reads

The loop caches the mapping and the routes. The service refreshes the cache
when a mapping or a route changes, from the change events of those entities.
The observation table sends no change notification, because a tick changes
many times each second and the party stream carries each value.

** The one place an if remains

After a successful store, the loop offers an FX spot datum to the CRM bridge
under the condition =datum.type() == fx_spot=. A third asset class that feeds
CRM needs an edit at that line. It is the one place where an =if= stands in for
a registered hook.
