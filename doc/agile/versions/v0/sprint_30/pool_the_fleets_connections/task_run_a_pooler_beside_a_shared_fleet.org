* Goal

A host that shares its PostgreSQL between environments runs a pooler in
transaction mode beside the fleet, its ports in the environment's =.env=, and the
services reach PostgreSQL through it. The server sees the pooler's cap rather than
the sum of every service's pool, and an idle environment closes the connections it
is not using.

* Acceptance

- The pooler is a unit of each environment, generated with the fleet's units,
  part of =ores-<env>.target=, and started before every service unit.
- Its configuration lives under =build/config/= with the rest, and states the
  transaction mode, the prepared-statement support the statement task decided,
  =default_pool_size=, =max_db_connections=, =max_client_conn= and an idle
  server timeout, so the server's budget is one number a reader can find.
- The pooler authenticates each client with that client's own password, against
  a credential file generated from the environment's =.env=, so no user is
  written by hand and no environment's credentials are readable by another.
- The pooler's port is derived from the environment's base port and stated in
  its =.env=; =base_port + 7= is the free offset (0 and 1 are the gateway, 2 the
  web, 4 the site, 5 and 6 NATS and its monitor).
- The services' connection options name the pooler's port; the listener's and the
  administrative paths' name PostgreSQL's, and both are stated in the
  environment's =.env=.
- A full build, ctest and fleet start are green, Acme provisioning completes, and
  the journal has no ERROR or FATAL line.
- =pg_stat_activity= shows the fleet's connections arriving from the pooler, and
  the count of them settling to the cap and to nothing when the fleet is idle.
- The measured before and after are recorded on the task: connections per
  environment, idle and at peak.
- An environment without the pooler still starts, so the direct path is not
  broken by this change.

* Plan

The unit follows the shape =systemd_generate.py= already emits for NATS
(=_nats_unit= and its template, lines around 397-442): a =Type=simple= unit, a
port check in the start path, an =ExecStart= built from the checkout, and
=After=/=Wants= wiring so the services are ordered behind it. The difference is
that the services' units already start after NATS, so the pooler joins that same
ordering.

Where the binary comes from for a development host: the host package
(=apt install pgbouncer=), pinned by version in the unit's documentation, because
this host runs services as systemd units rather than containers - the container
is pauli's task. The version floor is whatever the statement task decided.

** What the configuration must state

Measured on this host (Debian forky/sid, pgbouncer 1.26.1), the installed default
file sets only the paths, the listen address and =auth_type = md5=; every other
value is the built-in default. =pool_mode= is wrong for us, =max_db_connections=
caps nothing, and =max_client_conn= is below what one fleet asks for, so the
generated file states them rather than inheriting:

| Setting | Built-in default | What the generated file states |
|---------+------------------+--------------------------------|
| =pool_mode= | =session= | =transaction= |
| =max_prepared_statements= | 200 | left alone: 200 is already right |
| =max_db_connections= | 0, unlimited | the environment's server budget |
| =max_client_conn= | 100 | above the fleet's worst case |
| =default_pool_size= | 20 | the per-database share of the same budget |
| =server_idle_timeout= | 600 | the idle period the environment states |

The credential file is the part that has to be generated rather than written.
=pgbouncer= refuses a client in two ways that both read as a password failure:
=auth_type = md5= with an empty userlist, and =auth_type = any=, which this
version refuses outright with "auth_type=any requires forced user" unless every
database entry pins a =user=. Neither works when every service logs in as
itself, so the file states:

#+begin_example
[databases]
* = host=<db host> port=<db port>

[pgbouncer]
listen_addr = 127.0.0.1
listen_port = <base_port + 7>
auth_type = plain
auth_file = <checkout>/build/config/pgbouncer-<label>.users
pool_mode = transaction
max_client_conn = <the fleet's worst case>
max_db_connections = <this environment's budget>
#+end_example

=plain= sends the password across loopback in clear, which is what =psql= already
does on this host. A pooler reached over a network states =scram-sha-256= and a
file of verifiers instead. The wildcard entry is what keeps the file free of
per-database lines: a client that asks for =ores_dev_<env>= is sent to
=ores_dev_<env>=, with its own credentials.

** The block: one endpoint per context

The acceptance asks for the services to name the pooler's port and the listener
to name PostgreSQL's. The code cannot do that yet.
=postgres_listener_service= connects with =ctx_.connection_options()=, and a
context holds one endpoint. Point a service at a pooler and its =LISTEN= goes
with it, where transaction pooling hands the session to somebody else at the
next commit.

So the first change is a second endpoint on the context - the listener's - which
defaults to the service's own so that nothing moves unless an environment states
it. It is two settings, =db-listener-host= and =db-listener-port=
(=ORES_<APP>_DB_LISTENER_HOST/PORT=), read the way the database ones are, and
they reach =postgres_listener_service= through the context rather than through a
new parameter on every call site.

The order is therefore: the second endpoint and its test; then the generated
configuration and the unit; then the fleet run that measures
=pg_stat_activity= before and after. Writing the unit first would produce a
configuration that breaks the listener the moment an environment adopts it.

** Why not the host's own daemon

The package installs a system-wide unit on 6432 that reads
=/etc/pgbouncer/pgbouncer.ini=. It cannot serve the fleet: its config is
root-only, it defines no databases, its userlist is empty, it runs in session
mode, and it caps nothing. One daemon for every environment also puts every
environment's credentials in one file. This task disables it
(=systemctl disable --now pgbouncer=) and runs one pooler per environment as a
user unit, from a config the environment generates.

Verification is deliberately about the server: the connection count from
=pg_stat_activity= grouped by =datname= and =client_addr=, before and after, idle
and during a provisioning run.

* Notes

** Measured before this task started, 2026-11-21

Taken while answering whether a pooler was needed at all, on
=ores_dev_merry_newton= with pgbouncer 1.26.1 installed from sid.

- The server carries 199 connections of =max_connections = 1500=, across eight
  development databases, of which 187 are idle. The heaviest environment,
  =ores_dev_prime_origin=, holds 105 because its =.env= states four connections a
  service rather than two. Nothing is short of connections today.
- The elastic pool moves the per-environment worst case from about 42 to about
  155, and leaves the idle case at about 34. Eight environments bursting at once
  would reach about 1240 of the 1500.
- A named prepared statement prepared by one client and executed by two later
  clients through a transaction-mode pooler returned the right value, with
  =max_prepared_statements= left at its default. The repositories' pattern works
  behind a modern pooler with no setting of its own.
- Debian's =pgbouncer= versions: bullseye 1.15, bookworm 1.18, trixie 1.24.1,
  forky and sid 1.26.1. There is no bookworm backport, so a Debian 12 host
  cannot meet the statement floor from the archive.

** What went wrong with the host daemon, 2026-11-21

Worth keeping because the error messages mislead. The system unit started, and
every client failed with "password authentication failed" - not because the
password was wrong, but because =auth_type = md5= with an empty =userlist.txt=
refuses everybody. Switching to =any= moved the failure to "bouncer config
error", which the log explains as "auth_type=any requires forced user". Neither
message names the real cause. A pooler configured per environment does not reach
either state, because its credential file is generated from the same =.env= the
services read.
