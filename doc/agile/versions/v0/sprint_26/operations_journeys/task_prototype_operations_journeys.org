* Notes

*The prototype moved the design.* The walk over the clickable screens settled
the points the journeys had left open. The services screen became a roster: one
row per expected instance under its service, kept whether the instance reports
or not, with instance counts, the installation's own state words, and version
skew made prominent. The compute wrappers left the services roster for the
grid, because a wrapper runs on a node and belongs with the node. The grid
itself became the installation's, not the tenant's. And the database
fingerprint stopped being a read of its own: the login answer carries the row,
so the versions panel adds no request. Each journey records its part of this in
its =* Prototype= section.

*The walk found the data-model linkages.* Five captures in the product
backlog's inbox record what the accepted design needs from the models:
[[id:A1D7FC12-4105-41F7-8885-CCE07120034C][The service heartbeat carries no host]]
would place each wrapper on its node;
[[id:B7AE6C4F-5597-419D-A396-AD64D871C900][The login answer does not carry the database]]
would feed the versions panel;
[[id:B7B53CD1-4A11-403E-8844-13177864F0E7][The services roster has no read]]
would serve the expected roster and the states beyond running;
[[id:3621E2BC-2670-4E59-8721-32F86B640F24][The grid read is scoped to the session tenant]]
records the filter that the grid's ownership removes; and
[[id:8C1D6E61-3661-49F2-90BB-00ED7C4F113C][The node summary drops the failure fields]]
would stop a node that fails everything from reading as idle. The permission
gap that every journey records is already captured tree-wide, so it is linked
rather than filed again:
[[id:CCB1D9D1-B5F8-43D5-B5E5-A6A3A5BDC9E7][Nothing gates a hand-written operation handler]].

*The branch is the record.* =prototype/operations-journeys= holds the clickable
prototype and is never merged; this branch carries the documents the walk
accepted. The decisions above were made against the prototype, so the two stay
together: each journey names the branch, its route and this task, and the
branch stays on the repository as the evidence. Nothing in the prototype is
production code.

* Result

Accepted by the user on 2026-10-04. Snapshot: branch
=prototype/operations-journeys=; the routes are =/prototype/services=,
=/prototype/grid=, =/prototype/bus=, =/prototype/logs= and =/prototype/versions=,
behind an index at =/prototype=.

- *Services*: a roster, one row per expected instance under its service, kept
  whether the instance reports or not; instance counts, the installation's own
  state words, and prominent version skew.
- *Grid*: one row per node, with the compute wrappers in their own panel
  beside it, showing which wrapper reports and which is missing.
- *Bus*: the server's vitals and one row per stream; running totals kept apart
  from current numbers, and a time range with an inclusive start.
- *Logs*: a filter bar that combines filters, emission time told apart from
  receipt time, and a result count over the page.
- *Versions*: the client, the server and the database panels; the database row
  rides the login answer, and the panel states it as unknown until the answer
  carries it.
- *Frame*: Operations is an area, not tabs — one screen per journey with
  "Back to operations" navigation, and the footer with both builds on every
  screen.

The design record is on =main=: each journey carries a =* Prototype= section
naming the branch, the route and this task, the wireframes follow the accepted
design, and the data-model linkages sit as captures in the product backlog's
inbox. The prototype branch itself never merges.
