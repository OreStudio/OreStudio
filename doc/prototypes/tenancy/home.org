* Summary

The first screens built from the [[id:E6E32AB5-2F25-4230-AB93-E38E75DE23B6][Application shell prototype]] spoke the
implementation's language. The home page counted and listed *journeys*, and a
system administrator reading a tenant was asked to *enter* it and *leave* it.
Neither word is one a person uses about their work.

This prototype redraws the home screen and the tenant screens in the person's
own words. The areas hold screens and buttons named for what a person does.
Home shows the state of the work. A tenant opens like any other record, and the
session that reads it is held for the screen and never offered as a step.

It is throwaway. It is not production code, it reads no service, and every value
on it is mock data.

Open the [[file:home/][home screen]].

* Detail

** The verdict

Accepted on 2026-10-04. It replaces the shell prototype's landing page and its
journey cards; the shell's menu across the header, the mode read from the
sign-in and the person's own screens under their name stand as they were.

** What changed from the shell prototype

| Shell prototype | This prototype | Why |
|-----------------+----------------+-----|
| The landing page lists every area's journeys as cards | Home shows the state of the work, with the next actions as buttons | A person opens Home to see whether anything needs them, not to read a catalogue |
| A journey is a card a person chooses | No screen says *journey*; screens and buttons are named for the action | *Journey* is how the screens are designed, not a word a person uses |
| System administration's area holds three journey cards | *Tenants* is one list, with *Add tenant* and *Remove tenant* as buttons on it | Adding and removing are actions on the list, not places to go |
| Reading a tenant's data means entering it and leaving it | Opening a tenant shows its overview, parties and people in place | The tenant session is how the read is done, not something the person asked for |

** System administration

- *Home* opens with a *System health* card: the tenants in service, on
  evaluation and setting up, a plain verdict (a green tick and *Everything is
  running*, or an amber mark and how many tenants need attention), and the
  recent activity. *Needs attention* lists the failed setups and suspended
  tenants, each with a button to it. A short tenant list follows, with a way to
  the full one.
- *Tenants* is the roster: search, type and status filters, *Show test
  tenants*, paging. *Add tenant* and *Remove tenant* sit on the list; a row is
  selected to remove it and clicked to open it.
- *A tenant* opens with tabs for its overview, its parties and its people. A
  quiet *View only* label is the one trace of the session underneath, and says
  that the tenant's own administrators make the changes. A failed setup offers
  *Try again*.
- *Remove tenant* says what removal does before it happens and asks for the
  tenant's code to confirm.
- *Add tenant* is one form: the organisation, what to start from, and its
  administrator.

** Tenant administration and the party user

The tenant administrator's home leads with the same kind of verdict in its own
terms (a locked account), live figures for sign-ins, and tiles for *Parties*,
*People* and *Tenant settings*. The party user's home says plainly which areas
are not in this release, and keeps them so people know they are coming.

** Colour carries the state

Status badges are filled: green is in service, blue is production, purple is
evaluation, amber needs a look, and red has failed. The idea came from a design
Gemini suggested for the same screen, with the system health card and the
recent activity beside it. Two of that design's row actions were left out on
purpose: *Act As*, because it offers the tenant session as a step, which is the
thing this prototype removes; and *Edit*, because a tenant's own administrator
maintains its details.

** What is real and what is not

The colours and type are the web app's own tokens, so the prototype is judged on
its words and its structure. The screens, the people, the tenants and the
activity are mock.

Two things the prototype draws have no server behind them yet:

- *Remove tenant.* Its wording (everyone signed out, no more sign-ins, the data
  out of use, no undo) is the design's assumption. The server has no removal.
  Since built: the server refuses sign-in at once, and people already signed
  in lose access within one access lifetime rather than at once, so the
  dialog says that instead.
- *Recent activity.* The provisioning runs can tell a tenant's setup story, but
  no read gathers the deployment's activity in one place.

** Where the code lives

=doc/prototypes/tenancy/home/index.html=: one file, plain HTML, CSS and JavaScript, no
framework and no build step. The site build copies the directory through
=ores-deploy-web-app=, beside the other prototypes.
