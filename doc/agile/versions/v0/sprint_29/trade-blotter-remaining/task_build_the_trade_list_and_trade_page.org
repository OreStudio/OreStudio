* Plan

The list ships in the first PR and the page in the second.

- *The list reads =trading.v1.trade_summaries.list=.* The read model already carries the filter record the prototype asks for: =search=, =trade_date_from=, =trade_date_to=, =status=, =book_id=, =counterparty_id=, =instrument_type=, the =_one_of= sets, and the order and page.
- *A portfolio tree sits beside the list, and it holds books.* A portfolio nests under a portfolio and a book hangs from exactly one portfolio, so the tree draws both: the briefcase for a portfolio and the book for a book, the two icons the icon guidelines already name. A choice names books: one book is an equals member, =book_id=, and the books under a portfolio are a one-of member, =book_id_one_of=. The read model already carries =book_id=, so the filter needs no new column. The tree itself still needs the hierarchy read, which is what the capture investigates: no column, but not no read.
- *The trade's other portfolios are out of scope here.* =ores_trading_trade_portfolios_tbl= records the portfolios a trade is reported in beside the book it is filed in. The tree follows the book, which is the trade's filing position. A list that must also answer for the reported portfolios needs a portfolio set on the summary, and that is a later decision.
- *The tree cannot be drawn from the reads that exist.* The junction investigation is answered in the capture. =refdata.v1.portfolios.list= has no party member and no tree read, so a party's hierarchy is only reachable by walking every page, which the list standard forbids. Books can be asked for by =parent_portfolio_id_one_of=. Both reads scope to the party by erasing other parties' rows after paging, so the page and the total disagree. Per-node counts would be one call each. The tree therefore waits on a read of its own, and the list ships without it. The answers are in [[id:247B37A7-15AF-4C24-80D1-8BC4CD45DBF1][Read the portfolio tree's junctions from the server]], and the shape the doctrine gives the tree is in [[id:87771BE6-D4BF-40C2-B5DB-179A9696837D][Investigation: The shape of the portfolio tree read]]: the two existing lists zipped by the BFF for as long as a party's tree fits a page, then a node read model of its own.
- *The Id column shows an identifier, never the uuid.* The summary's =id= is a uuid, which is unreadable in a list. The trade's identifiers are =ores_trading.trade_identifier= rows typed =Internal=, =UTI=, =USI= or =ORE=, and no type is marked primary. The display rule for the first PR is the first that exists, in that order, so a real trade shows its internal reference and a UTI only when nothing better exists. That rule is a decision to confirm, and it belongs beside the enrichment the BFF already does.
- *Four columns are enriched in the BFF over the page's rows*, because the read model holds ids and not names: the counterparty and book names, the version pair from =trade=, and the display identifier above. Fifteen rows a page makes that cheap.
- *A composite instrument is not a structure.* =ores_trading.composite_instrument= with =composite_leg= is an instrument of one trade; =ores_trading.structure= with =structure_member= is a deal of several trades. The list states which a row is: =composite · N constituent trades= on a composite trade, =structure= or =package= on a deal, and =leg of STR-0007= on a trade a deal holds. The read model's =row_kind= already separates a trade row from a structure row, so only the composite and the leg markers need an enrichment read.
- *No notional column.* Notional is a property of the instrument and not of a trade: =bond_instrument=, =fra_instrument= and the equity option instruments carry one, =vanilla_swap_instrument= carries none because each leg states its own. The prototype drew one and is corrected; see =* What the list does not show= on [[id:1D348CB0-B7BD-4AA8-B61A-34A17AC3BA20][the trade page prototype]].
- *A structure is filtered by its own columns in the first PR.* The prototype asks that a structure match a filter when one of its trades does. The view does the opposite on purpose, because a structure row carries no book, state or date. The refinement waits for a decision; the first PR follows the view.
- *Authorisation is not drawn*, as the prototypes index records. The read model carries =authorisation_status= and the list ignores it.
- *A structure row opens the structure screen.* The list draws the deal's identifier as a link to =/trades/structures/:id=, which [[id:339F0405-43AE-4049-B6B3-EB12E5A38CA4][Menu structure]] already states, and the =leg of STR-0007= chip of a leg opens the same screen. A trade's own identifier still opens the trade page, so a leg is never taken away from its trade. The destination is [[id:3D378FE8-743B-4057-859D-961369D90845][Build the structure page]], so the link goes live when that task lands; this PR must not draw a link to a route that answers nothing.
- *The permission of each tab of the trade page.* A tab is drawn by the read it needs, and a tab whose read is refused is not drawn, because a control the person may not use is not drawn. Details and Instrument read =trading::trades=, Identifiers read =trading::trade_identifiers=, Links read =trading::trade_links=, and History reads =trading::trade_activities=. All four codes are seeded.
- *The links a lifecycle event writes.* Exercise writes an =Exercise= link from the exercised trade to the resulting trade, and a partial termination writes =CloseOut= from the original to the closing one. Novation writes =Novation=, a roll writes =Roll=, and a cancel and rebook writes =MisbookingCorrection=. Expire, Cancel, Unexpire and Uncancel write no link, because nothing new is recorded, and Execute writes none because the same trade goes live.

* Result

Two rounds have landed. The first settled the prototype: the list draws a portfolio tree that holds parties, portfolios and the books under them, states on every row whether it is a trade or a structure, and shows an identifier rather than the internal uuid. It also corrected two model errors, settled the two open items of the prototype audit, answered the tree's six junction questions and recorded the shape the doctrine gives the tree, with a measurement of a party's tree.

The second round shipped the list itself. The Trades area reads a page of the trade summary read model through the BFF, which enriches the page with the identifier, the book and counterparty names and the two versions. The screen is the shared record list, so the pager, the column menu, the search, the filters and the states are the standard ones, and the area is offered from the menu and the home folders with messages in the three catalogues.

What is not in it, and why: the portfolio tree waits on a count-per-book read of its own, and the investigation says the two existing lists are enough until a party's tree passes a page; the composite and leg markers wait on the same reads; the type and counterparty filters wait on a catalogue read and a pick list; the trade page is the next task, so a row does not open yet and a structure row states its kind rather than linking to a route that answers nothing. Book a trade is the area's Add once that screen exists.
