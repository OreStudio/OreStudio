ORE's date type spells an unset date as the empty string, and the corpus
uses both spellings: 414 empty FirstDate/LastDate elements corpus-wide and
278 omissions. Both spell the same statement, so the gate compares content
and treats an empty element as no content; the boolean pairing runs first,
because an empty element is also how ORE spells a true boolean.

=== corrections this run made ===
1. The union is deduplicated by trade id AND folded to one statement per
   security, and the folded union is what is imported. Importing the
   documents the union was folded from leaves whichever copy the import
   saw last while the comparison holds another.
2. A date is compared as a date. Basic (20160203) and extended
   (2016-02-03) ISO spellings are the same day.
3. A value is read as a date only when it spells a real calendar date. The
   earlier rule accepted any eight-digit string, so a bond leg's notional
   10000000 canonicalised to a date while the exporter's 10000000.000000
   stayed a number, and one value read as both a loss and an excess. The
   reading before this fix was in-scope lost 408, unexplained 63; before
   the fold and the date fixes, lost 1745, unexplained 1293.
4. Nested bondData is folded too. A forward bond states its bond inside
   ForwardBondData, and the first fold only reached a trade's direct
   BondData child, leaving every forward bond's issue restated.

=== the KnockOutSwap, which never exported (D23) ===
The corpus's one KnockOutSwap trade was saved and then dropped from the
export, because its instrument never reached the database:
  warn: Instrument save failed ... new row for relation
  "ores_trading_scripted_instruments_tbl" violates check constraint
  "ores_trading_scripted_instruments_tbl_trade_type_code_check"
  [KnockOutSwap_example]
The import sent the type to scripted_instrument, whose closed trade-type
check does not name it. swap_leg names the knock-out swap among the nine
rates families whose legs it holds, and knock_out_swap_instrument holds the
barrier as typed columns, so the type is routed to the swap family instead.
The row now lands and the trade exports:
  trade_type_code KnockOutSwap  start 2024-05-02  maturity 2029-05-02
  barrier_start_date 2027-05-03  barrier_level 0.0500000000  UpAndOut
The export states the trade, its envelope, BarrierData/Type, the level and
BarrierStartDate, and no LegData: the import writes no swaps legs for any of
the nine rates families, which is recorded as defect 18 and is what makes
the exported document schema-invalid for that one trade.
