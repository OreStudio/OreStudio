#+description: Nothing regenerates a component class diagram, so the diagrams drift silently and ores.dq.api still draws the protocol it retired.

The class diagram at projects/<component>/<part>/modeling/<part>.puml is not produced by codegen. resolve_targets(address="ores.plantuml") returns 0 units for a component model, so the drift check renders nothing for that address and cannot see the file; and the generate_<name>_diagram cmake target only runs PlantUML over the existing .puml to refresh the PNG, it does not rewrite the .puml text. A repo-wide search finds no writer: compass.py only carries a skeleton template for a new diagram, and the ER diagram template is the only mustache in the plantuml facet. The automated half was authored once, by hand or by an LLM pass, and frozen.

The consequence is measurable. ores.dq.api.puml draws 209 class boxes, among them save_catalog_request, save_catalog_response, delete_catalog_request and get_catalogs_request with a data/success/message shape. None of those types exists: the current protocol declares list_catalogs_request, get_catalog_request, put_* and remove_*. H01 calls a diagram that predates the code it draws a finding, and this one predates the whole protocol migration.

The stale names are not only in the diagram. 38 entity models carry a * Protocol block whose property values still name the retired types -- :save_request_class: dq::messaging::save_catalog_request and its sibling keys -- against 9 that name the current put_* form. That is M09s legacy fragment: the property names are historical in the template too, which now renders put_{{slug}}_request under the old key, but the values in those 38 models were never refreshed. They span ores.dq, ores.assets, ores.reporting, ores.synthetic and ores.codegen, so the fix is cross-cutting rather than one component.

Found while starting the ores.dq clean-standard H01 pass; recorded on that task with the measurement.
