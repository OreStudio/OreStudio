* Goal

The change stream carries what the stores announce. One subscription hears every entity event, each message becomes the coarsest change that is true of it (this collection moved for this tenant), and the pump has something to drain on every tick.

* Acceptance

- One subscription hears every entity event, whatever its component or collection.
- A received event records one change naming the tenant, the party when the event has one, and the collection.
- An event that names no tenant records nothing, because no reader could be shown it.
- The coalescer and the frame name the collection rather than a row key, because a key is the entity's own record and no two entities share one.
- The feed runs beside the ticker in the server and stops when the server drains.
- A unit test proves each mapping without a broker, and the live stream test proves an event arrives as a frame.

* Plan

The first real producer of a change decides the shape of a change, so the
shape changes here rather than being carried into the feed.

- A subject names a collection and an action; it never names a row. The row
  key is the entity's own record, encoded by that entity's codec, so one
  subscription cannot decode the key of every entity. The change therefore
  names the component and the collection and nothing finer, and the
  coalescer drops the identifier it was scaffolded with. A client that
  hears a frame refetches the collection it draws; naming a row was an
  optimisation that no producer can supply.
- Parsing runs from the end of the subject, because the delivered subject
  carries the deployment prefix: action, collection, version, component.
  The collection token drops its =_events= suffix, so it is the same name
  the route path uses.
- The tenancy travels in the =X-Tenant-Id= and =X-Party-Id= headers, which
  the publisher sets. A message without a tenant is dropped: no reader
  could be shown it.
- =change_feed= takes an =ores::nats::message= and records it, so a case
  builds a message and asserts the frame that a drain produces, with no
  broker in the test.
- The server subscribes through the same registrar that already returns the
  subscriptions the service runner keeps alive, and runs the ticker from the
  runner's start hook. Both ends now exist, so the stream is no longer empty.
- The pattern is =*.v1.>=. A NATS wildcard is a whole token, so the
  collection's =_events= suffix cannot be matched in the subscription and is
  filtered in the parse instead.

* Notes

*The live proof found what the cases could not.* The check is: sign a browser in,
open =/api/v1/changes=, write something, read a frame. Three things blocked it in
turn, and each was a real defect rather than a test gap.

*First, nobody could sign in.* Signing in answered =Authentication is not
configured= although the log showed =Fetched JWKS public key from IAM= at startup:
the door was built with =server.verifier()= before the runner installed the
verifier. Fixed by [[id:692E58A3-E3E1-4C4F-B399-328C5827DD3E][Let the door reach the verifier]].

#+begin_src text
$ curl -s -X POST http://127.0.0.1:21601/api/v1/auth/sessions \
    -H 'Content-Type: application/json' \
    -d '{"principal":"tenant_admin@acme_corporation","password":"…"}'
{"error":"Authentication is not configured"}
#+end_src

*Second, the pattern heard nothing.* With the door fixed, the stream opened and
delivered no frame at all, and the pump logged nothing, so nothing arrived from the
broker. The subscription was =*.v1.*_events.>=: a NATS wildcard is a whole token,
so =*_events= is a literal, and the server accepts the subscription and delivers
nothing to it. The pattern is now =*.v1.>= with the collection filtered in the
parse, and a case walks the pattern token by token so the spelling cannot regress
quietly. Captured as
[[id:6AA25394-9066-42C6-ADAE-FDAD2E78E45F][An events collection cannot be wildcarded]].

*Third, main had lost the work twice over.* The build could not link because
=ores.iam.core= called =ores::synthetic::service::routed_code_count=, which did
not exist; main was fixed while I waited. Then the merged increments turned out to
be gone from main entirely: merging #4293 deleted 174 files, including
=change_feed=, the collection-shaped change and the door's verifier. Captured as
[[id:560D4814-B8AB-4136-A9C8-48B87FC3488B][A merge took an old tree over two merged increments]],
and restored by =hotfix/restore-the-feed-and-the-door=.

*What the frames prove.* A session opened as =tenant_admin@acme_corporation=, then
a second sign-in. One stream carried three components' stores without the client
asking anything: =iam.login_info= and =iam.sessions= from the sign-in, and
=marketdata.delivery_counts= from the feed path. Every frame named its tenant and
its component, and the party was empty for the tenant-wide ones.

What is still not proven: nothing in this task. The unit cases cover the mapping
and the frame, and the deployment covers the composition.

* Result

The stream now has a producer. =change_feed= turns one NATS message into one
change: the subject gives the component, the collection and the action, read
from the right so that the deployment's prefix does not matter, and the headers
give the tenant and the party. A message with no tenant records nothing.

The first real producer also decided what a change is. A change names the
collection and not the row, so =change_event= and =coalesced_frame= lost their
identifier, the coalescer keeps a set of dirty collections instead of a map to
identifiers, and a frame reads:

#+begin_src text
event: iam.tenant_types
data: {"tenant":"acme","party":"ops","component":"iam","entity":"tenant_types"}
#+end_src

The server subscribes once, in the same registrar that already returns the handles
the runner keeps alive, and runs the ticker from the runner's start hook, so the
hub is no longer empty. The window is 150 ms, the constant the design states.

The pattern the subscription uses is =*.v1.>=, not =*.v1.*_events.>=. A NATS
wildcard is a whole token, so the second spelling is a literal that matches
nothing; the server accepts it and delivers nothing, and the stream stayed silent
with no error to read. The live run below is what found it, after the unit cases
had passed the parser and the frames a hundred times. The feed rejects what is not
an event in the parse instead, and the design states the cost of that.

Proven on a running deployment, once the session door could sign a browser in and
the pattern could match: a signed-in caller opens =/api/v1/changes=, signs in a
second time, and reads

#+begin_src text
event: iam.login_info

#+end_src

followed by the keep-alive comment. Three components' stores reached one open
stream without the client asking for anything.
