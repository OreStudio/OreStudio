Two operations act on settings without being entity verbs, so they live in the
component's reserved =ops= namespace rather than in the resource grammar
[[id:C650CBC9-FDED-4C68-981F-7902E296928E][NATS entity protocol specification]] § "Domain operations" defines for
entities.

=clear_bootstrap_mode= ends a tenant's bootstrap window. It is not a write of
one setting: it clears =system.bootstrap_mode= and sets =onboarding.tenant=,
and it must succeed for the tenant that is activating whether or not the
activating account holds the permission an ordinary setting write needs.

=complete_party_onboarding= marks one party's onboarding complete. The party it
names is the party being onboarded, not the caller's own, so it cannot be an
ordinary write: a write record's party comes from the authenticated context,
and the two are different parties here. The tenant is still derived from the
validated token, so the operation can only ever affect a party inside the
caller's own tenant.

=get_setting= reads one setting by the name it is known by. The entity's own
read is addressed by identifier, which no caller outside this component holds,
and a setting is always spoken of by name. It is the read a component makes of
the installation's configuration -- how often a sweep runs, how long a token
lives -- so it is deliberately narrow: one name in, one value out, and no way
to list or write anything.

A component that needs a setting reads it over the wire rather than reaching
into this component's tables. The alternative would put one component's schema
in another's query, and the point of a service boundary is that it does not
matter which.

* Physical space

The shell commands are switched off. Two of these messages change platform
state rather than read or write a row: one clears bootstrap mode once the first
administrator exists, and the other completes a party's onboarding. The shell
renders the =system_setting= entity's unit, and nothing in the shell sends
these three.
