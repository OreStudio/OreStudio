This page defines the [[id:68FAC606-569C-4B9B-932B-3B3A0181AC8B][service architecture pattern]]
Queue-Based Load Leveling in the [[id:EA249899-6611-407F-A43A-B37019EBD1A7][pattern language]].
A queue sits between the work that arrives and the service that does it, so a
peak waits instead of overloading the service. In ORE Studio report runs over
their quota wait as =queued=, and compute holds assignments in JetStream.

* Also known as

- /Load levelling/.

* Context

Work arrives in bursts: thousands of reports fire at the same minute. The service
that does the work has a fixed capacity.

* Problem

How does a service survive a burst of work larger than its capacity?

* Forces

- Capacity sized for the peak is idle most of the day.
- Refusing the burst loses work.
- A person must be able to see work that waits.
- Waiting work must not be lost on a restart.

* Solution

Put a durable queue between the source and the service. The source adds work at
any rate; the service takes it at its own rate. The queue is visible, so a person
sees what waits, and durable, so a restart loses nothing.

* Failure handling

#+ATTR_HTML: :class hug-leading
| Concern | What the pattern does |
|---------+-----------------------|
| Errors | A failed item leaves the queue with its error; it does not block the items behind it. |
| Timeouts | Time spent waiting counts against nothing until the item starts. |
| Retries | An item taken but not finished returns to the queue. |
| Idempotency | An item may be taken twice; see [[id:26AE458C-5E23-423B-BEBE-1B55D83A7AA5][Idempotent Receiver]]. |
| Observability | Queue length and wait time are measured, per tenant. |

* Pitfalls

- *A queue nobody can see.* Work waits with no state a person can read.
- *A queue that only grows.* Capacity below the average rate is not levelling; the backlog never clears.
- *Plain arrival order across tenants.* One tenant's burst delays everyone; see [[id:6E7979E9-8065-49D1-97AF-27375013A795][Fair Share]].

* Security

No security consequence beyond availability.

* Resulting context

- Benefits :: Bursts become waits, and the service runs at a steady rate.
- Liabilities :: Latency during bursts, and a queue to watch.
