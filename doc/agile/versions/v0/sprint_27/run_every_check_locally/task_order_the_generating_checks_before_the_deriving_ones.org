* Result

A check can name what it must follow, and each phase is ordered by that
declaration. component-drift now runs before tangle-shell, tangle-http,
site-page, component-docs, cmake-sources, recipe-inventories and
physical-inventory -- every check that derives from generated output.

The sort is deliberately conservative. It takes one ready check at a time in
catalogue order, so only a check that declares a dependency moves, and it moves
no further forward than the first check that names it. Nothing else is
reshuffled.

The tests pin the property that matters: component-drift precedes every check
that names it, only the generator moves, an unknown dependency raises, and a
cycle raises.

Verified: pytest projects/ores.codegen/tests/test_local_checks.py passes 31, and
the next run's prepare phase opens with component-drift.

The run that verified it also surfaced a trunk defect worth its own task. The
gate aborts at the first model that fails validation:
ores.dq.risk_report_config.org is missing the subcomponent flag and states no
primary key, and component-drift stops there, so components after dq are never
regenerated in that run. A single bad model turns the tree-wide gate into a
partial one, and the failure reads as drift rather than as a broken model.
