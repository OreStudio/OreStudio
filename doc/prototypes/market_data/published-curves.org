* Summary

The published-curve screens, as one plain page with three surfaces: the list of
published curves, the delta of one curve against a chosen as-of, and the
approvals queue with the subject of a =marketdata.curve_publish= request in its
row.

It argues three things. A published set is a row a person reads, with the act
that published it, and a candidate is a set nobody has approved. A delta marks
each point as changed, added, dropped or unchanged, and it says in words when
nothing changed. The queue row needs the subject beside the existing kinds, and
it needs more space than the one line it holds today.

It is throwaway. It reads no service, it holds no session, and every value on
it is mock data. It exists because three journeys settle what a publish *does*
and nothing yet settles what a person *sees* while reading or deciding one.

* Detail

** The question

The journeys name three gaps, and each one meets the screen before it meets the
server:

1. No read lists the tenant's published curves. A reader finds the set in use
   for one series, and never the tenant's sets together.
2. No read returns a point-by-point difference against the published set. The
   decider reads a published as-of and compares by eye.
3. The queue row carries a generic view. It holds the account and the roles a
   role request names and a trade subject for a trading authorisation, and
   nothing that names a curve, a party and an as-of.

The screen set answers the first two, and the third is a change to a surface
that already exists: the Requests queue at =/requests=.

** The surfaces

Switch with the bottom bar, or with =?surface=list=, =?surface=delta= or
=?surface=queue=. The default is =list=.

| Surface | Query | What it draws |
|---------+-------+---------------|
| List | =?surface=list= | The tenant's published curves, the filters, the states and the pager. |
| Record page | =?surface=list&curve=USD-SOFR-3M&party=ACME+London= | One published set, with Details, Published points and History tabs. |
| Delta | =?surface=delta&curve=USD-SOFR-3M&party=ACME+London&asof=2026-10-06T16:00:00Z= | The candidate set point by point against the published set at the chosen as-of. |
| Queue | =?surface=queue= | The Requests queue, the person's own requests, and the subject of a curve publish in its row. |
| Request page | =?surface=queue&open=r1= | One request a decider opens: its subject, the delta, the checks, the rule, the decisions and the answer. |

The prototype adds one screen to the approvals surface: a published curve keeps
a list and a record page, and the queue is the existing Requests screen with
one column changed. It does not add a second approvals screen.

** The list

The list follows [[id:2BF7F03F-6BF4-45FF-8E26-4D3B4E2D943D][Record screen
standard]]: the breadcrumb, the plural as the title, one sentence, a search and
a filter, the table, and the pager.

| Column | What it holds |
|--------+---------------|
| Curve | The curve configuration code, monospace, and the first column |
| Party | The party the published set belongs to. The same code in two parties is two curves |
| Published as-of | The instant the set was built at, exact, because it is the subject |
| Publisher | The account that applied the approval |
| Published | The published instant, relative, with the exact value on hover |
| Points | How many pillars the set holds, right-aligned |
| State | Published, or Candidate |

A row opens the record page. Two filters sit beside the search: a party select,
and a *Show candidates* toggle. A candidate row is drawn under the published
sets, with no publisher and no published instant, so a set nobody approved
cannot be read as one pricing uses. The search, the order and the pager are
client-side in the prototype; the target is the list contract's own filter and
order.

*RS-LIST-21* gives the list its states, and the prototype draws each one:

- No records. "There are no published curves yet." It says a curve becomes a
  published set when a person publishes an approved candidate, it names the
  bootstrap and the request, and it offers to open the delta.
- Nothing matches. "No published curves match the search." and a way to clear
  it.
- First load. "Loading…" in the body of the table.
- Error. The words of the server and Retry, and never a modal box.

The published set is read-only. The publish record is written by the gate that
applies an approved request and never by a screen, so the list draws no Add, no
Edit and no Delete, and the record page says so in one line. This is the
read-only exception (*RS-EXCEPT-01*), and the journey names it.

The record page carries the display field as its title, the party and the as-of
in the lead line, and three tabs: Details, Published points and History. The
Details tab names the subject, the publisher and the authorising request, and
it ends with the last-changed line. The Published points tab lists the pillars
with the value the set holds for each. The History tab states the raise, the
approval and the publish as one timeline.

** The delta

The delta takes its baseline from the publish record: the as-of the published
set was built at, the publisher and the authorising request. A select chooses
another as-of, so a person compares against an earlier set. The candidate is the
set the bootstrap built, and it states that nobody has approved it.

The table names one row for each pillar, and each row reads one of four ways:

| Mark | How the row reads |
|------+-------------------|
| Changed | The published value stands struck through, the candidate value stands beside it, and the change is stated in basis points with its sign |
| Added | The published cell is a muted dash, the candidate value stands beside it, and the mark says Added; the change cell says new pillar |
| Dropped | The published value stands, the candidate cell is a muted dash, and the mark says Dropped |
| Unchanged | The change cell is a muted dash and the row is muted; unchanged rows are hidden until *Show unchanged points* is pressed, and the count of hidden rows is stated |

A dropped point is drawn because a comparison that hides a removal is not a
comparison. The model has no place for it yet: an observation carries no
=valid_to=, so the screen cannot say when the published point stopped applying.
The prototype draws the removal and leaves the record open.

The summary above the table counts the four marks, and the page states when it
hides rows. When nothing changed, the delta says so in one notice: *No point
changed. The candidate matches the published set at this as-of point for point.
There is nothing to raise, and the published set stays the one in use.* The
table then holds one line: every point here is unchanged.

When the curve has no published set, the delta says there is nothing to compare
against and not that the sets agree. A candidate against an empty set is not a
delta, and the screen sends the person to the queue.

** The queue

The queue is the Requests screen that exists today, with one column changed. It
keeps its layout: the person's own requests above the queue, the search and the
kind filter, the table, and the answered tail below. The table keeps its four
columns, Who, Asked for, Why and Waiting, because that is the shape a decider
already reads.

The *Asked for* column is where the change sits. Today it holds one line of
text: the roles a role request names, or the kind's name. A curve publish needs
a badge, the curve, the party and the as-of, so the column takes 42% of the
table and two lines for that kind, and the role and counterparty rows keep one
line. The badge carries the kind, and the code stands beside it in monospace so
a reader can name the kind: =marketdata.curve_publish= appears beside
=iam.role_grant= and =refdata.counterparty_change= in one table.

A decider opens the request by the row, on a click and on Enter. The request
page then reads in the order the existing screen reads: the subject, the reason,
the delta, the checks, the rule, the decisions so far, and the answer last. The
answer offers Approve, Refuse and Hold, a comment that is required on a refusal,
and a note that the decision is recorded under the decider's name. A hold states
that the request stays in the queue and that the asker is told. The page marks
each check *unknown* and explains that no operation runs the checks yet, so a
decider reads unknown as not checked and never as passed.

The prototype lets the reviewer look as three people, because the queue is
scoped by the decide permission: a tenant administrator who holds every decide
permission and sees every kind, the head of market risk who sees only curve
publishes, and an operations person who sees only reference data. The permission
rule is the point: the market-data kind joins the queue because the row read
learns the kind's subject, and not because the table holds every kind.

** Driving it

The bottom bar switches the surface and its state, and the query string carries
the difference between the state and the default, so any pair can be linked. A
row of the list opens the record page, and a tab is written to =?tab=. A row of
the queue opens the request. The search, the filters, the sorts, the pager and
the as-of select all write the query string. The answer panel refuses a refusal
with no comment under the field. The *Hide gaps* button turns the server-gap
notes off, so a reviewer can read the design without them.

** What is fake

Everything on the page is mock data: the five published sets, the three
candidates, the twelve pillars and their values, the two parties, the six
requests, the decisions, the kind's rules and the checks are hard-coded
literals. There is no server, no session and no build step. A decision writes a
sentence into the panel and nothing else; reload and the page is as it was.

The reviewer should know three assumptions. The tenant administrator holds every
decide permission, so one table can show the kinds together; the Acme
demonstration lets that account read the whole queue, and it does not let it
decide a market-risk request. The published as-ofs are mock instants, and the
current time of the mock tenant is 07 October 2026, 09:00 UTC. The kind's
deciding group is drawn from the permission the kind names, because the model
names a permission and not a group.

** Where the code lives

The prototype is =doc/prototypes/market_data/published-curves/=. The directory
holds one file, =index.html=, with its CSS and its JavaScript inline: no
framework, no =prototype.css=, no =prototype.js=, and no build step. The site
build copies the directory as it stands and adds nothing to it.

The product screens would live here:

| Surface | Where |
|---------+-------|
| The list and the record page | A new =PublishedCurvesPage= and =PublishedCurvePage= under =projects/ores.web/packages/web/src/marketdata/=, with a route at =/market-data/published-curves= in =AppRoutes.tsx= and a path in =shell/paths.ts= |
| The delta | A panel under =web/src/marketdata/=, reached from the record page and from the request page, and drawing the kind's change lines |
| The queue and the request page | =web/src/inbox/RequestsPage.tsx= and =RequestPage.tsx=, which exist; the kind's descriptor in =web/src/inbox/kinds.tsx= gains its subject line |
| The queue read | =projects/ores.web/packages/bff/src/inbox.ts= and =wire-protocol/src/inbox.ts=, whose request view carries the subject |
| The delta read | =wire-protocol/src/request-changes.ts=, whose =RequestChange= holds one line per subject with each field's before and after, and =bff/src/curves.ts= |
| The published-curves list | A read over the publish records in the marketdata component's =ores.marketdata.operations=, served by =bff/src/curves.ts= |

The model already holds most of it. =ores.marketdata.curve_publish= is the
subject, keyed by the request, and its index =curve_publishes_series_published=
orders the publish records the list reads. The change shape exists too: one line
names its operation, its subject and each field's before and after, and a curve
pivot answers it with one line for each pillar, =put= when the point stands and
=delete= when the candidate drops it. So the delta is a rendering question for
the point table, and not a second record.

Two reads are missing, and the note names them where the screen draws them: a
list over the publish records, and =marketdata.v1.curve_candidates.diff=. One
operation is missing for the checks, =marketdata.v1.curve_bootstrap.validate=.

** The verdict

Open. It is offered for sign-off with the four model decisions the journeys now
state: the withdrawal or supersession rule, the zero-approval path, the publish
notice, and the maker and checker pair on the kind.

The design to sign off is: the list and its record page as drawn, the delta with
its four marks and its words for nothing changed, the subject in the *Asked for*
column with the space it needs, and the request page in the order the existing
screen reads.

** What it does not settle

The list's filter. The prototype filters by party and by published or candidate.
Whether the work needs a filter by publisher or by age is open, because no
tenant has yet held enough published sets to ask.

The withdrawal in the list. A withdrawn set has no marker and no state on the
publish record, so the list draws published and candidate and nothing else. The
withdrawal decision in [[id:B05A31CC-FA22-4534-848E-601A30822992][Withdraw or
replace a published curve]] decides what the row reads afterwards.

The dropped point. The delta draws a point the candidate drops, and the model
cannot say when the published point stopped applying. The supersession decision
owns that answer.

The request page's story. The product has a request story screen. This prototype
does not draw it, and it does not decide whether the published curve's history
links into it.
