* Goal

The roster answers over the bus with the two facts the coverage screen cannot
read today: the level each bundle publishes at, and how many rows each member
has staged. Without them a person can see which bundles exist and cannot tell
where they write or whether there is anything to publish.

* Acceptance

- =ores_dq_bundles_list_fn= returns the level each bundle publishes at, so the
  roster groups by level without a second read.
- The roster states how many rows each member has staged, taken from the
  member's own artefact table, without a call per dataset from the client.
- One operation on the DQ bus answers the roster, with the level and the counts
  in one reply, and its own roundtrip and handler tests.

* Plan

1. Extend =ores_dq_bundles_list_fn= with =level=, read from
   =ores_dq_dataset_bundles_tbl=, and =ores_dq_bundle_datasets_list_fn= with
   =staged_count=, counted from the member's artefact table by dynamic SQL.
2. Declare the operation as a codegen operation model beside
   =ores.dq.publish_bundle=: a request naming the bundle and a response carrying
   the bundle, its level and each member with its artefact type, target subject,
   staged count and publishability.
3. Serve it from a hand-written handler beside the publish handler, registered
   on its own subject.
4. Test the SQL directly, the protocol with a roundtrip, and the handler with
   the level and counts it returns.

The staged count is the part to settle first: counting each member's artefact
table costs one scan per dataset, and the coverage screen would ask for it on
every row of the roster. The design note already flagged this as the open
question for the build.

* Result

Done. One operation answers the roster, and the coverage screen can draw the
two facts it was dashing.

- =ores_dq_bundles_list_fn= returns the level each bundle publishes at.
- =ores_dq_bundle_datasets_list_fn= returns the artefact table and the staged
  count for each member, counted from that table for that dataset.
- =ores.dq.bundle_roster= declares the operation: a request naming a bundle or
  none, and a reply carrying every bundle with its level and dataset count and,
  for the bundle named, its members with their counts.
- A request naming no bundle answers the roster alone, because the counts cost
  one count per member. The model says so, and the handler holds to it.
- The handler asks for =dq::datasets:read= and refuses a caller holding only the
  write with an error reply rather than a roster that claims to have failed.

Four handler cases and the generated roundtrip cover it: every bundle named
with its level, the members in the bundle's own order with the counts the SQL
returns, a bundle that does not exist answering no members, and the refusal.
The DQ api and core suites pass, 134 core cases among them.

Two things the data said and the model did not are in the Notes: the artefact
table name carries no product prefix, and a type may name a family of tables
that the count sums.

What this does not do is draw the counts: =api/dq.ts= has no roster read and the
coverage screen still dashes the staged column. That is tracked as its own task
so the screen change lands with a read behind it.

* Notes

- *Two things the data said that the model did not.* The artefact type names its
  table without the product prefix every create script adds, so the count has to
  name =ores_||artefact_table= or the relation is not found. And an artefact type
  may name a family of tables, comma separated, as the scripts do with eight of
  them; a row is staged if it sits in any of them, so the count sums the family.
  Both were found by running the function, not by reading the model.
- *The count is exact and scoped to the bundle named*, as agreed on 2026-11-25:
  one count per member of that bundle, never for the whole roster. The world
  bundle answers in 42 ms with 512186 rows in one of its members, which is the
  cost the design note worried about and it is affordable at this scope.
