* Goal

The tests run through pgbouncer, the way the fleet does. Since PR #4962 and
PR #4969 the pooler is on by default: =ORES_DB_POOLER_ENABLED= is 1, each
service's database port in =.env= is the pooler's port (base + 7), and CMake
gives the test suites every =.env= variable. A developer who runs the local
gate or =compass test run= with the default =.env= gets a green run, and a red
run names a real defect.

** What was observed

On 2026-11-21, in clever_dijkstra, with the pooler on, the local gate's ctest
step had 16 failures. With the pooler off, the same tree passed 47 of 48 checks.
An experiment found three causes, none of them in transaction pooling:

1. Nothing runs the pooler while ctest runs. The gate's =db= step runs
   =compass services stop=. The pooler unit =ores-pooler-<env>.service= is
   =PartOf= the fleet target, so it stops too, and only the
   =step-consumers= check starts the fleet again, at the end. The as-service
   suites (refdata, inbox, workflow) then connect to a closed port.
2. The 13 =config_parser_tests= read the real environment. Each one asserts
   the default database port 5432 inside a fake environment that holds
   nothing, but the parser reads =ORES_<SVC>_SERVICE_DB_PORT= from the
   process: boost's =parse_environment= ignores the fake provider. These
   tests open no connection. They passed before only because the direct
   port equals the default.
3. The =pgtap= check runs beside =ctest=. Both run after =db= on the same
   database. =iam_tenant_purge_test= deadlocks in the gate and passes each
   time it runs alone.

With NATS and the pooler started by hand, =ores.refdata.core.tests= (199 s),
=ores.inbox.core.tests= (21 s) and =ores.workflow.core.tests= (24 s) all
passed. pgbouncer's log showed 26 logins for them: 12 as refdata_service, 10
as inbox_service and 4 as workflow_service. So the tests work through the
pooler. The gate and the tests around them do not.

* Acceptance

- With the default =.env= (pooler on), =compass check= on a code change passes
  every ctest suite and the pgtap check, with no step started by hand.
- =compass test run= refuses to start when the pooler is on and not
  listening, and names the command that starts it.
- Each config parser test passes with the pooler's port in =.env=, and no
  test lists variables to strip.
- The pgtap check and the ctest check never run at the same time.

* Decisions

- The tests go through the pooler when it is on, as the fleet does. The cases
  that cannot be pooled are already tagged =[direct]= in
  =ores.database.tests= and use =ORES_TEST_DB_PORT=, which stays direct.
- A test does not strip variables to get a clean parse. The parser reads
  only the provider, so the fake environment a test sets is the whole
  environment.
- The environment states one database endpoint and derives it from the
  topology: =ORES_<SVC>_DB_PORT= is the pooler's port when a pooler is
  declared, and PostgreSQL's port otherwise. Only the code that renders the
  pooler unit reads the pooler keys. A machine that runs no pooler says so at
  configure time with =compass env configure --no-pooler=, which is what every
  CI job does.
