#+title: ores.trading.blotter
#+description: Codegen operation model for the blotter's two reads: one page of rows, keyed by the sort key and the row id, and one rail of counts per node.
#+type: ores.codegen.operation
#+component: trading
#+subcomponent: api
#+entity_singular: blotter
#+namespace: ores::trading::messaging
#+brief: The blotter's page and rail, read as the two questions the screen asks.
#+filetags: :model:operation:trading:
#+created: 2026-11-01
#+updated: 2026-11-01

The blotter asks two questions, and they are different questions. *Which rows
do I show?* is one page of rows, and *how many rows are at each node?* is the
rail. A single read answers both today and pays for the whole book to do it, so
at ten thousand trades the screen takes a minute and the store is asked for the
same views fifty times over.

These operations separate them. Neither takes a list of ids drawn from a
previous read: the filter is stated here, the page is keyed by the sort key and
the row id, and the counts are grouped by the store.

The TypeScript facet is off while the screen is served by the BFF. It turns on
when ores.http serves these reads, and the filter it names is the summary
protocol's own type, which that facet does not yet project.

The handler stays hand-written beside this model, because an operation model
generates no service handler. The store behind it is the summary view today and
a projection later, and this contract does not move when that changes.
