This page defines the [[id:68FAC606-569C-4B9B-932B-3B3A0181AC8B][service architecture pattern]]
Process Manager in the [[id:EA249899-6611-407F-A43A-B37019EBD1A7][pattern language]].
One component holds the state of a multi-step process and decides each next
step from the results so far. In ORE Studio that component is the workflow
engine, =ores.workflow=.

* Also known as

- /Orchestrator/.
- /Workflow engine/.

* Context

A process has several steps in different services, it outlives one request, and
it must survive a restart.

* Problem

Where does the state of a process that spans services live, and who decides
what runs next?

* Forces

- Steps that call each other couple every service to the order.
- The process must resume after a restart.
- A later step needs an earlier step's result.
- A person must be able to see where a run is.

* Solution

A process manager owns the run. It builds the step list from the run's request
and a registered definition, persists each step before it dispatches it, sends
the step's command, and waits for one completion event. It records the outcome
and dispatches the next step, built from the request and the earlier results,
addressed by step name. Steps never call each other.

* Failure handling

#+ATTR_HTML: :class hug-leading
| Concern | What the pattern does |
|---------+-----------------------|
| Errors | A failed step follows the definition's policy; see [[id:E8DAA8F6-9A41-44A7-A79C-58F7FDB5ADB2][Saga]]. |
| Timeouts | Every step states a deadline; see [[id:1C419534-33BC-423E-8503-9D3945AF8648][Timeout]]. |
| Retries | A restart re-dispatches every step left in progress, under its own identity. |
| Idempotency | Dispatch is at least once, so every step must converge on repeat. |
| Observability | The run and its steps are readable at any time, and every transition publishes an event. |

* Pitfalls

- *A step list that changes between dispatches.* The list must be a pure function of the stored request, or a recovered run changes shape.
- *A handler that calls the next step.* The order then lives in two places.
- *An unknown workflow type accepted.* The start must fail when the chain cannot be built, or a mistyped run looks like a success.

* Security

The manager dispatches with the step headers and no caller token; a step that
must act as a tenant uses [[id:C79B5E4D-71D0-44C2-9D06-444EA2AC1CB7][Scheduled Work Acting as a Tenant]].

* Resulting context

- Benefits :: One place holds the order and the state; steps stay single-purpose.
- Liabilities :: The manager is on the path of every run, and its availability matters.
