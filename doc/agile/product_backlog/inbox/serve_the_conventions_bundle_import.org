** Technical description

The rule: a model that declares a =:subject:= with a =:response:= states a
request, and a request that no registrar subscribes leaves its caller waiting
until the request times out. The bus answers =No responders are available= and
the caller reports a timeout, which is what the user sees.

The path: =projects/ores.refdata/modeling/ores.refdata.bundle_import_operations.org=
declares =refdata.v1.ops.begin_bundle_import=, =refdata.v1.ops.stage_bundle_family=
and =refdata.v1.ops.commit_bundle_import=, each with its response type. The
service that would answer them exists at
=projects/ores.refdata/core/src/service/bundle_import_operations_service.cpp=
and is exercised by =projects/ores.refdata/core/tests/bundle_import_commit_tests.cpp=,
which calls the class directly. Nothing registers the class: grep for
=bundle_import_operations_service= across the tree returns its own header,
its own source and that test, and no registrar. =refdata.core/messaging/bundle_import_registrar.cpp=
subscribes the generated entity verbs (=list=, =get=, =get_many=, =put=, …) and
not the three operations. The caller is
=projects/ores.ore/service/src/messaging/run_configuration_operations.cpp=, which
sends =begin_bundle_import_request= and then =commit_bundle_import_request= for
the run's conventions file.

The observation, from the gate check on the running fleet (the transcript
sits beside the task that added the check, at
=doc/agile/versions/v0/sprint_31/publish_every_kind_of_derived_market_object_through_one_lifecycle/evidence/subject_coverage.txt=):

#+begin_example
$ python3 build/scripts/check_subject_coverage.py

  in projects/ores.refdata/modeling/ores.refdata.bundle_import_operations.org,
  and nothing subscribes it.
FAIL refdata.v1.ops.stage_bundle_family: …
FAIL refdata.v1.ops.commit_bundle_import: …

The live failure was observed on 2026-11-02: =ore import-run= on a directory
with a conventions file fails with
=conventions.xml: Exception calling refdata.v1.ops.begin_bundle_import: NATS request timed out=.

** Disposition

*Hand it back.* The fix touches refdata's behaviour on the wire — a registrar,
a session, a permission — which is outside a gate check's blast radius, and the
environment that introduced it cannot be named from the record, so there is no
owner to hand it to by name. It goes to the refdata component, and this capture
is where it waits.

What the fix is: a registrar in =ores.refdata.core= that subscribes the three
subjects to =bundle_import_operations_service=, with the same session and
permission handling its sibling registrars use, and a NATS-level test that asks
the three subjects over the bus rather than calling the class. The gate check
stops excusing them the moment they answer — =subject_coverage_exceptions.json=
fails on an exception whose subject answers — so the fix and its removal from
that file are one change.

* Why

The subjects were declared, generated, codec'd and called, and the only
component that could answer them was never wired. Nothing detected it because
the unit tests call the service class directly and the recipe that exercises the
import path was last run before the bundle import existed. The gate check that
found it, =build/scripts/check_subject_coverage.py=, is the durable form of this
capture's observation.
