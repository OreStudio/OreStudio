This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A member sees the roles they hold and the permissions those roles carry.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want to see what I am allowed to do, and where it comes from." The member
reads the roles on their account and the permissions those roles carry. The
journey is done when the member can name every role they hold, and answer "may
I do this?" for any action the system offers.

* Actor and trigger

The member: an account of type =user=, signed in, reading their own record. The
trigger is a refusal — a screen answers "permission denied" — or curiosity from
the account menu. It starts when the member opens *My access*, and ends when
they close it. Nothing is written, so the journey keeps no server-side state.

This is the read half of the access topic. An administrator changes the same
records for somebody else — see
[[id:3C753578-BC0E-433C-92B5-38031F050ADC][Change someone's access]].

* Steps

1. *Open my access.* The member chooses *My access*. The system reads the roles
   assigned to the caller's account and lists them with their descriptions.
2. *Read the roles.* Each row shows the role name and what the role is for. The
   member's identity in the header comes from the session established at
   sign-in, not from a second read.
3. *Read the permissions.* The system reads the effective permissions of the
   account and lists the codes. Each code follows =component::resource:action=,
   so the member reads the component and the action from the code alone.
4. *Follow a permission back.* The member picks a permission and asks which role
   grants it. The system reads the permissions of the held roles and answers.
5. *Leave.* The member closes the screen. No change has been made.

* Screens and wireframes

One screen, read-only. Three panels: the caller's identity, the roles they
hold, and the permissions those roles carry. The member thinks of the three as
one answer to one question, so they are panels of one screen rather than
separate screens.

* Entities composed

#+ATTR_HTML: :class hug-leading
| Entity | What it contributes | Model |
|--------+---------------------+-------|
| =account= | The signed-in identity in the header: username and full name | [[id:81D4D50F-A8D4-47F8-9500-89F6AC460469][ores.iam.account]] |
| =role= | The roles the account holds: name and description | [[id:6C0F5B1A-9A3E-4D2C-8B7E-2F4A1C6D9E30][ores.iam.role]] |
| =permission= | The atomic codes the roles bundle: code and description | [[id:76B113F4-410A-4DE5-9757-A4E263B7B8E7][ores.iam.permission]] |
| =account_role= | The junction row that links the account to each role | no entity model — junction table |
| =role_permission= | The junction row that links each role to its permissions | no entity model — junction table |

The two junctions have no entity model of their own: they are many-to-many
links, and the joined shape is a query result rather than an entity. There is
also no module entity and no module table. The component segment of the code —
=iam= in =iam::accounts:read= — is what plays the part a module would play.

No credential field appears on this screen. =password_hash=, =password_salt=,
=service_password_hash=, =totp_secret= and cleartext passwords stay on the
server, and no read in this journey returns them.

* Operations and messages

#+ATTR_HTML: :class hug-leading
| Step | Operation | Subject | Status |
|------+-----------+---------+--------|
| Open my access | Read the roles I hold, with the permissions each grants and its assignment record | =iam.v1.roles.mine= | exists |
| Follow a permission back | Read the permissions one role bundles | =iam.v1.roles.permissions= | exists |
| Another account's access, which this journey does not ask for | Read the same shape for an account the caller names | =iam.v1.roles.by-account= | exists |

The reads are defined in
[[id:C47A4410-8624-431C-98FE-D05304CEC6D8][ores.iam.authorization_messages]], and
[[id:804C7048-DBBF-4B39-8737-BFB4949884C4][Authorised reads]] states the rule
they follow. =iam.v1.roles.mine= takes no account id, so it cannot name anybody
else: the account is the authenticated caller's, and the read needs no
permission beyond a session. The privileged read still takes an id and now
requires =iam::roles:read= before it looks the account up.

* What is missing

Nothing. All three gaps this journey recorded have closed, and the build that
closed them is recorded on
[[id:D5A29471-B0E3-4C69-B7CE-3477752C8ED7][Implement the access journeys in ores.web]].

=iam.v1.roles.mine= answers one composed shape: each role the caller holds, the
permission codes that role grants, and the =account_role= junction's own record
of who granted it, when and why. So the three gaps close together rather than in
turn. The read attributes a permission to the role it arrives through, which the
flat list could not; it carries the assignment tail, which no subject returned;
and it is scoped to the caller by construction rather than by a comparison that
has to be right.

A refusal is worth stating separately, because it is what the composed read
needed before it could be honest. =iam.v1.roles.permissions-by-account=
answered a flat list and nothing else, so an empty list meant both "you may
read nothing" and "this account holds nothing". The read that replaced it
carries a =result=, and a caller who may not have what it asked for is told
=denied= with the permission that was required. An account that holds no roles
answers =ok= with no rows, which is a different answer.
