* Goal

A new entity reaches the database with no hand-edited aggregate. Codegen owns
the list of a component's entity files; people own only the hand-written files
and the prose around them.

* Acceptance

- Codegen emits, per component, a create fragment listing each entity table then its notify trigger, and a drop fragment listing each notify trigger drop then its table drop.
- Each component's hand-written create and drop aggregate includes its fragment once, and no longer lists a generated entity file itself.
- A database recreate succeeds, and the set of tables, functions, triggers and policies it builds is identical to the set before the change.
- Adding an entity to a component needs no aggregate edit, and the drift check fails when a fragment is stale.

* Notes

From the [[file:evidence/hand_written_sql_census.md][hand-written SQL census]] in [[id:B9FE1B6D-08B1-4B06-BD76-5CDD12123568][Find why so much SQL is hand-written and generate what codegen can]].

Order inside a component does not depend on soft foreign keys: 88 tables are
already created before the parent their insert trigger checks, and every
recreate succeeds. What does need order: a table before its notify trigger, the
trigger drop before the table drop, functions from earlier components (the root
=create.sql= already orders those), and hand-written files that name a table
when they are created (SQL-language functions, views, =alter= scripts), which
must come after the fragment.

First check, before changing any aggregate: recreate a scratch database with one
component's aggregate reordered to the planned shape, and compare its catalogue
with the current one.
