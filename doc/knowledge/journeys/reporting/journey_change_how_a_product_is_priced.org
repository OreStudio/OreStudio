This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A market-risk owner changes the model, engine or parameters of one product in a pricing engine configuration, reads which reports the change reaches before it is saved, and may keep the change to one report by making a copy.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"The desk says my Bermudan swaption price is off, so I want to price it another
way, and I want to know what else that moves." The person owns one report. The
report binds a configuration, and the configuration is shared. A change to a
product row is a change to every report that binds it. The journey is done when
the product is priced the way the person meant, and the person has read which
reports the change reached, what it did not reach, and has either made the change
for all of them or for one.

* Actor and trigger

A market-risk owner or a tenant administrator runs this journey, inside their own
tenant, on a configuration their party owns.

The trigger is a figure the desk disputes, a model the desk has changed its mind
about, or a parameter that is wrong for the book. The journey starts on the
Products tab of a configuration in
[[id:386DD47E-DA9E-4EA7-B925-852048EE47B7][See the pricing engines a party holds]]
and ends on the same page, on the History tab, with the new version at the top.

The journey changes one product row and the parameters of that row. It does not
add or remove a product type, and it does not rebind a report. Adding a product
is *Add* on the Products tab. Moving a report to another configuration is a step
of [[id:87B9678E-2085-4968-8AEA-7184D1384F1D][Change what a report runs]].

* Steps

1. *Open the row.* On the Products tab the person opens one product. The product
   page shows the product type with its description, the model, the engine, and
   its parameters in two groups, model and engine. *Edit* opens the record dialog.
2. *Read who else is bound.* Before anything is typed, the dialog states the
   reach: the configuration is bound by N report definitions, named, and a change
   reaches the next run of each. It states what the change does not reach: a run
   already produced keeps what it ran with, and no operation says which version a
   run used. When only one report binds the configuration, the dialog says so.
3. *Change the pair.* The model and the engine are combo boxes, as in
   [[id:0D39E4B7-75FD-480A-A996-2234BCC7BCC8][Author a pricing engine configuration]].
   A pair that is not known to work is marked, never refused. Changing the model
   marks the engine for review, because the old engine may not run the new model.
4. *Change the parameters.* The parameters follow the pair. A parameter the new
   pair does not take is shown as *will be dropped*; a parameter the new pair
   usually needs and the row lacks is shown as *usually needed*. Nothing is
   dropped or added until the person says so.
5. *Read the difference.* A panel in the dialog shows the row before and after as
   a diff: the model, the engine, each parameter added, changed or dropped. It is
   the same diff the History tab draws, so the person reads one thing twice.
6. *Choose the scope.* Two choices, with the first selected when only one report
   binds the configuration and the second when several do:
   - *Change this configuration.* The change reaches every report named in the
     reach panel.
   - *Make a copy for this report.* The dialog asks for a name, copies the whole
     configuration with the change applied, and rebinds only the report the person
     came from. The other reports keep the configuration they have. The copy is the
     safe choice when the person does not own the other reports.
7. *Give the reason.* The person chooses a change reason for an amendment and
   writes a commentary when the reason needs one. The set of reasons follows
   whether a field changed, as the standard says. The write claims the version
   read; a configuration that changed since is refused with 409 and the screen
   offers to reload.
8. *Save.* The dialog closes and the page shows the new values. The Products tab
   marks the row for three seconds. A copy opens the copy's page, with a notice
   that the report is now bound to it.
9. *Read the history.* The History tab is the shared timeline of the
   configuration and its parts. The new version is at the top with its reason and
   its diff. *Revert to this version* is offered on any older version and writes
   its values back as a new version.
10. *Leave, or go on.* The person returns to the report and runs it. The run
    uses the new pricing. A run made after the change is not comparable with a run
    made before it for this product, and the page says so, with the same
    statement as [[id:87B9678E-2085-4968-8AEA-7184D1384F1D][Change what a report runs]].

Two screens on the record page: the product row dialog with the reach, the
difference and the scope choice, and the History tab with the revert. The dialog
is one dialog, not a wizard, because the change is one write.

* Prototype

The [[file:../../prototypes/reporting/change-how-a-product-is-priced/][change how a product is priced prototype]] owns this journey, and
[[file:../../prototypes/reporting/change-how-a-product-is-priced.org][its design note]] says what it argues, which states it can reach and what is
fake. It belongs at =doc/prototypes/reporting/change-how-a-product-is-priced/=.

It must draw the record page and the Edit dialog as the Record screen standard
draws them, with the reach, the difference and the scope choice added inside the
one dialog. It must show a configuration bound by one report and a configuration
bound by four, because the default scope choice differs. It must show the
parameters that will be dropped and the ones usually needed. It must show the
409 refusal and the History tab with a revert. It must state that no operation
makes a copy and no operation says which configuration version a run used. Every
value is a fixture.

* What is missing

1. *A vocabulary of models, engines and settings.* The same gap as in
   [[id:0D39E4B7-75FD-480A-A996-2234BCC7BCC8][Author a pricing engine configuration]].
   The prototype draws it from a fixture.
2. *Which reports bind a configuration.* The reach panel needs the definitions
   for a configuration. The read exists for a definition and not for a
   configuration.
3. *A change to a product is not one write.* A product and its parameters are
   written by separate requests, or by the whole document. A change of pair that
   drops three parameters and adds two is six writes. The screen would use the
   document write and send everything, which makes the version of the whole
   document move for a change of one row. The history shows the document as
   changed, not the row.
4. *The version a run used.* No operation says which version of a configuration
   a run was made with. The screen states that a run keeps its configuration and
   cannot say which version that was.
5. *A copy is two requests.* The copy and the rebinding are separate writes. A
   failure between them leaves a copy that no report binds. The screen reads the
   result back and says what landed.
6. *No check on write.* A pair that does not work, or a missing setting, is
   accepted and fails in the run.
