* Goal

One component, ores.inbox, holds the approval requests and the notifications as designed: a relational schema generated from codegen models, the approval rules enforced in the database and the service, notifications raised by any component, and the role request built as the first kind with its screens.

* Acceptance

- ores.inbox is a standard codegen component: overviews, generated CMake, C++, SQL, protocol and web types.
- The approval and notification tables match the accepted schema, with keys and foreign keys and no JSON.
- A member asks for a role, an administrator answers from the queue, and both are told through in-application notifications.

* Decisions

- *System lookups are foreign keys into the system tenant.* The approval and
  notification kinds, states, decision types, channels and the kind's
  permission are system reference data; every reference to them is a foreign
  key with =:use_system_tenant:=.
- *Closed sets are enums.* The delivery outcome is the C++ enum
  =domain::delivery_outcome=, backed by an immutable tenant-less lookup and an
  enforced database foreign key, as trading's enums are.
- *Rules live in the schema where they can.* The one-approval-per-person rule
  is a modelled unique index and a failed delivery's reason a modelled check;
  only the four-eyes rule is a hand-written trigger.
- *Fix the generator, not the output.* Defects the new component exposed were
  fixed in the codegen templates and planner, and the drift sweep shows no other
  component's output changes.
