This page documents a [[id:699A8D45-B67E-4D3E-9206-24FA17C51ADA][story]] in [[id:C863DD3D-740F-4234-B5AB-BD9F3950E09D][Sprint 31]]. It captures the goal, current status, acceptance criteria, and the tasks that compose it.

* Goal

ORE already needs one secret it cannot do without: the client secret that a provider's token exchange presents. Today it lives nowhere, because the rule was that a secret is named and never stored, and naming it was the only way to keep it out of the tree.

This story gives the secrets ORE must use a home. A secret is written once, encrypted with AES-256-GCM under a key that lives outside the database, the repository and the environment file. The service that owns the secret reads it back in memory, for a caller the bus already trusts, and a person who holds the read sees it through the gateway and leaves a record behind. A rotation replaces the key without re-entering anyone's secret, as one audited act.

The story settles what that home is before it builds one: a small service of ORE's own, inspired on a vault and not a copy of one, or a capability inside IAM, which already holds the rows the secrets belong to. A spike proves the cipher with one test before either choice is built on.

Then the store is modelled, served, wired into the provider registry and proven by the gates, so that the first secret ORE needs never reaches a file again.

* Acceptance

- A secret is written once and stored encrypted. The service that owns it, and a
  person who holds the read, get the value back. Nothing crosses the bus in
  plaintext, and no caller sees another tenant's plaintext.
- The key that protects the secrets is never in the database, the repository or an environment file, and its home is recorded.
- A ciphertext is bound to the row it belongs to, so a copy moved to another name, tenant or version does not open.
- A rotation rewrites every secret under a new key as one audited act, and leaves each plaintext unchanged.
- *Every use of a secret is recorded* against the caller that asked for it, and
  a person's reveal is recorded by the vault and by the gateway.
- The provider registry takes its client secret from this store, so no provider secret is in a file.
- The cipher is proven by a test before anything is built on it, and the gates cover the new code.

* Decisions

- *The decision to store a secret belongs to this story* (2026-11-26, product
  owner). The rule that a secret is named and never stored was replaced, while
  the identity story was in flight, by the rule that a secret is encrypted in
  the database under a key that lives outside it; see [[id:0D2294A4-873A-47FE-908A-60BC21F7AAA9][Sign a person up and in
  through an external identity provider]]. That rule needs a store, a place to
  put the key and an audit of every use, which is a capability of its own and
  not a step in a sign-in. It is therefore built here, and the identity story
  asks this store for its provider secret rather than growing one.

- *The custody service is a component of its own, and the kernel stays where it
  is* (2026-11-26, product owner, after the analysis). The vault is
  =ores.vault=, a Domain composite with =api=, =core=, =service= and =client=.
  =ores.security= keeps the primitives and stays a simple Foundation component,
  because Foundation (=ores.variability.core=) and Infrastructure
  (=ores.service='s runner, =ores.storage=, =ores.testing=) link it and a layer
  may only depend on layers below it. Placing the service inside the kernel was
  rejected for that reason; placing it inside IAM was rejected because custody
  of a third party's secret is not identity, authentication, authorisation or
  enforcement. See [[id:F9F1A2BA-94C2-4DAA-8689-F0871AA56801][Secret Custody in
  the Vault]].

- *A secret travels sealed, in both directions* (2026-11-26, product owner's
  requirement). No plaintext secret appears in a NATS message or an HTTP body
  inside the deployment. A write is sealed to the vault's transport key, and a
  resolve is sealed to the consumer's, which the vault looks up by the subject in
  the verified token and never takes from the request. Plaintext exists only
  inside the process that must use it. See [[id:4F28F755-7DA1-4EDD-9983-256622B6088A][Sealed
  Delivery of a Secret to Its Consumer]].

- *IAM decides and never holds; the vault holds and never decides* (2026-11-26).
  IAM keeps every one-way credential, the permission codes, and the provider's
  registry entry, which names a secret and does not contain it. The vault
  enforces no policy of its own, links no part of =ores.iam=, and adds only the
  record of each use. The owner of a secret is a consumer, not a person.

- *The migration is three phases* (2026-11-26). The provider's client secret
  first, because it is the value that is currently nowhere; then the service
  credentials, which is the change to how the environment file is generated;
  then the vendor credentials and the development artefacts. Each phase ends in
  a state the tree can run in, and every value the workspace holds today has an
  entry in [[id:DBF20EC5-63BB-4DE5-957C-5322DE0E487F][Secrets Register]].

- *A person may read a secret back, and the reveal is an audited act*
  (2026-11-26, product owner). HashiCorp Vault gives the value to any client
  whose token holds the read capability, through the command line, the GUI's
  reveal control and the API alike. A store that refuses that is a store nobody
  can operate. ORE keeps the capability and changes the hop: the vault gains no
  operation, the gateway resolves as a registered consumer and answers over the
  authenticated session, the response is never cached, and the vault and the
  gateway each record the act. The bus still carries ciphertext in both
  directions. See [[id:4F28F755-7DA1-4EDD-9983-256622B6088A][Sealed Delivery of
  a Secret to Its Consumer]].

- *The vault's screens are designed here and built later* (2026-11-26, product
  owner). The screens follow HashiCorp Vault's, and their journey and prototype
  are in scope, because a store is understood through the act that writes to
  it, and a person cannot check what the vault holds without that act. The
  implementation stays out: no screen is built in this story, and the
  =ores.http= route remains the only door. See [[id:5B2D332C-7480-40E4-A989-CC8B1D2124D5][Extract
  the vault's journey and prototype its screens]].

- *The pooler reads verifiers, and asks no one* (2026-11-28, after the review of
  PR #5220). The pooler authenticates each client from a SCRAM verifier, so the
  deployment holds no password for it to read, and a copy of a verifier opens
  nothing on its own. The alternative — a lookup function the pooler calls — was
  removed rather than wired: it would cost a database role that may read every
  verifier in the instance, and save a pooler restart that a rotation owes
  anyway. See [[id:929A4722-8F06-4DEF-B759-D0800D4AC6D5][Connection pooling for
  shared database instances]].

* Out of scope

- A secret ORE only proves and never recovers. A password hash is one-way by
  design and stays in IAM.
- The certificates a service presents to NATS. A TLS library reads a key from a
  path, the deployment issues and rotates a leaf per service every ninety days,
  and a leaf that must be a file is certificate management rather than custody.
- A general-purpose secret manager for the fleet: no dynamic credentials, no
  leases, no PKI engine, and no storage engine of its own.
- The BFF and the built screens. The write route is =ores.http='s own, so no
  server sits between a person and the vault. The journey and the prototype of
  those screens are in scope, and the screens themselves are not.
- The test double's and the seeder's fixtures. They move here only once the
  store exists and the gate can run without a file.
