* Goal

A convention family is reachable over the message bus by its own subjects, through its own handler and its own registrar, so a caller that wants one family never touches a type that carries all of them.

* Acceptance

- Every convention entity has a protocol header carrying its own list, get, put and delete subjects, and a handler and registrar to serve them.
- No protocol or handler translation unit reflects a type that holds more than one family.
- The subjects a family answers are derived from the same registry the apply uses, so the two cannot disagree about a family's name.

No plan was needed. The protocols and handlers already existed per family, so the task closed on that finding.

* Notes

- The aggregate cannot be deleted before its replacement exists. Deleting
  =conventions_document= now would leave the import path with no wire type,
  because the per-family operations and the bundle do not exist yet. So this
  task comes before the deletion, not after it.
- Order within the task. First generate one protocol message pair per family
  from the registry, additively, each in its own translation unit. Then generate
  the handler and registrar per family. Then the bundle operation that applies
  the families in one unit of work. Only then can the document operation and its
  aggregate be deleted, and the ORE path move onto the new shape.
- The registry already carries what the protocols need: family key, domain type,
  subject stem and write mode. The subject stem is the natural subject prefix for
  each family's messages, so the protocols and the apply fragment share one
  derivation and cannot disagree.

* Result

Nothing to generate. Codegen already emits a protocol and a handler for every
convention entity: =deposit_convention_protocol.hpp= carries the list, get, put
and delete subjects under =refdata.v1.deposit_conventions.*=, and every one of
the 166 generated protocol headers does the same for its own entity. Each has a
handler and a registrar. The task's premise was that this did not exist.

The remaining gap is not per-family messaging. It is the unit that applies
several families in one transaction, because a transaction needs one handler and
one message, and one message carrying every family is the aggregate that fails on
MSVC. That is the bundle, and its resolution is the staged import: stage the
families durably, then commit in one message that reads the staged rows and
applies them in one unit of work. The commit message then carries no family data
and no aggregate is instantiated.

That work belongs to the bundle task, which follows this one.
