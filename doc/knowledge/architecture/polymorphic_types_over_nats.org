#+title: Polymorphic payloads over NATS
#+description: Deprecated. How not to carry one of several concrete types in a message, why rfl cannot tag a variant of the trading instrument types, and the data-oriented replacement: one typed array per concrete type, joined by key.
#+type: knowledge
#+level: cross
#+filetags: :architecture:nats:rfl:serialisation:
#+created: 2026-06-25
#+updated: 2026-10-08

* Summary

*Deprecated.* This page records a pattern the codebase used and no longer
follows. Do not use it for new work.

The pattern: to carry one of several concrete types in a single message, tag
the payload. The page recommended one NATS subject per concrete type, a
discriminator field on the containing entity, and two-phase dispatch when the
reader cannot know the type until runtime.

Why it is deprecated: it is polymorphism at the message level who pays for it.
Data-oriented design puts the type in the container, not in a per-element tag.
A tagged payload field is one of two things, and both are wrong:

- A =std::variant= field. =rfl= encodes it as an =index= key holding the
  zero-based position of the active alternative, which breaks silently when an
  alternative is added, removed or reordered.
- A hand-written type-name plus encoded-body pair, such as
  =ores::trading::domain::instrument_payload=, which has no static type, no
  schema, and no compile-time check at either end.

* The rule

1. No =std::variant= field in a message.
2. No =std::string= field that holds an encoded value.
3. When a result set is heterogeneous, carry *one typed array per concrete
   type*. Each element's type is then static, from the array it sits in.
4. Join the arrays by their keys. Do not tag the elements.
5. The wire shape is a projection of the persisted entity, not a second
   artefact. Where the projected types are generated, generate the arrays that
   hold them too; a hand-written aggregate of typed arrays is the same
   hand-written second type system under another name.

This is the array-of-structs to struct-of-arrays change, applied to message
layout: the tag moves from every element to the container.

* Why rfl cannot tag the variant

This is the constraint that produced the deprecated designs, and it still
holds. Any replacement has to respect it.

=rfl= writes a =std::variant= as:

#+begin_src json
{ "index": 2, "value": { ... } }
#+end_src

=rfl::TaggedUnion= and =rfl::AddTagsToVariants= write a readable tag instead,
but they do not compile for the trading instrument types: they build an
=rfl::Literal= over every field name reachable through the variant, 502 of
them, which exceeds the fold-expression nesting limit on macOS and the
recursive-type limit on MSVC.

The consequence is that a typed replacement must be flat at the *leaf* level.
A nested variant — =swap_instrument_data= holding =rates_instrument_variant=,
or =fx_instrument_variant= — cannot be encoded either, so splitting only the
top-level alternatives is not enough.

* The violation this page records

=projects/ores.trading/api/include/ores.trading.api/domain/instrument_payload.hpp=
declared:

#+begin_src cpp
struct instrument_payload {
    std::string type;
    std::string body;
};
#+end_src

Every trading instrument crossed the export boundary through it:
=trade_export_item.instrument= in
=projects/ores.trading/api/include/ores.trading.api/messaging/trade_operations_protocol.hpp=.
The type name was a hand-written literal kept in sync with =trade_instrument=
by hand, and the body was the =rfl= JSON of the concrete type. The tag
duplicated =trade_type=, which the same message already carried on the trade
anchor and which the trade type catalogue already maps to the concrete type.

It is being removed in favour of typed arrays. See the component's own
overview for the current export message shape.

* What the deprecated pattern got right

Two parts of it are worth keeping in mind even though the pattern as a whole
is gone:

- *The discriminator belongs to the containing entity, not the payload.* That
  part survives: =trade.trade_type= identifies the concrete type, and the same
  is true of =market_feed_config.feed_type=. The change is that the reader no
  longer needs a tag on the payload to use it, because the batch it reads from
  is already typed.
- *A raw JSON blob is never acceptable.* The page said this and it was right.
  It is the reason =instrument_payload= is being removed rather than extended.

* Historical example: trading instruments

The page's canonical example was
=a separate save request per instrument type in instrument_protocol.hpp=, with
one NATS subject per concrete type. That file no longer exists: each instrument
entity now has a generated protocol of its own, which is the same one-subject-
per-type idea produced by codegen instead of by hand.
