* Goal

Nothing uploads an image: the BFF serves /api/images/:id as a read only, so a member can set an image id but nothing puts an image there, and the photo cannot be replaced. This task adds the upload path into ores.assets that stores the image and returns its id, and states the accepted formats and the maximum size once, so the picker and the server enforce the same rule.

* Acceptance

- An upload path into ores.assets accepts image bytes with their media type and returns the id of the stored image.
- The accepted formats and the size bound are stated in one place, and the server enforces them.
- The rule the accepted prototype states is the rule implemented: PNG, JPEG or WebP, at most 2 MB, and at least 128 by 128 pixels.
- The statement is available to the picker from the same source, so the picker holds no second copy.
- A refused upload carries a code the picker branches on.
- The stored image carries the uploaded media type and bytes, base64 in the database as the entity model states.
- Tests prove an accepted image lands and a refused image is refused with its code.
- The change regenerates cleanly and the assets suites pass.

* Plan

The upload has one shape: the caller presents a session, the body states the
bytes and their media type, and the server holds the rule and enforces it. The
rule is stated once, in a validator beside the service that applies it, and the
same statement is answered as data, so a picker reads it rather than keeping a
copy. The upload carries no account id: the profile is set by the self write
that references the returned image id, so nothing about the upload is
account-scoped.

1. Declare the pairs in a new operation model =
   ores.assets.image_messages.org= (=entity_singular: image_operations=),
   beside =ores.assets.image.org= and rendered to C++ and TypeScript from one
   source. The singular differs from the entity's, so the entity keeps its
   generated =image_protocol=.
   - =assets.v1.images.upload= takes =mime_type= and =data= (the bytes,
     base64). The reply is the shared result plus the id of the stored image.
     The bytes are not answered back: the uploader holds them, and a reader
     that wants them asks the image read by id.
   - =assets.v1.images.upload-policy= answers the rule as data: the accepted
     media types, the size bound, and the minimum width and height.
   - Neither message states =http_route=: the picker will reach both through
     the BFF over NATS.
2. State the rule once, in =
   ores.assets.core/validation/image_upload_validator.hpp=: PNG, JPEG or WebP;
   at most 2 MB; at least 128 by 128 pixels. =policy()= answers that record
   and =validate()= applies that record and nothing else. The validator reads
   the format from the bytes (PNG =IHDR=, JPEG =SOF=, WebP =VP8=/=VP8L=/=VP8X=
   headers), so bytes that are not the declared media type are refused rather
   than stored, and the refusal message is built from the policy it enforces.
3. Serve both subjects from a hand-written =image_operations_handler= and
   register it in the assets registrar beside the generated per-entity
   registrars. The handlers resolve the tenant and the actor from the bearer
   token. The upload carries no permission code, for the reason the self
   writes carry none: any signed-in account may upload, the image lands in the
   caller's tenant, and the account a photo appears on is decided by the self
   write that references it.
4. =image_operations_service::upload_image= decodes the base64 and validates
   through the validator, refusing with the code the picker branches on
   (=unsupported_media_type=, =image_too_large=, =image_too_small=,
   =invalid_image=). An accepted upload lands as an image with a minted id, a
   code derived from that id, the stated media type and the bytes; the store
   keeps the bytes base64-encoded in the text column, which the mapper
   performs.
5. Tests prove an accepted image lands with its media type and bytes, a
   refused image is refused with its code, and the policy answers the rule the
   validator applies. Then regenerate the CMake file lists, build, run the
   assets suites, and run the drift gates.
