* Goal

A refusal says the same thing whichever side refuses it, and says it once.

The C++ services and the PostgreSQL store both reject a write, and each carries
its own copy of the code, the SQLSTATE and the sentence. The code vocabulary is
30 string literals at 9,051 sites, every one of them generated from four
templates. The SQLSTATE vocabulary is nine values at 1,417 sites, and two of
those messages account for 673 of them. A caller cannot see the record, the
version or the field in the reply, because the pre-check that decides a refusal
sets a code and no message.

* Plan

** One document, two rendered artefacts

[[file:../../../../../projects/ores.database/modeling/ores.database.outcomes.org][ores.database.outcomes]] is the catalogue. It is a new codegen model type
(=ores.codegen.outcome_catalogue=), registered in =core.py= and =manifest.py=
and given a loader in =org_loader.py=. Each =**= entry under =* Outcomes=
carries its values in a drawer and its sentence in a named =message= source
block. The loader refuses a document whose placeholders and =:args:= disagree,
whose =store= entry names no SQLSTATE, whose =request= entry names one, or
whose codes or SQLSTATEs repeat.

Two facets read it.

| facet             | artefact                                                        |
|-------------------+-----------------------------------------------------------------|
| =ores.cpp.outcome= | =projects/ores.database/include/ores.database/domain/outcome_code.hpp= |
| =ores.sql.outcome= | =projects/ores.sql/create/utility/outcome_functions_create.sql=  |

The header holds the enum, =to_string=, =outcome_of=, =describe= and the two
=refuse= overloads. The SQL holds one function per store outcome, the shared
=ores_outcome_fill_fn= renderer, and =ores_outcome_raise_fn=, which maps a code
to its SQLSTATE and calls the function.

** Why a codegen model type and not a bespoke generator

The physical-space graph already gives the drift gates for free. A second
generation path would need its own.

** Where the two renderers agree

=ores_outcome_fill_fn= and =describe= substitute the same ={name}= placeholders
from the same closed argument vocabulary. The C++ test and the pgTAP test
assert the same literal, so a change to one renderer alone fails a gate.

** What this unit migrates

The two messages every entity repeats, 673 sites, and the null-value message,
77 sites. A trigger now states the code, the entity, the field and the value.

The per-model foreign-key wording already lives once, in the model, and stays
there.

** What the next unit carries

The service template's 44 refusal sites. They cannot fill a sentence from what
the repository returns: =remove= reports an enum rather than the versions
behind the conflict, and =prepare_change= holds no stringified key. Migrating
them needs the repository to carry the current version on a conflict.

* Result

criterion above holds on it.

The catalogue is [[file:../../../../../projects/ores.database/modeling/ores.database.outcomes.org][ores.database.outcomes]], a new codegen model type. It
holds 14 outcomes, three refused by the store and 11 by a request. Codegen
renders both artefacts from it:

  holds the enum, =to_string=, =outcome_of=, =describe= and the two =refuse=
  overloads.

  one message function per store outcome, the shared =ores_outcome_fill_fn=

SQLSTATE. A trigger now states the code, the entity, the field and nothing
else.

**What this task does not land.** The service template keeps its 44 refusal
sites. Two shapes cannot fill a catalogue sentence from what they hold today:
a removal conflict returns =remove_status::conflicting=, an enum with no
version behind it, and =prepare_change= holds no stringified key. The unit
that follows either drops the concrete key value from the two store sentences
or has the repository carry the current version on a conflict.

**A drift repair this task did not do, and the next one must.** Regenerating
=ores.cpp= at =HEAD= does not reproduce the committed scheduler, inbox,
synthetic and trading sources. =check_component_drift.py --all= never saw it,
because =COMPONENTS_UNDER_TEST= omits those components, and =--sweep= only
fails on files the branch touched. The visible symptom is
=job_definition_service.cpp= calling =request.filter= and =request.as_of=,
which the committed protocol lacks; regenerating the protocol adds both.
