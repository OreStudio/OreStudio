* Acceptance

- A template generates the writer from the same model as instrument_batch.
- Every array of the batch has a writer. The service refuses by name an array that the trade type does not hold. A bond row's remainder members have no writer yet, and the service refuses them by name.
- A round trip proves that an exported trade books back to the same rows, for a header with children.

* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

1. Add a =routed= mark to the batch members the loader builds, so a template can tell an instrument header from a child.
2. Add the archetype =ores.cpp.trade_type.writer=. It generates =instrument_batch_writer.hpp= in =ores.trading.core=: one write per batch member, through the member's =<entity>_repository=, with the create-only claim. A row states its trade id, its activity id and its version by the shape it has, as =trade_id_of= already reads the key by shape.
3. Add to the same header the check of the batch against the trade type: a routed array that is not the table =instrument_table_for= names for the anchor's trade type is refused by name.
4. Replace the three refusals and the bond write in =book_trade= with the generated writer. The bond container writes its header and its fact rows. The issue and its children stay with =put_bond_issue_composite=.
5. Prove it: a test for each routing refusal, a database-backed booking of one trade for a sample of kinds (a header only, a header with children, a family with a shared child), then the export-and-rebook round trip for the trades the Acme population holds.

* Notes

Decisions made in this task:

- The generated header =instrument_batch_writer.hpp= has one call for each batch member and no table of its own, so the template stays small. A row's shape decides where its keys go: the generated code reads =instrument=, =identity= or the flat members by =requires=, as =trade_id_of= does.
- The trade type check reads =instrument_table_for=. A routed array that is not the table of the anchor's trade type is refused with the code =instrument_not_routed=. This closes the gap that the review of the previous task named.
- A bond container writes its header only. The issue and its children stay with =put_bond_issue_composite=. The remainder members of a bond row (fact rows, schedules, legs, option block) are refused by name, by reflection over the row, as before.
- Children are written after the headers, in the order of the catalogue. The children link to the trade by a soft foreign key, so the order among them does not matter.

* Result

=book_trade= writes every array of an =instrument_batch= through a generated writer: one create for each row, in the same transaction as the anchor. The archetype =ores.cpp.trade_type.writer= generates it from the trade-type catalogue. The service states the trade id, the trade type and the activity id on each row, by the shape the row has. It refuses by name, before anything is written, a routed array that the trade type does not hold.

A swap trade with its header and two legs books, exports and books back to the same legs. An FX forward trade books with its instrument. The 32 trades of a provisioned Acme tenant stay whole.

Not done: a bond row's remainder members (fact rows, schedules, legs, option block) have no writer, and the service refuses them by name. The round trip is proved for one family with children, not for every kind. Three suites fail in the full run, and they fail the same way on a clean main.
