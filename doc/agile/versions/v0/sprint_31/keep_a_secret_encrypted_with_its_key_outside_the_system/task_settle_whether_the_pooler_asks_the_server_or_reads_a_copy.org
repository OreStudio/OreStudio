** What

=ores_utility_pooler_auth_lookup_fn= exists so a transaction pooler can ask the
server for a client's verifier instead of holding a copy of it. Nothing calls it.
Settle it: wire the pooler to ask, or remove the function and keep the copies.

** Why

=start_ci_pooler.sh= writes =auth_type = scram-sha-256= with an =auth_file=, and
the file is filled with verifiers that =compass vault provision= reads from
=pg_shadow= and writes under =build/keys=. No configuration anywhere sets
=auth_query= or =auth_user=, so the function, its drop script and its two
entry-point lines are the whole of its life. A standards review over PR #5220
found that, and the PR merged with it recorded rather than hidden.

Wiring it is the better design: a rotation then needs no pooler restart and no
copy of anything lives under =build/=. It costs a login role for the pooler
itself, which is one more credential in the environment file — the very thing the
register's second phase removed from the services.

Removing it keeps the verifier files, whose cost the register already states: a
verifier is useless without the password, and a rotation needs a pooler restart.

Doing neither is the only wrong answer, because a function nothing calls reads as
a mechanism that exists.
