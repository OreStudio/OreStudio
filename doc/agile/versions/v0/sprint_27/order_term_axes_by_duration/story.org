* Goal

A person who reads a surface or a curve sees each term axis in order of length: 1W, 1M, 2M, 3M, 6M, 9M, 1Y, 18M, 2Y. The order does not depend on the order of the lines in the file that declared the shape.

* Acceptance

- A shape whose term axis was stored out of order is read in order of duration, so the snapshot, slice and evolution reads return the nodes in that order without any change of their own.
- A term the parser cannot read keeps its stated order and follows the terms it can read.
- A second source that adds terms leaves the axis in order of duration.
- A shape stored before this change is read in order too, with no backfill.
- An axis that is not a term keeps the order its points state.

* Decisions

- The sort happens when the shape is read, in =read_series_shape=, and not when it is declared. Every read of the order goes through that one function. A sort at declare time would leave shapes already stored in the wrong order and would renumber stored values when a second source added a term. The stored order stays the order the source stated, which keeps the history honest.
- The order is by kind, then by length. FX overnight tenors come first, then periods, then dates, then futures continuations. A period counts a month as 30 days and a year as 365. Values that are not terms follow the terms, in their stated order.

* Out of scope

- A sort in the screens. The server sorts once, so every read shows the same order.
- A change to the stored order. The shape tables keep the order the source stated.

* Result

A term axis is now read in order of length, on every read, for shapes stored before this change as well as new ones. The screens needed no change. The decision to sort at read time and not at declare time is in the decisions. The marketdata core suite passes, and the order was checked on the live stack.
