* Goal

Close the security defect
[[id:89CD5129-06AA-448A-BED1-78F829ABC952][The session read handlers skip the permission check the catalogue grants]].
=iam.v1.sessions.list=, =.get= and =.get_many= answer any authenticated caller
with the tenant's sessions: client, address, country, byte counters and account.
The catalogue grants =iam::sessions:read= ("View active sessions") for exactly
this purpose, the account reads check =iam::accounts:read= and the login-record
reads check =iam::login_info:read=, so the three reads are unguarded by oversight
and not by design.

This lands before the Audit sign-ins screen, because that screen is built on
these reads.

  =forbidden= when the caller does not hold =iam::sessions:read=, and answer as
  they do today when it does.

  the registry is what claims the component has no unguarded read.

* Notes

- The fix is small and the whole resource now reads the same way: every verb
  checks the permission its operation needs, and a refusal is =forbidden=.
- The clean-standard registry entry for ores.iam recorded this class of defect
  as closed for accounts and login records; the session reads arrived later with
  the CRUD protocol and were never checked. The registry claim should be
  re-read after this lands rather than assumed.
- =iam::sessions:delete= is still required by the delete verbs and still granted
  by no role, which the inventory records as its own gap: only a holder of the
  =iam::*= wildcard can delete a session row. This task does not change that.

* Result

Done 2026-10-01, except for the test that asserts the refusal.

The guard is generated, not written. Review of the pull request caught that
=session_handler.hpp= carries =AUTO-GENERATED FILE - DO NOT EDIT MANUALLY=, so
the three guards had first been written by hand into a file the next
regeneration would overwrite. The model owns the decision now:
=projects/ores.iam/modeling/ores.iam.session.org= sets =:guard_reads: true= in
its flags, and =compass codegen regenerate --component iam --entity session
--address ores.cpp.nats-handler= emits the same three guards — =list_sessions=,
=get_session= and =get_many_sessions= each checking =iam::sessions:read= before
they decode. The account and login-record models set the same flag, so the three
entities guard their reads alike and stay guarded through later regenerations.

The comment rewording the review also flagged was dropped rather than kept: that
sentence lives in =cpp_nats_handler.hpp.mustache= and is emitted for every verb
of every component, so fixing it in one generated file would revert on the next
run. Filed as
[[id:EC7C2C75-5408-4350-AF9F-638A82EEC585][Every generated NATS handler says its reads check the permission a write needs]]
so it is fixed once, in the template.

Verification: the library and the suite build with the regenerated handler, and
=ores.iam.core.tests= passes whole — =All tests passed (425 assertions in 165
test cases)=. The first run of that suite failed 59 of 165 cases, every one of
them with a missing column (=account_status=, =is_registration_default=,
=tenant_type=) because the restored database was behind the SQL on main;
=compass db recreate -y -k= rebuilt it and the suite then passed, which is worth
knowing for every later task in this story.

*What is still missing.* No test exercises the refusal, and the reason is
larger than this task: =projects/ores.iam/core/tests/= mentions no permission
string, no =has_permission= and no =forbidden= anywhere, so no guard in the
component is covered — not the account reads, not the login-record reads, not
the write or delete verbs this guard copies. The session handler is therefore
not the odd one out; it is the first verb set whose refusal anybody wanted to
prove. The codegen suite already covers the mechanism — a model that sets
=guard_reads= generates guarded reads — so the cheap regression guard is a case
asserting that this model sets the flag; a case that calls a read without the
permission and asserts =forbidden= needs a harness the component does not have
yet. That decision belongs to whoever takes this task next.
