* Goal

Replace =fx_instrument_variant= with one typed array per product. The variant is
an aggregate that carries an entity, and the family this story is reworking is
the one place it survives on the FX path: every other family already returns a
carrier struct. The array an element sits in states its type, so nothing needs
a discriminator, and the range bounds unit has one more array to add rather
than a field to push into an aggregate.

* Acceptance

- =fx_instrument_variant= is deleted, and no source names it.
- The carrier is one typed array per product in =fx_instrument_data=, joined by trade id, with no discriminator and no aggregate holding an entity.
- Each =forward_fx_*= function returns its own concrete domain type, so a caller names the product it asked for.
- The import handler and the exporter drive the arrays through one shared visitor rather than an inner =std::visit=.
- No behaviour change: the ORE core suite passes unchanged.

* Plan

1. Add =fx_instrument_data= beside the other family carriers in =instrument.hpp=, with the seven instrument arrays and a =stamp_ids= overload.
2. Change the fifteen =forward_fx_*= functions to return their own product type, and have =map_fx_instrument= push into the array the product belongs to.
3. Add one visitor, =visit_fx_products=, that walks the arrays in order and returns whatever the visitor returns, so both the importer and the exporter keep their existing per-product bodies.
4. Swap the alternative in =trade_instrument=, delete the variant header, and join the arrays in =instrument_batch_mapper=.
5. Convert the tests that unwrapped the variant.

* Notes

- The evidence for this task is the parent story's decision and [[id:B607E5B7-190F-4D38-B515-8A7B27FB6B47][The atomised entity]]: the wire carries one typed array per part, and the array an element sits in states its type.
- The bond family carries its variation with =std::optional= fact rows beside a header, so it needs no variant. FX has no header, which is why the variant stood in for one; typed arrays answer the same question without inventing a header. The story records why the header was not taken.
- The equalities are not lost: a caller that needs to know which product it holds asks the array, and the routing by =trade_type_code= stays where the catalogue puts it, in the mapper and the exporter.
- The equity, credit and rates variants are untouched. They are the same defect in other families and want their own story.

* Result

The FX family carries typed arrays. =fx_instrument_variant= is deleted, no
source names it, and the family's carrier is =fx_instrument_data=: seven typed
arrays joined by trade id, with no discriminator anywhere. The fifteen
=forward_fx_*= functions return their own product type, =map_fx_instrument=
chooses the array, and one shared visitor walks the arrays so the importer and
the exporter keep their per-product bodies.

No behaviour change. The ORE core suite passes at 706 cases, and both
=ores.ore.core.tests= and =ores.ore.service= build. One review reply is
recorded above as rejected, with the gate that refuses it.

The range bounds unit now has its place: one more array on the carrier, stated
once in each of the two array lists, and no walk or branch to edit.
