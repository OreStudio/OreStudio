* Acceptance

- The build compiles and the tests pass on the dist-upgraded toolchain.

- The root steps and the failures met are in the record.

* Plan

Three moves, in this order, each proven before the next.

** The ports

The submodule moves to the commit the release move names and the manifest is
resolved against it before anything is compiled. The ports did not all stand
still: =cnats= 3.14.0 becomes 3.15.0, =lz4= 1.11.1, =zlib= 1.4, and
=vcpkg-cmake= 2026-11-09. =libpq= stays at 18.4, which is the newest the registry
holds: it speaks the protocol a 19 server answers, so the client library and the
server version are allowed to differ, and that is a decision rather than an
accident.

** The compiler and the standard library

The dist-upgrade moved GCC to 16 and rewrote the C++ standard library headers. A
precompiled header built before that is refused by clang, so the build tree's
=PCH= files were removed and the whole tree recompiles once.

** The database

PostgreSQL 19 was proven before the cluster was touched. A throwaway 19.0 cluster
was created with =initdb= on port 55432, the whole database was built on it with
=compass db recreate=, and its tables were counted against the 18 the environment
runs. The switch of the system cluster needs root and the steps are recorded in
=* Notes=.

* Notes

** Decision, 2026-11-24: the database stays on 18

The 19 move works. It stays out of this release because TimescaleDB has no package
for 19 in the Debian forky archive, in PGDG's forky or trixie suites, or in
TimescaleDB's own packagecloud repository, whose forky index is empty. Losing the
hypertables, the compression and the retention policies costs the fleet more than
staying one major version behind, and a plain table converts in place when the
package lands. The throwaway cluster was torn down after the measurement.

What the release does not bring, found while proving it.

- =postgresql-19-pgtap= and =postgresql-19-timescaledb= are not in the Debian 13
  archive. Only the core server, its JIT and =pgaudit= are. Both extensions are
  optional in =setup_extensions.sql=: without pgTAP the 110 SQL test files cannot
  run, and without TimescaleDB the create scripts keep plain tables, because each
  hypertable is guarded by a check that the extension exists.
- =libpq= has no 19 port in the registry, so the client library stays 18.4. That
  is protocol-compatible with a 19 server and is recorded as a choice.
- The environment's cluster is owned by =nobody=, not by =postgres=, which the
  Debian upgrade tooling assumes. Rebuilding the cluster is the simpler path here
  and the database is reproducible from SQL, which the throwaway cluster proved.

** The root steps

=pg_upgradecluster= keeps the data and rebuilds the cluster; dropping and
recreating is simpler and loses only what SQL rebuilds. Both are listed.

* Result

* Result

The ports and the compiler are picked up. The database stays on 18, with the 19
move proven and its blocker named.

The build compiled the whole tree on the new ports and the dist-upgraded
compiler and standard library: 29 minutes 43 seconds, from a tree whose
precompiled headers had to be rebuilt because the upgrade rewrote the C++
standard library headers. No port failed against the new registry.

The suite ran 108 tests. 104 passed. The four that failed were looked at one at
a time:

- =ores.refdata.core.tests=, =ores.inbox.core.tests= and =ores.workflow.core.tests=
  failed because the fleet was stopped and their pooler, on port 20407, was not
  listening. Started the fleet and all three passed: 99, 11 and 14 seconds.
- =ores.marketdata.core.tests= failed on two assertions in the narrowed-export
  test, which is main's fault and not this move's: =8f71717dfa= made a run carry
  the interest rate quotes its curves are built from and left the test asserting
  the older rule. The test was brought onto the rule and the whole binary passes:
  478 cases, 45316 assertions.

Every test that failed therefore passes when run against a running fleet, and
nothing in the suite failed on the toolchain or the ports.

The database move is recorded as the story's decision: TimescaleDB has no package
for 19 in Debian, in PGDG or in its own repository, and the hypertables, the
compression and the retention cost the fleet more than being one major version
behind. =setup_extensions.sql= and =technical_space_sql.org= now say "18" rather
than naming a major the environment cannot run.
