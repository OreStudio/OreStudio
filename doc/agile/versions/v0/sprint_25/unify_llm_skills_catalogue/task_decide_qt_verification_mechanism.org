* Goal

Qt verification today is a human driving the client while the QA Validation Runner records the result. That does not survive an unattended run. Settle the mechanism against one rule: assert on state, not on pixels, because an agent needs a predicate it can evaluate and a screenshot is not one. Build the layers in preference order. Widget-level tests under Qt's own test framework with the offscreen platform, so they need no display and run in CI beside the other tests. A scripted control surface inside the application, the Qt sibling of ores.shell run with a script file, which opens windows, invokes actions and reports state; the application already captures its own screenshots in-process so the evidence trail comes free. External screen automation only for pixel-parity work such as manual screenshots, where a human reviews the output anyway. Prove the choice on one real Qt feature before adopting it.

* Acceptance

- Widget-level tests run headless under the offscreen platform and are part of the normal test run, needing no display.
- A committed script can drive the Qt client non-interactively and report state a checker can assert on.
- Screenshots are recorded as evidence for humans and are never the basis of a pass or fail verdict.
- External screen automation is used only for pixel-parity work, and the reason is documented where an author will meet it.
- The QA Validation Runner keeps its human-driven role; the scripted path complements it rather than replacing it.
- One real Qt feature is verified end to end through the new mechanism before the task closes.
- The decision, the options rejected and why, are recorded.
