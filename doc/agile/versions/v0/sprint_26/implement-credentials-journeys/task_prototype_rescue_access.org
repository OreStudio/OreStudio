* Goal

Answer one question with a throwaway prototype: how does a tenant
administrator get one colleague back into the system, or shut the account
down, on one screen?

[[id:A441DA2E-4B74-49B3-97AD-1861647B7D94][Rescue access]] carries one screen.
It holds the account, its security state, the password form and the actions,
because the administrator thinks of them as one decision. The screen starts
from a support call, so the prototype decides how the screen opens, how it
shows the recommended action, and how it states the actions the server cannot
perform.

* Notes

The journey's gaps, from the * What is missing section of
[[id:A441DA2E-4B74-49B3-97AD-1861647B7D94][Rescue access]]. The screen states
each one, and the prototype decides how.

1. *No forgot-password or self-service recovery.* Nothing lets a member who
   cannot sign in start recovery. The only password subjects are
   =iam.v1.accounts.change-password= and =iam.v1.accounts.reset-password=.
2. *No activate or deactivate.* An account has no active flag. The only state
   an administrator can change is =login_info.locked=.
3. *The reset flag cannot be set over NATS.* =password_reset_required= exists,
   =account_operations_service::set_password_reset_required= implements it, and
   the HTTP route uses it. No NATS subject calls it.
4. *Locking does not end sessions.* =iam.v1.accounts.lock= writes the login
   record only, and an open session stays open until it expires.

The three write subjects exist and each needs its own permission:
=iam.v1.accounts.reset-password= needs =iam::accounts:reset_password=,
=iam.v1.accounts.lock= needs =iam::accounts:lock=, and
=iam.v1.accounts.unlock= needs =iam::accounts:unlock=. A tenant administrator
who holds the role has all three.

* Result

Built 2026-09-30. Snapshot: branch =prototype/rescue-access=. The product owner
has not chosen a variant yet, so nothing here is carried into the build.

Route =/prototype/rescue?variant=a|b|c=, switched from the bar at the foot of
the page, reached the same way as the member's screen: run
=npm run dev:web --workspace @ores.web= and open
=http://localhost:5173/prototype/rescue?variant=a=. No server is needed.

*Three variants on one screen.*

- *A · One decision screen.* The account, the reset form, the lock control and
  the gaps, stacked in the order a support call goes.
- *B · Diagnose, then act.* The security state leads and names the action it
  suggests; the reset form and the lock control sit side by side under it.
- *C · Roster and panel.* The account list stays in view on the left with each
  account's state, and the rescue panel fills the right.

*Recommendation: C, with B's diagnosis.* The administrator arrives from the
account list, so keeping it in view answers "which colleague" without a second
screen, and the state-names-the-action panel is what turns a support call into
a decision. A is the same content with the roster dropped; B repeats what C
keeps.

*Decisions the prototype settles.*

- *Lock and unlock are one control that shows the state it produces,* not two
  buttons that can contradict each other. The control is drawn for both states
  so a reviewer sees them; nothing is sent.
- *Lock states what it does not do.* The panel says a lock leaves open sessions
  open, because the journey's fourth gap is invisible otherwise.
- *The forced change is drawn, and disabled.* No subject carries
  =password_reset_required= over NATS, so the screen states that the reset
  writes the password directly and cannot ask for a change at the next sign-in.
- *Self-service recovery and activate or deactivate are gap lines, not
  controls.* Neither has an operation, so neither is drawn as a button.
- *The account's state belongs in the list as well as the panel,* so an
  administrator scanning the tenant sees who is locked before opening anyone.

*The journey is unreachable from the browser today.* No route serves
=iam.v1.accounts.list=, =iam.v1.accounts.get=, =iam.v1.login_info.get=,
=iam.v1.accounts.reset-password=, =iam.v1.accounts.lock= or
=iam.v1.accounts.unlock=. The subjects exist and each needs its own permission;
what is missing is the browser's path to them. The screen's build task cannot
start before those routes do, and that is the largest single item this journey
adds to the group.
