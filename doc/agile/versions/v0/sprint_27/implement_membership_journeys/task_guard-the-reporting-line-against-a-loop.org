* Acceptance

- A write that would make an account report to itself is refused by the store.
- A write that would close a longer cycle is refused, and the manager that was there stays.
- The refusal names the reason, so the screen can state it.
- A test covers the two-account cycle, the self cycle, and the manager that survives a refused write.
- =check_component_drift.py --component iam= reports no drift.

* Plan

1. Declare =:prevent_cycle: true= on the =reports_to_account_id= foreign key,
   the model's own way of asking for the guard.
2. Regenerate the component, so the accounts insert trigger gains the recursive
   manager-chain check.
3. Test the refusal at the service, where a write goes through the trigger.

* Notes

- *The guard is the model's own, not a hand-written check.* The codegen
  templates already carry a recursive =ancestor_chain= block behind
  =:prevent_cycle:=, used by the business-unit and portfolio hierarchies. The
  account model simply had not asked for it, so the entry is a property and a
  paragraph rather than new C++.
- *The check walks the manager chain in SQL.* It runs inside the accounts
  insert trigger, which fires for every new version, and raises =23514= when the
  chain reaches the row being written. That covers the self cycle and any longer
  ring, and it holds however the write arrives — the service, the shell, or the
  Acme publish.
- *The refused write leaves the old manager in place.* The trigger rejects the
  insert before the version is written, so there is no half-applied change, and
  the test asserts that.
