* Acceptance

- report_run_setup carries the setup parameters as typed columns and replaces the corresponding part of risk_report_config.
- report_analytic holds one row per analytic, keyed to a seeded lookup of the thirty-five analytic types.
- An analytic with parameters has a typed parameter entity; adding a type adds a lookup row and a table, never a column on the report definition.

* Notes

- The plan said each analytic type would own a typed parameter table. The work
  changed that, and the reason is on the record: thirty-five tables, one of them
  around seventy columns wide, is not a shape to maintain, and the reporting
  registry already solved this exact problem when it modelled a configuration's
  parameters -- a definition lookup, a value domain, and a row per value. The
  run's analytics use that pattern too, so a parameter is added as a lookup row
  and never as a column, which is the acceptance's own test. One table replaces
  the plan's thirty-five. The decision is stated in
  =ores.reporting.report_analytic_parameter='s model prose for review.
