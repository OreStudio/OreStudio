* Goal

This story is a wayfinder map: an index of decisions. Each decision
lives in its task. Tasks carry a =[wayfinder:<type>]= tag. Each task
names its blockers in its goal. The frontier is every BACKLOG task
whose blockers are all DONE.

** Destination

A web-idiomatic screen spec plus a clickable ores.web prototype for
the five bootstrap workflows: system bootstrap, operational tenant,
demo (ACME) tenant, tenant onboarding and party provisioning. The
screens use one server-side provisioning contract that ores.shell
also uses. The tenant lifecycle terms are formalised in the IAM
knowledge doc.

** Notes

- Screens are designed for the web, not cloned from ores.qt. Follow
  [[file:../../../../../knowledge/ui/ui_design_principles.org][UI design principles]] and [[file:../../../../../knowledge/ui/ux_language.org][UX language]].
- Every workflow runs server-side. Web, shell and Qt are thin callers
  of the same request. Build on [[file:../../../../../knowledge/architecture/internal_actor_impersonation.org][internal actor impersonation]], as
  the Acme provisioning does. No SQL shortcuts.
- Seed profile, not source: profiles are data, not code branches.
- Every new data type is generated with ores.codegen.
- Grilling tasks: use the grilling and domain-modeling skills.
  Research tasks: use the research skill.
- Legacy reference: ores.qt SystemProvisionerWizard,
  TenantProvisioningWizard, PartyProvisioningWizard and
  TenantOnboardingWizard; ores.shell =provision tenant=.

** Not yet specified

- Progress and failure screens: retry from a failed step, discard tenant.
- Re-provisioning or extending an existing tenant.
- How ores.web receives streamed progress events (the Acme response
  returns all steps at the end today).

* Decisions

- [[id:94C3AE99-8642-4418-982D-92C5FD805CCB][Decide the seed profile contract]]: every workflow is an =ores.workflow=
  instance; system bootstrap makes the admin only; profiles are data
  over a fixed step-kind catalogue; two profiles (Empty operational,
  ACME demo); new =party_essentials= bundle; resume on failure; who
  runs what is fixed.
- [[id:DDCB8562-405D-4D16-8C82-0144CBAB3612][Decide the bootstrap workflow catalogue]]: three workflows, three
  journeys (first run, new tenant, new party) built from shared steps,
  journey state in =ores.workflow=, journeys in web and shell,
  onboarding is first sign-in only, automatic handoff sign-in.
- [[id:7C655052-D82F-485A-A506-6F0C496546C6][Prototype the new tenant journey]]: variant A, a stepper page with a
  flat step rail; profiles may prefill tenant details (ACME does); a
  shared password field for the whole app.
- Every deployment is multi-tenant; "single-tenant" is just one tenant.
  First run does not ask.
- ACME's tenant admin reuses the creating super admin's password: the
  provision request carries a flag and the server copies the hash, so
  every journey behaves the same and asks for nothing. ACME forces no
  password change at first sign-in (a profile flag); Operational does.
  ACME's details stay hidden behind "Change settings".
- [[id:DA4BE50C-B2EC-4C6D-8DAA-9EB06D33B003][Prototype the first run journey]]: welcome screen, then one flat step
  rail from super admin to first sign-in; ACME asks for nothing in any
  journey; journeys are ordered step definitions rendered by one page.
- [[id:719CA9CC-14C8-4F56-9700-E60DC1F85245][Formalise the tenant lifecycle glossary]]: System bootstrap, Provision,
  Onboard and Seed profile are defined in the IAM knowledge doc's
  Tenant lifecycle section.
- Contract only: this map decides the server-side contract. Building
  the rework is a later story.
- System bootstrap is open to any caller for now.
- [[id:3A907A86-1AB7-4A8C-97FF-377795226941][Inventory client-side provisioning orchestration]]: GLEIF/synthetic
  tenant and party provisioning run client-side in shell and Qt; only
  Acme runs server-side, and its code must become profile data to host
  the others. Progress is not streamed yet.
- [[id:51075CB4-C21B-4D3E-84D9-708D49DCBD41][Define minimum data for an operational tenant]]: =base= bundle plus a
  counterparty size plus activated, onboarded parties. The party bundle
  plan seeds test and synthetic data, so it is demo-only.

* Out of scope

- ORE data import: day-to-day data loading, not bootstrap. Bundle
  publish of essential data (e.g. counterparties) stays in scope.
- Building the server-side provisioning rework: a later story.
- The Synthetic seed profile: dropped; ACME holds all test data.
- Localhost-only access until system bootstrap completes: a future
  hardening.
