* Goal

A person can see which public providers are in the system, whether their data is arriving, and the fixings themselves, and can act on a provider without a shell.

* Acceptance

- A screen lists each public provider: its name, kind, terms state, the items it serves, the last fixing received and its time, and the adapter's health.
- A provider's page shows its fixings over a window, as a table and a chart, for each item.
- A pair covered by several providers shows each provider's fixing side by side.
- A system administrator can pause and resume a provider and start a backfill of a date range; each action is audited.
- The screen follows the app's existing patterns, and a harness test drives it live.

* Plan

The user asked to stop at a checkpoint: the provider data is in the system and
a person can see it. So this task delivers the read side and the one write that
the data needs, the acceptance of a provider's terms. The other actions wait
for the review at the checkpoint (see Notes).

1. Make =market_fixing.series_id= filterable, so that one read takes the
   fixings of a few series and not the whole hypertable.
2. Add three BFF routes in =official.ts=:
   - =GET /api/marketdata/official= reads each provider that has a terms page,
     with its sources and its fixing series. The series are parsed from their
     item.
   - =GET /api/marketdata/official/fixings?series== reads the fixings of at most
     12 series, sorted by date.
   - =POST /api/marketdata/official/:code/accept-terms= calls the server-side
     acceptance.
3. Add the Official rates screen under Market data. It has three panels:
   - the providers, with their terms state and an Accept terms button for a
     person who holds =marketdata::providers:accept_terms=;
   - one provider's series, as a chart and a table of the latest fixings;
   - one pair from every provider, as published, inverted or crossed through
     the provider's base.

* Notes

Deferred until the checkpoint review:

- Pause and resume a provider, and start a backfill of a date range. Each
  action is audited.
- Delete a provider's fixings. When a provider's new terms withdraw permission
  to store, a system administrator deletes that provider's fixings from the
  durable table, and the deletion records who did it. The design is in
  [[id:F4BBEF34-D84C-4AE6-A3AA-DC47C3EE06EE][Public sources publish daily fixings through an adapter]].
- The adapter's health and the time of the last fixing in the provider list.
  The adapter reports them in its INGEST STATUS, but no read carries them to
  the web yet.
- A harness test that drives the screen live.
- A date bound on the fixings read. Today 12 series grow by about 260 rows each a
  year; the window read is task T6.

A crossed pair is shown as derived. The ECB's terms count a computed rate as a
change to its data, so the screen names the route of every value.

* Result

Delivered to the checkpoint the user asked for, and signed off. The Official rates
screen under Market data lists the four providers with their terms state, draws
one provider's fixings, and compares one pair across every provider, as
published, inverted or crossed. A system administrator accepts a provider's
terms at the version the screen showed; the service refuses a version that
changed since. Fixings are read by series through a new =series_id= filter.
Route tests, a render test, pair arithmetic tests and handler tests over NATS
cover it. The PR also links =ores.trading.service.tests= to the refdata core
repositories, which main's full build needed.

Pause, resume, backfill, deleting fixings, the adapter's health on the screen,
a date bound on the read, and a harness test stay deferred (see Notes).
