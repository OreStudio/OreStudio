* Goal

A market-state file is kept where a large blob belongs, and the row keeps what
makes it findable.

The payload column holds a compressed cube as base64 text. That adds a third to
the compressed size and puts the bytes in the database, which is the wrong place
for a grid that stores many runs. The row should keep the index, the size, the
digest and a storage key; the compressed file should live in the object store
and be fetched only by a reader that needs the values.

* Acceptance

- =ores_marketdata_market_state_payloads_tbl= carries a storage key and no
  payload column.
- The writer compresses the file, writes it to the object store, and inserts the
  row with the key, the compressed size and the digest.
- A read of the index does not fetch the object; a read of the values fetches it.
- The row's key, index and digest are the same facts as today, so a reader that
  only looks at the index is unaffected.
- The round trip is proved against a checked-in sample: store, read the index,
  read the values, decompress, compare.

* Plan

The object key follows the platform grammar: =marketdata/state/<run>/<family>.gz=.
The index, the digest and the size stay in the row because they are what a reader
filters on; the file itself is one object.

This is the change that lets the store hold a grid's worth of runs: rows stay
small and indexable, and the bytes are paid for only when they are read.
