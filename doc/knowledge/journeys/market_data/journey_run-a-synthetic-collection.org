This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A trader or market data operator starts and stops a named synthetic collection, and reads what it owns, what it covers and what is running before the start request is sent.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want this collection generating the market data my desk needs, and I want to
know what it spans before I start it." The journey is done when the collection's
feeds are running and the screen reads back which feeds started, which were
already running, and which were skipped; and, at the other end, when the
matching stop has left the subtree stopped. Synthetic market data is authored
and run by =ores.synthetic=, and a running feed writes observations that the
platform reads at once. Nothing in this journey is a candidate awaiting a
publish.

* Actor and trigger

The actor is a trader or a market data operator who holds the synthetic
market-data role for a party. The trigger is a session that needs live generated
market data: a demo, a test of a pricing run against a known curve shape, or a
desk that wants a currency covered that the live feed does not. The journey
starts at the collections list and ends when the person leaves it with the
collection running, or stopped, and a report of what the request changed. The
actor keeps a second journey for authoring the feeds a collection owns; this one
begins after they exist.

* Steps

1. *Find the collection.* The person opens *Market data*, then *Synthetic*, then
   *Collections*. The system lists the party's collections: the name and version,
   the description, the enabled flag, the feed count split into FX and IR, the
   asset classes, the dataset of origin, and who changed it and when.
2. *Open the collection.* The person selects a row and the system shows the
   collection: the name, the description and the enabled flag, then read-only
   provenance (dataset, version, modified by, performed by, recorded at, change
   reason), then the feeds it owns and its version history.
3. *Read what the collection owns.* The system shows one row per feed with its
   source name, its output series' oresmd URI, its process, its auto-start flag
   and its running state. The FX rows and the IR rows are listed apart. A feed is
   identified by its source name, which mirrors the namespace path.
4. *Check the coverage.* Before starting, the person reads what a start would
   span: the asset class by instrument type with the feed count per cell, the
   currencies covered, and every gap the collection has. An empty cell is a gap,
   not a zero.
5. *Check the contributors.* The person chooses *Validate Vintage*. The system
   checks each contributor against the market it must read: for an FX feed, the
   availability of the vintage it is grounded in; for an IR curve, the local
   binding-collision rule; a fixed-price feed needs neither. The summary says how
   many items pass or do not need validation.
6. *Start the collection.* The person chooses *Start*. The system sends one
   folder-scoped request naming the collection's folder; the server resolves the
   subtree and starts every feed beneath it, of every asset class, in one round
   trip. A selected feed leaf, or a selection that mixes a leaf with a non-leaf,
   uses the per-feed request instead. The request is refused if a contributor
   fails a check, and nothing is started.
7. *Read the report.* The system answers with the count started, the count
   already running and the count skipped, broken down by kind. The screen says
   what the request did and re-reads the running set, so the tree and the list
   now read a mix: running, stopped, or partial with its count.
8. *Stop the collection.* When the data is no longer needed the person chooses
   *Stop*. The same folder-scoped request stops the subtree, and the answer
   reports how many feeds stopped. A collection left enabled but stopped is a
   normal resting state.

Step 6 is one request for the whole collection, not one per feed: the client does
not walk the tree. The counts it returns are the only report of the fan-out, and
the skipped items are not named; see /What is missing/.

stop sit at the bottom with the dispatch they send, so the person reads the set
above the act.

The collection owns its FX and IR feeds as one-to-many children. The tree rows
the screen draws are not parsed out of a source name: they are =folder= rows,
and the collection node links back to its =market_data_generation_config=. A
running feed writes =market_observation= rows under the series' oresmd URI; that
write is the market-data service's, not this journey's.

=feed_configs.list= answers with the source names of the currently running
feeds, of every kind, and takes no filter; the screen joins that set to the
collection's own feed rows to draw a state per row. Starting a feed is keyed by
the feed config's own =config_id=, and the folder request is keyed by the
collection folder's =folder_id=, resolved server-side over the whole subtree.

* What is missing

1. *The coverage read is four lists and a join.* No subject answers "what does
   this collection span". The screen lists the FX feeds, the IR feeds, the
   template entries and the series, then counts the cells itself. The candidate
   is a coverage read scoped to a collection. Until then the screen joins four
   lists and says a cell it cannot fill is unknown.
2. *The running set is global, not scoped.* =feed_configs.list= returns every
   running source name the caller may see, with no collection or folder filter,
   as a list of strings. The screen cannot ask for one node's running set, and it
   cannot tell a stopped feed from one whose producer has died. The candidate is
   a scoped read carrying a per-feed state. Until then the screen reads the whole
   set and matches on source name.
3. *A skipped feed is a count, not a name.* The folder start answers with started,
   already running and skipped, aggregated and by kind, and with no per-feed
   detail. A person cannot see which feed was skipped or why, so a partial start
   is not actionable from the screen. The candidate is a report naming each
   skipped feed and its reason. Until then the screen prints the counts and says
   the detail is not on the wire.
4. *The folder handle is a UUID on the wire.* The request names the node by
   =folder_id=, not by a path; the shell resolves a codename to that id itself,
   but a web client carries the id it read from the list. The candidate is a
   folder path the server resolves. Until then the screen keeps the id it read.
5. *A start can collide and the client cannot predict it.* The Uniform Demo theme
   leaves its IR curves at auto-start false because they meet Realistic 2026 on
   currency and index family, and an IR contributor is refused on a binding
   collision. Nothing on the screen states the rule before the check runs. The
   candidate is the collision shown against the row. Until then the person reads
   the check's outcome only.
6. *No web screen exists.* No web page or HTTP route reaches these subjects as a
   journey. The shell exposes =synthetic start folder= and the matching verbs,
   and the Qt window is gone, so today the journey runs from the shell alone,
   per feed or per folder, with no coverage view. The candidate is a web page
   and a route. Until then the shell is the only surface.
7. *A collection has no schedule.* The feeds start when a person says so, and a
   collection left enabled with nothing running is a normal state, so the enabled
   flag and the running set are read together and mean different things. The
   candidate is a stated rule for what enabling does. Until then the screen shows
   both and the person reads them.
