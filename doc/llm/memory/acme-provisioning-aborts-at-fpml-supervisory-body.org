A fresh =compass db recreate -y -k= followed by =bootstrap setup ... --profile
acme_demo= runs to completion. Verified on 2026-10-07 against a recreated
database and a rebuilt tree:

Both ORE packages (1.8.16.0-4-g3b62ba248 and 1.8.17.0) publish under the
system tenant. =attach_photos= runs, so a change carried by that step *can* be
verified by a live bring-up again; the earlier guidance to verify it by its
seed and suite instead no longer applies.

*Why the old failure is gone:* the FPML publish wanted an
=FPML_SUPERVISORY_BODY= coding scheme the target tenant did not have, because
=fpml.coding_schemes= is deliberately not a bundle member. Whatever fixed that
landed before 2026-10-07.

*How to apply:* the bring-up is a usable end-to-end check again. It takes a few
minutes, because it drives a workflow run through eight steps.

*What bit us next, and what to check after a subject rename.* The bring-up is
the only thing that exercises the *whole* fan-out of a subject, so it is where
a rename breaks. The subject migration of 2026-10-07 left three kinds of
staleness that the conformance gate did **not** see, because the gate reads
only the =:subject:= a model declares:

- the =target_subject= values seeded into =dq_artefact_types_populate.sql=,
  50 of them, which nothing derives from a model;
- the subjects a service subscribes to in its own =registrar.cpp=, which are
  string literals in C++;
- the subject each receiving service parses back into a SQL function name, in
  a =subject_to_fn= helper duplicated per component -- six copies, and
  =ores.dq='s uses its own =ores_dq_<entity>_publish_fn= convention rather
  than =ores_<component>_<operation>_fn=.

After any subject change, run the ACME bring-up and grep for the old subject
string rather than trusting the gate alone.
