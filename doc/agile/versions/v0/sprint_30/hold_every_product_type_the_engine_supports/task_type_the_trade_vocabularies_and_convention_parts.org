* Acceptance

- a family model's parts state their cardinality, and the generated family put refuses a write that breaks it, naming the part
- trade key fields such as product type and call or put are typed vocabularies backed by lookup tables, and the UI offers them from those tables
- each named defect has a test that fails without its fix, or evidence that it was already fixed

* Plan

1. Give the family model's =* Parts= table a =cardinality= column (=one=, =optional=, =one_of=) and a =group= column, and have the loader refuse a model that leaves them out.
2. Generate a =check_part_cardinality= function into each family service, called by put and put_many before the transaction opens, refusing with a new =part_cardinality= outcome that names the part.
3. State the rules the four ORE mappers already enforce at export.
4. Census the trading columns that hold a lookup's vocabulary and do not check it, and census the values ORE's examples use for each vocabulary.
5. Declare a soft foreign key to the lookup on each column whose values the seeded lookup covers, and regenerate.

Lookup tables already exist for option type, long/short and product type (projects/ores.sql/create/trading/), so the vocabulary capture starts by finding the fields that still bypass them.

** The family put could not write a new convention

The test that a valid tenor basis swap is written found that the family put stamped its rows whole. stamp() reaches only a row's own fields, and a convention keeps its tenant and party in its =identity= member, so every family put of a new convention reached the store with the zero party and was refused. The family service now stamps each member that carries a stamped field, as the entity service does.

** What stays free text

- =instrument_underlyings.price_type= is a commodity price basis (=Spot=, =FutureSettlement=), not a bond price type.
- =instrument_option_exercise_fees.type= is an exercise fee kind; it matched the barrier census only by name.
- =instrument_options.payoff_type= and =payoff_type_2=: ORE's payoff set is wider than the seeded lookup, so a key would refuse valid trades. The seed covers every payoff ORE's examples use.
- =equity_outperformance_options.long_short= already has a literal check.
- The trade's own product type is already checked against =ores_trading_product_types_tbl=.

** Out of this task

- No screen edits a trade instrument today, so no UI offers these vocabularies. Every lookup is listable over the wire (=trading.v1.option_types.list= and the rest), which is what a trade editor reads. The editor belongs to the capture [[id:FCF06F0F-1D24-4C70-B143-2C74B85FA999][Offer the trade vocabularies from their lookups in a trade editor]].
- The conventions bundle writes the tenor basis rows through the repositories, not the family put, so the cardinality check does not cover it. Its rows come from ORE documents, whose 142 tenor basis conventions all state exactly one form.

Forty-three trading columns that held a vocabulary as free text now check it against the lookup table, as the FX instruments did.

- A test for each named defect: met. The family put's stamping defect is caught by the one-form test, which failed before the fix.
