* Goal

The harness turns round trip from a claim into a command. It is built once and every per-file-type task adds its type to it.

* Acceptance

- One command imports a file, exports it, and reports whether the two documents are equal, naming the first difference when they are not.
- The harness runs over every file of a type in the vendored corpus and reports a count of files that round trip.
- A new file type is added to the harness without editing the harness itself.

* Plan

1. Read the two rigs that already exist. The binding walker
   (=projects/ores.ore/core/include/ores.ore.core/xml/roundtrip.hpp=) imports and
   exports the generated domain classes and counts documents with one hardcoded
   counter per kind: =trades_mapped=, =currency_files=, =calendar_files=,
   =convention_files=. That is the shape the harness replaces, because a kind is
   data and a new kind must not edit the walker. The credit simulation slice's
   two test files are the entity-level rig the harness generalises, and they
   already do the two things the binding walker cannot: compare the exported
   document with the imported one, and carry an expected value rather than an
   empty vector.
2. Define the seam. A document kind becomes a value: a name, its root element,
   the corpus glob, an import function from a file to the entities and an export
   function back, and a comparison. The walker owns the directory walk, the
   counts, the timings and the report of the first difference; a kind owns its
   mapper pair and nothing else.
3. Register the kinds that already have a mapper, so the harness earns its place
   on its first run instead of being scaffolding for later work. Credit
   simulation is the first, and it is the register-through-the-harness proof.
4. Report a difference, not a count. A file that imports and exports without
   throwing has not round tripped: it has only not failed. The harness compares
   the two documents as parsed documents and names the first path that differs,
   which is the assertion the credit simulation label finding showed was missing.
5. Take the kinds in ascending corpus size, so a harness defect surfaces on 4
   files rather than on the run document's 416. SIMM calibration is the smallest
   and needs its binding generated first, which is why it is not the first kind
   registered.

* Notes

- The harness is not a new test framework. It is a registry plus a walker, and
  the walker is the same idea as the binding one, with the per-kind counters
  lifted into the registry so that adding a kind is a registration rather than
  an edit.
- The binding walker stays. It proves the generated bindings read and write a
  document; the harness proves the entities do. Where a kind has both, both run:
  a binding defect and a mapper defect are different defects and a single test
  cannot attribute them.
