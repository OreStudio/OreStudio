* Goal

The server reads every request body whole, into one buffer per connection, with a
single limit of 256 MiB for every route: small enough to be useless as a bound,
and applied before the route is known. So a JSON route accepts a 256 MiB body, a
large upload costs its own size in resident memory, and a body past the limit
closes the connection with no response at all.

After this story the route decides the limit. The headers are read on their own,
the route the request addresses is resolved, and the body is read under that
route's limit: a small default for a JSON call, an explicit large one for the
storage upload, and the server's ceiling over both. A body past the limit is
answered 413 with a reason instead of a silent close.

* Acceptance

- The limit is decided by the route, after the headers are read and before the
  body is held.
- A body past the limit is answered 413 with a reason, not closed.
- The refusal closes the connection, because the body was not read and cannot be
  framed.
- A route that takes an upload states its own limit, and the server's ceiling
  still caps it. The storage upload route keeps working at its current size.
- A client that sends =Expect: 100-continue= is told to proceed before it sends.
- The existing suites stay green.

* Decisions

- The limit lives on the route, not on the server alone, because only the route
  knows whether its body is a JSON document or an engine package.
- The default is 1 MiB, which is far above any JSON call the gateway serves and
  far below anything worth attacking with.
- Reading the headers first was chosen over a streaming parser because it is the
  same change that streaming will need in A3, and it lets the refusal happen
  before a byte of body is held.
