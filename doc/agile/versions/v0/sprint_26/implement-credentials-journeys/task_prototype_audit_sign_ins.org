* Goal

Answer one question with a throwaway prototype: how does a tenant
administrator read who is signed in, what they are doing, and who is failing
to get in?

[[id:22AC8DD8-A440-4330-9992-47A5E9985473][Audit sign-ins]] carries one
screen and one action. It is an event log, not a versioned entity, so it
carries no versions, no diff and no revert, and *Refresh* is the only action.
The prototype decides how the filters, the active sessions, the session
activity and the failed attempts share one screen, and how the screen states
the data it cannot read.

* Notes

The journey's gaps, from the * What is missing section of
[[id:22AC8DD8-A440-4330-9992-47A5E9985473][Audit sign-ins]]. The screen states
each one, and the prototype decides how.

1. *No subject for the auth events.* =ores_iam_auth_events_tbl= holds one row
   per login, failure, logout and token refresh, with continuous aggregates and
   no subject.
2. *No subject for the session statistics.* The three continuous aggregates
   exist with no subject.
3. *No operation to end another account's session.* The repository method
   =session_repository::end_session= writes the end time, and only the logout
   path calls it for the caller's own session.
4. *The activity and the audit data have no read path in the browser.* The
   session samples have neither a working subject nor a BFF route. Until the
   subjects exist, the session-activity panel must state that the data is not
   available.

Three of the reads are =partial=: =iam.v1.sessions.list= takes no account
filter, and =iam.v1.sessions.active= and =iam.v1.sessions.samples= exist and
reply with success and no rows. The BFF answers the active sessions from the
session repository, so that panel works in the browser today while the NATS
path does not.
