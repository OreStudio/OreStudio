* Goal

describe_product serves every product's schema: its fields, with type, list or scalar, accepted values and description, and its forms, with the script and engine of each; a script-only product's fields are its script's inputs, and annotations are held as data.

* Acceptance

- every product of the catalogue and every script with no element of its own has a schema
- labels, coded values, defaults and descriptions are annotations held as data
- each form states the script it runs and the engine its product tag prices with
- a test fails when a product has no schema
- ores.http serves a product's schema and the list of products as JSON routes over the trading service's operation
- the BFF serves the same under /api/trading/products, with a unit test of each route

* Plan

Agreed with the user on 2026-11-22:

- A product's schema is static data for an ORE release. It is extracted at
  build time from the XSD bindings of =ores.ore.core=, which are the one reading
  of ORE's schemas, and stored in Postgres in the shape trading reads, as a DQ
  dataset of the Open Source Risk Engine catalogue published into the system
  tenant, as the script library is. Nothing asks for a schema at request time.
- Every row is keyed by the ORE release it was extracted from, =engine_version=,
  as =reporting_ore_file_versions= is, so that the store can hold the schemas of
  more than one release.
- Trading owns the schema and validates against it: it merges the native
  element's fields with a script's inputs, the annotations and the forms, which
  are trading's data.
- Each form states its product tag (scripted) or ORE pricing engine type
  (native). =describe_product= takes an optional pricing configuration and, when
  given one, states the model and engine it assigns, read from analytics over
  the bus. The cost of a form is left to a later task.

The shape is a type graph, as the XSD is: a product names its element's root
type, and a type lists its fields, each a scalar with its kind, multiplicity,
whether it is required and the values it accepts, or a nested type. A type
shared by many products, such as a leg, is stored once per release.

The catalogue states each trade type's element. ORE's example portfolios show
115 of the 121 types under the element named after the type with =Data=, and six
otherwise (=CommoditySwap= under =SwapData=, =SyntheticCDO= under =CdoData=,
=PerformanceOption_01= under =PerformanceOption01Data=, and =InflationSwap= and
=EquitySwap= under both their own and =SwapData=); 43 types appear in no
example, so their element is read from ORE's source.

Four PRs, each ending in a check:

1. The native schema dataset: the catalogue's element column; the schema
   entities keyed by =engine_version=, with their staging tables; the extractor
   over the bindings, which writes the dataset's populate files; the publish
   function and the =world= bundle membership; and the build job's check that
   the extractor reproduces the committed files. A test fails when a native
   product of the catalogue has no schema.
2. The scripted schemas and the annotations: a script-only product's fields are
   its script's inputs; labels, coded values, defaults and descriptions are an
   annotations dataset keyed by =engine_version=.
3. =describe_product= and =list_products= in the trading service: the fields and
   the forms, each form with its script or engine type, and the model and engine
   of a stated pricing configuration.
4. The ores.http routes and the BFF routes under =/api/trading/products=, with a
   test of each.
