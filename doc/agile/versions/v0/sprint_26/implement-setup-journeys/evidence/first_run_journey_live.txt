Live proof of the first run journey, recorded 2026-09-28 on the
eager_maxwell environment at branch feature/build-the-first-run-journey
(commit 3523c3ec09), on a fresh installation: `compass services stop`,
the JetStream store removed, `compass db recreate -y -k`, and the fleet
started again. The browser bundle and the BFF were built from the same
commit before the fleet started, so the deployment served this branch.

The installation was empty: `/api/bootstrap` answered
`{"isInBootstrapMode":true,"message":""}` and the fleet held 25 running
units.

--- 1. the first screen, in a real browser ---

Google Chrome, headless, against http://127.0.0.1:21402/. The rendered
text, with the rail first:

  Welcome to ORE Studio  2 Create the administrator  3 Choose a starting
  point  4 Describe the tenant  5 Review  6 Provisioning  7 Hand off
  8 First sign-in  9 Ready

  Welcome to ORE Studio
  This installation is empty. Set it up in three stages.

  [Create the administrator] The account that owns this installation.
  [Create the first tenant] Choose a starting point and provision the tenant.
  [Sign in] The tenant administrator sets a password of their own.

  Back   Get started

The rail is the journey: nine steps on one page, the welcome screen in
front of them, and no sign-in form, because the installation has nobody
to sign in as.

   Corrected on 2026-09-29, after the walk was read again: the failure is
   the walk's input, not the deployment's data. The LEI above is mistyped

   Publishing the same dataset for the same tenant with the correct code,
   inside a transaction that was rolled back, inserts 668 parties, 668
   identifiers and 57 BIC identifiers. The import reads what the
   deployment holds, and the card works. The capture that recorded a data
   gap has been withdrawn; what the walk did find is that the form takes
   any string, and that a code the deployment does not hold arrives as the
   publication's SQL rather than as a sentence about the entity.

--- 3. the same journey through the ACME demo card ---

ACME asks for nothing, reuses the creating administrator's password, and
orders six steps. Its run was followed to rest:

  HTTP 200 status=in_progress current=2 steps: publish_bundle=completed,
    import_lei_hierarchy=completed, provision_party=in_progress
  HTTP 200 status=in_progress current=4 steps: ..., provision_party=completed,
    load_staff=completed, attach_photos=in_progress
  HTTP 200 status=in_progress current=5 steps: ..., attach_photos=completed,
    start_market_feeds=in_progress
  HTTP 200 status=completed current=6 steps: publish_bundle=completed,
    import_lei_hierarchy=completed, provision_party=completed,
    load_staff=completed, attach_photos=completed,
    start_market_feeds=completed, complete_provisioning=completed_with_warnings

The last step completed with warnings, which is a state the rail shows
rather than a failure it hides.

--- 4. what the two runs left ---

   id                                  |       code       |    status
---------------------------------------+------------------+---------------
 d8f4e19f-3156-4483-87d6-9a0c12b27015 | acme_corporation | active

The ACME tenant is active, because every step it ordered completed. The
Operational tenant is still bootstrapping, because its run stopped on the
failed LEI import: a tenant left half provisioned is visible as exactly
that, and the journey's retry is the action that resumes it.

    profile          |    state    | current step | steps
---------------------+-------------+--------------+-------
 empty_operational   | failed      |            1 |     4
 empty_operational   | compensated |            2 |     3

The runs themselves rest in failed and compensated, which is the
definition's own policy: provisioning stops on a failed step rather than
rolling back the work that completed.
