* Goal

The installation owns a class of data the schema does not name: the facts about the deployment itself. This story names it, gives it the policy shape it wants, and moves the Operations reads onto it, so a read of the fleet is honest rather than a workaround. It adds no security exception and no tenant parameter.

* Acceptance

- The codegen can express installation-scoped data, so a model declares its owner instead of hand-writing a policy.
- The samples, the roster, the logs, the bus and the versions carry the installation's policy shape and are read whole by a session the permission admits.
- The Operations grid reads the fleet whole under compute::grid_samples:read, and every claim it makes about the work counts is true.
- The grid's global view, including which tenant is using what, comes from what the installation observed about its own operation, with no policy exception and no cross-tenant read.

* Decisions

- *The installation records what it did; it does not read across tenants.* A
  super administrator needs to know which tenant is using the grid. The work
  that answers it, the batches, workunits, results, reports and schedules, is
  tenant-owned, so reading it across tenants is the widening the guard exists
  to stop. The answer is not a read at all: the compute service is already
  inside each tenant when it dispatches that tenant's work and when it takes
  the result back, so it records what it did as an installation fact. The
  grid's global view is a ledger the installation keeps about its own
  operation, not a view over its tenants' tables.
- *A usage row carries the operation, not the tenant's content.* The tenant,
  the host, the app version, the duration, the cores and the outcome. It does
  not carry the input bundle, the config, the output, the stderr or the report
  definition. Those stay tenant-owned, and a row that copied them would be a
  cross-tenant leak under another name.
- *The grid's global view needs no exception from the tenancy audit.* This
  supersedes the earlier framing of the global view as a cross-tenant
  aggregate, which was wrong. What the installation observes about itself is
  installation data from the moment it is written, so the guard never applies.
- *The policy flag is named for the rows it admits, not the session it
  serves.* =:rls_own_or_system_tenant_rows:= states both comparisons on the
  =tenant_id= side -- the session's own tenant's rows, or the system
  tenant's -- so no reader can mistake it for
  =:rls_system_tenant_visible:=, which names the session and emits the
  guarded =current = system= widening. Shared reference and installation
  data want the same rows and the same write rule, so one flag serves both,
  and the two flags are mutually exclusive.
