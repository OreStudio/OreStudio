* Goal

A curve configuration is drawn like every other configuration that comes off an ORE document. Its leaves are documented once, in the ORE parameter contract, keyed by curveconfig.xsd and XPath; its sections and entry elements come from data; and a person reads and changes a curve's leaves with the shared switch, documentation panel, value in force and control that a product parameter, an engine run setting and a convention term already use. Nothing about a curve section is restated in code.

* Acceptance

- Every leaf of curveconfig.xsd that ORE reads has a documentation entry in the ORE parameter contract, keyed by its schema and XPath, with a value set, or a recorded reason it is not documented.
- The curve sections and their entry elements are read from the curve_section data, so no screen holds a table that names them.
- A curve definition's leaves are drawn with the shared leaf parts: the Simple and Advanced switch, the documentation panel, the value in force and the control its value set gives.
- The curve configuration page follows the configuration screen standard: Details, one tab per section in the declared order, Used by and History, with a curve entry drawn as a collection row.
- A write whose value lies outside its leaf's value set is refused on the server, so every client gets the same answer.

* Decisions

- *A save echoes the stored document and writes only the families it touched*,
  decided 2026-10-28. A curve configuration is thirty-four families and the
  screen draws one entry at a time, so a document assembled from the screen would
  drop the rows it never read. The route reads the document, changes the named
  leaves and writes back those families, so a change to one curve leaves the
  other families at their versions. This also moved the edit (task CA40C9B0)
  ahead of the nested drawing (task 894F3A64): the echo is safe without it, and
  the contract documents 22 of the forty-odd leaves a segment holds.
- *A curve configuration's leaf is a /parameter/*, decided 2026-10-26. Three
  words the leaf standard already spends do not serve this kind, and a fourth
  was rejected when the convention leaf was named.

  | Candidate   | Why it was not chosen |
  |-------------+-----------------------|
  | /setting/   | Reserved to the engine run settings, the ORE =Setup= block, by [[id:E69C008D-7092-4855-98EC-47A75F422F61][Configuration screen standard]]: "The word is not used for a parameter of any other configuration." |
  | /term/      | The conventions' word, and it collides with *term structure*, which is exactly what =curveconfig.xml= configures. |
  | /field/     | Rejected when the convention leaf was named: "field is the record standard's word for any record and says nothing about ORE." |
  | /entry/     | Already the row: =curve_definition= is "one curve entry", and =curve_section.entry_element= names the entry element. |
  | /option/    | Already a thing inside a volatility config: the call or the put. |
  | /attribute/ | A leaf is an element *or* an attribute, so this word cannot name both. |

  /Parameter/ wins because the code already calls it that: the contract table is
  =ore_parameter=, its docstring says "A parameter an ORE document accepts ... a
  row documents one leaf of one ORE document", the configuration standard
  defines /Parameter/ as "one leaf of an ORE document", and the generator that
  writes convention terms as contract rows is =convention_parameter_rows.py=.

  The cost is one amendment. The [[id:852207A6-6785-43E6-A5D6-2D5C2C374101][ORE element and leaf screen standard]]
  defines /Parameter/ narrowly, as "a leaf of a product or of the document's
  global parameters". The first task widens it to cover a curve configuration.
  No screen prints the word for this kind yet, so the amendment changes a
  definition, not a screen.

- *The element type is the ORE entry element*, read from =curve_section=,
  decided 2026-10-26. That table already holds the container and the element its
  entries use: =YieldCurves= holds =YieldCurve=, =Correlations= holds
  =Correlation=. Its own model records nineteen sections across the
  seventy-six =curveconfig.xml= documents ORE ships; that count is the entity's
  claim, not a measurement this story has taken, and the extractor re-measures
  it in the first task. This is the
  shape the convention kind already has — a declaration in data that a screen
  reads and does not restate. =curve_section= is to this story what
  =convention_kind= was to [[id:3D6ACCDB-6209-47BC-86F5-864A65C6389B][Draw every ORE leaf the same way]].

- *The discriminator is not modelled yet, and the documentation does not wait
  for it.* =CurveType= decides which leaves a yield curve may carry, and refdata
  holds no curve type today: =yield_curve_config= is one flat row of the union.
  The contract keys a leaf by its schema and XPath, and the XPath does not
  depend on the discriminator, so the documentation proceeds without it.
  Whether the discriminator joins the key as the *element pair* that OL-DOC-05
  allows belongs to the task that moves the metadata into data.

- *This story does not own the structural refactor of the document.* The
  =curve_configuration_document= is still one aggregate carrying 34 families,
  and that is [[id:6E7E20DA-D08B-410B-B1B8-A571C40F83CF][Apply the same shape to the curve configuration document]].
  The two tasks meet at the same document and do not block each other, because
  the contract is keyed by schema and XPath and not by the aggregate.

- *The column a leaf travels in is generated from the projection*, decided
  2026-10-27. A curve entry is spread over =curve_definition= and one family
  table, and the projection that reads and writes =curveconfig.xml= is the only
  code that knows which column holds which element. The screen reads that fact
  from =bff/src/curve-sections.generated.ts=, which
  =generate_curve_section_parameters.py= writes out of the projection and checks
  against =curveconfig.xsd=: 250 columns of 22 tables across the 19 sections.
  The alternative, deriving the column from the element's name, is wrong for
  =CurveId= (a =curve_id=) and for =YieldCurveDayCounter= (a =day_counter=), and
  a hand-written table would drift from the projection in silence. The guard task
  emits the same map for the trigger, so one source serves both.

- *The curve page reads before it writes*, decided 2026-10-27. A curve
  configuration is one document of thirty-four families and a save writes it
  whole, so a page that drew the leaves of one section and saved would drop every
  row it does not draw. No guard covers the curve tables yet either. The page
  therefore reads, and two tasks carry the rest:
  [[id:894F3A64-F564-44B2-A6F1-AB00FF30A6B9][the nested collections]] and
  [[id:CA40C9B0-01FB-4B3E-B0CE-348313A6BB04][the write]], which waits for the
  guard so that no client can store a value outside its leaf's set.

* Out of scope

- Changing =curveconfig.xml=, the ORE XSD, or the generated ORE model.
- The structural split of the document by family, which the refactor task owns.
- Renaming a table, a configuration type code or an API route. The
  documentation and the screen words change; the model does not.
