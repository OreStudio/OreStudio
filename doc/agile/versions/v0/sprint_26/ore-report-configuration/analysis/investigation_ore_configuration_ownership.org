#+title: Investigation: who owns the ORE configuration
#+description: Which component owns each ORE configuration document today, which parts no component models, and the rule that decides whether a report definition owns an entity or references it.
#+type: investigation
#+level: s1
#+filetags: :ore-report-configuration:sprint_26:v0:
#+created: 2026-09-27
#+updated: 2026-09-27

* Summary

Ten of the seventeen configuration documents belong to a component that already
models them, wholly or partly. Seven belong to nobody: simulation, SIMM
calibration, sensitivity, stress, historical return, Basel traffic light, credit
simulation, and the run document itself.

The rule this produces: a report definition *owns* the configuration of its own
run, and *references* the configuration that is shared. Putting conventions,
currencies or curves into reporting would duplicate them; leaving simulation and
sensitivity unmodelled satisfies nobody.

* Detail

The =ores.ore= component is not the owner of any of them, even though it holds
the XML bindings for all of them. It is the translator: it reads and writes these
documents. The entities belong to the components that own the concepts.

** The rule

- *Owned* — the reporting domain owns the entity and the report definition has it
  as a child. This is everything in =ore.xml=, and every library that exists only
  to configure an analytic: simulation, sensitivity, stress, SIMM calibration,
  historical return, Basel traffic light, credit simulation.
- *Referenced* — another component owns the entity and the run names it:
  curves, pricing engines, conventions, calendars, currencies, counterparties,
  netting sets, IBOR fallback.
- *Shared* — =ore_types.xsd=, which carries value types and 54 enumerations and
  has no entities of its own.

The distinction is not cosmetic. An owned entity answers "what did this run
run with"; a referenced one answers "what does this organisation use", and the
two change at different rates and for different reasons. The consequence for the
model is that a run must pin the versions of what it references, or its result
is not reproducible.

** Where the analytics configuration should live

Reporting owns the run; =ores.analytics= owns pricing models today. Simulation,
sensitivity, stress and SIMM calibration are analytics configuration rather than
report configuration — a stress library is not a property of one report — so they
could live in =ores.analytics= and be referenced by the run. That is one of the
open decisions on
[[id:061CE0DF-F9DE-4AC7-9536-B2EB6C547531][The target report configuration
model]].
