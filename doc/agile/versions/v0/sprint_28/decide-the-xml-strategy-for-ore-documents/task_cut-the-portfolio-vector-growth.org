* Goal

Reading a portfolio spends 32.70% of its instructions in the trade vector's realloc_append and 19.29% in the trade move constructor (callgrind, import_portfolio_all_ore_example_files_can_be_parsed, 4.03 billion instructions in total, binary built from PR 3565). The generated append_to in xml/generated/portfolio.cpp calls emplace_back with no size hint, so each regrowth moves every trade already read. Cut that cost.

* Notes

Not decided, and the first step is to choose by measurement:

- Reserve a size. The binder does not know the child count ahead, so this needs
  a hint from the scanner or a heuristic reserve on the first append.
- Make the move cheap. The profile shows a large =memset= under the append, so
  default construction of a =trade= may cost as much as the move.
- Change the container for the repeated child, for example to a deque, which
  never moves an element. That changes the generated record type and every
  reader of it.

The same =append_to= template serves every repeated child, so a change there
touches all 13 tables. Prove the drift check and the corpus tests after it.

* Result

The generator now counts the members of each record, records held by value
included. A record with 1,000 or more keeps its repeated children in a
=std::deque=, which never moves an element. Four portfolio records qualify:
=trade=, =component_trade=, =derivative= and =component_sub_trade=. The
widest record that stays a vector has 454 members, so the threshold sits in a
gap of more than 10,000. Only =portfolio.cpp= and =portfolio.hpp= change in
their tables. The other families gain a default template parameter and no other
change.

Reading the portfolio test falls from 4,028,918,281 to 3,070,700,246
instructions, 23.8%. The import function alone falls from 2,910,831,513 to
1,952,347,014, 32.9%, and the binder from 2,310,204,223 to 1,339,979,756,
42.0%. The 340 KB zero fill of each new trade stays, and a throwaway reserve
shows no container could remove it: it reaches 3,027,004,932, within 1.4% of the
deque.

What is left is the shape of =trade=. It holds one member for every instrument
kind, 346,624 bytes, and a trade uses one. The fill is 33% of the test. A fix
changes the record, not the container, so it is a separate task and not started.

A test pins the property: trades keep their address while the document grows.
Run against a plain =std::vector=, the same check fails. I confirmed that with a
separate program, not by building the old tree again.

The benchmark gate asked for a row because the generated headers sit under the
watched path. The XML benchmark measures scanning and the tape, not the binder,
so its numbers did not move.
