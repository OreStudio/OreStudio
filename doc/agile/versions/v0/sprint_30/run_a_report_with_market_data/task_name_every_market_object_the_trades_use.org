* Acceptance

- The run's todaysmarket.xml forwards every interest rate index the portfolio names for which the market data holds a curve, and the curve configuration builds each one.
- No trade of the baseline run fails with 'did not find object' on an index whose curve the market data holds.
- The configuration is derived from the trades and the market data, not hand-listed per party.
- A test fails when a named index with a curve is left out, or one without is added.

* Plan

A prototype came first: a run's package was amended by hand and run on the
vendored ORE 1.8.17.0 (=ore-1.8.17.0-x64-linux=), so each rule was seen to
work before it was coded.

1. A party publishes the curves it bootstraps as =DISCOUNT/RATE/CCY/NAME/TERM=
   factors, and the run's market data carries them. A curve built directly
   from those factors (a =Direct= segment of type =Discount=, read with the
   currency's tenor-based zero convention) forwards the index it is named
   for. Added by hand for GBP-LIBOR-3M, the index stopped failing.
2. A term rate such as =GBP-SONIA-3M= is projected off its overnight index's
   curve. Forwarded by hand on =Yield/GBP/GBP1D=, the trades on it built:
   31 of 416 where 1 had.
3. Both rules run in the package step, on the files it already holds: the
   configuration, the market data and the portfolio. Only what the
   portfolio names is added, so the market stays what the trades use.

The prototype also found that the GBP, USD, JPY and CAD OIS conventions did
not resolve; that became
[[id:BABA997F-305E-4FBC-9756-4CF79A704A50][Export one convention for each index id]].

* Decisions

- *Where:* the package step (=report_package_handler=), through
  =ores::ore::xml::name_forwarding_curves=. It sees the configuration the
  run was authored with, the market data and the portfolio together, so it
  can add exactly what the trades name and the data holds. A seed or a
  provisioning step would hand-list curves, and would not see a curve
  published later.
- *Derived from what the trades name, not from the requirements function.*
  The package step holds the portfolio the ORE projection wrote, which names
  each index as ORE spells it; the requirements are oresmd addresses. Using
  the portfolio avoids a second mapping between the two spellings.
- *Equity, commodity, inflation and credit are not configured here.* No
  quote of those classes exists, so a configuration for them would move the
  failure from "did not find object" to "no quotes". They belong to
  [[id:9EFEAA52-D458-4CCF-A6C6-7C5A6A2EF6DC][Give every generated trade type its market data and pricing engines]],
  which supplies the data and its configuration together.

* Notes

- The live run of 2026-11-17 forwards GBP-LIBOR-3M and USD-LIBOR-1M on their
  published curves, and GBP-SONIA-1M, 3M, 6M, 12M and CAD-CORRA-3M on their
  overnight curves.
- The 73 index failures left name indices no curve is published for:
  GBP-LIBOR-6M, 12M and 1W, EUR-EURIBOR-12M, and single trades on SGD, SAR and
  others. They need a published curve, which the market data task supplies.

* Result

A run now forwards each index its trades name for which the market has a
curve: a published curve, read from its discount factors, or a term rate on
its overnight index's curve. ORE builds 32 of ACCOUK's 416 trades, where it
built none at the story's start, and index failures fell from 148 to 73. The
rest wait on equity, commodity, inflation and credit data.
