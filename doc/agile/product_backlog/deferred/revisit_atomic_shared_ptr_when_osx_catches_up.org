#+title: Revisit std::atomic<std::shared_ptr<T>> once macOS libc++ supports it
#+description: The estate publishes shared_ptr snapshots through ores.platform's atomic_shared_ptr, which is mutex-backed because the macOS CI toolchain (Xcode 16.2 libc++) doesn't implement the C++20 atomic<shared_ptr> specialization for non-trivially-copyable T and fails to compile. Revisit once macOS/libc++ catches up: the switch back to the standard type is then a one-file change in the shim.

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

=ores.platform= carries =concurrency/atomic_shared_ptr.hpp=, a
=shared_ptr= plus a =std::mutex= that publishes an immutable snapshot: a
reader gets one whole object and the object survives a later store.
It stands in for =std::atomic<std::shared_ptr<T>>=, which the macOS CI
toolchain (Xcode 16.2, libc++) fails to compile: the name falls through
to libc++'s generic =atomic<T>= primary template for
non-trivially-copyable =T=, which =static_assert=s trivial copyability --
=shared_ptr= isn't trivially copyable. Linux/clang (libstdc++) accepts
the atomic form fine, implementing the C++20 P0718 =atomic<shared_ptr>=
specialization.

Once macOS's libc++ (or whatever Xcode ships by then) implements that
specialization, switch the shim's implementation to it: it's the more
idiomatic, self-documenting expression of the same snapshot-swap pattern
(cf. =ores.analytics.quant='s use of =immer::atom= for the same need).
Because every caller now names the shim and not the standard type, the
switch is one file, and this capture is the only place that has to
change with it.

* Why

Portability now over idiom now; don't let a toolchain gap force a
permanently less-modern pattern once the gap closes. Low priority --
purely a style/idiom improvement, no functional or performance
difference once macOS support lands (see the mutex-vs-atomic discussion
on [[id:BA82072F-0B2B-48F4-9C22-8D6D39337099][the multi-named-CRM engine task]]: an uncontended mutex around a
shared_ptr copy is not measurably slower than the atomic form on this
workload, since refresh() is rare and the critical section is just a
refcount bump).
