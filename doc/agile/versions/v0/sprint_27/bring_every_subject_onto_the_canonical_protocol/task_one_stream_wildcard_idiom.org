* Goal

One way to state the subjects below a prefix, used at every stream-provisioning and subscription site, so a bare nats_subject constant stops looking like the natural thing to pass.

* Acceptance

- One helper states the subject and its children, and the market data, synthetic, compute wrapper and workflow services all use it
- No site appends a literal =".>"= or a =">"= to a subject, and no helper returns a bare wildcard string
- A test that provisions a stream and then publishes through the ingest loop finds a stream, from an empty JetStream

* Plan

Put the fact where every caller already reaches for it: =ores.nats::client=,
which owns both =make_subject= and =make_stream_name= and therefore the only
place that knows the deployment prefix.

1. =subjects_below(subject)= states the one thing no constant states -- the
   subjects below a base -- and prepends the prefix. A subscription that wants
   the family asks for this instead of appending =">"= by hand.
2. =covering_subjects({subjects})= states what a stream's filter needs: each
   prefixed subject and its wildcard, so a stream cannot be provisioned on the
   bare constant alone.
3. Every stream site passes =covering_subjects=, including the workflow
   service's two leaf subjects: a leaf is the base of an empty family, and one
   idiom is worth two inert filters that make the next subject below them free.
4. The marketdata domain keeps only the *base* constants, with the trailing dot
   gone, and =synthetic_tick_subject_for(source)= builds a producer's subject
   from one. The two wildcard helpers go: the client states that now.

The =marketdata.v1.tick= rename this task also carried landed with the subject
migration.

* Notes

A =nats_subject= constant names one subject. A JetStream stream and a
subscription need the subject *and everything below it*, which is a different
string, and nothing in the tree said so. The four sites spelled it three ways:

| Site | Filter, before | Spelling |
|------+----------------+----------|
| =marketdata/service/app/application.cpp= | =market_tick_wildcard()=, =synthetic_tick_wildcard()= | named helper |
| =synthetic/service/app/application.cpp= | ="synthetic.v1.ops.tick.>"=, ="synthetic.v1.ops.sandbox_tick.>"= | hardcoded literal, the first duplicating the helper above |
| =compute/wrapper/app/application.cpp= | =work_assignment_event::nats_subject + ".>"= | inline concatenation |
| =workflow/service/app/application.cpp= | two exact leaf subjects | no wildcard; nothing publishes below them |

All four now call =nats.covering_subjects(...)=, and the ingest loop subscribes
with =nats_.subjects_below(domain::synthetic_tick_subject)=.

The bare constant sitting beside the wildcard is what made the mistake easy,
and it was not hypothetical: the ingest loop test at
=marketdata/service/tests/app_feed_ingest_loop_tests.cpp= passed the bare
=market_tick::nats_subject= to =ensure_stream=. A stream on a prefix matches
none of its children, so the republish to
=marketdata.v1.ops.market_tick.<tenant>.<party>.<key>= found no stream and
threw =No responders available for request=. Fixed in PR 2735.

That test passed on a developer machine for a reason worth keeping: the service
had provisioned the stream correctly weeks earlier, and =ensure_stream= returns
early when the stream already exists, so the fixture's narrower subject was
never applied. The defect only appears against an empty JetStream, which is what
CI starts from -- and what the hotfix that removed CI must not lose.
