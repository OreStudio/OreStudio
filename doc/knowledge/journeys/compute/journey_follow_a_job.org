This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A signed-in person follows one compute job end to end: its state, the node it ran on, its timings, its inputs and outputs, and where its time went.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want to follow this job from submission to output." The person opens one
batch or one job and reads one screen: the batch it belongs to, the job's state,
the node it ran on, when it was dispatched and when its output arrived, the
input bundle it read and the output archive it wrote. The journey is done when
the person can say where this job is, what it is doing, and what it produced.

* Actor and trigger

The actor is what the rows admit, and the session decides the rows. A member
sees their own job, a tenant administrator sees their tenant's, and the super
administrator sees every job. This is one journey: the activity is the same
"where is this job" over three visible sets, and permissions and row-level
security already describe the sets, so the journey does not split on the actor.

The rows are a tenant's. Workunits, batches and results belong to the tenant
that owns them, so every read here narrows to the session's tenant. A
super administrator who wants another tenant's job reaches it by acting inside
that tenant, not by widening a policy
([[id:5A5D6490-AF64-4AAF-8B3D-48EF3EDAF3D2][Tenant ownership and the
information flow]]).

The trigger is a job the person cares about: a result they are waiting for, a
batch that looks stuck, or a job whose output a report needs. The person opens
the screen from a batch reference, a job id or a result id. The journey ends
when the job's state, its node, its times and its files are all accounted for.

This journey writes nothing. It reads the job's rows, the node registry and the
current samples. It does not cancel, requeue or re-run anything: that is
control, and it is deferred.

* Steps

1. *Find the job.* The person opens the screen and gives a batch reference, a
   job id or a result id, or reads the batch's own list. The system answers with
   the job, its batch and the runs of that job. A batch carries its
   =external_ref= and its =status=, and a job is a =workunit= of that batch.
2. *Read the state.* The system states where the job is. The workunit has no
   status column: a job with no =canonical_result_id= is not done, and one with
   it is. Each run of the job is a =result= with its own =server_state=, which
   is 1 Inactive, 2 Unsent, 4 InProgress or 5 Done, and its own =outcome=, which
   is 1 Success, 3 ClientError or 4 NoReply
   ([[id:1805BAFC-7E43-4D9C-822F-17C3455C6E00][Compute job lifecycle]]).
3. *Read the node.* The system names the node each finished run ran on, from
   the =host_id= the submit recorded, and joins the host's =external_id= and
   =display_name= so the person reads a name and not an id. A run that has not
   finished may show no node yet: the dispatcher creates the result without one
   and the submit binds it
   ([[id:0739BC05-3713-4695-8B7B-04D9DBA1AEE0][ores.compute.host]],
   [[id:4A441171-D5FB-4942-B406-F0B9F7D32B87][ores.compute.result]]).
4. *Read the timings.* The system states when the batch was dispatched, when
   the run's row was written, and when its output was received. The run's
   =recorded_at= is when the dispatcher wrote it and =received_at= is when the
   output arrived, so the two bracket the run.
5. *Read the inputs and outputs.* The system states the input bundle the job
   read, from the workunit's =input_uri= and =config_uri=, and the output
   archive it wrote, from the result's =output_uri=. The person can take either
   away: the input with the shell's download-input command and the output with
   download-output
   ([[id:A6E676BD-E907-4F29-8D55-07174C846AA9][How do I download a compute job
   input from the shell?]]).
6. *Read where the time went.* The system draws one bar for the run, from its
   dispatch to its output, and splits the batch's jobs into one row each, so the
   person sees which jobs overlapped and which waited. Inside the bar the
   system can show only what it stores: the job was queued, then it ran, then
   its output arrived. The phases between those points are not recorded, and
   the waterfall must say so rather than draw a guessed split.
7. *Read the release that ran it.* The system states the workunit's
   =app_version_id= and, through it, the app's =engine_version= and the
   =wrapper_version=. This is the release the job runs: the version of ORE
   behind the work, written on the workunit when the job was stored, so a job
   that behaved differently from its neighbours can be told apart by its build.
   It is also the answer about this job rather than about the machine. The
   wrapper heartbeat carries the wrapper's release and the host, so the build a
   node runs is known; the node sample carries the host and no release. Neither
   names the app version the job pinned, so the job's own =app_version_id= is
   the fact about the work rather than an inference from the machine that
   happened to run it
   ([[id:1E563104-6F89-4858-9395-D869A7E817A6][ores.compute.app_version]]).
8. *Follow the lineage.* The system draws the chain that put this job on the
   grid: the scheduled job, the report definition, the report run, the batch,
   the workunit and the result. The selected job is the highlighted workunit,
   and its siblings in the same batch stay visible beside it, so the person
   reads what this job belongs to and what else the batch carried. The flow
   chart is one column of nodes, top to bottom:

   #+begin_example
   scheduler.job_definition      the job the scheduler fires
     └─ report_definition        scheduler_job_id
          └─ report_instance     definition_id, trigger_run_id
               └─ batch          external_ref = report instance id
                    ├─ workunit   batch_id  ← the selected job
                    │    └─ result   workunit_id, outcome
                    ├─ workunit   batch_id  ← a sibling
                    │    └─ result   workunit_id, outcome
                    └─ workunit   batch_id  ← a sibling
                         └─ result   workunit_id, outcome
   #+end_example

   Every hop is stored except the batch's link to the report run, which is the
   batch's =external_ref= and not a checked relationship; *What is missing*
   states that. A shell-dispatched batch carries an operator string in
   =external_ref= and has no report behind it, and the screen must say so
   rather than draw an empty report.
9. *Compare the job with its neighbours.* The system draws the batch's jobs as
   a timeline, and, when the range holds enough neighbours, a duration
   distribution and a duration by node. The person asks whether this job is
   normal, whether one node is slow, and whether the batch is nearly done.
10. *No such job.* The reference matches nothing, the job belongs to another
    tenant, or the person's rows do not include it. The screen says so and offers
    the way back to the batch list. It does not present the empty answer as a
    job with no state.
11. *Leave, or go on.* A failed run continues in
    [[id:4E3AB7E8-5F4C-458F-B0CF-006731B0DA4A][Diagnose and reproduce a
    failure]], where the error and the node's logs are read. The load the job
    sat in continues in
    [[id:32ECF41B-B27B-4A69-B7F0-A4131F993297][Watch the grid]].

* Screens and wireframes

One screen. The finder bar, the job header, the run table, the timeline, the
lineage chart, the duration charts and the file panel are panels of that screen,
because the person reads them as one answer. The screen is read-only: it creates
nothing, changes nothing and destroys nothing.

The panels are the charts [[id:0169FDD7-9B88-4766-9AE9-93FE87200700][Compute
journeys]] names for following a job:

| Panel | Chart | Answers |
|-------+-------+---------|
| Batch rows | *Job timeline* | What ran when, and what overlapped? |
| Run bar | *Job waterfall* | Where did this job's time go? |
| Distribution | *Duration distribution* | Is this job normal? |
| Node comparison | *Duration by node* | Is one node slow? |
| Lineage | *Job lineage* | What report caused this job, and what ran with it? |

The timeline is the cluster Gantt: one row per job of the batch, a bar per run.
The waterfall is the one job's own bar, split by phase as far as the stored
times allow. The lineage chart is the chain from the scheduled job to the
results, with the selected job's workunit highlighted and its batch siblings
beside it; this screen owns the chart, and
[[id:4E3AB7E8-5F4C-458F-B0CF-006731B0DA4A][Diagnose and reproduce a failure]]
reuses it. The two duration charts compare the job with its neighbours, and
they need a range of finished runs to say anything.

Every list on the screen pages on the server, per the
[[id:2BF7F03F-6BF4-45FF-8E26-4D3B4E2D943D][Record screen standard]]. The batch
rows, the run table and the lineage's workunit list each carry First, Previous,
Next, Last, a page size and Load all, with the page and the page size held in
the address. A new search, a new filter, a new order or a new page size returns
to page one, and Load all is offered only when the server's total is 1000 or
less. No list reads with a fixed large limit, and none pages to the end to show
everything.

* Entities composed

| =workunit= | The job: =batch_id=, =app_version_id=, =input_uri=, =config_uri=, =priority=, =target_redundancy= and =canonical_result_id= | [[id:2A6D37BD-EA76-4BAE-AD20-53E04DD48EFE][ores.compute.workunit]] |
| =result= | One run of the job: =workunit_id=, =host_id=, =server_state=, =outcome=, =output_uri=, =error_message= and =received_at= | [[id:4A441171-D5FB-4942-B406-F0B9F7D32B87][ores.compute.result]] |
| =host= | The node a run ran on: =external_id=, =display_name=, =cpu_count=, =ram_mb= and =gpu_type= | [[id:0739BC05-3713-4695-8B7B-04D9DBA1AEE0][ores.compute.host]] |
| =app_version= | The wrapper and engine build the job used: =wrapper_version= and =engine_version= | [[id:1E563104-6F89-4858-9395-D869A7E817A6][ores.compute.app_version]] |
| =report_definition= | The report whose run submitted the batch: =scheduler_job_id= | [[id:FB4A11C5-07EA-4923-B8AC-65F46EBA517C][ores.reporting.report_definition]] |
| =report_instance= | One run of that definition: =definition_id= and =trigger_run_id= | [[id:9FCCF6C8-9C10-403B-BDA4-C3E28706BD67][ores.reporting.report_instance]] |
| =job_definition= | The scheduled job that fired the run: =job_name= and =schedule_expression= | [[id:BD750888-6B72-48C1-AE74-DDC535705022][ores.scheduler.job_definition]] |
| =node_sample= | A node's work in an interval, for the duration comparison: =tasks_since_last=, =avg_task_duration_ms= and =max_task_duration_ms= | [[id:3F8B2D15-6A47-4C93-B8E1-2F5A9D0C4E76][ores.compute.node_sample]] |

The job's identity is the workunit's id. The runs are the results that carry
that =workunit_id=, and the run that counted is the workunit's
=canonical_result_id=. A job with =target_redundancy= above one has several
runs, and the timeline shows them as one row's bars.

The lineage chain is stored hop by hop. The report definition names its
scheduler job in =scheduler_job_id=, and the report run names its definition in
=definition_id= and the firing in =trigger_run_id=, which is the scheduler job
instance's id. The run the scheduler fired is joined to its definition through
the job's action payload, which names the definition
([[id:D4938956-1A5E-4F67-BCE8-7A951CE957E9][Report definition and schedule]]).
The batch names the report run in its =external_ref=, which the submit handler
writes as the report instance's id, and the workunits name the batch in
=batch_id=. The last two hops are confirmed in
[[id:1805BAFC-7E43-4D9C-822F-17C3455C6E00][Compute job lifecycle]]. The
batch-to-run hop is the one the model does not state as a relationship; see
*What is missing*.

The duration charts read =node_sample=, which describes a node's interval and
not a result. Its =avg_task_duration_ms= and =max_task_duration_ms= are means
and maxima over the tasks of that interval, so a chart built on them compares
nodes rather than following one job. The result itself carries no duration.

Every read above is generated from an entity model and carries its subject. The
workunit read carries a =list_by_batch_id= variant, and the result read carries
a =list_by_workunit_id= variant, so the batch, its jobs and their runs are
three reads that line up by id.

Each of these reads is gated by a permission. The generated handler
authenticates the token, checks the entity's read code
(=compute::batches:read=, =compute::workunits:read= or
=compute::results:read=), and serves the session's tenant, with the row-level
policy doing the narrowing. The dedicated codes the seed holds are the ones the
handlers check.

The browser reads the screen through a hand-written BFF route on the
[[id:6A63AAC7-4869-493A-97E7-55B919874784][journey runtime]]. No route serves
a compute screen yet.

* What is missing

1. *A tenant cannot list its own jobs.* The reads exist, but no journey and no
   screen carry them, so the tenant administrator's question "what is my tenant
   running?" has no answer today. The operations grid screen is the system
   administrator's and shows the installation. This journey is the missing
   screen
   ([[id:77DA388B-FC5A-41AE-B88C-4BF34C82D7C9][A tenant cannot list its own
   jobs]]).
2. *No per-phase times.* The waterfall wants queued, dispatched, downloaded,
   running, uploaded and validated. The service records the run's creation and
   its output's arrival, and nothing between, so the waterfall can draw a bar
   with two ends and no phases. Per-phase timestamps on the result, written by
   the dispatcher and the wrapper, are the missing piece.
3. *No per-result duration.* The result carries no start time and no duration,
   and =node_sample= carries interval means and maxima, not per-result values.
   The duration distribution and duration by node charts therefore compare
   nodes over an interval rather than placing this job in a distribution.
4. *A run in flight may show no node.* On the JetStream path the dispatcher
   creates the result without a =host_id= and the submit binds it at the end,
   so the node is known only when the run is done. The screen must say the node
   is not yet known rather than leave the field blank.
5. *The workunit has no status.* Its state is derived from
   =canonical_result_id=, so a job that has run and failed reads as done, which
   is correct for the grid and surprising for a person. The screen must show
   the run's =outcome= beside it, and acceptance does not filter by outcome
   ([[id:1805BAFC-7E43-4D9C-822F-17C3455C6E00][Compute job lifecycle]]).
6. *A batch's canonical runs may all have failed.* Acceptance moves the batch
   to =closed= even when every canonical result failed, so a closed batch is not
   a successful batch. The screen must state the outcomes and not equate closure
   with success.
7. *The node summary drops the failure fields.* A job's own outcome is on the
   result, so the job view is complete, but the neighbouring node comparison
   cannot state a node's failures
   ([[id:8C1D6E61-3661-49F2-90BB-00ED7C4F113C][The node summary drops the
   failure fields]]).
8. *The batch names its report run in a text field, not a relationship.* The
   submit handler writes the report instance's id into =batch.external_ref=, so
   the hop from a job back to its report is real in the implementation. It is
   not in the model: the compute batch model describes =external_ref= as "the
   originating finance system or project" and states no link to a report run,
   and no read lists batches by =external_ref=. =compute.v1.batches.get=
   resolves one batch once the report run's id is known, and the reverse
   question, "which jobs does this report have", has no subject. A report
   instance id on the batch, or a batch filter on =external_ref=, is the
   missing piece
   ([[id:E9ACBB66-33D0-4EC4-A3B0-E701BDCAD157][ores.compute.batch]]).
9. *The report run names neither its batch nor its workflow instance.*
    =report_instance= carries =definition_id= and =trigger_run_id= and no
    =batch_id=, so the run cannot state what it produced.
    [[id:D4938956-1A5E-4F67-BCE8-7A951CE957E9][Report definition and schedule]]
    places "the workflow instance that ran" on the instance, and the model has
    no such column; the workflow instance id is carried in the run's start
    message and read through =workflow.v1.instances.list=. A run that named its
    batch would let the lineage be read from the report end without the
    =external_ref= convention
    ([[id:9FCCF6C8-9C10-403B-BDA4-C3E28706BD67][ores.reporting.report_instance]]).
10. *The scheduler firing is recorded but not readable by id.* The report run's
    =trigger_run_id= is the scheduler job instance's id, and the only scheduler
    instance read is the paged =scheduler.v1.job-instances.list=; no read
    returns one instance by id, and the =job_instance= table has no generated
    entity model. The lineage reaches the scheduled job through the
    definition's =scheduler_job_id=, which is cleared when the definition is
    suspended or archived, so a run whose definition has since been paused
    loses its live schedule link
    ([[id:3D1E9A64-7C2B-4F58-9E01-6A5D2C4B8E17][ores.scheduler.scheduling_operations]]).
11. *The bridge row is not a lineage.* =workflow_batch_link= names the batch,
    the workflow step and the workflow instance, and the bridge deletes the row
    when the batch reaches a terminal state. It is a live note that a step is
    waiting, not a durable link, and it names a workflow step rather than a
    report run, so the lineage chart cannot be built on it
    ([[id:5A9D3E27-8C14-4B6E-9F2A-1E7B4D0C8A53][ores.compute.workflow_batch_link]]).
