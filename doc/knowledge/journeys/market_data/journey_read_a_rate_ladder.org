This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A trader reads one currency's rate ladder at an as-of - every maturity as a row, every provider as a column, the consensus and the distance between them, with the curve the same quotes draw.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want this currency's swap ladder at this as-of: every rung with its maturity,
each provider's quote beside it, and how far apart they are. Then I want the same
numbers as a curve." The journey is done when the person has read the ladder and
can name the provider that moved and the rung where the market is thin.

* Actor and trigger

The actor is the trader or the quant. The trigger is a price to check against a
curve, a basis to explain, a rung a provider has gone quiet on, or a curve that
moved and a wish to see which rungs moved. The journey starts at *Market data /
Rate ladder*, reached from the instrument search or the area's menu, and ends
when the person leaves the page.

The journey reads and changes nothing. Every number is an observation the
deployment holds; a ladder is a read over those observations, not a record.

* Steps

1. *Open the ladder.* The person opens *Market data / Rate ladder*. The system
   opens the currency, the instrument and the forward start the address states,
   or the last view the person read.
2. *Choose the currency and the instrument.* The person picks =AUD= and
   =IR_SWAP=. The system answers the party's ladder for that currency,
   instrument and forward start at the as-of.
3. *Read what the numbers mean.* The system states the instrument, the forward
   start, the day count, the quote type, the rung count, the source count and
   the as-of, so no number is read without its facts.
4. *Read a rung.* One row per maturity: the tenor code, the maturity date and
   year fraction the server computed, and one column per provider that quotes
   it. A provider that does not quote a rung is absent, shown as a gap, never
   as a zero.
5. *Read the consensus and the distance.* The system states the value it
   derives across the quoting providers, the method it used, how many providers
   it rested on, and the distance from the best quote. A consensus over one
   value says so.
6. *Read the spread.* The system states the 30Y − 2Y spread per provider and
   across the consensus, which is what a ladder is read for.
7. *Read where the market is thin.* The system lists the rungs a provider is
   missing, so a gap is looked at rather than inferred from a dash.
8. *Read the curve.* The person switches to the curve the same quotes draw. No
   new read is taken; the shape and the ladder are one answer.
9. *Meet a stale verdict.* A quote older than the instrument kind's threshold
   is marked stale by the server. The person may sort by age; the person does
   not decide what stale means.
10. *Leave.* The address holds the currency, the instrument, the forward start,
    the as-of and the provider set.

* Screens and wireframes

One read-only page: the facts row, the controls, the ladder table, the curve and
the thin-market list, so a person never reads a number without its facts.

| Step | Shape on the screen | Judgement |
|------+---------------------+-----------|
| Open the ladder | Breadcrumb, title, one sentence, Refresh | The standard draws it, RS-LIST-01 to RS-LIST-03 |
| Choose the currency | Two pickers and one as-of | A view no rule draws yet: a derived read, not a list of records |
| Read what the numbers mean | Labelled values in one row | The standard draws it, RS-PAGE-05 |
| Read a rung | Table, rungs as rows, providers as columns | A view no rule draws yet: no pager, no sort by column header |
| Read the consensus | One column and one distance column | A view no rule draws yet |
| Read the spread | A total row under the ladder | A view no rule draws yet |
| Read where the market is thin | A second table, one row per incomplete rung | A view no rule draws yet |
| Read the curve | Segmented control over a chart | A view no rule draws yet; the client draws, the server states the order |

* Operations and messages

#+ATTR_HTML: :class hug-leading
| Step | Operation | Subject | Status |
|------+-----------+---------+--------|
| Choose the currency | the instrument catalogue, to name the ladder | =marketdata.v1.ops.list_instruments= | missing |
| Read a rung | the ladder: rungs, maturities, quotes, consensus | =marketdata.v1.ops.get_rate_ladder= | missing |
| Read a rung's history | the ticks behind one cell | =marketdata.v1.ops.get_series_ticks= | exists |
| Read the curve | the shape over the rungs | =marketdata.v1.ops.get_rate_ladder= | missing |

=marketdata.v1.ops.get_series_ticks= is per series, so a client that draws this
ladder from it must join several series, order the rungs itself and compute the
maturity dates, the consensus and the spread. That is the work the operation
removes.

* What is missing

- =marketdata.v1.ops.get_rate_ladder= — rungs with maturity date, year fraction,
  one quote per provider and the consensus, ordered by maturity. The maturity
  date needs the calendar and the day count, which are server facts; until the
  operation exists the screen cannot show a date it is allowed to trust.
- The rung order. A rung quoted with a convention (=ON=, =TN=, =SN=) sorts
  before =1W= and carries its own maturity date; the server decides the order
  and the client may re-sort only within it.
- The consensus method. The prototype shows one; the server must state which
  (=median=, =mean=, =first=) so two clients do not disagree, and must state how
  many providers it rested on.
- The staleness verdict, per quote and per instrument kind. Today the threshold
  would be a client constant.
