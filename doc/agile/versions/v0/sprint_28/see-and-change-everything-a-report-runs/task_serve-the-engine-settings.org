* Result

The reporting service now answers the engine settings, its three parts, the ore parameters and their value domains. The four engine settings models had their messaging, eventing and history addresses switched off, so the work was to remove that section and generate the C++ surface: protocol, handler, registrar, service, event, history provider and shell commands. The registrar of the service now registers the handlers of these six entities, and the ore parameters had a generated handler that nothing registered.

The Member role reads and writes the engine settings and reads the ore parameters and their value domains. A person who may edit a report may therefore edit the settings it binds. Deleting stays with the administrative roles.

The BFF serves the configurations at =/api/reporting/engine-settings=: the list, one configuration with its three groups and the reports that bind it, the documentation of each setting, the history, and the writes. A group is written alone against the version of its part, and the service makes the next version of the central row. The BFF refuses a value that its setting does not accept, so a thread count of zero never reaches the service. The wording of each setting comes from its ore parameter, so the BFF holds only what a setting is and never what it means.

The ore parameters and the file types are rows of the system tenant. A tenant other than the system tenant sees none of them until a provisioning step copies them. That gap is older than this change and affects the file types too.
