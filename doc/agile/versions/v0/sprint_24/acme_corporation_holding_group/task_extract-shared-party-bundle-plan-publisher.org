* Goal

Extract one shared helper that publishes every bundle in party_provisioning_bundle_plan() for a given party_id and waits for each, parameterised over which client abstraction issues the request, so provision_acme and shell's provision party share one implementation instead of two independently-maintained copies of the same loop.

* Acceptance

- A single function/template drives party_provisioning_bundle_plan() publishing for both callers; provision_acme's per-office market-data steps and ores.shell's provision party continue to behave identically (verified via the acme_bank_system_provision.ores recipe and a manual provision party run); no duplicated bundle-iteration logic remains in either ores.iam.core/messaging/tenant_handler.hpp or ores.shell/app/commands/provision_commands.cpp.

* Plan

Added a shared, templated =publish_party_provisioning_plan()= helper
to =ores.dq.api/messaging/party_provisioning_plan.hpp=, alongside the
existing =party_provisioning_bundle_plan()=. It is templated over the
publish and wait operations rather than a shared base class, since
=provision_acme= (ores.iam.core, via =internal_request_client=) and
=ores.shell='s =provision party= (via =nats_client=) reach NATS through
unrelated client abstractions with no common type to write one
non-template implementation against — the part that was genuinely
duplicated was the plan-iteration loop, not the transport. Both
=tenant_handler.hpp= and =provision_commands.cpp= were rewired to call
the shared helper, passing lambdas that adapt their own
publish/wait-for-workflow-instance calls, removing the two
hand-written copies of the loop.
