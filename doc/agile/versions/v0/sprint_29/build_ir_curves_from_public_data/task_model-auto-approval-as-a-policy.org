* Goal

A request closes without a person only when a stated policy says so, and the
policy is data an administrator turns on and off, visible wherever the request
and the kind are read. The system can therefore bootstrap an installation and
run its tests unattended, and a desk's own act still waits for its decider.

* Acceptance

- A deployment setting states whether the installation enforces approvals, and a kind states which raises it lets through without a person.
- A request closed by either rule records a decision that names the policy in words, with the system as its decider and never the asker.
- The request and the kind show that the decision was taken by policy, so an auto-approved act never reads as one a person signed.
- Turning either rule off restores the person's decision, with no code change and no restart of the reading service.

* Plan

The rationale first, because it decides the shape. A maker and checker pair
exists to put a second person in front of a consequential act a person proposed.
It is not a toll on work the system does on its own behalf. So a request needs
nobody in exactly two situations, and each is a separate decision by a different
person about a different thing:

1. *The deployment does not enforce approvals.* A development installation, a
   test bed, a demonstration being built: waiting on a click it will always be
   given costs time and proves nothing. This is an operator's decision about an
   environment, so it is one setting, =inbox.approvals.mode=, seeded =enforced=
   and set to =auto_approved= where nobody's book is at stake.
2. *The maker is the installation.* The system tenant is the installation: its
   curves are bootstrapped from the quotes its own feeds publish, which is no
   person's judgement. This is a risk decision about one kind, so it is a column
   on the kind, =auto_approval_code=, whose value =system_tenant= names that and
   whose default =none= keeps the pair.

Neither is inferred from what the subject happens to be. A gate that read a
tenant or a party and decided would put a control where nobody looking at the
approvals could see it, could not be switched off without a build, and would not
say in the record why nobody signed.

The decision that follows:

- =approval_request= gains =auto_approval_code=, empty for a person's decision,
  so the *record* states the rule and a screen filters on it. A kind whose policy
  changes later leaves the requests it closed stating the rule that closed them.
- The lifecycle reads both, in that order, and closes the raise approved in the
  same act with the system as its decider and a comment that states the rule in
  words.
- A raise that names parts is never closed by policy: the parts are people
  answering, and a close that skipped them would leave them open forever.
- =approvals_required= goes back to being a count of people, and nothing else.
  A kind that asks for zero and names no policy now refuses the raise rather than
  writing a request no person could ever answer: one concept, not two.

Visibility: the request carries the rule and its decision says it in words; the
request page draws an =Auto-approved= chip beside the state and the sentence under
the asker; the queue carries the same chip; the kind's list in the shell shows
the policy column; and an operator reads or changes the deployment mode with
=system settings get|set inbox.approvals.mode=.

* Notes

** What it does not do yet

- The deployment mode is read per tenant, falling back to the installation's row,
  but there is no screen for either: an operator states it with the shell
  =system_settings= verbs. A ribbon on the application shell that says the
  deployment does not enforce approvals needs a settings read on the BFF's site
  route, which today answers without a session.
- =system_setting= carries no system-tenant overlay, so every tenant reads the
  installation's row only when it has none of its own.
- The development database was altered by hand: the column on each of the two
  tables, the policy on the curve publish kind, and the =inbox.approvals.mode=
  row. The create and populate scripts carry all four, and a recreated database
  builds them from those files alone; a =compass db recreate= is still worth
  running before this is relied on.

* Result

A request now closes without a person only where a policy says so, and both
policies are data.

- The inbox reads =inbox.approvals.mode= and the kind's =auto_approval_code= at
  the raise, closes the request approved in the same act as the system, writes
  the rule on the request, and says it in the decision in words. Six cases hold
  it: every-raise closes, a system-tenant raise closes only in the system
  tenant, the deployment closes a kind that names no policy of its own, a count
  of zero with no policy refuses the raise, and a person's request still waits.
- The curve publish kind states =system_tenant=, so the provisioning run
  publishes all 20 currencies with no person: the live run's requests carry
  =system_tenant= and their decisions read "Approved by policy: a
  marketdata.curve_publish request raised in the system tenant is the
  installation acting on its own behalf, so no person stands before it", with the
  market data service as the decider.
- A desk's raise in a tenant is untouched: it waits for Market Risk, and the
  request page says which of the two it was.
- The market data gate no longer reads a tenant or a party. It raises.
