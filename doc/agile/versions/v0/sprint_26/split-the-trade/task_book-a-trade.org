* Goal

A caller books a trade through one service operation that writes the anchor, its booking and its state atomically, and a duplicate trade id comes back as a conflict, not a raw unique-key violation.

* Acceptance

- One operation writes the anchor, the booking and the state in one transaction; a failure in any of them writes none.
- A second booking of the same trade id surfaces as a domain conflict.
- Build, ctest, pgTAP and the local check set pass.

* Plan

- An operation model, =ores.trading.trade_operations=, generates the
  =book_trade_request= and =book_trade_response= messages on
  =trading.v1.trades.book=. The handler and the service are hand-written,
  because an operation model generates neither.
- =ores_trading_book_trade_fn= writes the anchor, the booking and the state in
  one statement, so a failure in any of them writes none. The anchor insert
  uses =on conflict do nothing=: a trade id already booked writes nothing and
  returns false, which the service answers as a conflict with code
  =already_exists=. The function runs as the caller, so grants and row-level
  security apply.
- The service stamps the tenant, party and audit fields from the caller's
  context, so the anchor's party is always the caller's.
- The handler requires =trading::trades:write=, the permission the wide
  trade's writers already hold.
