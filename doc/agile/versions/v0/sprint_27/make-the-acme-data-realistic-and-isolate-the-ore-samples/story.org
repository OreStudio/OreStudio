* Goal

The ACME data that demonstrates the system reads as ORE sample data. The
netting agreements, netting sets, CSAs and portfolios were built from the ORE
examples and keep their names, their one currency, their retired overnight
index and their test-book descriptions. The datasets carry the ORE catalogue,
the ORE methodology and the ORE licence. A reader cannot tell the official
ACME data from the data that exists only to make the samples import.

This story separates the two and makes each one right.

1. *The ACME base bundle is realistic.* It is inspired by the ORE samples and
   improved. The ORE sample reporting configurations, CSAs, agreements and
   portfolios are the starting point. The result looks and behaves like a real
   group's data. It follows the report definitions that exist for each party,
   and supplies the configuration those reports need to run.
2. *The ORE samples bundle carries only what the sample import needs.* We keep
   =ore_samples= and retarget it. It holds the reference data that makes the
   ORE sample import work out of the box, and nothing else. Every item is
   clearly labelled as ORE sample data. It installs on every party, so each
   party can import the samples. Every import lands in a sandbox portfolio
   tree, and its books go into that tree.

The realistic ACME data and the sample data are different data. The ORE
samples keep ORE's own CSA terms, so an imported sample still reproduces the
ORE reference results. The ACME data does not copy ORE's terms.

* Acceptance

- Agreement number and netting set code are unique per party, and a CSA has
  its own party. Two parties can hold the same codes.
- The ACME base bundle holds realistic agreements, netting sets, CSAs and
  portfolios for each party. Its datasets, methodology, catalogue and licence
  are ACME's, not ORE's.
- A reader of the ACME base data cannot tell it came from the ORE samples.
  No code, name or description reads as test data.
- The base bundle follows the report definitions each party holds. Every
  netting set, counterparty and portfolio a seeded report definition names
  exists for that party.
- The =ore_samples= bundle holds only the reference data the sample import
  needs. Every item in it is labelled as ORE sample data in its code and its
  description.
- The =ore_samples= bundle installs on every party. After provisioning, each
  party resolves all 19 ORE netting set ids and the portfolio names the
  samples use.
- A sample import creates its portfolio and books inside a sandbox portfolio
  tree. It creates nothing in the ACME portfolio tree.
- The sample CSAs keep ORE's terms.

* Decisions

Taken with the product owner on 2026-10-10:

- Two bundles, kept apart. An ACME base bundle and an =ore_samples= bundle.
- The base bundle comes first. The samples bundle is retargeted after it.
- The samples bundle is the existing =ore_samples=, retargeted. It is not a
  new bundle.
- The samples bundle installs on every party. The base bundle follows each
  party's report definitions.
- All sample imports go to a sandbox portfolio. Their books go into the
  sandbox tree.

- Agreements, netting sets and CSAs are party-scoped. The agreement number and
  the netting set code are unique per party, and the CSA gets its own party.
  This is a bilateral contract between one ACME legal entity and one
  counterparty. It also lets the samples bundle install the same codes on every
  party. It is the first task, ahead of the two bundle tasks.

Known problems to design around:

- *Agreement numbers and netting set codes were unique per tenant.* PR #2598
  review item 6 records that agreements are unique per tenant while netting
  sets look their agreement up per party. The first task fixes this. Its open
  risk is every lookup by number or code that names no party. They were not
  searched yet.
- *The current bundle names real banks.* The sample agreements name real banks
  by LEI. They stay sample data. Their code and description must say so.

Open, to settle in the tasks:

- The rule for a netting set with no party. The column is nullable today, and
  a party-scoped CSA needs a party.
- Which banks each ACME legal entity faces, and which agreement type and
  governing law each uses.
- The CSA archetypes: variation margin, initial margin, and none. Their
  currencies, thresholds, minimum transfer amounts, call frequencies and
  overnight indices, per party.
- The ACME portfolio and book tree, and how the sandbox tree sits beside it.
- Where an imported sample's books land today. The sprint 18 import work added
  a "pending book". Its current behaviour was not re-read.
- The licence and catalogue for ACME-authored datasets.
- The names and codes that mark an item as sample data.

Evidence read so far: the three netting dataset scripts and their methodology
text in =ore_sample_netting_dataset_populate.sql= and
=ore_sample_portfolios_dataset_populate.sql=, the Sprint 26 task
=task_ore-sample-netting.org=, the =acme_demo= profile steps, and the
investigation of what each report needs. The database was not queried.

* Out of scope

- Generating trades and fixings for a relative time horizon. That is the
  story "Seed a relative-time trade population with the market data it needs".
  It follows this one, because it builds on the realistic netting and
  portfolios.
- The =backfill-identity= party-RLS failure.
- Changing how the ORE import resolves names. This story changes the data it
  resolves against.
