* Acceptance

- One constructor per drawn fx code, with the trade type fixed by it and terms holding only that table's columns.
- The writer hands over constructed rows and assembles no fx product.
- A provisioning run books the same fx population as before, and the suites are green.

* Plan

An fx row is the whole instrument: no fact table sits beside it, so the
table's own cross-column checks are the product's shape. Each constructor
mirrors the checks of the table it writes, which is where they become
refusals rather than errors a run discovers.

Seven terms structs, one per table, and one constructor per routed code, with
the trade type fixed by the constructor.

* Result

Every fx product the planner reaches is constructed by a function that names
it. The writer holds no fx assembly: it fills the terms, calls the
constructor, appends the row and stamps the audit columns.

Proved by a provisioning run on a recreated database against a baseline taken
from the previous build: the population is identical -- forward 8, vanilla 4,
barrier 12, digital 4, asian 4 -- and the tenant's total trade count is 829
both times.

The suites are green: =ores.trading.api.tests= at 548 assertions in 147 test
cases with nine new fx cases, and =ores.synthetic.core.tests= at 1741
assertions in 79.

* What the constructors now refuse that nothing did before

- a double barrier without two barriers;
- a barrier type that names an upper barrier without one, or a lower barrier
  without one, which is the check the store states and the writer did not;
- a digital without a strike, a touch without a barrier, a double touch with
  one;
- an fx swap that buys and sells the same currency;
- a variance swap whose end is not after its start, or whose strike is not
  finite and positive;
- an average forward without an index, and a target redemption forward without
  a target.

* What the population still does not reach

The planner cycles sixteen fx types but each config states eight trades per
book, so the cycle stops at the eighth code. FxVarianceSwap, FxAccumulator,
FxTaRF and the rest of the second half never book, and the same is true of the
bond and credit families recorded earlier. The constructors for those codes
exist and are tested; nothing draws them.
