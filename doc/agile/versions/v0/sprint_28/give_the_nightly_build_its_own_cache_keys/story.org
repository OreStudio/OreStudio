#+title: Story: Give the Nightly Build its own cache keys
#+description: The clang cache prefix is shared by continuous-linux.yml and nightly-linux.yml, but the two build the same variant with different flags: the nightly's debug jobs carry code coverage, so sccache keys those objects differently and the two caches hold objects the other cannot use. Restore takes the newest match, so whichever workflow ran last can hand the other a useless cache, and the prune step actively deletes the other's entry. Scope the compiler cache keys to the workflow, and lower the nightly ceiling so all six variants fit the 10 GB repository cap.

* Decisions

- *The cache key carries the workflow name.* A shared prefix is harmful because
  the two workflows do not build the same objects for the two variants they
  share. The Nightly debug jobs pass =code_coverage=1=, which adds
  =-fprofile-arcs -ftest-coverage= to every compile line, and sccache hashes the
  compile line. Continuous Linux would therefore restore a nightly entry it
  cannot use, and the per-workflow prune step would delete the other workflow's
  newest entry.
- *One transitional legacy prefix stays in Continuous Linux.* The entries that
  exist under the old prefix were built by the continuous jobs, so that workflow
  restores them once while the scoped cache is cold. Remove the line after the
  first warm continuous run.
- *The Nightly ceiling falls to 1000M per variant.* Four nightly variants and
  two continuous variants share one 10 GB repository cap, and the sum of the
  ceilings must fit it.
