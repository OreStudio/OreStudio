* Summary

Access control in this system is decided in two places, and knowing which
is which is the point of reading the cluster in order. The *application*
decides what an authenticated actor is allowed to ask for, through roles
and permissions. The *database* decides what rows that actor may see at
all, through row-level security. The second is the backstop: a bug in the
first is contained by it, which is why both exist.

Between those two sits the awkward case that generates most of the
subtlety here — a service acting on behalf of a user rather than as
itself. Read the cluster as: what an identity is, what a role grants it,
how a service borrows one, and what the database enforces regardless.

Management]] — start here. The identity lifecycle, authentication against

almost every access bug is one being mistaken for the other.

[[id:504863AB-C45A-47E8-BB77-AADCB620A305][The entry journeys]] — the

** What a role grants

roles compose permissions, users are assigned roles. Read second, because
it is the concrete model the abstract vocabulary above resolves to, and it

[[id:37D5E28C-A83F-4EDC-891B-4F6F23B2BB42][Session modes and

see".

[[id:C84899BD-5EC8-4AA7-88D7-CE7ED19BC573][Book Access and Permissions]] —

** What a read may return

[[id:804C7048-DBBF-4B39-8737-BFB4949884C4][Authorised reads]] — how a read
decides whether to answer, which of the tree's two permission checks it uses,
why a self read and a privileged read are different subjects rather than one
subject with a parameter, and where a refusal travels. Read it before adding a
read, and especially before changing one that answers about somebody else's
access.

** How a service acts for a user

The mechanisms are established patterns, and the identity group of the
[[id:EA249899-6611-407F-A43A-B37019EBD1A7][pattern language]] holds them: Access
Token, Client Credentials, Token Relay, Token Exchange, Grant Management, and the
composite Scheduled Work Acting as a Tenant. Each pattern page states its
failure handling, its pitfalls and its sources. The pages below decide between
them and record how ORE Studio uses them.

[[id:3E20C1A0-7BA1-4F31-8C34-1E5F13558890][Service-to-Service Auth
Patterns]] — the decision guide: which identity pattern a call needs, with the
questions that decide it and the table of which layer acts as whom.

[[id:AAC60D20-8696-4455-9292-E8FAE1389CBC][Internal Actor Impersonation]] —
Token Exchange in its in-process form inside IAM, used by tenant provisioning to
act as several parties in turn. Read it for the worked example and for the
expiry failure it met.

[[id:78B82824-0BBB-4442-A9FA-E1F265DF57BD][Run grants and run tokens]] — IAM's implementation of Scheduled Work Acting as a Tenant: the run
grant entity, the exchange and its checks, the run token's claims and the cache
rules. Read it before building any work that a schedule starts in a tenant.

[[id:B3165E6F-AE8C-4DBD-8F87-2EC4F276FCF0][Report execution at scale]] — the
first component to use run grants: the role, the audience and the moments
reporting grants and revokes.

** What the database enforces regardless

[[id:B28747DF-A735-1C84-4E43-11ADFA8B05E3][PostgreSQL Row-Level Security]] —
the database mechanism, described before any project-specific use of it.
Deliberately last: it is the backstop, and it is easier to see why the
backstop is shaped as it is once the application-level model above is
clear. An agent changing a query that crosses a tenant boundary should
have read this page first.

** What a person does with it

[[id:D602E114-F896-42CA-893A-841AD6FC3221][User Journeys]] — everything above says what
the system enforces. This one records what a person is trying to do, written from
the goal rather than from the entity. Read it when the question is "what should
this screen do" rather than "what does this entity hold". Each journey document
also lists the operations and subjects its steps need, so the distance between
the design and the server shows up as a table rather than as a surprise during
the build.

* Reading it in reverse

There is one case for inverting the order. If you are debugging a query
that returns fewer rows than expected, start at row-level security and
work upwards: the database is the layer most likely to be silently
filtering, and it does so by design rather than by error.
