* Notes

** Use cases the design must serve

Each row is a reader or an actor, what it needs, and what happens today.

| # | Who | Needs | Today |
|---+-----+-------+-------|
| 1 | Any reader of any tenant, on a history | The name, picture and type of the author of an entry. The author may be a service of the system tenant. | Hidden by the tenant wall and the C++ tenant filter. The toggle hides nothing and the service has no picture. |
| 2 | A service acting inside a tenant, such as the inbox service or the refdata service | To know that the account named by a soft foreign key exists in the tenant: the notice recipient, the portfolio right, the sandbox owner and members, the approval requester and decider, the delivery and the preference. | The check reads the accounts table under the actor's party rule. The service is in no party, so it finds no account and the insert fails. The engine user passes because it has no actor. |
| 3 | A super admin acting in the system tenant, during tenant setup | To update the service accounts, for example to attach their pictures. | The party rule hides the service accounts, so the update says "Account does not exist" and the tenant stays in bootstrap mode. |
| 4 | A member | The people of the parties the member works in. | Works. The party rule limits the read. |
| 5 | A tenant administrator | Every person of the tenant. | Works, because the administrator is linked to every party. |
| 6 | The sign-in lookup, and a session with no actor | The account by username, before a session exists. | Works. A session with no actor is not restricted. |
| 7 | Any tenant | To write its own accounts. No tenant writes a system account. | Works. No change wanted. |

Use cases 1 to 3 are the failures. Use cases 4 to 7 must keep working.

** What the failures share

The accounts table answers three different questions with one rule. The third question is answered by other tables, and the rows of the accounts table need only the first two.

- *Who is this?* A reader names an author. The answer is a name, a picture and a type.
- *Does this exist?* An insert checks a reference. The answer is yes or no.
- *What do we know about this person?* A reader opens a profile. The answer is private data.

The party rule is right for the third question. It is wrong for the second. For the first, it is right for the people of a tenant and wrong for the services. A reader sees the name and picture of a person only when the product owner's rule lets the reader see that person: the parties the reader has access to, and the system party. A history entry by a person outside those parties shows the username only, as it does today. The tenant rule is wrong for the services of the system tenant in the first question.

** The design

Share the open rows of the accounts table by the standard that reference data already follows.

*** No column split

The split of confidential data from open data already exists. The credential, the contact information (address and phone), the sign-ins and the sessions are other tables, each with its own read code. The accounts table holds what colleagues need to know about each other: username, type, status, full name, picture, email, job title, reports-to and default party. The product owner confirmed on 2026-10-11 that none of these is to be hidden. The accounts table is the open table, and no column moves.

What fails is the rows a reader may see, not the columns. The design therefore shares rows:

- The column =shared= is a boolean on the accounts table, false by default. The seed sets it to true for the service accounts and for the super admin.
- A shared row is owned by the system tenant. The policy admits a row of the system tenant only when =shared= is true. A later human account in the system tenant stays hidden until a person sets the column.
- The party rule passes a shared row. It keeps applying to the people of a tenant.

*** One standard for data read across tenants

The standard has six building blocks. Reference data already uses blocks 1 to 3.

1. *Owner.* A shared row has =tenant_id = system=.
2. *Policy.* The existing shared-reference tables use one permissive policy. Its =using= clause admits the rows of the current tenant and the shared rows of the system tenant. Its =with check= clause admits only the current tenant, so a write stays inside the tenant. The accounts table takes this shape. Its tenant policy is permissive today, not restrictive, so widening =using= is enough. The party rule is the only restrictive policy. It stays on the tenant-owned rows of the accounts table, and it passes shared rows.
3. *Read.* The generated read declares =:tenant_read_scope: shared=. The template then leaves out =where("tenant_id"_c == tid)=, and the policy decides. The accounts read states that predicate today in the paged read and in the count. Both change with the template.
4. *Guard.* The read has a =:read= code, or an allow-list row with a reason, as the authorised-reads rules require.
5. *Existence check.* A reference to a row that the party rule hides is checked by a security definer function that returns only yes or no. It names no column, so it leaks no data. The function takes the account id and nothing else. It derives the tenant from =app.current_tenant_id=, and it answers true for an account of that tenant or a shared account of the system tenant. A caller cannot name another tenant, so the function is not an oracle across tenants. The function sets a fixed =search_path=. The grant is revoked from =public= and given to the service roles by name.
6. *Page.* One page states the blocks, and the checklist for a new shared table.

*** What each use case gets

| # | Answer |
|---+--------|
| 1 | The services are system-owned shared rows of the accounts table. They are admitted by block 2 and read with block 3, so every tenant sees them. |
| 2 | Block 5. =ores_iam_account_exists_fn(id)= replaces the =exists (select ... from ores_iam_accounts_tbl)= in every soft-foreign-key trigger. The party rule no longer matters for a reference check. |
| 3 | A service account is a shared row. The party rule does not apply to shared rows, so the update of a service account no longer depends on the actor's parties. |
| 4, 5 | The people of a tenant stay tenant-owned. The party rule keeps applying to them. |
| 6 | No change. |
| 7 | No change. Block 2 is select-only. |

** Decisions

The product owner settled these on 2026-10-11.

- *Who a person sees.* A person sees everyone in the parties they have access to, and everyone in the system party. The party rule keeps applying to the people of a tenant. The system party is the one party every person may see. The accounts table has two row classes: the people of a tenant, under the party rule plus the system party, and the shared rows, which every tenant reads.
- *The super admin.* Every tenant may see the super admin account. It stays a =user= account, because humans sign in with it. The shared policy admits a system tenant row when =shared= is true, so the super admin is admitted by its flag and not by its type.
- *One delivery.* The existence function, the shared rows, the shared-read standard and the documents ship together in one change. The existence function does not ship first.
- *No column split.* Decided 2026-10-11. The accounts table is already the open table, because the confidential data lives in other tables. No column moves, and nothing hides email or job title.

** Open points for the reviewer

- The system party is a party of each tenant. Its members are visible to everyone in that tenant. The services of the system tenant need no link to it, because block 2 admits them.
- Which soft-foreign-key checks use block 5? The generated triggers come from models, so the change is in the template and every generated trigger changes with it. The implementation lists every trigger and function that reads the accounts table, in every domain, not only inbox and refdata. A test proves each one for a service actor in a tenant.
- *Fallback.* The attach photos failure blocks tenant setup now. If the change grows beyond one delivery, the product owner decides before anything splits. The smallest fix for that case is a write of the service pictures with no actor, which another environment already holds as a hotfix.

* Result

The design is in PR #3115. This task builds it. The accounts table is the open table and no column moves, as the product owner decided.

What changed:

- The accounts table has the column =shared=. The seed sets it for the 23 service accounts and for the super admin.
- =accounts_select_policy= admits the current tenant and the shared rows of the system tenant. One policy per command keeps every write inside the tenant. The party rule passes a shared row.
- =ores_iam_account_exists_fn(id)= answers yes or no for the session's tenant and the shared accounts. The generated soft foreign key trigger calls it for every foreign key to the accounts table, through the map =EXISTENCE_FUNCTIONS= in the codegen loader. Sixteen entities were regenerated.
- The account repository states =:system_tenant_visible: true=. A tenant administrator reads the 23 services and the super admin beside the 59 people.
- The delete rule of an entity that is visible to the system tenant keeps to the own tenant. The pgTAP test found that the rule, which runs with the owner's rights, closed a shared row for another tenant.
- The web directory counts every account type except a user as system activity.
- The standard "Data read across tenants" states the six blocks and the checklist. The multi-tenancy and authorised-reads pages describe the accounts case.

Evidence:

- =test/iam_accounts_shared_visibility_test.sql= passes 13 pgTAP assertions, including a service acting in a tenant that finds a person only through the existence check.
- A clean provision of the Acme dataset completes. The step =attach_photos= passes, all 23 services and all 59 people hold a picture, and the workflow reaches COMPLETED. The step failed before on main with the party rule.
- The inbox and refdata test suites pass. The web suite passes (1045 tests).
- The IAM core suite has 7 failures: run grant exchange (4), the role grant applier (1), the member role test (1) and the login of a suspended tenant (1). All 7 pass when only =accounts_party_visibility_policy= is dropped, so they come from the party rule on main and not from the shared rows. They were hidden before because the old development database did not have the rule.

Not done:

- A service that acts in a tenant still cannot read a person through the table. Only the existence check serves it. The seven failing tests read people as a service. Whether a service acting in a tenant should read the people of that tenant is a decision for the product owner.
- The People list of a tenant now shows the shared rows. They carry the service tag.
