* Goal

Each ACME party's bond book holds bond trades across a range of counterparties
and tenors. The data follows the model of a real trading system: a bond is a
security with fixed terms, held once by the tenant. A trade is a position in that
security. It holds a reference to the security and its own size, date,
counterparty and book.

* Acceptance

- A provisioned ACME tenant holds one bond issue for each security of the
  pool, and the pool spans the config's tenor band.
- Every trade of a security reads the same issuer, issue date and maturity.
- No security belongs to a book. More than one book holds the same security.
- A trade is dated on or after the issue date of its security and before its
  maturity.
- The face value of a security states no trade's size. The size of a trade is
  the notional on its bond instrument.
- A second run writes nothing and moves no trade version.

* Notes

PR #3365 wrote one issue for each book, from the first trade of that book. All
trades of a book then shared one maturity, and the drawn tenor never reached the
data. It also took the face value and the issuer from that first trade.

The cause was the model, and not a missing field. The issue is the security
master. A trade names it through =bond_instrument.issue_id=. The schedule
=tenor= of =1Y= is the coupon period and is correct.

Open items, not done here:

- The issuer of a security comes from the counterparties of the config that
  writes it first. Two configs of one tenant could name different issuers for
  one security. The issuer needs a tenant-wide source.
- A run that stops half way through the legs of a new issue leaves an issue
  that the next run treats as complete.
- Pricing is not proven. The ORE validator found no quotes for the as-of date.
- The writer has no database-backed test.

* Result

Gap found: the generator wrote one issue for each book, so a book had one
maturity. It is fixed. The planner now builds a pool of securities, one for each
whole year of the tenor band. A security has an issue date six months before
the as-of date, a maturity of that date plus its term, and an issuer taken from
the scope. Each trade draws a security from the pool. The writer gives a
security a unit face value, takes the issuer from the security, and reuses an
issue that the tenant already holds.

Result on a provisioned database: 9 issues with maturities from 2027 to 2035,
32 trades in 4 books, and a second run that wrote nothing.

The tests changed. The case that asserted one security for each book now
asserts the opposite. New cases check that the trades of a security agree on
its terms, that a maturity is the issue date plus the term, that a trade date
falls inside the life of its security, and that books share securities.
