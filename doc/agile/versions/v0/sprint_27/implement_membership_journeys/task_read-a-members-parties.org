* Acceptance

- =iam.v1.ops.get_my_parties= answers the caller's own associations, each with the party's name, short code, category and business centre, and the account's stored default.
- The read needs no permission and cannot name another account: the request carries no account identifier and the session names it.
- A party IAM's cache cannot name answers with empty strings, so the screen states the gap rather than drawing a half-read row.
- The browser reaches it over =GET /api/me/parties=, through the wire-protocol seam, parsed at the boundary on both sides.
- The shell reaches it, because codegen emits the command from the message.
- =compass lint=, =check_component_drift.py --component iam=, =check_subject_conformance=, =check_route_auth_declarations= and =check_handler_permissions= pass.
- The C++ tests cover the naming rule, and the BFF tests cover the route.

* Plan

1. Declare the request, the response and the party summary in
   =ores.iam.account_messages.org=.
2. Regenerate the component, so the C++ protocol, the TypeScript protocol and
   the shell command all follow from the one declaration.
3. Serve it from =account_operations_handler=, which already holds the party
   cache: the associations come from the junction repository and the names from
   the cache, reloaded once on a miss.
4. Register the subscription in =registrar.cpp=.
5. Wire the browser path: the wire-protocol seam, the BFF route and the web
   client method.
6. Test the naming rule as a pure projection, and the route end to end.

* Notes

- *The naming already exists, twice.* The sign-in reply names parties from
  IAM's party cache (=auth_handler.hpp=), and =update_account= takes a party
  identifier with no name. This read reuses the cache and states the same
  summary shape the sign-in reply does, because the member's screen is asking
  the same question outside the sign-in step.
- *Two near-identical summaries now exist.* =party_summary= in
  =ores.iam.login_messages.org= and =my_party= here. They are not merged: the
  login summary is part of the sign-in contract and carries =id= rather than
  =party_id=, and changing it would move the login wire shape. The duplication
  is recorded rather than silenced.
- *The cache is the only name the IAM service may read.* The service depends on
  =refdata.api=, not on refdata's repository, so a name can only come from the
  per-tenant mirror. A miss reloads the partition once, then answers empty
  strings rather than failing the whole read.
- *The shell command is generated.* Codegen emitted
  =account_operations get-my-parties= and its recipe from the message
  declaration, so the second client is served without hand-written work. That
  is the story's decision that a journey is reached from both clients.
- *A message's declaration order is load-bearing, and nothing checked it.* The
  response was first declared above the =my_party= it carries, and codegen emits
  the structs in the order the model states them, so the generated header
  referenced a type that did not exist yet. Every documentation gate passed;
  only the compiler caught it. The fix is the order in the model, and the gap is
  filed as a capture: the model linter could refuse a message whose field names
  a type declared later in the same file.

fixed here and the gap is captured at

later in its model]].
