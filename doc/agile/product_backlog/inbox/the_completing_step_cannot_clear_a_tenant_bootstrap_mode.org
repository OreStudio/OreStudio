* What

Make the completing step of tenant provisioning able to clear the settings
it clears. The provisioner seeds every new tenant with bootstrap mode set
and tenant onboarding pending, and the completing step writes both to their
finished values. Both writes are creates over rows that already exist, so
the store refuses them and the step reports a warning rather than a
completion.

* Why

A tenant is created with two settings rows: bootstrap mode true, and tenant
onboarding pending. The completing step marks the tenant active and then
asks the settings service to clear bootstrap mode and complete tenant
onboarding. The settings service builds a new setting value with no version
and saves it, which the store reads as a create, and a create over a live
row is refused by design. The step therefore completes with one warning
that names the refusal, and the tenant keeps bootstrap mode.

The consequence reaches the person the journey is for. The login reply
carries the tenant's bootstrap mode, and the browser's gate makes the setup
page the only page while a tenant reports it. So the administrator of a
tenant whose provisioning has finished is told that provisioning has not
finished, and the same administrator can never reach the tenant's own
pages. The tenant's status and its bootstrap mode disagree, and the status
is the one the completing step set directly.

The write the completing step means is an update: the row exists, its
version is known to the deployment, and the finished value replaces the
seeded one. Either the settings service states the version it read for a
setting the tenant already holds, or it offers the update as an operation
of its own. The tenant onboarding flag rides the same call, so it fails the
same way and belongs in the same fix.
