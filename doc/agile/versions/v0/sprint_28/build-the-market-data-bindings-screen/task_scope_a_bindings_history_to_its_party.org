* Goal

A binding's history is read by its source name, which every party of a tenant may hold. The server's lookup, read_any_by_source_name, filters by tenant and source name only and takes the newest row, so in a tenant where two parties hold the same source the history can come from the wrong party. The BFF now refuses the history of a name the party does not hold, but it cannot choose the right party's row. Scope the lookup to the caller's party, in the generator template if the same rule holds for other entities with a party, or for this entity alone if not, and decide which in the task result.

* Acceptance

* Plan

** The read belongs to the generator, not to the entity

=feed_binding_service::get_feed_binding_history= turns the declared key into a
row id through =repo_.read_any_by_source_name=, then reads every version of that
id. That resolver is not this entity's code: =key_resolvers= in
=projects/ores.codegen/library/templates/ores.cpp.repository.repository_impl.org=
emits =read_any_by_<key>= for every entity whose declared =key_field= is not its
primary key. The resolver filters tenant and key only, orders by =valid_from=
descending and takes one row, so the newest row of any party wins.

The sibling finder =read_latest_by_<key>= already keeps the session's party, in
memory and after the fetch. A resolver cannot copy that shape unchanged: its
=sqlgen::limit(1)= takes one row before any party filter can run, so another
party's newer row consumes the limit and the caller's own history reads as
empty. That is the defect, and it is why =assertBindingVisible= in the BFF cannot
repair it: the BFF can refuse a name the party does not hold, but it cannot make
the server pick the party's own row.

** What it touches

Measured on =a1152ae6ee=: 57 resolver definitions in 57 generated repository
files across 10 components. 31 of them own a party column and take this fix; the
other 26 have no party to scope to. One of the 31 has an optional party column
(=batch.external_ref= in =ores.compute=), where a null party means the row
belongs to the whole tenant; the shared =read_latest_by= keeps such a row for
every party, and this fix keeps the same rule.

The entity screen specification states the rule the code broke, at
=doc/knowledge/ui/entity_screen_specification.org= line 570: a history is read
for one row, addressed by the row's own id when its kind has one, *because the
key a model declares for the row may be shared by other rows: every party holds
a contact of each type*.

** The change

1. Filter by the session's party inside the resolver, after the read and before
   the single row is taken, copying the =read_latest_by= rule including the
   optional column's null case. Drop =sqlgen::limit(1)= so the filter sees every
   candidate, then keep the newest one: the query keeps its =valid_from=
   descending order, so the first row left is the party's newest version. The
   party cannot go into the query itself without splitting the template on the
   optional column, which is one entity in ten.
2. Carry the rule in the header doc of =read_any_by_<key>= and in the
   =key_resolvers= docstring, so the next reader does not have to rediscover it.
3. Regenerate the components that own a resolver and commit only the resolver
   bodies.

** Verification

- A repository test in =ores.marketdata.core= with two parties of one tenant
  holding the same =source_name=, each with its own version, asserting the read
  returns the caller's party's newest row. Today it returns whichever is newer.
- The generated code of every affected component compiles, which is the check
  that the optional-party branch and its null case are right.
- =compass check= green, with =component-drift= proving the committed generated
  files match the template.

* Notes

** The decision: the template, not this entity

The resolver is emitted by =key_resolvers= for every entity whose declared key
is not its primary key, so the rule the entity screen specification states at
line 570 applies to all of them, not to a binding alone. The template fixes it
once. The alternative, a hand-written override for =feed_binding=, would leave
the same defect in 30 other resolvers, including the two the specification names
by example: party identifiers and party contacts, of which every party holds one
of each type.

** The test and why it would fail on the old code

=feed_binding_history_resolves_to_the_session_party_s_row= in
=projects/ores.marketdata/core/tests/repository_entity_repository_tests.cpp=
writes two bindings under one source name, one per party, and reads each back
under its own party. It measured green on 2026-10-17 with 6 assertions.

The two rows it writes are 5 ms apart, which is what makes the test bite. Read
from the database after the run:

| Party | valid_from |
|-------+------------|
| the other party | 2026-10-17 11:23:05.126433+01 |
| the session's party | 2026-10-17 11:23:05.120994+01 |

The other party's row is strictly newer, so the old read, which ordered by
=valid_from= descending and took one row before any party filter ran, returned
that row for *both* parties. The test asserts each party's own id, and fails.

** The synthetic service test link failure, and why it is gone

Before the rebase, =compass build= failed at =ores.synthetic.service.tests= with
undefined references to every =feed_kind_registry= member. The test includes
=projects/ores.synthetic/service/src/feed_kind_registry.hpp=, a private header
with no export attribute, and the service library was compiled with
=-fvisibility=hidden=, so the 117 symbols were defined in the shared object but
absent from its dynamic symbol table.

The rebase onto =50b2ac29df= removed it. Commit =a2c824b07b [codegen] Make hidden
visibility a part's decision= moved the flag from every part to a per-part
declaration, and the synthetic service part does not ask for it, because its
classes carry no export attribute and its suites link them — the rule the
=hidden_visibility= docstring in =org_loader.py= now states. The target links and
builds on the rebased tree; the capture raised for it was withdrawn rather than
kept as a false record.
