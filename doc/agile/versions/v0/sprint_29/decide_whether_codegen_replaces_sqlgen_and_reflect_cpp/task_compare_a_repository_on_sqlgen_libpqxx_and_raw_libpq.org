* Acceptance

- One entity's repository work runs on sqlgen, libpqxx and raw libpq against
  the same table, with the same row type and the same timestamp parser.
- Each workload has a median, a range and an allocation count.
- Each client's translation unit has a compile time and a peak memory.
- Every large gap has a cause, found on the wire and not guessed.

* Plan

The entity is the change reason category of =ores.dq=: nine columns, a text
key, and the shape of most control-plane entities. The benchmark is in
=evidence/repository_bench/=.

- =row.hpp= is the row every client writes and reads, with =recorded_at= as a
  =time_point=. Every client parses the timestamp with
  =ores::platform::time::datetime::from_iso8601_utc=, as the real mapper does.
- Each client creates a session table, =pg_temp.bench_crc=, with the columns
  and primary key of =ores_dq_change_reason_categories_tbl= and none of its
  triggers. The triggers cost the same whatever client writes, so without them
  the benchmark measures the client.
- =sqlgen_client.cpp= uses the same calls as the generated repository:
  =insert= in a transaction, and =read= with =where= and =order_by=.
- =pqxx_client.cpp= uses prepared statements, one round trip each. Its copy
  variant writes through =stream_to=.
- =libpq_client.cpp= writes a batch in pipeline mode with a prepared insert, and
  reads with prepared statements in text format.
- =main.cpp= runs five rounds of each workload on each client: write 1,000
  rows, read all 1,000, and 1,000 point reads by code. It counts C++
  allocations with a replaced =operator new=.
- =build.py= compiles each client as its own unit with the project's release
  flags and reports each unit's wall time and peak memory.

The server traffic was then traced with =strace= and TLS off
(=PGSSLMODE=disable=), to count the statements each client sends.

* Notes

** Why sqlgen reads are slow

sqlgen reads every query through a cursor. One read sends =BEGIN=, =DECLARE
sqlgen_cursor_N CURSOR FOR SELECT ...=, =FETCH FORWARD= until the cursor is
empty, =CLOSE= and the end of the transaction: six round trips where the other
clients send one. A point read therefore costs 5–7 times as much on sqlgen.
Every repository read in the services pays this today, and a service behind
the pooler pays it on each acquire as well. A read of 1,000 rows hides the cost,
because the transfer of the rows is most of the time.

** Writes

sqlgen and prepared libpqxx both send one prepared insert per row, so both are
bound by the round trip. Pipeline mode and COPY remove that bound: 3–5 times
faster than sqlgen for a batch of 1,000. COPY through =stream_to= is the
fastest batch write. It suits tick ingest and bulk loads; pipeline mode suits
control-plane batches, which need a result for each row.

** Allocations

sqlgen allocates 24 C++ objects per row it writes or reads, and 114 per point
read, against 9–17 for the others. The causes are not measured. The likely
ones are the SQL text sqlgen builds for each call, the cursor statements, and
=rfl::Timestamp=, which the mapper formats to a string and parses again.

** Compile cost

The sqlgen unit takes five times as long as the libpq unit to compile, and 2.3
times as much memory. libpqxx is between them. A generated repository on libpq
is the cheapest of the three to build.

* Result

The control plane should target raw libpq through a thin generated layer, with
prepared statements, pipeline mode for batches and COPY for bulk loads.
Against sqlgen, a point read is 5–7 times faster because it is one round trip
and not six. A batch write is 3–5 times faster, and the translation unit
compiles in a fifth of the time. libpqxx is close to libpq at run time, but it
does not have pipeline mode, it needs a clang triplet, and it compiles twice as
slowly as libpq. Binary results are not needed for this entity: a read of 1,000
text rows takes about 4 ms on every client. The absolute numbers come from a
loaded machine and must be measured again when it is quiet.
