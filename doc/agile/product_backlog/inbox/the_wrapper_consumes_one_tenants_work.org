#+title: The wrapper consumes one tenant's work
#+description: A wrapper subscribes to the system tenant's assignment subject, while the dispatcher routes each workunit to its own tenant's subject. Every other tenant's work is dispatched and never picked up.
#+type: capture
#+level: cross
#+filetags: :compute:telemetry:dispatch:defect:
#+created: 2026-10-07
#+updated: 2026-10-07

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

A wrapper subscribes to exactly one assignment subject, and the launcher
bakes the system tenant into it:
=compute.v1.work.assignments.ffffffff-ffff-ffff-ffff-ffffffffffff.{platform}=.
The dispatcher routes each workunit to the subject of the tenant that owns
it — =workunit_dispatcher.cpp= publishes to
=assignments.{tenant_ctx.tenant_id()}.{platform_code}=. A workunit owned by
any other tenant is therefore dispatched to a subject no wrapper listens
on, and no result is ever produced for it.

Measured on the live fleet on 2026-10-07: one workunit and two batches sit
under tenant =1365492c-4583-403d-bc4b-46433980a79f=, while the five
registered hosts sit under the system tenant. The wrapper consumes the
system tenant's stream alone.

* Why

Silent and wrong: the work is accepted, stored and dispatched, and nothing
reports that it was never picked up. The grid's own counters exposed the
gap — the poller's summary read =0= workunits while the installation held
one — which is how this was found.

The fix is a design decision, not a one-line change, and it has two
candidates. A wrapper could consume every tenant's assignment subject, which
matches the grid's ownership: one set of hosts runs every tenant's work. Or
the dispatcher could route to the single tenant the launcher already names,
which matches the fleet as deployed. The chosen one belongs on the compute
grid design page, because it settles what a wrapper is: an installation
actor or a per-tenant one.
