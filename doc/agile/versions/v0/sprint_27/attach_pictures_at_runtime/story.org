* Goal

Pictures are attached at runtime through one seam: an assets operation
ensures a template image exists in a tenant, and an IAM operation reconciles
accounts' pictures from a scope. Staff photos, party logos, counterparty
logos and the service accounts' pictures all use it, and both =ores.shell=
and =ores.web= can run it.

* Acceptance

- =assets.v1.images.ensure= copies a system-tenant template image into a
  tenant and returns its id, idempotently, with no workflow context.
- =iam.v1.accounts.attach-pictures= reconciles the accounts a scope names:
  each account that wants a picture and has no =image_id= gets one.
- The three places that copy templates today use the assets operation; no
  copy logic is duplicated.
- The wanted picture code rides the account API, so the handler stops
  reading =ores_dq_accounts_artefact_tbl=.
- The service accounts' pictures attach from the service registry at
  installation bring-up and on demand, and
  =iam_service_account_pictures_populate.sql= plus its
  =validation_ignore.txt= entry are gone.
- Both clients reach the same subjects; no behaviour is client-specific.

* Decisions

- *One seam per concern.* Copying a template into a tenant is the assets
  service's job, exposed as =assets.v1.images.ensure=. Deciding which account
  gets which picture is IAM's job, exposed as
  =iam.v1.accounts.attach-pictures=. Neither knows about the other's tables.
- *Runtime and server-side, so both clients are equal.* The operations are
  ordinary NATS subjects, so =ores.shell= and =ores.web= reach them through
  the same generated protocol. No behaviour lives in a client.
- *Reconcile, do not orchestrate.* Each operation is idempotent and safe to
  re-run; the caller supplies a scope, not a step-by-step plan. This is what
  lets the installation bring-up and an operator's re-run use the same call.
- *The provisioning step keeps its place.* =attach_photos= stays the place a
  tenant's staff photos are attached; it becomes a caller of the two
  operations rather than an owner of the copy logic.

* Out of scope

- Re-picturing an account when its template image changes. The reconcile
  fills a missing picture and leaves an existing one alone. Whether a changed
  icon should overwrite every account that carries the old one is a product
  decision, and it changes the idempotence rule.
- The dead =attach_staff_photos_best_effort= wrapper. It has no callers and
  retires with the legacy synchronous handler, not here.
