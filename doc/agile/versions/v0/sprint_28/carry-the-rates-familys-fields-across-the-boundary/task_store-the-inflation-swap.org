* Acceptance

- The import reads the CPI leg's index, base level and observation lag into the product's fact row.
- The export writes them back into the CPI leg, which currently leaves the leg with no payload at all.
- A test states the document's own values as its expectations and proves both directions.

* Plan

1. Write the failing case first, against the document's own values:
   =Inflation_CPI_Swap.xml= states =UKRPI=, =210= and =2M= on its CPI leg, so
   the case asserts those three and nothing the mapper invents.
2. Read them on import from the CPI leg, which is where the document states
   them. A swap states one such leg; a second would be another product.
3. Write them back on export onto the same leg, because the shared leg reverse
   states a cashflow, fixed or floating payload and nothing for a CPI leg.
4. Record the money limit rather than paper over it: =BaseCPI= is an =xs:float=
   in the schema and the generated binding has no lexical form.

* Notes

- The import and the export now key the CPI leg the same way, on
  =LegType == CPI=, and both take the first such leg. Before that the import
  keyed on "the leg carries a CPILegData" and the export on the leg's type, so a
  leg typed otherwise lost its index on the way out; and with two CPI legs the
  export wrote the first leg's values onto both.
- Open, recorded rather than fixed: an =InflationSwap= stated with a =YY= leg
  hits the same refusal, because neither direction has a YY branch. Captured as
  =an-inflation-swap-on-a-yy-leg-cannot-be-stored=.
- Open, recorded: the store's =check (base_cpi > 0)= refuses a =BaseCPI= of zero
  or below, which the schema's =xs:float= admits. Kept, because an index level of
  zero is not an economic value and no document in the corpus states one; a
  finding needs evidence, and this is a conflict to decide rather than a defect
  to fix here.
- An unstated observation lag is stored as an empty string in a nullable column,
  so "not stated" and "stated empty" are one value in the store. That is the
  component's nullable-string pattern, not this unit's.
- No test exercises the insert. The store's two constraints were confirmed by
  querying =pg_constraint= on a recreated database, and the mapper case proves
  the value is now supplied, but nothing asserts the row reaches Postgres. A
  pgTAP case pinning the check would close that gap and is not in this unit.
- The case's two halves are independent: the export half is fed values the
  document never stated, so a reverse that wrote a constant fails there rather
  than being carried by the import's own output.

* Result

An inflation swap is stored with the index, base level and lag its document
states, and exports them back. The import reads them from the CPI leg; the
export writes them onto the same leg, which the shared leg reverse leaves with
no payload at all.

Proved red first: against the merge base the case fails on an empty
=inflation_index_code= and an absent =base_cpi=; after the change it passes
fourteen assertions, three of which name =UKRPI=, =210= and =2M= and three of
which name values the document never states, so the two halves cannot carry each
other.

Money: =BaseCPI= is an =xs:float= in the schema, and the generated binding is a
plain =float= with no lexical form, so the digits are the schema's own limit and
a value from the document round-trips float to double to float unchanged. Two
consequences worth naming. The leaf re-spells a document's =114.4= as
=114.400002=, because the serialiser prints a float at nine significant digits.
And the export adds one double-to-float conversion, which is not one of
finding 7's sites: those are casts that discard a lexical form the leaf could
have carried, and this leaf cannot. Giving it one would be a codegen change of
the =moneyFloat= kind the FX rework made, and it is not this unit's.

A trade imported before this unit was left half-written: its trade row and its
=rate_instruments= header exist, and it has neither a fact nor any legs, because
the instrument save is non-fatal and the leg writes come after it. Nothing needs
migrating, but re-running the import is not the remedy: the planner mints a
fresh trade id per trade, so a second run adds a duplicate and leaves the broken
header in place. Delete the =rate_instruments= header first, which cascades the
family, and then the trade: a trade delete does not reach the header, and the
import's own cleanup closes bookings only.
