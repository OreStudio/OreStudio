* Goal

Implement the =IMM_ROLL= branch of the tenor resolver
(=ores.marketdata.api::domain::resolve_end_date()=), which currently
throws =std::logic_error= whenever
=tenor_convention.resolution_algorithm= is =IMM_ROLL=. This means
stepping through [[id:013BC5B0-9461-4AD4-A55E-374BCF34D8A4][IMM Dates]]'
quarterly roll schedule by =offset_multiplier= roll-quarters from the
horizon's most recent roll, rather than the anchor+offset arithmetic the
=ANCHOR_OFFSET= branch already implements. Also seed the
=tenor_convention_resolution= rows for the =CREDIT_CDS_IMM= convention
(=offset_unit = 'ROLL_QUARTER'=, =offset_multiplier= = the roll-quarter
count per nominal tenor, e.g. =1Y 1RQ=) — deliberately not done in the
originating task since the exact roll-quarter-per-tenor mapping was not
sourced anywhere in the knowledge cluster and fabricating it would have
been a hack.

* Result

Already delivered. Nothing was implemented for this task, because main already
does it and the capture it came from had gone stale.

The capture was right when it was written: the resolver threw for an =IMM_ROLL=
convention. The unified tenor resolution work then superseded that design. The
algorithm vocabulary is now =(ANCHOR_OFFSET, SCHEDULE_STEP)=, the old
=IMM_ROLL= algorithm row is gone, and =IMM_ROLL= survives only as a
=measured_from= anchor. =CREDIT_CDS_IMM= is seeded as a =SCHEDULE_STEP= row
whose schedule is =ROLL_QUARTER=, in
=refdata_tenor_convention_resolutions_populate.sql=.

The resolver computes the roll closed-form in
=projects/ores.refdata/api/src/domain/tenor_resolution.cpp=:
=roll_quarter_date()= takes the 20th of the March/June/September/December
quarter and advances to the next weekday, and =walk_roll_quarter()= counts the
requested quarters forward from the anchor. That is the rule
=doc/knowledge/domain/imm_dates.org= states, which defines the closed form as
"20th + business-day adjustment" rather than the third-Wednesday form used
elsewhere in the industry.

Two tests pin it: =resolve_end_date_migrated_credit_cds_imm_resolves_to_pinned_roll_quarter=
and =resolve_end_date_walks_roll_quarter_from_anchor_with_zero_offset=, both in
=domain_tenor_resolution_tests.cpp=. They pass, and =ores.refdata.api.tests=
passed in the full gate.

Acceptance met as written above, by the earlier work. No code changed here.

** Why

The persisted tenor data model (=tenor=/=tenor_anchor=/
=tenor_convention=/=tenor_convention_resolution=) was deliberately
designed so credit/CDS's genuinely different resolution algorithm fits
without a schema change: =resolution_algorithm= and the
=offset_unit=/=offset_multiplier= columns already accommodate it. Only
the resolver code and CDS-specific seed data are outstanding — this
capture exists so that gap doesn't get silently forgotten once the
["DQ dataset for tenor reference data"] work closes as apparently
complete for two conventions.
