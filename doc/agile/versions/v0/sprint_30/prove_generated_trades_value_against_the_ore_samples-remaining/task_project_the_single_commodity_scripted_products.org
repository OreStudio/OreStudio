* Acceptance

- The projection writes and reads the Asian option, accumulator, TaRF, generic and window barrier options, strike resettable option and forward volatility agreement.
- Each of them is built by its builder, and the planner calls it.
- The carrier holds the range bounds the accumulator and TaRF pay on.
- Their entries leave the known lists, or stay with a market data reason.

* Plan

ORE reads each of these types from a =<TradeType>Data= element, as the
engine's =fromXML= shows. The equity accumulator, TaRF and Asian option
already state the same shapes, so the commodity writers and readers mirror
them and use the same shared blocks.

1. Give the commodity carrier the range bounds, in the shared range bound
   rows the FX and equity accumulators use, and add its entry to the batch
   mapper.
2. Add the columns the forward volatility agreement and the strike
   resettable option state flat, through codegen: the FVA date, the premium
   date, the settlement date, the implied volatility strike, the reset
   strike, the trigger type, the trigger price and the premium amount. They
   land through the scalar terms table by their ORE elements. The option
   expiry is the maturity date, and the underlying strike is the strike.
3. Add the six types to the projection's table of products. Add commodity
   tables for barrier holders and product schedules, as the equity
   projection has, and read and write the range bounds of the accumulator
   and the TaRF.
4. Add a builder for each type, register it, and call it from the planner.
5. Record the generated trades, run the ORE engine test, and update the
   known lists.

The window barrier option stays out of this task. ORE's engine reads
=CommodityWindowBarrierOptionData=, but ORE's XSD does not declare it, so
the generated schema refuses to write it. The bindings generator has no way
to supplement ORE's schemas. That mechanism is a design of its own, so it
goes in a task of its own, and the type stays a passthrough until then.
