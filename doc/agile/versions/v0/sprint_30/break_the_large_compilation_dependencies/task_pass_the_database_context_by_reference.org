This page documents a [[id:31C868B9-306E-4282-BA8C-07E647021B34][task]] in the [[id:2B6612F6-D9F8-4DFF-8952-61716D22C2CF][Break the large compilation dependencies]] story. It captures the goal, current status, acceptance, and any notes or results.

* Goal

=ores.database::context= is passed by value through most repository and service signatures and stored by value in most services. Every header that names it includes =context.hpp=, and through it =pq/connection.hpp= (with =libpq-fe.h=), =pq/pool.hpp= (with =<mutex>= and =<condition_variable>=) and =pq/transaction.hpp=. Most of those headers only pass the context along. This task passes the context by reference, forward-declares it where it is only named, and keeps the connection detail out of its header, so a change to the context or to libpq rebuilds only the code that uses them.

* Acceptance

- A parameter that only reads or forwards a context takes =const context&=. A context stays a value where it is stored, such as a service's =ctx_=, and where it is returned, such as =with_tenant=, =with_party=, =with_roles= and =with_transaction=.
- Every place that keeps a context past the call, or captures it in a lambda that can outlive the call (an async handler, a thread, a deferred task), takes a copy. A script lists these places before the change, and the task records each one, because a compile does not find a dangling reference.
- =ores.database/domain/context_fwd.hpp= declares =class context;=. A header that only names a context includes it, not =context.hpp=.
- =context.hpp= includes neither libpq nor the pool:
  - the pool slot (=pq_slot=: mutex, pool, size) is held behind a pointer to an incomplete type, defined in the =.cpp=;
  - =pq::transaction= is forward-declared, since the context only holds a pointer to it;
  - =connection_options= and =open_policy= move to a small header without =libpq-fe.h=.
- The analysis of [[id:2E186CC8-BA83-4271-8EF0-DE2465994A8D][Find the headers that couple the build]] decides whether the context splits in two: the service-lifetime part (connection options, open policy, pool) and the per-request part (tenant, party, visible parties, actor, service account, roles, transaction). If it splits, this task does the split and records why.
- The repository and service codegen templates emit the new signatures and includes. Generated code is regenerated, not edited. Hand-written code moves by a codemod script, kept with the task, so it reruns.
- The rules of [[id:31F9FEF5-4693-4C63-AE93-E74BA88DE175][A context bound to a transaction cannot change its tenant or party]] hold unchanged, and their tests pass.
- Measured before and after, at named commits: the objects that depend on =context.hpp= and on =libpq-fe.h=, and the rebuild time after =context.hpp= is touched.
- Every test suite passes.

* Plan

The analysis that re-scoped this task is =Investigation: The headers that
couple the build=, which lives on branch
=feature/find-the-headers-that-couple-the-build= and lands in its own PR. It
settles two things this task must respect.

- The rebuild saving is inside =context.hpp= and not in its users. Cutting the
  include from all 1738 repository headers saves one object; cutting every
  header in the tree still leaves 179 of 365 objects reading the header.
- The =const context&= change is worth doing for run time (21874 copies) and not
  for rebuilds. The one lifetime-sensitive capture in the tree is synchronous
  (=ores.synthetic/service/src/feed_kind_registry.cpp:492=), so the change is
  safe today, and it must stay checked.

The work runs in a series of commits, each one verifiable on its own:

1. *Split the options out and hide the slot.* Add =pq/options.hpp= holding
   =connection_options=, =open_policy= and =backoff=, add =domain/context_fwd.hpp=,
   forward-declare =pq::pool=, =pq::transaction= and =pq::session_context= in
   =context.hpp=, and move =pq_slot= and the constructors into the =.cpp=. No
   signature changes, so no call site changes. This is the commit that moves the
   =pq= family's blast radius.
2. *Emit the new form from the templates.* Change the =repository= archetype to
   take =const context&=-, and regenerate. The service keeps a by-value
   constructor because it stores a copy.
3. *Move the hand-written call sites* with a codemod kept with this task, so it
   reruns.
4. *Add the check* that fails when a header includes the definition of a type it
   only names, with the type list the analysis produced.

Commit 1 is the only one that changes which headers are parsed. Commits 2 and 3
change copies into borrows, and their evidence is the run-time side plus the
pattern table from the analysis.

*The member keeps its copy.* This was settled by measurement rather than by
taste. Commit 1 on its own took =context.hpp= from 6.60 s to 2.85 s: the pool,
libpq, the codec chain and =<mutex>= left the header, so what remains is the
options, =tenant_id= (and the clock and format headers behind it) and the
standard containers. A pointer member would only stop the service headers
parsing those 2.85 s, and it would cost 103 use sites that become dereferences
plus a change in who owns the context: a =shared_ptr= shares the caller's
identity object and adds nullability, a reference member dangles, a pimpl needs
a declared destructor and moves every inline accessor. The same 2.85 s is
better attacked at =tenant_id.hpp=, which needs no ownership change at all.

So the templates take the context by =const context&=, and the =ctx_= member
stays a value. The copies that remain are one per service construction, which is
the ownership the services already had.

*The one place that must keep its copy.* The service runners are coroutines
(=boost::asio::awaitable=), and a coroutine keeps its parameters across every
suspension point. Taking their context by =const&= bound a reference to the
temporary at the call site, which died at the end of that statement while the
coroutine carried on. The IAM service then read a freed context and aborted with
=cannot allocate / corrupted double-linked list= in the pool construction path.

The compiler could not see it, the eleven test suites could not reach it, and
the build was green. Valgrind named it: the first invalid access was
=pthread_mutex_lock= inside =context::pq_pool()=, reached from
=auth_handler= via =run_signing_service=. The fix is to keep =context= by value
in =run_signing=, =run_signing_service=, =run_domain_service= and the two runner
front ends, and =context_by_reference.py= now refuses to convert them so a rerun
cannot reintroduce it. This is the case the acceptance criteria names: a
reference that outlives its call, which a compile never finds.

* Notes

Found during the publish lifecycle work: a change to =context.hpp= rebuilt most of the tree. A copy of a context costs a few small allocations and one atomic increment on the shared pool slot, which is small beside a database round trip, so the main gain expected is compile time, not run time. The task may measure the run-time cost too, but it does not need to.

*The declaration is used, not just declared.* The first cut of this task added
=context_fwd.hpp= and left every header including the definition, so the forward
declaration that makes the saving possible had no users. The check that now
guards the rule found 88 hand-written headers in that state and 87 of them now
take the declaration.

Two header families still include the definition and are recorded in the
baseline. The =repository= archetype emits it in 539 headers, and its
implementation does not include it itself, so the swap is two lines in the
archetype and a rebuild of five hundred files. That is the header-family work of
[[id:DEA440DD-F4B6-4D37-9083-5F3BB33F1018][Forward-declare what the analysis finds]], whose PR has to state the measured
effect. =cpp_convention_family_units= is one file and goes with it.

*The sweep must reach the models and the templates.* A =#+begin_src cpp=
block in a =modeling/*.org= file is pasted into a generated file, so a parameter
written there is a real parameter; editing the generated output instead puts the
tree out of step with its models, and the drift gate says so. A template is code
in the same way: a change to it is verified by regenerating and building, not by
reading the diff, and nothing compiles a =.mustache= file until a regeneration
puts it into the tree. =context_by_reference.py= has a mode for each layer
(=--templates=, =--models=, =--sources=, =--includes=) and each is run before the
code is regenerated, so the rerun after a rebase reproduces the whole change.

The check reads =build/scripts/forward_declarable_types.list=, which the analysis
feeds, and errs towards silence: a use it does not recognise counts as needing
the definition. That is the safe direction. A false offender would ask for an
include that does not compile; a missed one only leaves the debt where it was.

Do this after [[id:2E186CC8-BA83-4271-8EF0-DE2465994A8D][Find the headers that couple the build]], so the forward-declaration header and the split follow the conventions the analysis sets.
