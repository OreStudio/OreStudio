* Goal

A scheduled report run acts as the tenant and the party of its definition, with
no caller present. The steps of the run read and write the owners' data through
their operations, and row-level security applies as it does for a person.

Today a step calls the owners with its own service identity, which acts for the
system tenant and sees no party rows. This story builds the
[[id:C79B5E4D-71D0-44C2-9D06-444EA2AC1CB7][Scheduled Work Acting as a Tenant]] pattern as [[id:78B82824-0BBB-4442-A9FA-E1F265DF57BD][Run grants and run tokens]] specifies it, and wires it into reporting as
[[id:B3165E6F-AE8C-4DBD-8F87-2EC4F276FCF0][Report execution at scale]] describes. It unblocks the backlog task "Package the run input
through the owners' operations", in the story Complete the ORE report
configuration, which needs a run token to call the owners.

* Acceptance

- IAM stores run grants and serves =iam.v1.run_grants.create=, =revoke=, =get=
  and =exchange=, with the checks and claims the IAM page states.
- A run token carries the grant's tenant and one party, the role's permissions
  intersected with the grantor's, and the =act=, =grant_id= and =run_id= claims;
  every issue is logged.
- Every step service obtains run tokens through one shared cache in
  =ores.service=.
- Reporting creates, revokes and re-creates grants with the schedule, and
  suspends a definition whose grant lapses.
- A live test: a scheduled run's step reads a party's configuration document
  through its owner with a run token, and the same read with the service token
  returns nothing.

* Decisions

- *The design is settled.* [[id:78B82824-0BBB-4442-A9FA-E1F265DF57BD][Run grants and run tokens]] and [[id:B3165E6F-AE8C-4DBD-8F87-2EC4F276FCF0][Report execution at scale]] state the entity, the checks, the
  claims and the cache rules; this story implements them and records only
  departures from them here.
- *Reporting acts on schedule and unschedule now.* A manual run's grant, the
  suspension on =grant_lapsed=, the revoke on delete and the re-grant on a
  change of party each need the exchange or a person's token reporting does not
  hold, so they move to the exchange task.

* Out of scope

- The admission quotas, the step concurrency limits and fair dispatch in compute:
  the scale half of the reporting design.
- Packaging the run input, which is its own task in the backlog story and
  follows this one.

* Result

Closed with all four tasks DONE. A scheduled run acts as its definition's tenant
and party: IAM holds the tenant-scoped, party-isolated bitemporal run grant and
serves =create=, =revoke=, =get= and =exchange=; the exchange makes its five
checks in order, intersects the role's permissions with the grantor's, mints a
five-minute token carrying the =act=, =grant_id= and =run_id= claims, and logs
every issue; one shared cache in =ores.service= holds the tokens the step
services exchange; and reporting creates, revokes and re-creates grants with the
schedule.

Evidence, and its limits.

- The live chain reached =submit_compute= with =gather_trades=,
  =gather_market_data=, =assemble_bundle= and =prepare_ore_package= complete,
  and run =fccf4a19-5927-4678-852c-0b2b45015b4f='s issue log holds four
  =issued= rows — two from ReportingService and one each from OreService and
  ComputeService — so every step service exchanged through the cache and none
  was refused. The grant is recorded on the report instance at admission, so a
  reschedule cannot change an in-flight run's authority.
- The run did not reach =completed=, and that is not this story: the wrapper
  fleet was bound to the system tenant, so no wrapper subscribed to a tenant
  run's assignment, and =collect_compute_results= was still a pass-through.
  Both belong to [[id:3D1D3F74-12B2-408B-A84A-C9E6B1CA16AA][Run an example bundle through the compute grid from a report definition]],
  which is where the rest of the run now sits.
- The last acceptance bullet's scenario,
  [[id:16526A07-0976-43EA-BC1F-DCF5EF0B9011][Verify a run step acts as its party]],
  is still PENDING. Its positive half is what the live run shows; its negative
  half — that the same read with the service token returns nothing — the code
  asserts but no one has walked. It stays open against the story that now owns
  the run, rather than being closed with this one.

Three defects were fixed on the way, each because a check scoped a shared
registry to the caller's own tenant: the report instance FSM guard read its
states under the row's tenant, and both the workunit insert trigger and the
workunit dispatcher refused or hid a system-tenant app version and its
per-platform package. The last two are fixed in the codegen as a
=:system_tenant_visible:= read scope, so the generated code states the rule.
