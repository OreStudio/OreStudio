* Goal

A system administrator finds a tenant among many and acts on it from the roster: they search by code, name or hostname, filter by type and status, page through the list with its total, open a tenant's detail, and reach the operations a tenant offers from its row.

* Acceptance

- The roster searches over code, name and hostname, and pages with a total.
- The roster filters by tenant type and by status, and the See the tenants journey and its wireframe record both filters.
- The tenant type renders as a badge from the badge catalogue, the way the status does.
- Each row carries an actions menu: open the tenant, resume setup when its run is unfinished, and the retire or reset journey.
- Opening a tenant shows its details, its provisioning run and its parties, from a journey document written first.
- Every new behaviour is proved by a test, and each screen was read against the running deployment.

* Notes

- *The journey already asks for part of this.*
  [[id:F14135EC-F136-4D93-B8A6-D4386FF20684][See the tenants]] specifies a search
  field over code, name and hostname, paging with a total, and picking a row to
  go on to another operation. The task that built the roster,
  [[id:18E4CA0F-0668-46F2-97D3-A5EF58522928][Show the tenants a deployment holds]],
  closed DONE without them, because its acceptance did not carry them.
- *The proposed layout.* A page header with the title, a one-line description
  and *New tenant*; a search field and type and status filters above the table;
  columns code, name, hostname, type, status and actions; a footer that counts
  the rows shown against the total.
