#+title: How do I add a compute batch from the shell?
#+description: Create a compute batch with an external reference from the shell; the job count belongs to dispatch, not to the batch.
#+type: recipe
#+level: cross
#+filetags: :recipe:shell:compute:batch:
#+created: 2026-08-11
#+updated: 2026-09-26

The compute entity verbs live in their own shell menus, one per entity
(=apps=, =app_versions=, =platforms=, =batches=, =hosts=, =workunits=,
=results=). They talk to the ~ores.compute~ service over NATS; the
domain shapes and table renderers come from ~ores.compute.api~.

* Question

How do I add a compute batch from the shell?

* Answer

Log in as the system super admin (principals are =username@hostname=),
then run =batches add= with the batch external reference, the opening
status and an audit reason and comment. The external reference is the
script-friendly handle you use to dispatch and watch the batch later.

#+name: add-compute-batch
#+begin_src ores-shell :exports none
connect $ORES_NATS_URL
login super_admin@localhost Secure-Password-123
batches add $BATCH_REF open system.new_record "compute batch"
logout
exit
#+end_src

#+begin_src sh :noweb yes :results output :wrap example
./ores.shell ${log_args} ${connect_args} << 'EOF'
<<add-compute-batch>>
EOF
#+end_src

The command prints the created batch, including its id. The batch row
stores no job count: the count is session knowledge that you pass again
at =compute dispatch-batch=. A batch the grid must pick up starts
=open=; dispatch moves it to =dispatched=, and the grid closes it when
the last result arrives. =system.new_record= is the reason a row records
when an operator writes the first version.
