#+title: Parallelise bundle publishing
#+description: A bundle's datasets are published one after another, and that is most of a bootstrap's wall clock. The chain can now say which datasets are independent.
#+type: capture
#+level: cross

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

A bundle is published one workflow step per dataset, and the steps are chained so
that each waits for the one before it. Most of those datasets are independent of
one another, so most of that waiting buys nothing. The chain should say which
datasets actually read another dataset, and the rest should publish together.

* Why

Measured on a tenant bootstrap from the =acme_demo= profile, 2026-10-08, bright
faraday:

| step                  | ran for                |
|-----------------------+------------------------|
| system_provision      | ~1s                    |
| publish_bundle        | *2m 14s*               |
| import_lei_hierarchy  | ~0s                    |
| provision_party       | ~4s                    |
| load_staff            | ~7s                    |
| attach_photos         | ~11s                   |
| start_market_feeds    | beside the party chain |
| complete_provisioning | ~4s                    |

The run took 2m 41s end to end, so =publish_bundle= is about *83%* of a
bootstrap's wall clock, and it is now the only thing between a bootstrap and
being quick. The engine already runs independent steps together -- the same
change that lets =start_market_feeds= run beside =import_lei_hierarchy= -- so the
work here is not in the engine. It is in saying what a dataset depends on.

The chaining is deliberate and conservative rather than an oversight. When the
engine became a graph, a chain whose steps declare nothing runs flat, so
=bundle_publish_workflow= now declares that each dataset reads the one before it.
That was the only statement of dependency available and it preserved the order
that the ordinal used to carry. It is a placeholder for a real answer, not the
answer.

* Open questions

- *Where does the dependency live?* It is a fact about the datasets, and the
  datasets are DQ rows, so it could be a relation between them, a field on the
  dataset, or derived from what each publisher writes. Choosing this is the
  actual work.
- *Is publishing two datasets at once safe for the target tables?* Reference data
  has foreign keys between its tables, so a dataset that writes a child table may
  need its parent's rows to exist first even where it does not read the parent's
  dataset. Reading and depending are not the same relation.
- *What happens when one of a parallel batch fails?* Compensation order is
  derived from the graph's topological order, so a batch that fails part-way must
  still roll back in an order that respects the real dependencies.
