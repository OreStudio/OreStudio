* Plan

** Two flags, in the shape the party already uses

The party carries =is_registration_default= as a boolean column with =:default:
false= and a partial unique index over =tenant_id= where the flag is set and
the row is live. Both new flags take that shape, because a reader of either
model has already seen it.

| entity | flag | owner the index scopes |
|--------+------+------------------------|
| =counterparty_identifier= | =is_authoritative= | =counterparty_id= |
| =party_contact_information= | =is_primary= | =party_id= |

** Why a partial unique index and not a check

A check sees one row, and "at most one per owner" is a statement about a set.
A partial unique index is the only store-level shape that states it, and it
already states the same thing for =is_registration_default=. It also means a
second write that claims the mark is refused rather than silently leaving two
rows that both claim it.

** The precedence is the generator's default, not a rule

Journey 5 inferred the authoritative identifier by precedence, LEI first and
then BIC, because the column did not exist. The generator marks the first
identifier it makes for a counterparty, and the ten schemes rotate, so that row
carries LEI. Nothing in the store derives the mark from the scheme: the tenant
states it, and the precedence is only what a screen starts from.

The primary contact has no precedence to copy. The generator marks the first
row it makes for a party, which is the Legal contact.

** What this does not do

It does not make the flags settable from a journey screen. That is the jobs of
the screens themselves. Nor does it add the flag to the legacy Qt detail
fields, which =is_registration_default= is also absent from.

* Result

Every acceptance criterion holds on PR #2840.

=counterparty_identifier= carries =is_authoritative= and
=party_contact_information= carries =is_primary=, both =boolean not null
default false=. Each has a partial unique index over the owner, so the store
keeps at most one live row per owner with the flag set:

#+begin_src sql
create unique index if not exists counterparty_identifiers_authoritative_identifier_uniq_idx
on "ores_refdata_counterparty_identifiers_tbl" (counterparty_id)
where is_authoritative and valid_to = ores_utility_infinity_timestamp_fn();
#+end_src

Each flag is carried on 14 generated surfaces, symmetrically: the C++ domain
and write record, the repository entity and mapper, the history field mapper,
the service's table display, the generator, the shell command, and the
TypeScript domain and protocol.

The pgTAP suite =refdata_ownership_marks_test.sql= makes seven assertions: a
first claimant is accepted, a second is refused with =23505=, and a row that
leaves the mark alone is accepted, once for each flag, plus the count of
primary contacts on the party. Every fixture value it uses was checked against
the seeded schemes, contact types and lookup tables by reading them: =LEI= and
=BIC= and =MIC= are seeded schemes, =Legal= and =Operations= are seeded contact
types, and =WRLD=, =Operational=, =Bank=, =Corporate= and =Active= are the
values the neighbouring party and counterparty suites already use.

This branch also repairs what main had drifted: five categories of shell recipe
script, the shell recipe inventory, the physical-space field-group
description, the trading structure service, and the ER diagram. Each is the
output of its generator.

**What this task does not land.** The flags are not settable from a journey
screen; that is the screens' own tasks. A write that marks a second row while
the first still holds the mark is refused, so the screen that changes the mark
has to clear the old one in the same save, which the journey documents do not
yet say.
