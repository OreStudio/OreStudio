# Handover: the generated HTTP recipes send no request body

For the agent working in **MASD-Project/compass**, the C++ compass, on the
machine that owns that checkout. This document is self-contained: it states
what is wrong, where the faults are, the exact data contract ORE Studio's
template will consume, and how to prove the fix.

Written 2026-11-25 against compass commit `8259d8b2ae` (tag `v0.0.13`, the
build installed on the ORE Studio development machine). Line numbers are that
commit's.

## Why this is being asked

ORE Studio's C++ HTTP gateway (`ores.http`) is served by a library of Hurl
recipes generated from its entity models. The recipes exist to prove that each
route is wired to the service behind it. **None of them sends a request body or
the parameters its route requires**, so every write route answers 400 and the
recipe proves the opposite of what it asserts.

The ORE Studio task is *Generated HTTP recipes send no request body*, task
`60BBB3B1-6083-4A78-B51D-4FD2E81C54C2`, in story `FBF532B1-01B3-458D-ADC2-72F96027946E`.
Its acceptance:

- Every generated write recipe emits the body its route takes.
- The harness replays the corpus, and every recipe that asserts a 200 reaches
  its handler.
- A check fails when a generated recipe has no body, so the corpus cannot
  drift back.

The body cannot be written on the ORE Studio side: the recipe document, the
Hurl file and the request shape all come from compass. That is what this
handover asks for.

## The chain, as it stands

1. `codegen` codec, template `http_recipe.org.mustache` (in the ORE Studio
   repository, rendered by compass) turns an entity model into
   `doc/recipes/http/<plural>/<singular>.org`.
2. `http_recipe_library` codec, in this repository, tangles the `#+begin_src
   hurl` blocks of those documents into
   `projects/ores.http/scripts/library/<plural>/<plural>-<command>.hurl`.

Both stages lose the body: the template has no body to render, because the
codec supplies none.

## Fault 1: the recipe carries no body

### Where

- `projects/compass.codegen/src/ops/template_context.cpp:278` —
  `write_http_recipe`. It sets `command`, `heading`, `block`, `id`, `name`,
  `status`, `method_upper`, `pattern`, `subject`, `requires_session`,
  `commentary`, and nothing that describes the request.
- `projects/compass.codegen/src/ops/entity_surfaces.cpp:520` –
  `write_http_route`, which builds the route row. **It already sets `has_body`
  at line 631** (`get_many`, `put`, `put_many`, `delete_many`), and the row
  already carries `request` (the request message's name), `keys[]`, `kind`,
  `has_intent`, `allows_version`. Nothing new has to be derived: it only has to
  be copied into the recipe's endpoint rows and turned into text.
- `projects/compass.codegen/src/ops/entity_messages.cpp:236` — the `fields` of
  each message: `name`, `cpp_type`, optional `default`, `ts_type`. This is
  where a body's members come from.
- `projects/compass.codegen/src/ops/template_context.cpp:558` —
  `write_operation_http_route`, for the `:http_route:` operations. Every one of
  its routes is a POST and it sets no `has_body` at all.

### What the route actually accepts

The ORE Studio route parses the body with the generated JSON codec, which
default-constructs the request and reads the members it finds
(`projects/ores.utility/include/ores.utility/codec/struct_codec.hpp:70`:
`T out{}; detail::read_object(…)`). Therefore:

- A member that is absent keeps its default, so `{}` **is** a valid body: the
  request reaches the service. That is the acceptance's "reaches its handler".
- A `std::optional<…>` member is best left out of the body.
- A nested written row (`tag_change`, `tag_removal`, `change_intent`, `order`)
  can be emitted as `{}`, which default-constructs it.

### The data contract ORE Studio's template will consume

Add these per endpoint row in `write_http_recipe`, with exactly these names:

| Member | Type | Meaning |
|--------|------|---------|
| `has_body` | bool | the route parses a body: the route row's own `has_body`, or true for every route of `write_operation_http_route` |
| `body` | string | the JSON text, one line, no trailing newline; empty when `has_body` is false |
| `content_type` | string | `application/json` when `has_body`, else empty |
| `has_query` | bool | the route takes required query parameters instead of a body |
| `query` | string | the query string without `?`, URL-encoded; empty when `has_query` is false |

ORE Studio's template will then render, inside the same `<% %>` delimiter
block:

```
<%method_upper%> {{base_url}}<%pattern%><%#has_query%>?<%query%><%/has_query%>
Accept: application/json
Authorization: Bearer {{token}}
<%#has_body%>Content-Type: application/json

<%body%>
<%/has_body%>HTTP <%status%>
```

So the shape of the endpoint loop is fixed from the ORE side; the names above
are the contract.

### How to build the body

For a route with `has_body`:

1. Read the route's `request` member, and find the message with that `name`
   among the owner's `messages`. The owner is the `domain_entity` (or
   `junction`) whose `http_route.routes` these are, and for an operation its
   `operation` row. If no such message exists, use `{}`.
2. For each field of that message, in order:
   - a `std::optional<…>` field is **left out**;
   - a `std::vector<…>` field is `[]`, except a vector whose element type ends
     in `_key`: that one gets one element, an object holding the route's own
     `keys[]` (each `name` with the sentinel for its `cpp_type`) — so a
     `get_many` body is `{"keys": [{"name": "example-name"}]}`;
   - a field whose `cpp_type` the sentinel table knows becomes that value as a
     JSON literal (strings, dates, timestamps and UUIDs quoted; numbers and
     booleans bare);
   - anything else is `{}` — a written row, which default-constructs.
3. Join the members as `{"a": …, "b": …}` on one line.

Worked example, the `tags` entity, which is what a reviewer will read first:

| Command | Method and path | Body |
|---------|-----------------|------|
| `get-many` | `POST /api/v1/assets/tags/get-many` | `{"keys": [{"name": "example-name"}]}` |
| `add` | `POST /api/v1/assets/tags` | `{"change": {}, "intent": {}}` |
| `set` | `PUT /api/v1/assets/tags` | `{"change": {}, "intent": {}}` |
| `put-many` | `POST /api/v1/assets/tags/put-many` | `{"changes": [], "intent": {}}` |
| `delete-many` | `POST /api/v1/assets/tags/delete-many` | `{"removals": [], "intent": {}}` |

(`delete` is deliberately absent: see fault 3.)

## Fault 2: the path sentinel is the shell's absent token

`_sentinel_for_field` falls back to `__none__` — the shell's "this argument is
absent" token — for `std::string` and for every unmapped type, so 127 recipes
send it inside a URL path.

- `projects/compass.codegen/src/ops/entity_surfaces.cpp:65` —
  `sentinel_value`, whose table maps `std::string` and
  `std::vector<std::string>` to `__none__`.
- `projects/compass.codegen/src/ops/entity_surfaces.cpp:88` —
  `sentinel_for_field`.
- `projects/compass.codegen/src/ops/template_context.cpp:223` —
  `sample_path`, the only caller that puts a sentinel in a URL.

### What to do

Add `surfaces::http_sentinel_for_field(name, cpp_type)` beside the existing
pair and use it **only** from `sample_path`:

- every type the table already maps keeps its value (a UUID stays
  `00000000-0000-0000-0000-000000000000`, a number stays `0`, a date stays
  `1970-01-01`);
- `std::string`, and every type the table does not map, becomes
  `example-<name>` — the field's own name, so `DELETE
  /api/v1/assets/tags/example-name` and `GET /api/v1/assets/images/example-code`.

`example-` is chosen because it reads as a placeholder, stays a single URL
segment, and cannot be confused with an absent shell argument.

**Do not change `sentinel_value` or `sentinel_for_field` themselves.** They
also feed the shell recipes, and the shell's own sentinel defect is a separate
ORE Studio task (`90BDBB0E-45D6-4B38-A2F2-5573306E0B1B`). This change must
leave every `.ores` script byte-identical.

## Fault 3: a DELETE takes its intent as query parameters, not a body

This one is not in the ORE Studio task's text, and it is why 41 DELETE recipes
would still answer 400 after faults 1 and 2 are fixed.

The generated route for a `delete` is registered with `.no_body()` and three
query parameters, two of them required
(`projects/ores.http/assets/src/routes/assets/tag_routes.cpp:425`–`437`, from
the ORE Studio template `cpp_http_route_impl.cpp.mustache:377`–`384`):

```
.query_param("reason", "string", "", true, "Change reason code")
.query_param("commentary", "string", "", true, "Commentary")
.query_param("version", "integer", "", false, "Version")
.no_body()
```

and the handler refuses the request when either required one is empty. So a
`delete` recipe must be

```
DELETE {{base_url}}/api/v1/assets/tags/example-name?reason=__none__&commentary=__none__
Accept: application/json
Authorization: Bearer {{token}}
HTTP 200
```

where the two values are the existing `sentinel_reason` and
`sentinel_commentary`, URL-encoded. Leave `version` out: a recipe that states a
version asserts a precondition it cannot know.

So `has_query`/`query` are set for a route with `kind == "delete"` (in compass
terms: a DELETE method whose row has `has_intent` true): `reason=<…>&commentary=<…>`.
No other kind gets required query parameters; the paging parameters of a list
are optional and are deliberately left out of the recipe.

## The check that stops the drift

A new check codec in this repository, in `projects/compass.docs`, modelled on
`heading_numbers` — the smallest existing check codec, and the one whose shape
is easiest to copy:

- name `http_recipe_bodies`, version `1`;
- summary: *Reports an HTTP recipe that sends no body or not the parameters its
  route requires.*
- `reads = ct::inputs::every_document()`;
- one option, `source`, default `doc/recipes/http`, described as "The
  directory of the generated HTTP recipes, read recursively";
- one rule: `{"recipe_request", "An HTTP recipe sends the body or the
  parameters its route requires.", {}, ct::blame_method::line}`;
- `enabled_by_default = false`, registered in
  `projects/compass.docs/src/codecs/catalogue.cpp:44` beside
  `http_recipe_library`, with a header in `include/compass.docs/codecs/`.

Its `run` walks each document under `source`:

1. Skip a document whose `#+generated:` line does not name
   `http_recipe.org.mustache` — the hand-written recipes that predate the facet
   are not this codec's business.
2. For each `#+begin_src hurl` block that states a `:tangle`, read the request
   line (the first line that is neither blank nor a `#` comment):
   - `POST`, `PUT` or `PATCH`: the block must carry a blank line followed by a
     non-empty body line, before the `HTTP` line. Otherwise report
     *the recipe sends no request body*, remedy *the body is generated: fix the
     codec or the template, never the recipe*.
   - `DELETE`: the request line must state `reason=` and `commentary=`.
     Otherwise report *the recipe sends neither a body nor the parameters its
     route requires*.
3. Report at the block's first line, severity error.

Tests: a document with a body and one without, and a DELETE with and without
the two parameters, in the style of
`projects/compass.docs/tests/codecs_recipe_libraries_tests.cpp:98`.

## Non-goals

- The shell recipes and their sentinel. A separate task owns those, and this
  change must not alter a single `.ores` file.
- The hand-written recipes under `doc/recipes/http` that predate the facet.
- The status line each recipe asserts. It stays `HTTP 200`; whether a write
  that reaches its handler answers 200 or a domain refusal is a fixture
  question, and it is recorded on the task rather than solved here.
