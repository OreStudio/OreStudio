* Decisions

- *The probe answers for systemd-run, not for the manager.* The busctl
  transport exists because the sandbox refuses sd-bus clients on the user
  manager's private socket, and systemd-run is one of those clients. A
  probe that goes through busctl therefore proves the manager answers
  =busctl=, not that a scope can start.
- *The scope is a resource cap, not a correctness requirement.* Losing the
  =app-build-= slice cgroup inside a sandbox is acceptable, because the
  sandbox is the boundary. The unscoped fallback already existed for a
  manager that does not answer.

* Out of scope

- The other systemd binaries the services pillar shells out to for =tree=
  and =top= (=systemd-cgls=, =systemd-cgtop=). They read cgroup files
  rather than the manager bus, so the transport does not apply.
