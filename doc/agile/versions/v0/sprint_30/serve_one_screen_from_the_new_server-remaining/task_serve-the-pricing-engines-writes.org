* Notes

** A read and a write answer the same document

The document's JSON moved to =pricing_engine_shapes=, so the page, the two
reads and the two writes that answer a document state its members once. A
create would otherwise be a second statement of the screen's contract, and the
two would drift the first time a member changed.

** The configuration header's write is shared with the engine settings**

Both families register a reporting configuration before their record and remove
it again when the record is refused, so =register_configuration=,
=remove_configuration=, =party_for_new= and =intent_or_none= moved to
=reporting_configuration_rows=. The type code and the owning component are the
caller's, because they differ: engine settings are =engine_settings= and owned by
=ores.reporting=, pricing engines are =pricing_engines= and owned by
=ores.analytics=.

** The party and the time are the service's to stamp**

The gateway writes the nil party and the epoch on every row, as the BFF did. The
service stamps the party of the session that saves the document and the time of
its own clock, so a gateway that guessed either would be a second answer. The
tenant is not the service's: the tenant type refuses the nil id, so the gateway
states the caller's own.

** A removal leaves the reporting configuration in place**

The BFF removed the document and left the header, and this does the same. A
report binds a configuration by that header, and a removal that took the header
would break the binding of a report nobody touched. Removing the header belongs
to the screen that manages configurations, not to the removal of a document.

** The limits are the BFF's**

A document holds at most five hundred products and five thousand parameters, and
every name, description and value is bounded as the BFF's schema bounded it. A
document the screen accepts is therefore a document the gateway accepts.

* Result

The pricing engines' three writes are served at the BFF's paths, member names and
status codes, and the document a write answers is the document a read answers.

- A create writes the reporting configuration first and the document second, and
  a refused document removes the configuration again, so a refused create leaves
  nothing behind.
- A change takes the version the screen read and carries the party and the
  configuration the record already fills, so a write cannot move a document to
  another party or another report.
- A removal removes the document through the service that owns it and leaves the
  reporting configuration in place, because a report binds the document by it.
- A document that omits a product or a parameter removes it, which is how the
  service's own save reads a document.

Two statements moved to one home each rather than being copied: the document's
JSON to =pricing_engine_shapes=, so the page, the reads and the writes state one
contract, and the reporting configuration header's write to
=reporting_configuration_rows=, which the engine settings already needed.

The reporting part's suite passes 84 cases and 647 assertions, eleven of them for
these routes, and the inventory pairs 249 of the BFF's 328 routes, reporting 41 of
44.
