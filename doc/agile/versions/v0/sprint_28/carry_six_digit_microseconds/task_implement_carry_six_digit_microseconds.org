* Goal

Every timestamp the platform writes carries six digits of microseconds, and the parser reads them back, so a time_point survives a round trip through the database or the wire to the microsecond.

* Acceptance

- to_iso8601_utc writes six fractional digits and parse_utc_timestamp reads one to six back.
- A time_point survives to_iso8601_utc then from_iso8601_utc to the microsecond.
- The market observation test asserts the round trip and passes.

* Plan

One unit, in =ores.platform=, because the writer and the reader are one
contract: changing either alone is a trap, since a writer that states a
fraction the reader ignores looks fixed until the value is read back.

- =to_iso8601_utc= splits the instant into whole seconds and the microseconds
  under them with =duration_cast<microseconds>= and =floor<seconds>=. It
  formats the fraction itself, because =strftime= has no sub-second field and
  =to_time_t= alone throws the fraction away. The output is always six digits,
  ="YYYY-MM-DD HH:MM:SS.ffffffZ"=.
- =parse_utc_timestamp= reads an optional decimal fraction of one to six
  digits. PostgreSQL states none when the microsecond is zero, so the dot is
  optional. Fewer than six digits are right-padded, more are truncated, which
  is the nanosecond a =microseconds= duration cannot hold. A malformed
  fraction throws rather than being ignored.
- =to_db_string= derives from =to_iso8601_utc=, so it carries the fraction.
  The infinity sentinel is untouched: it is a whole-second literal used in SQL
  comparisons, not a formatted string.

Scope, stated because "to all" would misdescribe it: this is the platform and
wire layers. The *entity* layer cannot follow. =db_timestamp= is
=sqlgen::Timestamp=, which is =rfl::Timestamp=, which wraps a =std::tm= — a
struct with no sub-second field, parsed by =strptime= and written by
=strftime=. No format string can give it a fraction; the container type would
have to be replaced across every entity and mapper. The architecture page
records that asymmetry, so a reader does not expect microseconds from a
=valid_from=.

* Result

=to_iso8601_utc= writes six digits of microseconds and =parse_utc_timestamp=
reads one to six back, so a =time_point= survives a round trip through the
database or the wire to the microsecond.

=ores.platform.tests= passes with 349 assertions in 154 cases, including new
cases for the fraction written, the round trip, fewer than six digits,
PostgreSQL's =+00= form, a whole second with no fraction, and a malformed
fraction that throws.

=ores.marketdata.service.tests= passes with 244 assertions in 44 cases. That
suite is the end-to-end proof: the market observation mapper calls the
platform pair directly, so the tick's microsecond now reaches the
=microsecond= timestamptz column and comes back. Its assertion is the strict
millisecond again, not the whole second main had settled for.

Six suites asserted the writer's old output and were updated: =ores.database=,
=ores.utility=, =ores.shell.api=, =ores.shell.application=,
=ores.marketdata.api= and =ores.marketdata.core=.

=ores.trading.core.digest.tests= fails, and did so before this change: with
the change stashed the same 4 of 5 cases and 48 assertions fail. It is not
this task's defect and is left as found.
