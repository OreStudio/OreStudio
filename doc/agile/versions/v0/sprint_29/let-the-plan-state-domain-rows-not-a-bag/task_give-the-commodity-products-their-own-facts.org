* Acceptance

- CommodityAsianOption states an average type and its averaging window, and the constructor requires them.
- The basket option, rainbow, best entry and worst-of basket swap state numbered constituents, and their constructors refuse an empty basket.
- A provisioning run books every routed code, with constituents and averaging present, and the suites are green.
- The products the family still cannot distinguish are recorded, with what each one is missing.

* Plan

Two products the family can already state correctly, and one gap to name.

The Asian option gains its own terms: an average type and the window it
averages over, both required, because an Asian without an average is not an
Asian.

The four basket products gain members. The family already has
=commodity_basket_constituents=, a table nothing wrote to; a basket product
now constructs its members and numbers them, and refuses a basket of fewer
than two, because one member is not a basket.

The rest of the codes stay as they are, and the task records what each one is
missing rather than drawing it as something simpler without saying so.

* Result

Two more products state what they are. =CommodityAsianOption= requires an
average type and its averaging window, and the planner now draws them instead
of leaving the product as a plain option. The three basket option codes and
the worst-of basket swap construct numbered members, so the
=commodity_basket_constituents= table is written for the first time.

Proved by a provisioning run on a recreated database: 25 rows over 25 codes,
12 constituents over 4 products (three members each), and the Asian option's
row carries =Arithmetic= and a window. The suites are green:
=ores.trading.api.tests= at 485 assertions in 130 test cases,
=ores.synthetic.core.tests= at 1741 assertions in 79.

* What the family still cannot say

This is the part worth reading. Several of the twenty-five codes are still
drawn as a plainer shape, because the table has nowhere to put their facts:

| Product | What it needs | Where it would go |
|---------+---------------+-------------------|
| CommodityDigitalOption | a payout amount | no column |
| CommodityDigitalAveragePriceOption | a payout amount | no column |
| CommodityAccumulator | no target, which it now has by absence | none needed |
| CommodityTaRF | a target amount and target type | no columns |
| CommodityStrikeResettableOption | the reset dates and the strike it resets to | no columns |
| CommodityWindowBarrierOption | the observation window | no columns |
| CommodityGenericBarrierOption | the barrier's own shape, which ORE states per point | no columns |
| CommodityForwardVolatilityAgreement | a volatility strike and a realised-vol leg | no columns |
| IntradayPowerForward | the intraday delivery shape | no columns |
| CommodityBasketOption, RainbowOption, BestEntryOption | how the members combine | members only |

So the basket products can name their members but not say what they do with
them, and the TaRF cannot state a target at all. Those need the family's own
tables, the way the equity family has nine, which is a modelling task and not
a constructor's.
