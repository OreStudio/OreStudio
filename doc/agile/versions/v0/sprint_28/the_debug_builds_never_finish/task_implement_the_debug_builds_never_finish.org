* Goal

The compiler cache turns over inside the repository's allowance, so each Linux
debug leg starts warm and finishes inside its step budget.

* Acceptance

- =SCCACHE_CACHE_SIZE= caps each variant at 2 GB in both Linux workflows.
- A step frees room before the save, oldest entries of the same variant first,
  and only spills onto other variants when that is not enough.
- The verification step warns when nothing was stored, and prunes only when the
  new key is really there.
- The build step gets 350 minutes.

* Plan

Five changes, all in =.github/workflows/continuous-linux.yml= and
=nightly-linux.yml=, which carry the same cache block:

1. =SCCACHE_CACHE_SIZE: '2G'= in the workflow environment. sccache defaults to
   10 GB, which is the whole repository allowance.
2. A new =Make room in the repository cache= step before the save. It lists the
   sccache entries, and while this run's cache would not fit under a 9 GB
   budget it deletes, oldest first: this variant's own entries, then any other
   variant's. It runs the loop through process substitution, because a pipe
   would run it in a subshell and the running total would not survive.
3. The prune step becomes a verification step: it asks the cache service whether
   this run's key is there, warns when it is not, and prunes the older entries
   only when it is.
4. The step cap moves from 320 to 350 minutes, still under the 360 a hosted
   runner allows, which leaves room for the cache save after a slow build.
5. The CI document gains the rule and why the older order could not work.

* Notes

The logic was exercised locally by extracting the step out of the parsed YAML
and running it against a stub =gh= that served a fixture and logged deletes. The
first attempt deleted another variant's cache before its own stale entries,
which is what the fixtures caught: the deletion passes ran in subshells, so the
running total reset between them.

The real proof is the next two scheduled runs: a warm cache should return the
debug leg to about four hours, and its CDash row to green.

* Result

repository cache before saving, warn instead of failing when a save stores
nothing, and give the build 350 minutes. The deletion logic is exercised against
three cache layouts, and it was the fixtures that caught the subshell bug: the
two deletion passes ran in pipes, so the running total reset between them and
the step deleted another variant's cache before its own duplicates.

The proof that matters is the next two scheduled runs: a warm cache should put
