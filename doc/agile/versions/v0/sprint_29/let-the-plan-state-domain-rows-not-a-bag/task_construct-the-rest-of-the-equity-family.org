* Goal

Every equity product is constructed by name. The barrier table's three codes, the digital table's digital and touch, the accumulator table's accumulator and target redemption forward, the swap table's plain and basket swap, and the single-code tables all state what they are instead of being assembled from whichever bag fields happen to be set.

* Acceptance

- Each of the sixteen routed equity codes has a named constructor and the trade type code is fixed by it.
- Two codes sharing a table cannot fill each other's columns; the closed vocabularies are refused at construction.
- The writer holds no per-product assembly for equity; it hands the constructor's product to the batch.
- A provisioning run books the equity family with the same seventeen rows as before, and the suites are green.

* Plan

One header for the family, =equity_instruments.hpp=, holding a terms struct
per product and a constructor per routed code. The cliquet's own header is
folded into it so the family has one home, not one home per product.

The constructors that share a table are separate named functions, not one
function with a type argument, so the trade type code is never a parameter.
Where two products differ by a column, their terms differ by a column: the
digital's terms have a strike and no barrier, the touch's have a barrier and
no strike, the double barrier's second barrier is required while the single
barrier's is absent, and only the target redemption forward has a target.

The writer loses its per-product assembly. Its default drawing values --
=Price=, =Quarterly=, =Daily=, =Accumulator= -- stay in the writer, because
they are the generator's fallback and not facts of the product.

* Result

Every routed equity code is now constructed by name. The writer holds no
per-product assembly for the family: it fills a terms struct from the plan,
calls the constructor, and pushes the row the constructor returned.

Proved by a provisioning run on a recreated database: =generate_trades=
completed, the family holds the same 17 rows as before, and the rows are
spread over 16 trade types -- every routed code, including the ones no
earlier run had exercised through a constructor: the double barrier, the
touch, the target redemption forward and the worst-of basket swap.

The two suites that cover the change are green: =ores.trading.api.tests= at
436 assertions in 115 test cases, =ores.synthetic.core.tests= at 1733
assertions in 78.

Still with the caller, and named rather than hidden: child rows. A swap's
constituents and periods and an accumulator's range bounds are appended by
the writer from the plan, not by the constructor. They are the next task's
subject -- the plan carrying a trade envelope and an instrument batch -- and
the same treatment applies to them.
