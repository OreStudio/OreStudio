* Acceptance

- A test signs in as the inbox service's database user and runs the tell step's work, reading the request and writing the notice.
- A test signs in as the workflow engine's database user and starts and advances the book apply workflow.
- Any right a test shows missing is granted through the registry and no wider than the work needs.

* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

- Sign in to the database as the inbox service's own user, with the credentials the service reads from its environment, and do the work the service does: read a request and its kind, write the notice that tells the person who asked, run the three sweeps, and read who holds a permission.
- Sign in as the workflow service's own user, in the system tenant, and run the engine over it: start a run shaped like the book apply workflow, advance it step by step to the end, and stop one on a failure and resume it.
- Grant through the registry any right a test shows missing.

* Notes

- The inbox tell test first failed because main's account visibility policy hid every account that shares no party with a service actor, so the notice's recipient check failed. Main fixed the policy (f23c626a2b and the commits around it) and the test then passed with no change here. That failure is why the test checks the notice itself: the announcer logs a failure to tell and never throws, so only the notice shows the user may write it.
- The workflow service user needed no new right. The two engine cases pass as it stands.
- The engine cases use test step subjects with the book apply workflow's three-step shape, because the real subjects belong to running services that would answer them on a shared bus. They prove the engine's own database rights, which do not depend on the subjects. The real definition is covered by the refdata workflow tests.
- Not covered: the services' other handlers, and a start through the live bus.

* Result

The inbox service's and the workflow service's own database users are tested for the work they do.

- =approval_as_service_tests.cpp= signs in as the inbox service user. It reads a request and its kind, writes the notice for the asker and reads it back, runs the expiry, reminder and stalled-apply sweeps, and reads who holds a permission.
- Two cases in =workflow_engine_tests.cpp= run the engine over the workflow service user in the system tenant: a three-step run is started and advanced to completion, and a run is stopped on a failure and resumed.
- No right was found missing, so the registry is unchanged.

Evidence: the three inbox cases and the two engine cases pass on a database recreated from main with the account policy fix.
