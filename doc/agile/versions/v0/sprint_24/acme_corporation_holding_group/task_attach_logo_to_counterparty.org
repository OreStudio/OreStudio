* Result

Added a nullable =image_id= soft-FK to counterparties, following the
same generalised =ores_assets_images_tbl= pattern used for accounts.
Counterparty is fully =domain_entity=-codegen-driven (unlike the
hand-maintained accounts table), so the change was made at the model
level (=ores.refdata.counterparty.org=) and regenerated via =compass
codegen entity generate counterparty=, not hand-edited into generated
SQL.

Discovered and fixed a codegen gap along the way: the soft-FK
validation template hardcoded the target table's PK column as =id=,
which happened to hold for every existing soft-FK target but not for
=ores_assets_images_tbl= (PK column =image_id=). Extended the
=domain_entity= FK facet with an optional =:target_column:= property
(default =id=, so every other entity's generated SQL is
byte-identical) rather than special-casing counterparty -- a small,
reusable extension.

Regenerating counterparty also picked up unrelated template drift
that had accumulated since it was last generated (matching what
sibling entities like =counterparty_identifier= already reflect):
generator defaults (=version 0=/="system.test"= instead of =version
1=/="system.new"=) and the =counterparty_changed_event= field rename
(=ids= -> =counterparty_ids=). Updated the one stale hand-wired
subscriber reference in =application.cpp= and the one stale generator
test assertion to match; no behavioural regression -- verified via
full local build (clean) and =ctest= (74/74 passed) after a DB
recreate to pick up the new column.

No Qt upload-button UI in this task (out of scope -- see Acceptance).
