* Acceptance

- The CI run of the marketdata core tests includes the title cases and they pass.

* Plan

The question is whether CI runs the binary that holds the cases, and whether
the cases pass there. Three steps answer it, and none of them needs a local
build, which the host lock rules out.

1. Name the cases. =--list-tests "*title*"= on the binary that exists, with the
   =ENVIRONMENT= of its CTest entry applied, gives the two cases and their
   tags. The task's description says one case; there are two.
2. Read the gate. =continuous-linux.yml= runs =ctest= through =CTest.cmake=
   after =compass db recreate= and after NATS starts, and passes no label and
   no test name filter. Every test that CMake registers runs.
3. Read what CI recorded. =gh run view --job <id> --log= holds the per-test
   lines of the run, and the CDash project holds the totals for the same
   build. The two agree.

The cases need no database at all. =oresmd_schema_describer::describe()=
answers from its own tables, so the two cases stand alone, and the other 224
cases in the same binary are the ones the environment database serves.

* Notes

CI already runs the cases, so this task ends with no change to the workflow and
no change to the test. The entries below are the observations, in order, and
what a reader should not take from them.

- 2026-10-18. =continuous-linux.yml= runs every three hours. It recreates the
  database with =compass db recreate -y -D ores_ci=, starts NATS, then calls
  =ctest= through =CTest.cmake=. =CTest.cmake= calls =ctest_test()= with a
  parallel level and nothing else, so no test is filtered out by label or by
  name.
- 2026-10-18. Each component's =CTestTestfile.cmake= registers one test per test
  binary, and =projects/CMakeLists.txt= sets =ORES_CATCH2_ARGS= to
  =--allow-running-no-tests --durations yes --filenames-as-tags -r compact=. The
  first of those means a binary that runs no case at all still passes. The
  protection here is that the log names the cases, which is what the evidence
  file shows: =89: 0.000 s: every title names only the subject and the fields of
  its row=.
- 2026-10-18. Both release jobs of 2026-10-17 printed a ctest total, and both
  runs are red for reasons outside this component. The run at =e336bd0ffb=
  reports =100% tests passed out of 96= in its release job, and the run is red
  because its debug job hit the 320 minute limit of its CTest step while still
  compiling, at 7187 of 7536 targets, so that job never reached a test. The run
  at =132b3de2e6= reports =99% tests passed, 1 tests failed out of 96=, and the
  failure is =ores.synthetic.service.tests=. The marketdata core test passed in
  both release jobs.
- 2026-10-18. The binary in this worktree was built at =3a99d376d2= on another
  branch, so the local run is corroboration and not authority. The two CI logs
  are the authority, and both name the cases and pass.
- 2026-10-18. The environment here reports that the database schema is out of
  sync with this checkout. The title cases read no database, so the local run
  does not depend on that; the rest of the binary would.
- 2026-10-18. A reviewer should distrust the =0.000 s= duration: the compact
  reporter prints the time each case took, and a case that asserts over a table
  built once at first use spends its time in that first use, not in its own run.
  It is evidence that the case ran, not evidence that it is cheap.
- 2026-10-18. A reviewer should read =96/96= in the log as a completion counter,
  because ctest prints it as each test finishes. The run total is the separate
  summary line, =100% tests passed out of 96= or =99% tests passed, 1 tests
  failed out of 96=, and =evidence/cdash_build_totals.txt= holds the same
  numbers as CDash recorded them.
