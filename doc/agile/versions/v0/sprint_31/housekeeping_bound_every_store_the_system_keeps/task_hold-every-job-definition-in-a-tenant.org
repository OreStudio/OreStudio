* Goal

The scheduler holds every job in a tenant. The jobs the platform declares in
order to function are rows of the system tenant, and a job a service creates for
a tenant is a row of that tenant, so a job, its instances and the events about
them all name who they act for.

* Acceptance

- =tenant_id= is not null on the job definition table, and its primary key, its
  uniqueness indexes and its triggers state the tenant
- The write states the tenant a job belongs to, and a service that creates a job
  for a tenant names that tenant
- No job definition is written with a null tenant
- The scheduler fires a job with the tenant that holds it, and writes the
  instance with that tenant
- A pgTAP test covers a job created for a tenant and one created for the
  installation

* Analysis

Found while delivering
[[id:A71D89B6-2A44-4826-BF30-25E6E3AF631E][Deliver housekeeping as platform data]],
which publishes the sweep job into the system tenant and cannot settle where a
job belongs without settling this.

The table was built for a null tenant, and the write path never states one.
=job_definition_write= carries no tenant, and =job_definition_to_domain= leaves
it unset, so every job a service writes over the wire lands null. The jobs the
populate scripts seed land null for the same reason: the seed states =NULL=
where the column would take a tenant. Three shapes follow from that: the
uniqueness index is =nulls not distinct=, the version lookup compares the pair
as =(tenant_id = NEW.tenant_id or (tenant_id is null and NEW.tenant_id is
null))=, and the insert trigger validates the tenant only when it is set.

What a null tenant costs. Row-level security binds a row to a tenant, so a
null-tenant row belongs to no one: a tenant cannot read the job that runs for
it, and the job's instances carry no tenant either. The housekeeping story
requires the sweep and the policies to appear in each tenant's screens as work
the installation runs, which is a question about who owns the row.

Why it is more than a column change. A tenant that is not null belongs in the
key, so the key a request names becomes the pair, and every read, write and
delete resolves it. The write must state the tenant, which the request envelope
does not carry today: a service writes with its own session's tenant, and the
reporting and inbox services create jobs for other tenants. Both already hold
the tenant they write for, so the decision is where to state it: on the write,
which every caller then fills, or on the request, which lets a caller act for
one tenant at a time.
