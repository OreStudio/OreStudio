* Goal

A tenant session that reads =dq.v1.dataset_bundle_members.list= answers the
members of its own bundles and of the shared ones. Today it answers nothing for
a =world= or =platform= bundle, whose membership rows sit in the system tenant,
so a coverage screen reading that collection draws "this bundle carries no
dataset" for every shared bundle it holds.

* Notes

Found while drawing the coverage screen, on branch
=feature/draw-the-counts-on-the-coverage-screen=. The screen no longer reads the
collection: it draws the members from =dq.v1.ops.bundle_roster=, which resolves
them through =ores_dq_bundle_datasets_list_fn= and is not affected. The defect
is left for the collection itself, because the next consumer of it is a screen
that changes membership and needs the same rows.

The cause, measured on 2026-11-26 at =af61a1b942=:
=dataset_bundle_member_repository::read_latest(offset, limit)= and
=get_total_member_count= add =where tenant_id == ctx.tenant_id()=, while the
=bundles= and =datasets= repositories state no such predicate and let the row
level security policy decide. The policy
=dataset_bundle_members_read_policy= already admits the own and the system
tenant, so as the runtime user with the tenant setting applied the table answers
180 system-tenant rows for the acme tenant.

The predicate is generated from =read_tenant_filtered=, which the generator
derives from =:tenant_read_scope:= on the model. The junction meta-model does
not read that property: setting it on the =* Repository= drawer and on the
=* Flags= drawer of =ores.dq.dataset_bundle_member_junction.org= leaves the
generated repository unchanged. So the fix is in the generator: a junction
model must honour =:tenant_read_scope:= the way a domain entity does, and
=ores.dq.dataset_bundle_member_junction.org= then declares =shared=.
