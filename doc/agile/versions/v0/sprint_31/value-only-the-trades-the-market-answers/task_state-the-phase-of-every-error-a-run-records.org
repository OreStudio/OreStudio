* Goal

A reader of a run's errors can tell where each one came from: the run's own preprocessing, the engine, or the postprocessing of its results.

* Acceptance

- A recorded error states its phase alongside its scope, and the phase is one of preprocessing, engine or postprocessing.
- Every writer of an error states its phase: the workflow steps, the engine error reader and the results ingester.
- A read groups a run's errors by phase and answers the count of each.

* Plan

- The phase is the platform's own closed set of three words, so it is a checked
  column beside =severity= and not a lookup table. The scope is a table because
  the engine grows that vocabulary and a new group is a row; a phase row would
  be code the platform compiles. The check refuses a value no phase states,
  exactly as a foreign key to seeded rows would.
- =report_error_event= gains =phase_code= beside =scope_code=, and the model
  states why the two answer different questions: the scope is the engine's own
  word about what an error is about, and the phase is the platform's word about
  which part of the run was working when it failed.
- One vocabulary type, =domain::run_phase=, states the three codes and their
  words, so a writer can only name a phase the store holds, and a code read
  from a message is parsed once where it enters.
- One recorder writes every error a run holds, so it states the phase once. The
  log rows state the engine phase, because every one of them is a line of the
  engine's own log; a step that refuses its work states the phase it belongs to.
- The compensation that fails a report states the phase of the step it rolls
  back. The engine compensates only the steps that completed, so the failing
  step writes the failure itself and this is the fallback for a step that
  stopped without a word.
- A read answers a run's problems per phase, so a screen can open the errors of
  one phase without reading them all.

* Notes

The plan changed in two places once the code was read.

- The phase is a checked column and not a seeded lookup. =severity= is the same
  kind of fact — a closed set of the platform's own words — and it is a check in
  this very table; the scope is the one that cannot be, because the engine grows
  it. A three-row lookup would also owe a permission code, a screen and a
  service for rows nobody edits.
- The compensation is built for the steps that completed, in reverse order, and
  never for the failing step: =workflow_engine::begin_compensation= skips every
  step whose state is not =completed=. The failing step's handler writes the
  row itself, so the phase of the failure travels on that row; the compensation
  states the last phase the run completed, and its row is the fallback for a
  step that died without writing one.

Two surfaces moved with the column, because both write an error row: the shell's
=fail-report= command gained the phase as its first positional argument, and the
agent eval seed states =preprocess= on the run-level row it writes.

The gate's one failure is not this branch's. =pgtap= fails in
=scheduler_housekeeping_alerts_test.sql=: the pass is expected to raise four
notices for stores nothing bounds and raises none, and the function warns that
no account raises them. The same file passed at the base this branch was
rebased from before the housekeeping work landed, and the branch touches
neither the test nor the scheduler and inbox SQL. It is captured in
[[file:../../../product_backlog/inbox/pgtap-housekeeping-alerts-raise-nothing.org][the inbox]].

The ratchet records the column as two new wide-type warnings:
=report_error_event= and its entity now hold seventeen fields against a recorded
ceiling of sixteen, which the rule does not raise. The exception the check offers
is a source comment the entity template emits and the api domain template does
not, so accepting it would silence one of the two warnings and leave the other;
the pair is recorded here instead, and grouping the fields that belong together
is the work the rule asks for.

* Result

Every error a run records states the phase that produced it, beside the scope
the engine names. The phases are the platform's own closed vocabulary, and the
store checks them: =preprocess=, =engine= and =postprocess=.

- The engine's own log rows state =engine= whatever step reads them, because a
  row is the engine's account of itself and not the account of the step that
  collected it. The results ingester therefore states the engine's phase, which
  is what the row's subject already says: only the engine names trades.
- A step that refuses its work states its own phase. A compute result the
  engine failed states =engine= even though the collecting step is what reads
  it, because that failure is the valuation's, and a reader who read it as
  postprocessing would look in the wrong place for it.
- The compensation states the phase of the step it rolls back, because the
  engine compensates only the steps that completed and never the failing one.
- A read answers a run's problems split by phase beside its totals, and both
  the row and the run the list draws state it: the row states its phase, and
  the run states how many of its problems each phase recorded.
- A phase is not a filter of the generated read. A screen reads a run's errors
  and groups them, and a read of one phase would be a second way to ask what
  the rows already answer.
