* Goal

A person, or a scheduled run, asks for the inputs of one pair or of a whole asset class. The service resolves the item by the policy's provider order and inverse rule, reads the variance window of fixings, and stores one input snapshot with every point, used or left out with its reason. The same request on the same fixings stores a new version, not a duplicate.

* Acceptance

- synthetic.v1 operation capture_variance_inputs for a pair or an asset class, permission-checked, returning the stored input ids.
- Each point records the fixing value as stored, its date, the return it gives in market convention, and whether it was used; an unreadable value or a gap is kept with its reason.
- Tests cover the provider order, an inverted item, a short history, a value that is not a number, and an idempotent repeat.

* Result

The class calibration run captures the input of each GJR-GARCH feed it resolves
from a fixing, rather than a =capture_variance_inputs= operation of its own (see
the story's decision). =capture_variance_points= turns the policy's variance window
of the resolved item into points: each fixing kept as stored, its value, its log
return in the pair's market convention, and a reason for a point left out. An
applied run stores the input and its points once, under ids named by the party,
item and window, so a repeat stores nothing new.

Measured on a recreated database with Acme provisioned: an applied FX run stored 28
inputs and 7408 points, 28 of them the first points that have no return; a second
applied run left 28 and 7408 rows across all versions. The inputs hold 241 to 279
returns each: this environment has about a year of fixings per pair, not the five
the window asks for. =feeds_variance_calibration_tests.cpp= covers the reasons,
the market-convention sign of an inverted item, and a return across a skipped
point.
