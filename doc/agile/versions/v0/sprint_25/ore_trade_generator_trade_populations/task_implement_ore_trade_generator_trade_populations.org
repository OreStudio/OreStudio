* Goal

Put the choice in front of a decision-maker with the evidence attached.

There are several ways to produce a sized trade population and they differ on
things that matter: how long generation takes, how long loading takes, what ends
up committed to the repository, whether the same size always yields the same
book, and how much of =ores.trading= each can populate.

This task surveys those approaches, measures them where measurement is cheap,
and presents them as options. It does not choose. The deliverable is a
recommendation with its reasoning exposed, so the decision can be made and
disagreed with.

* Acceptance

- The candidate approaches are named and described, at minimum the four in
  Notes below, with any further candidate the survey turns up.
- Each is evaluated against stated criteria rather than impressions. Generation
  time, load time, what lands in git, reproducibility, achievable realism,
  coverage of the =ores.trading= instruments, dependency footprint, and
  maintenance cost.
- Speed is measured, not argued. Whatever is cheap to time is timed, at a size
  that extrapolates to the largest tier; where a measurement is too expensive to
  take, the task says so rather than guessing.
- A tradeoffs table compares the approaches on those criteria, and a
  recommendation is made with its reasoning stated so it can be contested.
- The question of realism at small sizes is answered for each approach: whether
  it can produce a tiny book that is a small firm's book rather than a large
  one's truncated.
- Approaches ruled out are recorded with the reason, so a later reader does not
  reopen them.

* Notes

Scoping findings, recorded so the analysis starts from them.

*** The candidates

#+ATTR_HTML: :class hug-leading
| Approach | Shape |
|----------|-------|
| Committed SQL dataset | Generate once, commit the SQL, seeder loads it as the rest of a dataset already is |
| Algorithmic generation in C++ | A generator writes to the database at provision time, sized by a parameter and reproducible from a fixed seed |
| ORE-Python TradeGenerator | Build trades through ORE's own API, emit XML, import through the existing =ores.ore= mappers |
| Archetypes multiplied | ORE fixes conventions for a modest set of archetypes; multiplying them across notionals, maturities and counterparties is our own work |

They are not mutually exclusive. A committed dataset for the small sizes and
algorithmic generation for the large ones is a fifth option, and the survey
should consider it rather than treating the four as a forced choice.

*** What exists already

=projects/ores.ore/core/domain/= carries =trade_mapper= and per-asset-class
mappers for swap, equity, FX, commodity, bond and credit, with =xml/importer=
and =xml/exporter=. The XML import half is largely built, which is why the open
question is generation and volume rather than import.

=projects/ores.seeder/= is Python only, =src/seeder.py= with datasets beside it.
An algorithmic C++ generator would be new work and needs a home;
=projects/ores.synthetic= is the obvious candidate and already carries the
synthetic market data generation.

=portfolios.json= in the Acme dataset carries 36 portfolios, each with an owner
unit code, an aggregation currency, a parent portfolio and a virtual flag. Those
fields are what a realistic assignment rule has to use.

*** Why volume decides much of this

At the order of 400,000 trades, committing generated SQL puts a large artefact
in git and building each trade through ORE-Python is unlikely to be viable on
time. Neither is disqualifying on its own, and both are cheap to test. A fixed
seed makes algorithmic generation reproducible, which removes the usual argument
for committing the data.

*** The reference

=/home/marco/Development/ORE/Engine/Examples/ORE-Python/TradeGenerator/= holds
=Readme.md= and =trade_generator_test.py=. Its lesson is the lookup: a trade is
built from an index such as =GBP-SONIA=, which selects a convention and a curve
config, and those supply payment frequency, calendars, business day conventions
and spot lags. The caller supplies only notional, maturity, rate and direction.
That knowledge is worth extracting whether or not the tool is adopted.
