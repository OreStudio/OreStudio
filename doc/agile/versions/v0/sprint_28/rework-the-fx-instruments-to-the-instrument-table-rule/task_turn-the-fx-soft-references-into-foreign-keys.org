* Result

Ten references became real keys and twenty-one stay soft with a recorded reason.

The ten are the family's closed vocabularies: =long_short= on the accumulator,
the digital option and the variance swap; =option_type= on the barrier, digital
and vanilla options; =barrier_type= on the barrier and digital options;
=exercise_style= on the vanilla option; and =moment_type= on the variance swap.
Each now carries a foreign key block to its lookup table, so the generated
insert trigger refuses a code the lookup does not hold. The nullable columns
validate only when they state a value.

Twenty-one references stay soft, in two groups:

- *The currency columns, fourteen of them.* A currency is =ores.refdata='s row,
  seeded per environment rather than by this component, and a trading database
  may hold only the codes its own imports loaded. A trigger check would refuse
  a document the store is meant to accept, so each column states the reason and
  the code is validated where the currency set is known.
- *The seven trade-type codes.* The column's own check pins the one code the
  table serves, and the trade-type catalogue routes the row to this table by
  that code, so a foreign key would duplicate the router.

The remaining text columns (=settlement=, =underlying_code=, =description= and
the settlement codes) name no table, so there is nothing to key them to.

* Decisions

- *A key is the trigger check, not a SQL constraint.* The tables are temporal,
  so a =REFERENCES= constraint would accept a closed version as current. The
  generated check reads the current row, which is what the rest of the family
  already does for its trade and activity keys.
- *A currency reference stays soft because its rows are not this component's.*
  The unit's acceptance allows a recorded reason, and the alternative would be
  a foreign key that fails in every database whose currency set is loaded after
  the documents.
- *The trade-type code stays soft because the check is stronger.* It pins the
  single code the table serves, where a key would accept any catalogue code.
- *The lookup's closed set is now stated twice.* The SQL check and the lookup
  table both hold it. Removing the checks is the discriminators unit's
  decision, not this one's, so they stay.
