A point-in-time record, written while the story that commissioned it was open, of an [[id:A7F8D9E2-3C4B-4A5D-B67C-8E9F0A1B2C3D][investigation]] into the work each provisioning request does, and what bounds it.

It is a snapshot, not a description of the system. Whatever it concludes that the code must keep doing belongs on the page that owns the subject; cite that page from code, recipes and models, not this one.

* Context

A provisioning step waits for each of its requests with one deadline. Work that
grows with the data inside a request makes that deadline a lie in both
directions: short enough to be safe, it fails on a loaded host; long enough to
always pass, it cannot tell a slow service from a stuck one.

The run that started this story failed step 13 of 15 with
=NATS request timed out= while it was calibrating surfaces, and the surface
deadline was then raised to 120 s. Raising a deadline is only honest if the work
behind it is bounded. This investigation asks, of every request a provisioning
step makes: what does its handler do per row, and what bounds that work?

The task is [[id:9CA04D58-E330-4F27-AF8A-B3BDBB2E63EC][Bound the work of a request]].

* Methodology

The starting list is the request types of
[[id:7C1E4A52-9B3D-4F67-8E21-5A6C9D0B3F14][Requests a provisioning step makes, and the deadline each states]],
which grouped them by deadline class. The list was re-derived from the handler,
because that page's 46 was a group count and not a type count:

#+begin_src sh
grep -oE "((ores|[a-z]+)::)+(messaging|api)::[a-z_]+_request" \
  projects/ores.iam/core/include/ores.iam.core/messaging/tenant_provisioning_handler.hpp \
  | sed 's/.*:://' | sort -u | wc -l
#+end_src

That gives 54 names at =2babccb0f0=. The handler sends 54 request types: the
grep's 54, minus =attach_account_pictures_request=, which the file serves rather
than sends, plus =clear_bootstrap_mode_request=, which it names through a
=using namespace=. A first pass of this inventory reported 46 because it matched
only the fully qualified =ores::X::messaging::= form, which misses a request
named through a component alias such as =iam::messaging::=, and because it
counted the served request as one the step sends.

For each type, the service handler was found by grepping its NATS subject in the
component that serves it, the service behind the handler was read, and four
things were recorded:

- what the handler does, in one sentence;
- the shape of its cost: =O(1)=, =O(page)= (bounded by a limit or by the ids the
  request names), =O(catalogue)= (a whole table read and narrowed in memory, or
  one query per row of the tenant's data), or =O(table)= (an unbounded read of a
  shared table);
- the line that decides it;
- whether the repository already offers a filtered or paged read the handler
  could use instead.

Handlers in =ores.marketdata=, =ores.refdata=, =ores.iam=, =ores.inbox=,
=ores.variability=, =ores.reporting=, =ores.assets=, =ores.dq= and =ores.synthetic=
were read.

* Paths taken

The deadline inventory said every read request was "bounded by the tenant's own
provisioning data: a catalogue of tens of rows". That claim held for the list
requests, which pass their filter down to SQL. It did not hold for five handlers
that read a whole catalogue and narrowed it in memory, which is the shape this
task exists to find. Each was rewritten to ask the store for its own rows, a page
at a time, through the shared =read_all_pages= helper. The write path was left
alone.

** 5 request types were unbounded and now cost what they name

| Request | What was read | What it reads now |
|---------+---------------+-------------------|
| =calibrate_fx_vol_surface_request= | Every FX volatility pillar and pillar source the tenant holds, narrowed in memory to one blueprint. | That blueprint's pillars, through =fx_vol_surface_pillars_filter=, and their sources by pillar id. |
| =compute_curve_request=, =publish_curve_request= | Every IR curve pillar the tenant holds, narrowed in memory to one config. | That config's pillars, through =ir_curve_bootstrap_pillars_filter=. |
| =publish_fx_forward_request= | Every IR curve config the tenant holds, narrowed in memory to one currency's funding curve. | That currency's funding curves, through =ir_curve_bootstrap_configs_filter=. The party is narrowed after the read, because the store keeps no filter for it, so the cost follows the parties that fund in that currency. |
| =publish_fx_vol_surface_request= | Every surface publish the tenant holds, to find a second raise of the same calibration. | This blueprint's raises, through =fx_vol_surface_publishes_filter=. |

** 2 request types still grow with the data

| Request | Shape | Why it is left |
|---------+-------+----------------|
| =list_accounts_request= | The password and picture steps ask for the tenant's accounts with =limit = 10'000=, then work one by one over the answer: one password reset, or one picture attach, per account. Past ten thousand, the rest are dropped without a word. | Captured as [[id:DC63BCCB-0967-4A2D-B978-2033DF7C943D][Provisioning asks for every account in one request, and drops what is past ten thousand]]: it needs a page the step advances through, which is the shape of the step that moves to its owning service. |
| =regenerate_calendar_dates_request= | One row per day for every calendar in use, about 37,000 days each. The request names no calendars: =in_use_only= is set, so the service loops them. | It runs as =build_calendars_step= with a 600 s deadline and writes in one batch, so the story's second clause covers it. Its read of the existing days loads each calendar into memory to subtract them, which is a memory cost rather than a longer request. |

* Recommendations

- Let the calendar materialisation ask the store which of the days it is about
  to write already exist, instead of loading every existing day into memory to
  subtract it.
- Give the account read a page the password and picture steps advance through:
  it is captured for that.
- Use the batch =read_latest(ctx, ids)= the repositories already offer in the
  =put_many_*= handlers, so a hundred-row write stops costing two hundred reads.
- Keep the rule in review: a handler that reads a catalogue and narrows it in
  memory is the shape to refuse. The five fixed here all had the filter
  available in the repository, unused.
