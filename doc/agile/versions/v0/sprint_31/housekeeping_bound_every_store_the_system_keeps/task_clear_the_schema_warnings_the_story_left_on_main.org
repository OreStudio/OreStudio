* Acceptance

- The retention ledger carries the tenant whose policy ran, in its primary key and in its row level security
- The sweep writes that tenant, and the due check reads the ledger for the policy's own tenant, so one tenant's run never suppresses another's
- The delivery count's key stays the natural key, and the exception is recorded once with its reason, in the model and in the validator's ignore file
- =./projects/ores.sql/utility/validate_schemas.sh= reports no warning from either file
- =./compass.sh generate= leaves no diff

* Plan

- The ledger is per-tenant rather than system-wide: the sweep applies the
  policies of one tenant, so a run belongs to that tenant, and the key and the
  policy follow. This is the smaller change, and it is also the true one, since
  the sweep's own read is filtered by tenant.
- The delivery count keeps its natural key. A party belongs to exactly one
  tenant, so the tenant cannot disambiguate a key it is implied by, and the
  validator's ignore file is where this repository records exactly this kind of
  exception, with the reason beside it.
- The model states the same reason, so the exception is not only in a file the
  validator reads.

* Result

Both warnings from this story are gone. The validator now reports 841 tables and
one warning, the vault one, which belongs to another environment.

The retention ledger gained the tenant it always implied: the column, the key,
the index and the row level security policy, and the sweep writes the tenant of
the policy it ran. The due check reads the ledger for that tenant as well, so a
run under one tenant cannot suppress a policy under another.

The delivery count keeps its natural key. A party belongs to exactly one tenant,
so the key the validator asked for would carry a value the rest of the key
already fixes; the exception is recorded once, with its reason, both in the model
and in =validation_ignore.txt=.

The third warning, on the vault's secret uses, is brave_hopper's and is left to
it. The job stays red until that lands, which is why this task's acceptance is
about the two files and not about the job.
