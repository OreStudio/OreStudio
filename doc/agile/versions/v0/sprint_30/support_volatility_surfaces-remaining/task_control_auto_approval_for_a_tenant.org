* Goal

A tenant can run without waiting on approvals, and anyone can see that it does. The existing =system.approvals.mode= setting is the switch. An operation with its own permission changes it for one tenant, and each change is a version with who and why. Provisioning turns it on and off around its steps, and a profile that omits the last step leaves it on for a demonstration.

* Acceptance

- Turning the switch on or off is a versioned record of who, when and why, and needs inbox::approvals:set_mode.
- A raise in a tenant with the switch on closes at once, and the request names the rule that closed it, from any party and any service.
- A raise after the switch goes off waits for a person, with no restart.
- A profile decides whether the switch stays on when provisioning ends, by ordering or omitting end_auto_approval.
- Auto-approval is on before every other provisioning step, and off after them.
- While the switch is on, every screen says so, with who set it, when and why.
- A request closed by the switch reads as auto-approved, and its decision names who set it and the version.

* Plan

Most of the switch existed. =system.approvals.mode= is versioned and is read per tenant, and the request records the rule that closed it. Three things were missing: a read that reaches the tenant's row from any party, write access to it, and a way for a session to learn the mode.

=approval_lifecycle= reads as the tenant, not the caller's party. =get_approvals_mode= and =set_approvals_mode= are inbox operations, so the screen does not read the settings table.

Dropped from the first draft: limiting the switch to some approval kinds, and a filter on the approvals screen. Nobody asked for either.

* Result

A tenant can now be put on auto-approval and taken off it, and every screen says when it is on. Acme provisions with it on and hands approvals to people when it ends.

The live run found three defects that the tests could not, because their database user has wider rights. No service role could read the settings table, so =system.approvals.mode= had never taken effect outside the tests. The inbox could not write it. Steps with no inputs run together, so the end step ran first and left the switch on.

If a provisioning run fails partway the switch stays on, and the notice shows it.
