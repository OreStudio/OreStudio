* Notes

The refusal is not a missing grant. =ores_variability_resolve_system_party_fn=
is SECURITY DEFINER and its EXECUTE is revoked from PUBLIC on purpose: it takes
a tenant as a parameter and reads across the tenant boundary, so only the
reading roles may call it. The defect is on the other side of the call — the
trigger that needs it was left as an invoker.

=setup_schema.sql= recorded the assumption that made this look safe: "A service
writes settings its tenant already holds, so the function stays off the
production service roles." That holds for an update, and the trigger is BEFORE
INSERT, so it never fires. It does not hold for a create, and the bootstrap is
where a service first creates one.

The reproduction is exact. With the trigger invoker, a service-role insert of a
tenant-wide setting returns:

#+begin_example
ERROR:  permission denied for function ores_variability_resolve_system_party_fn
CONTEXT:  PL/pgSQL function ores_variability_system_settings_default_party_fn() line 5 at assignment
#+end_example

which is the failure reported from bootstrap's last step. With the trigger
definer the same statement lands and the row carries the tenant's system party.

The insert needs the tenant context the service sets from the JWT
(=app.current_tenant_id=) to satisfy the table's RLS policies; without it the
refusal is a policy error instead, which is why a bare service insert does not
reach the trigger at all.

* Result

Done. The trigger is =SECURITY DEFINER= with =search_path = public, pg_temp=,
and a service-role insert of a tenant-wide setting resolves to the tenant's
system party instead of being refused.

Verified against a recreated database by reproducing the reported error and its
absence: the identical insert as =ores_brave_hopper_variability_service= raises
=permission denied ... line 5 at assignment= with the old shape and lands with
the fix. =resolve_system_party= remains ungranted to both service roles.

A full wizard run is the acceptance test that exercised it, and it was run: the
administrator was created and signed in as the system party, the last step
answered ={"success":true}=, and the authenticated status read then reported
=onboardingComplete: true=. The trigger fix alone was not enough for that run —
the row met the party-isolation policy next, which is what the system-party
sign-in is for, and the tasks that carry it are in the story's decisions.
