* Goal

The two configuration journeys and their prototypes say the same thing in the
same words, state what each configuration decides and how the two relate, and
the owner signs them off before any code changes.

The journeys are the design of record. They must carry the decided screen
words, the relationship between the two configurations and the lifecycle rule,
and they must not describe a tree that has since changed.

* Acceptance

- A journey exists for the engine run settings, and it names the pricing engine configuration and states how the two differ.
- The pricing engine journeys use *Pricing engine configuration* throughout, not *Pricing engines* or *Pricing model config*.
- The engine run settings journey uses *Engine run settings* throughout, not *Engine settings* alone.
- Each journey states, where a person meets the other configuration, what it decides and links to it.
- The pricing journey's Parameters tab is drawn as *Parameters*, and no screen or journey calls it *Settings*.
- The engine run settings lifecycle follows the section rule: a numbers-changing group is proposed and signed off; an operational group writes directly.
- The journeys no longer describe a tree that has changed, including the routes that exist and the defaults the source sets.
- Both configuration prototypes draw the standard words, the related configurations card and the link to the other configuration.
- Each prototype's design note states what changed and why, and the reporting group page is updated.
- check_prototype_inventory.py passes.
- The owner signs the journeys and prototypes off before any code change.
