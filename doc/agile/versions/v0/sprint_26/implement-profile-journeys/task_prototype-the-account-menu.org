* Goal

A clickable prototype of the application navigation that the design can be judged against, on a throwaway page with mock data. It draws the shell around a journey screen and argues three structural answers to the question nothing owns: where the member's own screens hang, where an administrator's screens hang, and what the trigger shows before the account has been read.

* Acceptance

- The prototype is published beside its description and the other prototypes, and it reads no service.
- Every journey that names the account menu can reach its screen from the prototype.
- The trigger's state before the account is read, the current screen, and the administrator's extra items are all renderable without reading the code.
- The verdict is recorded on the prototype page and the losing variants stay as the record.

* Plan

1. Collect what the journey documents actually say about the menu: every
   journey that names it, the screen each reaches, and the closing line that
   says the menu shows the new name and photo.
2. Read the shell as it stands, and the session the shell is given, because
   the trigger's promise depends on what the session carries.
3. Build the prototype as a static page under =doc/prototypes/account-menu/=,
   which is how the tree keeps throwaway prototypes: plain HTML, CSS and
   JavaScript, no framework and no build step.
4. Argue three structural answers to the question no document answers: where
   the member's screens hang, and where an administrator's hang. Draw each in
   the shell the application actually has, so a reviewer judges the navigation
   and not a page of its own.
5. Mark every item whose group has not landed with the group that owns it,
   because a menu that offers a screen nothing implements is a promise.
6. Publish it with the site build, beside the other prototypes; drive the
   whole state matrix without a browser; then look at the screens in Chrome.
7. Record the verdict on the prototype page and distil the decisions into the
   story.
