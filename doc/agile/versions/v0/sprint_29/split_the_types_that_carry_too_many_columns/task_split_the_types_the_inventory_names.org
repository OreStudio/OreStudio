* Plan

** The order

The inventory ranks the types. This task takes them in that order, one PR per
type, and does not start a type the inventory has not judged =split=. A type the
inventory cleared is not touched, however wide it looks.

** The shape a split takes

The target is [[id:B607E5B7-190F-4D38-B515-8A7B27FB6B47][The atomised entity:
a central row and its parts]]: the central row keeps the identity and whatever
the parts must agree on, and each part is a type of its own with its own key,
its own table, its own codec and its own repository. A part that only one screen
reads does not live in the central row.

A block that shares the parent's key, is written by the same owner, and is
always read with the parent is not a part: it is a field group, and the
inventory says so.

** What moves in one change

A split is one change, because half a split does not build:

1. the model file, split into one model per part;
2. every generated address regenerated: SQL, C++ domain, repository, service,
   protocol, and the TypeScript twins;
3. the seed data and fixtures the type feeds;
4. whatever carried the aggregate — a message, a document, a screen — becomes
   one typed array per part, joined by key;
5. the database recreated, never migrated.

** What proves it

- The parts' rows join to the central row on the key, and no part holds a column
  the inventory gave to another part.
- The wire carries one typed array per part. No part's fields appear as a nested
  object inside another's.
- The query builder's tuple for the type is no wider than the widest part, and
  the C1202 recorded on 2026-10-29 does not reproduce on the widest remaining
  entity.
- Every suite passes, and the screens that read the type still read it.

** What this task does not do

- No compiler flag, no unity exclusion, no field-group reshuffle to reach a
  column count. Those are treatments for the symptom, and the story exists
  because the symptom has a cause.
- No migration: the database is recreated, per the project's rule.
