* Goal

Give the synthetic trade population a configuration entity, so the
population is data a reviewer reads rather than a command a reviewer
trusts. The entity carries the booking party, the book scope, the
instrument family, the counterparty scope, the tenor band, the notional
band, the as-of anchor and the seed.

The generator that consumes it is a later task. This task is the model and
the layers codegen derives from it, in
=ores.synthetic=, beside the generation configs the component already
holds.

* Notes

** The pattern chosen, and the one it is mistaken for

The configuration is one table, =ores.codegen.entity=, bound to the
=uuid-identified-lookup= profile. The two scopes are repeating field sets
and are separate child tables referencing the config, the
*associated-entity* shape =gmm_component= and =ir_curve_template_entry=
already give their parent config.

The neighbouring pattern it is mistaken for is *composite parent and
parts*, the pattern the trading and refdata components use. The pressure
towards it is real: this repository is mid-way through a story that
atomises an entity onto its central row, and the codegen catalogue lists
multiplicity as a reason to split. It was not taken, because a scope row is
a link to a book or a counterparty that already exists and has its own
lifecycle, and because the component's own config children do not bump a
parent version. The cost of that choice is stated under
"What the model does not do".

The other pattern it could be mistaken for is *field group member*. A
band, an anchor and a seed have one change reason and one reader, so they
are columns on the one table; nesting them, or splitting each into a row,
would buy a join and a message for nothing.

** How each required field is held

| Field | Held as | Why |
|---|---|---|
| Booking party | Reference: =party_id= on the config, the row's own owning party | Every neighbouring synthetic config carries =party_id= this way, and it is what the writer sets =app.current_party_id= from. |
| Book scope | Repeating part: =trade_generation_book= rows | A party holds up to twenty books and the population spreads across them, so the scope is a set. |
| Instrument family | Reference: =asset_class_code= to the refdata catalogue | The catalogue is the authority, as =fx_spot_generation_config= already treats it. |
| Counterparty scope | Repeating part: =trade_generation_counterparty= rows | The reviewable part of the population: which counterparties the book faces. |
| Tenor band | Fixed columns: =min_tenor_code=, =max_tenor_code= | One change reason, one reader, two scalars. |
| Notional band | Fixed columns: =min_notional=, =max_notional=, =numeric= | Same, and money is an exact decimal. |
| As-of anchor | Fixed column: =as_of_date= | The generator's input, never a clock read inside a field generator. |
| Seed | Fixed column: =seed= | One number that fixes the population's shape with the anchor. |

** What the model does not do

- The book, counterparty and tenor references are soft. Books and
  counterparties are temporal refdata rows in another component, and
  =tenor.org= emits no single-argument validator to call; the generator
  task resolves them and is what fails loudly. The asset-class reference
  is the exception, because a validator for it already exists.
- The scope rows do not bump the config's version. Adding a book to a
  scope leaves the config's own version still, so the config's history
  does not record the scope change. This is the component's existing
  behaviour for its sub-configs, kept for consistency; the composite
  pattern would fix it and was not taken.
- The drift gates were run while a second agent held uncommitted work in the
  same worktree. All 51 gates that do not read the whole working tree passed;
  =component-drift= is the exception, because it compares =git diff= after an
  in-place regeneration, so any dirty file anywhere fails it. Its reported
  diff at =800a9955d1= named seven files, all of them that other task's, and
  none of this branch's. Re-run it once the worktree is clean to close the
  check.
- There is no DQ artefact staging for these tables. The investigation
  allows DQ for the parameters, not the trades, so staging is a reasonable
  follow-up rather than a defect.

* Result

The model is committed at =800a9955d1= on
=feature/model-the-trade-generation-config=, generated across every layer
the entity supports: SQL create and drop, domain types and their JSON and
table I/O, generator, repository, mapper, service, messaging protocol,
NATS handler and registrar, eventing, history provider, shell commands and
their recipes, and the wire-protocol TypeScript.

Two facts found by reading rather than by designing are worth carrying
forward. The asset-class vocabulary the insert trigger enforces is
=fx, interest_rates, credit, equity, commodity, inflation, bond=, so
"rates" is not a family code and "scripted" has no asset class at all;
the weights page groups by asset class and will need the same mapping. And
=compass db recreate -y -k= cannot win against the environment's own
services, which reconnect to the database inside the guard's half-second
window: the services must be stopped first, and restarted after.
