* Summary

The review is not a step inside the import form. It is its own screen, because
a second person decides there and the maker must not. One staged import shows,
per family and per dataset, what is new, what replaces a live row, what is
unchanged and what is refused, before any live row moves. It also names the
sandbox the import targets and, on every row, whether that row lands inside the
sandbox or in the party. Publish applies every staged family in one
transaction; discard removes the staged rows and touches nothing.

It is throwaway. Open [[file:stage-an-import/][the staged import]].

* Detail

** What it argues

- Staged is a state, not a copy of the live screen. The import id, the expiry
  and the visibility rule sit above every panel, and "live rows changed: 0" is
  the fact the review rests on.
- The plan is per family, with four counts: new, replaced, unchanged, refused.
  The row detail compares the staged row with the live row under the same key.
- Refusals come before the write. A row whose named value left its list, or
  whose currency the tenant does not hold, is named with the family, the row
  and the reason. The commit refuses the file whole.
- Omission is not a delete. The parts the file does not carry keep their live
  rows, and the screen counts them.
- The maker cannot decide. A convention every report reads draws Market Risk;
  the maker is shown beside the decider, and the publish button is the
  decider's.
- The staged rows, not the file, are the commitment. The file may change after
  staging; the commit reads these rows.
- The destination is on the screen. The chosen sandbox path sits above the
  plan, and every family row says where it lands. The trades and portfolios
  family creates virtual portfolios and virtual books in the sandbox; the
  convention, curve, market and run families carry no =sandbox_id= in the
  model, so they publish to the party. "Nothing outside the sandbox changes"
  is true for the book-tree rows, and the screen states the exception instead
  of hiding it.

** Variants and states

=?case=onboard|seed|defect|feed|one-dataset|promote|party=,
=?actor=admin|ops|maintainer|support=,
=?state=review|decide|declined|applied|expired=, =?family=swap=,
=?check=lookup=,
=?target=sb-import-onboard|sb-sample-seed|sb-import-repro|sb-import-feed=.
Discard and expiry are states, not tooltips: a discarded import leaves no live
row, and an expired one is swept with its record intact.

** What is real and what is not

The mechanism is the draft design's begin / stage per family / commit once, and
the per-family reply it promises (=world_kept=, =fx_skipped=, write counts, the
failing family). The family names, the FX skip and the merge policies are real.
The sandbox rules are the model's: a sandbox is anchored at an official
portfolio, an official book never sits under a sandbox portfolio, a sandbox's
root portfolios have no parent, and a virtual book has no ledger reference and
is not sweepable. The sandbox path and the split between rows inside and
outside it are displayed from that model. The counts, the import id, the expiry
and the row values are invented.

The screen has no server. No staging table, no begin, stage, commit or discard
verb and no sweep exists. That absence is exactly what the screen shows.

** Where it sits in the workflow

The staging run ends =completed= before this screen is read, and the decider's
publish starts a second instance. An instance cannot wait for a person: its
only wait is a deadline, and a step that stayed open for a decider would fail
by running out of it. So this screen reads a staged import, not a run, and the
[[file:one-import-run.org][Run]] screen follows the instance that applies it.

** The verdict

Not signed off. This screen asks the owner the hardest question: does a staged
import that only its owner and its decider can see count as "nothing changed",
or must the person see the staged rows to decide at all? It also asks whether
the trade import joins the atomic commit or keeps its partial behaviour. The
sandbox target asks whether a decider may approve rows that land in a sandbox
and rows that publish to the party in one decision, when only the first kind
can be thrown away with the sandbox.
