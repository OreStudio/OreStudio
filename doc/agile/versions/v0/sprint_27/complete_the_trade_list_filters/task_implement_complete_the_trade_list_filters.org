* Result

The spike answered the four questions.

- *Enum filter.* The generator accepts =:filterable: true= on an enum column and emits an enum-typed member, an equals and a one-of condition, a =filter_too_large= guard and a TypeScript =string= member. The shared =filter_value= had no enum overload, so the generated code did not compile. A template overload in =list_filter.hpp= now compares the text of the enum's =to_string=, found beside the enum. It serves every entity. A repository test narrows the trades by =counterparty_scope=, by equals and by one-of.
- *By-parent read.* =:list_by: true= belongs on the foreign key section of the model, not on the column. On a column that is also part of the primary key it works: the generator emits =list_by_trade_id= for the identifiers across the protocol, handler, service, repository, shell command and TypeScript twin. A repository test reads two identifiers of one trade and none of another.
- *View-backed entity.* Not supported. No entity in the models binds to a view. The =read_only= flag only suppresses writes on a table. The summary task therefore includes generator work: a read-model entity that has no table of its own.
- *The instant of a read model.* The existing =valid_at= condition names unqualified =valid_from= and =valid_to= columns, so it cannot narrow a join. The read model is therefore a set-returning SQL function that takes the =as_of= and applies it to every part it joins. The state and the booking in a row then come from one instant by construction. The generated repository reads from the function and appends the filter conditions.

Both findings change the summary task: it gains the generator work, and its acceptance states the function form.
