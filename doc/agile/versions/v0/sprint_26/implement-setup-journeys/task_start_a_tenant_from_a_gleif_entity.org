* Goal

A person starting a tenant has three ways to do it rather than two. They can
build it by hand, build it around a parent legal entity the deployment already
holds in its GLEIF data, or take the prefilled demo. The second is a search
first and a filled form afterwards, and the first may leave the legal entity
out, because a person provisioning their first tenant may not have an LEI yet.

* Acceptance

- The starting points are three, each a seed profile row: manual, from a GLEIF entity, and the prefilled demo.
- The manual card's legal entity is optional: a person who has no LEI can leave it empty and still creates the tenant with its own party.
- The GLEIF card opens on a search over the parent legal entities the deployment holds, and each result states the legal name, the LEI, the country, and how many parties its hierarchy would create.
- Choosing an entity derives the tenant's name, code, hostname, administrator and legal entity, every derived field stays editable, and choosing another entity derives them again.
- The code's shape is stated and enforced by the server, and the field applies the same shape while the person types.
- The GLEIF card states that it builds a tenant around a public registry hierarchy, and the tenant it creates is an evaluation one.
- No profile's name or shape is written in the browser: the third card is a row and the search follows the parameter type the row declares.

* Plan

*Three starting points, which are three rows.* The cards a person chooses from
are seed profiles, so the GLEIF way of starting is a row and not a branch in
the browser: the same executed step kinds as the manual card, its own copy,
and its own declared parameters. Its tenant is an evaluation one, like the
demo's, because a tenant holding a real entity's public hierarchy is a
simulation of that entity and not the entity itself, and its card says so
rather than implying otherwise.

*A legal entity is not required.* The parameter schema already tells an omitted
parameter from one the person cleared, and refuses only the ones a profile
declares as required, so a profile that declares its legal entity as optional
accepts an empty one. The import step has the same shape on the other side: the
publication returns =skipped= when it is given no root entity, which is the
branch the function already carries. So the manual card declares the entity
optional, a person without an LEI leaves it empty, and the run reports that it
had nothing to import rather than failing. A well-known placeholder LEI is
deliberately not used: it would put a fiction into a table derived from a
public registry, it would appear in the tenant's party hierarchy, and it would
make a step claim work it did not do.

*The GLEIF layout is the search.* Its details step opens on a search over the
parent legal entities the deployment holds, and each result states the legal
name, the LEI, the country and how many parties its hierarchy would create.
Once one is chosen the step collapses to a summary of what it derived: the
tenant's name, its code, its hostname, its administrator and the entity itself,
with *Change settings* opening the form. Every derived field stays editable, and
choosing another entity derives them all again. The form's shape follows the
type the parameter is declared as, so the browser holds no profile's name: a
setting declared as a legal entity is searched for, and one declared as a string
is typed.

*The matching belongs to the read.* The country browser the shell already had
answers one country's page, which cannot serve a search: the deployment holds
18348 root entities, and neither BARCLAYS PLC nor DEUTSCHE BANK falls inside a
page of a thousand of them. So the read gained a second question beside the
first — =dq.v1.lei-entities.search=, matched on the legal name or on the start
of an LEI, across countries, with the size of the answer stated by the caller —
and the count of parties travels with every match, computed by walking the same
IS_DIRECTLY_CONSOLIDATED_BY relationships the publication walks. A screen
therefore sends what the person typed rather than fetching a page and filtering
it, and the shell gained =lei search= for the same read. The count was checked
against the publication: BANK OF AMERICA CORPORATION's hierarchy counts 668,
which is what publishing it for a tenant inserted.

*The code is the server's shape.* The code a person types ends up in the
hostname and in the administrator's principal, so its shape belongs to the
tenant model rather than to a form: the server states it, the provision
request refuses a code that does not match it and says why, and the field
applies the same shape while the person types so a screen never offers a value
the server will refuse. The rule the old client applied, and the one to state,
is a lowercase letter first, then lowercase letters, digits and underscores, up
to fifty characters. The derivation from a name is a way of proposing a code,
not a rule: the name is lowercased, runs of spaces and hyphens become
underscores, anything else is dropped, a leading non-letter is stripped, and
the result is truncated. Typing in the code stops the name deriving it, and
typing in the hostname stops the code deriving that; the hostname's default is
the code itself, which is what the old client did.

*The code is the server's shape, and the check has a test.* The rule lives in
=ores.iam.core/service/tenant_code_check.hpp=, the provision request applies it
before the row is written, and a unit test asserts it directly: the accepted
shape, each way of breaking it, and the sentence the caller shows for each.
*The shape is the table's as well as the request's.* =check_tenant_code= and
=check_tenant_hostname= state the rule to a caller as a sentence, and the tenant
model states it as the table's own checks, so a row written by the shell, a
script or SQL is held to what the screen applies. Making the rule true uncovered
two writers that were writing what it refuses, and both moved with it: the
synthetic generator produced codes like =CD_tenant-3=, and the test harness's
suite tenant carried the suite's dots. See
[[file:evidence/tenant_shape_rule.txt][the evidence file]].

*The field applies the shape while the person types.* The code's shape is the
server's, so the field applies it rather than judging it afterwards: the value
is lowercased as it is typed, everything outside lowercase letters, digits and
underscores is dropped, a leading digit or underscore goes because a code starts
with a letter, and it stops at the length the server accepts. The hint states
the same shape, so a screen never offers a value the server will refuse and
somebody never learns the rule from a refusal.

*Nothing to import is a step that says so.* The manual card declares the legal
entity as optional, and the import step threw when a run supplied none, which
stopped a run whose card promises a tenant built from the party it creates for
itself. The step now reads an absent entity as empty, completes with a warning
and logs why; the rail shows that sentence beside the step.

*What this task leaves.* The legal entity the manual card may leave out is added
later through the *New party* journey.

* Notes

- The search read was found broken before it was built on: the browser sent no
  country, the handler read that as "list the countries", and every answer was
  a country with no name, so no entity ever matched. The new question answers a
  search instead, and the country browser keeps the behaviour the shell's
  =lei countries= command depends on.
- The party count a match states is the work the run does, not an estimate:
  668 for BANK OF AMERICA CORPORATION is the number of parties the publication
  inserted for the same hierarchy. See
  [[file:evidence/gleif_search_and_party_counts.txt][the evidence file]].
- The =legal_entity= parameter type is what the browser keys the search on, so
  the card carries no profile's name; a profile that declares a string keeps a
  text field.

- The entity field is one state at a time. While nothing is chosen it is a
  search box, with a sentence saying what choosing does. Once an entity is
  chosen the box and the list go away and the entity stands in their place,
  named, with its LEI, its country, the parties its hierarchy would create and
  a *Change* action; *Change* opens the search again with a *Keep* action
  beside it. A search box that keeps the letters somebody typed says nothing
  about what they chose, and the walk found exactly that: the field read
  =Barc= while the tenant had already been built around BARCLAYS PLC.

* Result

Three starting points are rows: the manual card, the register card and the
demo. The register card leads with the entity the tenant is built around,
derives the tenant's name, code, hostname, administrator and legal entity from
the one chosen, and states how many parties that entity's hierarchy would
create — a count checked against the publication itself. The search that finds
an entity matches a name or an LEI in the read rather than filtering a page in
the browser, because the deployment holds 18348 root entities and the entity
somebody wants is not on any one page of them.

The manual card leaves the legal entity out: the step that imports a hierarchy
reads an absent entity as empty, completes with a warning and says there was
nothing to import, which the rail shows beside it.

The code's shape is stated once and applied everywhere: the field applies it as
a person types, the provision request refuses a code that breaks it with a
sentence, and the table holds every other writer to it — as it does for a
hostname that names a port, which would make the tenant's own administrator
unresolvable. Two writers the rule caught were fixed with it: the synthetic
generator, whose codes carried the template's hyphen and a faker noun's
capitals, and the test harness's suite tenant, which carried the suite's dots.

Proved on the live deployment and at the schema:
[[file:evidence/gleif_search_and_party_counts.txt][the search and the counts]] and
[[file:evidence/tenant_shape_rule.txt][the shapes the table refuses]].
