* Goal

Replace the sixteen analytic switches of the risk report configuration with the analytics of the configuration as rows, and give each analytic its parameters, so that a configuration says which analytics a run executes and how. A report definition owns neither, because it binds a shared configuration. Publish the rows through DQ datasets that are generated from the domain entities, and populate each party's datasets with the analytics and parameters decided for its reports. The same change moves the rest of the run document, the Setup choices and the Markets block, onto the configuration: everything in the run document that is not a data file is a choice of the shared configuration, and the data files are named from the file types table.

* Acceptance

- The report_analytic and report_analytic_parameter entities are removed. A configuration_analytic junction links a configuration to an analytic type with its order and active flag, and the existing configuration_parameter entity holds the parameter values. An analytic type appears once in a run document, which holds for all 416 ORE samples, so a parameter definition identifies the analytic a value belongs to.
- The switch columns are removed from risk_report_config, and the run document is built from the analytic rows and the parameter rows. A stored run document, and the import-run path that writes the old rows, are changed or removed.
- The DQ staging tables for the analytic rows and the parameter rows are generated from the entities. A staged row names its configuration, its analytic type and its parameter definition by name and not by id, because ids differ between databases.
- Each ACME party publishes the analytics and the parameters decided for the reports that bind each configuration, and a test shows that the exported analytics equal the decided ones.
- A configuration with no analytic is refused at publish or by a trigger, because a database check cannot count child rows.
- Every Setup parameter that is not a data file is a column of =risk_report_config=, which is DQ enabled, so the staging table is generated with it. The values come from the shipped samples: the log mask, the paths, =implyTodaysFixings=, =continueOnError=, =buildFailedTrades=, =lazyMarketBuilding=, =includeTodaysCashFlows=, the calendar and the convention. The flags are text columns that hold the value in the spelling ORE uses for that parameter, so a sample imports and exports without any change.
- The Markets block is held on the configuration: =report_market_binding= is renamed =configuration_market_binding= and re-keyed to the configuration, with DQ staging, and ACME publishes the roles it needs.
- =report_run_setup= and its file name columns are removed, because the file names come from the file types table. =ore import-run= maps a sample Setup onto the configuration and stores no file names.
- The exported Setup of every ACME definition contains each non-file parameter that the samples set in at least half of their run documents, and a test shows that the exported Setup carries the stored choices.

* Plan

1. Take stock of what holds analytics today: =report_analytic=, =report_analytic_parameter=, =report_run_setup=, =report_market_binding=, the sixteen switches of =risk_report_config=, the run document builder, and the =import-run= path of the run store.
2. Decide the model. The recommendation is a =configuration_analytic= junction between a configuration and an analytic type, with the order and the active flag, and the existing =configuration_parameter= entity for the values. A parameter definition names its scope, analytic type and name, so it already says which analytic a value belongs to. Decide what happens to the run setup and the market bindings, which are also keyed by definition.
3. Decide how the "at least one analytic" rule is enforced, because a database check cannot count child rows. The options are a trigger on the analytic rows and a check in the publish.
4. Remove the old entities and the switches, generate the new ones, and generate the DQ staging from them. The staged rows name the configuration, the analytic type and the parameter definition.
5. Decide the analytics and parameters of each report from the ORE samples, record them in the report design, and publish them in each party's datasets.
6. Build the run document from the rows, and test that the exported analytics equal the decided ones for all 78 definitions.
7. Add the non-file Setup parameters as columns of =risk_report_config=, regenerate, and publish the decided values with the configurations.
8. Rename =report_market_binding= to =configuration_market_binding=, re-key it to the configuration, and add its DQ staging and its ACME rows.
9. Remove =report_run_setup=. Change =ore import-run= to map the Setup onto the configuration, and the generator to build the Setup from the columns.

* Notes

The analysis is [[id:4D47DE4D-A52F-46E5-BA75-C2141BEB72D3][The analytics of a configuration and their parameters]]. It recommends keeping two entities, renamed =configuration_analytic= and =configuration_analytic_parameter= and re-keyed to the configuration, in place of the earlier idea of reusing =configuration_parameter=.

Names. These entities are attached to a configuration and not to a report, so none of them carries a =report_= prefix.

Evidence for the model, from the 416 ORE samples: no run document repeats an analytic type, so (configuration, parameter definition) identifies a value. The first assignment of analytics to the reports was wrong in six places, and the flat switches cannot hold the parameters the corrected analytics need: the historical window of the stressed VaR, the quantiles of the VaR, and the exposure profile flags. See rule D22 of the report design.

Parameters that name a file are not stored here. They are resolved from the file types table, see the tasks "Add the ORE file types table with well known names" and "Name every ORE file from the file types table".

* Result

The analytics with their parameters, the run choices and the market bindings now belong to the shared, DQ enabled configuration. =report_run_setup= and =report_market_binding= are gone, and a definition has no run document of its own: the run document is built from the configuration it binds, and the data file names are not stored. ACME publishes 49 configurations with 76 analytics, 175 parameter values, the run choices and one pricing market binding each.

Found on the way: the as-of date was missing from every live or end of day export, a bug that existed before this work. The generator now resolves it when it builds the run document. A text binding table with one slot too many caused an intermittent crash and is fixed.

Acceptance is met. Left for later tasks: the ORE file types table, which names every file, and running the exported packages in ORE.
