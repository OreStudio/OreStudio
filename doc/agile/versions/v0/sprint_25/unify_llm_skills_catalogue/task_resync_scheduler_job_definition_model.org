* Notes

** Columns the model had wrong, now fixed

=schedule_expression= was =std::string= where the code has
=cron_expression=. The model now declares only the type and the
custom-type registry supplies the header, which is that mechanism's
first real use. =action_type= and =action_payload= carried SQL
defaults but no C++ member default, so the generated struct dropped
="execute_sql"= and ="{}"=; both now declare =:default_value:=.

** is_active: one type across the board, and it is bool

Boolean is the established convention — 42 =boolean= columns against a
handful of integer-flag outliers, of which =is_active= is one.

The codebase already agrees on =bool=: the domain struct, the protocol
struct, the Qt model and monitor window, the generator and the status
handler all use it. Only three places disagree, and they are the
storage side: the SQL column (=integer not null default 1=), the
repository entity (=int is_active = 1=), and this model. The mapper
converts between them.

So the change is to storage, not to the domain: the column becomes
=boolean not null default true=, the model declares =boolean= /
=bool=, the entity becomes =bool=, and the mapper conversion goes
away. Two populate scripts write the column and have to move with it.

** tenant_id: a correction, and a defect it exposed

An earlier note here said the hand-written =std::optional= was the
outlier and codegen's strong type was the convention to adopt. That
was wrong, and the DDL settles it: the column is ="tenant_id" uuid=
with no =not null=, so it is nullable, and a nullable column should be
optional.

The reason codegen's type is not equivalent is that
=utility::uuid::tenant_id::system()= is the max UUID from RFC 9562 — a
real, distinct tenant identity, not an absence. Its own header says
the type exists to prevent a nil UUID being confused with the system
tenant. So SQL NULL and =system()= denote different things, and
emitting a non-optional type for a nullable column conflates them.

=nullable_tenant_id: true= only makes the SQL column nullable. It does
not change the domain or entity type, which exposes a live defect in
the other entity that sets it: =synthetic.market_data_generation_config=
has =std::string tenant_id= in its entity and a mapper that calls
=from_string(v.tenant_id).value()=. =from_string= rejects nil and
=.value()= throws on an error, so a NULL tenant row crashes the
mapper. That is a registry component, and the bug is reachable from
the schema as it stands.

** The six hand-written operations are all live

- =read_all_active= — =scheduler_loop.cpp:82= loads every job it must
  fire, across tenants. The scheduling loop does not run without it.
- =find_by_name= twice — an overload pair, the one-argument form
  delegating to the tenant-scoped one. =job_definition_service.cpp:56=
  uses it so a save with an existing name updates in place instead of
  violating the unique constraint.
- =schedule= and =unschedule= — used cross-component by
  =ores.reporting='s =report_scheduling_service=, over NATS.
- =schedule_batch= — registered as a subscription in
  =registrar.cpp:51=.

None is cruft. Removing any of them breaks something that runs.

** The custom history is broken, not merely custom

=job_definition_handler.hpp:200= calls
=svc.get_definition_history(...)=, discards the result, and replies
=get_job_history_response{.success = true}=. The response carries
=std::vector<job_instance> instances=, which is never populated, so
every caller receives success and an empty list. The handler's own
comment says instance execution history is not implemented, and it
conflates two things: the service returns definition version history
while the response is shaped for execution records.

=JobDefinitionAuditDialog.cpp:133= sends this request, so the audit
dialog shows an empty history and reports no error.

This is the strongest candidate for the generic history provider
rather than for modelling as-is: there is no working behaviour to
preserve.

** What this means for sequencing

The protocol requirement is already met: =scheduler_protocol.hpp=
lives in =ores.scheduler.api/messaging/= and =ores.reporting= includes
it from there, so the cross-component types are in =api= already.

Codegen has the mechanism the hand-written operations need. Paste
blocks (=<<paste:KIND_UUID>>=, substituted from the entity's
paste-point blocks) let generated files carry hand-written regions, so
the operations can be modelled and pasted rather than lost.

Nothing here may be removed before its replacement is modelled. The
removal and the modelling belong in the same change, or the tree
builds against operations that no longer exist.

* Result

Partly done, and the part that is done is the one that could be done
without changing behaviour anyone depends on.

=is_active= is a boolean across the board. The domain was already
right — the struct, the protocol struct, the Qt model and monitor, the
generator and the status handler all declared =bool=. Only the SQL
column, the repository entity and the model said integer, with the
mapper converting. So the change went to storage: the model declares
=boolean= and =bool=, the regenerated DDL reads
=boolean not null default true=, the entity is =bool=, and the
mapper's conversions are plain assignments.

Two breaks sat below the model and would have shipped unnoticed. The
hand-written repository parsed the column with =std::stoi=, which
throws on the =t= Postgres returns for a boolean, and
=read_all_active= filtered on =is_active = 1=, which a boolean column
rejects. The parse now accepts =1=, =t= or =true= following
=fsm_service=, and the predicate compares against =true=. Two populate
scripts wrote the integer literal, one of them in =compute= seeding a
row into the scheduler's table, and a one-shot migration converts
databases that predate the change.

=schedule_expression=, =action_type= and =action_payload= were fixed
earlier in this task: the first now declares =cron_expression= and
lets the custom-type registry supply the header, which is that
mechanism's first real use.

=tenant_id= is filed rather than fixed, because the defect is not in
the scheduler. Its column is nullable and its code already uses an
optional, which is correct. Codegen is what emits a non-optional
strong type for a nullable tenant, and =system()= is the max UUID — a
real tenant rather than an absence — so the two are not
interchangeable. Filed as [[id:B69BF02C-9E16-4DAF-BC0C-C5DBE0EC1BF4][Make a nullable tenant column an optional type]],
which also carries the crash it exposed in =synthetic=.

The six hand-written operations are all live and none is cruft, so
they are filed as [[id:07494555-8EDB-48C2-8425-CB86EE366FDC][Model the scheduler's hand-written operations and remove them together]],
whose first constraint is that no commit removes an operation before
its replacement exists. The custom history is filed separately as
[[id:6110D479-CAF3-4915-8A64-698193893402][Replace the scheduler's custom history with the generic provider]]:
it discards the service result and replies success with an empty
vector, so there is no working behaviour to preserve.

The component therefore does not join the drift registry yet. Saying
otherwise would claim a guarantee the remaining facets cannot honour.

Findings, filed as [[id:9FE3FA66-514B-4C67-83E7-11973B8E520E][Clear the ores.scheduler component audit findings]]:

1. The model sets =:generator_facet_name: generator= while the tree
   has =api/src/generators= and every other component uses the plural.
   Regenerating creates a second directory beside the existing one and
   orphans it.
2. =core/src/builder/= is not a catalogued facet, so it is a folder
   name with no signed-off meaning.
3. The messaging reference documents four subjects while the registrar
   registers seven handlers: =schedule_jobs_batch=,
   =get_job_instances= and =get_scheduler_status= have no subject row.
4. The reference describes the history subject as retrieving execution
   history, which is what its handler does not do.

Also worth recording rather than filing: =core= has one test file,
covering the builder. The repository and mapper this task changed have
no tests, which is why the change was verified by compiling them and
by reading the SQL rather than by running anything.
