* Goal

The screen and the alerts pass both read ores_scheduler_store_bounds_vw for whether a store is bounded. The view was written while nothing could expire an object prefix, so it states one unbounded however often its policy applies; the sweep now applies it, and the view must say so.

* Result

The view names the sweep as the mechanism of every action the sweep performs,
an object prefix's expiry included, and it reads boundedness from the last
outcome the same way it does for a chunk drop. The two object prefixes now read
as bounded the moment their policy will be applied, and as unbounded when the
last run failed, which is the rule the other stores already had.

A store the sweep cannot reach is untouched by this: a node's scratch folder
still reads unbounded with the node's release as its mechanism, and the alerts
pass still tells a person about it. That is the case the notices exist for, and
it is why the pass's own test now reads the stores it expects from the view
instead of stating a number: the count follows the catalogue.

The vocabulary loses =storage_lifecycle=, because no row can state it any more.
The client's not-applied case is the node's release alone, and the store that
exercises it is the scratch folder rather than an object prefix.
