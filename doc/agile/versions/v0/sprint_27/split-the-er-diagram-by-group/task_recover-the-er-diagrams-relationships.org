* Notes

The diagram still marks 1,473 columns as FK while only 273 of them have a
target that any script states. The gap is the naming heuristic in
=apply_column_markings=, which marks every =*_id= column and everything in
=FK_COLUMNS=: =tenant_id= appears 454 times and =change_reason_code= 373
times. Those markers are left alone here -- this task is about the arrows
-- but a column marked FK with no edge is the next thing the diagram
says that the schema does not. Worth a task once the split lands.

* Result

The parser drew no edges because =FK_TARGET_TABLES= named its targets
without the =ores_= prefix that every table in the model carries, so no
lookup could match. The map is deleted.

The targets now come from the schema itself. A create script states a key
in one of three ways, and all three are read: the comment the create
template emits above a trigger check, a =REFERENCES= clause on a column,
and a named =FOREIGN KEY= constraint. Each is attached to the table in the
same script that declares the column, so a hand-written script holding
several tables still resolves; a key whose column belongs to no table in
its script, or to more than one, is left out rather than guessed at.

Of 339 stated keys, 338 resolve to a table and 328 become edges: the rest
are duplicates of the same table pair and keys a table holds to itself.
That a key no script states still draws nothing is a test, so the arrows
cannot drift back into a list kept in the parser.

The 57 columns whose target the SQL states but whose name never said so --
=day_counter=, =calendar_code= and their like -- now carry the FK mark.
