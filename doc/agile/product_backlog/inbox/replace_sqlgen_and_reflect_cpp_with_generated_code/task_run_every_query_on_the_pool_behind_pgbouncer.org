* Goal

Every service reaches postgres through pgbouncer, and every query a service
runs goes through its context's pool: a repository, a statement or a raw-SQL
helper. Two changes make this so.

- The raw-SQL helpers (=execute_raw_*= and =execute_parameterized_*= in
  =bitemporal_operations.cpp=) stop opening a connection per call. They lease
  a connection from the context's pool through =database::transact=, so a call
  on a context bound to a unit of work runs on that unit of work's
  transaction, and the tenant, party and actor settings are
  transaction-local, as they are for every other query.
- pgbouncer runs in transaction pooling mode as a systemd unit of each
  environment, beside nats-server, and the services connect to it.

The first change delivers [[id:964B4B51-C5C7-4339-AC51-593CE49CFB07][Run every hand-written query on a pooled connection]], and this task
closes it. The first change comes before the second: transaction pooling hands a server
connection to another client at each commit, so the session-level settings
the raw helpers set today would leak to that client.

* Acceptance

- No raw-SQL helper opens its own connection. Each one runs through
  =database::transact=, on the pool or on the bound unit of work's
  transaction.
- No code sets a tenant, party, actor or service setting at session level.
- An idle compute claim opens no connection: =strace= on the claim thread
  shows no =connect= and no name lookup. The idle CPU of
  =ores.compute.service= is measured before and after, and both numbers are
  recorded on this task.
- The change in semantics (a raw helper called inside a unit of work commits
  or rolls back with it, not on its own) is brought to the user for sign-off
  with its evidence before it lands, and the unit-of-work tests state the new
  behaviour.
- =compass systemd generate= emits a pgbouncer unit for each environment,
  part of =ores-<env>.target=, with its port in the environment's =.env= and
  its configuration under =build/config/=. Every service unit starts after it.
- The services' connection options name pgbouncer's port. The listener and
  the administrative paths (database recreate, schema restore) connect to
  postgres directly.
- Full build, ctest and the fleet start green; Acme provisioning completes;
  the journal has no ERROR or FATAL line; =pg_stat_activity= shows the
  services' connections arriving from pgbouncer.

* Notes

Target state: [[id:42930B6A-544A-4F7E-ACF4-9ABC60F2B408][The environments share the database through a transaction pooler]]. Its caps,
its list of what connects directly and its prepared-statement rule are this
task's specification.

Points to settle in the plan:

- One pgbouncer for the machine or one for each environment. The target doc
  caps server connections for each environment's database and for the
  instance; one pgbouncer in front of the shared instance enforces both. A
  unit for each environment fits =ores-<env>.target= and keeps environments
  independent, but then the instance cap is only the sum of the environment
  caps. Bring the choice to the user with the numbers.

- LISTEN needs a session that stays on one server connection, which
  transaction pooling does not give. The =postgres_listener_service= keeps a
  direct connection to postgres.
- Our libpq layer prepares statements. pgbouncer keeps protocol-level
  prepared statements across transaction pooling only from version 1.21, with
  =max_prepared_statements= above zero. Check the packaged version and set it.
- pgbouncer bounds the server connections. Size =default_pool_size= against
  the fleet (24 services, each with its own pool) and postgres's
  =max_connections=; see the max-connections recipe.
- =database_options= and =context_factory= read the port from the
  environment; decide whether pgbouncer's port replaces =ORES_DB_PORT= for the
  services or sits beside it.
- The unit follows =render_nats_unit= in
  =projects/ores.compass/src/systemd_generate.py=, with tests in
  =test_systemd_generate.py=; =compass env status= and the smoke check should
  report it.
