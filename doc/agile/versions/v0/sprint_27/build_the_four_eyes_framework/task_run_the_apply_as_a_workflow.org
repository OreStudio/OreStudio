* Goal

* Acceptance

- The book apply workflow is registered with the engine. Its policy is stop. Its steps are re-check, apply and tell, in that order, each naming the step it reads and a deadline, and none has a compensation.
- The refdata service answers the re-check and the apply steps. The inbox answers the tell step for every kind.
- Each step is idempotent: the engine's record of a finished step is replayed, and the apply marks each line once.
- A re-check that finds a refused line moves the request to apply_failed before anything is written. A refused apply ends the request in apply_failed. A failure of the infrastructure fails the step and leaves the request approved.
- The apply acts for the tenant and is scoped to the parties of the request's own lines, read through a function that answers party ids only.
- The tell step tells the person who asked. The notice says applied, or the state the request ended in.
- Starting the workflow on the last approval is the task "Start the apply on the last approval". The scheduled retry is "Retry a stopped apply until the window ends". The run already shows on the workflow screens, which list every run the engine holds.

* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

- Define the workflow in =ores.refdata.api=, as the iam, dq and ore workflows are defined in their api libraries, and register it in the engine.
- Share one step command, the request id, between the refdata steps and the inbox step. It lives in =ores.inbox.api=, so =ores.refdata.api= now links the inbox api.
- Serve the re-check and apply steps in =ores.refdata.service=, beside the proposal service. Serve the tell step in the inbox, because telling a person is the inbox's work.
- A step handler follows the engine's contract: read the workflow headers, replay a finished step, do the work, then publish a completion or a failure.
- Keep the mapping from a service result to a step result in plain functions with tests.

* Notes

- No NATS test of the step handlers exists, as no other handler has one. The definition, the step mapping, the party function and the notice have tests.
- The party function reads past the party policy. A workflow has no party, and the books and the lines are party-scoped, so the apply could not otherwise find either.
- The notice reuses the decided notice with the state "applied" or "apply_failed". The web may need words for those two states.
- *Known gap.* The raise and the apply write inbox tables and read accounts, and they run under the refdata service's database user. The tests run under the read-write role, which has every right, so they do not show whether that user may do it. The registry grants the refdata service no inbox rights today. The task "Grant the refdata service the inbox access it needs" closes this, and it proves the fix by running the raise and the apply as that user.

* Result

The book apply workflow exists and the services that own its steps answer them.

- =book_apply_workflow= is defined in =ores.refdata.api= and registered with the engine. Its policy is stop. Its steps are re-check, apply and tell, each naming the step it reads and stating a deadline, with no compensation.
- The refdata service answers the re-check and apply steps. A re-check that finds a refused line moves the request to apply_failed before anything is written. The apply acts for the tenant, scoped to the parties of the request's lines, which =ores_refdata_book_change_parties_fn= answers by party id alone.
- The inbox answers the tell step for every kind, with the decided notice and the state applied or apply_failed. The step command is one request id, shared from =ores.inbox.api=.
- The tests that wrote ordinary user accounts into the shared test tenant, which ended its bootstrap and made later tests fail on =modified_by=, now write service accounts. The generated =book_change= test gets its service-account requester from a seed on the derived model's request key, so a regeneration keeps it.

Evidence: the whole =ores.refdata.core.tests= binary passes in one process in default order (353 cases, 4774 assertions), and the whole =ores.inbox.core.tests= binary passes (39 cases, 201 assertions). The new cases cover the definition (five), the step mapping (five), the party function and the notice. The cmake source, handler permission, test case reachability, pasted block symbol, populate reference and derived-model checks pass, the strict ER parse is clean and the diagrams match, and the catalogue drift sweep is clean.

Not done here: starting the workflow on the last approval, the scheduled retry, an end-to-end NATS test of the step handlers, and the full ctest suite. They are the next two tasks and a limit noted above.
