Represents the composite product types ORE states. =trade_type_code=
discriminates the exact product, and the constituent trades live in the
=composite_legs= child table keyed by this instrument's =trade_id=.

The parent row carries only the basket identity and its optional free-text
description: the basket's constituents are child rows, so there is no
per-leg block to hold here. The table is bi-temporal and audited, so the
model takes the ordinary audited shape and needs no shape flag.

* C++

The C++ domain class is decomposed into nested sub-structs (the C1202
pattern from PRs #1047/#1071/#1075/#1083/#1085): the implicit scaffolding
columns (version, tenant_id, workspace_id, the primary key) and the
columns marked =:group: identity= above fold into an
=instrument_identity identity;= member (see the
ores.trading.instrument_identity field-group model), the implicit audit
columns fold into an =ores::dq::domain::audit_record audit;= member (see
the ores.dq.audit_record field-group model), and the remaining columns
stay flat in between. The SQL schema, DB entity and column lists are
unaffected -- only the domain class and the mapper's domain-side accesses
nest. The entity templates consume these annotations; domain and
repository profiles regenerate correctly.

** Service declarations
The composed service writes the instrument first, then its leg set,
because the leg table's trigger refuses a leg whose parent is not
current. The generated surface serves one entity at a time, so the two
calls that express the composition are carried here. Both bodies build
their own repositories, so the service holds no member the generated
class does not already state.

** Service implementations
#+begin_src cpp :name implementation :implements D3E7A5F2-8B4C-4D1E-9A6F-2E1C7B4D8A3F
std::vector<domain::composite_leg>
composite_instrument_service::get_legs(const std::string& trade_id) {
    BOOST_LOG_SEV(lg(), debug) << "Getting legs for composite instrument: " << trade_id;
    repository::composite_leg_repository leg_repo;
    return leg_repo.read_latest(ctx_, std::vector<std::string>{trade_id});
}

void composite_instrument_service::save_composite_instrument(
    const domain::composite_instrument& v, const std::vector<domain::composite_leg>& legs) {
    auto t = v;
    if (t.identity.trade_id.is_nil()) {
        static boost::uuids::random_generator gen;
        t.identity.trade_id = gen();
    }
    const auto id_str = boost::uuids::to_string(t.identity.trade_id);
    BOOST_LOG_SEV(lg(), debug) << "Saving composite_instrument: " << t.identity.trade_id
                               << " with " << legs.size() << " legs";
    stamp(t.identity, ctx_);
    stamp(t.audit, ctx_);
    repository::composite_leg_repository leg_repo;
    repository::composite_instrument_repository instrument_repo;
    std::vector<std::string> stale_leg_ids;
    for (const auto& existing : leg_repo.read_latest(ctx_, std::vector<std::string>{id_str}))
        stale_leg_ids.push_back(boost::uuids::to_string(existing.identity.id));
    if (!stale_leg_ids.empty())
        leg_repo.remove(ctx_, stale_leg_ids);
    instrument_repo.write(ctx_, t);
    for (auto leg : legs) {
        leg.identity.trade_id = t.identity.trade_id;
        stamp(leg, ctx_);
        leg_repo.write(ctx_, leg);
    }
    BOOST_LOG_SEV(lg(), info) << "Saved composite_instrument: " << t.identity.trade_id;
}

** Handler methods

The composed write reads and writes legs through the instrument service,
which owns both repositories. The registrar subscribes these subjects, so
the methods sit on the handler's public surface.

#+begin_src cpp :name handler_methods :implements B9E2F4A1-3C7D-4E8B-A5F0-2D6C1B8E3A7F
    void put_with_legs(ores::nats::message msg) {
        BOOST_LOG_SEV(composite_instrument_handler_lg(), debug)
            << "Handling " << msg.subject;
        auto req_ctx_expected = ores::service::service::make_request_context(
            ctx_, msg, verifier_);
        if (!req_ctx_expected) {
            error_reply(nats_, msg, req_ctx_expected.error());
            return;
        }
        const auto& req_ctx = *req_ctx_expected;
        if (!has_permission(req_ctx, "trading::composite_instruments:write")) {
            error_reply(nats_, msg, ores::service::error_code::forbidden);
            return;
        }
        auto req = decode<put_composite_instrument_with_legs_request>(msg);
        if (!req) {
            BOOST_LOG_SEV(composite_instrument_handler_lg(), warn)
                << "Failed to decode: " << msg.subject;
            error_reply(nats_, msg, ores::service::error_code::bad_request);
            return;
        }
        put_composite_instrument_with_legs_response resp;
        try {
            service::composite_instrument_service svc(req_ctx);
            auto instrument = req->instrument;
            svc.save_composite_instrument(instrument, req->legs);
            resp.instrument = std::move(instrument);
            resp.result.outcome = ores::utility::domain::outcome::ok;
        } catch (const std::exception& e) {
            BOOST_LOG_SEV(composite_instrument_handler_lg(), error)
                << msg.subject << " failed: " << e.what();
            resp.result.outcome = ores::utility::domain::outcome::failed;
            resp.result.code = "internal_error";
            resp.result.message = e.what();
        }
        reply(nats_, msg, resp);
    }

* Messages

The basket and its constituent legs are one user-visible write: a basket
is meaningless without its legs, and the leg table's insert trigger
refuses a leg whose parent is not current yet. The derived write carries
the instrument alone, so the composed write and the by-instrument leg
read are stated here, beside the derived protocol, and the handler serves
them from this same model.
