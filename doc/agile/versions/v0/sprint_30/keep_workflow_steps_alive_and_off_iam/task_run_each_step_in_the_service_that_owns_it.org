* Acceptance

- Each step kind is dispatched to its owning service's subject.
- ores.iam runs only identity steps and links no synthetic, marketdata or reporting core library.
- The parallel steps of a run execute in different services at once.

* Plan

Every step of a provisioning run is dispatched to one subject,
=iam.v1.ops.provision_tenant_step=, served by ores.iam. That is why iam links
the synthetic and refdata cores: it compiles code for work its own data has
nothing to do with. It is also why the parallel steps of a run queue: one
service takes them.

The move is one kind at a time, because each kind drags its own dependencies:

1. State the owner of each kind once, where the definition states a step's
   subject, so the engine stores the owner with the row and every service reads
   the same table. Done here, as =step_subject_for_kind=.
2. Move a kind whose work a service already owns, end to end, and drop the
   executor and the link it needed from iam. Start with =build_calendars=: the
   work is refdata's own, the step calls a request to refdata today, and no iam
   state is involved, so it proves the dispatch with the least code moved.
3. Then =generate_trades= into ores.synthetic, which drops iam's
   =ores.synthetic.core= link and takes the longest step off iam's workers.
4. Then the marketdata kinds: the curve, forward and surface publishes, the
   surface blueprints and the subscription setup.
5. Then the reporting, dq and inbox kinds: =schedule_reports=,
   =publish_bundle= and the two approval-mode steps.

Each stage is its own PR, because each one moves an executor and its link, and
a stage that lands alone is a stage a run can be proved against.

* Result

Stage 1 is done: the dispatch names the service that owns each kind, and
ores.refdata serves the calendar step in its own process.

- =step_subject_for_kind()= states the owner of a kind once, beside the words
  and the budget the definition already keeps there, and =make_step= stores the
  owner on the step the engine persists. A kind no service serves is sent to
  ores.iam, which refuses it, so an unserved kind fails where a person can read
  it instead of waiting for nobody.
- ores.refdata serves =build_calendars= on
  =refdata.v1.ops.provision_tenant_step=, through the same =step_routes= and
  =serve_step_commands= the book-apply steps use, so the step is a durable
  consumer on refdata's own stream. It calls the calendar materialisation
  service directly rather than sending refdata a request about refdata's data.
- ores.iam no longer has an executor for the calendar step, and no longer links
  =ores.marketdata.core=, which nothing it compiled had used.
- A test states the dispatch two ways: the table's answer for a kind, and the
  subject a built definition puts on the step.

What this stage does not do, and the plan's later stages cover: the remaining
16 kinds still run in ores.iam, and it still links =ores.synthetic.core= for
=generate_trades=. The parallel steps of a run now reach two services, and they
reach the rest as the stages land.

Proven end to end on 2026-11-13. =compass smoke ticks --fresh= provisioned
Acme from a recreated database, and the calendar step was dispatched to
=refdata.v1.ops.provision_tenant_step= and served by ores.refdata:

#+begin_src text
[ores.refdata.messaging.provisioning_step_handler] build_calendars: wrote 473025 day(s)
for tenant b5506162-acc4-4e9e-9eae-8a35323dc4e1
#+end_src

The step row records the owner it was dispatched to and the completed state, and
the run went on to step 13 of 15. It failed there on a refusal from
=ores.analytics.quant= — "expiry 1W: the row dated 2026-11-16 is before the spot
date 2026-11-17" — which refused all 40 surfaces. No marketdata or quant code
changed on this branch, and the refusal is captured as
[[id:C15F8BD5-6941-43CC-A989-75F4C01E5377][The 1W FX quote is dated before the spot date, so every surface is refused]].

The run also found two defects in this change, both fixed before the proof run:

- ores.refdata already served a step family on the default consumer, so a
  second family on the same stream replaced its filter: the data-quality
  publish of the countries stopped being delivered and the first run stalled
  for twenty minutes. The provisioning family now has a group of its own, and
  =serve_step_commands= refuses a second family on one stream rather than
  letting a service silently stop serving one.
- The calendar step wrote =modified_by = "system"=, which the account trigger
  refuses now that the tenant has accounts. The step acts as its own service
  account, which is an account of the system tenant, so the trigger accepts it.
