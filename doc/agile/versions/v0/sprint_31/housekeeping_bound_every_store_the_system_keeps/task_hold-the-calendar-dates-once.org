* Goal

The calendar dates exist once per installation, in the system tenant, and every
tenant reads them there, so adding a tenant adds no copy of a calendar it shares
with every other tenant. A party keeps its own holidays: its exceptions stay its
own rows and are applied over the shared days when it reads them.

This task follows the party scope, not the other way round: the overlay is per
party, so the exception must name its party first
([[id:BB0570CB-7C89-4079-AE37-39EB300F2252][Scope the calendar exceptions to a
party]]).

* Acceptance

- The dates are materialised into the system tenant, once, and no tenant holds a
  copy
- A tenant reads them through the shared-reference policy, as it reads the
  calendars and the exceptions
- A party's own exceptions still change the days that party reads, in both
  directions: an extra holiday closes a day the rules open, and a business-day
  override opens a day they close
- Two parties in one tenant read different days on the same date when their
  exceptions differ
- A party with no exception of its own reads the shared days unchanged
- The recompute path stays, and rebuilding the system tenant's copy is a command
  rather than a migration
- A test covers a tenant reading the installation's dates

* Analysis

The decision is recorded on
[[id:A54B0989-BFCB-45C6-80B7-279BF9843E78][Decide whether calendar dates are
stored or computed]]. In short: a calendar's days follow from its rule and its
exceptions, both of which the platform authors and publishes once, so the days
are the same in every tenant. A per-tenant copy is therefore the same bytes
written twice, and the treatment the classification names for derived reference
data -- recompute, or share one copy -- applies.

What this task does not do: it does not stop materialising. The dates sit on the
pricing path, and moving the computation there would charge every run for work
the installation can do once. It moves the materialisation's target from the
caller's tenant to the system tenant, and makes the copy readable across
tenants.

The read is the part that needs care, and it has two halves. The first is the
policy: =ores_refdata_calendar_dates_tbl= carries the tenant in its key and its
reads filter on the caller's tenant, so a shared-reference read policy must admit
the system tenant's rows, as the exceptions' own read already does with
=where (tenant_id = caller or tenant_id = system)=.

The second is the overlay, and it is what keeps a party's own holidays. The
shared copy is the baseline the rules state; the party's exceptions are applied
over it at read time, with the semantics the materialiser already uses:
=is_business_day = false= closes a day the rules open and =true= opens a day they
close. The read is therefore a merge keyed by date and party rather than a plain
select, and it is cheap: a party that adds no exception carries no rows to merge,
and a party that does carries a handful. A test that publishes one party's
exception and reads the dates must show the day changed for that party and
unchanged for another.

* Notes

** Where the work stands

The task is implemented, and the refdata core suite passes on a fresh database.
Three changes carry it.

The exceptions' natural key now carries the party. =party_id= is a natural key
column, so the generated composite index holds a party's rows to one per
=(calendar, date)=; the installation's rows get their own partial unique index,
=calendar_exceptions_installation_uniq_idx=, because PostgreSQL treats one null
as distinct from another. A party and the installation can therefore both answer
for one day, which is what the overlay needs.

The materialisation writes at the level that owns the calendar: a calendar of
the installation's in the system tenant, and a tenant's own calendar in its
tenant. A tenant that reads a shared calendar writes nothing for it, so its
provisioning step records no day. The stored days are the installation's answer,
so they carry the installation's exceptions only; a party's exceptions are never
written into the copy.

=calendar_day_service= is the party-aware read. It takes the stored days, with
the caller's own row winning over the shared one for a date, applies the
installation's exceptions and then the party's own, and returns the resolved
days. The tenor resolution and the pair expiry rule read through it, so two
parties answer differently on one date.

The tests are =a_party_reads_its_own_exception_over_the_days_the_installation_states=
and =a_calendar_of_the_installation_is_built_once_and_read_by_a_tenant=, in
=service_calendar_day_service_tests.cpp=.

** A caution for the next reader

The suite is not repeatable against a database that already holds a previous
run's rows. Synthetic calendars are named =X-<counter>= from a per-process
counter, so one run's code names a different calendar in the next, and the dates
left under an old code make a calendar look materialised that nobody built in
this run: the case "a calendar nobody materialised is refused" then resolves.
A green run needs =compass db recreate= first. That is a defect of the fixtures
and not of this work, and it is recorded here rather than fixed in this task.

** What is left

- *The copies a tenant already holds are not removed*, and there is no operator
  command that rebuilds the installation's copy on demand. Both are the subject
  of [[id:EFBFDD7E-D423-4F5E-A89E-894A1D4F286A][Purge the calendar days a
  tenant already holds]], which this task names rather than absorbs: the purge
  is a per-tenant act, and the command is a shell surface of its own.
- The generated calendar-date list still shows the stored days, so a screen that
  must show a party's own days needs a read of its own; this task serves the
  date math.
- An exception that names a date outside the materialised window is not applied,
  because there is no stored day to move. The materialisation owns the window.

* Result

The dates are held once, in the system tenant, and a party states only the days
it moves.

- The exceptions' natural key carries the party, and the installation's rows
  have a partial unique index of their own, so both levels can answer for one
  day.
- The materialisation writes at the level that owns the calendar: the
  installation's calendars in the system tenant, and a tenant's own calendar in
  its tenant. A tenant's run writes nothing for a shared calendar, so
  provisioning a tenant adds no copy.
- =calendar_day_service= answers a date for the caller's party: the stored days
  with the installation's exceptions applied, then the party's own. The tenor
  resolution and the pair expiry rule read through it, so two parties answer
  differently on one date without either touching the stored copy.
- The dates table's read admits the installation's rows beside the caller's
  through the two model flags, and its soft-delete rule stays in the caller's
  tenant.

Proved on a fresh database: the refdata core suite passes, 565 cases including
the two new ones (a party reading its own exception over the installation's day,
and a tenant reading a calendar the installation built); the whole refdata label
passed on the branch before it was merged with main, and the core suite again
after the merge.

Left to [[id:EFBFDD7E-D423-4F5E-A89E-894A1D4F286A][Purge the calendar days a
tenant already holds]]: the purge of copies a tenant was given before this
change, and the operator command that rebuilds the installation's copy. The
screen read of a party's days is UI work and is named in the notes.
