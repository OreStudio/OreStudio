* Acceptance

- Every test that claims something about a trade's representation is listed with what it asserts.
- Each planted defect is applied, the suites are run, and the tests that fail and pass are recorded.
- A test that claims more than it checks is named, with the fix the story should make.

* Plan

The audit found that the tests pass because they do not compare what a
roundtrip writes with what it read. The fix is the well known round-trip
property test with a canonical comparison: reading a document and writing it
back must give an equivalent document, and the test names every difference.
Everything runs in memory or in the system temp directory; no test names a
directory of its own.

1. *Inventory what each test claims.* Four groups touch a trade's
   representation: the codec roundtrips (=ores.trading/api/tests=, a struct
   survives encode and decode), the repository tests (=ores.trading/core/tests=,
   a struct survives the database), the ORE XML tests (=ores.ore/core/tests=:
   projection, exporter, import, corpus roundtrips) and the generator tests
   (=ores.synthetic/core/tests=). Only the ORE XML group can claim anything
   about ORE, and the generator group claims nothing about ORE at all. Record
   each test, its claim and what it asserts.
2. *Build a differ on the value fingerprint.* =value_fingerprint= already reads
   a document without a schema into a sorted list of path and value, numbers
   written as the decimal they mean and =xs:all= order ignored. That is the
   canonical form XMLUnit gives Java; no mainstream C++ XML diff exists, and
   libxml2's C14N keeps number spelling and sibling order, so it would report
   noise. Add, beside the fingerprint in =ores.ore.core/xml=:
   - =value_difference=: a path, a kind (lost, added or changed) and the value
     before and after.
   - =diff_values(expected, actual)=: every difference between two
     fingerprints, not the first. The fingerprint's paths carry no index, so
     values are matched as a multiset per path, and a path whose values differ
     on both sides pairs them as changes before counting the rest as lost or
     added.
   - A fingerprint scoped to one element of a document, so a portfolio is
     compared trade by trade, matched on the trade's id, and a difference
     names its trade and type.
   - A formatter that states the differences as one readable line each.
   Unit tests cover each kind of difference, numbers spelled two ways, sibling
   order, and a repeated element. The values sweep in
   =xml_roundtrip_values_tests.cpp= moves onto the differ and its
   =fingerprint_difference=, which names only the first difference, is
   deleted.
3. *Make the corpus roundtrip compare content.* The roundtrip gains an
   in-memory form, text in and text out, so the test needs no directory. The
   test =roundtrip mirrors every portfolio in the ORE example corpus= compares
   each trade of each sample with what our model writes back, and fails naming
   the file, the trade, its type, the path and the values.
4. *Known losses, asserted exactly.* Each accepted loss is a trade type, a path
   and a reason in a list in the test, asserted for equality as
   =known_export_gaps= is: a new loss fails, and a loss that stops happening
   fails until its entry is removed. The first run's differences, every one of
   them, are the baseline the list starts from; a loss we judge a defect
   rather than a gap is fixed or recorded on the story that fixes trades. The
   FxSwap far leg, stated today only as a code comment, becomes an entry.
5. *A passthrough is a failure.* A trade no family maps is written back as its
   type and envelope alone and counted apart; it fails unless its type is on an
   explicit list of unmapped types.
6. *Correct the tests that claim more than they check.* The first one is
   =a_vanilla_option_exports_its_expiry_and_style=: it checks no style, and its
   comment says ORE implies European exercise for an FxOption, which ORE
   refutes (=Exercise type "" not recognized=). The corpus name =mirrors every
   portfolio= is earned once step 3 holds.

The other direction, from our model to XML, and the proof that the tests catch
defects, are later tasks of the story: a property-based test with RapidCheck
and mutation testing with Mull.

* Notes

** What the audit found before any planted defect

- The FX option reader ignores the document's =Style= and sets
  =exercise_style= to "European" (=fx_instrument_projection.cpp=, =read_fx_option=);
  the writer writes no =Style= at all (=write_fx_option=). Every FX option loses
  its style on the roundtrip, and ORE refuses one with no style, which is why
  the run of 2026-11-03 failed every generated FxOption.
- The FxSwap writer writes an empty far date and zero far amounts: the model
  has no far leg, a gap stated only in a code comment.
- The corpus roundtrip's own comment says the per-document suites assert deep
  field fidelity for the products they name and the corpus suite asserts the
  walk. So a product with no deep suite of its own is compared by nothing.
- The values sweep compares content, but only through the XML binding layer
  (document to generated record to document), never through our trade model.

** What the roundtrip loop found beyond the corpus test

The corpus test compares document to trade model to document in memory. It
does not pass through the database, so it cannot see a row that the batch
writer stores and the export reader never reads back.

- The export reader read the shared child tables (schedules, the option
  block, strikes, range bounds) only for rates and credit trades. The FX and
  equity option rows, and an equity accumulator's range bounds, were stored
  and never exported. Fixed: the reader now reads the shared children once
  for every trade on the page, except bonds, whose own reader reads them.
- Equity basket constituents and equity swap periods have no batch read, so
  the export reader never reads them. Open.
- The export reader is hand-written, while the batch writer is generated
  from the catalogue's batch members. A reader generated from the same list
  would make a forgotten table impossible. Open.
- ORE parses a commodity swap from =SwapData=, which every ORE example uses.
  The projection reads and writes =CommoditySwapData=, the XSD's spelling,
  so ORE cannot price a commodity swap we export. Fixed.

** Modelling decisions for the remaining families

Agreed with the product owner on 2026-11-04.

- Barriers are entities. Each =BarrierData= block is an =instrument_barrier=
  row (type, style, rebate and the other terms), keyed by trade, role and
  ordinal, and its levels are =instrument_barrier_level= rows. One row with
  one level is a single barrier, one row with two levels is a double
  barrier, and several rows are a multi barrier. The 15 holders of
  =BarrierData= share the one table.
- Underlyings follow the barriers. Each =Underlying= block of ORE's
  =underlying= type is an =instrument_underlying= row (type, name,
  identifier type, currency, exchange, weight, price type and the
  commodity future terms), keyed by trade, role and ordinal. A product's
  fact row keeps the first name as its summary. A product stored before
  the rows were kept writes that name.
- A bond position on a basket names no single issue. Agreed with the
  product owner on 2026-11-05: =bond_instrument.issue_id= is optional for
  a =BondPosition= only, and the basket's bonds are =instrument_underlying=
  rows with the basket's name in =position_identifier=. A single-bond
  position, which the synthetic generator writes, keeps its issue.
- An empty element states no value to the corpus differ, because ORE reads
  =<FirstDate/>= as it reads no =FirstDate=.
- Scripted trades model every parameter. ORE reads any scripted trade,
  generic or named, as named parameters of five kinds (Event, Number,
  Index, Currency, Daycounter), each a scalar, a list of values or, for an
  event, a schedule or a derived schedule (=scriptedtrade.cpp=). A
  parameter table covers every scripted product.
- A total return swap, a composite trade and a contract for difference
  embed whole trades. Each embedded trade becomes a trade of its own,
  projected by its own family and linked from the parent.

* Result

The audit found the trade representation tests passed because none compared
what a roundtrip writes with what it read. The task built that comparison
and drove what it found to nothing.

- A differ on the value fingerprint names every difference between two
  documents, trade by trade, with numbers compared as the decimals they
  mean, sibling order ignored and an empty element read as an absent one.
- The corpus roundtrip compares each of the 182 trades in ORE's 132 example
  portfolios with what the model writes back, and fails on any difference
  not on its known list. That list went from 1432 entries to none, so a
  loss from now on fails the test.
- Closing it modelled what the model dropped: barriers, underlyings,
  scripted parameters, embedded trades joined by structures, leg payloads,
  schedules, settlement and monitoring terms, and a table of single-valued
  product terms, each with its rows in the database.
- A roundtrip through the database, run on the example trades of each
  batch, found defects the in-memory test cannot see: seed data short of
  ORE's spellings and indices, and table checks that refused valid ORE
  trades. Those are fixed; the issues it found and this task leaves open
  are captured in the product backlog.
- A minimal Acme starting point provisions what that roundtrip needs.

Acceptance: the first criterion is met in the Notes, and the third named
the FX option test and the corpus test's own claim, both now corrected. The
second, planted defects, was not done: the Plan moved that proof to the
story's later tasks, a property-based test and mutation testing.
