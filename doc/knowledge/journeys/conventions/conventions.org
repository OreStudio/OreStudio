#+title: Conventions journeys
#+description: The market terms an instrument is built on: 26 convention kinds, how the curated ones arrive by a DQ publish and the one that does not, how a person reads which document a run takes, changes one, authors one, and verifies a new party's set.
#+type: knowledge
#+level: cross
#+filetags: :knowledge:user_journey:refdata:
#+created: 2026-10-07
#+updated: 2026-10-18

A convention is the set of market terms an instrument is built on: the day
count, the calendars, the payment frequency, the index, and whatever else the
instrument family fixes before a trade exists. There are **26** convention
kinds, one per instrument family, from the deposit convention up to the
cross-currency basis swap. Each kind is its own table with its own term columns,
and no two kinds carry the same ones.

ACME holds **10,991** convention rows across those 26 kinds. **2,155** belong to
each of the five parties and **216** are held once for the tenant. The rows did
not arrive by hand. **25 of the 26 kinds arrived from a data quality publish**:
24 on =refdata.v1.ops.publish_conventions_from_dq= for the dataset *ORE
Instrument Conventions*, and =currency_pair= on its own subject and its own
dataset. The 26th, =tenor=, has no DQ route at all — there is no
=ores_dq_tenor_conventions_artefact_tbl= — and its 4 rows are copied from the
system tenant when the tenant is created.

* The lifecycle these journeys cover

Five journeys cover the life of these rows, and the order below is the order the
life takes.

1. A party is provisioned. Its conventions arrive inside that run, as the first
   member of the =party_essentials= bundle: 2,155 rows for the party, and 33 rows
   the tenant already held.
2. A curated correction is published. That path exists and cannot carry a
   correction to a tenant that already holds the row for 25 of the 26 kinds.
3. A person asks what a run will read. Today no answer exists: there is no
   default marker on any kind, no name column to look a document up by, and the
   conventions configuration a report binds carries no rows.
4. A person changes one convention of one kind. The change reaches every run of
   the party, because the export reads the party's whole document and not the
   bound configuration.
5. A person authors a term set no curated document states.

Only the third and the fifth are reachable today with what the server offers.
The first two are real lifecycle steps that the tree already performs. The
fourth cannot be finished: choosing a different document for a kind has nowhere
to be written, because no default exists.

The three reading journeys are cheap to build: the rows are stored, the lists
are generated and the histories exist. The two that change something are not,
and each says in its own /What is missing/ which server gap stops it. The
default marker is the one gap that blocks more than one journey.

* Where the 25 and the 1 come from

#+ATTR_HTML: :class hug-leading
| Route | Kinds | Subject | Bundle and scope |
|-------+-------+---------+------------------|
| the 24-kind array | 24 | =refdata.v1.ops.publish_conventions_from_dq= | =party_essentials=, once per party |
| currency pair | 1 | =refdata.v1.ops.publish_currency_pair_conventions_from_dq= | =base=, once per tenant |
| none | 1 (=tenor=) | — | copied by =ores_iam_provision_tenant_fn= |

Four kinds carry no =party_id= column and are held once for the tenant:
=currency_pair= 179 rows, =overnight_index= 23, =ibor_index= 10 and =tenor= 4.
Two of those four are in the 24-kind array, which is why a publish reports
=records_skipped 33= on every party after the first.

* A convention is a lookup that other records point at

A person starts from the instrument they want to trade, never from the entity
name, and most of a convention's fields are picks from the reference data lists
the classifications journey maintains, so a convention references those lists and
never edits them. But no other record points at a convention today: a trade
carries its scheduling terms inline, and a report binds a conventions
configuration whose contents are empty. So a convention is referenced by the
conventions file a run exports, which names every document the party holds, and
by nothing finer than that.
