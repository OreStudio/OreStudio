* Notes

** Why it broke only on Windows

Clang on Linux and AppleClang accept =std::getenv= without comment. The MSVC
STL marks it deprecated in favour of =_dupenv_s=, and the tree builds with
=-Werror=, so the deprecation is fatal there and nowhere else.

** The codebase already answers this

=ores.platform/environment/real_environment_provider.hpp= documents that
callers must go through the provider because =std::getenv= breaks the
Windows build under =-Werror=. The provider returns an
=optional<string>=, so the emptiness check moves from =*from_env != '\0'=
to =!from_env->empty()=.

** No new dependency

=projects/ores.utility/src/CMakeLists.txt= already links =ores.platform.lib=,
and the same function already calls
=ores::platform::process::executable_path()=.

* Result

=version.cpp.in= reads =ORES_VERSION_MANIFEST= through
=ores::platform::environment::environment::get_value=, which returns an
=optional<string>= and never names =std::getenv=. The =<cstdlib>= include
went with it.

=ores.utility.lib= builds and links with the change, compiling the
regenerated =version.cpp=.

The local gate ran all 52 checks rather than the usual handful, because
=.in= is not a class the checker knows, and four of them failed:
=component-drift=, =cmake-sources=, =tangle-shell= and =backlog-indexes=.
None touches this change. They are drift on main in
=ores.shell/scripts/library/report_instances/=, a generated
=report_trigger_types= directory and =product_backlog/inbox.org=, and the
gate's own prepare steps rewrote those files in the working tree. Their
side effects were reverted before this commit; they belong to whoever
landed that shell work.

Not verified here: the Windows build is the one that failed, and only
Windows can verify it. The deprecation is specific to the MSVC STL, so the
next Nightly Windows run is the proof.
