* Goal

ores.ore owns the description of ORE: its files and their versions, the leaves of its schemas with their documentation and release range, their value domains and value sets, and the map from a leaf to the column that stores it. The tables, their DQ datasets and publish functions, their operations and their generators move from ores.reporting to ores.ore with no row changed, so the product schema can be built on them.

* Plan

Draft, from the inventory below. The move is two families, because one of them
is written by compass.

1. The ORE files: =ore_file_category=, =ore_file= and =ore_file_version=, with
   their datasets, publish functions, operations, shell commands, HTTP and BFF
   routes, and the Python generators that write them. Nothing in compass names
   these tables.
2. The parameters: =ore_parameter=, its value domain, value set, value set
   value, value set catalogue, vocabulary, setting value set and element map
   column. Compass's =ore_value_sets= codec writes four of their seeds and the
   convention validator SQL with the reporting table names and paths built in,
   so this family waits for a compass release that reads them from the models.
   Agreed with compass on 2026-11-22: the codec takes each table's name and
   component from its model (=:tablename:= and =#+component:=), the data document
   maps each role to an entity name, seeds go to
   =populate/<component>/<component>_<plural>_populate.sql=, and the functions and
   the writer stamp are named after the value set entity's component. Nothing
   generated on main changes until the models move. The release is held until
   compass's document service is built, past this sprint; compass notifies this
   session.
The entities keep their names (=ore_file=, =ore_parameter= and the rest), so the
move is a relocation and the C++, TypeScript and shell names stay; their tables
become =ores_ore_*_tbl= through =:tablename:=, which 29 models already set to a
name the entity does not derive.

3. Reporting's own C++ reads of =ore_parameter= (=run_document_service.cpp:74,261=)
   become an entity-mirror cache, =cached_by= reporting, in the same PR as the
   parameters move, so no release has reporting's C++ reading =ores.ore='s tables.

=ores.ore.core= gains the database and the generated repositories, services and
handlers of these entities; =ores.ore.api= their domain types and protocols. The
dependencies allow it: =ores.ore.api= links no reporting library, and
=ores.reporting.core= already links =ores.ore.core=.

* Notes

** What the second PR found

- Compass 0.0.13 takes the names of the value set tables, their seeds, the
  validator functions and the writer stamp from the models, so moving the models
  moved the four compass seeds to =populate/ore= and repointed refdata's
  generated validators, with no compass edit; =curve_parameter_paths= is pointed
  at the moved parameters seed in =.compass.org=.
- Reporting's =run_document_service= read =ore_parameter= through its repository.
  It now takes the analytics' parameters as data: the service supplies them from
  an entity-mirror cache of =ores.ore='s parameters (=cached_by: reporting=, the
  list of analytic parameters as the cache's aux index), loaded on first use with
  the reporting service's own token and refreshed by the parameters' events; the
  tests supply them from the store. The cache needs =ores.eventing.core= in
  reporting's core, under the =core_link_edges= exception IAM's core carries for
  its party cache (approved).
- A service serves one family of step commands per stream, so the ore service's
  publish-from-DQ steps join its import steps on one consumer; a second
  =serve_step_commands= stopped the service at start.
- Reporting's engine settings proposal calls =ores_ore_setting_value_verdict_fn=
  from C++, which became =ores.ore='s with the move; it is recorded on
  [[id:68EA32A5-733C-43C2-A757-30C6EEBECEEE][Read other services' data through event-fed caches]].
- =ore import-run= fails on main as well as here: since the recent DQ changes no
  service subscribes =refdata.v1.ops.begin_bundle_import=, which the run
  configuration import calls; so the import could not exercise the cache's
  name-to-id direction live, which reporting's database tests cover.

** What the first PR found

- Moving a model regenerates the whole stack in the new component and removes
  the old one's generated files (157 written, 132 removed for the three files
  entities); what codegen does not own is the wiring: the SQL entry files, the
  registrars, the hand-authored shell application build file, and the shell
  group's =#+parts:= list, without which the generated top-level build file
  drops the new part on the next generate.
- A service's database role is granted its tables by prefix in
  =iam_service_db_grants_create.sql=, so the ore service had no right to
  =ores_ore_*= until the prefix was granted. Every unit and pgTAP test passed
  without it, because they connect as the test user; only reading the files
  through the running ore service showed it.
- The cross-component checks stay correct: reporting's file type trigger and the
  ORE file trigger, which read each other's tables, are security definer, so
  neither service needs a grant on the other's table.
- An ORE file names a reporting configuration type and a reporting file type
  names an ORE file, so the ORE file seeds keep their place inside reporting's
  populate order, included from there.

* Result

Done in two PRs. =ores.ore= owns the description of ORE: the ORE files, their
categories and their contents per release, and the parameters of ORE's documents
with their value domains, value sets, vocabulary and element map. Their models,
tables (=ores_ore_*=), DQ datasets and publish functions, operations under
=ore.v1=, history, shell commands, HTTP and BFF reads, pgTAP tests and generators
moved from =ores.reporting= with no row changed. The ore service publishes the
parameters from DQ and is granted its tables through the service registry.
Compass 0.0.13 writes the value set seeds and refdata's validators from the
models. Reporting reads the parameters through an entity-mirror cache fed by
their events, not from =ores.ore='s table; refdata's and analytics' triggers call
=ores.ore='s value set functions, as a trigger may. The knowledge page on the
ownership of ORE rows states what =ores.ore= owns.
