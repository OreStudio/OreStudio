* Acceptance

- The forward build checks the spots and both funding curve configs before it reads the expiry rule or a curve.
- A re-run of publish_party_forwards on a provisioned Acme tenant takes a fraction of the 8 minutes it took, measured.

* Plan

The marketdata log of the slow re-run showed a refusal such as "No funding curve is configured
for PLN" arriving 1 to 3 seconds after its request: the build read the pair's expiry rule, which
reads every calendar date (13515 rows, 270 to 816 ms a read), and the base currency's whole
discount curve before it looked for the quote currency's funding curve. 560 of the 716
party-pairs (179 pairs, 4 parties) cannot be built, and every run asks for each of them.

The build now reads the convention, the spots and both funding curve configs first, and the
expiry rule and the curves only for a pair that passed them. The refusal a pair gets is the
same, except where the expiry rule itself refuses.

expiry rule and the curves, so a pair a party cannot build is refused before the calendars are
read. On a fresh Acme setup the forwards step took 29 seconds instead of 3 minutes 11, and a
re-run 3.9 seconds instead of 8 minutes (see the Measurements). ores.marketdata.service.tests
passed.
