* Goal

Add the write the [[id:08169F5D-29B0-4758-968A-3C1875203A8A][Shape the role
catalogue]] journey has never had. A role's permission list can be composed and
saved in one operation, permission-gated, with the change reason and commentary
every other write carries.

The junction row also gains the audit tail =account_role= already has, so a
bundle change records who made it, when and why. The permission codes the role
write and the permission CRUD check are seeded, so an administrator holding the
documented code reaches them.

* Acceptance

- =iam.v1.roles.permissions.put= replaces a role's bundle: the codes it names
  are the codes the role bundles once it returns. An addition is recorded with
  the caller's actor, the reason it gave and its commentary; a removal closes
  the row it removes.
- A removal has no reason of its own. The delete rule closes the row and leaves
  the tail the grant wrote, so a bundle reads as its live rows plus when each
  ended. Restamping the tail on removal would lose who granted the permission,
  which is the record the journey exists for.
- The write is refused without =iam::roles:update=, as a =denied= result
  carrying that code, before anything is read or written.
- An unknown permission code is refused as =invalid=, and no row is written.
- The junction row carries =assigned_by=, =assigned_at=,
  =change_reason_code= and =change_commentary=. The write records the reason it
  is given, and an empty reason becomes =system.new_record=, the same default
  every other write in the tree applies, so the store is never asked to invent
  one.
- The response carries the bundle as stored, so the screen that saved it reads
  back what it wrote instead of hoping.
- The codes the handlers check are the codes the seed defines:
  =iam::roles:write= for the generated role write, and
  =iam::permissions:write= and =iam::permissions:delete= for the permission CRUD.
- The caller's account id is resolved from the request's actor in one place,
  and a test proves a username resolves to its account. Every subject that needs
  the caller uses it; none parses the actor as a uuid.
- The shell and the HTTP gateway reach the same subject, and a role's bundle
  can be written from either.

* Result

A role's permission bundle can be written. =iam.v1.roles.permissions.put=
takes the role and the complete bundle it should carry, checks
=iam::roles:update= before it looks anything up, resolves every code before
it writes anything, and answers with the codes as stored. The
role-permission junction gained the audit tail =account_role= already had, so
an added permission records who added it, when and why, and a removal closes
the row while the grant's tail survives.

The caller resolution the write needs is fixed underneath it: the access
subjects built the caller's account id by parsing the request's actor, which
is a username, as a uuid, so =iam.v1.roles.mine=, =.by-account=, =.assign=,
=.revoke= and both by-name subjects failed every live request. The service
resolves the actor to their account in one place now, and a test proves a
username resolves.

Three permission codes the handlers check are seeded (=iam::roles:write=,
=iam::permissions:write=, =iam::permissions:delete=); twelve remain, and
they are filed as a capture with the gate that would protect them once
seeded.

Evidence: the database was recreated from the changed create scripts (555
permissions, 133 role-permission assignments); the five IAM suites pass, with
seven new cases over the caller resolution and the bundle write; all 22 local
gates pass on the rebased base, as does the ER diagram check, and CI reports
18 of 18 checks green on the pull request. Two review rounds ran before the
PR, and every accepted finding is in the commits above.
