#+brief: The value of a series coordinate at an instant; TimescaleDB hypertable partitioned by ts.
#+created: 2026-10-25
#+updated: 2026-10-25

A tick is a value of a series at a time, and the series has one owner, a tenant and a
party, so each row carries the owner of its series. The ingest copies the owner from the
series that it resolved.

The table has no trigger, no valid_to and one index on the series and the time. A
correction is a new row, and the reader takes the latest. There is no notification trigger:
the live path publishes the tick, and the table is the history.

Row-level security uses the policies of the other tables, in the scalar subquery form. The
session functions that the other tables call cost about 8 to 10 microseconds for each
filtered row, because the planner calls them again for every row, and a subquery around the
setting makes it evaluate the setting once for each query. FORCE makes the policies apply
to the owner too.

The marketdata tick writer role has BYPASSRLS and INSERT only. PostgreSQL refuses COPY into
a table with row-level security for a role that the policies apply to, and this role is
exempt. It does not own the table and has no SELECT.

The table is not compressed, because row-level security is not supported on compressed
chunks. Retention drops whole chunks. See doc/knowledge/architecture/tick_ingest_pipeline.org.

* Columns

** party_id
:PROPERTIES:
:type:     uuid

:END:

Party that owns the series this tick belongs to. The ingest copies it from the
series, and the party policy filters every read by it.

** series_id
:PROPERTIES:
:type:     uuid

The table is not compressed, because row-level security is not supported on
compressed chunks. Retention drops whole chunks.

The tenant and party policies take the value of their session setting through a
scalar subquery, so the setting is read once for each query rather than once for
each row. The party policy is =select= alone and =restrictive=, and carries no
null passthrough: an ingest session states its visible parties.

** Indexes

| name      | columns           | unique | current_only | where_extra |
|-----------+-------------------+--------+--------------+-------------|
| series_ts | series_id, ts desc | false  | false        |             |

One index serves the reader that takes the latest tick of each coordinate of a
series. The table is not keyed, so the index is the only structure over it.

* Physical space

No facet beyond the SQL schema renders: the model states =:sql_only: true=.

The table sends no notification. The live tick stream carries each new value, and
a notification for each row would take a database-wide lock at every commit and
tell a client to reload a series that changes faster than the client can read it.
