This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A quant composes one interest-rate curve feed: its currency, index and role, the short-rate process and the parameter values it is seeded with, the tenor ladder the curve is bootstrapped from, and the previews that say whether the choice is sane.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want the feed to publish the curve the desk agreed, rather than a flat or
inverted one that nobody notices until pricing uses it." The journey is done
when the feed is saved and reads back with the chosen process, one value row
per parameter definition, and an ordered ladder of at least one entry.

This journey authors a *generated* curve. It is not the market-data curve
blueprint, which shapes a real curve from quotes. Here the short-rate process
decides the shape the synthetic curve will have, and the Curve Template decides
the grid it is published on; neither is the other's consequence.

* Actor and trigger

The actor is a quant who holds the market-data management role, or a desk
analyst acting for the collection. The quant is the maker: the feed is theirs to
author. The trigger is a new currency and index to simulate, a new short-rate
model, a changed parameter set, or a changed ladder. The journey starts at the
collection in the synthetic tree and ends when the person leaves the saved feed.

A saved feed is a configuration. It produces nothing until the feed is started,
and starting it is a separate journey. The model calls this record the
=ir_curve_generation_config= and the screen calls it the curve feed.

* Steps

1. *Open the collection.* The person opens *Market data*, then *Synthetic*, and
   chooses a collection in the tree. The system shows the collection's folders
   and its feeds: for each IR curve feed the currency, the index family, the
   tenor, the role, the process type, the source name and whether it is enabled.
   The person filters on the page.
2. *Open or start a feed.* The person selects a row and the system shows the
   feed screen, or the person chooses *New IR curve* and the system shows the
   same screen empty. The collection and the owning party come from the tree;
   they are not typed again.
3. *Set the curve's identity and its price source.* On the *Instrument* tab the
   person chooses the currency, the index family, the tenor and the role
   (=discount=, =projection= or =self_discounting=), names the fixed-leg payment
   frequency that a swap ladder resolves its schedule with, and writes a
   description. The tenor is empty for an overnight family and may be =FOMC=
   only for =sofr=. The person then chooses =fixed=, which uses the
   =initial_rate= value as entered, or =vintage=, which reads the starting
   short rate from a market-data observation; under =vintage= the person sets
   the source, the date and the series, the last through the oresmd URI editor.
   The vintage option is unavailable until the currency and the index family are
   set.
4. *Choose the short-rate process.* On the *Process* tab the person chooses a
   process from the yield curve process type catalogue: =VASICEK=,
   =COX_INGERSOLL_ROSS=, =HULL_WHITE= or =TWO_FACTOR_GAUSSIAN=. Changing the
   process replaces the parameter rows with that process's definitions, and the
   system shows each definition's description.
5. *Fill the parameter values.* The system lists one row per parameter
   definition of the chosen process: the symbol, the label, the description, the
   default, and the minimum and maximum where the definition carries them. The
   person enters a value in each row. The screen refuses a value outside its
   bounds; the server refuses a missing parameter, a duplicate, and a value
   whose definition belongs to another process type.
6. *Read the previews.* The person asks for the curve shape and the system draws
   the rate against the tenor implied by the current parameter values and ladder
   rows, one marker per ladder entry. The person reseeds and chooses between one
   and eight paths, and the system draws that many sample short-rate draws over
   the horizon at the matching seed. Both previews are stateless and save
   nothing.
7. *Define the ladder.* On the *Curve Template* tab the person adds, changes,
   removes and reorders rows. Each row carries a zero-based sequence, a start
   tenor, an end tenor and an instrument. A point instrument, a deposit or a
   swap, sets its start to =SPOT=; an interval instrument, a forward rate
   agreement, sets its start to the period's own front tenor. The system refuses
   an empty ladder and a pair of overlapping windows.
8. *Check the provenance and the history.* On the *Provenance* tab the person
   reads the price source, the vintage binding, who changed the feed and when,
   and every version with the change from the one before. A revert is a new
   version, not a deletion.
9. *Save the feed.* The person chooses *Save*. The system writes the config,
   then its parameter values, then its ladder rows, and replies with the version
   it wrote. The feed is not running; a running feed keeps its old parameters
   until it is stopped and restarted.
10. *Leave.* The person goes back to the collection. Nothing has been published,
    and the feed has produced no curve yet.

Step 9 is three writes, not one: the config, its values and its ladder are
separate resources, so a failure between them leaves a config whose process or
ladder is partly updated; see /What is missing/.

The config and its two child row sets are versioned, so each has a history. The
process types and their parameter definitions are system-tenant reference data:
the screen reads them and never writes them. The vintage series is referenced by
an oresmd URI, not by a foreign key.

The three =partial= rows are the generated list verbs: each filter is
=id_one_of= alone, so no list is scoped to a parent collection or to a parent
feed. The screen lists the tenant's rows and matches on the page. Every other
subject above is generated from the component's protocol and exists.

* What is missing

1. *Saving a feed is three writes, not one.* The config, its parameter values
   and its ladder rows are separate generated resources with separate =put=
   subjects, and no operation writes all three together. A failure between the
   writes leaves a config whose process or ladder is partly updated. The
   candidate is an apply operation that writes the config and both child sets
   together. Until then the screen writes the config first, then the values,
   then the ladder, and says what it wrote.
2. *No list is scoped to its parent.* Every filter is =id_one_of=: nothing names
   "the IR curve feeds under this collection", "the parameter values of this
   feed" or "the ladder rows of this feed". The candidate is a parent filter on
   each list, or a scoped read. Until then the screen lists the tenant's rows
   and matches on the page.
3. *No screen exists.* No web page, HTTP route or shell verb reaches any
   synthetic curve operation. The Market Simulator window was the removed Qt
   client's, and the generated detail dialog for this config is disabled. The
   candidate is a web page and a route. Until then the journey runs only from
   the shell.
4. *A saved feed is not a running feed.* Save writes the configuration; the feed
   produces nothing until it is started, and a running feed keeps its old
   parameters, values and ladder until it is stopped and restarted. The screen
   says so and offers no restart. The candidate is a restart on save. Until then
   the person stops and starts the feed.
5. *The previews take loose inputs, not a saved feed.* Both operations take a
   process type and a parameter vector rather than a config id, so the editor
   assembles the request and the server never reads the stored row. The
   candidate is a preview keyed by the feed. Until then the editor sends what
   the form holds.
6. *No approval kind covers a feed change.* The inbox models a generic approval
   kind, but only =iam.role_grant= is seeded. A feed change is written with no
   second pair of eyes, and no comment. The candidate is an approval kind for a
   feed, with its decide permission and its required approvals. Until then a
   save takes effect at once and the history names the writer alone.
7. *The tenor and instrument references are undeclared.* The ladder's start and
   end tenors, the index tenor and the instrument code are soft references: the
   screen offers the reference-data list, but the database holds only text, and
   the application layer validates it. The screen cannot tell a stored code the
   list does not hold. The candidate is a declared reference. Until then the
   screen marks a value it cannot find in the list.
