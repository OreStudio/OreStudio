* Goal

The application's dark theme is the GitHub-dark palette the project site uses, and the landing-page review argued a different one: a blue-black surface ramp on slate neutrals, an indigo accent reserved for interaction, and a sky hue for content that is not built yet. The reviewed screens also lean on tokens the theme does not carry — accent tints, a tinted elevation glow, a radius scale, and a micro-label size — so every screen that wants them hard-codes a value instead. Move the theme onto the reviewed scheme and add the missing roles, from the one block every screen reads.

* Acceptance

- styles.css carries the reviewed scheme: the surface, line, ink and accent ramps.
- Every token the application uses today is still declared, so no screen loses its colour.
- The roles the reviewed screens need and the theme lacks are declared: accent tints, an elevation glow, a hue for future content, the radius scale, and the micro-label size.
- The web check passes: typecheck, format and tests.

* Plan

The theme is one block, and every screen reads it through Tailwind utilities, so
the palette is a single edit with an application-wide effect. That is also the
risk: a token that vanishes takes a screen's colour with it, and nothing in the
web check reads a colour.

So measure before choosing. Take the reviewed screens' scheme, then hold every
role it defines against the surface it will sit on and compute the contrast
rather than trusting the eye. The review draws its accent where it looks right
on a mock screen; the application has to pass AA with it.

Then confirm the tokens survive the build. Tailwind prunes what nothing uses, so
a token is only proved by looking for it in the emitted stylesheet.

The accent is the one role that gets worse, and deliberately: the review's
indigo at 500 measures 4.00 as text and 4.35 for the inverse ink on a fill, so
it fails AA on both sides. At 400 it measures 5.98 and 6.51.

=ink-faint= is below AA for body text before and after. It is used 175 times,
almost always on a secondary line, so it is left where it is rather than
changed under cover of a palette move.

The prototypes are not touched. Each one copies the tokens from
=styles.css= by hand, as the prototypes index requires, so all of them still
carry the old scheme. That is a follow-up, and a candidate for a check that
reads the copies against the source.

* Result

The theme carries the reviewed scheme from one block, and every screen moved
with it: the surfaces, the lines, the ink and the three semantic colours all
took the new ramp, and the accent is indigo at 400.

The review's own indigo at 500 did not survive the measurement. It fails AA on
both sides the application uses an accent on, so the hue is the review's and
the lightness is a floor the review could not see from a mock screen. Of the
roles that changed, five improved their contrast and only the accent and its
bright step got worse, both still inside AA.

The roles the theme lacked are declared beside the palette: the accent at ten
and twenty percent for the tile fill and its hairline, a sky pair for content
that is not built yet, the violet the reviewed screens use in a gradient, a
three-step radius scale, a tinted elevation, and the micro-label size and
tracking. =--color-accent-dim= was a grey that no screen used; it is now the
tint its name claims.

Two things are deliberately not done here. The 175 uses of =ink-faint= are
left below AA, because a palette move is the wrong place to change a
secondary line. And the prototypes still carry the old tokens, because each
copies them by hand; refreshing thirty of them, or checking the copies against
the source, is its own change.

The web check was red on trunk when this started, on six files the formatter
had never seen. They are formatted here, because the check cannot pass
otherwise.
