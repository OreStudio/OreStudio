* Goal

Every generated Acme staff account must be able to log in with the
shared =Secure-Password-123= password, matching the parent story's
own acceptance criterion (staff accounts exist to exercise RBAC —
trader, middle office, etc. — which requires actually logging in as
them). Currently blocked: =account_service::login()= requires a row
in =ores_iam_login_info_tbl= (created by =ores_iam_system_provisioner_create.sql=
for =super_admin=/=tenant_admin=), but the accounts publish-from-dq
SQL path used to bulk-create the ~59 generated Acme staff accounts
never inserts one, so login throws "Login tracking information
missing" for every one of them. Discovered while testing the curated
Acme staff connections added by [[id:9A94B0D4-4244-4A6B-8AFA-26AC69681519][Tidy up the saved connections database
and decommission Barclays/NatWest]].

* Acceptance

- Every generated Acme staff account has a row in
  =ores_iam_login_info_tbl= immediately after =--source acme=
  provisioning completes (=SELECT count(*) FROM ores_iam_accounts_tbl
  a LEFT JOIN ores_iam_login_info_tbl li ON li.account_id = a.id WHERE
  li.account_id IS NULL= returns only non-=user=-type accounts, if
  any).
- Logging in as any generated staff account (e.g. the curated Acme
  connections' personas) with password =Secure-Password-123=
  succeeds.
- The fix lands in the accounts publish-from-dq SQL function (or
  wherever bulk account creation happens), not a one-off backfill
  script — any future bulk-created account must get a login_info row
  by construction.
