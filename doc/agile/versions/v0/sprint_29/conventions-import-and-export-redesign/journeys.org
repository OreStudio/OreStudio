This page describes a transition, not the current state. It must not be
linked from durable documentation; when the work lands, the durable record is
the knowledge page it produces.

* Summary

This page collects the user journeys for importing and exporting ORE and other
data, and reads them as requirements on an import mechanism. It does not choose
a mechanism. The owner decides that.

The journeys live under
=doc/knowledge/journeys/data_exchange/=. They cover a whole environment, a party,
one dataset, a retry, a party-scoped user, a failed family, market data, support
and archive exports, and the preview the person wants before a write.

* Requirements the journeys impose

#+ATTR_HTML: :class hug-leading
| Requirement | Journeys | What it means |
|-------------+----------+---------------|
| Atomicity | Reproduce a defect; Onboard a party; Import one dataset; See what a failed family left behind; Review an import | A file is applied in full or not at all. The person must never read a half file. |
| Size | Reproduce a defect; Seed a fresh environment; Promote an environment; Export for archival | A real party's data exceeds one request. The mechanism must take a file in parts and still be atomic. |
| Who may do it | Onboard a party; Import as a party-scoped user | The import is scoped to the session's party. An operations user and a tenant administrator are different actors, and today only the administrator holds the permissions. |
| Resumability | Reproduce a defect; Retry a failed import | A failed or interrupted import can be retried without doubling the data, and the person can read what the first attempt left. |
| Visibility before commit | Retry a failed import; See what a failed family left behind; Review an import | The person sees the per-family effect and the refusals before the live tables change, and nothing staged is visible to a reader. |
| Cross-component scope | Reproduce a defect; Seed a fresh environment; Promote an environment; Export to share with support; Export for archival | One file set carries conventions, curves, market data, portfolios, trades and run documents, which live in different owning services. |
| Audit | Promote an environment; Retry a failed import; See what a failed family left behind; Export for archival | The person can say which file was applied, by whom, into which party, when, and what it wrote. The current exports carry no audit columns. |
| Idempotency | Seed a fresh environment; Promote an environment; Retry a failed import | Applying the same file twice converges to the same state. Conventions replace by key today; trades do not and duplicate. |
| Ordering | Seed a fresh environment; Promote an environment | Parents are applied before parts: currencies before trades, conventions before curves, run document before its bindings. |
| Failure reporting | Reproduce a defect; Retry a failed import; See what a failed family left behind; Import market data | Every refused row is named with its family or file, and a skipped family is reported, not dropped. |
| Isolation of one dataset | Import one dataset; Export to share with support | A person can import or export one dataset without sweeping in the rest. |
| Export consistency | Export to share with support; Export for archival | The parts of an export are read at one instant, or the manifest says they were not. |
| Retention and reversibility | Onboard a party; See what a failed family left behind; Export for archival | Omission is not a delete, and a rollback reaches every row the import wrote. |

Some requirements conflict today. The trade import keeps every trade that
saved and reports the failures, so it is deliberately partial. The run import
refuses before the first write and then undoes what it stored, so it aims at
all-or-nothing. A mechanism chosen for one contradicts the other unless the
journeys say which applies where.

The run import's undo covers curves, market data, pricing engines and the run
document. It does not cover conventions. The conventions save writes each family
in its own write. So the one component the design is about is the one that is
neither atomic nor rolled back.

* The shapes the journeys demand

** (a) All-or-nothing within one owning service

The write lands in one service, one database and one transaction. The service can
refuse the whole file or apply it whole, and the caller needs no staging table
outside the service.

| Journey | Why this shape |
|---------+----------------|
| [[id:239695F8-8486-404B-ADBC-85EFD1D0612F][Import one dataset in isolation]] | The file is one owner's data: conventions, or curves. |
| [[id:64DCC69B-113C-4766-BC4E-DD6CC3CC912D][Import market data from an external feed]] | The quotes and fixings all belong to marketdata. |
| [[id:8E23A435-96D8-4FF8-80FF-FB9894A2B68A][See what a failed family left behind]] | A family is one entity in one service, and its failure must not leave a partial family. |
| [[id:4FD3AE3D-27DE-4984-890A-CD78852D32FC][Review an import before it is applied]] | When the file carries one family, the preview and the commit sit in that service. |

** (b) Multi-owner with per-owner atomicity

The file set crosses owning services. One component can be applied atomically
alone, but the set as a whole cannot be one transaction without a distributed
transaction or a staged apply. The journeys in this shape demand per-owner
atomicity and a named overall outcome.

| Journey | Why this shape |
|---------+----------------|
| [[id:8953CEFB-4E41-4D95-B18C-44ACAC9D4B9B][Reproduce a defect from an exported environment]] | Trades, conventions and market data come from several services. |
| [[id:388355DD-6437-44CB-B48B-63B25B48CF1F][Seed a fresh environment from ORE sample directories]] | Currencies, portfolios, trades and configuration are several owners. |
| [[id:7057D248-6CA8-4F70-AD35-08850D5C22F6][Onboard a party with its conventions and portfolio]] | Conventions are refdata, trades are trading. |
| [[id:D911D082-3759-4645-9452-00CD60B1679E][Promote an environment between systems]] | The whole set moves, in dependency order, across two installations. |
| [[id:B74EB57C-30FB-4659-8BA4-63E7A3ED76B3][Retry a failed or interrupted import]] | A retry must converge every owner that the first attempt touched. |
| [[id:EEACF799-D2A9-45E0-AF82-BF9168C057A4][Import as a party-scoped user]] | The same multi-owner set, seen through who may write it. |
| [[id:EBB81C0A-54C2-410A-865D-2DCDD1E8EDCE][Export to share with support]] | A report problem often needs trades, conventions and market data together. |
| [[id:33AF3CCA-50BE-4CAD-A4DA-4C3917E4EA9F][Export for archival]] | A complete copy is every owner, read at one instant. |
| [[id:4FD3AE3D-27DE-4984-890A-CD78852D32FC][Review an import before it is applied]] | When the file set spans owners, the preview must span them too. |

* What this page does not decide

1. Whether the mechanism is one typed message per family, a staging table, a
   bytes handoff, or an in-process session. Those are the draft design's options
   and the owner's call.
2. Whether a trade import stays partial or becomes all-or-nothing. The journeys
   demand both, for different actors and different files.
3. Whether the export is one package or one command per component. The journeys
   demand a manifest either way.
4. Whether the import gets its own permission, or borrows the write permission of
   every row it creates. The party-scoped journey demands one of the two, and the
   seeded roles today support neither for a non-administrator.

* Open questions

1. Is a half-applied ORE file ever acceptable? The trade import says yes by
   design; the conventions import says no.
2. Does a staged import visible only to its owner count as "nothing changed", or
   must the person see the staged rows to decide?
3. Is the audit of an import a property of the file, the workflow instance, or
   the rows it writes?
4. Can the person who runs the import decide, or does a family that other
   functions read need a second person? The conventions authoring journey
   already names Market Risk as the decider.
5. What is the export of record when the installation is gone? The ORE files lose
   the audit columns and the row versions, so an archive today is not a restore
   point.
