* What

Let an entity model for a hypertable declare a bucketed range read, and generate everything the read needs. The model would state four things.

- The time column the buckets cut, and the grouping key, if any. The grid samples have none. The node samples group by host.
- For each column, how a bucket reduces it: the newest value, the sum, the maximum, or a mean weighted by another column.
- The largest number of buckets, and for a grouped read the largest number of cells, that one read may return.
- The permission that gates the read.

From that the codegen would produce the repository read, the request and reply messages with the reply as columns on a regular time axis, the handler skeleton, and the TypeScript schema.

The reply shape is the one the grid and node series use. It carries the start, the bucket width and the bucket count once. Each column is one array. A =samples= array says how many samples each bucket held, so a bucket with none is a gap and not a measured zero. A grouped read lists its keys once and lays each column out row-major.

* Why

The entity codegen generates a paged read and a newest read. Neither groups rows into buckets, so the grid series and the node series reads were written by hand in =compute_telemetry_repository.cpp=. Both repeat the same work: widen the range to whole buckets from the epoch, refuse a range that needs too many buckets, build the SQL, and fill dense arrays from sparse rows.

Every sample table will need the same read. The service samples, the NATS server and stream samples, and the telemetry logs are all time series that a screen wants as a chart over a range. Each one written by hand repeats the axis rules and risks a different gap convention. A generated read keeps one shape and one set of limits.

The shape is data-oriented on purpose. A chart reads one column, the time axis is implicit, and nothing repeats per point. Generating it keeps later reads from drifting back to a list of rows.
