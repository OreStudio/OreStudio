* Acceptance

- The command takes a report definition name, resolved within the party the
  caller is signed in to, and refuses a missing or ambiguous name by name.
- A definition that has never been scheduled produces a package, which proves
  consent is created at admission and not only by scheduling.
- =Input/ore.xml= names the documents, the portfolio and the market data, and
  validates against the ORE schema.
- The command names the report instance it made, downloads every stored tarball
  and unpacks each into its own folder.
- A failed run reports the instance's output message. A run that dispatches and
  then fails must not read as a run that never started.

* Notes

Every part of this path is built and tested: the trigger model, the admission
service, the consent, and the package chain. What has never happened is one run
through all of it, because the tests stop at dispatch and the live path needs the
workflow service and its JetStream stream.

This task is where the earlier work is proved rather than extended. If the run
fails, the failure belongs to whichever layer is at fault, not to this task, and
the first thing to do is establish which layer that is.

* Result

A person names a report and gets the packages on disk. `ore build-packages
"<report definition name>" <out_dir>` resolves the name in the party the session
is signed in to and refuses one that belongs elsewhere, naming it.

Proved on a definition that had never been scheduled, `run_grant_id` and
`scheduler_job_id` both null. It produced instance `ec6fd2d7` with
`kind=package`, an `on_demand` trigger carrying no scheduler job, and
`output_message` "Report execution completed.". The output holds `Input/ore.xml`
plus the four configuration documents, `portfolio.xml`, `market.txt` and
`fixings.txt`, and the run document names all seven where they are. The proof
script reports PASS and the schema validates.

Two things make this a thin proof, and both are recorded rather than papered
over. The portfolio is empty with zero trades and `fixings.txt` is zero bytes,
so the package is structurally right and substantively empty; market data is
real with 39131 points. And the run needed two streams created by hand with the
`nats` CLI, so it does not reproduce from the code alone.

What was found on the way matters more than the proof. Commit `515cf28072` moved
workflow step dispatch to JetStream and registered a stream for one step subject,
so every other component's step subject published into nothing and timed out.
Provisioning stalled after the IAM step and left the tenant bootstrapping, which
is why nothing in this task was reachable at first. The minimum was fixed here,
for the two synthetic publish-from-DQ subjects. The general gap is captured
separately, and its durable-subscription half is not optional: each step subject
is served by a core queue subscription that never acknowledges, so a message on a
stream is redelivered until `max_age`.
