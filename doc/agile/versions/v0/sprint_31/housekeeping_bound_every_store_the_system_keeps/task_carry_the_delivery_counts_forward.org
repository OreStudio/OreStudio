* Acceptance

- The recorder overwrites the counter for a subscription instead of appending a version of it
- The table holds one row per subscription and feed, and its size does not grow with the flush cadence
- A measured day of recording shows the row count unchanged

* Plan

What the counter is. =ores_marketdata_delivery_counts_tbl= is the metering record
behind billing: how many messages a party received, per provider and item, in a
metering period. =usage_recorder= drains the in-memory meter every thirty seconds,
and =bill_handler= reads the counts to bill. It is state, not a series: for one
subscription and one period there is one number that goes up.

It is not TimescaleDB. The create script contains no =create_hypertable= and the
table is absent from =timescaledb_information.hypertables=. TimescaleDB would not
help: chunk retention and compression are irrelevant to 23 mutable rows, and a
hypertable's unique index must include the partition column, which the natural
key does not carry.

Why it grows. The entity is modelled with the default temporal axis, so every
write appends: a new id, a new version, and the previous row closed. The
natural-key index includes =flushed_at=, so each flush is a distinct row even for
the same subscription and period. Measured on one environment: 1,260,554 rows
behind 23 subscriptions, all written in a day.

The right shape already exists in the codegen. =:current_state: true= drops the
temporal axis: no =valid_from=/=valid_to=, no version, no audit tail, no history
surface, and the model's own primary key. That is precisely a counter table, one
row per key.

The change:

1. Model =delivery_count= with =:current_state: true=, its natural key as the
   primary key: tenant, party, provider, item, period, feed.
2. Regenerate, which removes the version column, the exclusion constraint and the
   history messages, and makes the primary key the natural key.
3. Make the recorder accumulate rather than append: it holds the running total for
   each key across drains and writes that total, so the store holds one row per
   subscription and period.
4. Adapt =bill_handler= and the event registrar to the generated shape without a
   history surface.

If the delivery rate over time is wanted, that is a different question with a
different answer: a sample per interval in the telemetry store, which is already a
hypertable with a retention period, and not a second life for the billing counter.

* Result

The delivery count is a counter now, not an appended series.

The cause was the model, not the engine. The entity carried the default temporal
axis, so every flush appended a version with a new id, and the natural-key index
included =flushed_at=, so each flush was a distinct row. One environment held
1,260,554 rows behind 23 counters, all written in a day. The table was never a
hypertable, so TimescaleDB was not involved and would not have helped.

The entity now states =:current_state:= and keys on party, provider, item, period
and feed. The recorder carries the running total for each key, seeds it from the
store on the first flush so a restart does not lose the count, and writes the
total. The rating step reads one row per period instead of summing an hour's
rows.

Regeneration removed this entity's history surface: its history provider and
field mapper, two shell verbs and one eventing integration test. The
hand-written registrar and a stale generated source had to follow.
