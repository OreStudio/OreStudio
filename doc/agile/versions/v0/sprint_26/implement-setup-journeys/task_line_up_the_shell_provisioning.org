* Goal

=ores.shell= and =ores.web= drive the same three journeys through the
same server-side operations, so that neither is the reference and neither
can drift.

The shell is not a bystander in this work. It already carries the three
Setup journeys as porcelain commands, and three recipes under
=doc/recipes/shell/provisioning/= run a whole system provisioning end to
end, one per value the =--source= flag accepts. =acme_system_provision.org=
uses =--source synthetic= and =barclays_system_provision.org= uses
=--source gleif=; both run the system, tenant and party stages.
=how_do_i_provision_the_system_with_acme_corporation_holding_group.org=
uses =--source acme=, which reaches the synchronous =provision-acme=
handler this task retires, and stops after the tenant stage. They are the
sequences the browser is being built to match.

Those three commands orchestrate on the client today. This task removes
that orchestration, because the accepted
[[id:94C3AE99-8642-4418-982D-92C5FD805CCB][seed profile contract]] already
decided it: "ores.web and ores.shell are thin callers. The shell's
client-side orchestration is deleted." The work moves to the server, and
both clients become callers of one contract.

* Acceptance

- =provision system=, =provision tenant= and =provision party= call the
  same subjects the browser calls, and hold no sequence of their own.
- The orchestration they do today — publishing bundles, waiting on
  workflows, generating a synthetic organisation, associating the
  administrator with the operational parties — happens on the server, in
  one request per stage, or is recorded as deliberately staying in the
  client with the reason.
- The three end-to-end provisioning recipes —
  =acme_system_provision.org=, =barclays_system_provision.org= and
  =how_do_i_provision_the_system_with_acme_corporation_holding_group.org=
  — each run from an empty database to a working tenant, and they are the
  proof.
- The generated recipes that name the retired subjects —
  =doc/recipes/shell/bootstrap/bootstrap.org= and
  =doc/recipes/shell/tenant_provisioning/tenant_provisioning.org= — are
  regenerated against the new models rather than edited.
- The shell's command tests pass, and each command's flags still cover
  what its recipe passes.
- No flag or default is silently dropped: a knob the shell offers and the
  generic request cannot carry is either added to the request or recorded
  as gone, with the reason.

* Notes

The commands' own header says each "spans one of the GUI provisioning
wizards end-to-end". The GUI is gone, so these commands are now the only
description of what those wizards did. That makes them evidence as well as
code: the inventory in step 1 is the record of the wizard behaviour the
journeys replace, and it should not be deleted with the orchestration.

All six recipes under =doc/recipes/shell/provisioning/= are hand-written
and tangle to scripts in the shell's library. Three of them run a whole
system provisioning, one per value the =--source= flag accepts:

- =acme_system_provision.org= creates a tenant called =acme=, provisions
  it with =--source synthetic=, then adds a party and sets the default
  party.
- =barclays_system_provision.org= creates =barclays=, provisions it with
  =--source gleif= against a root LEI, then adds a party and sets the
  default party.
- =how_do_i_provision_the_system_with_acme_corporation_holding_group.org=
  creates =acme_corporation= and provisions it with =--source acme=,
  which reaches the synchronous =provision-acme= handler. It stops after
  the tenant stage, and it publishes two compute packages and the
  risk-management bundle on the way.

The other three are single-stage or unrelated: =tenant_provision.org= is
the tenant stage alone, =party_provision.org= is the party stage alone,
and =bootstrap_smoke.org= uses the raw verbs rather than =provision=.

=--source= is a flag of the porcelain =provision tenant= and not of a
script; its permitted values are =gleif=, =synthetic= and =acme=. The
=acme= value is the one that depends on the handler the generic request
replaces, so it is the value this task has to re-point; the other two
already go through work the generic request is meant to carry.

=doc/recipes/shell/tenant_provisioning/tenant_provisioning.org= is a
different thing: one generated recipe with a section per command in that
submenu, including one that calls =tenant_provisioning
provision-acme-tenant=. It is generated, so it regenerates when the
command changes and is never edited by hand.

* The orchestration, and where each piece went

The inventory of plan steps 1 and 2, kept as the record of what the
wizards did that the journeys replace. A piece is either a request now or
it is stated as staying where it was.

| Piece the shell did | What it is now |
|---------------------+----------------|
| Read the system's bootstrap answer | Kept: the first run reads it before it creates anything, exactly as the browser does. =iam.v1.bootstrap.status=. |
| Create the initial administrator, then sign in as it | Kept: the order the browser's journey takes, because a provision request needs a session. =iam.v1.bootstrap.create-admin= and =iam.v1.auth.login=. |
| Create the tenant row and its administrator | The server's, inside the provision request: =tenant_provisioning_service::provision=. |
| Publish the base bundle and wait on its nested run | The server's, as the =publish_bundle= step kind. The wait is the run's. |
| Publish the party-scoped bundles, per party, and wait | The server's, as the =provision_party= step kind, which now also activates the party, marks its onboarding complete and joins the administrator to it. |
| Import the counterparties | The starting point's parameter: the =publish_bundle= row names the dataset and the parameter whose value completes it. Nothing read =counterparty_size= before this task, so a browser-provisioned tenant held no counterparties. |
| Generate a synthetic organisation | Stays a shell tool, which the accepted seed profile contract decided: the =synthetic generate= command is a recipe's own step and not provisioning's. |
| Associate the administrator with the operational parties | The server's, inside the =provision_party= step kind, so a tenant's own run and a party stage alone do the same thing. |
| Complete provisioning: mark the tenant active, clear bootstrap mode | The server's, as the =complete_provisioning= step the tenant run appends. |
| Resolve a party by name or identifier | The server's: the party request resolves it through the party read, and refuses a reference the tenant does not hold before it starts a run. |

Flags the command offered and the request cannot carry, with the reason
each is gone: =--tenant-type= (the starting point states it, and a
request that named it would be a second starting point), =--bundle= and
=--source= (both are the starting point's), =--root-lei= (a parameter
now: =--param root_lei=), =--dataset-size= (the counterparty set belongs
to the tenant's starting point, not to one party), and the synthetic
generator's knobs (that tool's own, and it is not provisioning's).

The recipes' own runs found one defect this task did own and fixed: the
completing step of a run wrote the tenant's flags as the run's administrator,
whose party is one the provisioning created, while a tenant's flags live under
the tenant's system party, so the write was refused as a duplicate create and
the tenant was left reporting bootstrap mode with its onboarding incomplete. It
acted as the system party after that, and the browser's path had the same
defect: the demonstration and GLEIF cards both left a tenant that way.

The work also found a defect it did not own: =ores.iam.core.tests= fails
on a second run against one database, because the generated eventing
integration tests seed a soft-FK parent row and close only the row under
test. The fix is one codegen template and a regeneration of 53 files
across five components, so it is captured rather than carried here:
[[id:D42BD56B-584A-4CEF-8257-64AE14850DD9][A generated eventing integration
test leaves the parent row it seeds active]].

* Result

The three porcelain provisioning commands are thin callers of the same
subjects the browser's journeys call. =provision system= reads the
deployment's bootstrap answer, creates the administrator, signs in as it
and sends one provision request; =provision tenant= sends the same request
for every tenant after the first; =provision party= sends one party-stage
request for a named party. Each follows the run through the same progress
read the journey's rail renders. The 696 lines of client-side
orchestration are gone from the file, which is 407 lines and holds no
sequence of its own.

The orchestration they did moved rather than vanished. Publishing bundles,
importing the hierarchy, activating parties, joining the administrator to
them and completing the tenant are the step kinds the run dispatches; the
counterparty set is a starting point's parameter, which nothing read
before, so a browser-provisioned tenant held none; and the synthetic
generator stays a shell tool, which the seed profile contract decided. The
inventory of plan steps 1 and 2 records every piece and every flag that is
gone with its reason.

Two verbs retired with their last caller,
=iam.v1.bootstrap.provision-tenant= and =iam.v1.tenants.provision-acme=,
and the generated recipes, shell units and scripts that named them
regenerated. The generic request declares the request budget creating a
tenant needs, which is the budget the bootstrap verb it replaced used.

The proof is the three end-to-end recipes, run one recreate each from an
empty installation to a working tenant, recorded in
=evidence/three_recipes_from_empty_installations.txt=. The runs found a
defect on the browser's path as well as the shell's: the completing step
wrote a tenant's flags under the administrator's party rather than the
tenant's system party, so a demonstration or GLEIF tenant was left
reporting bootstrap mode with its onboarding incomplete. The step acts as
the system party now, and both paths end with the flags right and one row
each. The GLEIF tenant holds the 12,959 counterparties its =small=
parameter names.

What is left is the story's own last step and not this task's: the browser
half of proving the three journeys on a fresh database, and the journey
documents' "what is missing" lists, which still describe the state before
the story. One defect the work found is captured rather than fixed,
because its fix is a codegen template and 53 files across five
components: [[id:D42BD56B-584A-4CEF-8257-64AE14850DD9][a generated eventing
integration test leaves the parent row it seeds active]].
