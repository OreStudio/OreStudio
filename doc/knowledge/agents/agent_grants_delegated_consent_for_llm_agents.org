#+description: A person's revocable consent that one agent acts for them, bounded by a role, until an expiry; keys redeem it.

This page states the target design. It does not describe what is built.

* Summary

An agent grant is a person's consent that one named agent acts for them, in
one tenant and one party, bounded by a role made for the work, until an expiry
of at most ninety days or until the person revokes it. It is ORE's second form of the
[[id:AE30F62E-3B9E-4B59-9D11-E8FEE876949A][Grant Management]] pattern, after the run grant: the person consents once, and a
credential redeems the consent each time the agent calls. The claim of this
page is that the grant, not the credential, is the unit of consent, so the
way an agent signs in can change without changing what it may do or how it is
recorded.

* Detail

** The grant and its role

A grant belongs to one account. It names the agent, so that a person who uses
two agents grants each separately and can tell their actions apart; it fixes
the tenant and the party the agent acts in; and it names a role, as a run grant
does. At creation, IAM checks that the person holds every permission of the
role, so a person cannot grant more than they hold. At every exchange, the
token carries the role's permissions intersected with the person's current
permissions, less the permissions no agent ever holds ([[id:1679B2CE-05C2-4CFF-9A4B-47EC721CB10A][Withholding of administrative permissions from LLM agents]]). A grant of the
person's whole permission set would be a session in disguise, which [[id:AE30F62E-3B9E-4B59-9D11-E8FEE876949A][Grant Management]] names
as a pitfall; a role made for the work is the principle of least privilege
(Saltzer and Schroeder, 1975) applied to delegation.

IAM seeds one role made for agents, =AgentReader=, which holds explicit read
codes and no wildcard. A tenant administrator defines others for the work their
people delegate, such as one that books trades; a role that names a withheld
permission cannot be granted. A read-only grant is a grant of a read-only role.

** The key, a credential at rest

A key redeems the grant. Grant Management keeps a grant's id from being a
credential by requiring the client's own token as well; an agent outside ORE
has no token of its own, so the key it stores is its credential. This departs
from the pattern deliberately, and the departure is bounded ([[id:6B455B15-0FDB-4E1E-A2A8-CEFC4C1D155C][Security review of delegated access for LLM agents]]):

- every grant has an expiry, at most ninety days, and no grant is open-ended;
- the key is generated from 256 random bits, shown once, and stored as its id,
  by which it is found, and a SHA-256 hash of its secret, against which it is
  compared; a fast hash suffices because the secret is a long random value, not
  a password a person chose;
- the key is never written to a log, a refusal or a row, and ores.http keys its
  cache by the hash;
- a grant may have several keys, so a key is replaced before the old one is
  revoked, and one key can be revoked alone;
- failed exchanges are limited per tenant and per key, as the prototype
  limited failed sign-ins ([[id:039005AD-8319-416C-9F70-6A5477FEE89D][The ores.agent prototype: findings for the target design]]).

The key has the form =ores_ak_<tenant id>_<key id>_<secret>=: the tenant tells
IAM where to read, and neither id is a secret. Later, an OAuth client can
redeem the same grant: the consent page of an OAuth sign-in creates a grant
exactly as the grants page does, and everything after the grant is unchanged
([[id:BEF95B2A-42BF-40DA-BC3D-7B703C34ED73][Decide how an outside MCP client authenticates]]).

** Its lifecycle

A grant is created active by its person. It ends when the person or an
administrator revokes it, or when its expiry passes, and an ended grant does
not return. A person who is disabled or removed does not change the grant's
state; each exchange checks that the person is still active, as each run-grant
exchange checks its grantor ([[id:78B82824-0BBB-4442-A9FA-E1F265DF57BD][Run grants and run tokens]]). Revocation takes effect at the next
exchange, at most five minutes later ([[id:1162906F-BB72-486E-9A11-30D567C65F3E][Delegation tokens for LLM agents: subject and actor claims]],
/How soon a change reaches the agent/).

** Where a person governs it

A person creates, lists and revokes their grants on one page of ores.web. The
page shows each grant's agent, role, expiry, keys and when each key was last
used, links to the agent's sessions ({SES}), and links to what the agent did ([[id:2D36D474-2CF9-4498-AF49-818CEF080B98][Auditing of LLM agent actions]]).
