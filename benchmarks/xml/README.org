* What this measures

Two axes, because they answer different questions.

- *Time* is what a caller waits for. It moves on a shared machine and it is
  recorded anyway, because a change that doubles it is worth seeing.
- *Cache and instruction counts* are why the time moved. They come from
  =cachegrind=, which simulates the memory hierarchy without needing
  privileges.

Three modes, so the cost of the document model can be separated from the cost
of scanning.

| Mode | What it does |
|------+--------------|
| =scan= | reads the events and keeps nothing |
| =tape= | builds the transient document model |
| =pugi= | loads a pugixml DOM, the baseline the model is judged against |

Every count is divided by the repeat count before it is recorded, so a row for
one input is comparable with a row for another. The repeat count is a column
of its own, so the division can be undone.

* Running it

#+begin_src sh
./benchmarks/xml/run.sh              # measure and append to history.tsv
./benchmarks/xml/run.sh --no-record  # measure and print, leave the history alone
./benchmarks/xml/compare.py <older-commit> [<newer-commit>]
XML_BENCH_BUILD=build/output/other-preset ./benchmarks/xml/run.sh
#+end_src

=run.sh= builds the benchmark from the product sources using the build tree's
own flags, including its optimisation level, so it needs a configured tree but
no CMake target. It is not part of =ctest= and not part of any check: it takes
minutes and it is not a pass or fail.

=history.tsv= is long-form: one row per case, metric, repeat count, commit,
date and compiler. Appending is safe, and =compare.py= prints the delta between
any two commits that appear in it, using the most recent run for each.

The commit column names the tree that was measured, and every name in it must
be reachable from =main= or the row is untraceable.

* Cache tooling, and what it does not cover

=cachegrind= simulates the first level and one last level, and counts
instructions. It has no second-level model, so a miss that leaves L1 is either
served by the last level or counted as an LL miss. *L2 is not measured*, and
nothing in this directory claims to measure it.

It needs no privileges and its counts are stable to a few hundred instructions
of process startup. Over a run of a million instructions that is noise; over a
run of two thousand it is not, which is why the inputs are repeated until each
run is in the millions.

The miss rates cachegrind prints are recorded as well as the counts.
Utilisation is a rate, and a count alone does not say whether the working set
fits.

=perf= is installed but =/proc/sys/kernel/perf_event_paranoid= is 3, so
unprivileged processes cannot read hardware cache counters. That is the only
route to L2 numbers on this machine, and it needs =sudo sysctl
kernel.perf_event_paranoid=1=.

* A benchmarking framework

No C++ framework reports cache misses, so the cache axis needs cachegrind
whatever else is adopted.

| Option | Cost | Reach for it when |
|--------+------+-------------------|
| Google Benchmark 1.9.5 | a vcpkg dependency; the port is vendored, the source is not cached | the suite grows and you want percentiles, counters and a baseline file |
| nanobench 4.6.0 | one header, MIT, also vendored as a port | you want low-overhead microbenchmarks and HTML or CSV out |
| Catch2 =BENCHMARK= | already a dependency | the case is trivial and you want it beside the tests |

This directory uses none of them yet. Adding a dependency means a =vcpkg
install= against a build tree that is behind, and the measurement works
without it. The hand-rolled loop records the one statistic that matters on a
shared machine, best of five. Google Benchmark is the right home for the time
axis once the tree is current, because it writes a baseline file a script can
diff.

* The baseline at 32864d66de

Counts are per parse. One 478 KB portfolio, one 63 KB currency file, and the
6.3 MB calendar file.

| Input | Mode | ns/parse | Instructions | D1 misses | LL misses | D1 miss rate |
|-------+------+----------+--------------+-----------+-----------+--------------|
| small | scan | 101,815 | 1,547,849 | 1,130 | 76 | 0.2% |
| small | tape | 116,591 | 1,832,536 | 5,286 | 97 | 0.7% |
| small | pugi | 63,395 | 790,891 | 6,281 | 89 | 1.7% |
| portfolio | scan | 594,546 | 8,418,553 | 8,524 | 685 | 0.3% |
| portfolio | tape | 700,254 | 10,070,097 | 34,787 | 1,527 | 0.8% |
| portfolio | pugi | 921,256 | 5,340,115 | 39,480 | 1,352 | 1.5% |
| large | scan | 11,040,601 | 283,470,610 | 279,771 | 117,019 | 0.3% |
| large | tape | 16,839,946 | 317,511,465 | 1,228,316 | 1,104,749 | 1.0% |
| large | pugi | 14,794,060 | 193,358,570 | 906,683 | 774,798 | 1.2% |

Two readings.

*The tape is the cache cost.* Building it multiplies first-level data misses by
4.1 on the portfolio and 4.4 on the 6.3 MB file, and last-level misses by 2.2
and 9.4. A token is twenty bytes, so the 478 KB document becomes a 721 KB tape
and the 6.3 MB document becomes a 15.9 MB tape. The scan-only column is the
floor and it is far below both trees. This qualifies the claim that the
generated DOM is the expensive artefact: it is expensive relative to scanning,
and so is the tape.

*The scanner executes about 1.6 times pugixml's instructions* on the same
document, though it is now faster in wall time on both the large files. It wins
on allocated bytes and on time, and loses on work per byte.

* What the first measurements changed

The suite was first run before the stack was rebased, with a runner that
recorded totals rather than per-parse counts and that appended =-O2= after the
tree's =-O3=. Those rows were removed rather than relabelled, because a
comparison across two optimisation levels says nothing. What they found is
recorded in the message of =ef31c41f11= and in the scanner itself: the
=normalise= pre-scan was forty percent of the parse, and =memcmp= on the tag
path was another tenth. Both were fixed and the scanner's instructions fell by
48% on the portfolio and 25% on the 6.3 MB file.

* What is not a gate

"When the XML layer changes, run the benchmark" is a convention, not a check.
Making it one means a check that fails when =projects/ores.ore/core/src/xml/*=
changed and =history.tsv= gained no row for the current commit. That is a
deliberate omission: a gate on a benchmark that takes minutes needs a waiver
mechanism, and choosing one is a design decision rather than an obvious
default.
