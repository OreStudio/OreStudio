#+title: Let the owning component measure an object prefix or a host folder
#+description: The sampler measures only the stores the database can see, so the four stores that live outside a relation read as not measured: compute.job_inputs, compute.job_outputs, compute.node_scratch and compute.package_cache. The object prefixes belong to ores.storage and the folders to the compute wrapper, and neither reports a size. A person opening one of those stores reads that nothing measures it and cannot tell growth from a single sample.

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Let the component that owns a store report the store's size, and write it as a
sample the housekeeping screen can plot.

Today =ores_scheduler_sample_retained_stores_fn()= measures only the stores the
database can see: it reads =pg_total_relation_size= for the two relation shapes,
and skips every other store. Four of the ten catalogue rows are that other
shape — =compute.job_inputs= and =compute.job_outputs= are object prefixes, and
=compute.node_scratch= and =compute.package_cache= are folders on a compute
host — so they read as not measured, and the screen says so in as many words:
"Nothing measures this store yet, so its size and its growth are unknown."

The size is knowable where the store lives. =ores.storage= walks its own bucket
directory, and the compute wrapper walks a node's folder. What is missing is a
way for either to say what it found and have it land in
=ores_scheduler_retained_store_samples_tbl= beside the database's own samples.

* Why

A store nobody measures is a store nobody can bound by evidence. The retention
policies for =compute.job_inputs= and =compute.job_outputs= expire objects by
age, and no screen can say whether the policy is holding the prefix at a size or
whether the prefix grows faster than the policy removes. The two folders carry
the same gap: =compute.package_cache= is bounded by its content keying and its
size is the whole argument for that design.

The measurement cannot move into the sampler. A listing of one prefix is a read
of the object store through NATS, paged a hundred keys at a time, and a folder on
a node is not reachable from the database at all. The sampler would have to ask
each component for every store on every run.
