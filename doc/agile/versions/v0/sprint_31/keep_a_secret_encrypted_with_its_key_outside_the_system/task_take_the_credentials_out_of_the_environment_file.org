This page documents a [[id:31C868B9-306E-4282-BA8C-07E647021B34][task]] in the [[id:9D20C630-1504-4E5C-9110-C83D00DB03A1][Keep a secret encrypted, with its key outside the system]] story. It captures the goal, current status, acceptance, and any notes or results.

* Goal

Carry out the register's phases. Delete the demonstration login, hold the
provider's client secret and serve it to the gateway at the token exchange, then
move the service credentials and the IAM signing key to the vault. The
environment file stops carrying a value for a =secret= row: it names the vault
entry, and the deployment gains one system credential per unit for the
consumer's transport key. Each service resolves its database password at start,
and IAM resolves its signing key, before either opens a pool. The register
records what each phase moved and what it left.

* Acceptance

- A provider's client secret is written once through the sealed write, and the gateway obtains it at the token exchange without any part of the tree holding it.
- A service's database password is resolved at start and never written to a file, and the environment file declares its name and not its value.
- The test passwords and the NATS leaves stay as the register states, and the register records what each phase actually moved.

* Plan

The register's phases land separately, because each one ends in a tree that
runs and phase 2 changes how every service boots.

*Phase 0 — the demonstration login, done in this change.* Environment format
version 38 removes =ORES_SHELL_LOGIN_PASSWORD=: the generator no longer writes a
person's credential into a file shared by every checkout, =compass shell= reads
it from the process environment only, =compass notify= raises with one the
developer exports, and the username stays because it is not a secret. The
recipes already exported the variable, so they keep working.

*Phase 3 — E5, already true.* The register said the development TLS key is
written into the environment file. It is not: ={nats_tls_key}= is a path, the
key is a file under =build/keys/nats= with mode 0600, and the shell presents its
own leaf. The register is corrected rather than the code.

*Phase 1 — E4, waiting.* The gateway must resolve a provider's client secret at
the token exchange, and no token exchange exists yet: the external-identity
story begins with its architecture notes. The register records the wait, and the
=client_secret_ref= column is the seam it will use.

*Phase 2 — E1 and E2, next.* Each service resolves its database password, and
IAM its signing key, from the vault before it opens a pool. Reading the code
first changes the shape of it, because of one circularity the register does not
name: a service reaches IAM with =make_service_token_provider=, which signs in
with the service account's *database password* — the value the vault would
hold. The vault cannot authenticate its callers by an IAM token when the token
is what they are asking it to make possible.

The resolution is the established one for this problem, and it is written as
[[id:5FADF948-4520-41D3-B4F0-BE4873C06AF0][Secure Introduction of a Workload to
the Vault]]: the platform that launches the unit delivers its key pair, the
vault holds the public half, and a challenge the vault seals to that key proves
which consumer is calling before any token exists. It is the
platform-integration family of the secret-zero problem rather than a new
mechanism: systemd is the platform, the key pair is the material it injects, and
the exchange is good once.

The pieces then are:

1. =vault.v1.ops.challenge= and =vault.v1.ops.credential=, with cases that a
   consumer cannot read another's entry even with a valid key, and that a replay
   of a recorded request does not work. *Landed in PR #5203*: the consumer row
   gained the account it runs as, so one ownership rule serves both paths, and
   the vault registers the two subjects beside the custody five.
2. Provisioning writes each service password into the vault, as
   =db.<service>.password= owned by that service's actor, in the *system*
   tenant: the password protects a database role the deployment owns, so a copy
   per tenant would be the wrong shape. The vault writes them itself, with
   =--provision=, because the writer cannot hold a token. *The vault's half is
   landed*: one document registers the consumers and stores the values, each
   consumer before the secret that names it, and a value written twice becomes a
   new version rather than a second secret. What remains is =compass v* working
   out which values to generate and handing them over. The value is generated
   once and never written to the environment file.
3. The environment file's =secret= rows become names (a new format version), and
   =ores.service='s runner resolves the entry before it builds its database
   context, handing the value to the option mapper.
4. IAM's signing key follows the same route, with the public half still
   published as it is now.

The design of (1) is written, before its code, as
[[id:5FADF948-4520-41D3-B4F0-BE4873C06AF0][Secure Introduction of a Workload to
the Vault]], because it adds a second authentication path to the vault and the
next caller will want to know why. That page also records the alternatives it
rejects: a bootstrap token path in IAM, which moves the problem rather than
solving it; the NATS leaf as the identity, which the broker does not forward to
a subscriber; and a shared bootstrap secret, which is strictly weaker than a
key pair.

Writing these values needs an authenticated writer, and the first value is the
password of the service that issues tokens, so the provisioner's own secret zero
is the circle one step earlier in the boot. The design page now settles it: the
provisioning step runs the vault's binary with a write verb and hands it the
values on standard input, so the writer is the store that already holds the
keys and no new identity has to be bootstrapped. The alternative — provisioning
signs in with the shell account through the gateway — was rejected because it
would make IAM's own password a permanent credential file beside the vault's and
put a person's login in an unattended boot.

* Notes

2026-11-27 — PR #5203 lands the exchange itself: =challenge= answers a nonce
sealed to the consumer's key, =credential= redeems it and answers the consumer's
own secret, and a challenge is good once. The three cases run against the real
tables. What remains of phase 2 is provisioning, the environment format version
and the start-up step in =ores.service=.

2026-11-28 — Phase 2's format lands. Environment format version 39 removes
=ORES_{service.env_key}_DB_PASSWORD=: the file names each service's vault entry
and carries no value for it, and the fleet starts with every service resolving
its own password. =compass vault provision= is now the rotation as well as the
write: it invents each password, sets it on the role, sets the hash IAM signs the
service in with through a new function,
=ores_iam_service_account_credential_set_fn=, reads back the verifier the pooler
needs, and stores the value in the vault. One act, because a value that reaches
three of its four homes is a service nobody can sign in.

The IAM function is the piece the first attempt lacked: the seed that writes a
service credential returns early when one exists, by design, so nothing could
change it. It carries an =entity_writes= exception with its reason, and the
reason is that rotation is a deployment act with no session to carry it.

The pooler is the piece that still does not pass. Moving it to
=scram-sha-256= with the server's verifiers, and a lookup function so no
plaintext is kept beside it, is written and installed; the live pooler refuses
the clients' SCRAM with =SASL authentication failed= even though the verifier it
holds matches the server's to the byte. The environment therefore runs with
=ORES_DB_POOLER_ENABLED=0= for now, which is a stated cost — the connection cap
the pooler exists to give — rather than a silent one. It is captured.

What the fleet showed, cold: 26 units running, none failed, sixteen services
resolving from the vault with no token, IAM and the vault reading the credentials
the deployment placed for them, and the environment file carrying no service
password at all.

2026-11-27 — The start-up resolve lands, and with it the first service that
takes its password from the vault. =ores.service='s runner asks for the password
before the application builds its context: the unit states its consumer and the
secret's name, the platform placed its key pair, and the runner exchanges a
challenge for the value. A bounded retry covers the wave a fleet start is; a
refusal after it leaves the configured password standing and logs why, until the
format stops carrying one.

Two findings changed the design, both from running it rather than reading it.
The start order matters and cannot be left to chance: the vault fetches the keys
that verify tokens from IAM before it subscribes, so IAM precedes the vault, and
every unit that resolves is ordered after the vault — ordering only, no
=Requires=, because the fallback exists. And IAM is the second process that
cannot resolve: it has to exist before the vault does. Its password stays a
credential file beside the vault's, which the register now states.

Proved live: after the unit gained its two credentials, =ores.dq.service=
restarted, resolved =db.dq_service.password= over the bus at version 1 with no
token, and opened its pool on it.

2026-11-27 — =compass vault provision= lands. It reads the service registry,
generates one key pair per database service under =build/keys= (or reuses the
pair it finds), and hands the vault one consumer and one =db.<psql_var>.password=
per service, owned by the service account the registry states. The passwords are
the ones the environment file already holds, so no role changes and nothing
breaks while the start-up step is still missing; the file stops carrying them in
the next piece. It skips the vault, which cannot ask itself.

Run against this environment: 17 consumers and 17 secrets in the system tenant,
version 1, and the key pairs written 0600. =--dry-run= prints the document with
each value replaced by its length, so an operator can look before it writes.

2026-11-27 — The vault's provisioning write lands: =ores.vault.service
--provision= reads one JSON document, registers the consumers it names and
stores the values it names for them, then exits without opening a subscription.
Consumers go first, so a value's owner is a consumer the vault already knows. A
value sealed to the vault's own transport key and then opened by the ordinary
write, so provisioning runs the path the bus runs rather than a parallel one. It
is the one act on the vault that no caller authenticates, and the design page
says why that is the only arrangement that closes the boot.

Two runs proved it rather than the tests alone: the verb wrote a throwaway
consumer and value against this environment's database, the rows came back in
the system tenant with the vault's own account as performer and the document
untouched, and the five document cases and one integration case hold the shape.
Two things the live run taught. The store closes a deleted version rather than
removing it, so a smoke row stays as history and the count an operator reads
must filter on =valid_to=; and the rotation test counts the *names* a tenant
holds, so a new case that invents a name per run grows that count — the new case
writes the name the file already writes.

2026-11-27 — The consumer's half of the exchange lands in =ores.vault.client=:
=read_credentials= takes the two files the deployment places for a unit, and
=resolve_credential= runs the four steps against a vended request function, so
the exchange is proved by a test that answers the protocol instead of by a mock
that agrees with whatever is sent. Six cases, no database. Two facts came out of
writing it. The vault's transport *public* key cannot be read from
=vault.v1.ops.public_key= at this point, because that read requires the session
the exchange exists to make possible, so the deployment places it as a second
credential beside the unit's own key; the design page now says so and says why
answering in clear is worse. And the worry that the client could not declare its
dependencies was wrong: =extra_dependencies= on the component's own model page is
the slot for exactly that, which =ores.vault.core= already uses. The build
dependencies are declared there, the recipe says where, and the capture that
claimed otherwise is deleted.

2026-11-27 — PR #5182 delivers phase 0 and the two register corrections, and the
task stays STARTED: the acceptance's remaining two bullets are phase 2, which
changes how every service boots, and phase 1, which waits on the token exchange.
The gates the merge checks for a closed task are met by this change's own
evidence (compass suite 602 passing, the gate 8 of 8, the environment regenerated
at version 38).
