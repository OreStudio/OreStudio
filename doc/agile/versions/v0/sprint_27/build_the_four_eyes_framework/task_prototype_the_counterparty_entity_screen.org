* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

- Draw the counterparty as the product draws the party: a list, a record on tabs, a dialog for each card. The tabs are the kinds of row a counterparty holds: details, identifiers, contacts, business centres, the parties that may trade with it, and history.
- Reuse the shared four-eyes controls of the sibling prototypes for the waiting, decision and declined screens, so the request is drawn as the other prototypes draw it.
- Mark each change with the function that decides it from the approval policy, and let the review's button save a change nobody gates and raise one request for the rest.
- Test every state and the click paths with a small DOM stand-in run under node, because the prototype is plain files with no build.

* Notes

- The product owner said the screen is not the onboarding journey. Onboarding is a workflow. The screen to build is an entity screen like the parties screen, with the links a counterparty adds, so this prototype is of the record.
- The earlier onboarding prototype stays as the record of the workflow. This one sits beside it.
- The policy rows give the gating: the counterparty, its identifiers and its party links need Operations, and the contact information and the business centre links need nobody.
- The prototype shows no delete. The policy has no delete row for a counterparty, so a counterparty is closed through its status.
- Open question for the product owner: should a contact change stay ungated? The policy says so today.
- The product screen cannot raise a request yet. Only the book is gated on the server. The counterparty needs the same chain the book had: its model marked gated, a pending change, a preview and raise, and an apply.

* Result

The counterparty is drawn as a record screen that saves a change nobody gates and raises a request for the rest.

- =doc/prototypes/parties/keep-a-counterpartys-details-current/= holds the page, with a design note beside it. The group page and the top page list it.
- The list searches and opens a record. The record has six tabs and a dialog for each card, and a new counterparty is the same dialog as an edit.
- The review shows each change with its decider. A request that is raised is drawn as waiting, as the checker's decision with its checks, and as declined, and an approved one writes a new version.

Evidence: every state loads and each click path runs under a DOM stand-in in node: edit then raise then approve, a direct contact save, a gated party link, a new counterparty, the maker refused as decider, and a failed version check. The prototype inventory check reports a problem about the site build that is on main and not in this change.

Not done here: a review of the prototype by the product owner, and the product screen.
