#+title: Story: Gather a run's inputs by declared dependency
#+description: ores.trading has no way to group trades, so a report's gathering hands one opaque blob to one export and nothing downstream can address a part of the population. Give trading a batcher with a pluggable strategy that partitions a report's trade population into trade sets, each named by a batch key and carrying an as-of; the simplest strategy batches by book. Then declare the inputs a run needs, hold them as a graph, read each trade set to produce its data, and assemble the package only when every declared input is present.

* Goal

A step declares the artifacts it consumes and produces, and a run's chain is held as a persisted dependency graph that the engine dispatches from.

* Acceptance

- A step definition names the steps whose results it reads, and the declaration travels with the run.
- The engine refuses a chain that names a step no earlier step produces, and fails a run naming the inputs it is waiting on.
- The run's chain is two relations, a step per position and an edge per dependency, and materialised_steps_json is gone.
- The engine dispatches every step the graph says may run, completes a run when every step has answered, and reconstructs the graph from the database after a restart.

* Dependencies between the tasks

Two things gate everything: the *artifact declaration* and the *dependency
graph*, because the first says what to wait for and the second says whether it
has arrived. The batcher is the third, because the batch keys it produces are
what the producers are named by.

#+begin_example
trade sets in ores.trading (Merry Newton)          [outside this tree]
  └─ partition a run's trade population into trade sets

declare what a step consumes and produces
  └─ hold a workflow as a dependency graph
       ├─ partition a run's trade population into trade sets
       └─ assemble the package once every input is present

batch keys
  ├─ export a trade set as an archive
  │    └─ map a trade set's archive into the ORE portfolio
  ├─ resolve a trade set's market data requirements
  │    └─ export the market data a trade set requires

hand each configuration to its owner by id at an as-of   [per run, not per set]
#+end_example

The producers are independent of each other, so they can be built in any
order once the batch keys exist. What they cannot do is *wait* for each other:
only the graph can say whether a run is still gathering.

Configurations are the exception to the fan-out: a configuration belongs to the
definition, not to a trade set, so that task is independent of the batcher.

* Decisions

The remainder is carried in [[id:AC05783F-3917-4401-902B-40C5277300A7][Gather each trade set and its market data]].

- *A run's chain is a relation, not a document.* The chain a run was started
  with was a JSON snapshot on the instance, because =build_steps= is a function
  of the start request and the engine must not rebuild it after a restart. The
  other =*_json= columns in this schema are payloads — opaque wire messages a
  service must not interpret — and storing those verbatim is right. A chain is
  not a payload: the engine parses it, orders it and asks it which step reads
  which, which is a relation stored as a document and the reason the schema
  could not answer the graph's questions in SQL. The chain is settled as two
  relations instead — a step per position and an edge per dependency — and the
  document, the step count and the dispatch cursor go with it. Owned by
  [[id:E3988B3F-BB78-4E9C-850A-78CA4CEAF72D][Hold a workflow as a dependency graph]].

*Open, to settle inside the tasks.* Each is recorded with the task that owns
it, and none is closed:

- *The batching strategy boundary.* The first strategy batches by book, and
  the batcher is in ores.trading. What a later strategy may see — the grid's
  state, the population's shape — is not settled, and the interface is the
  place that decides it. Owned by
  [[id:D054BDD3-351F-42D3-9638-7D3BAEEAD332][Partition a run's trade population into trade sets]].
- *The archive's shape.* One archive per trade set, with a member per instrument
  type plus a manifest; not one archive per set per type. Owned by
  [[id:8BC0E84C-9B4B-4A12-8E3F-E86EF2A8A807][Export a trade set as an archive]].
- *Where the oresmd requirement grammar lives.* It is C++ codecs today, so
  "resolve it in the database" means moving the grammar or splitting the
  resolution. Owned by [[id:7D9C535D-ED63-43A6-AD1D-54E6E73CF2CF][Resolve a trade set's market data requirements]].
- *How the graph's edges are persisted.* An edge table keeps a step's
  producers open-ended; a depends-on column keeps the read simple. Owned by
  [[id:E3988B3F-BB78-4E9C-850A-78CA4CEAF72D][Hold a workflow as a dependency graph]].
- *What carries a configuration document to storage.* One transport shape for
  every kind, or a message type per kind. Owned by
  [[id:75159083-58A4-4266-A64B-4FDC94EF0426][Hand each configuration to its owner by id at an as-of]].

*Blocked outside this story.* Trade sets do not exist yet: they are being built
in =ores.trading= by Merry Newton. The batcher task is blocked on that landing,
and the rest of the story is blocked on the batcher, so the critical path starts
outside this tree. What the batcher needs from a trade set is small and stated
on the task so the two efforts agree early: a name, an as-of, and the trades in
it.

*The as-of is cross-cutting.* Every market and trade table is bitemporal, so an
as-of read is a =valid_at= read and needs no new machinery — but the run
document's =asofDate= is currently passed to nothing, and every producer has to
be handed it for the same run to be reproducible. The story's acceptance says
every gathered artifact is reproducible for a stated as-of; that is the test.

*What this story does not do.* It does not change the compute side. The package
the run assembles, the assignment that carries it and the node that runs it
keep the shape the storage-capability work gave them.
