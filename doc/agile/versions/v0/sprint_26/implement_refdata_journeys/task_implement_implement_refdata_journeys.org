* Plan

1. Wire: register the 28 lists' list, put, put_many and delete operations, and
   the generic history request, in the wire package's operations.

   name, plus a generic history route; reuse =/api/change-reasons=.

   with the change reason, and the shared history panel.
4. Menu: add *Classifications* to the tenant administration menu.

* Result

Maintain a classification list runs in ores.web against the real server, built
from the accepted [[id:CB72DF9A-ED51-4E92-8A1E-FA03230FC077][reference data prototype]]:

- Reference data is an area of the application and tenant menus and a live tile
  on Home. Classifications is an index of the 28 lists by topic with row counts;
  a list has Add row and Reorder on it, a filter and a Label column; a row opens
  on its own page with Details and History tabs and is edited, removed and
  reverted in dialogs.
- Rows are painted from the shared label catalogue (badge definitions and
  mappings), with a new shared =ui/Label.tsx= the tenant screens now use too; a
  label is chosen from the list's own labels first and written as a badge
  mapping.
- History shows a timeline with each version's provenance, compares any two
  versions, and draws each changed field as an old and a new line with the
  changed characters marked.
- Edit actions follow the person's permissions; the ORE vocabularies are
  read-only.

Found and fixed on the real server: lists refuse ordering by display order;
two lists require =as_of= in their list request; conflicts arrive with no
words; the calendar name and day counter handlers were never wired into the
refdata service. Found and captured: the broker client is slow under
concurrent calls, and tenant sessions never reach tenant administration, with
sixteen more captures from the journeys.
