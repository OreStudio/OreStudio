* Goal

Every scripted trade's configuration states what its engine reads: the parameters the engine treats as mandatory are stated on the pair the scripted products name, with the values ORE's own example configuration states, so no scripted trade stops for want of one. Whether the trade then prices is the market data's question, which this task does not own.

* Acceptance

- the pair states every parameter the scripted builder reads mandatorily

- a report over the provisioned book records no missing parameter for a scripted product

* Plan

A scripted trade is priced by a script, and the builder that runs it reads its
parameters from the pricing engine configuration before anything else, throwing
on any mandatory one the configuration does not state. The ORE code reads ten of
them with no default: the model, its base currency, whether base currency
enforcement and dynamic FX apply, the grid coarsening rule, and the engine,
samples, regression order, time steps per year and interactivity. The report
recorded "parameter BaseCcy not found" for 48 scripted trades.

The parameters are the pair's, not a product type's, and the curation already
has a place for them: =curation/pair-settings.json= states a setting once per
(model, engine) pair and the merge puts it on every product that names the pair.
Two of the ten were already there, because a product that delegates to a script
cannot price without knowing its model and engine. The other eight join them,
with the values the ORE example configuration states for every scripted product.

That leaves the vocabulary: a setting is only carried into a seeded
configuration when the curation marks it required, and the mark is the word at
the end of its description, so each setting the pair now states also gets a
description from the code that reads it. The base currency's own description
said "Required" in the middle of a sentence and so was not marked.

The base currency is a default and not a claim about a trade: with
=EnforceBaseCcy= false the engine infers the trade's own currency when the trade
has exactly one, which is every scripted trade the generator books.

* Notes

- The setting's required flag is the word at the end of its description, which is
  a fragile contract. The base currency carried "Required" mid-sentence and was
  read as optional, which is how a mandatory parameter stayed unstated while the
  curation looked right.
- The scripted trades now get past their configuration and stop on market data:
  the equity and commodity curves and spot objects their underlyings name, and
  the fx volatility objects their indices need. Those are the market data tasks'
  work, not this one's.
- Nine rows still ask for the =AsianBasketOption= script, which the run does not
  publish, and eleven still ask for basket data. Both belong to other tasks.

* Result

The two pairs the scripted products name state every parameter the engine reads
with no default, and the seeded configurations carry them: the run's
pricingengine.xml block holds Model, BaseCcy, EnforceBaseCcy, FullDynamicFx,
GridCoarsening, Engine, Samples, RegressionOrder, TimeStepsPerYear and
Interactive.

The report records no missing parameter for a scripted trade, down from 48 rows.
It still records 538 error rows, as many as before: the 48 rows this task closed
gave way to 48 rows of market data the scripted trades now reach, which are
curves, indices and fx volatility objects the trades name. Of the rest, 11 rows
ask for basket data and 9 for the script library the run does not publish.
