This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A trader who owns a curve puts the day's candidate set in front of a second pair of eyes, so that only an approved curve can become the one the system uses.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I built today's curve from the market, and I want it to be the curve the desk
prices from. Somebody else has to say yes first." The journey is done when the
system holds a raised approval request that names the candidate set, and the
trader can read it back as waiting.

* Actor and trigger

The actor is the trader who owns the curve: the maker. This is the person who
holds the market-data management role, updated the series from the feed or by
hand, and holds the raise permission. The trigger is a candidate curve that has
been built or refreshed and reviewed, and is now ready to leave the trader's
hands. The journey starts at the curve's candidates for a value date and ends
when the request is raised and visible under *My requests*. It does not end
with a published curve: a second person decides that in
[[id:A85B6C4E-0F93-4410-BF2E-7167722849ED][Decide a publish]], and the approved
set becomes usable in
[[id:53F31919-86FA-4E35-8594-9E72197C4A3B][Publish the approved set]].

A request waits on a person, so the ask is written down rather than kept in the
browser. The trader leaves the screen after raising it; the request carries the
state. The trader must not decide their own request. That rule is a rule of the
approval record, not of this screen; see /What is missing/.

* Steps

1. *Open the curve.* The trader opens the curve by its =oresmd_uri=. The system
   reads the series and shows its identity, how it was derived, and the recipe
   that produced it.
2. *Read the candidates for a date.* The system lists the observation rows the
   derivation wrote for the value date: each point named by its =oresmd_uri=,
   with its value, its =observation_datetime= and its =source= tag. The trader
   reads the day's points as one set, keyed by the identity the points carry.
3. *See what changed against the last published.* The trader asks for the
   difference between these candidates and the curve the system last published.
   The system has no published version to compare against; see /What is
   missing/. Until then the panel shows each point beside a note that no
   published marker exists, and the trader compares by eye against the previous
   snapshot they choose.
4. *Read the provenance.* For each derived point the system shows the
   =observation_lineage= row: the derivation config, its version and the source
   as-of the point was built from. Beside it the trader reads the recipe's
   config and pillars, so the set can be named point by point.
5. *Write the reason.* The trader writes why the set should be published, in
   their own words. The system keeps the reason on the request; there is no
   candidate-set entity to hang it on yet.
6. *Raise the request.* The trader chooses *Raise publish request*. The system
   raises an approval request for the signed-in trader, waiting, with the kind
   the request names. No market-data kind is seeded today; see /What is
   missing/.
7. *Confirm the separation of duties.* The system does not offer decision
   controls to the person who raised the request, and refuses a decision by the
   asker. The trader reads the request back as waiting, under *My requests*.
8. *Leave.* The trader goes back to the curve. The request stays waiting until
   somebody decides it, or until its kind's expiry closes it.

Step 6 is the step that leaves somebody waiting, so the journey carries state
from that step on: the request is a record, and both this screen and the
approver's screen read the same one.

* Screens and wireframes

One screen. The curve and its recipe sit at the top, the candidate points sit
in the middle — with the change against the last published beside them — and the
ask and the trader's requests sit at the bottom, so the trader reads what they
are asking about above the act of asking.

A market observation is evidence: nobody signs it off. What this journey asks
for is a decision about a set of those observations, and the decision is the
=approval_request=, which is why the ask is an =ores.inbox= record and not a
column on =market_series=.

=inbox.v1.ops.raise_approval= is generic: it is defined in
[[id:353B9AFD-C3B5-46BF-8D1B-E0362AE3CD23][ores.inbox.approval_operations]] and
takes a =kind_code= and a =reason=. It will raise a market-data ask the day a
market-data kind exists. The kind's owning operation, which applies an approval,
does not exist; that is the publish operation the third journey needs.

* What is missing

1. *There is no market-data approval kind.* One kind is seeded today,
   =iam.role_grant=, and nothing registers a kind for a curve publish. The
   candidate is a kind, =marketdata.curve_publish=, with its own
   =decide_permission_code=, its =comment_on_approve= rule and its
   =approvals_required= count, seeded beside the IAM kind. Until then the raise
   cannot be given a kind, so *Raise publish request* is disabled and the panel
   says a market-data approval kind is missing.
2. *There is no candidate set.* A point of the curve is held by
   =market_observation=, whose identity is the =oresmd_uri= and which has no
   =point_id= and no tenor column; nothing groups the day's points into the one
   thing a publish is about. The candidate is a set marker, or a detail table
   keyed by the request's id that names the series and the as-of the set was
   built at. Until then the screen lists the points for one as-of and the
   trader names the set in the reason.
3. *There is no change against the last published.* Nothing marks a series or a
   build as published, so there is no version to diff against, and no subject
   returns a delta. The candidate is a published marker on the series or the
   build, plus a read such as =marketdata.v1.curve_candidates.diff=. Until then
   the delta column is shown empty, with the reason stated, and the trader
   compares against a snapshot they choose.
4. *The approval has nothing to apply it.* The decision is generic, but the
   component that owns the kind applies it through an operation of its own, and
   no publish operation exists. The candidate is
   =marketdata.v1.curve_bootstrap.publish=. Until then a market-data request
   could be decided and still nothing would change, which is why the kind
   cannot be seeded before the operation is.
5. *No permission pair separates maker from checker.* The approval record
   refuses a decision by the person who asked, so four-eyes holds at the
   record. Nothing in market data yet splits the raise permission from the
   decide permission, so one account can hold both. The candidate is a pair of
   permission codes on the kind, one to raise and one to decide. Until then the
   screen shows the decide permission as read-only text and cannot warn the
   trader that they hold it.
6. *Nothing tells the approver that a request waits.* No notification kind
   exists for a market-data request, so the queue is the only signal. The
   candidate is an =ores.inbox.notification_kind= such as
   =marketdata.curve_publish_requested=. Until then the screen says the request
   was raised and does not promise anybody is told.
