* Goal

One provision request replaces iam.v1.bootstrap.provision-tenant and iam.v1.tenants.provision-acme. It takes a profile code and the parameter values the profile's declared schema accepts, refuses values the schema does not declare or does not accept, and answers with the instance id the run follows.

* Plan

Step 6 adds the one verb the two clients will share.
=iam.v1.tenants.provision= takes the profile code, the tenant's own
name, code, hostname and description, its administrator's username,
email and password, and the profile's parameter values. It answers at
once with the id of the run it started, the tenant it created and that
tenant's administrator account.

The decisions taken here:

- *The tenant type is the profile's, not the request's.* A tenant row
  carries a type validated against =ores_iam_tenant_types_tbl=
  (=production=, =evaluation=, =automation=), and the two cards differ
  exactly there: Operational is for real use, ACME demo is for demos and
  testing. So =seed_profile= gains a =tenant_type= column, seeded
  =production= and =evaluation=. Neither the screen nor the request
  carries the field. Had the request carried it, the BFF would have had
  to invent a value, and the profile would have stopped being the whole
  starting point.
- *The request carries no "inherit the administrator's password" flag.*
  A server cannot read the caller's password. "Use my password" is the
  client sending the password it already holds as =admin_password=; the
  profile's =inherits_admin_password= stays screen guidance, which is
  the only thing it can be.
- *Validation is a pure function over the declared schema.* The refusal
  names the field, and the function is tested without a database. It
  refuses a profile it does not know, a parameter the profile does not
  declare, a required parameter that is missing, a value that is not one
  of a =choice= parameter's choices, and a value that does not read as
  the declared =data_type=.
- *The tenant and its administrator are created synchronously; the run
  carries the provisioning steps.* The tenant has to exist for the first
  tenant to be reachable at all, and creating it is fast. The work the
  profile orders — bundle publishes, an LEI hierarchy, parties, feeds —
  is minutes long, and that is what the instance id answers for.
- *The tenant creation moves into a service both verbs call.* The
  bootstrap verb does the same four things today: call the SQL
  provisioner, create the administrator, associate it with the system
  party, assign =TenantAdmin=. The successor and the verb it retires
  must not drift apart while both are reachable, so the sequence moves
  to =service/tenant_provisioning_service.hpp= and both handlers call
  it.
- *The two retired subjects stay until their last caller moves.* The
  story's plan puts the shell's alignment in step 12, and the shell is
  the last caller of both =iam.v1.bootstrap.provision-tenant= and
  =iam.v1.tenants.provision-acme=. Their own orchestration covers work
  the run cannot do until step 7 orders it, so retiring them here would
  leave the =--source acme= path producing a tenant with none of its
  data. The retirement is step 12's, with the shell, and this task
  records it rather than claiming it.
- *The run itself is step 7's.* =provision_tenant_workflow= is the next
  task. Until it is registered the engine records that it has no
  definition for the type and creates no instance, so this task proves
  the request, its refusals, the tenant and its administrator on the
  live deployment. It does not yet prove the run, and the last
  acceptance line is met in step 7.

* Result

=iam.v1.tenants.provision= is in. It takes the seed profile's code, the
tenant's own name, code, hostname and description, its administrator's
username, email and password, and the profile's parameter values, and it
answers with the id of the run it started, the tenant it created and
that tenant's administrator account.

What it does, in the order it does it:

- *It refuses before it creates anything.* An unknown profile code, a
  tenant or administrator field with no value, a parameter the profile
  does not declare, a required parameter with no value, a value that is
  not one of a choice parameter's choices, and a value that does not read
  as the declared data type are each refused with the field named. The
  check is a pure function over the profile's declared schema
  (=service/seed_profile_parameter_check.hpp=), so it is tested without a
  database, in 12 cases. A parameter the request omits takes the
  profile's default; a required one with no default to take is refused.
- *It creates the tenant and its administrator.* That sequence moved to
  =service/tenant_provisioning_service.hpp=, and the bootstrap verb this
  one replaces calls it too, so the two cannot drift apart while both are
  reachable. The tenant's type comes from the profile: =seed_profile=
  gained a =tenant_type= column, seeded =production= for Operational and
  =evaluation= for ACME demo.
- *It starts the run.* The handler reads the profile's ordered steps,
  puts them and the accepted parameter values into
  =provision_tenant_workflow_request=, mints the instance id, and
  publishes a =start_workflow_message= carrying it, so the answer names
  the run without waiting for the engine to create it. The engine treats
  a repeated id as the same run.

The browser reaches the verb through =POST /api/provision-tenant= and
the client's =provisionTenant= method, each with tests that call it the
way a caller does.

Two things are recorded rather than claimed:

- *The run's steps are step 7's.* No definition registers
  =provision_tenant_workflow= yet, so the engine receives the start and
  records that it has no definition for the type, and no instance row
  exists. That is why the last acceptance line is met in step 7. The
  tenant stays in the =bootstrapping= status the SQL provisioner gives it
  until the run completes.
- *The two verbs this one replaces stay reachable.* The shell is the last
  caller of both =iam.v1.bootstrap.provision-tenant= and
  =iam.v1.tenants.provision-acme=, and the story's plan moves the shell
  in step 12. Retiring them here would leave =--source acme= creating a
  tenant with none of its data, because the work those verbs orchestrate
  is the work step 7 orders.

The generated shell library scripts the seed profile models produce had
never been committed by this story's earlier tasks; they are committed
here beside the new =tenant_provisioning-provision-tenant.ores=.
