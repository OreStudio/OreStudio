* Acceptance

- Each market-state family has a table or a stored payload in ores.marketdata/modeling, with its generated layers committed.
- marketdata's ingest calls the ores.ore readers and writes the families it reads.
- A scenario cube is stored as a compressed payload whose index names the dates, scenarios and factors it holds, not as one row per value.

* Plan

The cube is stored as the file the engine wrote, not as rows. A row for each
value would be millions per run and a read that wants one factor would unpack
all of them, so the payload is one compressed blob and the index beside it is
what a reader asks first.

The index is the distinct values of the family's *key* columns, which the
catalogue already states, so the dates, scenarios, factors and market objects an
index names need no list of their own.

The file cannot travel in a message: NATS carries a megabyte and a production
cube is tens of megabytes. The reporting service therefore names the run's output
archives and lends the run's own token, and this component downloads, unpacks and
stores what it finds. Both components read the same archive and each keeps what
it owns: reporting the results, marketdata the state.

* Result

The market state a run priced against is read, indexed and stored, and the run's
own post-processor hands it over.

- =ores_marketdata_market_state_payloads_tbl= takes the file as the engine wrote
  it, gzipped and held as base64 text, with the headings, the row count, the
  distinct values of each key, the compressed size and the digest beside it. It is
  a hypertable on the observation date and RLS-scoped like the tables it sits by.
- =read_market_state= reads every market-state file of a run out of its archive
  and leaves the results alone, naming them back to the caller.
- =marketdata.v1.ops.store_market_state= takes the run's ids, the date it priced
  at, the storage token and the archive locations, and answers what it stored and
  what it left alone. It reads the archives rather than receiving them, because a
  cube does not fit in a message.
- The post-processor calls it once per run, after its figures are loaded. A state
  that is not stored is logged and stated in the step's message rather than
  failing the run.
- The families that are market state are stated once, in the catalogue, so the
  store and the corpus gate cannot disagree.
- The run's market inputs (=marketdata=, =fixings=, =dividends=) are not
  covered here. The catalogue does not name them, and they move to
  [[id:9CC7AFA7-3755-40D1-AC2C-A2F2E9D3ED5B][Land the market inputs in the market data store]].
