* Goal

A person browses identity shapes the way they browse any other record: a paged list, and a detail page per shape that states what the shape is for and lists its entries.

* Acceptance

- The shapes screen is a paged record list of shapes, with code, family parts and description.
- Opening a shape shows its details, its entries and its history.
- Every seeded shape has a description that says what it is for.
- The identity writer enforces the shape entries as before, and the shape suite still names every family in use that no shape states.

* Plan

The shapes screen read every field row of every family into one page. A family
had no row of its own, so it had no place for a description and no single key
a record page could open it by. The record framework opens a page by one key
and lists a page's parts by one parent field.

1. Split the entity in two. =series_identity_shape= becomes the header: a code
   such as =ir.index_fixing.ibor=, the asset class, the series subclass, the
   index family and a description. A check holds the code to the family's parts,
   and a unique index keeps one shape per family. The field rows become
   =series_identity_shape_entry=, named by a uuid like a calendar rule, with the
   shape code as a foreign key and listed by it, and a unique index on
   (shape code, field). A two-part key would leave the entries with no history
   provider, which the generated registrar says outright.
2. Regenerate the whole stack from the two models, and wire the new handlers,
   history provider, events and shell commands.
3. Move the hand-written readers: the shape guard joins shapes and entries by
   code into the same family map it held before; the pgTAP suite reads them
   joined through a view; the build check reads the entry seed.
4. Split the seed into seven shapes, each with a description, and their 29
   entries.
5. Serve both as record resources. The registry took only refdata, so the
   permission prefix now comes from the resource's subject. The BFF's own shape
   routes shrink to one joined read for the oresmd editor.
6. Rebuild the screen as a record list and a record page with details, entries
   and history tabs, as the calendars are.
