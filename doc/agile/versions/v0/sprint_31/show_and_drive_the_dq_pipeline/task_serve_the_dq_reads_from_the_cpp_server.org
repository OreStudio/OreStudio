* Result

Done. ores.http answers the four DQ collections and ores.web reads them from it.
The BFF is not served and no route was added to it.

- =projects/ores.http/dq= is a part with a hand-written aggregate over four
  generated route units: datasets, dataset bundles, bundle members and artefact
  types, 39 routes in all, registered by the server's application.
- The http-route facet is on =ores.dq.dataset=, =ores.dq.dataset_bundle=,
  =ores.dq.dataset_bundle_member_junction= and =ores.dq.artefact_type=, so the
  units and their tests are generated and the route-area rules cover them.
- =api/dq.ts= is one module for every DQ call: the four reads, =readCoverage= to
  fetch them together, and =readinessOf= to decide which of four reasons keeps a
  member from publishing. Its test asserts the envelopes, so a read of the wrong
  key fails instead of drawing an empty table.
- The gate builds the tree, rebuilds the database from the schema and runs every
  suite: 109 of 109, including =ores.http.dq.tests=.

* Notes

The C++ server has HTTP parts for analytics, assets, compute, core, iam,
marketdata, refdata, reporting, synthetic, trading and workflow, and none for
dq: the reads the screens need are served by nobody.

The BFF is deliberately not served, because it is being decommissioned. Writing
a route there would be work for a component on its way out; the screens are
built against =ores.http=.

Most of the route code is generated: a DQ entity model that opts into
=:ores.cpp.http-route.enabled: true= renders its route header, implementation and
tests into =projects/ores.http/dq/=, so this task is the part's scaffold, the
facet on the right models, the aggregate registration and the build.
