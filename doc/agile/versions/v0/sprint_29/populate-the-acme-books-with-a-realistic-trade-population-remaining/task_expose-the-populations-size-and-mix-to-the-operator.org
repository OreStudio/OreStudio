* Acceptance

- The ACME provisioning surface states the population's total size and a percentage per asset class, with the seeded values as the defaults.
- The percentages are validated: a mix that does not sum to one hundred is refused, and a class whose count falls under its routed-code floor is reported before the run starts rather than after it fails.
- A provisioning run started from the surface writes a population whose measured mix matches the percentages the operator stated, within the tolerance the weights page sets.
- The knobs reach the generation configs the run creates, so the surface states the mix and the generator still draws it.

* Plan

The knob is part of starting a run, so it starts where a run starts.

The web surface already starts a tenant from a seed profile:
=POST /api/provision-tenant= takes a profile code and the tenant and administrator
fields, and the profile's =generate_trades= step carries the populations as
argument rows. So the knob is an optional part of that request — a total and a
percentage per class — that the server turns into the step's arguments, and the
seeded rows stay the default when the request states none.

Three seams, and the arithmetic lives in one of them:

- The request. The provision-tenant body gains the total and the mix, optional,
  with the seeded values as the defaults the screen shows.
- The validation, in the same place: a mix that does not sum to a hundred is
  refused with the sum it came to, and a class whose count falls under its
  routed-code floor is refused with the smallest total that would fit it. Both
  are refusals of the request and not of the run, so an operator learns before a
  tenant is half built.
- The step. The provisioning handler's =generate_trades= step states the configs
  it records, so that is where a computed count per class becomes
  =trades_per_book= per config. The arithmetic must not appear twice: the screen
  shows what the server will do rather than computing its own answer.

What the retune settled and this task inherits: a class cannot state fewer trades
than it routes codes, and its share of the total cannot fall below that floor, so
the total has the smallest value where every class fits. At a thousand every
class is its weight exactly; the surface should say so when the numbers asked for
cannot hold, and name the smallest total that can.

* Result

An operator states the population a run writes: a total and a percentage per
class, and the run books that.

The knobs are profile parameters, which is what makes the screen free. The
provisioning form renders every parameter a profile declares, so the nine rows
this profile gains — a size and eight shares — appear as fields with no screen
code at all, and the server is the only place the arithmetic lives.

What a run does with them: a class's trades are its share of the total, spread
over the configs that class books into, with the remainder going to the first
configs so the class states its share exactly rather than a rounded-down version
of it. Nothing is applied when the run states no size, so the seeded counts stand.

Three refusals, each naming what the operator can do about it:

- A mix that does not sum to a hundred says what it summed to.
- A class the run records no config for is refused by name, because its share
  would be taken and nothing booked against it.
- A class whose share cannot hold its codes is refused with the smallest total
  that would hold them, which is the floor the planner states: the codes it
  cycles, multiplied by the configs it books into.

Measured end to end on a probe tenant with the mix stated as rates 44 and equity
10: a thousand trades, 440 of them rate trades and 100 equity, which is what the
operator asked for and not what the page states. The demonstration tenant is
untouched at the page's mix.

One decision worth keeping: the size is a knob on its own. A run that states a
total and no mix keeps the mix its recipe states, so an operator can make the
book bigger without restating the page.
