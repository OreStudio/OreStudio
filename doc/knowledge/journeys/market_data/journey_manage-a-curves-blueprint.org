This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A trader or quant defines a curve's blueprint for a currency: its identity and family role, its output series, its pillar list and order, and its bootstrap and tenor conventions.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want this curve to be built the way the desk agreed, so every bootstrap of
it reads the same pillars and the same conventions." The journey is done when
the blueprint is saved and reads back with its pillars in order, and with the
discount curve set if the family role is PROJECTION.

* Actor and trigger

The actor is a trader who holds the market-data management role, or a quant
acting for the desk. The trader is the maker: the blueprint is theirs to
author. The trigger is a new currency, a new curve the desk must publish, a
changed pillar list, or a changed convention. The journey starts at the curve
list for a currency and ends when the person leaves the saved blueprint.

A saved blueprint is a candidate. It changes nothing that pricing reads until a
curve is bootstrapped from it and that output curve is published; the blueprint
itself is never published. The model calls this record the IR curve bootstrap
config, and the screen calls it the curve's blueprint.

* Steps

1. *Find the currency's curves.* The person opens *Market data*, then
   *Curves*, and chooses a currency. The system lists that currency's
   blueprints: the output series' oresmd URI, the family role, the discount
   curve, the interpolation method, the day count, the split tenor and the
   version. The person filters by URI or by family role.
2. *Open or start a blueprint.* The person selects a row and the system shows
   the blueprint screen, or the person chooses *New blueprint* and the system
   shows the same screen empty. The currency comes from the list; it is not
   typed again.
3. *Set the identity and the family role.* The person chooses the family role,
   =FUNDING= or =PROJECTION=, and names the output series. The output series is
   a =market_series= row: the person either links an existing one or the system
   mints a new one with the blueprint's oresmd URI. The series reads
   =OBSERVED= until the first bootstrap stamps it =IR_CURVE_BOOTSTRAP= with
   this blueprint's id and version.
4. *Choose the discount curve for a projection.* If the role is =PROJECTION=,
   the person chooses the =FUNDING= blueprint this curve discounts off. The
   system offers only this currency's =FUNDING= blueprints. The server refuses a
   projection that points at another projection, or at itself.
5. *Define the pillars.* The person adds, changes, removes and reorders pillar
   rows. Each row carries a zero-based sequence, a start tenor, an end tenor and
   a curve role (=DEPOSIT=, =FRA= or =SWAP=). The system offers the tenor codes
   from the reference data and the curve roles from their code list, and it
   resolves each tenor label through the tenor machinery.
6. *Set the bootstrap method and the conventions.* The person chooses the
   interpolation method (=LOG_LINEAR_DISCOUNT=, =CUBIC_SPLINE= or
   =FLAT_FORWARD_THEN_LOG_LINEAR=), the day count, the tenor convention
   (=RATES_SPOT_FORWARD= or =RATES_SPOT_FOMC=) and the split tenor. For a
   single-segment method the split tenor is the last pillar's end tenor; the
   system offers it from the same tenor list.
7. *Save the blueprint.* The person chooses *Save blueprint*. The system writes
   the config, then the pillar rows, each as a new bitemporal version, and
   replies with the version it wrote. The screen shows the saved blueprint; a
   candidate that publishes nothing.
8. *Check the history.* The person opens the history of the config or of one
   pillar. The system shows every version with the field-level difference from
   the one before. A revert is a new version, not a deletion.
9. *Leave.* The person goes back to the curve list. Nothing has been published,
   and no curve has been built yet.

Steps 7 is two writes, not one: the config and its pillars are separate
resources, so a failure between them leaves a config whose pillar list is
partly updated; see /What is missing/.

The history request is the generic one, with =entity_type=
=ores.refdata.ir_curve_bootstrap_config= or
=ores.refdata.ir_curve_bootstrap_pillar=; both register a history provider.
Saving the config and the pillars is two calls, not one: the subjects above are
the generated resource verbs, and no operation writes both together.

* What is missing

1. *A blueprint has no name.* The config carries an output series, a currency
   and a role, and no name or description column. The screen titles a blueprint
   by its output series' oresmd URI, which is long and identical for two
   currencies only in their URI text. The candidate is a name or a label
   column. Until then the screen shows the URI and the currency.
2. *A curve has no typed identity at the wire.* The blueprint is keyed by the
   output series UUID, and every curve read is keyed by the oresmd URI. No
   subject names a curve by (currency, family role). The candidate is a typed
   curve identity. Until then the person matches on the URI.
3. *Saving a blueprint is not atomic.* The config and its pillars are separate
   generated resources with separate =put= subjects, and no operation writes
   both. A failure between the two writes leaves a config with a partly updated
   pillar list, and the save is a transaction the caller must compose. The
   candidate is an apply operation that writes the config and its pillars
   together. Until then the screen saves the config first, then the pillars,
   and says what it wrote.
4. *No approval kind covers a blueprint change.* The inbox models a generic
   approval kind, but only =iam.role_grant= is seeded. A blueprint change is
   written with no second pair of eyes, and no comment. The candidate is an
   approval kind for the blueprint, with its decide permission and its required
   approvals. Until then a save takes effect at once and the history names the
   writer alone.
5. *The tenor references are undeclared.* The pillar's start and end tenors,
   the split tenor and the tenor convention are soft references: the screen
   offers the reference-data list, but the database holds only text, and the
   application layer validates it. The screen cannot tell a stored code the list
   does not hold. The candidate is a declared reference. Until then the screen
   marks a value it cannot find in the list.
6. *No screen exists.* No web page, HTTP route or shell verb reaches any curve
   operation. The generated detail dialog and controller for this config are
   disabled, and the hand-written workbench went with the removed desktop
   client. The candidate is a web page and a route. Until then the journey runs
   only from the shell.
7. *A currency's blueprints are not a typed scope.* The list filter is generic;
   nothing names "the curves of this currency" as a scope the server resolves.
   The candidate is a filter on currency and family role, or a scoped read.
   Until then the screen lists all the tenant's blueprints and filters on the
   page.
