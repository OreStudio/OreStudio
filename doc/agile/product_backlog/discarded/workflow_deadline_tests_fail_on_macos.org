#+title: The workflow step-deadline tests fail on macOS
#+description: Two ores.workflow.core.tests cases fail on both macOS CI jobs: the overdue step is marked failed, but its run does not reach the failed state, and a late answer leaves one row where the test expects two.

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Two step-deadline cases in =workflow_engine_tests.cpp= fail on both macOS CI
jobs and pass on Linux. In "workflow_engine stops a run whose step outlives its
deadline", =expire_overdue_steps()= returns 1 and the step row is =failed=, but
the instance stays in its previous state and carries no "did not answer
within" error. In "workflow_engine keeps a failure when the step answers
later", the same instance check fails, =outcome.resumed= is false, and the
history holds one row where the test expects two. Both cases come from the
task that gave a workflow step a deadline.

* Why

The macOS jobs of Continuous MacOS run 36957593572 (commit =7fb78ed6e4=) fail
on these cases alone. The pattern (step updated, instance not) suggests the
instance transition depends on ordering or timing that differs on macOS. Not
yet re-checked on a later commit: run 36987873236 was still running when this
was filed.

* Resolution

Fixed by [[id:CB941293-1DBD-4FC3-B291-78374B10AC4D][Hotfix: the workflow deadline
pass reads an entry it has freed]]. The pass read the run id through a reference
into a map entry it had already erased; libstdc++ left the bytes in place, so
only macOS saw the wrong id. Valgrind proved the invalid read on Linux.
