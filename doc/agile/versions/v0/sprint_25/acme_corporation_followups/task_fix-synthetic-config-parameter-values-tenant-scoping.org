* Goal

Every synthetic theme publish (=synthetic.themes.realistic_2026=) fails on
a fresh database with "Invalid parameter_definition_id: %. No active
yield_curve_process_parameter_definition found with this id." The
values-table insert trigger
(=ores_synthetic_config_process_parameter_values_insert_fn=) validates
the parameter_definition_id soft FK scoped to =NEW.tenant_id=, but the
publish path resolves each definition id from the *system-tenant*
catalogue (=synthetic_publish_from_dq_create.sql:690= joins on
=ores_utility_system_tenant_id_fn()=). The trigger's check must align
with the system-tenant scoping, matching the sibling validate function
=ores_synthetic_validate_yield_curve_process_parameter_definition_fn=
(=synthetic_yield_curve_process_parameter_definitions_create.sql:170=).

The generated file is produced by the
=sql_schema_domain_entity_create.mustache= template, so the fix is made
in the template and the file regenerated, never edited by hand.

Stable identifiers: the fix must keep resolving definition ids by the
enforced composite natural key =(process_type_code, parameter_name)=
from the system tenant -- raw UUIDs are unstable across reprovisionings
and nothing may bake them in.

* Result

The fix was verified end-to-end on a fresh database through the shell
provisioning leg (2026-08-10):

- =synthetic.themes.realistic_2026= and =ore_samples_2016= publish for
  all four Acme parties (holding + UK/US/HK) -- no "Invalid
  parameter_definition_id" anywhere.
- Staff photo attach lands for all four parties: 59 accounts, 58 with
  distinct =image_id=s.
- All three offices' =synthetic_feeds= steps complete; the IR curve
  and FX feeds tick (20 IR curves per office, 7 points per publish;
  13 FX feeds per office, 59 ticks; 3933 market observations
  persisted) with zero feed-related errors in the IAM or synthetic
  service logs.

Two further masked bugs surfaced once the feeds ran for the first
time and were fixed within this cascade (both recorded in the review
task's findings table): F13 -- the values table's RLS party-isolation
policy shadowed =config_id= with the inner IR-config table's own
column (=synthetic_rls_policies_create.sql=, fixed 6ef39a7f2); F14 --
the feed start read the parameter-definitions catalogue with the
caller's tenant instead of the system tenant
(=ir_curve_feed_config_handler.hpp=, fixed 716efb0d0).

Open design question (F15, recorded in the review task): the feed
controller keys feeds by =source_name= service-wide, so only the
first office's feeds actually tick; the US/HK starts report
"already running" and their per-party series receive no observations.
