* Goal

GLEIF counterparty import should have first-class support for
attaching a logo/flag image to a counterparty when one is available,
instead of the demo-only bolt-on this replaces.

The removed code (=tenant_handler.hpp::attach_demo_counterparty_logo=,
called from =provision_acme= after Step 7) polled
=get_counterparties_request= every 2 seconds for up to 8 minutes
waiting for the GLEIF import (Step 2, ~13k rows, by far the largest
and slowest bundle publish in the whole flow) to land BARCLAYS PLC,
then copied a hardcoded =demo_counterparty_logo= template image onto
it. Problems with that approach:

- It's a random, disconnected extra step tacked onto the *end* of
  =provision_acme=, unrelated to the GLEIF import that actually
  produces the counterparty rows it depends on.
- The up-to-8-minute silent poll (only failures log anything) reads
  exactly like a hang from the caller's side — this cost significant
  debugging time working out it wasn't actually stuck, just slow.
- It's hardcoded to one specific counterparty (BARCLAYS PLC) for demo
  purposes, not a general mechanism.

The fix belongs in the GLEIF import/publish pipeline itself: when a
GLEIF counterparty entity has a known logo (LEI-keyed or similar),
attach it as part of that same publish, not as a separate polling
step racing the import's own completion.

* Acceptance

- GLEIF counterparty publish attaches a logo image to a counterparty
  when one is available, as part of that same publish pipeline (no
  separate post-hoc polling step in =provision_acme= or elsewhere).
- BARCLAYS PLC (or whichever counterparty is used to demonstrate this)
  ends up with a rendering logo after a normal =--source acme=
  provisioning run, with no unbounded/silent wait.
- =attach_demo_counterparty_logo= and its call site in
  =tenant_handler.hpp= (already removed as part of this discovery) stay
  removed; the replacement lives in the GLEIF/refdata layer.
