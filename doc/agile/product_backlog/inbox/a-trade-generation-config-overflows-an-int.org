#+title: A trade generation config overflows an int
#+description: Provisioning ACME with the acme_demo profile fails at generate_trades: recording the trade generation config 'ACME ACMCOR bond population' fails with 'value 2167221318 is out of range for type integer'. A 32-bit integer column holds a value that needs bigint. The tenant, party, LEI hierarchy, staff, passwords and market data subscriptions all provision, so only the trade population is blocked. Find the column, decide whether it should be bigint or numeric, and fix the model so the seed can record the config.

* What is already ruled out

Read on 2026-10-25, after the failure while provisioning ACME with the =acme_demo= profile.

- *The profile.* =iam_seed_profiles_populate.sql= states =seed: 42= and =trades_per_book: 8=, with notionals between 100000 and 10000000. Nothing near 2167221318.
- *The parser.* =provision_step_arguments.hpp= reads a trade generation assignment with no =trades_per_book= member at all: the fields end at =seed=, a =std::uint64_t=. So the parser cannot put a value there either.
- *The schema.* =synthetic_trade_generation_configs_create.sql= has =seed bigint=, =trades_per_book integer= and both notionals as =numeric(38, 12)=. The types match the model.

So the value is not in the file being read, and not in a column of the wrong type on the config. It arrives from the code that assembles the row, or from a sibling insert the same step makes — the message names the config while the failing statement may belong to the book or counterparty table, both of which the step writes in the same breath.

* The next diagnostic

The failing statement's column, not the value, is what is missing. Two ways to it: read the synthetic service's debug log for the rejected statement, or record one config directly through the shell's =trade_generation_configs put= with the profile's own numbers — if that succeeds, the config path is innocent and the fault is in a sibling table the step writes.

* Why it matters

Until it is fixed, a provisioned tenant has no trades: the blotter, the reports that read a trade population, and every synthetic test that expects rows are all blocked behind this one overflow.

* The cause, found

The value is uninitialised memory, not a computed number. Parameter =$14= is =trades_per_book=, and =record_trade_generation_config= in =tenant_provisioning_handler.hpp= sets every member of the write record except that one. The generated write struct declares =std::uint32_t trades_per_book;= with no default initialiser, alone among its members, while the domain and the entity both state =8=. So the record carried whatever was on the stack, 2167221318, and the insert refused it.

The profile's own =trades_per_book: 8= never reached the write either: =trade_generation_assignment= had no member for it, so the JSON key was ignored.

* The fix, applied

1. =trade_generation_assignment= gains =std::optional<std::uint32_t> trades_per_book=, and the parse refuses an entry that states none, in the same way it refuses a missing seed.
2. =record_trade_generation_config= sets =request.change.write.trades_per_book= from the entry.

The build is green with both. Not yet done: re-running the step to see the row land, because the ACME tenant is already provisioned and the shell's single-step command has not been found.

* The lesson to encode

A generated write struct whose members lack default initialisers turns an omission into garbage rather than into a compile error or a refusal. The protocol template supports a default per member, so the generator should emit one where the model states it. That is a template change and a regeneration of every protocol, and it wants its own task: it is the difference between this class of bug being possible and being impossible.

* The first attempt to prove the fix

The database was recreated clean and ACME provisioned again on the fixed binaries. The run reached staff loading — 25 accounts exist — and then the *shell's own session expired* while it polled the workflow, so the script aborted after five failed polls. What the run left behind: 25 accounts, no trade generation configs, no trades, and no rows at all in =ores_workflow_workflow_steps_tbl=, so the run's fate cannot be read from the record.

So the fix is compile-verified and not yet runtime-verified. The next attempt should avoid the expiry — run the =generate_trades= step on its own rather than the whole bootstrap, or give the shell a session long enough to outlast the poll.

* The second attempt, and the wall in front of it

From scratch again: database recreated, services started, ACME provisioned. The run now stops almost at once:

  [1/1] system_provision: in_progress
  ⚠ Poll failed (1/5): Session has expired. Please log in again.

The shell's own access token dies within the first minute of the run, five polls fail, and the script aborts. What the database shows afterwards: 25 accounts, no configs, no trades — the workflow does not advance past staff loading once the polling session is gone.

So provisioning is blocked a second time, and by something else: the access lifetime. The IAM default is =access_lifetime_s = 1800= in =token_settings.hpp=, and the token dies far sooner than that, so the value in force is either configured lower or the token is being invalidated — a key rotation when the services restart is the obvious candidate, since the shell logs in before the workflow runs and the token is rejected moments later.

That is the next thing to find, and it is a different bug from the overflow. The overflow fix stands written and compiled; it cannot be proved until a provision completes, and a provision cannot complete until the session outlives the run.

* Proved

The third attempt provisioned from scratch and completed: all 9 steps, =generate_trades: completed=, script exit 0, and the two ORE packages published. The rows are what the profile states:

| name | seed | trades_per_book | min_notional |
|---|---|---|---|
| ACME ACCOHK bond population | 42 | 8 | 100000.000000000000 |
| ACME ACCOUK bond population | 42 | 8 | 100000.000000000000 |
| ACME ACCOUS bond population | 42 | 8 | 100000.000000000000 |
| ACME ACMCOR bond population | 42 | 8 | 100000.000000000000 |

And the population behind them is 160 trades, 8 per book across the four parties' books. The overflow is gone, and the profile's value is what reaches the column.

* The second blocker, which was real

The two failed attempts were not the overflow. The shell's access token expired mid-run, and the IAM default is 1800 seconds: =iam.token.access_lifetime_seconds= in =variability_system_settings_populate.sql=. A provision from scratch takes longer than half an hour here, so the session died while the workflow ran and the script aborted.

Raising that setting to 7200 in the running database before provisioning made the run complete. Whether the seed should ship a longer lifetime for provisioning, or whether the provisioning script should refresh its own token, is an open question for the IAM owner; this capture records the workaround, not a recommendation.
