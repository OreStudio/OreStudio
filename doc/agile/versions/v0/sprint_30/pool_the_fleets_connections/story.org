* Goal

A service gets the connections its work needs, and the database carries only
what it can. The fleet's connection behaviour is one documented approach with two
settings rather than two code paths: a service's pool states the connections it
keeps and the ones a burst may reach, and where several environments share one
PostgreSQL a pooler stands between them and the server. A developer's own
database needs neither, and pauli runs the fleet as containers, the pooler among
them.

* Acceptance

- A service's pool keeps a few connections and may burst to the concurrency its
  work has, closing what it no longer needs, so a burst does not starve a step
  and an idle service holds only its floor.
- Where a pooler stands in front of a shared PostgreSQL, the server sees the
  pooler's cap and not the sum of every service's pool; where none stands, a
  developer's database sees the service's own floor and burst and nothing else.
- The listener and the administrative paths never pass through a pooler.
- The pooler is deployed to pauli as a container beside the fleet, and to a
  shared development host as a unit, from one configuration.
- The pooled path is exercised on every change, so the direct path developers use
  is not a blind spot.
- The knowledge graph states all of the above as the current state, and a reader
  who has never seen this work can say which connections a service holds, why,
  and what to change to hold fewer.

* Decisions

- *A pooler is a deployment option, never a developer requirement, 2026-11-21.*
  The problem is a shared instance carrying many environments and hundreds of
  idle connections; a developer with their own PostgreSQL has none of it. The
  services read =ORES_<APP>_DB_HOST= and =DB_PORT=, so a pooler is a different
  host and port and nothing else, direct and pooled are one switch, and the
  default is direct. The parity risk - a behaviour that only appears through the
  pooler - is paid for by running the suite through one in CI rather than by
  asking every developer to install a daemon for a problem they do not have.
- *The pool asks for a burst, not for a bigger number, 2026-11-21.* The pool
  opens every connection in its constructor and never opens another, so the size
  is a ceiling on concurrency rather than a cushion: two connections against two
  step workers and four lanes met =No connection came free within the acquire
  timeout=, and the answer at the time was a retry. The pool states a floor and a
  burst ceiling instead, and closes what a burst leaves idle. Raising the single
  number for everyone is rejected: it keeps every connection for life and
  multiplies by every service in every environment.
- *The saving is server side only, 2026-11-21.* A service's connections do not
  shrink; they stop terminating at PostgreSQL. Measured on this host, one idle
  environment held 38 server connections, two a service, against
  =max_connections = 1500= shared by six development databases. Behind a
  transaction pooler the same fleet keeps a handful and closes them when idle,
  and the ceiling is stated per environment instead of summed across services
  nobody counts.
- *The two questions separate behind a pooler, 2026-11-21.* While a pooled
  connection is a server connection, =db-pool-size= answers both "how much
  concurrency may this service have" and "how much of the server may it take".
  Behind a pooler the first is the service's - workers times lanes, plus the
  handler work beside them - and the second is the pooler's =default_pool_size=
  and =max_db_connections=. The pool may then be sized to the work without the
  server seeing it, which is the whole reason a pooler is worth its operational
  cost on a shared host and nowhere else.
- *Named prepared statements decide the version floor, 2026-11-21.* The
  repositories run named prepared statements, cached per client connection and
  sent with =PQsendPrepare= when a connection has not prepared them. A name lives
  on a server connection, so transaction pooling loses it unless the pooler
  tracks it: pgbouncer 1.21 and later do, with =max_prepared_statements=; PgCat's
  transaction mode does not, and neither does pgbouncer 1.18. Sending repository
  statements unnamed, as hand-written SQL already does, removes the floor at the
  cost of planning every execution. The task that takes this measures the cost
  rather than assuming it.
- *The listener and the administrative paths stay direct, 2026-11-21.*
  =postgres_listener_service= holds a session to =LISTEN=, which transaction
  pooling would hand to somebody else at the next commit, and =compass db
  recreate= and the schema restore are not request traffic. They name
  PostgreSQL's port while the services name the pooler's.
- *The pool states two numbers, not one, 2026-11-21.* It keeps a floor and may
  burst to a ceiling, and closes what a burst leaves idle. The three settings
  are =db-pool-min=, =db-pool-max= and =db-pool-idle=, stated per service in the
  environment, and the idle period is what makes a ceiling affordable: an idle
  service holds its floor, not its burst. The single number it replaced answered
  two questions at once and could be right for neither.
- *The named statements stay, and the pooler carries the floor, 2026-11-21.*
  Sending them unnamed costs about 21 microseconds a statement: a statement that
  returns nothing ran 26,378 times a second named against 16,980 unnamed, and a
  range lookup over half a million rows showed no difference. Our repositories
  run short indexed statements, which sit near the first figure, so the cost is
  real. The floor is pgbouncer 1.21 or later with =max_prepared_statements=,
  which 1.24 and later default to 200, and it excludes Debian 12's 1.18. A
  pooler keeps the statements of the client that made them and replays them onto
  whichever server connection that client lands on next, which is exactly what a
  repository that prepares on a pooled connection needs.
- *pauli gets a container, a shared development host gets a unit, 2026-11-21.*
  pauli runs the fleet as podman containers pulled from the registry, NATS
  among them, so the pooler joins it the same way: an image, a configuration, and
  the services' options pointing at it. A development host that shares its
  PostgreSQL runs the same binary as a systemd unit. One configuration serves
  both, and a developer's machine runs neither.

* Out of scope

- Read replicas, load balancing and sharding. A single pooler in transaction mode
  answers the connection problem; routing is a different one.
- PgBouncer's own high availability, and a second pooler per host.
- Moving the tests onto a pooler as their default. They run directly, and one CI
  job runs them through a pooler.
- The abandoned =cap server connections across environments= task, whose goal
  this story meets by other means; it stays abandoned rather than revived.
