* Goal

ores.orgmode.service runs the indexing step on the raw table's change notification: it parses each loaded page with ores.orgmode.parser and writes one row per page (org id, title, description, tags), one per section (page, order, anchor, heading path, level, text, and a tsvector weighted by title, heading path and text) and one per link between pages, replacing the previous index whole so no reader sees half of one.

* Acceptance

- Loading the pages makes the service index them, and the index holds one section per heading of every loaded page.
- A second load replaces the index whole; a reader during the rebuild sees the old index or the new one, never a mix.
- The indexing step can be run again without reloading, and gives the same index.

* Plan

The index is derived data: the service computes it from the knowledge pages
and can compute it again at any time. So it is not a bitemporal entity. It
has no versions, no history and no writer but the service, and it lives in
three plain tables in the system tenant, which every tenant reads.

| Table | One row per | Columns |
|-------+-------------+---------|
| =ores_orgmode_knowledge_index_pages_tbl= | loaded page | page id, path, title, description, tags |
| =ores_orgmode_knowledge_index_sections_tbl= | heading, plus the page's preamble | page id, order, anchor, heading path, level, text, =search= (tsvector) |
| =ores_orgmode_knowledge_index_links_tbl= | =[[id:...]]= link | page id, section order, target id, text |

1. *Shape.* The tsvector is weighted in SQL: the page title A, the heading path
   B, the text D, with the =english= configuration. A GIN index covers it. The
   anchor is the heading's =:ID:= when it has one, else a slug of the heading
   path, unique within the page.
2. *Replace whole.* One SQL function,
   =ores_orgmode_replace_knowledge_index_fn(jsonb)=, takes the whole index and
   deletes and inserts the three tables in one transaction. A reader sees the
   old index or the new one, by MVCC, never a mix. The function is the
   tables' only writer.
3. *Build.* A core =knowledge_indexer= reads every current knowledge page,
   parses each with =ores.orgmode.parser=, flattens the heading tree into
   sections and links, and calls the function once. It is pure apart from
   the read and the call, so a test can run it on fixed pages.
4. *Trigger.* The pages change only through a publish. The bootstrap
   publishes them in SQL before the service starts, so the service rebuilds
   the index when it starts. A later publish goes through the service's
   publish step, which rebuilds the index after it changes pages and before it
   reports the step complete. No change notification or debounce is needed.
   An operation, =orgmode.v1.ops.reindex_knowledge_pages=, rebuilds it on
   demand without a reload. It needs the installation permission
   =installation::knowledge_index:rebuild=, which SuperAdmin holds and a
   tenant administrator's =*= does not cover.
5. *Prove.* After a recreate, the index holds one section per heading of every
   loaded page; a second run gives the same rows.
