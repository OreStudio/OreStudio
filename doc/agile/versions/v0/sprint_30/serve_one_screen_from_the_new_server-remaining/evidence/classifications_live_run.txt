The six routes take the list as a path parameter in the BFF and as one generated
route per list in ores.http, so the pairing names a family of 28 routes, one per
list, at the addresses the screen calls.

What the run shows. Three lists read whole and answer the same rows in the same
order: monetary-nature, tenor-anchor and day-counter, the last of them 71 rows.
The catalogue answers the same 28 lists with the same count for each. The four
writes a read-only list refuses answer a 403 at both servers with the same
words. A row is created on an editable list, refused when the same code is sent
again, read back by both servers with the same fields, and removed, after which
both servers no longer hold it.

The run found one thing the port had to put right. ores.http listed the codes by
their bytes, which puts every upper-case code before the lower-case one, and the
screen listed them the way a browser collates: =Act/360= before =ACT/360=. The
day-counter list showed the difference. The shared sort now folds the case and
puts the lower-case letter first, and the day-counter list reads in the screen's
order.
