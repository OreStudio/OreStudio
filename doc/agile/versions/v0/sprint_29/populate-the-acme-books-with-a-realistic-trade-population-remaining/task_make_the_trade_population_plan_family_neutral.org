* Goal

Synthetic has one planner interface, one shared plan envelope and one shared writer. The plan carries a payload that belongs to its family, so a bond slot is a bond and a commodity slot is a commodity trade. The asset class a config names selects its planner, and a class with no planner is refused by name. The population size is a config field and not a constant.

The bond planner is the first implementation. It is the only one this
task delivers. A second family needs references and market data that this
task cannot supply, so each family proves the seam in its own task, and
the extension point is exercised by the bond population until the first of
them lands.

* Acceptance

- A planner is a pure function of the generation scope and returns a plan.
- The plan carries a family-specific payload, and no slot states a bond
  fact outside the bond family.
- One writer executes any plan through the shared booking client.
- The config's asset class selects the planner, and a class with no
  planner is refused by name.
- The bond planner implements the interface, and the old bond-only free
  function is deleted.
- Adding a family adds a payload type, a planner and one arm where the
  writer reads the payload. It changes no booking logic and no envelope.
- The bond population exports as the ORE portfolio the engine reads, and
  reverse-maps without loss.
- The population size is a config field, and the =trades_per_book=
  constant is gone.
- A second run of any planner books nothing.

* Plan

1. The envelope stays. =trade_population_plan= keeps the config id, the
   party and the as-of. =trade_population_slot= keeps the keys every
   family shares: the trade id, the slot number, the book, the
   counterparty, the netting set, the trader, the trade type, the trade
   date, the notional and the currency.

2. The payload becomes a variant. A slot carries
   =std::variant<bond_terms, commodity_terms>=. =bond_terms= holds the
   security id, the issue id, the issuer, the issue date, the maturity,
   the tenor in years, the calendar and the reference curve.
   =commodity_terms= holds the commodity, the delivery and maturity
   dates and the price, strike, barrier or averaging fields its shape
   needs. A family is a type, so a reader of a slot sees which facts it
   carries and no others.

3. The writer reads the payload, and the payload stays plain data. The
   trading protocol carries one typed array per entity, so a family's
   terms become batch members only through a trading type. Putting that
   mapping on the payload would make =ores.synthetic.api= depend on
   =ores.trading.api= and invert the layering, so the writer extracts the
   payload it knows and fills the batch itself. Adding a family therefore
   adds one arm where the writer reads the payload. It changes no booking
   logic, which is the part of the invariant that matters.

4. The planner becomes an interface. =trade_planner= answers
   =plan(scope)=. A registry maps =asset_class_code= to a planner, and a
   class with no entry is refused by name. The free =plan_population= is
   deleted.

5. The shared validation moves up. Book, counterparty, trader, notional
   band and tenor band are checks every family makes, so they run once
   before the planner is called and not inside each planner.

6. The bond planner becomes the first implementation. It states bond
   terms for each slot and produces what =plan_population= produced, so
   the existing tests keep their meaning.

7. The size moves to the config. =trades_per_book= leaves the planner
   header for a column on =ores.synthetic.trade_generation_config.org=,
   regenerated through codegen.

8. Delivery order, one verifiable commit each: the planner interface and
   registry with the bond planner behind it; then the payload, so a slot
   carries its own family's terms; then the population size as a config
   column, generated through codegen. A family of its own is a task of its
   own, because it needs references and market data this task cannot
   supply.

* Notes

=trades_per_book= is a column the create script states as =not null= with
no SQL default, so a fresh database has no value to fall back on. The C++
side defaults to eight and the ACME seed states eight, which is what keeps
the two in step; a new tenant's seed data has to state it too.

* Result

Synthetic now has a planner interface, a registry keyed by the config's
asset class, and a plan whose slot carries the terms its own family states.
The free =plan_population=, which held the bond family inline and refused
every other class by hand, is deleted. The bond planner implements the
interface, and a class with no planner is refused by name.

The population size left the planner header for a column on
=ores_synthetic_trade_generation_configs_tbl=, generated through codegen,
so a tenant sizes its own book. The bond population is unchanged apart from
where it reads that count.

Not done, and moved out deliberately: every other asset class. A family
needs references and market data this task could not supply. Commodity
became its own task and waits on the commodity catalogue.

The extension point is therefore exercised and tested, but proven by one
implementation. The first family task that lands proves the other half of
the claim.
