* Goal

A person signed in to ores.web creates a grant for one agent: its name, read only or read and write, and an expiry. The grant gives a key, shown once and stored hashed. The agent sends the key as a bearer token, and ores.http exchanges it for a short session whose token names the person as sub and the agent as act. The person lists their grants and revokes one, which ends the agent's access at once.

* Acceptance

- A grant is created, listed and revoked in ores.web by a person who holds
  =iam::agent_grants:create=, seeded on the role =AgentDelegator= and not on
  Member; administrators list everyone's with =iam::agent_grants:read= and
  revoke with =iam::agent_grants:revoke=. A grant names a role the person
  holds, and has an expiry of at most ninety days.
- Its key is shown once, stored only as the hash of its secret, and never
  appears in a log, a refusal or a row.
- A request with a valid key acts as the person, with =act= =agent:<grant id>=
  in its token and the role's permissions held by the person, less the withheld
  permissions; an expired or revoked key or grant, a wrong secret, a key for
  another tenant and a lapsed person are each refused with 401.
- A role that names a withheld permission cannot be granted, and no agent's
  token carries one, whatever the person holds.
- The exchange opens or reuses the key's session, which the sessions window
  shows apart from the person's, with the agent's name; ending it revokes the
  key.
- Every rule above has a test.

** The data

| Entity | Columns | Notes |
|--------+---------+-------|
| =ores.iam.agent_grant= | id, party_id, grantor_account_id, agent_name, scope (=read_only= or =read_write=), not_after, revoked_at, revoked_by, revoke_reason | tenant and party isolation; readable over the wire, written only by IAM's operations, as the run grant |
| =ores.iam.agent_key= | id, grant_id, secret_hash, revoked_at | the id is the key's lookup prefix; the secret is never stored |
| =ores_iam_agent_token_issue_log_tbl= | when, tenant, party, grant, key, account, outcome, reason | hand-written, as the run token's issue log; it gives each key's last use without versioning the key on every call |

A key is =ores_ak_<tenant id>_<key id>_<secret>=: the tenant tells IAM where to
read, the key id finds the key, and the secret is 256 random bits, base64url,
compared by its SHA-256 hash.

** The operations

=ores.iam.agent_grant_messages=: create a grant, which returns its first key
once; create another key; revoke a grant; revoke a key; and exchange a key for
a token. Creating and revoking take the person's own session and refuse a token
that already names an agent, so an agent never makes a grant. The exchange is
called by ores.http with its own token and needs =iam::agent_keys:exchange=.

The exchange checks the key, the grant (active, not past =not_after=) and the
person (active), reads the person's effective permissions in the grant's
tenant, keeps for a read-only grant only the codes ending in =:read= or
=:lookup= that the person's codes cover, and mints a five-minute token: =sub=
the person, =username=, =tenant_id=, =party_id= and =visible_party_ids= the
grant's party, =roles= the permissions, =grant_id= the grant and =act= the
agent's name. Every exchange appends a row to the issue log, refusals included,
and failed exchanges are limited per tenant and per key.

** ores.http

In =http_session='s bearer branch, a token that begins with =ores_ak_= is an
agent key: an exchanger, injected as the session store is, returns a cached
token until thirty seconds before its expiry, or exchanges the key with IAM.
The route then serves the request with that token, as it serves any other.

** Order

1. The models, generated: domain, SQL, repository, protocols, wire types and
   shell commands; the permissions seeded.
2. IAM: the key utility, the read-only filter, the operations service, its
   handler and the issue log, with unit tests for the pure parts.
3. ores.http: the exchanger and its cache, wired into the bearer branch.
4. ores.web: the grants page, over HTTP routes for create, list and revoke.
5. Proof: a grant made in ores.web, a key that reads through ores.http, a
   read-only key refused a write, a revoked key refused, and the issue log.
