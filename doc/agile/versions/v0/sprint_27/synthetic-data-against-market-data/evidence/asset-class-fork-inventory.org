#+title: Asset-class fork inventory — synthetic generation pipeline
#+description: Every FX/IR fork in the synthetic generation and ingest pipeline, classified genuine or spurious against the one-pipeline rule.

* Status after implementation

The inventory is the as-found record at =9c1c4af10e=. Several of its findings
have since been acted on and must not be quoted as current.

- The binding mode and the producer subject are one builder for every kind
  now, so a sandboxed IR curve is expressible (=f09d43f5bf=).
- =ensure_feed_binding= no longer exists anywhere. The FX-only
  =start(ore_key, ...)= path and its vintage copy are deleted, and
  =bind_feed= is called from both live start paths, so binding auto-creation is
  reachable (=2e3ca06d17=).
- The control-plane duplication is closed by the per-kind registry (task
  =9DC69ED9=, branch =feature/give-the-synthetic-control-plane-one-registry=).
  The seven spurious forks below that were still open — the repository probe
  that resolved the kind, the per-kind start duplication, the folder loops,
  the per-kind permission literals, the FX-only vintage handler, the
  duplicated simulate plumbing and the repeated factory build — now exist once
  over registered kinds. The one fork deliberately left open is the shared
  embedded base struct for the two generation-config entities, which needs a
  codegen model and schema change.

* Summary

24 forks were found across the factory, the four control-plane handlers, the
feed controller, the two producers and the marketdata ingest, of which 13 are
spurious. The producers themselves are not the problem: the datum, the config
fields and the process maths differ and the factory registry already selects
between them. The biggest spurious fork is the control plane around the
factory — =feed_config_handler= and =folder_feed_control_handler= each
re-implement start/stop/enable/child-loading once per asset class instead of
once over registered kinds. The second is that binding mode and the producer
subject are honoured by FX and silently dropped by IR
(=ir_curve_feed.cpp:301= hardcodes =synthetic_tick_subject=;
=application.cpp:212= hardcodes =binding_mode::bound=), so a sandboxed IR curve
is not expressible at all. The third is a dead-code cluster in
=feed_controller:= the FX-only client-supplied-params =start(ore_key, ...)= has
no production caller, yet it is the /only/ path that calls
=ensure_feed_binding=; binding auto-creation was therefore unreachable from the
live control plane at the time of the survey. =tick_plan=, =market_tick= and
=feed_ingest_loop::persist= are already one path for every asset class and need
no change.

* Forks

** producer datum and process — GENUINE
- What: =fx_spot_feed= advances one scalar process and publishes one =market_tick= per step; =ir_curve_feed= advances one short-rate process and fans it out to N pillar ticks priced by =curve_instrument_pricer= (DEPOSIT/FRA/SWAP). Both implement =IFeed=.
- Branches on: not a branch — two classes behind one interface, selected by kind string.
- Evidence: =projects/ores.synthetic/api/src/feeds/fx_spot_feed.cpp:248=, =projects/ores.synthetic/api/src/feeds/ir_curve_feed.cpp:106=, =projects/ores.marketdata/api/include/ores.marketdata.api/domain/i_feed.hpp:70=
- Verdict: GENUINE. The datum shape (one scalar vs one curve slice) and the pricing maths are exactly the variation the rule permits.

** generation-config datum fields — GENUINE
- What: =fx_spot_generation_config= carries base/quote currency, =ore_key=, =gmm_initial_price=; =ir_curve_generation_config= carries =currency_code=, =index_family=, =tenor=, =role=, =fixed_leg_payment_frequency_code=, =vintage_series_uri=, =description=.

- Verdict: GENUINE. These are the asset class's own identity and instrument grid.

- What: FX components are =gmm_component= rows (mean/stdev/weight) fed to =process_factory::make_process= as three equal-length vectors; IR parameters are =ir_curve_generation_config_process_parameter_value= rows joined onto the =yield_curve_process_parameter_definition= catalogue by name and fed to =map_parameters_to_yield_curve_process=.

* The proposed common pipeline

#+begin_example
market_data_generation_config (container: kind, scope, binding_mode,
                               enabled, auto_start, folder_id)
  └── per-kind generation_config (datum fields + process-parameter linkage)
        │
        ├─ registry: kind → { config_resolver, build_input_loader,
        │                      producer_builder, permission,
        │                      preview_process_maker, vintage_anchor }
        │
        ▼
feed_factory::make(kind, ctx, build_input)   ← the ONE dispatch
  → producer_subject(source_name, binding_mode)   ← ONE subject builder
  → IFeed (asset class supplies only: advance process + emit datum batch)
        ▲
        │  one tick_clock drives every producer
        │  one controller owns add/start/stop/conflict/binding
        ▼
market_tick (one type) → synthetic.v1.tick.<source>
        │
        ▼
feed_ingest_loop: plan_tick → per-binding persist (series + observation)
  + one registered post-ingest hook per datum type (CRM bridge today)
#+end_example

The asset class plugs in at exactly two places: the =build_input_loader= that
reads its config rows into a typed =feed_build_input=, and the =IFeed=
producer that advances its process and emits its datum. Everything between the
config row and the observation write is one path.
