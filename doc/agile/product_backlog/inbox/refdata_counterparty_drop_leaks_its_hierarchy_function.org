#+title: Counterparty's drop leaks its hierarchy function
#+description: The generated drop for a self-referencing-hierarchy entity does not drop the hierarchy function the same generation created; ores.workspace.workspace declares the Extra drop statements paste block and counterparty does not, so every drop-and-recreate of refdata leaves ores_refdata_counterparties_hierarchy_fn behind.
#+type: capture
#+level: cross
#+filetags: :codegen:sql:refdata:inbox:
#+created: 2026-09-28
#+updated: 2026-09-28

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Binding =self-referencing-hierarchy= makes the create file emit
=ores_<component>_<entity_plural>_hierarchy_fn=, and the drop template
knows nothing about it. The =Extra drop statements= paste block
(=5E47F108-1350-4540-B3C2-E83DD5379B2D=) is the mechanism for it, and
=ores.workspace.workspace= now declares the block. =ores.refdata.counterparty=
draws the same function through the same profile and declares no block.

* Why

A drop-and-recreate of refdata therefore leaves
=ores_refdata_counterparties_hierarchy_fn= behind: =git grep -n hierarchy
projects/ores.sql/drop/refdata/refdata_counterparties_drop.sql= finds
nothing, while the create file defines the function. Nothing fails,
because =create or replace= covers the second create, so the leak only
shows as a stale function body surviving a drop that claims to undo the
component. The fix is one paste block on the counterparty model and one
regeneration, and refdata is in =COMPONENTS_UNDER_TEST=, so the drift
gate would confirm it.
