* Summary

Components in ORE Studio communicate over NATS. A message is addressed by a
four-segment subject -- component, version, resource, verb -- and the component
that owns the first segment is the one that serves it, so a subject is answered
by exactly one service or by none. Request and reply is one pattern on the bus;
events published under the =events= segment are the other, and a request is
answered once where an event may have any number of independent consumers.

A payload carries business data and nothing else. Identity, tenancy, version and
audit provenance are derived server-side from the authenticated connection and
never travel on the wire. Entity operations share one verb set and one pair of
envelopes across every component, so a client that has read one component's
protocol has read them all.

** What the bus is

[[id:C9C24C99-F16C-45BE-A262-1C0F4502765E][ores.nats]] — the library that wraps

** Where a subject may live

[[id:A7B3C9D2-E5F1-4A8B-9C6D-3E2F1A0B8C7D][ORE Studio Messaging
Reference]] — the namespace map: which component owns which subjects, and the
rule that no subject is ownerless. Read this before writing a subject, because
a subject in the wrong namespace is served by the wrong service and nothing
reports it.

** What a message must look like

[[id:C650CBC9-FDED-4C68-981F-7902E296928E][NATS Entity Protocol
Specification]] — the centre of the cluster. The subject grammar, the eight
verbs, the request and response envelopes, the write model that keeps
server-owned fields off the wire, the error model, the event contract, and the
security rules. Read it before writing any message; it is the page the rest of
the cluster defers to.

[[id:8883F219-5D1F-4C29-B3F9-47D1622C9248][NATS Wire Format]] — the seam the
specification assumes rather than restates: the envelope against the payload,
and the process-wide encoding choice. Read straight after, because it is what
says which bytes are the message and which are not.

** How a payload may vary

[[id:C951B5F1-B51C-4274-BA4D-6297AD46A4FB][Polymorphic types over NATS]] —
one subject per concrete type, and why a variant is never carried as an untyped
blob. Read when a message has to carry more than one shape, which is exactly
when a shortcut is tempting.

** What a write claims, and what the past means

[[id:CE4752C0-7A3C-46B4-AC97-922C5B940BB1][Optimistic Concurrency
Versioning]] — what the version on a write actually asserts, who owns it, and

[[id:85892C17-BB81-4724-9B84-20E21D41C499][History Diff Architecture]] —
presenting one version against its predecessor. Read after the version page,

[[id:AF46793A-FF6C-4066-A059-279CE9936420][Identity and Access]] is a separate

seam.

[[id:DF2B616F-E112-4C57-A73B-69F85BE96EF4][Market Data Architecture]] is a
domain cluster whose interface happens to be this protocol. Read the protocol
here and what market data does with it there.

criteria a message's shape is reviewed against. It judges the shape; it does not
