* Plan

Give the taxonomy the class, then plan the family under it.

The seven classes the catalogue states are the classes a config may name, and a
scripted payoff belonged to none of them. Filing it under =equity= would be a
half-truth — the codes are equity payoffs written as scripts — and it would also
put two planners on one class, because the equity family already answers there.
So the catalogue gains a =scripted= class, and everything that reads it follows
from the model: the code row, its display order, its prose and its badge.

The planner states the three codes the ORE projection writes an element for:
the generic scripted trade, the double digital option and the performance
option. =Autocallable_01= routes like the others and is named out of scope: the
projection has no writer for its data element, so the trade would book and then
export as an empty product.

The parameters are the document's own members rather than the population's
keys, because the projection writes every key it does not recognise as an element
the schema does not hold. That is what the round-trip case in the ORE suite
proves: the three types carry their parameters back through the export and the
import.

ACME charters a cross asset solutions book and one config, six trades.

* Result

The scripted family books, exports and reads back.

Measured on a fresh tenant: six scripted trades, two of each of the three codes
the projection writes an element for, in a population of 190 — 3.2 per cent of it
against the weight's three. The provisioning run completes all nine steps.

Decisions this task settles:

- *The class is new, and the taxonomy is where it goes.* The seven classes could
  not carry a scripted payoff, and the two honest alternatives were both wrong:
  filing the family under =equity= puts two planners on one class, and naming a
  class the catalogue does not hold is what the store's own validator refuses.
  The catalogue gains =scripted=, and the seed SQL, the badge and the docs that
  read it are generated from that one declaration.
- *One code is out of scope, by name.* =Autocallable_01= is routed and has no
  writer in the ORE projection, so it would book and export as an empty product.
  The task states that rather than booking it.
- *The parameters are the document's, not the generator's.* A key the projection
  does not recognise is written as an element the schema has no member for, so
  the population states exactly the members the document holds — and a
  round-trip case in the ORE suite keeps it that way.

The family prices as far as its underlyings let it: a scripted trade reads the
equity surfaces and spots the equity family already needs, and the engine runs the
script the row names. The class states no market data of its own, which is the
point of a script that observes other classes.

The asset class the taxonomy gained is a model change, so the three SQL files
generated from it are in this diff; nothing else in refdata is regenerated, and
the curve-configuration drift main already carries is untouched.
