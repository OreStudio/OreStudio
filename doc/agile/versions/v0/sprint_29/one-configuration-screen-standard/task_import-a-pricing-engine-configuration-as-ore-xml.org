** The protocol

Two requests and two responses, in the shape the currencies' pair established:

- =preview_pricing_engines_import_request= carries the file's text and the
  target: the reporting configuration to compare against, or nothing for a
  configuration the file would create. The response states the root element it
  found, the products and settings the file holds, the names of the root-level
  settings, the difference in counts and in rows, and three lists of what the
  system does not know.
- =import_pricing_engines_request= carries the same file, the same target or a
  new configuration's name and variant, the keys of the removed rows the person
  kept, and the reason and commentary. The response states the configuration it
  wrote, what it added, changed, deleted and kept, and the rows it could not
  write.

A row of the difference is named by a key: a product by its type and which
product of that type it is (=Swap#0=), a setting by its product's key, its scope
and its name (=Swap#0/engine/DiscountingCurve=). The key is what a choice names,
and it is what makes two products of the same type, or a setting repeated twice
in one scope, tellable apart.

** The parse

=pricing_engines_import::parse= reads the text with pugixml and answers the same
analytics =pricing_engines_document= the exporter writes: the products in their
order, each carrying Model, ModelParameters, Engine and EngineParameters, then
one GlobalParameters block, with a =position= per scope so the export comes back
in the order the file wrote. A text that is not well formed, or whose root
element is another document's, answers a refusal that names the root element it
found and writes nothing.

Three things the tables cannot hold are named rather than dropped:

| What | Kind | What happens to the row |
|------+------+-------------------------|
| an attribute or element with no column | =dropped= | written without it |
| a product with no type, a setting with no name, a product with no model or engine | =missing= | the product is left out, or the row is named and the save refuses it |
| a setting stated twice in one owner and scope | =duplicate= | the first value stands, because analytics refuses a repeated setting |
| a product type the vocabulary does not hold | =unknown_type= | written as the file states it, and named |

The vocabulary is analytics': the handler reads the pricing engine types and
passes the codes to the difference, so the parser decides nothing about what a
screen may offer.

** The difference, and the person's choices

A product is matched by its type and by which product of that type it is; a
setting by its product, its scope and its name, and then by which repeat of that
name it is. Nothing is matched by identity, because the file states no
identifiers.

Only removed rows ask a question, and the review starts every one of them at
*Keep it*: a file that omits a row usually omits it by accident.
=pricing_engines_import::kept_by_default= states that default once, so the
screen and the command cannot default differently, and the import request
carries the keys of the removed rows the person kept.

** The write

The import re-reads the target and re-parses the file, so the write acts on the
configuration as it stands rather than on the preview's reading. It assembles the
document with =pricing_engines_import::merge=: the file's rows laid over the
target's, each row keeping the identity and the version of the row the target
already holds, so a write corrects a row rather than replacing it and the history
stays one line per setting. A kept removal is carried from the target with the
settings it owns; a removal the person dropped is absent from the document,
which is how the analytics save removes it.

It then saves through =analytics.v1.pricing_engines_documents.put=, the same
operation the configuration's own screen uses, so the validation, the history and
the party rules are the screen's, and the person's reason and commentary travel
on the rows, which is where that save keeps them.

** A configuration the file creates

The screen's create writes the reporting configuration the record fills and then
the document, because analytics finds a document by that reporting configuration.
Both the browser and the shell import, so neither may carry that order: the ORE
service's handler registers the reporting configuration through reporting's own
=put_configuration=, saves the document, and removes the header again if the save
is refused, so a refused import leaves nothing behind.

** The official configuration, and what is not built

The configuration screen standard makes a file put into an official configuration
a proposal, with a sign-off. Sign-off is not built. The import writes directly,
with the person's reason and commentary, and the review states that in as many
words before the press. It is the one place this build does not reach the
standard, and it is recorded as the known gap rather than dressed as an approval.

** The screen

Import stands on the list header between Refresh and Workflows (RS-ORE-02), at
=/reporting/pricing-engines/import=, and follows the standard's five steps on the
steps UI: the file, what it holds, what the system does not know, the target
(new or existing), and the difference with *Keep it* as the default for a removed
row. The preview is read twice: once on leaving the file step, which states what
the file holds and what the system does not know without a target, and again on
leaving the target step, which states the difference against the configuration
the person chose.

The five steps are the shared module's, not the kind's: =OreImportPage= takes a
kind that declares its document, its target and its wording, so the currencies
and the pricing engines draw the same dialog. The kind's own file states what a
row is called and what the review offers for it, and nothing else.

** The command

=pricing_engines import <id or --new-name> --file <path> [--dry-run]= sends the
same two operations, prints what the file holds, what the system does not know
and the difference, and then writes, keeping every removed row, because a command
line states no per-row choice. =--dry-run= stops after the preview.

* Notes

- The parse is pugixml's, and the root element is refused with the element it
  found named, as the currencies' import does. The difference from that import
  is that nothing here is matched by identity: the file states no identifiers,
  so a product is matched by its type and by which product of that type it is,
  and a setting within its product by its scope and its name.
- The position an import writes is the place a setting takes in its own scope.
  The live round trip is what found that the first cut numbered it by which
  repeat of its name it was, which put every first occurrence at zero and let
  the export break the ties by id: the values were right and the order was not.
  The round-trip case now carries three settings of one scope in an order no
  sort would produce.
- The vocabulary that decides whether a product type is known is analytics', and
  the service reads it: a type it does not hold is reported, and the row is
  still written, because the tables hold any type code.
- A target the caller names and analytics refuses is a refusal of the whole
  preview, in analytics' own words. One case follows from that: a configuration
  whose header exists but which holds no document cannot be a target, because
  analytics' read finds nothing. A person who wants to fill such a
  configuration has to start a new one, or fill it from the screen.
- A *change reason* is required, and the analytics save keeps the one a row
  states. The import states the person's reason on every row it writes, which is
  how the screen's own save carries one.

* What the standard asks that this build cannot express

The configuration screen standard's Import section, step 4, says that a file put
into an official configuration is a proposal, drawn for sign-off. Nothing in the
system is a proposal and no sign-off is built, so the import writes directly,
with the person's reason and commentary, and the target step says so before the
last press rather than promising an approval it cannot make. Making it a real
proposal needs the lifecycle the standard's own /States/ section names for
official configurations — a state, a reviewer and a transition — and that is a
task of its own. This is the one place where the build does not reach the
standard, and it is recorded as a gap rather than dressed as an approval.

Two smaller ones follow from the same shape:

- The standard says the review "claims the version read". The analytics save
  takes the document whole and stamps it, so the import carries the version of
  every row it touches and the save's own conflict rules apply; there is no
  separate claim the screen makes and the service checks.
- The standard's third step names three kinds of unknown. This document has a
  fourth: a product with no model, with no engine, or with no type at all, which
  analytics refuses as a whole document. The preview names each as =missing=
  rather than leaving the person to meet the refusal after the press.
