* Context

A change to one header rebuilt most of the tree, and the publish lifecycle work
found the case: =ores.database/domain/context.hpp=. It is included by most
repositories and services. Through it each of them parsed =libpq-fe.h=, the
pool, =<mutex>= and =<condition_variable>=, although most only pass a context
along.

The story assumed that the cost came from libpq and the pool. This investigation
tests that assumption on two axes, because they are different questions.

- On *parse cost* the assumption is wrong. =libpq-fe.h= costs 0.04 s. Of the
  6.6 s that =context.hpp= costs, almost all is the decimal and text-form codec
  headers behind =pq/transaction.hpp= and =<chrono>= behind =tenant_id.hpp=.
- On *rebuild blast radius* the assumption is right. Four files include
  =pq/pool.hpp=, and 365 objects rebuild when it changes, because
  =context.hpp= is the door they all come through. Cutting that one edge takes
  147 objects off =pq/pool.hpp= and =pq/transaction.hpp= each.

So the answer is two lists, not one, and the story is ordered by the second.

* Methodology

Two instruments, both kept beside this investigation in =evidence/=, and both
driven by the build's own records so they rerun on any commit.

| Instrument | What it reads | What it answers |
|------------+---------------+-----------------|
| =header_blast_radius.py= | =ninja -t deps=, plus the source text of every =#include= | how many objects and targets rebuild when a header changes, and through which include chain |
| =header_cost.py= | =compile_commands.json= and clang =-ftime-trace= | what a header costs to parse, alone and inside a real translation unit |
| =type_usage.py= | the header, its direct includers, and the compiler | which types the header defines, which includers only name them, and which fall back to the full definition when the compiler is asked |
| =header_blast_radius.py --cut= | the dependency record and the include graph | how many objects stop rebuilding when one include edge is cut |

Run them with:

#+begin_src sh :results verbatim
python3 evidence/header_blast_radius.py \
    --build-dir build/output/linux-clang-release-ninja --top 30

python3 evidence/header_cost.py headers \
    --build-dir build/output/linux-clang-release-ninja --runs 5 \
    --header ores.database/domain/context.hpp

python3 evidence/header_cost.py sample \
    --build-dir build/output/linux-clang-release-ninja --count 14

python3 evidence/header_cost.py compare \
    --build-dir build/output/linux-clang-release-ninja --runs 4 \
    --shadow "projects/ores.utility/include/ores.utility/uuid/tenant_id.hpp:string_generator.hpp"

python3 evidence/type_usage.py \
    --build-dir build/output/linux-clang-release-ninja \
    --header ores.database/domain/context.hpp --verify

python3 evidence/header_blast_radius.py \

* Rebuild blast radius, and what a forward declaration can cut

The story has two objectives and they are measured differently. Read them
separately or the numbers mislead.

- *Blast radius*: how many objects must be rebuilt when a header changes. That
  is the number of objects whose dependency record lists the header.
- *Parse cost*: how much time each of those objects spends reading it.

A forward declaration changes the first and not the second. A constant reference
changes neither: a signature change does not change an include edge. So the
story's forward-declaration work must be ordered by blast radius, and the codec
work by parse cost, and neither ranking substitutes for the other.

** The headers that are dragged in

The pair of counts that matter is objects that rebuild against files that
include the header themselves. A header with a few direct includers and a large
object count is one that almost every reader receives through another header,
which means one cut edge can remove many rebuilds.

| Objects | Files including it | Header |
|--------:|-------------------:|--------|

| 365 | 4 | =ores.database/pq/pool.hpp= |
| 365 | 6 | =ores.database/pq/transaction.hpp= |
| 715 | 12 | =ores.utility/codec/text_form.hpp= |
| 365 | 4497 | =ores.database/domain/context.hpp= |

| 835 | 1288 | =ores.platform/time/datetime.hpp= |

The =pq= family is the clearest case in the tree: four to eight files include
each of those headers, and 365 objects rebuild when any of them changes, because
=context.hpp= is the single door most of the build goes through.

=context.hpp= is the opposite case. 4497 files include it themselves, so nothing
upstream can be cut: its 365 objects are its own readers. That is why forward
declarations in the *users* of =context.hpp= cannot help, and why the useful
work is inside =context.hpp= itself.

** The usage patterns of =context=

=context= is the type the story is about, so the patterns are worth counting in
full. 4497 files include its header. Across the tree there are 21874 by-value
=context= parameters, of which 11141 sit in generated headers: the =repository=
template emits =void write(context ctx, ...)= for every method of every entity,
and the =service= template emits =explicit service(context ctx)= plus a member.

| Pattern | Files | Occurrences | What it means |
|---------|------:|------------:|---------------|
| =using context = ores::database::context;= | 1172 | 1172 | a type alias: names the type and needs no definition |
| reference or pointer | 1054 | - | forward-declarable today |
| by-value parameter | 3570 | 21874 | a copy per call; a =const&= removes the copy |
| member by value (=ctx_=) | 1305 | 1305 | stored for the service's lifetime |
| construction | 420 | 420 | =context(options, tenant, ...)= in an application or handler |

A file can match several patterns. Grouping the 4497 by what the file needs:
472 only name the type, 2268 need only a by-value parameter, and 1752 need the
definition for a member, a construction or both.

So the answer to "why so many copies" is the codegen templates, not hand-written
code: 11141 of the 21874 parameters come from =repository= and =service=
archetypes. The pattern is systemic, and so is any fix.

** Can a reference or a pointer improve it?

Per pattern, on the two axes that matter: does the call get cheaper, and does
the rebuild radius fall.

| Pattern | A =const context&= | Verdict |
|---------|---------------------|---------|
| by-value parameter in a synchronous call | removes a copy; the reference lives for the call | *Do it.* Strictly better, no lifetime risk. |
| by-value parameter in a header | lets the header drop the include | *Does not help rebuilds*: see the ceiling below |
| member =context ctx_= | a reference member dangles as soon as the service outlives its caller; a =shared_ptr= adds an allocation, nullability and an ownership story to a type that is copied today | *Keep the copy.* A copy costs a few small strings and one atomic increment on the shared pool slot, which is nothing beside a database round trip. |
| construction | the caller builds the object and needs the definition | *Keep.* |
| type alias | needs no definition already | *No change.* |

The lifetime risk is currently absent, and it must stay that way. No header
stores a =context&; no lambda captures a context at all. There is exactly one
reference capture in the tree,
=projects/ores.synthetic/service/src/feed_kind_registry.cpp:492=, and it is a
=std::ranges::all_of= inside a synchronous function, so the reference cannot
outlive the call. That file is the list to re-check when a copy becomes a
reference, because a compile does not find a dangling reference.

** The ceiling on cutting headers

If 2268 includers could drop the include, the rebuild radius should fall. It does
not, and this is the measurement that settles the story's premise. Cut the
include from every file that matches a pattern, recompute the reach from each
object's own sources:

| Cut | Objects reading =context.hpp= | Saved | Files cut |
|-----|------------------------------:|------:|----------:|
| all 1738 repository headers | 320 of 321 | 1 | 1738 |
| all 1357 service headers | 301 | 20 | 1357 |
| every header in the tree | 179 | 142 | 8687 |

Cutting the include from all 1738 repository headers saves *one* object. The
reason is the shape of the dependency, not the count: an object is a unity unit
compiling up to sixteen sources, and if any one of them, or any header it
includes, needs the definition, the object depends on =context.hpp=. Every
service =.cpp= constructs or holds a context, so no header-level cut reaches it.

Even cutting every header in the tree leaves 179 of 365 objects reading the
header: those are the =.cpp= files that build a context or store one. The type's
blast radius is structural. It is not a header-hygiene problem, and no amount of
forward declaration fixes it.

** What cutting one edge saves

The dependency record says which objects read a header today, and the source scan
says how they reach it. Remove one edge, recompute the reach from each object's
own sources, and the saving is exact. These figures are the prediction for the
work, measured at =27cad5a0c6= over the 321 of 365 objects whose sources the
record names.

| Before | After | Saved | Edge cut |
|-------:|------:|------:|----------|
| 321 | 174 | 147 | =context.hpp= no longer includes =pq/pool.hpp= |
| 321 | 174 | 147 | =context.hpp= no longer includes =pq/transaction.hpp= |
| 321 | 321 | 0 | =context.hpp= no longer includes =pq/connection.hpp= |
| 498 | 315 | 183 | =json_codec.hpp= no longer includes =text_form.hpp= |
| 498 | 498 | 0 | =protocol_codec.hpp= no longer includes =text_form.hpp= |
| 654 | 435 | 219 | =text_form.hpp= no longer includes =decimal.hpp= |

Two of these say as much as the ones that save. Cutting =pq/connection.hpp= from
=context.hpp= alone saves nothing, because =pq/pool.hpp= and =pq/statement.hpp=
reach it too: the family must move together. Cutting =text_form.hpp= from
=protocol_codec.hpp= alone saves nothing, because =json_codec.hpp= reaches it
too. A cut saves only when it is the last path, so the plan must name the edges
that together close the door.

* The cost is a chain, not a list

Three chains carry nearly all of the header cost. That structure, not the
individual rows, is what the decisions must break.

** The codec chain

=decimal.hpp= (4.03 s, boost multiprecision) is included by =text_form.hpp=
(4.99 s), which adds =boost/asio/ip/address.hpp=, =boost/lexical_cast.hpp=,
=<filesystem>=, =<format>= and =magic_enum=. =protocol_codec.hpp= (6.15 s) and
=json_codec.hpp= (4.95 s) then include =text_form.hpp= so that each text form
can be defined inline.

Everything below that inherits the chain:

- 638 generated =*_protocol.hpp= headers, each of which includes
  =protocol_codec.hpp=. In the sample a unit that reads one pays 0.5 to 1.5 s
  for it.
- =context.hpp=, through =pq/transaction.hpp= (145 ms own) → =pq/statement.hpp= →
  =pq/codec.hpp= → =decimal.hpp=.

** The clock chain

=<chrono>= costs 2.32 s, and C++23 pulls =<format>= and =bits/chrono_io.h= with
it. It is not one door but a habit: 4311 files include it directly, so a reader
of most of this tree pays it whichever header it came through.

Two doors carry it into the headers this analysis ranks highest.
=datetime.hpp= needs it by value in its own inline functions.
=boost/uuid/uuid.hpp= includes =uuid_clock.hpp= and =<chrono>= itself, so every
translation unit that names =boost::uuids::uuid= pays it, and that is 2826 files
directly and every one of the 837 objects that read =tenant_id.hpp=.

The fix here is narrower than the codec chain's. =datetime.hpp= cannot drop it,
because =std::chrono= types cannot be forward-declared and its own inline
functions use them by value. =boost/uuid/uuid.hpp= is not ours to change. What
is left is to stop naming a =boost::uuids::uuid= in a header that most of the
build reads.

** The logging chain

=make_logger.hpp= (3.87 s) includes
=boost/log/sources/severity_channel_logger.hpp= (3.58 s) to declare one typedef,
=logger_t=. Every translation unit that logs pays it: 565 objects in 189
targets.

* Cycles and cross-component includes

- Include cycles among project headers: none. The graph is a DAG, so forward
  declarations within it are safe.
- Includes of another component's =src/= tree: none, in 0 of the 52075 edges.
  The component boundaries hold, so no decision here is blocked by a leak.
- The heaviest cross-component edges are ordinary library use:
  =ores.refdata= → =ores.utility= (5058 edges), =ores.refdata= →
  =ores.database= (3500), =ores.trading= → =ores.utility= (3322).

* Order of work

Two objectives, two orders. The story's goal is rebuild cycles, so the
blast-radius work comes first and the parse-cost work follows. They overlap in
the codec chain, which is why the codec change appears in both.

** For rebuild cycles

Ordered by the objects that stop rebuilding, largest first, and grouped so each
group closes a door that one cut cannot close:

1. =context.hpp= stops including =pq/pool.hpp= and =pq/transaction.hpp=, and
   takes =connection_options= and =open_policy= from a new small header without
   libpq: 147 objects each off the =pq= family's blast radius, and libpq,
   =<mutex>= and =<condition_variable>= out of 365 objects' dependency records.
2. =pq/pool.hpp= and =pq/statement.hpp= stop reaching =pq/connection.hpp=, or
   =connection_options= moves out of it, so the cut in step 1 is not undone by
   the other path.
3. =json_codec.hpp= and =protocol_codec.hpp= stop including =text_form.hpp=:
   183 objects off =text_form.hpp=.
4. =text_form.hpp= stops including =decimal.hpp=: 219 objects off
   =decimal.hpp=.
5. Split =context= into the connection part and the per-request part, and give
   the 1305 services the per-request part only. This is the only step that moves
   =context.hpp='s own radius, and it needs its own task and its own design: it
   changes what a service stores, and it must keep =with_tenant=, =with_party=,
   =with_roles= and =with_transaction= returning complete copies.

Step 5 is not a header change and must not be dressed as one. The measurement is
blunt about it: cutting every header in the tree still leaves 179 of 365 objects
reading =context.hpp=.

** For parse cost

6. =text_form.hpp=: move the text-form definitions into a =.cpp=. This is the
   same change as steps 3 and 4 seen from the other side: 3568 object-seconds
   and the drag on =decimal.hpp= at once.
7. =protocol_codec.hpp= and =json_codec.hpp=: declare only what they must, once
   the forms are out of line.
8. =tenant_id.hpp=: delete the unused include. 0.69 s on 837 objects, no design
   change, so it rides in the same PR as anything else.
9. =error_code.hpp=: move the two =magic_enum= users to the =.cpp=.
10. =make_logger.hpp=: split the logger handle. This needs its own task, because
    it changes every call site.
11. =decimal.hpp=: only after its own measurement of the pointer-indirection
    cost. The exactness is a domain requirement, so this is a trade-off and not
    a clean win.

Steps 1, 2 and 5 belong to [[id:908E710A-C9A3-433E-AC93-92B67FB76B6C][Pass the database context by reference behind a
forward declaration]], which must be re-scoped. Its reference change is worth
doing for run time: 21874 copies disappear, and the only reference capture in
the tree is synchronous. Its forward declarations in the users of =context= buy
nothing for rebuilds, and its acceptance should say so instead of promising
them. Steps 3 and 4 belong to
[[id:DEA440DD-F4B6-4D37-9083-5F3BB33F1018][Forward-declare what the analysis finds]].

* Paths taken

- The first cost instrument used =clang -fsyntax-only -ftime-trace=<path>=. It
  reported zero for every header. Clang writes the trace only for a real
  compile, so the probe now compiles to an object and reads the =.json= beside
  it.
- The trace groups its events by category, not by time. Pairing the begin and
  end events in file order put every span at nesting depth one and reported 48 s
  of a 7 s compile. Sorting the events by timestamp first fixes it.
- The first A/B removed an include by copying the header to a shadow tree that
  mirrored the whole repository path. The =#include= then resolved to the real
  header, so the measurement compared the header with itself and reported a
  saving of zero. The shadow now mirrors only the part the include path
  resolves.
- The first per-type check replaced the header with nothing but a forward
  declaration. Every candidate failed, and the failures were about types the
  header pulled in rather than the type under test. The stub now keeps the
  header's own =#include= lines and drops only the definitions, which asks the
  narrower question.
- The first "which types are only named" count took the type name's syntactic
  context as the answer. The compiler disagreed: 0 of 10 sampled pass-through
  includers compiled without the definition, because a header they include
  holds the type by value. The syntactic count is an upper bound and the
  verification is the result; the tool reports both for that reason.
- Removing =magic_enum/magic_enum.hpp= from =error_code.hpp= does not compile,
  because two inline functions call it. That result is the point of the
  evidence: it turns an opinion into a fact, and it moves the decision from
  *delete the include* to *move the functions*.

* Conclusions

- Reach and cost are different questions and this build answers them with
  different headers. The most widely included headers are free; the most
  expensive ones reach a third to a half of the build; two are both.
- The cost is carried by three shapes: the codec chain rooted in
  =text_form.hpp= and =decimal.hpp=, the clock habit of =<chrono>=, which
  =datetime.hpp= and =boost/uuid/uuid.hpp= carry into most objects, and the
  logging chain opened by =make_logger.hpp=.
- Rebuild radius and parse cost are separate, and the story's lever is the
  first. Forward declarations reach the types that are held by pointer or
  reference and nothing else.
- The copies are real and systemic: 21874 by-value =context= parameters, 11141
  of them from two codegen templates. The copy is cheap, so this is a run-time
  tidy-up and not a rebuild fix.
- =context.hpp='s radius is structural. Cutting the include from all 1738
  repository headers saves one object; cutting every header in the tree still
  leaves 179 of 365 objects reading it, because the =.cpp= files that build a
  context need the definition whatever the headers do.
- The story is right about the rebuild fix and wrong about the parse cost.
  libpq costs 0.04 s to parse, yet it sits under 375 objects. Keeping it out of
  =context.hpp= is a blast-radius fix worth 147 to 375 objects; it is not a parse
  time fix.
- A single unused include in =tenant_id.hpp= costs every one of 837 objects
  0.69 s. This is the cheapest change in the whole analysis and needs no design
  decision.
- The include graph is a DAG and no component includes another's =src= tree, so
  no decision is blocked by a cycle or a boundary leak.
- Codegen output is 94% of the project headers by count and none of the top
  twenty by reach. One template change reaches all 638 protocol headers.

* Recommendations

- Carry out steps 1 to 4 as one PR series under
  [[id:DEA440DD-F4B6-4D37-9083-5F3BB33F1018][Forward-declare what the analysis finds]], in the order given. Steps 1 and 2
  prove the instrument as well as the fix: the same measurement before and after
  states the effect.
- Re-run both scripts after each step and record the result beside this one, so
  the ranking stays a measurement and not a memory.
- Keep [[id:908E710A-C9A3-433E-AC93-92B67FB76B6C][Pass the database context by reference behind a forward declaration]] as
  written, and add the codec chain behind =pq/transaction.hpp= to its scope. On
  the measured numbers the forward declarations are the smaller half of its
  gain.
- Make the forward-declaration check that the story asks for read the type list
  this analysis produced. A type joins the check by adding a line.
- Do not change =decimal.hpp= before measuring what the pointer indirection
  costs at run time. It is the only decision here that trades correctness risk
  for compile time.
