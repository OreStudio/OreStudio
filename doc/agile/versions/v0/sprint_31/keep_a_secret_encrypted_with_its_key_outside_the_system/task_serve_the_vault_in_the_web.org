* Goal

The vault has two HTTP doors — a write and a reveal — and no screen. A person
cannot list the secrets their tenant keeps, cannot see a consumer, cannot rotate or
delete either, and cannot read a value back except by hand-rolling a request. The
shell now serves all of that; the web serves none of it.

* Acceptance

- =ores.web= has a vault area: a list of the tenant's secrets, a list of its
  consumers, a write flow, a reveal that is an audited act, and a delete.
- The gateway exposes the doors those screens need, with the permission each one
  requires, and the route inventory states them.
- The screens state what the vault is and is not: a value is sealed end to end,
  and the screen shows the reveal as a recorded act rather than a copy.
- A web test covers each screen's refusal, and the gate passes.

* Plan

(The questions this task opened with, and how the tree answered them.)

- *Who seals a value a person types?* The gateway does, and did before this task:
  =POST /api/v1/vault/secrets= takes the plain value and seals it to the vault's
  transport key under =custody_context::write=, so the bus carries ciphertext and
  the vault never accepts a plain value. A browser therefore needs no sealing
  library, and the decision stays where the audit already is.
- *Which doors were missing?* Two of the four a screen needs: one secret's
  metadata and the delete. Both exist on the bus and neither had a route, so the
  gateway gained =GET /api/v1/vault/secrets/{name}= (the describe operation) and
  =DELETE /api/v1/vault/secrets/{name}= (the remove operation), each on the
  permission the vault itself enforces. The list and the consumers landed first,
  in #5250.

The screens follow the journey the previous task designed
([[id:5B2D332C-7480-40E4-A989-CC8B1D2124D5][Extract the vault's journey and
prototype its screens]]) and the prototype it settled. The vault has no page of
cards: like Requests, its list is where the menu arrives, so its addresses are a
constant beside the paths and not members of them, which name the screens of an
area's page.

* Notes

*The gateway seals a plain write, and did before this task.* A browser needs no
X25519 to write a secret: =POST /api/v1/vault/secrets= reads the vault's
published key, seals the value under =custody_context::write=, and forwards
ciphertext. The vault never accepts a plain value, and the person's plaintext
touches one process rather than the bus. The trade is that the plaintext crosses
the gateway over the session's connection, which is the same connection every
other write uses.

*The vault has no page of cards.* Its list is where the menu arrives, as the
requests queue is. So the list's trail is Home and Secrets, a record is the step
below it, and its addresses are a constant beside the paths rather than members
of them: a member states the screens of an area's page.

*A permission a person lacks is not drawn.* Add, Change, Delete and Reveal are
absent for a person without the permission each needs, and never drawn disabled.
The screens say what is missing in words where a person would otherwise wonder
why a value cannot be asked for.

*What a browser is told about the vault's ciphertext.* The list door forwards the
vault's own rows, and a row holds the value sealed under the key encryption key.
The screen shows none of it, and the browser can open none of it, but the read
that answers a screen should not carry it at all
([[id:658F3BAE-4E9F-467D-A554-A78E5E6FE525][The list of secrets carries each
value's ciphertext]]).

* Result

The vault is served in the web. Three screens stand on six gateway doors, and
the permission a person holds decides what each one offers.

- *Secrets* lists what the installation holds: the name, the consumer that owns
  it, the key version that protects it and when it was written. It carries no
  value and says so.
- *A secret* states the record and keeps the value masked. Reveal asks the vault
  for it, and the screen states that the ask was recorded rather than offering a
  copy. Change writes a new version; Delete removes the value and leaves the use
  record that describes the delete.
- *Consumers* lists the services the vault may seal a value to and whether each
  is enabled. It cannot add one: the vault registers a consumer when the workload
  asks, and no door registers one on somebody's behalf.

The gateway gained the two doors the screens needed:
=GET /api/v1/vault/secrets/{name}= forwards the describe operation on
=vault::secrets:read=, and =DELETE /api/v1/vault/secrets/{name}= forwards the
remove operation on =vault::secrets:delete=. Both carry the person's own token,
so the vault checks the permission and records them as the actor.

*Proven.* The web package's tests: 2786 passing, ten of them the vault's, each
drawing a screen from seeded reads and a seeded access and stating what it shows
and what it does not. The type check is clean. The route inventory regenerates
with six vault routes. The local gate is green.

*Proven live*, against the gateway built from this branch and signed in as the
system administrator: the list answered 16 secrets and 16 consumers in the shape
the screens parse; the write stored =web.task.probe= and answered its key
version; the record answered the owner and =written_at= in the wire's own form;
the delete removed it and the record then answered that no such secret exists.
The probe was the only row written and it is gone.

*Not proven, and not true yet.* A person cannot reveal a secret a service owns.
The reveal door resolves as the gateway, and the vault refuses because the
secret's owner names a service: =GET .../web.task.probe/value= answered 404,
"This secret belongs to another consumer", although the probe's owner was a
consumer and the caller held the resolve permission. The screen draws the
control and shows the vault's answer, and the gap is captured
([[id:269D12F7-BDC0-4667-A825-912C4B83AC76][A person cannot reveal a secret a
service owns]]). The vault's rule is documented and the fix is a decision about
which side yields, so it is not taken here.

*Not built, and captured.* A secret's versions (the record shows the current key
version and no history), key rotation, consumer registration, and the uses
screen. The list door also still forwards each value's stored ciphertext, which
no screen needs
([[id:658F3BAE-4E9F-467D-A554-A78E5E6FE525][The list of secrets carries each
value's ciphertext]]). And the reveal itself is refused for every secret a
service owns
([[id:269D12F7-BDC0-4667-A825-912C4B83AC76][A person cannot reveal a secret a
service owns]]), which the live pass found and no test could.
