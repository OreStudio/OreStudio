* Goal

Every tenant can read the open data of an account, such as the name, picture and type of a service account, through the same pattern that shares reference data. The confidential data of an account stays inside its tenant and behind its own permissions.

* Notes

** Use cases the design must serve

Each row is a reader or an actor, what it needs, and what happens today.

| # | Who | Needs | Today |
|---+-----+-------+-------|
| 1 | Any reader of any tenant, on a history | The name, picture and type of the author of an entry. The author may be a service of the system tenant. | Hidden by the tenant wall and the C++ tenant filter. The toggle hides nothing and the service has no picture. |
| 2 | A service acting inside a tenant, such as the inbox service or the refdata service | To know that the account named by a soft foreign key exists in the tenant: the notice recipient, the portfolio right, the sandbox owner and members, the approval requester and decider, the delivery and the preference. | The check reads the accounts table under the actor's party rule. The service is in no party, so it finds no account and the insert fails. The engine user passes because it has no actor. |
| 3 | A super admin acting in the system tenant, during tenant setup | To update the service accounts, for example to attach their pictures. | The party rule hides the service accounts, so the update says "Account does not exist" and the tenant stays in bootstrap mode. |
| 4 | A member | The people of the parties the member works in. | Works. The party rule limits the read. |
| 5 | A tenant administrator | Every person of the tenant. | Works, because the administrator is linked to every party. |
| 6 | The sign-in lookup, and a session with no actor | The account by username, before a session exists. | Works. A session with no actor is not restricted. |
| 7 | Any tenant | To write its own accounts. No tenant writes a system account. | Works. No change wanted. |

Use cases 1 to 3 are the failures. Use cases 4 to 7 must keep working.

** What the failures share

The accounts table answers three different questions with one rule.

- *Who is this?* A reader names an author. The answer is a name, a picture and a type.
- *Does this exist?* An insert checks a reference. The answer is yes or no.
- *What do we know about this person?* A reader opens a profile. The answer is private data.

The party rule is right for the third question. It is wrong for the second. For the first, it is right for the people of a tenant and wrong for the services. A reader sees the name and picture of a person only when the product owner's rule lets the reader see that person: the parties the reader has access to, and the system party. A history entry by a person outside those parties shows the username only, as it does today. The tenant rule is wrong for the services of the system tenant in the first question.

** The design

Group the data by who may read it and why, not by the entity.

*** Two tables

- *Open table.* The data that names and recognises an account: id, tenant, version, username, account type, status, full name, picture, picture code and the column =shared=. It holds no contact data and no private data. The party rule applies to its rows that a tenant owns. It does not apply to its shared rows.
- *Confidential table.* The rest: email, default party, job title, reports-to link. It keeps the tenant rule, the party rule and its read codes. It has no shared rows.
- The column =shared= is a boolean, false by default. The seed sets it to true for the service accounts and for the super admin. The shared policy admits a row only when it is owned by the system tenant and =shared= is true. A later human account in the system tenant stays hidden until a person sets the column.
- The columns of each table are settled in the review of this design. Job title and reports-to may move to the open table if the organisation read needs them.

**** One write, two tables

- The open table is the account. It carries the =version= and the temporal columns =valid_from= and =valid_to=. Optimistic locking checks this version. Every foreign key and soft foreign key points at the open table.
- The confidential table is a one-to-one side table keyed by the account id. It has its own temporal columns, so its history is kept. It has no version of its own for locking.
- One function writes both tables in one transaction, and it checks the version of the open table once. A write that changes only confidential columns still increments the version of the open table, so one version describes one account.
- The migration copies each existing row into both tables, with the same id, version and temporal columns. It is in scope for this story. The reads and writes switch to the new tables in the same change, so no reader sees a half-moved account.

*** One standard for data read across tenants

The standard has six building blocks. Reference data already uses blocks 1 to 3.

1. *Owner.* A shared row has =tenant_id = system=.
2. *Policy.* The existing shared-reference tables use one permissive policy. Its =using= clause admits the rows of the current tenant and the shared rows of the system tenant. Its =with check= clause admits only the current tenant, so a write stays inside the tenant. The open table takes this shape. Its tenant policy is permissive today, not restrictive, so widening =using= is enough. The party rule is the only restrictive policy. It stays on the confidential table and on the tenant-owned rows of the open table, and it passes shared rows.
3. *Read.* The generated read declares =:tenant_read_scope: shared=. The template then leaves out =where("tenant_id"_c == tid)=, and the policy decides. The accounts read states that predicate today in the paged read and in the count. Both change with the template.
4. *Guard.* The read has a =:read= code, or an allow-list row with a reason, as the authorised-reads rules require.
5. *Existence check.* A reference to a row that the party rule hides is checked by a security definer function that returns only yes or no. It names no column, so it leaks no data. The function takes the account id and nothing else. It derives the tenant from =app.current_tenant_id=, and it answers true for an account of that tenant or a shared account of the system tenant. A caller cannot name another tenant, so the function is not an oracle across tenants. The function sets a fixed =search_path=. The grant is revoked from =public= and given to the service roles by name.
6. *Page.* One page states the blocks, and the checklist for a new shared table.

*** What each use case gets

| # | Answer |
|---+--------|
| 1 | The open table. The services are system-owned rows. They are admitted by block 2 and read with block 3, so every tenant sees them. |
| 2 | Block 5. =ores_iam_account_exists_fn(id)= replaces the =exists (select ... from ores_iam_accounts_tbl)= in every soft-foreign-key trigger. The party rule no longer matters for a reference check. |
| 3 | A service account is a shared row of the open table. The party rule does not apply to shared rows, so the update of a service account no longer depends on the actor's parties. |
| 4, 5 | The people of a tenant stay tenant-owned. The party rule keeps applying to them in the confidential table. |
| 6 | No change. |
| 7 | No change. Block 2 is select-only. |

** Decisions

The product owner settled these on 2026-10-11.

- *Who a person sees.* A person sees everyone in the parties they have access to, and everyone in the system party. The party rule keeps applying to the people of a tenant. The system party is the one party every person may see. The open table has two row classes: the people of a tenant, under the party rule plus the system party, and the system-owned rows, which every tenant reads.
- *The super admin.* Every tenant may see the super admin account. It stays a =user= account, because humans sign in with it. The shared policy admits the system tenant's rows whole, as the shared-reference tables do. It does not limit them to non-=user= types.
- *One delivery.* The existence function, the table split, the shared-read standard and the documents ship together in one change. The existence function does not ship first.

** Open points for the reviewer

- The system party is a party of each tenant. Its members are visible to everyone in that tenant. The services of the system tenant need no link to it, because block 2 admits them.
- Which soft-foreign-key checks use block 5? The generated triggers come from models, so the change is in the template and every generated trigger changes with it. The implementation lists every trigger and function that reads the accounts table, in every domain, not only inbox and refdata. A test proves each one for a service actor in a tenant.
- *Fallback.* The attach photos failure blocks tenant setup now. If the change grows beyond one delivery, the product owner decides before anything splits. The smallest fix for that case is a write of the service pictures with no actor, which another environment already holds as a hotfix.
