#+description: What each Qt reference data screen offered against what ores.web shows today: fields, children, actions and history.

* Summary

The Qt client had 63 reference data entities, each with a list window and 61
of them with a detail dialog. The web covers them in three shapes: 12 have a
record screen of their own, 24 are rows of the one classification screen, and
9 are kinds of the one convention screen. Six more are reached from another
area, such as books in the trading journey. Five exist in the record registry
but have no screen, and seven are not in the web at all. The field tables
agree on most entities. The largest gaps are the calendar's source, editability
and base calendar, the event's source, and the terms of seven convention kinds,
which the web lists by id only. The section The gaps, judged lists every gap,
including the calendar dates browser, the party hierarchy tab and the currency
import and export. The web is richer than Qt on currencies, parties and every
classification.

This page is a measurement, taken on 2026-10-25 against the Qt vault, which is
not versioned, and against this checkout. The script that produced it is
=doc/agile/versions/v0/sprint_29/inventory_the_qt_screens_and_audit_the_ux_standards/evidence/qt_web_matrix.py=,
and a reviewer reruns it against the Qt sources and this checkout. The
judgements, which fields are not a gap and why, are in the script too, so the
tables below are the script's output and not a hand copy.

* Detail

** How the matrix was built

The Qt side is read from =ores.qt/refdata=. An entity exists where a
=<Entity>MdiWindow=, a =<Entity>DetailDialog= or a =Client<Entity>Model= exists.
The fields of a dialog are the members of the entity struct that the dialog
source reads into widgets or writes back from them. The widget names are not
read, because they differ from the wire names and because some dialogs build
their combo boxes in code. The columns of a list are the struct members its
model returns for the display role. The actions are the toolbar actions the
window adds.

The web side is read from the registries: =REFDATA_RECORDS= and
=CLASSIFICATION_LISTS= in the wire protocol package, the convention kinds in
=conventionKinds.ts=, and the =FieldSpec[]= table beside each record screen. A
Qt entity is matched to a web surface by its entity type, such as
=ores.refdata.currency=. An entity the registries do not name is matched by
hand in the script, with the surface that covers it.

Three kinds of field are not counted as a gap. The provenance fields
(=version=, =modified_by=, =performed_by=, =recorded_at=, the change reason and
commentary) are read by every web screen and asked of no one, per the
[[id:2BF7F03F-6BF4-45FF-8E26-4D3B4E2D943D][Record screen standard]]. A parent key such as =calendar_code= is implied by
the address of a part. A =party_id= is the party scope the web lists under.
The script names each such field and the standard section that explains it.

** Coverage at a glance

| Web surface | Qt entities | Note |
|-------------+-------------+------|
| Record screen | 12 | A list, a record page and dialogs of its own |
| Classification screen | 24 | One shared screen; a row is code, name, description and display order. Four lists are read only |
| Convention screen | 9 | One shared screen; swap, deposit and tenor basis swap have editable terms, the rest list ids only |
| Another area | 6 | Books and portfolios in the trading journey; tenors on the resolution page; the counterparty composite on the party page; the bootstrap config in synthetic feeds |
| Registry only | 5 | Reachable as a picker or a tab of another record, with no screen of its own |
| None | 7 | The calendar date browser, the three CRM configurations, instrument codes, payment frequencies and tenor schedules |

** What the Qt screens had beyond the standard

Every Qt list window had the same toolbar: Reload, Add, Edit, Delete and
History. Every dialog had the same shape: a tab widget with a General tab and
a Provenance tab, a Save, a Delete and a Close button. Currency alone split its
fields over four tabs: General, Formatting, Rounding and Provenance. The table
lists the windows that added to that standard or lacked part of it.

The shared history dialog showed a timeline of versions on the left and, on
the right, two combo boxes to choose the versions to compare, a toggle between
all fields and only the changes, and the difference as text.

** What the web has that Qt did not

- Children on the record page. The currency page has countries, calendars and
  groups tabs. The party page has identifiers, contacts, memberships, centres
  and counterparties tabs. The Qt currency window had no children at all.
- Every classification carries a =display_order=, and the two lists that Qt
  kept as code and description only carry a =name=.
- The party carries =transliterated_name=, =codename=, =party_category= and
  =is_registration_default=. The contact carries =is_primary=.
- The currency carries =ore_currency_type=, =spot_days=, =day_basis= and
  =base_precedence=. The calendar carries an =image_id=.
- The convention screen knows 26 kinds, and Qt had dialogs for 9. Tenor basis
  swap, which is one of the three kinds with editable terms, had no Qt dialog
  at all; nor did the FX, inflation, commodity and bond kinds.
- Workflows on the list header, and the change notification that turns Refresh
  gold, which Qt did not have.

** The gaps, judged

A gap is a Qt field or part that a person could use and the web does not
offer. Each row says what the pipeline must decide.

| Entity | Gap | What it means |
|--------+-----+---------------|
| Calendar | =source=, =is_editable=, =base_calendar_code= | The web cannot say where a calendar came from, whether it may be edited, or which calendar it derives from. The record page has a Derive action but no base |
| CalendarEvent | =source= | Same as the calendar: where the event came from |
| CalendarDate | the whole browser | Qt listed the resolved dates of a calendar. The web has no view of a calendar's dates |
| Seven convention kinds | every term | CDS, FRA, IBOR index, OIS, overnight index, tenor and zero are listed by id. A person reads no term and edits none. Swap, deposit and tenor basis swap are the only kinds with terms |
| Party, Counterparty | the hierarchy tab | Qt drew the parent and child tree. The web shows =parent_party_id= as one field |
| Currency | import XML, export CSV, export XML | Qt had file import and export on the list. The web has no import or export on a record screen. Conventions import through documents instead |
| Registry only, five | a screen | Business centres, business unit types, countries, party id schemes and counterparties are pickers or tabs, with no list and no record page of their own |
| None, seven | everything | The three CRM configurations, instrument codes, payment frequencies and tenor schedules have no web surface. Whether each is still wanted is for the topic order to decide |

** Dropped on purpose

These Qt parts are absent from the web because a standard section replaces
them, and the pipeline does not bring them back.

| Qt part | Replaced by |
|---------+-------------|
| The Provenance tab on every dialog | The last-changed line under the details and the History tab (RSS Last changed; RSS History) |
| The show-related toolbar actions, such as Show rounding types on the currency window | A code that names another record is a link to its page (RSS Fields) |
| Save, Delete and Close in one dialog | Edit opens a dialog that saves or cancels; Delete is an action of the record page with its own confirmation (RSS Amend; RSS Delete) |
| Reload on the toolbar | Refresh in the header, which turns gold when the server changed (ESS Refresh) |
| Two combo boxes to pick the versions to compare | The timeline draws each version and its difference from the one before (ESS History and the timeline) |
| A Provenance tab's modified by and recorded at as fields | Hidden audit columns in the list and the last-changed line (RSS The table) |
