A point-in-time record, written while the story that commissioned it was open, of an [[id:A7F8D9E2-3C4B-4A5D-B67C-8E9F0A1B2C3D][investigation]] into An audit of every seeded value set against the ORE 1.8.17 C++ source: what each set states, what the code accepts, and the disagreements that make a set refuse a value ORE takes..

It is a snapshot, not a description of the system. Whatever it concludes that the code must keep doing belongs on the page that owns the subject; cite that page from code, recipes and models, not this one.

* Context

The value sets state every parameter's allowed values. This audit asks a
different question from the branch that introduced them: does a set state what
ORE actually accepts? It compares every seeded set with the C++ that reads the
parameter, and it records the disagreements.

* Methodology

Every set whose kind can hold a rule was compared with the code. The merged
model was built from the curation, every parameter's readers were found in the
source, and each set was compared with what those readers accept: a list, a
bound, a switch, a pattern or free text. The code is the authority, not the ORE
user guide.

* Findings

** A catalogue set can refuse a valid document when its registry holds a word

The curve leaves =BusinessDayConvention= and =DayCounter= are declared as
catalogue sets over =ores_refdata_business_day_convention_catalogue_v= and
=ores_refdata_day_counter_catalogue_v=. Those views expose the registries'
=code=, and the registries hold words: =Following=, =1/1=. An ORE document
states its own spelling, =F= and =ACT/365=, so the guard refuses a document that
ORE accepts. The two sets are text until the registries carry the spelling the
document writes; the finding is the reason, and it is not one of the thirty-one
below, which compare sets with the code that reads a parameter and not with the
rows a catalogue holds.


** F-01 CalibrationStrategy refuses two values ORE accepts, too narrow
:PROPERTIES:
:SEVERITY: High
:END:

- Set code: =calibrationstrategy=
- Parameter: =ModelParameters/CalibrationStrategy=
- Set as it stands: enumerated, =CoterminalDealStrike=, =CoterminalATM=,
  =DeltaGammaAdjusted=, =None=.
- What ORE accepts: six values. The parser accepts =CoterminalATM=,
  =CoterminalDealStrike=, =DeltaGammaAdjusted=, =UnderlyingATM=,
  =UnderlyingDealStrike= and =None=. The enum holds the same six values.
- Evidence:
  #+begin_src cpp
  // OREData/ored/model/irmodeldata.cpp:76
  CalibrationStrategy parseCalibrationStrategy(const string& s) {
      if (boost::algorithm::to_upper_copy(s) == "COTERMINALATM")
          return CalibrationStrategy::CoterminalATM;
      ...
      else if (boost::algorithm::to_upper_copy(s) == "UNDERLYINGATM")
          return CalibrationStrategy::UnderlyingATM;
      else if (boost::algorithm::to_upper_copy(s) == "UNDERLYINGDEALSTRIKE")
          return CalibrationStrategy::UnderlyingDealStrike;
  #+end_src
  #+begin_src cpp
  // OREData/ored/model/irmodeldata.hpp:79
  enum class CalibrationStrategy { CoterminalATM, CoterminalDealStrike,
      UnderlyingATM, UnderlyingDealStrike, DeltaGammaAdjusted, None };
  #+end_src
- Case handling: the parser uses =boost::algorithm::to_upper_copy=. The exact
  spelling of a set value does not matter to ORE.
- Direction: too narrow. The screen refuses =UnderlyingATM= and
  =UnderlyingDealStrike=, and ORE accepts both.
- Correction: in
  =projects/ores.seeder/datasets/ore_pricing_engines/curation/value-sets-guide-enums.json=,
  under =sets=, entry =calibrationstrategy=, add =UnderlyingATM= and
  =UnderlyingDealStrike= to =values=, with =order= 4 and =order= 5.

** F-02 Scheme refuses GaussLobatto and accepts a value one engine refuses
:PROPERTIES:
:SEVERITY: High
:END:

- Set code: =scheme=
- Parameter: =EngineParameters/Scheme=
- Set as it stands: enumerated, the nine FDM schemes plus =Segment=:
  =CrankNicolson=, =Hundsdorfer=, =Douglas=, =CraigSneyd=,
  =ModifiedCraigSneyd=, =ImplicitEuler=, =ExplicitEuler=, =MethodOfLines=,
  =TrBDF2=, =Segment=.
- What ORE accepts: ORE reads =Scheme= in two engine families, and the accepted
  lists differ.

  The finite difference engines parse nine schemes:
  #+begin_src cpp
  // OREData/ored/utilities/parsers.cpp:754
  FdmSchemeDesc parseFdmSchemeDesc(const std::string& s) {
      static std::map<std::string, FdmSchemeDesc> m = {
          {"CrankNicolson", ...}, {"Hundsdorfer", ...}, {"Douglas", ...},
          {"CraigSneyd", ...}, {"ModifiedCraigSneyd", ...},
          {"ImplicitEuler", ...}, {"ExplicitEuler", ...},
          {"MethodOfLines", ...}, {"TrBDF2", ...}};
  #+end_src

  The variance swap engine accepts =GaussLobatto= and =Segment= only:
  #+begin_src cpp
  // OREData/ored/portfolio/builders/varianceswap.hpp:107
  std::string schemeStr = engineParameter("Scheme", {}, false, "GaussLobatto");
  if (schemeStr == "GaussLobatto")
      settings.scheme = ...::Scheme::GaussLobatto;
  else if (schemeStr == "Segment")
      settings.scheme = ...::Scheme::Segment;
  else
      QL_FAIL("invalid var swap pricing engine parameter Scheme (...)");
  #+end_src
- Case handling: both comparison functions are case-sensitive.
- Direction: too narrow and too wide. The set refuses =GaussLobatto=, which the
  variance swap engine accepts and uses as its default. The set accepts
  =Segment=, which every finite difference engine refuses.
- Correction: in
  =projects/ores.seeder/datasets/ore_pricing_engines/curation/value-sets-code.json=,
  under =sets=, entry =scheme=, add =GaussLobatto= to =values=. State in the
  description that =GaussLobatto= and =Segment= apply to the variance swap
  engine, and that =Segment= does not apply to a finite difference engine. A
  single set cannot be exact for a name that two engine families read. The
  union of the two lists is the closest exact set that the model can hold.

** F-20 Integer sets that ORE stores in a Size have no minimum, wrong bounds
:PROPERTIES:
:SEVERITY: High
:END:

These sets are =integer= with no minimum and no maximum. ORE reads each value
with =parseInteger= and stores it in a =QuantLib::Size=. A =Size= is unsigned.
ORE silently converts a negative value to a very large positive value. The value
set must refuse a negative value.

* Corrections to this audit, made when the findings were applied

The findings were applied in [[id:6282679D-A8A2-44BA-895D-CEBBA62E0E88][Correct the value sets against the ORE code]]. Three do not hold as written.

** F-04 and F-05 are not applied: Model and Engine name a builder, not a fixed list

The evidence is one builder's comparison for a scripted trade. The same element
names a builder from ORE's registry for every other product type, and the
registry holds far more names than the five a scripted trade accepts. The
seeded population states LGM, BlackScholesMerton, DiscountedCashflows,
CrossAssetModel, GarmanKohlhagen and eleven more, and the valid name depends on
the product type. A set of five would refuse every valid interest rate
configuration, so both sets stay text and their descriptions say what they name.

** F-03 is applied in part: Calibration is text for a reason the audit missed

The IR and FX builders read it through =parseCalibrationType=, which accepts five
values. The scripted trade builder stores the same parameter as a plain string
with a default of =Deal= and never compares it, so no list bounds it there. The
union of a five-value list and an unvalidated string is text, and the set says so.

** The business day convention catalogue now states ORE's spellings

The audit did not reach the catalogue contents. ORE's parser maps 26 spellings
onto seven conventions, and the registry holds the seven; the catalogue view
states the crosswalk, so a document that says =F= and one that says =Following=
are the same rule. The day counter registry already held ORE's spellings.

* Sets not decided

** =runtype=, parameter =GlobalParameters/RunType=

ORE never reads this value from a configuration and never validates it. ORE
writes the value itself, for example at =analytic.cpp:243= (=NPV=),
=xvaanalytic.cpp:573= (=Exposure=), =stresstest.cpp:149= (=Stress=) and
=sensitivityanalysis.cpp:213= (=SensitivityDelta= or =SensitivityDeltaGamma=).
The builders compare the value with a few words, for example
=cdo.hpp:89= and =swaption.cpp:125=. A user can write any word in the XML and
ORE does not refuse it. The parameter is therefore neither a fixed list nor
free text. Decide whether the setting belongs in the model at all before a
value set is authored.

** =mctype=, parameter =GlobalParameters/McType=

ORE sets this value and never parses it. =xvaanalytic.cpp:574= sets =Classic=,
=xvaanalytic.cpp:986= sets =American=, and =capfloor.cpp:141= compares it with
=American=. The audit found no reader that accepts or refuses a user value.
Decide whether the setting belongs in the model before a value set is authored.

** =calibrationindexterms=, parameter =EngineParameters/calibrationIndexTerms=

The audit found no reader of this name in the ORE source. The link may come
from the ORE guide only. A search of =OREData=, =OREAnalytics= and =QuantExt=
found no string literal =calibrationIndexTerms=.

** =conversion_ratio_discretization_grid=, parameter
=EngineParameters/ConversionRatioDiscretizationGrid=

The audit found no reader of this spelling. ORE reads
=Pricing.ConversionRatioDiscretisationGrid= with an =s= at
=convertiblebond.cpp:89=, and that name has its own set. The two names look
like a duplicate. Confirm which name ORE uses before a value set is authored.

* Limits of this audit

- This audit reads the parser and the call site. It does not run ORE.
- A =number= set that ORE reads as a comma separated list keeps the =number=
  kind. Examples are =buckettimes=, =calibrationmoneyness=,
  =heston_initialvalues= and =heston_maximuminitialvalues=. The model has no
  list kind, so the audit does not report these sets.
- The audit found no explicit =QL_REQUIRE= bound on a real valued engine
  parameter other than =beta=.
- The audit compares the =integer= kind against a =Size= store for the sets in
  F-20. It did not trace every one of the 46 integer sets to its store type.
