#+title: ores.reporting.report_error_event
#+description: Codegen entity model for the reporting =report_error_event= table. The errors a report run produced, each one carrying what it is about so a screen can place it.
#+type: ores.codegen.entity
#+component: reporting
#+filetags: :model:entity:reporting:
#+brief: An error a report run produced, and what it is about.
#+entity_singular: report_error_event
#+entity_plural: report_error_events
#+entity_title: Report Error Event
#+created: 2026-10-16
+#+updated: 2026-10-17

One error a report run produced, held against the run. A report run is one
execution of a report definition, and a run whose analytics fail is still a run
that completed: the engine finished, wrote its report, and said in its own log
that a trade would not build. Those errors are facts about the run, they belong
to it, and they are what this table holds.

An error is a fact about an instant: it is written once and never changed. The
model therefore states =:current_state:= and =:immutable:= in the =* SQL **
Flags= drawer, as [[id:47E6903C-DFA7-4D2F-B044-C1C74428F719][ores.reporting.report_trigger_event]]
does. A current-state immutable table has no validity window and no audit tail:
there is no =version=, no =valid_from=/=valid_to=, and no =modified_by=,
=performed_by=, =change_reason_code= or =change_commentary=. Because it has no
audit tail, the time is a column of its own, =event_time=.

=event_time= is the moment the errors were collected from the run's output. The
engine's structured log does not carry a time: a =log_structured.json= line
states its =category=, =group=, =message= and =sub_fields= and nothing else, and
=engine_log_error= parses no timestamp. There is therefore no engine instant to
copy, and the collection instant is the truth the recorder can state.

A row says four things: how bad the error is, what it is about, what it said,
and which subject it names. The first is =severity=. The second is =scope_code=,
drawn from the engine's own vocabulary, and it is what places the error:
=Trade= on the trade, =Analytics= on the analytic, =Curve= on the curve, and
=Report= on the run itself. The third is =message=, the engine's own words.

The fourth is =subject= and =subject_id=, a discriminator and a value, holding
the identifier of the thing the error names: =trade= and a trade id,
=analytic= and an analytic type, =curve= and a curve id. It is a discriminator
and a value rather than one column because the ids are of different kinds — a
trade id is a UUID the portfolio builder minted, a curve id is a free-text name
such as =[IndexCurve(GBP-SONIA,Yield/GBP/GBP1D)]= — and one column holding
both would be a text column no reader can key on. It is not a database foreign
key for the same reason: the engine names trades by its own ids and curves by
their ORE names, and neither is a key any table here holds. The pair is stored
so that a screen can find every error about one subject, and it is a
discriminator rather than a fixed column per kind because the engine adds
sub-fields to the groups it already has, as the corpus shows it doing when an
=Analytics= error grew a =tradeId=.

=scope_code= and =subject= are not the same question. The scope is the group the
engine emitted, which is what the error is about at the level the engine named
it; the subject is the particular thing, and it can be narrower than the scope.
An =Analytics= error that names a =tradeId= is about that trade and not about
the analytic as a whole, and its subject says so.

A run that fails before the engine sees it, because a workflow step did not
complete, produces a row too, with scope =Report=. That is why the table is one
table rather than two: a reader opening a report wants its errors in one place.

How bad the error is: =error= or =warning=. The engine states this per message
as its =category=, and an =ALERT= the engine wrote is an =error= here. A warning
is an error the engine chose to continue past, which is why it is the same
table: the repair is the reader's to judge, and hiding it would be the mistake
that produced this task.

A synthetic row is a warning rather than an error: the severity is a closed set
the store checks, and a fixture that drew one at random would be refused.

** Checks

| expression |
|------------|
| ("subject" is null) = ("subject_id" is null) |
| "severity" in ('error', 'warning') |
| ("subject" is not null) or ("subject_version" is null and "subject_as_of" is null) |

The first is the invariant that matters to a reader: a row names a subject in
full or names none, and never half of one, and the version and the instant it
was current at belong to the subject rather than stand alone, so a screen that looks a row up by
its subject either finds it or is told the row is about the run. That a row
naming no subject is a row about the run is what the scope says, and the writer
that reads the engine's log is where the two are kept in step.

** Indexes

| name    | columns                                                             | unique | current_only | where_extra         |
|---------+---------------------------------------------------------------------+--------+--------------+---------------------|
| subject | tenant_id, subject, subject_id                                      | false  | true         |                     |
| run_subject | tenant_id, report_instance_id, scope_code, subject, subject_id, message, detail | true | false | subject_id is not null and severity = 'error' |
| run_report  | tenant_id, report_instance_id, scope_code, message, detail     | true   | false        | subject_id is null and severity = 'error' |

The two unique indexes say what makes one error row the same as another. A
row that names a subject is the same row when the run, the scope, the subject
kind, the subject id, the message and the detail agree. The detail is what
tells one analytic's failure from another's on the same trade. A row that names no subject is the same row when
the run and the scope agree, and its subject is now a scope code so that two
different scopes cannot collide.

Only errors are made unique. A warning the engine writes twice is a warning
about two things, and the run keeps both.

They exist because the step that reads a run's output can run more than once at
the same time. The recorder asks the database whether the run already holds its
errors, and two callers can both find none; the index lets one of them win and
the other fail rather than write the reasons twice.

*** read_counts_by_report_instance_ids

Counts a run's problems by severity, one row per run that recorded any. The
generated list answers rows, so a caller that wanted a count would read every
error of every run and count them in C++; the store answers the question in one
statement instead, and the rows never leave it.

#+begin_src cpp :name implementation :implements F2EB1914-5E94-42CA-9C77-46BDB364BF9E
std::vector<messaging::report_error_count>
report_error_event_repository::read_counts_by_report_instance_ids(
    context ctx, const std::vector<boost::uuids::uuid>& report_instance_ids) {
    if (report_instance_ids.empty())
        return {};

    BOOST_LOG_SEV(lg(), debug) << "Counting the problems of "
                               << report_instance_ids.size() << " run(s).";

    // One bound array rather than one parameter per id, so a list of forty
    // runs is still one statement.
    std::string id_array("{");
    for (std::size_t i = 0; i < report_instance_ids.size(); ++i) {
        if (i > 0)
            id_array += ',';
        id_array += boost::uuids::to_string(report_instance_ids[i]);
    }
    id_array += '}';

    // The tenant and the policy on the table narrow the rows exactly as they do
    // for the generated reads; no party is stated here.
    const auto rows = query_builder::execute_parameterized_multi_column_query(
        ctx,
        "SELECT report_instance_id::text,"
        "       count(*) FILTER (WHERE severity = 'error')::text,"
        "       count(*) FILTER (WHERE severity = 'warning')::text"
        " FROM ores_reporting_report_error_events_tbl"
        " WHERE tenant_id = $1::uuid"
        "   AND report_instance_id = ANY($2::uuid[])"
        " GROUP BY report_instance_id",
        {ctx.tenant_id().to_string(), id_array},
        lg(),
        "Counting the problems of each run");

    std::vector<messaging::report_error_count> counts;
    counts.reserve(rows.size());
    for (const auto& row : rows) {
        if (row.size() < 3 || !row[0] || !row[1] || !row[2])
            continue;
        messaging::report_error_count count;
        count.report_instance_id = boost::lexical_cast<boost::uuids::uuid>(*row[0]);
        count.errors = std::stoll(*row[1]);
        count.warnings = std::stoll(*row[2]);
        counts.push_back(std::move(count));
    }
    return counts;
}

messaging::get_report_error_counts_response
report_error_event_service::get_report_error_counts(
    const messaging::get_report_error_counts_request& request) {
    messaging::get_report_error_counts_response response;
    // The cap is the same one the generated filters state, so one caller cannot
    // ask the store for more runs than the list reads allow.
    if (request.report_instance_ids.size() > 1000) {
        response.result = refuse(outcome_code::filter_too_large,
                                 {.field = "report_instance_ids", .limit = "1000"});
        return response;
    }
    response.counts = repo_.read_counts_by_report_instance_ids(ctx_, request.report_instance_ids);
    return response;
}

#+begin_src cpp :name declaration :implements B9E2F4A1-3C7D-4E8B-A5F0-2D6C1B8E3A7F
    /**
     * @brief Serves reporting.v1.ops.get_report_error_counts.
     *
     * A read of the errors of the party's runs, so it is gated by the same code
     * the generated error reads are gated by.

    void get_report_error_counts(ores::nats::message msg) {
        BOOST_LOG_SEV(report_error_event_handler_lg(), debug) << "Handling " << msg.subject;
        auto req_ctx_expected = ores::service::service::make_request_context(ctx_, msg, verifier_);
        if (!req_ctx_expected) {
            error_reply(nats_, msg, req_ctx_expected.error());
            return;
        }
        const auto& req_ctx = *req_ctx_expected;
        [[maybe_unused]] const auto correlation_id = ores::service::messaging::log_handler_entry(
            report_error_event_handler_lg(), msg, req_ctx.tenant_id().to_string());
        if (!has_permission(req_ctx, "reporting::report_error_events:read")) {
            error_reply(nats_, msg, ores::service::error_code::forbidden);
            return;

        if (!req) {
            BOOST_LOG_SEV(report_error_event_handler_lg(), warn)
                << "Failed to decode: " << msg.subject;
            error_reply(nats_, msg, ores::service::error_code::bad_request);
            return;

            failure.result.code = "internal_error";
            failure.result.message = e.what();
            reply(nats_, msg, failure);
        }
    }
