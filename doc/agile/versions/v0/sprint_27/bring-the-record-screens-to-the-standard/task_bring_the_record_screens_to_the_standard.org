* Acceptance

- The classification list and row page, the tenant list and page, and the
  parties list use the shared list, header, tabs, details and dialogs.
- Each remaining difference is named in the standard's conformance table, as
  an exception the standard names or as a server gap with a capture or task.

* Plan

Five units, each committed after a typecheck, the web tests and a format
check:

1. Extend the shared list: =RecordTable= split from =RecordList= for a tab
   that lists records the page only reads; choice and toggle filters held in
   the address as =f.<id>=; notes above the table; a source scope for one
   owner's records; rows with no page do not open. Move the parties list on.
2. Move the tenant list onto the shared list, with its filters and notes. The
   row menu goes; Delete and Resume setup are on the tenant page.
3. Move the tenant page onto =RecordHeader=, =useTabs=, =RecordDetails= with
   the last-changed line, and =RecordTable= for its parties and people.
4. Bring the classification list and row page to the standard. The shared
   delete and revert dialogs take the write, so a kind with its own write API
   uses them.
5. Record the conformance in the standard; add the roles task and capture the
   tenant and party server gaps.

* Result

The classification, tenant and party screens now use the shared record
parts. The shared list gained filters, notes, a scope, rows with no page and a
=RecordTable= for tabs; the delete and revert dialogs gained a core that takes
the write. 301 web tests and 222 BFF tests pass, and every screen was driven
in headless Chrome against the running services, including a saved edit and a
revert. The roles screens are a new task in this story, and the tenant and
party server gaps (order, search, tenant history) are captured in the inbox.
