* Goal

A person who asks for a run gets one, whether or not the report has ever been
scheduled. The report holds its consent to run, and admission creates that
consent from the person asking when it does not yet exist. Every later trigger,
on demand or scheduled, reuses it.

This is the half of [[id:822CEF08-980C-4548-9C7B-04CFF433CEFB][the trigger
story]] that gives a run its authority. Without it a run that no schedule
produced cannot act, which is why building a report's ORE packages fails today.

* Acceptance

- A definition that holds no consent is admitted on demand, and the instance
  that results records a run grant.
- The consent is recorded on the definition and reused, so a later trigger
  asks IAM for nothing.
- The scheduled path still admits its runs.

* Plan

The consent is created in one place both acts reach:
=report_run_grant_service::ensure= returns the grant the definition already
holds and asks IAM for one when it holds none, then records its id on the
definition.

The reporting service reaches IAM on the person's own token. The trigger
message carries that token in its Authorization header, whatever the scheduler
does when it publishes its own firing, so the handler relays it with
=nats_client::with_delegation= and IAM reads the person as the grantor. A
trigger that carries no person -- the scheduler's firing, when reconciliation
has already cleared the job's consent -- is refused by name rather than served
by the service account, because a service account's consent is a different
thing from a person's and the story says so.

Two decisions:

1. The consent is created once and written back to the definition. Every later
   trigger reads it off the row and does not call IAM. A concurrent
   double-admit needs no lock here: IAM enforces the natural key of party,
   resource and grantor, answers a repeated create with the grant that already
   exists, and catches its own insert race on that unique index. Both
   admissions therefore record the same id, and the write-back is idempotent.
2. Unscheduling keeps the consent. Consent belongs to the report and serves an
   on-demand run as well as a schedule, so withdrawing it when the schedule is
   removed would refuse a person's own runs after they turned their schedule
   off. The consent is revoked by IAM's own revoke operation, not by
   unscheduling. This removes =unschedule_one='s revoke call; =schedule_one=
   still revokes a grant it created for a schedule it could not record.

* Result

Built. =report_run_grant_service= is the one place a definition's consent is
settled, and the trigger path calls it before it admits. A definition that no
schedule ever ran now runs on demand: =service_report_run_grant_tests.cpp=
admits one and reads back both the definition's grant and the instance's.

Unproven here: the end-to-end =ore build-packages= run, which needs the
workflow stream and a live workflow service. The test admits a package instance
and stops at the dispatch, because the test's subject prefix covers no stream.
