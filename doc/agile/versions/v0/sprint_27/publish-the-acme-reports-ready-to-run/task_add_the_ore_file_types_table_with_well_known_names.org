* Goal

Add a lookup entity that lists the kinds of file in the ORE universe and gives each its well known name. The names follow the convention of the ORE samples, so a configuration never repeats a file name. The table covers the input documents (pricing engines, conventions, curve configuration, today's market, simulation, sensitivity, stress test, netting, collateral balances and the rest), the data files (portfolio, market data, fixings), the files the engine writes for each analytic, and the intermediate files that two analytics share.

* Acceptance

- An entity model, generated into the SQL, C++ and TypeScript layers, holds the file type code, a name, the kind (input document, data file, output file or intermediate file), the configuration type or analytic it belongs to, and the well known file name or name pattern.
- The table is seeded for every file kind found in the 416 ORE samples. Each default name is the most common name in the samples, and the count that supports it is recorded.
- A file that may be split has a name pattern with a key, for example portfolio_{{BOOK_ID}}.xml. The table can hold the pattern. Splitting itself is a later task.
- A test compares the seeded names with the ORE samples, so a name that drifts from the convention is found.

* Plan

1. Build the list of file kinds from the ORE schemas and the 416 sample run documents: each configuration type has a document, the data files are the portfolio, the market data and the fixings, and each analytic has output files.
2. For each kind, count the names the samples use and take the most common plain name. Record the count. Drop the relative prefix of the examples, because a package keeps its inputs in one folder.
3. Model the entity: file type code, name, kind, the configuration type or analytic it belongs to, and the name or name pattern. Generate the layers from the model.
4. Seed the table as system data. Add a test that compares the seeded names with the samples.
5. Allow a key in the pattern, for example =portfolio_{{BOOK_ID}}.xml=, and document the syntax.

* Notes

Decisions made while building the table.

- A file type is one parameter of the run document that carries a file name, keyed by the analytic that names it (empty for the Setup block) and the ORE parameter. The code is =scope.parameter=, for example =setup.conventionsFile= or =npv.outputFileName=. The pricing engines file of the simulation analytic is a different file type from the Setup one, because the samples give the two different names.
- A name that embeds an eight digit date is set aside, because the date is a value of the run and not part of a name. =fixings_20160205.txt= is the most common fixings name (268 samples) but the table holds =fixings.txt= (62), and =market.txt= (75) in place of =market_20160205.txt= (153).
- =logFile= is not a file type. It is a stored choice of the configuration.
- A value that lists several files, such as the pca input files of calibration, is left out, because it is not one file.
- Kinds: an output file has Output in its parameter name or is =outputFile=; an XML value is an input document, except a portfolio, which is a data file; a CSV or text file that another analytic also writes, or whose parameter says Input, is an intermediate file; the rest are data files.
- Only four Setup documents have a configuration type today (conventions, curve configuration, today's market, pricing engines). The other documents get theirs when the tasks that add their entities land.
- A name may be a pattern with a key between double braces. The check constraint accepts =portfolio_{{BOOK_ID}}.xml= and refuses a malformed key. Seeding a split file is the job of the split task.
- The seed is generated, and =generate_file_types_populate.py --check= compares it with the samples. The check is part of the local gate (=file-types-seed=).

Counts from the samples, measured on 2026-10-12 over the 416 run documents: =pricingengine.xml= 189 of 416 plain uses of =pricingEnginesFile= and 150 more with a relative prefix; =netting.xml= 209 of 252 uses of =csaFile=; =collateralbalances.xml= 23 of 23; =sensitivity.xml= 70 of 76; =stresstest.xml= 15 of 19; =npv.csv= 333 of 368; =flows.csv= 314 of 336; =curves.csv= 315 of 331.

The table lists names and patterns. It does not hold content. The content of an input document comes from the entities of its configuration type.
