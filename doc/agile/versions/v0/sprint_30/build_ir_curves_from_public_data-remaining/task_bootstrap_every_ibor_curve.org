* Goal

Every IBOR feed of every currency has a bootstrapped curve that reads its own IBOR quotes and discounts off the currency's overnight curve, publishes like any other curve, and carries the projection role so no consumer takes it for a discount curve.

* Notes

- The seeds: =marketdata_market_series_ibor_curves_populate.sql= holds the 40 series and
  their junctions, and =refdata_ir_curve_bootstrap_ibor_configs_populate.sql= the ten configs
  and their seventy pillars. The IBOR config seed must run *after* the overnight config seed,
  because a projection config resolves its discount curve by name as the file runs; the first
  order put it before and the insert failed with a NULL discount.
- The ordering is the remaining change, and it is not a role sort: the sweep takes its order
  from a build plan derived from the inputs each curve declares, and a curve whose input is not
  live is deferred rather than failed. The design, its three outcomes and the one planner every
  builder shares are [[id:12FEEA51-92A0-45C1-A9DA-67C7DB670C2C][Market Data Build Order]].
- The quotes themselves need the synthetic feeds started: after a fresh recreate the dataset
  must be published and the synthetic service restarted so the adapters announce and the feeds
  run, as the previous task's live run showed.

- The overnight chain is the template: two market_series rows (the curve output with
  =instrument=discount...curve_id=<name>= and the quote ladder with =instrument=ir_swap=), one
  config, seven pillars, and the republish service that stamps the output series.
- PROJECTION is supported and unexercised: =curve_republish_service.cpp= reads
  =curve_family_role= and =discount_curve_config_id=, loads the funding config's output as the
  discount curve, and passes it to the engine for a projection config. The schema and a trigger
  require a PROJECTION config to name an active FUNDING config, and the engine rejects a
  discount curve that does not cover the pillar dates.
- Blocked on [[id:0A87FC5F-F15E-40D8-8CF6-572D24A203EE][Make the ICE and Tradeweb feeds tick]]: without a notation and a feed
  route, ICE and Tradeweb quotes are published as internal ticks and dropped, so no quote series
  exists to bootstrap from. All 417 seeded =ir_swap= series are =tenor=1D=; none is an IBOR tenor.
- Per curve: one output series (provider =ore=, OBSERVED, curve_id = the config name), three
  quote series per ladder (=fwd_start=0D/3M/6M, =tenor=<index tenor>=), the config
  (PROJECTION, discount = the currency's FUNDING config, RATES_SPOT_FORWARD), and seven pillars
  (SPOT-1M/3M DEPOSIT, 3M-6M and 6M-12M FRA, SPOT-2Y/5Y/10Y SWAP). GBP-SONIA is a valid discount
  curve for GBP-LIBOR-3M.
- Ordering: a projection curve needs its discount curve published for the same as-of first;
  nothing sequences that today, so the sweep must publish FUNDING before PROJECTION or retry.
- The output identity carries no role: the oresmd instrument is =discount= for every curve, and
  the projection role lives on the config, so a consumer must read the config, not the series.

* Result
The task shipped. One firing of the scheduled sweep planned the thirty seeded
curves, built the twenty funding curves, then built the ten IBOR projections
against the funding curves it had just published, and published all thirty. No
curve was deferred and none failed.

** The order is a plan, not a role sort

=curve_build_planner= (=ores.marketdata.core=) orders a set of artefacts by the
inputs each one declares, and states the nodes no input allows: an input the set
does not hold, or one that is itself held out. Its three parts are pure, so order,
missing inputs and cycles are decided without a database.

The sweep builds its nodes from the configs it reads -- a projection declares the
funding config it discounts off -- and visits the plan's levels in order. A node
no level holds is deferred unvisited, and a cyclic set is refused rather than
retried, naming the curves. The plan and the outcomes are
[[id:12FEEA51-92A0-45C1-A9DA-67C7DB670C2C][Market Data Build Order]].

** A deferred curve is not a failure

=curve_republish_service= returns a =curve_deferral= rather than throwing when a
pillar has no quote or the funding curve has published nothing: the build did not
start, so the curve keeps the set it had, and the next firing tries again. The
publish path answers in the same words -- published, raised, deferred, refused,
failed -- so the sweep reports a curve's fate without restating it, and counts the
three outcomes apart.

On the fresh database, before any quote existed, a firing reported =published 0 of
30 curve(s): deferred 30, failed 0=. Before this change the ten projections failed
in the pass that published their funding curves, and the log could not tell that
ordering from a break.

** A projection reads its funding curve from that curve's reference date

The funding curves' first pillar is a three month deposit; every IBOR ladder starts
with a one month deposit. The engine refuses a discount curve that does not span a
pillar's dates, and a stored set leaves out its own reference date, where the
discount factor is one. The projection now anchors the funding curve it reads at
the as-of before the engine judges coverage
(=curve_republish_service.cpp=). Without the anchor the ten projections deferred
with =discount_curve does not cover pillar '1M'=; with it they publish.

** What the quotes were, and what is still provisioning's

This environment was recreated and not provisioned. Nothing the installation
publishes was there: the adapter and supplier catalogues are DQ datasets of the
=system_core= bundle, and the =system_provision= step of the provisioning run is
what publishes them into the system tenant. A bare database therefore knows no
adapter, refuses every announce, and demands nothing from any feed. Provider terms
are not the cause: the simulated vendors carry no terms at all (=ice=, =tradeweb=,
=bloomberg=, =lseg=, =demo=, =composite=), and the terms a person must accept
belong to the public single-source providers (=boe=, =ecb=, =nyfed= and the rest).

The bring-up is =compass shell -f
how_do_i_provision_the_system_with_acme_corporation_holding_group.ores=, which runs
=system_provision= and then the tenant's own steps. It did not run after the
recreate, and =compass db status= says so: =bootstrap mode true -- system
provisioning wizard not yet run=.

Publishing the catalogues by hand -- =marketdata.adapters=, =marketdata.suppliers=,
=synthetic.market_data_providers= and the synthetic feeds datasets -- got the
adapters as far as announcing and being accepted, and the environment stops there:
the synthetic service does not answer the market data service's demand subjects
inside the supervisor's two second wait, so no feed starts and no quote series
holds an observation. That is
[[id:6A8F01EC-54BE-4730-B7EC-8CF6438A6725][Start the synthetic service on a fresh database]],
which is in flight elsewhere.

So that this task's own chain could be proved, the live run seeded one flat quote
per pillar directly: 210 observations, =source = 'provisioning hack: flat quote'=.
They are not the feeds' work and stand in for it. Deleting them
(=delete from ores_marketdata_market_observations_tbl where source = 'provisioning
hack: flat quote'=) returns the environment to the feeds, after which the curves
defer until the synthetic service serves them.

** The party copies, and what provisioning needed

The system tenant's thirty curves are not the whole story: a party bootstraps its own copy of
each, from the quotes its own subscriptions deliver, and the first full provisioning run found
two things wrong with that copy.

- *Every party was on the wrong feeds.* The =acme_demo= profile subscribed each entity to
  Bloomberg, the uniform demo collection, LSEG and the derived FX volatility source -- none of
  them to ICE or Tradeweb, whose feeds quote the IBOR ladders. A curve reads the quotes of its
  own party, so every party's IBOR curves waited with =no series of ice ...= and never
  published. The profile now subscribes every entity to both.
- *The copies were written in name order.* The store checks a projection's discount curve as
  each row lands, and the batch named =USD-LIBOR-1M= before =USD-SOFR-FOMC=, so the party's
  whole copy was refused with =Must reference an active FUNDING config=. The plan now sorts its
  batch so each config follows the one it names (commit =893acad5d7=), which the schema's
  funding-only rule makes a two-pass sort.

After both, a clean =compass db recreate -y -k= and the documented bring-up published twenty
funding curves and the ten IBOR curves for each of the four entities, plus the system tenant's
thirty: =select curve_family_role, count(*) ...= answers 20 and 10 per party, every projection
with a live publish.

The bring-up still stops one step later, at =publish_party_surfaces=, on a defect of the
volatility surfaces rather than of the curves: =expiry 1W: the row dated 2026-11-17 is before
the spot date 2026-11-18=, forty surfaces across the four parties. The feed's spot and the
calibration's spot differ by one business day, which belongs to
[[id:95541791-E25C-44A5-9625-C8A1E44976D7][Support volatility surfaces -- the remaining work]].

** After the review

The first review round found one fault that changes behaviour and a set of
smaller ones. The fault: the engine's "the funding curve does not cover this
pillar" was turned into a deferral, so a projection whose funding curve had
published and could still not span it waited for ever, and the sweep reported
success because nothing failed. It is now thrown, with both curves named, which
is what the sweep counts as a break; a projection whose ladder reaches past its
funding curve has a test of its own, with every pillar quoted so nothing else
can be the reason.

The rest were cheap: two =contains()= calls, fifteen test cases that now name
their suite and log what they assert, the map a firing reads its curves through
aliased, and a party batch that no longer ends with a silent append of what it
could not order -- the drop pass above already removed those and named them.

Three findings were declined with reasons, and they are in the review table
above: the status string is a protocol field rather than a local type, the
anchor date is consistent with how a stored set is re-dated on read, and a
cyclic configuration cannot be expressed at all, because the schema refuses a
projection that discounts off another projection.

After the fixes, =ores.iam.core.tests=, =ores.marketdata.core.tests= and
=ores.marketdata.service.tests= pass. The sweep's own suite failed once under
three suites in parallel, on
=app_feed_ingest_loop_tests.cpp:1325= (=writer->held() >= 1=), and passes
alone: it is a timing check in the ingest loop, untouched here.
