* Goal

A system administrator removes a tenant from the tenant list or the tenant's
own screen, and the confirmation says exactly what removal does.

*Depends on server work that does not exist yet.* The prototype's *Remove
tenant* has no server behind it:

- =ores_iam_terminate_tenant_fn= marks a tenant terminated and keeps its data,
  but only the test database manager calls it. No bus operation and no web
  route reach it.
- Whether sign-in refuses a terminated tenant, and whether token refresh does,
  is not yet known. Until it is, the prototype's wording (everyone signed out,
  no more sign-ins) is an assumption.

So this task starts with the server: a bus operation over the terminate
function, held to =iam::tenants:delete= or the code the permission seeds name,
and a check of what sign-in and refresh do for a terminated tenant.

* Acceptance

- A bus operation terminates a tenant, refuses the system tenant, and needs a
  permission only the system administrator holds.
- Sign-in to a terminated tenant is refused, and the behaviour of a session
  already open in it is known and stated.
- The tenant list and the tenant's screen offer *Remove tenant*; the dialog
  asks for the tenant's code and says what removal does, in words that match
  the server's behaviour.
- Tests prove the refusal of the system tenant, the permission and the
  refused sign-in, and the dialog is read against the running deployment.

* Plan

- What the server already does, read in the code: =iam.v1.tenants.delete=
  checks =iam::tenants:delete=, and the delete rule closes the tenant's row
  and marks it =terminated=, keeping its data. The table's check keeps the
  system tenant =active=, so its removal fails. Sign-in reads the account's
  tenant and refuses one that is removed or not active. Token refresh read no
  tenant at all, so a person already signed in kept renewing their access.
- So no new bus operation is needed. The server change is one guard: refresh
  refuses a token whose tenant sign-in would refuse, so access ends within one
  access lifetime.
- The BFF adds =DELETE /api/tenants/:code=, which checks the typed code against
  the address and refuses the system tenant before it asks the server.
- The web replaces the roster's not-built *Retire or reset* entry with *Remove
  tenant*, adds the same button to the tenant's screen, and asks through one
  dialog whose words match the server.

* Result

A system administrator can remove a tenant.

- *Server.* Token refresh now refuses a token whose tenant is removed or not
  active, the same tenants sign-in refuses. A person signed in to a removed
  tenant loses access within one access lifetime. Removing the system tenant
  is refused by the table's check, and a repository test proves the row stays
  active.
- *BFF.* =DELETE /api/tenants/:code= checks the typed code, refuses the system
  tenant with a reason, and removes through =iam.v1.tenants.delete=.
- *Web.* *Remove tenant* sits in each roster row's menu, except the system
  tenant's, and on the tenant's screen. The dialog says that nobody can sign
  in, that people already signed in lose access within the session's access
  lifetime in minutes, and that the data is kept. It asks for the code before
  the button works.
- *Clean-up.* The leftover =tenant-session-ended= error code and its handler
  from the enter-and-leave design are gone.

Checks: BFF 142, web 235 and protocol 70 tests pass; the C++ change and its
tests compile. The C++ tests did not run locally, because the deployment's
database predates SQL merged by another environment, and recreating it would
delete the user's accounts and tenants. They run once the user agrees to the
recreate.
