* Notes

Split out of [[id:2A061FF5-B1A6-4F4C-A898-9F17EFA13146][Search the convention
list, validate its terms, and return its draft history]]. That task's fifth unit
-- the sub-periods coupon type list -- shipped on its own, because it is a
single new lookup entity and the other four are four different kinds of change.

Reconnaissance at =2a0c6342f0= (trunk), before any of the four was started.

*The family mapping is data the journey already writes out.* The table under
/Choose the instrument/ in
=doc/knowledge/journeys/conventions/journey_define_the_conventions_for_an_instrument.org=
already lists 28 rows of =| Family on the picker | Convention entity | Subject
prefix |=, so the rows a server-side list would carry are known. What is missing
is a refdata entity to hold them. Decide whether the list is one entity
(=(family, entity, subject_prefix)=) or whether the family is derivable from
something already in the tree; no =instrument_family= concept was found.

*The term filter needs a codegen decision before it needs code.* A generated
=list= today derives =id_one_of= and, for a column a model marked =:list_by:= or
=:list_by_uuid:=, a =list_by_<column>= subject and a =<column>_one_of= filter.
The journey wants a convention reachable "by an index, a calendar or a day
count", and those are plain text term columns with no such marking. So the first
question is whether the filter is a per-column opt-in of the existing kind, or a
single free-text term filter over all of them, and the answer changes every
convention's protocol. Decide that before editing 29 models.

*The term validation is feasible but must be verified column by column.* A census
of the text columns across the convention models, by name:

| column name | count | lookup it should name |
|-------------+-------+-----------------------|
| index, short_index, long_index, spread_index | 13 | floating_index_types |
| day_count_fraction, fixed_day_count_fraction, short_fixed_day_count_fraction | 12 | day_count_fraction_types |
| calendar, fixing_calendar, fixed_calendar, settlement_calendar, advance_calendar, tenor_calendar, spot_calendar | 18 | calendar_names |
| business_day_convention, fixed_convention, short_fixed_convention, fixed_payment_convention, roll_convention, start_delay_convention | 15 | business_day_convention_types |
| fixed_frequency, frequency, short_fixed_frequency | 11 | payment_frequencies |
| sub_periods_coupon_type | 2 | sub_periods_coupon_types |
| pair_code | 2 | currency_pairs |

That is a name-to-validator map, so the work can be a codemod rather than 29
hand edits. Two cautions. First, the validators exist
(=ores_refdata_validate_floating_index_type_fn= and
=ores_refdata_validate_payment_frequency_fn= both read their own lookup table),
but the ones checked at a glance for =calendar=, =business_day_convention_type=
and =day_count_fraction_type= did not resolve to a =from ores_refdata_..._tbl=
line with the same grep, so confirm what each reads before wiring it -- the
=calendar= column names a =calendar_name=, and a validator that reads
=ores_refdata_calendars_tbl= would be the wrong check. Second, only 3 of the 29
convention models carry an =* Insert trigger ** Validations= table today, so the
codemod has to add the section as well as the rows.

*The draft history version needs its premise tested first.* The journey says
=refdata.v1.history.get= "returns saved versions only", so the history view is a
post-write view. That is not quite what the tree does:
=projects/ores.history/api/include/ores.history.api/service/version_builder.hpp=
builds one =entity_history_version= per row the repository returns, and the
repository's =read_all(id)= is newest-first, so the reply already carries the
current row as its first entry. If the journey's *now* row is the record as it
stands, the server provides it. If it is the *unsaved* form state, no server can,
because the values are only ever in the browser. Read the prototype at
=doc/prototypes/conventions/= and settle which of the two the screen means before
writing any code; the answer may be that this unit is dropped rather than built.
