#+title: An append-only table cannot put the tenant first in its primary key
#+description: A tenant-scoped current-state entity gets 'primary key (id)', so the schema validator warns TENANT_002; only a read-only model draws a tenant-first key.
#+type: capture
#+level: cross

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Give a tenant-scoped, append-only entity whose key is natural — not a surrogate
uuid — a way to put =tenant_id= in its primary key. The table template draws
such a key from =immutable_tenant_key=, and nothing sets that flag, so only a
=read_only= model reaches a tenant-first key.

The case that surfaced it, =ores.vault.secret_use=, turned out not to need the
flag: its key is one generated uuid, which is unique across every tenant, and
TENANT_002 now recognises that shape and stays silent for it. A natural-key
counter such as =ores_marketdata_delivery_counts_tbl= is the case that remains,
and so is the composite-key case.

* Why

The SQL template draws a tenant-first key from =immutable_tenant_key=, and
nothing sets that flag: the only tables that carry =primary key (tenant_id,
id)= are =read_only= models, so the flag is derived from read-only rather than
from the question "is this row one tenant's".

The validator's rule was narrowed on 2026-11-26 so that a key of one generated
uuid is not asked for the tenant: such a key cannot collide across tenants, and
the rule is about natural keys that can (see =_pk_is_one_surrogate_uuid= in
=plantuml_er_parse_sql.py=, with its cases beside the other validator tests). A
natural-key or composite-key append-only table still has no way to state a
tenant-first key, which is what this capture asks for.

=ores_marketdata_delivery_counts= is the natural-key case that keeps the
validation job red today; it belongs to its own environment.
