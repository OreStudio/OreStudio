* Acceptance

- Account credentials live in their own entity with their own read and write codes.
- A profile update cannot clear a credential, because it cannot reach it.
- No credential column travels on the wire.
- The credential entity is projected across the whole stack, exactly as the account is: SQL schema, domain type, repository, protocol, handler, sub-registrar, CRUD service, history provider, presentation, shell command, HTTP route, eventing, notify trigger, and the TypeScript twins. The secrets stay off the wire because the columns are =:no_wire:=, not because the entity has no wire surface.

* Plan

=ores.iam.account= stops carrying the secret material, and a new entity
=ores.iam.account_credential= carries it, one row per account, keyed by
=account_id=.

The account model keeps every column it declares, so a whole-row write
through it is lossless and cannot reach a credential, because there is none
on the row. The credential model declares =password_hash=,
=service_password_hash= and =totp_secret=, all =:no_wire:=, and drops
=password_salt= outright: the stored hash embeds its own salt, nothing ever
read the column, and every writer wrote it empty.

The credential entity is projected across the whole stack, exactly as the
account is: SQL schema and notify trigger, domain type, repository,
generator, protocol, NATS handler and sub-registrar, generated CRUD service,
history provider, presentation mapper, shell command, HTTP route, eventing,
and the TypeScript twins.

Two flags carry the design, and neither is an exception:

- =:read_only: true=, the same flag the account entity sets. It suppresses
  the generated client-facing write verbs and leaves the reads
  (=iam.v1.account_credentials.list=, =.get=, the version reads) plus the
  repository's own =write=. A generated update is deliberately absent: it
  would deserialise a record whose =:no_wire:= secrets were skipped, and
  replace the row whole, which is the blanking bug this task exists to kill.
- =:no_wire:= on =password_hash=, =service_password_hash= and =totp_secret=.
  This is the estate's own mechanism for putting an entity on the wire while
  keeping a value off it, and it is what makes the reads safe: the record
  carries id, account_id, version and audit, and no secret.

The write cases are hand-written service methods over
=account_credential_repository::write=, because a write is the one thing a
generated verb cannot do here:

- Change own password: read the credential, prove the current password
  against =password_hash=, write the new hash. Session-owned, no code.
- Administrator reset: read the credential, write the new hash. Gated by
  =iam::accounts:reset_password= and =iam::account_credentials:write=.
- TOTP enrolment, verification and disable, and service-credential rotation.

TOTP enrolment is the one case where a secret must leave the server, because
the person has to scan it. It cannot be a field of the credential record,
since =:no_wire:= skips the member in both directions. It is therefore its
own operation message with a purpose-built field, exactly as =password=
travels inward on =save_account_request= today. Codegen does not supply it;
it is hand-written like the password path.

The repository gives =read_latest_by_account_id= (the FK declares
=:list_by:=) and the generated =write=, so the service resolves an account
by username and then its credential by account id.
=check_service_credentials= leaves the account repository and becomes
=account_operations_service::verify_service_credentials=, which reads both,
refuses a user account, refuses an empty or absent hash with a log line that
says it is a data fault, and compares the SHA-256 of the supplied password.

=create_account=, =create_service_account=, =signup_service=,
=reset_password= and =change_password= write the credential repository
instead of the account. =reset_password= no longer writes the account row at
all: a password change is a credential change, and the profile history must
not record one.

The hand-written SQL follows: the system provisioner and the service-account
seed write a credential row, the seed repairs an account whose credential row
is missing, and the DQ publish moves the staged hash into the credential row.

=iam::account_credentials:write= joins the permission catalogue and gates
=iam.v1.accounts.reset-password= beside =iam::accounts:reset_password=, so a
role that may edit a profile cannot thereby change what an account signs in
with. =iam::account_credentials:read= joins it as the code the generated
reads check, which is what the resource's read pair means once the entity is
projected: an administrator may ask which accounts hold a credential and when
it changed, and may not see one. =save_account_request= loses =totp_secret=,
the last credential field on the account protocol.

* Open decision

Where the credential writes are addressed from. Either they stay on
=iam.v1.accounts.*=, which is where =change-password= and =reset-password=
already are, gated by the credential codes; or the resource takes its own
verbs, =iam.v1.account_credentials.*=, and the credential concerns leave the
account namespace entirely, =save_account_request.password= among them. The
second is the truer reading of "the resource owns its codes and its verbs",
and it moves the web and shell callers with it. The modelling above is the
same either way; only the subjects move.

* Delivered so far

=ores.iam.account_credential= exists and holds the secret material, one row per
account. =ores_iam_accounts_tbl= carries no credential column, so a write through
the account cannot reach one: measured live, a profile write through
=PUT /api/accounts/<username>/profile= took the IAM service account to version 2
while its credential row kept its own id, version and =service_password_hash=. The
same write used to set that hash to NULL. This is the part PR #2721 landed, and it
holds whatever the entity's facet set becomes.

=password_salt= is gone: the stored hash embeds its own salt and nothing read the
column.

A nullable =:no_wire:= column exposed a codegen defect: the mapper emitted
=v.secret_hash.empty()= against an =rfl::Skip=, which declares no member
functions. The mapper template now branches on =:no_wire:= and reads the wrapped
value, with a regression test in =test_no_wire_columns.py=.

=account_type= and =account_status= stay on the account. They are not secrets, and
they round-trip through the generated domain type, which is the property whose
absence caused the lost hash.

* Not done, and why

The entity was modelled as internal, with a Physical space table withdrawing every
wire facet. The reasoning was that "no credential column travels on the wire" is
best served by having no wire surface, and that the account verbs already own the
writes. The first is wrong: the estate already answers that question with
=:no_wire:=, which exists to put an entity on the wire with a value kept off it, so
withdrawing the facets sidesteps the mechanism instead of using it. The second is
an argument for =:read_only:=, the flag the account entity itself sets, not for a
bespoke shape. The third reason, that only the data layer was needed, stopped
being true as soon as anyone asked the roster which accounts hold a credential and
when it changed. There is no =iam::account_credentials:read= code today because the
read path was removed first, which is circular.

The correction is in the Plan above. It is a facet and wiring change, not a
redesign: the columns, the table, the repository, the service writes and the SQL
all stay as they are.
