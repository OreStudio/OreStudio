* Result

The schema setup is re-runnable, and the class is gated rather than the instance.

*What was wrong.* Two classes, and only the first was the one the leftover named.

- One hand-written file used =create trigger= instead of =create or replace
  trigger=. It is the only statement of its kind in the tree.
- The populate phase could not run twice at all. Its scripts state version zero,
  and the version gate refuses a create that meets a live row, so 53 files
  stopped on the first row the first run had written.

*The fix.* The create side takes the OR REPLACE spelling the generator already
uses. The populate side declares itself a reseed: =foundation_populate.sql= and
=populate.sql= each run their body in one transaction that opens the replace
gate with =ores_utility_allow_version_replace_fn()=. That is the mechanism the
gate documents for exactly this caller, so one change closes all 53 files
without touching any of them. A re-run therefore re-asserts each seeded row at a
new version rather than skipping it: the data converges, and the version history
records the re-assertion.

*The gate.* =check_sql_hygiene.py= gained a third check: DDL that a second run
cannot repeat. It reports a =create trigger= with no =or replace=, a =create
policy= with no preceding =drop policy if exists=, a =create table= with no =if
not exists=, and the same for views, functions, sequences, types and domains. It
searches text the lexer has masked, so a statement inside a comment or a
function body is not mistaken for one the server runs. It reports 0 problems
over the 1538 files of =projects/ores.sql=, and it fails on a fixture that
carries one of each defect.

*Verified.* =compass db recreate -y -k= completed, and a second
=setup_schema.sql= run over that database then completed with =ON_ERROR_STOP on=
and no error lines. The populate summary reported the reseed.

*Left over.* The raw shell surface and the reporting defect this work exposed
are separate: the first is the story's other task, and the second is captured as
