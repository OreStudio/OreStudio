#+title: ores.vault.secret
#+description: Codegen entity model for the vault secrets table: a secret a tenant keeps, sealed under a key version and bound to its row.
#+type: ores.codegen.entity
#+component: vault
#+filetags: :model:entity:vault:secrets:
#+entity_singular: secret
#+entity_plural: secrets
#+entity_title: Secret
#+brief: A secret a tenant keeps, sealed under a key version.
#+created: 2026-11-26
#+updated: 2026-11-26

A secret one tenant keeps, sealed under a key that lives outside the database.
The row holds the sealed value and the version of the key that sealed it, and
the value is bound to the row it sits in, so a ciphertext copied into another
row, another tenant or another version does not open.

The plaintext is never a column and never a wire field. A consumer asks for the
value by name, and the answer leaves sealed to that consumer's own key, so the
value exists in the clear only inside the process that must use it.

The sealed value itself is on the generated wire surfaces, because the sealed box
hands over one opaque string and the codec carries it as one. That is the
baseline and not the contract: =describe= answers the metadata alone, and only
the write request and the resolve reply carry a sealed value.

Two invariants decide the shape. A tenant keeps a secret once by its =name=,
which is the natural key: the name is what a consumer asks for and what the
audit records, so a tenant cannot hold two secrets that answer one ask. And the
=owner= names the consumer permitted to resolve it, by the actor its token
carries, which is a fact about the row and not about the caller: the vault answers a resolve with the owner's key,
and a row with no owner is a row nobody may read.

** name
:PROPERTIES:
:type:         text
:cpp_type:     std::string
:natural_key:  true
:sortable:     true
:searchable:   true
:END:

The name a consumer asks for, such as =identity_provider.google.client_secret=,
unique within the tenant. It is the name the audit records and the name a
rotation reports, so it is stable and a person rarely types it.

#+begin_src cpp :name generator
std::string("identity_provider.google.client_secret")
#+end_src

** owner
:PROPERTIES:
:type:         text
:cpp_type:     std::string
:sortable:     true
:searchable:   true
:END:

The consumer permitted to resolve this secret, named by the actor its token
carries, such as =http@system.ores=. The vault seals a resolve to the public key
registered for the subject that actor's token carries, so the owner is what
decides who can open the answer. Naming the actor rather than the subject lets a
person write a secret for a service, whose subject changes with the process that
registers, without knowing which process answers.

#+begin_src cpp :name generator
std::string("http@system.ores")
#+end_src

** sealed_value
:PROPERTIES:
:type:     text
:cpp_type: std::string
:END:

The sealed value: one Base64 string carrying the nonce, the tag and the
ciphertext, bound to this row's tenant, name, owner and key version. It is
opaque to every reader: a copy of it opens only under the key encryption key
the vault's process holds.

#+begin_src cpp :name generator
std::string("tw+/9+zJr9z55w001kE3JIKMVsxyInWcHcPlyHtFmyBG6qSRrDRcLG2")
#+end_src

** key_version
:PROPERTIES:
:type:     integer
:cpp_type: int
:END:

The version of the key encryption key that sealed this value. A rotation
re-wraps the value and moves this number, and a resolve uses the version to
choose the key it opens with, so a rotation never has to happen in one instant.

#+begin_src cpp :name generator
1
#+end_src

** description
:PROPERTIES:
:type:     text
:cpp_type: std::string
:nullable: true
:END:

What the secret is for, in a person's words, such as =The Google client's
secret=. Nothing reads it but a person, and it never repeats the value.

std::string("The provider client's secret")
#+end_src
