#+title: Story: Stop ores.shell menus from silently shadowing each other
#+description: Four shell menus are registered twice, and the CLI resolves a duplicate by registration order in repl.cpp, so the first unit to register a verb owns it. The generated iam units win for accounts list, roles list and roles get, permissions list, and tenants get, add and delete; the hand-written definitions of those seven verbs are unreachable. The help for a menu describes only the first unit, so the other unit's verbs are hidden although they still answer. The dq side of the same class is fixed in the generator, which no longer renders a shell-command unit for an artefact-staging-only entity.

* Goal

The shell has one owner per menu and per verb. A duplicate registration fails loudly at startup instead of being resolved silently by the order of the calls in repl.cpp, and the dead hand-written verbs are migrated or deleted.

* Acceptance

- No two shell command units register the same menu name, and a duplicate would fail at startup rather than be shadowed.
- The seven dead verbs are either migrated to the generated menus or deleted with the reason recorded.
- The shell's command surface is unchanged for every verb that currently answers.
- A menu's help lists every verb that answers at that address, including the ones another unit contributes.
