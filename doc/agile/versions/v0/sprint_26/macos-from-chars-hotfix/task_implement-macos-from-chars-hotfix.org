   affected suites.

* Notes

- The failing case in the full ore suite is
  =credit_simulation_roundtrip_through_the_database=, which needs
  =ores_analytics_credit_simulation_configs_tbl=. The tree creates that
  table and wires it into =analytics_create.sql=, so the failure is this
  worktree's database rather than the tree: the database was recreated
  before the SQL landed. The database is recreated and the suite re-run;
  the result is recorded here once it is known.
- The scope is exactly one call site. The two other =from_chars= uses
  parse integers (a date field and a list-page limit) and libc++
  implements those, so they stay. The floating-point =to_chars= calls --
  one in the same mapper, one in the bond mapper, one in the refdata rate
  formatter -- also stay, on three pieces of evidence: the macOS compiler
  reported no error on the one in the same translation unit as the
  failure, the refdata rate formatter is older than the failure and the
  macOS job completed its build on 2026-09-25 (it failed in the tests),
  and libc++ implements the floating-point =to_chars= while the
  floating-point =from_chars= only arrived in libc++ 20, which Xcode
  16.2's libc++ 19 predates.
- The shim's implementation decision is tested rather than assumed.
  =strtod= would have been shorter, but it follows =LC_NUMERIC= and skips
  leading whitespace, and the standard overload does neither; the tests
  pin both. Boost's lexical cast is library code the estate already
  depends on, so the shim adds no dependency.
- Recreating the database on this worktree needed =compass env configure=
  first: the tree moved the environment format to version 26 and the
  worktree's =.env= was at 25. That is per-worktree state, not a tree
  defect, and it is worth knowing before the next recreate.

* Result

=ores.platform= gains =numeric/floating_point.hpp= and its umbrella, and
the credit simulation mapper reads its transition-matrix bounds through
=ores::platform::numeric::parse_double= instead of the floating-point
=std::from_chars= that libc++ deletes. The mapper's behaviour and its
error message are unchanged.

Verified: the shim's 5 cases and 43 assertions pass, including the round
trip against the floating-point =to_chars= the estate formats with; the
credit mapper's 14 cases and 63 assertions pass; and no floating-point
=from_chars= remains in the estate.
