* Goal

book_purpose_type and ledger_feed_type became non-nullable on the book, the artefact that feeds it, and the trigger that validates it. The publish function that reads the artefact and writes the book was not updated, so it inserts neither: every tenant setup fails at its books step with 'missing_field: book_purpose_type' and no tenant can be provisioned.

* Acceptance

- A tenant setup publishes its books and completes.
- The books carry a purpose and a ledger feed.

* Plan

The failure names its own column, so the work is to find every writer of it
rather than to read the error again. That column arrived on three things at
once — the book, the artefact that feeds it, and the trigger that validates it
— and the loaders were brought to it while the publisher between them was not.

Reproduce by retrying the run that failed, which is the only path that reaches
the publisher, then hold the published table against the artefact to see
whether the values crossed.

* Result

A tenant can be provisioned again. The publisher reads book_purpose_type and
ledger_feed_type out of the artefact and writes them on, so the trigger that
validates them has something to validate, and the tenant setup walks its steps
instead of failing at the third.

Three changes in a row moved the same two columns across three tables and each
one left the next reader behind: the columns went onto the book, the loaders
learnt to write the artefact, and nobody told the publisher that reads it. The
lesson is not that the publisher was missed. It is that nothing compares a
publish function's INSERT list against the table it writes — the same gap a
loader census would close, and the third defect this session that a check
looking at column lists would have caught.

The error also reaches the browser as the whole PL/pgSQL body, several hundred
words of it, laid out in the step panel. That is a presentation defect of its
own and is not fixed here.
