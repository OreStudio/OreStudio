* Goal

The owner's testing after the vendor view task found four places where the
latent provider and the vendor views do not behave like every other feed. The
dashboard gives Latent no Start, no Stop and no state; a latent surface's log
records no start or stop; and a view's page fails, because its record arrives
without its provider and its run state. This task makes each behave as every
feed does.

* Acceptance

- The dashboard's Latent row has Start and Stop, which stop and start its nodes, and a state: Serving when they all run, Stopped when all are stopped, and a count otherwise.
- A latent surface's log records its start, with the source that first holds it, and its stop, when its last holder releases it.
- A view's page opens through ores.http and through the BFF, with its provider and whether it runs.
- Tests cover each: the dashboard control fetches the whole graph, the shared surfaces say start and stop, and both servers' view reads carry the provider and the run.

* Plan

1. *The dashboard control.* =useFeedGraph= turns its query off for an empty
   node, the whole graph, so =ProviderNodeControl= never fetches and draws
   nothing. A whole-graph read is its own query. The control's tests placed
   graph data in the cache, which hid the off query; the new test lets the
   query run.
2. *The Latent state.* A provider with no simulated source takes its state from
   its nodes, the same nodes its Start and Stop act on.
3. *The latent journal.* =basic_shared_surfaces= starts a surface on its first
   attach and stops it on its last detach; it says both to the latent node's
   journal, naming the source.
4. *The view read.* =ores.http='s =feed_key_routes= and the BFF's =FEED_KEYS=
   read fx, IR and vol feeds with their provider and run; views join them.
