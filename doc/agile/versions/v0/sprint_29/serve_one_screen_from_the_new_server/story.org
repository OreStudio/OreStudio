* Decisions

*Parity first, screens after, and the BFF stays where it is.* Moving a screen first
would make the port a rewrite of the client and the server at once, and a failure
would have two possible causes. The browser keeps calling the BFF until every route it
needs has an equivalent, so each step is judged against a layer that already works.
The other reason is the sharper one: a request must never depend on both servers at
once. A screen split across them would carry two sessions, two cookie stores and two
answers to the same question, and a fault would be a fault in the seam rather than in
either side. Building the layer behind the BFF means no request ever crosses that seam
during the migration, and the cutover is one switch thrown once rather than a hundred
screens half moved.

*A cutover at parity is the shortest one there is.* If every route the browser uses is
already answered and proved by the new server, the removal is an act of configuration
and deletion rather than a second migration: the work left is the switch, the fleet
entry and the old unit, not a list of screens still to fix.

*One functionality per pull request, merged as it lands.* A pull request that closes a
feature and a pull request that removes the BFF are different kinds of change, so they
do not share one. The BFF's removal is a set of pull requests written after the
coverage is complete, against a layer that has nothing left to prove.

*Coverage is the route inventory, not a claim.* =doc/knowledge/architecture/http_route_inventory.org=
already lists every route both servers answer and the kind each one is. A resource the
C++ server does not answer is a row the table shows as the BFF's, so progress is read
from the table rather than from a story saying it is done.
