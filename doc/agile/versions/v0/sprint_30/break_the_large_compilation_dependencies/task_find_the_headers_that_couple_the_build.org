* Goal

The story knows one header that couples the build, the database context. It does not know the others, or how much each costs. This task analyses the include graph and produces the list of headers to change, with one decision for each type in them. * Acceptance

- A script, kept with the task, reads the build's own dependency record (=ninja -t deps= on the release build) and reports, for each project header, the number of objects that depend on it. It reruns on any commit.
- The same report covers the third-party headers that project headers pull in, such as =libpq-fe.h=, =<mutex>=, =<condition_variable>=, Boost.Asio, Boost.Log and the codec libraries, and names the project header that brings each in.
- For each header above a threshold the task states, the analysis records:
  - what the header defines, and which of those types its includers only name (a parameter by reference or pointer, a return by pointer, a member behind a pointer) and which they use in full (a member by value, a call, a template argument, =sizeof=);
  - the chain of includes through which the heavy dependencies arrive;
  - one decision per type: forward-declare (with a =_fwd.hpp= where the type has a namespace or template parameters), move to a smaller header, split the type, hide the detail behind a pointer to an incomplete type, or keep with a reason.
- The analysis looks for include cycles and for headers that include another component's implementation detail, and lists each it finds.
- The analysis says which headers are generated by codegen and names the template to change for each, since a hand edit to generated code does not survive a regeneration.
- The analysis estimates the gain of each decision from its dependency counts, and orders the work by that gain. [[id:DEA440DD-F4B6-4D37-9083-5F3BB33F1018][Forward-declare what the analysis finds]] takes the list in that order.
- A clang =-ftime-trace= sample of a few typical objects confirms that the headers the counts rank highest are also the ones that cost the most parse time. Where the two disagree, the analysis says so and ranks by time.
- The result is an investigation in the story folder (=compass add investigation=), linked from the story.

* Plan

Two instruments, so that reach and cost are measured separately and neither is
argued:

1. =evidence/header_blast_radius.py= reads the build's own dependency record
   (=ninja -t deps=) and counts, for each header, the compile objects and
   targets that depend on it. It also scans the source text of every =#include=
   for the third-party attribution, the include chains, the cycles and the
   cross-component edges, and reads the =AUTO-GENERATED FILE= banner for the
   codegen template of each generated header.
2. =evidence/header_cost.py= parses one header with clang =-ftime-trace= and
   sums the exclusive time of each file, so a header that only includes others
   does not inherit their cost. It has four modes: =headers= for one header at a
   time, =tu= for one real translation unit, =sample= for a spread of units, and
   =compare= for an A/B on one include.

Then: rank by both, multiply the two into object-seconds, and order the work by
that product while respecting the chains, because removing a leaf before its
root measures the same time twice.

The two false starts and their fixes are recorded in the investigation's
* Paths taken, so the next reader does not repeat them.

* Notes

Started from the database context during the publish lifecycle work: changing =context.hpp= rebuilt most of the tree, and most includers only pass a context along. Candidates to check first, without numbers yet: the database context and the =pq= headers under it, the codec headers in =ores.utility/codec=, =ores.utility/domain/protocol.hpp=, the logging headers, and the NATS client and message headers.

Forward declaration is not free: a type named only by reference can still need its full definition where a default argument, an inline function body or a =std::vector= member uses it. The analysis records where this blocks a forward declaration.

* Result

The analysis is written and both instruments are kept with the task:
=evidence/header_blast_radius.py= and =evidence/header_cost.py=.

What it found:

- Reach and cost are different questions. The most widely included headers
  (=export.hpp=, =severity_level.hpp=, =wire_traits_fwd.hpp=) cost 0.02 to
  0.05 s. The costliest ones reach a third to a half of the build.
- The cost travels in three chains: the codec chain (=text_form.hpp= 4.99 s,
  =protocol_codec.hpp= 6.15 s, =decimal.hpp= 4.03 s), the clock chain
  (=<chrono>= through =datetime.hpp= and =boost/uuid/uuid.hpp=), and the
  logging chain (=make_logger.hpp= 3.87 s pulling Boost.Log's logger).
- The story's premise named =libpq-fe.h= as the reason =context.hpp= is
  expensive. It costs 0.04 s. The bulk is the codec chain behind
  =pq/transaction.hpp= and =<chrono>= behind =tenant_id.hpp=.
- One unused include in =tenant_id.hpp= costs 0.69 s on 837 objects and needs
  no design decision.
- No cycles and no cross-component detail includes, so no decision is blocked.
- Rebuild radius and parse cost are different measures. The forward
  declarations the story asked for reach only the types held by pointer or
  reference.
- The copies are systemic and come from the codegen templates: 11141 of 21874
  by-value =context= parameters. Changing them to =const&= is worth doing for run
  time, with one synchronous reference capture to re-check, but it does not
  shorten rebuilds: cutting the include from all 1738 repository headers saves
  one object.
- =context.hpp='s radius is structural. Cutting every header in the tree still
  leaves 179 of 365 objects reading it, because the =.cpp= files that construct
  a context need the definition. The only change that moves the radius is the
  split of the type, which needs its own task.
- A pointer is worth it for the stored member, for parse cost and not for
  rebuilds: at most 186 objects stop parsing a 6.6 s header and about 20 stop
  rebuilding. =shared_ptr=, a raw pointer and a pimpl all compile on a generated
  service header; they differ in ownership, and the raw pointer is the one that
  makes the code worse. The choice belongs to the split task.
- The decisions, the pattern table and the objects each cut saves are in the
  investigation's * Rebuild blast radius and * Order of work.

The decisions and the order of work are in the investigation's * Decisions and
* Order of work, in two lists because the story has two objectives. For rebuild
cycles the first change is the database family: =context.hpp= stops including
=pq/pool.hpp= and =pq/transaction.hpp= and takes the two options types from a
small header. For parse cost the first change is the codec chain: =text_form.hpp=
moved out of line, then =protocol_codec.hpp= and =json_codec.hpp=.
