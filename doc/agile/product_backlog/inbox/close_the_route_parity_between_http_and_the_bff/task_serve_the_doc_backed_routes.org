* Goal

Serve the twelve routes the BFF answered from the checkout's doc tree, so the QA
scenarios and the agile browser keep working when the BFF goes. The routes are
=GET /api/qa/scenarios=, =GET /api/qa/scenarios/:id=, =GET /api/qa/docs/:id=,
=PUT /api/qa/scenarios/:id/run=, =POST /api/qa/scenarios/:id/steps/:step/images=,
=GET /api/qa/scenarios/:id/files/:name=, and the six =/api/agile/*= reads.

The earlier decision left these out because they read and write the checkout and
a deployed gateway holds none. That left the QA and agile screens with no home
once the BFF goes, and a QA run is how the product is proved in a browser, so
they have to be served.

They are not served from the checkout. The knowledge base story moves the org
pages into PostgreSQL and serves them through a knowledge service, so these
routes read the docs where they then live, and a run writes back through the
same service. The addresses and shapes stay the BFF's.

* Acceptance

- The twelve routes answer the same shapes the BFF answered, at the same addresses.
- The docs are read and written through the service that holds them, not from the checkout.
- An id that is not a document id is refused rather than used as a path.
- The org docs are parsed by =ores.orgmode=, so the two servers read the format through one parser.
- A scenario run writes its outcomes back through the page write at the version it read, and the next read sees them.
- A screenshot is served back as an image and nothing else in the scenario's folder is.
- The inventory pairs the twelve routes and the local gate is green.

* Plan

The routes are served over the database read, not from the checkout. The gateway
asks the knowledge service for a page by its org id, parses the text with
=ores.orgmode=, and answers the shape the BFF answered. The service holds pages
and nothing about steps or sprints: a scenario's shape and an agile tree's shape
are this part's reading of the text, which is also what makes them testable
without a database.

The units:

1. The scenario reads: =GET /api/qa/scenarios= reads the pages of the scenario
   kind and answers one summary per page, =.../:id= one page parsed whole, and
   =GET /api/qa/docs/:id= any page of a served type, its text as it stands.
2. The run write: =PUT /api/qa/scenarios/:id/run= writes the outcomes it names
   into the page's =Result= tables with =ores.orgmode= and puts the page back
   through [[id:7C83579B-4DA3-4EF8-BF5B-33E97C2E3874][Write an org page back through the service]],
   at the version it read. The scenario's verdict follows from the steps: it
   closes when none is pending, failed if any failed, passed otherwise.
3. The images: =POST .../steps/:step/images= writes the screenshot to object
   storage under the scenario and the step, and =GET .../files/:name= reads it
   back by its bytes, serving only a PNG, JPEG, GIF or WebP. Keeping the address
   means the doc's own links and the web client need no change.
4. The agile reads: the six =/api/agile/*= routes read the pages of the agile
   kinds and derive the sprints, the board, the charts, the backlog and one doc
   by id. The work trees are the repository's own and are answered empty until a
   repository is stated beside the service, which is what the BFF answered
   without one.

The twelve pair in the inventory as they are served, and the gate covers the
part's parsing with org strings, so a format change fails a test rather than a
screen.

* Notes

- Delayed on 2026-11-22, before any code was written, then planned over the
  database read the same day. The first plan read the checkout's doc tree, which
  is what the BFF does; that is the wrong target, because the knowledge base
  story loads the org pages into PostgreSQL and serves them through a service. A
  port of the file reading would be deleted the day the load lands.
- Two things the knowledge base story must state for this to work, both agreed
  on 2026-11-22: the loader takes every doc that has an =:ID:= and a =#+title:=,
  not only the user-facing pages, and the service states a page write, which is
  [[id:7C83579B-4DA3-4EF8-BF5B-33E97C2E3874][Write an org page back through the service]].
- The consequence for the switch: the QA and the agile screens stay on the BFF
  until this task lands. Every other screen can move, so the BFF outlives the
  switch and is retired after this task.
- The BFF's own file reading is not kept as a fallback. A deployment states no
  doc root any more, so there is one way to read a doc and not two.
