* Goal

The export carries each trade's instrument as a typed array, not as an encoded
payload. =export_portfolio_response= holds one array per instrument entity and
one per child table, every element keyed by its trade id, all of it generated
from the trade-type catalogue. =instrument_payload= and its codec are deleted.

* Acceptance

- =instrument_payload=, its codec and its test are deleted. No message in
  ores.trading declares a =std::variant= field or a =std::string= field that
  holds an encoded value.
- =export_portfolio_response= carries =instrument_batch=: one typed array per
  routed instrument entity and per child table, every element keyed by its
  trade id, beside the trade anchors.
- The batch type, its =append= overloads, =find=, =find_all=, =merge= and its
  TypeScript twin are generated from =ores.trading.trade_type_catalogue=, not
  hand-written. Every batch member is a generated type.
- The producer appends typed rows and the exporter rebuilds the in-memory
  instrument by trade id, so the exporter's dispatch is unchanged.
- The polymorphic-payload page records that the pattern is removed, not merely
  deprecated.

* Plan

1. =ores.trading.trade_type_catalogue= gains a =* Batch= section: the child
   tables the export carries, and an instrument-type table for the one family
   whose document shape is a container over its rows (bond crosses as
   =bond_instrument_data=). The loader turns that into the member list, deriving
   each member's name from the entity's declared plural and each TypeScript
   interface and module from its element type, and it refuses an override that
   names no routed instrument or a child that no model declares.
2. Two archetypes render the batch: =ores.cpp.trade_type.batch= emits
   =instrument_batch.hpp= with the arrays and the readers (=trade_id_of=,
   =append=, =find=, =find_all=, =merge=), and =ores.ts.trade_type.batch= emits
   the TypeScript twin from the same model.
3. A hand-written =instrument_batch_mapper= holds the two conversions between
   the batch and the in-memory carrier: =append_instrument= for the import path
   and the tests, and =rebuild_instrument= for the exporter.
4. The protocol model drops =trade_export_item.instrument= and adds
   =export_portfolio_response.instruments=. The storage export stores the
   response itself, so the blob carries the same two arrays a live caller
   receives.
5. The producer is rewritten to append typed rows straight into the page's
   batch: no intermediate map, no variant, and no per-trade pairing, because
   every row already carries its trade id.
6. =rpa_instrument= leaves =rates_instrument_variant=. No trade type routes to
   it since RPA became a credit product, so it could never be produced; the
   dead branch in the ORE import handler and the two stale references go with
   it.
7. The two test suites that built an export item from a payload now build a
   batch, and the payload's own test is deleted.

* Notes

- The batch is generated from the catalogue rather than from the entity facet
  list, because the catalogue already knows which table holds each trade type
  and the batch's membership follows the routing exactly: 29 instrument arrays
  for the 29 routed tables, plus the 7 child tables the export carries.
- =trade_id_of= reads the key shape a member has rather than each member
  carrying an accessor: a generated entity nests its key in an identity group,
  a document container holds the entity that does (=bond_instrument_data=), and
  a flat child states it directly. A model that gains or loses the group needs
  no change to the generated header.
- The producer never builds a variant. It pushes the typed rows each service
  returns straight into the page's batch, so the intermediate map, the copy per
  item and the phase that paired rows with items are all gone.
- The storage export stores the response itself rather than a vector of items,
  so the blob carries the same two arrays a live caller receives.
- =rpa_instrument= was removed from =rates_instrument_variant=: no trade type
  routes to it since RPA became a credit product, so no array could hold it and
  =append_instrument= would have had an arm it could only drop. What is left of
  the generated =rpa_instrument= entity (its table, service and protocol) is
  untouched and belongs to the recorded retirement capture.
- The regeneration also refreshed three eventing integration tests and one
  component file list that trunk had left stale: the templates render
  =event_subject_wildcard=, while the committed files still spelled the subject
  prefix out by hand. They are generated files, so the gate demands the
  regenerated form.

* Result

=instrument_payload=, its codec and its test are deleted. =export_portfolio_response=
carries =instrument_batch=: 36 generated arrays, one per routed instrument
entity and per child table, every element keyed by its trade id. The batch type,
its readers and its TypeScript twin are generated from the trade-type catalogue.
A trade's instrument is rebuilt by the exporter from the array its table names,
so its reverse-mapper dispatch is unchanged.

and this task's validation is static, as the current process asks.
