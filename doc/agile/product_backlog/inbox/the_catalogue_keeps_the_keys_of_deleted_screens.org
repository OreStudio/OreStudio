#+title: The i18n catalogue keeps the keys of the deleted screens
#+description: No check finds an unused key, so the words of the deleted entity screens sit in three catalogues and are translated forever.

#+level: cross

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

The English catalogue carries keys that no code reaches, because the screens
that used them are deleted. Measured on 2026-09-27 against the component's
sources, these name nothing:

- =home.quickActions=, =home.components=, =home.entities=, =home.planned=,
  =home.whatIs= and =home.greeting= — the deleted home screen and shortcut grid.
- =nav.site= and its neighbours — the deleted sidebar.
- =component.entities=, the =shortcut.*= keys, and the history, entity and
  dialog blocks that belonged to the generated entity screens.

The catalogue test does not see them. It compares the key *sets* of the three
languages, so a key present in all three passes whether or not anything reads
it.

* Why

Two costs, and the second is the one that compounds. A reader looking for the
words of a screen finds three other screens' words beside them, and cannot tell
which are live. And every language is translated against the source catalogue,
so deleting a screen does not delete its words: they are carried, reviewed and
translated again for as long as nobody looks.

The check is cheap and belongs with the catalogue test: for each key, search
the sources for the literal, and fail on a key that only the catalogue names.
It cannot be exact — a key built by interpolation, such as =password.rule.${rule}=,
never appears as a literal — so the check needs a declared allowance for the
dynamically built families, which is a list somebody can review.
