* Goal

Every component that moves bytes calls the storage interface rather than its own
copy of it, and the copies go. One HTTP client, one archiver and one set of key
builders remain in the tree, the shell's storage verbs are the raw surface rather
than five verbs named after their callers, and no consumer reaches storage
through a hand-rolled path, key or retry loop.

The buckets stay the consumers' business: each names its own, and nothing in
storage needs to learn the names for the migration to work.

- =ores.compute.wrapper= links the storage interface and its own HTTP client and
  archiver are deleted, including the download path that opens its destination
  before it reads the status.
- =ores.ore= and =ores.reporting= reach storage through the interface, and the
  =report-data= bucket name each of them duplicates lives in one place per
  component rather than in two anonymous namespaces.
- The shell exposes the raw surface — a bucket, a key and a local path — and the
  consumer verbs (=ore upload=, =compute publish-package=, =compute
  download-input=, =compute download-output=) are thin wrappers over it.
- The base URL is plumbed one way, not three, and no service defaults to a port
  the server does not listen on.
- A grep for a second Beast client, a second libarchive archiver or a hand-built
  storage path outside the component returns nothing.

* Result

* Result

The consumers write the platform protocol, and the database rebuilds on the path
to it.

**What it delivers**

- One bucket, =ores=, and a key of the form =service/purpose/id[/name]=, stated in
  [[id:286B7167-9B8A-4937-BBA5-E9D285AFECE3][Object Storage]] and built and parsed
  by =ores.storage.api/net/object_keys.hpp=. An id may carry dots, so a UUID plus
  its extension stays one segment; an empty segment, dot, dot dot and a space are
  refused, and a service never writes under another's segment.
- compute writes =compute/packages=, =input=, =config= and =output=, with the
  per-platform bundle keyed by app-version and named by its file, and a batch
  input key the shell used to hand-build. ore writes
  =ore/imports/{request_id}.tar.gz= and
  =ore/packages/{instance_id}/ore_package.tar.gz=. reporting writes
  =reporting/runs/{instance_id}/trades.msgpack= and =market_data.msgpack=, and the
  =report-data= literal both components kept is gone. The seeded compute package
  URIs move with them.
- The storage component's own fixtures speak the protocol, and the api suite
  covers the dotted id, the round trip, and the refusals.

**What is left**

- Three service handlers still build a transfer with no token, so their HTTP calls
  answer 401: =ores.ore/service/src/messaging/report_package_handler.cpp:81=,
  =ores.trading/core/include/ores.trading.core/messaging/trade_handler.hpp:365= and
  =ores.marketdata/core/include/ores.marketdata.core/messaging/market_series_handler.hpp:214=.
  Each needs the service's bearer threaded in the way the import handler got it:
  =nats_client::token()= on the service path. Everything else that moves bytes
  carries one -- the shell's four sites, the compute publisher, and the import
  handler.
- The raw shell surface -- a bucket, a key and a path -- is not built, so the
  consumer verbs remain the only way to reach storage from the shell.
- Two input-shape findings, neither about storage: an imported ORE tree whose book
  has no portfolio above it needs =--parent-portfolio-name=, and the MinimalSetup
  example has 20 swaptions refused by
  =ores_trading_swaption_instruments_tbl_long_short_check=.

**Evidence**

- Live, with the protocol keys and the new token chain:
  =compute publish-package ORE 1.8.17.0 x64-linux= uploaded
  =ores/compute/packages/ORE-1.8.17.0/ORE-1.8.17.0-x64-linux.tar.gz= and reported
  its sha256; the row's =package_uri= is that path and a HEAD answers 200.
  =ore upload external/ore/examples/MinimalSetup= reported
  =ores/ore/imports/<request_id>.tar.gz= and a HEAD answers 200. =ore import= then
  completed (completed_with_warnings) and saved 20 trades, having downloaded the
  tarball with the service's own token and permission.
- The authentication work that made those work: the HTTP boundary verifies the
  platform's RS256 session tokens (with the symmetric authenticator kept for the
  login token), =nats_client::token()= gives the service path a bearer,
  ReportingService, ComputeService, OreService and MarketdataService hold
  =storage::objects:read= and =write= (1008 role-permission assignments when the
  seed was reapplied), and =ore upload= captures the session.
- Suites: storage api and core, compute api and core, http api, ore api, core and
  service, shell storage and application.
- =check_component_drift.py --all= reports no drift, and the codegen unit suite is
  706 passed.
