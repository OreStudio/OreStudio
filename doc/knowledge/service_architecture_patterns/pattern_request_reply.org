This page defines the [[id:68FAC606-569C-4B9B-932B-3B3A0181AC8B][service architecture pattern]]
Request-Reply in the [[id:EA249899-6611-407F-A43A-B37019EBD1A7][pattern language]].
A requester sends a message and receives one reply on an address the
request names. In ORE Studio every service operation is a NATS request with a
private inbox as its reply address.

* Also known as

- /Request-response/.
- /Return Address/, the companion pattern in Hohpe and Woolf for the reply's destination.

* Context

Services talk over a message bus, not direct connections. A caller needs an
answer: data, a decision, or a refusal.

* Problem

How does a service ask another for an answer over a bus that only moves
one-way messages?

* Forces

- The bus delivers messages one way; a reply needs an address.
- The caller must not wait forever for an answer that may never come.
- A refusal must be told apart from an answer, or a client decodes an error as data.
- Several replicas serve one subject, and only one should answer.

* Solution

The requester creates a private inbox and sends the request with the inbox as its
reply address. One replica of the serving queue group receives it, acts, and
publishes one reply to the inbox. A refusal is a reply too: an empty body with an
=X-Error= header. The requester waits up to its timeout, reads =X-Error= first,
and only then decodes the body.

* Failure handling

#+ATTR_HTML: :class hug-leading
| Concern | What the pattern does |
|---------+-----------------------|
| Errors | A refusal is an =X-Error= reply: =unauthorized=, =forbidden=, =bad_request= or =token_expired=. A client reads the header before the body. |
| Timeouts | The requester waits at most its timeout; see [[id:1C419534-33BC-423E-8503-9D3945AF8648][Timeout]]. No reply does not prove the work was not done. |
| Retries | Only =token_expired= is retried, once, after a renewal; see [[id:93737023-4FB7-45CD-9511-9B27DBACB2FC][Retry]]. |
| Idempotency | A repeated request is a new delivery; the replier must tolerate it if the operation writes. |
| Observability | The subject, the correlation id and the outcome are logged on both sides. |

* Pitfalls

- *A refusal decoded as a body.* The client reports a decode error; the real cause is the =X-Error= header it did not read.
- *No subscriber.* A request to a subject nobody serves waits for its whole timeout and then fails, with nothing in any service's log.
- *A long operation behind a request.* Work that takes minutes holds the caller; it belongs in a workflow that answers at once with a run id.
- *A timeout read as "nothing happened".* The replier may have finished after the caller gave up.

* Security

The request carries the caller's token, and the replier authorises it on every
request. The inbox is private to the requester's connection, so another client
cannot read the reply.

* Resulting context

- Benefits :: A service call over the bus, with one answer and a clear refusal path.
- Liabilities :: The caller is blocked for the call's length, and a slow replier holds it.

* In ORE Studio

The curve construction, [[id:446F28DF-155A-47EC-8D66-FDB90A8FBFA7][Bootstrapping a curve: from quotes to a published set]], is a request-reply: the compute reads the quotes and answers the solved points.

The market data path, [[id:FDD02CA9-1DAD-4162-95AC-C7C5C611DDDC][a public fixing, a curve and a report]], is a chain of it: each hop calls a service and waits for the answer before the next.

The default timeout is 30 seconds, set once in =ores.nats/service/timeouts.hpp= for every overload.

- [[id:8ECCBD02-21F5-455C-B520-193E4631092F][Anatomy of a Service]] — every service operation is a request with an inbox; a refusal is an empty reply with =X-Error=.
- [[id:A47C612B-9CAB-4656-B4FC-E9DA1D414F83][Job actions]] — the request form of =nats_publish= waits for the trigger's acknowledgement.
- [[id:7D4D8598-555D-4E86-8006-3BC79E926382][How the compute grid queues and claims work]] — a node claims a job with a request and receives the assignment in the reply.
- [[id:E1A582A6-9E12-4074-877E-91ACD7E64301][The history call returns every tick of a range in one reply, or refuses the range]] — a client asks for a span of ticks and receives every tick of it in one reply.

* NATS patterns

The [[id:B4E6F1A2-7C3D-4E5F-8A9B-0C1D2E3F4A5B][NATS service patterns]] hub states how each of these is written in
=ores.nats= code:

- [[id:49F0A1B2-C3D4-4E5F-8A71-8293A4B5C6D7][Bounded Request]] — every service operation is a bounded request with a stated deadline.
- [[id:5A01B2C3-D4E5-4F60-9B82-93A4B5C6D7E8][Classify Transport Failure]] — a timeout, a no-responders signal and a refusal are three different outcomes.
- [[id:6B12C3D4-E5F6-4A71-8C93-A4B5C6D7E8F9][Report a Refusal Off the Body]] — a refused request is answered off the body, with an =X-Error= code.
- [[id:7C23D4E5-F607-4B82-9DA4-B5C6D7E8F901][Report a Failure in the Body]] — a request the service handled is answered in the body.
- [[id:8D34E5F6-0718-4C93-8EB5-C6D7E8F90112][Never Let an Exception Cross the Bus]] — no exception may cross the reply boundary.
- [[id:C1D2E3F4-A5B6-4C7D-8E9F-0A1B2C3D4E5F][Prefix Every Subject With make_subject]] — the request subject is environment-relative in code.
