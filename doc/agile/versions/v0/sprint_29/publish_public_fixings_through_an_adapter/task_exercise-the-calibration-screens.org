* Acceptance

- Calibrate all calibrates one feed a call, and each feed's row shows a mark
  and the server's words as it finishes.
- An applied calibration writes each moved level and deviation as a new
  version of the feed, under =system.calibration=, with a commentary that names
  the fixing; a run on the same fixings writes nothing.
- A running feed whose calibration changed says it applies at its next start,
  and the run offers to restart those feeds.
- A feed's History tab keeps every version and filters to its calibrations.
- The feed page follows the prototype: banner, record tab, flow tab with the
  recent calibrations.
- A fixing URI links to its fixing series page.
- The two points the PR #4331 review asked before merge are addressed.

* Plan

DSH started the task and built the list action, the system-only guard, the
outcome filter and a progress panel. The panel ticked three fixed stages around
one read, and the events tab restated that read; calibration stored nothing, so
there was no log to show.

1. Server: the calibrate request names one feed and asks to apply. The handler
   compares the resolved level and deviations with the stored ones
   (=change_of=, a pure function) and writes what moved through the generated
   services, claiming the versions it read.
2. BFF: =POST /api/synthetic/calibration/:assetClass/run=.
3. Web: a run panel driven one feed a call; the feed page rebuilt to the
   prototype; a Calibration only filter on the History tab; fixing URIs link to
   the fixing series page.
4. The PR #4331 review: claimed writes in accept and withdraw, two tests.

* Notes

- Calibration writes versions (2026-11-01, chosen by the user). The stored
  level becomes the last calibrated value, so =keep_fixed= keeps that one; the
  hand-entered value stays in the history.
- A running feed is not restarted by a run: a restart moves the series to the
  new level in one step, so the run offers it and the person chooses.
