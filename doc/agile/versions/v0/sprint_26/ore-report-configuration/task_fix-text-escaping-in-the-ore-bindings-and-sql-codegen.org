* Goal

Text survives import, storage and export unchanged. An ampersand, an apostrophe,
a quote or an angle bracket in an ORE document is stored in the database as the
character itself, and the export writes it back escaped exactly once. A string
the SQL codegen writes into a literal cannot break the script it is written into.

* Notes

Found while reviewing PR #2500 (today's market round trip).

**The binding decodes attributes and not element text.** In
=projects/ores.ore/core/src/domain/domain.cpp=, the tokenizer passes an
attribute value through =unescapeString= (line 429). Element text goes through
=stripComments= only (line 635), which removes comments and unwraps CDATA but
decodes nothing. The writer's =escape_xml= escapes all five characters on the
way out. So a text value with =&amp;= loads as the literal =&amp;=, and saves as
=&amp;amp;=: it gains one level each cycle.

The database already holds the wrong value. After the today's market database
test ran in =bright_faraday=, the entry for one correlation held the decoded
text in its attribute column and the escaped text in its element-text column:

#+begin_src
 key_value                    | target
------------------------------+---------------------------------------------
 EQ-RIC:.STOXX50E&EQ-RIC:.SPX | Correlation/EQ-RIC:.STOXX50E&amp;EQ-RIC:.SPX
#+end_src

**The harness change hid it.** PR #2500 removed the save/load cycle from
=make_roundtrip_kind= in =roundtrip_harness.hpp=, because the cycle reported a
difference in five today's market files. The diagnosis was correct and the
remedy was not: the difference was this defect. The in-memory and database round
trips still pass, because the original and the rebuilt document both carry the
same undecoded value. Restore the cycle once the binding is fixed.

**Other kinds are exposed too.** Corpus files with an entity in element text, by
kind: =todaysmarket= 5, =curveconfig= 5, =simulation= 3, =sensimarket= 1.

**=unescapeString= matches by prefix.** It compares the entity name with
=strncmp(i, *j, sequenceLen)=, where =sequenceLen= is the length of the text in
the document. =&a;= therefore matches =apos=. No corpus file is affected; fix it
in the same change.

**The generator is out of band.** =xsdcpp= is a sibling checkout, not on
=PATH=, and regeneration overwrites its output wholesale. See
[[id:2DB7C1A3-3191-4D6E-8355-B8BE30BB7809][xsdcpp]] for the checkout, the pin
and the regeneration steps.

**The SQL codegen writes =error_message= into a literal unescaped.**
=_soft_fk_validation_node_to_dict= in
=projects/ores.codegen/src/codegen/org_loader.py= copies the property as is,
and the templates emit it as =raise exception '{{error_message}}'= (domain
entity and junction create templates). The apostrophe in "today's market"
aborted a recreate with two of five tables built. Every consumer is a SQL
literal and no model holds an apostrophe today, so doubling each apostrophe in the loader
changes no current output. Check =book_error_message= on the trade model, which
reaches the template by another path, and any other model property emitted
into a literal.

Once fixed, remove the "keep an apostrophe out of error_message" step from
=doc/recipes/codegen/how_do_i_add_a_new_codegen_entity_model.org=.

* Result

Text now survives import, storage and export unchanged.

**The binding.** The defect was in =xsdcpp='s embedded parser, not in ORE
Studio code. =stripComments=, the element-text path, removed comments and
unwrapped CDATA but decoded nothing, while attributes went through
=unescapeString=. It is now =decodeText=, which decodes references outside
CDATA. =unescapeString= also matched entity names by prefix, so =&a;= and =&;=
both decoded as an apostrophe; a name must now match exactly.

The fix lives in =xsdcpp= (=src/XmlParser.cpp= and =test/XmlParser_test.cpp=),
so the next regeneration keeps it. The ORE Studio bindings take only the three
parser hunks of that regeneration, which are byte-identical to the generated
ones. The same regeneration also changed the =trade= and =componentSubTrade=
types, an unexplained generator drift unrelated to escaping, which would make
the trade parser accept unknown child elements. That is recorded on
[[id:2DB7C1A3-3191-4D6E-8355-B8BE30BB7809][xsdcpp]] and left out.

**The harness.** The round-trip harness compares after a save and load cycle
again, as before PR #2500. The today's market corpus passes with it, and the
database test proves an ampersand is stored as the character.

**The SQL codegen.** The loader doubles apostrophes in =error_message= and
=book_error_message=, the only model text written into a SQL literal. No model
holds one today, so no generated file changed. The recipe no longer tells
authors to avoid apostrophes.

**Component audit.** The task touched =ores.ore= and =ores.codegen=. The
automated half, =projects/ores.codegen/validate_docs.sh=, passes for all 41
components. The task added or moved no file, folder, type or component: it
changed one parser function, the harness comparison, one loader function and
their tests. So the shape, morphology, naming, registry and diagram checks
have nothing new to judge. The comment checks were applied to the changed code.

**In =xsdcpp=.** Committed on =fix-abstract-element-refs= as =09f0dec=, after
=2f7dc07=, which commits the resolver fix in =Reader.cpp= that had been
uncommitted since the 2026-09-26 regeneration.
