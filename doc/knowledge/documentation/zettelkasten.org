* Summary

Zettelkasten (/German: slip-box/) is a knowledge-management method developed
by sociologist Niklas Luhmann, who used it to produce an extraordinary volume
of academic work over several decades. Its two key principles are that each
note captures exactly one idea (the /atomic note/ discipline) and that every
note is permanently addressable by a unique identifier, enabling a web of
typed links to emerge across the collection. ORE Studio uses Zettelkasten as
the conceptual foundation for its documentation graph: every =.org= file
carries a UUID =:ID:= property, files link to each other with
=[[id:UUID][Title]]= references, and [[id:C53486A1-54A3-4FD3-BC5F-15F4CE6BC4ED][org-roam]] maintains the index and
back-link database that makes the graph navigable.

* Detail

** The method

Luhmann's physical slip-box contained tens of thousands of index cards, each
with a unique alphanumeric address. A new note was not filed by subject but
placed wherever it could be cross-referenced to an existing note; the
address was written at the top and outgoing references were written inline.
Over time the collection self-organised into dense clusters of related ideas
connected by an explicit link graph — something that no hierarchical filing
system produces automatically.

The digital Zettelkasten community has translated these principles into
plain-text formats: each note is a single file, the unique identifier is a
UUID or timestamp, and links between files replace the handwritten references
on cards. The emergent structure from following links reveals which ideas are
central (high in-degree) and which are peripheral, without the author ever
imposing a top-down taxonomy.

** Why ORE Studio uses it

ORE Studio's documentation spans domain concepts (ORE instrument types,
interest rate curves), architecture decisions (component split, CMake
conventions), agile artefacts (stories, tasks, sprints), LLM instructions,
recipes, and manuals. A hierarchical directory structure alone cannot
represent the cross-cutting links: a concept defined in [[proj:doc/knowledge][=doc/knowledge/=]]
is referenced from [[proj:doc/agile][=doc/agile/=]] tasks, from [[proj:doc/recipes][=doc/recipes/=]], and from
[[proj:doc/manual][=doc/manual/=]]. Treating the documentation as a Zettelkasten graph means:

- Any page can link to any other page by UUID — location in the directory
  tree is not part of the link and files can be moved without breaking
  references.
- The knowledge graph visualisation ([[https://github.com/org-roam/org-roam-ui][org-roam-ui]]) immediately reveals
  which concepts are central to the project and which are peripheral.
- LLMs can navigate the graph programmatically: =compass show <UUID>= prints
  a node's outgoing and incoming links, giving instant traversal without
  reading every file.

** The atomic note discipline

The most important constraint is the one hardest to maintain: each file
should capture one idea, not a collection of loosely related ones. When a
file grows, the right response is usually to extract a sub-topic into a new
file and link to it, not to add another section. ORE Studio enforces this
weakly — the document types (knowledge, recipe, component overview, task,
story) are each scoped to a single subject — but within each type the author
must resist the temptation to include tangential detail.

** Creating a knowledge document

Every knowledge document is created by the same procedure. A document that
skips a step is either a duplicate, unreachable, or unreviewed, and each of
those costs a later reader more than the step would have cost the author.

1. *Search before writing.* Find the pages that already cover the subject,
   with =compass doc find= and a search of the titles under =doc/knowledge=.
   A subject already covered is extended or linked to, never written a second
   time; overlapping material is reached by an =id= link to the page that owns
   it.
2. *Choose the title.* The title follows the rules in /The house style/ below,
   and the file name is the title in snake case.
3. *Scaffold the page* with
   =compass add knowledge --slug <file name> --parent-dir <dir> --title "<title>" --description "<one sentence of at most 120 characters>" --tags "<tags>"=.
   Compass writes the frontmatter and the =:ID:=; neither is written by hand.
4. *Write the sections.* =* Summary= states what the subject is and the claim
   the page argues, in its first sentence. =* Detail= carries the argument and
   its evidence. =* See also= links the related pages, each with its relation
   (see /Choosing the connection is the work/). =* Sources= lists every work
   cited, in full.
5. *Draw what the prose describes as a process or a structure.* A lifecycle,
   an interaction between components or a structure of parts is drawn as a UML
   diagram, as /Diagrams/ in /The house style/ states.
6. *Link and wire.* The page links to the pages it relies on, the structure
   note of its cluster lists it, and the page links back to that structure note
   from its =* See also=. A page with no way in is not part of the graph.
7. *Check.* Run =compass-ng check= for the links and the back-links, review the
   prose against [[id:180D0EB5-C08A-4C96-B266-3DF593E8F5E3][Review and write academic prose]], and build the page with
   =compass site page <file>= to read it as a reader will.
8. *Commit* with the component bracket =[doc]=, the diagrams' sources and
   images included.

** The house style

*** Prose

Every knowledge document is written in academic prose. The register is that of
a paper in the field: third person, present tense, the subject stated before
the argument, the argument before its limits, and the limits stated rather than
left to inference. The layered standard of
[[id:180D0EB5-C08A-4C96-B266-3DF593E8F5E3][Review and write academic prose]] applies to every page: claim, spine,
paragraph, sentence, term, evidence and honesty. A page describes the current or
the target state; it never narrates its own writing or its earlier drafts.
Working notes, the private language of an author, and the idioms of a source are
not copied; the page states the idea in the field's own terms.

*** The data source

ORE Studio's market data is synthetic, and the simulation is built so that no
process differs between live and synthetic data. A general knowledge page
therefore states its point independently of where the data comes from: it does
not describe sources as observed or simulated, and it does not explain how a
value is generated. Synthetic data generation is a subject of its own, owned by
the pages of the synthetic generation section of
[[id:DF2B616F-E112-4C57-A73B-69F85BE96EF4][Market Data Architecture]]. A general page refers to it by a link
alone, such as a =* See also= entry, and the synthetic page owns every detail.
A page mentions synthetic data in its text only when its point depends on a
property of the synthetic data itself.

*** Citations

Every claim is derived from what the page states, cited to a source, or
labelled as unsupported. Sources are preferred in this order:

1. peer-reviewed academic papers and scholarly books;
2. standards and official documents: ISDA definitions, FpML, regulators,
   central banks and benchmark administrators;
3. vendor documentation;
4. reputable secondary sources, where nothing better exists.

Private notes and unpublished material are never cited. A citation names the
author, the year and the work in the text, and appears in full in =* Sources=,
with a link where a stable public address exists. Each citation is checked
against the source before the page is committed: author, year, venue and page.

*** Diagrams

A page draws a UML diagram wherever a picture states a point more clearly than
prose: a lifecycle, an interaction between components, or a structure of parts.
The diagram supports the argument and does not replace it; the prose still
states what the diagram shows.

| What the page describes | Diagram |
|-------------------------+---------|
| The states an object passes through and what moves it | State diagram |
| Messages between components, actors or services over time | Sequence diagram |
| Components and the interfaces between them | Component diagram |
| Types and their relations | Class diagram |
| Tables and their keys | Entity-relationship diagram |

Each diagram is written in PlantUML. Its source sits beside the page, with a
file name that names the diagram's subject, and opens with the licence header
the other diagrams carry. The image is rendered with
=plantuml -tpng <file>.puml=, and both the source and the image are committed.
The page embeds the image with a =proj:= link, under a =#+caption:= that states
in one sentence what the diagram shows, followed by a line naming the source
and the command that regenerates it. A diagram draws one point; two points are
two diagrams. A rendered diagram is read before it is committed, so that a
label that overlaps or a layout that misleads is caught. The process is
exemplified in [[id:CA61B445-B6DC-41D3-ACF9-D3FB32D0D342][The fixing process: observation, authorisation, application and reversal]].

*** Titles

A title reads like the title of an academic paper. It is a noun phrase naming
the page's subject and its scope; it is not a sentence, and it holds no finite
verb. The claim the page argues belongs in the first sentence of its summary,
where it can be refined without renaming the page, and not in its title.

| Reads like a paper title | Reads like a sentence or a test name |
|--------------------------+--------------------------------------|
| Layered Validation of Scripted Trades | A scripted trade is validated in three layers |
| Derivation of FX volatility quotes from historical fixings | A derived source publishes what it infers from stored fixings |
| Data classification by owner count | The bundle and package catalogue lists who writes each set |
| Twin Recipes: Mapping Native Terms to Script Inputs | A twin recipe maps a native product's terms onto its script |

The forms that serve:

- a nominalisation of the act the page studies: /Derivation of .../,
  /Classification of .../, /Validation of .../;
- a gerund phrase: /Tracking market data identity from fixing to report/;
- a subject and its qualifier: /Pin risk in the expiry of near-the-money options/;
- a short subject, then a colon and a subtitle stating the approach or the scope:
  /Interest Rate Benchmark Types: IBOR vs. RFR/.

A structure note takes the name of its cluster, such as /Fixings/. The file
name is the title in snake case; a structure note's file name ends in =_hub=.

The rule replaces an earlier one that asked argumentative pages for
contestable claims as titles. Luhmann's cards were indeed claims, and a page
here still argues one, but a claim used as a title reads as the name of a unit
test, grows long, and changes whenever the claim is refined. The capture
[[id:8398F1D5-6980-44E2-A72A-7B376F9BE7F0][Retitle the knowledge pages written as assertions]] records the pages that still carry
such titles.

** Writing a note

The atomic rule says how much a page holds. Two more rules, taken from
Luhmann's practice rather than from the plain-text community's retelling
of it, say how the page joins the collection.

*** Choosing the connection is the work

Luhmann filed a new card behind a specific existing card, never by
subject, and that choice was where the thinking happened. A tool can
narrow the field but cannot decide, because the decision is the exercise.
An agent asked to file a page searches for candidates and presents them;
the author chooses.

Each candidate carries a relation, and four cover the ground:

- *contradicts* — the new page tensions or refutes the existing claim.
- *completes* — it adds evidence or a consequence.
- *exemplifies* — it is a concrete case of a principle.
- *answers* — it resolves a question the other page left open.

Contradiction is worth more than resemblance: two pages that say the same
thing in different words are one page's worth of knowledge with two
copies to maintain. The relation is written in the annotation a See also
link already carries, as the hub rows of [[id:7474935C-95D1-3034-B833-83DCD9FB3A09][the knowledge index]] do. The
=id=, =file= and =proj= link types of [[id:C53486A1-54A3-4FD3-BC5F-15F4CE6BC4ED][org-roam]] answer a different
question — how a link resolves — and say nothing about the relation.

A new page also links out and is linked back before it is committed. The
back-link is what makes it reachable from the cluster it joined;
compass-ng's =lint= enforces it for the pages a structure
note orders, and the convention holds for every other page.

*** One improbable neighbour

The pages nearest a new one are the pages it resembles. Look once outside
that cluster for a page it could connect to in a non-obvious way, and
write the sentence that explains the crossing. This is what lets the
collection answer back rather than merely file. The [[id:DFC57D4F-9AB2-4428-BDEC-BF44D106A75D][Scheduler]] hub does
it when it links to this page, to say why its order is authored rather
than computed.

** Anti-patterns

- *Summarising a source instead of saying what it means here.* A
  research-paper page is worth the commentary on what the result changes,
  not the abstract restated.
- *Filing by tool decision.* An agent that picks the thread has removed
  the exercise; it may propose, not choose.
- *Only the near neighbours.* The similar pages are the easy candidates,
  and the contradiction is the one that pays.
- *A page holding several claims.* Split it; a page with two theses
  cannot be contradicted cleanly by either.
- *A sentence as a title.* A title states the subject as a paper's title
  does; the claim goes in the summary.
- *An uncited claim.* A claim that is neither derived nor cited is labelled
  as unsupported, or removed.
- *A hub that restates its cluster.* The structure note gists and links;
  a second copy of the content drifts.
- *A page with no way in.* A page nothing links to is not in the graph,
  whatever directory it sits in.

** Structure notes

Luhmann's slip-box contained a second kind of card. Alongside the
atomic notes sat /Überblicksnotizen/ — overview notes, usually rendered
in English as *structure notes* — whose content was not an idea of their
own but an ordering of other people's. A structure note names a cluster
and lists its notes in an argued sequence, saying how each follows from
the last and why the order is the one it is.

The distinction is between two kinds of address. An atomic note is
addressable because it has an identifier; a structure note makes a
cluster /approachable/, which is a different property. A reader who
knows an identifier can reach any note directly, but a reader who knows
only a subject has no way in. Search returns the notes that mention a
term, ranked by resemblance; it cannot say which of them to read first,
nor which three of forty are load-bearing. That judgement is authored,
not computed, and the structure note is where it is written down.

The resulting shape is a hub with spokes. The hub carries no content
that the spokes do not already hold, which is the discipline that keeps
it honest: a structure note that restates its cluster becomes a second
copy to maintain and drift away from. It gists and links, and the detail
stays in exactly one place. The same rule governs any index in this
graph, including this one.

Structure notes are also what make the collection navigable to an agent
rather than merely searchable. An agent grounding itself in a domain
before doing work has the reader's problem in an acute form: it knows
the subject and not the identifiers, and the cost of reading the wrong
five pages is paid in context it cannot recover.

ORE Studio holds them under the =structure_note= tag, and
[[id:7474935C-95D1-3034-B833-83DCD9FB3A09][the knowledge index]] opens with
the set. One exists per domain cluster: market data resolution, interest
rate curves, volatility, identity and access, MASD, and the entity
lifecycle.

Three conventions keep them honest. A structure note *argues* its order
rather than listing one, saying what each page makes possible for the
next; an order with no reason is a table of contents, which the index
already provides. It *gists and links*, holding no content its cluster
does not, so there is nothing in it to drift. And it *says what it
excludes*, naming the neighbouring cluster and why the boundary falls
where it does, because the reader who arrived at the wrong hub needs
pointing at the right one more than the reader at the right hub needs
reassurance.

A cluster earns a structure note when reading its pages in the wrong
order costs something real. Where the order does not matter, the index
entry is enough.

Some pages belong to a cluster without belonging to its sequence: a
provenance note, a research paper, anything reached when the question
changes rather than when the subject advances. A note holds these in a
section marked =# aside=, and the marker is what the tooling reads. The
alternative was to recognise such sections by their wording, which asks a
script to interpret prose and gets it wrong the first time a note is
phrased differently.
