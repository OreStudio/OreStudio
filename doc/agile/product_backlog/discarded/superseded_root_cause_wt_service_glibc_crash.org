* What

=ores.wt.service='s Wt httpd crashed intermittently on startup with a fatal
glibc assertion:

#+begin_example
Fatal glibc error: tpp.c:83 (__pthread_tpp_change_priority): assertion
failed: new_prio == -1 || (new_prio >= fifo_min_prio && new_prio <= fifo_max_prio)
#+end_example

This fires inside glibc's priority-protected mutex code
(=PTHREAD_PRIO_PROTECT= and =INHERIT=). Nothing in ORE Studio sets thread
priorities, so the call came from Wt's compiled httpd or a Boost internal
it depends on. The =bright_faraday= environment where this was diagnosed
had =ulimit -r= (real-time priority) at =0=, both soft and hard, which is
the condition that trips this assertion.

* Why it is retired rather than fixed

The service it is about is gone. The controller binary and
=projects/ores.controller/= were removed in sprint 24 (PR #1806), which
the sprint 25 investigation confirmed, and =ores.wt.service= is part of the
legacy presentation that the sprint 26 pass removes. There is no crash loop
left to root-cause and no service left to re-enable. The hotfix this
capture leaned on, =enabled = 0= in the controller service-definitions
SQL, went with the controller.

The finding is kept because it is about the environment rather than about
Wt: a process that asks for real-time or priority-protected scheduling
under =RLIMIT_RTPRIO = 0= trips this glibc assertion. If a live service ever
reports it, the cause is here.
