One entity's BFF route descriptor, as a TypeScript data module: the
collection the route listens on, the path parameter that carries the
natural key, the wire field that key lives in, the array fields a batch
delete and a list response use, and the subjects the requests travel on.
The generic factory reads the descriptor and registers the five routes, so
an entity adds no handler of its own.

The module holds values and one value import. There is no function in it,
which is what makes it safe to generate: nothing here is behaviour that a
template would have to be taught to reproduce.

The subjects are not written here. They are imported from the entity's
own generated protocol module, which is rendered from the same model, so
the descriptor and the wire shape cannot disagree about a subject name.
The projection names the messages =org_loader.entity_protocol_messages=
derives -- the list request after the plural, the save, delete and history
requests after the singular -- by reading the enriched entity's derived
message list, so a rename in the derivation moves the descriptor with it.

The requests and the path carry the key the model declares, so the factory
states that key and nothing is translated between an address and a request.
The descriptor names every member of it, because a path segment carries one
value: a key with two members -- a junction's, which is the pair it links --
is addressed by two segments. Stating one member of a pair would address
half a row, so the route states all of them or none.

The optional members are gated on the presence of the subject, not on the
=has_get=/=has_remove=/=has_history= literal: pystache reads the string
=false= as truthy, so a section on the literal would emit the member it
means to omit. The literals are still projected for a consumer that wants
them. No domain entity derives a single-record get, so =get= is absent
today; a current-state entity derives no history pair, so =history= is
absent for it.

=save= is optional for the same reason, and it is what lets a read-only
entity have a screen at all. A read-only entity derives no put request, so
there is no write route to state; the list and the single-record reads
still exist, and a descriptor that named a save subject the protocol
module does not export would not compile. Only =list= is required, because
a descriptor with no way to read the collection reaches nothing.

A junction is not served, and the reason is not the one this paragraph
used to give. It said the junction's delete request names one array per
side while the factory sends a single key -- that was true of the shape
the canonical protocol replaced. The generated removal now carries one key
record with both members, so nothing would be half dropped.

What actually stands in the way is that the route's address is a path, and
a path segment carries one value. A junction's key has two members, so it
needs one segment each, and neither the descriptor nor the factory states
more than one key field today. The archetype admits =domain_entity= until
that is stated, so a junction is given no route rather than a route that
addresses half of it.
