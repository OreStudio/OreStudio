This page documents a [[id:31C868B9-306E-4282-BA8C-07E647021B34][task]] in the [[id:C29FE5A3-61F0-4D2F-BE4F-8A02223EABEF][IR Rates synthetic data: dataset seeding, index cleanup, dual-curve, quoting conventions]] story. It captures the goal, current status, acceptance, and any notes or results.

* Goal

Give =feed_binding= a product-kind discriminator (or equivalent), and
make every consumer of =get_feed_bindings_request= filter by the kind
it actually cares about, so binding an IR curve feed never contaminates
FX-only screens (and vice versa).

Root-caused while manually testing [[id:48D6933D-05F4-4B34-B796-FE1B4A2A6444][Extend SyntheticBindingDialog to
cover IR curve configs]] (scenario step "Confirm no regression to the
FX-only flow" failed):

- =ores_marketdata_feed_bindings_tbl= / =feed_binding=
  (=projects/ores.marketdata/api/include/ores.marketdata.api/domain/
  feed_binding.hpp=) carries only =ore_key= and =source_name= -- no
  field distinguishing FX from IR (or anything else).
- =FxSpotGridWindow::reload()=
  (=projects/ores.qt/mktdata/src/FxSpotGridWindow.cpp=) fetches *all*
  enabled bindings via =get_feed_bindings_request{offset=0,
  limit=1000}= with no kind filter, and =buildRows()= renders every
  one as a currency-pair row via =pair_from_ore_key()=.
- Before this story, only FX spot configs could ever be bound, so this
  happened to work. Now that =SyntheticBindingDialog= can bind IR
  curve configs too, an IR binding (e.g. ore_key ="USD/LIBOR-3M"=)
  shows up in the FX Spot grid, misparsed as if it were a currency
  pair.
- =CrmCrossRatesMatrixMdiWindow= and any other consumer of the same
  request are likely exposed to the same issue -- worth auditing all
  callers of =get_feed_bindings_request=, not just FxSpotGridWindow.

* Acceptance

- =feed_binding= carries a way to identify what kind of series it
  binds (FX spot / IR curve / ...), populated at bind time.
- =FxSpotGridWindow= only ever lists FX bindings; binding an IR curve
  feed no longer produces a row in the FX Spot grid.
- Every other consumer of =get_feed_bindings_request= (CRM matrix,
  etc.) is audited and filters by the kind it expects.
- No regression to the existing FX-only binding/display flow.

* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

Investigated whether an asset-class taxonomy already exists before
inventing a new one for =feed_binding= -- it does:
=ores::marketdata::domain::asset_class= (=fx, rates, credit, equity,
commodity, inflation, bond, cross_asset=), already used on
=market_series.asset_class= (DB-validated via
=ores_refdata_validate_asset_class_fn= against the persisted
=refdata.asset_class_code= lookup table). Reusing this exact enum for
=feed_binding= rather than introducing a separate fx_spot/ir_curve
value set, so the codebase has one way of modeling asset class, not
two competing ones.

Consumers of =get_feed_bindings_request= audited:
- =FxSpotGridWindow= -- needs FX-only filtering (the actual bug).
- =ClientFeedBindingModel=/=FeedBindingMdiWindow= -- generic admin
  list/history window; fine to keep showing all kinds, picks up the
  new column automatically once it exists.
- =CrmCrossRatesMatrixMdiWindow= -- checked, doesn't touch
  =feed_bindings= at all, not affected.

Steps:
1. Add an =asset_class= column to
   =projects/ores.marketdata/modeling/ores.marketdata.feed_binding.org=
   (=domain::asset_class=, =is_enum: true=, validated via
   =ores_refdata_validate_asset_class_fn=, mirroring =market_series='s
   own column exactly).
2. Regenerate SQL + all C++ layers for the =feed_binding= entity via
   =compass codegen entity generate=.
3. =SyntheticBindingDialog::createBindings()= populates =asset_class=
   from =BindableConfig= at bind time (FX -> =asset_class::fx=, IR ->
   =asset_class::rates=, matching the enum's own naming).
4. =FxSpotGridWindow::reload()=/=buildRows()= filters to
   =asset_class == fx= only.
5. No migration/backfill needed: ores.sql has no incremental migration
   runner -- schema changes apply via a full =compass db recreate=,
   so the new column exists from the next fresh DB build onward, no
   ALTER TABLE required.
6. Manual QA: re-run the bind-and-verify scenario, this time also
   confirming the FX Spot grid stays clean after an IR bind.

Ran into two blockers while executing this plan, both filed
separately rather than worked around silently:
- =org_loader.py= rejects the legacy =Primary key=/=Natural keys=
  split on =domain_entity= models (contrary to the unify-entity-key-
  modeling story's own stated scope) -- worked around by migrating
  =feed_binding.org= to the unified =Columns= format first (own
  commit, verified 0 PK/natural-key-semantic changes via build+test),
  filed as [[id:B7FE7D34-82B3-4166-8936-94997182CF80][its own task]].
- =default_value= on an =is_enum= column generates invalid C++ (a
  char literal assigned to a scoped enum) -- worked around by
  dropping =default_value= entirely, matching
  =market_series.asset_class='s own no-default precedent (value-
  initializes to the first enumerator, =fx=, which is what we want
  anyway). Filed as a capture.
- Also noted, not filed separately: the =Validations= table entry
  (=ores_refdata_validate_asset_class_fn=) does not actually get wired
  into the generated insert trigger -- =market_series.asset_class= has
  the identical gap already, so this is pre-existing/shared, not
  introduced here. Left the Validations entry in the model anyway
  (documents intent, costs nothing); value is still constrained by the
  C++ enum type and the SQL =CHECK (asset_class <> '')=.

* Result

=feed_binding= now carries =asset_class= (reusing
=ores::marketdata::domain::asset_class=, the same enum
=market_series= already uses -- one canonical way of modeling asset
class, not a second one). =SyntheticBindingDialog= sets it at bind
time; =FxSpotGridWindow= filters to =asset_class == fx=, so an IR
curve binding no longer produces a row in the FX Spot grid.
=ClientFeedBindingModel=/=FeedBindingMdiWindow= (generic admin list)
and =CrmCrossRatesMatrixMdiWindow= were audited -- the former is
unaffected (still shows all kinds, by design), the latter doesn't
touch =feed_bindings= at all.

Manual QA caught two further real bugs beyond the original scope,
both fixed in the same branch:
- The generic Feed Bindings admin dialog has no field for
  =asset_class=, so a binding created through it left the column
  uninitialized, corrupting the row (serialized as garbage). Root
  cause: a codegen bug where =default_value= on an =is_enum= column
  was SQL-string-quoted for the C++ template too, producing invalid
  C++ (fixed in =org_loader.py=, confirmed no other entity affected).
  =feed_binding.asset_class= now safely defaults to =fx=.
- =IrCurveEditor= had no way to see a curve's =ore_key= before
  binding it, and the IR =ore_key= computation itself (in both
  =SyntheticBindingDialog= and =IrCurveEditor=) was missing its
  =RATES/YIELD/= prefix -- just the bare qualifier (e.g.
  ="AUD/AONIA"=) instead of the real market-data key shape
  (="RATES/YIELD/AUD/AONIA"=, matching =ir_curve_feed.cpp='s own
  =find_series("RATES", "YIELD", qualifier)= call and FX's equivalent
  ="FX/RATE/EUR/USD"= shape, checked against real ORE key conventions
  in =external/ore/examples=). Both fixed; =IrCurveEditor= now shows a
  selectable ORE key label mirroring =FxSpotRateEditor='s.

Verified end-to-end via the linked test scenario: bind FX + IR feeds,
start both, confirm the FX Spot grid shows only the FX row, confirm
the IR tick still persists to =market_observations= despite being
filtered from the display. All 5 steps PASS.
