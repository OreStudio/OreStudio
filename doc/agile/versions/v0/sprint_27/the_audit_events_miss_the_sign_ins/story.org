* Goal

The audit sign-ins screen shows almost nothing, on an installation whose
authentication log is not empty. Three separate defects see to that.

An account with several parties finishes signing in at party selection, not
at the login. The login handler knows this and says so in a comment -- but
the selection handler never records the event, so the sign-in is never
logged. Every account the ACME profile provisions has five parties, so
every sign-in it makes is invisible to the screen.

A refused sign-in is recorded against no tenant and under the principal the
person typed, which is hostname-qualified. The row is therefore both
unfindable by a tenant-scoped read and unreadable as a username.

And no read answers at all. A wire timestamp crosses the protocol as text,
text does not compare against the =event_time= timestamptz column, and
PostgreSQL refuses the comparison rather than coercing the parameter. Every
read fails, the BFF turns the failure into an empty list, and the screen
states there is nothing to show -- which is exactly what a working screen
would say about an empty log.

* Acceptance

- A sign-in that completes at party selection records a =login_success=.
- A refusal records the tenant that was reached for and the bare username.
- The events read answers for every window, including =all= and =day=.
- Recording an event never refuses a sign-in that already succeeded.

* Result

Merged as PR #3022. A sign-in that completes at party selection now records
its =login_success= against the chosen party, and a failure to record cannot
refuse a sign-in that already succeeded. A refusal records the tenant that was
reached for and the bare username. The time bounds are cast through =nullif=,
so the events read answers for the day window and for all. Verified against a
running installation.
