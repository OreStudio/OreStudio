* Acceptance

- Each step kind is dispatched to its owning service's subject.
- ores.iam runs only identity steps and links no synthetic, marketdata or reporting core library.
- The parallel steps of a run execute in different services at once.

* Plan

Every step of a provisioning run is dispatched to one subject,
=iam.v1.ops.provision_tenant_step=, served by ores.iam. That is why iam links
the synthetic and refdata cores: it compiles code for work its own data has
nothing to do with. It is also why the parallel steps of a run queue: one
service takes them.

The move is one kind at a time, because each kind drags its own dependencies:

1. State the owner of each kind once, where the definition states a step's
   subject, so the engine stores the owner with the row and every service reads
   the same table. Done here, as =step_subject_for_kind=.
2. Move a kind whose work a service already owns, end to end, and drop the
   executor and the link it needed from iam. Start with =build_calendars=: the
   work is refdata's own, the step calls a request to refdata today, and no iam
   state is involved, so it proves the dispatch with the least code moved.
3. Then =generate_trades= into ores.synthetic, which drops iam's
   =ores.synthetic.core= link and takes the longest step off iam's workers.
4. Then the marketdata kinds: the curve, forward and surface publishes, the
   surface blueprints and the subscription setup.
5. Then the reporting, dq and inbox kinds: =schedule_reports=,
   =publish_bundle= and the two approval-mode steps.

Step 3 (=generate_trades=) needed a prerequisite the plan did not foresee, and
it is served: iam answers =iam.v1.ops.enter_tenant_as_service=, which gives a
service account a session inside a tenant it serves, scoped to one of that
tenant's parties and carrying the service's own permissions. The story's
Decisions state why that session names no person. Step 2 avoided the need
because the calendar work is refdata's own data and it writes as its own
service account; =generate_trades= writes trades through requests that answer a
session, which is why a request that grants one was necessary.

Step 4 moves one kind at a time, because each brings its own machinery.
=subscribe_market_data= goes first: it reads the tenant's feeds and gives each
party a subscription and a route, all of it marketdata's own data, so it proves
a second service's step dispatch with the least code moved.

When a step moves a kind that runs *beside* another in the same run — the
surfaces beside the schedules, or the curves beside the trades — measure that
the two services work at once, which the =generate_trades= run already shows.

Each stage is its own PR, because each one moves an executor and its link, and
a stage that lands alone is a stage a run can be proved against.

* Notes

- The rest of step 4 is not the same shape as the first three kinds. Two of the
  remaining kinds read the *system* tenant's blueprints: =publish_party_curves=
  copies the system's curve blueprints and =give_party_surface_blueprints= the
  system's surface blueprints, both through an administrator session in the
  system tenant. A service session cannot read the system tenant, and by design
  it is refused there, so those two need the blueprints to reach the tenant by
  another route before they can move. That is a decision, not a port.
- Two more bring machinery rather than only requests: the forwards and surfaces
  kinds retry a request and read back what an earlier attempt did, through
  =request_retry.hpp=, which lived in iam.core. It has moved to ores.service,
  with the refusal error type it shares with iam's internal client, so a service
  that is not iam can retry a step's work; that move changes no behaviour and
  leaves no coupling behind.

* Notes

- The two blueprint-copying kinds were held by how a blueprint reaches a
  tenant, not by the steps. The story decides it: a service reads the
  installation's blueprints in the system tenant as itself, through its own
  database context, so neither step enters an administrator session and
  nothing a tenant may read changes. =publish_party_curves= moved to
  ores.marketdata on that decision, and =give_party_surface_blueprints= is
  moving now: it copies each party's surfaces in that party's session, as the
  curve step does.
- The planners moved with it. =plan_party_curves= and =plan_party_surfaces=,
  with the fixture their tests share, are in ores.marketdata.core now: they
  are pure planning over marketdata and reference data types, and the service
  that runs the steps is theirs. Once the surface step moves, iam links that
  library no more.
- Story Decisions and the task's Measurements have to be read together: a
  step's authority is the session it holds, and the catalogue read is the
  reason this step needs no other.
- A party's plan is one act but not one request. The first run on the rebased
  tree failed with "A batch of fx_vol_surface_pillar carries more than 1000
  elements": a party's surface plan holds more rows than a write request may
  carry, so both writers send their rows in batches of 1000. The run then
  passed, with the four parties' curves and surfaces written.
- The catalogue is read by the service, not by the tenant. Widening the
  blueprint tables to every tenant worked and was withdrawn: a read is narrowed
  twice, by the policy and by the repository, so the repositories had to widen
  too, and that changed every reader. The scheduled =publish_due_curves= sweep
  then planned 22 curves instead of 2, and its suite caught it. ores.marketdata
  now reads the installation's rows in the system tenant through its own
  database context, as =feed_ingest_loop= already does, and no policy, model or
  repository changed. The commits that widened it stay in this branch's history
  and are reverted by the tree; squash them away when the branch is rebased for
  its PR.
- The publish the step raises is an approval request, and the account that
  raises it is the service's, which lives in the system tenant. The inbox reads
  the maker where it lives for a service account, and a request a policy
  authorised is decided by the installation, so the rule that keeps a person
  from deciding their own request no longer refuses it. Case
  =a_service_acting_in_a_tenant_is_its_maker_read_where_it_lives=, and the acme
  run before the catalogue was withdrawn proves the path end to end: 20 curves
  published for each of four parties, raised and closed as =marketdata=.
- The =ores.refdata.core.tests= segfault was a stale test binary, not a defect.
  =curve_configuration_database_roundtrip_tests= died in the destructor of a
  =std::vector<fx_convention>= whose size read as =0xdf2df2df2df2df2f=, the
  fill of memory no constructor ever wrote. =libores.ore.core.so= had been
  rebuilt after =conventions_package= gained its =fx= member, and the test
  binaries had not: =split_conventions= returns by value into a slot the
  *caller* sizes, so the newer library wrote the member past the older caller's
  object, and the caller then destroyed a vector at the old offset. Rebuilding
  =ores.ore.core.tests= and =ores.refdata.core.tests= fixed both suites with no
  source change: 548 cases and 6172 assertions in refdata, 31 cases and 43805
  assertions in the ore conventions tests. The earlier note blaming =main= was
  wrong; the five widened repositories were a coincidental suspect, and the same
  stale binary was behind the two =app_feed_ingest_loop_tests= failures that
  disappeared on the next build.
- =ores.marketdata.service.tests= fails two =app_feed_ingest_loop_tests= cases
  on this tree. They fail in isolation, they do not touch step dispatch, and
  the file changed on main this week; nobody has shown they are main's, so the
  suite is recorded as not green.

* Result

Stage 1 is done: the dispatch names the service that owns each kind, and
ores.refdata serves the calendar step in its own process.

- =step_subject_for_kind()= states the owner of a kind once, beside the words
  and the budget the definition already keeps there, and =make_step= stores the
  owner on the step the engine persists. A kind no service serves is sent to
  ores.iam, which refuses it, so an unserved kind fails where a person can read
  it instead of waiting for nobody.
- ores.refdata serves =build_calendars= on
  =refdata.v1.ops.provision_tenant_step=, through the same =step_routes= and
  =serve_step_commands= the book-apply steps use, so the step is a durable
  consumer on refdata's own stream. It calls the calendar materialisation
  service directly rather than sending refdata a request about refdata's data.
- ores.iam no longer has an executor for the calendar step, and no longer links
  =ores.marketdata.core=, which nothing it compiled had used.
- A test states the dispatch two ways: the table's answer for a kind, and the
  subject a built definition puts on the step.
- Step 3 is done as well: =generate_trades= is served by ores.synthetic, iam
  has no executor for it, and a provisioning run passes with the step in its
  new home. Step 4 has begun: =subscribe_market_data= runs in ores.marketdata,
  and three of the eighteen kinds now have an owner outside iam. The two services do work at once: the last run had iam publishing a
  party's curves and forwards while synthetic was writing that party's
  population, which is the acceptance line about parallel steps.

What this stage does not do, and the plan's later stages cover:

- 15 of the 18 kinds still run in ores.iam. It no longer links
  =ores.synthetic.core=: stage 2 moved =generate_trades= into ores.synthetic. It
  still links =ores.refdata.core= for the party repository that its identity
  handlers read,
  which is identity work and not this task's to remove.
- That the parallel steps of a run execute in different services at once is not
  yet measured. Nothing in the definition dispatches two *parallel* kinds to two
  services today: =build_calendars= sits in the tenant-setup run beside the
  identity steps, which all run in iam. The line is proven when a kind that runs
  beside another in the same run moves, which stages 2 and 4 bring.
