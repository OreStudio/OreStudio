* Goal

The ingest of ticks no longer pays a commit, a series read, a notification and two acknowledgements for each tick. A burst of ticks drains at least ten times faster than the 143 rows each second of today.

* Acceptance

- The observation table has no notification trigger and no event mapping.
- One batch writes the rows of one tenant in one transaction, and a series read happens once for each series.
- Producers and the republish use core NATS, and the two tick streams are no longer created.
- A lag gauge shows the age of the newest tick of each source.
- The burst drain rate is measured with the tick injector and recorded in the task.

* Plan

Step 1 of =tick_ingest_pipeline.org=, scoped to what the existing observation table
allows. Step 0 showed that batching that table stops at about 8,300 rows each second,
because its insert trigger runs for every row. The append-only table that lifts this
ceiling moves ticks out of the table that eleven readers use, so it is a task of its own.

1. The observation model sets =notify_trigger= and the three event addresses to false.
   Remove the generated trigger SQL, the event registrar and the event header.
2. The ingest loop queues ticks in a bounded queue that drops its oldest entry. A worker
   takes every tick that has arrived and stores them in one transaction for each tenant,
   with the last row of each key, and splits a failing batch until the failing row is alone.
3. A series is read once and its id is cached.
4. The loop republishes after the commit on core NATS. The two feeds publish on core NATS.
   Both services delete the three tick streams when they start.
5. The status log gives the lag of each source, the depth of the queue, the drops, and the
   size and time of the last batch.
6. Measure the burst with the tick injector.

* Result

A burst of 4,000 ticks, which is 40,000 rows, drains in about 21 seconds. The rate in the
steady phase is about 2,260 rows each second, against 143 before. That is about 16 times
more, and it meets the acceptance of ten times. The queue dropped nothing. The lag of the
live feeds stayed at 0.1 seconds.

What changed:
- The observation table sends no notification, and nothing generates the event or its
  registrar. The database-wide lock at commit is gone.
- A batch costs one transaction for each tenant, one series read for each series, and one
  series cache. A tick no longer costs a commit.
- The feeds and the republish use core NATS. Both services delete the three tick streams
  when they start.
- The status log shows the lag of each source and the state of the queue.

What did not change, and what the numbers say about it:
- A batch of 1,205 ticks is about 12,000 rows, and it took 5.5 seconds. The step 0 table
  gives about 8,300 rows each second for the same table inside the database, so the client
  path costs about four times what the database costs. The row building, the string
  conversion of =sqlgen::insert=, the shape check and the manual point check are the
  candidates. A later pass should profile them, and =COPY= is one option.
- The trigger of the observation table still runs for every row. The ceiling of this
  table is about 8,300 rows each second for one connection. The append-only table of step
  1b lifts it to about 187,000.
- The lanes, the age gate, the recent window and the live subject with tokens are step 2.

Verified: =ores.marketdata.service.tests= and =ores.synthetic.api.tests= pass, with new
cases for the queue and for the rows of a batch. The burst was run against this environment
after a restart of the fleet on the new binaries.
