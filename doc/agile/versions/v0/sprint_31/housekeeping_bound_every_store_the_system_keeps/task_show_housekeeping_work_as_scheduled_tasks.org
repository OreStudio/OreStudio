* Goal

* Acceptance

- Each sweep registers a scheduler job definition, and its firings create the job instances the scheduler already records
- The task screens list the housekeeping jobs beside every other job, with the last run, its outcome and what it freed
- A person can enable, disable and change the cadence of a housekeeping job from those screens
- A disabled policy is visible as disabled rather than absent

* Plan

The sweep is already a job definition, and the scheduler already records a job
instance for each firing. What was missing was that a person could see either.
The shell's screens read job definitions and instances through the tenant the
session holds, and the platform's own jobs were seeded with no tenant at all
while the inbox's jobs were seeded under the system tenant. The four jobs the
scheduler runs for the installation were therefore invisible in the screen that
reports them, beside the three that had a tenant.

The correction is in the seed and the model, not in the read: a system job is
the system tenant's job. The four definitions now carry the system tenant, the
column is not null, and the screens' ordinary tenant-scoped read shows them to
the system tenant and to nobody else. A system job is not a job without an
owner; it is one whose owner is the installation.

The model said a job may belong to no tenant, and the seed obliged by writing
NULL. A first attempt made the screens read every definition across tenants;
that was working around the seed rather than correcting it, and it was removed.
The seed writes the system tenant, the model states that a job is never
tenantless, and no read had to change.

The ledger the sweep writes had no reader outside SQL, so a person could see
that a sweep ran but not what it removed. It is now a read model: a view over
the ledger joined to the policy each row names, so a run carries the period and
the state the policy has now, and a policy turned off after a run keeps its
history. Codegen gives the view a repository and a protocol, and the shell reads
it with a command beside the policies it reports.

Tuning is on the policy rather than on the job. A policy is the system tenant's
row, so an operator holding the write permission changes a period or turns one
off, and the sweep applies the change at its next firing. A job definition
belongs to the tenant that owns the schedule, and the shell's commands address
the caller's own; the sweep's cadence is the installation's, and changing it is
a separate question about who owns the platform's schedule.

* Notes

- The environment had never been provisioned after its rebuild, so there was no
  human account to sign in with and the scripted session could not start. The
  shell's own bootstrap command created one; that is environment setup, not part
  of this task, and it is why the first attempt reported a failed auto-login.
- A job definition changed by raw SQL does not reach the running scheduler. The
  notify trigger returns null for every update, because a versioned table's
  update is the close of the row the insert that follows replaces. A definition
  edited that way stays stale until the service restarts; a probe that changed
  the cadence to every minute fired nothing until it did. The same change made
  over the wire does reach it, which is how the firing above was produced.
- The cause of the invisible jobs was the seed, not the read. Trunk corrected it
  while this branch was open: the job table's tenant column is not null, and the
  platform's jobs carry the system tenant as a published dataset. This branch
  took that work in a merge and kept only the run ledger and the commands.
- The four permissions the new commands check did not exist, and the retention
  policy entity's three were missing too, so the policy protocol added earlier
  was reachable only by a holder of =scheduler::*=. All seven are seeded now.
- The runs filter never reached the request: the command read its value flag
  with the helper that answers only for a boolean switch. Found by running the
  command against the installation, where the filtered list answered every run.
- The notice suite passed only on an installation that had never raised a sweep
  notice, and its last assertion read the notice without running the pass that
  clears it. Both are corrected; the suite now passes on a provisioned
  installation as well as on a fresh one.
- Three of the eight policies read =skipped= because the sweep cannot reach the
  object store or a host's disk. The run states that in its detail, and the
  object prefixes are the remaining store nothing bounds: that is the
  object-storage lifecycle task, not this one.

* Result

The sweep appears in the scheduler's status view beside every other job, with
its cadence, its next firing and its last run. Its firings are job instances the
instance list shows. It is one of nine jobs the installation runs, and it is the
system tenant's row like the rest, so the tenant-scoped read a person already
uses answers for it.

The shell reads housekeeping from the stores it bounds. =housekeeping policies=
lists the eight policies with the store each bounds, the action, the period, the
cadence, whether it is on and why it exists. =housekeeping runs= lists what each
sweep removed, one row per policy, carrying the policy's period and its state as
the policy states them now, so a policy turned off keeps the runs it made while
it was on and reads as off beside them. =--policy= narrows the list to one.

A person changes what housekeeping does from the same menu: =enable=, =disable=
and =period= write the policy, each write stating the version it read, and the
sweep applies the change at its next firing. The job's own cadence is the
scheduler's, changed with =scheduler cadence= beside every other job.

What the run cannot do, it says. Three stores read =skipped= with the reason in
the row, which is the object-storage task's work and not a silence here.
