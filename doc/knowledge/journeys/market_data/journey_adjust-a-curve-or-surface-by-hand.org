This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A trader corrects a candidate curve or surface by hand where the market is wrong or thin, with a manual point or a spread overlay, and each correction carries a reason.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want to override the parts of this candidate the market got wrong or never
gave me, and I want the hand value to stay put while the feeds keep ticking."
The journey is done when every correction the trader intended is on the
candidate, each carries a reason, and the candidate still reads as a candidate:
nothing has been published.

The trader keys a point for three reasons. The market is wrong, so the hand
value corrects it. The market is thin or absent, so the hand value stands in
for it. The trader wants a what-if, so the hand value is a candidate only.

* Actor and trigger

The actor is the trader, acting as maker: the person who holds the market-data
management role for this party and owns the candidate. An approver owns the
decision to publish, in a different journey. The trigger is a bad print, a
stale or missing quote, a thin tenor, a broken pillar, or a request from
pricing to mark a point by hand. The journey starts at a candidate curve or
surface and ends when the trader leaves it, still a candidate.

A manual point is a candidate correction. It stays a candidate until it is
approved and published; see /What is missing/ for the override and shift
operations and the precedence rule that do not exist yet.

* Steps

1. *Open the candidate.* The person opens *Curves and surfaces* and selects
   the candidate curve or surface. The system reads the =market_series= row
   and lists its points with =marketdata.v1.market_observations.list_by_series_id=.
2. *Read the points.* The system shows one row per =oresmd_uri= with its
   value, its =source= tag and its =observation_datetime=. The row carries no
   actor and no marker that says the value was written by hand, so the screen
   cannot yet tell a manual point from a feed point. See /What is missing/.
3. *Key a curve point.* The person chooses *Set manual point*, picks a tenor,
   types a value and states a reason, and confirms. For a curve the coordinate
   is the tenor. The system has no override operation, so the button names the
   subject it needs and changes nothing. See /What is missing/.
4. *Key a surface point.* For a surface the coordinate is an expiry and a
   strike. The person picks both, types a value and states a reason. There is
   no strike-label vocabulary and no surface point coordinate, so the screen
   cannot address the point; it marks the strike picker as absent.
5. *Clear a manual point.* The person selects a manual point and chooses
   *Clear manual point*. The system would drop the override so the feed value
   shows again. There is no way to identify which point is manual and no
   operation to clear one, so the button is inert. See /What is missing/.
6. *Apply a spread overlay.* The person chooses *Apply spread overlay*, picks a
   parallel shift or a twist, picks a node or a segment to apply it over, types
   the shift and states a reason, and confirms. The system has no shift
   operation, so the button names the subject it needs and changes nothing.
   See /What is missing/.
7. *Read the corrected candidate.* The system would redraw the curve or
   surface with the manual points and the overlay applied, and mark each
   correction with its reason. Because no correction was written, the screen
   shows the feed values unchanged.
8. *Confirm the hand value survives a feed update.* The person waits for, or
   forces, a feed update. The hand value should stay until it is cleared: a
   feed tick writes the point again and the manual value must win. No
   precedence rule exists, so a feed write is indistinguishable from a hand
   write and either can overwrite the other. See /What is missing/.
9. *Leave unpublished.* The person chooses *Leave unpublished* and returns to
   the list. The corrected candidate is still a candidate.

Writing a correction, if it existed, would be immediate: the reply would carry
the corrected candidate, so the journey carries no state of its own. The only
state it would leave is the row on the candidate, which stays until it is
cleared.

* Screens and wireframes

One screen. The candidate and its points sit at the top, the two correction
forms sit in the middle, and the state of every correction sits at the foot.
Each correction form asks for its reason, and the foot states that a manual
point survives later feed updates until it is cleared.

=marketdata.v1.market_observations.put= exists, but it writes a row
indistinguishable from a feed write: the =market_observation= table has no
actor, no source kind and no reason, and its =source= column is a producer
channel tag, not a marker that a person wrote the value. The subject is
therefore =partial= as an override. The generic history read is
=marketdata.v1.history.get= with =entity_type= =ores.marketdata.market_series=;
=market_observation= registers no history provider, so an override would
leave no readable trail.

* What is missing

1. *Observations carry no actor and no source kind.* The
   =market_observation= table is append-only, bitemporal and deliberately
   carries no audit columns; its =source= column names the producer channel,
   so a row cannot say that a person wrote it. The candidate is a source kind
   on the point, or a separate override entity that records the actor, the
   value and the reason. Until then the screen cannot mark a row as manual and
   shows every row as a feed value.
2. *There is no override operation.* The subject
   =marketdata.v1.market_observations.override= (with a matching clear) would
   have to be added to write a manual point and to remove one. Until then
   *Set manual point* and *Clear manual point* name the step and stay inert;
   the screen does not fall back to =.put=, because that would write a feed
   row with no reason and no actor.
3. *There is no precedence rule between a manual point and a later feed
   write.* Nothing decides whether a hand value or the next tick wins, so a
   manual point cannot be promised to survive. The candidate is a stated
   precedence: a manual point wins for its coordinate until it is cleared,
   and a feed write to that coordinate is held or rejected. Until then the
   screen warns that a feed update may overwrite a hand value.
4. *There is no spread overlay operation.* The subjects
   =marketdata.v1.curve.shift= and =marketdata.v1.surface.shift= would have to
   be added, each naming the kind (parallel or twist), the node or segment it
   applies over, the shift and the reason. Until then *Apply spread overlay*
   names the step and stays inert.
5. *There is no strike-label vocabulary and no surface point coordinate.* A
   surface point is an expiry and a strike, and nothing says whether a strike
   is an absolute level, a delta or a moneyness, so a surface override cannot
   be addressed. The candidate is a vol quoting convention, and with it a
   strike coordinate in the =oresmd_uri=. Until then the screen shows the
   expiry and marks the strike picker as absent.
6. *A correction cannot carry a reason.* The change reasons exist
   (=dq.v1.change_reasons.list=), but a point has no field to hold one, so the
   reason the person types has nowhere to go. The candidate is a reason field
   on the override entity from item 1, or a reason on the observation. Until
   then the reason field is shown but not stored.
7. *The correction leaves no history.* =market_observation= registers no
   history provider, so even if a manual point were written, =marketdata.v1.history.get=
   could not show when it was made or by whom. The candidate is a history
   provider for the override entity. Until then the screen cannot show the
   trail of a by-hand correction.
