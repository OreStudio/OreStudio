* Acceptance

- systemd_generate.py no longer queries postgres; compass systemd generate works against the org model alone; regenerated units for all 19 services no longer pass --nats-url/--nats-subject-prefix/--nats-wire-format; compass shell no longer passes them either; every service (systemd-launched domain services, compass shell) still starts and connects to NATS correctly; ores.qt client launch is confirmed to already pass none of these (no change needed there).

* Plan

- systemd_generate.py: replaced fetch_service_definitions/
  fetch_dependencies's psql queries against
  ores_controller_service_definitions_tbl/
  ores_controller_service_dependencies_tbl with a new
  load_service_registry(project_root), which imports
  codegen.org_loader.load_org_service_registry_model and reads
  projects/modeling/service_registry.org directly -- no DB round-trip.
  fetch_service_definitions/fetch_dependencies now take the loaded
  services list instead of env, and derive desired_replicas/enabled/
  depends_on/args_template straight from the model's deployment
  aspect (binary_name is always identical to service_name, confirmed
  against the old populate script's seed data, so no separate lookup
  is needed).
- Stripped --nats-url/--nats-subject-prefix/--nats-wire-format from
  DEFAULT_ARGS_TEMPLATE and from _substitute_args's placeholder
  substitutions -- every service already resolves these from .env via
  the shared-domain fallback tier (task A of this story's earlier
  chain). Kept the nats-tls-* trio CLI-supplied via {nats_tls_args},
  out of scope per the mapper fallback-tier task's Decisions.
- compass_services.py's _service_units() called
  systemd_generate.fetch_service_definitions(ctx.env) directly with
  the old signature -- a second, not-otherwise-mentioned consumer this
  task's migration would have broken. Fixed to
  load_service_registry(ctx.root) + fetch_service_definitions(services).
- compass.py's shell subcommand: removed ORES_SHELL_NATS_URL/
  ORES_SHELL_NATS_SUBJECT_PREFIX/ORES_SHELL_NATS_WIRE_FORMAT from
  flag_for -- ores.shell's own parser (parser.cpp) already reads its
  ORES_SHELL_NATS_* mirror via its "SHELL" app-prefix mapper, so
  passing them again on argv was redundant. Left the TLS trio
  threaded, same scope boundary as above.
- Verified end-to-end rather than just at the Python level:
  `compass systemd generate` (no DB touched, confirmed by reading the
  generated units -- no --nats-url/--nats-subject-prefix/
  --nats-wire-format anywhere, e.g. ores.iam.service's ExecStart=),
  `compass systemd quadlet`, `compass systemd deploy`, `compass
  services start` (all 23 units + nats-server reach active/ready),
  `compass services status` (all running), and `compass shell
  --dry-run` (only the TLS trio threaded). Ran the full ores.codegen
  (117/117) and ores.compass (43/43) pytest suites; no existing
  systemd_generate.py test coverage existed to extend.

* Result

compass systemd generate/quadlet now read
projects/modeling/service_registry.org's deployment aspect directly via
codegen.org_loader -- zero DB dependency, closing the last of the five
original argv-threading layers. All 19 fleet processes' rendered units
(25 concrete units total, including compute.wrapper's 5 replicas) no
longer pass --nats-url/--nats-subject-prefix/--nats-wire-format;
compass shell no longer threads them either. Verified live: generated,
deployed, and started the full fleet (23 running units + nats-server),
all reaching active/ready and connecting to NATS correctly purely via
.env's shared-domain fallback, exactly as the acceptance criteria
require. Also found and fixed a second consumer
(compass_services.py's _service_units()) that called the old
fetch_service_definitions(env) signature directly and would have
broken on this migration.
