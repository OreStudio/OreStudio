* Goal

Apply safe drift to the =refdata-cpp= component and use it as the *reference
implementation* for the per-component drift workflow. The remaining 11
components each get their own task that follows this pattern.

** Why refdata is the pilot

Refdata is the most heterogeneous component:
- 25 domain_entity models (more than any other component)
- Mix of UUID-PK and string-PK entities
- Mix of stateful and stateless repositories in production
- Child entities (contact_information, identifier) with by-parent lookup
- =party_repository= has hand-crafted methods (=read_system_party=, pagination,
  CTE descendants) that cannot be regenerated

Solving refdata establishes the template flags and exclusion pattern that
everything else inherits.

- =service_list_by_uuid_parent= — implemented as a =list_by_uuid: true=
  sibling flag on the *existing* foreign-key =list_by= mechanism (not a

  Repository stays string-typed; the service converts uuid → string

- =service_find_prefix= (bool) — renames the single-record accessor

- =has_uuid_include= (derived, =core.py=) — gates the shared
  =<boost/uuid/uuid.hpp>=/=<boost/uuid/uuid_io.hpp>= includes across all
  of the above plus the pre-existing =has_parent_id= hierarchy code.

** Corrections to the stale plan

Two of the plan's per-model specifics didn't hold up against the current
schema and were corrected rather than implemented as literally written
(both flagged to and confirmed by the user before implementing):

- *=business_unit='s find-by-code column*: the plan named =unit_code=,
  but =unit_code= is nullable and not part of the natural key — the real
  natural key is (=party_id=, =unit_name=). Used that pair instead;
  documented the discrepancy directly in =business_unit.org='s Flags
  section.
- *The four child entities' find-by-code* (=party_contact_information=,
  =party_identifier=, =counterparty_contact_information=,
  =counterparty_identifier=): the plan named a single column
  (=contact_type=/=id_scheme=), but each entity's actual natural key is a
  *composite* — e.g. "one contact record per type per party" means
  uniqueness is (=party_id=, =contact_type=), not =contact_type= alone.
  A bare =find_X_by_code(contact_type)= would have been genuinely
  ambiguous (arbitrary row among every party sharing that type).
  Implemented =find_X_by_code(parent_uuid, code)= instead via
  =service_find_by_code_parent_column= in the org model.
