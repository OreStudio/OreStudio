This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Bring every ORE trade type under a round-trip test. Add a hand-written
fixture for each of the 43 types that no example exercises, and add a
mapper for each one that has none.

* Why

=domain.hpp= declares 122 =oreTradeType= values. The examples tree under
=external/ore/examples/= names 79 of them across 1623 XML files. The
other 43 appear in no file, so no test that walks the examples tree can
reach them.

The coverage test added with the v17 sync walks that tree and nothing
else. It compares the canonical serialization of each example to a
committed golden. That design is cheap and it scales with upstream, but
it is blind to any type upstream ships no example for. A mapper for one
of those 43 types can rot with no test to notice.

The v17 sync showed the risk. Five FX types changed =OptionData= and
=BarrierData= from a repeated element to a single one. The compiler
caught that class of break because the member type changed. A schema
change that still compiles but maps to the wrong field would pass
silently, and for these 43 types there is no test that would disagree.

The work splits by what is missing:

- *Four types have hand-written code already.* =BondFuture= and
  =BondPosition= have a mapper. =BondPosition= and
  =EquityOptionPosition= have a test reference. =Failed= is the enum
  sentinel, not a product; =exporter.cpp= and =importer.cpp= handle it.
  These four need a fixture only.
- *Thirty-nine types have nothing.* No example, no mapper, no test. Each
  one needs a mapper and a fixture. The six new v17 types that lack an
  example — =BondFutureOption=,
  =CommodityForwardVolatilityAgreement=, =EquityAutoDeltaHedgedOption=,
  =EquityForwardVolatilityAgreement=, =ForwardVolatilityAgreement=, and
  =FxForwardVolatilityAgreement= — are inside this group.
  =IntradayPowerForward=, the seventh new type, has an example and is
  therefore outside it.

The 39 span four families, and a family shares most of its shape. An
equity barrier option and a commodity barrier option differ in the
underlying and little else. So the unit of work is a family, not a type.
That argues for splitting this capture into several stories rather than
one.

* Open question

Is a mapper for every type the goal, or is a round-trip test enough for
the types that already have one? The two answers give very different
sizes of work. A fixture per type is mechanical. A mapper per type is a
design decision per family, and it touches =ores.trading=, not only
=ores.ore=.
