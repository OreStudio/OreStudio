the cache steps after it have room to finish.

* Notes

** Why the guard alone was not enough

Changing the cache steps to =always()= makes them run after a cancelled
job, and the step statuses prove they do. It does not give them time. The
job is torn down roughly thirty seconds after it exceeds the limit, and
uploading a two-gigabyte compiler cache takes minutes. The save would
start and be killed.

** The arithmetic

The job limit is 360 minutes, setup takes about 8, and the cache delete
and upload need a few minutes. Capping the CTest step at 320 leaves about
30 minutes for them, which is ample, and still lets a cold build compile
roughly six sevenths of the tree before it is cut.

** Once warm, it never binds

A warm build finishes in about an hour, so the timeout only ever applies
to the runs that are still filling the cache -- exactly the runs whose
partial cache has to be kept.

* Result

The CTest step is capped at 320 minutes. A run whose build overruns now
stops with roughly thirty minutes of job left, enough for the guard, the
delete and the cache upload to finish. Before this, the job was torn down
about thirty seconds after the limit and nothing was saved.

A warm run finishes in about an hour, far inside the cap, so the timeout
only ever applies to the runs still filling the cache -- the ones whose
partial cache has to be kept.

The gate passes 7 of 7 (classes =ci=, =docs=).

Not verified here: no run has yet been cut by the new cap. The first run
that overruns is the proof, and its cache entry growing is the signal.
