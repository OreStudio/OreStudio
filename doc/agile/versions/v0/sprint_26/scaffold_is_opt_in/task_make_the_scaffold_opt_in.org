* Plan

The finding came out of the ores.nats clean-standard analysis. Listing that
component in the codegen catalogue made the drift gate offer to create
`domain/stub.hpp`, `src/domain/stub.cpp`, `tests/stub_tests.cpp` and the
umbrella header `ores.nats.hpp` -- the last of which that task had just
deleted as dead code. The scaffold archetypes hung off `ores.cpp.component`
and `ores.cpp.service-app`, keyed on `#+component_kind:` alone, so any
non-composite component re-emitted them on every regeneration.

   header, the two stub archetypes and the two stub tests into it, renaming
   them to match the facet.

   the scaffold is now a sibling of `ores.cpp.component`, and correct the
   guard message in `core.py`.

   `:ores.cpp.scaffold.enabled: true`, so a new component still links and
   tests before its first model.
5. Update the skill, the runbook, the scaffold verifier, the fixtures and the
   architecture docs.
6. Add the regression test and re-run the codegen suite, the inventory check,

* Notes

** Why the scaffold is a facet and not a flag on the model

The scaffold already had a home in the physical space; the bug was that its
home was `ores.cpp.component`, which every component uses for life. A
separate facet makes "this is first-generation only" a property of the
address rather than a convention someone has to remember, and it reuses the
switchable-facet mechanism the repo already has (`ores.sql.populate`,
`ores.cpp.shell-command`, `ores.cpp.eventing-integration-test`).

** What still emits from the scaffold by design

A component created from the overview scaffold carries the opt-in line, so
its first build works with no models. The line and the four files are
removed together when the first real model lands, and
`grep -rn 'ores.cpp.scaffold.enabled: true' projects/*/modeling/` lists
whatever still carries scaffolding. No component in the tree carries it
today.

* Result

The scaffold is opt-in. `ores.cpp.scaffold` is `#+default: disabled` and
holds the umbrella header, the two stub archetypes and the two stub tests;
`ores.cpp.component` and `ores.cpp.service-app` hold only what a component
keeps for life. The C++ scaffold address is `ores.cpp`, the component
overview scaffold opts a new component in with one line, and
`test_scaffold_is_opt_in.py` proves that no scaffold path appears without
it -- including for a facet-scoped address -- and that no `stub.hpp`,
`stub.cpp` or `stub_tests.cpp` exists anywhere under `projects/`.

Verified: codegen suite 565 passed, physical-space inventories 42/42 up to
date, `check_component_drift.py --all` reports no drift, `validate_docs.sh`
passes all 40 components, and a dry run of `--address ores.cpp` against a
mature part (`ores.iam/core`) emits only `export.hpp` and `tests/main.cpp`.
