* Acceptance

- One current row exists per product type code in the whole database.
- A tenant provisioned from scratch reads the system rows and can book against them.
- The trade check reads the system rows, and no reader names a tenant copy.
- The migration removes the per-tenant copies from an existing database and runs twice without effect.
- compass db recreate ends in the same state.

* Plan

The catalogue is already seeded into the system tenant, and the trade check
already reads those rows by naming the system tenant. What is missing is the
read and the copy.

- Give the three tables the own-or-system-tenant policy, so a session reads its
  own rows and the system tenant's and writes stay its own. This is the shape the
  meta model calls =:rls_own_or_system_tenant_rows:=, not the system-tenant
  widening, which is for a session that must see every tenant.
- Mark the three entities =:system_tenant_visible:= in their repository drawer.
  Without it the generated read filters on the session's tenant alone and a
  tenant reads nothing, because the policy admits rows the query has already
  excluded.
- Stop the provisioner copying the catalogue into each tenant.
- Delete the copies an existing database holds, in a script that runs with the
  seed and does nothing on a second run.
- Prove it: a session of a provisioned tenant reads the catalogue, and the
  database holds no copy.

* Notes

** 2026-11-02 — the catalogue is one copy

The provisioner's copy was a bridge. The previous task replaced the trade type
table, and the tables were tenant-isolated, so a tenant that booked a trade saw
no product types unless the catalogue was copied to it. That copy is gone, and
the isolation it made necessary with it.

The two halves have to move together. The policy on its own is not enough,
because the generated read names the session's tenant: a tenant would ask for
its own rows, the policy would not matter, and it would read nothing. The
repository flag on its own is not enough either, because the policy would refuse
the rows the query asked for. Both are stated, and the suite proves the read.

Provisioning a tenant end to end runs and generates its trades, so the trade
check reads the one catalogue while the writes land in the tenant.

** 2026-11-02 — the review found the cleanup did nothing

The cleanup script deleted no rows. Each of the three tables carries an
=on delete ... do instead= rule that turns a delete into an update of
=valid_to=, so the delete closed nothing, and the guard the generator now adds
to that rule compares against a session tenant the populate scripts never set.
The copies stayed, and the suite passed because it ran on a database recreated
from scratch, where no copy had been made. The script now disables the rule
around the delete, the way the tenant purger removes a tenant's rows, and it was
run against a database that did hold copies: 5 product type rows and 4 family
rows deleted, none left, and a second run deleting none.

The write-half test asserted the text of the policy rather than its behaviour.
It now updates a shared row from a tenant session and expects the refusal, and
deletes one and expects the system row to stay open, which also covers the rule
guard. The counts a tenant reads are compared against what the system session
read in the same run, so the suite does not break when the catalogue grows.

A tenant cannot override a catalogue row: it reads the system's, and a save
would be a write of a row it does not own. The catalogue is read-only to a
tenant, and a screen that offers an edit for a shared row is offering a write the
database refuses. That is stated here rather than left to be discovered, and the
screens that draw it are a later task.

* Result

One catalogue exists, and every tenant reads it.

=ores_trading_product_types_tbl=, =ores_trading_product_type_asset_classes_tbl=
and =ores_refdata_product_family_codes_tbl= carry the own-or-system-tenant
policy: a session reads its own rows and the system tenant's, and writes stay
its own. The generated repositories read both, which is the half that makes the
policy reachable. The delete rules state the own-tenant limit themselves,
because a rule runs with the owner's rights and row-level security does not bind
it.

The provisioner no longer copies the catalogue into a tenant. A script that runs
with the seed deletes the copies an existing database holds; it disables the
soft-delete rule around the delete, because the rule would only have closed the
rows, and a closed copy is still a copy the next session reads.

Gates at =7eb7691dd5=: 47 local checks, 98 C++ suites, and 77 pgTAP suites on a
database recreated from the commit. Provisioning a tenant from scratch reads the
one catalogue: afterwards the database holds 121 product types with no copy under
any tenant, no market copy and no family copy, and the tenant session reads 121
types and 8 families.

A tenant cannot override a catalogue row. It reads the system's, and a save would
be a write of a row it does not own, so the catalogue is read-only to a tenant.
The screens that draw it come later, and they must not offer the edit.
