* Goal

* Acceptance

- The ledger is readable and writable by a session of the system tenant only, and a test shows that a tenant's session reads none of it.
- The dispatcher queues each result it creates, and a submit removes its entry.
- A claim takes the next entry for the node's platform with skip locked, and two claims never take one entry.
- A claim chooses across tenants, so with two tenants queued the claims alternate between them.
- A claim enters the owning tenant to mark the result in progress. A result that is no longer waiting ends the claim for that entry, which is deleted, and the server takes the next.
- The token in the reply is minted at the claim and covers the keys of that job. If IAM refuses, the entry returns to the queue.
- The heartbeat extends the lease of every entry the host holds.
- A submit for a result whose entry is claimed by another host changes nothing. A result with no entry is accepted as before.
- The check and the write of a submit are one conditional update, so two concurrent submits cannot both write. The first task reads the state and writes afterwards, which leaves a gap that this task closes.

* Result

The installation owns a work ledger, =ores_compute_work_ledger_tbl=, with one entry for each result that waits or runs. Only a session of the system tenant reads or writes it. The policy is written =tenant_id = current and tenant_id = system=, so it admits no tenant's rows to anyone else, and the RLS guard does not flag it. The dispatcher queues each result it creates, and the server serves =compute.v1.ops.claim_work= from the ledger.

A claim takes the next entry for the node's platform in one statement with =for update skip locked=, prefers the tenant with the fewest entries claimed, then the priority and the age, and sets the host, the lease and the attempt. It then enters the owning tenant, mints the storage token for that job, and marks the result in progress. A result that is retired, done or gone ends the claim for that entry, which is dropped, and the server takes the next. The heartbeat extends the leases of a host, and a submit from a host that does not hold the claim is ignored, while a result with no entry is accepted as before.

Verified by 11 repository tests against the database, including skip locked, the fair order, the priority, release, extending a lease, and that a tenant's session reads and writes none of the ledger. Pure tests cover the grant builder and the holder check. Verified live, with the push wrappers stopped: the dispatcher queued three jobs for each of two tenants, four claims alternated between the tenants and returned tokens, the ledger showed four claimed entries with leases of five minutes, a submit from another host was ignored, the holder's submit was accepted and removed its entry, and a claim dropped an entry whose result had been retired and served the next.

Not done here, as planned: the wrapper does not claim yet (the next task), the push queue still runs beside the ledger so entries for results the push queue finishes are removed by the submit, and the reaper over expired leases and the bound for each tenant are in the task after next. A result with no entry is accepted as before until the push queue is removed. The ledger is hand-written and the capture "Codegen an installation-owned current-state table" records why.
