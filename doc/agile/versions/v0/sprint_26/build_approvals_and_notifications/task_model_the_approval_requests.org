* Acceptance

- Five codegen models in projects/ores.inbox/modeling generate the tables, with
  primary keys, foreign keys to IAM accounts and permissions, and validation of
  the system-tenant lookups.
- The database refuses a decision by the person who asked, a withdrawal by
  anyone else, and a second approval by the same person.
- A recreate seeds the six states, six decision types and the iam.role_grant
  kind, and the inbox permissions.
- The scaffold stubs are gone; the parts build and their tests pass.

* Plan

- The three lookups use the simple-lookup profile, held by the system tenant
  like IAM's account statuses. A request or decision checks its codes through
  the lookup's validation function, because a same-tenant foreign key cannot
  see system-tenant rows.
- The request and decision use the uuid-identified-lookup profile, with
  row-level security and foreign keys to IAM accounts.
- The four-eyes rule and the one-approval-per-person index live in a
  hand-written SQL file beside the generated tables, since codegen has no paste
  block for a trigger.
- Hold reasons wait for the first kind that holds; the role request does not.
- The kind's expiry is a nullable number of days, null meaning no expiry.

* Result

Five models generate the approval tables: kinds, request states and decision
types as system-tenant lookups, and the request and decision as tenant-scoped,
row-level-secured records with foreign keys to IAM accounts. Every reference to
a system lookup, the kind's permission included, is a foreign key with
=:use_system_tenant:=. The one-approval-per-person rule is a modelled partial
unique index; the four-eyes rule is a hand-written trigger, the one rule
codegen cannot express.

A recreate seeds six states, six decision types, the iam.role_grant kind and
the inbox permissions. The probe in =evidence/inbox_rules_probe.sql= shows the
database refusing an unknown kind, the asker deciding, a stranger withdrawing
and a second approval by one person, and accepting another person's approval
and the asker's withdrawal.

Hold reasons wait for the first kind that holds; the role request does not.
