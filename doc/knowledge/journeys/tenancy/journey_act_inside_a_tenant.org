This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A system administrator opens one tenant and reads its parties and people in place; the server reads them inside the tenant for each read, and the person never enters or leaves anything.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

"* Goal

"I want to see who is in this tenant and how it is organised." The system
administrator opens a tenant and reads its parties and its people on the
tenant's own screen, as tabs beside its details. The journey is done when the
administrator has read what they came for; there is nothing to leave.

The tenant's data is still read from inside the tenant. The server holds a
session in the tenant for each read, and only for that read, so the tenant's
audit trail says who looked, and the administrator's own session never changes.

* Actor and trigger

The system administrator: an account that holds the =SuperAdmin= role in the
system tenant, with the permission =iam::tenants:impersonate=. The trigger is a
question that only the tenant's own data answers: which parties it holds, who
has access, what its members signed in to. The journey starts on the tenant's
screen in [[id:9A77690B-8190-4237-94F1-D8111F3FB0B9][See one tenant]] and ends
when the administrator leaves the tenant.

The rule behind the journey: a tenant's data is read from inside the tenant.
The session's token names the tenant, row-level security scopes every read from
it, and no read takes a tenant as a parameter. So the administrator does not
get a second, cross-tenant way to read; they get a session in the tenant, and
the ordinary reads do the rest.

"* Steps

1. *Open the tenant.* From the roster, or from the home page, the
   administrator opens a tenant. Its screen opens on the *Overview* tab: what
   the tenant is and how its setup went.
2. *Read its parties.* The administrator chooses the *Parties* tab. The server
   enters the tenant, lists its parties with =refdata.v1.parties.list= a page
   at a time, and leaves. Each party names the party it belongs to, and shows
   its business centre with the flag of the centre's country.
3. *Read its people.* The *People* tab lists the accounts that can sign in to
   the tenant, the same way, each with their picture or, without one, their
   initials.
4. *Move on.* The administrator goes back to the roster, or anywhere else.
   Their session is system administration throughout: the menu, the home page
   and every other read are unchanged by the tabs.
5. *Refused.* A session that is not in system administration, an account
   without =iam::tenants:impersonate=, the system tenant, or a tenant no row
   names is refused with a reason. A suspended or terminated tenant can be
   read: its data is still there, and reading it is how an administrator
   decides what to do with it.

The tabs write nothing. A quiet *View only* label says that the tenant's own
administrators make the changes. Each read inside the tenant carries the
administrator's own read permissions, resolved from their roles in the system
tenant and filtered to the =:read= codes, so every service refuses a write that
checks its permission. The token names the tenant the administrator acts from
in the claim =acting_from_tenant_id=, and refresh refuses a token that carries
it. A system administrator changes a tenant in one way only: by removing the
whole tenant, from system administration.

"* Screens and wireframes

No new screen. The tenant's screen gains *Parties* and *People* tabs beside
its *Overview*, and the [[id:DD68AA9D-6EA5-477A-8432-566962D938FB][Home screen prototype]] draws them. The
wireframe below is the first design, which entered the tenant with a button
and showed a banner on every screen while inside; the tabs replaced both.

* Operations and messages

#+ATTR_HTML: :class hug-leading
| Step | Operation | Subject | Status |
|------+-----------+---------+--------|
| Read a tab | Issue a session scoped to one tenant, record the entry | =iam.v1.ops.enter_tenant= | exists |
| Read the tenant | List the tenant's parties, paged | =refdata.v1.parties.list= | exists |
| Read the tenant | List the tenant's accounts, paged | =iam.v1.accounts.list= | exists |
| After the read | End the tenant session, record the exit | =iam.v1.ops.leave_tenant= | exists |

=iam.v1.ops.enter_tenant= is a domain operation, because it acts on a session
and not on an entity. Its request names the tenant by id. Its reply is the
token, the tenant's name and code, the party the session acts as, and the
access lifetime. The token carries the tenant, the tenant's system party, every
party of the tenant as visible, the administrator as subject and actor, and a
claim that names the tenant the administrator acts from, so audit columns and
the banner can say who is really acting.

The browser reaches the tenant's data through the BFF, as
=GET /api/tenants/:code/parties= and =GET /api/tenants/:code/people=. For each
request the BFF enters the tenant, reads, and leaves, whether or not the read
succeeds. The tenant token is held for that read alone and never put on the
browser's session, so any other request the browser makes meanwhile is answered
as system administration. Each read therefore records one entry and one exit
in the tenant's audit trail. The pictures and flags a page names are read in
that same visit and kept by the BFF, so the browser fetches each one from
=GET /api/tenants/:code/images/:id= with no further entry. Leaving does not
revoke the tenant token, because no token is revoked in this system; it lasts
at most one access lifetime.

* What is missing

1. *Closed: a session scoped to another tenant.* =iam.v1.ops.enter_tenant=
   and =iam.v1.ops.leave_tenant=, in the operation model
   =ores.iam.tenant_session_messages=, issue and end it. The entry checks
   =iam::tenants:impersonate= against the database, because a person's token
   carries no permissions.
2. *Closed: a claim that says who is really acting.* The token carries
   =acting_from_tenant_id=, and refresh refuses a token that carries it.
3. *Closed: the cross-tenant party read.* =refdata.v1.parties.list-of-tenant=
   is removed; the parties are read inside the tenant.
4. *Closed: a person's token carries their permissions.* Login, party
   selection and refresh read the effective permissions, and an empty list
   refuses every check
   ([[id:31644F1D-5A51-4742-BF6B-1E72F4697229][Give a person's token the permissions they hold]]).
5. *Closed: no entering or leaving.* The tenant's parties and people are tabs
   on its screen, and the server holds the tenant session for each read
   ([[id:4F510088-2ABB-4204-A5E1-90B1C112BAA7][Make the shell speak to people plainly]]).
6. *The tenant's accounts are read, not its sessions or sign-ins.* The tabs
   show parties and people. Reading a tenant's sessions and failed sign-ins
   from system administration has no tab yet.
