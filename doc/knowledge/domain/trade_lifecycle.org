* Overview

A trade's operational state follows a finite state machine. This document
describes that machine: the states a trade can be in, the events that cause
transitions between them, and the taxonomy of activity types used for P&L
attribution and reporting.

[[id:DCF3C3CD-23E5-4F45-AE9C-CA91CC7F3B08][Trade status FSM implementation]] covers how the machine is held
in the database.

* Two Core Concepts

Trade status and activity type are distinct concepts that are often confused
because both relate to what has happened to a trade. They serve different
purposes and must be modelled separately.

** Trade Status

The /trade status/ is the operational state of a trade at a given moment. It
answers the question: /what state is this trade in right now?/

Status drives:
- Whether a trade is included in risk and P&L calculations (only =live= trades).
- What operations are permissible on the trade.
- Reporting and reconciliation filters.

** Activity Type

The /activity type/ classifies the event that created or changed a trade record.
It answers the question: /why does this trade record exist, and what kind of change
does it represent?/

Activity type drives:
- P&L attribution: which P&L bucket did this change fall into?
- Trade activity reporting: how is the day's activity broken down?
- Confirmation workflow: does this activity require a new legal confirmation?
- Audit and reconciliation.

Activity types are grouped into four categories: New Activity, Life-Cycle Event,
Misbooking, and Valuation Change.

* Two Machines

A trade runs two state machines, and they answer different questions.

| Machine | Question | Spine | Applies to |
|---------+----------+-------+------------|
| *Internal* | Where has this trade got to in our books? | The audit spine, moving on the internal version | Every trade |
| *External* | What have we and the counterparty agreed? | The commercial spine, moving on the external version | Trades faced outward |

[[id:74721BF2-2290-4AA7-8871-E215DA04351F][Confirmations and deal versioning]] draws the same division from the
version side: the internal version moves on every recorded change,
while the external version moves only when the terms the customer
agreed to change. The machines are that rule expressed as state.

The consequences differ in kind, which is the evidence that these are
two machines and not one. An unverified trade is an internal control
exception. An unconfirmed trade is a counterparty risk, because the
terms are not enforceable in the form the parties agreed.

Neither machine reads the other's state. Each is complete on its own
terms, and they meet only in a shared vocabulary of events and one
shared state.

** The internal machine

Every trade runs this one, whatever it faces.

[[proj:doc/knowledge/domain/trade_lifecycle_internal.png]]

| State | Description | Initial | Terminal |
|-------+-------------+---------+----------|
| =booked= | Recorded in our books. | Yes | No |
| =verified= | Our record matches the execution. | No | No |
| =live= | Contributing to risk and P&L. | No | No |
| =expired= | Contract ceased naturally: expired, matured, exercised. | No | Yes |
| =cancelled= | Removed from the book. | No | Yes |

| From | To | Event | Notes |
|------+----+-------+-------|
| (initial) | =booked= | Book | Any trade-creating activity. |
| =booked= | =verified= | Verify | Our record is checked against the execution. |
| =verified= | =live= | Confirm | The counterparty has agreed the terms. |
| =verified= | =live= | Activate | There is nobody to agree terms with. |
| =live= | =expired= | Expire / Mature / Exercise | Contract ceases naturally. |
| =booked= | =cancelled= | Cancel | Cancelled before verification. |
| =verified= | =cancelled= | Cancel | Cancelled before activation. |
| =live= | =cancelled= | Cancel / Terminate | Cancelled or terminated while active. |

Two events reach =live=, and the machine does not distinguish the
kinds of trade that send them. It has no knowledge of counterparties
or of confirmation.

Authorisation is not a state here. It is our workflow rather than a
term of the deal, so it is metadata on the trade.

** The external machine

A trade runs this one where it faces a counterparty with terms to
agree. An intra-entity transfer has nobody to agree with, and a test
or hypothetical booking agrees nothing, so for those the machine never
starts.

[[proj:doc/knowledge/domain/trade_lifecycle_external.png]]

| State | Description | Initial | Terminal |
|-------+-------------+---------+----------|
| =unconfirmed= | Terms not yet agreed. | Yes | No |
| =queried= | The two records differ. | No | No |
| =affirmed= | Both sides agree the economic terms. | No | No |
| =confirmed= | The binding written record, as of an external version. | No | No |
| =cancelled= | Nothing left to agree. | No | Yes |

| From | To | Event | Notes |
|------+----+-------+-------|
| (initial) | =unconfirmed= | Book | The trade exists; the terms are not yet agreed. |
| =unconfirmed= | =affirmed= | Affirm | The counterparty agrees the economic terms. |
| =unconfirmed= | =queried= | Query | The counterparty's record differs from ours. |
| =queried= | =affirmed= | Resolve | The difference is settled. |
| =affirmed= | =confirmed= | Confirm | The binding record supersedes the earlier agreement. |
| =confirmed= | =unconfirmed= | Amend | A confirmable amendment moves the external version. |
| any | =cancelled= | Cancel | The trade is cancelled at any point. |

Only =cancelled= is terminal. A confirmed trade returns to
=unconfirmed= whenever a confirmable amendment moves the external
version, which is why confirmation is stated as of a version rather
than once and for all.

** How the machines relate

They share a vocabulary of events and one state. Nothing else connects
them, and neither inspects the other.

| Event | Internal machine | External machine |
|-------+------------------+------------------|
| Book | (initial) → =booked= | (initial) → =unconfirmed= |
| Verify | =booked= → =verified= | — |
| Affirm | — | =unconfirmed= → =affirmed= |
| Query | — | =unconfirmed= → =queried= |
| Resolve | — | =queried= → =affirmed= |
| *Confirm* | =verified= → =live= | =affirmed= → =confirmed= |
| Activate | =verified= → =live= | — |
| Amend | — | =confirmed= → =unconfirmed= |
| Expire / Mature / Exercise | =live= → =expired= | — |
| *Cancel* | any → =cancelled= | any → =cancelled= |

Two events are broadcast to both machines, and they are the whole of
the relationship.

*Confirm* advances the external machine to =confirmed= and the
internal machine to =live=. Neither transition is conditional on the
other; both machines simply respond to the same event.

*Cancel* terminates both, in the one state they share. A cancelled
trade is cancelled in our books and has nothing left to agree with
anyone, and the shared colouring in both figures marks it as the same
state.

The arrangement decides the case that a single machine cannot express.
A trade with no counterparty never emits Affirm, Query or Confirm, so
its external machine never leaves =unconfirmed= and is simply not
consulted. Its internal machine reaches =live= on Activate instead.
[[id:03C12558-69AC-4925-AAE1-85FFF75B10BA][Counterparty scope and booking nature]] sets out which trades those are.

Adding a third machine needs no change to either of these. A
settlement or a confirmation message has its own states and subscribes
to the events it cares about, which is how Calypso separates trades,
payments and messages.

* Temporal Versioning and Amendments

** Normal Amendments

When a trade's terms are amended (e.g. Restructure, Novation, Upsize), ORE
Studio does not create a new trade record. Instead, it uses temporal versioning:

- The existing trade row's =valid_to= is set to the current timestamp.
- A new row is inserted with the same =id=, =valid_from= set to now, and
  =valid_to= set to infinity.
- The new temporal version carries status =booked=, pending re-confirmation of
  the amended terms.
- On confirmation, the status transitions to =live=.

This preserves the full amendment history of the trade under a single =id=.

#+begin_example
trade_id = X
─────────────────────────────────────────────────────────────────
 valid_from    valid_to       status   terms
─────────────────────────────────────────────────────────────────
 2026-01-10    2026-03-01     live     notional=10M
 2026-03-01    ∞              new      notional=15M   ◀ upsize
─────────────────────────────────────────────────────────────────
#+end_example

** Cancel and Rebook

The =successor_trade_id= field is used exclusively for /cancel and rebook/
scenarios, where a trade is cancelled and an entirely new trade is created to
replace it. This is distinct from a normal amendment:

- The original trade is moved to =cancelled= status.
- A new trade with a fresh =id= is created (entering =booked= status).
- The new trade's =successor_trade_id= is set to the original trade's =id= for
  traceability.

Use cases: Misbooking correction, administrative re-booking.

** Misbooking Correction

A misbooking creates a /correction trade/ with =successor_trade_id= pointing to
the erroneous original:

1. Original erroneous trade: status → =cancelled=.
2. Correction trade created: fresh =id=, =successor_trade_id= = original =id=.
3. Correction trade status begins at =booked=, and reaches =live= through
   verification and, where the trade faces a counterparty, confirmation.

* Activity Type Taxonomy

Activity types are used for P&L attribution and trade activity reporting. They
are classified into four categories.

** New Activity

New Activity events require legal confirmation. They produce a trade record in
=booked= status, reaching =live= through verification and, where the trade
faces a counterparty, confirmation.

| Activity Type      | Description                                                                                                              | Status Effect                                                           |
|--------------------+--------------------------------------------------------------------------------------------------------------------------+-------------------------------------------------------------------------|
| New                | A new legal contract. Trade exists today but did not exist yesterday.                                                    | New trade → =booked=                                                       |
| Close-Out          | Equal and opposite trade to close an existing open position. May include a value-transfer deal (buyout, buy-back).       | Original trade → =cancelled=; new close-out trade → =booked=              |
| Early Termination  | Trade terminated before its scheduled maturity. Covers close-out, tear-up, and compression (netted swap elimination).   | Original trade → =cancelled=; termination trade → =booked= if applicable  |
| Restructure / Roll | Terms of an existing trade renegotiated: components added, removed, or heavily modified. Requires new confirmation.      | New temporal version of trade → =booked=                                   |
| Partial Close-Out  | Notionals of an existing trade reduced. Also known as tear-up or downsize. Requires new confirmation.                    | New temporal version of trade → =booked=                                   |
| Upsize             | Notionals of an existing trade increased. Requires new confirmation.                                                     | New temporal version of trade → =booked=                                   |
| Novation           | Trade counterparty changed (assignment). Bank may step in/out with or without risk change. New confirmation required.    | New temporal version of trade → =booked=                                   |
| Funding Roll       | P&L from new funding tickets rolling a book balance from day T to T+1. Includes interest paid/received on the position. | New trade → =booked=                                                       |
| Contra Revenue     | Revenue reduction (expense-like): brokerage, agency commissions, bullion fees, sales credits, transfer pricing.         | New trade → =booked=                                                       |
| CVA / WWR          | Credit Valuation Adjustment or Wrong-Way Risk trade. Captures counterparty default risk and correlated credit exposure.  | New trade → =booked=                                                       |

** Life-Cycle Events

Life-Cycle Events are changes to the value of the trade specific to the terms of
the original contract. No legal confirmation is required.

| Activity Type      | Description                                                                                                              | Status Effect             |
|--------------------+--------------------------------------------------------------------------------------------------------------------------+---------------------------|
| Rate Reset         | Daily fixing impact: actual rate versus previous day's projected rate, for floating-rate products such as IRS.           | None                      |
| Floating Reset     | Floating rate reset per the terms of the trade; similar to Rate Reset but may also include spread changes.               | None                      |
| Fixings            | A fixing has been published; cashflows referencing the fixing are updated. P&L captured between day-0 and cash trade.    | None                      |
| Notional Reset     | Notional changes per contract terms (e.g. resettable notional). Not an upsize or downsize; no confirmation needed.       | None                      |
| Strike Reset       | Strike reset per contract terms. Supported for resettable call/put and resettable double-digital barriers.               | None                      |
| Expired            | Trade status changed because it expired out of the money, referenced against an expiry fixing.                           | =live= → =expired=        |
| Exercised          | Trade status changed because it was exercised in the money, referenced against an expiry fixing.                         | =live= → =expired=        |
| Physical Delivery  | Physical settlement during the life of the trade or at expiry.                                                           | None                      |
| Cash Settlement    | Cash payment during the life of a trade or at expiry. Includes option rebates.                                           | None                      |
| Maturity           | Contract ceases after its last fixing or payment. Trade has passed its maturity date. No confirmation required.          | =live= → =expired=        |
| Triggered          | Trade amended due to a barrier trigger event.                                                                            | Depends on trigger type   |
| Corporate Actions  | Action initiated by a company that impacts issued equity or debt.                                                        | None                      |
| Rebalance          | Change to various components per a defined event within the original confirmation.                                       | None                      |
| Amortisation       | Change in notional per the terms of the initial trade.                                                                   | None                      |

** Misbooking

A misbooking is a change to a trade due to an error in the booking terms of the
original contract.

| Activity Type | Description                                                                                                              | Status Effect                                           |
|---------------+--------------------------------------------------------------------------------------------------------------------------+---------------------------------------------------------|
| Misbooking    | Correction of an erroneous booking. Creates a correction trade with =successor_trade_id= referencing the original trade. | Original → =cancelled=; correction trade → =booked=        |

** Valuation Changes

Valuation Changes are changes to the value of a trade that are not specific to
the terms of the contract. They represent changes in analytics, models, or static
data inputs. No confirmation is required. These are treated as amendments — they
do not change the trade's operational status.

| Activity Type               | Description                                                                                         | Status Effect |
|-----------------------------+-----------------------------------------------------------------------------------------------------+---------------|
| Model / Model Parameters    | P&L from changes within valuation models impacting trade value.                                     | None (amend)  |
| System Release / Analytics  | P&L from changes within valuation models due to a system or analytics upgrade.                      | None (amend)  |
| Static Data                 | Amendments to static data inputs to the trade (e.g. counterparty change affecting funding curves).  | None (amend)  |
| Script Changes              | Change to the valuation script for structured trades, impacting trade value.                        | None (amend)  |

** Cancellation

| Activity Type | Description                                                                                             | Status Effect          |
|---------------+---------------------------------------------------------------------------------------------------------+------------------------|
| Cancel        | Trade removed or set to Cancelled/Deleted status. Leads to reversal of historic ledger postings.        | any state → =cancelled= |
