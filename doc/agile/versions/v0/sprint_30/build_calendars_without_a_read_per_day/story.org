* Goal

Provisioning a tenant builds its holiday calendars well inside the =build_calendars= step's 600 s, so a new tenant is ready without a manual rebuild.

On 2026-11-10 the step timed out on this machine. The step started at 22:38:20 and the client stopped waiting at 22:48:20. The refdata service wrote each calendar of 13,515 days in about 35 s, and it went on until 23:01:58. For each day, the batch write of =calendar_date_repository= read the day's current version in its own transaction (=begin=, =set_config=, =select=, =commit=) before the insert. =pg_stat_statements= for the database counted 454,068 such transactions for 445,995 inserted days. The server spent about 2 minutes on them, and the run took about 24 minutes, so round trips cost the rest. The materialiser had already read the calendar's existing days, and it passed on only the new ones, so each read only found that the day did not exist.

* Decisions

- The materialiser states a new claim for each day it writes, and the repository keeps its API. The materialiser already reads the calendar's existing days and passes on only the new ones, so a read for each day only repeats it.
- A new claim is version 0, and the insert trigger checks a version only when it is not 0. So a day that a concurrent materialisation wrote between the read and the insert gets a second version with the same value. The old code read the day's version just before its insert, so it also wrote a second version. Only materialisations write these rows, and they write the same values, so this is accepted.
- The calendars stay one after the other. Each one is now in-memory work and one pipelined write, and parallel writes would add contention on a database that several environments share.
