#+title: Storage policy
#+description: How object storage assigns ownership: one bucket per tenant and data class, the key grammar that addresses a report and its runs, the object capability each caller presents, and the rule that storage never trusts a key.
#+type: knowledge
#+level: cross
#+filetags: :knowledge:architecture:storage:multi_tenancy:security:target_state:

* Summary

Every object has one owner: a tenant or the platform. The bucket names the
owner and the data class, and the key names the object within it. A tenant
therefore owns a bucket, never a prefix inside a shared bucket, and one
tenant's bytes can never sit beside another's under one allocation.

Access is by *object capability*: a signed, short-lived grant that names the
exact buckets and key prefixes a caller may touch and the operations it may
perform. Storage verifies the grant and the ownership of the key it is asked
to move, so the caller never derives authority from knowing a key. A step
service presents its run token; a worker node presents a grant minted for the
one assignment it is running; a person presents their session.

This page settles the tenancy question [[id:286B7167-9B8A-4937-BBA5-E9D285AFECE3][Object Storage]]
left open. It states the target, not the shape of the tree today; see
[[*Distance from today]].

* The owner of an object

An object is owned by exactly one of two parties:

- a *tenant*, for bytes a tenant caused to exist: a run's inputs, an engine's
  output, a report's data;
- the *platform*, for bytes the deployment provides to every tenant: engine
  and application packages, seed datasets, images and other reference
  artefacts.

Ownership is the security boundary, so it is stated where a policy can be
attached to it: the bucket. A prefix inside a shared bucket would leave the
boundary to be derived from the key on every request, and a single mistyped or
mis-parsed key crosses it. A bucket that is a tenant's cannot contain another
tenant's object at all.

Two consequences follow and are accepted:

- *Storage stops being one allocation.* The tree today runs one bucket,
  =ores=, and says a second bucket is a deployment decision
  ([[id:286B7167-9B8A-4937-BBA5-E9D285AFECE3][Object Storage]]). That is
  reversed here: the bucket set is part of the policy, and the deployment
  provisions it.
- *Every object moves.* There is no compatibility path from =ores/...=; the
  policy states the target and the migration is its own work.

* The bucket set

| Bucket | Owner | Purpose | Read by | Written by | Retention |
|--------+-------+---------+---------+------------+-----------|
| =platform.packages= | platform | engine and application version packages | nodes | the platform | long |
| =platform.artefacts= | platform | seed datasets, images, reference artefacts | services | the platform | long |
| =t.{tenant_id}.inputs= | tenant | run inputs, assembled bundles, packaged run archives | step services, the ore service, nodes | step services, the ore service | pruned at run end |
| =t.{tenant_id}.outputs= | tenant | engine outputs and report results | reporting | nodes | per the tenant's policy |

- ={tenant_id}= is the tenant's UUID. It is stable and unambiguous, and it is
  what the storage service checks a capability against. A short code may be
  added as a human-readable label in the middle of the name, but the UUID is
  the identity.
- The class segment is =inputs= or =outputs=. The two differ in retention, in
  who writes them, and in who reads them, which is what earns each its own
  bucket. They are not split per report: see [[*The key grammar]].
- =platform= is not a tenant and never appears in ={tenant_id}=. A platform
  bucket holds no tenant's bytes.

A new tenant gets its two buckets at provisioning, with the tenant's row. A
bucket that already exists is left as it is; the operation is
create-if-absent.

* The key grammar

Inside a tenant bucket:

#+begin_example
{definition_id}/{service}/{purpose}/{instance_id}/{name}
#+end_example

Inside a platform bucket:

#+begin_example
{service}/{purpose}/{id}/{name}
#+end_example

- =service= is the owning domain component in lower snake case: =reporting=,
  =ore=, =compute=. A service writes only under its own segment.
- =purpose= says what the object is for within that service, in the plural
  where it is a collection: =runs=, =packages=, =results=.
- =definition_id= is the report definition the bytes belong to. It is first so
  that one prefix selects everything a report owns, across services.
- =instance_id= is the report instance, so one run's objects stay apart from
  the next run of the same definition.
- =name= is the file's own name where the object has one, so =trades.msgpack=
  and =market_data.msgpack= under one run stay apart. An object that is the
  id's own archive carries no name and ends in its extension.
- =id= in a platform key identifies the platform object: the app version, the
  dataset, the image.

A segment holds letters, digits, dots, hyphens and underscores, and never a
slash. Dot and dot dot are refused, a slash is the only separator, and a key
can never leave the bucket that owns it. Storage validates a key only as a
path; it never parses a segment.

The grammar is a rule the domains keep and =ores.storage.api/net/object_keys.hpp=
is where it is written down and checked, as it is today. What changes is the
bucket it builds against and the leading =definition_id=.

* Addressing a report

The definition id first makes the report the unit of listing. With definition
abc = =4caf8694-3155-415f-960d-e88e44abcc02=, the inputs bucket holds:

#+begin_example
4caf8694-.../reporting/runs/fccf4a19-.../trades.msgpack
4caf8694-.../reporting/runs/fccf4a19-.../market_data.msgpack
4caf8694-.../ore/packages/fccf4a19-.../ore_package.tar.gz
#+end_example

| Question | Operation |
|----------+-----------|
| the inputs of one run (the code path) | read the exact keys; no listing |
| everything report abc owns on the input side | =list(t.{tenant}.inputs, "4caf8694-.../")= |
| one run of report abc | =list(t.{tenant}.inputs, "4caf8694-.../")= then the instance segment |
| a tenant's whole input side | the bucket |

A caller never walks other reports to find one: the store filters by prefix,
and a listing returns only the keys under it. The report definition owns the
prefix, not a bucket, because a bucket is an administrative unit and a report
is not: a tenant with a thousand definitions would otherwise own a thousand
buckets, each with its own policy, quota and lifecycle. Split a bucket only
when the administrative treatment differs, which for report data it does not.

* The object capability

A caller proves its right to an object with a capability: a signed token,
short-lived, that names what it may touch and nothing more.

#+begin_example
{
  "iss": "iam",
  "sub": "<the service or node the grant was minted for>",
  "tenant_id": "<the tenant whose buckets it may reach>",
  "grants": [
    { "bucket": "t.<tenant>.inputs",  "prefix": "4caf8694-.../", "ops": ["get"] },
    { "bucket": "t.<tenant>.outputs", "prefix": "4caf8694-.../fccf4a19-.../", "ops": ["put"] },
    { "bucket": "platform.packages",  "prefix": "app/.../1.8.17.0/", "ops": ["get"] }
  ],
  "exp": "<unix seconds, the assignment's deadline>",
  "jti": "<unique id, for the issue log>"
}
#+end_example

- IAM mints the token and signs it with the key it already publishes through
  JWKS, so storage verifies it without calling the issuer. This is the
  [[id:4E0D934A-21D4-4609-8B7C-29F6D9A6A52D][Access Token]] mechanism with an
  object scope rather than a permission scope.
- The scope is a set of grants, so one token covers the inputs, the output and
  the package of a job without granting the rest of the tenant's data.
- =exp= is the assignment's deadline. A token outlives its job by no more than
  the job's own grace.

Who presents what:

| Caller | Credential | Scope |
|--------+------------+-------|
| a person | session token | the tenant's buckets |
| a step service | its run token | the tenant's buckets |
| a worker node | an assignment capability | the exact keys of the assignment |
| the platform | a service token | the platform buckets, and any tenant bucket for provisioning and pruning |

The run token already carries the tenant and the party
([[id:78B82824-0BBB-4442-A9FA-E1F265DF57BD][Run grants and run tokens]]), so a
step service needs no second token to reach its tenant's buckets. Its party
does not narrow a bucket, because a bucket is a tenant's and the party is a
row-level concept; the storage service checks the tenant and no more.

* Enforcement

The storage service is the enforcement point. Before it moves a byte it
checks, in order:

1. *The token verifies.* Signature against the published key, and =exp= in the
   future.
2. *The operation is granted.* The request's operation is in some grant's
   =ops=.
3. *The key is inside a granted prefix.* The request's key starts with that
   grant's =prefix=, compared segment by segment so a prefix cannot match a
   sibling by string accident.
4. *The bucket is owned as claimed.* The bucket's tenant equals the token's
   =tenant_id=, and the bucket is one the grant names. This is the check that
   makes the rest defence in depth rather than the only control.

Today =objects_handler= checks one global permission, =storage::objects:read=
or =:write=, and trusts whatever bucket and key arrive. Under this policy that
permission stays as the coarse gate that says a caller may use storage at all,
and the capability decides which objects it may touch. A principal holding the
permission can then reach only the objects its capability names, and never
another tenant's.

Storage never derives a tenant from a request field a caller supplies. It
derives it from the bucket, which the policy fixed, and compares.

* Lifecycle

- *Inputs are the run's.* A run's inputs are pruned when the run reaches a
  terminal state. They are not the record of the run; the database is.
- *Outputs are the deliverable.* They are retained under the tenant's policy,
  and the report's post-processing reads them from the outputs bucket.
- *Platform objects outlive tenants.* A package is not re-uploaded per tenant
  and is not removed when a tenant is removed.
- *Offboarding is a bucket operation.* Because the tenant owns buckets, its
  data leaves with =drop bucket=, not with a prefix sweep that can miss a key.
  That is the second reason the owner is the bucket.

* Compute assignments

The worker node holds no standing storage credential. The orchestrator mints
an assignment capability for the job and puts it in the assignment, beside the
result id and the package, input and output keys. The node uses it to fetch
the package and the input and to write the output, and then it is done with
it.

- *One job at a time.* A node runs one assignment at a time, so it holds one
  job's capability and no other job is exposed by concurrency.
- *Sequential residue.* One job at a time is not enough on its own: a job's
  work directory must be removed when the job ends, or the next tenant's job
  can read the previous tenant's extracted input. The node owns that cleanup.
- *The package is shared.* The engine package is read from a platform bucket
  under a =get= grant, so every node reads the same bytes and a node can reach
  no tenant object it was not assigned.
- *Results return through the orchestrator.* The node sends the result id, the
  output key and the outcome; the compute service, under its own identity,
  loads the result row tenant-scoped, checks it belongs to the assignment's
  workunit, and records it. The node writes no tenant row and names no tenant.

* Distance from today

- *One bucket.* The tree runs one bucket, =ores=, and a deployment needs four
  classes of bucket, two of them per tenant.
- *A global permission.* =objects_handler= checks =storage::objects:read|write=
  and trusts the key. It must verify a capability and check the bucket's owner.
- *No capability exists.* There is no mint operation, no claim set and no
  issue log. IAM mints, storage verifies.
- *No tenant in any key.* Keys are =<service>/<purpose>/<id>[/<name>]= and name
  no tenant, and no definition id.
- *Bucket provisioning.* Buckets are created on first write by the store. A
  tenant's buckets must exist with the tenant, and offboarding must drop them.
- *The node holds a standing identity.* The wrapper authenticates to storage
  with its own service token, which reaches whatever that identity's
  permission reaches. It must present a per-assignment capability instead.
- *No lifecycle rules.* Nothing prunes a run's inputs; nothing retains an
  output under a policy.

* Decisions

- *The owner is the bucket, not the prefix.* A bucket cannot hold another
  tenant's object; a shared bucket with per-tenant prefixes leaves the
  boundary to a parse on every request.
- *One bucket set per tenant, by data class.* Inputs and outputs differ enough
  in retention and in who touches them to earn a bucket each. Reports do not:
  their identity is a key prefix, and a bucket per report is policy sprawl.
- *The tenant's UUID names the bucket.* It is stable, it is what a capability
  checks, and it survives a rename of the tenant's short code.
- *Access is an object capability.* Least privilege is per object, so knowing
  a key confers nothing, and a compromised node reaches only its own job.
- *Storage derives the tenant from the bucket, never from a request field.*
- *A step service presents its run token.* It is already tenant-scoped, so the
  run-token design needed no second credential.

* Open questions

- Whether the run token narrows to the run's key prefix, or a step service may
  reach its whole tenant's buckets. The run's own inputs argue for the
  prefix; another step of the same run may need the same bucket anyway.
- Whether a capability is minted by IAM or by the orchestrator holding a
  delegation. IAM signs today, and the orchestrator is the party that knows
  the exact keys.
- The exact retention of outputs, and whether it is per tenant or per report
  definition.
- Whether a deployment needs a =scratch= class for intermediate bytes that are
  neither a run input nor a deliverable.
