* Goal

Split from Browse, search and call operations through five tools. The five tools filter their lists by the grant's scope, reads alone for a grant that only reads, but not by the person's permissions, because no route states the permission its service checks: the services check it, behind NATS. Deriving one from a route's component and entity matched no permission resource for 267 of 1146 operations, and only loosely for the rest, and a list that hides an operation the person may call misleads more than one that shows an operation the call then refuses. Each route therefore declares the permission its handler checks, generated routes from their model and hand-written ones from the handler they reach, and the lists filter by the token's permissions.

* Acceptance

- Every generated entity route states the permission its handler checks, by the rule the handlers apply.
- list_areas, list_entities, list_operations, find_operations and call_operation show an operation that states a permission only when the token grants it and it is not withheld from agents.
- Narrowed when work started: the other routes state none yet, so no gate refuses them; see [[id:895DDD23-019B-4024-BCD8-E2F6C5822486][State the permission of the routes no rule derives]].

* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

- The generated handlers apply one rule, measured over 4,700 of them: a read
  checks =component::entity:read=, a put =:write=, a delete =:delete=. Only
  =list_roles=, =get_role= and =list_permissions= check none. A generated
  entity route already names its component, entity and identifier, so
  =entity_route_catalogue= states the same permission.
- The screen routes name their entity in the singular, the operation routes
  are IAM's and their handlers check a permission conditionally, and the
  compass-ng engine passes no model property a route template could read, so
  none of them state one here.
- The scope is narrowed to what can be derived exactly: a list that hides an
  operation the person may call misleads more than one that shows an
  operation the service then refuses.

* Result

The 414 generated entity operations state the permission their handlers
check, and the OpenAPI document carries it as =x-ores-permission=; none of
them names a permission no handler checks. The five MCP tools hide such an
operation from a token that lacks its permission, or whose permission no agent
may hold, and =call_operation= refuses it. The other 739 state none yet and
stay listed, which [[id:895DDD23-019B-4024-BCD8-E2F6C5822486][State the permission of the routes no rule derives]] takes up. Four booking routes main added
without a catalogue place, which kept the server from starting, are declared,
and an operation that validates is read as one that only reads.
