* Purpose

A list screen shows one row that joins several tables. A read model answers that
row with one query that the service pages, sorts and filters. The row has no
table of its own, so nothing writes it, nothing versions it and nothing
announces a change to it.

The profile keeps the read-only current-state surface: =list=, =get= and
=get_many=, with no write verb and no version read. It replaces the table with a
view. The model states the select in its =* SQL ** View= section, and the
generated view is =security_invoker=, so the tenant policies of the base tables
apply to the caller.

* Reference entity

None yet. The first model to bind it is the trade summary, in =ores.trading=.

A view has no rows of its own to announce, so the eventing facets go with the
notify trigger. A hard gate in =resolve_targets= withdraws them, for the same
reason as for the staging profile: a shape profile fixes
=ores.cpp.eventing-integration-test= to true, and two profiles that fix one
address differently are a binding the loader refuses.
