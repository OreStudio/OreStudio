This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A tenant administrator or market-risk owner names a report, binds the configurations it reads, chooses the analytics it runs and their settings, scopes it to a portfolio, saves it, reads back exactly what was written, and leaves it on demand or hands it to the schedule journey.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I need a new report that runs our analytics over my portfolio, and I need to be
sure it can actually run before I schedule it."

The person has a question the existing reports do not answer: another analytic
set, another portfolio, another party. They want a report definition they can run
and, later, schedule. The second half of the sentence is the hard one. A report
that runs nothing, or that runs an analytic whose input nothing produces, looks
complete on the screen and fails on the grid. The person wants the screen to say
what the definition needs before it leaves their hands, and to say plainly where
it cannot: nothing today answers "what does this report need in order to run"
beyond the configuration types its report type requires.

The journey is done when a definition exists that reads back as the person wrote
it: a name, a report type, five bound configurations, the analytics they chose
with their settings, and a portfolio scope. It has never run, and the front door
already draws that state.

* Actor and trigger

A tenant administrator or a market-risk owner runs this journey. The
administrator creates reports for the tenant's parties; the market-risk owner
creates the report the desk or the committee asks for. Both act inside one
party, and the party of a new definition is the party of the session, not a
choice.

The trigger is a request for a report that does not exist yet. A regulator asks
for exposure profiles the party does not produce, a committee wants the same
numbers over a portfolio nobody configured, or a party joins the group and needs
the reports its siblings already run. The person opens
[[id:891DE3CB-2374-4FD9-B7FB-D8892F5174A1][See the reports a party runs]], finds
no row that answers the question, and presses Create.

This journey writes a definition and the configuration it binds, and creates no
run. Nothing in the application creates a report today: no BFF route serves
reporting, and the definitions that exist were seeded. The screen this journey
describes does not exist, and the operations below are the ones it would send.

* Steps

The journey is four steps on the standard steps UI, the one the system bootstrap
journey uses. A step carries an id, a title for the rail, a lead sentence and a
body, and the last one is final; the rail is drawn from the same list, so the
rail and the steps cannot disagree
([[id:6A63AAC7-4869-493A-97E7-55B919874784][Journey runtime]]). Going back is
refused at the first step, and when the step before the current one is final
([[id:166B2D77-6D04-47D5-A651-5431E1F2E082][UX Language]], section *The rail*).

1. *What it is.* The person types a =name= and a =description=, and chooses a
   =report_type= from a combo box. The combo box reads
   =ores_reporting_report_types_tbl=, and the type is a category that also names
   the workflow which runs the report. One type is registered today: =risk=, the
   full ORE risk analytics run, which names =report_execution_workflow=. More
   types are expected, so the control is a combo box reading the table rather
   than a fixed set of choices: a type added as a row must appear without a code
   change. The name is unique within the party, so the screen refuses a name the
   party already uses and says which row holds it. The definition is created
   official unless the person clears =is_official=, and an official report never
   reads a sandbox: its scope cannot name a sandbox portfolio or a virtual book.
   The screen states that rule where the flag sits, because a person who clears
   it is widening what the report reads. The step also asks for the
   =concurrency_policy=, which decides the state a run is born in: skip, queue,
   or fail.
2. *What it reads.* The screen sends
   =reporting.v1.report_type_configuration_types.list= for the chosen type and
   shows every configuration type that type cannot start without. The five
   configuration types are the whole vocabulary: =conventions=,
   =pricing_engines=, =todays_market=, =curve_configuration= and
   =risk_report_config=. For each slot the person picks a configuration the
   party already holds: the screen lists the candidates with
   =reporting.v1.configurations.list_by_configuration_type_code= and writes the
   binding with =reporting.v1.report_configurations.put=, one row per
   configuration type. The screen says what each slot supplies, because a person
   choosing between two configurations needs to know what the choice decides:
   - =conventions= supplies the instrument conventions the trades are read with,
     one document for each convention kind.
   - =pricing_engines= supplies the pricing model of each product and its
     parameters.
   - =todays_market= supplies the market data a run prices against, by market
     role. The configuration binds one configuration to each role with
     =reporting.v1.configuration_market_bindings.put=.
   - =curve_configuration= supplies the curves: their definitions,
     bootstrapping, segments and quotes, and the volatility and correlation
     configuration.
   - =risk_report_config= supplies the ORE-level run settings a party shares:
     base currency, observation model, VaR and SIMM settings, and threading. It
     also carries the analytics the next step changes, and the scope.

   Each slot also names the screen that holds its data, because a person reading
   what their report reads should be able to reach it. *Only conventions has
   one*: =PATHS.conventions=, which is =/refdata/conventions=.
   =pricing_engines=, =todays_market=, =curve_configuration= and
   =risk_report_config= have no screen in the application, and the step states
   that rather than drawing a link that would not resolve. A configuration is
   never copied to be shared: several definitions bind the same row, so the
   screen names how many other definitions bind the configuration a person just
   chose. Nothing here creates a configuration, and nothing here writes the run
   settings inside a =risk_report_config=.

   The portfolio scope is not a field of the definition. It lives on the bound
   =risk_report_config=, in the portfolio and book junction tables keyed by that
   row, so choosing a configuration is choosing the scope the report reads. The
   screen reads the scope off the configuration and says so.
   **No operation in this journey's set writes the scope**, and *What is
   missing* records it.
3. *What it runs.* The person turns analytics on. The screen reads the
   vocabulary with =reporting.v1.analytic_types.list= and offers these fourteen
   analytic types, which are the whole picker: =npv=, =sensitivity=, =cashflow=,
   =curves=, =simulation=, =saccr=, =parametricVar=, =portfolioDetails=,
   =creditcurves=, =pfe=, =calibration=, =pnlExplain=,
   =historicalSimulationVar= and =xva=. Each choice is a
   =configuration_analytic= row carrying =analytic_type_code=, =display_order=
   and =active=, written with =reporting.v1.configuration_analytics.put= or
   =put_many=. Each analytic's settings are
   =configuration_analytic_parameter= rows of =parameter_name= and =value=, in
   positions, written with
   =reporting.v1.configuration_analytic_parameters.put=. An analytic is turned
   off by setting =active= false, never by deleting its row, so the settings stay
   readable for the person who turns it back on.

   Adding an analytic that the configuration carries no row for is a flow of its
   own, the one [[id:87B9678E-2085-4968-8AEA-7184D1384F1D][Change what a report
   runs]] carries: the list of the fourteen types, then the detail that states
   what the analytic is and how it is calculated with every parameter given a
   control chosen for its shape and a note on what it means, then the effect of
   turning it on. The flow writes one analytic row and its parameter rows.

   =pfe= reads a cube that =simulation= writes, so a report that enables =pfe=
   without =simulation= cannot work. The flow refuses to turn =pfe= on and states
   the rule where the two analytics sit. The statement is honest about where the
   rule lives: it is enforced by the ACME seeder, in
   =generate_risk_config_data.py=, function
   =check_exposure_needs_simulation=, and *nothing in the reporting service
   validates it when a definition is written*. A caller that does not use this
   screen can write the combination today, and the run fails later.

   The analytic rows hang off the configuration, and the configuration is
   shared, so the screen states which other definitions bind the same
   configuration and would run the changed analytic set from their next run. This
   is the one place in the journey where a person's local choice reaches rows
   they did not open, and the screen says so rather than hiding it behind a save
   button.
4. *Review and save.* The final step states every value before the write: the
   name, the description, the report type, the official flag, the five bindings,
   the analytics with their =active= and =display_order=, the parameter values,
   and the portfolio scope. On confirmation the screen sends
   =reporting.v1.report_definitions.put= for the definition, after the binding
   and analytic writes of steps 2 and 3. The definition is written on demand:
   =schedule_expression= is empty and =scheduler_job_id= is null. Its
   =fsm_state_id= is null until first activation, =run_grant_id= is null until the
   grant is created at admission, =pre_processing= is =execute=,
   =prepared_input_key= is empty, =post_processing= is =execute=, and
   =concurrency_policy= is the policy the person chose. Then the screen reads the
   definition back with =reporting.v1.report_definitions.get= and shows the stored
   row rather than the values the person typed, and lists the party's definitions
   with =reporting.v1.report_definitions.list= so the new row is visible among its
   siblings. The definition is bitemporal, so an edit writes a new version and a
   past run keeps the version it ran under.

   It has never run. There is no =report_instance= for it, so the front door
   draws it as never run, which is a state
   [[id:891DE3CB-2374-4FD9-B7FB-D8892F5174A1][See the reports a party runs]]
   already draws for the definitions the seed writes. =run_grant_id= is empty:
   the grant every run acts under is created at admission, by whichever act needs
   it first, scheduling or a person asking, so a definition that has never been
   scheduled can still run on demand.

   This step is final, so *Back is refused from it*, and the rail says so: the
   mark beside the review carries the final flag, and the step offers no Back
   ([[id:166B2D77-6D04-47D5-A651-5431E1F2E082][UX Language]], section *The
   rail*). Once the review has stated every value and the definition is written,
   there is no earlier state to return to. From here the person either stops, with
   a definition they can run when they want, or goes on to
   [[id:933649DD-1F86-4B40-99FD-1D4316D39A46][Choose when a report runs]] and
   gives it a recurrence. This journey writes no schedule, and nothing here makes
   the report produce anything: it creates the definition that a run or a
   schedule then uses.

* Screens and wireframes

One screen, four steps, on the standard steps UI: the rail the system bootstrap
journey draws, with the step list as its only source. The steps are *What it is*,
*What it reads*, *What it runs*, and *Review and save*, in that order. The rail
marks each step done, current or ahead, and it knows position only: it cannot say
how many items a save would refuse. The step floor carries Back unless going back
is refused, which it is at the first step and when the step before the current
one is final
([[id:6A63AAC7-4869-493A-97E7-55B919874784][Journey runtime]]); the review is
final, so it draws no Back at all.

The screen writes four kinds of row and reads each one back: the definition, the
bindings, the analytic rows, and the parameter rows. Two of its answers are
absences it must state rather than draw round. The first is the checklist: the
screen can name the configuration types the report type requires, and it cannot
name what else a run needs. The second is the analytic rule: the screen refuses
=pfe= without =simulation= because the seeder enforces that pair, and no service
check exists to point at. A third is where the configuration data lives: only
conventions has a screen, and the other four are stated as missing.

The prototype that argues this screen offered three structural variants of it, a
single form, a wizard and a checklist. The product owner chose the standard steps
UI, so the variants are gone and the screen commits to the four steps above.

* Prototype

The [[file:../../prototypes/reporting/create-a-report/][prototype]] draws this journey on the standard steps UI, and [[file:../../prototypes/reporting/create-a-report.org][its design note]] says what it follows and what is fake. It belongs at
=doc/prototypes/reporting/create-a-report/=.

The prototype must draw the four steps on the rail the system bootstrap journey
uses, with done, current and ahead marks and no Back on the final step; the five
configuration types with what each supplies;
the fourteen analytic types as a picker with =active= toggles; the refusal of
=pfe= without =simulation=, with the rule stated and the seeder named as where it
lives; the scope read off the bound configuration, since no operation writes it;
and a review that names the field values rather than counting them. It must label every drawn value a fixture, because no
operation here creates a report and no service check exists for the analytic
rule it refuses.

The definition is the row the journey creates and the other rows are what it
reaches: a binding names a configuration, the configuration owns the analytics,
and each analytic owns its parameters. That chain is why *What it runs* says whose rows the analytics are. A person
who changes the analytic set of a shared configuration changes what every
definition binding it runs, and no copy stands between them.

The scope is two levels down that chain: =risk_report_config= holds it in
=ores_reporting_risk_report_config_portfolios_tbl= and
=ores_reporting_risk_report_config_books_tbl=, keyed by that row. The definition
carries no portfolio field at all.

Every row above carries =party_id= and is party-scoped by row-level security. The
definition is bitemporal, so an edit writes a new version and a past run keeps
the version it ran under. The analytic rows and their parameters are temporal
too: turning an analytic off sets =active= false and writes a version, so the
row stays readable.

The writes are five: a definition, its bindings, its analytic rows, their
parameters, and a configuration when the party holds none of a type.
=reporting.v1.report_definitions.put_many= exists for a caller that creates
several definitions at once; this journey writes one, and a person creating the
next report runs it again. The
definition write is the only one that creates the row the front door then lists;
the others attach what the definition reads. =configuration_analytics.put_many=
exists for the case the screen builds a set and writes it once, and =put= for
the case a person flips one toggle.

Two of these writes reach rows the person did not open. A binding is shared with
every definition that binds the same configuration, and an analytic row belongs
to the configuration rather than to the definition, so a screen that edits the
analytic set of a shared configuration changes the next run of every definition
binding it. The journey states this and no operation warns about it.

No BFF route serves this screen. The prototype adds one, for example
=POST /api/reporting/reports= for the definition and its bindings,
=GET /api/reporting/reports/<definition-id>= for the read-back, and
=GET /api/reporting/report-types/<report-type>/configuration-types= for the
checklist half the screen can show. The handler authenticates the caller's token
and checks a report-definition write code, which does not exist yet.

* What is missing

1. *Nothing validates the rule between two analytics.* =pfe= reads a cube that
   =simulation= writes. That rule lives in the ACME seeder,
   =generate_risk_config_data.py=, function =check_exposure_needs_simulation=,
   and it is a guard over the seed's own data, not a constraint on the database
   and not a check in the reporting service. A definition written by any other
   caller can enable =pfe= without =simulation=, and nothing refuses it. The run
   then fails, later, on the grid. The screen this journey describes can refuse
   the pair, and it cannot make the refusal true for callers that do not use it.
   A report also needs at least one analytic: a run with none produces nothing,
   and nothing states that either.
2. *No operation answers what a report needs in order to run.*
   =reporting.v1.report_type_configuration_types.list= names the configuration
   types a report type cannot start without, and that is all. Nothing names the
   analytics a run must enable, the inputs each analytic reads, or the pairs that
   cannot work together. A screen therefore cannot show the full checklist a
   definition must satisfy, and it cannot answer the person's question "can it
   actually run" before the run. It can only show what it bound.
3. *No operation writes or reads the portfolio scope.* The scope lives on the
   =risk_report_config= row, in
   =ores_reporting_risk_report_config_portfolios_tbl= and
   =ores_reporting_risk_report_config_books_tbl=, and no operation in this
   journey's set touches either table. The scope a definition reads is the scope
   of the configuration it binds, and that configuration is built by the seeder.
   A person who needs a scope no configuration carries cannot state it here.
4. *Nothing creates the run settings inside a =risk_report_config=.* The base
   currency, the observation model, the VaR and SIMM settings and the threading
   are columns of a row this journey cannot write. When the party holds no
   configuration with the settings a new report needs, the journey stops.
5. *The refusal to save =pfe= without =simulation= is the screen's own rule.*
   The prototype draws it as a refusal. A build would have to keep that rule in
   the screen, since no service check exists, and a second client would have to
   keep it again.
6. *No BFF route serves reporting, and nothing in the application creates a
   report today.* Every definition that exists was seeded. This journey's screen,
   its review, its read-back and its refusals are new, and it has no row in any
   build to attach to.
7. *No write permission is named for creating a definition.* The reads in this
   journey's set are gated by the reporting service's read codes. No code names
   the right to create a definition or to change a shared configuration's
   analytics, and a person who may write one and not the other cannot be told
   apart. The tenant administrator holds =*= and reaches everything.
