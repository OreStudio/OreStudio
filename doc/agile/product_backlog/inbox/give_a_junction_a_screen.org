* What

Make a junction render a working screen. Probed with
=projects/ores.iam/modeling/ores.iam.account_party_junction.org=, given a
Presentation drawer and =:ores.ts.web.enabled:=. Three things are missing, and
only the first is what the code says:

- =ores.ts.web.bff_route.org= declares =#+model_types: domain_entity=, so a
  junction gets a declaration and UI metadata and no route. Its two siblings,
  =ores.ts.ui.org= and =ores.ts.web.org=, already admit =junction=.
- =write_record_for= derives the record from =entity['columns']=, which a
  junction does not have -- its fields are its two sides. The generated
  declaration came out with =writeFields: []=, so a save would send an empty
  record.
- The route has one path segment and a junction's key has two members.

* Why the stated reason is wrong

The archetype's own comment says a junction is not served because "its delete
request names one array per side, and the generic factory sends a single key, so
a junction route would silently drop half its key". That describes the shape the
canonical protocol replaced. The generated removal carries one key record with
both members:

#+begin_src typescript
export interface AccountPartyRemoval {
    key: AccountPartyKey;      // { account_id, party_id }
    precondition: Precondition;
}
#+end_src

So the factory does not have to send a pair of arrays, and nothing would be half
dropped. The real blocker is only that =keyField= is singular: the route's
address is one path segment and this entity's address is two values.

* Decision needed

How a two-member key is addressed by an HTTP path. Either the descriptor carries
a list of key fields and the path grows a segment per member
(=/api/account_parties/:account_id/:party_id=), or both values travel in the
query and body and the path carries a synthetic identifier. The first keeps the
rule that the address and the request state the same key, which is why the key
work was done; the second does not.

* Notes for whoever takes it

- Both sides are uuids, so the detail form's fields are not text a person can
  type. A usable screen needs lookup controls that name the account and the
  party, which the shared form does not have yet -- see the "dynamic_combo" and
  "LookupSource" support in =ui-contract.ts=.
- =order_column: party_id= is declared on the junction, so the list's order is
  the model's business rather than the screen's.
