* Goal

The previous task generated the wire form of dq's *domain* types. A dq process
does not send domain types: it sends =catalog_event=, =list_catalogs_response=
and their kin, which come from the protocol templates. Those still go through
reflect-cpp, so the component's actual traffic is unchanged. This task gives the
protocol messages the same treatment, and takes the chance to state each type's
field list once instead of twice.

* Plan

** Why the messages are a task of their own

The previous task proved the seam on domain types. A message is a different
shape: it holds domain types, other messages, vectors and optionals of both, and
it is the type the wire actually carries. Its codec also has to be reachable
from a translation unit that only saw the struct, which the domain half did not
need.

** The shape of the type is stated once, by the template that declares it

A codec file that repeats a struct's member list is a second statement of the
same fact, and the two drift. So the shape is stated as a =wire_fields= function
in the type's codec header, and the codec's translation unit iterates nothing:
it calls the function. That retired the domain half's list from its =.cpp= in
this task.

The list stays in the codec header rather than moving beside the struct, which
is where it would read best. A struct's own header is rendered for every
component, so stating the shape there means gating that template on the codec
facet's opt-in: machinery for no gain, because the two orders are still one
statement and the per-type byte comparison still proves the encoding. A message
states its shape the same way, for the same reason.

=wire_fields= is a free function found by argument-dependent lookup, so the
carrier layer can ask any type whether it has one: the two carriers,
=json_codec<T>= and =msgpack_codec<T>=, grow one =if constexpr= -- a type with a
=wire_fields= is an object, everything else keeps its text form. That is
what makes a message holding a domain type work: the encoder recurses through
the field list rather than knowing the type.

** Where the code lives

One codec pair per entity -- ={entity}_protocol_codec.\{hpp,cpp\}= -- not one
per struct: a protocol header declares a dozen structs, and a file each would
triple the file count for nothing. The header declares a =<message>_codec= struct
per message and the =wire_traits= specialisation that names it; the translation
unit defines them, which is the containment the previous task proved.

The protocol header includes the codec header at its end, so a translation unit
that sends a message sees the specialisation. Without that include the seam
silently falls back to reflect-cpp -- the failure mode the previous task's review
found and fixed.

** How it is proved

The per-message byte comparison, in both formats, over values the component's
own generators produce. Plus the domain half's existing comparison, which must
stay byte-identical while its field lists move out of the codec units.

* Notes

Every message a dq protocol header declares now carries a generated codec, and
the protocol header is what every sender includes, so the component's NATS
traffic takes the generated path end to end -- not only the domain types the
previous task proved. The seam needed no change: =wire_traits= was already the
one name.

** The shape is stated once, by the template that declares the struct

The protocol template writes a message's =wire_fields= from the same iteration
that writes its struct, so the two cannot drift and no second template states
the member order. The domain half moved to the same footing in this task: its
list sits in the type's codec header, which is the header a message that holds
the type includes.

The list is in a codec header rather than beside the struct because a struct's
own header is rendered for every component: stating the shape there means
gating that template on the codec facet's opt-in, which is machinery for no
gain while the order is stated once either way.

** The trait specialisation is the codec

The previous task put the four functions on a =<type>_codec= struct and had the
specialisation forward to them. The struct was a workaround for the read
direction, where two types differ only in what they return; a specialisation has
no such problem, so the struct is gone and the four functions are the
specialisation's own.

** The envelope needed carriers of its own

A message carries =result=, =precondition=, =order= and their kin, and those are
hand-written, so their shapes and their enums' text forms are hand-written too,
in =ores.utility/domain/protocol_codec.hpp= beside the structs. An enum travels
by the enumerator's name, which is what the reflector derives; the names are
spelled out rather than derived, so a rename is a change to the wire and says
so.

** The opt-in is what made it landable

The protocol header is rendered for every component, so the field list and the
specialisations sit behind the facet's own opt-in: a component that has not
opted in renders the header it has, byte for byte. The flag is resolved by the
same helper the other opt-in facets use, in =core.py=.

** One thing the field loop could not say

A message's fields state their own =name=, which shadows the message's name
inside the field loop, so the codec's member pointer (=&{{name}}::{{name}}=) read
the field's name twice. The message states its name a second time as
=struct_name= for that line to reach.

* Result

dq's protocol messages carry generated codecs, and so does every domain type
they hold: the protocol header states each message's shape beside its struct and
names the codec, the codec's four functions are defined in one translation unit
per entity, and the envelope's hand-written types state their shapes the same
way. Eleven messages are compared with reflect-cpp byte for byte in both
formats, a =catalog_event= goes through =ores::nats::wire_codec= in both
directions, and the four suites this touches are green: 116 cases and 963
assertions in =ores.dq.core=, 45 and 283 in =ores.dq.api=, 179 and 818 in
=ores.utility=, 56 and 170 in =ores.nats=. The codegen suite is 1678 passing and
dq's generated tree has no drift.

What this leaves is the rest of the estate: every other component still renders
protocol headers with no field list and keeps reflect-cpp, which is the
per-component task list the story already carries. Step 7 -- deleting
reflect-cpp -- waits for those, and for the infrastructure components' own
hand-written JSON.
