* Goal

An imported ORE trade lives in the anchor and its components, with its envelope resolved to entities: a counterparty or netting set that does not resolve rejects the trade.

* Acceptance

- The import books each trade's anchor, booking and state in one write, with entry channel stp.
- ORE's Trade/@id is a trade_identifier row under the ORE scheme, and each envelope additional field is a trade_additional_field row.
- An envelope counterparty is resolved by name; a name that matches no counterparty is an item error and nothing is written for the trade. The default counterparty applies only when the envelope names none.
- An envelope netting set is resolved through its ORE alias; one that resolves to none rejects the trade.
- The wide trade and the envelope are still written, so export and the instruments keep working until their own tasks.
- Build, ctest, pgTAP and the local check set pass.

* Plan

The import resolves the envelope before it writes anything, then books the
trade, then writes the wide trade the instruments still reference.

- The counterparty: the envelope's CounterParty as an ORE counterparty
  identifier, then as a short code. A name that matches none rejects the
  trade. The import's default counterparty applies only when the envelope
  names none.
- The netting set: the envelope's NettingSetId as an ORE netting set
  identifier. An id that matches none rejects the trade (owner's choice: the
  sample netting dataset carries the aliases, instead of the import creating
  sets). A trade with no NettingSetId books with no netting set, as in ORE.
- The booking comes first. The anchor, booking and state are one write whose
  pins check the book, counterparty and netting set against the trade's
  party, so a trade the booking refuses leaves nothing behind. The booking is
  =stp= and =actual=; the scope is external when the trade has a
  counterparty. ORE's Trade/@id becomes an ORE trade identifier, and the
  envelope's additional fields become rows in the document's order.
- The trade date becomes optional on the booking: ORE documents may omit it.
- The instrument step skips a trade the trade step did not save, so a
  rejected trade reports its one reason.

* Notes

- Follow-up: the identifier get request matches on the value alone and
  returns one row, which the import then checks for the ORE scheme. A value
  that another scheme also holds can hide an ORE alias. A lookup by scheme
  and value would close it.
- Follow-up: the handler has no automated test; it needs a service harness
  with NATS. The live runs in the evidence file stand in for it.
- Seen, not changed: the CDS instrument of Example_63 fails the credit
  tenor check in the instrument step, which this task does not touch.
- The anchor's identifier and additional fields are written after the
  booking. A failure there leaves a booked anchor without them and skips the
  wide trade; the import reports it against the trade.
