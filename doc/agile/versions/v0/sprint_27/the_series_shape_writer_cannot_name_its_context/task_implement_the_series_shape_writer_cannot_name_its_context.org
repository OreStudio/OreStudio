* Acceptance

- The definition spells the parameter type the way its own declaration does.

* Plan

=bdb7215934= wrote the class' interface and its definition differently in one
commit. The header declares =declare(ores::database::context ctx, ...)=; the
definition writes =declare(context ctx, ...)=. The definition sits in
=ores::marketdata::service::app=, where no =context= is visible, so clang
refuses it and suggests the qualified name.

The sibling class in the same directory, =curve_republish_service=, declares a
member alias =using context = ores::database::context;= and both its header and
its definition use it. That is why its identical-looking definitions compile.
=series_shape_writer= spells the type out instead, so its definition has to
spell it out too. Qualify the one token rather than add the alias: the header is
the interface and already states the type in full.

Nothing else in the file is out of scope. Every other name it uses resolves from
the includes or from its own anonymous namespace, and clang reports one error
for the translation unit.

* Notes

The rest of =bdb7215934= is codegen output for two new entities, =series_axis=
and =series_axis_value=, which the drift gate reports in step with their models.
The commit's other hand-written change is four lines in
=curve_republish_service.cpp= that call =declare= and pass their own =ctx=; that
file already has the alias, so it compiles.

A repository-wide scan for a definition that names a bare =context= is not
usable as a gate: most of the matches are inside =ores.database= itself, where
=context= is the class, or in a file that carries a =using=. What distinguishes
this one is that its own header spells the type in full while its definition
does not.
