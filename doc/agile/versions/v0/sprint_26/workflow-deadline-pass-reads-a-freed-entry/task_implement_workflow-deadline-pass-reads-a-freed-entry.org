* Acceptance

- No read through =waiting= happens after its entry is erased.
- An exception after the step is failed erases the entry once, through the
  handler, not twice.
- Valgrind reports no error on either deadline case, and the workflow suite
  passes.

* Plan

Diagnosis: the loop binds =const auto& waiting = it->second=, fails the step,
calls =it = awaiting_.erase(it)=, and then reads =waiting.instance_id= to find
the run. The node is freed by then. libstdc++ leaves the freed bytes in place,
so Linux reads the right id by accident; on macOS the id reads back wrong, the
run lookup returns nothing, the =continue= skips =stop_on_failure=, and the run
keeps its state. That is every macOS symptom: the step is failed, the run is
not, and a retry refuses a run that has not stopped.

A second fault sat beside it: if the run read or =stop_on_failure= threw, the
handler erased =it= again, which by then pointed at the next entry or at
=end()=.

Fix: move the erase to the end of the expiry branch, after the run is read and
stopped. The handler's erase is then the only one on that path.
