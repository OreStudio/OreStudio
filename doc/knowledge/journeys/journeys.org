A [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]] describes what one person is trying to do, before anything is
built. Each journey is one document: the actor, the trigger, the steps, a
wireframe of the screen, the entity models it composes, and the operations and
messages each step needs — including the ones the server does not provide yet.

These documents describe what a person does in the interface, which screens they
move between, and what each screen shows. A journey is a definition, and where a
journey needs resumable state, *the journey is not server-side — its state is*,
kept as a [[id:FDF3C079-4E18-4DB7-911F-7691AD1F5665][workflow instance]] in
=ores.workflow=. Most journeys need no such state at all. See
[[id:3361CF92-89B0-481E-9E51-ACE2FEEF2FAA][Journey execution]] for the four
composition classes and where the transaction boundary sits.

Journeys are grouped by /logical topic/, never by component. A component is an
implementation concept, and it changes as the code moves; what a person is
trying to do does not. A journey belongs to the group a designer would look in,
not to the folder the code happens to live in.

* How to read a journey

Every journey carries the same sections. =* Goal= says what the person wants in
their own words. =* Actor and trigger= says who runs it and what brings them
there. =* Steps= is the path. =* Screens and wireframes= shows the screen, which
composes several entity field sets into one place. =* Entities composed= names
the models whose fields appear. =* Operations and messages= lists every NATS
subject the journey needs and marks each one =exists=, =partial= or =missing=.
=* What is missing= gathers the gaps, which are the work that has to happen
before the journey can be built. =* Related journeys= is not documentation
decoration: the screen should carry a link for each one, so a person can move
between related screens without going back to a menu.

* Prototypes

Some journeys have a clickable prototype. Every prototype is a static page
under [[id:D913FE21-6CF6-439A-89CF-6A1928AFA094][Prototypes]], which is the
only inventory and states the one way to add one: plain HTML, CSS and
JavaScript, no framework and no build step. A journey document links its own
prototype under =* Prototype= and names the commit that accepted it.

* One screen, not one per entity

A journey is one screen organised around a goal. The list, detail and history
primitives do not exist: commit =e47043269f= deleted them with the generated
entity screens, and no generic component has replaced them. The journey is the
replacement. Each step draws the one view it needs — a step that lists records
draws its own table, and a step that shows one record draws its own form — so
contact details and sign-in state are panels on the account journey, not screens
of their own. The entity models supply the fields; the journey decides which
fields belong together and in what order.
[[id:6A63AAC7-4869-493A-97E7-55B919874784][The journey runtime]] defines the
step and the rail that orders the steps.

* Adding a journey

Group a new journey by the topic a designer would look it up under, then
scaffold it into that group's folder:

#+begin_src sh :results verbatim
compass add user_journey \
  --slug <slug> \
  --parent-dir doc/knowledge/journeys/<group> \
  --title "<title>" \
  --description "<one line>" \
  --tags "user_journey,security"
#+end_src

The file is =journey_<slug>.org=. Wire it into the group hub's table. The full
contract is on [[id:CA94C762-B0C8-40E7-85CE-D4C6355023CC][Document type: user_journey]];
the recipe is [[id:62D58EB6-9977-411C-8403-E3A12DB4CB3D][New user journey]].
