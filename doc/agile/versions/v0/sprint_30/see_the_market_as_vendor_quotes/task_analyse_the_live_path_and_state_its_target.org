** What the docs said that the code does not do

- The pipeline doc designs lanes, conflation, a recent window and a subject with
  separate series and coordinate tokens. The ingest has none of them: it stores
  and publishes each batch, its subject holds the whole datum URI as one token,
  and the history read answers from the store only. The doc now has a /What is
  built today/ section.
- The pipeline doc named the tenant and the party in its designed subject, and
  the stored-once page said the live path republishes to each party. Both now
  point at the target page.

** Decisions

1. *The subject names the feed, not the party.*
   =marketdata.v1.ops.market_tick.<provider>.<feed>.<instrument_type>.<series_token>.<coordinate_token>=.
   A provider can have several feeds (real time, delayed, end of day), and a route
   picks one of them, so the feed is part of the key. The split tokens let one
   wildcard cover a series, such as a volatility surface, which the quotes view
   needs.
2. *The entitlement is checked where a watch starts.* The broker checks only the
   client certificate, so it cannot refuse a subscription. A person never reaches
   the broker: the browser goes through a web server, which the installation
   trusts. The market data service answers which feeds a party may watch, by the
   rule the history read uses, and the web servers and the shell watch only those.
   Subject permissions on the broker are a separate change and are not needed.
3. *One rule for history and live.* The route picks the feed, and the
   subscription's right lets the party show its ticks. The system tenant watches
   and reads every feed.
4. *Metering is unchanged.* The ingest keeps counting, for each route, the ticks
   it publishes on the route's feed, so a party's bill does not change when the
   copy goes.
5. *Add before remove.* The ingest publishes the feed subject beside the party
   copies, the shell moves, and the copies are removed last, so the system works
   after each task.

6. *A screen needs the display right.* The rule today, =may_show=, accepts the
   display or the non-display right. A vendor licenses the non-display right for
   machines, and it does not allow a screen. So a watch or a read for a screen
   needs the display right, and a service with no screen needs either right.
   The question for the market data service names the use. (2026-11-18, product
   owner.)

** Changes to the later tasks

- /Publish each vendor's ticks on its own live subject/: the subject builder with
  split tokens, one publish for each tick, the meter and the CRM bridge kept for
  each route.
- /Reach the vendor subjects through the party's subscriptions/: a new market data
  operation that answers which feeds a party may watch, with the system tenant
  rule; the shell moves to it. No other consumer reads the party subjects.
- /Stop copying live ticks per party/: remove the per-party subject and its
  builder; keep the counts for each route.
- /Read a vendor's recent ticks through the subscription/: smaller than planned.
  The read exists (=get_series_ticks=). It needs the system tenant rule. There is
  no recent window, so it reads the store.
- /Build the quotes view/ and /Retire the synthetic display tap/: both web
  servers, the TypeScript BFF and =ores.http=, carry the tick routes. The
  retirement covers the arrivals raster of the run-the-market screen as well as
  each feed's Ticks tab.
