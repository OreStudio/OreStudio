* Acceptance

* Plan

Reproduce the failure before touching the generator, with the variable the
workflow exports:

#+begin_src sh
ORES_SHELL_LOGIN_USERNAME=tenant_admin@acme_corporation \
  python3 external/ore/tools/generate_script_library.py --check \
  --shell ./build/output/linux-clang-release-ninja/publish/bin/ores.shell
#+end_src

It answers "error: the shell refused a script: Usage error: Login username
provided but password is missing!" — the same two lines Continuous Linux has
printed since 2026-11-27.

Then drop the login from the environment the generator hands the shell.

* Result

The generator calls the shell to parse scripts, and the shell refuses to start
when it carries a login name and no password. Since environment format version
38 took the demo password out of =.env= while the username stayed, the workflows
that export the file hand the shell exactly that pair: a username with nothing
beside it. Continuous Linux has been red on the step since 2026-11-27 for this
reason, and the suites never were: the failure is the check's own shell call.

The generator now removes every =ORES_SHELL_LOGIN_= variable from the
environment it gives the shell, which is what a parser needs and what a client
does not. A developer who exported only the username, as the file's own comment
suggests, was hitting the same wall in =./compass.sh check=.
