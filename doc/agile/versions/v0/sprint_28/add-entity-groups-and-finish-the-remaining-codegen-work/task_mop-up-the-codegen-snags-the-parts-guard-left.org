* Acceptance

- The ores.cmake.* guard in generate.py is gone, and the graph renders a part's CMake the way it renders any other component's.

* Notes

Work in progress on =feature/mop-up-the-codegen-snags-the-parts-guard-left=.
The guard is lifted, the link libraries are modelled, and no
=src/CMakeLists.txt= loses a link. It does not build yet, and the reason is
the finding below.

** Lifting the guard exposed more than link lists

Two things the task did not anticipate.

1. No part declared =#+component_kind:=, so all of them defaulted to =flat= and
   the flat archetype served every one -- deleting the service executables and
   using the wrong baseline. 47 parts now declare =api=, =core= or =service=,
   and the 17 that became =service= carry =:ores.cpp.service-app.enabled: nil=
   so the service-app facet does not overwrite the =app=, =config= and
   =main.cpp= they own by hand. =ores.telemetry/core= stays flat on purpose:
   the core template links a sibling =ores.telemetry.api.lib= and there is no
   api part.

2. 59 components lost links -- 281 tokens -- because the hand-maintained files
   carry links the baseline does not. 56 =extra_dependencies= blocks now
   declare them.

** Still open: hand-written CMake that is not a link

Regeneration also deletes hand-written content the templates cannot express.
Each of these needs a paste point, the mechanism =ores.storage/service= uses:

- Every api part loses =-fvisibility=hidden -fvisibility-inlines-hidden=, which
  the hand files carry and =ores.cmake.component.api_src= does not emit.
- =ores.http/server= loses the block that installs =scripts/generate_keys.sh=
  into the runtime directory.
- =ores.ore/core= and =ores.dq/core= lose MSVC =/bigobj=; =ores.ore/core= also
  loses =set_source_files_properties(... -Wno-unused-const-variable ...)=.
- =ores.trading/api= loses MSVC =/constexpr:= and Clang =-fbracket-depth=;
  =ores.trading/core= loses its WIN32 =STATIC= handling and platform-conditional
  install.
- =ores.telemetry/database= loses two =target_include_directories= entries
  (=ores.telemetry/core/include=, =ores.logging/include=); they should arrive
  transitively through the linked targets, but that is not proven.
- =ores.synthetic/core= loses =${CMAKE_CURRENT_SOURCE_DIR}= from its include
  dirs.

Five =tests/CMakeLists.txt= were materialised for =ores.compute/client=,
=ores.compute/wrapper=, =ores.http/core=, =ores.http/server= and
=ores.iam/client=; their roots gained =add_subdirectory(tests)=.

*v --sweep* is clean and =--component= is clean for =history=, =geo=,
=storage-cpp= and =refdata=. The whole-tree build has not been run.

* Result

* Remaining

The CMake content is now covered. Two paste points, =cmake_prologue= before
the library target and =cmake_finalize= before its install rule, are in every
src archetype and in both branches of the header-only ones. The seven places
that lost content declare it, and =ores.trading/core= declares
=#+win32_static_library: true= because its WIN32 =STATIC= choice replaces the
template's =add_library= rather than adding to it.

What still blocks the task:

1. =test_handler_permissions= fails two tests. Both are about permission codes
   that are not seeded. Adding =#+component_kind:= to 47 parts changes which
   archetypes render for them, and that reaches past CMake into the generated
   source, protocols and shells. Measure that blast radius before going
   further: it is bigger than this task assumed, and it may want its own task.
2. The whole-tree build has not been run. It is the only thing that can prove
   the link lists, the compile options and the includes all still hold.
3. =ores.telemetry/database= lost two =target_include_directories= entries that
   are now redeclared; whether they were needed at all, given the linked
   targets, was not established.
