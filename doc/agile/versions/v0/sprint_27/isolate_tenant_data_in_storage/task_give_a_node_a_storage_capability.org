* Goal

A worker node holds no storage credential, so it cannot download its package
or its input, and no job can run. IAM mints a short-lived object capability
naming the tenant, the bucket and the assignment's exact key prefixes. The
compute dispatcher asks for it and puts it in the assignment; the wrapper
presents it; storage enforces it and holds no database lookup on the path.

* Acceptance

- IAM mints a signed, short-lived capability naming the tenant, the bucket and the key prefixes, and the operations allowed.
- The compute dispatcher asks IAM for the capability and puts it in the work assignment.
- The wrapper presents the capability to storage for the package, the input and the output, and holds nothing else.
- Storage refuses a request whose key is outside the capability's prefix, whose operation is not granted, or whose bucket is not the capability's tenant's.
- A run's package and input download and its output upload without a standing storage credential.

* Plan

Four slices, each built and verified before the next:

1. *The claims.* =jwt_claims= carries a list of =storage_grant= values, and the
   signer and both verifiers round-trip them. *Landed*: 13 assertions pass in
   =ores.security.tests=.
2. *IAM mints.* A =iam.v1.ops.mint_storage_capability= operation, held by the
   services that dispatch work, that signs a capability naming a tenant and its
   grants. The signer is the one IAM already holds, so storage keeps one
   verifier. *Landed*: the operation is modelled, the protocol reuses the
   security claim row, the ComputeService role holds the permission, and the
   IAM service builds.
3. *Storage enforces.* The HTTP route reads the capability's grants and answers
   from them — bucket, key prefix and operation — instead of the account's
   permissions. A token with no grants keeps today's permission path. The
   tenant check arrives when a tenant owns its own bucket; until then the
   prefix is the whole scope. *Landed*: =capability_allows= admits only a
   granted bucket, a key inside that grant's prefix and the grant's operation;
   two cases in =ores.storage.api.tests= pin =split_object_path= and 38
   assertions pass.
4. *The assignment carries it.* The dispatcher asks IAM for a capability for
   the package, the input and the output, and puts it in
   =work_assignment_event=; the wrapper presents it in place of its empty
   bearer. Until the tenant-bucket work lands, the grants name the =ores=
   bucket and the keys the tree uses today. *Landed and proven live*: see
   Result.

* Notes

*Result methods.* The run is driven from =ores.shell=: provision the tenant,
import the ORE example, schedule the definition (which is what mints the run
grant), trigger it, then read the result row.

*Two defects had to be fixed before the capability could pay off.* Both are the
same mistake in different places: the compute service ran a trusted
wrapper-facing write under its own system-tenant context, so a tenant's row was
invisible to it.

- The =results.submit= handler looked the result up with the service context.
  RLS scoped the read to the system tenant, the row belongs to the reporting
  tenant, and the handler answered "Result not found" with the job already
  finished on the node. Fixed by carrying =tenant_id= on the assignment and on
  the submit, and scoping the write with =tenant_context::with_tenant= — the
  convention =submit_compute_request= already follows.
- The results soft-FK check demanded the host live in the result's tenant. A
  compute host is a deployment-level registry row: a node registers on first
  heartbeat under the system tenant, and one shared fleet serves every tenant.
  Fixed with =:system_tenant_visible: true= on the =host_id= soft FK, the same
  relation =app_version_id= already declares.

*Left open by this task.* The engine printed
=Error: Error in ORE analytics: error opening file Input/market_20160205_flat.txt=
and still exited 0, so the wrapper recorded a success for a run that produced
no analytics. The input archive holds =market_data.msgpack= and
=trades.msgpack= where the ORE run configuration wants
=Input/market_20160205_flat.txt=. That is the input-shape half of
[[id:4DEAE6E4-6C1E-4B9A-A4C6-E28770EBD1D3][the reporting-compute handoff]], but the
wrapper trusting an exit code over the engine's own log is a new finding and is
captured separately: [[id:8E55B78D-0928-45D9-B61F-7A5D3619A381][treat an engine error as a failed result]].

*The same tenant-context mistake is still in the reaper.* =reap()= lists
InProgress results with the service context, so it can never see a tenant's
rows. It is captured as [[id:85B38AFE-2388-4436-B620-07B351B8F4E9][scope the reaper to each tenant]].
