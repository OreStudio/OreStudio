* Goal

The web paints a state or type value with a Tag and a tone the screen picks, so the same value is drawn in different colours on different screens. The platform already has one badge catalogue, with a code domain for each value and a mapping from value to badge, and the Qt client draws from it. The web needs one shared component that does all the badge management: it reads the catalogue once, finds the badge for a code or for a value in a code domain, draws the value as the row wrote it in the catalogue's colours with the catalogue's tooltip, draws the reserved unmapped badge when nothing maps, and shows plain text while the catalogue loads. Then every screen uses it, and the hand-picked tones leave the state and type values. Seed: AccountLockBadge and useBadge in ui/, added by Polish the audit sign-ins screen. The web has 77 uses of Tag in 26 files. Each use is either a state or type value, which moves to the component, or a plain marker such as a count or a kind, which stays a Tag. The first task is that audit.

* Acceptance

- One shared Badge component reads the catalogue and paints a badge by code or by value in a code domain.
- The component draws the unmapped badge when no badge maps, and plain text while the catalogue loads.
- Every use of Tag in ores.web is classified as a state or type value, or as a plain marker, in a table on the story.
- Every state or type value paints through the component, and no screen picks a tone for it.
- A check fails the build when a screen passes a state or type value to Tag with a tone.
- The values the web needs and the catalogue lacks are added to the catalogue seed and its page.
