#+title: The environments share the database through a transaction pooler
#+description: A transaction-mode pooler in front of the shared instance caps server connections across the environments.
#+type: knowledge
#+level: cross
#+filetags: :architecture:database:connections:environments:
#+created: 2026-10-26
#+updated: 2026-11-21

* Summary

Where several environments share one PostgreSQL instance, a pooler in
transaction mode stands in front of it, and each environment's services connect to
it. The pooler holds a capped number of server connections for each database and
for the instance, and closes the ones it is not using, so an idle environment
costs the instance almost nothing. A connection carries nothing between
transactions ([[id:3C334C3B-2760-4278-95B8-B71268E8FD18][A transaction sets its own tenant context, so any connection serves any tenant]]) and a
statement keeps its meaning as transactions move between server connections, so a
server connection serves any service of its environment from one transaction to
the next.

* Detail

** The caps

| Cap | Set for |
|-----+---------|
| Server connections for each environment's database | the environment's peak concurrent transactions |
| Server connections for the instance | below =max_connections=, with room for direct connections |
| Server connections kept open while idle | a timeout, so an idle environment holds none |

A service's pool ([[id:729F746E-36DD-40A2-A592-6972239E31F0][A service holds a few long-lived connections and never connects per query]]) is what the service may have open at once - its floor
and its burst ceiling; the pooler's cap is what the environment may have running
at once. That is why the two are separate numbers: a service may ask for the
concurrency its work has without that number becoming the instance's problem.

** What connects directly

Work that needs a session goes around the pooler:

- the listener on =LISTEN= that =postgres_event_source= in =ores.eventing= runs, which turns
  entity change notifications into events,
- a lock held across transactions,
- the tick lanes ([[id:BCD7D253-8B1E-4887-B476-EDD3EDE01BE6][Ticks reach the store through sharded binary COPY in bounded batches]]), whose long COPY batches would hold a pooled server
  connection for their whole length,
- the administrative paths - recreating a database, restoring a schema - which are
  not request traffic and must not be queued behind it.

These name PostgreSQL's address while the services name the pooler's
([[id:929A4722-8F06-4DEF-B759-D0800D4AC6D5][A pooler stands where the database is shared]]).

** Prepared statements

The statements keep their meaning across server connections only while the pooler
tracks them, which pgbouncer does from 1.21 with =max_prepared_statements= set;
a pooler that does not track them requires the statements to be sent unnamed. A
deployment that runs a pooler therefore states the pooler's version with its
configuration, and the tests that run through a pooler fail if the two ever
disagree.
