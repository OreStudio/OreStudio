* Goal

Every rates instrument row, the header and the facts alike, is pinned to the trade anchor by a composite key over the tenant, the trade, the party and the trade type, so a row cannot disagree with the anchor it belongs to.

* Acceptance

- ores_trading_trades_tbl carries the unique index the composite key needs.
- Every rates instrument row, the header included, carries a foreign key to the anchor over the tenant, the trade, the party and the trade type.
- A row whose party or trade type disagrees with the anchor's is refused, and a case proves it.
- The generated models, the SQL and the repositories agree on the key.
- The change to the trade model is recorded where the other families can join it.

* Plan

1. *The anchor's index.* Add the unique index the composite key needs to the
   trade model and regenerate. This is a change to =ores_trading_trades_tbl=,
   not to this family, so record it where the other families can join it.
2. *The instruments' key.* Declare the composite foreign key on the header and
   on each of the eight fact tables, over the tenant, the trade, the party and
   the trade type.
3. *The fallout.* The repositories key on the trade id today; the composite key
   adds the party and the type, so the generated key parameters, the services
   and the shell surfaces follow, and the tests that build a row without the
   anchor's party will start to fail — that is the check working.
4. *A refusing case.* A repository case that writes a row whose party or trade
   type disagrees with the anchor's, and expects the store to refuse it.
5. *Before branching.* The trade anchor is shared with every other family and
   with in-flight work; check the fleet for what else is touching it before
   starting.
