* Goal

The lifecycle manager writes one record before it adds the =TimeStamp= global
attribute, so the =Replica index= line at the top of every service log is the
only line without a timestamp. Every other line reads

#+begin_example
2026-11-20 09:40:30.999853 [INFO] [ores.refdata.service.app.host] ...
#+end_example

and that one reads

#+begin_example
 [INFO] [ores.logging.lifecycle_manager] Replica index: 0
#+end_example

All log lines should look the same.

* Acceptance

- Every record a service writes carries a timestamp, a severity word and a
  channel, including the first one.
- A service start writes no line that lacks a timestamp: the check is
  =grep -vhE '^[0-9]{4}-[0-9]{2}-[0-9]{2} ' publish/log/*.log= returning nothing.
- The timestamp and the rest of the format do not otherwise change.

* Plan

=projects/ores.logging/src/lifecycle_manager.cpp= configures the sinks, writes

#+begin_src cpp
if (cfg.replica_index)
    ORES_LOG_SEV(lg(), ores::logging::info) << "Replica index: " << *cfg.replica_index;
#+end_src

and only then adds the clock:

#+begin_src cpp
core.add_global_attribute("TimeStamp", boost::log::attributes::local_clock());
#+end_src

The record therefore reaches a formatter that names =%TimeStamp%= with no such
attribute in the record's set.

The fix is to add the global attribute before the first record the manager
writes, not to special-case the message: the manager should be fully configured
when it logs anything. Move the attribute registration to the top of the
configuration path, ahead of the replica line and of any other setup record, and
check the console sink path takes the same order. If the sinks are created after
the attribute, so much the better: the attribute belongs to the core, not to a
sink.

Worth checking while there: whether any other early record (the =Log level= line,
the sink creation warnings) is written before the formatter is set, and whether
the tests assert any of this. None of them does today, which is why the gap went
unnoticed; a test that starts the manager with a replica index and asserts the
first record's timestamp would keep it fixed.

Found while measuring PR #4922; the logger handle did not cause it and the PR
was merged without blocking on it. See
[[id:1CCAE6BF-99D4-4CEB-84BF-D115152DC664][Split the logger typedef out of make_logger.hpp]].''')

* Notes

The fix is one move, not a special case: the =TimeStamp= global attribute is
registered before the sinks are created, so every record a formatter sees names
it. The attribute belongs to the core, so it cannot depend on which sink is up.

The test is the part that keeps it fixed. It configures file logging with a
replica index, lets the manager write its record, flushes the core and reads the
file back, and it asserts that *every* line opens with the timestamp shape,
not only the one that used to miss it. It failed on its first run for a
different reason worth recording: the check compared the wrong offsets, which
proves the test reads the format rather than a substring.

While this ran, two things the sweep script needed became clear, and it has
them now:

- It must never rewrite =ores.logging/src/logger.cpp= (the one call of Boost's
  macro the handle exists to hide) or the two =boost_severity= files. A quick
  hand-run of the same replacements had already broken the backend once.
- A file that writes =using ... boost_severity;= decides how the name is spelled
  in its own scope, so the qualification step leaves it alone.

The script keeps =--check=, which reports stragglers and exits non-zero, because
branches in flight will keep arriving with the old macro until the tree settles.

* Result

Every record a service writes now looks the same. The =Replica index= line
carries its timestamp because the clock is registered before the first sink is
created, and 0 of the 26 log files hold a line without one, where every service
had exactly one before.

=ores.logging.tests= keeps it that way: a new case starts the manager with a
replica index, writes a second record, and asserts that every line in the file
opens with the timestamp shape.
