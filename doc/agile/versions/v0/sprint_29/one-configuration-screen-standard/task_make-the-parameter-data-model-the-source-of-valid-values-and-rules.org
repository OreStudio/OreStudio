* Goal

One parameter model states a parameter's control and its rule, and every screen
reads it from there. A parameter's allowed values, its bounds, its pattern and
its catalogue live in the value set tables and nowhere else. The per-pair
=kind= and =options= columns go, because the value set now says the same thing
once instead of on every pair that takes the setting. The engine run settings
reach the same contract, so the =Setup= parameters stop carrying a second copy
of their control in the group settings table. The screens keep one source, the
write path keeps one enforcement point, and a build check fails when a
parameter loses its set.

* Acceptance

- The value set tables are the only place that states a parameter's control and
  its rule. No screen, server or seed restates an allowed value.
- The 15 settings whose set said text although the guide lists their choices
  state an enumerated or boolean set, from a curation entry that names the
  guide as its source. The settings that stay text say in the set why they are
  text.
- =ores_analytics_pricing_pair_settings_tbl= holds no =kind= and no =options=
  column. The C++, the protocol, the SQL, the TypeScript, the shell recipe and
  the seed are generated from the model without them.
- =usual_value= stays, because the pricing screen shows the usual setting of a
  pair, and it states a value and not a rule.
- Every =Setup= parameter that the engine run settings screen draws has a value
  set and a link, and that screen draws its control and checks its value from
  the set through the same fields the pricing screen reads.
- A check in =build/scripts/local_checks.py= fails when a parameter a screen
  draws has no value set, when a set breaks its own rule, or when a per-pair
  override column returns.
- The build, the four test suites, the drift checks and a live environment
  prove the behaviour: a change to a set changes the screen's choices, a
  refused value names its set, and the ORE export and import still roundtrip.

*** Which parameters still have no value set, and why

- The pricing, convention, curve and global parameters have no gap: 251
  parameters (61 =ModelParameters=, 173 =EngineParameters=, 17
  =GlobalParameters=) carry 1 link each, and =generate_value_sets.py= fails on
  the first one that does not. The links also cover 461 convention and curve
  leaves, which is why 712 links stand against 251 pricing parameters.
- 72 sets are =text=. That is the deliberate statement that a parameter is free
  text, and it is data, not a gap. It is also under-stated for 15 of them: the
  guide lists their choices and the code typed them as text, and a code set
  replaces a guide set. They are =Curve=, =FepCurve=, =OptionExpiryPosition=,
  =Policy=, =RegressorModel=, =SensitivityDecomposition=,
  =SeparateCallPutVols=, =SpreadOnIncomeCurve=, =useIndexCDSPricer=,
  =Calibration=, =CalibrationStrategy=, =FxCalibration=, =ReversionType=,
  =TreatSecuritySpreadAsCreditSpread= and =VolatilityType=.
- The =Setup= scope is the real gap: the engine run settings screen draws 15
  settings and none of them has a set or a link. Their control lives in
  =ores_reporting_engine_settings_group_settings_tbl= as =kind=, =options=,
  =minimum= and =maximum=, so the second screen restates what a set would say.
- The =Setup= block holds 54 more parameters from the ORE input files, such as
  =outputPath=, =csvSeparator= and =baselTrafficLightConfig=. No screen draws
  them and the contract states their domains, so a set would be a rule nothing
  reads. Three of them do name a catalogue vocabulary (=dateCalendar=,
  =dateConvention=, =baseCurrency=) and are a candidate for a later task.

** Where the value set model still cannot state what a per-pair column stated

- *A kind that is also a flag.* =SeparateCallPutVols= accepts =true=, =false=
  or a regular expression inclusion pattern. A set is one kind, so it cannot say
  "a switch or a pattern"; it stays =text= and its description says why. The
  per-pair =select= column could not state it either, and refused a pattern the
  guide allows, so nothing is lost here.
- *A vocabulary the evidence states in part.* The guide lists =Bootstrap=,
  =BestFit= and =None= for =Calibration=, and the documents ORE ships write
  =Deal=. The set stays =text= with the reason. Making it enumerated would
  refuse a value the seeded population holds, so the task needs the ORE
  enumeration read from the source before it narrows.
- *A per-pair difference.* The per-pair columns could, in principle, state one
  list for one pair. They never did: every row of a setting carried the same
  list. The set is keyed by =(scope, name)= and cannot state a difference by
  pair. If ORE ever needs one, the link becomes keyed by the pair too; that is
  a model change and no screen needs it today.
- *A default per pair.* =usual_value= states the value ORE's examples use and is
  a value, not a rule, so it stays on the pair row. It is not in the set, and a
  set cannot state it: two pairs may use different example values for one
  setting.
- *Documentation prose.* The =format= text of a =Setup= ore parameter still says
  "A whole number, at least 1." The set is the rule and the prose is
  documentation a person reads; the pricing contract's prose no longer repeats
  the choices, and the =Setup= prose could follow in the documentation task.

** Decisions

- *The =Setup= sets share a code where the rule is shared.* Eleven flags take
  =setup.flag=, and the two fixing lags take =setup.fixing_lag_days=, because a
  set states a rule and the rule is the same. The alternative, one set per
  setting, would repeat the same rule fifteen times.
- *The numeric bounds moved into the shared check.* A =whole= setting stated a
  floor in the group settings row. The value set states it now, and the function
  the parameter trigger calls applies it, so a bound is data and one function
  reads it.
- *The proposal service asks the database rather than re-reading the tables.*
  The engine run settings proposal path had its own copy of the rule. It asks
  =ores_reporting_value_in_set_fn= now, so a proposal is refused with the
  sentence the store would use, and the whole-number width check the apply makes
  stays with it.
- *The check reads the curation and the seed, not a live database.* The gate
  must run on a pull request, where no environment exists. A stale seed is
  caught by comparing the curation with the committed script.
- *The =Setup= block's 54 input-file parameters get no set.* No screen draws
  them and the contract states their domains. =dateCalendar=, =dateConvention=
  and =baseCurrency= do name a catalogue vocabulary and are a candidate for a
  later task; they are recorded here rather than decided silently.

* Result

The parameter data model is the one source of a parameter's control and rule,
on both configuration screens, and a check holds it.

- The value set tables state every parameter's allowed values. 266 parameters a
  screen draws carry 1 link each, and the 224 sets state an enumerated list, a
  catalogue, a range, a regular expression, a switch or text.
- The =Setup= scope joined the contract. Six sets state the fifteen engine run
  settings' controls, the group settings table lost its copy, and the screen
  draws and checks from the set through the same fields the pricing screen uses.
- The per-pair =kind= and =options= columns are gone from the model, the SQL,
  the C++, the protocol, the TypeScript, the shell recipe and the seed. The
  compiler found the last reader, a hand-written proposal check, and it asks the
  store's own function now.
- Fifteen settings the guide states a vocabulary for stopped being free text:
  thirteen carry the guide's list, and two stay text with the reason in the set.
- =build/scripts/check_parameter_value_sets.py= runs in the local gate. It
  fails on a parameter a screen draws with no set, on a set whose kind cannot
  hold its rule, on a stale seed, and on a per-pair override column returning.
  Each of those was proved by breaking it and reading the failure.

Proven live on a recreated, provisioned environment: adding a value to
=setup.observation_model= in the database added it to the screen's choices, and
raising the floor of =setup.n_threads= moved the bound the server enforced, with
no server change. A group write below the floor was refused. A pricing engines
document exported and previewed with 0 rows added, changed or removed and 0
issues. A parameter write outside its set was refused by the trigger, naming the
value, the setting and the set. The retired columns appear in no reply.

Not done here, and stated rather than hidden: the =Setup= block's 54 input-file
parameters have no set because no screen draws them; three of them name a
catalogue vocabulary and want a later task. =Calibration= stays text until the
ORE enumeration can be read from the source, because the guide's list omits a
value the seeded documents write. The pending provenance columns on the row are
the story's own task, not this one.

Commits on the branch, in order: the inventory, the =Setup= sets, the guide's
choices, the engine settings screen reading the set, the retired per-pair
columns, the gate, and the proposal check.
