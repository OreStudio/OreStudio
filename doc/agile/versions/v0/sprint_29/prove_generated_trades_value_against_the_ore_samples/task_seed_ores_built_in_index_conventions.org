* Goal

Every tenant holds the Ibor and overnight index conventions ORE defines in code, each with its oresmd address, so a convention lookup answers for them.

* Acceptance

- A script mines ORE's =ored/utilities/indexparser.cpp= into seed rows of =ibor_index_convention= and =overnight_index_convention=: day count, fixing calendar, settlement days, business day convention, end of month and the oresmd address. The seed names the ORE version it was mined from.
- Population loads the seed; a provisioned tenant finds the conventions of =EUR-EURIBOR-6M= and =USD-SOFR= through =convention_lookup=.
- A tenant may override a seeded convention with its own.

* Plan

1. Mine ORE's built-in tables. =ored/utilities/indexparser.cpp= holds the two
   hardcoded maps, =onIndices= (27 overnight families) and =iborIndices= (54
   Ibor families), and each name maps to a QuantLib or QuantExt class whose
   constructor states settlement days, currency, fixing calendar and day
   counter. A script takes the ORE source directory as an argument, as
   =external/ore/tools/datum_catalogue/regenerate.sh= does, and writes a
   committed table of the 81 families: kind, class, settlement days, fixing
   calendar, day counter, business day convention and end of month, with the
   ORE version it was mined from. The ORE source is not vendored, so the table
   is the artefact and the script re-derives it.
2. Extend =tools/ore_conventions/oresmd_index_map.tsv= to every mined family,
   by running the codecs over the family names the way
   =generate_oresmd_index_map.ores= does, so 81 families gain an address
   rather than the 64 that have one today.
3. Generate the Ibor and overnight convention rows from that table, replacing
   the hand-written =refdata_{ibor,overnight}_index_conventions_populate.sql=
   rows and their per-row QuantLib comments. A family whose index the codecs
   cannot spell, or that the synthetic feeds name but ORE does not define,
   carries no address and says why.
4. Make the corpus-derived seed's =IborIndex= rows state the family address:
   a convention defines the family, and an address that carries a tenor can
   never be found.
5. A test of =convention_lookup= over exactly the rows population writes: it
   answers for =EUR-EURIBOR-6M= and =USD-SOFR=, and a tenant row that states
   the same address wins over the seeded one.

* Notes

- Measured while starting this task (2026-11-07); the census and every number
  below are in =evidence/index_convention_addresses.txt=.
- ORE defines more index families than we seed. Of the 81 built-in families,
  12 of 27 overnight and 7 of 54 Ibor have a seeded convention row; 24 and 40
  respectively have an address in the map at all.
- Not one seeded row states an address, and the corpus-derived seed's ten
  IborIndex rows state a tenor, so no row is reachable by
  =index_definition_of= today.
- The earlier note, that the seed already held the family addresses, was
  wrong.
- ORE's source is on this machine but outside the repository (a Vault
  checkout), so the mined table is committed and the script re-derives it on
  demand. That answers the acceptance's "mined from indexparser.cpp" without
  vendoring the engine.
- The fields come from ORE itself, not from a text pass over its source.
  =index_catalogue= in =external/ore/tools/datum_catalogue= already asks ORE
  what it made of each index name; it now reports the physical fields too
  (settlement days, fixing calendar, day counter, business day convention,
  end of month). Built against the ORE engine checkout on this machine and
  run over a sample, it answers
  =EUR-EURIBOR-6M -> 2, TARGET, Actual/360, ModifiedFollowing, end of month=,
  which is exactly what the hand-written =refdata_ibor_index_conventions_populate.sql=
  row states from the same class. So the 32 hand-written rows are the
  validation set for the miner.
- The names come from a script now: =tools/ore_conventions/extract_builtin_indices.py=
  reads both maps and writes name, kind, class and the index name to probe
  (an Ibor family is probed at 3M; four families are both kinds, USD-SOFR
  among them, and the kind is part of the identity). 81 entries, and ORE
  accepts every probe.
  A family that is both an overnight index and a term rate is the one thing
  the lookup cannot do: =index_definition_of= drops the tenor, so both rows
  answer to one family address and the lookup reports a conflict. The kind
  should decide: no tenor asks the overnight convention, a tenor the Ibor one.
- The day counter mapping is 1:1 and derived, through =code_catalogue=, a new
  harness tool that prints the name ORE reports for a code:
  =ACT/360 -> Actual/360=, =ACT/365.FIXED -> Actual/365 (Fixed)=,
  =ACT/ACT.ISDA -> Actual/Actual (ISDA)=, =ACT/ACT.ISMA -> Actual/Actual
  (ISMA)=, =BUS/252 -> Business/252(Brazil)=. These are the only five the
  81 built-ins need.
- The calendar field is the one open question. refdata's calendar codes are
  not ORE's calendar names: refdata holds =UnitedStates.SOFR=, and ORE's
  parser refuses that string, building =US-SOFR= or =US= instead. So a row's
  =fixing_calendar= needs a choice, and no translation between the two
  vocabularies exists in the tree. Two of the 39 calendar names the built-ins
  use have no ORE code at all (=JoinHolidays(London stock exchange, TARGET)=
  and =Bratislava stock exchange=). Until that is settled the generated seed
  cannot state a fixing calendar that both refdata and ORE accept.
