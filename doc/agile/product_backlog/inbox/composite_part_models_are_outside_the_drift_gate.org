#+description: A catalogue component's modeling_dir is its own modeling/, so the <part>/modeling/component_overview.org models of a composite are discovered by no entry: check_component_drift.py never renders them and their generated CMakeLists.txt and component_files.cmake have no gate. regenerate_cmake_component_files.py covers the file lists only, and the workspace clean-up had to render the three parts by hand.

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

A composite component's parts each carry a =modeling/component_overview.org=
that is an =ores.codegen.component= model, and they generate that part's
=CMakeLists.txt=, =component_files.cmake= and =modeling/CMakeLists.txt=. No
catalogue entry names them: a component's =modeling_dir= is its own
=modeling/=, so =discover_models()= never reaches
=<component>/<part>/modeling/=, and neither =check_component_drift.py= nor its
=--sweep= renders them. Rendering one directly does work:
=codegen.generate._generate_single(<part>/modeling/component_overview.org,
False, projects/ores.codegen, address="ores.cmake")= writes the whole part's
CMake output.

* Why

The consequence is that a part's generated CMake files are hand-maintained in
practice, and a full-facet regenerate clobbers them: the =cmake_component_src=
template emits a minimal link list, while every real component's part carries
its own =target_link_libraries=. This pass hit it -- the workspace clean-up
lost three parts' link lists to a part render and restored them from git --
and =regenerate_cmake_component_files.py='s own docstring already names the
hazard for the file lists, though not for the =CMakeLists.txt= files
themselves.

A later pass measured the gap rather than assuming it, on 2026-09-28, and it
is narrower than it first looks:

- The file lists are covered. =regenerate_cmake_component_files.py= walks a
  composite's parts -- it rendered =projects/ores.shell.workspace=, a part
  created that day, without being told it existed -- and =--all --check= is a
  standing gate. What it writes is =src/component_files.cmake= and
  =tests/component_files.cmake= only.
- What no gate covers is the part's own =CMakeLists.txt=, =src/CMakeLists.txt=
  and =tests/CMakeLists.txt=. These are scaffolded once from
  =cmake_component_{root,src,tests}.mustache= and then hand-customised with the
  component's link libraries, so a regenerate is destructive and a check that
  renders them would fail for every composite in the tree at once.
- =check_component_drift.py= renders a component's own =modeling_dir=, so a
  part model that gains or loses something is invisible to it. The
  workspace-cpp entry in =COMPONENTS_UNDER_TEST= does not change that.

The two candidate fixes are therefore not equivalent. Teaching the discovery to
expand =#+parts:= is a whole-tree change: it would fail on main for every
composite whose part CMakeLists differ from the template -- which is all of
them -- so it can only land with a way to declare a part's link list in its
model. A narrower first step is a check that reads each composite's
=#+parts:=, walks =<root>/<part>/modeling/component_overview.org=, and asserts
the file exists together with the part's =CMakeLists.txt= and
=src/CMakeLists.txt=, leaving their content alone. That catches a part that was
declared and never scaffolded, or scaffolded and never added to the root, which
is the failure this pass actually met. Which of the two is wanted is a
maintainer's call, so the item stays in the inbox.
