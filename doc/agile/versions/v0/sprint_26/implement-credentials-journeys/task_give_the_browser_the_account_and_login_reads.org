* Goal

Give the browser the two reads every credentials screen starts from. The
administrator's screen opens on the tenant's accounts, and both the
administrator's screen and the member's read one account's login record. The
subjects behind both already work and =ores.http= already forwards them; what is
missing is the path the browser can actually use, because the BFF is its only
HTTP surface and serves neither.

This is the first slice of the build. It adds no screen: it makes the reads
answer, so the screens have something to read when their own tasks start.

* Notes

- *The count was wrong, and silently so.* =accountPageSchema= read the wire's
  count as =total_available_count=, which IAM never sends: its list replies
  state =total=, and its =total_available_count= is a name other components use.
  Because the field carried a default of 0, the account list would have answered
  =totalCount: 0= for every tenant rather than failing, and the read had no
  production caller to notice. The live call now reports 25.
- *A get names its row through a key object.* The first live call answered
  =bad_request= because the request was ={username: ...}= where the server
  decodes ={key: {username: ...}}=. The wrapper is there so a =get_many= can
  take ={keys: [...]}= without a second shape. A fake client that records the
  body cannot catch this; only a call to the real server can, which is why the
  routes were exercised live before this task closed.
- *List requests state their order.* The server does not apply defaults to a
  field that is absent, so the client writes =order= explicitly. An empty order
  field means the key, which is what makes a page of an unordered set
  reproducible rather than able to repeat or skip rows.
- *An expected absence is a value, not an error.* An account that has gone since
  the list was read and an account that has never signed in are both states a
  screen shows, so those routes answer 200 with nothing. A malformed account id
  is a client bug and answers 400.
- *Found on the way:* the =@ores/bff= =dev= script cannot start the server from
  its own package, because both its env path and the site-config default resolve
  against the caller's working directory. Filed as
  [[id:E5CBCBA4-312D-4C88-B20A-6B281EABB7F5][The @ores/bff dev script cannot start the BFF from its own package]];
  the verification above ran the server from the workspace root instead.

* Result

Done 2026-09-30.

The browser can read accounts and login records. Four routes answer, each over a
subject that already worked:

| Route | Subject | Answers |
|-------+---------+---------|
| =GET /api/accounts= | =iam.v1.accounts.list= | The page of accounts the caller may see, with =totalCount= |
| =GET /api/accounts/:username= | =iam.v1.accounts.get= | One account, or nothing |
| =GET /api/login-info= | =iam.v1.login_info.list= | The page of login records |
| =GET /api/login-info/:accountId= | =iam.v1.login_info.get= | One record, or nothing |

=@ores/wire-protocol= gained the browser-facing login-record shape, the wire
schema with its field-by-field translation, the two get-request key shapes, an
order on both list requests, and a new =credentials.ts= holding the four reads
over the same narrow caller the account operations use. Ten route tests and one
corrected client test came with them, and the four routes are in the component
specification.

Two defects were fixed or found on the way: the account page's count read a field
IAM never sends, which made every list report zero, and the =@ores/bff= =dev=
script cannot start the server from its own package.

Verification: typecheck clean across the workspace, 301 tests green in three
packages (bff 83, web 167, wire-protocol 51), Prettier clean. Live against the
fleet with the BFF run from source: the account list answered 2 of 25 accounts
with the count right, one account and one login record answered, an absent
account answered nothing, a request without a session answered 401, and a
malformed account id answered 400.
