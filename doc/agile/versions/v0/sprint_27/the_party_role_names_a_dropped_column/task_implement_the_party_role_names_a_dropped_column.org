* Acceptance

- The build compiles past trade_party_role_table.cpp.
- The party roles create script names no column the table does not have.

* Plan

Commit =178610c4e8= removed the =party_id= and =counterparty_id= columns from the
=trade_party_role= model and regenerated. Two free-text sections still name
=counterparty_id=: the C++ =** Table display= table and the SQL =** Indexes=
table. The generator emits both verbatim, so the model drift gate stays green
and only the compiler and the database see the disagreement.

Remove the two rows and regenerate the entity. The generated C++ table writer
loses the column, and the create script loses the index. The index is not merely
redundant: =create index= on a column the table does not have fails, so
=ores_trading_party_roles_tbl= could not be created either.

* Notes

The two rows survived because =* Columns= is parsed and validated while
=** Table display= and =** Indexes= are free text. Only a compile or a database
recreate catches the disagreement.

No other entity has this defect. A scan of all 377 generated table writers,
against the members of the class each one streams, and of every generated
create script, against the columns of the table it creates, reports nothing
else. That scan lives at =build/evidence/scan_generated_column_refs.py= as
scratch; it caught both of these on the buggy revision, and it is a candidate
for a permanent gate.
