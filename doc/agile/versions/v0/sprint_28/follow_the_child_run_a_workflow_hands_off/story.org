* Goal

A person who provisions a tenant should not be told it is ready while its setup is still running. The provisioning run records the id of the run it creates, so the shell should follow that child run to completion before it reports success.

* Acceptance

- run_and_follow reads the last completed step's child_instance_id and follows that child run when this session can read the run's tenant
- bootstrap setup, and a provision tenant run from the system tenant, print the tenant ready only after the child run completed
- a child run in another tenant is not read: the command names its instance id, reports that the setup continues there, and exits successfully
- an unreadable step result fails the command; a readable result that names no child is no handoff
- the wait counts every step the instance planned, so a run is never called finished while a step it owes is missing
- the transient 'Workflow instance not found' first-poll warning is not printed as a warning
- proven by live runs as super_admin (bootstrap setup, child followed through four steps) and as tenant_admin@acme_corporation (provision tenant, child reported) on a recreated database

* Decisions

- *Follow the child only in a tenant the session can read.* The child
  run is created in the tenant being provisioned, so the steps read
  refuses it to every caller outside that tenant except the system
  tenant. A tenant administrator's session therefore cannot follow it,
  and polling it aborted a healthy provisioning after five refusals.
  The shell reads the tenant the handoff step recorded, follows a child
  it may read, and otherwise reports that the setup continues in the
  new tenant, names the run, and returns success. The alternative was a
  cross-tenant read, which is a widening of tenant isolation and was
  rejected.
- *The wait counts the steps the run planned, not the rows created so
  far.* The engine creates a step row when it dispatches the step, so
  the visible list can be one step short exactly when a step finishes.
  A live run declared a two-step run finished after one step and
  returned while the tenant's setup was still running.
- *One timeout budget per command.* A caller who asks for an hour waits
  an hour at most, including the run the first one hands work to.
- *A step with no recorded result is no handoff.* Many steps finish
  without recording one, so an empty result must not fail a run. A
  result the server does not hold is a failure, because the handoff is
  then unknown.
