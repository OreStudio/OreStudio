Live run of the forced password change and the password policy read, 2026-09-28,
environment eager_maxwell, branch
feature/carry-the-forced-password-change-and-read-the-policy.

The IAM service was rebuilt and restarted on the branch's binaries, and the
password policy was read before anybody signed in, because the screen that
shows the rules is the one a person signs in on:

  GET http://localhost:21402/api/password-policy

  {"success":true,"message":"","minLength":12,"requireUppercase":true,
   "requireLowercase":true,"requireDigit":true,"requireSpecial":true,
   "specialChars":"!@#$%^&*()_+-=[]{}|;:,.<>?"}

The rules are the validator's own record: the validator states them once and
enforces the same record, so nothing on screen can drift from what the server
applies.

An Operational tenant was then provisioned through the browser's route, whose
starting point declares that its administrator sets a password at first
sign-in:

  POST /api/provision-tenant  {"profileCode":"empty_operational",
                               "tenantCode":"op_pw","tenantHostname":"op-pw.example",
                               "adminUsername":"admin_pw", ...}

  {"success":true,"instanceId":"6bf8eee0-3bd0-42b0-bf41-906c6a882e5b",
   "tenantId":"c53e3592-eb1a-4dbb-8cf4-b632873a5ef5",
   "accountId":"01a0ea23-90d2-729f-9252-d1ee31c959fb"}

The run completed, and the administrator's first sign-in, through the browser's
own route, answers that the change is required:

  POST /api/session  {"username":"admin_pw@op-pw.example",
                      "password":"Secure-Password-123"}

  {"outcome":"active","session":{...,"passwordResetRequired":true}}

What this proves, against the task's acceptance:

- the starting point's force-password-change choice reaches the account the
  provisioner creates: the profile's row says so, the login record holds it,
  and the sign-in answer carries it;
- a read returns the password policy the server enforces, and the browser
  reaches it through its own route with no session, which is how the sign-in
  screen can show the rules before anybody has signed in;
- no client declares the rules: the answer above is the server's own record,
  and the validator enforces the same record it states, which its tests pin by
  refusing a password one character short of the stated length and accepting
  the same password at it.
