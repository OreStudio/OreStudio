A point-in-time record, written while the story that commissioned it was open, of an investigation into the shape the portfolio tree read must take, before any change is proposed.

It is a snapshot, not a description of the system. Whatever it concludes that the code must keep doing belongs on the page that owns the subject; cite that page from code, recipes and models, not this one.

* Context

The trade list carries a portfolio tree on its left. The prototype settles what it draws: portfolios nested by parent, the books that hang from each portfolio, a count of the trades in each, and the two icons that tell a portfolio from a book. The prototype reads mock data, so it proves the screen and not the server.

The junction capture answered what the reads can do today. This investigation asks the prior question: given our data-oriented design, the entities we hold and the service boundary, what should the tree read *be*? The order matters, because the first shape that works is rarely the one that survives review.

* Methodology

Read the doctrine first, then the entities, then the boundary, and only then the candidate shapes.

* Paths taken

*** The classification comes first

The doctrine asks what the data *is* before it asks what the pattern is. The tree is not one entity, because it draws two; it is not a list of one entity kind, because its rows are portfolios and books; it is not a family, because nothing is written in one transaction; and it is not a bundle, a package or an artefact.

It is a screen whose rows span several entities, so the pattern table sends it to one place: *a read model, never a client join*. That closes the classification question and leaves the shape.

*** What the entities already say

| Entity | Owns | The tree needs |
|---|---|---|
| =ores.refdata.portfolio= | =party_id=, =parent_portfolio_id=, =name=, =is_virtual=, =sandbox_id=, =status=, =purpose= | identity, parent, label, sandbox |
| =ores.refdata.book= | =party_id=, =parent_portfolio_id= → portfolio (mandatory, exactly one), =name=, =book_status=, =sandbox_id= | identity, parent, label, sandbox |
| =ores.trading.trade_booking= | =trade_id=, =book_id=, =trade_date= | which book a trade is filed in |
| =ores.trading.trade_summary= | =book_id=, =row_kind=, =trade_count= | the count per book, already read for the list |

So the tree is two hierarchies in one shape: a portfolio nests under a portfolio, and a book hangs from one. Both carry the party and the sandbox, which are the two axes the tree filters on. And the count is not a property of either: it is the trading side's opinion about a book.

*** The boundary decides where each read lives

The tree needs refdata's rows and a trading count. The tempting shape is one view that joins them: a =portfolio_tree_node= read model in trading, selecting from the refdata tables and counting the trading ones. It would be one call, one pager, one array.

The doctrine forbids it. A service reads another service's data through that service's NATS API, never through its tables: reaching across the boundary couples the two schemas, and it bypasses the owning service's authorization. A view that selects refdata tables from trading is exactly that reach, whether or not Postgres allows it.

Nor can the pieces simply be dropped into a client join of entities. The rule that closes that door is the same one that closed the classification: a screen spanning entities is assembled for display from reads, not built by the screen out of raw entity rows.

*** The one precedent worth copying

=trade_summary= is the shape the doctrine endorses, and it is worth naming precisely because it looks like the forbidden view and is not. Its view =union all=s two tables of *one* component, trading, into one row type with =row_kind= as the discriminator; every table it reads belongs to trading. That is a read model inside one service. The tree's tempting view would union two *components*, and no amount of syntactic similarity makes that the same thing.

*** Where the shapes split

| Shape | What it is | Verdict |
|---|---|---|
| R1 | A =portfolio_tree_node= read model in refdata (portfolios and books, =node_kind=, =parent_id=, label, sandbox), plus a count-per-book read in trading, zipped in the BFF | Right by the boundary, and the same shape as =trade_summary= |
| R2 | Extend both list filters with =party_id=, fix the erase-after-paging, and let the BFF build the tree from two lists plus the count read | Least new codegen, but two page walks and a client-built hierarchy |
| R3 | One view in trading over refdata and trading tables | Rejected: crosses the service boundary, couples two schemas, bypasses refdata's authorization |

* What the legacy Qt tree did

The retired application at =ores.qt= had this screen, and reading it answers three of the questions the doctrine left open. Its files are =trading/src/PortfolioExplorerTreeModel.cpp= and =PortfolioExplorerMdiWindow.cpp=, with =api/src/ClientManagerTrades.cpp= for the read.

*** The shape it chose

- *The root is the party hierarchy, not one party.* =load(parties, portfolios, books)= builds party nodes nested by =parent_party_id=, so a holding company shows its regional companies as sub-nodes. A party's portfolios hang under its party node, portfolios nest by =parent_portfolio_id=, and books are leaves under their portfolio. A party with no visible parent becomes a root, and a portfolio whose party is invisible gets a bare fallback node rather than vanishing.
- *Virtual portfolios are structural parents*, and the model distinguishes them by the outline briefcase icon. That is the same icon the new prototype uses for a portfolio.
- *The tree is assembled in the client from three whole lists.* There is no server tree read: the window fetches parties, portfolios and books, then =load= builds the hierarchy in memory, and calls =expandAll()=.

*** The counts

- Each book's count is fetched in the background, *one request per book*, through a =QFutureWatcher= per book, and stored in a map.
- A portfolio's count is =subtree_count=, which sums the map over the subtree in the client. So the legacy answered the open question by summing in the client, not by aggregating in the database.
- =set_trade_count= emits =dataChanged= for the book and every ancestor, so the labels above it update as counts arrive.

*** The filter it sent

- =selected_filter= returns =book_id= for a book, =portfolio_id= for a portfolio, and nothing for a party node.
- The request carried a single opaque =node_id= string, and the server resolved whether it named a portfolio or a book.

* Conclusions

The doctrine's verdict stands, and the legacy sharpens six points.

1. *The tree is a read model* by classification, and the legacy shows the alternative in the flesh: three whole lists read on every visit and the hierarchy built in memory. It works, and the relationship-view rule rejects it, because it reads every row to draw the part the reader sees.
2. *The hierarchy is refdata's and the count is trading's.* The legacy read both from one client, which is the same two-read split this investigation recommends.
3. *The count per node is summed in the client*, as the legacy did, so no recursive aggregate belongs in a view. What the legacy got wrong is the batching: one request per book is per-object where the sixth axiom asks for batch. The count read must be one call returning a row per book.
4. *A typed filter, not an opaque node id.* The legacy's =node_id= string is a primitive standing in for two different keys, which the wire rules forbid. The new read names its members: =book_id= for a book and a portfolio member for a portfolio.
5. *The party belongs in the tree.* The legacy nests parties by =parent_party_id=, and the relationship-view rule agrees: "A group is a party, nested by its own parent". The prototype drew a single party root; it now nests parties and carries three node kinds, so the model and the screen agree.
6. *The open question is now only size.* Whether the hierarchy is read lazily or as whole lists depends on how large a party's tree is, which is one measurement, not a design choice.

* The measurement of a party's tree

| Portfolios | 48, of which 20 are virtual and 4 are roots | =jq length .../portfolios.json= |
| Books | 38 | =jq length .../books.json= |
| Portfolios per party | group 1, UK 21, US 13, HK 13 | =jq '[.[].company_code] | group_by(.) | map({(.[0]): length}) | add' .../portfolios.json= |
| Books per party | group 2, UK 20, US 8, HK 8 | the same over =books.json= |
| Largest party tree | 42 nodes: the party, its 21 portfolios and its 20 books | derived |
| Whole-group tree | 90 nodes: 4 parties, 48 portfolios, 38 books | derived |

* What the measurement decides

A party's tree is *tens* of nodes. The largest is 42, and the whole holding company is 90. At that size the node read model is premature: one page of the two existing lists draws the whole tree, which is exactly what the legacy did and why it got away with it.

Two consequences, and both are cheap:

- *Read whole, then guard the ceiling.* The BFF reads =portfolios.list= and =books.list= at a page size above the tree size and zips them. The guard cannot compare =total= with the rows it holds, because =total= counts the tenant while the rows are party-scoped; it compares the rows against a page that came back full, and says the tree may be partial when it did.
- *The party filter is still missing.* Neither filter carries =party_id=, and the party is applied by erasing other parties' rows after the pager, so =total= counts the tenant. At 90 nodes this reads acceptably, and the erase is the defect to fix when either list is touched.

The node read model therefore becomes the answer to a *measured* threshold rather than the first step: when a tenant's tree passes the page size, or when a lazy tree is wanted for its own sake, the =portfolio_tree_node= read model is the shape to build, and this page already states it.

* Recommendations

1. Write the classification down on the checklist before building: a read model spanning refdata entities, assembled on the server for display.
2. Carry three node kinds, as the legacy did: party, portfolio and book, with the party nested by =parent_code=.
3. *Draw the tree from the two existing lists for now*, because the measurement says a party's tree is tens of nodes. The BFF reads both lists at a page size above that, zips them into party, portfolio and book nodes, and refuses to draw a tree whose =total= exceeds the rows it holds.
4. Read the count as one batch, never one call per book: the trading count read with a row per book, filtered by =book_id_one_of=, which the list already carries.
5. Sum the subtree in the client, as the legacy did, and never aggregate it in a view.
6. Build the =portfolio_tree_node= read model when the tree passes the page size, or when a lazy tree is wanted for its own sake. The shape is stated above and does not change.
7. Fix the erase-after-paging defect in both refdata repositories the next time either list is touched, because it makes every paged read disagree with its own total.
8. Do not build the tree in the list's PR. The list is settled and shippable without it; the tree is its own task.
