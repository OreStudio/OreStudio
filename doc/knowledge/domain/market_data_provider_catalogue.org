#+description: The simulated providers a synthetic collection can stand for, why a provider is optional, how the synthetic mark keeps a simulated feed apart from a real one, and how a system collection's feeds reach every tenant.
#+type: knowledge
#+level: cross

* Summary

=market_data_provider= is a reference-data table of the providers whose
market data the synthetic feeds simulate: data vendors such as Bloomberg and
Refinitiv, exchanges such as CME and LSE, a broker, and the ORE examples, a
reference set. It is declared in =ores.synthetic.api/domain/market_data_provider.hpp=,
and a collection's required =provider_code= is validated against its =code=.

The rows arrive through DQ, as the installation's other reference data does.
The =synthetic.market_data_providers= dataset stages them in
=ores_dq_market_data_providers_artefact_tbl=
(=projects/ores.sql/populate/synthetic/synthetic_market_data_providers_artefact_populate.sql=).
The dataset is a member of the =system_core= bundle, so the system
provisioning step of a profile such as =acme_demo= publishes it into the
system tenant through =ores_synthetic_publish_market_data_providers_from_dq_fn=
on =synthetic.v1.ops.publish_market_data_providers_from_dq=. The function
refuses any other target tenant, so a tenant's own setup never writes the
catalogue.

* Detail

** Why it exists

A desk reads Bloomberg's FX spot, an exchange's settlement prices, a broker's
composites: the market has providers, and a synthetic installation that
simulates the market needs to say which provider a feed stands for. A
system-scope collection names its provider, so the installation runs a
simulated provider once and every tenant reads it as that provider's data.

** The row

| Column | Meaning |
|--------+---------|
| =code= | The provider's code, lower case, the provider segment of a source name |
| =name= | The provider as a person knows it, without the synthetic mark |
| =kind= | =data_vendor=, =exchange=, =broker= or =reference= |
| =description= | What the provider's feeds simulate, in a sentence or two |
| =display_order= | The order screens list providers in |

The system tenant manages the rows, as it manages the yield curve process
types; the catalogue is in =ores.synthetic= because only synthetic generation
uses it.

** Every collection names a provider

A collection names the provider it stands for, so every feed has one. The ORE
examples are a provider of their own, =ore=, of kind =reference=. There is no
generic provider.

** The synthetic mark

Every provider here is simulated, and nothing may read a simulated feed as the
real one. Every source name starts =synthetic.=, which the feed tables check,
and a provider's feed's source name starts =synthetic.<provider code>.=.
Screens name a provider with the mark, as "Bloomberg (synthetic)". A real
provider integration belongs in market data, under its own namespace, and
cannot collide.

** The fact the code shape does not show

A collection's scope decides who reads its feeds. A system collection belongs
to the system tenant and its system party, as its feeds do, and row-level
security lets every tenant read a system collection and every feed and part
under it. Writing stays with the system tenant. The synthetic service's
generated repositories state the same with =:system_tenant_visible: true= on
each entity (the collection, its feeds and their parts, the folders and the
provider), so a tenant's service call returns the system rows the policy admits.
No dataset publishes a system collection yet, so a tenant sees only the
provider catalogue so far.

Providers are published into the system tenant alone, and the roles that may write a
provider belong to the system tenant. The provider table's policy admits the system
tenant's rows to every tenant for reading, and a tenant writes only its own rows. A
provider code is therefore unique in practice. A tenant that holds the write
permission and writes a provider with a system code would make a lookup by code
ambiguous, which the catalogue does not guard against.

Only one enabled, bound system collection may run at a time: the conflict
guard of the collection rejects a second. So one provider is chosen as the
bound, authoritative source for a pair such as EUR/USD, and the other
providers' collections run sandboxed. A rate blending service is the planned
owner of blended rates: it will read the providers' spots and publish the
blended EUR/USD itself. A tenant consumes a
system feed's ticks through a feed binding, which stores each tick once for
every party that binds the source.

** How a set of feeds names its provider

Feeds come from a synthetic feeds dataset, the one way to set them up: a DQ
dataset of artefact type =synthetic_feeds=, published by
=ores_synthetic_publish_feeds_from_dq_fn=. A publish that names a party makes a
party collection in that party. A publish that names none, into the system tenant,
makes a sandboxed system collection held by the system party. Each FX and IR feed row of the dataset may carry a
=provider_code=. The published feed's source name then starts
=synthetic.<provider code>.=, and the collection names the provider when
every feed row names the same one. The feed tables check only the =synthetic.=
mark: the provider part of a source name holds because the one publish
path builds it, not because a constraint ties it to the provider.

=synthetic.feeds.bloomberg= is the provider dataset today
(=projects/ores.sql/populate/synthetic/synthetic_feeds_bloomberg_populate.sql=),
in the =synthetic_bloomberg= bundle that =acme_demo= publishes. It holds what
the ACME reports need: a USD spot for each of 26 currencies, and a curve on
the overnight benchmark of each of 28 currencies, plus the USD FOMC short
end. A bank reads all its spots from one vendor, so one provider quoting
every pair is the realistic case. The 13 spots the Federal Reserve H.10
release quotes start from its 2026-05-05 vintage; the other 13 start at an
illustrative fixed level, which is not a sourced quote.

** The provider feeds

Three providers have system feeds, in datasets of the =system_core= bundle
(=projects/ores.sql/populate/synthetic/synthetic_feeds_providers_populate.sql=):

| Provider | Feeds |
|----------+-------|
| Refinitiv | Fourteen cross spots between the major non-USD currencies, which Bloomberg leaves to the cross-rates matrix |
| ICE Data Services | LIBOR curves of USD 1M and 6M, and GBP, CHF and JPY 3M |
| Tradeweb | Dealer composite curves of EURIBOR 1M and 6M, GBP and JPY LIBOR 1M, and CHF LIBOR 6M |

One series has one running publisher, in the whole service, whatever the binding
mode, so each dataset names series that Bloomberg and the 2016 ORE Samples do not. A
feed's series is its currency, its index tenor and its pillar, or its currency
pair. Bloomberg stays a party collection, bound, because the demo's reports read
its ticks.

CME, LSE and Eurex have no feeds. They quote futures and equities, which have no
feed kind yet, and the IR curve config admits term tenors only for the LIBOR and
EURIBOR families, so a CME Term SOFR curve cannot be stored.

The synthetic service starts the auto-start feeds of the system collections when it
starts, in the system tenant. Only the system tenant starts and stops a system
feed. A start or a stop from another tenant skips it, and the feeds that should
run, for another tenant, leave the system feeds out.
