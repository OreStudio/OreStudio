* Goal

Every documented leaf of curveconfig.xsd is linked to the value set its values belong to, derived from the parse function ORE uses for it, so no screen rests a valid value in code.

* Acceptance

- The extractor records the parse function behind each leaf, as the conventions extractor records the parser behind each term.
- Every documented leaf is linked to a value set: a catalogue of refdata data, a list an ORE parser accepts, or its type.
- A leaf whose parser states no list is text only where its type says why, and any other parser with no list stops the generator instead of falling back to free text.
- The conventions precedent's classifier is reused where a kind is shared, so a day counter means the same in a curve and in a convention.

* Notes

- *The conventions method does not carry across, and this is the finding of the
  first pass.* The conventions extractor learns a term's type from the parser
  its read wraps, or from the `build` method applying a parser to the member the
  read stored. A curve config has neither for most leaves: =YieldCurveConfig=
  declares no =build= at all, and ORE parses these strings in the curve
  construction code, far from the parser class. Measured on ORE
  =3d75a6908=, the extractor finds a parse function behind 27 of 434 leaves.
- *What is left is a designed choice, not a mechanical derive.* Name-based
  recognition of ORE's vocabularies adds 53 more leaves: currency, calendar, day
  counter, business day convention, index and convention name, by the name ORE
  gives the leaf. That still leaves 354. Some of those are genuinely closed
  lists whose parser lives elsewhere, =InterpolationMethod= and
  =VolatilityType= among them, so a curated map from leaf name to set covers
  them, at the cost of provenance: the set is authored and marked to review
  rather than derived from a parse function.
- *The derive is a catalogue, a curated parser link, or the type.* The owner
  chose the curated map on 2026-10-27. A leaf whose name is one of ORE's
  vocabularies takes that catalogue (currency, day counter, business day
  convention, 29 leaves); a leaf the curation links to a parser takes that
  parser's list, which is still derived from the ORE source (5 curated links,
  7 leaves); a leaf whose type the extractor read takes its type's set (26
  leaves); the rest are text (151). A link is keyed by the section it applies
  to, or by =*|= when the name means the same thing in every section, so a link
  never silently widens to a family its reason does not name. The generator prints the text ones, so the
  coverage is read, not assumed.
- *A rule from the conventions task cannot be reused as written.* That task
  stops the generator when a parser states no list, so a list the extractor
  failed to read cannot become free text. Here most leaves have no parser to
  appeal to, so the rule would stop every run. The replacement has to say what
  a leaf with no parser is, and why that is not a silent fallback.

* Result

213 documented leaves are linked to a set. 62 carry something narrower than
text: 29 draw on a refdata catalogue, 7 on a list an ORE parser states, and 26
take their type's set. The other 151 are text, which is what the
curve configuration holds for them, and the generator names every one.

The set a leaf takes is a catalogue by name, a curated parser link, or its type.
The curation states, per link, the reason, the ORE source it came from and the
curator, and the values behind a link are derived from the parser's map rather
than transcribed.

`ore-parameter-value-sets` and `ore-parameters-seed` pass. `er-diagram` is red
on the inbox schema, which this branch does not touch; it is drift from a merge
after this branch's base.
