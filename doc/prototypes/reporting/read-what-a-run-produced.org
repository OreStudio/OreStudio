* Summary

This prototype argues what "the result" of a run is, and how much of it belongs
on the screen before a person goes looking for a file. It carries three
structural variants switched with =?variant=, and it answers to
[[file:../../knowledge/journeys/reporting/journey_read_what_a_run_produced.org][Read what a run produced]].

It is throwaway. It reads no service, and the archive manifest it draws is a
fixture, said so on the page.

* Detail

** The question

A run produces an output message, an archive in storage, and a set of files
inside that archive. Which of those is the thing a person came for? The three
variants answer differently, and the difference decides how much of the screen is
numbers and how much is files.

** The three variants

Switch with the bottom bar, or with =?variant=.

| Variant | Name | The structural argument |
|---------+------+-------------------------|
| =A= | Figures first | The numbers are the screen: headline figures, then a results table, with the archive as a modest footer action. |
| =B= | Artefact first | The screen is a manifest of what the run produced: the archive, the files inside it with row counts and sizes, and a download per file. The numbers are a preview of one selected file. |
| =C= | Narrative first | A short written summary of what the run did and what it means, with the figures embedded and the files at the end, for a reader who wants the sentence before the spreadsheet. |

** Two things the page refuses to fake quietly

The run carries an =output_storage_key= of the form
=reporting/runs/<instance-id>/output.tar.gz=, and the page shows that shape
rather than a friendly invented name.

Neither the file list nor the two downloads exist. **No operation lists the files
inside a run's archive**, and there is no archive download and no ORE package
download as operations either. Variant =B= draws a manifest and labels it a
fixture on the panel itself, so the gap is visible rather than designed around.
That is the honest shape of this journey today.

** The drill-down: from the run's figures to one trade

A run's result is not only an aggregate. The engine writes =npv.csv= into the
archive, and that file carries one row per trade, with the columns =TradeId=,
=TradeType=, =Maturity=, =MaturityTime=, =NPV=, =NpvCurrency=, =NPV(Base)=,
=BaseCurrency=, =Notional=, =NotionalCurrency=, =Notional(Base)=,
=NettingSet= and =CounterParty=. The page uses them, so a person can get from
the run's total to the trade that made it.

Each variant carries the drill-down in the shape it already argues. =A= puts the
per-trade table under the aggregate figures and keeps both. =B= offers the rows
when =npv.csv= is selected in the manifest, instead of a handful of preview
lines. =C= links from the prose to the table rather than reproducing the
figures in a sentence.

A row shows six columns: =TradeId=, =TradeType=, =NPV=, =NPV(Base)=,
=Notional= and =CounterParty=. Opening a row answers with that trade's result,
and, where the run recorded an error against that =TradeId=, the error itself.
The page reuses the run's own error fixtures for this, so a trade that failed
is reachable and shows why: the table covers a good number and a bad one.

A trade in the result is the trading trade with that id, so the row leads to the
trade. =trading.v1.trades.get= is what resolves the id.

The table is a fixture, and the panel that draws it says so. **No operation
parses the archive.** =ores_compute_results_tbl= carries the archive's location
and an outcome, not parsed rows. A built screen cannot serve these rows
until a result store or an archive read exists, and the page draws the gap
rather than hiding it.

** The figures come from the analytics the configuration names

A report's numbers are not free choice. Its report configuration names a set of
analytics, and those are what the report produces. Headline Position runs =npv=
and =sensitivity=, so the run this prototype draws shows an NPV, a Delta and a
Gamma, and says so on the screen: the figures are the output of those two
analytics and no others.

The archive follows the same rule. A run that runs only =npv= and =sensitivity=
does not write =cashflow.csv= or =saccr.csv=, so the manifest holds neither, and
a second fixture run on a report that does run =saccr= shows NPV and exposure
instead of Delta and Gamma. A reader can watch the analytic set change the
figures.

** A run can complete and still carry errors

The page draws one run that completed clean and one that completed carrying
eleven rows, eight =Analytics= errors and three =Configuration= warnings. The
second warns before the figures are trusted, and offers the way to see why.

** What is fake

The figures, the file names, the row counts, the sizes, the archive key and every
trade row are mock. Nothing reads a server. The file names are real ORE output
names — =npv.csv=, =saccr.csv=, =pricingstats.csv=, =log_structured.json= and the
rest — because an invented set would hide the shape of the thing being judged.

** Where the code lives

=doc/prototypes/reporting/read-what-a-run-produced/=. Three files, plain HTML,
CSS and JavaScript, no framework and no build step.

** The verdict

None yet. This page is on the branch that proposes it and waits for review.

** What it does not settle

Whether the result is read in the application at all, or exported and read
elsewhere. The archive listing, the per-trade rows and the two downloads are the
operations this journey needs and does not have, and they are the first thing
the real build would have to add.
