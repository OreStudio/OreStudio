* Goal

Answer one question with a throwaway prototype: what should the member's
*Security* screen look like in =ores.web=?

[[id:5FB73D18-4734-485B-B414-9EBD1B76A239][Protect my account]] carries one
screen. It holds the password form, the sign-in state and the places the
account is signed in, because the member thinks of them as one thing. The
prototype decides the layout, the order of the panels, the copy of the empty
and unavailable states, and how the screen presents the operations the server
does not have.

* Notes

The journey's gaps, from the * What is missing section of
[[id:5FB73D18-4734-485B-B414-9EBD1B76A239][Protect my account]]. The screen
states each one, and the prototype decides how.

1. *No way to end one session.* =iam.v1.auth.logout= ends only the caller's own
   session. A member who sees an unfamiliar sign-in cannot end it.
2. *No TOTP enrolment.* =account.totp_secret= exists, and nothing enrols,
   replaces or clears a secret for an existing account.
3. *=iam.v1.sessions.active= returns nothing.* The subject exists and is a stub.
   The route =/api/v1/iam/sessions/active= is =ores.http='s, and it forwards to
   the same subject, so it answers with no rows too.
4. *No session statistics.* The continuous aggregates exist with no subject.
5. *The current password is verified.* The journey document says the handler
   ignores =current_password=; on this tree
   =account_operations_service::change_password= verifies it. This claim is
   stale, and the correction belongs to the extraction pass.

Route =/prototype/security?variant=a|b|c=, switched from the bar at the foot of
the page. The page needs no server: the prototype answers its path before the
gate, so a reviewer runs

npm run dev:web --workspace @ores.web
#+end_src

and opens =http://localhost:5173/prototype/security?variant=a=.

*Three variants on one screen.*

- *A · Password first.* One column, in the order the member acts: the password
  form, the sign-in state, then the places the account is signed in.
- *B · Sessions first.* The sign-ins lead, because a member opens *Security*
  to check them; the form and the state share a row under it.
- *C · Two columns.* The password form is a fixed left column, so its rules
  stay in view while the state and the sessions fill the right one, and the
  gaps are listed once in a panel at the foot.

*Recommendation: C, on the panels only.* The two-column shape keeps the form's
rules visible and gives the session rows the width they need, which A and B
both trade away. The "Not available in this build" panel is the prototype's own
statement and is not part of the recommended screen: in the build, each line
becomes a real control or the screen says the data is unavailable where that
panel sits.

*Decisions the prototype settles.*

- *The session list is the reason the member opens the screen.* The password
  change is a form they use once; the sign-ins are what they come to read. A
  and B both put the sessions after the form; C keeps them in view.
- *The rules come from the server.* The prototype reads its policy from a
  fixture with the shape of =GET /api/password-policy=, and the built screen
  reads the route. The rules are the server's record, and the screen states
  them rather than holding a copy.
- *The current password is a confirmation the server checks.* The field stays,
  and the screen may say the server verifies it.
- *"End session" is drawn unavailable, not hidden.* A member who sees an
  unfamiliar sign-in must be told what the screen cannot do, because the
  remedy today is to change the password.
- *The sign-in state is tags and details, not a panel of its own.* The screen
  carries the four values the journey document lists without giving them the
  weight of a separate screen.

*Document claims the tree contradicts.*

- The journey document says the change-password handler ignores
  =current_password=. It verifies it on this tree
  (=account_operations_service::change_password=), so the "What is missing"
  item 5 and the note under the operations table are both stale.
- The journey document says the BFF answers =/api/v1/sessions/active= and that
  "the browser has a working read today". The route is =ores.http='s, it forwards
  to a subject that answers with no rows, and the BFF serves no session route at
  all, so the browser has no read on any path.

The corrections belong to the extraction pass, which owns the document. They
landed in the document on 2026-09-30, under
