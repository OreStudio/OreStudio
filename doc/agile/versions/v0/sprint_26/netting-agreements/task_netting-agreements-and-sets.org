* Goal

Give every netting set an identity of its own and tie it to the legal agreement that makes netting enforceable.

* Acceptance

- netting_agreement and netting_set are generated in ores.refdata across every layer the codegen covers.
- A netting set with an agreement has that agreement's counterparty and legal entity, enforced by a pinned key.
- A set without an agreement is allowed and records that its trades do not net.

* Plan

- Two models in =projects/ores.refdata/modeling=, on the
  =uuid-identified-lookup= profile (tenant-scoped, no workspace, since
  the trade shape design removes workspaces).
- =netting_agreement=: agreement number (natural key), the firm's legal
  entity and the counterparty (both required, fixed for the agreement's
  life), agreement type checked against ISDA, AFB, FBF and OTHER, and
  governing law.
- =netting_set=: code (ORE's netting set id, natural key), the agreement,
  the counterparty and the legal entity, call type, initial margin type
  and risk weight. The agreement and the two parties are optional,
  because an ORE document names a set by code alone. A check requires
  both parties when the set has an agreement, so the pinned key to the
  agreement is never skipped by a null.
- Generate every layer with =compass codegen entity generate=, then wire
  by hand what no generator owns: the SQL create and drop lists, the
  permission seeds, the core registrar, the shell menu and the CMake file
  lists.
- The credit limit the note names as part of a set's identity has no
  entity yet, so it is left out.

* Result

- =netting_agreement= and =netting_set= are generated in =ores.refdata=:
  SQL schema and notify triggers, domain types, repository, service,
  protocol, handlers, history providers, eventing, generators, shell
  commands and TypeScript wire types.
- Wired by hand: the refdata SQL create and drop lists, the permission
  seeds, the refdata core registrar, the shell refdata menu and the CMake
  file lists of the four components touched.
- A netting set with an agreement must carry both parties, by a check, and
  they must be the agreement's, by a pinned key. A set without an agreement
  is accepted.
- In Postgres, in a transaction that rolled back, with stub counterparties
  inserted with their own triggers off: an unknown agreement type was
  refused by its check (23514); a set naming another counterparty than its
  agreement's was refused by the pin (23503); a set with an agreement and
  no parties was refused by the check (23514); a set without an agreement
  and a matching set were accepted.
- After review: an amendment that kept the agreement's parties was
  accepted; one that changed the counterparty was refused (23514, fixed
  column); a negative risk weight was refused (23514).
- Row-level security: tenant isolation on both tables, and party isolation
  on reads; a set without a legal entity stays visible across its tenant.
- Build: linux-clang-debug-make clean. ctest: 89 of 89 binaries passed on a
  database recreated from this branch, including the two generated eventing
  integration tests and 38 generated shell command cases.
