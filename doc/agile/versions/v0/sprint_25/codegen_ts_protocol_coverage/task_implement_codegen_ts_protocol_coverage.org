* Goal

Give every IAM protocol header its TypeScript twin. A header holds all the
messages of one entity or one non-entity protocol, and its messages come from
one model. Both targets render from the same derived message list, so a message
exists in both or in neither, and no IAM protocol switches the facet off.

* Acceptance

- Every IAM protocol header has a TypeScript twin, and a check fails when one is missing.
- One header per entity or protocol holds its messages, and those messages come from exactly one model.
- An IAM entity has a TypeScript domain module, and the protocol interfaces reference it.
- No IAM protocol switches the TypeScript facet off.
- The generated tree regenerates with no diff, and ores.web typechecks with its suites passing.

* Plan

IAM generates 138 messages across 16 headers: 11 protocol models with 96
messages and 5 entity models with 42. Six protocols carry a TypeScript twin
today, 30 interfaces in all, so 108 messages have none, and five models opt the
facet out.

1. *Done, =45d967c308=.* The =ores.ts.domain= facet, the =_ts_type= projection
   for =ores::<component>::domain::<entity>= and a timestamp, and the loader-side
   derivation of the standard CRUD list, rendered by both twins. The five
   entity-derived protocols now have twins — =tenant=, =tenant_type=,
   =tenant_status=, =account_type=, =account_contact_information=, 40 messages —
   and the C++ came out byte-identical.
2. *Done, =5e5c6a8155=.* The junction. =ores.ts.domain= admits =junction=, so
   =AccountParty= is generated beside the entity interfaces, and the
   =account_party_messages= opt-out is gone — the first of the five. The C++
   junction block was never in play: the operation model owns that header.
   Removing the opt-out also needed the operation's domain import, or the
   interface would have named a type it never imported.
3. Model IAM's seven hand-written wire types. Planning corrected two assumptions
   and set the order below.
   - *Shapes.* =account=, =login_info=, =permission= and =role= are entities —
     each has a hand-written table. =account_version=, =session= and
     =session_statistics= are message-only: the first has no table and there is
     no version facet in the codegen at all (the story's "through the account
     entity's version facet" was wrong), and the other two carry members that no
     column has — =session= has =party_id=, =visible_party_ids= and =username=
     with nothing behind them, and the sessions table is a Timescale hypertable
     whose primary key is =(id, start_time)=.
   - *Order.* First a codegen enabler, then =login_info= (smallest entity,
     proves the soft-update path), then =permission= and =role=, then =session=
     with =session_statistics= (removes one opt-out), and =account= with
     =account_version= last, behind its own PR.
   - *The enabler.* Two models render one header today: the entity or junction
     block of =cpp_protocol.hpp.mustache= and an operation model for the same
     entity both write =<entity>_protocol.hpp=, and whichever renders last wins.
     Nothing may be modelled until one model owns the header.
   - *The risk.* =account= is the aggregate the authentication surface uses. A
     generated service, repository and handler write the same paths as
     hand-written auth-critical code (=account_service.hpp=, 14 KB;
     =account_handler.hpp=, 1200 lines), and its entity-derived CRUD set would
     collide with the 28 command messages in =account_messages.org=. Both
     =std::optional<uuid>= members need the reflect-cpp workaround re-verified.
4. Make a protocol header without a TypeScript twin fail the drift check, and an
   =:ores.ts.protocol.enabled:= key fail with it.

* Progress

The drift gate regenerated TypeScript for every registered component once the
facet admitted entities, and it stopped on =ores.refdata.business_unit=, whose
response carries =ores::utility::domain::hierarchy_node= — a hand-written
utility type with no projection. Fixed in =a302087bd9= by scoping the gate: a
component is regenerated at a TypeScript facet only once that facet's output is
committed for it. The facets and their output patterns are read from the
template library, so a component joins the TypeScript side of the gate the
moment its first generated file lands and no list needs maintaining. Every
other technical space is regenerated for every component as before.

IAM now regenerates at six technical spaces plus =ores.ts.domain=,
=ores.ts.protocol= and =ores.ts.ui=, and reports no drift; refdata regenerates
at the six plus =ores.ts.ui= alone; the full set passes in about twenty
seconds. The gate goes green on PR #2110 with all five checks.

* The login_info preview

Modelling =login_info= was previewed before anything was overwritten, and the
preview stopped it. Two blockers, both real.

- *The codegen cannot express a current-state entity.* The SQL template emits
  =valid_from= and =valid_to= unconditionally, and =no_audit_columns= removes
  only =version= and the audit tail, so generating =login_info= would replace
  its hand-written table with a bi-temporal one: the primary key becomes
  =(tenant_id, account_id, valid_from, valid_to)=, a GIST exclusion and two
  checks appear, the insert trigger and its function are replaced, and
  =login_info_locked_idx= — a partial index on =locked= — is dropped with no
  replacement. None of the five =entity_org= shapes touches the temporal axis.
  *Decided:* add a first-class current-state shape to the codegen rather than
  migrate the table, so the table's behaviour does not change and the generator
  gains the ability to express a table with no history.
- *Entity domains are never gap-checked and the IP type has no projection.*
  Generation emitted =last_ip: ;= because =_ts_domain_type= has no mapping for
  =boost::asio::ip::address=, and only operation and junction models run the
  silent-gap guard, so invalid TypeScript would have been committed. The
  projection is =string=: the reflector at =ores.utility/rfl/reflectors.hpp=
  143-159 writes =v.to_string()= through =ReflType = std::string=.

A third finding waits for a decision rather than a fix: an entity-derived
=login_info= protocol would emit subjects =iam.v1.login_info.*= while
=account_messages.org= already declares =list_login_info_*= in
=account_protocol.hpp=. The ownership gate does not cover it, because
=account_messages= declares the entity =account=, not =login_info=.

* The check that changed the tree

The drift check regenerates in place and then compares, so it writes what it is
meant to be checking. While a drafted =login_info= model sat in
=projects/ores.iam/modeling/=, an in-place =--all= run regenerated that entity
for real: sixteen hand-written files overwritten and thirteen new ones created,
all restored by hand. The draft then had to be shuffled between =build/output/=
and =modeling/= to keep the check safe, and one agent lost it to a temporary
directory being wiped.

A check that mutates what it checks is the defect; moving the file was the
workaround. =check_component_drift.py= gains =--dry-run=: it generates every
component into a temporary root, reports what would change or would be created,
writes nothing, and exits non-zero when anything differs. A drafted model can
then stay where it is. The memory =generate_one_entity_at_a_time= carries the
rule, and the proof is the drafted =login_info= model: present in the modeling
directory, the dry run must report its output and leave every file
byte-identical.

* Notes

The message inventory is
=build/output/iam_message_inventory.json=: every message, its fields, subject,
response, source model, and target file. It was produced from the generated
headers and checked against them, so the counts above are exact.

Two defects found while taking the inventory:

- =tenant_status_protocol.hpp:67= declares =std::vector<std::string> statuss;=.
  The template pluralises the entity name by appending =s=, so a name already
  ending in =s= becomes =statuss=. The delete-request field name needs the same
  treatment as the TypeScript twin, and the fix belongs with this work.
- =get_account_contact_informations_by_account_id_request= and its response are
  the only messages the codegen derives rather than a model declaring them
  (=core.py:3343=, from the =account_id= foreign key's =list_by=). They stay
  derived, so they are not part of the message models.

Two findings from reading the codegen, both of which shape the order of work:

- *Two of the five opt-outs have no model to project onto.* =account=,
  =account_version=, =login_info=, =session=, =session_statistics=,
  =permission= and =role= are hand-written domain structs; there is no
  =ores.iam.account.org= entity model at all, only a knowledge page that links to
  =account.hpp=. A generated TypeScript domain layer cannot cover them, so
  =account_messages= and =account_history_messages= need hand-written TypeScript
  domain types, or the account aggregate needs modelling, before their
  protocols can render. The five entity-derived protocols — =tenant=,
  =tenant_type=, =tenant_status=, =account_type=, =account_contact_information= —
  are fully model-backed and come first.
- *A partial derivation already exists.*
  =projects/ores.web/scripts/emit_protocol_ir.py= reads the entity models and
  emits a language-neutral protocol IR for the CRUD set, with =--all= and
  =--check=. It is a useful specification, but it is not a twin of the template:
  it does not cover =list_filter_column=, =has_as_of_lookup=, =has_batch_save=,
  =has_parent_id=, =read_for_cache=, =extra_list_requests= or =single_delete=,
  and its response collection name uses =entity_plural= where the header uses
  =entity_plural_short= (=tenant_types= against =types=). The derivation that
  feeds the TypeScript twin therefore belongs in the loader, beside the flags the
  C++ template already branches on, and the script should be retired onto it
  rather than trusted.

* Result

Part of the task shipped in PR #2110, which is why the task stays STARTED rather
than closing here. Its acceptance — every IAM protocol header with both targets
and no facet switched off — is not met yet.

Shipped. An entity model renders its protocol as TypeScript: the =ores.ts.domain=
facet, the =_ts_type= projection for =ores::<component>::domain::<entity>= and
timestamps, and the standard CRUD message list derived once in the loader so
both twins render from it. That gave =tenant=, =tenant_type=, =tenant_status=,
=account_type= and =account_contact_information= their twins. Junction models
gained the same treatment, which removed the =account_party= opt-out. The drift
gate now regenerates a component at a TypeScript facet only once that facet's
output is committed for it. Twelve of IAM's sixteen protocol headers have both
targets now, up from six, and the C++ output is byte-identical throughout.

Remaining. The four opt-outs — =account_messages=, =account_history_messages=,
=authorization_messages= and =session_messages= — are all blocked on the six
hand-written wire types that have no org model: =account=, =account_version=,
=login_info=, =permission=, =role=, and =session= with =session_statistics=.
Modelling them, deleting their hand-written headers and companions, and
re-pointing the account handlers, the IAM service and the shell is the rest of
the task.
