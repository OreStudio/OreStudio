#+title: Signing in with several parties leaves the person on the sign-in page
#+description: The API answers a login with outcome party-required for an account that holds several parties, and the web client stays on the sign-in page instead of asking which party to work in.
#+type: capture
#+level: cross
#+filetags: :web:iam:session:sign-in:bug:
#+created: 2026-10-25
#+updated: 2026-10-25

A person presses Sign in on the web and nothing happens. Seen on 2026-10-25 as a =Trading= persona opened with =compass open-as=, and reproduced without a browser the same day.

* What the API does

=POST /api/session= with ={"username": "tenant_admin@acme_corporation", "password": ...}= answers 200 with:

#+begin_example
{"outcome":"party-required","username":"tenant_admin", ...,
 "availableParties":[{"id":"127ccbab-...","name":"ACME Corporation HK Ltd"}, ...]}
#+end_example

So a login succeeds and states that a party must be chosen next; =POST /api/session/party= then completes it, and subsequent reads answer.

* What the screen does

The sign-in page renders, accepts the username and password, and after the button is pressed the page is still the sign-in page. A Playwright run against the running fleet captured exactly that: the page snapshot at the point of failure is the sign-in form, not a party chooser.

* So

Either the client does not treat =party-required= as a step it must take, or the party chooser is not reachable from the sign-in page. Either way an account holding more than one party cannot sign in to the web, whatever its permissions, and =compass open-as= inherits the fault because it fills the same form.

* Evidence

=projects/ores.web/tools/ui-tests/specs/trades.spec.ts= drives the case, and =test-results/.../error-context.md= holds the page snapshot. The UI tests are a development instrument and no pipeline runs them.
