This page documents a [[id:31C868B9-306E-4282-BA8C-07E647021B34][task]] in the [[id:5EA439A5-43AE-4223-9026-6B3D8C91AEEA][Give object storage a NATS and HTTP interface with authentication]] story. It captures the goal, current status, acceptance, and any notes or results.

* Goal

Storage is reachable over NATS and over HTTP, and both surfaces authenticate.
That needs a service of its own, so the component splits into the parts the
architecture requires — a public API, a core, and a service — before any surface
is modelled: the operation set is declared once, as an operation model, so that
its protocol header, its TypeScript twin and its shell commands generate, while
the handler, the service and the registrar are hand-written, because no facet
admits an operation model. The storage routes that already move bytes gain the
identity and permission checks they lack today, and both transports are made to
fail closed rather than fall back to allow.

* Acceptance

- The component is split into an api, a core and a service, its consumers link
  the public API rather than the implementation, and the catalogue and the
  permission registry name the new parts.
- Storage holds no bucket name, no bucket registry and no allow-list. The bucket
  is part of the key, the server validates it as a path segment and authorises
  the operation, and which buckets exist stays the caller's concern.
- An operation model declares the storage surface, and the generator produces its
  protocol header, TypeScript twin, shell commands and shell recipes from it. The
  handler, service and registrar are hand-written, and the task records that
  rather than implying a generation that no facet performs.
- Every storage route calls =auth_required()= and checks its own
  =storage::objects:= code before it acts; an unauthenticated put and get are
  refused, and a caller without the code is told so.
- The NATS handler checks the same codes, and =storage= joins
  =check_handler_permissions.py='s registry so the hand-written handler is gated
  like a generated one.
- The security preconditions are met rather than assumed: an authenticator is
  configured for the HTTP server and a verifier for the NATS service, because
  both transports otherwise allow every request, and the HTTP token carries a
  tenant, because login does not mint one today.
- A raw shell surface takes a bucket, a key and a local path, so storage is
  usable without a domain verb.
- A test proves the put, get, exists, list and delete round trip on both
  interfaces, and the refusal path on each.

* Plan

** The split comes first

A service needs somewhere to live, and this component has none: it is one flat
library behind a single public header that its consumers link directly, with no
=api=, =core= or =service= part. So the first move is structural, following
[[id:F27E5DF7-6223-4B6F-80A5-CEFBEB1BC756][Component architecture]]: an
=ores.storage.api= holding the modelled protocol and the path helpers the
consumers are allowed to see, an =ores.storage.core= holding the implementation
both interfaces call (the HTTP client, the archiver, the transfer helpers), and
an =ores.storage.service= holding the handler, the service entry point and the
registrar. The component joins the catalogue in the same move, because codegen
cannot discover a model until it does.

** The shape: an operation model, not an entity

Storage is not an entity: its value is opaque bytes, not a row. The generator has
a metatype for exactly this — =ores.codegen.operation= — and twenty models
already use it, including the whole of =ores.telemetry=, which passed the clean
standard as an operation-only component. Storage follows them.

What that buys and what it does not is the first thing to be honest about, because
the facets decide it:

| Facet | Admits =operation=? | Generates |
|-------+---------------------+----------|
| =ores.cpp.protocol= | yes | the protocol header |
| =ores.ts.protocol= | yes | the TypeScript twin |
| =ores.cpp.shell-command= | yes | the shell commands and recipes |
| =ores.cpp.nats-handler= | **no** | nothing |
| =ores.cpp.service= | **no** | nothing |

So the handler, the service and the registrar are hand-written, by design and by
precedent: =ores.scheduler='s operation model says so in its own page, and
=ores.iam='s =account_operations= adds a hand-written handler and wires it into
=registrar.cpp= by hand. The task therefore claims generation only where
generation exists.

=storage= is also absent from =component_catalogue.org=, so codegen cannot
discover a storage model at all. Adding it is part of this task, and it brings the
clean-standard rollout with it (a TypeScript twin that must be drift-clean, and a
component the drift gate can finally name).

** The operation set

The
[[id:C650CBC9-FDED-4C68-981F-7902E296928E][NATS entity protocol specification]]
fixes eight verbs and forbids inventing one. The subject family is
=storage.v1.objects.>=

| Operation | Subject | What it does |
|-----------+---------+--------------|
| put | =storage.v1.objects.put= | Create or replace one object at a bucket and key. |
| get | =storage.v1.objects.get= | Read one object's metadata, and its value when small. |
| delete | =storage.v1.objects.delete= | Remove one object. |
| exists | =storage.v1.objects.exists= | Answer whether the key is present, and its size. |
| list | =storage.v1.objects.list= | Page a bucket, filtered by key prefix. |

Two of those verbs, =exists= and a prefix-filtered =list=, are outside the
canonical eight, and every operation model in the tree is outside them in some
way: the subjects are ad-hoc, three-segment in one case, hyphenated in another,
and two declare subjects under a component that does not own them. That is the
precedent, not a licence. The decision the plan records is which way to lean:

- *Conformant:* no =exists= verb. The protocol has none and no =count= either,
  because existence is a read and a count is a property of a list, so =get=
  returns =missing= and the caller learns the size from a successful read.
- *Precedent:* keep =exists= as an operation, as the surface the target state
  names, and accept that storage is a domain-operation model rather than a
  conformant entity protocol — which is what every existing operation model is.

The plan's recommendation is the first, with =exists= kept only as an HTTP =HEAD=
and a shell convenience over =get=. It costs nothing and keeps the option of
conformance open.

** Where the bytes go

NATS carries commands and, if it ever carries values, small ones. HTTP carries the
bodies, because the request and response body already stream through a file body
and a multi-object must never sit in memory. No message in the tree carries a raw
byte payload today — an image travels base64-encoded in a text column — so
whether the NATS surface moves bytes at all is a decision below, not an
assumption.

** The HTTP projection

The routes already exist and keep their path shape; what changes is that they gain
the operations the surface declares and the authentication it lacks:

| Operation | Route |
|-----------+-------|
| put | =PUT /api/v1/storage/{bucket}/{key}= |
| get | =GET /api/v1/storage/{bucket}/{key}= |
| get (existence and length) | =HEAD /api/v1/storage/{bucket}/{key}= |
| delete | =DELETE /api/v1/storage/{bucket}/{key}= |
| list | =GET /api/v1/storage/{bucket}?prefix=&offset=&limit=&order= |

Today the server registers three of these by hand, advertises no =HEAD=, and
never authenticates (=projects/ores.http/core/src/routes/storage_routes.cpp:51-80=).
=HEAD= is already promised in the component's own header and implemented nowhere,
so the route set closes a promise as well as opening a surface.

** Authentication and authorisation, on both interfaces

The protocol's *Security* section is the rule: the caller is authenticated before
the operation is reached, identity and tenancy travel in the envelope or the
session and never in a payload, and authorisation is per operation and per
resource, so a read is never authorised by a write code.

The mechanics, as the tree actually implements them:

- *HTTP.* =auth_required()= only sets a flag on the route
  (=projects/ores.http/api/src/net/router.cpp:82-85=); enforcement is middleware
  that parses the bearer token, validates the JWT and sets the request's
  authenticated user (=projects/ores.http/api/src/net/http_session.cpp:140-193=).
  There is *no* permission hook on a route: the only permission checks in the
  whole server are hand-written in =iam_routes.cpp:413-449=, which calls
  =authorization_service::has_permission(account_id, code)=. Storage must
  therefore take an =authorization_service=, add a =check_auth= helper of its own,
  and call it at the top of each handler with a =storage::objects:= code. Every
  other route in the server — =risk=, =variability=, =assets= — authenticates and
  then checks nothing.
- *NATS.* The handler is hand-written, so it must build the request context with
  =make_request_context= and call =has_permission= itself. Nothing generates that
  call for an operation model, and =ores.scheduler='s operation handlers check no
  permission at all, which is the precedent to avoid rather than follow.
- *Permission codes.* The shape is =component::resource:action= and the constants
  header is hand-maintained, because codegen cannot emit a second namespace of
  constants. Storage needs =storage::objects:read|write|delete= added there and
  seeded as SQL, like the 401 rows that already exist for other components.
  =check_handler_permissions.py= compares a component's handlers against the seed
  literals, but only for the four components in its registry, so =storage= must
  join that registry or the new handler is ungated.

Three facts make "authentication configured" a precondition rather than a given,
and the task has to meet it explicitly:

- The HTTP middleware block is skipped entirely when no authenticator is
  configured, and that is a warning rather than a refusal
  (=projects/ores.http/api/src/net/http_server.cpp:41-53=).
- The NATS request context comes back unauthenticated when no verifier is
  configured (=projects/ores.service/src/service/request_context.cpp:89-90=).
- =has_permission= returns =true= for an empty permission list, to keep tokens
  that predate RBAC working (=projects/ores.service/include/ores.service/messaging/handler_helpers.hpp:198-216=).

One more blocks HTTP parity: login mints a token without =tenant_id=
(=projects/ores.http/core/src/routes/iam_routes.cpp:532-540=) while NATS refuses a
token that has no tenant (=request_context.cpp:55-57=). A storage permission check
on HTTP is tenant-agnostic until login is fixed, so either that fix rides here or
the acceptance is narrowed on purpose.

** The raw surface

=storage put=, =get=, =delete=, =list= and =exists= over a bucket, a key and a
local path — generated, because the shell-command facet admits an operation model.
The component has no shell unit today: the clean pass recorded items S01 and S02
as "Not applicable. No entity and no shell unit.", so this is an addition rather
than a restoration. The consumer verbs (=ore upload=, =compute publish-package=)
then wrap the same operations instead of running a parallel surface.

** Exercising both

- HTTP: an integration test against the running server with a real token — put,
  get, list, delete — asserting that the bytes come back identical, that an
  unauthenticated call is refused, and that a caller without the code is refused.
- NATS: a request/reply test through the hand-written handler for the operations
  that carry no body, including both refusal paths.
- End to end: a shell session against the live services, which is also what the
  component's suite cannot do today: its tests use bucket names the real server
  refuses.

** Decisions taken

- *Buckets are the caller's concern.* Storage holds no bucket name, no bucket
  registry and no allow-list. The bucket is part of the object key; the server
  validates it as a path segment and authorises the operation rather than the
  name; and which buckets exist is declared by the components that use them. The
  hardcoded pair goes, and with it the =report-data= 404 — the server stops
  having an opinion about a name it was never told.
- *Existence is a read.* No =exists= verb: =get= answers =missing=, HTTP answers
  =HEAD=, and the surface stays inside the canonical set.
- *Storage gets a service.* The component splits into api, core and service
  parts, so the operation set has a home and the consumers link a public API
  rather than an implementation.
- *The consumers move onto it.* =ores.compute.wrapper=, =ores.ore=,
  =ores.reporting= and the shell verbs are migrated, and the duplicates the
  migration leaves behind — the wrapper's own HTTP client and archiver, the
  hand-built keys — are deleted rather than kept beside the shared ones. That is
  the story's second task.

** Still open

- *Where the HTTP routes live once a service exists.* =ores.storage.service=
  could host both transports, or =ores.http= could keep hosting the byte routes
  and call the same core. The decision also fixes who owns the listener and its
  authentication configuration.
- *Tenancy on the wire.* Global buckets with namespaced keys, or a bucket per
  tenant, and whether the login =tenant_id= fix rides in this task.
- *Whether a small value travels over NATS at all,* given that no message
  carries raw bytes today.
- *Whether the batch forms ship first,* or the surface declares the single forms
  only and gains =put_many= and =delete_many= when a caller needs them.
- *How much clean-standard rollout rides along.* Adding the new parts to the
  catalogue and the permission registry brings the TypeScript twin and the drift
  gates with them.

* Notes

- The design above comes from reading the generator's metatypes and facets, the
  protocol specification, both authentication paths, and the component as it
  stands. The load-bearing facts are cited where they are stated.
- The security findings are not storage's own defects, and two of them are
  broader than this task: the allow-by-default transports and the empty-list

* Result

The component is a service, and both of its interfaces work against the running
fleet.

**What it delivers**

- =ores.storage= is a composite: =api= holds the modelled protocol and the path
  helpers a consumer links, =core= holds the streaming HTTP client, the
  archiver, the transfer helpers, the local store and the handler, and
  =service= is the process that binds the operation set.
- The surface is modelled once, as
  [[id:D469834F-DB7C-4486-B43F-CBD984744C36][ores.storage.objects]]: put, get,
  delete and list on =storage.v1.objects.>=. The generator produces the protocol
  header, the TypeScript twin and the shell commands from the model; the
  handler, service and registrar are hand-written, because no facet admits an
  operation model.
- Both interfaces authenticate and authorise per operation. The HTTP routes call
  =auth_required()= and then a =check_auth= of their own with
  =storage::objects:= codes; the handler builds a request context and checks the
  same codes. The codes are seeded, and storage is in the handler-permission
  registry, so five components and 174 codes are verified.
- The bytes sit behind one =local_store= that both interfaces call, so the
  routes and the handler cannot drift in how they treat a key, a bucket or an
  absent object.
- The bucket allow-list is gone rather than replaced. The server validates the
  bucket as a single path segment and creates it on first write.
- The shell has a raw surface generated from the model, and
  =ores.compute.wrapper= links the component: its own HTTP client and archiver
  are deleted, and with them the download path that opened its destination
  before it read the status.

**Evidence**

- Over the bus, through the generated shell verbs: put answered its size, get
  returned the exact bytes, get of an absent key answered =found=false=, list
  reported the object and its length, delete answered =removed=true=, and the
  list was empty afterwards.
- Over HTTP, with a token from =/api/v1/auth/login=: an unauthenticated GET
  answered 401, PUT answered the server's sha256, HEAD answered the length with
  no body, GET returned the exact bytes, LIST reported the page, and DELETE
  answered =removed=true= and =removed=false= for a key that was not there.
- Crossed: an object written over HTTP was read over the bus, and an object
  written over the bus was read over HTTP, byte for byte.
- Suites: the api part 4 cases and 5 assertions, the core part 17 cases and 60
  assertions, the shell unit 13 cases and 25 assertions. Every gate is green:
  component drift, the CMake source lists, model drift, protocol twin coverage,
  handler permissions, populate references, the shell recipe inventory and the
  documentation checks.

**What it does not deliver, and why**

- The raw shell verbs carry the value inline, and the generated menu is named
  =objects= after the entity. The target state asks for a =storage= menu whose
  verbs take a local path. The operation shell-command archetype derives the
  menu from the entity and renders a string field inline, so both are template
  changes rather than model changes. The file-shaped form is the HTTP interface
  today, which has no shell verb.
- The three services whose =http-base-url= disagrees with the port the server
  listens on, and the =report-data= bucket name duplicated in two anonymous
  namespaces, are each their own capture. Neither is made worse here.

**Defects found in shared tooling, left where they live**

- The service parser template passes the literal =SERVICE= as the environment
  prefix, so a new service reads the wrong database variables and refuses to
  start.
- The service application template leaves the context factory's service account
  empty, which the factory rejects.
- The part CMake templates emit a part's include directory as
  =projects/${name}/include=, which is the flat path, and the core profile omits
  LibArchive, Boost and the test link dependencies.
- Adding a part needs the composite root regenerated, and an operation model
  needs =:ores.cpp.shell-command.enabled: true= before shell commands appear;
  neither is discoverable from the model alone.
