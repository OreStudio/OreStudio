* Goal

=gather_market_data= exports every series the tenant holds, at whatever the
database contains at the moment it runs. Nothing can say which market data a
set of trades actually needs, so nothing can narrow the export, and nothing
ties the data to the run's date.

Resolve it, for one trade set: from its trades to the market data requirements
they imply, expressed as =oresmd=, and from those requirements to the series,
observations and fixings that answer them. The as-of is the set's.

* Acceptance

- The resolution answers, for one trade set, which oresmd data a run requires.
- A requirement that no series answers is reported as a gap, not skipped.
- The resolution reads at the set's as-of date, so two runs that share a set's
  membership but not its date resolve against different rows.
- Where the resolution lives is decided and recorded, with the reason.

* Plan

*The crux is where the requirement grammar lives.* A trade names its
instruments and those instruments name indices, currencies and tenors; the
definition's curve configurations name the quotes a curve needs. Both halves
already exist as rows. But an =oresmd= requirement is spelled by C++ codecs —
=oresmd_uri_codec= and =ore_key_codec= — so "all in the database" means either
restating that grammar in SQL or moving it into SQL and having C++ read it.
That is the decision this task exists to take, and the two honest shapes are:

- a SQL function that resolves a trade set to series and returns the rows, with
  the oresmd spelling left to the caller that already knows the grammar; or
- the grammar expressed once in SQL and consumed from both sides.

A split — SQL for set to trades to instrument attributes, C++ for the
requirement spelling — is the third shape and probably the first one built,
because it needs no grammar to move and still removes the per-trade round trip.
It should be recorded as a starting point rather than a resting place if the
grammar then has two homes.

*What the requirements are derived from* is the other half. The candidates are
the trades' instruments and the curve configurations the run binds; both are
needed, because a portfolio's instruments need curves and the curves need
quotes. The investigation should state which entity answers an oresmd
requirement today, because if none does, that entity is part of this task.

* Decisions

- *The resolution lives in SQL, in two functions, one for each owner.*
  =ores_trading_market_references_fn= reads a set of trades and returns
  each oresmd address its instrument rows hold, with the column that holds
  it. =ores_marketdata_requirement_coverage_fn= takes a party and a list of
  addresses and returns, for each, the party's series with that address and
  its latest point at the date. The grammar does not move: an address is
  the identity of the series that answers it, so matching is equality on
  the stored address and no codec is restated in SQL. Trading owns the
  first half and marketdata the second, so each service calls its own.
- *The trades are read at a system time and the market at a business date.*
  A trade's rows are read as they stood at the as-of, so an amended trade
  resolves as it was. A series is read as it stands now and its points
  are filtered by fixing date or observation time, because a series
  written today may hold points about an earlier day. A null as-of reads
  the current trade rows.
- *The column list is one array in the trading function.* No declaration in
  the schema says which columns hold addresses, so the list came from
  scanning every trading text column for one (=evidence/oresmd_columns_query.txt=).
  The capture /Audit every field that holds an oresmd URI/ owns making the
  list complete by construction.
- *Only explicit references are requirements here.* What a trade implies
  without naming it, a discount curve for each currency and an FX rate to
  the reporting currency, belongs to the market configuration, which is
  [[id:EB839A7A-0EB6-4FD2-85E8-9847CA0D8634][Name every market object the generated trades use in the party's market configuration]].
- *Wiring the functions into a run is not this task.* The export narrows
  to the requirements in [[id:86994A25-E1C5-41AF-BE1D-E13F0667EFB1][Export the market data a trade set requires]].

* Notes

No address resolves, even under the system party, which holds 301,650
fixings. The trades name term SONIA (=name=SONIA&tenor=3M=), while the
public SONIA series is the overnight index (=name=SONIA=, no tenor). They
also name ceased LIBOR, equities, commodities, inflation indices and
credit curves, and no series exists for any of them. The three types that
resolve to nothing hold bare ORE names, so their builders do not yet write
addresses.

* Result

party's series answer them or report a gap. Two SQL functions do it, one
in trading and one in marketdata, and nine pgTAP cases cover them. On
ACCOUK, 445 of 460 trades resolve to 109 addresses, and none is answered
yet: that list is what the later tasks of the story fill.
