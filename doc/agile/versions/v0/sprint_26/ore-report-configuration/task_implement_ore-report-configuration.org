* Goal

A report definition's configuration is a set of strongly typed entities rather than a flat row of switches, and every entity in the ORE configuration vocabulary is identified, owned, and reachable from the definition.

* Acceptance

- Every entity in the seventeen ORE configuration documents is identified and mapped to an owning component.
- A report definition reaches its configuration through typed entities and foreign keys, never through a flat table of switches or an XML or JSON blob.
- A new kind of report adds a workflow and a parameter block, not a column on the report definition.

* Plan

Read the schemas, not the examples. The vocabulary is 605 schema types in
=external/ore/xsd=, and hand-counting them is how the earlier
[[id:A3B7C9E1-4F2D-8A6B-5E1C-9D3F7A0B2E4C][ORE Model Configuration]]
analysis went stale. So the first artefact is an extractor,
=build/scripts/xsd_to_uml.py=, that reads the schemas and emits a JSON inventory,
PlantUML class diagrams and the entity-to-owner mapping. Everything else is read
off its output.

Then, in order:

1. *Scope the vocabulary.* Which documents configure a run, and which are market
   data, trades or observed data. The brief excluded the last three; the one
   exclusion that needs stating is that =simulation.xml= carries 116 classes of
   market-data override inside an in-scope document.
2. *Classify every class*, per document, as an entity, a value type or an
   excluded container, and review it rather than trusting the rule: 265 entities
   and 178 value types came out of that pass.
3. *Establish ownership.* Which component holds each document today, including
   the components that already model much of it — =ores.refdata= for conventions,
   calendars, currencies and counterparties, =ores.analytics= for pricing
   configurations. This is what stops the proposal from putting into reporting
   what somebody else owns.
4. *State the target*: the run document and the analytics libraries owned by the
   definition, the reference configuration referenced, and a kind classification
   that selects the workflow instead of three workflow-shaped columns.
5. *Wire it into the story* as a knowledge cluster, because the analysis outlives
   the story, and as six follow-on tasks, one per family of work.

The plan changed once, early: the cluster was first built as seven flat notes in
a working directory, and the earlier =ORE Model Configuration= page was found
only afterwards. The two are now reconciled — this cluster supersedes that page's
inventory and adopts its =ores.analytics= component-home decision — rather than
sitting side by side.

and the pricing configuration domain model.
