* Acceptance

- The registry scope attaches each service account's registry picture.
- Installation bring-up runs it; =ores.shell= and =ores.web= can re-run
  the same subject.
- =iam_service_account_pictures_populate.sql= and its ignore entry are
  gone.

* Plan

The service accounts are created at build time and their pictures are the
system avatars. With the wanted picture riding the account, the registry
only has to say which image each service names, and the reconcile does the
rest.

1. =ores_iam_service_accounts_upsert_fn= gains =p_picture_code= and sets the
   column, so a service account can name its picture like any other account.
2. The accounts-populate archetype passes the registry's derived =image_code=
   (the service name with dots as underscores, e.g. =ores_iam_service=), so a
   service account names its picture the same way a staff account does. The
   generator already derives it in =codegen/core.py=; only the template and
   the upsert need it.
3. Regenerate the =ores.sql.service= outputs.
4. Reconcile at bring-up. The =attach_photos= step already runs on the first
   provision and already acts on the system tenant for the super
   administrators, so it is where the system tenant's accounts are
   reconciled too. It is idempotent, so a later run writes nothing.
5. Delete the build-time =iam_service_account_pictures_populate.sql=, its
   =ores.sql.service.account_pictures_populate= archetype and tangled
   mustache, and its =validation_ignore.txt= entry. The operation is what
   attaches the pictures now.
6. Recreate and run the suite; the fingerprint moves with the schema.

* Result

The service accounts now name their pictures, and the build-time picture script
is gone.

=ores_iam_service_accounts_upsert_fn= gained =p_picture_code=, and the
accounts-populate archetype passes the registry's derived =image_code=, so a
service account names its picture exactly as a staff account does. The
hand-written infrastructure script names the two accounts the registry does not
hold, =http_user= and =compute_wrapper_user=. A recreate writes 20 picture
codes, the same 20 the deleted script covered, and every one of those codes has
a matching system avatar.

=attach_photos= reconciles the system tenant's accounts through
=attach_service_account_pictures=, called where the super administrators'
pictures are attached because a service account carries only the permissions
its own domain needs. The reconcile skips an account that already has a picture,
so it is idempotent and never overwrites an administrator.

=iam_service_account_pictures_populate.sql=, its
=ores.sql.service.account_pictures_populate= archetype and tangled mustache, its
facet row and its =validation_ignore.txt= entry are deleted.

The suite passes 94 of 94 after a full recreate.

* Not verified

The pictures could not be watched appear end to end. The ACME provisioning run
aborts before =attach_photos= at =fpml.supervisory_body=: the publish asks for
coding scheme =FPML_SUPERVISORY_BODY=, which does not exist for the target
tenant, because =fpml.coding_schemes= is deliberately not a bundle member. That
failure is outside this task; none of its files are touched here. Until it is
fixed the reconcile is proven by the seed, the avatar join and the suite, not by
a live bring-up.
