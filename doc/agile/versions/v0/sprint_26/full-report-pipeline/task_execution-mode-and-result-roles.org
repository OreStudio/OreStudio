* Goal

Give the report definition a run configuration, carry it into the workflow start message, and make the workflow build the phase list that configuration names. At the same time replace the positional results[N] access with a lookup by phase role, because a second chain shifts every index after the phase it adds.

* Acceptance

- A definition's run configuration selects the phases that run, and a run is reproducible from the database alone.
- No step consumer reads an earlier result by index; a missing result fails loudly instead of yielding an empty field.
- A definition whose configuration executes every phase still runs the existing chain unchanged.

* Plan

Four parts, in the order each depends on the one before it.

1. *Results addressed by role.* A step result becomes a named pair rather than a
   bare JSON string: =workflow_step_result= carries the step's name and its
   response, =workflow_step_results= is the list of them, and =find_step_result=
   answers the payload the named step produced. The engine builds that list from
   every forwarded step, an empty answer included, because the list it built
   before skipped empty answers and so its positions were not step indices. A
   builder that cannot find or cannot read what it consumes throws; the engine
   catches that at dispatch and starts compensation, so a missing result fails
   the run instead of publishing a command with an empty field.
2. *The run configuration.* The definition table gains =pre_processing=,
   =prepared_input_key= and =post_processing=, so the choice of phase is
   definition state and a run is reproducible from the database alone. The
   trigger validates the codes, refuses a substituting definition that names no
   archive, and copies the configuration into =report_execution_request=, the
   payload the engine stores and hands to =build_steps=.
3. *The chains.* One registered definition builds either chain from that
   payload. =execute= and =execute= are the seven steps the definition ran
   before; =substitute= replaces the four pre-processing steps with one that
   resolves the named archive; =ignore= replaces result collection with one that
   records the batch and leaves it unread. Submission takes the name of whichever
   step filled the input role, so no consumer is told which producer ran.
4. *The substitutes.* Both are reporting operations, and both answer in the
   result type of the phase they replace. That shared answer is what makes them
   indistinguishable to the step after them, and it is why the substitute
   requests name an existing result struct rather than a type of their own.

Deliberately not done here, and owned elsewhere in the story: the instance does
not record which phases were substituted (the substituted-pipeline task adds
it), retrieval is not yet separated from result collection, and resolving the
prepared archive does not read it, so nothing checks that it is a valid engine
input or digests it.

* Notes

** Decisions

- The run configuration is definition state: one entry per substitutable phase,
  with the prepared archive's location beside it rather than in the environment.
  A substituted run is therefore recognisable from the definition row before it
  runs, and an operator asking why a run produced no results reads the answer
  from the database.
- The chain is a pure function of =report_execution_request=, because the engine
  rebuilds it on every dispatch and on recovery. The configuration therefore
  travels in the start message and not only in the definition.
- A consumer addresses a producer by role, and the role resolves to a step name
  when the chain is built: submission is handed the name of whichever step filled
  the input role. Neither the phase nor its substitute knows about the other, and
  no step knows its own position.
- The two substitutes are implemented here rather than left to the proof task. A
  configuration that can select a phase must select one that can run; leaving the
  subjects unhandled would have made a substituting definition hang. What the
  proof task adds is the live run: a real grid, a real archive, and the instance's
  record of what was substituted.
- The DQ publish function gives a definition it publishes the =execute= and
  =execute= configuration. A DQ artefact describes what to report, not how much
  of the pipeline to run, so the artefact schema is unchanged and publishing
  behaves as it did.

* Result

A report definition now says how much of the pipeline a run executes, and the
workflow builds the chain that configuration names.

The run configuration is three columns on =ores_reporting_report_definitions_tbl=
— =pre_processing=, =prepared_input_key= and =post_processing= — so it is
definition state and a run is reproducible from the database with no operator
present. The trigger validates the codes, refuses a substituting definition that
names no archive, and copies the configuration into the workflow start payload,
which the engine rebuilds the chain from on every dispatch and on recovery.

Step results are addressed by the name of the step that produced them. The engine
now carries an entry for every forwarded step rather than only the ones that
answered, because the old list's positions were not step indices and one silent
step shifted every later result. A builder that cannot find or read what it
consumes throws, and the engine turns that into compensation, so a missing result
fails the run instead of publishing a command with an empty field. Five
=build_command= definitions moved to the signature; the provisioning workflow,
the only other consumer that read a result by position, reads =save_account= by
name.

One registered definition builds both chains. =execute= and =execute= are the
seven steps the definition ran before; =substitute= replaces the four
pre-processing steps with =resolve_prepared_input=; =ignore= replaces result
collection with =ignore_compute_results=. Both substitutes are reporting
operations and both answer in the result type of the phase they replace, which is
what makes them indistinguishable to the step after them, and submission is given
the name of whichever step filled the input role, so neither phase knows about the
other.

Deferred on purpose, and owned by other tasks in the story: the instance does not
record which phases were substituted, retrieval is not yet separated from result
collection, and resolving a prepared archive does not read it, so nothing checks
that it is a valid engine input or digests it.

The branch also carries one unrelated fix. The clean-http change stopped
