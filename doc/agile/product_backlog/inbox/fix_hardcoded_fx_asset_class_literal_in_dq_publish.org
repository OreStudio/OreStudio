* What

=projects/ores.sql/create/marketdata/marketdata_publish_from_dq_create.sql:121=
hardcodes =v_asset_class := 'fx';= when publishing a market series from a
DQ dataset. =ores_refdata_validate_asset_class_fn= now rejects that value
-- it expects title-case codes (=Bond=, =Commodity=, =Credit=, =Equity=,
=ForeignExchange=, =Inflation=, =InterestRate=, =SecuritiesFinancing=).
The whole =bundle_publish_workflow= fails and rolls back on the first
FX-asset-class row, so nothing downstream in that workflow (e.g. ACME's
=synthetic_realistic_2026= step, which creates the
=market_data_generation_config=/=fx_spot_generation_config=/
=gmm_component= rows) ever runs. Fix: update the hardcoded literal (and
any sibling asset-class literals in that function) to the current valid
=ores_refdata_asset_class_code= casing.

* Why

Blocks the standard ACME Corporation provisioning script
(=how_do_i_provision_the_system_with_acme_corporation_holding_group.ores=)
from ever creating synthetic configs for any of its three parties
(UK/US/HK) -- discovered while working the "Synthetic data scope and
binding" story's ACME-consolidation task, which needs those rows to
exist. Looks like drift from a recent =ores.refdata= asset_class
casing/reference-data change that wasn't propagated to this one
hardcoded literal in =ores.marketdata=.
