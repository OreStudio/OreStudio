* Acceptance

- A named constructor for the Cliquet exists beside the equity option instrument domain type.
- The constructor states only Cliquet facts, so a caller cannot give it a frequency for a product that has none.
- The equity trade population writer builds the Cliquet through that constructor instead of filling the row field by field.
- A provisioning run books the equity family with the Cliquet present, and the suite that covers the writer is green.

* Plan

Put the constructor in a hand-written header beside the generated domain
type, so codegen leaves it alone and the type keeps one home. Take a terms
struct rather than ten loose arguments, with the frequency required and
defaulted to nothing, so a caller cannot reach the construction without
stating one.

The row the constructor returns is the row the table accepts, so it refuses
what the check constraints refuse: a non-positive notional, a negative
strike, an empty underlying or currency, and a vocabulary outside the closed
set each column holds. The SQL stays as the backstop.

The writer keeps writing the other two codes in this table as it does now,
minus the cliquet frequency it used to copy into every row. Only the Cliquet
takes the constructor, and the provisioning run proves the family still
books.

* Result

The Cliquet is constructed by name. =construct_equity_cliquet_option= takes
an =equity_cliquet_option_terms= whose frequency has no default, stamps
=trade_type_code= itself, and refuses what the table's checks refuse, so the
writer no longer assembles the row from whichever fields the bag carries.
The two other codes in the same table keep their existing assembly minus the
cliquet frequency, which used to be copied into every row.

Proved by a provisioning run on a fresh database: =generate_trades= completed,
and the equity family holds the same 17 rows across nine tables as before.
The Cliquet row states =Quarterly=; the plain option's frequency is null, so
the cross-column check is satisfied by construction rather than by the
planner's restraint.

One finding, recorded and not fixed here: the planner draws the cliquet's
=moneyness=, =local_cap= and =global_cap=, and none of them reaches a table,
because the routed table has no such columns and the
=equity_cliquet_option_instruments= model that does state them is routed by
nothing. The constructor cannot state terms its row does not carry. Routing
that table is the family's own work, not this task's.
