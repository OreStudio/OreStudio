* What

=ores.platform::time::datetime::to_iso8601_utc= formats a time point as
=YYYY-MM-DD HH:MM:SSZ=, with a space between the date and the time. Its
parser =from_iso8601_utc= reads the same shape, so the pair is
self-consistent.

The name claims ISO 8601, and ISO 8601 puts a =T= between the date and the
time. The separator surfaced while testing =ores.utility=: the assertion
that a =faker::datetime= value round-trips through this formatter had to be
written with a space, not the =T= the name implies.

=to_db_string= is this same string without the trailing =Z=, so the
database literal is also the space form. PostgreSQL accepts both.

* Why

Two things are wrong today, and either fix clears both.

- The function name and its documentation promise a standard it does not
  emit. A caller who parses the value with a conforming ISO 8601 parser
  gets a failure, and a caller who writes one gets a value the tree cannot
  read back.
- The =ores.platform= component overview says time is "stored and
  transmitted as UTC, in ISO 8601 with a =Z= suffix". That sentence is
  inherited from the merged platform clean-up and is not true of the
  separator.

The choice is between renaming the pair and dropping the ISO claim, or
switching the separator to =T= and keeping it. The second is the standard
way and is what a conforming reader expects. It changes the stored and
transmitted shape, so it needs a compatibility decision and a sweep of
the callers rather than a quiet edit.
