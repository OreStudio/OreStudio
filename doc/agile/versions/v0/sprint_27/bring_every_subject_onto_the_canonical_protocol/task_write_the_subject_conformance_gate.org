* Acceptance

- A script enumerates every subject from the models and reports each one that is not {component}.v1.{resource}.{verb} or {component}.v1.{resource}_events.{action}, with a verb from the closed set of eight.
- It reads the models rather than the generated headers, so the defect is named at its source.
- Accepted exceptions live in one file beside their reason, and the file is the only place an exception may be recorded.
- The script is wired into the same place the other codegen checks run, and it fails the build on a new violation.
- Codegen suite test holds the gate against a model with a bad subject and against one with a good subject.

* Result

=projects/ores.codegen/scripts/check_subject_conformance.py= fails on any
subject a model declares outside the grammar: four lower snake_case segments,
a literal =v1=, a verb from the closed set of eight (=list_by_<relation>= by
prefix), an event action from its own three, and the reserved =ops= namespace
exempt from the verb set. It reads the models, not the generated headers.

The generator already refuses a bad verb when it *derives* a subject, so a
violation enters the tree exactly one way: a model that declares it by hand
with a =:subject:= property. The check reads those 159 declarations.

Accepted violations lived in =subject_conformance_baseline.json= with their
reason, and the file was a ratchet: a violation not in it failed, and an entry
that no longer violated, or named a subject the tree no longer declares, also
failed. It is now *empty*: the other tasks emptied it, and a test asserts the
tree declares no violation at all.

32 cases hold the gate, registered in the local runner under the =modeling=
and =codegen= classes so it runs on every change that can add a subject.
