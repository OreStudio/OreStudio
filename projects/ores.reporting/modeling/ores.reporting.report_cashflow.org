#+title: ores.reporting.report_cashflow
#+description: Codegen entity model for the reporting =report_cashflow= table. One figure of one cashflow a run produced, with the keys that say which cashflow it belongs to.

#+brief: One figure of one cashflow a run produced, with the keys that name the cashflow.
#+entity_singular: report_cashflow
#+entity_plural: report_cashflows
#+entity_title: Report Cashflow
#+created: 2026-10-31
#+updated: 2026-10-31

A cashflow is not a metric. A metric states one figure about a subject; a
cashflow states a row per payment, keyed by the leg and the payment number, and
the stressed families state each of its figures three times, as a base, a
scenario and the difference between them.

The row here is therefore narrow, and keeps the cashflow's own keys: one figure,
named by its heading, with the part of the stressed comparison it states. A
family of cashflows adds no column to this table, and no figure of a cashflow is
flattened into =report_metric=, because the keys that make a cashflow a cashflow
have no place in a metric.

The row is written once, with the run, and never edited; a correction is a new
run.

The run that produced the cashflow.

:PROPERTIES:

** family
:PROPERTIES:
:type:         text
:cpp_type:     std::string
:natural_key:  true
:filterable:   true

The family the cashflow came from: flows, stresstest_flows, or the calibration's

** subject_type
:PROPERTIES:
:type:         text
:cpp_type:     std::string
:natural_key:  true

The kind of record the cashflow belongs to: a trade, or a market object.

** subject_id
:PROPERTIES:
:type:         text
:cpp_type:     std::string
:natural_key:  true
:filterable:   true
:END:

The engine's own identifier for that record. It is text because the engine names
its records with strings, not with uuids.

** scenario
:PROPERTIES:
:type:         text

:natural_key:  true
:END:

The scenario the cashflow was stressed under, empty when the file states none.

** cashflow_no
:PROPERTIES:
:type:         text

** leg_no
:PROPERTIES:

:END:

The observation date the cashflow belongs to: the run's priced date when the file

** pay_date
:PROPERTIES:

** flow_type

:type:         text

:PROPERTIES:

** measure
:PROPERTIES:

:cpp_type:     std::string

:END:

The engine's name for the figure, which is its heading: Amount, Coupon,

** part
:PROPERTIES:
:type:         text
:cpp_type:     std::string
:natural_key:  true
:filterable:   true
:END:

** qualifiers
:PROPERTIES:
:type:         text

:nullable:     true
:END:

Every other qualifier the file stated, as a JSON object of name and value, so a

** value
:PROPERTIES:
:type:         double precision

The figure, as the engine stated it and never formatted.

** source
:PROPERTIES:

The family and the row the reader read, for provenance.

** Bitemporal natural keys

A run's cashflows are its own. The insert trigger closes the current row of the
same key, and the key names the run, so posting one run never closes another
run's rows.
