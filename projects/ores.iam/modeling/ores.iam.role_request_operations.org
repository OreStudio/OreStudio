#+brief: Asking for roles through an approval request, and reading back what was asked.
#+filetags: :model:operation:iam:
#+created: 2026-10-05
#+updated: 2026-10-08

How a person asks for roles beyond the ones they hold. One call does it all:
IAM raises an =iam.role_grant= request in the inbox as the person, then records
which account would hold which roles, keyed by the request. If the record cannot
be written, IAM withdraws the request it raised, so a person never leaves a
request in the queue that names nothing.

A role the request asked for is read back with the request's own record of it:
when the ask wrote it and when IAM applied it. The roles are read through a
second operation, and not through the
generated read of =iam.role_grant_request_roles=. That read is gated by a
tenant-wide permission, and IAM isolates those rows by tenant alone. Granting
it to a member would let them read what every other member asked for. The read
here is entitled to the person who asked, so a member sees the roles on their
own request and no others.

The request is decided in the inbox like any other. When it is approved, IAM
grants each role the account does not already hold.

The handler is hand-written beside this model, because it calls the inbox and
compensates when the second half fails.

Two limits are accepted rather than locked against. Two asks for the same role
at the same moment can both pass the check and both wait; approving both is
harmless, because a role already held is not granted twice. If recording the
roles fails and withdrawing the request fails too, the request waits in the
queue naming no roles; the handler logs it, and an administrator refuses it
from the queue.

* Physical space

The shell commands are switched on. Asking acts as the signed-in person, so a
shell session signed in as a member asks for a role as they would.
