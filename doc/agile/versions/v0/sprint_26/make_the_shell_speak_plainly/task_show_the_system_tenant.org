* Acceptance

- The roster lists the system tenant, and the type filter offers System.
- The system tenant opens on its overview, parties and people tabs.
- Its parties and people are read as the session's own tenant, with no entry into a tenant.
- The home page counts stay those of the tenants somebody set up.

* Plan

- The roster, the tenant screen and the tenant tabs each refused the system
  tenant on purpose, as the deployment's own bookkeeping. The user wants to see
  it, so lift all three refusals.
- The system tenant is the system administrator's own, so entering it would
  mean entering the tenant the session already acts in. Read it as the session
  instead: when the tenant named is the session's tenant, the read runs on the
  session's own client.
- Keep the home page counts as they are: they count the tenants somebody set
  up.

* Result

The system tenant is on the roster and opens like any other tenant.

- *Roster.* The roster lists the system tenant, and the type filter offers
  *System*. Test tenants stay hidden unless asked for.
- *Tenant screen.* =/api/tenants/system= answers the tenant, and the screen
  shows its overview, parties and people tabs. It has no *View only* label,
  because the system administrators are its own.
- *Read as the session.* A tab read on the session's own tenant runs on the
  session's client and enters nothing. Every other tenant is still entered for
  the read.
- *Home.* The counts and the short tenant list still leave the system tenant
  out.

Acceptance is met: BFF 136, web 232 and protocol 70 tests pass, including a
