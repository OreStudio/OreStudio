* Goal

Write the architecture as knowledge notes before the code: how ORE Studio relies on an external identity provider, from the door a person chooses, through the provider's own consent, the validated ID token, the link to their ORE account and the registration the deployment's policy grants, to the session that names its method; and how the same layer acts as an authorization server for a client of ORE's API. Each note holds one idea, follows the zettelkasten house style, draws as UML what it describes as a structure or a process, and links into Identity and Access and Delegated Access for LLM Agents rather than repeating them.

* Acceptance

- A structure note lists the atomic notes, each one idea, and the knowledge index links it.
- The notes cover ORE as a relying party, the identity link and why it is not an email address, the registration a first sign-in goes through, the session that names its method, and ORE as an authorization server for clients.
- Each note that describes a lifecycle, an interaction or a structure carries a PlantUML diagram rendered to PNG, with a caption.
- The notes name the alternatives they reject and why, and cite the standards rather than restating them.

* Plan

Five notes and one structure note, ordered by where a person's identity is
decided: what ORE trusts, what it writes down, what it creates the first time,
what it records when the session opens, and what it hands to a client that asks
to act for somebody. The structure note states that order and is linked from the
knowledge index and from the Identity and Access structure note, so the cluster
is reachable from both.

The pages state the architecture the story decided on 2026-11-25 and carry its
reasoning, not a status report: the tasks that build the flow are still in the
backlog, and a reader who wants the state reads the story. Every page that
describes an interaction or a structure carries a diagram, and each cites the
standard it applies rather than paraphrasing it.

Written after the decision task and the two entity models, so the vocabulary is
theirs: the provider row's fields, the link's issuer and subject, the registration
policy, the session, the authentication event, and the grant an agent key creates.

  issuer and subject, a first sign-in registering through the policy, a session
  that names its method, and ORE as an authorization server for its clients.

  Access structure note, so the cluster is reachable from the section it belongs

  instead of restating it.
