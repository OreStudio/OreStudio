* Acceptance

- The BFF has a session-guarded route for each of the identity, snapshot, slice and evolution reads.
- Each route sends the request to the server's subject, which checks its own permission, and returns a refusal as a reason.
- Each route has a test, including a refused request.

* Plan

One module, =curves.ts=, registers four POST routes under =/api/curves/=: series,
snapshot, slice and evolution. Each checks the structure of the request with a strict
schema, forwards it to the server's subject, and returns the reply without its success
and message. The server checks the permission and the shape. A refused read becomes a
422 with the server's words. The module follows the shape of =synthetic.ts=. A test file
drives each route through a canned client.

* Result

The BFF now routes the four curve reads. A signed-in session can POST to
=/api/curves/series=, =/snapshot=, =/slice= and =/evolution= with a typed identity and
read what the server answers. The module is =curves.ts=, registered in =server.ts=.

Each route checks the structure of the request and nothing more. The schemas are strict,
so a field the route does not know is refused, and an instant must be a wire timestamp.
An evolution states its instants or both ends of its range, and a stated set is capped at
500. The server keeps the permission and the shape rules. A refused read comes back as a
422 with the server's words, so the screen can show the reason.

Eleven tests drive the routes through a canned client: each read, the provenance flag,
both evolution forms, three refused requests that never reach the server, a server
refusal and a missing session. The whole BFF suite passes, and so do the web,
route-auth, open-reads, reachability and handler-permissions checks.

Left for the screen task: a page that calls these routes. The routes do not draw anything.
