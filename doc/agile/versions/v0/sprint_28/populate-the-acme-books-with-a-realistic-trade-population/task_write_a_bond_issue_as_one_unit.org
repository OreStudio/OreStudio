* Acceptance

- One operation writes an issue with its leg, amounts, rate and schedule, or none of them.
- The issue is create-only. A second write of the same issue answers a conflict and leaves the first whole.
- A refused child write leaves no issue row.
- The synthetic writer calls the operation. issue_complete and ensure_issue are deleted.
- A database-backed test proves the rollback.

* Notes

Rule, set by the owner on 2026-10-21: booking has nothing specific to
synthetic. The synthetic component generates trades. It builds the same
requests a regular booking sends and sends them through the same
operations. The UX uses the same operations to book.

What makes this the only booking interface:

- Synthetic uses the operations (this task and the next).
- The ORE import moves onto them, in a separate story. It then only parses
  the ORE document into the same requests, as synthetic only generates
  them. Until then it keeps its N calls and its =close_bookings=
  compensation.
- The entity puts stop creating the parts of a new trade and stay only for
  editing an existing trade. Not sized yet. A check should enforce it.

Today no UX code calls =book_trade=. Only synthetic and the ORE import do.
