* Goal

=ores.orgmode.service= states one write: a page by its org id, the org text it
now holds, the version the caller read, and the reason for the change. A stale
version is refused, and the page keeps the versions before it, as every record in
this product does.

The write exists because the org docs move into PostgreSQL and one of them is
written by a person in a browser: a QA run records its step outcomes into the
scenario page. Without a write the runner has nowhere to record them, and the
knowledge service would be read-only.

It is a page write and not a scenario write. The service holds pages, and a
scenario's shape is one reader's reading of a page, so the write states the text
it was given and nothing about steps.

* Acceptance

- A page write states the org id, the org text, the version read and the reason, and is refused when the version is stale or the reason is missing.
- A page that is written is re-indexed without a reload, so a read after the write answers the new text and the search answers its new sections.
- The page keeps its versions, and one of them can be read beside the page as it stands.
- The pages table is written only through this operation: no client writes it directly.

* Plan

The write follows the shape every other record write in this product has: a
=put_…_request= carrying a change (the row's write members, the precondition and
the change intent), a result carrying the outcome, and a history the same
mechanism records. The org id is the key, the text is the column, and the
version in the precondition is what makes two testers' saves a conflict rather
than a merge.

The service re-runs the page's indexing after the write, so the search and the
section list follow the text without a reload.

The route is =ores.http='s, forwarding the operation, and it is =PUT
/api/qa/scenarios/:id/run= that the QA screen calls: the gateway parses the page,
writes the outcomes into it with =ores.orgmode=, and puts the page back through
this operation.
