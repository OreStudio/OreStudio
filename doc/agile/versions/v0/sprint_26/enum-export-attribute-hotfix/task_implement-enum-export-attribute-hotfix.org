* Notes

- The exact diagnostic is quoted from the CI log of a Windows clang-cl job:
  =error: '__dllimport__' attribute only applies to functions, variables,
  classes, and Objective-C interfaces [-Werror,-Wignored-attributes]=. It
  cannot be reproduced on Linux, because =__dllimport__= is the Microsoft
  spelling of the attribute and clang on a Linux target does not know it --
  the local probe reports =-Wunknown-attributes= instead. That is itself the
  point: the macros expand per platform, and the platform that rejects the
  attribute is the one no pull request builds.
- The attribute is harmless where the compiler accepts it, which is why this
  survived review. cppreference is plain that =dllimport= applies to
  functions, data and classes, and neither MSVC nor clang-cl documents it on
  an enum; clang-cl is simply the only toolchain in the matrix that says so
  and the estate builds with =-Werror=.
- An enum needs no import or export attribute. =failure_policy= travels
  across the boundary as a =std::uint8_t=, and every other enum in the
  estate is declared without a macro.
- The check reads =projects/= only, which is where every C++ source and
  every visibility macro in the estate lives: the =export.hpp= of each
  component defines its macro and the headers use it.
- The check blanks comments before it scans, so a comment that describes
  the rule does not violate it. The comment left on the declaration is
  exactly such a comment.
- The first full test run failed five suites on
  =column "oresmd_uri" does not exist=, which is the local database rather
  than the tree: it was created before that column reached the schema. A
  =compass db recreate -y -k= took the suite to 89 of 89, including
  =ores.refdata.core.tests=, which was the one failure recorded on main
  earlier in the sprint. No code changed between the two runs.
