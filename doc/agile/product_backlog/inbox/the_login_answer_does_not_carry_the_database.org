* What

The versions screen states the database under the deployment: the fingerprint
of the schema it was built from, the build environment, the commit and the
created time. All four live in =ores_database_info_tbl=, written when the
database is created or recreated. One reader touches the row today: the
service context factory, which compares the stored fingerprint with the one
compiled into the code and refuses to start on a mismatch. No subject serves
the row to a person.

The accepted design gives it the second reader it needs. The =login_response=
already states the deployment's build in full through its =version= field,
and it must state the database row beside it: the fingerprint, the
environment, the commit and the created time. The iam service reads
=ores_database_info_tbl= at login and fills the fields. See the prototype
section of [[id:C3D59907-9D6A-448C-9A61-9E750755BBFB][Check the versions and the database]].

* Why

The versions screen and the footer answer the same question — what am I
talking to — and the database is its missing third. The server build rides
the login answer already, so the session keeps it with no second read; the
database row travels the same way, at the cost of one query against a
one-row table. It needs no new subject, no new permission and no new BFF
route, and it settles the audience question the journey raised: the row
reaches exactly the people the server build already reaches.
