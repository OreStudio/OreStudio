* Goal

Decide what a person's token carries and how it stays true, before any code
changes, so the next three tasks build one design: which tokens carry
permissions, where they come from, how a role change reaches them, and what the
check does with an empty list.

* Result

The design is in the story's Decisions. What exists today:

| Issue point | File | Permissions today |
|-------------+------+-------------------|
| Login, one party | =auth_handler.hpp= | none |
| Login, party choice pending | =auth_handler.hpp= | none; the token can only choose a party |
| Party selection | =account_operations_handler.hpp= | none |
| Party switch | =account_operations_handler.hpp= | none |
| Refresh | =auth_handler.hpp= | copied from the old token |
| Service login | =auth_handler.hpp= | read from the database |
| Internal impersonation | =internal_impersonation_service.cpp= | read from the database |
| Tenant session | =tenant_session_service.cpp= | the administrator's read codes |

So every person's token carries an empty list, the token check passes it, and
about 1,190 handler checks pass for every signed-in person. Production
services always build a verifier, so the empty list that means "no token, trust
the caller" arises only in tests and service-internal contexts.
