   the trade type.
3. *The fallout.* The repositories key on the trade id today; the composite key

   anchor's party will start to fail — that is the check working.

   type disagrees with the anchor's, and expects the store to refuse it.
5. *Before branching.* The trade anchor is shared with every other family and
   with in-flight work; check the fleet for what else is touching it before
   starting.

* Result

The rates header is pinned to the trade anchor on the party and the trade
type. The fleet check found one overlap: merry newton adds two columns to the
trades table, which does not touch the pin.

The task's premise was out of date, so the delivery differs from the plan:

- The anchor is a versioned table now (=Make every trading entity a regular,
  versioned table=), and its unique keys were removed because nothing
  referenced them (=Stop the trade's children copying its party=). A database
  composite foreign key cannot name a versioned table, and a unique index
  would serve nothing. No index was added. The pin is a codegen =Pinned keys=
  row on the header, which generates an insert-trigger check against the
  anchor's current row over =(id, party_id, trade_type)=.
- The fact and child tables carry neither =party_id= nor =trade_type_code=
  (design decision D3), so the header is the only row of the family that can
  disagree with the anchor. They are not pinned.
- The trigger stamps =party_id= from the session and row-level security hides
  other parties' anchors, so the observable refusal is the trade type. The
  party column is held to the anchor as well.
- Because the check runs at insert, a later amendment of the anchor does not
  re-check the header. The trade model's owner decides whether an amendment
  re-pins its children.

Tests: the cascade test now books its anchor as a ForwardRateAgreement, and a
new case refuses a header whose trade type differs from the anchor's.
