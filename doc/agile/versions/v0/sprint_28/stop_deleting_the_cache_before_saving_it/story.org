#+title: Story: Stop deleting the compiler cache before saving it
#+description: Both cache-saving workflows delete the sccache entry and then save it, because actions/cache/save cannot overwrite an existing key. When the save then fails, the entry is gone: the cache service does fail, with 400 responses and outages in the logs, and the two Linux clang entries have now disappeared. Save under a run-unique key with a restore-keys prefix instead, so a failed save can never destroy the cache, and drop the delete.

* Acceptance

- Neither workflow deletes a cache entry.
- Both restore from any recent entry and save under a run-unique key.
- A run whose local cache is too small to help does not become the newest entry.

* Decisions

- Saves use a run-unique key and restores match the key prefix. That removes
  the delete step entirely, so no save failure can destroy a stored entry.
- Old entries are left to the seven-day rule and LRU eviction rather than
  being deleted in place.
- The 1000 MB floor applies in both workflows, because prefix matching means
  the newest entry wins and a run that failed early must not become it.

* Out of scope

- Caching the macOS and Windows compiler caches. They still do not fit: the
  Linux variants alone approach the 10 GB repository cap.
