* Goal

Answer one question with a throwaway prototype: how does a tenant
administrator read who is signed in, what they are doing, and who is failing
to get in?

[[id:22AC8DD8-A440-4330-9992-47A5E9985473][Audit sign-ins]] carries one
screen and one action. It is an event log, not a versioned entity, so it
carries no versions, no diff and no revert, and *Refresh* is the only action.
The prototype decides how the filters, the active sessions, the session
activity and the failed attempts share one screen, and how the screen states
the data it cannot read.

* Notes

The journey's gaps, from the * What is missing section of
[[id:22AC8DD8-A440-4330-9992-47A5E9985473][Audit sign-ins]]. The screen states
each one, and the prototype decides how.

1. *No subject for the auth events.* =ores_iam_auth_events_tbl= holds one row
   per login, failure, logout and token refresh, with continuous aggregates and
   no subject.
2. *No subject for the session statistics.* The three continuous aggregates
   exist with no subject.
3. *No operation to end another account's session.* The repository method
   =session_repository::end_session= writes the end time, and only the logout
   path calls it for the caller's own session.
4. *The activity and the audit data have no read path in the browser.* The
   session samples have neither a working subject nor a BFF route. Until the
   subjects exist, the session-activity panel must state that the data is not
   available.

Three of the reads are =partial=: =iam.v1.sessions.list= takes no account
filter, and =iam.v1.sessions.active= and =iam.v1.sessions.samples= exist and
reply with success and no rows. The BFF answers the active sessions from the
session repository, so that panel works in the browser today while the NATS
path does not.

* Result

Built 2026-09-30. Snapshot: branch =prototype/audit-sign-ins=. The product owner
has not chosen a variant yet, so nothing here is carried into the build.

Route =/prototype/audit?variant=a|b|c=, reached the same way as the other two:
=npm run dev:web --workspace @ores.web= and
=http://localhost:5173/prototype/audit?variant=a=. No server is needed.

*Three variants on one screen.*

- *A · One log, sections.* One filter bar, then the active sessions, the
  session activity, the failures and the gap list as sections of one page.
- *B · Tabs over one filter bar.* The same four readings take turns in the
  body, so the page never grows past one screen.
- *C · Session-first timeline.* One row per session, expanded to its activity,
  with the failures and the gaps in a rail beside it.

*Recommendation: C.* The question this screen answers is asked about a session
("who is this, and what are they doing"), so the session is the unit and its
activity belongs under it rather than in a separate reading. The failures rail
stays visible, which is what explains the support call. A is the safe default
if the readings grow past three; B hides the failures while an administrator
reads the sessions, which is exactly when a locked account matters.

*Decisions the prototype settles.*

- *Refresh is the only action,* and no version, diff or revert control appears
  anywhere. The journey document fixes this, and the prototypes keep it.
- *The account filter is drawn, and disabled.* =iam.v1.sessions.list= takes no
  account filter, so the screen says the server cannot apply one rather than
  offering a control that silently does nothing.
- *The activity panel states that the data is not available.* Nothing serves
  =iam.v1.sessions.samples= on either transport, so no empty chart and no
  fabricated sample rows are drawn; the session row's own totals are shown with
  the reason beside them.
- *No events panel is drawn.* The authentication events have no subject at all,
  so the screen lists them as a gap instead of drawing an empty log. The
  journey's first two steps therefore cannot be shown until the subject exists.
- *The failure count and the lock state travel together.* A locked account is
  the case the screen exists for, so the state is a tag beside the count.

*The whole journey is unreachable from the browser today.* No route serves
=iam.v1.sessions.list=, =iam.v1.sessions.active=, =iam.v1.sessions.samples= or
=iam.v1.login_info.list=, and there is no subject or route for the auth events
or the session statistics. The journey document's claim that
=/api/v1/sessions/active= "works in the browser today" is stale.
