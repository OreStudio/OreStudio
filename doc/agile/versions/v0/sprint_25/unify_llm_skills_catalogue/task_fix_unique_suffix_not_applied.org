* Notes

Filed on a premise that does not hold, and abandoned once checked.

The premise was that =trade.external_id= carries
=requires_unique_suffix=, turning the counter on while receiving no
suffix. It does not. =external_id= is nullable and declares no
=:unique:=, so =requires_unique_suffix= is false for it.
=requires_unique_suffix= is set only for a non-optional
=std::string= column marked =:unique:= that has not opted out.

The corpus contains exactly one such column, =tenant.hostname=, and
the generator handles it correctly:

: r.hostname = std::string(faker::word::noun()) + ".example.com" + "-" + std::to_string(idx);

The template applies the suffix on both the =generator_expr= and the
plain-string paths. There is no defect in the mechanism to fix.

What the unused counter actually was is drift. =trade= has a uuid
primary key, no natural keys and no =:unique:= column, so
=needs_counter= is false and the current generator emits no counter.
The declaration in the committed file is a leftover. Regenerating
=trade= removes it, and also rewrites the whole function, because the
committed code uses field groups and namespace =generator= while the
generator now emits flat fields and namespace =generators=. That is
the codegen drift already filed, and the evidence is recorded there.

The lesson is about the filing rather than the code. The task was
written from the shape of the symptom while the build was broken and
the fix was the urgent thing, and the model was never opened to
confirm the column carried the property the premise depended on. One
grep would have settled it before a task existed.

* Result

Abandoned. The defect does not exist.

=requires_unique_suffix= is applied correctly wherever it is set, and
it is set on one column in the corpus. The unused counter that
prompted the filing is stale generated code in =trade=, recorded as
further evidence on the codegen drift task, which is where regenerating
the component belongs.
