This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A signed-in person reads what the browser, the deployment and the database are: the client build, the server build, and the database fingerprint.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"What am I talking to?" The person reads three builds in one place: the
browser's own, the deployment's, and the database under it. The journey is
done when all three are stated and compared, or when the screen says which of
them it cannot read and why.

* Actor and trigger

Any signed-in person. This is the one journey in the group that is not the
system administrator's: a member reporting a fault, an administrator checking a
rollout, and a support engineer on a call all ask the same question, and the
answer is not sensitive. The answer is built into every screen already — the
footer states the client and the server — and this journey adds the screen
that states all three together.

The trigger is doubt about a build: a screen behaves like yesterday's, a
release note asks for the deployment's version, or a support request asks
which database the deployment stores into. The journey ends when the three
values are read, and the person can say whether the build they are testing is
the build they think they have.

This journey writes nothing.

* Steps

1. *Read the footer.* Every screen carries a footer with two lines: the build
   the browser is running and the build the deployment is running. Two
   versions that disagree mean the browser holds a stale bundle, and the
   refresh that fixes it is not a guess. The server's version is absent until
   the deployment answers, and the footer says so rather than inventing one.
2. *Open the versions screen.* When the question needs more than the two
   lines — the platform, the commit, the database — the person opens the
   versions screen. The system shows one screen with three panels: the client,
   the server and the database.
3. *Read the client panel.* The system states the build the browser runs. The
   bundle carries it from the moment it was built and never changes
   afterwards: the release, the short commit the bundle was cut from, and
   whether the checkout had uncommitted changes at that moment. A person can
   match those three against the release they meant to test.
4. *Read the server panel.* The system states the build the deployment runs,
   in full: the release, the platform triplet and the build information, in
   the same composition the login answer stated — the answer that opened the
   session names the build it was opened against. The panel adds the address
   the browser is talking to, so a person testing two deployments keeps them
   apart.
5. *Read the database panel.* The system states the fingerprint of the
   database the deployment stores into: the fingerprint of the schema it was
   built from, the build environment, the commit and its date, and when the
   database was created. The four values arrive with the login answer — the
   same answer that states the server build — so the panel reads them without
   a second request. Today the answer carries the build and not the database
   — see *What is missing* — so the panel says the database is unknown rather
   than showing an empty row as though it were a fact.
6. *Compare the three.* Together the values answer what no single one can: a
   browser older than the deployment (a stale bundle), a deployment whose
   build does not match the schema the database records — which every service
   checks at its own startup, so the deployment would not be running — or a
   database built from a checkout nobody claims. The client and the server
   strings do not share a shape, so the screen shows them side by side for a
   person to compare; it cannot compare them mechanically.
7. *Leave, or go on.* The versions raise the next question: which instances of
   each service run which build, which the services screen answers per
   instance, and what a stale build did, which the logs answer.

* Screens and wireframes

Two surfaces, one answer. The footer is built and rides on every screen; the
versions screen is the one this journey adds, with its three panels. The
screen is read-only: it creates nothing, changes nothing and destroys nothing.

* Prototype

Accepted by the user on 2026-10-04. The prototype is merged into =main= and
kept there as the record; the branch names the accepted state.

- Branch :: =prototype/operations-journeys= (accepted at =285519db99=)
- Route :: =/prototype/versions=
- Source :: =projects/ores.web/packages/web/src/prototype/= on =main=; the hub at =/prototype= lists every prototype route
- Design record :: [[id:BFE393CC-15F5-4A35-BFF6-A5CFB817F0A7][Task: Prototype the operations journeys]]

The prototype settled where the database row comes from. The panel needs no
read of its own: the login answer that already states the server build must
state the database row beside it, and the session keeps both. Until it does, a
real session states the database as unknown, and the prototype shows that
state beside the settled one. The panel's shape is settled too: fingerprint,
environment, commit and created, in that order, which is the question "which
checkout built this database".

* Entities composed

#+ATTR_HTML: :class hug-leading
| Entity | What it contributes | Model |
|--------+---------------------+-------|
| =login answer= | The build the answering service runs, in full, and the database row, stated when the session opens | [[id:72596DEE-01BE-40A5-B084-4C38DB212191][ores.iam.login_messages]] |
| =bootstrap answer= | The same build, stated before anyone can sign in | [[id:4B98E2D0-8FE3-4321-8CFD-90A4C13422EA][ores.iam.bootstrap_messages]] |
| =service_sample= | Each instance's own version, for the step that follows this journey | [[id:34CDC835-C72C-44F1-A0E2-B163014E0D74][ores.telemetry.service_samples]] |
| =ores_database_info_tbl= | The fingerprint, build environment, commit and date of the database | no model: the table is deliberately not a codegen entity |

The client's build is not a model at all: the bundler stamps it into the
browser code at build time, and it cannot change while the tab is open. That
is the point of stating it — a client that matches the server proves the
bundle is current, and a client that does not says the tab is stale. The
database table is the other extreme: it is declared by hand in
=projects/ores.sql/create/database/database_database_info_create.sql=, and it
owes nothing to the code generators, because it records the checkout that
built the database before any service runs.

The login answer's job grows by one row under the accepted design. It states
the deployment's build today, and it must state the database beside it —
fingerprint, environment, commit and created — read once per login from
=ores_database_info_tbl=. The row's only reader today is each service's
startup check; the login answer becomes its second, and no subject of its own
is needed — see *What is missing*.

* Operations and messages

#+ATTR_HTML: :class hug-leading
| Step | Operation | Subject | Status |
|------+-----------+---------+--------|
| Read the client version, on every screen | (no operation: the build stamps the bundle) | — | exists |
| Read the server version, before sign-in | The bootstrap answer states the build the service runs | =iam.v1.bootstrap.status= | exists |
| Read the server version, at sign-in | The login answer states the same build in full | =iam.v1.auth.login= | exists |
| Read the server version, on every screen | The session carries the build it was opened against | carried by the BFF route =GET /api/session= | exists |
| Read the database fingerprint | The login answer states the database row | =iam.v1.auth.login= | missing |
| Read the per-instance versions | List the latest sample of every running instance | =telemetry.v1.services.list= | exists |

The server version is composed by =ores.utility::version::full_version_string()=
as the release, the platform triplet and the build information, and the login
answer carries it in full. The BFF keeps it on the session record, so the
footer states it from the first read onwards without asking the service again.

The database row is written when the database is created or recreated, and
exactly one row exists. Each service reads it at its own startup and compares
the fingerprint with the one compiled into the code, refusing to start when
they differ — so a person reading the fingerprint tells which checkout built
the database, and the deployment's own startup check is the reason the values
agree until somebody recreates the database under a running service. The
accepted design gives the row a second reader: the login answer carries it to
the session.

The versions screen needs a hand-written BFF route like the other operations
screens on the [[id:6A63AAC7-4869-493A-97E7-55B919874784][journey runtime]]. No route serves it yet; the prototype adds
=GET /api/operations/versions=, which reads the session's version and states
the database from the login answer. While the answer carries no database row,
the screen states the database as unknown.

* What is missing

1. *The login answer does not carry the database row.* The row exists and its
   only reader is each service's startup check, which compares the fingerprint
   and refuses to start on a mismatch. The accepted design gives it a second
   reader: the login answer states the deployment's build already, and it must
   state the database row beside it
   ([[id:B7AE6C4F-5597-419D-A396-AD64D871C900][The login answer does not carry the database]]).
   No subject of its own is needed, and the screen states *unknown* until the
   answer carries the row.
2. *The database row's audience rides the login answer.* The fingerprint names
   the commit and build environment the database was made from — build
   forensics, not customer data. Riding the login answer settles the audience
   with the server build's: everyone who may open a session may read it. The
   decision to record is that the two travel together, so a future change to
   one audience changes both.
3. *The client and the server strings cannot be compared mechanically.* The
   client states the release and the commit; the server adds the platform and
   the build information in a different composition. One shared shape would
   let the screen mark a mismatch instead of leaving it to the eye.
4. *The services screen cannot compare builds either.* Each service reports
   its release string only, so the per-instance versions this journey points
   to cannot tell two builds of one release apart. The gap is recorded on
   [[id:ED949529-0A80-4661-BBAC-E5DB7A6E5828][See the running services]].
