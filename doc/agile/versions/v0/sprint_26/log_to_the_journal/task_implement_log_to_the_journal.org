* Goal

The fleet logs to the console and systemd captures it into the user journal, so one interface reaches every service and no file is written. compass stops reading a log file to decide whether a service is ready, because that file is the thing being removed, and it gains a verb that tails any unit including nats-server, with the last warnings and the last errors a filter away. The environment plugin shows that tail, and those warnings and errors, for one service at a time.

* Acceptance

- No service writes a log file, and every service's output reaches the user journal.
- File logging is opt-in in ores.logging, matching the option the header already documents, and a unit that passes no filename writes no file.
- compass decides a service is ready by reading the journal, and a running fleet still reports running rather than starting.
- compass services logs prints a tail from the journal for any unit, including nats-server, which no selector reaches today.
- The tail verb can return only the last warnings or only the last errors.
- The Environment view opens a log overview for one service showing its tail and its warnings and errors.

* Plan

Four edits, and the third is the one that keeps the change from breaking the
fleet.

- =logging_configuration.cpp= gives =--log-filename= an empty default, which is
  what =logging_options.hpp= already documents. File logging then happens only
  when a caller asks for it, and no caller changes.
- =systemd_generate.py='s =DEFAULT_ARGS_TEMPLATE= becomes =--log-enabled
  --log-level {log_level} --log-to-console= and stops passing =--log-directory=
  and =--log-replica-index=. The node unit renderer stops redirecting stdout
  and stderr to a file, so systemd captures both into the journal.
- compass moves its reads to the journal. For readiness this is mostly
  deletion: the twenty-three =Type=notify= units answer through =ActiveState=,
  so =classify_unit= stops scanning anything for them and only =ores.web= keeps
  a string check, moved to the journal. =_detail_of=, =_snapshot_logs= and
  =_service_ready= read the journal too. Leaving this out is the silent failure:
  those functions read the file this task deletes, so every active unit would
  report =starting= forever.
- =clear-logs= and the log path reported by =compass services status= follow,
  because there is no log directory to clear or report.

Verification is a fleet start, because nothing else exercises readiness. The
fleet must be stopped again afterwards to leave the environment as it was
found.

* Result

=logging_options.hpp= already documented an empty filename as disabling file
logging, but =--log-filename= carried a non-empty default and
=--log-directory= carried =log=, so the documented opt-out could not be
reached and an empty filename alone would have tripped the validator's
directory-without-a-filename rule. Both defaults are empty now.

The generator passes =--log-enabled --log-level <level> --log-to-console= and
no longer passes =--log-directory= or =--log-replica-index=, and the node unit
keeps no =StandardOutput= or =StandardError= so systemd's own default, the
journal, applies. Readiness stopped being a log question for twenty-three of
the twenty-four units, because they are =Type=notify= and systemd reports them
active only after the service called =sd_notify(READY=1)=. The start path polls
=ActiveState= rather than a growing file, which deleted the byte-offset waiter
and its snapshot.

Not yet proven: no service has run on this change. The rebuild is what drops
the file sink from the compiled binaries, and until it finishes a fleet start
would still write a file in a relative directory. The open question is whether
=ores.web=, the one unit whose readiness still reads a line, logs =Service
ready= to the journal.
