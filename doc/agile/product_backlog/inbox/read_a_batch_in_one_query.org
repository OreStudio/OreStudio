* Goal

A bulk request to a generated service reads the rows it needs in one query per batch, not one per row. Put-many checks every row's precondition against one read of the current rows and answers from one read of the rows it wrote; get-many and delete-many read their keys in one query. Measured on the derived FX volatility source, a 1,000-row put of market observations took 8.65 s on average, of which the insert was 0.34 s and the rest about 2,000 single-row reads.

* Acceptance

- The service template reads the current rows of a put-many, get-many and delete-many batch with one query each, and put-many answers from one read of the rows it wrote.
- A put-many still refuses the whole batch when one row fails its precondition, and writes nothing.
- The regenerated services build and pass their suites, and the codegen drift gate is clean.
- A 1,000-row put of market observations is measured before and after, with the command, on the same environment, and the derived source's first history on a recreated environment is measured again.

* Notes

** Where the reads are

In =projects/ores.codegen/library/templates/cpp_service.cpp.mustache=, every bulk path calls the per-row =<entity>_read_one= helper inside a loop:

- get-many reads each requested key;
- put-many reads each row in =prepare_change= before the write, then each written row again to answer;
- delete-many reads each key before it is removed.

The market observation repository already declares a =read_latest= over a list of ids, and the service uses it in =get_market_observations=. A count of repository headers with a multi-line =read_latest= overload finds 510 of 562, so most repositories likely have one; this needs checking per key shape. A model whose declared key is not the storage key needs a list read by that key, so the template has to choose the read by key shape.

** Evidence

The measurement is in the Notes of [[id:ACF60CC6-3DB4-44C4-9059-B8D58180E7AB][Run the derived source in the system tenant]]: the first history of the derived FX volatility source wrote 2,600 days (55,070 observations) in 595.678 s at debug level. Batches of 1,000 took 8.65 s on average (1.86 to 15.43 s); the insert statement took 0.34 s on average. The marketdata log showed one "Reading latest market observation by id" per row, before and after each write.
