* Notes

- =compass sql= describes the row set of every run that post-processed on this environment, so four runs each carry the same 24 rows. Only one of them was triggered from the report page.
- The entity's codegen drift is not clean. =check_component_drift.py --component reporting= reports twelve untracked files it would materialise: the eventing header, the generator header and source, the CRUD handler and registrar, the history field mapper, the service, and the service-side event registrar for =report_result_row=. The generated CRUD service cannot serve this entity, so those layers were left out of the branch; the generator still emits them. The codegen drift job did not catch it because =codegen-drift.yml= does not watch =projects/ores.reporting/modeling/=. This is follow-up work: either the model states the layers it does not generate, or the job watches the model.

* Result

Merged as #3929. A person starts a run from the report definition's own page, the page lists the new run, the run page names its state and the batch and jobs it reached, and the results screen draws from =ores_reporting_report_result_rows_tbl=. The request path no longer parses an archive: the BFF asks =reporting.v1.report_result_rows.list= for the run and the service reads the rows by run.

The review found no blocking defect. Two of its points are settled: the value the post-processor writes is the figure the screen draws, and point 5 is generation, not hand-editing. The other four stand, and the run should be read with them in mind: the read returns every row of the run with no bound, four filter members are ignored, no permission is checked, and the BFF keeps dead tar constants. They are recorded in =* Review= for follow-up work.

One defect was found after the merge and is recorded under Notes: the entity's generation is not fully committed, so =check_component_drift.py --component reporting= fails on twelve untracked files. The drift job did not see it because it does not watch =projects/ores.reporting/modeling/=.
