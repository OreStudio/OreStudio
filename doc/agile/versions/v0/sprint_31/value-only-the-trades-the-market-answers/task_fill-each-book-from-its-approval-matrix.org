* Acceptance

- A book with an approval matrix books only the types that matrix names.
- A book whose matrix names a type the generator cannot draw states that type and the reason in the provisioning report.
- The report states, per book, the trades booked and the types left out.

* Plan

Two of this task's three acceptance items arrived with
[[https://github.com/OreStudio/OreStudio/pull/5157][#5157]]: a book is filled from
its own matrix, and a type the matrix permits but the generator cannot draw is
refused with its reason. What is missing is the *report*: the run states its
outcomes per configuration and per trade type, so nothing says what one book
received and what it was denied.

1. *The plan states its outcomes per book.* =plan_for_scope= already computes
   each book's types and the reason each one plans nothing; the merge into the
   configuration's list throws that attribution away. =trade_population_plan=
   gains =book_outcomes=: one entry per book of the scope, each holding the
   book's own type outcomes. A book the config's types do not reach keeps its
   entry, with every stated type left out and the matrix as the reason, so the
   report names a book that books nothing rather than omitting it.
2. *The run joins the two.* =trade_population_run= gains =books=: one entry per
   book, with the trades planned, written and already present, and the book's
   type outcomes from the plan. The counts are the run's own (a slot names its
   book), so a report cannot claim a book received trades the run did not write.
3. *One line per book in the report.* The provisioning step records, for each
   book, the trades written and present, the types it booked with their counts,
   and the types it did not, each with its reason. The existing per-type line
   stays: it answers what the configuration did, and the per-book line answers
   where it went.
4. *One type, not two.* A type's =planned= count says whether the book booked it
   and its =reason= says why it did not, so the report reuses
   =trade_type_outcome= rather than inventing a booked type and a left-out type
   that say the same thing twice.

* Result

A run now states the population twice: once per type, which answers what the
configuration did, and once per book, which answers where it went. The per-book
line names the trades written, the trades already present and the trades planned,
then the types the book booked with their counts and the types it did not with the
reason each was denied — its approval matrix, the party's missing market data, or
the builder's own refusal.

The attribution is the plan's, not the run's guess. Each book's answer is built by
walking the configuration's types in the class's own order, so a type the matrix
denies and a type the market cannot answer are told apart rather than collapsed
into one short count, and a book that books nothing keeps its entry so the report
names it.

The two properties this task's acceptance asks for beyond the fill itself are
therefore true of the report and not only of the store: a book whose matrix names
a type the generator cannot draw states that type and its reason, and the report
states per book what was booked and what was left out.
