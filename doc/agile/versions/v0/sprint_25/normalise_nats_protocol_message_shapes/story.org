* Goal

Run a systematic pass over every =ores.*.api= messaging protocol header
and flag request/response structs that were hand-written rather than
generated via =ores.codegen='s =cpp_protocol= template (=projects/ores.codegen/library/templates/cpp_protocol.hpp.mustache= /
=ores.cpp.protocol.protocol_header.org=). The codegen norm for a plain
=list_*_response= is no =success=/=message= fields at all (e.g.
=ores.iam.api='s =list_roles_response=, =list_permissions_response=,
and =ores.compute.api='s =list_apps_response=, =list_app_versions_response=).
Any struct that departs from this -- adds =success=/=message=, renames
fields, or otherwise doesn't match what codegen would produce -- is
drift and needs a decision: regenerate it properly, or document why
the exception is deliberate (e.g. a request that can genuinely fail
server-side beyond decode/auth errors, distinct from the common
error-reply path).

Concretely spotted so far: =ores.compute.api='s
=list_platforms_response= (=projects/ores.compute/api/include/ores.compute.api/messaging/platform_protocol.hpp=)
carries hand-added =success=/=message= fields, unlike its sibling list
responses in the same component and unlike the equivalent structs in
=ores.iam.api=. That's the one confirmed outlier; the inventory should
find the rest across all components (compute, iam, refdata, marketdata,
dq, scheduler, reporting, workspace, assets, trading, ...).

** Why

Discovered while implementing the ACME compute package publishing flow
(task 0F768B80-184A-44C7-B725-A594A873AB4A): the shell command and the
new standalone Qt "Upload Engines" dialog both had to special-case
whether a given =list_*_response= carries a =success= field or not,
which is exactly the kind of per-message inconsistency codegen exists
to prevent. Left unaddressed, every new caller has to rediscover the
same divergence by reading each protocol header instead of trusting a
single convention.
