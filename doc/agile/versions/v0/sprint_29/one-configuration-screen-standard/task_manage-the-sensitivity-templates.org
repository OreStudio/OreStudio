* Goal

Give the sensitivity templates a screen: the tenant's keys, each with its
asset class, its method and the method code ORE spells in a key, and its
description. A person reads the keys, adds one of the tenant's own, corrects a
description, and deletes a key it added, through the standard record screen.

The screen manages the keys alone. The shift sizes and shift schemes a key
implies belong to the sensitivity configuration, and the screen says so where
a person would look for them.

* Acceptance

- A sensitivity template is a key a pricing engine configuration puts on a
  product with the =SensitivityTemplate= setting, and the screen manages the
  keys of the tenant and nothing else.
- The list shows the code, the asset class, the method and the description,
  searches and orders on the server, pages at 15 rows, and opens a key's page.
- The record page titles the key by its code, offers Edit, Delete and History
  as the standard sets them, and its Details states the asset class, the method
  with its code, and the description, under the sentence that says what the key
  does not decide.
- A new key states its code once; a correction cannot change it. The form draws
  the asset class and the method as selects over what the table allows, and
  states the method code the chosen method implies rather than asking for it.
- The BFF serves the list, one key, the create, the correction, the removal and
  the history, and refuses a create of a code the tenant holds, a correction of
  a code it does not hold, and a write against a version that moved on.
- The screen is reachable where a person looks for sensitivity data, as one
  entry named Sensitivity templates.
- The words are in English, French and Portuguese.

* Plan

** What the record kind declares

| Declaration | Value |
|-------------+-------|
| Record kind | =sensitivity-templates=, the tenant's, with no party |
| Key | =code=, fixed once the row exists |
| Display field | =code=, because a template key is what a person knows a template by |
| Versioned | Yes, and writable |
| Natural order | The key's order, which is the store's default |
| Exception | None of the record standard's. The =SensitivityTemplate= setting is a code list that a configuration points at, which the configuration screen standard calls a field set of another kind; it is not a configuration of its own |

** The list contract

The screen searches and orders on the server, as the standard requires, and the
generated contract carried neither. The model now declares =code= and
=description= searchable, and =code=, =asset_class=, =method= and =description=
sortable, so the store searches the two fields a person searches by and refuses
no column the list offers. The generated filter gains =search=, so the contract
is extended rather than the screen reading every row.

** The BFF module

=sensitivity-templates.ts= registers six routes under
=/api/analytics/sensitivity-templates=: the page, one key, the two writes, the
removal, and the history, plus the choices the dialog draws. Each route names a
generated subject, so the wire shape is the protocol's and not the module's.

- The page reads one page through =analytics.v1.sensitivity_templates.list= and
  answers the store's =total=, so the pager counts every key.
- A create claims =must_not_exist= and a correction claims
  =must_match_version=, so a key written meanwhile is refused rather than
  replaced. The service states the refusal's code, and the module answers 409
  for a code the tenant holds and for a row that moved on, and 404 for a code it
  does not hold.
- Both writes derive =method_code= from the method. The table checks the pair,
  and a person types neither the code nor its token.
- A removal reads the row first and answers what it removed, because the
  versions stay in the history and the dialog says so.
- The history route reads the key's versions through the shared history read
  (RS-HIST-01). The generic =/api/history= route also serves the entity type,
  because that is the request the standard's timeline reads.

** The screen

Two pages under =web/src/sensitivityTemplates/=, one form module, and one module
of the reads and the permissions. The list and the record page use the shared
parts the classifications screens use: =RecordList=, =RecordHeader=,
=RecordDetails=, =Dialog=, =ReasonFields=, =useCloseGuard=, =DeleteDialog=,
=RevertVersionDialog= and =RecordTimeline=. The header actions are the standard
three: Edit, then Delete, with History as the second tab.

The form is one dialog with no tabs (the form has four fields), the asset class
and the method as selects over the choices route, the key as text on create and
as words on a correction, and the derived method code as a statement under them.
The reason and the commentary come last, and a new key carries =system.new_record=
in a note rather than asking for it.

** Where the screen sits

Sensitivity templates are read by the pricing engine configuration, which is
Product pricing in the reporting area, and the shifts they imply are the
sensitivity configuration's. The reporting area has no Sensitivity analysis card
or configuration yet, so the entry is a card of that area beside Product pricing
and Engine run settings, named Sensitivity templates, and the area opens for a
person who holds the read of any of its four screens.

** What the standard required that did not fit

- The configuration standard's "What this configuration decides" sentence wants
  its second half to link to the other configuration. The sensitivity
  configuration has no screen yet, so the half that names it is words and not a
  link.
- The record standard's natural order for reference data is the display order
  then the name. A template has no display order and its display field is its
  key, so the order is the key's.
- The History tab reads the generic history request, because RS-HIST-01 names
  it, so the module's own history route answers the same read for a caller that
  names the record's own address. Both are tested.

* Result

The screen is built, and it is driven on the running environment:

- the list reads the tenant's 19 keys, pages at 15, and searches and orders on
  the server;
- a key opens on its page, which states what the key decides and what it does
  not;
- a key the run added was created, corrected and removed, and each write shows
  in its history as a version with its reason and its commentary;
- the seeded keys are untouched: the count returns to 19, and =IR_FD= still
  reads version 1 with the words it was seeded with.

Six commits carry it: the model change that lets the list search and order on
the server, the BFF module, the descriptors it needed, the screens, the browser
run with the two faults it found, and a generator fix for a standing defect the
history read exposed.

** The defect the history exposed

The History tab answered nothing at first. A history provider reads with the
caller's tenant, and the entities whose rows the system tenant holds, which
includes every pricing engine vocabulary table, answered an empty list for a
row the caller may read. The provider now scopes to the system tenant for the
entities the model declares =system_tenant_validation= on, and the 29 entities
that declare it are regenerated. The pricing engine type, method, model, pair
and pair setting histories are fixed by the same change.

** Where the screen sits

The reporting area, as a card named Sensitivity templates, beside Product
pricing and Engine run settings. The two configurations beside it are what read
these keys: a product carries one with the =SensitivityTemplate= setting. The
area already had no Sensitivity analysis card, so the entry went beside those
two, and the area opens for a person who holds the read of any of its four
screens.
