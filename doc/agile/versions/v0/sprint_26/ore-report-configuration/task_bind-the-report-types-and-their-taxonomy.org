* Goal

A report type is our own classification, not ORE's. It decides which workflow runs a report and which configuration sets that run needs, so a new kind of report is a seeded row plus a workflow factory, never a column on the definition.

* Acceptance

- report_definition carries a report type foreign key to the seeded report types table; the text column report_type comes out.
- Every report type ORE Studio supports is seeded with a stable code, replacing the faker-generated sample values, and each one names the workflow it selects.
- Each report type names the configuration types a run of that type requires, so a report cannot be scheduled without its inputs, and a test proves the requirement for one type.

* Plan

Measured on 2026-10-03 before any change:

- One report workflow exists, =report_execution_workflow=, and the trigger
  handler hard-codes it for every definition whatever its type.
- Two report types are seeded: =risk=, which that workflow runs, and =grid=
  ("tabular export without analytics"), which no workflow can run because the
  workflow always submits to the compute grid. No seeded definition and no DQ
  template uses =grid=; every one uses =risk=.
- =report_definition.report_type= is a text column with no foreign key check.
- Nearly every shipped run document names pricing engines, today's market,
  curve configuration and conventions (777, 532, 415 and 414 of 416); the rest
  depend on the analytics chosen.

Decided with the operator:

- Seed =risk= only, selecting =report_execution_workflow=. =grid= goes until a
  workflow can run it; other kinds (imported, composite, diff) come with
  [[id:3B54C916-DA12-41F3-BD9C-DC8968821435][Classify report kinds and bind each to a workflow]].
- A =risk= report requires the four configuration types every run uses. The
  analytic-specific ones belong on the analytic types, as a follow-up.
- This task enforces the requirement and chooses the workflow from the report
  type at run time, not only the data.

Steps:

1. Report types gain the workflow they select.
2. A junction lists each report type's required configuration types.
3. The definition's =report_type= gains its foreign key check. The column keeps
   its name: renaming it reaches the DQ report-definition templates, the publish
   function, the shell and tests for no gain, and the foreign key is what the
   acceptance wants.
4. The trigger handler takes the workflow from the report type and refuses a
   definition whose bound configurations miss a required type, with a test.
5. One migration for databases created before the change.

* Notes

- The trigger refuses every definition that binds fewer than the four
  configurations =risk= requires. No seeded definition binds any configuration
  yet, so after this change no seeded report can be triggered until its
  configurations are bound. That is the enforcement the operator chose; it is
  stated here so the refusal is not mistaken for a regression.
- The check runs when a report is triggered, not when it is scheduled. A
  definition's configuration can change between scheduling and a run, so the
  trigger is the one place the answer is current.
- The existing foreign key from =report_configuration.configuration_type_code=
  resolves under the definition's tenant, while configuration types are seeded
  only for the system tenant. A report configuration in a non-system tenant is
  therefore refused today. Not changed here; it belongs with binding real
  configurations to definitions.

* Result

- =report_type= gains =workflow_type=; only =risk= is seeded, selecting
  =report_execution_workflow=. =grid= is gone.
- New junction =ores_reporting_report_type_configuration_types_tbl=, seeded with
  =risk= requiring =pricing_engines=, =todays_market=, =curve_configuration= and
  =conventions=. System-wide like the other reporting lookups (RLS exception
  recorded), with its permissions seeded.
- =report_definition.report_type= gains a soft foreign key resolved under the
  system tenant. The column keeps its name; see the plan.
- The trigger handler reads the workflow from the report type and refuses an
  unknown type (=unknown_report_type=) or a definition missing a required
  configuration type (=missing_configuration=, naming them). The comparison is
  =service::missing_configuration_types=, pinned by six unit tests.
- Migration =reporting_report_types_bind_workflow_and_requirements_migration.sql=
  for existing databases, exercised in a rolled-back transaction: it refuses
  while a current definition names a non-=risk= type, and otherwise leaves =risk=
  with its workflow and four requirements.
