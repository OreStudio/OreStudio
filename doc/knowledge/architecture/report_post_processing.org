#+title: Report post-processing
#+description: What post-processing makes of the engine's output: which reader reads which file, which table takes which family, who owns which format, what a refusal does, and what the whole thing costs.
#+type: knowledge
#+level: cross
#+filetags: :knowledge:architecture:reporting:postprocessing:results:

* Summary

Post-processing reads what the engine wrote and stores what it says. The output is
a set of delimited files, one per analytic: net present values, cashflows, curve
points, the market state the run read. The files are of three kinds, and each kind
goes to the store that owns it.

It is the phase whose cost is proportional to the size of the result, and the one
where throughput is decided. Like pre-processing it has a documented substitute: a
run configured to ignore results records where the output is and stops.

The formats are stated in
[[id:8BF75172-CD91-461A-A3BA-2B4E913D63A8][ORE output processing]], and the phases
in [[id:4F9639E5-AA68-4D47-BB05-8FA864FF9855][Report execution pipeline]].

* Detail

** What the step is handed

The run's compute results: one per workunit, each naming where its output archive
is. It also holds the run's own token, which is the authority to read them. It is
handed locations, never contents.

** What it does

| Step | Reads | Produces |
|------+-------+----------|
| Fetch | object storage, by each result's output location | the output archives |
| Unpack | each archive | the files the engine wrote |
| Route | each file's name, through the catalogue | the family, and its shape |
| Read | each file, through the reader its shape names | the run's figures |
| Load | the figures, one bulk statement for each family, in one transaction | rows in the store |
| Hand over | the archive locations and the run's token | the market state in the market data store |
| Record | the counts | the run's result summary |

Nothing in reporting parses an ORE file: the readers belong to =ores.ore= and
reporting calls them.

** How a file is routed

The catalogue says which family a file name belongs to, and the family's columns
say which shape its row is. One rule decides, and it is stated once in =ores.ore=:

| The row is | The family is | The store is |
|------------+---------------+--------------|
| keys, qualifiers and figures | a metric family | =ores_reporting_report_metrics_tbl= |
| a payment with a leg and a number | a cashflow family | =ores_reporting_report_cashflows_tbl= |
| the market state of the run, one column for each curve and tenor | a market state | the market data store |
| anything else | no family | left alone, and named in the log |

A file no family covers is counted and logged rather than refused: a run may write
a file this version does not model, and the archive still holds it.

** The readers

=ores.ore= declares each family's columns and their roles — key, qualifier,
measure — and derives its readers from that declaration rather than writing one
for each family:

- =read_metrics= turns each measure column into one figure named by its heading.
  A curve, a risk factor and a quantile therefore need no reader of their own, and
  a family that gains a column for each curve costs nothing.
- =read_cashflows= reads a family whose row is a payment. The stressed families
  state each figure three times; the reader turns =Amount_Base=, =Amount_Scen= and
  =Amount_Diff= into one figure named =Amount= with the part beside it, so a
  comparison needs no knowledge of the suffix.
- =index_payload= reads a market-state file without reading its figures: the
  headings, the row count and the distinct values of each key.

** The stores

=reporting= writes the run's figures.

- A metric row is the run, the party, the family, the subject, the observation
  date, the measure, the currency, the scenario, the risk factor, every other
  qualifier as one JSON object, and the figure. It is a hypertable on the
  observation date, and the family is a column rather than a table: sixty tables
  would be forty identical shapes and a union for every cross-family read.
- A cashflow row is the payment's trade or market object, its scenario, its leg,
  its number, its pay date, its flow type and its currency, one figure named by
  its heading, and the part of a stressed comparison it states. A payment is not a
  metric: its meaning is the relation between its keys, and those keys have no
  place in a metric row.

Both are written once per run and never edited; a correction is a new run.

The market data store writes the state.
=ores_marketdata_market_state_payloads_tbl= keeps the file the engine wrote,
compressed, with an index beside it: a row for each value would be millions of rows
for one run, and a read that wants one factor would unpack all of them.

** Why the store is shaped this way

- *One table for the metric families, not one for each.* The columns of fifty
  families fall into three jobs, and once the roles are known the shapes are one
  shape.
- *A separate table for the payments.* A cashflow's keys are what make it a
  cashflow, and flattening one into a metric loses them.
- *The engine's headings are stored, not translated.* A family's measure is the
  engine's own word, so nothing in the store has to be listed when ORE adds a
  column.
- *Loaded in bulk, in one transaction.* A partial load reads as a complete one, so
  a refusal leaves nothing behind.

** What a screen reads

A screen does not read a family. =ores.reporting.run_result= is a read model: a view
over the metric table that names each engine heading once — =NPV= is =npv= — and
reads the counterparty out of the qualifiers. The screen's shape therefore does not
change when a run states a new family, and no screen states a rollup twice.

** What a refusal does

A refusal stops the run and records the reason on the instance. The step refuses
when a family's row cannot be read whole, when a figure is not a number, when a date
cannot be read, and when a market-state file states no heading. It does not refuse a
file no family covers, and it does not treat the engine's null string as a zero: a
figure that was not stated is not stored at all.

** What the node leaves behind

The compute wrapper runs the engine with the output directory on local disk and
uploads that directory as one archive, which is the run's audit blob: whatever the
engine wrote is in it, modelled or not. The node projects nothing. It knows which
files it wrote but not what they mean, and everything a reader would call judgement
— which run this is, which party owns it, what date it priced at, whether the rows
load at all — belongs to the component that holds the run.

The node's reach is unchanged: the job directory, object storage over HTTP with the
token of the claim it was given, and =compute.v1.ops= to take work and say what
happened. It holds no user's authority and reaches no database.

** The substitute: ignoring results

When the run's configuration selects the substitute, the phase is not executed.
The workflow dispatches a step that records the output location on the run and
completes. Nothing is fetched, parsed or loaded.

This is what allows a run to complete while the result store is unwritten, and it
is deliberately the weakest of the substitutes: it proves that a run can reach a
terminal state and that its output exists, and it proves nothing about the
contents. Three conditions hold, as for pre-processing:

- *The output must still be recorded.* A run that ignores its results must still
  name where they are, or the work is lost the moment the archive expires.
- *The parallel phase must be indistinguishable.* Finalisation knows that the run
  completed and where the output is; it is not told whether the results were read.
- *The substitution must be recorded on the run.* A completed instance whose
  results were never ingested must not be mistaken for one whose results are
  queryable.

** What this costs, and what changes

A grid finishes many runs at once, so the cost of one run matters, and three
changes are in flight because of it.

- *The archive is fetched and unpacked twice for each run* — once by reporting for
  the figures, once by the market data store for the state. The fix is to fan the
  output out at the node, one object for each file, so each component fetches only
  what it models. See
  [[id:C6E58C64-D5A7-4077-9553-9D72D3AB8DDE][Fan a run's output out at the node]].
- *A family is read whole and written in one statement*, so peak memory grows with
  the family's size. The fix is blocks of rows, with the same one-transaction
  guarantee. See
  [[id:2B253ED2-E629-4A58-82BC-EEDEE3F0077F][Store a run's figures in blocks]].
- *The market state is held as base64 text in a row*, a third larger than the
  compressed file and in the database, which is the wrong place for it. The fix is
  the object store, with the index and the key in the row. See
  [[id:1D326204-29A2-4467-8DC7-779BD0C3CFAB][Keep the market state in the object
  store]].
