reply. Both corrections are in the journey's coverage table, so read that table
and not the prototype's subject strings.

as unchanged and the step to walk back to.

** What could not be built

1. *The BFF half.* The browser client and the screen are complete, but the BFF
   serves no counterparty routes. =api/counterparties.ts= calls
   =/api/counterparties=, =/api/counterparties/children=,
   =/api/counterparties/pick-lists= and the composite, centre and visibility
   writes; none of those routes exists in =packages/bff/src=, so the screen
   cannot yet run against the live fleet. Those routes are the one change the
   screen still needs, and this task's write scope did not include
   =packages/bff=.
2. *An existing counterparty's agreements, sets and collateral terms are not
   read.* Opening a row loads the identity, the identifiers, the contacts and
   the business centres, and starts the agreements empty, which is what the
   accepted prototype does. The confirm therefore stages no agreements for a
   counterparty opened from the list. This is the composite-read gap the journey
   document records.
3. *The business-centre junction is not in the journey's coverage table.* Step
   2 enters the centres, and the "Record every business centre a counterparty
   deals through" task requires the junction, so the screen reads and writes
   =refdata.v1.counterparty_business_centres= (those subjects exist in the
   tree). The coverage table names only =business_centres.list= for this step,
   so this is a subject the table does not list and the step text needs.
4. *The visibility junction is a write after the composite, not inside it.*
   =PutCounterpartyCompositeRequest= carries no party-counterparty rows, so the
   confirm sends =refdata.v1.party_counterparties.put= as its own act after the
   composite. A failure there leaves the counterparty written without its
   visibility row.
5. *History revert is not wired.* The History step reads the versions and the
   field-level difference through =HistoryPanel= and offers no revert, because
   reverting writes the old identity and children and that path through the
   composite write was not built.

** What contradicts the plan

The plan's step 3 says the journey's coverage table was reconciled with the tree
and every subject in it resolves. That holds. It does not say the table is
exhaustive, and it is not: the business-centre and visibility writes above are
missing from it while both sets of subjects exist. The two traps the Notes name
were avoided: the composite read is
=refdata.v1.ops.get_counterparty_composite_as_of=, and the landing list reads
its identifiers and contacts with =counterparty_id_one_of=, one call per child
type per page.
