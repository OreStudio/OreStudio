* Goal

IAM stores run grants: a person's consent that runs of one resource act in one
tenant and one party with one role. Grants are read like any entity and written
only through IAM's create and revoke operations, which make the checks.

* Acceptance

- =ores.iam.run_grant= exists as a codegen entity: tenant-scoped, party-isolated,
  bitemporal, with the fields of

- Its reads are on the wire, HTTP and the shell; it has no generic write verbs.
- =iam.v1.run_grants.create= creates a grant on behalf of the person, refuses a
  role the person does not fully hold in the party, and returns the active

3. An operation model for create and revoke, with a hand-written handler that
   checks the grantor and the role.

* Result

IAM stores run grants. =ores.iam.run_grant= is a tenant-scoped, party-isolated,
bitemporal entity whose reads are generated on the wire, the shell and the
TypeScript protocol, and whose writes are IAM's own operations. Codegen gained
the shape that makes this possible: a domain entity may now declare
=:client_read_only:= in its root flags, which keeps the repository writable for
the service and removes the write verbs from the wire.

=iam.v1.run_grants.create= refuses a session with no party or no permission
list, and a role the person does not hold in full; it returns the active grant
for the same resource, and re-activates a revoked one under the same id. A
create for an active grant returns it unchanged, so changing its role is a
revoke and a create. =iam.v1.run_grants.revoke= needs the grantor or the new
permission =iam::run_grants:revoke=, and a repeated revoke changes nothing.

The database was recreated for the new table, and the services were restarted.
Tasks 2 and 3 wait for the partition token work in the worktree clever
dijkstra, which adds the same claims, issue log and token cache.
