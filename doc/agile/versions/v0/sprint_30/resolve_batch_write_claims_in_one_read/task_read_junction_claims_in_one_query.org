* Goal

A junction batch write reads the current rows of all its pairs in one query and resolves every claim from that read.

* Acceptance

- The junction write(vector) and write(vector, claims) read the current rows of the batch once.
- A repository test proves the claims of a batch are still checked: a stale version is refused and writes nothing.

* Plan

- Add a private =read_current(rows)= to the junction repository: one query for
  each part of at most 1,000 links, an IN on each key column, filtered down to
  the requested pairs, as the entity compound keys do.
- Build every claim of the plain batch write from that read, and read once for
  the =any= claims of the claim-taking batch write.
- Make =apply_claim= a file-local function that takes the current rows, so no
  claim path reads a row on its own.

* Result

A junction batch write reads the current rows of its links in one query for
each part of at most 1,000 links, not one query for each row. The plain batch
write states every claim from that read; the claim-taking batch write reads
once for its =any= claims. All 27 junction repositories are regenerated.

Evidence, on the build of 2026-11-15 20:28: the new tests prove a plain batch
and a batch of =any= claims replace a live link and create a new one, and a
batch with a stale version is refused and writes nothing. The core suites of
every component with a junction pass: refdata 551/551, iam 306/306, dq 126/126,
inbox 84/84, assets 48/48, compute 81/81, reporting 307/307, trading 248/248,
and the three marketdata asset-class tests.
