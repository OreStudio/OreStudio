* Goal

Wire =ores.synthetic.service= to run =sandboxed= configs (per the
=binding_mode= primitive added by the previous task) end-to-end:
generating and publishing ticks under a distinct namespace that the
marketdata ingest loop (the real, bound-feed resolution path) never
subscribes to, regardless of any feed_binding row -- the exclusion is
structural, not merely a missing opt-in.

* Plan

- =feed_controller::start()= gained a =binding_mode= parameter
  (default =bound=, so every existing caller -- including the ad-hoc
  NATS control-plane, which has no config/binding_mode concept --
  keeps its current behaviour unchanged).
- Extracted the private =producer_subject= method into a free function
  =synthetic_producer_subject(source_name, binding_mode)= in
  =feed_controller.hpp=, directly unit-testable without a live
  controller instance (mirrors the =ir_curve_feeds_conflict= free-function
  pattern already used in =curve_feed_controller_tests.cpp=).
  =sandboxed= publishes on ="synthetic.v1.sandbox.tick.<source>"=
  instead of ="synthetic.v1.tick.<source>"=.
- =start()= skips =ensure_feed_binding(...)= entirely for =sandboxed=
  configs -- a =feed_binding= on that source_name would claim
  ingestion is happening on the bound subject, which would not be
  true. Belt-and-suspenders: the marketdata ingest loop's subscribe
  subject is *always* derived as ="synthetic.v1.tick." + source_name=
  from a feed_binding row (see =feed_ingest_loop.cpp=), so even a
  stray/buggy binding for a sandboxed source would still not reach it
  -- the two mechanisms (no binding, distinct subject) are independently
  sufficient.
- =auto_start_enabled_feeds= (=application.cpp=) now keeps the full
  =market_data_generation_config= row (not just a set of enabled ids)
  so it can read the container's =binding_mode= and forward it to
  =ctrl.start(...)=.
- *Live-verification bug found and fixed*: the JetStream stream
  =synthetic_ticks= only covers the ="synthetic.v1.tick.>"= subject
  filter. Publishing to the new sandbox subject with no matching
  stream made =js_publish= throw, which crashed the tick thread
  unhandled -- systemd was silently crash-looping the whole service
  (SIGABRT, restart counter climbing) the entire time the fix was
  "working" per its logs. Added a dedicated
  =synthetic_sandbox_ticks= stream for ="synthetic.v1.sandbox.tick.>"=,
  mirroring the existing =synthetic_curve_ticks= pattern (a new stream,
  not appended to =synthetic_ticks=, since =ensure_stream= only creates,
  never updates, an existing stream's subject list).
- Added =feed_controller_tests.cpp= covering
  =synthetic_producer_subject=: bound vs sandboxed subjects never
  collide (across several source-name shapes, including one needing
  sanitisation), and the sandboxed subject correctly falls under a
  prefix the ingest loop's hardcoded subscribe pattern never matches.
- *Live end-to-end verification* (after the JetStream fix): seeded a
  =sandboxed=, =party=-scope =market_data_generation_config= +
  =fx_spot_generation_config= + =gmm_component= directly via SQL,
  started the full service fleet, and confirmed: the feed auto-started
  with =binding_mode='sandboxed'= and the sandbox subject (service
  log); ticks published successfully (=SYNTHETIC PUBLISH= log, no
  crash); the marketdata ingest loop logged =no active
  subscriptions= throughout; no =feed_binding= row exists for the
  source; no =market_series=/=market_observation= row was ever
  created for the ORE key. Cleaned up via a full DB recreate.

* Result

=ores.synthetic.service= now runs =sandboxed= configs end-to-end:
=feed_controller::start()= takes a =binding_mode= (default =bound=,
matching every prior caller), publishes sandboxed ticks on a distinct
="synthetic.v1.sandbox.tick."= subject via the new
=synthetic_producer_subject()= free function, and skips creating a
=feed_binding= entirely for them. =auto_start_enabled_feeds= forwards
the container's persisted =binding_mode= automatically. A dedicated
JetStream stream (=synthetic_sandbox_ticks=) was added after live
testing surfaced that =js_publish= to an uncovered subject crashes the
process -- covered by =synthetic_curve_ticks='s existing "new stream,
not appended" precedent.

Verified live against a running fleet: a sandboxed feed auto-starts,
publishes ticks successfully, and is provably excluded from the bound
path -- the marketdata ingest loop never subscribes to it, no
feed_binding is created, and no market_series/market_observation ever
appears for its ORE key. =feed_controller_tests.cpp= (4 new cases)
covers the subject-naming primitive directly. =compass build= clean;
=ores.synthetic.*=, =ores.marketdata.*=, and =ores.qt.tests= C++
suites pass (one unrelated, pre-existing environment-config test
failure in =ores.synthetic.service.tests=, same as the prior task).
