* Goal

Move the one switch that sends the requests of ores.web to the C++ server, and test ores.web end to end. If ores.web breaks, move the switch back, use the BFF, fix the fault and try again. Retiring the BFF is not part of this task. This task depends on all the other tasks of this story.

* Plan

The switch already exists and is one variable. =baseForScreen= in
=projects/ores.web/packages/web/src/api/servers.ts= sends a screen's requests to
the prefix =/cpp= when the screen is named in =VITE_ORE_CPP_SCREENS=, and the
proxy in front of a deployment sends =/cpp= to =ores.http= and =/api= to the BFF.
So this task is: name every screen in that variable, and prove the browser works
against the gateway.

What stood in the way was the inventory's own count. Of the BFF's 334 routes, 322
are now paired with a route =ores.http= answers and 12 are not:

| The gap | Routes | What this task does |
|---------+--------+---------------------|
| the agile and QA file-backed routes | 12 | out of scope by the task that decided them, because they read and write the checkout and a deployed gateway holds none |
| the classifications | 6 | done: ores.http answers one generated route per list at the address the screen calls, so the pairing names a family of 28 routes, and the order it lists the rows in is the screen's |
| the market screens | 4 | done: curve analytics, the FX montage, instruments and the rate ladder are paired and proved on a live gateway |
| the quotes screens | 4 | done: the list, its feeds, its history and the vols-by-delta fit are paired and proved on a live gateway |
| the identity shape fields | 2 | done: the joined read the oresmd editor marks a URL's fields from is paired |
| the authorisation queue | 1 | done: the requests a decider may act on with each deal as it stands now, paired and proved on a live gateway |

A screen moves only when every route it calls is answered, so the flag cannot be
set for a screen whose routes are missing: the browser would answer 404 where it
answered a page, which is worse than the two-server deployment it has today.
Every route that is neither decided out nor file-backed is now served, so what
remains is to set the flag for the screens and prove them in a browser.

The end-to-end test is the second half and is the point of the task: build the
web bundle with the flag set, bring up the fleet, and drive the screens a person
uses against the gateway — sign in, choose a party, read each screen's list and
open one record. A screen that breaks is moved back to the BFF, the fault is
fixed, and the flag is tried again. Nothing in this task retires the BFF.

* Notes

- The authorisation queue is proved by its empty answer and its refusals: this
  database holds no authorisation request, because one is raised by booking a
  trade live and it holds no live booking. The row's members are proved by the
  workflow suite instead. See =evidence/authorisation_queue_live_run.txt=.
- A read this port answers refuses a query parameter it does not take, where the
  BFF ignored one. That is the port's convention, and it tells a person their
  query did nothing: the screens send only the parameters the routes declare.
- The two desk reads that answer a table this environment does not seed are
  proved by their refusal alone: the database holds no rate quote at any
  currency, instrument type or instant tried, and no curve bootstrap
  configuration. The catalogue and the FX montage came back whole, and the
  gateway's answer was identical to the BFF's in all four cases. See
  =evidence/market_reads_live_run.txt=.
