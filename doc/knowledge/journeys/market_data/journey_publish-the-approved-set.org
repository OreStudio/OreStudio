This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A trader applies an approved candidate set so that the curve the system uses becomes the new one, and pricing and reporting see it from that moment.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"The decision has been made. I want the curve the desk uses to be this one now,
and I want it to say who published it." The journey is done when the candidate
set is the published curve, priced and reported from, and the act carries the
name of the person who published it.

* Actor and trigger

The actor is the trader who owns the curve. The trigger is a request that has
reached its required number of approvals. The journey starts at the approved
set and ends when the published version is visible to pricing and reporting.
It follows
[[id:A85B6C4E-0F93-4410-BF2E-7167722849ED][Decide a publish]]; the request it
applies was raised in
[[id:239E4C3C-12E7-4A87-9DE3-16B9F093BC14][Ask for a publish to be approved]].

Publishing is a named, attributable act. The person who applies the approval is
recorded, and the moment the new version becomes visible is the moment of that
act. When the kind's =approvals_required= is zero, there is nobody to decide:
the raise is the publish, and the same operation applies it at once. When the
count is n, the publish applies only once n distinct approvals stand.

* Steps

1. *Open the approved set.* The trader opens *Approvals* or the curve and reads
   the set the approver said yes to. The system lists the approved requests
   with the curve each one is about.
2. *Read the approval.* The system shows the request, who approved it, when,
   and the comment. The trader confirms that the required number of approvals
   stands before publishing.
3. *Read the points that will be published.* The system lists the candidate
   points the approval covers: each =oresmd_uri=, its value and its source as
   the derivation wrote them. The trader reads exactly what is about to become
   live.
4. *Apply the approved set.* The trader chooses *Publish approved set*. The
   system records the act, marked with the signed-in trader and the time, and
   makes this version the published curve. There is no publish operation today;
   see /What is missing/.
5. *Watch the moment it becomes visible.* The published version becomes the one
   pricing and reporting read, from the published time. Nothing marks a curve
   published, so a reader cannot tell a candidate from the live curve; see
   /What is missing/.
6. *Record who published.* The act carries the publisher's name and the time.
   The approval record already names who decided; the publish does not yet name
   who applied it.
7. *Publish immediately when no approval is needed.* When the kind's
   =approvals_required= is zero, the raise is the publish and the set becomes
   live at once. No path applies a zero-approval request today; see /What is
   missing/.
8. *Tell the consumers.* The system tells the people and services that read
   this curve that a new version is live. No notification kind exists for a
   publish; see /What is missing/.
9. *Leave.* The trader goes back to the curve, now showing the published
   version.

Step 4 is the moment. Before it, the candidate set is evidence the market or
the recipe produced; after it, it is what the system uses. Nothing in the data
distinguishes the two states yet, which is the gap this journey and the two
before it exist to close.

=marketdata.v1.curve_bootstrap.republish= exists and writes the derived
observations, but its own contract says there is no review or approval gate: it
always auto-publishes. That is the opposite of what this journey needs, so it
is =partial= rather than the operation this step calls for.
=inbox.v1.notifications.raise= exists and is generic, but no market-data
notification kind tells it what a publish notice is.

* What is missing

1. *There is no publish operation.* Nothing applies an approval to a curve, so
   a decided request cannot become a live curve. The candidate is
   =marketdata.v1.curve_bootstrap.publish=, which takes the approved request
   and the candidate set and makes it the published version under the
   publisher's name. Until then the only write is
   =marketdata.v1.curve_bootstrap.republish=, which publishes unconditionally
   and ignores the approval.
2. *There is no published marker on a series or a build.* Nothing says which
   candidate set is the live one, so a reader cannot tell a candidate from the
   curve in use, and no delta or withdrawal has a baseline. The candidate is a
   published state on =market_series= — =published_at=, =published_by= and the
   as-of published — or a publish record of its own. Until then the publish
   control is disabled and the screen shows the latest observations without
   claiming they are published.
3. *There is no notification kind for a publish.* Consumers are not told a new
   version is live. The candidate is an =ores.inbox.notification_kind= such as
   =marketdata.curve_published=, with =message_key= and =mail_optional=, seeded
   beside the kind that raises it. Until then the consumers panel states that
   nobody is told.
4. *Zero approvals have no path.* =approvals_required= is a count the kind
   carries, including zero, but nothing moves a zero-approval request to
   approved without a person. The candidate is the rule in the inbox service
   that a raise with =approvals_required= 0 closes the request approved at
   once, which then lets the owning publish apply it. Until then a kind that
   publishes immediately cannot be expressed.
5. *The act names no publisher.* The approval records who decided, and this
   journey promises the person who publishes is named too. Nothing carries that
   name. The candidate is a =published_by= field beside the published marker.
   Until then the screen reads the name from the signed-in account and says it
   is not yet stored.
6. *There is no candidate set to publish.* The thing published would be a set
   of points with one as-of, and no entity holds it. The candidate is the
   candidate set of the first journey. Until then the publish has to name the
   series and the as-of and take whatever the derivation wrote under it.
