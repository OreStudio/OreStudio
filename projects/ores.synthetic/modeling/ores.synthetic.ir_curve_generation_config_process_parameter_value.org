One named process-parameter value of an =ir_curve_generation_config=,
referencing its =yield_curve_process_parameter_definition=. This is the
"value" half of the row-based parameter architecture: an IR curve
generation config stores its process parameters as one row per
parameter (kappa=0.1, rho=-0.5, ...), the parameter
=definition= supplies the vocabulary (name, description, bounds), and
the mapping layer materialises these rows into the strongly-typed
process-parameter structs of =ores.analytics.quant=
(=two_factor_gaussian_params=, =vasicek_params=, ...).

The =(config_id, parameter_definition_id)= pair is unique: each
parameter appears at most once per config. A hand-written DB trigger
(not the codegen single-argument Validations mechanism, which cannot
express a two-column lookup) enforces that the definition's
=process_type_code= matches the config's =process_type= -- a config
driven by =TWO_FACTOR_GAUSSIAN= may only carry values whose definitions
belong to =TWO_FACTOR_GAUSSIAN=. Both soft FKs are additionally
validated at insert time by the generated validation functions. No
standalone Qt layer: value rows are edited from inside the IR curve
generation config detail dialog, which reads definitions and value
rows via the normal codegen repositories.

* SQL

** Flags
:PROPERTIES:
:tablename: ores_synthetic_config_process_parameter_values_tbl
:END:

The =:tablename:= is the base every SQL object name for this entity is
composed from (table, insert/notify/delete functions, triggers, delete
rule). It deliberately drops the =ir_curve_generation_config_= prefix
(the parent already scopes the rows): the conventional
=ores_synthetic_ir_curve_generation_config_process_parameter_values_tbl=
is 72 characters, and PostgreSQL truncates identifiers to 63 bytes —
table, functions and triggers would all collapse onto one identical
63-character name, so the last =create or replace= silently replaces
the earlier objects (the insert trigger that fills =valid_from= /
=valid_to= is the one that gets lost). See the SQL naming
conventions doc for the codegen-side rule.

** parameter_definition_id
:PROPERTIES:
:table:             ores_synthetic_yield_curve_process_parameter_definitions_tbl
:error_message:     Invalid parameter_definition_id: %. No active yield_curve_process_parameter_definition found with this id.
:nullable:          false
:use_system_tenant: true
:END:

The definitions are system-tenant reference data: the populate script
seeds them once under the system tenant, and the publish function
(=ores_synthetic_publish_theme_from_dq_fn=) resolves them by name when
inserting tenant rows. The default tenant-scoped check
(=NEW.tenant_id=) would therefore reject every theme insert;
=:use_system_tenant:= resolves against
=ores_utility_system_tenant_id_fn()= instead, matching the
=process_type= validation trigger on the same table. =config_id= above
keeps the default resolution: the config row is a genuine tenant row.
