* Goal

A report values the trades whose market data the system can answer, and states plainly why it left the others out. The run resolves each trade's market data requirements before the engine sees it, excludes every trade the market cannot answer, and records where each error came from: the preprocessing of the run, the engine, or the postprocessing of its results. A product approval chain states what the party may trade, what each desk within it may permit, and what each book may carry, each level equal to or narrower than the one above, and the generator fills each book from its own level of it.

* Acceptance

- A party level product approval matrix states the product types the party may trade, and a book level matrix states the types that book may carry and is a subset of the party's.
- The generator fills a book with the product types its approval matrix names, and no other.
- A run resolves every trade's market data requirements before the engine and excludes each trade whose requirements the market does not answer, naming the cause for each gap.
- A book stated in a report names the trades that were not valued, with the cause of each.
- A run with no complete trade does not reach the engine and fails in preprocessing with the cause summary.
- Every error a run records states the phase that produced it: preprocessing, the engine, or postprocessing.
- A trade is never both excluded in preprocessing and failed by the engine, so an engine error means the trade's market data was complete.

* Decisions

Settled on 2026-11-25, when the story was formed.

1. *One run, three phases, and every error states its phase.* The phases are the
   preprocessing of the run, the engine, and the postprocessing of its results.
   =report_error_event= keeps =scope_code= as the engine's own group name, which
   its model page argues it must be, and gains a phase beside it. A run that
   never reached the engine states scope =Report= and phase =preprocess=, which
   is the shape the model already describes.
2. *An incomplete trade is a state, not an error.* It is recorded in the run's
   market readiness, not in the error table, so that table keeps meaning
   "something went wrong" rather than "something was absent".
3. *Exclude per trade, not per book.* The book states the count it lost and the
   causes, so a half valued book is visible rather than silently short.
4. *An incomplete trade never reaches the engine.* A trade is excluded or
   failed, never both, so an engine error means the trade's market data was
   complete: that is what makes an engine error a real valuation error.
5. *A run with no complete trade fails in preprocessing.* An empty valuation is
   not a valuation, and the grid is not spent on one.
6. *Three approval levels, at party, desk and book.* The party's set states what
   it may trade, each desk's states what that desk permits, and each book's what
   that book may carry, each level a subset of the one above it. The desk is the
   level a firm grants a mandate to, and a book already names its owner unit, so
   the chain follows a link the model had. A portfolio is not a level of it:
   moving a book between portfolios is not an approval. See [[id:193B547F-EF40-4138-85F8-5AB8B5610DB4][Product approval matrix]].
   The generator fills a book from its own set, which is what makes a population
   plausible: the book that trades cable holds cable options.
7. *Book affinity is data and not code.* It is the product approval matrix a real
   firm keeps, so the simulator and a real desk share it. No rule enters the
   platform for the simulator's sake: =expected_market_data= and
   =plan_on_expected_market_data= stay utilities of the simulator, and the truth
   about what a run can value comes from the run's own resolution.
8. *Market readiness has three grains.* By address, because each gap has a cause;
   by trade, because a trade is excluded as a whole; and by run, because a reader
   wants the counts. Each answers a different question and none is derived at
   read time from the others.
9. *The requirement resolution already exists per trade.*
   =ores_trading_market_references_fn= returns =trade_id= and the address, and
   the repository collapses it to a distinct set before the run ever sees it. The
   first code change is to stop discarding the trade, not to build a new
   resolver.
10. *A population states its outcome per book, and one type says both.* A run's
    report names the trades it wrote by configuration and again by book, because
    the first answers what the run did and the second where it landed. A book's
    entry carries the types it booked and, for each type it did not, the reason:
    its own approval matrix, the party's market data, or the builder. One outcome
    type is used for both readings — the count says whether the book booked the
    type and the reason says why it did not — rather than a booked type and a
    left-out type saying the same thing twice. The plan owns the types and the
    run owns the counts, and a book's planned count is the sum of its types, so
    the two halves cannot disagree.
