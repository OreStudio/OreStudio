* Goal

The two Membership journeys run in ores.web against the real server. The member reads the parties their account works in, sets the party quick sign-in uses, and switches the party the session acts for. The tenant administrator reads the reporting line as a tree and corrects it, with every change recorded and no loop.

* Acceptance

- Every Membership journey in the catalogue runs in ores.web against the real server.
- A party reads as a name, never as a bare identifier, on both journeys.
- The server refuses a reporting-line change that would make a loop, and the tree screen states the refusal.
- Every gap a journey document records is closed or stated on the screen, and the statement is recorded on this story.

* Plan

The prototypes come first, because the screen decides what the server must
serve. Both journeys carry gaps no screen can be sized around without seeing it:
neither can name a party today, the reporting line has no tree read and no cycle
guard, and a change to it has no approval. A prototype shows the shape, the copy
and the empty states, and it makes the server work visible before anybody plans
it.

* Decisions

- *The accepted variants are A on both screens.* Where I work puts a card per
  party with both actions on the card they change, so nothing depends on a
  selection made elsewhere. Reporting lines puts the indented tree beside the
  selected person, with the whole tenant on one screen and the controls in a
  fixed place. Each prototype task's =* Result= records what the accepted
  variant settles and what the rejected ones gave up.
- *The prototypes precede the build.* A screen with three missing operations
  cannot be sized from its document alone. The prototype shows the layout, the
  copy and the empty states, and the build tasks are written from what the
  product owner accepts.
- *A prototype is a static page under =doc/prototypes/membership/=.* React is
  for the product. The
  [[id:D913FE21-6CF6-439A-89CF-6A1928AFA094][Prototypes]] page states the one
  way to add one, and nothing here adds a second.
- *A party reads as a name on both journeys.* The account-party association
  carries =party_id= alone and no read outside sign-in turns it into a name.
  Both screens show a party, so the lookup is one server gap and not two, and
  the prototypes state the gap rather than inventing a name in a panel the
  server cannot fill.
- *The journey documents stay with the extraction pass.* Where a prototype
  disproves a claim in a journey document, the correction is recorded on the
  task and on this story, and lands in the document with
  [[id:1BDBC708-2749-41D0-9E2F-6B0EB7FBE645][Extract the remaining component
  user journeys]].
- *The reporting-line approval is stated, not built, unless the build carries
  it.* The journey makes a change a proposal that a superior or a tenant
  administrator approves, and nothing in the platform holds an approval. The
  prototype states who approves and draws the line still, so the gap is visible
  in the design rather than discovered during the build.

- The journey extraction, which is
