* Plan

The routes fall into three groups, each a reviewable unit:

- The bootstrap and setup reads: =/api/bootstrap=, =/api/bootstrap/administrator=,
  =/api/bootstrap/complete=, =/api/tenant-setup= and =/api/registration-policy=.
  The first two run with no session and the BFF rate limits the policy read,
  which the C++ server cannot do yet.
- The roster: =/api/tenants=, =/api/tenants/{code}= (read and remove) and
  =/api/overview=. Each needs the deployment read and joins the provisioning runs.
- The reads inside a tenant: =/api/tenants/{code}/parties=, =people=,
  =accounts/{username}/sign-ins= and =images/{id}=. Each enters the tenant for
  the read alone. The parties read reuses =party_page_routes::read_page= with a
  request that carries the tenant's token.

On 2026-11-11 the task served the roster first, and the other two groups
moved to [[id:76115CCB-0D67-4833-8A6B-050F744C1677][Serve the reads inside a tenant and the bootstrap routes]].

- =deployment_access= is a new unit in the IAM part. It names the deployment
  read and refuses a caller whose roles do not cover it, by the rule
  =ores::security::authorization::grants= states. The operations routes can use
  it too.
- =tenant_roster_routes= is a new unit in the IAM part: =GET /api/tenants=,
  =GET /api/overview=, =GET /api/tenants/{code}= and =DELETE /api/tenants/{code}=.
  Each checks the deployment read first, as the BFF did, and follows the BFF's
  reads: the tenant types decide which rows show, test tenants are hidden and
  counted, and each tenant joins its newest provisioning run. A failed run read
  leaves the runs out and says so.
- A tenant read the BFF failed with a plain error, which it answered as a 500,
  fails here as unanswered, a 502. The browser treats both as a failed read.
- The IAM part takes =ores.workflow.api= for the run reads.
