#+title: Merge without waiting for the checks; run them hourly
#+description: Pull requests merge without waiting for the local checks. The checks run on a roughly hourly cadence instead, and what they find is triaged from the report rather than blocking the change that exposed it.
#+type: memory

A pull request merges without waiting for the local checks. The suite runs on a roughly hourly cadence, not at the point a change is offered, and its findings are triaged afterwards as their own tasks. A red report is a work item, not a reason to hold a merge.

*Why:* The suite is the only gate left after the GitHub PR triggers came out, but a C++ change pays a full build, a database recreate and every test suite, which is an hour or more on one workstation. Gating every merge on that makes the checks the slowest part of the day. Running them hourly keeps the same coverage and moves the delay from the person waiting on a PR to the report that lands within the hour.

*How to apply:* Raise and merge PRs without running or waiting for compass check. Every failure becomes its own task, whether trunk or a feature branch, and the branch it was found on does not need to be green to merge. The run itself is not yours to make: it belongs to the hourly validation in the ores_dev_swift_curie worktree, which owns the build lock and runs the build, the database recreate and the suites. See static_validation_only_the_hourly_run_builds_and_tests for what the implementing agent does instead. This replaces the earlier position that a red tree cannot merge; six trunk defects were found this way and all of them were fixed as follow-ups rather than by holding the branch that happened to notice.
