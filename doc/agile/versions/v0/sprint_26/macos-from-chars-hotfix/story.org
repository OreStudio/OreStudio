* Goal

The macOS build stops on the credit simulation mapper:

#+begin_src text
projects/ores.ore/core/src/domain/credit_simulation_mapper.cpp:63:9: error:
  call to deleted function 'from_chars'
   63 |         std::from_chars(text.data(), text.data() + text.size(), value);
#+end_src

libc++ on Apple platforms does not implement the floating-point overload
of =std::from_chars=. It declares it deleted rather than absent, so the
call compiles under libstdc++ and MSVC and fails on macOS, and nothing in
a Linux or Windows build reports it. The estate parses one floating point
that way -- the transition-matrix bounds of a credit simulation, read from
ORES's own XML -- while the format side uses =std::to_chars=, which libc++
does implement.

=ores.platform= gains =numeric::parse_double=, and the mapper moves onto
it. The shim is the same shape as =concurrency::atomic_shared_ptr=: a
standard facility a supported library does not provide lives in one place
with the reason written down, instead of a call site discovering it when
the macOS job runs.

* Acceptance

- No floating-point =std::from_chars= remains in the estate, and the two
  integer uses stay as they are.
- The shim's contract is tested: a complete number parses, anything
  around it is refused, and every double the estate formats with
  =to_chars= parses back to itself.
- The credit simulation mapper keeps its behaviour, including its error
  message for a bound that is not a number.
- The affected suites pass, and the macOS job gets past the mapper.

* Decisions

- The shim lives in =ores.platform=, not =ores.utility=. What it encodes
  is a standard-library gap on a supported platform, which is what
  =concurrency/atomic_shared_ptr.hpp= in the same component exists for,
  and the component that needs it already links =ores.platform=.
- The implementation is Boost's lexical cast, not =strtod=. =strtod=
  follows the program's =LC_NUMERIC=, so a comma would parse as a decimal
  point in some locales and not others, and it skips leading whitespace
  where the standard overload does not. The shim's tests pin both
  differences.
- The floating-point =to_chars= calls stay. libc++ implements them, and
  the macOS compiler reported no error on the one in the same translation
  unit; replacing a working call would change the text the estate writes
  for no gain.

* Out of scope

- Any other library gap that only macOS sees. This story fixes the one
  that stops the current build; the shim is where the next one of the same
  family goes.
