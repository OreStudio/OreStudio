* Goal

The rate planner cycles nine routed types and each seeded rate config states eight slots, so slot 0 to 7 selects the first eight types and the ninth is never reached: a provisioned tenant books 24 rate trades over eight types and holds no knock-out swap at all. The fx planner cycles sixteen types against the same eight slots, so its variance swap and its accumulator never appear either. Either the config states a slot per type, or the type is drawn by name rather than by position, so a population of any length states every type it routes.

-

The same defect keeps two fx products out of the population. The fx planner
cycles sixteen routed types and each seeded fx config states eight slots, so
the last eight types are never drawn: a provisioned tenant holds no fx variance
swap and no fx accumulator, though both construct and both route. The rate
family is the case that was measured first; the fault is one rule, stated once
in each planner, and the fix belongs to both.

The fix is written and its tests pass: the seeded rate configs state nine trades
and the fx configs sixteen, which is one per routed code, and the planner tests
state the rule and name the knock-out swap, the fx variance swap and the fx
accumulator as the codes a short config was missing.

The provisioning run has not been made. Main does not compile since #4103
merged: =ores.synthetic.service= still calls
=market_data_client::list_market_data_sources()=, which that merge removed in
favour of =list_feeds()= returning a =feed= row, and a provisioned database has
no feeds table at all. The rename is half finished, so this is not a caller
rename that another branch can patch: reverting the WIP commit 84605bcf70
conflicts in fifty files.

Until main builds, this task cannot produce the run its acceptance asks for.

A planner draws its routed codes by the slot's position, so a config that states
fewer slots than its family routes states a prefix of the list and the codes past
that position are never drawn. The rate configs stated eight slots into nine
codes and the fx configs eight into sixteen, so a provisioned tenant held no
knock-out swap, no fx variance swap and no fx accumulator, though all three
construct and all three route.

The fix is in the data, not in the cycle: the seeded rate configs state nine
trades and the fx configs sixteen, which is one per routed code — the rule
commodity (25) and credit (5) already followed. The planner tests state the rule
at that size and name the three codes, so a config that falls short again shows
up as a missing code rather than as silence.

Measured on a fresh tenant: 27 rate rows over 9 codes with 3 knock-out swaps, 64
fx rows over 16 codes with 4 variance swaps and 4 accumulators, 8 range bounds in
place of 4, and every other family unchanged at 24 bonds, 25 commodity rows with
12 constituents, 17 equity rows and 5 credit rows. The tenant holds 162 trades
where it held 127.

Two consequences worth stating rather than leaving to a reader.

- The population grows by 35 trades and the mix moves with it: fx now carries 64
  of 162 trades, which is 40% against the 25% Trade Population Weights states.
  The mix was already far from those weights before this change — rates were 19%
  against 42% — so sizing every class to its weight is its own piece of work and
  is captured rather than attempted here.
- A tenant that wants a thinner book still can, by lowering trades_per_book; it
  gives up the codes past its slot count by doing so. The seed comment says this
  where the configs are stated, so the trade-off is written where it is made.
