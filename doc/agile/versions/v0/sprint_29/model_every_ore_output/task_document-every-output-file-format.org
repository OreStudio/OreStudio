* Acceptance

- Every catalogued family states its file parameter, its analytic, its key and every column with its type.
- Each figure says what it measures and its unit: money, a rate, a count or a date.
- The column tables are generated from the catalogue, and a check fails when the page and the catalogue disagree.
- Each family names a checked-in sample file that exercises it.
- The ORE knowledge page and the run-output journey link to it.

* Plan

The catalogue generator writes the page, so the column tables cannot drift from
the readers. What the catalogue cannot know, what a figure means and its unit,
lives in =output_family_docs.py= beside it, one entry for each family; the
generator refuses a family without one. Units that the writers set were checked
in the vendored source: the pricing and run timings are microseconds, nanosecond
clocks divided by 1000. The page is one knowledge doc with a Summary, the rules
for reading a family, the outputs not read into rows with their reasons, and a
section for each family. =--check= covers the page, and the local gate runs it
when the generator, the descriptions, the samples or the page change.

* Measurements

Every number this task claims about a tree, with the command that produced it
and the commit it was measured at. A number without both is not a measurement,
because a clean-up record describes a tree and trunk moves under a branch: a
consumer count, a gate's component count and a suite's size all change with no
code changing, and the reader of a bare number cannot tell which tree it came
from. Where the raw output matters, put it in an =evidence/= file beside the
task and name that file in the Command column.

* Result

other names, parameter, analytics, key, every column with its kind and role, what
