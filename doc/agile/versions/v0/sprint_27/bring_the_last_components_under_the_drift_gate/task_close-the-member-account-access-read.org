* Result

=read_account_access= gates on =iam::roles:read= and returns another
account's roles, who assigned each one and when. Member was granted that same
code so a member could read the role catalogue, and the accounts trigger gives
Member to every person at version 1, so every member could read every
account's access.

The catalogue does not need the code: the role and permission models name
their list and get subjects in =:open_reads:=, and the generated handlers for
those subjects carry no permission check. The web asks for
=iam.v1.roles.list= and =iam.v1.permissions.list=, never the gated =get_many=
or the versions, and =get_role_permissions=, which the "Can I?" panel reads,
is ungated too. Member now holds neither code.

Failure 2, =write_trade_booking_publishes_an_event= aborting on an empty
optional, was already repaired on main by =a08ce20beb= (the generated
eventing tests seed a party). This branch is off current main, so no change
was needed; the suite was run to confirm rather than assumed.

* Collision with #2916

Trunk landed =cfaa867ac1= (#2916, =eager_maxwell=) for the same failure, from
the other side: it keeps the grant and takes Member back in the case before
the call. That makes the case pass while a real member still reaches another
account's access, so the guard no longer covers what it was written for.

This branch keeps that case -- it still proves the gate refuses a caller with
no role at all -- and restores the case that holds only Member as the guard
for the grant. Both pass, which is only possible with the grant off Member.

Verified before the merge that nothing a member reaches needs the code:
=list_roles= and =get_role= carry no permission check, no client sends
=iam.v1.roles.get_many= or the versions, and =get_role_permissions= is
ungated.
