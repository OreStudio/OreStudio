* Plan

** Analysis (pre-implementation, no code touched)

Inventory: 20 =application.cpp=/=host.cpp= pairs (17 domain services
+ =ores.cli=/=ores.shell=/=ores.compute/wrapper=/=ores.http/server=;
=ores.wt.service= uses its own =application_context.cpp=/
=ore_application.cpp= shape entirely, no =host.cpp=) plus each
tool's =config/options.hpp=.

*** host.cpp — genuine shared-code candidate, not codegen

17 of 20 files (all domain services) are byte-identical modulo
naming — confirmed by diffing normalized copies
(=s/iam\.service/X/= etc — zero diff). Pure behavioural boilerplate
(parse -> init logging -> log -> construct app -> run -> catch/log/
rethrow), no per-service data baked in: the textbook case for a real
shared template function, not a codegen archetype. Two variants
needed — sync (=int=) and async (=boost::asio::awaitable<int>=),
since coroutine-ness can't be templated away cleanly in C++20
without =if constexpr= complexity that isn't worth it here.

*Drift bug found*: =ore.service= and =workflow.service= have
=if (be == nullptr) throw;= before logging, silently skipping the
=BOOST_LOG_SEV(lg(), error) << "Error: " << e.what()= line every
other domain service prints for non-boost exceptions — stale from an
earlier archetype revision, never regenerated. A shared helper fixes
this for both as a side effect instead of two manual patches.

The 3 divergent tools have *real* semantic differences, not just
boilerplate drift:
- =ores.cli=: sync, constructs =application(std_output, cfg.database)=
  (not default-constructed), plus a pre-application "DB-free command"
  interception branch (=cfg.ore_roundtrip=) before the main try block.
- =ores.shell=: sync, constructs
  =application(cfg.connection, cfg.login, cfg.script_path)=, calls
  =app.run()= with no arguments (no =io_ctx=, no =cfg=).
- =ores.http/server=: otherwise identical to the domain-service async
  shape, differing only in three string literals (startup banner,
  shutdown message, failure message) — a trivial variability-switch
  candidate, not a real shape difference.

*** application.cpp's make_context — already unified

Fixed in PR #1821 (this story). No further work needed; the codegen
archetype is the correct home and is already consistent across all
18 files that build a database context.

*** config/options.hpp composition — universal pattern, real variability is in the wiring

Every tool's =options= struct follows the same shape: optional
=logging=, then zero or more of {=nats?=, =database?=} (already
properly factored as shared library types
=nats_options=/=database_options=/=logging_options=), plus
app-specific fields. The duplication E3647ADD targets is the
*wiring* around this (variables_map construction, environment_mapper
setup, help/version handling) for the 17 domain services, not the
composition itself.

Surveyed the 5 tools E3647ADD's =standard_service_options= design
explicitly excludes, to see whether they could adopt it too:

| Tool             | Composition                          | Fits a monolithic helper? |
|------------------+---------------------------------------+----------------------------|
| =ores.wt.service= | logging+database+nats                | Yes — identical to domain-service shape despite a different (Wt) runtime |
| =ores.http/server= | logging+database+nats+extra         | Yes, if composable (extra options_description layered on top) |
| =ores.cli=        | logging+database, no nats            | No — needs opt-in sub-blocks |
| =ores.shell=      | logging+optional nats, no database   | No — needs opt-in sub-blocks |
| =ores.compute/wrapper= | logging+nats+extra, no database | No — needs opt-in sub-blocks |

*Recommendation for E3647ADD* (flagged in its own task's Notes, not
implemented here — that task owns its own design): build
=standard_service_options= as composable opt-in blocks rather than
monolithic assume-everything-present, so all 5 of these tools could
adopt it too, not just the 17 domain services already in scope
there.

** Implementation scope for this task

Given the analysis, this task implements the one clear, low-risk,
high-value win — the shared =host.cpp= template — and leaves the
config-composition opportunity as a flagged recommendation for
E3647ADD (a different task's territory) rather than a second
implementation here:

1. Add =ores::service::run_host()= (sync) and
   =ores::service::run_host_async()= (or an =awaitable= overload) to
   =ores.service=, extracting the parse/log/construct/run/catch
   envelope as a template function parameterised on the parser type
   and an application-construction callable.
2. Migrate the 15 domain services whose =host.cpp= is already
   byte-identical to the canonical shape (excludes =ore.service=/
   =workflow.service=, migrated as part of fixing their drift, and
   =http.server=, migrated with its 3 string literals passed as
   parameters) to call the shared helper instead of duplicating the
   envelope.
3. Fix =ore.service=/=workflow.service='s drift as part of their
   migration — they get the correct (logging) behaviour for free by
   using the shared helper rather than their stale hand-copy.
4. Update the =component-service= codegen archetype
   (=ores.cpp.service-app.host_impl.org=) so future-generated
   =host.cpp= files call the shared helper too, instead of embedding
   the envelope inline.
5. Leave =ores.cli=/=ores.shell=/=ores.compute/wrapper= as hand-written
   =host.cpp= — their differences (sync execution + custom
   constructor args + cli's interception branch) are real, not
   boilerplate drift, and forcing them onto the shared helper would
   need parameterising away genuine behavioural differences rather
   than removing duplication.
6. File a follow-up capture/task for E3647ADD's design
   recommendation (composable opt-in option blocks) rather than
   implementing it here.

*Critical bug caught by live verification, not unit tests*:
=run_host_async='s =host_runner_options= parameter was originally
=const host_runner_options&= with a default =={}=. Since
=boost::asio::awaitable= coroutines start lazily, =host::execute=
(not itself a coroutine) returns immediately after producing the
awaitable — destroying the temporary/local options object before the
coroutine body ever runs. Every migrated service SEGV'd on startup.
=ctest= never caught this (no test exercises =host::execute=); a live
=compass services start= cycle did. Fixed by taking
=host_runner_options= by value, documented the coroutine-lifetime
hazard on the parameter itself so it isn't reintroduced.

Verified: local build clean; =ctest= 71/71 passed twice (before and
after the coroutine-lifetime fix); live systemd verification — full
=compass services stop=/=start= cycle, all 22 units ready with 0
retries, =ores.http.server='s custom banner/shutdown lines confirmed
correct in its log, =ores.ore.service=/=ores.workflow.service=
confirmed healthy (drift fixed). Local DB was recreated mid-task to
clear an unrelated stale-schema issue (a prior migration not yet
applied locally) that was masking real verification the first time
around.

*Second unrelated bug hit and fixed during full-suite verification*:
=ores.synthetic.service.tests= crashed deterministically (unhandled
=boost::filesystem::filesystem_error=, EINVAL on
=create_directories=) on a =feed_controller_tests.cpp= test added by
PR #1844 (merged into =main= same day, unrelated to this task's own
diff). Root cause: =ores.testing='s =logging_listener.cpp= uses the
raw Catch2 test name as a log filename with no length cap; that
test's name was 289 bytes, over the 255-byte =NAME_MAX= most Linux
filesystems enforce per path component. Fixed by shortening the test
name to 212 bytes. Filed
[[id:A6CF498D-56A9-4DAF-B294-686C3AC3F395][Sanitize Catch2 test names used as log filenames]] for the general
fix (cap/sanitise in =logging_listener.cpp= itself, so this can't
recur for any future long test name repo-wide) rather than
implementing it here — out of this task's scope, and a shared-infra
change deserves its own review.
