* Notes

- The rule is checked in the session, after the identity is known and before the
  handler runs, so a route cannot forget to ask. Only a request proven by a cookie is
  guarded: a cross-site form can neither set an Authorization header nor read a
  token, so a bearer client is not asked for the session's headers.
- The deployment's own origin is taken from the request's =Host= and the deployment's
  TLS flag rather than from configuration, so there is nothing to keep in step and a
  deployment behind a proxy that rewrites =Host= is the case that will need a setting.
- The bearer path needs no case of its own: the storage upload end-to-end test sends a
  PUT with a capability token and none of these headers, and it answers 200.
