* Acceptance

- Entity models and tables exist for provider, source, vendor instrument and mapping, with history, and the source_kind code table holds live, replay, test, simulated and derived.
- Row-level security lets every tenant read the rows and only the system tenant write them.
- A repository test shows a mapping is unique per provider, scheme, id and field for a period.

* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

1. Add the =source_kind= code table to ores.refdata with the five kinds.
2. Model provider, source, vendor instrument and mapping as codegen entities in ores.marketdata.
3. Generate the SQL, C++, shell and wire types, and wire the registrars.
4. Make the system tenant own the rows and let every tenant read them.
5. Test the constraints in the repository.

* Result

The system tenant owns the rows and every tenant reads them. Seven repository tests cover the constraints. The build and the tests pass.

Known gaps:
- A range exclusion does not stop mapping overlap. Only the unique pair of instrument and start does.
- No test shows a tenant reading system rows.
- No role holds the new permissions yet.
- No catalogue rows are installed yet.
