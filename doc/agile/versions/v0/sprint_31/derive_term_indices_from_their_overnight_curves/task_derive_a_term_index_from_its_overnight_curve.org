* Goal

A term index of a currency that has an overnight curve gets its curve and
fixings from that curve. Term SOFR and IBR are the compounded overnight
forward over the term. EYTIBOR, WIBOR and the generic indices of KRW and
other currencies are the overnight forward plus a stated spread. Each rule is
data beside the curve configs, and task 3's list reads it.

- JPY EYTIBOR 3M, KRW GENERIC 3M and PLN WIBOR 6M answer, each with its

* Plan

The rule is data, and the row it belongs on is the synthetic curve config,
because that config is the only thing that states an index rate. Reading the
pipeline settled this:

- =ir_curve_feed= is the sole publisher of =market_member_kind::index_rate=
  on the run's board, and it publishes the rate of its own config's pillar
  whose end tenor equals the index tenor.
- =index_fixing_feed= writes a fixing from whatever the board holds as that
  index's rate, so a fixing needs only a board rate.
- The marketdata bootstrap (=curve_republish_service=) publishes discount
  factors, never rates, so it cannot serve this.

Five indices need it, over three existing overnight configs:

| Term index | Currency | Overnight index | Rule |
|------------|----------|-----------------+------|
| SOFR 1M | USD | SOFR | compounded over the term |
| IBR 3M | COP | IBR | compounded over the term |
| EYTIBOR 3M | JPY | TONA | overnight plus a stated spread |
| GENERIC 3M | KRW | KOFR | overnight plus a stated spread |
| WIBOR 6M | PLN | POLONIA | overnight plus a stated spread |

1. *The rule on the config.* =ir_curve_generation_config= gains
   =rate_source= (=process= | =compounded_overnight= |
   =overnight_plus_spread=), =derived_spread_basis_points= and
   =derived_spread_source=. A derived config states no process parameters:
   its rate comes from its currency's overnight config, which is the one
   config of that currency that funds (a =FUNDING= role and no tenor), so no
   new reference is needed. Checks: a =process= config states no spread; a
   spread config states both the points and their source.
2. *The derived rate.* =ir_curve_feed::index_rate()= answers a derived
   config from the board's overnight curve instead of its own pillars:
   =compounded= is the simple forward over the term,
   =(P(t)/P(t+T) - 1) / year_fraction(t, t+T)= — the OIS compounded rate of a
   daily overnight curve — and =spread= is the overnight rate plus the
   stated points. Both read the primitives already there:
   =curve_instrument_pricer::fra_rate= and
   =day_count_calculator::year_fraction=. Nothing compounds or adds a spread
   in the tree today, so this is the new arithmetic.
3. *The five rows.* One =ir_curve_generation_config= per derived index,
   seeded against the currency's overnight config, with the spread of the
   two spread indices stated and sourced.

*The derived index is a node of the feed graph.* The signed-off design gives
the graph four node kinds — source, upstream, latent, view — and makes a node
the thing that runs, stops, starves and fails. A derived index has an upstream
(the currency's overnight curve node), so it is a *view*: the same kind the
vendor views of a latent surface take, one level down. It is not an `upstream`
node, which is the kind the graph gives every feed without one.

That decision settles four things the current build gets wrong:

1. *It must start and stop like any node.* Its config is already a candidate of
   the curve kind, so it already appears in the graph — as an `upstream` node
   that cannot start, because its build refuses it. It builds a fixing generator
   instead, and the graph states it as a view with a =curve= edge to its driver.
   Its adapter is offered that one address, as every other feed is, so the
   party's subscription is answered and the fixings exist on a fresh provision;
   the graph's halt withholds the offer, which is what stops them when the curve
   stops. Starting the config builds the same node by hand, for a run in which
   no party demands it.
2. *It publishes under its owner.* The value we compute from data we hold is
   published by =derived=, the provider that holds 2,275 computed instruments
   already and that every party is subscribed to. The simulator's fixing
   publisher (=simulated-fixings=) keeps its documented role, stating the
   indices a vendor would otherwise have published; nobody subscribes to it,
   which is exactly why a derived index must not be stated there.
3. *It needs a notation of its own.* =provider_notation= has no entry for
   =derived=, so nothing can mint ids for it. A =derived_notation= states the
   fixing address the way =simulated_fixing_notation= does, under the =derived=
   provider. A provider has one notation and it spells every id that provider
   serves, so the notation reads the source's volatility points too
   (=derived_fx_vol=, =rate_lnvol=, such as =USDCZK/2M/10BF=), not only the
   fixings: the catalogue test reads every installed row of the provider, and a
   notation that knew one family refused the other.
4. *Its instruments and mappings belong to =derived=*, not to
   =simulated-fixings=, so that the party's existing =derived= subscription
   entitles it.

*What a starved node states: nothing.* A derived node whose curve feed stops
publishes no new fixing. It does not repeat the last value, because a repeated
value is a statement about a day nobody observed, and it does not backfill the
days it missed when it resumes: the input stopped, so the output stopped, and
the hole is the honest record. That is what a fixing is — a fact about a date,
stated once. A person who needs a value for a day the platform did not state
enters it by hand, with an explanation, where fixings are adopted for a party's
trades: see [[id:FA5C96A3-1F8E-4F9B-8973-40D92055D7DD][System-level fixing observations and party-level fixings]],
and the fixings manager that owns that act is a separate piece of work. The
provider states what it observed; the party decides what its trades fix on.

One constraint holds throughout: the upstream is the *run's own* curve node,
never a party's published curve, because reading a party's set back would
invert the dependency the approach page forbids.

Deferred to a follow-up task if it costs more than a slice: publishing a
*projection curve* for a derived index. The acceptance of this task asks
for the fixing addresses to answer and for the compounded equality, and
both follow from the board rate alone.

Test: a unit test proves the compounded rate equals the forward implied by
two discount factors of the overnight curve and that the spread form adds
its points; a fresh provision shows the five fixing addresses answering.

* Seeding and the run

The five configs are staged as artefact rows of a dataset of their own,
=synthetic.feeds.derived=, and the dataset publish writes them like every other
generated feed: one collection under the provider =derived=, the folders
=Synthetic > Derived > Rates > IR Curves=, and each config's source name by the
naming scheme, =synthetic.derived.ir.yield_curve.<index>.<currency>.<tenor>=.
Writing the rows by hand was tried first and abandoned: a dataset whose feeds
are not its own artefact rows cannot be republished, and its publish fails
because the collection names no provider.

Two consequences had to be met in the catalogue:

1. *A simulated source of the derived provider.* A feed start looks its
   provider up by its one default simulated source, and =derived= had only the
   stored-data source of FX volatility, =derived-fx-vol=, on the session
   =derived-local=. The simulator's source is now =derived-a=, on
   =synthetic-local=, and it is the provider's default; the stored-data source
   stays, no longer the default.
2. *Its fixings are not the vendor fixings.* The simulated fixings seed writes
   the ids of the indices a vendor would have published. A derived index states
   its own address under =derived=, so that seed leaves derived configs out and
   the derived seed writes them.

*Two sources of one provider, each scoped to its own items.* A route demands
every item of its provider unless its feed is scoped, so a second source under
=derived= was handed all 2,280 ids of the provider and refused them: the smoke
counted 5,816 of 8,096 accepted. Each source now states the items it reads,
=derived-fx-vol= by its scheme and =derived-a= by the fixing address, and the
five fixings are answered by the adapter that serves them.

*Starvation is enforced where the value is stated.* A node is *starved* when
the graph says one of its inputs does not run. The graph is rebuilt whenever a
stop or a start lands, and the fleet now publishes the resulting halted set to
every feed; a derived fixing feed asks it on each tick and states nothing while
it is in the set. The feed itself therefore decides, not the runner: a run
stopped and restarted would restate its history and fill the hole. The unit
test =a_starved_node_states_no_fixing_and_makes_up_no_day= proves the two
halves: nothing is stated while starved, and the day the node was starved
through is absent after it resumes.

The shell gained the graph's node verbs, =synthetic start node <name>= and
=synthetic stop node <name>=, because a stop of a *node* is the one that
starves its dependants and the shell could reach only runs and folders.

* Result

The five term indices are published from a dataset of their own, offered to the
adapter of the derived provider, and state 520 fixings each on a fresh provision
with nobody starting a feed: the run's subscription demands them, and the graph
withholds the offer when the curve they read stops. They are view nodes reading
the run's own overnight curves. The rule, the arithmetic and the seeding all
follow the design recorded above; the hand-written rows the earlier attempt used
are gone.

Starvation is proven twice: the unit test shows that a starved node states
nothing and makes up no day, and a live run shows the same end to end, where
stopping the SOFR overnight curve's node logs the derived node as starved and
adds no fixing to the series.

The local gate is green on everything this branch touches: the build, the
synthetic, shell and market-data suites, the ticks smoke, and every pgTAP suite
but =scheduler_publish_housekeeping_test.sql=, which fails on a fixture of
main's retention work (=Invalid modified_by: system=) and not on this branch.
