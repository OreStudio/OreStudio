* Acceptance

- Events are written when a subscription or route opens or closes and when an instrument enters or leaves a party's demand.
- The fan-out counts deliveries for each party and instrument and writes them in batches with the store write.
- A party administrator reads the party's own events and the system tenant reads all.

* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

1. Model the three events as entities with history and row-level security by party: the subscription interval, the demand interval and the delivery count. None holds a price.
2. Let the system tenant read the events of every tenant, with the widening listed in the register that audits such policies.
3. Plan the intervals as a pure comparison of the state now with the intervals that are open: open what is new, close what ended or changed, leave the rest.
4. Write the intervals after each read of the catalogue, so they cost nothing at tick time.
5. Count deliveries in memory in the fan-out, one addition for each party and item of a batch, and write the counts in batches every 30 seconds and at stop.
6. Test the planner and the meter without a database.

* Result

The service records usage as events, with no price. Three entities hold them, each with history and row-level security by party: the subscription interval, the demand interval and the delivery count. The system tenant reads the events of every tenant, and the widening is listed in the register with its reason. =usage_planner= compares the state now with the open intervals: it opens what is new, closes what ended, and closes one interval and opens the next when the source or the rights change. =usage_recorder= writes the intervals after each read of the catalogue, so they cost nothing at tick time. =delivery_meter= counts the deliveries of the fan-out in memory, one addition for each party and item of a batch, and the recorder writes the counts every 30 seconds and at stop, and puts a count back in the meter when the store does not answer. Fifty-one service test cases pass, including the planner and the meter. The build of the service and the core tests passes.

Left for later tasks:
- The recorder and the count flush were not run against a database, because the worktree =.env= is at version 32.
- A party administrator reads the events through the generated list calls under the party isolation policy. No usage screen exists yet; the screens task builds it.
- The access record, a person viewing the data, is not modelled. The page marks it as later.
- A delivery is counted when the loop publishes it, whether or not the store accepted the tick.
