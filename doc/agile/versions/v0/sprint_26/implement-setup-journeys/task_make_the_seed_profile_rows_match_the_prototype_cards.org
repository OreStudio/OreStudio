* Notes

- *Carried as data.* =summary=, =bullets_json=, the parameter =label= and the
  declared choices are rows, because a new profile must be able to state its
  own card. A label in particular cannot be derived from the parameter name:
  the name is a key a shell command types and the label is a sentence a person
  reads, and deriving one from the other would put English in the code.
- *Bullets as a JSON array.* They are card copy with no identity and no
  lookup, so they are a =jsonb= array on the row rather than a fourth entity;
  =ores.marketdata.observation_lineage.source_series_ids= is the precedent for
  a serialised array column. The read parses it and refuses a value that is not
  an array of strings, because =jsonb= guarantees valid JSON and not a list.
- *A nullable =jsonb= reaches the wire as an empty string.* The generated
  domain member is a plain =std::string=, so a SQL null arrives as =''=: the
  read treats that as "no choices". Found by the live route going red on the
  first attempt, not by a test, which is why the client test now feeds =''=.
- *Two prototype values deliberately not carried.* The prefill hostname stays
  =acme_corporation= and the administrator email stays
  =admin@acme_corporation.com=, because the implemented principal convention is
  =username@hostname= and both the shell recipe and this environment's login
  use that pair; the prototype's =acme_corporation.localhost= and
  =tenant_admin@acme.example.com= have no counterpart in the code.
- *Two prototype fields deliberately not carried.* The logo stays in the image
  store, which the story already decided, and the party list stays provisioning
  output the tenant record holds once the run finishes.
- *The step arguments are unchanged.* The prototype's step lists are the
  progress rail's labels, which the workflow definition owns (step 7); the
  kinds the rows order are the contract's catalogue and already match its
  sequence.
- *The card copy is English in data.* Profile copy is registered data rather
  than i18n keys, so it is not translated by the catalogue that translates the
  screen's own words. That is inherent to "a profile is a row"; translating
  registered copy is its own concern and is not attempted here.

The rows now state the card the accepted prototype draws. Read from
=prototype/first-run-journey=, the two profiles carry the prototype's name,
audience, tagline and bullets:

#+begin_example
Operational    Production-ready setup   For real use
  Standard reference data and counterparties

  parameters: Root LEI (required), Counterparty set (choice small/large,

#+end_example

The model gained what those need: =summary= on the profile (renamed from the
longer =description=, which no screen read), =bullets_json= as a JSON array,
and a =label= and =choices_json= on a parameter, so the form can put a sentence
above the field and offer a choice rather than accept free text. Three columns,
one of them a rename.

The read carries them through unchanged: the composed shape exposes =bullets=,
and each parameter exposes =label=, =choices= and the hint. Both tests assert
the new literal, and the client suite gained a case for a bullet column that is
not a list of strings.

Verified on the live deployment, signed in through the BFF: =GET
/api/seed-profiles= returns the two cards above, in that order. Five C++ suites
pass, the whole workspace typechecks, formats clean and passes 118 tests, the
tree builds, the sweep finds no drift in any file this branch touched, and the
model-drift, SQL-hygiene, protocol-twin, handler-permission, populate-reference
and lint gates are green.

Deliberately not carried, with reasons in =* Notes=: the prototype's prefill
hostname and administrator email (the implemented principal convention wins),
the logo (image store) and the party list (provisioning output). The step
kinds and their arguments are untouched; the prototype's step labels belong to
the workflow definition that step 7 of the story builds.
