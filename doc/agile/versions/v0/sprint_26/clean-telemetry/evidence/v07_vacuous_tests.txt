V07 - Vacuous tests: ores.telemetry
===================================

Standard item
-------------
V07: "No vacuous test. Every test fails when its subject does nothing, so a
test that asserts only a length, a non-throw, a truthiness, or one production
run against another is a finding. Assert a literal expected value."

Verdict rules used
------------------
passes   At least one assertion states a literal expected value (string,
         number, enumerator, named struct field, or a computed expectation
         that a degenerate subject fails). A no-op subject fails the case.
finding  The assertions do not pin a literal expected value and a degenerate
         implementation of the named behaviour satisfies them. Includes:
         size/count without content, non-throw on a void or unobserved
         happy path, bare truthiness, and one production value compared to
         another.
boundary Rejection of malformed, absent, or out-of-range input, or the
         disabled/edge branch of a flag. The expectation is the rejection
         itself and a literal exception type is stated. Not a finding.

Boundary cases and why they are not findings (9)
------------------------------------------------
These assert the rejection of input the subject must refuse. The expected
outcome is the rejection itself, and a literal exception type is stated in
all but one case. A subject that accepted the bad input would fail them.

  boost_severity_tests.cpp

  trace_id_tests.cpp

Two of these are worth a small strengthening, though neither makes the case
vacuous. logging_read_options_throws_on_invalid_level uses REQUIRE_THROWS
where the thrown type is logging_exception, and
validate_throws_on_invalid_severity uses REQUIRE_THROWS where
to_boost_severity throws std::invalid_argument. Pinning the type would state
the literal expectation.

Fixes that need the code under test to change first
---------------------------------------------------
These findings cannot state a literal expectation until the subject gains a
seam.

  logging_options_validator accept cases (5)
    validate() returns void. No assertion can distinguish a real validation
    from an empty body. It must return a result (a status or a list of
    errors) before an accept case can assert a literal.
  database_sink_backend constructor and setter cases (3)
    The backend's only observable output is the telemetry_log_entry passed
    to the handler inside consume(), and the handler is a test lambda that
    the current cases never invoke. Either the cases must build a
    boost::log::record_view and call consume(), or the class needs a getter
    for the stored source, session id, and account id.
  make_forwarding_handler_handles_exceptions
    The swallow path writes to std::cerr. A literal check on the literal
    "[Logging Sink Error]" text needs the error stream to be injectable.
  span_ids_are_time_sortable, trace_ids_are_time_sortable
    Both compare two generator runs. To assert a literal millisecond value
    the generator needs an injectable clock (or a constructor that takes
    one).

The pattern the findings share
------------------------------
The findings are all self-referential: the assertion is derived from the
subject's own output instead of from a value the test author picked. Three
shapes appear.

First, a happy-path call is asserted only to not throw. The subject returns
void (logging_options_validator::validate) or writes through a callback the
test never invokes (database_sink_backend), so an empty implementation
passes. Second, an identifier or context object is asserted through its own
predicate or against another object the same code produced: is_valid(),
is_session(), is_root(), has_value(), a pointer compared to another pointer,
or a round trip. The test proves internal consistency, not a specified
encoding, so a self-consistent but wrong implementation survives. The id
codecs are the clear case: nothing pins a byte to a literal. Third, the
database integration cases use threshold counts (>= 1, >= 2, >= 3) against
a shared database rather than a before/after delta or literal row content,
so a query that returns the wrong rows still passes.

No test in the component is empty or commented out, and the
"produces valid json" and repository query cases do state literal values.
The gap is concentrated in void APIs, in identifier predicates, and in the
repository integration cases.

Judgement calls
---------------
Three verdicts were the hardest.

  span_id_generator_is_thread_safe, trace_id_generator_is_thread_safe
    The only assertion is all_ids.size() == 400, which the standard lists as
    a length-only finding. I marked both passes because the set is filled by
    inserting 400 ids and the size therefore encodes the uniqueness property
    the case claims; a constant generator fails. The case still cannot
    detect a data race, so a reviewer may prefer to flag it.
  parse_help_returns_empty, parse_version_returns_empty
    The absence of a result is a clean boundary, but the printed-output
    check is only non-emptiness. I marked both findings on the strength of
    that check, since a printed newline would pass. A reviewer who treats
    the help and version branches as boundaries may prefer boundary.
