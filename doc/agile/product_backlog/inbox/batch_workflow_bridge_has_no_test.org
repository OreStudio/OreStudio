#+title: The batch workflow bridge has no test
#+description: The bridge's tenant-scoped removal was wrong and no test saw it; add an integration test that writes a link for one tenant, finishes the batch, polls, and asserts the link is gone.

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

=batch_workflow_bridge= is the service-level poller that fires
=step_completed_event= when a batch finishes and then removes the link. It
has no test, and the gap is not theoretical: the success path removed the
link as the service's own tenant while the link belonged to another, the
tenant-scoped DELETE matched nothing, and the bridge republished the
completion event on every poll. A review found it; no test did.

Write an integration test in =projects/ores.compute/service/tests/= that
makes the tenant difference real: seed a batch for one tenant, write a link
for that tenant, build the bridge with the system tenant's context, call
=poll_once()=, and assert the link is gone. A second case should assert
that a link whose batch is still open survives the poll, which pins the
other half of the seam.

* Why

The bridge is the only path from a finished batch back to the workflow that
waits on it, and its failure mode is a loop rather than a crash: the event
repeats forever and nothing logs an error. It is also the seam the G02 note
described, where the read is cross-tenant and the write is tenant-scoped,
which is exactly the kind of asymmetry a test should hold still.
