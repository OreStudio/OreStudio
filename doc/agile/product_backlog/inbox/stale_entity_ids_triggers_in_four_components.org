#+title: Forty generated notify triggers still emit the retired entity_ids payload
#+description: The shared postgres event listener parses every notification as the canonical entity_event_notification and returns on a parse failure, so the 30 refdata, 8 trading, 1 dq and 1 workspace notify triggers that still emit the retired entity_ids payload drop every entity event for those tables. PR 3 regenerated marketdata's six, which is the one component under test; the other four need the same regeneration.
#+type: capture
#+level: cross
#+filetags: :codegen:eventing:sql:
#+created: 2026-09-27
#+updated: 2026-09-27

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Regenerate the notify triggers of =refdata=, =trading=, =dq= and =workspace=
onto the canonical payload. Their committed SQL is behind the template, and
the template moved on 2026-09-21, so every entity event those four
components raise is currently dropped on the floor.

The trigger template now emits the canonical =entity_event_notification=:

#+begin_src json
{ "event_id": "...", "entity": "ores.refdata.account_type", "key": "{...}",
  "action": "created", "version": 1, "occurred_at": "...",
  "correlation_id": null, "tenant_id": "..." }
#+end_src

The committed triggers still emit the retired shape:

#+begin_src json
{ "entity": "ores.refdata.account_type", "timestamp": "...",
  "entity_ids": ["..."], "tenant_id": "..." }
#+end_src

=projects/ores.eventing/core/src/service/postgres_event_source.cpp= parses
every payload as =domain::entity_event_notification= and returns early when
the parse fails. Its legacy branch is unreachable, so a legacy payload
produces nothing: no log line a subscriber can see, no event, no error.

Files still carrying =entity_ids=:

| Component | Files |
|-----------+-------|
| refdata   | 30    |
| trading   | 8     |
| dq        | 1     |
| workspace | 1     |

=marketdata='s six were regenerated by PR 3, which is what makes
=series_classification_rule_eventing_integration_tests= pass: that test failed
3 runs out of 3 against the legacy trigger and passes against the canonical
one, unmodified.

=ores.synthetic= is deliberately not on the list. Its nine committed notify
triggers are already canonical, so nothing there needs regenerating. Its
eventing integration tests did fail during PR 3 — all eight of them — but for
the opposite reason: the restored development database was a day behind HEAD
and still held the legacy function, which
=select prosrc like '%entity_ids%' from pg_proc where proname =
'ores_synthetic_folders_notify_fn'= showed plainly. The committed SQL and the
running database can disagree in either direction, and only one of the two is
a defect in the tree. Worth remembering when a green suite turns red after a
schema restore: check the installed function before the source.

* Why

This is the one defect in the marketdata clean-up whose blast radius leaves
the component. It is recorded rather than fixed here because regenerating
four other components would put their generated trees into a marketdata PR,
and three of those components are being cleaned in other worktrees
(=ores.refdata=, =ores.trading=, =ores.dq=) whose regenerations would then
collide.

Worth doing as a single repo-wide change once those land, because the fix is
identical everywhere and the drift gate can prove it: regenerate, reapply the
schema, and watch the eventing integration tests of each component go green.
