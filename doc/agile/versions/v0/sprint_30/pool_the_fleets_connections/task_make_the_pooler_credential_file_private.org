* Acceptance

- The directory the deploy stages the credential file in is traversable and
  not listable, and the file is readable only by the uid the container drops
  to.
- A local user of the host that is neither root nor that uid cannot read a
  password in the file.
- The pooler still reads it after it drops privileges, proven on a deploy.

* Plan

Three facts decide the fix, and two of them need a live deploy to read:

1. The image creates its own =pgbouncer= user with =adduser -D=, so the uid it
   drops to is the image's, not a fixed number. Read it from the image rather
   than assume it: =podman run --entrypoint sh <image> -c "id -u pgbouncer"=.
2. Rootful podman maps container uids to host uids one to one, so that uid is
   the one to own the file on the host. Under a rootless deploy the mapping
   moves, and the same rule has to be stated in terms of the mapped uid.
3. =write_config= writes the users file =0644= today and the comment claims
   the directory keeps it private. =mkdir -p= and =scp -r= use the umask, so
   the claim is not true.

The shape:

- The staged and remote directory becomes =0711=: traversable, so the
  container's root can reach the file, and not listable, so a local user
  cannot even see the names in it.
- The file becomes =0600=, owned by the uid read above.
- A test or a gate check asserts the modes the deploy leaves behind, so a
  later change to the staging path cannot quietly widen them.
