* Goal

Stop the FX services reading one row per key when the repository already offers
a batch read. Each of the seven services has three such loops: the =get_many=
lookup, the =put_many= precondition check and the =put_many= read-back. The
repository's batch read is a single query, and the services do not use it on
these paths.

The shape is seven of seven services, so the fix is a component decision, not
an FX one. The family is where it lands first.

* Acceptance

- No FX service issues a per-key read on a path that reads a collection. The reply stays positional: one entry per requested key, in the order asked for.
- A =put_many= call reads the written set once, not once per element.
- The decision — shared service base, codegen template, or per service — is recorded, with the reason.
- The same defect is reported on the other components the base or the template reaches, so it is fixed once, not seven times.

* Plan

The service implementation is generated from =cpp_service.cpp.mustache= and
=tangle= reproduces it from =ores.cpp.service.service_impl.org=, so a hand edit
to the seven services is overwritten on the next regeneration and the drift
gate refuses it. The unit is therefore a template change, gated per entity so
the other components' services stay byte-identical until their own unit:

1. Add a section to the service template's anonymous namespace, rendered only
   when the entity opts in, that indexes a batch read's rows by the trade id
   they carry.
2. Render =get_many= and =put_many= through one =repo_.read_latest(ctx, keys)=
   call when the entity opts in, and keep the per-key loop otherwise.
3. Set the opt-in flag on the seven FX models, regenerate the trading
   component, and confirm no other component's service changed.
4. Assert the positional reply: a request whose middle key is absent still
   answers one entry per key, in the order asked. A service-level test needs
   the database harness the repository tests already use.

1. Read the generated service template and count the loops the whole component carries, not just the FX ones.
2. Decide the seam. A shared base or the template is preferred, because the defect is in the generated shape.
3. Land the change and regenerate.
4. Run the trading suite, then the other components' suites the template reaches.

* Result

The seven FX services answer a key set in one database read. Each =get_many=
calls =repo_.read_latest(ctx, keys)= once and joins the rows back to the order
asked for, and each =put_many= reads the batch it just wrote in one statement
rather than one per row. A caller sees the same positional reply, so an absent
key still answers an empty entry in its place.

The fix is in the service template, because the services are generated. A new
per-entity flag, =:service_batch_reads:=, renders the one-read path; the rest of
the template is unchanged, so the other thirty-one trading services regenerate
byte for byte and no other component changes. The flag is set on the seven FX
models only, because the batch path reads the row's =identity.trade_id=, which
is the key those entities declare.

* Decisions

- *The lever is the template plus a per-entity flag, not a shared service base.*
  The batch path needs the entity's key expression, which the template already
  holds per entity. A base class would have to be told the key, and the
  repository read is already generic.
- *The flag is named for what it turns on, not for the family.* Any entity keyed
  by its trade id can set it; the FX family is the first because that is where
  the audit found the reads.
- *The reply stays positional.* The obvious alternative, dropping absent keys,
  would make a caller match entries to keys by position on the wrong list.
