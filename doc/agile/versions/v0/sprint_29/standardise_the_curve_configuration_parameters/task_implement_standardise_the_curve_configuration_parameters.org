* Goal

The work that follows the documentation task, and it owns the rest of the story. The curve section metadata moves into data, each documented term is linked to its value set, the page draws a curve's leaves with the shared leaf parts, and the write path checks a value against its set. It also corrects the entity docstrings that call these leaves *settings*, since that word belongs to the engine run settings.

* Acceptance

- The curve sections and their entry elements are read from the curve_section data, so no screen holds a table that names them.
- Each documented leaf is linked to its value set, and the write path refuses a value outside it, so every client gets the same answer.
- A curve definition's leaves are drawn with the shared leaf parts: the Simple and Advanced switch, the documentation panel, the value in force and the control its value set gives.
- The curve configuration page follows the configuration screen standard: Details, one tab per section in the declared order, Used by and History, with a curve entry drawn as a collection row.
- The =yield_curve_config= and =curve_definition= docstrings call these leaves by the story's word, not *settings*.

* Notes

- *The docstring correction is done, and it is a cross-layer regeneration.*
  =yield_curve_config= and =curve_definition= described their leaves as
  *settings*, the word reserved to the engine run settings. Correcting the two
  models regenerates the C++ domain headers, the refdata and dq create scripts,
  and the ER diagrams. The diagram run also picked up drift from merges after
  this branch's base, so diagrams the change does not concern move with it;
  leaving them stale keeps =er-diagram= red.
- *Two of this task's original items are already delivered.* The value sets were
  carried by [[id:52535EEC-CB9C-4ECF-A9EB-C2F186B2677D][their own task]], and the curve sections have been in the
  =curve_section= data since before this story, so the page reads them rather
  than restating them. What is left is the page and the write check.
