* Goal

Decide -- and record the decision -- on the ~20 hand-crafted trading
instrument sub-types (bond, every equity_* variant, every fx_*
variant, commodity, composite + composite_legs, credit, scripted,
swap_legs) that carry =workspace_id= in SQL but have no codegen model
at all: bring them under codegen (large, separate effort) or
explicitly accept them as permanently hand-crafted and move on.
Either way, verify their hand-written repository/service code
actually filters by =workspace_id= correctly today.

(=book=/=portfolio= were originally scoped into this task too, on the
mistaken belief they lacked =has_workspace_id=. They don't lack it --
both inherit it from the =fk-scoped-child= profile, and were
regenerated/verified with the inheritance-query fix in PR #1846. See
the audit task's correction note.)

* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

Decision: bring the ~20 hand-crafted trading instrument sub-types
under codegen (per explicit direction), rather than accept them as
permanently hand-crafted. Piloted with =equity_position_instrument=
(smallest by hand-crafted domain-struct line count) to prove the
model authoring pattern and find any template gaps before rolling
through the rest.

Pilot steps:
1. Author =projects/ores.trading/modeling/ores.trading.equity_position_instrument.org=
   using the modern primary-key format (=:primary_key: true= column
   property, not the legacy top-level =* Primary key= heading that 70+
   other models still use -- tracked separately as task 836BB4CE),
   with =instrument_identity=/=audit_record= field-group nesting,
   explicit =party_id_from_session=, =Insert trigger/Validations=, and
   =SQL/Checks=+=SQL/Indexes= tables to reproduce the exact hand-crafted
   SQL semantics.
2. Regenerate =ores.sql.schema=, =ores.cpp.domain=, =ores.cpp.repository=:
   zero-diff against the hand-crafted files except genuine, systemic
   template improvements that apply to any entity regenerated today
   (workspace_id FK validation, =clock_timestamp()=, cosmetic
   include-guard naming, additive doc comments).
3. Regenerate =ores.cpp.generator=: **hard build failure** --
   =no member named 'version'/'tenant_id'/'workspace_id'/'instrument_id'=.
   Root cause: the generator facet template
   (=ores.cpp.generator.generator_impl.org=) had never been updated to
   support the identity/audit field-group nesting mechanism
   (=domain_identity_group=/=domain_audit_group=) that the
   domain/entity/mapper templates already implement -- it unconditionally
   emitted flat =r.{{name}}= regardless of grouping. This entity is the
   first to ever exercise the generator facet against a field-group-nested
   model that can actually be regenerated (every prior identity-grouped
   entity, e.g. =fra_instrument=, is permanently blocked from
   regeneration by the unrelated legacy-primary-key bug, task 836BB4CE,
   so the gap was never caught). Fixed by adding conditional
   =identity.=/=audit.= Mustache prefixes throughout the scaffolding
   block, the per-column loop, and the audit-fields block.
4. Rebuilt: **second build failure** in the repository layer's debug
   log line (=v.instrument_id= inside =BOOST_LOG_SEV=) and the service
   layer's nil-check (=v.instrument_id.is_nil()=, =e.instrument_id.is_nil()=).
   Root cause: primary-key columns live in a separate
   =primary_key= dict in core.py (not the =columns= list), so the
   =is_identity_group_column= flag set on ordinary columns never reached
   primary-key fields. Fixed in =core.py= by also flagging the
   =primary_key= dict and its =columns= list, and updating
   =value_log_fields= to respect it; fixed the two service-template nil
   checks (=save_X=/=save_Xs=) the same way.
5. Rebuilt again: **third build failure**, this time from a hand-crafted
   integration point (=trade_handler.hpp=) calling
   =svc.get_equity_position_instruments(ids)= -- a batch-get wrapper the
   repository layer already supports (=has_batch_read=) but the service
   template never generated (a genuine, pre-existing template gap, not
   caused by this pilot -- =fra_instrument_service.cpp= carries the same
   method by hand because it can never be regenerated to prove it).
   Fixed by adding a =has_batch_read=-gated batch-get method to
   =ores.cpp.service.service_header.org=/=service_impl.org=.
6. Full project build green; =ores.trading.{api,core,service}.tests=
   100% pass; full =ctest= suite 71/71 test binaries pass (one
   pre-existing, unrelated failure in
   =ores.marketdata.core.tests= from a live DB schema drift --
   confirmed zero diff in any marketdata file, not caused by this work).
7. Verified zero further drift: re-ran every regenerated address a
   second time and diffed -- byte-identical output (plus the expected
   additive =component_files.cmake= sync).
8. Deliberately did **not** generate the entity's messaging/eventing
   facets (=ores.cpp.nats-handler=/=nats-event-registrar=/etc.): a
   whole-component drift-check run surfaced them as generatable, but
   none of the sibling trading instrument sub-types (e.g.
   =fra_instrument=) carry them -- they're dispatched instead through
   hand-crafted, category-level handlers
   (=equity_position_instrument_handler.hpp= et al. already existed
   for the *category*, not per-concrete-subtype). Generating
   per-entity messaging files would have introduced a second,
   inconsistent NATS-dispatch mechanism alongside the established one.
   Scope stayed at domain/entity/mapper/repository/service/generator/SQL,
   matching every other instrument sub-type.

Net effect: three genuine, systemic template/codegen-core bugs found
and fixed (generator field-group nesting, primary-key
identity-group-flag propagation, service-layer batch-read gap) --
all three affect every current and future identity/audit-grouped
entity, not just this one. This significantly de-risks bringing the
remaining ~19 entities under codegen: the pattern is proven and the
three blockers a first mover would have hit are gone.

* Result

Decision recorded: bring the ~20 hand-crafted trading instrument
sub-types under codegen. Piloted end-to-end with
=equity_position_instrument=: model authored, all facets
(SQL/domain/entity/mapper/repository/service/generator) regenerated
zero-diff (beyond genuine systemic template improvements), full
project build green, =ores.trading.*= tests 100% pass, full repo
=ctest= 71/71 test binaries pass (one pre-existing, unrelated
=ores.marketdata.core.tests= failure from live DB schema drift, no
diff in any marketdata file). Re-regenerated every address a second
time to confirm zero further drift.

Three genuine, systemic codegen bugs found and fixed along the way
(none specific to this entity -- all three affect every
identity/audit-field-group-nested entity, past and future):
1. The generator facet template
   (=ores.cpp.generator.generator_impl.org=) never implemented
   identity/audit field-group nesting -- flat =r.{{name}}= regardless
   of grouping. Fixed with conditional =identity.=/=audit.= prefixes.
2. Primary-key columns live in a separate dict in core.py, so the
   =is_identity_group_column= flag never reached them -- the
   repository's debug-log line and the service's nil-checks referenced
   a flat field the identity-grouped domain struct no longer has.
   Fixed by flagging the =primary_key= dict too and updating
   =value_log_fields= and the two service-template nil checks.
3. The service facet never generated a batch-get wrapper despite the
   repository supporting it (=has_batch_read=) -- a hand-crafted
   integration point (=trade_handler.hpp=) expects every instrument
   service to expose one. Added a =has_batch_read=-gated
   =get_{{entity_plural_short}}= method to the service templates.

Scope deliberately excluded messaging/eventing facets: none of the
sibling trading instrument sub-types carry per-entity generated NATS
dispatch (they're handled through hand-crafted, category-level
handlers instead) -- generating them here would have introduced a
second, inconsistent dispatch mechanism.

Closing this task now that the decision is made and proven. A
follow-on task tracks converting the remaining ~19 entities, now
considerably de-risked since the pattern is proven and the three
blockers a first mover would hit are already fixed. Most of the
remaining entities also need task 836BB4CE (legacy Primary key
heading) resolved or worked around per-entity, since they use that
older model format.
