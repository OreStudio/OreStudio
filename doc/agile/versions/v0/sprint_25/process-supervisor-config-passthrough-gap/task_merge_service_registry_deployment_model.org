#+title: Task: Merge service deployment config into service_registry.org as a new aspect
#+description: service_registry.org currently models only DB-access aspects per service (psql_var, env_key, iam_role, DML/select/execute grant prefixes), keyed by short names (iam, refdata, ...). Extend it in place to also carry a deployment aspect per service (replicas, enabled, description, depends_on, and an optional Extra args list of genuinely per-service CLI flags), one heading per fleet process the systemd generator needs to know about. Rename headings to full binary names (ores.iam.service, not iam) since that is the join key compass systemd generate actually needs (TLS cert/key filenames, unit basenames). Add the 3 processes that have no DB role (ores.http.server, ores.wt.service, ores.compute.wrapper) as deployment-only entries (no psql_var/iam_role/etc.), and drop the stale controller entry (no binary exists for it anymore). Extend org_loader.py's load_org_service_registry_model to parse and return the new deployment fields alongside the existing DB-grant fields. This is a pure model+parser change -- no consumer (systemd_generate.py, the SQL grant generator) is touched in this task, so it is safely reviewable in isolation as long as both aspects round-trip correctly.

  discriminator for "is this a real service entry" moved from

  comma-split), and extra_args (list, one per == Extra args== bullet)

  9 tests covering both aspects' presence/absence, replica counts,

  dropped controller entry, the total count (19), and that the
  pre-existing DB-grant-prefix parsing still round-trips correctly.
- Deliberately did not touch systemd_generate.py or any other consumer
  in this task -- it still queries postgres as before. That migration
  is the next task in the chain (wire_systemd_generate_to_codegen_model).

* Result

service_registry.org now models each of the fleet's 19 processes as one
entity with two independent optional aspects: DB access (present for the
16 with their own NATS-domain-service role) and deployment (present for
all 19). Headings renamed to full binary names, the stale controller
entry dropped. load_org_service_registry_model extended to parse and
return both aspects; verified via a scratch script and 9 new pytest
cases (all pass), plus the full existing ores.codegen suite (117/117
green) confirming no regression to DB-grant generation.

Review caught that "no consumer touched" was too strong a claim: two
consumers not named in the original description would have broken --
env_init.py's independent regex-based heading parser (fixed to route
through org_loader.py instead), and 5 SQL/shell mustache templates that
unconditionally referenced fields the 3 new DB-less entries don't have
(fixed with a filtered+re-marked service_registry_db_services list and
a computed short 'component' field in core.py). Verified both fixes by
regenerating the real downstream artifacts and diffing against what's
committed -- confirmed byte-identical except for the stale controller
entry disappearing -- then deliberately did not commit the regenerated
artifacts themselves, since doing so would have silently discarded an
unrelated, legitimately hand-added grant (PR #1758) the templates have
no construct to represent; regenerating+committing that is out of scope
here and belongs with whoever next touches that grant's own model gap.

systemd_generate.py itself remains untouched and still queries postgres
-- migrating it is the next task in the chain.
