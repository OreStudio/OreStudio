PR 3, the model-authoring pilot: commodity_instrument

Measured 2026-09-27 on feature/model-missing-trading-families, with the
tree at 06aa8f3a80.

What was done
-------------
One focused pass authored the missing model for the commodity instrument
family from four sources: the table
=projects/ores.sql/create/trading/trading_commodity_instruments_create.sql=
for its forty columns, indexes and checks; =equity_position_instrument.org=
for the format, since it is an instrument sub-type of the same kind; the
hand-written domain type for the field groups and the C++ type behind each
column; and the loader for any property whose spelling was in doubt.

The model is parked beside this file as =pr3_commodity_instrument_model.org.txt=,
four hundred and fifty lines, binding =:profile:  trading-instrument= like
its nine modelled siblings. It is not committed under
=projects/ores.trading/modeling/= because a model may not land without its
regeneration, and the regeneration is not finished (see below).

What the regeneration does
--------------------------
Running the in-place regeneration with the model in place changes
twenty-one existing files and creates thirteen. The twenty-one are the
hand-written stack, which becomes generated: the domain type, JSON I/O,
table and table I/O, the entity, mapper, repository and service, the
handler and the event registrar, the create and notify-trigger scripts and
the drop script.

The domain type is the significant change. Today it is decomposed into
=commodity_terms=, =commodity_option=, =commodity_pricing= and
=commodity_exotic= sub-structs, reached as =v.terms.=, =v.option.= and so
on. The model converges it to the canonical shape its nine modelled
siblings already have: =instrument_identity= plus flat optional blocks.

So the model cannot be committed on its own. The drift gate requires the
regeneration, and the regeneration changes the shape a consumer reads.

The consumer surface, measured
------------------------------
Four files read the nested shape and move with the model:

- =projects/ores.ore/service/src/messaging/ore_import_execute_handler.cpp=
- =projects/ores.ore/core/src/domain/commodity_instrument_mapper.cpp=
- =projects/ores.ore/core/tests/xml_commodity_mapper_roundtrip_tests.cpp=
- =projects/ores.shell/application/src/app/commands/trading/commodity_instrument_commands.cpp=

Nothing else in the tree references the nested types by name, and no other
file reads =.terms=, =.pricing= or =.exotic= in a commodity context.

What this means for the other seven
-----------------------------------
=composite_instruments=, =credit_instruments= and =scripted_instruments=
are instrument sub-types and take the same model, regeneration and consumer
migration. =composite_legs= and =swap_legs= are children over the same
scope, and =activity_types= and =fpml_event_types= bind =simple-lookup=
instead. =product_type= waits for PR 4, which owns its shape (defect 10).

Authoring the model is the cheap part: one pass, from sources that are
already in the tree. Migrating the consumers and proving the regeneration
is the work, and each family carries its own two to four consumers.

How to resume
-------------
Move the parked model back to
=projects/ores.trading/modeling/ores.trading.commodity_instrument.org=,
run =check_component_drift.py --component trading-cpp= without =--dry-run=,
migrate the four consumers above, regenerate the trading source lists,
build, run the trading suites and the ORE suites, and require the drift dry
run to be empty. Then repeat for the remaining six table-backed models.
