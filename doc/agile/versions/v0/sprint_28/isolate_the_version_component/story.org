* Goal

Know which commit produced a running binary, without a commit changing
any compiled artifact.

* Acceptance

- A commit changes no compiled file, so the build after a commit relinks
  no target.
- A running service, the shell and the web server report the commit that
  produced them, wherever they run.
- The same mechanism serves a local build, a package and a deployed
  image.
- A missing or unreadable manifest degrades to the release version with a
  clear marker. It never stops a service starting.
- The relink set a commit causes is measured before and after.

* Design

Agreed 2026-10-14.

** Nothing is embedded in a binary. =version.cpp.in= loses
=@ORES_BUILD_INFO@=. =version.hpp= keeps only the release numbers and the
platform triplet, which change at release time, not per commit. Nothing
compiled changes when a commit lands, so the relink set is empty.

** A manifest carries the fast-changing facts. A JSON document written at
build time:

#+begin_src json
{
  "format": 1,
  "version": "1.8.17.0",
  "commit": "bdf73e1d24",
  "commit_full": "bdf73e1d24...",
  "dirty": false,
  "branch": "main",
  "built_at": "2026-10-14T11:06:00Z",
  "triplet": "x64-linux",
  "checkout_label": "brave_hopper"
}
#+end_src

A build step writes it rather than =configure_file=, so regenerating it
costs one file write and recompiles nothing.

** Lookup order, first hit wins:

1. =$ORES_VERSION_MANIFEST=
2. =version.json= beside the running executable
3. =usr/local/share/ores/version.json=
4. =etc/ores/version.json=

Resolving "beside the running executable" reuses the existing
=ores.platform::process= executable path, so =ores.version= depends on
=ores.platform=. Checked: no library cycle, because =ores.platform='s
library does not link =ores.utility=.

** Why each target works. A local build writes the manifest into
=publish/= next to the binaries. A package and a deployed image copy
=publish/= wholesale, so the manifest travels with the binary and the
executable-relative lookup finds it without knowing the working
directory.

** Reading it. =ores.version= reads and caches the manifest once, so the
file is not read per call. =build_info()= returns the commit;
=full_version_string()= and =format_startup_message()= keep their shape.

** No signing yet. This is a development traceability mechanism, so the
manifest binds to nothing and a stale manifest beside a new binary is
possible. Signing, and binding the artifact digest into the manifest,
are deferred.

* Decisions

- Nothing is embedded in a binary; a manifest is the only carrier of the
  commit. Chosen over a linker-owned stamp and over
  =LINK_DEPENDS_NO_SHARED=, which cannot be scoped to a single dependency
  and would blunt ABI-change detection for every shared library of a
  target it is set on.
- The manifest is not signed yet. It is for development traceability.
- The manifest is JSON because the reader is C++ and the writers are a
  build step and a packaging step.

* Out of scope

- Signing the manifest, and binding the artifact digest into it.
- =LINK_DEPENDS_NO_SHARED=. Considered and rejected for this work.
- The wider observation that relinking dependents of a changed shared
  library is not required for correctness, so most of the 179 relinks are
  wasted work. Worth a separate decision.
