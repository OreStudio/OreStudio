This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Take the first usage sync off the path to "Service ready", or write its intervals
in one batch, so the market data service starts within its 90-second start limit
on a fresh database.

* Why

=ores.marketdata.service= sends its ready notice only after
=usage_recorder::sync= has run once. On a fresh database that sync opens about
2,700 demand intervals, and it writes them one row at a time, each with its own
event. On 2026-11-16 two of three starts on a fresh database ran past the limit.
systemd killed the service, and the =ores.marketdata.official= unit, which
requires it, failed with "Dependency failed". The restart read 2,707 open
intervals, opened none, and was ready in under two seconds, so the first start
had done the work and was only slow. =compass services start= then reports one
unit that did not start, and any chain that follows it stops.

The same first sync also logs a duplicate key on
=subscription_intervals_party_id_provider_code_inte...= for the system tenant.
That error does no harm: the next sync finds the row.
