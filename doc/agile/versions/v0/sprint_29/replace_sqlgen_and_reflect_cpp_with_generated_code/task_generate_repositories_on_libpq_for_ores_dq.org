* Acceptance

- The repository, entity and mapper templates emit no sqlgen code.
- ores.dq's repositories keep their interface; no caller changes.
- Each read is one round trip; no cursor.
- ores.dq's suites pass, and the generated code builds as a unity build.

* Plan

Match sqlgen first: the move changes the library, not the behaviour.

1. A light query builder in =ores.database=, =ores::database::q=, with the
   names the repository templates used with sqlgen: =read=, =where=,
   =order_by=, =limit=, =offset=, =delete_from=, =insert=,
   =insert_or_replace=, the list-filter conditions and the =execute_*=
   helpers. It writes the SQL sqlgen wrote, binds every value as an untyped
   text parameter the server types from its use as it typed sqlgen's
   literals, prepares a fixed statement once per connection and runs a
   varying one unnamed, and raises the same =repository_exception=.
2. A text mode on the layer, so a repository reads text into the entity
   sqlgen filled and the mapper is unchanged.
3. The bridge: one libpq pool shared by every copy of a context.
4. A component chooses its backend with =#+repository_backend: libpq=. Its
   repository source comes from a new archetype, the sqlgen one with its
   namespace swapped; its entity drops the sqlgen key and timestamp
   spellings and states its columns; its mapper reads the key without
   =.value()=.
5. Move =ores.dq=, port its hand-written sqlgen code, and run its suites and
   those of every component that reads its repositories.

* Notes

** Why a query builder and not generated statements

The analysis story chose generated statements. Matching sqlgen first is
cheaper and safer with a builder that keeps sqlgen's names: the 1,800-line
repository template moves by a namespace swap, and its Python-built query
fragments are unchanged. The builder is runtime SQL from fixed shapes, light
to compile, and a fixed shape is still prepared once per connection. Typed
binary rows and generated statements follow once sqlgen is gone, in
[[id:551DA90D-4457-4CA2-9617-B18C5FDAEDBF][Read and write typed binary rows in the generated repositories]].

** What else moved

- The one hand-written dq repository, dataset dependencies, and the fsm state
  read by machine name, pasted from its model, now use the builder.
- An entity with a write observer cannot move yet: the builder refuses it at
  compile time. Only ores.trading has observers.
- The service template emitted an unprefixed =refuse_direct_write= in every
  gated entity's service. #3923 renamed it in two generated services, which a
  regenerate would undo; the template now names it for its entity.

* Result

=ores.dq= runs on the libpq layer. Its repositories are generated by a new
archetype through the =ores::database::q= query builder, which writes the SQL
sqlgen wrote and runs it on the layer; its entities and mappers carry no
sqlgen spelling, and its repositories kept their interface, so no caller
changed. Any component moves by stating =#+repository_backend: libpq=.
