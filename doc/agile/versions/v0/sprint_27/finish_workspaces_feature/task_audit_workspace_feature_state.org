**** Correction (found while landing the inheritance-query fix, PR #1846)

The first pass of this audit claimed =book=/=portfolio= "neither
declares =has_workspace_id= nor the profile" -- *wrong*. Both declare
=:profile: fk-scoped-child=, and that profile's own Assignments table
(=projects/modeling/variability_fk_scoped_child.org=) sets
=has_workspace_id: true= as a default every adopting entity inherits
without repeating the flag in its own file. The original audit only
grepped for the literal string =has_workspace_id= directly in entity
files and for the =workspace-scoped-lookup= profile by name -- it
never checked what *other* profiles supply as defaults. CI's
=refdata-codegen-drift= check caught this correctly when the
inheritance-query template fix (PR #1846) regenerated =book=/
=portfolio= with the new resolution-chain logic and the checked-in
files (generated before the fix, but still =has_workspace_id=-active)
didn't match. Both are now correctly counted as covered, and were
regenerated/verified as part of that PR -- no separate backfill task
needed for them.

*** The 23 uncovered tables

~20 =ores.trading= instrument sub-types (bond, every equity_* variant,
every fx_* variant, commodity, composite + composite_legs, credit,
scripted, swap_legs) -- *no codegen model file exists at all*
(confirmed: no matching =.org= under =projects/ores.trading/modeling/=).
These are entirely hand-crafted C++ across domain/repository/service/Qt,
independent of workspace specifically -- a pre-existing "not yet
brought under codegen" gap that happens to also carry =workspace_id=.

** Qt layer: no per-entity codegen flag exists -- and none is needed

Checked every Qt template (=cpp_qt_*.mustache=) and the domain/
repository/mapper/generator templates for any =workspace_id=/
=has_workspace_id= reference. *Zero Qt templates reference workspace
at all.* This initially looks like the gap the user's "much like page
support" framing anticipated -- but it isn't, once the actual
architecture is understood:

Unlike pagination (which needs per-entity generated UI: page
controls, row-count labels), workspace scoping is injected
*transparently* at the network layer via a single shared mechanism
(documented in
=projects/ores.workspace/core/modeling/multi_workspace.org=):
=WorkspaceContext= on the Qt session -> =EntityController='s MDI-area
event filter -> =ClientManager= injects the =X-Workspace-Id= NATS
header on every request. No entity-specific Qt code is needed for
scoping to apply; every generated (or hand-crafted) Qt widget that
goes through the standard =ClientManager= call path is already
workspace-aware for free. The workspace chip/badge in window titles
is likewise a shared mechanism in
=EntityController::show_managed_window()=, not per-entity generated
code.

*Conclusion*: there is no missing "workspace widget" codegen flag to
build. The per-entity thing that actually needs =has_workspace_id= is
the *service/repository query layer* (so the =WHERE= clause actually
filters by workspace) -- which already exists as a flag, just under-
applied (see the 25 uncovered tables above).

** The inheritance feature does not actually work yet, for any entity

The =has_workspace_id= repository template
(=cpp_domain_type_repository.cpp.mustache=) generates an *exact-match*
predicate:

#+begin_src cpp
where("workspace_id"_c == wid && "valid_to"_c == max.value())
#+end_src

Not the resolution-order/inheritance query the architecture doc
describes as the target design
(=workspace_id = ANY(:resolution_order)= with =DISTINCT ON=
deduplication). The architecture doc itself flags this
(=multi_workspace.org=: "Phase 2 repositories currently use an
exact-match... Phase 5 will upgrade these"), but Phase 5 was never
done -- confirmed by reading the template directly, not just the doc.

*This means the single-parent inheritance chain -- the headline
feature of the whole workspace design (a child workspace transparently
sees its parent's data) -- does not work for any codegen-generated
entity today.* A workspace with a parent only sees its *own* local
rows; nothing falls through to the parent. This is arguably the single
biggest gap found in this audit, bigger than any per-entity coverage
gap, because it affects every one of the 21 already-covered entities
equally.

* Result

Audit complete. Headline findings (full detail in =* Notes=):

1. Of 46 production tables carrying =workspace_id=, 21 have real
   codegen coverage (13 via the raw flag, 8 via the
   =workspace-scoped-lookup= profile) and *25 do not* -- including two
   entities (=book=, =portfolio=) that have codegen models which
   simply never got the flag added, and ~20 trading-instrument
   sub-types with no codegen model at all.
2. There is *no missing Qt codegen flag to build* -- workspace scoping
   is already generic/shared at the network layer
   (=WorkspaceContext=/=EntityController=/=ClientManager=), unlike
   pagination. The "much like page support" framing doesn't apply to
   the Qt layer; it applies to the service/repository layer, where
   =has_workspace_id= already exists as a flag but is under-applied
   (finding 1).
3. *Biggest finding*: the =has_workspace_id= repository template
   generates an exact-match =workspace_id == wid= predicate, not the
   resolution-order/inheritance query
   (=workspace_id = ANY(:resolution_order)=) the architecture doc
   describes as the target design. Single-parent inheritance -- the
   headline feature of the whole workspace concept -- does not
   function for any entity today, codegen-generated or not.
4. The three known open codegen tasks are all still valid and
   orthogonal to what this audit found; none of them cover the
   book/portfolio backfill, the trading-instrument coverage decision,
   or the inheritance-query upgrade. Two new follow-up tasks filed for
   these (see parent story's Tasks table).
