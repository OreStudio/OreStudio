#+title: Synthetic feed graph
#+description: The synthetic feeds as a graph of named nodes and stored edges: how each node's state and reason are kept and passed down the edges, how a node is stopped, and where its messages live.
#+type: knowledge
#+level: cross

* Summary

The synthetic market is a graph: a vol surface depends on a spot and two
curves, and each vendor's quotes depend on that surface and on the vendor's
simulated source. Today those dependencies are real but unstated, reached
through the run's market board, so no screen can show them and a stop says
nothing to what depends on it. This page designs the graph as data: named
nodes, stored edges, a state with a reason for every node that flows down the
edges, a stop for every node, and a message log for every node. Its names
follow [[id:90D85E90-E7EA-48D8-9245-313ECA3F9392][Synthetic feed naming scheme]]. The owner signed the five
choices below off on 2026-11-22, each as recommended, as recorded on
[[id:46546EEB-580D-4C37-9398-422D3A18D692][the task]] that designed it.

* Detail

** The nodes

A node is anything that runs and can be stopped. Every node is named by the
naming scheme, and the name is its identity in the graph, in its message log
and on the screens.

| Kind | What it is | Stored as | Example name |
|------+------------+-----------+--------------|
| upstream | one vendor's own path for a spot or a curve | an FX spot or IR curve feed row | =synthetic.bloomberg.fx.fx_spot.audusd= |
| latent | the one hidden vol market of a pair, published by no vendor | a vol surface feed row, under the =latent= source | =synthetic.latent.fx.fx_vol_surface.audusd= |
| view | one vendor's noisy quotes of a latent surface | a contributor link row | =synthetic.bloomberg.fx.fx_option.audusd= |
| source | a vendor's simulated source, the adapter every one of its feeds publishes through | a source of the market data catalogue | =bloomberg-a= |

The source is a node because a view publishes through it: a stopped source
stops its views, as it already stops its own spots and curves.

** The edges

| From | To | Role | Today |
|------+----+------+-------|
| latent | upstream spot | =spot= | stored: =spot_oresmd_uri= and =spot_provider_code= |
| latent | upstream curve | =base_curve=, =quote_curve= | found by a rule: the collection's curve of the currency that is not a projection and has no tenor |
| view | latent | =surface= | stored: the link's =feed_id= |
| view | source | =source= | derived: the catalogue source of the contributor's provider |
| upstream | source | =source= | derived: the catalogue source of the provider of the feed's collection |

A feed's collection is the market data generation config it belongs to, which
stands for one provider. The two source edges stay derived after this design:
the provider is stored on the collection and on the contributor, and the
catalogue maps a provider to its simulated source, one source for each provider
today. Choice 1 stores the edges that were found by searching the feeds; these
two are a lookup of a stored key, not a search.

** The states, and how they pass down the edges

| State | Means | Reason it carries |
|-------+-------+-------------------|
| running | publishing, or for a latent surface, stepping | |
| stopped | an operator stopped this node | who, when and why |
| starved | an input is not running | the input node, and that node's own reason |
| failing | the node runs but cannot produce | the diagnostic, such as =no market: curve:USD= |

The rule: a node runs when it is not stopped and every input runs. Otherwise
it is stopped if an operator stopped it, starved if an input does not run,
and failing if it runs but its last attempt produced nothing. A starved node
names the input that starved it, so the chain reads back to the first cause.
Starting a node clears its own stop; the nodes below it recover when all their
inputs run again, with no action of their own.

- *Precedence.* A node has one state, the first that holds of stopped,
  starved, failing and running. A stopped node whose input also stops stays
  stopped and keeps its own reason; its log records the starve as well.
- *A failing input starves.* A failing node produces nothing, so for the nodes
  below it it does not run: they are starved, and name it. A surface that
  fails on =no market: curve:USD= starves its views.
- *The graph has no cycles.* Every edge points from a node to a kind that comes
  before it: a view to a latent surface and a source, a latent surface to its
  upstreams, an upstream to its source, and a source to nothing. So a change
  walked down the edges ends.

** How a starved state reaches the value

A state derived from the graph is a statement about the run, so a node whose
offers are withheld publishes nothing, because the demand that started it is
withdrawn with the offers. That covers every feed the market data service
demands. It does not cover a node a person starts by hand, which no demand
withdraws, and a node that reads another node's value rather than copying its
offers: a derived term index states its fixing from the curve its input
publishes, and the board keeps the last value an input wrote after that input
stops. Such a node would publish a rate for a day nobody observed.

The halted set is therefore published to the feeds as well as applied to the
offers. Every graph rebuild -- a stop, a start, a restart -- writes the set of
nodes that are not running into one place, and a feed that reads another
node's value asks it on each tick and states nothing while its own name is in
it. The decision sits inside the feed rather than in the runner, because a run
that were stopped and started again would restate whatever history it states
on its first tick, and fill the hole the starve left. A feed that keeps running
and says nothing keeps the hole.

A derived term index is the case that made this necessary: its curve's node
stopping starves it, and the fixings it does not state for those days stay
absent when the curve returns, because a fixing is a fact about a date and not
a value to repeat. Such a node is offered to its adapter like every other, so
the demand that answers a party's subscription is what carries it, and the
withdrawn offer is what stops it while the graph says it does not run; the
guard inside the feed covers the run a person started by hand, which no demand
withdraws.

** The choices, signed off

*** How the edges are stored

- /Option A, typed columns on the dependent node./ A latent surface carries
  its spot, its base curve and its quote curve as columns; a view carries its
  surface. Every edge a kind must have is a column the insert can refuse when
  it is missing.
- /Option B, one edge table./ Rows of (node, input, role) for every edge,
  maintained by the publish and by every edit.
- /Adopted: A./ A surface without a spot or a curve is not a surface, and a
  column states that where a row in a side table cannot. The spot pair is
  already stored this way. The curves become two columns that name the curve
  node by its name under the scheme, so no edge is found by a rule any more.
  The graph read builds the edges from the columns in one place.

*** How a stop is stored

- /Option A, one table of stopped nodes./ The source stop built for sources
  becomes a stop for any node, keyed by its name, with who, when and why, and
  its history.
- /Option B, a stop flag on each kind's own row./
- /Adopted: A./ One rule, one history and one pair of verbs, stop and start a
  node by name, whatever its kind. The stopped simulated source table becomes
  this table.

*** How a node's state is kept

- /Option A, derived in the service./ The service holds the graph in memory,
  built from the database at start and rebuilt when a feed's config changes.
  A state is computed from the stops, the runs and the last diagnostic, and a
  change is walked down the edges.
- /Option B, stored in a table./
- /Adopted: A./ A state is a consequence of other facts, and a stored copy of
  a consequence goes stale the moment one of its facts moves. What must last,
  the stops, is stored by choice 2.

*** Where a node's messages live

- /Option A, telemetry log entries./ Each message is a log entry of the
  telemetry service, tagged with the node's name and, for a starve, the name of
  the node that caused it. Telemetry already stores, ages out and queries log
  entries, with trace correlation
  ([[id:F9757D88-A92E-474E-9E8E-C703D604A0B2][ores.telemetry]]).
- /Option B, a JetStream stream with a subject per node./ The names are valid
  subject tokens, so this is possible, but perishable observations are not what
  the bus's streams are kept for
  ([[id:45D4751E-5089-4C82-9B37-63EFBD4A0B18][JetStream streams and consumers]]).
- /Option C, a table of the synthetic service's own./
- /Adopted: A./ No new store: a node's page reads its log from telemetry by
  the node's name. The messages are the state changes with their reasons, the
  operator's stops and starts, and the diagnostics a node raises, such as a
  latent surface's refused expiry or missing convention. It needs a check that a
  log entry carries an attribute a query can filter on; the story's diagnostics
  task owns that check.
- /Settled in building it./ The check held: a telemetry entry's tag is the
  node's name, and the existing log read filters on it. Every part of the
  service reports a node's events through one interface, =node_journal=, with
  three calls: =say= an event with its reason, =raise= a diagnostic and =clear=
  it. The runner says why a run starts and stops: demanded and run by a source,
  by hand, released because the demand dropped, its offer was withdrawn, or its
  source stopped. The stop and start of a node say each state they change. A
  latent surface raises the reason it publishes nothing and clears it when it
  publishes again. Telemetry is the one implementation; a test records instead.

*** The journal and the scheduler trace

Two records of the synthetic market exist, for two readers, and neither stands
in for the other.

| Record | Holds | Rate | Kept | Read by |
|--------+-------+------+------+---------|
| Scheduler trace | each decision of the market loop: a tick with its gaps and heat, a regime transition, a series added or removed | every tick | a fixed ring in memory, lost on restart | the Market tab's pace and raster charts |
| Node journal | each event of a node, with its reason, and its diagnostics | a few a day for a node | telemetry, aged out by its policy | the node's Messages tab |

The rule: what a person reads on a feed's page goes in the journal; what a
chart plots goes in the trace. The trace marks a series added or removed, but
the loop does not know why, so the reason is the runner's, said in the journal.
Each journal entry carries the market time the trace stamps its events with,
so a message lines up with the Market tab's charts without merging the records.

*** How the screens read the graph

- /Option A, one read of the whole graph./ A verb that answers every node with
  its state, reason and cause, and every edge with its role.
- /Option B, a read per node of its neighbours./
- /Adopted: A, with a filter by node./ The graph is small, so the whole read is
  cheap: 188 feed nodes and 8 sources in the seeded datasets today, counted
  from the system tenant. The filter answers one node's upstreams and
  downstreams for its page. Both the BFF and ores.http serve it.

** What the screens show

- Every feed page shows its state with its reason and, for a starved node, a
  link to the node that caused it.
- Every feed page lists its upstreams and its downstreams, each a link with its
  state; the vol feed's upstream links are the first of these.
- Every node has a Stop and a Start, with the confirmation the source stop has:
  what stops with it, and why.
- Every feed page has a Messages tab: its log from telemetry.
