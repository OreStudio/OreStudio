* Decisions

- *The party provisioning workflow is deleted, not moved.* The first task chose
  option 2, each commissioner owns its payload, and planned to move
  =provision_parties= to refdata. Nothing sends =workflow.v1.parties.provision=:
  the shell and the web provision a party through =iam.v1.parties.provision=.
  The workflow is deleted with its payload, handler, definition and permission,
  which reaches option 2's goal with no dead code to move. (Product owner,
  2026-10-02.)
- *One operation model holds the whole conversation.* The start message, the
  step event, the step result, the run, step and definition reads and the retry
  are one =ores.workflow.workflow_messages= model, because the TypeScript
  projection cannot reference a message in a sibling model. (Implementation,
  2026-10-02.)
- *What a model cannot state stays in one header.* The step outcome and log
  level enumerations, their reflectors and the NATS header names are in
  =workflow_vocabulary.hpp=. The enumerations are registered custom types, so
  they cross to TypeScript as strings. (Implementation, 2026-10-02.)
- *An empty filter is no filter.* The instances list filters were
  =std::optional<std::string>= and are plain strings with an empty default. The
  handler already read an empty value as no filter, and the shell can only fill
  a field with a default. (Implementation, 2026-10-02.)
- *Two shell verbs stay hand-written.* =workflow wait= polls and =workflow start=
  publishes on the stream with no reply, so neither is a message the shell
  facet can generate. They join the generated =workflow= menu through
  =extend_menu=. (Implementation, 2026-10-02.)
