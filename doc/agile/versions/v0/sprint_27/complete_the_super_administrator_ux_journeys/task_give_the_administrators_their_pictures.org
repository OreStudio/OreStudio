* Plan

The work has three parts: vendor the pictures, seed them, attach them.

** Vendoring. The super administrator's source picture is a single badge, so it
copies as it is. The tenant administrator's source is a sheet that carries both
badges, so the vendored file is the tenant badge cropped to its circle
(=convert tenant_admin_avatar.png -crop 480x480+530+10 +repage=). Both land
beside =external/acme/Acme-corp.png=.

** Seeding. Two populate scripts mirror =acme_party_logo_populate.sql=: one
system-tenant template row in =ores_assets_images_tbl= per script, keyed
=super_admin_avatar= and =tenant_admin_avatar=, with the PNG data base64 and an
idempotent guard. =populate.sql= runs them after the ACME logo seeds.

** Attaching. The =attach_photos= step gains =attach_administrator_photos=,
which runs at the top of the step, before the parties loop:

- The tenant administrator is the account the run acts as
  (=command.admin_account_id=), read through =account_service=.
- The super administrators are the system tenant's SuperAdmin holders, the
  same rule =bootstrap_mode_service= uses. Each picture is written through a
  token minted for that account (=internal_impersonation_service=), so the
  write takes the real request pipeline with its tenant checks and audit.
- The template keys are code constants, not step arguments: these pictures
  are the product's own, while the parties and datasets stay the profile's
  data.

** Idempotence. =copy_template_image= returns the tenant's existing copy by
code, and the new =attach_account_photo= skips an account that already carries
a picture, so a second run changes nothing.

** Refactor. =attach_account_photo= carries the read-echo-write block the staff
photos used, and =resolve_step_actor= delegates to the new =actor_of=, which
the super administrator path reuses.
