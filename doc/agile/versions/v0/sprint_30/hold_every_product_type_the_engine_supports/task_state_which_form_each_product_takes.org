* Goal

Every routed type states the form ORE reads it as, and a test proves the element our export writes is the element ORE's schema declares for that trade type, so a product whose form we model differently from ORE fails loudly.

* Acceptance

- the catalogue states, per type, whether ORE reads it natively, through a scripted class of its own, or through the generic ScriptedTrade
- for every routed type, the element the export writes is the one ORE's schema declares, checked by a test
- the generic ScriptedTrade and its library scripts stay supported as a route of their own, so both forms a product can take are available

* Plan

- The =construction= column names the form ORE reads the type in. ORE's trade
  factory gives three forms a type can take, plus our container: =native= (a
  trade class with its own element), =scripted= (a =ScriptedTrade= subclass with
  its own element), =script= (the generic =ScriptedTrade= that names a library
  script) and =container=. =script= is new: the generic ScriptedTrade was stated
  as =scripted=, which hid that it is the only type whose product lives in a
  library script, not in its element.
- Set the column from =external/ore/catalogue/trade_types.tsv= with a script,
  not by hand: every registered type ORE builds as a ScriptedTrade subclass
  becomes =scripted=, and =ScriptedTrade= becomes =script=.
- Add =script= where the value set is declared: the codegen loader, the product
  type model's check and its documentation. Regenerate the =trade= and
  =trading-cpp= components.
- The trade type coverage check fails when a registered type states a
  construction its ORE form does not allow (=native= allows =native= or
  =container=; =scripted= allows =scripted= or =script=). The catalogue cannot
  drift from ORE again without the gate failing.
- A Catch2 test in =generated_trade_export_tests.cpp= checks that every recorded
  trade writes all of its product under the element =trade_types.tsv= records
  for its type.

* Notes

** Nothing branches on construction

Before the change, only the database check and the codegen loader read the
=construction= value; no C++ or SQL code chose a path by it. Changing 35 rows is
a change to data and documentation, with no behaviour to migrate.

** The test detects the defect it exists for

With =FxTaRFData= renamed to =ScriptedTradeData= in the recorded =FxTaRF.xml=,
the new test fails with "FxTaRF writes Trade/ScriptedTradeData". The file was
restored afterwards.

* Result

The catalogue states the form ORE reads every registered type in: 34 types moved
from =native= to =scripted=, and the generic =ScriptedTrade= takes the new value
=script=, so the four forms (=native=, =scripted=, =script=, =container=) are
distinct in the model, the SQL check and the codegen loader. The trade type
coverage check now fails when a registered type states a construction its ORE
form does not allow, and reports 0 disagreements. The test "every recorded trade
writes the element ORE reads for its type" passes for all 83 recorded types and
fails when one writes another element. The generic =ScriptedTrade= keeps its own
row and route, so both forms of a product stay available.
