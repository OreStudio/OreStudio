* Goal

Serve the standard import in two steps. The preview states what importing a
document would change, and writes nothing. The import acts on the same answer.
Both are the ORE service's: the gateway hands the document over and states what
comes back, a refusal included, because the person reads the reason on the step.

* Acceptance

- The C++ server answers
  =POST /api/reporting/pricing-engines/ore-import/preview= and
  =POST /api/reporting/pricing-engines/ore-import= at the BFF's paths, with the
  BFF's member names and status codes.
- The preview writes nothing and states the service's own words, a refusal
  included.
- The import states what the service saved and the rows it could not write.
- The screen's id is joined to the configuration the service reads, and a write
  that names no configuration is joined to an empty one.
- A document is refused by size by the service, and the route's own body limit is
  twice the document's so that the JSON escaping does not refuse it first.
- The gateway reads no XML, builds no XML and validates none.
- A test proves each refusal; the happy paths need a live estate and this task
  does not prove them.
- Each route in scope names its C++ equivalent in the inventory.
- The local gate is green.

* Plan

Branch =feature/serve-the-ore-import=.

The two routes are forwarded, not composed. The gateway states the document, the
configuration the service should write into, the name and variant of a new
configuration, whether removals are kept, and the reason. It states back what
the service answers.

This is the only write in the area that acts on a document a person did not
build through a screen, which is why it is its own task and its own PR.
