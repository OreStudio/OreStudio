* Decisions

- The macOS failure is a missing export, not a test bug. =ores.database= builds
  with hidden visibility, and libc++ compares a catch against the typeinfo
  pointer rather than its name, so a type thrown in the library and caught in
  the test never matches. Exporting the type is the fix, and it matches what
  =ores.logging= already does with =logging_exception=.
- =getenv= is replaced by the environment provider =ores.platform= already
  owns. Its header states the same MSVC deprecation and solves it with
  =_dupenv_s=, so routing through it removes the warning without a suppression.
- Warnings-as-errors stays off. Turning it on is the last step, after the
  remaining warnings are gone.

* Out of scope

- =-Wsubobject-linkage= and =-Wmaybe-uninitialized= as GCC 13 reports them.
  They do not reproduce under the GCC 16 this worktree has, and they appear to
  describe coroutine frames, which are local to a translation unit.
- The MSVC =C4244= narrowing that =std::optional<int>= reports. It needs an
  MSVC build to locate, and the failing build predates this branch.
- Re-enabling =ORES_WARNINGS_AS_ERRORS=. It is already off on main, set by
  =2d0b992507=.
