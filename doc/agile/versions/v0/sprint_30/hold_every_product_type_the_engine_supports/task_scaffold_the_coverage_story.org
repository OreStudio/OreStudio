* Acceptance

- the story and its sixteen tasks are wired into sprint 30
- each task names the types it closes or the evidence it establishes
- the coverage gap is stated once, from ORE's own source, so a reader can size the remaining work

* Plan

Survey ORE's own source for what it does with each of the 121 catalogue types,
then write the story and one task per body of work. The survey is a script over
the checkout: for each code, whether =instruments.xsd= names an element, whether
the trade type is registered in =databuilders.cpp=, and the class the element is
read as, following the base chain to see whether it is a =ScriptedTrade=
subclass. The 30 unrouted types partition by element shape, which is what makes
ten modelling tasks rather than thirty.

* Measurements

Every number this task claims about a tree, with the command that produced it
and the commit it was measured at. A number without both is not a measurement,
because a clean-up record describes a tree and trunk moves under a branch: a
consumer count, a gate's component count and a suite's size all change with no
code changing, and the reader of a bare number cannot tell which tree it came
from. Where the raw output matters, put it in an =evidence/= file beside the
task and name that file in the Command column.
