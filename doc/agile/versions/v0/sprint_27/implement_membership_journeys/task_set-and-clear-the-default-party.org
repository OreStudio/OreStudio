* Acceptance

- =iam.v1.ops.set_my_default_party= still stores a party the member works in, and refuses one they do not.
- An empty =party_id= clears the stored default, and clearing a default that is not set succeeds without writing.
- The browser reaches the write over =POST /api/me/default-party=, parsed at the boundary.
- The C++ tests cover storing, clearing and clearing twice; the BFF tests cover storing, clearing, the refusal and a caller with no session.
- =check_component_drift.py --component iam= reports no drift, clang-format is clean, and the three TypeScript packages typecheck.

* Plan

1. Make clearing expressible: an empty =party_id= is unambiguous, because a
   party id is a UUID. Record the rule on the message.
2. Take an optional party in the service, so "no default" is a value it can
   store, and make it idempotent for a default that is already clear.
3. Skip the membership check on a clear, because clearing names no party, and
   leave the check in place for a set.
4. Wire the browser path: the wire seam, the BFF route and the web client.
5. Test the service at the database and the route end to end.

* Notes

- *Clearing needed no new subject.* The journey's candidate was a nullable
  body or a =clear-default-party= subject. The request already carries a string
  party id, and a party id is a UUID, so an empty string is unambiguous and the
  smallest change that makes "no default" expressible. The prototype drew *Clear
  default* as unavailable; after this it is a real control.
- *The membership check stays where it is.* It is the guard that stops a member
  storing a party they cannot act for, and it is the reason the screen may offer
  only the account's own parties. A clear skips it because it names no party.
- *Changing the service signature did not move its callers.* The parameter is
  now =std::optional<boost::uuids::uuid>=; the existing tests and the handler
  pass a plain uuid, which converts.
