* Acceptance

- A batch made by a report run shows the run's name in the tree and in the details, with a link to the run.
- A party reads by name where the session knows it.
- The report run page names the report and the party, and a failed run that made no batch says so.
- The job page shows the app version by its engine version, with its id in a tooltip.

* Plan

The BFF adds two names to a batch: the name of the report run that made it, read in one statement for the page from the reporting service, and the name of its party, from the parties the session knows. The report run page gains the report's name and the party's name. The web shows them where it showed ids, and keeps each id in a tooltip or in the details. The model's own field names stay the labels of an id, as the approved prototypes state, so a row that holds an id keeps its model header.

* Notes

Found by looking at the screens with a real report run: the Jobs tab read =9abaf1a1-6624-45b1-b42b-bacbd4a3270d= where it could read "NPV 2026-10-23 22:07:58". A report run is named by the reporting service, so the batch needs one read of the runs of the page, and a failed read leaves the names out and does not fail the page.

I first changed the job page's App Version ID row to read as the version. Two tests failed, because the prototypes use the model's own field names. The Release panel already states the engine and wrapper versions beside the id, so I put the row back.

The operator reads no report run name, because a run belongs to a tenant party. The party name is known only for the parties the session acts for, so the operator sees party ids.
