This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A signed-in person browses the batches, workunits and results of the compute grid that they may see, finds one, reads its details and takes its input or output away.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"Show me the work the grid ran for me. Let me open a batch, see its jobs and
their runs, read why one failed, and take its input or output away." The
person has finished when they have found the record they came for, read its
details, and downloaded what they needed.

* Actor and trigger

Three actors use this screen, and the session decides what each sees.

- The *operator* is a system administrator in the system party. They see every
  tenant's batches, workunits and results, and the node each run used.
- The *tenant administrator* sees every batch of their tenant, across parties.
- The *party member* sees only the batches of their own party.

The trigger is a question from the Usage tab or the Overview tab: "1268 results
failed. Which ones?" or "What did my party run today?" The journey starts on the
Jobs tab of the compute grid screen. It ends on a record page or on a saved
file. The screen is read-only.

* Steps

1. The person opens the Jobs tab. The system reads the first page of batches
   that the session may see, newest first, and shows each with its =external_ref=
   and its =status=.
2. The person narrows the list. They type a batch reference or id, choose a
   =status=, or (as operator or tenant administrator) choose a party. Each change
   returns to page one.
3. The person opens a batch. The system reads one page of its workunits and
   shows them under the batch, each with its =priority= and =target_redundancy=.
   The person may open several batches.
4. The person opens a workunit. The system reads its results and shows them as
   leaves of the tree, each with its =server_state= and =outcome=.
5. The person selects any row. The details panel shows that record's own fields
   under the model's headers. For a result it shows the outcome, the error
   message, the host and the time received.
6. The person follows the Input URI link of a workunit or the Output URI link of
   a result. Each link is the stored file's own address and the system serves the
   file as a download. A result has no input of its own: the person reaches it
   through the result's Workunit ID link. The file is large, so the download streams.
7. The person follows a reference in the details: the batch of a workunit, the
   workunit of a result, the canonical result of a workunit, or, as operator, the
   host of a result. The workunit's page continues in
   [[id:1439FB25-A388-40C7-930A-3A814B703DDD][Follow a job]].

No step needs the server to finish work later, so the journey carries no state
beyond the address: the filters, the open rows and the pages live in the URL.

* Screens and wireframes

One screen. The finder bar, the tree and the details panel are panels of the
Jobs tab. The tree is the relationship view the
[[id:2BF7F03F-6BF4-45FF-8E26-4D3B4E2D943D][Record screen standard]] names: it
shows how a batch holds workunits and a workunit holds results. The pager is the
request. Each level pages on the server with First, Previous, Next, Last, a page
size and Load all, and Load all appears only when the total is 1000 or less.
Opening a node never reads more than one page of its children.

State is a badge, as the [[id:166B2D77-6D04-47D5-A651-5431E1F2E082][UX
Language]] sets it. A batch's =status= is blue for open, sky for processing and
assimilating, and green for closed. A result's =server_state= is gray for
Inactive, blue for Unsent, sky for InProgress and green for Done. Its =outcome=
is green for Success, red for ClientError and amber for NoReply. Gray means
inactive only.

The screen shows only fields the entity models hold, under the models' own
headers. It computes no count and no state: a closed batch and a failed result
are read from =status= and =outcome= as stored. The references in the
details (the node, the job, the party) are links, not text.

The screen shows four states in words: loading ("Reading the batches..."), empty
("No jobs match. Clear the filters."), error (the server's
reason and a Retry action) and refused ("Your role cannot read jobs.").

* Operations and messages

| Step | Operation | Subject | Status |
|------+-----------+---------+--------|
| 1, 2 | Read a page of batches | =compute.v1.batches.list= | partial |
| 2 | Filter batches by status, party or reference | (the list takes an offset and a limit only) | missing |
| 4 | Find the results whose =outcome= is not Success | (=read_by_state= filters on =server_state= only) | missing |
| 3 | Read a page of a batch's workunits | =compute.v1.workunits.list_by_batch_id= | exists |
| 4 | Read the results of a workunit | =compute.v1.results.list_by_workunit_id= | exists |
| 5 | Read one record | =compute.v1.batches.get=, =compute.v1.workunits.get=, =compute.v1.results.get= | exists |
| 5 | Read the node of a result | =compute.v1.hosts.get= | exists |
| 5 | Read a run's times, sizes and peak memory, and their aggregates per workunit and batch | (no field on the result; the submit message does not carry them) | missing |
| 6 | Download an input or an output | (no route serves the stored file) | missing |
| 1 to 5 | Reach the reads from the browser | (no BFF route for jobs) | missing |

Each read checks its entity's read code (=compute::batches:read=,
=compute::workunits:read=, =compute::results:read=) and serves the session's
tenant. The row-level policy narrows a party member to their own party. The
Member role holds the batch read in the seed. A live check on 2026-10-22 showed
that a party member is refused the workunit and result reads with =forbidden=, so
the member sees the batches and cannot open one. The seed must give the Member
role the workunit and result read codes.

* What is missing

1. *No filters on the batch list.* The list pages by offset and limit. Status,
   party and reference filters need a server-side predicate, or the screen
   cannot find one batch among thousands.
2. *No way to find failed results.* "Which of the 1268 failed?" has no read.
   =read_by_state= filters on =server_state=, and every stored result is Done,
   so the failed ones are not separable. A read by =outcome=, and a way from a
   result to its batch, would answer it. Until then the person opens batches
   and reads each result's =outcome=. The screen shows no per-batch job or
   failure count, because the models hold none.
3. *No run statistics on the result.* The result holds no start time, no end
   time, no input or output size and no memory figure. The wrapper measures the
   run's duration and the bytes it fetched and uploaded, but it only sums them
   into =node_sample= per node and interval, so a node's mean is stored and a
   job's own value is not. The engine reports its peak memory use in its own log
   (=peakMemoryUsage (bytes) | memoryUsage (bytes)=), which the wrapper
   publishes as a log line keyed by the result id and the platform does not parse
   into a field. The host row holds its total =ram_mb= only. Per-run fields,
   written by the wrapper in the submit message, are the missing piece:
   =started_at=, =finished_at=, =input_bytes=, =output_bytes= and
   =peak_memory_bytes=. A workunit and a batch show the aggregate of the results
   below them: the earliest start, the latest finish, the sums of the bytes and
   the largest peak memory. The aggregate is a grouped read, not a stored field.
   The prototype draws all three levels in a dashed block labelled "proposed,
   not stored yet".
4. *No download route.* =input_uri= and =output_uri= name stored objects. The
   browser has no route to stream them, and the route must check that the
   caller may read the owning record first.
5. *No BFF route.* The web client reads through hand-written BFF routes, as
   the grid series does. A route for the paged tree is needed.
6. *Node names for tenants.* A result names its host. A tenant administrator
   or a party member should probably not see the installation's node names.
   The owner must decide. Until then, the prototype shows the node to the
   operator only.
7. *A run in flight has no node.* As in Follow a job, the node is bound when
   the run ends. The details say "not yet known".
