* Plan

1. Define the wire shapes and the joined shape once, in
   =@ores/wire-protocol=: the three response pages, the two request shapes, and
   =seedProfileChoiceSchema=, which is what the browser parses. The profile's
   step arguments stay on the server — the kind fixes their shape in code — so
   the joined shape carries each step's kind and position and no more.
2. Add the wire-client method. It reads the profile page, then each profile's
   steps and parameters, joins them, and sorts by the order the profile
   declares: the profile page comes back in key order, because the generated
   read orders by key and the profile's own column is what orders the cards.
3. Add the hand-written BFF route, authenticated like every other read that
   needs a session, and record it in the component specification's route table.
4. Test both ends as their callers use them: the client against a scripted
   transport asserting the joined literal and the subjects it called, and the
   route through Fastify's inject with a session and a fake client asserting
   the served body and the 401.
5. Prove it on the live deployment: sign in through the BFF and read the route.

* Notes

- *The join lives in the client.* Three subjects answer the read and the browser
  may name none of them, so the method that composes them belongs next to the
  subjects. The BFF route is then a parse and a return, which is what makes it
  reviewable against the others.
- *The arguments stay on the server.* A step row carries the arguments its kind
  consumes, and the kind fixes their shape in code. The joined shape carries the
  kind and its position, which is what the starting-point card shows, and no
  copy of a handler's contract crosses to the browser.
- *The order is the profile's.* The generated paged read orders by key, so the
  two profiles arrive in whatever order their surrogates sort in. The method
  sorts by the =display_order= the model carries, because that column exists to
  order the cards; the test is written so the seeded order and the key order
  differ, which is what makes the sort observable.
- *The route is not called by the browser yet.* The journey screen adds the
  call; the component specification already says a route no module calls is
  served and reachable, and a screen adds the call it needs.
- *Two bootstrap routes were missing from the specification's table.* They were
  added by an earlier task in this story and the table was not updated; this
  change adds all three rows, so the table is the browser's whole authority
  again.

* Result

The browser can read the starting points. =GET /api/seed-profiles= answers with
every profile, each carrying the step kinds it orders and the parameters its
form declares, parsed from the schema the wire and the browser share.

=@ores/wire-protocol= gained the three response pages, two request shapes, the
joined =seedProfileChoiceSchema= and the =OresClient.seedProfiles()= method
that composes the three subjects and sorts the answer by the order each profile
declares. =@ores/bff= gained the authenticated route, which is a parse and a
return. The component specification's route table gained this route and the two
bootstrap routes an earlier task added without recording them.

Measured on the live deployment, signed in through the BFF:

Both ends are tested the way their callers use them: the client against a
scripted transport, asserting the joined literal and the six subjects it
called, and the route through Fastify's inject with a live session and a fake
client, asserting the served body and the 401. The whole workspace typechecks,
formats clean, passes 117 tests across the three packages, and the tree builds.

Left to the screens that own them: no browser module calls the route yet, and
the provision request that consumes a chosen profile is step 6 of the story.
