#+title: Story: Carry every trading instrument as a typed batch
#+description: The export carries each trade's instrument as instrument_payload, an untyped std::string type plus a JSON std::string body, because rfl cannot tag a std::variant of the trading instrument types. That is an untyped payload and a hand-written second type system; the project's own wire rule forbids both. Replace it with one typed array per concrete instrument type, joined back to its trade by trade id, and delete the hand-written codec. Deprecate the polymorphic-payload pattern in the knowledge base and apply the same rule everywhere it is used.

* Goal

Every trading instrument crosses the export boundary as a typed array, not as
an untyped payload. A message carries no =std::variant= field and no
=std::string= field holding an encoded value; a heterogeneous result set
travels as one typed array per concrete type, and the receiver joins the
arrays by key. The hand-written codec that named the active alternative and
encoded it as JSON text is deleted.

* Acceptance

- =instrument_payload= and its codec are deleted. No message in ores.trading
  declares a =std::variant= field or a =std::string= field that holds an
  encoded value.
- =export_portfolio_response= carries one typed array per concrete instrument
  entity and per child entity, keyed by trade id, alongside the trade anchors.
- The batch type and its append and lookup helpers are generated from the
  model, not hand-written.
- The producer appends typed values and the ORE exporter looks them up by
  trade id; the XML round trip is unchanged.
- The polymorphic-payload pattern is recorded as deprecated in the knowledge
  base, with the replacement rule.

* Decisions

- *D1, the layout.* One typed array per concrete instrument entity, and one per
  child entity, all flat. Struct-of-arrays, not array-of-structs with a tag.
  The tag moves from every element to the container. Splitting only the
  top-level alternatives is not enough: =swap_instrument_data= holds a
  =rates_instrument_variant= and =fx_instrument_variant= is itself a variant,
  and rfl cannot encode a nested variant for the same reason it cannot encode
  the outer one.
- *D2, generation.* The batch type and its append and lookup helpers are
  generated. A hand-written aggregate of typed arrays is the same hand-written
  second type system under another name, which is the defect being removed.
  The existing trade-type routing generator is the hook: it already knows every
  instrument table, and it already emits the include list.
- *D3, the discriminator.* The trade type the anchor already carries decides
  which array holds a trade's instrument, through the generated
  =instrument_table_for=. No per-element tag is added, because the container
  already states the type.
- *D4, one round trip.* The exchange stays a single request and response.
  Splitting it into one subject per family was considered and rejected: the
  exporter rebuilds one document, so N round trips add a reassembly protocol
  and remove no data. Per-type subjects remain correct for single-entity CRUD,
  where the generated protocols already provide them.
- *D5, the sweep is empty.* =instrument_payload= is the only untyped payload
  in the tree; no protocol header declares a =std::variant= field. The
  =std::string type= fields in ores.iam are tenant and account classifications,
  which are business data and not tags, so the deprecation changes no other
  code.
- *D6, the bond container is modelled first.* Every other family's batch
  members are generated entities, but the bond family's documents are
  hand-written C++: =bond_instrument_data= and the 22 structs beside it. A
  hand-written type cannot cross in a generated batch without a hand-written
  TypeScript twin, and that twin would be a second hand-maintained type system
  of about 170 members. The container is therefore declared as =field_group=
  models before the batch is generated, so every batch member is generated.
  This is the container grammar the bond relational design sequences over.
