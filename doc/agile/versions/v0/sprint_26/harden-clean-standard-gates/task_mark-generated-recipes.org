* Goal

Give generated org output the codegen marker every other generated kind already
carries, and give the generated recipes the gate they have never had.

The recipe templates do carry a marker, but as a Mustache comment, and Mustache
comments produce no output. So no generated recipe reached the tree with one:
247 files sit at the generated recipe path shape and 172 carry the =:tangle=
block a generated recipe exports, against 6,478 tracked C++ files that name their
template. Nothing could tell a generated recipe from a hand-written one, and
nothing checked either, because the sweep rendered per technical space and the
recipe facets need a facet from another space.

* Acceptance

- Every generated org document carries a marker naming its template, emitted at
  the render seam rather than by each template.
- The marker does not disturb the document's frontmatter, its blurb, or the doc
  index that reads them.
- The sweep renders the whole =ores= address, so the recipe facets fire and the
  generated recipes are covered.
- The rollout changes nothing but the marker: no generated recipe is rewritten
  beyond adding one line, and the check proves it.
- A test fails if the org marker stops being emitted.

* Plan

*Where the marker goes, and why there.* Org has no licence block to append a
marker to, so the marker is a =#+generated:= keyword inserted after the leading
=:PROPERTIES:= drawer. Placement is not cosmetic. The doc index reads the drawer
from the first line and folds whatever precedes it into the document's blurb --
the prose =compass show= prints -- so a marker above the drawer gives the blurb
the drawer's own text. And the blurb skips =#+= lines and blank lines and stops
at anything else, so a =#= comment in the same position becomes the blurb too.
Both were measured against =doc_index.extract_blurb= before the change: the
=#+generated:= keyword after the drawer preserves the blurb and the id, and a
marker above the drawer corrupts the blurb.

*The coverage half.* =_render_components= expands =ores= into the technical
spaces, and passing =ores= to it does not render the whole address. A facet
whose =#+requires_facet:= names a facet in another space therefore never fires,
which is how the recipe facets were missed: for =ores.trading= the per-space path
gives 1,867 files and no recipe, while rendering each model at the whole address
gives 2,003 files and 22 recipes. The sweep now asks for the whole address; the
per-component modes keep the expansion they have always had.

*The rollout, and its safety rule.* Applying a marker to files that already exist
is a rewrite, and 58 of the renderable recipes disagree with their models by more
than a marker. So the rollout wrote a recipe only where the marker was the sole
difference, and left the rest alone. That is the rule the check enforces, and it
is what keeps a hand edit from being overwritten by a marker pass.

* Notes

*Measured at the rebased head.*

- The whole-address render produces 185 recipe files. 111 took the marker with
  nothing else changed, 60 differ by more than the marker and were left alone,
  and 14 the render produces are absent from the tree entirely.
- The rollout is exactly additive: 113 files changed, 113 lines added, 0 removed,
  and every added line is a =#+generated:= line, over the 113 the marker pass
  wrote. Two of those were reverted when the rebase moved them into the stale
  set, so the branch carries 111 and =git grep -l "^#+generated:" -- '*.org'=
  finds 111 tracked org files carrying it.
- The canonical doc index loads all 281 org files under =doc/recipes/shell/= and
  =doc/recipes/http/=, every one with a non-empty blurb, and none with the marker
  in its blurb.
- 6,478 tracked =.cpp= and =.hpp= files carry the C++ marker, measured with
  =git grep -l "AUTO-GENERATED FILE - DO NOT EDIT MANUALLY" -- '*.cpp' '*.hpp'=.
  That is the figure the comparison is against, and it is smaller than the number
  of files on disk because generated trees outside version control do not count.
- The sweep renders the whole address now and reports 857 files drifting across
  the catalogue in CI, against 645 before it reached the recipes; the same run
  reports 858 locally, so the figure moves by one with the clang-format version
  the machine has. It takes about a minute and stays green: none of that drift
  is this branch's.
- Proved end to end: appending a line to
  =doc/recipes/shell/trade_types/trade_type.org= makes the sweep exit 1 and name
  that file, where before the change it could not see a recipe at all.
- Codegen suite 906 passed; =compass lint= clean; =validate_docs.sh= 40 of 40.

*What the rollout exposed, none of it fixed here.*

1. *60 recipes are stale against their template.* Fifty-eight differ only inside
   their =#+begin_src ores-shell :tangle ...= blocks, and only by =__none__=
   becoming =-= in the placeholder positions, with no prose changed, so they are
   stale rather than hand-edited. Which of the two the shell accepts is the shell
   owner's call, and the staleness is filed as a capture.
2. *Two more the rebase exposed, and the reason the branch carries 111 rather
   than 113.* =doc/recipes/shell/lei_entities/lei_entity.org= and
   =doc/recipes/shell/lei_relationships/lei_relationship.org= are staging shims,
   and main's staging-only change means the generator now renders them with no
   command sections at all: 77 lines where the tree holds 224. Regenerating them
   would delete 147 lines of generated recipe content, and whether a staging shim
   should keep a recipe at all is the =dq= owner's call, not a marker pass's. The
   marker was reverted on those two so this change stays purely additive, and the
   finding is filed with the staleness.
3. *76 files sit at the generated recipe path shape that no render produces.*
   The shape holds 247; the render accounts for 171 of them once the 14 it
   produces but the tree lacks are set aside, leaving 76 with no model behind
   them, which is what a retired or renamed template leaves. Nothing deletes
   them, and nothing should: a clean-up that removed files no render produces
   would delete whatever a hand-written nested recipe looks like.
