* When to use this skill

- When adding, editing, reviewing, or removing comments in code.
- After code changes, before committing.
- When the user asks to clean comments in a diff or across the
  repository.

* How to use this skill

1. *Choose the scope.* Default to diff-only cleanup: inspect the
   complete staged and unstaged patch and edit only the comments that
   patch introduces or changes. Use repository-wide cleanup only when
   the user explicitly asks for it; otherwise unchanged comments in a
   file are out of scope.

2. *Apply the comment rules* from [[file:comment-rules.md][the comment
   rules reference]]. In one line: comments are sparse, above the code,
   never narrated as edit history, never end-of-line — except Doxygen
   =///<= trailing comments, the codebase convention for documenting
   public API (see the [[id:0FB2EA84-EBB8-45C8-A8C8-F5815431C2D2][code review checklist]]).

3. *Remove comment clutter:* commented-out code; comments that merely
   restate the code or the method name; edit-history narration.

4. *Preserve necessary comments:* TODO, FIXME and similar work
   markers; linter, formatter, compiler, coverage, and generated-code
   directives; non-obvious reasoning, constraints, and business
   rules; pre-existing comments during diff-only cleanup.

5. *Focus only on comments.* Do not change executable code, behavior,
   or formatting unrelated to the moved or removed comment. Regenerate
   generated files instead of editing them.

6. *Report the outcome* with a before/after table (see
   [[file:before-after.md][examples]]). If the code already complies, say so —
   do not force changes onto compliant code.

# Code Comment Rules — Reference

This file is the canonical rule set for code comments in ORE Studio.
It merges two prior-art sources:

1. The `comment-cleanup` skill from
   [motlin/claude-code-plugins](https://github.com/motlin/claude-code-plugins/blob/main/plugins/code/skills/comment-cleanup/SKILL.md)
   (Apache-2.0, copyright 2024 Craig Motlin) — the scope, remove,
   preserve, and placement rules.
2. The `clean-code-comments` skill on
   [mcpmarket.com](https://mcpmarket.com/tools/skills/clean-code-comments)
   — the Comment Guidelines list, transcribed by the ORE Studio user
   (the page declares no license).

## Scope

- Default to diff-only cleanup: inspect the complete staged and
  unstaged patch and edit only comments introduced or changed by that
  patch.
- Looking at every changed file is too broad — unchanged comments in
  those files are outside scope.
- Use repository-wide cleanup only when the user explicitly asks to
  clean all comments, the whole repository, or a named directory. The
  same rules apply to existing comments inside the requested scope.

## Comment Guidelines

- Use comments sparingly.
- Do not comment out code — remove it instead.
- Do not add comments that describe the process of changing code.
- Do not add comments that include past-tense verbs like added,
  removed, or changed. Example:
  `this.timeout(10_000); // Increase timeout for API calls`
  This is bad because a reader does not know what the timeout was
  increased from, and does not care about the old behavior.
- Do not add comments that emphasize different versions of the code,
  like "this code now handles".
- Do not use end-of-line comments, except Doxygen `///<` trailing
  comments, the established convention for documenting public API (see
  the [code review checklist](../../../doc/knowledge/architecture/code_review_checklist.org)).
- Place comments above the code they describe.

## Remove comment clutter

- Delete commented-out code.
- Delete comments that merely restate the code or the method name.
- Delete edit-history narration using terms such as "added",
  "removed", "changed", "updated", or "now handles".
- Remove redundant comments without hesitation when the code is
  already self-explanatory.

## Preserve necessary comments

- Preserve TODO, FIXME, and similar work markers.
- Preserve linter, formatter, compiler, coverage, and generated-code
  directives.
- Preserve non-obvious reasoning and business rules.
- Preserve pre-existing comments during diff-only cleanup.
- Do not remove a comment that a convention or tooling requires to
  stay — for example a Doxygen documentation block or an enclosing
  scope marker such as `#region` / `#endregion`; removing it would
  leave the API undocumented or the scope empty.

## Place comments cleanly

- Do not use end-of-line comments, except Doxygen `///<` trailing
  comments, the established convention for documenting public API.
- Move a necessary end-of-line comment to its own line immediately
  above the code it describes, using the same indentation.

## Boundaries

- Focus only on comments. Do not change executable code, behavior, or
  formatting unrelated to the moved or removed comment.
- Do not edit generated files that should be regenerated instead.

# Before / After Examples

These examples are original illustrations built for this skill. They
apply the rules from `comment-rules.md` to realistic code comments.
They are illustrations, not quotes from any real codebase.

| Rule violated | Before | After | Why |
|---|---|---|---|
| Past-tense narration | `this.timeout(10_000); // Increase timeout for API calls` | Remove the comment | The reader cannot know what the timeout was increased from and does not care about the old behavior. |
| Process-of-change comment | `// Updated the cache to use the new key format` | Remove the comment | It narrates the change, not the code. |
| Version emphasis | `// This code now handles the v2 response format` | Remove the comment | It emphasizes a version of the code; the current code handles whatever it handles now. |
| Commented-out code | Two dead lines: `// int x = 42;` above `// x += 1;` | Delete both lines | Commented-out code is clutter; remove it instead. |
| End-of-line comment | `foo(); // Syncs the database` | Move above: `// Syncs the database.` then `foo();` — or remove it if the function name already says it | End-of-line comments break scanability; comments belong above the code at the same indentation. |
| Redundant restatement | `// Sort the list` above `list.sort()` | Remove the comment | The code restates the method name. |
| Necessary comment kept | `// Prices are quoted per 1M notional — divide by 1e6 before comparing` | Keep as is | It explains non-obvious business logic the reader cannot recover from the code. |
| Doxygen exception | `int x; ///< pixel x-coordinate` | Keep as is | Doxygen `///<` trailing comments are the codebase convention for documenting public API. |

## How to read these examples

The first six rows show comments removed or moved. The last two rows
show the cases the rules protect: a comment that carries a business
rule no amount of renaming can recover, and the Doxygen `///<`
convention for public API. The test for any comment is: if the code
changed tomorrow, would this comment still be true and still be
needed? If not, remove it.
