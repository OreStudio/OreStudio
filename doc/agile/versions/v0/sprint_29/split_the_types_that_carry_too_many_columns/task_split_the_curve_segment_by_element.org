* Acceptance

- No segment row carries a column that the element its segment_type names cannot use.
- The twelve elements' settings are parts, and a part exists only for the elements that have it.
- The curve recipe's read, the ORE projection and the fixtures state the segment and its parts as separate arrays.

* Plan

** The rules a split obeys

The data-oriented model decides the shape, not the column count. Its rules, and
the reasons behind them, are in
[[id:BBD43BF2-9FEE-42B0-A667-9468AF759DC2][Data-Oriented Design in ORE Studio]] and
[[id:56AD6F46-99E0-482E-B7B5-C9FDEC8A7641][The data classification checklist]]; this task applies them and
does not restate them. In short:

- a type holds one component: fields that share one invariant, hold at one
  instant, and are keyed by the same key;
- a part is joined by key and never nested, so the wire carries one typed array
  per component and no part's fields appear inside another's object;
- a field read on a different cadence, or by a different screen, job or service,
  goes with its readers and not with the row it happens to sit in;
- the classification comes first. A compile error never reclassifies data: if a
  shape has to be denormalised for a compiler, the classification stays and the
  denormalisation is recorded;
- the centre keeps the identity and whatever the parts must agree on. A part one
  reader needs does not stay on the centre.

** This grouping

=curve_segment= carries =segment_type= and twenty columns that exist for one of
twelve elements alone: projection curves for simple and tenor basis segments, a
discount curve and a spot rate for cross-currency ones, a reference curve for
zero-spread ones, and the rest. 33 members, 28 of them nullable, which is a
union of elements written as nullable columns.

The element is the type of the segment, not the value of one of its columns. A
segment row keeps =segment_type=, its position, its priority and the terms every
element shares; each element's settings are its own part, present only for the
elements that have them.

The curve recipe's read composes a definition, its segments and each segment's
part:

=curve_definition= -> =curve_segment= -> the element's part -> =curve_quote=.

** What proves it

- No segment row carries a column its element cannot use.
- The parts are joined to the segment by the segment's key, and the recipe read
  returns each part as its own array.
- The ORE bootstrap of a fixture produces the same curve as before the split.

* Notes

** The settings each element reads

The ORE schema (=external/ore/xsd/curveconfig.xsd=) and the projection's
=import_segments= agree on what each of the twelve elements states. Neither
the convention nor the pillar settings are shared by every element, so neither
can stay on the segment row:

| Element          | Conventions | Pillar settings | Its own settings                        |
|------------------+-------------+-----------------+-----------------------------------------|
| Direct           | optional    | yes             | none                                    |

| AverageOIS       | required    | yes             | the projection curve                    |
| TenorBasis       | required    | yes             | four projection curves                  |
| CrossCurrency    | required    | yes             | discount curve, spot rate, two curves   |
| ZeroSpread       | required    | yes             | the reference curve                     |
| DiscountRatio    | optional    | yes             | three curves and their currencies       |
| FittedBond       | none        | yes             | the flat extrapolation flag             |

| YieldPlusDefault | none        | none            | the reference curve                     |
| IborFallback     | none        | yes             | the ibor index, the RFR curve and index, the spread |

** The parts

A part is one component: fields that hold one invariant. An element has a part
when it states that component, and a segment holds at most one row of each
part, so each part's =curve_segment_id= is unique on the live rows. The parts
are children of the segment, keyed by its id, as =curve_segment_curve= is:

| Part                               | Columns                                              | Elements                                                                  |
|------------------------------------+------------------------------------------------------+---------------------------------------------------------------------------|
| curve_segment_convention           | conventions                                          | Direct, Simple, AverageOIS, TenorBasis, CrossCurrency, ZeroSpread, DiscountRatio, BondYieldShifted |
| curve_segment_pillar_rule          | pillar_choice, priority, min_distance                | Direct, Simple, AverageOIS, TenorBasis, CrossCurrency, ZeroSpread, DiscountRatio, FittedBond, IborFallback |
| curve_segment_projection           | projection_curve                                     | Simple, AverageOIS                                                        |
| curve_segment_tenor_basis_curves   | projection_curve_pay, _receive, _long, _short        | TenorBasis                                                                |
| curve_segment_cross_currency_terms | discount_curve, spot_rate, projection_curve_domestic, _foreign | CrossCurrency                                                   |
| curve_segment_reference            | reference_curve                                      | ZeroSpread, BondYieldShifted, YieldPlusDefault                            |
| curve_segment_weighted_average     | reference_curve_1, reference_curve_2, weight_1, weight_2 | WeightedAverage                                                       |
| curve_segment_discount_ratio       | base_curve, numerator_curve, denominator_curve and their currencies | DiscountRatio                                              |
| curve_segment_extrapolation        | extrapolate_flat                                     | FittedBond, BondYieldShifted                                              |
| curve_segment_ibor_fallback        | ibor_index, rfr_curve, rfr_index, spread             | IborFallback                                                              |

The shared components are parts of their own, rather than columns repeated on
a part per element, because each holds one invariant every element that states
it agrees on: the pillar settings are the same three rules wherever they
appear. A part per element would repeat the convention column on eight tables
and the pillar settings on nine. The volatility split did the same with the
proxy block two kinds share.

A part's row exists only when the element states it. A required field makes
the part present on every segment of the elements that require it; a part of
optional fields is written only when the document states one of them, so no
part row is all null.

** Where the element-to-part rule lives

The projection's =import_segments= is the one statement of which element
reads which part: each element's loop calls one reader per part it has. The
section generator already reads that function to tell the screen which leaves
a kind shows. It now also reads which part each leaf is in, and it writes the
SQL that refuses a part row whose segment's element does not have that part.
So the screen, the database and the projection cannot disagree about it.

* Result

The element is the reason for the split, not the column count. A curve
segment's =Type= fixes one of twelve ORE elements, and the schema and the
projection agree on what each element states: no setting is shared by all
twelve, not even the convention or the pillar settings. So the segment row
keeps only what every element has, its definition, its type and its place,
and each component of settings is a part of the segment keyed by its id: the
convention, the pillar rules, the projection curve, the tenor basis curves,
the cross currency terms, the reference curve, the weighted average, the
discount ratio, the flat extrapolation flag and the ibor fallback. A shared
component is one part rather than a column repeated on a part per element,
because the pillar rules are the same three rules wherever they appear.

The projection's =import_segments= is the one statement of which element has
which part: each element's loop calls one reader per part. The section
generator follows those calls, so the screen's leaves name the part each is
in, and it writes the SQL functions each part's trigger calls to refuse a part
its segment's element does not have. The export takes each segment's parts
from an index and refuses a part of the wrong element, a part of no segment
and a second row of one part. A part of optional fields is written only when
the element states one of them, so no part row is empty.

The ORE round trip of every corpus file and of every element is unchanged,
the live Acme publish stores 35 segments with 35 convention parts and no
other part, and the database refuses a part on the wrong element.

The component audit: =validate_docs.sh= passes for all 39 components. The ten
parts are refdata entities of the shape =curve_segment_curve= already has, a
child keyed by the segment's id, so no component gains a part or a boundary;
the ore projection, the document service, the shell aggregator, the SQL lists
and the BFF only name the new entities.
