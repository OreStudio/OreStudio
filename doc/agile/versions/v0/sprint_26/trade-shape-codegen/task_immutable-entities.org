* Result

A model declares =:immutable: true= in its =* SQL ** Flags= drawer. The
generator refuses it unless the drawer also says =:current_state: true= and
the =* Flags= drawer =:read_only: true=: only a current-state table has one
row per key, and only a read-only entity has no derived write verb that
would ask the store to change a row.

The table gets a =_immutable_trg= trigger that refuses every update and
delete with SQLSTATE 55000, and the drop script removes it. The repository
writes with =sqlgen::insert= instead of =insert_or_replace=, so a second
write of the same key fails on the primary key instead of overwriting.

The generated C++ still has its =remove= methods. The store refuses them
and =:read_only:= keeps every delete verb off the wire, so no client
reaches them; removing them would touch the repository, the service and the
generated tests for no behaviour gained.

Evidence: =test_immutable_entity.py=, seven cases, including the two
refused flag combinations and the mutable control. The rendered DDL was
run against the development Postgres in a rolled-back transaction: the
first insert succeeded, a duplicate key, an =UPDATE= and a =DELETE= were
each refused, and the row was unchanged. The codegen suite is 1088
passed; the drift dry run changes no generated file apart from the
known =clang-format= wrapping in =trade_service.cpp=.
