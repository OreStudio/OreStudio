* Acceptance

- The installation screens have a read of their own that a tenant's wildcard does not grant, the server guards them by that read, and the menu and cards draw them by it, not by the session mode
- The table How today's menu differs on the menu structure page is empty

* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

- Name the read =installation::deployment:read=, in a component the wildcard =*= does not cover, so a tenant's administrator does not hold it. Grant it to the super administrator role by name.
- State the rule once for the services (=grants= in =ores.security=) and once for the browser and the BFF (=permissionCovers= in =@ores/contracts=), with the same tests.
- The BFF refuses a deployment route by that read, read from the caller's roles on each call, and no longer by the session mode.
- The menu and the cards ask for the read and no longer take a scope or a mode. The page states the rule.

* Notes

- The BFF reads the caller's roles for each guarded call, one more NATS read each time. A grant the caller lost stops the next read. If this shows up in a profile, the roles can be cached for a short time.
- The services behind these routes (tenant list, telemetry, grid) still check their own permissions or none. The BFF is the guard this task adds, as the mode guard was. A service-side check of the new read is a separate piece of work.
- Seven BFF guards changed: the tenant list, one tenant, a tenant's inside reads, the overview, a tenant's removal, and the four Operations reads. A tenant's parties route keeps its refusal of system administration, which is a different rule.
- =actsOnDeployment=, the =scope= field of a menu entry or card, and the =mode= props of the area pages are gone.
- The fake clients in five BFF test files now answer the caller's roles: the deployment read for a system administration session, and =*= for any other, which is the case that must be refused.

* Result

The installation screens are drawn and served by a read of their own.

- =installation::deployment:read= is seeded and granted to the super administrator role by name. The wildcard =*= does not cover it, in the services, the BFF and the browser.
- Tenants and the Running services, Compute grid, Message bus and Telemetry logs cards ask for it. The BFF refuses the routes behind them without it.
- The menu structure page states the rule and its table of differences is empty. The role-based access control page states the exception to the wildcard.

Evidence: the BFF suite (62 files, 674 tests) and the web suite (105 files, 1148 tests) pass with new cases for the wildcard exclusion, the typechecks and Prettier are clean, the permission is present and granted after a database recreate, and the populate reference and handler permission checks pass.

The two new cases for the C++ rule were run from a direct compile of =authorization_grants_tests.cpp= against the build's Catch2 (7 cases, 14 assertions pass), not through the queued cmake target. The edited IAM service file passes a syntax check with the build's own flags.

Not done here: a service-side check of the new read, and a test that signs in as a tenant administrator against a running stack.
