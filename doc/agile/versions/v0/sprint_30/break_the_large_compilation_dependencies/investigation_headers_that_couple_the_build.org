A point-in-time record of the include-graph analysis commissioned by
[[id:2E186CC8-BA83-4271-8EF0-DE2465994A8D][Find the headers that couple the build]]
under the story
[[id:2B6612F6-D9F8-4DFF-8952-61716D22C2CF][Break the large compilation dependencies]].

* Context

A change to one header rebuilt most of the tree, and the publish lifecycle work
found the case: =ores.database/domain/context.hpp=. It is included by most
repositories and services. Through it each of them parsed =libpq-fe.h=, the
pool, =<mutex>= and =<condition_variable>=, although most only pass a context
along.

The story assumed that cost came from libpq and the pool. This investigation
measures the build's include graph and the parse cost of each header, and it
tests that assumption. It does not hold: =libpq-fe.h= costs 0.04 s to parse and
=context.hpp= costs 6.6 s. The bulk arrives another way, through the decimal and
text-form codec headers that =pq/transaction.hpp= pulls in.

The answer the story needs is therefore two lists, not one. A header reaches
many objects, or it costs a lot to parse, or both; the work order must weigh
both.

* Methodology

Two instruments, both kept beside this investigation in =evidence/=, and both
driven by the build's own records so they rerun on any commit.

| Instrument | What it reads | What it answers |
|------------+---------------+-----------------|
| =header_blast_radius.py= | =ninja -t deps=, plus the source text of every =#include= | how many objects and targets rebuild when a header changes, and through which include chain |
| =header_cost.py= | =compile_commands.json= and clang =-ftime-trace= | what a header costs to parse, alone and inside a real translation unit |

Run them with:

#+begin_src sh :results verbatim
python3 evidence/header_blast_radius.py \
    --build-dir build/output/linux-clang-release-ninja --top 30

python3 evidence/header_cost.py headers \
    --build-dir build/output/linux-clang-release-ninja --runs 5 \
    --header ores.database/domain/context.hpp

python3 evidence/header_cost.py sample \
    --build-dir build/output/linux-clang-release-ninja --count 14

python3 evidence/header_cost.py compare \
    --build-dir build/output/linux-clang-release-ninja --runs 4 \
    --shadow "projects/ores.utility/include/ores.utility/uuid/tenant_id.hpp:string_generator.hpp"
#+end_src

- =export.hpp=, =severity_level.hpp= and =wire_traits_fwd.hpp= are read by most

* The cost is a chain, not a list

Three chains carry nearly all of the header cost. That structure, not the
individual rows, is what the decisions must break.

** The codec chain

=decimal.hpp= (4.03 s, boost multiprecision) is included by =text_form.hpp=
(4.99 s), which adds =boost/asio/ip/address.hpp=, =boost/lexical_cast.hpp=,
=<filesystem>=, =<format>= and =magic_enum=. =protocol_codec.hpp= (6.15 s) and
=json_codec.hpp= (4.95 s) then include =text_form.hpp= so that each text form
can be defined inline.

Everything below that inherits the chain:

- 638 generated =*_protocol.hpp= headers, each of which includes
  =protocol_codec.hpp=. In the sample a unit that reads one pays 0.5 to 1.5 s
  for it.
- =context.hpp=, through =pq/transaction.hpp= (145 ms own) → =pq/statement.hpp= →
  =pq/codec.hpp= → =decimal.hpp=.

** The clock chain

=<chrono>= costs 2.32 s, and C++23 pulls =<format>= and =bits/chrono_io.h= with
it. Two doors open it: =datetime.hpp=, which needs it by value, and
=boost/uuid/uuid.hpp=, which includes =uuid_clock.hpp= and =<chrono>= itself. So
every translation unit that names =boost::uuids::uuid=, which includes every one
that reads =tenant_id.hpp=, pays it.

** The logging chain

=make_logger.hpp= (3.87 s) includes
=boost/log/sources/severity_channel_logger.hpp= (3.58 s) to declare one typedef,
=logger_t=. Every translation unit that logs pays it: 565 objects in 189
targets.

* The include chain behind =context.hpp=

The trace of a translation unit that reads only =context.hpp= puts its 6.38 s
here:

| ms | File |
|---|------|
| 406 | =c++/16/format= |
| 379 | =boost/math/special_functions/lanczos.hpp= |
| 246 | =c++/16/chrono= |
| 199 | =boost/multiprecision/detail/default_ops.hpp= |
| 145 | =ores.database/pq/transaction.hpp=, its own body |
| 135 | =c++/16/bits/stl_bvector.h= |
| 122 | =c++/16/bits/chrono_io.h= |
| 110 | =boost/multiprecision/cpp_dec_float.hpp= |

The chain is =context.hpp= → =pq/transaction.hpp= → =pq/statement.hpp= →
=pq/codec.hpp= → =decimal.hpp= → boost multiprecision, and
=context.hpp= → =tenant_id.hpp= → =boost/uuid/uuid.hpp= → =<chrono>=. =libpq-fe.h=
does not appear in the first fourteen rows.

So the task's stated fix, keeping libpq and the pool out of =context.hpp=,
saves far less than the premise predicted. It is still right, because a header
that only names a type should not include it, but the larger win in the same
header is the codec chain behind =pq/transaction.hpp=.

* Cycles and cross-component includes

- Include cycles among project headers: none. The graph is a DAG, so forward
  declarations within it are safe.
- Includes of another component's =src/= tree: none, in 0 of the 52075 edges.
  The component boundaries hold, so no decision here is blocked by a leak.
- The heaviest cross-component edges are ordinary library use:
  =ores.refdata= → =ores.utility= (5058 edges), =ores.refdata= →
  =ores.database= (3500), =ores.trading= → =ores.utility= (3322).

* Decisions, one per header family

| Header | Decision | Reason |
|--------|----------|--------|
| =ores.utility/codec/text_form.hpp= | *Move* the text-form definitions to a =.cpp=, leaving declarations | The forms are defined inline so each =text_form= is visible to the codec; doing so costs 4.99 s on 715 objects. The abandoned task [[id:8856431C-F316-423C-B142-FAC42D87B1AC][Keep the codec headers light]] proposed this and was not carried out. |
| =ores.utility/domain/protocol_codec.hpp= and =ores.utility/codec/json_codec.hpp= | *Keep*, but lose the inline text forms with the row above | Both are template code that must see the encode/decode interface. Their own cost falls with =text_form.hpp=. |
| =ores.utility/decimal/decimal.hpp= | *Keep* for now; record the split as a candidate | =cpp_dec_float_50= is a by-value member and the arithmetic operators are inline over it. Hiding it behind a pointer would remove 4.03 s from 831 objects and cost every arithmetic call an indirection. This needs its own measurement. |
| =ores.logging/make_logger.hpp= | *Split*: hold the logger behind a small handle, so the typedef does not need Boost.Log's sources | One typedef pulls 3.58 s into 565 objects. The call sites already go through a macro. |
| =ores.utility/uuid/tenant_id.hpp= | *Move*: drop the unused =<boost/uuid/string_generator.hpp>= include | Nothing in the header uses it; the =.cpp= already includes it itself. Measured saving 0.69 s on 837 objects. |
| =ores.utility/serialization/error_code.hpp= | *Move* the two inline functions that call =magic_enum= into the =.cpp= | =operator<<= and =to_string= are the only users. Removing the include alone does not compile, which the A/B run proved: the fix is to move the code, not the line. |
| =ores.database/domain/context.hpp= | *Forward-declare* =pq::pool=, =pq::transaction= and =pq::session_context=; *move* =connection_options= and =open_policy= to a small header; *hide* =pq_slot= behind a pointer to an incomplete type defined in the =.cpp= | This is the story's known case. It removes libpq, =<mutex>= and =<condition_variable>= from 365 objects. The larger remaining cost in the same header is the codec chain behind =pq/transaction.hpp=. |
| =ores.database/pq/connection.hpp= | *Move* =connection_options= out; *keep* the rest | The rest needs libpq to name =PGconn=. |
| =ores.database/pq/pool.hpp=, =pq/transaction.hpp=, =pq/statement.hpp=, =pq/codec.hpp= | *Keep* their own types; lose the family's cost as =decimal.hpp= and =context.hpp= change | These are the implementation of the database component, and a caller that names them uses them in full. |
| =ores.platform/time/datetime.hpp= | *Keep* | =<chrono>= is needed by value in its own inline functions, and =std::chrono= types cannot be forward-declared. |
| =ores.utility/codec/wire_fields.hpp=, =member_count.hpp=, =wire_traits_fwd.hpp= | *Keep* | Template metaprogramming over =<tuple>= and =<type_traits>= only; 0.02 to 0.34 s for 789 to 813 objects. There is nothing heavy to remove. |
| =ores.logging/severity_level.hpp=, =boost_severity.hpp=, =ores.utility/export.hpp=, =ores.platform/export.hpp= | *Keep* | 0.03 to 0.05 s each. Reach without cost is not a problem. |
| =ores.utility/domain/protocol.hpp= | *Keep* | Plain data structures over =<string>=, =<vector>=, =<optional>=; 0.96 s for 562 objects. |
| 638 generated =*_protocol.hpp= | *Regenerate* after =cpp_protocol.hpp.mustache= changes; never hand-edit | A hand edit does not survive regeneration. |

* Order of work

By the object-seconds table, with the chain respected so one change is not
undone by the next:

1. =text_form.hpp=: move the text-form definitions into a =.cpp=. Removes about
   3568 object-seconds and shrinks =protocol_codec.hpp= and =json_codec.hpp=
   with it.
2. =protocol_codec.hpp= and =json_codec.hpp=: declare only what they must, now
   that the forms are out of line. Another 2400 object-seconds fall out of the
   same change.
3. =tenant_id.hpp=: delete the unused include. 0.69 s on 837 objects, no design
   change, so it can ride in the same PR as anything else.
4. =error_code.hpp=: move the two =magic_enum= users to the =.cpp=.
5. =make_logger.hpp=: split the logger handle. This needs its own task, because
   it changes every call site.
6. =context.hpp= and the =pq= family: the story's known case, on the corrected
   understanding that libpq is cheap and the codec chain is not.
7. =decimal.hpp=: only after its own measurement of the pointer-indirection
   cost. The exactness is a domain requirement, so this decision is a trade-off
   and not a clean win.

Steps 1 and 2 are one PR: they are the same decision applied to the headers that
share it. Step 7 is a candidate, not a commitment.

* Paths taken

- The first cost instrument used =clang -fsyntax-only -ftime-trace=<path>=. It
  reported zero for every header. Clang writes the trace only for a real
  compile, so the probe now compiles to an object and reads the =.json= beside
  it.
- The trace groups its events by category, not by time. Pairing the begin and
  end events in file order put every span at nesting depth one and reported 48 s
  of a 7 s compile. Sorting the events by timestamp first fixes it.
- The first A/B removed an include by copying the header to a shadow tree that
  mirrored the whole repository path. The =#include= then resolved to the real
  header, so the measurement compared the header with itself and reported a
  saving of zero. The shadow now mirrors only the part the include path
  resolves.
- Removing =magic_enum/magic_enum.hpp= from =error_code.hpp= does not compile,
  because two inline functions call it. That result is the point of the
  evidence: it turns an opinion into a fact, and it moves the decision from
  *delete the include* to *move the functions*.

* Conclusions

- Reach and cost are different questions and this build answers them with
  different headers. The most widely included headers are free; the most
  expensive ones reach a third to a half of the build; two are both.
- The cost is carried by three chains: the codec chain rooted in
  =text_form.hpp= and =decimal.hpp=, the clock chain opened by =datetime.hpp=
  and =boost/uuid/uuid.hpp=, and the logging chain opened by =make_logger.hpp=.
- The story's premise is wrong about the cause and right about the fix. libpq
  costs 0.04 s. =context.hpp= is expensive because of the codec and clock chains
  behind =pq/transaction.hpp= and =tenant_id.hpp=.
- A single unused include in =tenant_id.hpp= costs every one of 837 objects
  0.69 s. This is the cheapest change in the whole analysis and needs no design
  decision.
- The include graph is a DAG and no component includes another's =src= tree, so
  no decision is blocked by a cycle or a boundary leak.
- Codegen output is 94% of the project headers by count and none of the top
  twenty by reach. One template change reaches all 638 protocol headers.

* Recommendations

- Carry out steps 1 to 4 as one PR series under
  [[id:DEA440DD-F4B6-4D37-9083-5F3BB33F1018][Forward-declare what the analysis finds]], in the order given. Steps 1 and 2
  prove the instrument as well as the fix: the same measurement before and after
  states the effect.
- Re-run both scripts after each step and record the result beside this one, so
  the ranking stays a measurement and not a memory.
- Keep [[id:908E710A-C9A3-433E-AC93-92B67FB76B6C][Pass the database context by reference behind a forward declaration]] as
  written, and add the codec chain behind =pq/transaction.hpp= to its scope. On
  the measured numbers the forward declarations are the smaller half of its
  gain.
- Make the forward-declaration check that the story asks for read the type list
  this analysis produced. A type joins the check by adding a line.
- Do not change =decimal.hpp= before measuring what the pointer indirection
  costs at run time. It is the only decision here that trades correctness risk
  for compile time.
