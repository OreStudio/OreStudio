* Goal

Signed in as the super administrator, the deployment's own world is real and named: the administrator is greeted by a human name and shown a picture, and the system administration area lists the accounts the installation runs on — the platform's service accounts among them.

The analysis behind the story: of the super administrator's journeys, first run, new tenant, the roster, the tenant screen and acting inside a tenant are built, and retire or reset and the operations journeys are their own sprint 27 stories. The legacy Qt application kept the deployment's own accounts on a first-class screen, under Operations > User Accounts, and the web's system administration area holds only the roster. What remains is the super administrator's own sight of the deployment, and this story lands it.

* Decisions

- The deployment's own accounts are read as the session's own tenant, the
  ordinary accounts read, with no cross-tenant read added. The session's
  tenant is the system tenant for a super administrator, so the read
  already answers with the deployment's accounts.
- The system administration menu gains the accounts entry, revisiting the
  accepted navigation prototype's Tenants-only menu.
- The first run keeps its three fields (username, email, password); the
  creation paths record the administrator's name with a default.
- The administrator pictures are the product's own, so their template keys
  live in the provisioning code as constants, not in the seed profile's
  arguments; the parties' datasets stay the profile's data.
- The administrator pictures are the platform's system avatars, not ACME
  data, so they ship as the assets.system_avatars dataset: a base-bundle
  member, so ACME, GLEIF and every other bundle consumer installs it, and
  published to the system tenant at database build time because the super
  administrator's account lives there.
- The DQ image pipeline carries the live table's own (mime_type, data)
  shape rather than SVG text, so an SVG document and a raster picture
  stage alike and the pipeline holds no format knowledge.
- The super administrators are the system tenant's SuperAdmin holders, the
  rule the bootstrap service already uses, and each picture is written
  through a token minted for that account rather than a direct write.

* Result

Done at sprint 27. The audit task merged with PR #2663, and the three
delivery tasks merged after it: the accounts with PR #2667
(=3a14832191=), the names with PR #2669 (=977ca8945d=), and the pictures
with PR #2671 (=22a01d5bb9=). Every acceptance holds:

- The system administration area reads the deployment's own accounts, the
  service accounts among them. Yes: the accounts lead serves the
  system-administration screen alone, and each row shows the account it
  is.
- The initial administrator and a provisioned tenant's administrator carry
  human names, and every surface that greets or names a person prefers the
  name. Yes: each name is stated once in production code, and the web
  falls back to the username.
- The two administrator avatars are part of the seeded pictures. Yes in
  the tree: =assets.system_avatars= is a base-bundle member published to
  the system tenant, and the =attach_photos= step attaches both pictures.
  The live proof needs a rebuild, a service deploy and the destructive
  database recreate, and stays with the operator.

The run evidence: the debug build completed exit 0 with every target
built, and ctest passed 40 of 94 tests. The other 54 refused to start
because the development database does not match the build (fingerprint
cbe0f2224158b690 expected, 7f079ef54352500a found), which the pictures
task records; the fix is the operator's =compass db recreate=.
