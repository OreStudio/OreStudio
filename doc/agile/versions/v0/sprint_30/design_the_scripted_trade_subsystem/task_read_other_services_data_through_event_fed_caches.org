* Goal

No service's C++ reads another service's tables or functions. Data a service
needs from another is held in an entity-mirror cache, declared with =cached_by=
on the owning entity's model, filled from the owner's list operation and kept
fresh by its change events. SQL triggers and functions may read another
component's tables, as they validate a row in its own transaction.

* Acceptance

- trading's blotter rail (=trade_summary_repository.cpp=) reads books, portfolios and instrument codes from caches rather than joining refdata's tables
- iam's =tenant_session_service.cpp= takes the visible parties and the system party from refdata through a cache or refdata's operation, not by calling refdata's SQL functions
- reporting's =engine_settings_proposal.cpp= reads approval requests through inbox's operation or a cache, not from inbox's table
- scheduler's =mq_action_handler.cpp= sends through mq's interface, not by calling mq's SQL function, or the call is recorded as an allowed kind with its reason
- reporting's engine settings proposal asks =ores.ore= for a setting's verdict, rather than calling =ores_ore_setting_value_verdict_fn=, and holds no copy of the rule
- each cache is generated by the nats-event-cache facet and placed as entity_mirror_cache_placement states
- a check reports any hand-written C++ of one component whose SQL names another component's table or function; SQL triggers and functions are out of its scope

* Notes

Raised while planning [[id:6E4060D6-DF49-44C9-97E3-6CDB8F6954C3][Describe every product by its schema]], which reads the ORE
metamodel through an entity-mirror cache rather than in SQL.

The rule, from the user on 2026-11-22: a service's C++ does not read another
service's tables or functions; a SQL trigger or function may, because it
validates a row in the row's own transaction. So refdata's convention term
validation, which reads reporting's element map, vocabularies and value set
functions, and analytics' parameter value trigger, which calls
=ores_reporting_validate_parameter_value_fn=, stay as they are; the move of the
metamodel to =ores.ore= repoints them.

A scan on 2026-11-22 of hand-written C++ found four reads, and the move of the ORE parameters made a fifth, of another component's
tables or functions:

| Read | Where | What it reads |
|------+-------+---------------|
| trading's blotter rail | =projects/ores.trading/core/src/repository/trade_summary_repository.cpp:710-727= | refdata's instrument codes, books and portfolios |
| iam's tenant session | =projects/ores.iam/core/src/service/tenant_session_service.cpp:226,283,294= | =ores_refdata_visible_party_ids_fn=, =ores_refdata_read_system_party_fn= |
| reporting's engine settings proposal | =projects/ores.reporting/service/src/service/engine_settings_proposal.cpp:581= | =ores_inbox_approval_requests_tbl= |
| scheduler's MQ action | =projects/ores.scheduler/core/src/service/mq_action_handler.cpp:65= | =ores_mq_messages_send_fn= |
| reporting's engine settings proposal | =projects/ores.reporting/service/src/service/engine_settings_proposal.cpp:172= | =ores_ore_setting_value_verdict_fn=, which became =ores.ore='s when the parameters moved |

The scan matched =ores_<component>_*_tbl= and =_fn= names in hand-written,
non-generated C++ under each component's =src=, leaving out the shared utility,
outcome, DQ and IAM functions.
