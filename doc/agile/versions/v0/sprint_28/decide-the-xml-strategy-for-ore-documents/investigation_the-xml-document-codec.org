#+title: Investigation: What the XML document codec should be
#+description: What an XML layer that turns an ORE document straight into ORE Studio records looks like, and what a measured prototype says about its speed, memory and fidelity against the generated xsdcpp binding.
#+type: investigation
#+level: s1

A point-in-time record, written while [[id:36BA97C5-F6F8-4101-9141-40390B35237A][the story]] was open, of an
investigation into how ORE XML should become ORE Studio records.

The prototype it describes is throwaway. It exists to answer one question
with measurements instead of opinion.

* Context

ORE XML crosses the boundary at two seams: =ores.ore.core.xml.importer= on
the way in and =ores.ore.core.xml.exporter= on the way out. Both reach C++
through a binding generated by =xsdcpp=, a sibling checkout that is not
vendored, not in =vcpkg.json=, not in CMake and not on PATH.

The bond review found the first defect of that arrangement. Whenever ORE's
schema types a money element as a bare =xs:float=, the generated binding maps
it to a C++ =float= (=Generator.cpp=, lines 405-406). =StrikeData/Value= and
=settlementData.dv01= are such elements. The document's digits therefore pass
through a 32-bit binary value before any mapper sees them, and no mapper can
put back what the float dropped. Three fields keep their digits only by
accident: their elements carry an attribute, which forces the generator to
build a class, and that class happens to derive from =xsd::base<T>=.

Three costs follow from the same structure, and none of them can be fixed in
a mapper.

- *Fidelity.* The digits are gone before the boundary is crossed.
- *Cost.* The generated DOM is an object graph. Every present optional leaf
  is a =new T=. Every repeated child container is a =new std::vector<T>=,
  even when the document contains no such child.
- *Ownership.* About 122,000 generated lines decide the shape, split between a
  13,500-line =domain.hpp= and a 4.3 MB =domain.cpp=, and about 830 KB of
  hand-written mapper across 21 files decide the meaning. Neither can be
  checked against the other, and the regeneration that would refresh the
  first is blocked by drift on =trade= and =componentSubTrade=.

The question this investigation answers: what should that layer be?

* The shape the guidelines dictate

The [[id:BBD43BF2-9FEE-42B0-A667-9468AF759DC2][data-oriented design
guidelines]] place this payload outside the three regimes. Their own words:
document-shaped payloads sit at the boundary of the stack, where a mapping
layer converts them to and from the core data model, and "the document tree
is transient; the entity representation, designed for performance, is the
review target."

That inverts the usual instinct. A good XML layer for ORE Studio is not a
good XML library. It is a *conversion pipeline* whose only observable output
is records shaped like the entity model. Three rules come out of it.

- Never materialise a general document tree. Every node kept is a copy that
  was not needed.
- The document buffer is the only input storage. A value is a span of that
  buffer until something outside the boundary demands a copy.
- A value crosses the boundary once. It is read from text by a decimal
  parse, never through a binary float.

The axioms then say how to build the pipeline.

| Axiom | What it means here |
|-------+--------------------|
| Access patterns drive layout | The layout is the entity layout, not the document layout. |
| SoA over AoS | Repeated records are one contiguous run per field group, not a node per element. |
| Separate hot from cold | The scanner is hot. The schema tables are cold and const. |
| Handles over pointers | Element names become schema-derived integers, not strings compared at run time. |
| Batch over per-object | One sink call per completed record, not one per element. |

* Methodology

Three sources of evidence, each one rerunnable.

- *A prototype.* =prototype/= holds a scanner, a table-driving codec and a
  benchmark with eight labelled variants behind one switch. =prototype/run.sh=
  regenerates the tables, builds the probe and prints every number this page
  quotes, into =prototype/RESULTS.txt=. The numbers below are that file's; if
  the two disagree, the file is right.
- *The corpus.* =prototype/corpus.cpp= reads every XML document under a set of
  roots and reports what it rejected. It runs over =external/ore=,
  =assets/test_data=, =doc/agile=, =external/fpml= and =external/fix=.
- *The existing tools.* =scripts/validate_ore_examples.sh= validates a tree
  against =external/ore/xsd/input.xsd= with =xmllint=. It is the bar the corpus
  already meets, and the bar the writer has to keep.

The environment is =swift_curie=, preset =linux-clang-release-ninja=, on a
machine shared with eleven other worktrees, so timings move by up to a third
between runs. The allocation counts do not move, and the argument rests on
them.

* Paths taken

** Route A: keep the generated binding and extend it

The machinery partly exists. =domain_xsd.hpp= carries a hand-patch, reapplied
by =scripts/reapply_ore_lexical_form.py=, that gives =xsd::base<T>= a lexical
string for floating-point T. Extending it to every numeric leaf needs a
generator change and a parser change.

This route keeps all three costs and adds a fourth: the fix lives in a
checkout this repository does not own. Every future ORE schema change, every
extension and every bug fix lands there, and the regeneration that applies it
is currently blocked. It is the cheapest route to state and the dearest to
live with.

** Route B: adopt a document library

Five candidates were weighed.

| Library | Shape | Reach for it when | Reject it here because |
|---------+-------+-------------------+------------------------|
| pugixml | DOM, ~35 bytes a node | you want a tree, well tested, already a dependency | the tree is thrown away, and one allocation per node is the cost we are trying to remove |
| RapidXML | in-situ DOM | throughput matters more than maintenance | unmaintained since 2010, and it mutates the buffer |
| Expat | SAX callbacks | you want a mature streaming parser with no tree | a per-event callback is the interface this design already has, with a layer of C on top |
| libxml2 reader | pull parser | you need XPath, encodings, recovery | heavy dependency for a subset we can state in full |
| simdxml | SIMD structural index | you query multi-gigabyte documents | Rust with no C++ binding, and its win is XPath over corpora we do not have |

pugixml is the credible one and it is already linked into =ores.refdata=. It
was measured, not dismissed. It solves scanning and nothing else. The
mapping, the presence bits, the exact decimals and the writer remain ours,
and it builds a tree we would discard.

** Route C: own scanner plus generated tables

The prototype. It was built to settle three numbers: how fast the scan can
be, how few allocations a document can cost, and whether a table can carry
the mapping.

* The design

** Four structures

- =field=. One element or attribute of one schema type: name, name hash,
  value kind, byte offset, presence bit, enumeration spellings. 32 bytes,
  =const=, generated.
- =record_type=. The field array for one schema type.
- =document_type=. Root element name, item element name, item record type.
- *Record layout.* A plain struct whose first member is a =uint16= presence
  bitmask.

Adding a field is one line in a table. There is no per-field code, in either
direction.

** The scanner

A zero-copy pull reader of about 300 lines. It returns
=event{kind, name, value}=, where the name and value are =string_view=s into
the document buffer.

It allocates nothing per event. It reserves one scratch buffer once, for the
rare value that carries an entity reference. It keeps an explicit stack of
open element names, 64 deep, instead of recursing. It tracks no line numbers
in the hot path: =line()= and =column()= count newlines to the error offset,
once, when an error happens.

The subset is stated rather than assumed: elements, attributes, text,
comments, processing instructions, CDATA, and the five predefined entities.
A declaration, a depth over 64, or a mismatched end tag is rejected with the
line and column. That is the whole of what ORE writes.

** Names become integers

The schema knows every name it will ever write. The generator hashes each
element and attribute name with FNV-1a at generation time and emits the hash
next to the literal. A lookup compares a 32-bit hash and then the bytes.

A type today has at most a few dozen children, so a linear probe over
precomputed hashes is enough. The generator is the place that changes when
that stops being true: it knows the whole set and can emit a perfect hash
instead. This is the difference between a table and an interpreter: the
lookup cost is a property of the table, and the table is generated.

** Presence, not optional

A record carries a =uint16= bitmask. Bit n says field n arrived. An absent
integer stays zero and an absent string stays empty; the bit is what tells
"not in the document" from "written as zero".

This deletes =xsd::optional= and the =new T= it performs for every present
leaf. It also deletes the ambiguity that =std::optional<std::string>= leaves
in the model, where an empty string and an absent one are the same value.

** Two layouts, one table

The same field array drives two record layouts. In one, text is a
=std::string= owned by the record. In the other, text is a =std::string_view=
borrowing the document buffer.

=offsetof= is what makes this work: the table records where a member sits in
a named layout, and the engine is templated on a policy that names the layout
and says how a value lands in it. The layout is a parameter, the mapping is
data, and neither is duplicated.

The borrowed layout is the one the DOD reading asks for. It holds only
integers, views and a bitmask, so a whole document costs one allocation for
the output vector and one for the scanner's scratch buffer.

** The writer is the same table

Writing walks the same field array in the same order, emits only present
fields, formats integers with a bounded decimal writer, escapes only the five
XML characters, and appends to one reserved buffer.

One direction cannot drift from the other because there is only one table.
The round trip in the prototype is identical at the record level.

** What the table cannot say

Defaults, unit conversion and derived fields stay hand-written. In the sample
document, mapping ORE's =Metal= and =Crypto= currency types onto a monetary
nature is a hook.

The claim is not that the mapping disappears. It is that the *mechanical*
part of it becomes data that a generator can check against the schema, and
the semantic part becomes a short function a reviewer can read.

** Where exact money enters

A =decimal_text= field kind stores the document's own digits as a span. No
float exists on that path at all. The span is parsed exactly once, into
=ores::utility::decimal::decimal=, which is the type the rest of the model
already uses.

This is the guideline's one-way numeric conversion rule, enforced by the
shape of the codec rather than by a convention.

* Evidence

Everything below is printed by =prototype/run.sh= and captured in
=prototype/RESULTS.txt=. Times are the best of seven runs on
=swift_curie=.

** One document end to end

=external/ore/examples/Input/currencies.xml=, 63,341 bytes, 179 records.

| Path | Time | Allocations | Bytes |
|------+------+-------------+-------|
| xsdcpp DOM then the hand-written mapper | 1.28 ms | 4,674 | 526,276 |
| pugixml DOM then the table | 0.13 ms | 446 | 35,904 |
| table codec, records own their strings | 0.19 ms | 535 | 156,432 |
| table codec, records borrow the buffer | 0.14 ms | 2 | 161 |
| scanner only, no records | 0.10 ms | - | - |

The three record-producing paths agree row for row on all 179 records. The
prototype was checked against the production path, not against itself.
The borrowed layout is not one of them: it reports a checksum of the fields it
read rather than a record set, because its records do not own the strings a
comparison would need.

Two readings, one of them uncomfortable.

- Most of the current path is not parsing. =load_data= alone costs 0.39 ms
  and 2,252 allocations. About two thirds of the 1.28 ms the whole path costs
  is the hand-written mapper, and the largest part of that is formatting a log
  line per record.
  That is a defect, it is unrelated to XML, and it inflates every comparison
  against the current path.
- The pull-event interface costs about 40%. The scanner alone beats pugixml
  on the documents that matter: 678 MB/s against 600 MB/s on 478 KB and 568
  against 465 on 6.3 MB. The full table codec is slightly slower than
  pugixml plus the same table. Folding the tokenizer into the interpreter
  removes the event struct and the call per event. That is a local, known
  optimisation, and it is the reason the prototype is a design probe and not
  a product.

** Parser throughput

| Document | Size | Scanner | pugixml | xsdcpp load |
|----------+------+---------+---------+-------------|
| currencies.xml | 63 KB | 638 MB/s | 1,330 MB/s | 162 MB/s |
| portfolio.xml | 478 KB | 678 MB/s | 600 MB/s | not measured |
| curveconfig.xml | 751 KB | 708 MB/s | 584 MB/s | 135 MB/s |
| conventions.xml | 945 KB | 655 MB/s | 543 MB/s | 154 MB/s |
| calendar_adjustments.xml | 6.3 MB | 568 MB/s | 465 MB/s | 234 MB/s |

pugixml wins on a document that fits in cache and loses by a factor of two
on the largest one, because on the largest one it is paying for its nodes.
The scanner holds 568-708 MB/s across the corpus. The machine is shared with
eleven other worktrees, so the times move by as much as a third between runs;
the allocation counts do not move at all, and they are the number this
argument rests on. This table is one run's values, printed by =run.sh= into
=RESULTS.txt=, and a rerun will print different milliseconds.

The =xsdcpp= figure for =portfolio.xml= is missing for an honest reason: the
built library in this worktree predates the checkout's =domain.hpp=, so the
generated =trade= layout the executable sees is not the one the library was
compiled with. Loading a portfolio crashes on that mismatch. Rebuilding the
tree takes about an hour and changes no conclusion here.

Throughput is not the constraint at ORE's document sizes. The largest
document in the corpus parses in 11 ms. Allocation, and the tree those
allocations build, are the constraint.

** Fidelity

Every numeric leaf in three real documents, compared against what a binary
value can hold. *Digits lost* means the decimal value itself changes. *Form
lost* means the value survives and the spelling does not: trailing zeros and
notation.

| Document | Numeric leaves | Digits lost via double | Digits lost via float | Form lost |
|----------+----------------+------------------------+-----------------------+-----------|
| portfolio.xml | 860 | 0.2% | 16.2% | 34.3% |
| curveconfig.xml | 2,101 | 0% | 0% | 99.0% |
| ois_portfolio.xml | 739 | 0% | 9.2% | 49.3% |

This separates two defects that the bond review ran together.

- Typing a money element as =float= loses digits for one value in six in a
  real portfolio. That is a wrong answer, and it is what =StrikeData/Value=
  and =settlementData.dv01= do today.
- Typing it as =double= keeps the value for all but two of the 860 leaves
  and loses the document's statement of it. A trading system that writes back
  =100= where the document said =100.00= has not corrupted a number, but it
  has changed a document, and a round-trip test cannot tell the difference
  without the lexical form. Those two leaves are the ones a double cannot
  hold, and they are why money is a decimal and not a double.

The codec removes both by never creating a float on the path.

** Order independence

=currencyDefinition= is an =xs:all=, so its children may arrive in any order.
Reversing the order of all nine elements in a document produces identical
records. A name-keyed table gets this for free; a positional mapper does not.

The first run rejected four documents and the reason is worth keeping. All
four are =ore.xml= files that contain =<!--> 1.D Other Pricing Parameters
<-->=, a comment opened and abruptly closed on its own line. XML forbids it

=-->=. The scanner ended the comment at the =>= of the opener and read the
rest of the line as markup.

The lesson is the corpus, not the bug. A subset asserted from reading a

* Writing

The round trip this design owes is not a reproduction of the document. It is
two properties. The values survive, and the output validates against ORE's
schema. Comments, indentation, element order within an =xs:all= and the
original spelling of a number are outside the contract, and dropping them is
what makes the writer cheap.

The bar is already set by the corpus.
=scripts/validate_ore_examples.sh= passes 1,623 of 1,623 documents against
=input.xsd= today, so the writer has to keep all of them valid, including the
output it produces for documents it has just read.

| Property | Required |
|----------+----------|
| Element names, nesting and attributes | Yes |
| Required elements, at their schema cardinality | Yes |
| Every value, numerically exact | Yes |
| Output validates against =input.xsd= | Yes |
| Comments, CDATA and processing instructions | No |
| Whitespace, indentation and attribute order | No |
| Order within an =xs:all= | No |
| The original spelling of a number | No |

Four decisions follow.

**One table, two directions.** The writer walks the same field array in
schema declaration order. That order is required for =xs:sequence= and is one
valid choice for =xs:all=. It emits only present fields, so absence survives
and the writer cannot invent an element the reader never filled. The two
directions cannot disagree because there is one table.

**Cardinality comes from the schema, not from the data.** The table records
=minOccurs=, =maxOccurs= and whether an attribute is required. That is what
lets the writer emit a valid document when a record is missing an optional
value, fail loudly when it is missing a required one, and repeat a child as
often as the schema allows. A writer without cardinality produces output that
validates by luck.

**Nothing may be silently dropped.** "No data lost" is only true if every
element the reader accepts has a home. Content the schema names and the model
does not claim is a generation error, because the table and the model are
generated from the same inputs. Content the schema does not name, the three
=xs:any= sites and anything ORE adds in a future schema, is captured into a
residual annex on the record and written back. The prototype skips it, and
skipping it is data loss with a quiet face.

**The writer is cheap because it does not look back.** One buffer, reserved
from an estimate and grown geometrically. Integers through a bounded decimal
writer. Escaping decided by one scan and applied only to text that needs it.
And it is parallel over record ranges for free, because records are keyed and
cannot refer to one another inside a document, so a large export writes N
buffers and concatenates them.

* Numeric accuracy

One invariant governs this work: a number that enters as text and leaves as
text means the same number to ORE before and after.

Three kinds, three rules.

- *Money.* A decimal, parsed from the document's digits, never through a
  binary float. Exact by construction, and the reason the
  [[id:36BA97C5-F6F8-4101-9141-40390B35237A][story]] exists.
- *Counts and integers.* An integer, parsed as one.
- *Continuous quantities.* A =double=, per the guidelines. Volatility,
  correlation, weight and day-count fraction stay binary. A double cannot hold
  every decimal, so "exact" here means the double round-trips to itself: the
  writer emits the shortest form that reads back to the same value.

**The field kind is not the schema kind.** ORE types money as =xs:float= in
some elements, as =xs:string= in one product and as =xs:double= in another.
Following the schema would reintroduce the defect the bond review found, one
element at a time. So the table's kind comes from two inputs. The XSD gives
the shape, and the project's money vocabulary gives the classification.

That vocabulary already exists and is already enforced, in
=build/scripts/check_money_decimal_columns.py= and in the =field_group=
models. The generator reuses it rather than inventing a second list, which
also keeps the XML boundary and the database boundary speaking about money in
the same words.

**The bound.** ORE reads those elements as =float= itself. A decimal we write
back is more precise than ORE can consume, so the round trip is exact inside
our model and bounded by ORE's on the far side. That is a property of ORE's
schema, not a defect in the codec, and it is the second reason the table
carries our classification instead of the schema's.

* The document layer, built

The first unit is in the product tree and measured. It is the layer that
replaces the generated DOM, and it is deliberately schema-free.

The pieces are =ores.ore.core/xml/scanner=, a zero-copy pull reader of about
500 lines, and =ores.ore.core/xml/document=, which holds one document as an
ordered tape of elements, attributes and text. A token is offsets into the
document's own buffer, so it is twenty bytes and building one copies no text.

Two properties of the tape matter.

- *It keeps the document's order.* Order is what made the original valid, so
  the writer needs no schema to produce valid output: it walks the tape.
- *It keeps nothing that carries no data.* Comments, processing
  instructions, CDATA boundaries and the whitespace between elements are
  gone. Whitespace that is the whole content of an element is kept, because
  that is the element's value.

**What it proves over the corpus**

| Property | Result |
|----------+--------|
| Documents read | 1,623 of 1,623 |
| Written back and compared equal | 1,623 of 1,623 |
| Written documents validating against =input.xsd= | 1,623 of 1,623 |
| Unit tests on the scanner and the document | 22 cases, 120 assertions |
| Decimals in the corpus that read and write as the same value | all of them |

The equality is data equality. Two documents compare equal when every
element, attribute and non-formatting text matches exactly, including the
digits of every number, and whitespace between elements is ignored.

The numeric test walks every text leaf that claims to be a decimal, reads it
with =ores::utility::decimal::decimal::from_string=, renders it back with
=to_string()= and reads that again. The two values must be equal, and no
corpus value may be refused. That is the format half of numeric accuracy: the
canonical renderer the export path will use is exact over every value ORE
ships.

**What it does not prove**

The tape never converts a number, so this layer cannot lose one. The other
half of numeric accuracy, text to a domain value and back, belongs to the
projection, and that is where the decimal classification of each field
matters. It is not proven yet.

**Two defects the corpus found that reading the schema could not**

Both were silent data loss, and both were in the scanner rather than in the
writer.

- A text node lost its leading whitespace, because the scanner skipped
  whitespace before deciding whether it was looking at markup. ORE's script
  libraries put indented code in CDATA, and every one of them came back
  shorter than it went in.
- A comment opened as =<!-->= is an abrupt close that XML forbids and ORE
  ships. The terminator search started inside the opener and ended the
  comment on its own first line, so the rest of the line was read as markup.

Neither would have been found by a test written from the schema. Both were
found on the first corpus run.

* Conclusions

0. *The entity path streams, and does not build the tape.* The benchmark
   settled this after the fact: the tape multiplies first-level misses by 4.5
   on the portfolio and 10.6 on the 6.3 MB file against scanning alone, and a
   projection into an entity record needs none of that traffic. The tape stays
   for the round trip, where the whole document is the point, and the
   projection fills records as the scanner walks past them.
1. *The generated DOM is the wrong artefact for this seam.* Not only because
   it is slow, though it is three to five times slower. Because it puts a
   parser's data structure between the document and the model, and the
   guideline that governs this boundary says the tree is transient.
2. *The mapping wants to be data.* A table can be checked against the XSD by
   constructing it. 800 KB of mapper can only be reviewed. The prototype
   generates its table straight from =currencyconfig.xsd= and
   =ore_types.xsd=, and the only thing the generator cannot derive is the
   C++ member name, which it snake-cases and then lets the compiler check.
3. *A scanner we own is cheap and wins where it counts.* About 300 lines,
   no dependency, and zero allocations per element. It does not beat pugixml
   at raw scanning on a small document. It does beat it on the measure that
   matters at scale, and it carries the exactness property that no library
   gives us.
4. *Exact money needs no machinery once the seam never produces a float.*
   The shape is a =decimal_text= field kind that carries the document's digits
   as a span. The prototype declares the kind and does not yet construct a
   =decimal=, so this is a design argument with a measured format rule behind
   it, not a working decimal path.
5. *The remaining cost is the interface, not the algorithm.* The pull event
   is a known, local optimisation with a clear direction.

* Recommendations

Adopt route C, in the order the tasks below set out. Keep =pugixml= as a
build-time tool for reading the schema and nothing more. Do not build a
general document library: no XPath, no run-time schema validation, no DOM.
State the subset and reject anything outside it. Measure per document family
so the allocation property stays true, and fix the per-record log formatting
on the import path because it is the largest single cost in the importer
today and has nothing to do with XML.

* How the work divides

The recommendation is to adopt route C, in the order below, and to remove
=xsdcpp= only when no document family depends on it. All twenty root
elements are in scope. The eleven with a mapper migrate; the nine without
are new models built on the same codec afterwards.

Thirteen tasks. Each is a pull request that leaves the tree working. Task 0
has landed, so the sequence below starts from a codec that already reads and
writes the whole corpus; what it cannot yet do is hand a document to a domain
type.

Four things about the order.

- Task 1 comes first because it is the gate every later task is measured
  against, and it is nearly free today.
- Task 5 comes before any family migrates, because a family that moves to the
  codec before the round-trip harness exists moves without a test that its
  data survives. The harness is what makes tasks 6 to 10 verifiable one at a
  time.
- Tasks 6, 7 and 8 each migrate one family completely: reader, writer, and
  the deletion of that family's mapper in the same change. The tree never
  holds two live implementations of one document.
- Task 11 is independent and should be taken early. It removes about two
  thirds of the current importer's cost without touching XML, and it makes
  every comparison after it honest.

Task 12 is last because the generated binding still serves every family that
has not moved. It cannot be removed while one root element is still read
through it.

* What this does not settle

- *=xsi:type= and =xs:choice=.* ORE's schemas use neither today, and =xs:any=
  appears three times. The codec skips unknown subtrees rather than
  preserving them. That is enough to import and not enough to round-trip
  content the schema does not name.
- *Namespaces.* The prototype ignores prefixes. ORE writes one unqualified
  document namespace plus =xsi=. A document that binds two prefixes to two
  namespaces would parse but not be distinguished.
- *The drift on =trade= and =componentSubTrade=.* Unresolved, and irrelevant
  to route C, which derives its own tables from the XSD and never touches the
  generated binding.
- *The schema-to-table generator at full scale.* The prototype generates one
  simple type. The real generator must handle nested complex types, repeated
  children, attributes, and the three =xs:any= sites. That is the main body
  of work in phase 1, and its size is not yet measured.
- *Whether the domain boundary wants borrowed records.* This analysis assumes
  records are materialised once per batch at the database boundary. If the
  insert path can consume views, the borrowed layout goes all the way and the
  per-value string copy disappears.
- *What the writer does with content the table cannot express.* A document can
  carry an element no field claims, because the schema says =xs:any= or
  because ORE added one. The reader skips it. The writer can only drop it or
  fail. Dropping silently is how the credit export came to lose a required
  element from seventeen documents, so the default must be to fail in tests
  and to count in production.
- *The nine root elements with no mapper.* They are in scope and sequenced
  last, but their domain models do not exist yet, so their size is a guess
  made from the document counts and the schema, not a measurement.
