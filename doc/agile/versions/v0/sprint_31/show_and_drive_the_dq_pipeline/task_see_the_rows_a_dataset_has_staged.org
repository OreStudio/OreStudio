* Goal

A dataset's page gains a Contents view: the rows its artefact table holds, paged,
so a person reads the data a publish would write instead of trusting a count of
it. The Qt Data Librarian never offered this: it read a dataset's own row and its
metadata, and left the staged rows to psql.

The view answers the question the coverage screen raises but cannot settle. A
member says "512,186 rows staged", and a person who has never seen one of those
rows cannot tell a correct catalogue from a plausible one.

* Acceptance

- A read over the bus answers the rows of one dataset's artefact table, paged,
  with the dataset named rather than the table: the caller does not know, and must
  not need to know, that a dataset's rows live in =ores_<artefact type>_artefact_tbl=.
- The read states the columns it answers as well as the rows, because every
  artefact family has its own columns and the screen cannot know them.
- The dataset's page draws them as a table with that heading, paged, so a family
  of half a million rows reads like one of twelve.
- The view is a read. Changing a row is
  [[id:88F9E5B4-20FF-4EEC-B8A0-97B35970E120][its own task]].
- A test reads the rows of a seeded dataset and asserts a known row and its
  column names.

* Notes

The hard part is not the read but the shape of the answer. There is one artefact
table per family, and each carries its own columns beside the two every family
shares, =dataset_id= and =tenant_id=. Countries carries =alpha2_code=,
=alpha3_code=, =numeric_code=, =name=, =official_name= and =image_id=; the next
family carries different ones. A screen that must draw any of them reads the
columns with the rows, and the store can state them: the catalogue already
describes every artefact type's table, and =information_schema= describes its
columns. The design decision this task owns is which of the two the answer
carries, and whether the read is one per family or one generic read over a
whitelisted table name.

Two limits worth stating in the design:

- A count and a page are not the same evidence. The count says how much exists;
  the page says whether it is right, and only for the rows it shows.
- A family of half a million rows is the case to design for, not the exception:
  =geo.ip2country= holds 512,186 in the provisioned environment.

The write half is
[[id:88F9E5B4-20FF-4EEC-B8A0-97B35970E120][Read and write an artefact row over
the bus]], which reads one row by key to correct it. This task reads many to look
at them. They share the read path and land in whichever order suits the sprint.

Asked for on 2026-11-26, after the coverage screens were reviewed. The Data
Librarian drew a lineage graph of a dataset and never its rows, which is the gap
this closes.
