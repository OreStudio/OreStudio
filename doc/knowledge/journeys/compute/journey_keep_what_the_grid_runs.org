This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A signed-in person reads the apps the grid may run, their versions and packages, and the concurrency policy that governs how many of a thing run together; a super administrator writes the catalogue.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want to know what the grid may run, and how much of it may run at once." The
person opens one screen and reads the apps the grid knows, the versions of each
app, the platforms each version is packaged for, and the concurrency policy that
governs a run when another run of the same thing is already in flight. A tenant
needs this before it submits anything, because the catalogue is what tells it
what it may ask for. A super administrator also writes the catalogue. The
journey is done when the person knows what may run, and, for the writer, when
the catalogue states it.

* Actor and trigger

Two things are true of this journey, and they do not split it. Reading the
catalogue is every signed-in person's: a tenant needs to know what it may
submit, so the reads admit everyone. Writing the catalogue is the super
administrator's: the version, the platform and the package are the
installation's, and a tenant does not publish them. That is one journey with a
permission on the write, not two journeys with two screens.

The catalogue rows are the installation's. The apps, their versions, the
platforms and the packages are a global registry: they live under the system
tenant and every tenant reads them, which is what
=:system_tenant_visible: true= states on the =app=, =app_version=,
=app_version_platform= and =platform= repositories. Their reads do not narrow
to the session's tenant, and the write does. The concurrency policy is shared
reference data of the same kind, seeded under the system tenant
([[id:5A5D6490-AF64-4AAF-8B3D-48EF3EDAF3D2][Tenant ownership and the
information flow]]).

The trigger is a submission: a person is about to dispatch a batch and needs to
know which app version and platform to name, or a super administrator has a new
engine build to publish. The journey ends when the catalogue has answered the
reader, or when the writer's change is stored.

This journey reads everything and writes the catalogue. A reader writes
nothing. A writer creates and retires apps, versions, platforms and packages;
the journey does not run a job.

* Steps

1. *Open the catalogue.* The person opens the screen. The system lists the apps
   the grid knows, each with its =name= and =description=, and, for each, its
   versions. Every session reads the same list, because the registry is the
   installation's.
2. *Read an app's versions.* The system states each version's
   =wrapper_version=, =engine_version= and =min_ram_mb=. The version is the
   engine build a job pins, and the memory it needs is the requirement a
   capacity plan reads
   ([[id:1E563104-6F89-4858-9395-D869A7E817A6][ores.compute.app_version]]).
3. *Read a version's platforms and packages.* The system states each platform
   row of the version: the platform's =code=, =display_name=, =os_family=,
   =cpu_arch= and =is_active=, and the package's =package_uri= and =sha256=.
   The wrapper downloads the package that matches its own triplet and verifies
   it against the digest, so the two fields are what the grid runs
   ([[id:E0010C05-D225-462B-A194-330F12A41B28][ores.compute.app_version_platform]],
   [[id:256097D3-ED41-40C3-99DC-C61C6B13E80A][ores.compute.platform]]).
4. *Read a version with no package.* A version whose platform rows carry no
   package can be dispatched and never run: the dispatcher stores the workunit,
   publishes no assignment, and the job sits unsent forever. The system must
   mark that version, because the catalogue is where the mistake is visible
   before a batch is wasted
   ([[id:1805BAFC-7E43-4D9C-822F-17C3455C6E00][Compute job lifecycle]]).
5. *Read the versions in flight.* The system draws a node-by-version matrix:
   which release is running on which node. The job's engine build is on the
   workunit's =app_version_id=, and the running wrapper's release and its host
   are on the service heartbeat, so the two halves of the matrix come from two
   reads
   ([[id:34CDC835-C72C-44F1-A0E2-B163014E0D74][ores.telemetry.service_samples]]).
6. *Read the jobs per release.* The system draws the jobs grouped by the
   release they pinned: one bar per =app_version=, each marked as its app's
   newest or an older one, and a count of how many jobs still run an older
   release. The job's release is the workunit's =app_version_id=, a fact about
   the work written when the job was stored, so the chart counts what actually
   runs and never guesses from the machine. The wrapper heartbeat carries the
   release and the host, so a node's running build is known; that build is the
   wrapper's, not the app version this job pinned, and the node sample carries
   the host and no release. A count above zero on an older bar is a half-finished upgrade,
   and the chart is where it shows. The newest release is the highest
   =engine_version= of the app, which is the version the submit handler already
   picks; *What is missing* states why the model should say so itself.
7. *Read the concurrency policy.* The system states the concurrency policy that
   governs a run of one definition when another is already in flight. The
   policy is reporting's: =skip= records the new run as skipped, =queue= lets it
   wait in the queued state, and =fail= records it as failed without executing.
   A report definition carries the policy code
   ([[id:4597D5A9-C591-4992-ABEE-8822C10D8D96][ores.reporting.concurrency_policy]],
   [[id:D4938956-1A5E-4F67-BCE8-7A951CE957E9][Report definition and schedule]]).
8. *Read how close a policy is to its limit.* The system draws the in-flight
   work against the policy's cap. The policy states a behaviour, not a number,
   so the screen must say what the cap is or that there is none. This panel is
   the one the use cases name and the data does not yet answer; *What is
   missing* states why.
9. *Publish or retire, a super administrator only.* The writer adds an app, a
   version or a platform row, attaches a package and its digest, or retires a
   platform with =is_active=. The package upload is the shell's =compute
   publish-package=, which computes and verifies the SHA256 server-side, and
   the generated writes cover the rows. A non-writer finds the controls
   withheld and the screen says why: the catalogue is the installation's.
10. *An empty catalogue.* No app is registered, or an app has no version. The
   system says the grid has nothing to run and does not offer a dispatch. That
   is the first-run state, before any package is published.
11. *Leave, or go on.* A reader who now knows the version continues in
    [[id:1439FB25-A388-40C7-930A-3A814B703DDD][Follow a job]] or
    [[id:01238DF2-9745-451A-B288-7C0F141E35B6][Plan the grid's capacity]]. The
    super administrator who needs the deployment's own build continues in
    [[id:C3D59907-9D6A-448C-9A61-9E750755BBFB][Check the versions and the
    database]].

* Screens and wireframes

One screen. The app list, the version table, the platform and package table, the
versions-in-flight matrix, the jobs-per-release bars and the concurrency panel
are panels of that screen, because the person reads them as one answer. The
screen reads for everyone and writes for the super administrator: the write
controls are the only part of the screen withheld from a reader, and they are
withheld by permission and not by a second screen.

The panels are the charts [[id:0169FDD7-9B88-4766-9AE9-93FE87200700][Compute
journeys]] names for keeping what the grid runs:

| Panel | Chart | Answers |
|-------+-------+---------|
| Node grid | *Versions in flight* | Which release is running where? |
| Release bars | *Jobs per release* | How many jobs still run an older release? |
| Concurrency | *Concurrency against the cap* | Am I throttling myself? |

The versions-in-flight matrix is a node-by-version grid. The jobs-per-release
bars are drawn from the workunits' =app_version_id=, not from the nodes, so the
panel states the release each job runs and marks each app version newest or
older. The concurrency panel plots in-flight work against a cap, and the cap
must be a real number the screen can cite.

Every list on the screen pages on the server, per the
[[id:2BF7F03F-6BF4-45FF-8E26-4D3B4E2D943D][Record screen standard]]. The app
list, the version table and the platform and package table each carry First,
Previous, Next, Last, a page size and Load all, with the page and the page size
held in the address. A new search, a new filter, a new order or a new page size
returns to page one, and Load all is offered only when the server's total is
1000 or less. No list reads with a fixed large limit, and none pages to the end
to show everything.

The catalogue is the installation's. An app version is addressed by
=(=name=, =engine_version=, =wrapper_version=)= on the write, and a platform row

=compute publish-package= is the one write that is not a generated entity
operation. It uploads the tarball to storage under the app's package key,
computes and verifies the SHA256 server-side, and registers the =app=,
=app_version= and =app_version_platform= rows. The generated =put= operations
cover the rows on their own. The shell uploads the package bytes over HTTP to
storage, and no browser upload path exists: the shell is the only client today.

=reporting.v1.concurrency_policies.list= is reporting's read, not compute's. The
policy is a property of a report definition, and the grid reads the definition's
policy code to explain why a run of the same definition did or did not start.

The browser reads the screen through a hand-written BFF route on the
[[id:6A63AAC7-4869-493A-97E7-55B919874784][journey runtime]]. No route serves
a compute screen yet.

* What is missing

1. *There is no concurrency cap in the grid.* The use case names a policy that
   "caps how many of a thing run together", and no such row exists. The only
   concurrency policy is reporting's, and its three codes, =skip=, =queue= and
   =fail=, state what happens to a new run when another is in flight. They state
   a behaviour and not a number, so the chart "Concurrency against the cap" has
   no cap to read. The nearest numbers are the report quotas and the grid's
   per-tenant assignment cap in
   [[id:B3165E6F-AE8C-4DBD-8F87-2EC4F276FCF0][Report execution at scale]], and
   those are capacity-test targets with no table
   ([[id:4597D5A9-C591-4992-ABEE-8822C10D8D96][ores.reporting.concurrency_policy]]).
   The journey states this rather than inventing a cap.
2. *The versions-in-flight matrix needs a range and a join.* The node sample
   carries no release, so the matrix cannot be drawn from it. The wrapper
   release and its host are on the service heartbeat, and the engine build a
   job pinned is on the workunit. A range read that joins results to workunits
   and app versions is the missing piece.
3. *A package cannot be published from a browser.* The upload is a shell verb,
   which uploads over HTTP to storage. The journey's writer reaches the package
   step through the shell and the rows through a screen, and the two are not one
   action. A browser package upload, or an explicit statement that publishing
   stays a shell operation, is the missing decision.
4. *A version with no package is not marked.* The catalogue can state a version
   whose platform rows carry no package, and the dispatcher will store its jobs
   and never publish an assignment. The screen must state that, and the model
   could state it too.
5. *The registry has no history view.* A package's digest changes when it is
   republished, and the model keeps the current row only. The journey shows the
   current catalogue and cannot say what a job ran if the version's package was
   replaced. The result's =output_uri= and the log lines are the only record of
   the old run.
6. *One tenant's work is dispatched to nobody.* The catalogue is what a tenant
   reads before submitting, and the wrapper's single assignment subject means
   the tenant's submission may not be picked up. A catalogue screen that says
   "the grid may run this" is not yet a promise the fleet will
   ([[id:0072F772-F879-4DDB-8944-96433843CE17][The wrapper consumes one
   tenant's work]]).
7. *Nothing marks a release newest.* The jobs-per-release chart marks each bar
   as the app's newest release or an older one, and the =app_version= model
   states no flag and no ordering that says which build that is. The only rule
   today is the highest =engine_version=, and =engine_version= is text, so the
   comparison is a string comparison. That is the rule the submit handler
   already uses when it picks a version for a report, so the chart and the
   dispatcher would agree; a model that states the newest version, or a
   version-aware type, would make the mark a fact rather than a convention
   ([[id:1E563104-6F89-4858-9395-D869A7E817A6][ores.compute.app_version]]).
