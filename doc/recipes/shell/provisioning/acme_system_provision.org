The synthetic counterpart to the [[id:87246342-8B5C-4345-9BAD-7A2F40985DF4][Barclays (GLEIF) provision]]: same
three-stage flow, but the organisation is generated synthetically with
a fixed seed. The =ores-shell= block is tangled into the runnable
script library as =acme_system_provision.ores=.

* Question

How do I provision a fresh system from the shell with an Acme tenant
and a synthetic organisation?

* Answer

Bootstrap =super_admin= and install an =Acme Corp= tenant from the
operational starting point, generate a synthetic organisation with a
fixed =--seed 42= so the party names are deterministic, then provision
the root operational party. The party name below is in lock-step with
the seed: change =--seed= and discover the new root party with
=parties list --category Operational=.

=.synthetic generate= is a shell tool and not part of provisioning: a
starting point publishes the reference data a tenant works from, and
what a tenant's organisation then looks like is the generator's answer
rather than a profile's. The starting point's own step publishes the
base data the generator reads, which is why the command runs after
=provision system= returns.

Expectations match the Barclays recipe (services up, fresh
bootstrap-mode database). =connect= takes the endpoint from
=$ORES_NATS_URL=.

#+name: acme-system-provision
#+begin_src ores-shell :exports none
connect $ORES_NATS_URL

provision system super_admin Secure-Password-123 super_admin@localhost.com --tenant-admin-password Secure-Password-123 --tenant-code acme --tenant-name "Acme Corp" --tenant-hostname acme --profile empty_operational
logout

login tenant_admin@acme Secure-Password-123
synthetic generate --seed 42
logout

login tenant_admin@acme Secure-Password-123
provision party "Lloyds Wealth Management Ltd"
accounts set-default-party "Lloyds Wealth Management Ltd"
logout

exit
#+end_src

#+begin_src sh :noweb yes :results output :wrap example
./ores.shell ${log_args} ${connect_args} << 'EOF'
<<acme-system-provision>>
EOF
#+end_src
