* Acceptance

- The apply re-checks each line's base version against the live row, because the book can change between the raise and the apply. It replays the write with the maker's reason and commentary, which the line keeps.

- A line holds an applied marker. The apply writes each line through the real book service, with the request as the reason, and marks it applied in the same transaction, so a line applies once and a second apply finds nothing to do.
- A request that is not approved is not applied.
- A refusal from the real write rolls the whole apply back, moves the request to apply_failed with the line and the reason in the row's commentary, and returns the refusal.
- An infrastructure failure rolls back and returns transient, leaving the request approved.
- A re-check reads the stored lines against the live row and writes nothing.
- apply_failed is a final state. Only an approved request moves to it, and a request already there answers ok.
- The workflow, the start on the last approval, the retry and the screens are the next task, "Run the apply as a workflow".

- Add the =apply_failed= state and =ores_inbox_fail_apply_fn=, which moves an approved request to it. It is not a decision: no person decides it, so no decision row is written.

- Tell a refusal from the infrastructure failing by the error text. A write the database answers is a refusal. A lost connection or a timeout is transient and is never retried as a refusal.

* Notes

- The apply runs the real write with the line's own base version as the claim, so the re-check at apply is the write's own precondition. A book that moved since the raise makes the write refuse, and the whole apply rolls back.
- The reason the apply states is the line's reason code, and its commentary is "Approval request <id>" followed by the maker's commentary.
- The kinds the apply could not tell apart by text are listed in =is_infrastructure_failure=. It is a short list of markers and has its own test.
- The gate is not yet built, so any caller may still write a book directly. The apply does not yet pass the request to a gate.

* Result

An approved request's lines are written to the books in one transaction, each once, and a refused apply ends the request in apply_failed.

- The =apply_failed= state is final. =ores_inbox_fail_apply_fn= moves only an approved request to it, writes the line and the reason in the row's commentary, and answers ok when the request is already there.
- The pending line gains an =applied= marker and a read by request. =recheck= reads the stored lines against the live book and writes nothing.
- =apply= locks the request row, reads its state again under the lock, and writes every unapplied line through the real book service with the request as the reason. It marks each line applied in the same transaction. The first refusal rolls everything back and moves the request to apply_failed.
- An error with no server label, or a FATAL one, is a failure of the infrastructure. It returns transient and leaves the request approved. An ERROR is a refusal, whatever text follows it.
- A request holds at most 1000 lines. The raise, the recheck and the apply refuse more.
