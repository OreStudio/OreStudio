This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A trader or quant finds one instrument across every kind the party can see, reads the source and the freshness behind it, and opens the screen that fits its kind.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want to find one thing — a rate ladder, a curve, a pair or a surface — by its
currency, its pair, its name or the provider behind it, and open the screen that
reads it." The journey is done when the person has one row and is on the screen
its kind leads to.

* Actor and trigger

The actor is the trader, the quant or the operations person who reads market
data for the party. The trigger is a price to check, a curve to read after a
publish, a surface to inspect, or a currency a colleague named. The journey
starts at *Market data / Find an instrument* and ends on the kind's own screen.

The journey reads and changes nothing. It is the one door into the market-data
area: every other screen in the group is reached from a row it returns.

* Steps

1. *Open the search.* The person opens *Market data / Find an instrument*. The
   system focuses one input and states the party whose instruments it will
   return. The party is the session's, not a filter: a client never decides
   which party's data it sees.
2. *Type a currency.* The person types =aud=. The system returns one row per
   instrument the party can see that matches the currency on either side:
   a rate ladder, a curve, two pairs (one found from its quote side) and a
   surface.
3. *Narrow by facet.* The person picks a provider or a kind. The system
   narrows the same answer; it does not read again. A kind with no match drops
   out of the answer rather than showing an empty section.
4. *Read a row.* The person reads the kind badge, the display name, the source
   list, what the instrument holds (rungs, pillars, grid) and its freshness.
   The name and the kind are the server's: the client does not build a label
   from a URI, and it does not decide whether a value is stale.
5. *Open the kind's screen.* The person presses Enter. A LADDER opens the rate
   ladder, a CURVE the curve inspector, a PAIR the FX montage, a SURFACE the
   published surface. A FIXING opens the observations for that fixing.
6. *Meet an empty answer.* The query matches nothing. The system says so in
   words and names the facets that would match; it does not show an empty list
   as if the read had failed, and it does not fall back to everything.
7. *Leave.* The query and the facets are in the address, so the person can send
   the view to someone else.

* Screens and wireframes

One screen: an input and three facets above a list. The badge on each row is
what four separate curve and surface lists used to be.

| Step | Shape on the screen | Judgement |

| Open the search | Page title, one sentence, one input, three facets | The standard draws it, RS-LIST-01 to RS-LIST-03 |
| Type a currency | Row per instrument with a kind badge | A view no rule draws yet: one list over five kinds |
| Narrow by facet | The same list, narrowed | The standard draws it, RS-LIST-04 |

* Operations and messages

#+ATTR_HTML: :class hug-leading
| Step | Operation | Subject | Status |
|------+-----------+---------+--------|
| Type a currency | list the series the caller can see, with axes | =marketdata.v1.ops.list_series_identities= | partial |
| Read a row | the instrument catalogue: kind, name, facets, freshness | =marketdata.v1.ops.list_instruments= | missing |
| Narrow by facet | the same catalogue, filtered server-side | =marketdata.v1.ops.list_instruments= | missing |

=marketdata.v1.ops.list_series_identities= returns series, not instruments: one
entry per series with its axes, but no grouping into a curve or a surface, no
display name, no provider facet, no kind and no freshness verdict.

* What is missing

- =marketdata.v1.ops.list_instruments= — the definition of an instrument. It
  groups the series into one entry per instrument and states the kind, the
  display name, the facets, the axes in draw order, the sources and the
  staleness verdict. Until it exists the screen must group and name on the
  client, which is the duplication this journey exists to remove.
- The name rule. Three curves called =IR AUD IR_SWAP= and five called
  =AUD-AONIA= differ only by forward start or provider, so the name must carry
  the field that distinguishes peers (=IR AUD IR_SWAP 0D=) and leave the source
  out, because a source is a facet and not an identity.
- The party scoping. =list_series_identities= answers for every party the login
  can see; a session must see one.
