* Acceptance

- Every route the BFF registers appears in the inventory with its source file and line.
- Every route ores.http registers appears in the inventory with its source file and line.
- A route added to either server without a row fails a check.
- The inventory is regenerable by one command, and the command is recorded beside it.

* Plan

Two shapes had to be read, and neither has a manifest yet: the BFF registers a
route with a Fastify call whose first argument is a literal =/api/...= path, and
ores.http registers one with =router->get/post/put/patch/delete_/head=. A tool
reads both and writes one table; a check compares the table with the tree, so the
list cannot go short without the gate saying so.

The table carries the classification beside each route, and the tool never writes
those cells: it keeps what it finds and leaves a new route's cells empty. The
deciding stays with a person, and a regeneration cannot overwrite a decision.

* Notes

- The BFF's 288 rows carry the route the module registers, not the screen that
  calls it. The distinction matters for the classification: a route that exists
  because a screen renders a grid looks exactly like a route that exists because a
  domain object needs reading, and only the payload tells them apart.
- Five ores.http routes state a path the code composes. They are listed by the
  variable's name and the line that declares it, because inventing a resolved path
  the extractor cannot verify would be worse than naming what it found.
- The tool says what it cannot see: a route registered from a generated table (K1)
  or from a loop over a family is not a literal call and would be missed. The answer
  is to teach the tool that shape, not to add a row by hand.
- Two behaviours are proven by mutation, not by reading the code: appending
  =router->get("/api/v1/probe")= to a route file makes the check fail, and so does a
  =.get('/api/probe'= in a BFF module; removing a row for a route that still exists
  fails too.
