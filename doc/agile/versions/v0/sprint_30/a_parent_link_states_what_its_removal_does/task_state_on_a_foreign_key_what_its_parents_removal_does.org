* Goal

The codegen model gains a removal behaviour on a foreign key, for example
=:on_parent_remove: cascade=, =refuse= or =keep=, with =:keep_reason:= for the
last. The SQL template builds the parent's delete rule from every link that
names that parent: it closes the =cascade= children, as
=<parent>_cascade_delete_fn= does today, and it refuses the removal with an
outcome that names the child while a =refuse= child is current.

* Acceptance

- A foreign key accepts =cascade=, =refuse= or =keep=, and codegen refuses any
  other value.
- A parent with a =cascade= child closes that child in the same statement as
  its own row; a pgTAP case shows it.
- A parent with a current =refuse= child is not removed, and the caller gets an
  outcome that names the child; a pgTAP case shows it.
- Regenerating the models without any new declaration gives byte-identical SQL.

* Notes

- The parent learns its children from the child models, so codegen needs the
  reverse index: for each table, the links that name it. The loader in
  =projects/ores.codegen/src/codegen/org_loader.py= builds the delete cascade
  list today from the parent's own section.
- Decide how a system tenant parent treats tenant children. A tenant cannot
  remove a shared row, but the system tenant can, and its children may live in
  other tenants. Row-level security binds the delete rule's statements to the
  current tenant.
- A cascade child may itself be a parent, so a removal can walk a tree. Decide
  whether the generated functions chain, as the portfolio tree's rule does with
  its own touch function, or whether the depth is refused.
