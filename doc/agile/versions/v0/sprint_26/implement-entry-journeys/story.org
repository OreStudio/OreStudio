* Goal

The two Entry journeys run in ores.web against the real server. Sign in is finished: every refusal says which refusal it is, the forced password change blocks the workspace until the member sets a password of their own, the party step names the places a person works and marks their default, and a lapsed party-selection token returns them to the door with words rather than a generic failure. Sign up is added end to end: the deployment states whether it accepts self-registration, the screen reads that answer before it offers a form, the server refuses the registration it should never have accepted, and the person is told exactly what their new account has and what it still waits for. Registration's end state is the subject of the analysis this story opens with, because where a new account lands is a platform decision, not a screen decision.

* Decisions

- *A default lives on the row its actor may write.* Row-level security decides who may set a value, so a default nobody can set is not a default. The tenant flag belongs to the super administrator, because only a system-tenant session may write a tenant row; the party and role flags belong to the tenant administrator, because those tables are tenant-isolated.
- *A boolean stays a setting; a reference becomes a flag.* The two registration flags have no referent and stay in the variability settings, where they already live. A default party or role is a reference, and stored as a string it can name a row that does not exist — which is the failure mode of the hard-coded =Viewer= it replaces.
- *Waiting is a state, not an absence.* A new =account_status= of =pending= is written when the tenant nominates no default party, read by the roster, and refused by sign-in with its own code and its own words.
- *The door asks one policy read,* =iam.v1.auth.registration-policy=, separate from the bootstrap read: one answers what the deployment offers a person who is not in it, the other whether the deployment has been set up.
- *The address names the tenant.* Both Entry journeys resolve the tenant from the address they are served at, so the person types a username and not a =user@hostname=. A registration that resolves to no tenant is refused with a reason; it never falls back to the system tenant by omission.
- *A refusal is a code.* Both responses gain =error_code=, so a screen branches on a value rather than on English prose.
- *The authorisation flag closes the door honestly.* Until the approval workflow exists, =system.signup_requires_authorization= closes registration and the policy read states why. It must not claim an approval that nothing performs.
- *The setup journeys own the defaults, not the sign-up screen.* The person who opens the door is not the person who decides what it opens onto, so [[id:84C231B8-C861-44CF-89FB-D7A840D3EBDE][First run]] confirms the first tenant as the default tenant and states whether the installation accepts self-registration, and its first sign-in lets the tenant administrator nominate the party and the role. [[id:4C062ECC-D6D4-4BA4-8F96-10E141663D9C][New tenant]] and [[id:9AB6C90E-5338-435A-9559-4E426D612EB6][New party]] ask the same questions when they create a tenant or a party later. The three Setup journey documents now carry those steps. The screen work belongs to [[id:DCF3E855-AEDF-4520-97B6-815A428DB514][the setup story]], which owns the setup screens; this story supplies the model, the policy read and the write paths they call.
- *The switch is the deployment's, and it is read at system scope.* =system.user_signups= is seeded on the system tenant and defaults to =false=, so a deployment nobody has asked refuses registration. A tenant override is possible but nothing sets one, and the door reports the deployment's answer rather than inventing a per-tenant one.
- *The target state lands with the fix, by the product owner's choice.* The open registration door stays open until the implementation lands. That is a known and accepted risk for the duration of the work, and it is the reason the flag enforcement is the first implementation task rather than the last.

* Out of scope

- The approval workflow behind =system.signup_requires_authorization=, which is a workflow in =ores.workflow=.
- Email verification, invitation delivery and the notification that tells an administrator somebody is waiting.
- Self-service password recovery from the door, which needs a delivery mechanism outside IAM.
- The Directory screens that release a pending account and show it on the roster. The target state states the requirement; [[id:BEE7132B-C76F-4373-B776-13262F267ECE][Directory journeys]] owns the screen.
