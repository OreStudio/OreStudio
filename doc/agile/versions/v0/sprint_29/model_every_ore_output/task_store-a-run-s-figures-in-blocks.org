* Goal

The post-processor's memory does not grow with the size of a run's output.

Today it reads a whole family into memory, builds every row, and inserts them in
one statement. A large run holds millions of rows before the first is written.
It should read a block of rows, write the block, and read the next.

* Acceptance

- The readers hand back rows a block at a time, or the post-processor asks for a
  block and gets one.
- Each block is inserted with one statement, so the round trips stay proportional
  to blocks and not to rows.
- Peak memory for a run is bounded by the block size and not by the family's row
  count, and the bound is stated.
- A refusal still stops the run before any block is written, or the write is one
  transaction so a partial load cannot be seen.
- The measured peak memory and the wall clock of a large synthetic run are
  recorded on the task.

* Plan

The unit is a block of rows, stated once, and both readers and writers use it.
The insert stays one statement per block, which is the same shape as today's one
statement per family but with a ceiling.

The run's figures are written in one transaction, so a refusal part way through
leaves nothing behind: a partial load reads as a complete one, which is the rule
this story already keeps everywhere else.

Baseline first: a hidden benchmark loads a generated raw cube the way the handler
did, read whole then inserted, and reports the wall clock and the peak resident
memory. Then:

1. =read_metrics_in_blocks= and =read_cashflows_in_blocks= hand rows over a block
   at a time; the whole readers wrap them.
2. =read_run_output= reads one file and hands each block of reporting rows to a
   sink; =read_run_outputs= wraps it for the tests.
3. =post_process_results= opens one unit of work, reads one file at a time, writes
   each block of 10000 rows as it comes, and commits once. A refusal anywhere
   leaves the unit of work uncommitted, which rolls back every block written.

The marketdata state store is unchanged: its files are a run's scenario and
calibration files, which are small beside the cubes.

* Notes

- The whole load costs about 3.7 KiB a row at peak: the reader's rows, the
  repository's entities and the insert's parameters are all held at once. The
  block load holds one block of each, so the load adds 68 MiB whatever the cube's
  size; the cube's own text, which storage returns whole, is the rest.
- The wall clock did not move, and should not: a block is one pipeline with one
  sync, so round trips fell from one per family to one per block, but each row
  still runs the bitemporal insert trigger, which looks for a current row of the
  same key to close. That trigger sets the 2500 rows a second.
- No end-to-end run proves the handler: since the conventions split merged, every
  report run fails while its input is built, before post-processing; captured as
  Every report run fails on an orphan commodity future part. The rollback is
  proven by a repository test and the block load by the benchmark, both against
  the real tables.

* Result

A run's rows are loaded a block at a time: the handler reads one file at a time
and writes each block of 10000 rows as it is read, in one transaction committed
once, so a refusal anywhere leaves nothing behind. Peak memory for a 500000-row
cube fell from 1992 MiB to 202 MiB, bounded by one file's text and one block of
rows rather than by the family's row count; the wall clock is set by the insert
trigger and did not change. Every acceptance bullet is met; a block is one
pipeline of row statements with one sync rather than one statement, which keeps
the round trips proportional to blocks.
