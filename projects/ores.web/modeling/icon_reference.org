The icon vocabulary for this interface, and the process for adding to it.

An icon set drifts when each screen picks its own. Two screens then use different
marks for one idea, and a third invents a fourth. This document exists so that
does not happen: the table below is the whole vocabulary, and adding to it is a
process with a checklist rather than a decision made at a call site.

Derived from the Qt client's =doc/knowledge/ui/icon_guidelines.org=, which is the
source of truth for the artwork itself. The two specifications that once used it
are superseded: =entity_specification.org= describes entity screens that are
deleted, and =component_specification.org= now specifies the browser shell and
the transport.

* 1. The system

One icon set: /Microsoft Fluent UI System Icons/. The Qt client also carries a
Solar set as an alternate theme; this interface does not, because supporting two
sets doubles the vocabulary for no gain. Fluent only.

/Naming./ Icons are =ic_fluent_{concept}_{size}_{variant}.svg=. Sizes are 16,
20, 32 and 48. Variants are =regular= and =filled=.

/Sizes./

| Size | Where |
|---+---|
| 16px | Inline with text, dense tables, the reload action |
| 20px | Buttons, navigation, the standard action size |
| 32px | Headers, emphasis |
| 48px | Feature icons, onboarding, empty states |

/Variants./ Regular is the outline style, for passive states and secondary
actions. Filled is solid, for active states, emphasis and primary actions. The
star is the clearest example: regular when not favourited, filled when it is.

/Colour./ Icons are monochrome and recoloured at use, not shipped in colour. The
default is =rgb(220, 220, 220)=.

* 2. How the Qt client declares them

Worth knowing, because the port mirrors it and because a mismatched name fails
silently as a missing icon rather than as an error.

An =Icon= enum in =IconUtils.hpp= lists every concept, alphabetically. A
=getIconDef()= function in =IconUtils.cpp= maps each enum member to a definition:

#+begin_src cpp
case Icon::Publish: return {"ic_fluent_arrow_upload_20", "upload-square.svg"};
#+end_src

The first string is the Fluent base name without the variant suffix; the second is
the Solar counterpart, which this interface does not use. The enum is the
vocabulary and the mapping is how a concept becomes a file.

In the port there is no resource file and no second set, so one table in the icon
module replaces both.

/Two cautions./

Entries marked "verify against source" name no icon file in the source document,
or name one that duplicates another. Before using one, open
=projects/ores.qt/resources/icons/= and confirm the file exists, because a wrong
name renders as nothing rather than as an error.

Search, Filter, Settings and Undo are named by the entity specification but are
absent from the Qt inventory. They are standard Fluent icons and are listed here
with their expected file names, but their files should be confirmed before use.

* 4. Adding an icon

Seven steps, in the Qt client. The equivalent here is fewer, because there is no
resource file and no C++ enum to edit, but the discipline is the same: the
artwork, the mapping, and the documentation are updated together.

/In the Qt client:/

1. Find a semantically appropriate icon in both sets, both variants.
2. Copy it into the Fluent directories, both variants. (In the Qt client,
   also the Solar directories; this interface uses Fluent only.)
3. Add it to =resources.qrc=.
4. Add an entry to the =Icon= enum, alphabetically.
5. Add the mapping in =getIconDef()=.
6. Use it through =createRecoloredIcon=.
7. Document it in the icon guidelines, in the right category.

/Here:/

1. Find the icon in the same two sets, both variants, and confirm it is not
   already in the table under another name.
2. Add it to the icon module's table, which is the equivalent of the enum and the
   mapping in one.
3. Add it to the table in this document, in the right category, with what it is
   for.
4. If it is a new /concept/, add a row to the entity specification's icon table
   too, because that table is what an implementer reads.

Step 4 is the one that matters. An icon added to the module but not to the
specification is an icon the next person will not find, and will re-add under a
different concept.
