* Summary

ORE Studio is a set of services that talk over
[[id:D9B0988E-D783-43D6-BCCD-CE2F70022B9C][NATS]], share no tables, and act for
many tenants and parties. The problems that come from this are not new. Every
microservice platform meets them, and the literature names the solutions:
Token Exchange, Saga, Idempotent Receiver, Bulkhead. This hub is the pattern
language of the platform. It lists the established patterns ORE Studio uses, and
each page states the pattern's forces, its failure handling, its pitfalls, its
use here and its sources.

The purpose is a shared vocabulary. A design says "use Token Exchange" and links
one page. The reader then knows the mechanism, the known failure modes and how a
timeout or a retry is handled, and nobody finds them again by accident.

Three rules govern the language:

- *The established name.* A page is titled with the pattern's name in its
  source. A local name is an alias.
- *A source for every pattern.* A solution with no authoritative source is a
  local convention, and it belongs in an architecture page, not here.
- *The pattern owns the mechanism; the user owns the use.* A pattern page names
  each use and links it. The architecture page that uses a pattern links the
  pattern and states only its own choices.
  [[id:2BF68189-57CF-42F7-BA33-9673B7D620DD][Document type: service_architecture_pattern]] states the
  contract.

* Scope

The hub covers the patterns that govern how services work together across a
process boundary. It does not cover code-level design patterns inside one
component, user interface patterns, or the local conventions of the codegen,
such as the SQL, HTTP and shell entity patterns: those have no outside source
and keep their own pages. [[id:2BF68189-57CF-42F7-BA33-9673B7D620DD][Document type: service_architecture_pattern]]
states the boundary.

* Reading order

Read the groups in order. Each group answers one question about two services
that must work together, and a later group often uses an earlier one.

** The identity group

/Who is this request acting as, and how does the next service know?/ A request
carries an identity from the edge to the database, where row-level security
uses its tenant and party. These patterns decide which identity a call carries:
the caller's, the service's own, or one exchanged for a purpose. Work that
starts from a schedule has no caller, and the composite pattern in this group
covers it.

Read Access Token first, then Client Credentials and Token Relay, which are the
two ways a call carries a token it already has. Token Exchange and Grant
Management come next, for an identity no call carries. The composite comes last.

** The communication group

/How does a message get from one service to another, and back?/ The bus carries
requests, replies and events. These patterns decide how a reply finds its
request, how bulk data travels, and how several replicas share the work.

| Pattern | Source |
|---------+--------|
| Request-Reply | Hohpe and Woolf, /Enterprise Integration Patterns/ |
| [[id:4F11D22B-2830-4E8E-B752-552F0C59CD07][Correlation Identifier]] | Hohpe and Woolf; Newman |
| Claim Check | Hohpe and Woolf |
| Competing Consumers | Hohpe and Woolf; Azure Architecture Center |

** The coordination group

/How does work that spans services stay consistent?/ No transaction spans two
services. These patterns decide how a long piece of work is sequenced, how it is
undone, and how a step survives being delivered twice.

| Pattern | Source |
|---------+--------|
| Saga | Garcia-Molina and Salem; microservices.io |
| Process Manager | Hohpe and Woolf |
| Idempotent Receiver | Hohpe and Woolf |

** The resilience group

/What happens when a service is slow, gone or wrong?/ Every call can fail. These
patterns bound how long a caller waits, decide when to try again, and keep one
failure from spreading.

| Pattern | Source |
|---------+--------|
| Timeout | Nygard, /Release It!/ |
| Retry | Azure Architecture Center; Nygard |
| Bulkhead | Nygard; Azure Architecture Center |
| Circuit Breaker | Nygard; Azure Architecture Center |

** The load group

/What happens when many tenants want the same thing at once?/ Thousands of
tenants share one platform. These patterns absorb a peak, cap what one tenant
can take, and share capacity fairly.

| Pattern | Source |
|---------+--------|
| Queue-Based Load Leveling | Azure Architecture Center |
| Throttling | Azure Architecture Center |
| Fair Share | Azure Architecture Center, Priority Queue; fair-share scheduling |

** The data group

/Who owns data, and how does another service read it?/ A service owns its tables
and serves them through operations. These patterns state that boundary and how a
reader keeps a copy without owning it.

| Pattern | Source |
|---------+--------|
| Database per Service | microservices.io |
| Cache-Aside | Azure Architecture Center |

** The observability group

/How does a person follow what one action did across services?/ Each service
writes its own logs and no transaction spans them. These patterns join the
records of one action, show which service called which, and say where the time
went. Correlation Identifier, in the communication group, is the first step; the
patterns here build on it.

|---------+--------|
| [[id:32FE1EB9-653F-4E12-9474-406BB884C56A][Distributed Tracing]] | microservices.io; W3C Trace Context; OpenTelemetry |
| Log Aggregation | microservices.io |

* Choosing a pattern

Start from the question, not from the pattern. Find the group whose question
your design faces, then read the pages in that group. Each page's =* Context=
says when the pattern applies and =* Related patterns= names the alternatives.
When no pattern fits, write the design without one and record the gap on the
story. Do not stretch a pattern to fit.

To add a pattern, run =compass add service_architecture_pattern= with its group, fill in every
section, cite its source, and add it to its group above. See
[[id:3153AA4B-23D4-4111-9710-5A4971102EDC][How do I create a new doc?]].

* What this hub does not cover

[[id:AF46793A-FF6C-4066-A059-279CE9936420][Identity and Access]] owns the IAM
model: accounts, roles, permissions and row-level security. The identity group
here owns how an identity travels between services.

[[id:4F95A407-AD43-4CBD-952E-1CCACAA90080][Workflows]] owns the workflow
engine. The coordination group names the patterns the engine implements; the
engine's own contract stays in that cluster.

[[id:4682A7D5-04FC-494B-BD7C-6816500EB3C9][Message Queue]] owns the subject
grammar and the message contract. The communication group names the patterns
the bus carries.
