* Goal

The gateway decides how much body it will accept, refuses what is past the limit,
and then reads everything it accepted into one string. The storage upload route is
the one route that legitimately takes a large object, so a 256 MiB engine package
costs 256 MiB of gateway memory for as long as the request runs. Two concurrent
uploads cost twice that, and the pool of worker threads holds the request open
while the memory stays.

After this story the accepted body is carried to where it is going instead of held:
the session reads it in chunks, the route that wants it consumes those chunks, and
memory is bounded by the chunk window rather than by the object. The storage upload
writes to a temporary file and renames it when the body ends, and the download
serves from that file with a fixed buffer.

* Acceptance

- A route states that it takes its body in chunks, and the session reads it that
  way; every other route keeps the buffered path it has today.
- The per-route limit and the server ceiling apply to a chunked body exactly as
  they apply to a buffered one, and a body past them is still answered 413.
- A body that stops arriving is closed on the stall deadline instead of holding a
  worker and a connection for the life of the process.
- The storage upload writes a temporary file and renames it on the last chunk; a
  request that fails leaves no object behind.
- The storage download serves the file with a buffer that does not grow with the
  object.
- A 256 MiB upload moves the gateway's resident memory by less than 1 MiB, measured
  by a test that reads the process's own RSS across the request.
- The grid wrapper's transfer tests pass against the streamed routes.

* Decisions

- The session reads the socket and hands each chunk to a sink the route supplies,
  on the connection's own executor. Letting the handler read the socket, or handing
  it the parser, would move the read off the executor that owns the socket; a
  channel between the two would buy concurrency the destination does not need.
- The chunk is the memory bound, and nothing more: the sink runs inline on the
  connection's executor, so a slow sink costs the connections that share that
  executor, which is the trade taken here because the destination is a local file.
- The sink outlives the handler call, and the session holds a guard that discards
  an unpublished sink, so a refused, failed or abandoned request leaves nothing
  behind and no error path has to remember to clean up.
- Streaming is opt-in per route, because a JSON route is simpler to serve from one
  string and nothing gains from a sink there.
- The download is split from the upload. Serving a file needs a response written in
  chunks, which increment B1 owns, so [[id:9A622B67-34FA-4426-9526-508CFB7A690C][Serve the download from the file]] waits on
  that rather than inventing a second response path here.

* Out of scope

- Streaming a response other than the storage download. Increment B1 owns response
  streaming for every route.
- Resumable or ranged transfers.
