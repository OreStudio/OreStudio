* Goal

An MCP client, Claude Code, Claude Desktop or a small local model's agent,
connects to ores.http, works as a person who signed in, finds the operations
that person may call, and calls them. The catalogue is shown in small steps
with a way to discover what exists, because the models may be very small.

ores.http speaks MCP itself, with boost.taar as the reference implementation.
The analysis is in [[id:FC0847D1-9F09-42EF-A4BD-D5E3C34398EA][How ores.http serves MCP]] and
[[id:6DFC4BF5-65AC-4E75-90EA-FBDC1272E01C][How the model sees ORE's operations]].

* Acceptance

- =/mcp= on ores.http serves MCP's Streamable HTTP transport: =POST=, =GET=
  and =DELETE=, sessions by =Mcp-Session-Id=, JSON-RPC through ORE's codec,
  and =initialize=, =ping=, =tools/list= and =tools/call=. It passes the
  official MCP conformance runner for what it implements.
- =tools/list= answers a fixed set of tools whatever the catalogue holds: list
  the areas, list an area's entities, list an entity's operations, find
  operations by words, and call an operation. Every answer is short and lists
  only what the person may call.
- Every route declares its tool name, its area and entity, and whether it
  writes, and a gate refuses a route that does not. Every route that takes a
  body declares its schema with =body<T>()=.
- An outside MCP client acts for a person through an agent grant the person
  creates in ores.web, with a key the agent sends; its token names the person
  as subject and the agent as actor, and the person can revoke it.
- Every write an agent makes records the agent, and the person sees in ores.web
  everything their agents did, so a call over MCP is never mistaken for one the
  person made.
- Six eyes for agents: an agent's write raises an approval request that its
  person approves, and then the approval a person's own write would need, by
  someone who is neither; a trade goes through the existing trade
  authorisation. No argument the model sets counts as an approval.
- A set of real requests, each run with a small model through browsing and
  through search, records how often it reaches the right operation and in how
  many steps.
- The gates cover the new code.

* Decisions

- *ores.http speaks MCP itself, with boost.taar as the reference* (2026-11-21),
  carried over from [[id:BBEDFA8E-D43D-4F48-8FD7-1A3CC9F47E3E][Bring the assistant into ores.web on the target architecture]].
- *The catalogue is browsed in small steps, with search beside it*
  (2026-11-21): a declared hierarchy of areas, entities and operations, each
  step a short list, because the full catalogue is about 107,000 tokens and the
  models may be very small.
- *An agent acts through a grant, by key first and OAuth later* (2026-11-22,
  product owner). A person creates a grant for one agent in ores.web, read only
  or read and write, with an expiry; its token names the person as =sub= and
  the agent as =act=. OAuth 2.1 comes later as a second way to create the same
  grant. See [[id:BEF95B2A-42BF-40DA-BC3D-7B703C34ED73][Decide how an outside MCP client authenticates]].
- *Six eyes for agents* (2026-11-22, product owner). Every agent write is held
  unless a rule exempts it: its person approves, then the approval a person's
  own write needs, by someone who is neither. Trades use trade authorisation.
- *The architecture is written first* (2026-11-22, product owner), as
  zettelkasten notes with UML that build on ores.agent's experience, and the
  other tasks start once it is approved.
- *The architecture is approved* (2026-11-22, product owner), as
  [[id:47B179BF-C982-4BB1-AF4F-35E00B9D2750][Delegated Access for LLM Agents]], with four choices: a trade an agent
  books is held through its operational authorisation, which names the
  agent's person before Operations; an agent's actions are recorded on every
  row it writes and in one log of its calls, reads included; no automatic
  approval rule closes the person's part of an agent's request; and the
  catalogue's first step is the sixteen published HTTP areas.
- *The security review's decisions* (2026-11-22, product owner), from
  [[id:6B455B15-0FDB-4E1E-A2A8-CEFC4C1D155C][Security review of delegated access for LLM agents]]: an agent grant names a role, and its token carries the role's
  permissions held by the person; some permissions no agent ever holds
  ([[id:1679B2CE-05C2-4CFF-9A4B-47EC721CB10A][Withholding of administrative permissions from LLM agents]]); =act= is =agent:= and the grant's id; the key is a bounded
  credential at rest, with an expiry of at most ninety days; IAM's entry into
  the tenant a key names is registered; and an agent's calls form sessions of
  their own, shown apart from its person's ([[id:4DCD0684-F6AE-4E84-BB9D-2AE2DAFDB667][Sessions of LLM agents]]).
- *Delegating to an agent is a permission* (2026-11-22, product owner):
  =iam::agent_grants:create=, on a seeded role =AgentDelegator= and not on
  Member, so each tenant decides who may use agents; administrators read and
  revoke everyone's grants with =iam::agent_grants:read= and =:revoke=.

  confirmation in the client is the same person at the same keyboard and
  leaves no record in ORE.
