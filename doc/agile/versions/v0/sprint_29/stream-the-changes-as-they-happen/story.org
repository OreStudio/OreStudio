* Acceptance

- A change published to the hub reaches every open stream.
- A stream that is not read drops its oldest frames instead of growing without limit.
- A quiet stream writes a keep-alive comment and does not spin on the queue.
- A closed subscription ends the stream.

* Decisions

*A change names a collection, not a row.* The first real producer settled it. An
entity event's subject names the collection and the action, its headers name the
tenant and the party, and its key is that entity's own key record, encoded by
that entity's codec. One wildcard subscription cannot decode the key of every
entity, so a frame says "this collection moved for this tenant" and the client
refetches the collection it draws. Keys can return as an optimisation when a
per-entity decoder exists; the frame's event name is then unchanged.

*The stream hears the broker, not the database.* The server subscribes to
=*.v1.*_events.>= and turns what it hears into changes. It does not read the
stores' notify channels itself, so a change published by another service process
reaches a client of this one.

* Result

One slice, and the path it proves: a publish reaches every open stream, a slow reader loses its
oldest frames rather than the server's memory, a quiet stream is kept alive without spinning,
a closed subscription ends the body, and an entity event from any component becomes one frame
per collection per window.

Not proven end to end in a browser: the session door holds no verifier, so no one
can sign in to open a stream. See the task's notes.
