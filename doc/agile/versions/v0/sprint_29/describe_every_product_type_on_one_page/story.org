* Goal

One page a person can read to find out what a product type is before they book
it: every type the tenant may book, what each one means, where its documentation
lives, and which books and permissions allow it.

Today the catalogue is stated in rows a screen reads one deal at a time. A
trader who has never booked a =BondOption= has no page to open, and an
operations person who is asked why a book refuses a type has no page to quote.
The knowledge corpus describes the families in prose, one document per family,
and nothing joins that prose to the catalogue the store holds.

* Acceptance

- A page lists every product type the catalogue holds, by the name a desk uses
  and the code the store holds.
- Each type states what it is, the asset class it belongs to, and where its
  documentation is: the ORE product page, the knowledge document, or both.
- Each type states what allows it: the books a tenant has enabled for it, and
  the permission a person needs to book one.
- A type the catalogue holds and no page can describe is listed as undescribed
  rather than hidden, so the gap is visible.

* What the work will have to settle

- Whether the page is a catalogue page or a knowledge page. A list of types with
  their books and permissions is reference data and belongs on a screen; the
  prose of what a cap/floor is belongs in the knowledge corpus, and the page
  links to it rather than restating it.
- Where "which books allow this type" comes from. If no rule exists yet, the
  page states what it can and the story carries the gap.
- Whether documentation is read from ORE's own product pages at build time or
  written once by hand. Reading it keeps it true; writing it is what the corpus
  already does for the families.
