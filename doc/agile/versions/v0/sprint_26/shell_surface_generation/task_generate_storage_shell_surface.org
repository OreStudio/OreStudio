* Notes

The two surfaces are not substitutes, which is why nothing is retired.

| Verb | Generated | Hand-written |
|------+-----------+--------------|
| put | =put-objects <bucket> <key> <content> <content_encoding>= over NATS | =storage put <bucket> <key> <file>= over HTTP |
| get | =get-objects <bucket> <key> [--include_content]= over NATS | =storage get <bucket> <key> <destination>= over HTTP |
| delete | =delete-objects <bucket> <key>= over NATS | =storage delete <bucket> <key>= over HTTP |
| list | =list-objects <bucket> <prefix> [--offset] [--limit]= over NATS | =storage list <bucket> [prefix]= over HTTP |

The generated unit carries the object in the request, so it cannot move a file,
and the hand-written one moves a file, so it cannot carry content inline. Each is
the only path to what it does.

=storage_transfer= is not a shell convenience: ore's import and report-package
handlers, trading and marketdata use it too, so the file path is live
infrastructure and the menu is its interactive surface.

The hand-written menu has no recipe and no script, and the component's suite does
not cover it. The suite's 13 cases all belong to the generated objects unit.
That is recorded rather than fixed: writing tests for a command this task keeps
is work the clean standard's V-items would ask for, not this story's.

* Result

Storage closes with no code change. Its one model, the objects operation, renders
its unit with four verbs, and the hand-written storage menu stays with a recorded
reason.

The menu is signed off per verb rather than retired. It moves files over HTTP
through storage_transfer, where the generated unit carries content inline over
NATS, so neither command answers the other's request. The file path is used by
ore, trading and marketdata as well, which is why it is not a shell-only
convenience.

The suite passes 28 assertions in 13 cases. Those cases cover the generated unit;
the hand-written menu has none, and no recipe or script calls it.
