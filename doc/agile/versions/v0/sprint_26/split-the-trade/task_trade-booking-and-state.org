* Goal

A trade's booking and lifecycle state live in their own temporal tables keyed by the anchor, the netting set cannot name another counterparty's or entity's set, and a virtual book holds only drafts, tests and hypotheticals.

* Acceptance

- trade_booking (book, netting set, trade date, execution time) and trade_state (status) are temporal and reference the anchor with an enforced foreign key.
- A booking's netting set is pinned to the anchor's party and counterparty.
- A booking names a virtual book only while its trade is a pre-agreement draft, a test or a hypothetical; going live needs a real book in the same write.
- Build, ctest, pgTAP and the local check set pass.

* Plan

- =trade_booking= and =trade_state=: =uuid-identified-lookup= profile, keyed by
  =trade_id=, temporal, with an enforced foreign key to the anchor.
- Both copy the anchor's party, pinned to the anchor, because row-level
  security reads it. The booking also copies the counterparty, pinned the
  same way, so the netting set can be pinned to the trade's counterparty and
  party. The book is pinned to the party. The anchor gains two unique keys,
  =(tenant_id, id, party_id)= and =(tenant_id, id, counterparty_id)=, for the
  database pins.
- The state reuses the wide trade's guarded transition, keyed by the trade id.
- The virtual-book rule is checked by whichever row is written second: the
  booking reads the current state, the state reads the current booking. An
  actual trade goes live by writing its real booking before the state.
- The booking operation (anchor, booking and state in one write, with the
  duplicate trade id as a domain error) moves to its own task: it is the
  first consumer of the three tables and needs a service operation of its
  own.

* Result

- =trade_booking= (book, netting set, trade date, execution time) and
  =trade_state= (activity, status) are temporal components keyed by the trade
  id, with an enforced foreign key to the anchor.
- Both copy the anchor's party; the booking also copies its counterparty.
  Database pins hold the copies to the anchor; trigger pins hold the book to
  the party and the netting set to the counterparty and party.
- The state takes its status through the guarded =trade_status= transition.
- A virtual book holds an actual trade only while it is a draft; whichever
  of the booking and the state is written second checks the other.
- The tenant purger removes every version of both components before it
  deletes the anchors.
- The booking operation moved to its own task, "Book a trade in one write".
