#+title: Task: Refuse a report while the previous one is unprocessed
#+description: report_submit_handler creates a batch and its workunits for every submit_compute step and never asks whether an earlier batch for the same tenant and party is still open. A stalled engine therefore queues more work behind work that cannot finish. Refuse the step, with a reason the run can report, while an earlier batch for that party is unprocessed, so the queue cannot grow past what the grid is draining.

* Result

The gate the trigger handler already asked for never fired:
=ores_reporting_in_flight_instance_fn= joined the instance's FSM state to the
instance's own tenant, and every state row belongs to the system tenant, so
the join matched nothing and the function always answered that no instance
was in flight. The concurrency policy each definition states -- fail, queue
or skip -- was therefore never applied, and every scheduler firing admitted
another production run.

The state is now joined by id and read as the system's, as the guard on the
instance table already reads it. Applied to pauli: 0 of 161 live definitions
reported an in-flight instance before, 39 after, which are the definitions
whose instances sit pending or running.

PR #4885. =compass check --exclude-heavy=: 23/23 passed. No automated test
covers it: the SQL suite cannot create a tenant and the function is granted
only to the reporting service, so the evidence is the live comparison above.

Still to do, outside this task: the 247 pending and 44 running instances the
bug accumulated now block their definitions, and need a clear-down.
