This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A market-risk owner or tenant administrator reads the pricing engine configurations the party holds, what each one prices with, which reports bind it, and what it leaves unpriced.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"Which engine prices my swaptions, and which of my reports use it?" The person
owns reports for a party. A figure looks wrong, or a new product type is now
traded, and the question is not about one report. It is about the configuration
that decides how every report prices a product. The journey is done when the
person has found the configuration, read the model and the engine it gives each
product, read which reports bind it, and knows whether any product the party
trades has no row.

* Actor and trigger

A market-risk owner or a tenant administrator runs this journey. The person acts
inside their own tenant and reads the configurations their party owns. A
configuration is party-scoped by row-level security, so nobody sees another
party's.

The trigger is one of three. A figure disagrees with the desk and the person
suspects the pricing. A report binds a configuration and the person wants to know
what is in it. Or a new product type is booked and the person wants to know if
anything prices it. The journey starts on the list and ends on a configuration's
page, or on one of the three journeys that change a configuration.

This journey reads. It writes nothing. Adding, changing and importing are the
journeys it links to.

* Official, approved and draft

A party does not hold many official pricing configurations. Model risk controls
the model settings: the quant team, market risk and model validation sign them
off. A party therefore holds one official configuration for each cycle, usually
=intraday= and =eod=, and every official report of that cycle binds it. The
other configurations are drafts. A draft is a place to try a change, and no
official report can bind it.

Each configuration shows one of four statuses:

#+ATTR_HTML: :class hug-leading
| Status | Meaning |
|--------+---------|
| Approved | A version of it was signed off. The latest signed-off version is the version in force. |
| In review | A candidate for a cycle waits for sign-off. It is not in force. |
| Draft | It changes in place and needs no sign-off. No official report can bind it. |
| Retired | It is no longer in force. Its history stays. |

An approved version never changes in place. A change to it is a proposal for a
new version. The version in force stays in force until the sign-off completes.
[[id:41C7A1F2-8E5B-4D36-9A0C-7B2E5D1F6A93][Sign off a pricing engine change]] draws
that flow. The configuration that is official for a cycle shows an *Official for*
tag. The list is short on purpose, and the screen says so.

* Steps

** Step 1: the list

1. *Open the list.* The person opens *Pricing engines* under the reporting area.
   The screen is a record list as the
   [[id:2BF7F03F-6BF4-45FF-8E26-4D3B4E2D943D][Record screen standard]] draws one:
   breadcrumb, the plural as the title, one sentence, *Refresh* and *Add*, a
   search, a filter, a paged table, and the four states.
2. *Read a row.* A row is one configuration: its name, its status, the cycle it is
   official for, its variant tag, the count of products it covers, the count of
   reports that bind it, and when it last changed. A configuration with an open
   proposal carries a tag that says so. The variant tag is the ORE file family the configuration came from,
   such as =AMC=, =SABR= or =delta-gamma=; a configuration with no variant shows a
   dash.
3. *Find one.* The search runs on the server over the name and the description.
   A filter narrows by variant. A second filter narrows by status. A third filter,
   *Used by reports*, shows only the configurations a report binds, or only the ones
   no report binds.
4. *Start a change from the list.* *Add* opens
   [[id:0D39E4B7-75FD-480A-A996-2234BCC7BCC8][Author a pricing engine configuration]].
   The *Workflows* menu offers
   [[id:BC2066E8-C595-47C0-97CE-19DF182F616E][Bring in a pricing engines file]]
   and the queue of
   [[id:41C7A1F2-8E5B-4D36-9A0C-7B2E5D1F6A93][Sign off a pricing engine change]].

** Step 2: one configuration

5. *Open the page.* A click opens the record page: the name as the title, the
   lead line with the status, the cycle it is official for and the version, the
   access mark, and the actions for a person who may take them. On an approved
   configuration the action is *Propose a change*, not *Edit*, and *Delete* is not
   offered. On a draft the actions are *Edit* and *Delete*. A banner states a
   pending proposal, how many roles have approved it, and that the version in
   force stays in force. The tabs are held in the address.
6. *Read Details.* The name, the status, the cycle it is official for, the version
   in force and the roles that signed it off, the description, the variant, and the
   last-changed line. A configuration carries a link to the reporting configuration row it is
   bound through, and the page names it, because that row is what a report
   definition binds.
7. *Read Products.* One row for each pricing engine type the configuration
   covers, in =position= order: the product type with its description, the model,
   the engine, and the count of parameters the row carries. The product type is a
   code from the pricing engine type vocabulary, and the row shows the instrument
   type it maps to. The tab offers *Add* under the table and *Edit* on a row, as
   the standard draws a parts panel.
8. *Read Parameters.* The settings in three groups: the *global* parameters of
   the whole document, the *model* parameters of each product and the *engine*
   parameters of each product. A parameter is a name and a text value. The tab
   says where each one applies, because the same name can sit in two scopes.
9. *Read Reports.* The report definitions that bind this configuration, each with
   a link to its page, its cycle, its portfolio, the product types it needs, what
   this configuration leaves unpriced for it, and the version it runs with. A
   report whose cycle differs from the configuration's is marked. The tab states
   the rule: a report needs a price for every product type in its portfolio, and a
   configuration that several reports bind must cover all of their portfolios
   together. It also states the reach: a change reaches the next run of each of
   these reports once it is approved, and a run already produced keeps what it ran
   with.
10. *Read History.* The shared timeline of the configuration and its products,
    newest first. Each version in force shows the roles that signed it off. A
    proposal that waits shows at the top and is not a version in force. On an
    approved configuration, *Propose a revert* replaces *Revert*: it writes an older
    version's values as a new proposal, which needs the same sign-off.

** Step 3: what the configuration leaves unpriced

11. *Read the coverage strip.* Above the Products table, one line states how many
    of the product types the reports that bind the configuration need have a row
    here. With no report bound, it counts the product types the party trades. A
    product type that is needed and not covered is named, because a product
    with no row has no model in a run: the run fails or skips it, and the result
    is smaller than the book. The strip is a reading, not a fix. It links to
    *Add* on the Products tab, and to
    [[id:D998F36A-9716-48E7-BC70-BC4813115591][Change how a product is priced]].
12. *Leave.* The person goes to a report that binds the configuration, or on to
    change it.

* Screens and wireframes

Two screens: the list, and the record page with five tabs. The sign-off has its own
screen, in its own journey. A journey is one
screen composed around a goal, so the Products tab carries the coverage strip and
the Reports tab carries the reach, rather than a separate screen for each.

* Prototype

The [[file:../../prototypes/reporting/see-the-pricing-engines-a-party-holds/][see the pricing engines a party holds prototype]] owns this journey, and
[[file:../../prototypes/reporting/see-the-pricing-engines-a-party-holds.org][its design note]] says what it argues, which states it can reach and what is
fake. It belongs at =doc/prototypes/reporting/see-the-pricing-engines-a-party-holds/=.

It must draw the list and the record page as the Record screen standard draws
them, with no layout of its own. The list must show the name, status, the cycle a
configuration is official for, variant, product count, report count and last
change, a server search, a variant filter, a status filter and a used-by filter,
the pager, and the states first load, empty, nothing matches and error. It must
show an approved configuration that is official for a cycle, with a pending
proposal, and a draft. An approved configuration must offer *Propose a change* and
no *Delete*. The record page must carry Details, Products, Parameters, Reports and
History. The Products tab must carry the coverage strip with a product type the
party trades and the configuration does not cover. The Reports tab must state the
rule and the reach, with a row for each report and what it leaves unpriced. Every value is a fixture and the page says so.

* What is missing

1. *A route and a screen.* No BFF route serves pricing engines and no screen
   reads them. The list and the page are new. The configuration is reachable from
   the browser today only through the shell.
2. *Reads of the parts by configuration.* The document read returns the whole
   document, which is enough for a page. The list of configurations needs a count
   of products and a count of reports for each row, and no operation returns a
   count. Until one does, the list reads one page of configurations and the counts
   come from a second read, or the column is dropped.
3. *The reports that bind a configuration.* =report_configurations.list= lists
   the bindings of a definition. Nothing lists the definitions that bind one
   configuration, which is the question the Reports tab asks and the question
   [[id:87B9678E-2085-4968-8AEA-7184D1384F1D][Change what a report runs]] asks as
   "who else is bound". The tab needs the read by configuration id.
4. *The products the party trades.* The coverage strip compares the configuration
   with the instrument types of the party's trades. No operation returns the
   distinct instrument types of a party's book. Until one does, the strip is a
   fixture and says so.
5. *A variant is a tag, not a thing.* =config_variant= is free text. The filter
   offers the values the page has read, and cannot offer a vocabulary.
6. *No status, no cycle and no sign-off.* The record carries a name and a
   description, and nothing that says a configuration is draft, in review,
   approved or retired. Nothing says which one is official for a cycle, and
   nothing records who signed a version off. The prototype draws all three from a
   fixture. A build needs a status and a cycle on the configuration, and a record
   of the sign-off on each version.
7. *A report binds a configuration, not a version.* =report_configuration= holds
   the configuration, so a report runs with the latest version. A version in force
   needs a pointer, or the write of a proposal must not touch the rows that a run
   reads. The Reports tab shows the version in force, and the screen cannot show
   which version a run used.
8. *The product types of a report's portfolio.* The rule needs what each report
   holds. No operation returns it, so the tab uses a fixture.
