* Notes

** What the component is, and what that makes not applicable

ores.shell holds no entity, junction or operation model of its own. Its single
model is =component_overview.org=, metatype =ores.codegen.component=, and every
generated unit under =projects/ores.shell/<component>/= is output of that
*other* component's model, rendered into this tree.

Three consequences run through the whole checklist.

- The Entity section (M01 to M10) is about this component's own models, and there
  are none. Each item is recorded not applicable with that reason rather than
  left blank.
- The Protocol section (P01 to P06) is about the subjects this component owns.
  The shell serves none: it is a client of every other component's protocol. The
  items that speak of subjects this component declares are not applicable; the
  ones about consumers following a protocol change in the same work (P05) very
  much are, because the shell is the consumer that breaks first.
- G01 has two halves. The shell's own models are already byte-identical, which
  the baseline proves. The generated units it hosts belong to their own
  components' G01, and a change to a shell-command template changes them all,
  which is why the codegen sweep exists.

** Where the component sits under other components' work

The shell is the render target of twelve components' shell-command facets, so a
model change anywhere reaches this tree. Twenty generated units right now carry
their components' pending model drift rather than this component's: sixteen in
refdata and four in synthetic, missing a =party_id= positional and stale usage
text. Their own clean-up stories bring them current; regenerating them here would
absorb another component's change.

** The shadowing exception this branch supersedes

The registry carries an accepted exception on item S01 that reads "Four
hand-written shell units survive and are registered after the generated
aggregator, so some overlapping verbs are shadowed and the rest duplicate
generated behaviour." That was true when it was written. Story 42C0752B, merged
as PR #2272, removed the possibility: a second unit no longer registers a second
menu, it extends the one that exists, and a duplicate name fails at startup. The
exception's reason is now stale and belongs to whichever component it is filed
on, which is not this one; this note is so the two are not read as agreeing.
