* Acceptance

- A list shows the configurations of the party, with the variant, the product count and the setting count, and it searches and sorts.
- A record page shows one configuration with its products and settings, and offers Change, Add product, Remove and Delete to a person with the write permission only.
- A change states the difference, runs the checks, asks for a reason and saves the whole document against the version it read. A stale version is a conflict, and the dialog offers to read again.
- Authoring is a journey of six steps: name, products, model and engine, settings, check, review and save. It starts empty or from a copy.
- The models, engines, pairs and settings come from lookup tables, seeded from the ORE user guide chapter on the pricing engine configuration: pricing_model_engine_pair and pricing_pair_setting for the pairs and their settings, pricing_model and pricing_method for the description of each model and engine, and sensitivity_template for the sensitivity template keys.
- A product dialog shows the model and the engine side by side, each with its description and the source of the words. A setting shows its meaning under its field. A tenor setting offers the tenor list, and a sensitivity template setting offers the templates.
- Saving a document removes the products and parameters that the new version omits.
- The BFF routes, the web client and the screens have unit tests.

- The reach of a change. No operation lists the reports that bind a configuration, so the screens say so.
- Deleting a configuration leaves its reporting configuration header. A later change removes both.

* Notes

- *Document save.* The service stamps the tenant and the party itself, and it keeps the change reason that a row names. The BFF therefore puts the reason on every row of the document.
- *Vocabulary source.* The ORE user guide chapter lists the pairs and the settings. Where the guide and the ORE code spell a name differently, the generator takes the code's spelling, and it drops any name that the code does not know. The descriptions of the models and engines come from the guide where it has them. Where it has none, the description is written for ORE Studio and carries the source =authored=, so a person can find it and review it. The allowed values of a setting come from the ORE parsers where a parser fixes them.
- *Required settings.* The guide marks a setting optional when ORE has a default. A setting that is not marked is required. A new product starts with the required settings only.
- *Sensitivity template.* A template is a key. The pricing engine configuration puts it on a product, and the sensitivity configuration sets shift sizes for the products that carry it. The screens offer the templates and state what each one is. A link to the shifts of a template needs the sensitivity configuration screens, which are not built.
- *Timestamps.* A row the browser creates carries the epoch in the wire format, and the service stamps the real time.
