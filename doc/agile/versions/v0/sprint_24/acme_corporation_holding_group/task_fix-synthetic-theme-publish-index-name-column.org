* Goal

=ores_synthetic_publish_theme_from_dq_fn= must publish a synthetic
theme (e.g. =synthetic.themes.realistic_2026=,
=synthetic.themes.ore_samples_2016=) without error, so every party's
synthetic market-data feed actually starts. Currently every call
fails with =ERROR: column existing.index_name does not exist=
(=ores.synthetic.messaging.publish_from_dq_handler= log). As a
consequence, [[id:9A94B0D4-4244-4A6B-8AFA-26AC69681519][Tidy up the saved connections database and decommission
Barclays/NatWest]] temporarily removed =synthetic_realistic_2026= from
the shared =party_provisioning_bundle_plan()= (used by both Acme's and
Barclays'/generic provisioning) to stop every provisioning run logging
a hard failure for it — that entry must be restored once this is
fixed, no other client change needed.

* Plan

Once the upstream fix landed on =main=, went further than a plain
revert of the workaround, per explicit direction: Acme should pull in
*all* the config needed to exercise ORE Studio's synthetic-data
scenarios out of the box, not just today's default theme, since live
pricing and legacy-ORE-Samples pricing (via workspaces) are both
coming soon and re-provisioning shouldn't be needed to test them
later.

- Reverted the =party_provisioning_bundle_plan()= workaround: restored
  =synthetic_realistic_2026=.
- Added =synthetic_ore_samples_2016= to the same shared plan --
  publishing a theme's *config* is safe/cheap even though only one
  theme's *feed* should ever run at a time (existing
  =MarketSimulatorWindow= rule); a party can now immediately test
  either theme once feed-starting/workspace-scoped pricing lands, with
  no re-provision.
- Split the CRM Cross-Rates Matrix topology out of both vintage
  bundles into its own standalone, vintage-independent =crm_topology=
  bundle (=dq_dataset_bundle_populate.sql=/=dq_dataset_bundle_member_populate.sql=),
  per explicit direction that CRM must always be available regardless
  of which synthetic-data theme/vintage a party happens to publish.
  Added to the shared plan alongside the two themes.
- None of this required any Acme-specific C++ change: every addition
  is a SQL bundle registration consumed by the existing, generic
  =party_provisioning_bundle_plan()= loop that both Acme's provisioner
  and =ores.shell='s generic "provision party" flow already share --
  no new hardcoding of Acme into C++. The pre-existing Acme-specific
  bespoke provisioning logic in =tenant_handler.hpp= (=provision_acme=)
  predates this task and is tracked separately by [[id:4D2F72BC-09C5-41B6-A9BB-AF2B8B140B50][Extract shared
  party-bundle-plan publisher]].
