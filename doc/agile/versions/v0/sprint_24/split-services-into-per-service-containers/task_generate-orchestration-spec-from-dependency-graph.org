* Goal

Read ~service_definition~/~service_dependency~ from the DB and emit
the equivalent ordering directives for the orchestration layer chosen
for the per-service rollout (podman-compose ~depends_on~, or
~podman generate systemd~'s ~After=~/~Requires=~), so the dependency
graph that currently drives ~process_supervisor~'s topological launch
order in-process stays data-driven instead of becoming a hand-
maintained static file once each service is its own container.

* Acceptance

- A generator reads ~service_definition~/~service_dependency~ and
  produces a valid ordering spec for the chosen orchestration
  mechanism, without hand-editing.
- Changing a dependency edge in the DB and re-running the generator
  changes the emitted ordering accordingly, with no code change.
- The generated spec is verified against a real multi-service startup
  (at minimum IAM before one of its dependents), confirming the
  emitted ordering is actually honoured by podman/systemd.
