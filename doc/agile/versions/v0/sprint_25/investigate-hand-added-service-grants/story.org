#+title: Story: Investigate hand-added cross-service grants in generated iam_service_db_grants_create.sql
#+description: While removing the controller from the db recreate pipeline (task 3620F51C, PR #1867), regenerating iam_service_db_grants_create.sql from the service registry model (ores.codegen ores.sql.service address) revealed the committed file carries hand-added grants with explanatory comments that the generator does not emit: iam_service gets select on ores_assets_ + execute on ores_assets_get_template_image_fn (Acme provisioner logo copy) + select on ores_dq_ (cross-entity party membership); refdata_service gets select on ores_assets_ (party image soft-FK validation). A wholesale regeneration would silently drop these load-bearing grants — the file no longer matches generator output and the next codegen run produces an unexpected diff. Investigate whether the registry model/template should express per-service cross-domain grants so generation is lossless, whether these grants are correctly placed, and how to close the drift so regeneration never silently drops grants.

generator output exactly.

* Acceptance

- Root cause documented: why the four hand-added grants exist
  (Acme provisioner logo access, party image soft-FK validation,
  cross-entity party membership), why the generator does not emit
  them, and whether they are correctly placed in the file.
- A decision on the fix: extend the registry model/template with
  per-service cross-domain grant lists (generation becomes lossless),
  or an alternative that guarantees regeneration never silently drops
  grants (e.g. a generator guard that fails on unexpected manual
  content).
- The committed file matches what the generator produces (regeneration
  is a no-op diff), or the drift is closed by an explicit mechanism
  with a test proving it.
