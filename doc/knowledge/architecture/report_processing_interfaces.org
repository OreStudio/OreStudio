* Summary

This page is the reference for what a report run sends and stores. It collects
the messages of the pipeline, the messages that control it, and the objects a
run reads and writes, so that an implementer has one list to work from rather
than one per phase.

Subjects marked *designed* do not exist yet; an unmarked subject is implemented
and its name is the one in the protocol header. A substitute's subject is
dispatched instead of the phase it replaces, never alongside it.

* Detail

| =reporting.v1.ops.trigger_report_instance= | the shell, or the scheduler on a firing | reporting | definition, tenant, and the firing's identity |
| =workflow.v1.start= | reporting | the workflow engine | workflow type, the run's request, and its run configuration |
| =reporting.v1.report.gather-trades= | the workflow engine | reporting | instance, definition, tenant |
| =reporting.v1.report.gather-market-data= | the workflow engine | reporting | instance, definition, tenant |
| =reporting.v1.report.assemble-bundle= | the workflow engine | reporting | the two storage keys and the counts they carry |
| =ore.v1.report.prepare-package= | the workflow engine | ores.ore | the two storage keys |
| =reporting.v1.report.resolve-prepared-input= *(substitute)* | the workflow engine | reporting | instance, tenant, and the prepared input key |
| =compute.v1.report.submit= | the workflow engine | ores.compute | instance, tenant, correlation, and the tarball URIs |
| =compute.v1.work.assignments.{tenant}.{platform}= | ores.compute | a worker node, by queue group | result, workunit, package and its digest, input, output |

** The messages that control the run rather than perform it

| Subject | Publisher | Consumer | Purpose |
|---------+-----------+----------+---------|
| =scheduler.v1.job_definitions.put= | reporting, when reconciling | the scheduler | create or update a definition's schedule |

** The bulk reads pre-processing depends on

These are not steps of the run, but the first phase cannot work without them.
Both exist, as operation subjects on the component that owns the data.

| Subject | Publisher | Consumer | Payload |
|---------+-----------+----------+---------|
| =trading.v1.trades.export-to-storage= | pre-processing | ores.trading | the book scope and the target key; returns the trade count |
| =marketdata.v1.series.export-to-storage= | pre-processing | ores.marketdata | the target key; returns the series count |

Both write into the platform bucket under the key the caller supplies, which is
=reporting/runs/{instance}/trades.msgpack= and
=reporting/runs/{instance}/market_data.msgpack=
(=projects/ores.reporting/core/src/service/execution_storage_plan.cpp=). Neither
filters by the run's scope beyond the trades call's book list, so a report whose
scope is narrower than its tenant still exports the tenant's data. That is what
the designed, scope-limited reads below would close; they do not exist.

| Subject | Publisher | Consumer | Payload |
|---------+-----------+----------+---------|
| =trading.v1.ops.scope-read= *(designed)* | pre-processing | ores.trading | scope and as-of timestamp; returns the trades |
| =marketdata.v1.ops.resolve= *(designed)* | pre-processing | ores.marketdata | the selected trades; returns the items they require |

** Storage

#+ATTR_HTML: :class hug-leading
| Object | Key | Written by | Read by |
|--------+-----+------------+---------|
| the engine package | =compute/packages/{app}-{version}/{app}-{version}-{platform}.tar.gz= | seeded, once per engine build | the worker node |
| the gathered trades | =reporting/runs/{instance}/trades.msgpack= | ores.trading, asked by pre-processing | the packaging step |
| the gathered market data | =reporting/runs/{instance}/market_data.msgpack= | ores.marketdata, asked by pre-processing | the packaging step |
| the package | =ore/packages/{instance}/ore_package.tar.gz= | the packaging step | the worker node |
| a prepared input | whatever the definition's =prepared_input_key= names | seeding, or an earlier run | the run, on the substitute path |
| the engine output | =compute/output/{result_id}.tar.gz= | the worker node | retrieval, post-processing |

All keys are under the platform bucket =ores=, so the object path is
=/api/v1/storage/ores/{key}=. The engine package and the output path are built
by =ores.compute.api/net/compute_storage.hpp=, and the three reporting keys by
=projects/ores.reporting/core/src/service/execution_storage_plan.cpp= and
=projects/ores.ore/service/src/messaging/report_package_handler.cpp=.

The packaging step re-downloads the two gathered blobs and re-tars them without
parsing them, so the objects need not be MsgPack the engine understands. The
tarball it produces is the =Input/= directory shape the engine expects, which is
why the prepared substitute for a test run is a bundle a person could hand the
engine.

Both object access paths are as specified in
[[id:286B7167-9B8A-4937-BBA5-E9D285AFECE3][Object Storage]]: the command subjects
=storage.v1.objects.put/get/delete/list= for control, and
=PUT/GET /api/v1/storage/{bucket}/{key}= for bytes.

** Naming

- Entity verbs name a resource and a verb, as the
  [[id:C650CBC9-FDED-4C68-981F-7902E296928E][entity protocol]] specifies.
- Not every subject here is an operation. The phase subjects are addressed by
  the service that owns the phase (=reporting.v1.report.*=, =ore.v1.report.*=,
  =compute.v1.report.*=) rather than under a shared =ops= segment, because the
  phase a service implements is part of that service's own surface.
- The subject of a substitute names what it does — =resolve-prepared-input=,
  =ignore-compute-results= — rather than naming the phase it replaces plus a
  flag.
