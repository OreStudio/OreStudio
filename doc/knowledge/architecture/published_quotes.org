#+title: Published quotes are loaded once from public sources and read by the calibration
#+description: The architecture of the published quote table: one append-only table of what public bodies published, the publisher catalogue, the provenance chain from fetch to row, the seed command, and the reader that the calibration uses.
#+type: knowledge
#+level: cross
#+filetags: :marketdata:published_quote:calibration:
#+created: 2026-10-23
#+updated: 2026-10-23

* Summary

A public body such as the ECB or the Federal Reserve publishes rates every day. The system loads what they published into one append-only table, =published_quote=, and keeps for every row where it came from. The loading is a job of its own with a seed command. A stochastic generator never loads anything: its config points at an item and a policy, and a reader returns the value with its provenance. The two halves meet only at that reader.

* Detail

** Two layers

#+begin_example
 publishers (ECB, Fed, Treasury ...)      what the world published
        |  fetcher classes (one per access route, such as Frankfurter)
        v
 LOADER  -- seed command, daily top-up --> published_quote + provenance tables
                                                  ^
                                                  |  published_quote_reader (read only)
 CALIBRATION -- a generator config names an item and a policy
#+end_example

- The loader knows nothing of stochastic processes. It loads ranges and records provenance.
- The calibration knows nothing of publishers or HTTP. It calls the reader, as the vintage read did.
- A feed never fetches. When the table has no value, the feed keeps its fixed level and the screen says so.

** The table

=ores_marketdata_published_quotes_tbl= is one table for the whole system. It is a hypertable on =ts= with a chunk interval of one year, because daily rows for a small set of series are sparse. Rows are only added, a correction is a new row, and the reader takes the latest =retrieved_at=. The prose calls a row a =published_quote=, and the table name is the longer form. The system tenant owns it, every tenant reads it, and a loader role alone writes it. It has no retention, because the history is kept.

| Column | Meaning |
|--------+---------|
| =item_id=, =item_uri= | What the value is, in oresmd notation |
| =ts= | The valid time the publisher gives. A publisher that gives only a date gets midnight UTC, and =granularity= says =day= or =instant=. A =day= row is eligible on its own date, whatever the time of the publication, because the clock compares dates and not instants |
| =value= | =numeric=, exactly as published. A day that the publisher marks as missing (=ND= in H.10, =.= in FRED, an absent day at the ECB) has no row. The loader never stores a null |
| =source_key= | The id the publisher used, such as =D.USD.EUR.SP00.A= or =DEXUSEU= |
| =retrieved_at= | The transaction time |
| =fetch_id= | The HTTP response that produced the row |

** The item is in oresmd notation

A published quote is not vendor data, so its item is provider-neutral: one row serves a Bloomberg, an LSEG and a Demo generator through the catalogue mapping. A publisher's own key stays on the row as provenance, and a table =publisher_series= maps =(publisher, source key)= to the oresmd item, which is the pattern of the vendor instrument mapping. No source is written into code.

A cross rate, such as USD/JPY from EUR/JPY and EUR/USD, is not stored. The reader computes it, reports it as derived and names both rows.

** The provenance chain

#+begin_example
 row --> fetch --> load --> publisher (version)
#+end_example

- *publisher* is a catalogue entity: a code (=ecb=, =fred.h10=, =ust=), a name, the fetcher that reads it, the terms URL, =terms_read_at=, the credit text, =allows_storage=, a credential reference and a rank. It is bitemporal, so a change of terms keeps its history, and a load records the version it used. A publisher can be enabled only when =terms_read_at= is set.
- *quote_load* is one run of the seed command: who, which range and items, the tool version and the counts.
- *quote_fetch* is one HTTP call: the URL with every secret removed, the time, the status, a SHA-256 of the body, its size and =raw_ref=, which points to the stored body in =ores.storage=. The raw bodies are kept so any row can be traced back to the bytes.

Frankfurter is a fetcher, an access route, and not a publisher. It is asked for one provider at a time and never for the blended rate, so each row names the bank that published it.

** Seeding

The shell command is =quotes seed --publisher ecb --from 2020-01-01 --to today [--items ...] [--refresh]=. It calls one NATS operation, =marketdata.v1.ops.seed_published_quotes=, which needs the permission =marketdata::published_quotes:seed=. The names follow the existing =marketdata::<entity>:<verb>= permissions and =marketdata.v1.ops.<verb>= subjects. A load is idempotent because the loader checks =(publisher, source key, ts)= before it inserts and skips a day that is loaded, unless =--refresh= is given. No unique constraint enforces it, because a refresh adds a second row for the same key and a hypertable unique index must also hold the partition column. =today= comes from the market clock of the capture [[id:CF2FFE22-85E6-4490-B44D-37657F9B76EE][A system clock drives the date the feeds read]]. Until a system clock exists, the host clock gives the date, and neither the seed command nor the daily job waits for it. The daily top-up is a scheduled job that runs the same operation from the last loaded day to today. No other code fetches.

** How the calibration points at it

A generator config has =price_source= of =fixed= or =published=, and for =published=:
- =quote_item_uri=, the item;
- =quote_policy=: =latest_on_or_before_clock=, or =exact:<date>= for a repeatable run;
- =quote_window_days=, the window of the volatility.

=published_quote_reader= has =latest(item, on_or_before)= and =window(item, to, days)=. Each returns the value with a provenance handle: publisher, source key, =ts=, =retrieved_at= and fetch. The feed screen shows it: "ECB EUR/USD of 22 Oct, retrieved 23 Oct 06:00 through Frankfurter". A pair that no publisher covers stays =fixed= and says so. A window skips the days that have no row, so a window with gaps holds fewer returns. The log return spans the gap, and the reader reports the number of returns it used.

** Why not market_observation

It would reuse readers and screens, but its rows belong to a series keyed by item, provider and party, they are bitemporal, their values are text, and its chunks are 30 days. It would put a shared cache of the world inside party series, and it has no place for the fetch and load provenance.

** Secrets

A credential is never in a table, a log or a stored URL. A publisher row holds a =credential_ref=, such as =env:ORES_MARKETDATA_SERVICE_FRED_API_KEY=, and a =secret_source= interface resolves it. Hashing does not fit: a hash cannot be turned back into the key that a provider needs. The first implementation reads the service environment, as the database passwords are read. A second one, an encrypted table with AES-256-GCM through OpenSSL, can follow without a change to the publisher rows.
