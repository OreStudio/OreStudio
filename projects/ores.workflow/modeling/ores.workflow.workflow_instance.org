Tracks the lifecycle of a workflow execution, including its type, the entity it
acts on, its status, the serialised request that triggered it, and any result or
error produced. Instances are append-mostly; status transitions are the primary
mutation.

** target_kind
:PROPERTIES:
:type:     text

:END:

What the run acts on, named by the caller: 'tenant' for a run that provisions a
tenant. The engine stores it and never interprets it, so a component states its
own kind without the engine learning that component's vocabulary.

A run that acts on no entity leaves it empty.

** target_id
:PROPERTIES:
:type:     uuid
:cpp_type: boost::uuids::uuid
:nullable: true
:END:

Identity of the entity the run acts on, in the kind =target_kind= states. It is
not a foreign key: the engine cannot hold one to every component's tables, so it
is a soft reference, the way a status row names its badge.

The target is not the owner. =tenant_id= states the tenant whose work the run is,
which scopes the run and governs who reads it. The target states what the run
works on, which may be a different tenant entirely. Provisioning is the case that
makes the difference plain: the run belongs to the tenant that asked for it, so
that tenant can follow its own work, and it acts on the tenant it creates, which
cannot read the run because its session does not exist yet.

* Indexes

The list query filters by state and orders by type, and a lookup names one
instance, so the tenant index and the tenant-scoped unique index are the hot
paths. The engine's own list read is not: it spans every tenant, so it cannot
use a leading =tenant_id=, and it reads the open rows in one pass at startup.
That pass is bounded by the runs in flight rather than by the table, so a scan
is the honest cost of recovering all of them. A read that asks which runs act on
one entity leads with the target index, which is how a component finds the work
it has in flight on something it owns.

** Repository
:PROPERTIES:
:tenant_read_scope:        shared
:entity_singular_short: instance
:entity_plural_short:   instances
:entity_singular_words: workflow instance
:entity_plural_words:   workflow instances
:END:

Reads rely on the row-level security policy instead of an application-level
=tenant_id= predicate. That policy admits a row to its own tenant, and to a
system-tenant session it admits every tenant's rows.

The engine is a cross-tenant service. It holds the system tenant and drives runs
that belong to whoever asked for them, so a =tenant_id = ctx.tenant_id()=
predicate on top of the policy hides every other tenant's run from the engine.
A run it cannot read back is a run it cannot advance or recover: the step insert
is refused, the published marker and the step progress become silent no-ops, and
the completion event finds no step. A tenant session still reads only its own
rows, because the policy is what draws that line.
