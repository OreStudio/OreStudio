* Goal

One page a person can read to find out what a product type is before they book
it: every type the tenant may book, what each one means, where its documentation
lives, and which books and permissions allow it.

Today the catalogue is stated in rows a screen reads one deal at a time. A
trader who has never booked a =BondOption= has no page to open, and an
operations person who is asked why a book refuses a type has no page to quote.
The knowledge corpus describes the families in prose, one document per family,
and nothing joins that prose to the catalogue the store holds.

* Acceptance

- The store holds one product type table, with one current row per code, seeded
  from the system catalogue. No tenant holds a copy, and no second catalogue
  states a product type.
- Every product type carries a description of what the product is, and the
  source that description came from.
- A page lists every product type the catalogue holds, by the name a desk uses
  and the code the store holds.
- Each type states what it is, the markets it references with its home market
  named, the family it belongs to, and where its documentation is: the ORE
  product page, the knowledge document, or both.
- Each type states what allows it: the books a tenant has enabled for it, and the
  permission a person needs to book one. Both come from a junction against the
  catalogue.
- Every place a product type is named links to its page.
- The pricing engine types join the catalogue rather than restating it.
- A type the catalogue holds and no page can describe is listed as undescribed
  rather than hidden, so the gap is visible.

* Decisions

- *Product type means the 121 codes a tenant books, and nothing else.* The
  eight-value =product_type_t= enum is not a product type: it dissolves into a
  set of asset classes, a product family and a construction method. No routing
  family survives it, because nothing routes on the enum: the instrument table on
  the row routes. The markets a product references are a junction, because a type
  may reference two, and one of them is marked as the market it is grouped under.
  [[id:E7095E28-EB36-427C-9C14-AB6AB0593B33][The axes a product type carries]] settles the columns, the junction, the
  spellings and what a missing axis means.
- *One table, one copy.* The catalogue is declared once in codegen and seeded
  into the system tenant. Every tenant reads those rows. The per-tenant copies
  and the provisioner copy go, because the trade check already reads the system
  rows and a second copy can only drift away from them.
- *The row carries the documentation.* A description, the source it came from,
  and the knowledge note it belongs to. The page links to the note for the prose
  rather than restating it.
- *Every use joins the catalogue.* The pricing engine types join it by a column,
  because each names at most one product type; the allowed books, the permission
  and the flow classification join it by a junction, because each is a set.
  [[id:23F5286D-2B19-45BE-B63F-E8FD541AA917][How the pricing engine types join the product type]] settles which of the
  108 name a product, which are finer, which are building blocks and which name
  a product the catalogue lacks. No use keeps a list of its own, and no screen
  holds a code.
- *The page is a screen.* It reads the store, and it shows what the catalogue
  holds rather than hiding a type it cannot describe.

* Out of scope

- The desk-facing product type. A desk treats four configurations of =Swap= as
  four products. That is a finer classification many-to-one onto this catalogue,
  and it stays a capture.
- Risk classes per product type. [[id:327EFD17-5708-4A54-AF4B-52CF60E87C01][Risk Classes]] proposes the relationship, and it
  belongs to the risk work.
- The trade population weights as data. The note links the codes it weights;
  weighting the generator is the population story's work.
- The asset class taxonomy beyond the code sets the axes need.
  [[id:7F5EBFBD-FB8C-4E79-B386-7098104D3EDB][Asset classes]] carries its own analysis.
