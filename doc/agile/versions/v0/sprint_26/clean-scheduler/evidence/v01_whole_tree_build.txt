Why the direct command, and not `compass build`
------------------------------------------------

`./compass.sh build` was run first, and it failed before reaching the
compiler:

    systemd-run --user --scope -q --collect ... cmake --build --preset ...
    Failed to connect to user scope bus via local transport: No data available

The wrapper cannot run in this session. This session's commands execute inside a
bubblewrap sandbox with an unshared PID namespace -- /proc/1/comm inside it is
`bwrap`, and /proc/self/ns/pid is not the host namespace -- so systemd-run
cannot reach the user manager. The manager itself is present on the machine:
/run/user/1000/systemd exists and `busctl --user list` shows
org.freedesktop.systemd1. The two commands are the same command: compass runs
`cmake --build --preset linux-clang-debug-make -j 3`, and
build/output/linux-clang-debug-make is that preset's binary directory. The
direct run is recorded because it is the only form the environment allows, not
because it is a different check.

The rebased head, 3955878f0d, and the workflow component
=================================================

After the second rebase the whole-tree build was run again, and it fails, in
main's workflow component and not in this one. Three separate causes, all
reproduced on a still tree:

1. =projects/ores.shell/workflow/tests/= has no =main.cpp=, and its
   hand-written =component_files.cmake= does not list one, so
   =ores.shell.workflow.tests= links with no =main=:
   "undefined reference to `main'". Every other shell part's tests directory
   carries that file, and the only difference between them is the module name
   the logging listener registers. This branch adds the file, mirroring the
   sibling parts with =ores.shell.workflow.tests= as its module name; the
   target then builds and passes 102 assertions in 36 cases.
2. =projects/ores.workflow/api/src/CMakeLists.txt= declares its api target as
   =INTERFACE=, so the eight =.cpp= files under =api/src/= -- among them the
   definitions of =operator<<(std::ostream&, workflow_instance const&)= and its
   step sibling -- are compiled into nothing. =libores.workflow.core.so= keeps
   them undefined, and the first executable that links it fails:
   "libores.workflow.core.so.0: undefined reference to
   `ores::workflow::domain::operator<<(...)'". The declaration and the
   definition both exist; what is missing is a target that compiles them. The
   export header repeats the claim that the api is header-only, which its own
   =src/= directory contradicts.
3. =projects/ores.workflow/core/tests/CMakeLists.txt= does not link
   =ores.eventing.core.lib=, although its eventing integration test includes
   =ores.eventing.core/service/entity_event_publisher.hpp=. The compile fails
   with "file not found". The scheduler's equivalent test target links both
   =ores.eventing.api.lib= and =ores.eventing.core.lib= and compiles.

None of the three is in a file this branch touches, and none is scheduler's to
fix. What this branch did build at this head, from the same log: the three
scheduler libraries, its service entry point, its three test binaries, its
consumer =ores.reporting=, and =ores.shell.exe=. The scheduler's part of V01
holds; the tree-wide clause is blocked by another component's integration.
