* Acceptance

- One operation writes a counterparty with its identifiers, contacts, netting
  agreements, netting sets, netting set identifiers, CSAs and eligible
  currencies, or none of them.
- One operation writes a party with its identifiers and contacts, or none.
- Both are reached on a subject of their own and both carry the caller's change

- The reply carries the parent as the store left it, so a caller reads the
  version it must state next.
- =compass check= is green apart from what is already red on main.

* Plan

** The shape already exists for the read

=counterparty= and =party= each declare a =composite_as_of= read pair in their
own =* Messages= section, and the generated protocol header and its TypeScript
twin render it from there. A hand-written handler method and a custom
subscription complete it. The composite write takes that shape, because it is
the one the two models already teach a reader.

| parent       | operation                                       | children |
|--------------+-------------------------------------------------+----------|
| counterparty | =refdata.v1.ops.put_counterparty_composite=      | identifiers, contacts, netting agreements, netting sets, netting set identifiers, CSAs, eligible currencies |
| party        | =refdata.v1.ops.put_party_composite=             | identifiers, contacts |

The counterparty's eight are the eight the journey's confirm lists. The
visibility row is the journey's ninth write and is not one of them, so it stays
out: it belongs to the party that grants the visibility, not to the
counterparty.

** One transaction, and the mechanism is already there

=ores::database::repository::unit_of_work= owns one pooled connection and one
transaction, and its =ctx()= returns a context bound to that transaction. Every
repository call made with that context joins it, and the destructor rolls back
what was not committed.

So the handler opens one unit of work, builds each service on =uow.ctx()=, and
calls the services' domain-level =save_*= methods. Nothing new is needed in the
repository layer, and no service grows a method of its own.

** What the caller states

The request carries a =change_intent=. The handler applies its reason and
commentary to every row before the services stamp it, so the audit trail reads
the caller's reason rather than a default. The reply reads the parent back from
the committed transaction, so it carries the version the store gave it.

** What this does not do

It does not delete children the caller left out. A composite write upserts what
it is given, in one transaction; the journeys remove a child through its own
delete operation, and folding removal into the composite needs the current set
to diff against, which the request does not carry.

* Result

* Result

Both composite writes exist and the two subjects are reachable.

=counterparty= declares =put_counterparty_composite_request= carrying the
counterparty and its seven children, and =party= declares
=put_party_composite_request= carrying the party and its two. Each has a handler
method and a custom subscription, and each renders into the C++ protocol header
and its TypeScript twin.

The handler opens one =unit_of_work=, builds every service on =uow.ctx()=, calls
the services' =save_*= methods in turn, and commits once. The unit of work rolls
back when it is destroyed uncommitted, so a refusal anywhere leaves none of the
writes behind.

| Check | Result |
|-------+--------|

| =check_component_drift --component refdata --address ores= | no drift, across every address |
| generated protocol, read | both request structs carry the fields and the subjects, and the response members match the designated initialisers the handler writes |
| generated handler, read | both methods build their services on the unit of work's context and commit once |
| generated registrar, read | both subjects are subscribed |

**What this task does not land.** No suite covers the composite handler. The
rollback it relies on is covered by =ores.database.tests=, but the wiring from
the request to the eight services is reachable only through NATS, and the
repository has no handler-level test precedent to copy. The hourly validator's
ctest will not reach it.

It also does not remove a child the caller leaves out; that needs the current
set, which the request does not carry.
