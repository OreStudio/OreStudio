* Decisions

- Root cause: fx_spot_subscription.cpp (projects/ores.marketdata/client/src/fx_spot_subscription.cpp)
  called rfl::json::read<fx_spot_tick> directly instead of
  default_wire_codec().decode<T>(), ignoring the tenant's negotiated
  wire codec entirely -- the one NATS-tick call site the original
  wire-format migration sweep missed, since it's a fire-and-forget
  subscription handler rather than a request_sync call the sweep
  grepped for. Fixed by commit 7fe8798452, PR #1809, under
  Task-ID 1FC899C9-48A9-416C-87D0-FF4BB54F0DB7 / Story-ID
  1A815B1E-904E-460C-A2FB-31D9E3B392E2 (the NATS wire-format story) --
  landed the same day this story's diagnostics task was authored, so
  by the time this story picked up, the fix was already on main.
  Verified live 2026-08-04: msgpack environment, FX Spot Monitor rows
  ticking, zero decode-failure warnings in the client log.
- While verifying the fix live, the user reported the CRM screen
  still blank. That premise (a provisioning-bundle gap) turned out to
  already be fixed on main (commit d49f97f06, 2026-07-30) -- verified
  via DB query, all three Acme offices have topology configs seeded.
  Live investigation instead found two real bugs in
  CrmCrossRatesMatrixMdiWindow/Controller
  (projects/ores.qt/marketdata/):
  1. crmClient_'s token_provider snapshotted currentAuthToken() once
     at construction instead of refreshing it per-request, silently
     breaking every CRM request ~35+ minutes into a session once the
     JWT expired (ClientManager's own proactive refresh timer keeps
     the session's token current, but this window never re-read it).
     Fixed with a thread-safe token holder refreshed on the GUI
     thread at the top of every reload().
  2. The CRM name picker (showMatrix()) queries topology configs
     across every party visible to the caller (no party filter on
     get_crm_topology_configs_request), while reload() scopes the
     actual rates query to only the current party. Picking a name
     that exists for a different party silently opened a matrix that
     could never show a row -- a legitimate empty response, not a
     request failure, so nothing surfaced it as an error. Fixed by
     filtering the picker to the current party, with an explicit "no
     CRM configured" message when it has none.
- Fixing those two bugs surfaced the real, larger gap: the default
  login party (Acme Corporation Plc, the holding company) genuinely
  has no CRM/treasury data at all, by current provisioning design
  (acme_bundle_populate.sql scopes books/portfolios/CRM to the three
  operating offices only). Whether a holding company should have
  treasury-level FX/CRM visibility is a product question, not a bug
  -- discussed with the user and broken out as its own story:
  [[id:C8FA1CE7-F4D7-4D9B-B6A5-1B3A623D7071][Holding company treasury functionality: FX/CRM visibility, Group Treasury book, consolidated reporting]],
  rather than decided unilaterally here.
