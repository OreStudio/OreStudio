* Goal

A provider is system reference data, seeded with the main vendors,
exchanges, a broker and a generic provider, and published through DQ. A
collection has a scope and may name its provider, every feed carries the
synthetic mark, and the ACME reports' FX and IR currencies have feeds from
one provider.

* Acceptance

- The provider catalogue is generated across every layer and published into
  the system tenant from the =system_core= bundle.
- A collection's scope ties its tenant and party: a system collection is the
  system tenant's and its system party's; row-level security lets every
  tenant read it.
- Every feed's source name starts =synthetic.=, and the feed tables check it.
- The ACME reports' FX spots and IR curves have feeds, set up by one synthetic
  feeds dataset that names its provider.

* Plan

Model the provider catalogue in =ores.synthetic= and publish it through DQ;
tie scope to tenant and party on the collection and widen row-level security
for system collections; mark every feed synthetic; then replace the 2026
Realistic dataset with a Bloomberg feeds dataset that covers the ACME
currencies, published the one way synthetic feeds are published.

* Notes

- The "synthetic theme" is renamed to the synthetic feeds dataset: artefact
  type =synthetic_feeds=, =ores_synthetic_publish_feeds_from_dq_fn= on
  =synthetic.v1.ops.publish_feeds_from_dq=, dataset codes =synthetic.feeds.*=,
  and the =start_market_feeds= step's =dataset= argument. It is the one way to
  set up synthetic feeds.
- =synthetic.feeds.bloomberg= replaces the 2026 Realistic dataset, in the
  =synthetic_bloomberg= bundle: a USD spot for 26 currencies and an
  overnight-benchmark curve for 28, which covers the currency gaps of
  [[id:E2FA0F12-2972-468B-93E8-2097E9E40113][the ACME feeds capture]]. Each feed
  row names its provider (=provider_code= on the FX and IR artefacts); the
  collection names the provider when every row agrees. The 2016 ORE Samples
  dataset is unchanged beyond the rename.
- The IR index families gained =cdi=, =czeonia=, =buboron=, =telboron=,
  =tlref=, =camara=, =ibr= and =hibor=, named as ORE's conventions name them,
  with matching overnight index conventions.
- A first attempt published Bloomberg as a system collection through a
  second publish path. It was reverted: it duplicated the one path, and the
  generated repositories do not read the system tenant, so no tenant could
  bind to it.
- The dead party provisioning plan (=party_provisioning_plan.hpp=, a
  hard-coded bundle list nothing called) is deleted.

* Result

Shipped:

- =market_data_provider= in =ores.synthetic=, generated across every layer,
  with eight providers published from DQ into the system tenant.
- Collection scope tied to tenant and party, the conflict guard kept, row-level
  security widened for system collections, and the synthetic mark checked on
  the FX and IR feed tables.
- The "synthetic theme" renamed to the synthetic feeds dataset, the one way to
  set up feeds; a feed row may name its provider.
- =synthetic.feeds.bloomberg= replaces the 2026 Realistic dataset: 26 USD
  spots and 28 overnight-benchmark curves plus the USD FOMC short end, with
  eight new IR index families and their conventions.

Not met: a system collection is readable in SQL but not through the
services, because the generated repositories read the caller's own tenant
alone, so no dataset publishes one yet. Tenants consume the Bloomberg feeds
from their own party collection.
