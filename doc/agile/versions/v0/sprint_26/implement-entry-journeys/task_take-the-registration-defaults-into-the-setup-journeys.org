* Goal

The Setup journeys carry the registration defaults. [[id:84C231B8-C861-44CF-89FB-D7A840D3EBDE][First run]] states whether the installation accepts self-registration and confirms the first tenant as the tenant a registration lands in, and its first sign-in lets the tenant administrator nominate the party a new account joins and the role it receives. [[id:4C062ECC-D6D4-4BA4-8F96-10E141663D9C][New tenant]] and [[id:9AB6C90E-5338-435A-9559-4E426D612EB6][New party]] ask the same questions when they create a tenant or a party later. The target state records where the defaults come from and corrects the switch's scope.

* Acceptance

- First run carries a registration step, and it is clear which actor sets each value.
- Its first sign-in nominates the party and the role, and says that neither is required.
- New tenant and New party offer the same nomination when they create the tenant or the party.
- The target state records that the setup journeys own the defaults, and says why the sign-up screen cannot.
- The switch's scope is stated: the deployment's answer, read at system scope, seeded false.

* Plan

1. Add the registration step to First run, after provisioning and before the hand-off, because that is where the tenant exists and the system administrator is still the actor.
2. Put the two nominations on the first sign-in, which is where the tenant administrator already is and where the party choice is made.
3. Add the operations the step needs to the journey's coverage table, marked by whether the subject exists.
4. Record the same questions on New tenant and New party, which create the two things a default points at.
5. Add the section to the target state, and correct the switch's scope while there.
