This page documents a [[id:31C868B9-306E-4282-BA8C-07E647021B34][task]] in the [[id:FBF532B1-01B3-458D-ADC2-72F96027946E][Close the route parity between ores.http and the BFF]] story. It captures the goal, current status, acceptance, and any notes or results.

* Goal

Three independent fallbacks each turn "not configured" into "allow", and each is
silent:

- *HTTP.* The middleware that parses the bearer token, validates the JWT and sets
  the request's authenticated user is skipped in its entirety when the server has
  no authenticator. The server says so once, as a warning, and serves the request.
  =projects/ores.http/api/src/net/http_session.cpp:140-193=, guard at =:152=;
  =projects/ores.http/api/src/net/http_server.cpp:41-53= logs and continues.
- *NATS.* The request context is built by =make_request_context=, which returns
  the base, unauthenticated context when no verifier is configured
  (=projects/ores.service/src/service/request_context.cpp:89-90=). A handler then
  runs with an empty identity rather than refusing.
- *Authorisation.* =has_permission= returns =true= when the context's permission
  list is empty, deliberately, to keep tokens minted before RBAC working
  (=projects/ores.service/include/ores.service/messaging/handler_helpers.hpp:198-216=,
  short-circuit at =:202-203=). A token with no permission claims therefore passes
  every check that uses it.

The three compound. A deployment that omits the authenticator accepts an
unauthenticated HTTP request; one that omits the verifier accepts any NATS
request; and even with both configured, a token that carries no permissions is
authorised for everything.

* Acceptance

- A server that holds no authenticator refuses to start, or refuses every request that is not declared open; it never accepts everything with a warning.
- A request that carries no verifier is refused on the message bus too.
- =has_permission= no longer answers true for an empty permission list, so a token that grants nothing is refused.
- A test proves each of the three.

* Plan

The capture names three fallbacks, and measuring them first changed the work:
two of the three had already been closed since it was written, and one had not.

** What was already closed

- *Authorisation.* =has_permission= refuses a token whose permission list is
  empty. =projects/ores.service/tests/handler_helpers_tests.cpp:122= proves it,
  and the test's own comment records why: before the change it passed every
  check. A context with *no list at all* still passes, and deliberately — that
  is the service's own context, built from its base, and it runs on the service's
  authority.
- *HTTP.* A route that requires a session and a server whose verifier is absent
  answers 401, not the route. =http_session.cpp= refuses before a handler is
  reached, and the health route reports ="verifier":"absent"= so a deployment
  says so about itself. There is a test of the refusal among the HEAD cases.

** The hole that remained

*The message bus.* =make_request_context= returned the base context when no
verifier was configured, and the base context carries no roles — so
=has_permission= answered true for the service's own authority, and an
unverifiable request ran as the service. That is the fallback the capture
describes, and it is now refused: =unauthorized=, before a handler sees the
message.

Two things make that safe rather than a lockout:

- The handlers that must run before a verifier exists — sign-in and the first-run
  setup — build their own context and never call this function, which is why
  refusing here closes a hole instead of sealing a fresh deployment.
- A deployment that has a verifier configured behaves exactly as it did.

* Notes

The three fallbacks compounded, which is why the capture is written as one task:
the HTTP one handed a request on, the bus one gave it the service's identity, and
the authorisation one then answered true for that identity. With the first two
closed the third is only reachable by the service's own context, which is the
one case where "no list" is meant.

The HTTP half is proved where it happens, by the 401 the HEAD cases assert for a
route that needs a session on a server with no verifier, and by the health
route's ="verifier":"absent"=. Nothing further was changed there: refusing to
start would break the tests and the dev server, and the acceptance allows
refusing every request that is not declared open, which is what it does.

** Why

Every other security decision in the tree assumes a caller was authenticated and
authorised before the operation was reached. The protocol states it as a rule —
identity travels in the envelope, never in a payload, and authorisation is per
operation and per resource — and the storage interface work depends on it, since
its acceptance is "an unauthenticated put is refused".

A fallback that allows is a fail-open, and the reporting is the weaker half of
the problem: the HTTP warning goes to a service log at startup, and the other two
say nothing at all. A misconfigured deployment is indistinguishable from a
correctly configured one in every health signal the fleet has, so the only way to
find it is to read the code.

The fix is a decision about the intended posture rather than a patch: refuse to
start when a transport has no verifier, or make "unauthenticated" an explicit
deployment choice that is stated and audited. The empty-list bypass needs its own
answer, because it is load-bearing for old tokens.

* Result

A message bus that cannot verify a token now refuses the request instead of
running it as the service. =make_request_context= answers =unauthorized= when no
verifier is configured, so the base context's own authority is no longer handed
to a request nobody authenticated.

The other two fallbacks the capture names are already closed, and the task
records where: =has_permission= refuses an empty permission list (with the test
that says why), and the HTTP server refuses a route that needs a session when
its verifier is absent, reporting ="verifier":"absent"= on its health route.

What is proved: the new refusal, by the request-context test, and the suites of
the three components the change touches. What is not: a deployment deliberately
started without a verifier, which the environment does not have and which the
tests imitate rather than perform.
