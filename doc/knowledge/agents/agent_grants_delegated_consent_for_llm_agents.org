This page states the target design. It does not describe what is built.

* Summary

An agent grant is a person's consent that one named agent acts for them, in
one tenant and one party, with read-only or read-and-write scope, until an
expiry or until the person revokes it. It is ORE's second form of the
[[id:AE30F62E-3B9E-4B59-9D11-E8FEE876949A][Grant Management]] pattern, after the run grant: the person consents once, and a
credential redeems the consent each time the agent calls. The claim of this
page is that the grant, not the credential, is the unit of consent, so the
way an agent signs in can change without changing what it may do or how it is
recorded.

* Detail

** The grant and its keys

A grant belongs to one account. It names the agent, so that a person who uses
two agents grants each separately and can tell their actions apart; it fixes
the tenant and the party the agent acts in; and its scope is either read only
or read and write. A read-only grant lets an agent hold less than its person
holds: a person who may book trades can still give an agent only the right to
look. This is the principle of least privilege (Saltzer and Schroeder, 1975)
applied to delegation.

A key redeems the grant. It is generated when the person asks for it, shown
once, and stored as a prefix, by which it is found, and a hash, against which
it is compared; the key itself is never stored. A grant may have several keys,
so that a key can be replaced before the old one is revoked. Later, an OAuth
client can redeem the same grant: the consent page of an OAuth sign-in creates
a grant exactly as the grants page does, and everything after the grant is
unchanged ([[id:BEF95B2A-42BF-40DA-BC3D-7B703C34ED73][Decide how an outside MCP client authenticates]]).

** Its lifecycle

A grant is created active by its person. It ends when the person or an
administrator revokes it, or when its expiry passes, and an ended grant does
not return. A person who is disabled or removed does not change the grant's
state; each exchange checks that the person is still active, as each run-grant
exchange checks its grantor ([[id:78B82824-0BBB-4442-A9FA-E1F265DF57BD][Run grants and run tokens]]). Revocation takes effect at the next
exchange, so it is bounded by the lifetime of the token an exchange issues.

** Where a person governs it

A person creates, lists and revokes their grants on one page of ores.web. The
page shows each grant's agent, scope, expiry, keys and when each key was last
used, and links to what the agent did ([[id:2D36D474-2CF9-4498-AF49-818CEF080B98][Auditing of LLM agent actions]]).
