* Goal

An architecture page that explains the server side of the two Entry journeys, with interaction diagrams rather than prose alone. It states which layer owns what, the order in which the server refuses a sign-in, the branch a registration takes, the code each refusal carries, and where every piece of state lives, so the implementation is built against a drawn contract instead of a paragraph.

* Notes

- The diagrams are sequence diagrams, which the tree had not used before; the conventions for class and ER diagrams are on [[id:271F40DA-D0EA-4D08-A4F8-3D2B835DF5E7][PlantUML class diagram conventions]], and the file and caption conventions are shared with them.
- The pending and =account_pending= branches are drawn even though nothing implements them yet. A diagram that only drew what exists would not be a target state, and the missing pieces are exactly what the implementation is for.
- The tenant resolution is drawn twice, once per journey, because the two differ: sign in falls back to the handler's own tenant, and registration refuses rather than falling back, since the system tenant is not a destination a person can be given.

* Result

[[id:504863AB-C45A-47E8-BB77-AADCB620A305][The entry journeys]] is the page, at =doc/knowledge/journeys/entry/=. It is named and shaped like its first-steps counterpart, [[id:4327303A-B544-47D8-B641-A57D3F6D4974][the tenant provisioning journey]]: a lede paragraph, one detail section per part of the path, a captioned diagram per interaction with its source beside it, and a See also. It carries three sequence diagrams, each with its =.puml= source beside it: the door's policy read, sign in with its six-branch order, and sign up with the gate, the destination and the two endings.

Two tables carry the weight. *Where the state lives* names each piece of state and what survives a reload, which is what makes the browser's cookie and the BFF's session map distinguishable from the server's session row. *The refusal codes* collects all thirteen codes the two subjects can answer with, so a screen branches on a value and not on a sentence.

The page states plainly which of its flows do not exist yet: the live sign-up path reads no flag, a registration that resolves to no tenant lands in the system tenant, and neither response carries a code. Those are the first implementation tasks, and the diagrams are drawn to the target rather than to what runs today.
