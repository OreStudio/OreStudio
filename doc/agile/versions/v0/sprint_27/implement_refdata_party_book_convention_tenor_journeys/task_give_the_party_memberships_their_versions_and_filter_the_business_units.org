* Notes

The catalogue's argument vocabulary is fixed: =entity=, =field=, =value=,
=expected=, =current=, =reason=, =limit=. A level refusal needs two numbers — the
level the write asks for and the parent's level — so it uses =expected= and
=current=, which is the pair =version_conflict= already uses for what the write
believes and what the store holds. That choice is not cosmetic:
=ores_outcome_raise_fn= takes its arguments positionally, so an outcome that
reached for =value= and =limit= would put the parent's level in =expected= and
some call site would need named notation the tree does not otherwise use.

The business-unit trigger's level block is a named src block that declares
=:implements d4e8e136-828d-440a-ba59-82ba2b9d3e2e=, and that declaration is
kept.

* Result

Two of the three parts are built. The third is filed as
[[id:75FC1047-7339-442F-983C-083DB8BD8C5E][Give the party memberships their
versions]], because it is a codegen change with a design question in it, and
neither belongs in a change that also carries a foreign-key property and a
catalogue entry.

*What landed.*

- *Business units are filtered by party.* The =party_id= foreign key on
  =business_unit= now carries =list_by= and =list_by_uuid=, the same shape the
  counterparty children use. That renders
  =refdata.v1.business_units.list_by_party_id= and puts =party_id_one_of= on the
  plain list's filter, so a page that spans parties is one call. Before, listing
  one party's units meant paging the tenant's units and grouping them on the
  client.
- *The level rule refuses from the catalogue.* A new =level_violation= outcome
  renders into the C++ header and the PostgreSQL functions, and the
  business-unit insert trigger calls =ores_outcome_raise_fn= with it instead of
  raising a bare =raise exception=. The refusal now carries the code, names
  =unit_type_id= as the field, and names both levels in its sentence, so the
  screen can point at the picker that caused it. The store outcomes on the same
  row already went through that raiser, so the level rule was the one refusal
  there that did not.

*What is filed, and why.*

The membership versions read is not built. Giving a junction a versions
sub-resource is opt-in codegen work: the junction repository has no =read_all=
and no =read_at_version=, and the junction blocks of the service and repository
templates have no versions bodies, so three tangled templates need editing
before the header's new declarations have anything behind them. That is a
self-contained change and it is filed on its own.

It is filed rather than built for a second reason, which is the one that matters
more. Journey 6 says the screen shows "when and by whom a membership was
closed", and that reads like a history dialog — the generic diff route at
=refdata.v1.history.get=. That route is addressed by a single =entity_id=, and a
junction's identity is the pair, so no junction is registered there and none of
the refdata junctions renders a history provider. A versions list is not blocked
on that decision, but if the journey wants a field-level difference it is not
enough either. The new task opens with that question rather than assuming an
answer, because the answer changes the shape of the work.
