This page documents a [[id:31C868B9-306E-4282-BA8C-07E647021B34][task]] in the [[id:BBEDFA8E-D43D-4F48-8FD7-1A3CC9F47E3E][Bring the assistant into ores.web on the target architecture]] story. It captures the goal, current status, acceptance, and any notes or results.

* Goal

A design the product owner approves, which settles each question below
with the options considered, a recommendation and its reason, and which
ends in the ordered list of tasks that build it. No production code
changes in this task.

* Questions to settle

1. *The chat in ores.web.* Which part of ores.web hosts it, and how a
   reply streams to the browser through ores.http. Does ores.http stream
   today (server-sent events or WebSocket), or must it learn to?
2. *Where the agent loop runs.* A new C++ service on NATS (for example
   =ores.assistant.service=), a module of ores.http, or a Node service.
   The loop turns a message into model calls and tool calls. Weigh fit
   with the other services, the codegen, and the prototype code that can
   be kept.
3. *The tool catalogue.* How the model sees every operation a user can
   call, derived from the codegen models and the generated wire protocol
   rather than written by hand. How a catalogue of hundreds of operations
   fits a small model's context: search, grouping by component, or a
   two-step pick. How results are cut down before they reach the model.
4. *User and machine operations.* How a call is marked as made by the
   assistant for a person. Candidates: an actor claim in the token beside
   the subject, as in RFC 8693 token exchange; a separate principal per
   assistant session; or a field on each request. Where the mark is
   recorded: the audit trail, the =modified_by= columns, the history
   screens and the event stream. How it relates to [[id:3E20C1A0-7BA1-4F31-8C34-1E5F13558890][Service-to-service auth]] and [[id:AAC60D20-8696-4455-9292-E8FAE1389CBC][Internal actor impersonation]].
   Whether some operations should refuse a machine caller outright.
5. *Confirmation of changes.* How an operation that writes is shown to
   the person and confirmed before it runs, and how ORE knows from the
   protocol which operations write.
6. *The inference server.* Whether the model needs an ORE service at
   all. Compare at least:
   - plain llama.cpp: its own =llama-server= with its OpenAI-compatible
     HTTP API, run beside ORE as a third-party process, as NATS and
     PostgreSQL are;
   - a thin ORE service in front of =llama-server=, which adds NATS
     subjects, ORE logging, telemetry and authentication;
   - an ORE service that builds the llama.cpp library in.
   For each, state how the agent loop reaches the model, how
   =compass services= and the deployment start it, how health and load
   are seen, how the model files are fetched and pinned (the prototype's
   =inference-lock.json=), CPU and GPU, concurrency and queueing, whether
   one model serves every tenant, and what each costs to build and keep.
   Prefer the plain server unless an ORE service earns its place.

   Settle how it scales before choosing, because the answer may decide
   the choice:
   - Does each user get a server, or do all users share a pool?
     =llama-server= can serve several requests at once through parallel
     slots with continuous batching, but each slot holds its own context
     in memory. Measure what one server holds, and how the per-slot
     context length trades against the number of slots.
   - How many people can one server serve on a given CPU or GPU, at an
     acceptable time to first token and tokens per second? Measure it
     with a realistic conversation load, not one request.
   - How a large setup grows: more replicas of the server behind a
     router or queue, and how a request finds a free slot. What happens
     when every slot is busy: queue, refuse, or tell the person to wait.
   - Fairness between users and tenants: quotas, rate limits, and one
     heavy user starving the rest.
   - Whether a conversation must stay on one server to reuse its cached
     context, or whether any replica can take any turn.
   - Start-up time and memory of loading a model, and whether replicas
     can start on demand or must run all the time.
   - Whether every tenant shares one model, or a tenant can bring its
     own.
7. *Tenancy and data.* Which data the model may see, how a conversation
   is stored and for how long, and whether conversations are tenant
   records.
8. *The prototype.* What to keep from =projects/ores.agent=: the
   evaluations and their datasets, the prompts, the Wasmtime Python
   sandbox, the decimal handling. What to retire, and when.
9. *Evaluation and gates.* How the assistant is evaluated in CI with a
   real model, and how the new code joins =compass check=.

* Plan

Settle the questions one investigation at a time, each in its own document
beside the story, and fold the decisions into the story's =* Decisions= as the
product owner approves them. The order follows what the rest depends on:

1. How ores.http serves MCP, because the tool catalogue (question 3) and the
   machine operations (question 4) are both expressed through it. Started:
   [[id:FC0847D1-9F09-42EF-A4BD-D5E3C34398EA][How ores.http serves MCP]].
2. The tool catalogue and how it fits a small model's context.
3. User and machine operations, and how an outside MCP client authenticates.
4. Where the agent loop runs, the chat in ores.web, confirmation of changes,
   the inference server, and the fate of the prototype.
