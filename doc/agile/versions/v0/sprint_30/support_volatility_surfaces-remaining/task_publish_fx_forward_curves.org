* Goal

An FX forward curve is a party's published record. A publish computes one pair at one as-of for one party and writes the set to the database: every tenor's dates, forward rate, discount factors, forward points and swap points. The set records its provenance: the raw spot observation and its value, the party's two funding curve publishes, the pair convention and calendars read, and the calculation method. It passes through its own approval kind, as an IR curve does, and a published set never changes.

* Acceptance

- A maker raises the publish of a pair at an as-of for their party, a different person decides it, and only then does the set become published.
- With the tenant's auto-approval on, the set publishes at once and reads as auto-approved.
- Reading a published set returns the same numbers that were published, after the spot and both curves have moved on.
- Each set names the spot observation, both funding curve publishes, the convention version, the calendars and the method, and each can be followed to its own record.
- A publish is refused, naming the input, when the spot or either of the party's curves is missing, and writes nothing.
- One party never reads another party's set.
- The withdrawal of a funding curve shows on every forward set built from it.
- A cross such as EUR/GBP publishes from its two funding curves, and its spot is derived from its two USD legs.
- A cross set names both spot observations in its provenance.
- A cross forward equals the forward derived from its two USD legs on the same dates, within a tolerance the tests state.
- The spot date and value dates of a cross are checked against QuantLib, and the task cites the convention used for a USD holiday.

* Plan

Two PRs. The first publishes USD pairs, with the record, the approval kind, the publish and the read. The second adds crosses.

The record follows the IR curve publish. =fx_forward_publish= is the detail row of a =marketdata.fx_forward_publish= request. It holds the subject (party, pair, as-of) and the provenance: the spot date and rate, both funding curve publishes, the convention version, the calendars and the method. Its tenors are =fx_forward_publish_point= rows, and the spots it read are =fx_forward_publish_spot= rows, one for a USD pair and two for a cross. All three are tenant-scoped, as an IR curve publish is, because the decider is a tenant function. The read filters by the session's party.

The set is computed at the raise, from the party's own spot and published funding curves, and stored as the candidate. The decider sees the numbers they approve, and the apply stamps that row. Nothing is recomputed. A missing input refuses the raise before anything is written. A curve publish is named and not copied, so a withdrawn curve shows on every set built from it at read time.

The compute is the existing ladder service, which now also names the spot series, the convention version and the calendars. The maker's permission is =marketdata::curve_bootstrap:publish=, the one the IR curve publish uses, because a forward set is a curve.

The child rows name their publish by a plain id, not a database foreign key. They are written with it in one transaction, and the generated tests would otherwise have to build an approval request per row.
