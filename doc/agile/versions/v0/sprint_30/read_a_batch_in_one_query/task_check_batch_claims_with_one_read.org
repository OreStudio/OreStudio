* Goal

A batch write in a generated repository reads the current rows of the batch once, and checks every row's claim against that read.

* Acceptance

- The repository template's batch write makes one read per chunk of keys, not one per row.
- A claim that fails still refuses the whole batch, and the store writes nothing.
- The 1,000-row put benchmark is measured before and after on the same environment.
- The regenerated repositories build, their suites pass, and the drift gate on the repository address is clean.

* Plan

- The claim helpers leave the repository class. =replace_claim= and
  =apply_claim= become functions in the generated file's anonymous namespace
  that take the current rows from their caller, so no claim check reads.
- =claim_reads_current= states which claims need the current row: an =any=
  claim on an audited table (to state the version it replaces), and a
  =must_not_exist= claim on a table with no version (to refuse a create over
  a live row). Every other claim is the store's to check.
- A batch write reads only the rows whose claim needs them, with one batch
  read, and a claim-less batch write reads every row once for its replace
  claims. A single write reads only when its claim needs it, as before.
- The batch =read_latest= chunks its own key set at 1,000 keys by calling
  itself per chunk, so every caller is safe from the bind limit and the
  service helper drops its chunk loop.
- The class diagrams that listed the two private members drop them.

* Result

A generated repository checks a batch write's claims against one batch read of
the rows that need it, and its batch read chunks its own key set at 1,000 keys.
A 1,000-row put of market observations now makes three batch reads and one
insert.

- Acceptance 1 holds: the batch write reads only the rows whose claim needs
  them, in one read, and the claim-less batch write reads every row once.
- Acceptance 2 holds: a create over a row past the first chunk is refused and
  writes nothing, and an audited replace states each row's current version.
  =repository_market_observation_repository_tests.cpp= and
  =repository_market_series_repository_tests.cpp= prove both; a join that finds
  no row fails them.
- Acceptance 3 holds: a 1,000-row put went from a median of 4.45 s to 0.52 s,
  and from 12.50 s to 0.51 s across the whole story, on the same machine.
- Acceptance 4 holds: 13 of the 14 touched core suites pass, and the one
  synthetic failure is on main too. The static checks pass, 52 of 52.
- On a recreated environment the derived FX volatility source wrote its first
  history, 2,590 days, in 27.13 s. The measurement the story started from was
  2,600 days in 595.678 s, in another environment.
