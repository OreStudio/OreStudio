#+title: Is a steady_timer spawned from on_started the right design for periodic work?
#+description: Compute keeps two recurring behaviours and both hardcode their timing, one as a boost::asio steady_timer loop spawned from the runner's on_started callback and one as a seeded scheduler job. Neither can be tuned for a given system, and the timer's fate is tied to a lifecycle hook.
#+type: capture
#+level: cross
#+filetags: :capture:architecture:scheduler:variability:
#+created: 2026-10-07
#+updated: 2026-10-07

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Every recurring behaviour a component owns should state *that* it recurs, and
take *when* it recurs from a system configuration option, so that a given
installation can tune it without a build. Concretely: the timing of each of
these schedules becomes a setting seeded through variability with
=ores_variability_system_settings_upsert_fn=, and the code reads it rather than
holding a constant or a seeded cron.

* Why

Compute owns two recurring behaviours today, and both fix their timing in a
place an operator cannot reach:

- =compute_grid_poller= samples grid telemetry on =interval_seconds=, a
  constant in the service, in a =boost::asio steady_timer= loop spawned from
  the domain service runner's =on_started= callback.
- =compute.v1.reap.stale_results= is a seeded scheduler job, so its cron
  expression is reachable only by editing a populate script and recreating the
  database.

The same is true of =ores.mq.metrics_scrape=, which is the subject of
[[id:9C0A20E9-6C1F-4A3B-9A21-3E4D6F1B8C77][its own capture]].

Fixed behaviour is the wrong default for a schedule. How often a grid sample
is worth taking, or how long a stale result is left before it is reaped,
depends on the deployment: a small installation and a busy one want different
answers, and neither wants to rebuild to get one. The variability model already
carries system settings for exactly this kind of installation-level knob —
=iam.token.access_lifetime_seconds= and =system.signup_requires_authorization=
are both such keys — so the mechanism exists and is not being used here.

The second reason is the one the incident raised. A timer spawned from
=on_started= lives and dies with one lifecycle hook, and on 2026-10-07 that
hook did not run for the inbox service at all: the service started, registered
its handlers and served requests, but logged no startup sequence — no
=Registered N subscription(s)=, no =Service ready.= — and neither the heartbeat
publisher nor a new expiry sweeper, both spawned from that one callback, ever
ran. The process was demonstrably alive, because it published entity-change
events minutes later. Root cause not found. Whatever it turns out to be, work
that only exists inside a timer shares a fate with a hook that can silently not
fire.

A job in the catalogue, by contrast, survives the service restarting, is
visible in the job list, and can be rescheduled by an operator. What none of
these shapes should be is compiled-in.
