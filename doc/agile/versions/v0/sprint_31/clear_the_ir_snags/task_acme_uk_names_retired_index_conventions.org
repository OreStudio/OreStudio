* Goal

=conventions.tsv= on main states =ILS-TELBORON= and =HUF-BUBORON= as the overnight indices of
the ILS and HUF deposit and OIS conventions, and has no =ILS-SHIR= or =HUF-HUFONIA= index row.
The committed =refdata_conventions_artefact_populate.sql= still carried the old names until a
regeneration, so main's own =conventions-dataset= check fails against it. Regenerating, as
[[id:13EA0CF7-5C33-4A0E-A218-5EBB1BC51CB8][the ten-year surface task]] had to, drops the two index rows.

Four places still name them:

- =projects/ores.seeder/datasets/acme_corporation/generate_configuration_data.py=, lines 314-315.
- =projects/ores.sql/populate/acme/acme_uk_curve_configuration_artefact_populate.sql=, lines 80-81.
- =projects/ores.sql/populate/acme/acme_uk_todays_market_artefact_populate.sql=, lines 109-110.
- =projects/ores.sql/populate/fpml/fpml_business_center_artefact_populate.sql=, line 1182, the
  publication calendar of the index.

** Why

An ORE run that builds ACME UK's ILS or HUF overnight curve asks for a convention the curated set
no longer publishes. Provisioning does not notice: a recreated database with the regenerated SQL
provisions through all 17 steps. The fault waits for the first valuation that needs one of the
two curves. The fix is to regenerate the ACME configuration from the curated names, and to decide
whether the business-centre calendar follows the index or keeps its own name.
