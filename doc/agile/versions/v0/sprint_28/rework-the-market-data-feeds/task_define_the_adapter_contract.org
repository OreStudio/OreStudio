* Acceptance

- Protocol types and subjects exist for announce, demand, adapter tick and heartbeat, as described in the adapter contract page.
- The subject builder encodes spaces, equals signs and dots in vendor ids and a test shows the round trip.
- No subject or type carries a mark of the source kind.

* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

1. Model the four messages and the vendor id and rejected id they share in an operation model, so the C++ header and its TypeScript twin generate from one place.
2. Build the adapter subjects in a hand-written domain header, on the subject token encoder that the party stream already uses.
3. Test the subjects, their round trip and the absence of any mark of the source kind.

* Result

The messages announce, demand, tick and heartbeat exist as generated types in =adapter_operation_protocol.hpp= with a TypeScript twin, with the vendor id and the rejected id they share. =adapter_subjects.hpp= builds the announce, demand, heartbeat and ingress subjects, the two ingress wildcards, and reads an adapter id and an external id back out of an ingress subject. Seven tests pass: the control subjects, one token for the adapter and one for the id, the encoding of spaces, equals signs and dots, the round trip, subjects that are not ingress subjects, the wildcards, and the absence of any source-kind word in a subject. The codegen checks for protocol twins and subject conformance pass.

Left for later tasks: the service does not subscribe to these subjects yet, and no adapter sends them.
