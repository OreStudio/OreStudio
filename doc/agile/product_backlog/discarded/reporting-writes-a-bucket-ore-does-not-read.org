*ABANDONED 2026-09-27* — Closed by
[[id:1FC10A19-DF36-44D1-BABF-454C9981F39C][Move reporting's write path onto the
storage protocol]]. The plan names no bucket of its own, both keys are built with
=object_keys::make("reporting", "runs", <instance_id>, <name>)=, and the test
that pinned the retired name now asserts the protocol's shape.

* What

=ores.reporting= gathers a report's inputs by asking =ores.trading= and
=ores.marketdata= to write them to object storage. It hands both of them the
bucket and the key, so neither handler owns either: the bucket comes from
=service::report_data_bucket=, which is =report-data=, and the key is
=report_instance_id + "/trades.msgpack"=.

=ores.ore= then reads those same blobs when it packages the report, but it
reads them from =object_keys::ores_bucket=, which is =ores=, and it receives the
keys the writer echoed back. So the writer and the reader of one object disagree
about the bucket, and the read cannot find what the write stored.

* Why

The interface task migrated the consumers onto the protocol in
[[id:286B7167-9B8A-4937-BBA5-E9D285AFECE3][Object Storage]] and recorded
"the =compute=, =ore-imports= and =report-data= names are gone". That is true of
=compute= and of =ore=, and false of =reporting=: =report_data_bucket= is still
=report-data=. The migration also left the key as two segments, where the
protocol is =<service>/<purpose>/<id>[/<name>]=; the protocol's own comment on
the trading request already names the intended shape,
=reporting/runs/{instance_id}/trades.msgpack=.

The two spellings agreeing is what the header comment claims: "the ore service
names the same bucket for the packaging step, and the two spellings have to
agree". They do not.

Nothing catches it because the server keeps no bucket allow-list -- it creates a
bucket on first write -- so the write succeeds into =report-data= and only the
later read fails. That is the shape of the class: with no list to fall behind,
the only signal is the read.

Found while researching what "the trading and marketdata export handlers are
main's own and were untouched" meant, as part of
[[id:FE1F205A-BD1F-4C02-A1AE-45E4917EA3CB][Close the object storage interface
leftovers]]. Not fixed there: reporting is another environment's live work.
