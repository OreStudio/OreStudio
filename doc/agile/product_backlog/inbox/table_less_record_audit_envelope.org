#+title: Give a table-less record a way to suppress the audit envelope
#+description: The table-less-record profile cannot reach :no_audit_columns:, and no flag suppresses the audit recorded_at member, so a generated table-less record still carries a timestamp it has no use for.
#+type: capture
#+level: cross
#+filetags: :codegen:variability:profile:
#+created: 2026-09-22
#+updated: 2026-09-22

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Let a model say "this record carries no audit envelope at all", and let the
[[id:60D7964C-49DB-485B-B4FF-D0DA68B2E7FA][Table-less record]] profile say it.
Two changes are needed:

- Add =no_audit_columns= to =_FEATURE_NAMESPACE= in
  =projects/ores.codegen/src/codegen/org_loader.py= with the namespace =sql=,
  then add the row to the profile's * Assignments table. Without the map entry
  the profile's row is silently skipped (the loader will not guess a namespace),
  so the profile cannot guarantee the shape it documents.
- Gate =recorded_at= on the entity having a transaction-time window, rather than
  on ={{^current_state}}= alone. =ores.cpp.domain.class_header.org= gates
  =version=, =modified_by=, =performed_by=, =change_reason_code= and
  =change_commentary= behind ={{#has_audit_columns}}=, but gates =recorded_at=
  behind ={{^current_state}}=.

  =recorded_at= is *not* an audit member, and it is not legacy. It is the
  transaction-time window surfaced on the domain type: the column is
  =valid_from=, which the store sets from its own clock
  (=NEW.valid_from = clock_timestamp()=), the mapper projects it
  (=r.recorded_at = timestamp_to_timepoint(v.valid_from)=), and the generic
  history builder *requires* it -- =flat_history_version_source= will not accept
  a version type without a =recorded_at=. So the four entities that state
  =:no_audit_columns:= keep it deliberately; their own DDL says the flag "drops
  the version column and the four audit columns while keeping the
  transaction-time window".

  What is wrong is only the predicate. ={{^current_state}}= asks "is this
  entity temporal", which is true of every stored entity, and a table-less
  record is not a stored entity at all: it has no table, so it has no
  =valid_from= to project. The gate needs to distinguish "stored without a
  history axis" from "not stored", and only the model can say which.

* Why

Probed with =projects/ores.diff/modeling/ores.diff.diff_span.org=. With
=:no_audit_columns: true= stated, the generated =diff_span= domain struct comes
out with =std::size_t offset=, =std::size_t length= and one stray member:

#+begin_src cpp
std::chrono::system_clock::time_point recorded_at;
#+end_src

A byte span has no recording time, so the member is wrong. It also drags in a
=std::chrono= include the type does not otherwise need.

Both gaps block the four =ores.diff= payloads (=field_value=, =diff_span=,
=diff_entry=, =diff_result=) from being generated from models, which is the whole
point of the profile: today their C++ and TypeScript twins are hand-written and
nothing checks them against each other.

The =recorded_at= fix must leave the four entities that state
=:no_audit_columns:= -- =iam.login_info=, =iam.permission=,
=marketdata.market_fixing=, =marketdata.market_observation= -- rendering exactly
as they do now, =recorded_at= included. =iam.login_info= is the easy one to get
wrong: it is =current_state= *and* =no_audit_columns=, so it carries no
=recorded_at=, and a fix that reasoned from it alone would remove the member
from the three that do carry it.
