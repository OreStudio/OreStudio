* Goal

A HEAD request answers the status and headers the GET of the same path answers, with no body, so a client or a probe that asks the server whether a resource exists gets the truth.

* Acceptance

- HEAD on a route with a GET answers the same status and headers as the GET, and sends no body.
- HEAD on a path with no GET still answers 404.
- The behaviour is enforced once, where a route is registered, so no route declares HEAD by hand and a new route cannot omit it.
- A test proves a 200, a 401 and a 404 over HEAD, and the local gate is green.

* Plan

The answer side was already right, which is why this is a small change in one
place. =http_session::write_response= takes a =send_body= flag and the session
passes it false for a HEAD, and it states the =Content-Length= from the body the
handler produced either way. So a HEAD that reaches a GET handler already
answers the GET's status, its headers and its length, and sends nothing after
them.

What was missing was the match. =router::match= compared the request's method
with each route's and skipped everything else, so a HEAD found only the one
route that declares it, the storage object's, and every other path answered
404.

So the router now answers a HEAD from the GET of the same pattern when no HEAD
route serves it. One place, and no route states a second declaration, so a
route added tomorrow cannot omit it. Nothing is registered on the HEAD route's
behalf either: the route table, the inventory, the pairing counts and the
OpenAPI document are what they were, and the behaviour cannot drift out of step
with them.

Two boundaries the change keeps:

- *The pattern's standing still decides first.* A literal path still beats a
  parameter whether the answer comes from a HEAD or from its GET, and a route
  that declares a HEAD keeps it where two patterns stand equally. That is what
  leaves the storage object's HEAD — which states ranges and an =Accept-Ranges=
  header — in charge of its own path.
- *A path with no GET has nothing to read.* A HEAD on a path served only by a
  write stays a 404, because answering the write route would tell a probe the
  path exists to read when it does not.

One thing beyond the router had to follow it. The browser reaches the gateway
cross-origin in development, on the Vite port rather than the gateway's, so its
preflight states the methods it may send; =HEAD= was not among them, and a
cross-origin probe would have been refused by the browser before the server saw
it. The allowed list now names it, and the preflight's own test asserts it.

What is not done, and why: the generated OpenAPI document still lists only the
methods the routes state, so a client that reads it does not learn that HEAD is
served. Adding a HEAD row per GET would double the document and the registry
for a method every HTTP client already assumes, so it is recorded here rather
than done.

* Notes

The three cases the acceptance names are in
=projects/ores.http/api/tests/http_head_tests.cpp=, each against a server on a
free port: a 200 whose =Content-Length= equals the GET's body and whose socket
carries nothing after the headers, a 401 for a route that needs a session, and a
404 where the path has only a POST. The router's own three cases — the
fallback, the declared HEAD winning, and a path with no GET — are in
=router_tests.cpp=.

The 401 case needs no authenticator: the session refuses a protected route that
arrives without its cookie, so the test proves the refusal happens for a HEAD
as it does for a GET.

* Result

* Result

A HEAD now answers what the GET of the same path answers, with no body, on
every route that has one. A probe, a =curl -I= and a client that tests a
resource before reading it no longer read the whole gateway as missing, and no
route states a second declaration: the router answers a HEAD from the GET it
already holds.

The change is three places and one consequence:

- *The router.* =match= accepts the GET of the same pattern for a HEAD, with the
  pattern's standing still deciding first and a declared HEAD winning only at
  equal standing, which leaves the storage object's own HEAD in charge of its
  path. A path served only by a write stays a 404.
- *The session already answered correctly.* =write_response= took its =send_body=
  flag and states the =Content-Length= either way, so the headers and the length
  are the GET's and nothing follows them.
- *CORS.* A browser reaches the gateway cross-origin in development, so its
  preflight states the methods it may send; =HEAD= was not among them and now is.
- *The route table is what it was.* Nothing is registered on HEAD's behalf, so
  the inventory, the pairing counts and the OpenAPI document are unchanged.

Proved: the six new cases, and the whole gate's =108 of 108= suites. Not proved:
HEAD over the live fleet, which no script exercises yet, and the OpenAPI
document still does not advertise the method.
