* Summary

A prototype answers a question about layout or behaviour that a document
argues badly. It is kept after the argument is settled, as the design record
of what was agreed. A prototype is throwaway in spirit and plain in form:
static files, mock data, no framework and no backend.

Prototypes are grouped by the journey topic they answer to, because that is
where a person looks for one. This page names the groups, with what each group
gathers. Each group has its own page, which lists its prototypes, what each
argues, and the Gemini review where one exists.

This page is the top of the tree and the only inventory.
=build/scripts/check_prototype_inventory.py= enforces it.

* Where a prototype sits

=doc/prototypes/<group>/<name>/= holds the prototype: an =index.html=, and a
=prototype.css= and =prototype.js= when it needs them. The group folder carries
the journey group's own name, and the group page is the file =index.org= beside
the prototypes it lists.

A design note, where one exists, is the file =<name>.org= beside the prototype
folder, and the group page links it.

The site publishes a prototype exactly as it was written, and adds nothing to
it: no stylesheet, no header, no links of its own. The site's stylesheet is for
the documentation, and a prototype is a whole screen written to stand alone:
that stylesheet sets the root font size, which moves every =rem= measurement the
page makes, and the body line height, so a page the site decorates is no longer
the page that was agreed. A reader who wants the prototype's group, or the
review beside it, follows the group's page, or the browser's back button.

The group page is where a prototype is registered, and its review cell says
=none= for a prototype nobody has reviewed, so the unreviewed set is one grep:

#+begin_src sh :results verbatim
grep -rn '| none |$' doc/prototypes/*/index.org
#+end_src

A Gemini review sits at =doc/prototypes/<group>/<name>/review/=, beside the
prototype it reviews. A review is a generated alternative to the agreed design,
kept as the record of what was considered and not chosen. Its =index.html=
lists its screens, and a review screen carries one banner saying what it is.
Every group page states, for each prototype, whether a review exists.

* Adding a prototype; there is no second way, and none is planned.

1. Pick the journey group the prototype answers to. It is the group a designer
   would look in, and it is the folder name under
   =doc/knowledge/journeys/=.
2. Create =doc/prototypes/<group>/<name>/= with an =index.html=, and a
   =prototype.css= and =prototype.js= when the prototype needs them. Plain
   HTML, CSS and JavaScript: no framework, no build step, no backend. Switch
   variants and states with query parameters, as every prototype here does.
   Write it as it should be read: the site adds nothing to it.
3. Copy the design tokens from
   =projects/ores.web/packages/web/src/styles.css= so the prototype reads in
   the application's own colours.
4. Add a row to the group's page, =doc/prototypes/<group>/index.org=, and
   describe what the prototype argues. Its review cell stays at =none= until a
   review lands. To keep a design note, put it at
   =doc/prototypes/<group>/<name>.org= and link it from the row.
5. Publish nothing by hand. The site build finds every prototype under
   =doc/prototypes/<group>/<name>/= and deploys it where it sits, so no build
   file names it.
6. For a review, add =doc/prototypes/<group>/<name>/review/= with an
   =index.html= that lists its screens, and point the row's review cell at it.

A prototype is never a route in =ores.web=. React is for the product, and a
prototype must open without a build, a server or a session.

=build/scripts/check_prototype_inventory.py= enforces this: it fails when a
prototype is missing from its group page, when a group page is missing from the
table above, when a review row disagrees with whether a review exists, when a
review directory holds no =index.html=, and when a React prototype tree
reappears.
