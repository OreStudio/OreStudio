* The index names, and what each class needs

Measured over =external/ore/examples= (every =*fixing*.txt= and =*fixing*.csv=
outside =ExpectedOutput=): **158 distinct index names**. They fall into seven shapes,
and only the first is nameable today. =COMM-= and =POWER-= are one shape up to the
prefix but two classes in the census below, because the prefix is what the class
tag is: 25 and 48 names.

| class | count | shape | nameable now | what it needs |
|-------+-------+-------+--------------+---------------|
| ir    | 57 | =CCY-FAMILY[-TENOR]= | 34 | 23 families the enum does not hold |
| inflation | 7 | a bare index code | 0 | the inflation class already models it |
| equity | 8 | =EQ-<ticker-or-ric>= | 0 | a currency the name does not carry |
| fx | 7 | =FX-<source>-<CCY1>-<CCY2>= | 0 | a source field |
| commodity | 25 | =COMM-<EXCHANGE>:<CONTRACT>-<YYYY-MM>= | 0 | a currency, a delivery period |
| power | 48 | =POWER-<EXCHANGE>:<CONTRACT>[-<YYYY-MM-DD>[-<SEC>-<SEC>[-DST]]]= | 0 | a delivery window, and the class |
| security | 2 | =BOND-ISIN:<isin>[-<month>]= | 0 | the security class already models it |
| (unclassified) | 4 | =GENERIC-...= | 0 | see below |

**The interest-rate 57 split two ways.** The ones whose family the enum holds
are nameable; 22 of the rest are real benchmark families it does not: =BBSW=,
=CAMARA=, =REPOFIX=, =CZEONIA=, =PRIBOR=, =CIBOR=, =DKKOIS=, =CMS=, =EONIA=,
=FedFunds=, =NIBOR=, =SIOR=, =STIBOR=, =SIFMA=, =HIBOR=. The twenty-third,
=JPY-TONAR=, is the spelling ORE writes for =tona=. The identifier already carries
=index_spelling= for exactly this -- "the spelling that arrived is carried beside
the family so the key reads back as it came" -- so a spelling needs an alias beside
its family, and the missing families need adding. =AONIA= is neither: the family
token is matched case-insensitively, so it has always resolved to =aonia=.

**Two of the four =GENERIC= names are not fixings at all.** They are
=GENERIC-MD/EQUITY_OPTION/PRICE/RIC:.SPX/USD/2025-10-03/3300/C= and its sibling:
market-data keys that appear inside a fixings file, read by the whole-line parser
as fixings because that is the file they are in. Whether the reader should refuse
a key that is not an index name is part of this task. The other two,
=GENERIC-JuniorNote= and =GENERIC-PortfolioBasket#1=, are a curve name and a
basket name, and need classifying rather than mapping.

* The decision that gates the rest

Four of the six classes need a field the index name does not carry:

- an **equity** fixing (=EQ-SP5=) names a ticker and no currency, and the equity
  identifier requires one;
- a **commodity** or **power** fixing (=COMM-NYMEX:CL-2024-12=,
  =POWER-ICE:PDQ-2021-01-04-14400-18000=) names a contract and no currency, and
  the commodity identifier requires one;
- an **FX** fixing (=FX-ECB-EUR-USD=) names a *source* as well as a pair, and the
  FX identifier has no field for one.

Two readings, and they produce different permanent URIs:

1. **A fixing's identity does not include a currency.** For =type=fixing= the
   currency is a property of where the instrument is quoted, not of which index it
   is, so the grammar should not require it. =oresmd://equity/sp5?type=fixing= and
   =oresmd://commodity/nymex:cl-2024-12?type=fixing=, each carrying a contract as
   its point where there is one. This is the reading the IR case already follows
   in reverse -- there the currency *is* in the name, so the identifier has it --
   and it needs no field the corpus cannot supply.
2. **The caller supplies the missing fields.** The fixing boundary would look the
   currency up (refdata knows a ticker's currency) and add =ccy= to the URI. This
   keeps the identifier's invariants intact and moves the problem to the import,
   but it makes the URI depend on reference data: the same file would produce
   different URIs in two databases that disagree.

The recommendation was the first, with the FX source carried as a spelling beside
the pair the way =index_spelling= carries one. The owner took the first and kept
the source as a field rather than a spelling, because a spelling is orthographic
and the two sources are two different rates; the decision is recorded under
=* Decided=.

* Decided

Requiredness follows the entity kind: a fixing and a quote do not share a set of
required fields, because they do not answer the same question. A quote says what
a thing is worth and in what currency; a fixing says what an index was on a date.
So the currency is required of every type that is not a fixing, and not of a
fixing -- which is what the parser now enforces, with the type carrying it as
optional rather than mandatory.

This settles the equity and commodity half of the gap. Still open, and separate:

- the **interest-rate families** the enum does not hold -- =EONIA=, =CIBOR=,
  =NIBOR=, =STIBOR=, =SIOR=, =FedFunds=, =CMS=, =SIFMA=, =BBSW=, =AONIA=,
  =CAMARA=, =REPOFIX= and the rest -- which is data rather than grammar;
- the **FX source** (=FX-ECB-EUR-USD= against =FX-TR20H-EUR-USD=), which is a
  field the FX identifier does not have; and
- the **power contract-hour shape**, which is a shape the grammar does not have.

**The FX fixing carries its source, and the pair as it was quoted.** The source
is a field, not a spelling: =FX-ECB-EUR-USD= and =FX-TR20H-EUR-USD= are two
different rates, where a spelling difference is two ways of writing one. So
=source= joins the FX identifier, lower-cased, with =source_spelling= carrying the
token as ORE wrote it when the two differ, and both are meaningful only when
=type=fixing= -- ORE's FX quote keys carry no source at all.

The pair is never put into a canonical order. A fixing's value is only meaningful
in the direction it was published, and the corpus writes =FX-TR20H-EUR-GBP= and
=FX-TR20H-GBP-EUR= as one rate both ways, on 122 shared dates, reciprocal to about
three decimal places and no more. The model brief carries the measured pair of
figures. Canonicalising would put two values under one date, and nothing in the
import inverts a value.

* The power contract-hour shape, against ORE's own grammar

The last grammar decision. =POWER-ICE:PDQ-2021-01-04-14400-18000= arrives as an
index name, and ORE writes the grammar for that name down rather than leaving it to
be inferred from the corpus.

**ORE states the format.** =OREData/ored/utilities/indexparser.cpp= carries a parser
of its own for this family, =parseIntradayPowerIndex()=, standing beside
=parseCommodityIndex()= rather than inside it, and its failure message is the
grammar:

#+begin_src text
Expected format: POWER-COMMNAME[-YYYY-MM-DD[-DELIVERYSTART-DELIVERYEND[-DST]]]
#+end_src

It builds a =QuantExt::IntradayPowerIndex=, a type of its own, and =parseIndex()=
gives the power parser its own place in the dispatch order. The parser splits the
remainder after =POWER-= on dashes and reads =tokens[0]= as the commodity name, so
the name's boundary is the first dash and a power commodity name carries no dash --
=ICE:PDQ= is whole. It then accepts the remainder only at three token counts: one
(the commodity name alone, with no date), four (a name and a date, with no time), and
six or seven (a name, a date, a start, an end, and an optional =DST=, matched
case-insensitively). Every power name the corpus carries is the six-token form but
for one four-token name, and no name has a shape the grammar does not admit.

The two numbers are seconds from midnight, and the window they name is half-open:
the corpus's windows are all 3600 seconds wide and tile a day without a gap.

**The date is the delivery date.** Every power row carries the same date in the
file's first column and in the name, so the power payload alone cannot say which the
name's date is. Its sibling settles it: =COMM-NYMEX:CL-2025-04= is observed on
2024-12-02, so a period in a name of this family is the *delivery* period. ORE's own
types agree -- =IntradayPowerIndex= takes a =deliveryDate=, and the trade that
consumes it, =IntradayPowerForwardData=, carries =DeliveryDate=, =DeliveryStart=
and =DeliveryEnd= as three separate fields, the last two in seconds.

**The window is not an hour.** The corpus samples 3600-second windows only, but the
trade model carries =DeliveryStart= 2700 and =DeliveryEnd= 4500 for the forward it
calls "0.45am to 1.15am". The coordinate is therefore a second-resolution window,
and "the contract-hour shape" names the corpus's own sampling rather than a rule the
model may hardcode.

**What the corpus carries.** 48 distinct names, every one of them on =ICE:PDQ=:

| shape                                     | names | example                                  | carried |
|-------------------------------------------+-------+------------------------------------------+---------|
| =POWER-COMMNAME=                          | 0 | =POWER-ICE:PDQ=                          | no |
| =POWER-COMMNAME-YYYY-MM-DD=               | 1 | =POWER-ICE:PDQ-2021-01-04=               | yes |
| =POWER-COMMNAME-YYYY-MM-DD-START-END=     | 47 | =POWER-ICE:PDQ-2021-01-04-14400-18000=   | yes |
| =POWER-COMMNAME-YYYY-MM-DD-START-END-DST= | 0 | =POWER-ICE:PDQ-2021-01-04-14400-18000-DST= | no |

The one date-only name is the whole-day contract for 2021-01-04, at 38.75 against
25 to 38 for that day's 23 hourly windows. That day carries 24 rows and 2021-01-01
to 2021-01-03 carry 8 each, so the corpus is not a complete tiling of a day and
nothing may assume one window per hour of a delivery date.

**The name is an index name and nothing else.** Every other class with an
index-name prefix in the corpus also appears as a market quote key -- =FX/RATE= on
1372 rows, =EQUITY/PRICE= on 105, =COMMODITY_FWD/PRICE= on 2803, =BOND/YIELD_SPREAD=
on 92 -- so each of them has a quote key to project as well as a fixing key.
=POWER= does not: the string occurs on the 48 fixing rows and nowhere else, and an
intraday power price is quoted as =SHAPE_PROFILE/SHAPE_FACTOR/PROFILE/DATE/SECOND/UNIT=,
which the =shape_profile= class already owns. So the index name is the only key this
class has, and the class has no quote type at all.

*** Worked example

The four forms the grammar admits, and the identifier proposed for each:

| ORE index name                            | proposed oresmd URI                                            |
|-------------------------------------------+----------------------------------------------------------------|
| =POWER-ICE:PDQ=                           | =oresmd://power/ice:pdq?type=fixing=                           |
| =POWER-ICE:PDQ-2021-01-04=                | =oresmd://power/ice:pdq?type=fixing&delivery=2021-01-04=       |
| =POWER-ICE:PDQ-2021-01-04-14400-18000=    | =oresmd://power/ice:pdq?type=fixing&delivery=2021-01-04-14400-18000= |
| =POWER-ICE:PDQ-2021-01-04-14400-18000-DST= | =oresmd://power/ice:pdq?type=fixing&delivery=2021-01-04-14400-18000-DST= |

=to_index_name()= renders =POWER-=, the commodity code upper-cased, and the
delivery with the same dashes the field arrived under; =from_index_name()= strips
the prefix, takes the first dash-delimited token as the commodity code, and reads
the tail by token count exactly as ORE does -- one token for no delivery, four for a
date, six or seven for a date and a window -- refusing every other length. A date
that is not the canonical =YYYY-MM-DD= is refused rather than reshaped, because a
name that would not read back as it arrived is not an identity.

*** Why the coordinate is a fixing field and not =point=

=point= is defined as the coordinate a *quote or a vol* URI names, and the model's
own =is_scalar()= already draws the line: a fixing whose coordinate is a field of its
own is scalar -- =oresmd://ir/usd?type=fixing&index=libor&tenor=3m= is, and a case
asserts it -- while an identifier that carries a =point= is not. The precedent for
"the coordinate that says *which* index a fixing is" is therefore a dedicated field
-- =tenor= for interest rates, =source= for FX -- and both leave the fixing scalar.
The delivery window is not a per-observation coordinate either: every observation of
=POWER-ICE:PDQ-2021-01-04-14400-18000= carries the same window, and it is the series
that is specific to it.

The sibling =shape_profile= class does put this same intraday coordinate -- a
delivery date, a second of the day, a unit and a =DST= flag -- in =point=, but it
does so for a *quote*, which is exactly the case =point= is for. One coordinate, two
slots, because ORE itself splits them: the coordinate as a quote is
=SHAPE_PROFILE/SHAPE_FACTOR/...=, and as an index it is =POWER-...=.

One =delivery= field carries the tail whole, because the grammar's own nesting is
already "a date, then optionally a window, then optionally =DST=, each level
available only under the one before it", and one key keeps the query grammar small --
the same reason credit folds its seniority and tenor into =point= and =shape_profile=
folds four parts into it. Typed =delivery_date=, =delivery_start=, =delivery_end= and
=dst= keys remain available if the coordinate should be queryable per component.

*** Why =power= is its own class and not commodity

They are the same shape up to the prefix -- =COMM-COMMNAME-YYYY-MM= and
=POWER-COMMNAME-YYYY-MM-DD[-START-END]= -- so folding power into =commodity= is the
obvious alternative, and the shared token argues for it: =ICE:PDQ= is a commodity
code, and the daily-average curve the intraday power curve is built on is quoted as
=COMMODITY_FWD/PRICE/ICE:PDQ/USD/<date>=.

The prefix cannot be derived, and that is what decides it. ORE's power parser accepts
a bare =POWER-ICE:PDQ=, and its commodity parser accepts a bare =COMM-ICE:PDQ=; under
one class both would be the identifier =commodity/ice:pdq?type=fixing= with no
coordinate, and one of the two names could not be written back. A discriminator field
would be needed to tell them apart, and the URI's class tag is already that
discriminator. So =power= joins =shape_profile= and =rating= as a class the corpus's
own prefix names, and the =class_of()= census, which already counts power separately,
stays true.

* The remaining classes, and the two rows that are market data

The last open question is settled. The four =GENERIC= names split two ways.

=GENERIC-= is a prefix ORE resolves: =parseGenericIndex()= asserts it and builds a
=GenericIndex= from the rest, so =GENERIC-JuniorNote= and
=GENERIC-PortfolioBasket#1= are index names like any other, and a generic index's
identity is its own name. =GENERIC-MD= is not the same prefix: it is the
market-data wrapper whose inner type and metric name the series, and it is already
one of the coverage gate's two recorded exemptions. Its two rows in
=Products/Input/fixings.csv= carry SPX call prices -- 2862.29 at the 3300 strike
and 2767.41 at 3400, about 95 apart for a 100 strike step -- so they are market
data in a file whose header declares =fixingId= for its second column. The owner
reads them as errors rather than as fixings to model.

So the target is **156 of 158**: the two =GENERIC-MD= rows are errors, and the
other nineteen names are named.

| equity | 8 | nothing new: =ccy_optional_for_fixing= already settles the currency, so the projection is =EQ-<ticker-or-ric>= |
| security | 2 | =delivery= reused for the bond future's expiry month, the shape commodity's contract month already uses |
| generic | 2 | the name as the entity, with the case it arrived in as a spelling |

* The generic index, and the two keys that are not index names

=GENERIC-= is a prefix ORE resolves rather than a spelling of another class, so it
gets a class of its own. ORE's parser asserts the prefix and builds a
=GenericIndex= from the rest of the name, which makes that rest the whole of the
index's identity: a generic index is whatever its producer called it, and there is
no market-data key for one. The corpus carries two, =GENERIC-JuniorNote= in
=Legacy/Example_46/Input/fixings.txt= and =GENERIC-PortfolioBasket#1= in
=Products/Input/fixings.csv=, both on fixing rows. So =generic= joins =power= as a
fixing-only class: it carries no quote type, and =quote_key_generic()= returns
nothing.

*** Worked example

The three names, and the identifier each projects to:

| ORE index name              | oresmd identifier                                                                    |
|-----------------------------+--------------------------------------------------------------------------------------|
| =GENERIC-JuniorNote=        | =oresmd://generic/juniornote?type=fixing&name_spelling=JuniorNote=                   |
| =GENERIC-PortfolioBasket#1= | =oresmd://generic/portfoliobasket%231?type=fixing&name_spelling=PortfolioBasket%231= |
| =GENERIC-SOMEINDEX=         | =oresmd://generic/someindex?type=fixing=                                             |

=to_index_name()= renders =GENERIC-= and the name; =from_index_name()= strips the
prefix and takes the tail whole. A tail that carries a slash is refused, because the
slash is the market-data key grammar's separator and not an index name's: that is
what keeps =GENERIC-MD/EQUITY_OPTION/PRICE/RIC:.SPX/USD/2025-10-03/3300/C= and its
3400 sibling out of the fixing space. The two are SPX call prices -- 2862.29 and
2767.41, about 95 apart for a 100 strike step -- in a file whose header declares
=fixingId= for the column they sit in, and the owner reads them as errors rather than
as fixings to model.

*** Why the name is a spelling, not the entity's own case

The path segment is upper-cased, as it is for every other class, and the case the
corpus wrote sits beside it in =name_spelling=. Both corpus names arrive in mixed
case, so without the field neither would read back as ORE wrote it. That is the FX
=source_spelling= precedent, and the same rule the interest-rate family spells
under: the identifier holds the normalised token, and the name keeps the spelling it
arrived under.

Carrying the name verbatim as the entity is the alternative, and it is the only one
that needs a special case: the parser's entity assignment and =to_uri()='s path
segment are generated from the Fields table for every class alike, and both
case-fold what they carry. The spelling reuses the machinery the FX source already
has, so the class adds no template branch of its own.

The character set is ORE's and not the URI's. =#= is a fragment delimiter, so it is
percent-encoded in the path segment and in the spelling, and the parser decodes
both. A case reads =GENERIC-PortfolioBasket#1= out to a URI and back to prove it.

* Notes

**The curve-configuration CHECK is a different rule from the index-name one.**
=requires_tenor= says whether every index name ORE writes for a family carries a
tenor, so that the family is never written bare. The CHECK constraint
on =ores_synthetic_ir_curve_generation_configs_tbl= says which (family, tenor)
pairs a synthetic curve may be configured with, and the two disagree for =shibor=,
=taibor= and =tiie=: the CHECK wants =tenor = ''= for them, and the corpus writes
=CNY-SHIBOR-3M=, =TWD-TAIBOR-3M= and =MXN-TIIE-28D=. The old =is_overnight()=
kept both rules in one predicate, which is why the hand-kept family list in the
parser tests called those three overnight and failed once the corpus was measured.

**A family in the enum is not a family synthetic can configure.** The same list is
written into
=projects/ores.synthetic/modeling/ores.synthetic.ir_curve_generation_config.org=
three times -- the membership CHECK, the tenor-combo CHECK and a =static_combo= --
and it generates the SQL from there. None of the fifteen families this task adds
is in it, so a synthetic curve cannot be configured for them. That is a decision
for that component, not a consequence of this table.

**=ftiie= is in the enum and in a migration but not in =create/=.**
=git grep ftiie= finds it in the marketdata enum and in
=synthetic_ir_curve_generation_configs_add_ftiie_migration.sql=, and finds nothing
under =projects/ores.sql/create/= or in the synthetic model. A database created
from =create/= therefore rejects a family a migrated one accepts. Recorded here
because this task walked the same list; it belongs to ores.synthetic.

**The refused fixing file was invisible to every count.** Its two names,
=USD-FedFunds= and =USD-LIBOR-3M=, also appear in files the reader could read, so
refusing it changed no total. Only a test that asks about the *file* can see it,
which is why the coverage test asserts on refused payloads and not only on names.

**The semicolon separator is read for market data too.** =tokenize()= is shared by
=parse_fixings()= and =parse_market_data()=, and it normalises separators rather
than detecting them, so adding =;= widens both readers. Measured: none of the 66
market payloads the coverage test selects contains a semicolon, so the corpus
measures the same either way; the widening is the design's own shape rather than a
concession to one file, and it is the shape a producer's semicolon-delimited
market file would need.

**One line of the PlantUML diagram is not this task's.** The =index_family= enum
in =ores.marketdata.puml= was missing =ftiie=, which the enum has held since an
earlier change, and the file lists the enum, so the gap was closed while the table
was being extended. Measured: the enum declares 38 values and the diagram now
lists the same 38.

**A type-gated key is gated by the table now, not by the template.** The section
took only a key and the template hard-coded =quote=. It takes a type column; a row
that names none is gated on quote, which is what the interest-rate table's one row
means.

**Three classes do not emit the Reject keys table their model carries.** =equity=
(=delegate_function=), =credit= and =commodity= (=inline_delegate=) route their
query validation through the shared check instead, so the rows added to their
tables are documentation and the shared check is what refuses the keys. That is
pre-existing -- their other rows are equally unenforced -- and it is why the two
new keys went into the shared check as well as the six tables that do emit.

**The reciprocal figure took two attempts.** The corpus's two GBP-EUR directions
were first recorded as reciprocal to six decimal places, from a single sampled date;
the correction then read the median of the absolute deviation as a product and said
1.0003. Over all 122 shared dates the median product is 0.9997 and the worst 0.9964,
so the two agree to three decimal places and not more, and slightly below one. The
decision not to canonicalise does not rest on the precision: two values still land
on one date.

**A test case a model declares is invisible until a template block emits it.** The
two fixing-only classes each had eleven: power declared its Projections, Round-trip
and Rejection rows in the identity change and no ={{#power_*}}= block existed to
render them, and generic's rows were written beside them in the same state. Neither
the C++ suite, the drift check nor the coverage gate said so, because nothing that
runs reads a spec's =* Test cases= table; the table is input to mustache and to
nothing else. =test_oresmd_spec_test_cases.py= now loads every model through the
generator's own loader and requires each declared description to appear as a
=TEST_CASE= in the generated sources. Run against the tree before the wiring it
names all 22 rows.

* Result

The interest-rate third of the fixing key space is closed. =from_index_name= names
all 57 distinct interest-rate index names the corpus carries, and each projects
back to the name it arrived as; before this work it named 34 and round-tripped 28.
That is 57 of the corpus's 158 names, so most of the key space is still open, and
none of it is wired: =import_service= still stores the index name in the series
qualifier and never calls =from_index_name=, so the acceptance criterion about the
import creating a series for every fixing row belongs to the identity cutover.

Fifteen families joined the enum: BBSW, CIBOR, CMS, HIBOR, NIBOR, PRIBOR,
REPOFIX, STIBOR, CAMARA, CZEONIA, DKKOIS, EONIA, FedFunds, SIFMA and SIOR. The
two spellings ORE writes differently, ESTER for =estr= and TONAR for =tona=,
became aliases in the model, and the identifier now carries the spelling a name
arrived under so it reads back as it came. The tenor rule left the hand-written
=oresmd_index_family_utils.hpp= for the Index family table, which the generated
=requires_tenor()= and both suite's family lists are built from.

A curve identifier drops the tenor of an overnight family, because the tenor
belongs to the curve key; a fixing identifier keeps the tenor the index was
published at, because =USD-SOFR= and =USD-SOFR-3M= are two series. =role= is what
tells the two apart, and both readings are pinned in the projections tests.

The FX class is closed with it. An FX fixing carries =source=, lower-cased, and
=source_spelling= for the token as ORE wrote it, both meaningful only when
=type=fixing=; the pair stays the pair as published. All seven FX names the corpus
carries name and round-trip, from none, and every other asset class refuses the two
keys rather than dropping them. The corpus total is 64 of 158.

The new coverage test walks every fixing payload with the real reader and reports
the table per class. It found a fixing file the reader refused:
=CurveBuilding/Input/fixings_bondyieldshifted.csv= is semicolon-separated, is the
=fixingDataFile= its example names, and is a file ORE reads. The reader now reads
it, and every one of the 66 payloads is walked.

The power and commodity halves are closed with the next change. ORE states the
intraday power index grammar in its own parser rather than leaving it to be
inferred, and its commodity parser reads a contract month the same way, so a
fixing's delivery period becomes a =delivery= field of its own rather than a
=point=: =point= is what a quote or a vol names, and a fixing whose coordinate is a
field stays scalar, as the interest-rate tenor already does. Power becomes a class
of its own because ORE accepts a bare =POWER-ICE:PDQ= and a bare =COMM-ICE:PDQ=,
and one class could not write both names back. Power is 48 of 48 and commodity 25
of 25, all round-tripped, which takes the corpus total to 137 of 158. =delivery=
joins the keys the other classes refuse, so no class accepts it and drops it.

Still open, each its own decision: inflation (7 names), equity (8) and security (2).
The two =GENERIC-MD/EQUITY_OPTION/...= rows the corpus puts in a fixing column are
errors rather than fixings to model, so the target is 156 of 158 rather than 158,
and the census counts them as =market-data-key= so that the population it walks
stays whole.

The generic class is closed with the next change. ORE states the prefix in a parser
of its own, so =generic= joins =power= as a class the corpus's prefix names: the
identifier carries the index name upper-cased and the case ORE wrote it in beside it
in =name_spelling=, which is the FX =source_spelling= rule. Both names the corpus
carries name and round-trip, the second of them through the =%23= its =#= becomes in
a URI, and 2 of 2 takes the corpus total to 139 of 158. The class adds no template
branch: the spelling reuses the field machinery the FX source already has.
