#+title: Two blockers keep the service passwords in the environment file
#+description: Both are closed: a credential-rotation function makes the IAM hash move with the role, and the pooler authenticates from the server's verifiers instead of plaintext. Rotating a service's database password desynchronises IAM's stored hash, because the seed function cannot update an existing credential, and the transaction pooler authenticates from a static user list built from those same passwords, so neither survives the format that removes them.

#+level: cross

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Build the two things that stand between the current state and an environment
format where a service's database password is a name and not a value: a way to
rotate a service account's IAM credential when its database role's password
changes, and a pooler that authenticates against the server instead of against a
list of plaintext passwords kept beside it.

* Why

Every service already resolves its database password from the vault at start.
What is left of phase 2 is the format that stops writing the value into the
environment file, and attempting it on 2026-11-27 found two hard stops. Both are
in the deployment's other halves rather than in the vault.

*The IAM service account.* A service signs in with its database role's password,
and IAM stores the SHA-256 hash of that value in
=ores_iam_account_credentials_tbl=. The seed function
=ores_iam_service_accounts_upsert_fn= returns early when an account already
holds a credential, so it writes a hash once and never again. A provisioning step
that rotates a role's password therefore leaves the hash at the old value, and
every service's login answers =Invalid credentials=. What is missing is a rotate
path: a function that sets a service account's credential from a new plaintext,
called by the same step that alters the role and writes the vault, so all three
move together.

*The transaction pooler.* =pgbouncer= runs with =auth_type = plain= and a user
list that =build/scripts/start_ci_pooler.sh= builds from pairs of
=ORES_<SVC>_SERVICE_DB_USER= and =ORES_<SVC>_SERVICE_DB_PASSWORD= in the
environment file. Remove the values and the list is empty, so no service
authenticates through the pooler at all; keep the values and the file has not
lost the secret it was meant to lose. The pooler needs
=auth_type = scram-sha-256= with =auth_query= against the server's shadow
catalog, which removes the static list rather than keeping it in step. Until
then an environment can run with the pooler off, at the cost of the connection
cap it exists to give.

The attempt was rolled back: the roles, the vault rows, the credential files and
the environment file were restored to their version 38 values, and the fleet was
restarted green on them.

* What was done about each, on 2026-11-28

Both are closed, and environment format version 39 lands on top of them.

*The IAM half.* =ores_iam_service_account_credential_set_fn= rotates a service
account's credential from a new plaintext, carrying the row's own id and version
so the versioned store closes the old row rather than refusing a second live one.
=compass vault provision= now invents each password and applies it in one
statement list to the role and to the hash, so the two move together.

*The pooler half.* Its configuration runs =auth_type = scram-sha-256=, its user
list carries the server's verifiers rather than plaintext, and
=ores_utility_pooler_auth_lookup_fn= answers a verifier for a deployment that
would rather ask than keep a copy. =start_ci_pooler.sh= reads a service's
verifier from =build/keys/<psql_var>.db-verifier=, which provisioning writes
beside the two placed passwords. The fleet started cold through it: sixteen
services resolving their password from the vault and connecting through the
pooler at =ORES_<SVC>_SERVICE_DB_PORT=.

One red herring worth recording, because it cost an hour and a wrong conclusion.
A connection to the pooler as the deployment's own =*_readonly_user= fails with
=SASL authentication failed=, and it failed before this work too: the user list
is built from variables named =*_DB_USER=, which is the service accounts'
spelling, and the deployment's accounts are spelled =*_USER=. They are not pooled,
by naming and by intent — the pooler exists to serve workloads, not the
administrator's own connections — so that failure says nothing about whether the
pooler works. Asking as a service account is the test.
