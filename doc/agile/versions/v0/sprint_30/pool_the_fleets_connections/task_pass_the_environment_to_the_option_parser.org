* Goal

The environment stops being a hidden input to the option parser. A test that
asserts a compiled default passes no environment by construction, and a test
that asserts an environment value states the value it expects. Adding an
option the parser reads from the environment then changes no test.

* Acceptance

- =standard_service_options::parse= takes the environment as an argument, and
  no test body clears a variable by name.
- A defaults test passes an empty environment and asserts the compiled
  default, so the developer's =.env= cannot reach it.
- One test states an environment value for the port and asserts it wins over
  the compiled default, which the suites do not cover today: they cover a
  command-line override only.
- The thirteen =config_parser_tests.cpp= suites carry no
  =scoped_environment_override= allowlist of their own.
- A new option that the parser reads from the environment breaks no defaults
  test.

* Plan

** The mechanism, as it stands

Each service parses through =standard_service_options::parse(od, arguments,
app_name)=, which stores the command line and then layers
=parse_environment(od, make_mapper(app_name))=. The mapper accepts
=ORES_<APP>_<OPTION>= first and then the shared domains, so the compute
service reads =ORES_COMPUTE_SERVICE_DB_PORT=, which the environment's
=.env= now sets to the pooler's client port for every service.

=parse_defaults_returns_expected_values= parses with no arguments and asserts
=database.port == 5432=. Its own comment says why it clears anything: local
ctest loads the whole =.env= into the test process, so it clears the three
names the parser read when the comment was written. The pooler added a fourth
name the same parser reads, so the port arrives from the environment and the
assertion sees the pooler's port. The service is right to read it; the test's
isolation is what failed.

** Why clearing is not the same as ignoring the environment

A default is observable only when nothing supplies a value. A test that
asserts whatever the environment says stops being a defaults test: it would
assert the developer's port locally and the compiled one in CI, where there is
no =.env=. That is exactly why the suite is green in CI and red on the local
gate. The number would then depend on a checkout, and no test would catch a
broken default.

** The decided shape

1. Give the mapper a constructor over an explicit environment
   (=std::map<std::string, std::string>=) beside the one over the process
   environment.
2. Give =standard_service_options::parse= an overload that takes that map.
   The three-argument form stays and means "the process environment", so the
   generated per-service parsers change not at all.
3. A defaults test calls the four-argument form with ={}=. An env-wins test
   passes ={{"ORES_COMPUTE_SERVICE_DB_PORT", "<port>"}}= and asserts that
   port, which is the case nothing covers today.
4. Drop the =scoped_environment_override= allowlists from the suites.

The rejected alternative is to complete the allowlist in each suite with
=<APP>_DB_PORT= and =<APP>_DB_LISTENER_PORT=. It is correct and cheap, and it
leaves the same trap for the next option the parser reads.
