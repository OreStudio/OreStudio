The build now publishes the browser bundle and the site configuration beside the
binaries, and the service registry names them, so the gateway serves the
application and the screens call the gateway's own routes.

What the run shows. The gateway answers the application and what it was built
from: / is the index, an asset is served with its own type, and a screen path
answers the shell. /api/site and /api/site/deployment answer the site
environment. The harness signs in against the gateway and drives the screens:

| Suite | Gateway | The BFF |
|-------+---------+---------|
| smoke.spec.ts and identity-shapes.spec.ts | 4 passed, 2 failed | 4 passed, 2 failed |

The same two fail on both servers, so the switch does not break them: the
currencies search, which the gateway now answers on the server and the screen
still does not take up, and a shape write in the editor. The whole harness is 842
cases on one worker and asks for data this database does not seed, so the switch
is proved screen by screen and not in one run.

What serving the bundle found and fixed:

- The bundle routes captured the bundle by this, and the bundle was a local in
  the function that registered them, so the first request read a destroyed object
  and the gateway died. It had never fired, because no deployment had served a
  bundle. The routes now hold the bundle.
- A whole read of a generated record route ignored the query, so a screen that
  searches a list it holds whole was answered the list. The template states the
  order, the search and the filters once and both reads take them.
