* Goal

The engine's entry points read and write through generated repositories, which compare tenant_id with ctx.tenant_id(). The engine's context is the service's own tenant, so a workflow started on behalf of any other tenant is invisible to it from the second write onwards: the step insert is refused, the command stamp and the step progress are silent no-ops, and the completion event finds no step. Every engine path works for whichever tenant the service runs in.

* Acceptance

- A workflow started for a non-system tenant runs to completion, with each step advanced by its own completion event.
- A start for a non-system tenant reports success only after the instance, its first step and the step's published marker are all written.
- Recovery finds in-progress instances in every tenant, not only the service's own.
- An integration test starts a workflow for a tenant other than the service's and asserts its steps advance.

* Plan

Reproduce first, at the tenant boundary the service actually runs with. The
existing engine tests build the engine in the run's own tenant, so they cannot
see this defect at all; the new cases build it the way =ores.workflow.service=
does — engine in the system tenant, run in the test tenant — and assert the run
reaches =completed=.

Then decide between the two candidate fixes and take the one the component
already intends:

1. Carry the tenant on every message and rebuild a tenant-scoped context per
   operation. Rejected: =step_completed_event= has no tenant, so it would need a
   wire change and a migration of every publisher, and the recovery pass would
   still need a way to look across tenants.
2. Let the tables' row-level security policy decide the reads, which is what the
   policy, the repository facet's =:tenant_read_scope:= knob, and the engine's
   own header already say should happen. Chosen.

The engine is a cross-tenant service by design: =workflow_rls_policies_create.sql=
states that a system-tenant session must reach every tenant's rows, the engine
header documents its context as having no tenant filter, and the repository's
=tenant_id = ctx.tenant_id()= predicate was the one part that disagreed. Marking
both entities' reads =shared= removes only that predicate; mutations stay
tenant-scoped, and the policy still confines a tenant session to its own rows.

The change is at the model source, so the generated repositories are regenerated
rather than hand-edited, and the drift gate covers it.

* Notes

The query paths had to move with the engine. =get_steps= and =get_step_result=
both read through the service's own context, and both were broken for every
non-system caller in the same way: a tenant's =workflow start= could never
confirm that its run had been accepted, and =check_step_idempotency= always
missed, so a re-dispatched step re-executed instead of replaying its cached
result.

=get_steps= came back with the read scope alone, because it already guarded its
answer against the caller's tenant. =get_step_result= did not, and the read scope
turned it into a cross-tenant leak: it took only a step id, it had no caller
check at all, and the predicate that had confined it to the system tenant was the
very thing this task removed. It now takes the tenant the caller is asking about
— the one the engine put in the command's =X-Tenant-Id= header — and answers only
inside that tenant. The local review found this, not a test; that is what the
review pass is for.

Two things found on the way are not fixed here, because they are not about
tenants. Both are filed in the inbox:
[[id:E296B5EC-F01B-4664-9DE1-E5EFCE6E123C][the engine leaves completed_at and the
published marker unwritten]] and
[[id:0F5115A5-05FA-4A0E-A24B-1305F6DBC41B][workflow tests leave in-progress runs
behind]].

** The defect

Every read the generated repositories produce carried =tenant_id =
ctx.tenant_id()=. The engine holds the service's own tenant — the system tenant,
by =context_factory= — so from the second write onward a run belonging to any
other tenant was invisible to it: the published marker and the step progress were
silent no-ops, and the completion event found no step.

** The query path

Removing the predicate also removed what had confined the step-result query to
the system tenant. =get_step_result= had no caller check, so it had to learn
which tenant it was answering about before the predicate went: the request now
carries that tenant, the read is scoped to it, and the row is checked against it.
=workflow_query_handler answers for the tenant a request names= covers the three
answers: the step's own tenant finds it, another tenant does not, and a request
naming no tenant does not either.

** The fix

=:tenant_read_scope: shared= on =ores.workflow.workflow_instance= and
=ores.workflow.workflow_step=, then =check_component_drift.py --component
workflow-cpp= regenerated both repositories. The reads lost the predicate and now
rely on the policy; deletes and the version claims are unchanged. Two dead
=stamp_audit= declarations, never defined and never called, went with them.

Not a shortcut past isolation. The policy admits a row to its own tenant and, for
a system-tenant session, to every tenant's rows. Verified directly against the
live database as the service's own role, which has =rolbypassrls = false= and so
is really subject to the policy:

#+begin_src sql
set role ores_brave_hopper_workflow_service;
set app.current_tenant_id = '00000000-0000-0000-0000-0000000000aa';
select count(*) from ores_workflow_workflow_instances_tbl
 where valid_to = ores_utility_infinity_timestamp_fn();   -- 0
set app.current_tenant_id = 'ffffffff-ffff-ffff-ffff-ffffffffffff';
select count(*) from ores_workflow_workflow_instances_tbl
 where valid_to = ores_utility_infinity_timestamp_fn();   -- 125, every tenant
#+end_src
