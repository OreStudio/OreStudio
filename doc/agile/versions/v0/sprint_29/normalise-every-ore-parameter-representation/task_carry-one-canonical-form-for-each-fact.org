* Goal

One fact is held once. A value set states the canonical form of each of its
values and every other spelling ORE accepts for it, so a screen offers the
canonical forms, a writer may send any spelling the set knows, and the store ends
up holding the canonical one. The compiled tables in
=projects/ores.ore/core/src/domain/conventions_fields.cpp= stop being the place
that knowledge lives.

* Acceptance

- Every parameter whose ORE reader accepts more than one rendering is named, with
  the reader that accepts it and the canonical form chosen for it.
- The map from an accepted rendering to the canonical form is data: the value set
  states it, and no compiled table holds ORE's spellings.
- A write converts an accepted rendering to the canonical form at one boundary for
  every parameter, and a rendering the map does not know is refused naming the set.
- The screens offer the canonical forms and not the accepted ones, and the guard
  accepts every accepted rendering.
- A check fails when a table holds more than one rendering of one fact.

* Discovery

The spellings live in one file, in six tables, and the numbers are read from it by
=evidence/alias_census.py=, whose output is =alias_census.txt= beside it:

| Table | Spellings | Canonical forms |
|-------+-----------+-----------------|
| =business_day_conventions= | 26 | 7 |
| =day_counters= | 72 | 23 |
| =frequencies= | 18 | 9 |
| =compoundings= | 4 | 4 |
| =date_rules= | 12 | 12 |
| =day_counter_spellings= | 11 | 11 |
| **total** | **143** | **66** |

Two tables name fewer canonical forms than spellings, which is the whole problem:
=Unadjusted= answers to five spellings, =ACT/ACT.ISDA= to eight, and a store that
holds the spelling it was handed holds the same fact six ways.

Four of the six tables convert in one direction only. =business_day_conventions=,
=day_counters=, =frequencies= and =date_rules= map a spelling onto the canonical
form the store holds; =day_counter_spellings= maps the other way, from the stored
form onto the spelling an export writes. A set that states both directions states
the fact once.

=compoundings= and =date_rules= have one spelling per canonical form, so they are
not aliases at all: they are the set's own values, and the table adds nothing.

** The same knowledge is stated three times

=evidence/alias_copies.py= reads the other two copies, and =alias_copies.txt=
holds what it printed. The reader's tables are one statement; the refdata entities
convert with a table of their own, and the conventions seeder normalises with a
third before it writes a row:

#+begin_src text
  business_day_conventions: 26 renderings, the reader
                           27 renderings, refdata (and 'Nearest' is not a rendering the reader accepts)
  day_counters:            72 renderings, the reader
                           34 renderings, the seeder (5 of its keys no reader accepts, 43 reader rows it lacks)
  frequencies:             18 renderings in both
#+end_src

So the story's claim is measured rather than asserted: three tables in three
components hold the same knowledge, and two of them disagree with the reader.

** Two mismatches the reader cannot see

Comparing the reader's tables with the parser map that accepts the renderings
found two defects, both fixed in this slice:

| Mismatch | Effect |
|----------+--------|
| =Act/360 (Incl Last)= is a rendering ORE's parser accepts, and =day_counters= held no row for it | the engine reads a document this store refuses |
| =ThirdThursday=, =ThirdFriday=, =MondayAfterThirdFriday=, =TuesdayAfterThirdFriday= and =EveryThursday= are rows =date_rules= holds and ORE's parser never produces | a rule nothing can apply |
| =NthBusinessDay= and =EighthBusinessDay= are renderings ORE's parser accepts, and =date_rules= held no row for them | the engine reads a document this store refuses |

The check that found them now runs on every build: a rendering one source names
and the other does not stops the generator and names the rendering.

* What is not an alias

A boolean is the case the guard already settles. ORE's XML writes =Y= or =N= and
the screens write =true= or =false=, and the guard accepts all four and stores
what arrived. That is one fact written two ways, and the story counts it: the set
that governs a flag states =true= and =false= and the guard maps =Y= to =true=.

The aliasing is therefore about the tables above and the flag's two pairs, and
nothing else in the tree.

* Plan

** The canonical form is a column on the value

=ores_reporting_ore_parameter_value_set_values_tbl= gains =canonical_value=,
null when the row *is* the canonical form and the canonical value when it is
another spelling of one. The set's values therefore state both directions, and a
screen asks for the rows whose =canonical_value= is null.

The alternative, a second table of aliases, states the same fact twice: the alias
row would carry a value and a pointer to a value row, and the set's own value
would be the only thing that decides what is canonical. One column keeps the row
count and the ordering the set already states.

** A catalogue set could not state it, so the four sets became enumerated

=convention.business_day_convention=, =convention.day_counter= and their two
=curve.= twins were catalogue sets: their values were the rows of the refdata
registers, and a catalogue set holds no value rows, so it has nowhere to put a
canonical form. The registers hold every rendering ORE accepts — 72 day counters,
where 23 facts exist — because a guard refuses a spelling the register lacks. A
set drawn from them therefore offered the same day counter four times, which is
the defect the story is about, in the one place a person sees it.

So the four sets state their renderings themselves, and the registers keep their
own job: they are the whitelist a column guard checks, and the rows a convention
holds. A rendering is a fact about a parameter, so it lives with the parameter's
rule, not with the entity that happens to spell it. The registers still accept
every rendering, so no stored value changes and no guard loosens.

The alternative, marking the rendering rows in the registers, would have made a
26-row convention register hold 19 spellings, and every screen that lists a
register would have to filter rows that are not conventions.

** Conversion happens in the guard, not in the mapper

The mappers convert today, before the store sees a value, so the store's guards
never meet a spelling. That is why the knowledge had to live in code: a value that
never reaches the database cannot be converted there.

A helper, =ores_reporting_canonical_value_fn(set_code, value)=, returns the
canonical form of a value the set knows, and the four leaf guards call it as they
walk the column they are about to write: =NEW.column = ores_reporting_canonical_value_fn(...)=.
The guard is the one boundary every writer passes through, so the shell, a screen,
an import job and a publish function all convert once, in one place.

The columns are guarded but not rewritten today, and a BEFORE trigger may rewrite
=NEW=, so no schema change is needed to carry this.

** The order the slices go in

The change has a state that is worse than either end: mappers stopped converting
and the guard not converting yet would let a spelling reach a row unwatched. So:

1. Seed the renderings into the sets from the compiled tables, with a generator
   that reads =conventions_fields.cpp=, so the set states what the table states and
   a check compares them. Nothing changes at runtime, and a combo shows a fact
   once for the first time. **Done, PR #4244.**
2. Teach the guards to convert, and keep the mappers converting: the guard's
   conversion is then exercised by a test that writes a spelling straight to a
   table, and the import path still converts first, so no row changes. **Done,
   PR #4248.**
3. Stop the mappers converting, in one commit, so the spelling reaches the guard
   for the first time. The round-trip suites prove nothing was lost, and a check
   that no table holds a non-canonical value proves the guard converted.
4. Delete the compiled tables and the census script's reason to exist, which is the
   story's "no compiled table holds ORE's spellings".

Slice 1 is data and a generator; 2 and 3 are the runtime change; 4 is the
deletion that makes the claim true.

** The check

A query over the map and the guarded tables: for every child row, the value a row
holds must equal the canonical form of its set, so a spelling that reached a row
by any path is named with its table, its column and its set. The check reads the
map, so a column that gains a guard gains the check with it.

* Result

** Slice 1: the set states the form a configuration holds

A value row names the form a configuration holds and is empty when the row is
that form, so one table states which renderings are accepted, what each means and
which one a configuration carries. The four sets that drew on a refdata
catalogue became enumerated, because a catalogue set holds no value rows and so
had nowhere to put the column; the registers keep the whitelist a guard checks.

The numbers, measured after the seed and read back through =ores.shell=:

| Set | Choices | Renderings |
|-----+---------+------------|
| =convention.day_counter= | 23 | 52 |
| =curve.day_counter= | 23 | 52 |
| =convention.business_day_convention= | 7 | 20 |
| =curve.business_day_convention= | 7 | 20 |
| =convention.frequency= | 9 | 9 |
| **total** | **71** | **153** |

The renderings are read from ORE's reader and its parser rather than curated, so
the check that they agree runs on every build. It found five defects, all fixed:
three renderings the reader refused and five rows it could never apply.

Acceptance, as it stands:

- Every parameter whose ORE reader accepts more than one rendering is named, with
  the reader that accepts it and the canonical form chosen for it. **Done**, by
  =ore_aliases.py= reading the reader's six tables and the five parsers.
- The map from an accepted rendering to the canonical form is data, and no
  compiled table holds ORE's spellings. **Half done**: the reading direction is
  data; the direction a write emits is still =day_counter_spellings= and
  =bdc_spelling=, because the store's form is not always a form a document may
  write. Slice 4 states that direction as data too.
- A write converts through one boundary and refuses a rendering the map does not
  know, naming the set. **Done**: the four guards convert, and a value outside the
  set is refused with the set's name.
- The screens offer the canonical forms and the guard accepts every rendering.
  **Done**: a combo offers the canonical forms, and the guard accepts a rendering
  and stores its canonical form.
- A check fails when a table holds more than one rendering of one fact. **Not
  yet**: slice 3's query over the map and the guarded tables.

** Slice 2: the guard stores the form

=ores_reporting_canonical_value_fn(set_code, value)= answers with the form the set
names for one value, and with the value itself when the set states no other
rendering of it. All four guards call it after they accept a value, so a rendering
does not reach a row by any of the four write paths.

Two of the guards walk columns they read from a table, so they rewrite the row
through its JSON form: a trigger cannot name a column that a query named.

The measurement that matters, on a freshly recreated database whose conventions
were published afterwards:

#+begin_src text
$ psql -f tmp/noncanon.sql
NOTICE:  checked 73 columns: 0 hold a rendering
#+end_src

The 73 are the guarded columns whose set states a rendering. Before this slice the
same query named 45 rows, all of them =A365=, a rendering of =ACT/365.FIXED=,
written by the conventions publish: the publisher is a writer that never went
through the mappers. After it, the same publish leaves =ACT/365.FIXED= in all 45.

|------+----------------------+--------------------|
| a curve column | =A365F= | =ACT/365.FIXED= |

| a run setting | =NONE= | =None= |

** Slice 3, part one: the check

=ores_reporting_canonical_value_violations_fn()= names every live row in a guarded
column whose value is not the form its set names, with the table, the column and
the set. It reads the element map, so a column that gains a guard gains the check
with it, and it reads only the live version of a row: a value written before the
rule existed is history, not a defect.

On the database whose conventions were published after slice 2 it answers nothing.
Run it with:

./compass.sh sql -- -c "select * from ores_reporting_canonical_value_violations_fn()"
#+end_src

** Slice 3, part two is a decision, not a patch

Stopping the mappers converting was tried, and the measurement stopped it. The
reader was changed to check a spelling against its table and hand the spelling on,
which is the shape the task describes; =ores.ore.core.tests= then failed on 72
pinned exports of the ORE corpus, because that suite models the row path *without*
a database, and the canonicalisation it used to perform in memory now happens in
the guard.

The suite's pinned bytes therefore describe a pipeline that has a canonicaliser.
Reverting the readers leaves them describing the one that exists; keeping the
change means re-pinning 72 documents whose only difference is that they keep the
spelling the document wrote, and accepting that the suite then measures the codec
rather than the store.

Two ends are honest and this tree can have either, not both:

| End | The reader | The export |
|-----+------------+------------|
| the store canonicalises, and the codec states the renderings too | converts, as it does now, and the tables stay | writes a spelling the schema allows |
| the store canonicalises alone | passes the spelling on | writes the stored form, so a form the schema cannot write needs a spelling from data first |

The second end is where the story points, and it needs the export spelling stated
as data before the codec can stop. That is the next slice: a column on the value
row for the form an export writes, or a writer that reads the set. Until then the
compiled tables have a reason to exist, and slice 4 waits on it.

** What the next slice needs

Slice 2 adds =ores_reporting_canonical_value_fn(set_code, value)= and calls it
from the four leaf guards while the mappers still convert. The helper reads a
set's rows: the enumerated values, or the catalogue relation the set names. It
returns the value when the set holds no row for it and the guard's whitelist is
what refuses it, which is the one case a reader has to keep straight.

The three copies of the knowledge named in Discovery are still there. The refdata
=conventions_code= header and the seeder normalisers are slice 3 and 4 work: once
the guards convert, each has no reason to.
