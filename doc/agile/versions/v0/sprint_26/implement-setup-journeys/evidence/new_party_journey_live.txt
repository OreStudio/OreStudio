# New party journey, walked live

Environment: eager_maxwell (linux-clang-debug-make), web/BFF on 127.0.0.1:21402,
NATS on 21405, against a database rebuilt from the models with
`compass db recreate -y -k` and a fleet started with `compass services start`.

The deployment the walk ran against was made in one command, as the shell:

    bootstrap setup super_admin Secure-Password-123 super_admin@localhost.com \
        --tenant-admin-password Secure-Password-123 \
        --tenant-code probe --tenant-name "Probe Plc" --tenant-hostname probe \
        --profile empty_operational

    [2/3] Logging in as 'super_admin'...
    [3/3] Provisioning tenant 'probe' from 'empty_operational'...

          warn: The starting point names no legal entity, so there was nothing to import.

That tenant holds no operational root party -- `empty_operational` imports no
hierarchy -- so the walk also exercises the other branch of the placement rule:
the party a person adds becomes the tenant's root.

The browser was driven over the DevTools protocol by a throwaway script
(`build/evidence/party_walk.py`, not committed), signed in through the BFF as
`tenant_admin@probe`, and every screen below is what it printed.

## What this walk does not prove

- *The accounts picker.* The prototype showed one and the built journey does not
  carry it, because nothing writes the chosen associations: the run joins the
  caller alone. The journey document says so under *What is missing*.
- *A party added under a tenant that has a root.* The probe tenant holds no
  operational root, so the walk proves the branch where the new party becomes
  the root. The branch that places a party under an existing root is covered by
  the BFF route's own test, not by this walk.
- *The scripted end-to-end proof the task's last acceptance line asks for.* It is
  still owed; this file is a manual walk, recorded.

## A defect this walk found, and one it inherited

The first attempt failed at the run's only step:

    ✕ Create the tenant's parties
      The party 'ENPROBE, s.r.o.' was not saved:

The cause was this change's own: the run recorded the party's LEI before
activating the party, and an identifier's insert bumps the version of the party
it belongs to, so the activation that followed was refused as a party that had
moved on. The party was left Active=false at version 2 with its LEI already
written. The LEI is now recorded last, and the walk above is the run after that
fix.

The deployment this was first attempted against also had a marketdata service
that had died on a stale schema (`column "oresmd_uri" does not exist`), which
left the party stage waiting on a bundle step for 25 minutes and then failing
with a timeout instead of the cause. Two captures record that: a service exits
on one failed query, and a run whose dependency is dead reports a timeout.
Neither is this journey's, and neither is fixed here.
