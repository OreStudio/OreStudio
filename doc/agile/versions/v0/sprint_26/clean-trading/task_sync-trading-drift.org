* Goal

Make the checked-in ores.trading tree equal to what its models
generate, and make the component build and pass its suites at that
tree. This is item group G plus the protocol items P01, P02, P03 and
P05, and the wiring item W01. It changes no model and no data shape: it
lands work the generator already produces and deletes what the
generator supersedes.

The measured baseline is 1636 files that would change and 115 that
would be created. Of the changes, 1434 are the generated-file banner
alone, 78 are the eventing rename, 123 are substantive template changes
and 1 is the root =CMakeLists.txt=. A component usually cannot be
cleaned by landing that much at once, but here it is safe, because 88
per cent of the changes are attributable to one cause and the generator
already reproduces the tree's semantics.

** What the survey before regeneration found

=instrument_protocol.hpp= holds two groups, and only one can go here.

- The nine rates families. Their structs go, because the generated
  per-family headers replace them.
- Four families with no model at all: =commodity=, =composite=,
  =credit= and =scripted=. Their messages live only in this header, so
  deleting the whole file would break their handlers and their shell
  units. They stay until PR 3 models them, and the header disappears
  when the last one moves.

Consumers of the nine families' consolidated request types outside the
trading component, all of which this PR migrates:

- Nine hand-written shell units under
  =projects/ores.shell/application/src/app/commands/trading/=, one for
  each rates family.
- =projects/ores.ore/service/src/messaging/ore_import_execute_handler.cpp=.

The shell has two trading command trees. The generated one is
=projects/ores.shell/trading/= and the regeneration rewrites 66 of its
files. The rates units and the four unmodelled families' units are
hand-written under =ores.shell/application/=. Check both when the
protocol moves.

=registrar_rates.cpp= registers the nine families against
=rates_instrument_handler.hpp=. Both are deleted, and the generated
per-family registrars are wired at the same composition point. Read the
composition point before deleting, because the drift gate cannot see an

** 2. Apply D1 before regenerating, not after

The generator emits per-family protocols, handlers and registrars for

because it is the composition point: =registrar.cpp= calls
=detail::register_rates_handlers=, and the other families keep the same
shape.

** The consumer migration the wire rename forces

names or subjects. Per family, the mapping is:

| Consolidated | Generated | Subject |
|--------------+-----------+---------|
| =get_<family>_instruments_request/response= | =list_<family>_instruments_request/response= | =trading.v1.<family>_instruments.list=, unchanged |
| =save_<family>_instrument_request/response= | =put_<family>_instrument_request/response= | =...save= becomes =...put= |

The families are fra, vanilla swap, cap floor, swaption, balance

The request and response fields differ from the consolidated ones as

The call sites are the nine hand-written shell units under

=projects/ores.ore/service/src/messaging/ore_import_execute_handler.cpp=.
The shell units also carry the subject strings as literals, so the

** The first generator defect the build found

The regenerated component does not compile, and the defect is in the
generator, not in the model. =evidence/pr2_generator_defect_equality.txt=
holds the error and the templates.

=cpp_domain_type_class.hpp.mustache= emits a defaulted =operator== = for
every domain class. =cpp_field_group.hpp.mustache= emits no comparison
for the field-group struct it generates. A domain class whose member is
a field group therefore has its comparison implicitly deleted, and the
build treats that as an error under =-Werror=. At 39f99acef3 neither
file had a comparison, so the committed tree compiled; the current
templates add one to the domain class and not to the field group.

Every trading entity with a field-group member is affected, which is
=trade= and the entities that inherit =instrument_identity=. This is
item G05 work: fix the field-group template at its source in the org
source that tangles to =cpp_field_group.hpp.mustache=, add a regression
test to the codegen suite, then regenerate. Item G07 applies while the
defect is open: do not refresh any other artefact that the same
generator feeds.

The other field-group models are one in =ores.dq= and one worked
example in =ores.codegen=. Neither component is in
=COMPONENTS_UNDER_TEST=, so no registered component changes, but
=ores.dq='s generated output does and that is recorded here.

** The second generator defect: the repository ignores the group pair

The API library builds after the equality fix. The core library stops on
the 26 instrument repositories, and the defect is in the repository
template.

Two grammar forms exist for a grouped entity. =trade= uses the modern
=** Domain groups= table, which replaces the struct body entirely. The 26
instrument entities use the older pair, =:domain_identity_group:= and
=:domain_audit_group:=, which nests those two groups and leaves the
entity's own columns flat. The domain-class template and the mapper
template honour the pair; the repository template does not, so it emits
=v.instrument_id= where the domain type has =v.identity.instrument_id=.
The committed tree compiled because that repository was hand-written;
the regeneration replaces it.

Evidence: =evidence/pr2_generator_defect_repository_group.txt=.

Two ways forward, and the choice is a model-shape decision:

- Teach the repository template the pair, addressing the grouped columns
  through their member. This keeps the current model shape and the wire
  format, and it is the smaller change.
- Migrate the 26 models to the =** Domain groups= table. The loader then
  requires every column to be in a group, so each entity needs a third
  field group for its own columns, the struct body changes from "two
  nested members plus flat columns" to a member list, and the wire JSON
  changes shape for 26 instrument types. It also needs the loader to
  resolve the shared =ores.dq.audit_record= group across components;
  the table form resolves a group only beside the entity's own model
  today, which is a second small defect the experiment confirmed.

Recorded recommendation: take the first now, because the component's
acceptance is drift-clean regeneration, not a wire reshape, and revisit
the table form when PR 3 models the remaining families.

** The group prefix reaches further than the repository

The repository template is fixed, and the repository layer builds. The
service layer stops at the same defect in its own template:
key_from reads v.instrument_id with no member, the version literal has
no scaffold prefix, change_commentary is an audit member read flat, and
a compound key's integer member is passed to a parameter that takes
text. Evidence:
=evidence/pr2_generator_defect_service_group.txt=.

The template states its conversions inline, as {{#is_uuid}} arms, at six
sites and has no arm for a number. The durable fix is to prepare those
expressions in core.py as string fields and have the template splice
them, the way it already splices =primary_key.v_args= and
=removal_key_args=. That deletes the inline arms instead of adding a
fourth type to each one.

The same class of site may exist in the service header, the table I/O,
the JSON I/O, the generator and the history-difference payloads. Expect
the build to name them one at a time; each is the same prefix or the
same text conversion.

** The enum write field

With the prefixes and the key text in place the services compile, and
one error is left: =to_domain= assigns a text wire field to the domain's
enum member.

    v.classification.product_type = write.product_type;

The model states both sides. The column is text (=:cpp_type:
std::string=, =:type: product_type_t=) and the field group that carries
it declares =domain::product_type=, so the domain is an enumeration
while the wire is text. The conversion between them is what is missing,
and the domain header already provides it as
=product_type_from_string=. Evidence:
=evidence/pr2_generator_defect_enum_write.txt=.

The fix is an arm in both =to_domain= functions for a write field whose
column states =:is_enum: true=, with a regression test, because every
enum column in every component needs the same arm.

** Where the build stands after the enum arm

The enum arm is in, and the whole ores.trading component compiles: the
API library, the core library, the service library and the executables.
Two further blockers were cleared on the way.

- The generated shell command units take a product type as an argument
  and the shell's token reader had no conversion for it, so the build
  stopped on its own static assert. =product_type= now states its own
  =parse_token=, which the reader finds by argument-dependent lookup, as
  ores.synthetic's =binding_mode= and =scope= do.
- The six =component_files.cmake= lists were stale, so the nine
  generated registrar sources were never compiled and the service
  library linked with undefined handler registrars. Item G06.

** The consumer migration the tree build now reaches

The tree build stops at 67 per cent in ores.ore's hand-written
=ore_import_execute_handler.cpp=. It speaks the old consolidated
protocol: 26 =using= declarations name old request types and 192 lines
reach through =req.data.=.

This is a rename and a reshape, not a rename alone. The generated write
request carries the domain object under the entity's own member rather
than under =data=, and it carries a change intent:

    save_bond_leg_amount_request req;      becomes
    req.data.amount_role = ...;            put_bond_leg_amount_request req;
                                           req.bond_leg_amount.amount_role = ...;

The read side is a rename with the paged fields to check: an old
=get_bond_issues_request= with =offset= and =limit= becomes
=list_bond_issues_request=, whose fields are the model's, not the
consolidated header's.

Every call site is read against the generated struct rather than
renamed mechanically, and the nine shell units under
=ores.shell/application/= need the same pass.

=evidence/pr2_consumer_migration_recipe.txt= states the mapping in full:
the four request shapes, the canonical construction the generated shell
units use, the line-by-line mapping, and the counts for the handler.
Two things a rename cannot carry: a whole-object assignment expands to
one assignment per member of the generated =<x>_write=, whose member
list the protocol header states; and every response check reads
=result.outcome= rather than a =success= bool. The handler's =nats_call=
helper needs no change, because it is templated on
=typename Req::response_type=.
