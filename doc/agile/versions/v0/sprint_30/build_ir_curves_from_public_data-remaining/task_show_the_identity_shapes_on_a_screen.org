* Goal

The identity shapes are data, so a person should be able to read them and change them without the shell. A screen lists the shapes of each series family, shows a shape's history, and lets a person with the right permission add or change a row. The oresmd editor reads the same shapes and marks the fields a family requires or forbids, so a person sees a bad identity before the writer refuses it.

* Acceptance

- A screen lists every shape the session reads, grouped by asset class, series subclass and index family, and shows whether each row is the system tenant's or the tenant's own.
- A person with the shape permissions can add, change and remove a row, and can read the versions of a row.
- The oresmd editor marks each field the family of the URI requires or forbids, and names the family it read.

* Plan

The service already served the shapes: list, get, put, delete and versions,
with change events. What was missing was the web.

The screen is a hand-written market data page with its own BFF module, not a
resource of the reference data record framework. That framework reads a record
by one key, names its permissions =refdata::=, and finds a row's history
through a history provider. A shape has a four-part key, =marketdata::=
permissions, and no history provider, because the provider interface takes a
single string id. The versions come from the protocol's own versions request
instead, which takes the whole key.

The editor names a URL's family as the writer keys it. The asset class is the
schema row's, which is the class the projector writes. The subclass is the
classification rule's: a datum rule by instrument and quote, with an empty
quote for every quote, and the one index rule for every fixing. The index
family is the fixing's family, or the =index= a series holds. The shapes are
stated per identity column, so a fixing field is named by the column the
projector writes it into, as =name= becomes =index_name=.

* Notes

A tenant reads the shared catalogue beside its own rows and may change only its
own, so the screen offers a change of a shared row only to the system tenant. The
service refuses the rest whatever the screen offers.

The editor's marks are advice. A person without the shape read permission
still composes a URL, and sees no marks.

* Result

The identity shapes have a screen under Market data. It lists every shape the
session reads, grouped by asset class, series subclass and index family, and says
whether each row is the shared catalogue's or the tenant's own. A row's versions
open beside it, with who changed it and why. A person with the shape permissions
adds, changes and removes rows.

The oresmd editor names the family of the URL on screen and marks each field
its shape requires or forbids. It says when no shape states the family, and it
names a required field that this kind of URL cannot write.

All three acceptance points are met. The harness proves the first two against
the running services, and the editor's tests prove the third.
