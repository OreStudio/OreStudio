* Acceptance

- The cost of sending repository statements unnamed is measured: the same
  statement, the same rows, prepared once and sent unnamed, against a real
  database, with the numbers recorded on the task.
- If the measured cost is acceptable, =detail::prepared= stops naming statements
  and the pooler has no version floor; if it is not, the floor is stated as
  pgbouncer 1.21 or later with =max_prepared_statements=, and every environment
  that runs a pooler states its version in one place.
- The choice is proven through a transaction pooler in both directions: a named
  statement fails behind a pooler without support, and the chosen arrangement
  passes.
- The hand-written SQL path, which already sends unnamed statements, is unchanged
  by the decision.
- The decision is recorded in the story, and the number that decided it with it.

* Plan

Both halves need a running pooler. The plan expected to wait for
[[id:3D23B905-359A-4DE0-9F35-1B047A54385B][Run a pooler beside a shared fleet]]
because the host could not install one. That changed: =pgbouncer= 1.26.1 is
installed from sid, and a second instance runs from the checkout as the user, so
nothing here waits on another task.

The measurement is =pgbench= against this environment's database, because it can
send the same script in both protocols from one binary: =M prepared= names the
statement once, =M extended= parses and plans it on every execution. Two
workloads bound the answer - =select 1=, where planning is most of the work, and a
range lookup over 512,195 rows, where it is nothing.

The pooler half runs the database suite through a transaction-mode instance twice,
once with =max_prepared_statements = 0= and once at its default, both against the
same checkout.

* Notes

** What the pooler does, exactly

The first attempt at this looked like good news and was not. A name prepared by
one client and executed by two later ones returned the right value, which reads
as a pooler keeping prepared statements for everyone. It was the same server
connection being reused: with sequential clients and =default_pool_size = 5=, the
pool hands back the connection it just took in.

Two concurrent clients show what happens. While one holds its server connection
in =pg_sleep=, the other gets a second one, and executing the name there fails
with "prepared statement does not exist" whether tracking is on or off. A
pooler's prepared statements belong to the client that made them; it replays
them onto whichever server connection that client lands on next. That is the
arrangement our layer needs, because a repository prepares on a pooled
connection and executes on later transactions of the same one.

** The four cases the pooled run fails

All four are connection-level cases, not statement cases, and they belong to
[[id:83C4FD4E-888C-4C3F-BE3D-50136487B458][Prove the pooled path in CI]]:

- =postgres_listener_service= times out, because a transaction pooler hands a
  =LISTEN= to somebody else at the next commit. This is the story's decision
  that the listener stays direct, seen from the other side.
- =pq_layer_tests.cpp:527= terminates a backend by pid, and the pid it reads
  through a pooler is the pooler's server connection.
- =pq_layer_tests.cpp:554= expects a failed prepare to report its own error.
- =pq_layer_tests.cpp:374= copies rows into a table with row-level security
  forced, and =COPY FROM= refuses that under a pooled session.

None of them touches the decision taken here, and none may be waved away: task 6
is where they are either fixed or declared out of scope for the pooled path.

** The previous decision is corrected

An earlier note on the story said a name prepared by one client executed by two
later clients, and concluded that a modern pooler needs no work for our
statements. The conclusion stands - the pooler does replay a client's own
statements - but the evidence for it was wrong, and is replaced by the
measurement and the concurrent-client test above.

* Result

The prepared statements stay, and the pooler carries a version floor instead.

=pgbench= against this environment's database, ten seconds a run: a statement
that returns nothing runs 26,378 times a second named and 16,980 unnamed, so
planning costs about 21 microseconds; a range lookup over 512,195 rows runs at
16.6 and 17.3 a second, where the difference is lost in the scan. The
repositories mostly run short indexed statements, which sit near the first
figure.

Through a transaction pooler, our layer breaks without statement tracking - the
first prepare after a server connection changes reports "prepared statement
ores_pq_set_context already exists" - and works with it, 71 of 75 database cases
passing. The four that fail are connection-level cases and belong to
[[id:83C4FD4E-888C-4C3F-BE3D-50136487B458][Prove the pooled path in CI]].

So: the floor is pgbouncer 1.21 or later with =max_prepared_statements=, which
1.24 and later default to 200, and the environments that run a pooler state that
version in one place. Sending the statements unnamed is rejected, with the 21
microseconds as the number that rejected it. The hand-written SQL already sends
unnamed statements and does not change.
