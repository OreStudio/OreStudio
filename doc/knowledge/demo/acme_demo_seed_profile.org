* Summary

A tenant is built from a starting point, and a starting point is an ordered list
of steps held as rows. The one the demonstration uses is =acme_demo=: nine steps
that install the system data, publish the tenant's own datasets, import the LEI
hierarchy, provision the parties, load the staff, set their passwords, attach
their pictures, subscribe every party to its market data provider and generate a
trade population. Nothing in that list is code. A variant changes a row's
arguments, and a tenant that wants a thinner book or a different feed changes a
value rather than a build.

* Detail

** The nine steps

#+ATTR_HTML: :class hug-leading
| Order | Step | What it creates |
|-------+------+-----------------|
| 5 | =system_provision= | publishes the system's own datasets into the system tenant, which every tenant reads as an overlay |
| 10 | =publish_bundle= | the =base= bundle, the =marketdata.reference_vintage_2026_05_05= bundle, the GLEIF counterparty set at the profile's chosen size, and the ORE counterparty aliases |
| 20 | =import_lei_hierarchy= | the Acme LEI hierarchy, whose root is =9695ACMEGROUP0000030=, as the tenant's four parties |
| 30 | =provision_party= | each party's own reference data, from the =party_essentials= bundle |
| 40 | =load_staff= | the staff of each of the four entities: 73 accounts, each with its role, job title, manager, business unit and contact record |
| 45 | =set_staff_passwords= | one development password for every staff account, set through the server's own password API |
| 50 | =attach_photos= | each account's picture and each party's logo, copied from the system tenant's templates |
| 60 | =subscribe_market_data= | one subscription and one route for every party, at the provider and source the row names |
| 70 | =generate_trades= | one trade population per trading entity, each booked into that entity's own book by its own traders |

The run then closes with =complete_provisioning=, which the workflow adds rather
than the profile: it hands the tenant to its own administrator, clears the
bootstrap flag, and declares the run done.

** Why the order is what it is

Three dependencies decide it, and each one has a failure behind it.

- The system data comes first, because a tenant is built on a system that already
  makes sense: a coding scheme validator resolves its scheme in the system
  tenant, and a template image is read from there.
- The staff come after the parties, and the passwords and pictures after the
  staff, because a password or a picture names an account that must already
  exist. Attaching a picture to an account that is not there is the step failure
  that taught this order.
- The market data comes after the staff and the parties, because the step acts as
  a party and writes a party's rows: a subscription written before the party
  exists has nothing to hang from.

** Which parts are data, and which are code

#+ATTR_HTML: :class hug-leading
| A person wants | They change |
|----------------+-------------|
| A different counterparty set size | the profile's =counterparty_size= parameter |
| A different feed for one party | the party's row in =subscribe_market_data= |
| Fewer trades, another book, another asset class | a value in the =generate_trades= config |
| Another staff population, another office | the seeder's =OFFICES= table, then regenerate the datasets |

The last row is the boundary: the staff, the business units, the portfolios and
the books are generated by the Acme seeder rather than written by hand, so a new
office is a table entry and a regeneration. The seed profile names the datasets
and the arguments; the seeder produces their contents. A change to the shape of
the organisation is a seeder change and a regeneration, and a change to what the
profile does with it is a value.

** What the profile leaves to the system

The profile publishes a set of datasets and follows the workflow that publishes
them, but it writes no catalogue row, no role and no permission. The providers,
the sources, the vendor instruments and the mappings belong to the system bundle,
and the roles and the permissions belong to the IAM seeds. A tenant is therefore
a reader of both, and a fault in either shows up in every tenant at once. See
[[id:922C155B-6733-4D2B-A675-A7361A5BDC63][A system bundle installs the catalogue
and the simulator installs its own universe]] and
[[id:3F19F33A-161C-4E61-BD92-CB32953DA8F9][the permission matrix]].

** The staff the profile now loads

Seventy-three staff accounts, of whom 31 hold the trading role, 16 the operations
role, 4 the controller role and 4 the finance role, with the rest split between
the viewer, sales and support roles. The controller and finance accounts exist for
the approval parts of the same name: before them, no seeded person held either
part's decide permission, so a book change could only be answered by a tenant
administrator. [[id:8B0D92BD-7D15-45B7-80EA-07D111F73EB3][The approval model]]
says who decides what, and
[[id:3F19F33A-161C-4E61-BD92-CB32953DA8F9][the permission matrix]] says which
role each function holds.
