This page defines one [[id:A7FCC423-1CA3-4345-BF5B-18D54207B00B][report]]:
Surface vega ladder Bump and Reprice. It shows the money the book gains or loses at
every strike of every expiry when the volatility surface is shifted at each of those
points and the book is repriced. A trading desk reads it to place a hedge at a named
strike and expiry, and the market risk function reads it to check that the wings and
the body of the surface are carried at the shape the book reports. It runs at the
close on the schedule. It leaves the engine's output archive in storage, which holds
the sensitivity file and the scenario file, and the run records where that archive
landed.

* Purpose

The report answers one question per surface point. What does a shift at this strike
and this expiry cost the book, or pay it? One bucket answers one point, so the ladder
shows the exposure over the whole surface and not only along its at-the-money spine.

The answer feeds a hedging decision. A desk decides where on the surface to buy or
sell volatility, and whether the wing and body exposures the ladder shows are the
ones the book is meant to carry overnight.

The report is not a report at a stated bump. ORE has no such concept. It has a
shift, and the shift is a setting of the configuration. The report, its analytics
and its reader know nothing about 0.1. They know the size the configuration states
and the buckets the engine keys. A desk that wants a tenth of a volatility point
states that size in the document the definition binds, and the same report then
answers that question.

* Frequency

A ladder is end of day. It is read as the risk statement of record and compared
across days, and a live ladder would price against a body that is not reproducible.
The definition runs on the schedule at the close.

An intraday variant is worth naming, because a desk that watches a volatility move
wants the same bucket list during the day. No intraday variant is seeded. One would
need three things: a definition whose cut selection is LIVE, a run settings row whose
market data type is live, and the same sensitivity configuration.

* Inputs

- Trades selected by scope. A definition states the scope it selects, and the ladder
  reads the trade set that scope names.
- Market data for the as-of date, from the end of day cut. The run settings row
  states market data type =eod=, so the valuation date is the weekday before the run
  date, and holiday calendars are not consulted.
- The sensitivity configuration the analytic binds, through
  =sensitivityConfigFile=. The document states a strike list on the volatility
  block, so the run shifts every strike of every expiry it names.
- The pricing engine the definition binds. It prices the book before the shift and
  again after it.
- The base currency, from the run settings row. The figures are expressed in it.

* Outputs

The run produces the engine's own output archive. The archive holds this report's CSV
artefacts, and the run records where the archive landed against the run instance. It
also records the cut the run minted, with the cut's label, kind and instant.

The engine names the two files the run declares. The shipped surface run names them
=sensitivity_fullSurface.csv= and =scenario_fullSurface.csv=, and the at-the-money
run beside it names =sensitivity_atmOnly.csv= and =scenario.csv=. The columns are the
same in each. The sensitivity file carries the value change of each shifted point in
its =Delta= column, and the scenario file carries the scenario values that lie behind
those figures. A reader sets a row of one file against a row of the other.

The rows a reader would query are a later phase. The result store is designed on
[[file:../architecture/report_post_processing.org][Report post-processing]] and is
not built, so today a reader opens the two files in the archive.

The bucket has three parts, the currency pair, the expiry and the strike, and the
reader takes all three out of the =Factor_1= key. The shipped sample writes FX
volatility keys in the form =FxVolatility/<pair>/<strike>/<expiry>=, so one key is one
point of the surface and one bucket of this ladder.

* ORE configuration

The run is a full-surface run. The run document states one =sensitivity= analytic
whose document carries a strike list. The fragment below is trimmed from
=external/ore/examples/MarketRisk/Input/ore_sensismile_surface.xml=.

#+begin_src xml
<Analytic type="sensitivity">
  <Parameter name="active">Y</Parameter>
  <Parameter name="marketConfigFile">simulation_fullSurface.xml</Parameter>
  <Parameter name="sensitivityConfigFile">sensitivity_fullSurface.xml</Parameter>
  <Parameter name="pricingEnginesFile">../../Input/pricingengine.xml</Parameter>
  <Parameter name="scenarioOutputFile">scenario_fullSurface.csv</Parameter>
  <Parameter name="sensitivityOutputFile">sensitivity_fullSurface.csv</Parameter>
  <Parameter name="outputSensitivityThreshold">0.000001</Parameter>
  <Parameter name="recalibrateModels">Y</Parameter>
</Analytic>
#+end_src

The =SensitivityAnalysis= document is a document of its own. ORE validates it against
[[proj:external/ore/xsd/sensitivity.xsd][sensitivity.xsd]], and it carries one
block for each risk class: the curves, the spots, the volatilities, the credit
families, the inflation families, the correlations and the rest. This report reads
the FX volatility block. Every factor block states four things. =ShiftType= says how
the shift is applied and is =Relative=, =Absolute= or =EqualTo=. =ShiftSize= says how
large it is and is a real, with an optional =key= for an alternative size.
=ShiftScheme= says where the shift is anchored and is =Forward=, =Backward= or
=Central=. The bucket list says which points move, and it is =ShiftTenors=,
=ShiftExpiries=, =ShiftStrikes=, =ShiftLossLevels= or =ShiftTerms=. =ShiftType= and
=ShiftScheme= are enums in
[[proj:external/ore/xsd/ore_types.xsd][ore_types.xsd]].

The switch that makes this ladder a surface ladder is =ShiftStrikes=. The shipped
pair of documents in
[[proj:external/ore/examples/MarketRisk/Input/SensiSmile/][SensiSmile]] shows it. The
at-the-money form, =sensitivity_atmOnly.xml=, states this swaption block:

#+begin_src xml
<SwaptionVolatility ccy="EUR">
  <ShiftType>Relative</ShiftType>
  <ShiftSize>0.01</ShiftSize>
  <ShiftExpiries>1Y,5Y,7Y,10Y</ShiftExpiries>
  <ShiftStrikes>0.0</ShiftStrikes>
  <ShiftTerms>1Y,5Y,10Y</ShiftTerms>
</SwaptionVolatility>
#+end_src

The full-surface form, =sensitivity_fullSurface.xml=, states the same block with one
list changed:

#+begin_src xml
<SwaptionVolatility ccy="EUR">
  <ShiftType>Relative</ShiftType>
  <ShiftSize>0.01</ShiftSize>
  <ShiftExpiries>1Y,5Y,7Y,10Y</ShiftExpiries>
  <ShiftStrikes>-0.02,-0.01,0.0,0.01,0.02</ShiftStrikes>
  <ShiftTerms>1Y,5Y,10Y</ShiftTerms>
</SwaptionVolatility>
#+end_src

That list is the whole difference in the document. One strike gives the at-the-money
ladder, and five strikes give a surface ladder over five points. The two run
documents, =ore_sensismile_atm.xml= and =ore_sensismile_surface.xml=, name the same
Setup files and differ in the market configuration and the sensitivity configuration
they bind, in the output file names they declare, and in a stress analytic the
at-the-money form carries and switches off.

For an FX pair the same switch applies to the FX volatility block. The shipped worked
document leaves =ShiftStrikes= empty there, which is the at-the-money form. This
ladder states a strike list in its place, and every strike in the list becomes a row.
The fragment below is that block, trimmed from
=external/ore/examples/MarketRisk/Input/sensitivity.xml=, with the empty element as
shipped.

#+begin_src xml
<FxVolatilities>
  <FxVolatility ccypair="USDEUR">
    <ShiftType>Relative</ShiftType>
    <ShiftSize>0.01</ShiftSize>
    <ShiftScheme>Forward</ShiftScheme>
    <ShiftExpiries>1Y,2Y,3Y,5Y</ShiftExpiries>
    <ShiftStrikes/>
  </FxVolatility>
</FxVolatilities>
#+end_src

The engine's own names for the two files are =sensitivity.csv=, which carries the
=Delta= and =Gamma= columns, and =scenario.csv=, which carries the scenario values that
lie behind them. A run that states output names in its analytic gets the names it
states. =Delta= is a value change and not a derivative. It is money per shift, and the
shift size is already inside it. The =Difference= column of =scenario.csv= carries the
same value, so a reader checks one file against the other.

The bump is a setting of the configuration and not the identity of the report. Two
reports over one book that differ only in shift size differ only in the document they
bind. A 0.1 vol point bump is =ShiftSize= 0.1 on a surface stored in vol points, or
=Absolute= 0.001 on a surface stored in decimals. The report itself, its analytics
and its reader are the same either way, and so is the number of buckets.

* A worked read

A reader opens the archive the run records and reads the two files in order. No step
needs a tool beyond a CSV reader.

1. Open the sensitivity file in the archive the run records.
2. Keep the rows whose =Factor_1= key begins =FxVolatility/=.
3. Read the currency pair, the strike and the expiry out of the key. Those three
   name the bucket.
4. Read =ShiftSize_1= on the row. It states the size of the shift that produced the
   figure, and it is the only place the size appears.
5. Read =Delta= on the same row. It is the value change of that trade at that point,
   already scaled by the shift.
6. Add =Delta= across the trades that share the bucket. The sum is the book's figure
   for that point.
7. Repeat step 6 for every strike of an expiry, then for every expiry in the list.
   The set of sums is the ladder.
8. Open the scenario file and find the row of the same trade and the same factor.
   Check that =Difference= agrees with the =Delta= of the row. A disagreement says
   the reader has paired the wrong factor.
9. Sort the ladder by expiry and read across the strikes of one expiry. The pattern
   is the shape of the book's exposure across that smile.
10. Compare the shape with the previous day's file, and state which point moved and
    which stayed.

The ladder is a set of value changes at one shift size. It is not a set of
derivatives, and a reader who compares two runs compares them only when the two
configuration documents state the same size and the same strike list.

* What is not built

- No mapper reads or writes a =SensitivityAnalysis= document. The document is a name
  in a lookup and a row in the file library, and it is not a modelled entity.
- The run package carries only the four Setup documents, which are conventions, curve
  configuration, today's market and pricing engines. An analytic document that no
  owner exports never reaches the engine.
- The store seeds no volatility market data. The dataset holds no
  =FX_OPTION/RATE_LNVOL= quote and no volatility surface configuration, so the engine
  refuses at the point it needs a volatility, and the run records that refusal
  against the run instance. The refusal is a fact about the environment and not about
  the report.
- No shift size is stated anywhere in the store.
- The shipped pair of example documents demonstrates the strike switch on the
  swaption block. No FX surface form is shipped, so the FX block in both files stays
  at the at-the-money form.
- No stored shape holds a bucketed ladder. The result store that would hold one is
  not built.

* Test coverage

No substitute is defined for this report, so a test run of it executes every phase.
It gathers trades and market data and assembles its own bundle. The full-pipeline
proof therefore exercises the report, and no smoke test does.

The mechanism the page describes is exercised by the shipped ORE sample. Its two
forms are the files in
[[proj:external/ore/examples/MarketRisk/Input/SensiSmile/][SensiSmile]], and the
expected output of the full-surface form is in
=external/ore/examples/MarketRisk/ExpectedOutput/SensiSmile/Surface/=. A reader
compares a run of that sample against that output.

The cut resolution the report relies on is exercised by the task that lit the
intraday reports,
