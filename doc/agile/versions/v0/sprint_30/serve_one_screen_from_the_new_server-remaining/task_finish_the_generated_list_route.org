* Acceptance

- The page, the order, the search and all filter members work on a generated list route, each with a test.
- The local gate is green.

* Plan

Compare the generated list route with what ores.web sends, then change the
route template so the two agree. Three decisions came from that comparison:

1. The route reads =sort= and =descending=, which ores.web sends, and not
   =order= and =desc=.
2. The route refuses an =f.*= filter that its entity does not declare, with a
   400, as the BFF does. A filter that narrows nothing would read as an answer.
3. A multi-valued filter uses its member name: =f.<column>_one_of=a,b= for a
   list of values, and =f.<column>_from= and =f.<column>_to= for a range. The
   route refuses an empty item in a list.

Each generated route test file also runs the paged list handler against a
client that is not connected. A request that the route accepts fails at the
forward step with a 500. A request that the route refuses gets a 400. The tests
read that difference, so they need no NATS.
