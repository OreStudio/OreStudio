#+title: Task: No config books credit, so the family never runs
#+description: The capture this task was promoted from said the credit writer existed and only a config was missing. It was wrong, and this is the correction.

The credit family is unimplemented in ores.synthetic. There is no credit trade planner and no credit writer: the planner registry holds bond, commodity, equity, fx and interest_rates, and grep finds no credit_terms, no credit_instrument and no credit_trade_planner anywhere in the project. The routed table, the trade type catalogue rows and the permission vocabulary exist; nothing writes them.

Measured on a recreated database: zero credit instrument rows, and the demo profile seeds bond, commodity, equity, fx and interest_rates only. The book is the one thing that does exist -- four credit books are seeded, including IG CDS EMEA in EUR.

The reference entity is the open question, and it is also a defect in its own right. credit_instruments.reference_entity is text whose model says "name or identifier", so a trade may carry whatever string a caller types, and nothing relates that string to the entity the risk is actually on. The tenant's 38,213 LEI entities sit in the DQ lei_entity dataset, which the synthetic service has no read path to.

* Decisions

- The population draws its reference entities from the DQ lei_entity dataset (option A). That means a read path from the synthetic service into the DQ subject, which is the work this task carries beyond the writer.
- The column cannot simply become an LEI. Measured while attempting the rename: the ORE importer writes a credit curve identifier or an issuer identifier into it (credit_instrument_projection.cpp: reference_entity is the issuer id, the credit curve id, or a qualifier such as =ACME= or =ACME-SR=), and the projection tests assert exactly that. A rename to reference_entity_lei plus a twenty-character check compiles but breaks the import path and misnames what imported trades carry.
- Two shapes reconcile it, and the choice is not made: (a) one column named for what it holds, the identifier the source states, with no referential integrity; or (b) two columns, the source's identifier and a nullable LEI, where the population writes the LEI and an ORE import leaves it empty. (b) is a real fix and keeps the import honest; it changes the table's shape and the import mapping.

* Scope

Three parts, in this order:

1. The column fix: rename, state the soft reference, and refuse a value that is not an LEI.
2. The read path: the synthetic service resolves reference entities from the DQ lei_entity dataset.
3. The family: constructors for the six routed codes, a credit planner, a writer arm, a book (IG CDS EMEA exists) and a config, proved by a run.
