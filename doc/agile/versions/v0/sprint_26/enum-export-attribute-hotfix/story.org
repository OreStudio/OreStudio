#+title: Story: Hotfix: a visibility macro on an enum breaks the Windows build
#+description: The workflow definition marks its failure_policy enum with ORES_WORKFLOW_API_EXPORT. The macro is dropped, and a check now fails a pull request that puts a visibility macro on an enum.

* Goal

Every Windows clang-cl job is red at one declaration:

#+begin_src text
projects/ores.workflow/api/include/ores.workflow.api/service/
  workflow_definition.hpp:149:17: error: '__dllimport__' attribute only
  applies to functions, variables, classes, and Objective-C interfaces
  [-Werror,-Wignored-attributes]
#+end_src

The offending line is the enum, not a struct:

#+begin_src cpp
enum class ORES_WORKFLOW_API_EXPORT failure_policy : std::uint8_t {
#+end_src

=ORES_WORKFLOW_API_EXPORT= expands to =BOOST_SYMBOL_IMPORT= or
=BOOST_SYMBOL_EXPORT=, which is =__declspec(dllimport)= or
=__declspec(dllexport)= on the Microsoft ABI, and neither attribute applies
to an enum. clang-cl reports it and =-Werror= makes the report fatal, so the
build stops while compiling a translation unit of =ores.dq.core.lib= that
includes the header. The first template instantiation of the enum does not
matter: the diagnostic is on the declaration, so any unit that includes the
header fails.

The fix drops the macro, because an enum needs no export attribute to cross
a binary boundary. The check that would have caught it before the merge did
not exist: no Linux or macOS compiler reports the defect, and the three
continuous workflows run on a schedule rather than on a pull request, so
Windows -- the only platform that reports it -- saw it at least twelve hours
after the merge. This story adds that check as well.

* Decisions

- The macro is dropped rather than the declaration rewritten. An enum is a
  complete type with no member table to import; the attribute is meaningless
  on it, and every other enum in the estate is declared without one.
- The check reads the macro definitions under =projects/= and keeps those
  whose body is a symbol visibility or DLL storage attribute, instead of
  matching a name that ends in =EXPORT=. The rule it enforces is the one
  the compiler enforces: an attribute that decides symbol storage does not
  belong on an enum. A name-based rule would report a macro that expands to
  something else and miss nothing real.
- The check runs on a new pull-request workflow rather than on a continuous
  one. All three continuous workflows are triggered by a schedule, so a
  check there reports after the merge. The scan needs no toolchain, so it
  costs a checkout and a second on every pull request.
- The declaration keeps a comment saying why it has no macro, because the
  surrounding structs all have one and the absence reads as an omission.

* Out of scope

- A pull-request build on any platform, which is the gate that would have
  caught this without a check at all. The gap is captured as
  [[id:D016B599-5E12-4E51-948C-B17DF0A4FFDF][No per-PR CI job builds or tests C++ outside the codegen paths]], and
  this incident is recorded there as its third instance.
- The =ores.shell.trading= translation unit that exceeds the MSVC limits,
  which is the other known reason a Windows job is red and is unchanged by
  this story.
- A DLL attribute written out at a declaration instead of through a macro,
  which the check does not see.
