* Acceptance

- The pgTAP scan joins the shapes the way the projector reads them, and the suite states
  the scope row-level security gives it, so no reader mistakes it for a cross-tenant check.
- The backfill response carries how many rows the shape refused and how many series fall
  in a family no shape states.
- The counts are asserted in a test, so a guard that refuses silently cannot return.
- A tenant's own identity is held to the shared catalogue, either by the two facts the
  suite and the guard's unit test already establish or directly, if a later task gives the
  fixture tenant an account.

* Plan

Two findings, both measured against the tree at =67803175ce=.

The pgTAP suite joins the shape row on the identity's own tenant:

#+begin_src sql
  join ores_marketdata_series_identity_shapes_tbl st
    on st.tenant_id = i.tenant_id
#+end_src

That described the per-tenant copy the shared catalogue removed. The writer reads
=tenant_id == tid || tenant_id == sys=, so the view is corrected to the same read and
now describes what the code does rather than a copy no tenant holds.

The correction is a latent one, and the record should say so plainly. The suite runs
under row-level security with one tenant in context, so it sees that tenant's identities
and no others: 330 rows of the 3,803 the table holds. The tenant-equal join therefore
could not be observed from inside the suite, and a temporary copy of the file with the
join reverted passes all eight of its assertions. My first reading of this called it a
coverage hole over ninety per cent of the rows; that reading came from a session with
=bypassrls= and it was wrong. What the suite proves is what the session can see, and the
file now says that in its own words.

The cross-tenant property is not lost, it is composed: this suite asserts that a
provisioned tenant reads the system tenant's shapes and holds no copy, and the guard's
unit test asserts that whatever shapes it is given are enforced. Together those say a
tenant's identity is held to the shared catalogue. Writing a tenant's identity in SQL to
prove it directly needs a series row, whose trigger validates an account username, and
the provisioner creates no accounts; that is why the proof is composed rather than
direct, and the price of a direct one is more fixture than the claim is worth.

The second finding stands as first reported. The projector counts what it refuses
(=backfill_result::refused=) and how many series fall in a family no shape states
(=unstated=), and the backfill response carries neither: it reports projected, already
projected and unreadable. A refusal and an unguarded family are what an operator most
needs to see, and today neither leaves the process. The response gains =refused_count=
and =unstated_count= from the model, the handler fills them and says them in its message,
and the projector's backfill counts are asserted by two cases: one series the shape refuses
is counted and left without an identity, and one series in a family no shape states is
projected and counted as unguarded. The refusal is also logged by name, which the field's
comment promised and the code did not do: the exception already names the series, its
family and the field.

* Notes

The join correction is worth keeping even though it changes no assertion: a query that
describes a copy nobody holds is a trap for the next reader, and a system-level check
that runs with elevated rights would read it as the writer does only after the fix.

The suite's scope is now stated where it is used. If a later task wants a tenant's own
identities held to the catalogue in SQL, it needs an account in the fixture tenant first,
which is a seeding question and not a shape question.
