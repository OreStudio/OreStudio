* Goal

Write the architecture as knowledge notes before the code: how ORE Studio relies on an external identity provider, from the door a person chooses, through the provider's own consent, the validated ID token, the link to their ORE account and the registration the deployment's policy grants, to the session that names its method; and how the same layer acts as an authorization server for a client of ORE's API. Each note holds one idea, follows the zettelkasten house style, draws as UML what it describes as a structure or a process, and links into Identity and Access and Delegated Access for LLM Agents rather than repeating them.

* Result

- Six notes: a structure note, ORE as a relying party, the identity link as the
  issuer and subject, a first sign-in registering through the policy, a session
  that names its method, and ORE as an authorization server for its clients.
- Five PlantUML diagrams, rendered to PNG and embedded with a caption and the
  command that made them: the flow, the link's structure, the registration's
  branch, the session's claims, and the consent flow.
- The structure note is linked from the knowledge index and from the Identity and
  Access structure note, so the cluster is reachable from the section it belongs
  to and from the index.
- Every page names the alternatives it rejects — matching an address, a broker
  beside IAM, refusing an unknown subject, holding the provider's tokens as the
  session, a consent with no grant behind it — and cites the standard it applies
  instead of restating it.
