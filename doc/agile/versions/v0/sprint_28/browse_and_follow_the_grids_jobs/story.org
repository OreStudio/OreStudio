* Goal

A person sees the batches, workunits and results that the session may see, as a tree with the details of each record, and can follow one job from its batch to its output.

* Acceptance

- The Jobs tab of the grid screen lists the batches the session may see, newest first, and opens the workunits of a batch and the results of a workunit one page at a time.
- The details of a batch, workunit or result show the entity's own fields under the model's headers, with state and outcome as badges, and the references as links.
- The list filters by status, party and reference on the server, and a failed result is found by its outcome.
- An app version page shows the release note stored with the version, its platforms and packages, and the other versions of its app.
- The person downloads a workunit input or a result output, and the route checks that the caller may read the owning record first.
- A job page states where the job is, the node it ran on, when it ran, and what it produced, and links to the report run behind its batch.
- An operator, a tenant administrator and a party member each see only what their session allows.

* Decisions

- 2026-10-22: The story builds what the journeys Browse the grid's jobs and Follow a job already specify. It adds no screen they do not draw. The reads for batches, workunits and results exist as generated subjects, so the first slice is the BFF route and the screen, not new compute code.
- 2026-10-22: The job page links to a page for the app version, and the page shows a release note stored on the version. The model has no such column, so the story adds one, =release_note=, to =app_version=, not to the package. A release is one engine build and one wrapper build, packaged for several platforms, and one note describes the release. The shell's =compute publish-package= writes the note with the bundle.
- 2026-10-22: The prototypes come before the build. The Jobs tab prototype was compared with the acceptance and redrawn, and the job page and the app version page were drawn. The screens use the model's own field names and add no other term. The glossary defines target redundancy and canonical result.
- 2026-10-22: A live check of the jobs routes found two gaps in the compute service, and each has a task. The batch key is a random identifier, so a list cannot read newest first until the recording time is sortable. The Member role is refused the workunit and result reads, so a party member cannot open a batch.
- 2026-10-22: The recording time is sortable through a model flag, =:sortable_recorded_at: true=. The flag adds the field =recorded_at= to the sortable fields and stores it in =valid_from=. The batch model orders by it, descending, so the Jobs tab reads newest first. The time is that of the current version, so a batch whose status changes moves to the top. The story accepts this order. A creation time would need a column the models do not hold.
- 2026-10-22: The run statistics are not part of this story. They belong to Draw the node heatmap and carry the engine run statistics. The screens show the Run statistics panel when those fields exist, and show no such panel until then.

* Out of scope

- Registering a compute node for a tenant.
- Charts of the grid over time, which the grid screen already carries.
- The report run naming its batch, and a scheduler job instance read by id. The job page links through the batch's =external_ref= until they exist.
