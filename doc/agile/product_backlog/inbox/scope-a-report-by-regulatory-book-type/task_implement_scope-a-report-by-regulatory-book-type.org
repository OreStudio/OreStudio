* Goal

A report that is a regulatory trading book measure reads trading books only, and the system knows it from one vocabulary: the regulatory book type that a book already carries. There is no second enum for the report.

* Acceptance

- A report definition states a regulatory book type, or none for a report that reads any book, and the value comes from the regulatory book type table that books use.
- The scope of a configuration is checked against the report: a book whose regulatory book type differs from the report's is refused, with a message that names the book and the report.
- The seed states the type of the regulatory reports (FRTB SA Capital, Stressed VaR, Headline Position and the other trading book measures) and leaves the valuation and data reports with none.
- The configuration page shows the type and the refusal.
- A test proves that a trading book report scoped to the whole entity reads trading books only, or is refused, as the rule decides.

* Notes

** Done (stage one: the data and the rule)

- =regulatory_book_type= on the report definition and on the catalogue artefact, as a nullable column checked against the regulatory book type table (model =ores.reporting.report_definition=, generated with =compass codegen entity generate=). The publish step copies it.
- The seed types FRTB SA Capital, Stressed VaR and P&L Attribution as =Trading=. The ACME populate scripts and the platform dataset are regenerated.
- The rule follows the precedent of the official report rule. The helper functions are in =reporting_resolve_book_ids_fn_create.sql=. The resolver takes the definition and returns only the books of its type. A typed definition refuses an explicit book of another type at three points: the definition itself, the binding of a configuration to it, and the books of a scope.
- =gather_trades= passes the definition to the resolver and says, when no book is left, that the report reads books of its type only.
- The pgTAP suite =reporting_regulatory_book_type_test.sql= has 16 tests and passes. Four were added in review: a portfolio of banking books only, a definition that cannot be found, and an omitted definition. With the guard removed from the resolver, the test for a missing definition fails. With the type filter removed from the portfolio branch, three tests fail. The official report suites and the publish suite still pass. The reporting C++ suites pass.

** Done (stage two: the screens)

- The wire schema, the BFF and the client carry =regulatory_book_type=. The edit form offers it as an optional choice, with the codes the server holds. An account that may not read reference data gets no codes, and the form then offers none.
- A save cannot blank the type. The BFF rebuilds the write from the read, so an edit that states no type keeps the one the report holds, and an edit that states null clears it. Three BFF tests cover keep, write and clear.
- The report page shows the type in words and explains what the report reads. An empty type reads as "every type".
- The configuration page tags each report that binds it with its type.
- The English, French and Portuguese words are added. The suites pass: 1,776 web tests and 837 BFF tests, and the typecheck is clean.

** Review of the pull request

- The model of =risk_report_config= did not hold the hand-written repository changes that this PR made to the generated files: =resolve_book_ids= with the definition, and =regulatory_book_type_of=. The drift gate would have failed on main after the merge, as it did for marketdata. The model now holds both, and the regenerated files differ from the committed ones in formatting only.
- The binding trigger of =report_configuration= is regenerated from the model, not edited in the SQL.
- The environment field named =bright_faraday=. That environment works on another branch now, and nothing of this task was in its tree, so it moved to =brave_hopper=.

** Not done

- No browser check of the new field. The tests render the components with canned data, and the running web build was not rebuilt.
- The refusal shows as the server states it: the id of the definition and no names. The story asked for the names of the book and the report. The words come from the database trigger.
- A run in which every trade fails to build still completes. That is issue 8 of the end to end run, and it hid the cause in this check: the engine could not build the HKD curve, built no trade and wrote no =npv.csv=, and the run said it completed.
