* Goal

A person configures the public sources, and the key of each, on the setup steps
screen. The screen asks for the sources the environment hosts and for the
credential of each one; a field is filled in from the deployment environment
when the variable is there. What the person saves goes to the database as a
tenant secret. The official rates adapter then starts from the stored sources,
so no deployment passes a source list on a command line and no key has to stay
in a file.

The step is the public sources step of the first run
(=projects/ores.web/packages/web/src/journeys/PublicSourcesStep.tsx=), which
today decides only the terms of each publisher.

* Acceptance

- The public sources step asks for the credential of each provider whose row in
  the catalogue names one: a single key, or a user and a password, as the row's
  =credential_ref= states.
- Each field is filled in from the environment of the service when the variable
  the row names is set there, and is saved as a tenant secret when the person
  continues.
- A stored secret is never sent to the browser: a field shows that a value is
  stored and asks for a new one only when the person replaces it.
- A value filled in from the environment reaches the browser once, in a response
  the browser neither caches nor a log records.
- A stored secret is protected at rest by a key that is not in the database, and
  the tenant boundary is enforced where the value is read, as on any tenant row.
- The adapter starts on the providers the tenant accepted and holds a credential
  for, with no =--source= argument and no key in its environment.
- A provider whose key is missing is named on the step and in the adapter's log,
  with the variable that would have supplied it.
- =no-committed-credentials= stays green: no key reaches a file that git tracks.

* Decisions

- *The database holds the secret, the environment only seeds it.* A key in the
  deployment environment cannot be changed without a deploy, and it sits in a
  file on the host. The step copies it once into a tenant secret; from then on
  the row in the catalogue names the stored secret and the environment needs
  nothing.
- *The provider row stays the one place a source is described.* =credential_ref=
  already names the variable a key lives in. It gains a second form that names a
  stored secret, so the field the step draws, the variable it prefills from and
  the secret the adapter resolves all come from the same row.
- *A source is hosted because the tenant accepted it, not because a deploy said
  so.* The adapter reads the providers whose terms the tenant accepted, which is
  the same decision the step already records, so =--source= has nothing left to
  say.
- *Prefilling sends the value to the browser once.* A field filled from the
  environment carries a secret the person did not type. That is acceptable
  because the step is reachable only by an environment administrator and only
  while no secret is stored; a stored secret is never sent back.
- *The setup steps screen owns configuration, not the shell.* The alternative,
  a =setup-rerun= argument per step, keeps the list in a person's memory and in
  a shell history, which is how the list arrived by hand on 2026-11-17.

* Out of scope

- Rotating a stored secret, and recording who read it.
- The derived sources, whose credentials the catalogue seeds already carry.
