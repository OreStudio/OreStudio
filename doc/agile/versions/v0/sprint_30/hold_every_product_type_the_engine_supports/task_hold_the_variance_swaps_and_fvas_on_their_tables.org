* Acceptance

- each of the four types routes to a table of its own (one table may serve an equity
  and an fx pair that state the same element), whose columns hold every scalar term the
  element states; lists, baskets and schedules are rows of child tables or of
  the shared rows (options, barriers, underlyings, schedules)
- the projection reads and writes the element from those rows, value for value,
  and a round-trip test reads ORE's or the user guide's example and writes it back
- the builder states the rows, and the generator books the element form
- the class-read entry for the type is removed: the scripted instrument table
  holds no element form of it, only the generic ScriptedTrade form where ORE's
  library carries one
- the catalogue names both forms of the type where ORE carries both
- the ORE engine test reads and builds each, with no error of the trade kind
- every fact the element states is a column or a row: nothing is held as text

* Plan

Follow the basket and rainbow task: one table per element per family, because
the equity family holds one variant row and the FX family one vector per
product.

- =equity_basket_variance_swap_instrument= and
  =fx_basket_variance_swap_instrument= hold LongShort, Strike, Notional,
  SquaredPayoff, Cap, Floor, SettlementDate and Currency. The members are the
  shared underlying rows under the role =underlying=, and the ValuationSchedule
  is a shared schedule row under the role =valuation_schedule=, as the
  commodity and pairwise variance swaps keep it.
- =equity_forward_volatility_agreement_instrument= and
  =fx_forward_volatility_agreement_instrument= hold every scalar the element
  states, the optional ones as nullable columns. The underlying is a shared
  underlying row.
- One header, =volatility_product_projection.hpp=, reads and writes the
  scalars for both families; the family projections add the shared rows.
- Four builders in =volatility_product_builders.hpp= replace the two scripted
  templates and return the family's rows. The planner books through them.
- The catalogue routes the four types to the new tables and names the library
  scripts =BasketVarianceSwap= and =ForwardVolatilityAgreement= as their
  scripted forms. The class-read entries are removed.

* Result

The four types are held natively, each on a table of its own:
=equity_basket_var_swap_instruments=, =fx_basket_variance_swap_instruments=,
=equity_fva_instruments= and =fx_fva_instruments=. The scalars are columns;
the FVA's implied volatility strike and quantity are doubles, as the model
rule for continuous quantities requires. The basket members and the FVA
underlying are underlying rows, and the basket's valuation schedule is a
schedule row. The projection reads and writes them, and the round-trip test
covers the user guide's FX basket variance swap and FVA plus an equity trade of
each that states every optional term. The builders state the rows and the
generator books them. The class-read entries are removed, and the catalogue
names the scripted forms =BasketVarianceSwap= and =ForwardVolatilityAgreement=.

Three table names were too long for the identifier budget. The codegen shortened
the SQL tables but the C++ entities kept the full names, so the repository
queried tables that did not exist. The codegen now refuses such a
=:tablename:=, and the three tables have short names.
