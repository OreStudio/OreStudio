* Plan

The work is a cross-cutting structural change, so it ran as a designed playbook rather
than a narrow refactor. The steps below are the historical record.

**Grounding.** Four parallel explorers mapped the persisted config model, the
simulate/preview path, the callers and permissions, and the factory and vintage seam.
The two integration suites are the behaviour contract; they were run green before
anything moved. The dev database was rebuilt from current SQL first, because main's SQL
had moved past the running database and the fresh test binary refused to start on the
fingerprint mismatch.

**One-way-door design.** The registry shape is the seam every future asset class
registers through, so three candidate designs were built in parallel and scored by an
independent cross-judge. The deciding constraints were two repo conventions:
=polymorphic_types_over_nats.org= fixes one NATS subject per concrete type, which rules
out merging the two simulate requests into one variant payload, and
=feed_factory_and_kind_seam.org= pins =feed_factory= as the one construction dispatch
point, which rules out folding it into the registry. The chosen design keeps both, and
registers a per-kind vintage anchor coordinate that one shared check reads, instead of a
second per-kind copy of the paging rule.

**Two registration points stay.** The factory builder and the control-plane entry are
registered separately, because the factory's own test pins =make_default_feed_factory()=.
=register_kind= throws at startup when the factory has no builder for the kind, so the
two cannot drift.

**Migration.** New registry first, wired to nothing; then one verb at a time, each
ending green against the pin. The vintage wire field is changed in the model and
regenerated, never by hand. =feed_controller::validate= and its private vintage helper
become caller-less and are deleted in the same wave, per the one-pipeline rule.

**Verification.** The two integration suites unchanged; the new stub-kind dispatch test
without a database; the grep predicate for per-kind literals; a before-and-after line
count; and the component drift and link-structure gates.

* Notes

Follow-ups found while grounding this task, deliberately left out of it:

- =ir_curve_preview_handler::preview_shape= builds its reference-data context
  from a hardcoded =RATES_SPOT_FORWARD= convention, while every feed path
  derives the convention from the config's qualifier. An FOMC-grid config
  therefore previews under the wrong grid. A live divergence between preview
  and run.
- The boot auto-start walk reads the IR process-parameter definitions
  catalogue without the system-tenant context the two handlers use, so on a
  real tenant it may read nothing.
- The shell keeps its own client-side FX-then-IR probe when it resolves a feed
  by id or name, so a third kind stays invisible to =synthetic= name
  resolution even though the server registry now dispatches it.
- The two generation-config entities still duplicate nineteen plumbing fields.
  Collapsing them needs a codegen model and a schema change, which this task
  put out of scope.
- =feed_kind_registry::targets()= drops a config whose container is not
  visible, so the folder cascade no longer counts it as skipped. The
  =config_id= foreign key makes this reachable only under row-level security,
  where the config is invisible anyway.

* Result

The control plane now asks one per-kind registry instead of re-deriving each
asset class's facts in every verb. A kind registers once, in
=make_default_feed_kind_registry()=, and that one entry carries its factory
kind, its config read permission, a loader over its own config rows, a lazy
resolver from a config row to a =feed_build_input=, its vintage anchor, and its
simulate decode and reply pair. =feed_factory= stays the one
producer-construction dispatch point; =register_kind= refuses a kind the
factory cannot build, so the two registrations cannot drift.

The verb bodies became registry code. The startability gate, the child load and
the factory call exist once, in =make_feed=; start, the folder cascade and the
boot walk keep only their own outcome handling. The permission gate that spans
kinds is derived from the registrations, so it holds for every registered kind
by construction. The vintage entry is keyed by config id and tagged with its
kind, so an IR curve config finally has a validity entry; that field change went
through the model and its generated C++ and TypeScript, not through a
hand-edited header. The two simulate subjects and their typed payloads stay,
per the one-subject-per-concrete-type rule; only the server-side envelope is
shared, so simulate has no client impact. =feed_controller::validate= and its
private vintage helper lost their last caller and are deleted.

Verification. The two integration suites pass with every assertion unchanged —
the test fixtures changed only to pass the registry into the handler
constructors. The new =feed_kind_registry_tests.cpp= registers a stub kind and
drives the real handlers, proving that start, stop, list, the folder cascade,
the boot selection, vintage validity and the simulate envelope all reach the
stub with no handler edit; it needs no database. The grep for per-kind
permission literals, =ores.synthetic.core= repository includes, kind constants
and per-kind loops over the six control-plane files returns nothing. The six
files fell from 1883 to 1165 lines while the registry adds 858.

Behaviour changes, all intended and stated: kind resolution follows the
registry's sorted kind order rather than a hand-written repository probe (the
same winner, now stated); an IR config gains a vintage entry; the vintage verb's
gate widens to the same all-kinds gate as list and the cascade; one unified
catch replaces the per-kind start-failure messages; and the folder response
keys are registry-derived. Two out-of-scope defects found during grounding are
recorded in Notes rather than fixed here.
