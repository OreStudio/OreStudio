* Goal

We do not know how far ORE Studio's entities are from "regular": an up-to-date
codegen model, fully current generated code, and any manual code confined to
paste blocks. Several attempts to answer this already exist, independently,
and none is trustworthy on its own:

- [[id:A3F8C2D1-7E4B-4F9A-B2C5-8D1E6A3F0B7C][Entity Coverage Matrix]] — hand-maintained Y/N per layer per entity; covers
  only 6 of ~20 components; stale since 2026-05-29.
- [[id:897A7156-504D-4581-AD4C-026D643C0838][Domain entity evaluation checklist]] — a strong 12-layer criteria list, but a
  manual checklist with no automation and no legacy/drift signal.
- [[id:8B02B617-2BF0-40A3-80F9-523D6D8B80C6][Entity Catalogue]] — hand-maintained navigation index, mostly unfilled.
- 14 ad hoc "Fix =<component>= entity model drift" tasks in
  [[id:A083FE26-521D-4046-9E58-AFB901B28809][Codegen developer experience improvements]] — scope is guessed per component,
  not measured.
- The dormant backlog story [[id:058DF966-13E0-4D97-9A8B-F22301411015][Entity evaluation skill and runbook]] (sprint 19,
  never built) proposed exactly this kind of tool and was never picked up.
- Task [[id:836BB4CE-0E1F-4ADD-B8B9-A7AA81753AF9][Fix legacy Primary key heading blocking codegen regen on 70+ models]] found
  one concrete legacy-model symptom that generalises the same question.

This story reconciles all of the above into a single, unified, *automated*
way of measuring drift: one tool that walks every codegen entity model and
every generated/hand-crafted artefact across every component, classifies
each entity along an agreed set of dimensions, and produces a quantified
report of what remains to make every entity "regular". The report is the
deliverable of this story; the accuracy of its measurements must be
verified before any remediation work is multi-tasked off the back of it —
fixing entities is explicitly out of scope here.

*Phased rollout*: prove the approach on one pilot component first
(=ores.refdata= — largest, most varied entity population, and the component
where the legacy primary-key-heading symptom was found) before running it
across the other ~19 components. The pilot validates the dimensions and the
tool's accuracy cheaply; only once it is trusted on refdata does it get
pointed at everything else.

** Candidate classification dimensions

To be confirmed/refined during the work, seeded from the checklist above:

- Component (=ores.refdata=, =ores.iam=, =ores.dq=, ... — all components,
  not just the 6 the old matrix covers)
- Tenancy scope (per-tenant / per-party / per-workspace / global)
- Meta-type (domain entity vs auxiliary/lookup type)
- Model format / legacy status (current =domain_entity= convention vs
  legacy =lookup_entity= vs legacy top-level =Primary key= heading vs no
  model at all)
- Per-layer coverage (SQL, C++ domain, repository, service, messaging/JSON
  IO, Qt, HTTP, CLI, Shell, Wt, manual chapter)
- Codegen regen drift (does regenerating the model reproduce the checked-in
  files byte-for-byte, or has the template moved on since last regen)
- Hand-crafted vs paste-block discipline (are manual customisations captured
  via paste markers, or raw edits to generated files that a regen would
  clobber)
- Compound vs single natural/primary key
- Variability knob presence
- Per-layer test coverage

* Acceptance

- An automated tool exists (compass command or script) that walks every
  codegen entity model and its generated/hand-crafted artefacts across every
  component and computes the classification, with no hand-maintained table.
- The classification dimensions are settled (see above) and documented.
- The tool's output is spot-checked against known-good and known-bad entities
  (e.g. =currency= as the reference specimen; the 16 primary-key-heading
  entities as known-legacy) until we are confident it measures drift
  accurately.
- A quantified report is produced: totals and per-component breakdowns of how
  many entities are "regular" vs not, and why not.
- The tool and dimensions are proven on the =ores.refdata= pilot before being
  run across the remaining components; the pilot report is reviewed and
  trusted before rollout continues.
- =entity_coverage_matrix.org=, =entity_evaluation_checklist.org=, and
  =entity_catalogue.org= are used as inputs (their criteria and known data
  points feed the tool/dimensions) and then deleted — they do not survive
  this story; the automated report is the sole source of truth going forward.
- The 14 ad hoc per-component drift tasks are re-scoped (or closed/replaced)
  using real data from the report instead of guesses.
- Fixing/regenerating entities is out of scope — this story only measures and
  reports.
