* Result

A static check now applies the server's own two rules to every declaration it can
read: every durably consumed subject is covered by exactly one stream filter, and
no two differently named streams overlap. It reads the three declaration shapes
the transport offers, resolves subjects through constants, and fails closed on a
shape it does not recognise or on a new transport call, so silence is only ever
possible for a file it never sees.

Shown failing before being accepted. A raw durable subscribe on an uncovered
subject produced "durable subject with no stream", naming the site and explaining
the five second timeout. A second stream over an existing filter produced "stream
subject overlap", naming both streams and both sites and the server error the
second would hit. Both reverts restored the tree to green.

On the tree it reports 19 streams, 17 durable consumers and 87 subjects, and the
stream count matches the number independently recorded when the streams were
investigated, which is evidence the extraction is faithful rather than merely
self-consistent.

The honest limit, stated rather than papered over: a stale stream already on the
broker cannot be seen statically. That was the actual cause of the overlap that
stopped IAM starting, and only the owning service's ensure_stream catches it, as a
fatal start. A service calling the cnats API directly is likewise outside the
check's reach.
