** The ABI mismatch with our toolchain

The project builds every vcpkg package with the default =x64-linux= triplet,
which uses GCC 16, and compiles our own code with clang 21. libpqxx 8 uses C++20
constrained templates in its headers. clang 21 and GCC 16 mangle a constrained
template parameter in different ways, so the probe failed to link:
=pqxx::internal::to_string_float<double>= has a =TkSt14floating_point= tag in
clang's name and none in the library. =-fclang-abi-compat=17= removes the
mismatch, but that flag changes the ABI of the whole project. The correct fix
is a triplet that builds libpqxx with clang. sqlgen and reflect-cpp do not have
this problem, because they are header-only.

** What the numbers mean

The one-round-trip cost (about 60 µs on localhost) controls every path that
sends one statement at a time. libpqxx's =pipeline= saves about 40% of it.
libpq pipeline mode saves 85–90%, because the server receives the next
prepared statement while it executes the current one. Bulk writes go through
COPY at about 1.3 µs per row, so COPY stays the path for tick ingest.

** The gaps a thin layer of our own fills

- Pipeline mode: release the =PGconn=, run =PQenterPipelineMode= with prepared
  statements, and seize it back. Or build the layer on libpq directly.
- Binary results and binary parameters for hot paths, if the repository
  comparison shows that text parsing costs enough to matter.
- Binary COPY, if the text format becomes the limit for tick ingest.

* Result

libpqxx 8 meets the data path's needs for prepared statements, transactions,
text COPY, LISTEN and NOTIFY, and SQLSTATE error classes. It does not support
libpq pipeline mode, binary results, or binary parameters other than =bytea=.
Pipeline mode is the gap that matters. On localhost it is 6–9 times faster than
one round trip per statement, and libpqxx's own =pipeline= does not come near
it. Adopting libpqxx also needs a clang triplet, because of the ABI mismatch.
The repository comparison decides whether libpqxx plus a thin pipeline layer,
or a thin layer on libpq alone, is the better base.
