* Summary

This prototype argues how a person changes the analytics a report runs, and it
answers to
[[file:../../knowledge/journeys/reporting/journey_change_what_a_report_runs.org][Change
what a report runs]]. The shape is decided. The screen is a wizard of three steps
titled =What this report runs=, and adding an analytic is a flow of its own with
three screens. The three variants behind =?variant=A|B|C= are three readings of
the add-analytic detail screen, which is the novel part; the wizard and the
switchboard are identical across them.

It is throwaway. It reads no service, and the page states which parts of the
change it cannot show, which rules the server does not enforce, and which
editors are deferred.

* Detail

** The wizard's three steps

1. *The definition and the configurations it binds.* The definition's name, type
   and party, then the five configuration types with what each supplies and a
   link to the screen that holds its data. Only conventions has a screen today:
   =PATHS.conventions=, =/refdata/conventions=. The other four are stated as
   missing, never drawn as working. The step also names the other definitions
   bound to the shared configuration, because the analytics belong to it and not
   to the definition that was opened.
2. *The analytics.* The switchboard: every analytic type, one row each, with the
   on/off control, the display order and the parameters summarised. This is the
   agreed switchboard and its shape is unchanged.
3. *Review and save.* What the change reaches and does not reach, that past runs
   keep their configuration, that a run either side of the change is not
   comparable, and the exact write before it is sent.

The wizard is deep-linked with =?step=1|2|3=. Step is part of every URL the page
writes, so a person who cancels a flow and reloads lands back on the switchboard.

** The add-analytic flow

Configuring an analytic inline in the switchboard is too busy, so the switchboard
carries an =Add analytic= action, and every row carries a =Settings= action that
opens the same flow for an analytic that already exists. The flow has three
screens:

- *The list.* The fourteen analytic types, each with a one-line statement of what
  it produces, and each marked as on, off, or with no row. Choose one, and nothing
  is written.
- *The detail.* What the analytic is, how it is calculated in plain words, and
  every parameter it takes with a helpful control, a note on what it means, and
  what a normal value is. The control follows the parameter's shape: a number
  field for a count or a size, a select for an enumeration, a toggle for a
  boolean, and a text field for a name.
- *The effect.* What turning it on does, what it reaches, what will be written,
  and any incompatibility it creates. The step is refused when the set cannot run.

The fixture carries settings for all fourteen types. =sensitivity=, =simulation=
and =pfe= carry the ones the journey names, and eleven more types carry at least
two settings each, so almost every choice on the list opens a screen with
something to set.

Switch the reading of the detail screen with the bar, or with =?variant=, and
open one flow screen directly with =?screen=list|detail|effect&analytic=<code>=.

** The three variants read the detail screen

| Variant | Name | The structural argument |
|---------+------+-------------------------|
| =A= | Document | The explanation as a short readable page, the parameters below it in a single column, each with its control and its note. |
| =B= | Two columns | Explanation and calculation on the left, parameters and the effect on the right, so a person reads and sets at once. |
| =C= | Guided | One parameter at a time with the explanation beside it, advancing through the settings, with a summary at the end. |

The page opens the flow on =xva=, which has five settings of four different
shapes, so the comparison is between layouts of the same content rather than
between different analytics.

** The toggle writes =active=, and never deletes

The page exists because turning an analytic off is a write of =active = false=.
The row keeps its =display_order= and its =configuration_analytic_parameter=
rows, and reads as off, so the history shows the report used to produce it. A
type the configuration never carried reads as "no row" and has no switch: adding
it is the add-analytic flow, which sets its parameters and then writes the row.
**No control on the page removes a row.**

** The incompatibility is a state, not a sentence**

=pfe= reads a cube that =simulation= writes, so =pfe= on without =simulation=
cannot work. The page shows that three ways rather than stating it once in prose.
The pair is marked on the switchboard, in red, with a tag on each side naming what
is broken. The add-analytic effect screen refuses the step and offers to turn
=simulation= on as well. And the rule is named beside both, with the honest note
that it lives in the ACME seeder, in =generate_risk_config_data.py=, function
=check_exposure_needs_simulation=, and in no service: the write would be
accepted and the run would fail later. As a fixture the page opens with =pfe=
staged on and =simulation= staged off, so the refusal is on screen rather than two
clicks away.

** What is deferred**

=simulation= and =pfe= need purpose-built editors for the cube, the shift and the
time grid. The page draws those settings as plain fields for now, =time_grid= as
a select and =exposure_cube= as a text field, and it says on the parameter that
the purpose-built editor is a later task. A plain field is not the design, and the
page does not pretend it is.

** What the change reaches, and what it does not**

A run keeps the configuration it ran with, with its outputs and its errors. The
configuration is shared, so the change reaches every definition bound to it,
including the three the person did not open. Nothing on the page writes the
definition's schedule, its processing phases, its concurrency policy or its other
four configurations.

** The runs that stop being comparable**

The results screen compares a run with a previous run of the same definition. A
run made after the change did not produce the same measures, so the comparison
between it and an older run is not a comparison, and step 3 says that plainly. It
places each run by its own start time against the definition's version history and
marks the placement an inference, because **no operation says which configuration
version a run used** and the analytics are not on the definition. The results
screen marks a comparison partial where a side carried errors; it cannot mark this
case at all.

** What is fake**

The definition, the five bindings, the eight analytic rows, the parameters, the
runs, the versions and the clock are fixtures. Nothing reads a server, the page
sends nothing, and the write is applied to the page's own array. The rules are
not fixtures: =active = false= is how the model turns an analytic off, and =pfe=
without =simulation= is a rule the seeder enforces and no service does. The link
on step 1 points at the application route =/refdata/conventions= and does not
resolve from =file://=; it is drawn because the route is real.

** Where the code lives**

=doc/prototypes/reporting/change-what-a-report-runs/=. Three files, plain HTML,
CSS and JavaScript, no framework and no build step.

** The verdict**

None yet. This page is on the branch that proposes it and waits for review.

** What it does not settle**

Which runs a change reached. Until an operation names the configuration version
behind a run, every placement on this page is an inference, and a build can only
repeat that inference. The parameter's allowed values are unsettled too: no
operation in the journey's set reads the value domain, so the page draws a select
only where its fixture knows the enumeration and a text field where it does not.
And the four configuration types without a screen are unsettled in the plain
sense: nothing shows them, so step 1 can only say where the data lives.
