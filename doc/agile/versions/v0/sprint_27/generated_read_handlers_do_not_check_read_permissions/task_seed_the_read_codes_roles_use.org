* Notes

Member's codes come from what the member screens read, traced on
2026-10-06: the reference data record routes (=REFDATA_RECORDS= in
=wire-protocol/src/records.ts=, 15 resources), the classification lists
(=wire-protocol/src/classifications.ts=, 28 lookups), and the furniture every
screen uses: badge definitions and mappings, change reasons, images and
feature flags. 48 codes. All are vocabulary or screen furniture; none names a
firm or a person except =assets::images:read=, which serves colleagues'
pictures and is in Member on purpose, as a workplace directory shows them.

=refdata::calendar_dates:read= is not seeded: the entity is read-only, so no
write code was ever defined, and nothing checked a read. It must be seeded
before the default guards it.

* Result

Member exists, with 48 explicit codes traced from what the member screens
read, and a trigger gives it to every person account when its first version
is written; a service account gets nothing, and Member taken away is not given
back. Three database tests prove the three cases. All 59 person accounts in
Acme hold it after a fresh provisioning (=evidence/who_holds_member.sql=).

134 read codes are seeded that no seed defined, each beside its write code
where it has one. The service roles are granted the reads they make on other
components, traced from the protocol headers each component includes: IAM
provisioning, the marketdata import, ORE, and reporting's template list.
Provisioning a tenant ran all seven steps under the guards.

Through the BFF, =ashley.moore= reads 51 of the 53 member routes
(=evidence/member_screens.py=). The two that answer 403, her sessions and her
picture, were guarded before this story and are captured as missing self
reads.

Support's description promises read access to everything, but it holds five
codes and Member; widening it is a product decision and is left open.
