#+description: ORE's script library as a world dataset of the system tenant, the methodology by which it is derived from ORE's distribution, the scripts a tenant publishes beside it, and the versions both give rise to.

* Summary

ORE's library of payoff scripts is reference data that ORE Studio adopts from an
external source, and the classification of reference data therefore places it
at the world level ([[id:7287B58F-964C-4D42-8EC4-6C5DA53EEE2D][Reference data classification by publication level]]). It
arrives as a dataset: a methodology derives staged rows from ORE's distribution
at a recorded commit, and the =world= bundle publishes them into the system
tenant, from which every tenant reads them. The rows are those of each script,
each of its variants (a variant serving a purpose such as =FD= or =AMC=), and its
inputs, results and calibrations ([[id:833F8F79-7FF0-42B0-8C52-E3ED6596843E][ores.trading.script]],
[[id:A2BE6361-0489-4A63-A1B7-6B07BB3F6000][ores.trading.script_variant]], [[id:F08D458F-B694-4B2F-A945-E22544A9222F][ores.trading.script_input]]). A tenant's own scripts
are rows of that tenant, written by the trading service when the tenant
publishes them. Every change to a script, from either source, constitutes a
version, and since a trade records the version on which it was booked
([[id:358CC548-3892-45A1-A916-DF4A48ADED03][Library and Inline Scripts in Scripted Trades]]), no change to the library
silently alters the valuation of a booked trade.

* Detail

** The library as a world dataset

The dataset belongs to the Open Source Risk Engine catalogue that
=external/ore/manifest.json= declares, and its provenance is recorded as for any
other dataset: the source is ORE's =scriptlibrary.xml= at the commit of ORE that
the repository carries, and the methodology states each step by which the staged
rows are derived from it. Each script is staged in the artefact table of the
entity that holds it, generated from that entity's model, and the trading
service's publish function writes the staged rows into the system tenant
([[id:F19A6B98-1CAD-4206-913B-A4EAAED2DEAF][From an entity model to a published row]]). The dataset is a member of the
=world= bundle, which the bring-up publishes, so that the library is present
before any tenant exists and no tenant holds a copy of it.

** The methodology

The methodology derives the staged rows in four steps, and the dataset's
generator performs them in order.

1. *Extraction.* Every script of ORE's =scriptlibrary.xml= is read, with its
   variants, results and calibrations, as ORE distributes it.
2. *Correction.* Where ORE distributes a script that ORE itself cannot execute,
   the methodology applies a correction to its text. A correction applies only
   when its text occurs exactly once, has no effect once the code already
   contains its replacement, and otherwise causes the generation to fail, so that
   any change ORE makes to the script is reviewed. The corrections comprise a
   missing semicolon in =WorstOfBasketSwap= and the =FD= variant of
   =GenericBarrierOption=, which rolled its values back only as far as the first
   monitoring date. Each is stated in the methodology, and the dataset therefore
   records that its scripts differ from ORE's and where.
3. *Parsing.* Every script is parsed with ORE's grammar
   ([[id:8FD7BD95-AAEC-4CF9-A9F4-D609A9DEFBD8][Script Parsing with ORE's Grammar]]) by the shell's =script check= command, and a
   script that fails to parse causes the generation to fail with the diagnostic
   that names its line and column ([[id:ECA442BB-48D7-47CB-9BAA-97FD1C0BBA9A][Diagnostic Reporting in Script Validation]]).
4. *Derivation of inputs.* The inputs of every script are derived from its syntax
   tree by the shell's =script inputs= command
   ([[id:92449D70-09E2-4391-B716-A1001F22B271][Derivation of Script Inputs from Free Variables]]), and for a script with several
   variants they are the merge of the variants' inputs. The inputs are not mined
   from the text by any other means.

Parsing and derivation are performed by the generator and not by the publish
function, because the bring-up publishes the =world= bundle in SQL before any
service runs. The staged rows are generated and committed, and are never edited
by hand; a check verifies that they are what the generator makes of ORE's
distribution, and a test of the scripting component verifies that the staged
inputs of every script equal those its parser derives.

** Versions of the library

A version of a script arises in one of two ways.

- *A new release of ORE.* When the repository adopts a new commit of ORE, the
  generator is run again and the dataset republished. The publish function
  writes a new version of every script whose staged rows differ from the
  published ones and leaves the others unchanged.
- *A tenant's publication.* A tenant publishes a script of its own through the
  trading service ([[id:3085E65E-413B-4E7A-B60A-5844A124C999][The Product Booking API]]), which parses it, derives its inputs
  and writes it as a version in the tenant, refusing a script that fails to
  parse with the same diagnostics. Where a tenant's script and a script of the
  world library share a name, the tenant's own script is the one its bookings
  resolve the name to. The trading service reports a warning when a tenant
  publishes a name the world library holds, and a later release of ORE that adds
  a name a tenant already uses leaves that tenant's script in force; no
  constraint forbids the pair, since the two rows lie in different tenants.

** Delivery to the engine

A scripted trade records its script by its name, the tenant that holds it and
the version on which it was booked, or states its script inline together with a
hash of the text. A script of the world library is held by the system tenant, and
the run reads it there through the shared-reference read by which every tenant
reads world rows, so that the recorded version resolves to one row whichever
tenant holds the trade. Each run writes the
library from the stored versions that its trades name, so that a script absent
from the store causes the failure of any run that requires it, and the engine
reads the stored versions rather than the copy distributed with ORE
([[id:708554F7-FA3A-49E1-8A11-4AE968C76758][Script Execution and Compilation in ORE]]).
