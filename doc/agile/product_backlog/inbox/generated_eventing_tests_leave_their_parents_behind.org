This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Make the generated eventing tests remove the parent rows they seed to satisfy a
child's soft foreign key, so a run leaves the system tenant as it found it.

* Why

Forty-eight of the 187 generated =*_eventing_integration_tests.cpp= files seed a
parent and then delete only their own row. The parent is system-tenant reference
data, so =scoped_database_helper='s per-tenant isolation does not reach it: every
run leaves one active row behind, forever, in the catalogue the deployment
reads.

That residue used to break the suite on its second run, because the synthetic
parent code came from a process-static counter and repeated; the seed profile's
code is unique per deployment now, so nothing collides and the defect is benign.
It is still wrong: a test that writes to a shared catalogue should remove what it
wrote, and the deletion is the same shape for every one of the forty-eight
because they all come from
=projects/ores.codegen/library/templates/cpp_nats_integration_test.cpp.mustache=.
