* Summary

Export runs the import backwards, with one difference.

1. *The read* loads the rows for a configuration.
2. *The reverse*, =projection::reverse=, builds the typed record from the rows.
3. *The write*, =projection::write=, emits the XML.

The difference is the rendering. A document that said =F= is stored as
=Following=, so the export states =Following=. That is deliberate: the store
keeps one form, and the exported document is one ORE reads back.

#+begin_src plantuml :file rows_become_an_ore_document_on_the_way_out.png
@startuml
participant "Caller" as caller
database "Table" as db
participant "Projection\n(reverse)" as reverse
participant "Projection\n(write)" as write

caller -> db : read the configuration's rows
db --> reverse : rows
reverse -> reverse : rows -> record
reverse --> write : record, stored codes
write -> write : emit elements
write --> caller : ore.xml
@enduml
#+end_src

A round trip therefore preserves everything except the rendering of a value
that has more than one. The database test says so where it compares the
document the store received with the document it hands back.
