* Acceptance

- ores_iam_create_initial_admin_fn refuses unless the deployment is in bootstrap mode, under a lock that makes the check and the create one step.
- A test runs two creates at once and proves exactly one succeeds.
- A failed create answers fixed words for each known failure and logs the detail, never answering an exception's text.
- The local gate is green.

* Plan

Found on 2026-11-11 in the review of the C++ bootstrap routes (PR 4603). The
BFF, the C++ route and the IAM handler each check bootstrap mode before the
create, and each check is a separate step, so none closes the window.
=ores_iam_create_initial_admin_fn= checks only the tenant context and the
inputs.

- The function takes a transaction-scoped advisory lock, reads the bootstrap
  flag, and raises unless the deployment is in bootstrap mode. It already
  clears the flag in the same transaction, so a second create waits for the
  first and then sees the flag cleared.
- The handler maps the function's refusals to fixed words: not in bootstrap
  mode, and each input rule. Any other failure answers that the administrator
  could not be created, and the log keeps the detail.
- The handler reads the SQLSTATE from =store_error=. The query helpers in
  =bitemporal_operations= threw a plain =runtime_error= and dropped it, so they
  now throw =store_error= with the server's SQLSTATE. It derives from
  =runtime_error=, and no caller of these helpers retries, so callers are
  unchanged.

the deployment is in bootstrap mode, so the check and the create are one step
