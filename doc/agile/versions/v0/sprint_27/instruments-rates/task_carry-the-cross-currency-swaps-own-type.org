* Goal

A cross-currency swap keeps its own product type through the import and the
export. Today the importer stores it as =Swap= and the exporter writes it back
as =SwapData=, so the two products are one on the wire and in the store, and a
cross-currency swap is indistinguishable from a plain swap after a round trip.

* Acceptance

- The importer stores =trade_type_code = "CrossCurrencySwap"= for a trade the
  document states as =CrossCurrencySwapData=, and =Swap= for =SwapData=.
- The exporter emits =CrossCurrencySwapData= and =TradeType
  CrossCurrencySwap= for a row whose type is =CrossCurrencySwap=, and
  =SwapData= and =Swap= otherwise.
- A document carrying one of each round trips with the two products still
  apart.

* Plan

1. The schema gives the two products an element each, =SwapData= and
   =CrossCurrencySwapData=, and both elements are the same XSD type
   (=swapData=). Which element the document used is therefore the only
   statement of the product type, and nothing else can recover it. The forward
   mapper reads whichever element is present and states the matching code.
2. The reverse mapper reads that code back and writes the element the code
   names. It takes the code from the row it was handed rather than from a
   parameter, so the exporter's existing dispatch — which already routes both
   codes to =reverse_swap= — needs no change.
3. The example document =IRFX_Cross_Currency_Swap_non_rebalancing.xml= carries
   one plain swap and one cross-currency swap, which makes it the test: the
   two must stay apart through the import, the batch and the export.

* Notes

- The schema gives the two products an element each of the same XSD type
  (=swapData=), so the element the document used is the only statement of the
  product type and nothing downstream can recover it. That is why the fix is
  in the mapper's two directions and not in the table.
- The reverse mapper reads the code from the row it was handed rather than
  from a parameter, so the exporter's dispatch, which already routes both
  =Swap= and =CrossCurrencySwap= to =reverse_swap=, needed no change.
- The example document was chosen because it carries one of each product, so
  the case proves they stay apart rather than that one type round trips.
- This is one clause of the staging unit "the header and the fact tables".
  The unit's other clauses — the header itself, the field move and the seven
  unwritten columns — are not in this task; the header's own task records the
  design and is not started.

* Result

A cross-currency swap keeps its own product type through the import and the
export. The importer stores =CrossCurrencySwap= where the document used
=CrossCurrencySwapData= and =Swap= where it used =SwapData=; the exporter
writes the element and the trade type the row names. The case that covers it
imports and exports a document holding one of each, and the two come out
apart.
