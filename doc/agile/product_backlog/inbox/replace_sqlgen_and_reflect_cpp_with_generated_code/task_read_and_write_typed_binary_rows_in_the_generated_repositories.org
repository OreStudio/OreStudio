* Acceptance

- The generated entity holds each column's own type: a uuid, a time point, a
  date, a decimal, never their text.
- The generated repositories read and bind in the binary format; the text
  mode of the layer has no generated caller.
- The mapper templates convert no column through its text.
- The code matches the docs that already describe this state: the time types
  and the WHERE clauses in [[id:4AAD3581-CFA7-4B44-A2DD-0236784E939F][the time architecture]], and the entity type
  mapping in =projects/ores.codegen/docs/cpp_generation_analysis.md=. The
  meta-model docs' entity and mapper examples show typed fields; the example
  of a text column decoded through base64 goes.
- The repository benchmark is measured before and after, and the timestamp
  parse no longer shows in a profile of a read.

* Plan

*Why now.* sqlgen is gone, so nothing outside the layer decides what a column
is any more. Until this task the row entity was the text shape sqlgen filled,
and the mapper parsed that text back into the domain type. The layer has held
binary codecs for =uuid=, =tenant_id=, =timestamptz=, =date= and =numeric=
since the libpq layer was built, so the row can hold the type the column has
and the mapper can stop converting.

*What stays text, and why.* A column keeps its text member when the layer has
no binary codec for it, or when the domain member is not the column: =inet=, a
base64 column, an enum held as its text and a value type such as
=cron_expression=. The mapper converts those, as it does today. String columns
are text in both formats, so nothing changes for them.

*The move, in three steps.* Each one ends in a build and a suite run:

1. *The layer binds and reads the typed row.* =query_builder::execute= binds
   each column through =pq::encode_param= and reads it through =pq::read=, and
   a generated statement asks for binary results. =db_timestamp= becomes
   =std::chrono::system_clock::time_point=, and the bitemporal never is
   =time_point::max()= in both formats, as the binary codec already reads it.
   The text forms stay in =pq::text= for hand-written SQL.
2. *The generator emits the typed row.* The entity template gives each column
   the type its column has; the mapper template copies those members across.
   =is_optional_uuid=, =is_required_timestamp= and their siblings no longer
   mean "the row holds text", so the flags that only existed to bridge the two
   shapes go with them.
3. *Regenerate and measure.* Every component regenerates through the
   =ores.cpp.repository= profile, then the suites run and the repository
   benchmark is measured on the old and the new path.

*What the benchmark compares.* The text path stays in the layer for
hand-written SQL, so one benchmark binary reads the same table through the
text forms and through the typed statement. That is the comparison the task
asks for: the cost the generated repositories paid at =954babc48b= against
the cost they pay now, on one tree and one machine.

* Result

The generated repositories read and write their rows in the binary format. Each
entity member holds the type its column has, the mapper copies it and converts
nothing through text, and the 40 columns the layer has no codec for state
`bind_text` and travel as the text the server renders. `db_timestamp` is the
clock's `time_point`, so one type runs from the column to the domain, and the
store's infinities are read as the clock's bounds.

Measured on the committed head: a full build; the database rebuilt from the
schema and the populate scripts; ctest 98 of 98 suites; the pgTAP suites, the
tick smoke and the step-consumer check; codegen pytest 1,659 passed. The local
check gate reports 53 of 54, the one failure being an RLS warning for a table
that comes from `main` and whose diagrams are current.

Follow-ups recorded, not done here: the junction entity's `tenant_id` is still a
string bound as text; the row's entity `operator<<` still uses reflect-cpp,
which is the next step of the story; and the round trip's cost was not measured
against the text layer it replaces.
