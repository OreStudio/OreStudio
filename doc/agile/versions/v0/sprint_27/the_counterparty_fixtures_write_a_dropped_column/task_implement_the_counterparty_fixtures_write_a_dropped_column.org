- No code names counterparty.business_center_code.

* Plan

=0d9dd1a899= took =business_center_code= off the counterparty and gave it a set
of centres through =ores_refdata_counterparty_business_centres_tbl=. It
regenerated the code and the schema, and wrote a new pgTAP test that asserts the
column is gone, but left the consumers that read or wrote it:

- =generators_tests.cpp= asserts the member on a generated counterparty.
- Nine pgTAP fixtures insert it into the counterparties table: the counterparty
  suite itself, the ownership marks suite, and the seven trading suites that
  seed a counterparty to hang a trade on.

Only the counterparty's column went. The party keeps its own
=business_center_code=, so the party generator test, =auth_handler=,
=tenant_provisioning_handler=, the BFF and the wire protocol all stay as they
are; each was read before being left alone.

The C++ line goes. The fixtures lose the column from the insert list and the
value from the same position in every row.

* Notes

=generators_tests.cpp= has two assertions of that shape, and only one is about a
counterparty: line 64 is in the party generator's test and stays.

The fixtures were fixed by a codemod that splits each insert's column list and
values at top-level commas, removes the column and the value in the same
position from every row, and refuses to write unless each row holds as many
items as the column list does. One fixture inserts two rows at once, which a
first version of the codemod read as one row of twenty-five values against
thirteen columns and refused; the count assertion is what caught it.
