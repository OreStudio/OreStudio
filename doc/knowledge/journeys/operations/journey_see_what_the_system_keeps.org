This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A system administrator sees every store the installation keeps, what bounds it, how large it is and whether it is growing.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want to know what this installation is keeping, how big each store is, and
whether anything is growing with nothing to stop it." The journey is done when
the administrator can say, for every store the installation keeps, what bounds
it and how large it is — or has found the stores that nothing bounds.

* Actor and trigger

The system administrator: an account holding the =SuperAdmin= role and acting
from the system tenant, in *system administration mode*. The screen belongs to
the *Operations* area beside the services, the grid, the bus and the logs,
because it answers a question about the installation and not about a tenant.

The trigger is a capacity question rather than a fault: a backup that takes
longer each week, a database that crossed a size somebody noticed, an audit
that asks how long the installation keeps its report outputs, or the plain
monthly check that nothing is filling the disk. A tenant cannot ask this
question of itself: the stores are the installation's, and their policies are
held by the system tenant, so a tenant administrator has no screen here.

The journey reads. Nothing on it changes a store, and opening it writes
nothing; the one act that writes is the step that leaves for
[[id:C647D403-BFF0-4910-83E4-4EFEBD4F39C4][Change what is kept, and for
how long]].

* Steps

1. *Open the housekeeping screen.* The administrator opens *Operations* and
   chooses *Housekeeping*. The system shows one screen: every store the
   installation keeps, one row each, with the policy that bounds it, its size,
   its growth and the outcome of its last sweep.
2. *Read the ground first.* The screen opens on a summary that a person can
   take in before reading any row: how many stores there are, how many are
   bounded by an enabled policy, how many are unbounded, and the total size
   under management. A store counts as unbounded when no policy names it, or
   when its policy names an action the sweep cannot apply — the second case is
   the dangerous one, because it looks bounded on paper.
3. *Scan the table.* Each row carries the store by the name a person knows it
   by — "Calendar dates", not =ores_refdata_calendar_dates_tbl= — with its
   description a click away, the shape it has (a chunked table, an ordinary
   table, an object-store prefix, a directory on a compute host), the policy
   that bounds it, the period, the state, the size, the growth and when it was
   last swept. The physical target sits beneath the name, because it is what
   the database and the sweep name the store by, and it is not what a person
   reads first. The administrator reads the sizes first
   and the states second, because a large bounded store is doing what it was
   told and a small unbounded one is a decision nobody made.
4. *Order by what matters.* The system orders by size, by growth, by last
   sweep or by state. Growth is the number that answers the trigger: a store
   that added 400 MB this week is a different problem from one holding 4 GB
   that has not moved.
5. *Open one store.* A row opens its detail: the policy's fields as the
   server holds them, the size today, the history of its size, and the last
   few runs of the sweep against it. The history is what separates a store
   that grew once from a store that grows every hour.
6. *Follow the store to its runs.* The detail links to the housekeeping log
   filtered to that store, so the administrator can read what the sweep did
   and why it says what it says, in
   [[id:F6622109-4F52-4DE9-9C06-6B0EAA7C8D2E][Read the housekeeping log]].
7. *Find what nothing bounds.* An unbounded store reads as such, with the
   reason: no policy, a disabled policy, or an action the sweep does not
   perform. The last is stated in the sweep's own words, so the screen reports
   the platform's behaviour rather than a guess about it.
8. *Leave by changing something.* From a store's detail the administrator
   opens its policy in
   [[id:C647D403-BFF0-4910-83E4-4EFEBD4F39C4][Change what is kept, and for
   how long]], which is where a store stops being unbounded.

The size of a store is not an entity: it is a measurement the server makes
when asked, and the screen shows it as such.

* What is missing

- *A name and a description for a store.* The store's identity is its target
  string, and nothing carries a human name or a sentence saying what the store
  is: the policy's =description= describes the policy, and its =code= names the
  policy. The store needs its own entry — a catalogue of the stores the
  installation keeps, with a code, a display name, a description, the shape of
  its target and how to measure it — and a policy should name one of those
  entries. Without it this screen either derives "Refdata Calendar Dates" from
  a table name, which says nothing about prefixes or directories, or writes
  twelve names into the client.
- *A size of a target.* Nothing in the tree reports how large a table, a chunk
  set, an object-store prefix or a host directory is; the only size query is a
  psql macro. The screen cannot answer its own first question without it. The
  subject would be something like =scheduler.v1.retention_targets.sizes=,
  answered from =pg_total_relation_size=, =timescaledb_information.chunks= and
  the storage service's own accounting, and it belongs beside the policies
  rather than in each screen.
- *A growth history.* The runs ledger records what a sweep removed and not the
  size it found, so no history exists to plot. The knowledge page promises
  "the size of its target before and after … the measured size over time
  yields a growth rate"; the schema does not deliver it. Until it does, the
  screen states the size it reads now and says the trend is unknown.
- *A read of the runs.* The table exists and the sweep writes it, but no wire
  type does; PR #5126 adds one. Until it merges the screen can show only the
  policy and the sweep's last job instance.
- *Which actions the sweep performs.* The sweep performs one of the three the
  policy model states, and records the rest as skipped. The screen must say so
  from data, not from a constant in the client: the set of supported actions
  belongs in the answer to the policies read.
- *The object store's own numbers.* No read reports bytes under a prefix, so
  the object-store rows can carry a policy and cannot carry a size.
