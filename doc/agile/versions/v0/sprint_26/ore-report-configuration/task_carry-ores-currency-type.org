* Goal

A currency carries the ORE currency type it was imported with, so the export writes back the same token and the currencies kind round trips over its whole corpus.

* Acceptance

- The refdata currency model has a column that carries ORE's CurrencyType verbatim, and the database has it after a recreate.
- The mapper reads and writes that column one to one, and no longer translates ORE's type into monetary_nature.
- The currencies kind is registered with the round-trip harness and all thirteen corpus files round trip.

* Plan

1. Add =ore_currency_type= to the currency model as a nullable text column,
   because ORE declares the element as a free string and most documents set
   none. A lookup would be wrong: the vocabulary is ORE's, not ours.
2. Regenerate the refdata artefacts for the currency entity and apply the
   column to the development database.
3. Read the token into the new column on import and write it back on export.
   Keep deriving =monetary_nature= from it, because that is our classification
   of a currency rather than a substitute for ORE's token.
4. Register the currencies kind with the harness and assert the whole corpus.

* Notes

- Three tests encoded the old contract, where =monetary_nature= doubled as
  ORE's token. They now set the token and assert it round trips, and one of
  them asserts the derivation explicitly: a token of =Crypto= comes back as
  =Crypto= with a nature of =synthetic=, which is the whole point of separating
  the two.
- The mapper can no longer round trip a currency that has a =monetary_nature=
  but no token, because ORE's document cannot express a nature. That is the
  contract now, and the tests say so rather than leaving it to be discovered.
- The column is nullable, so a document that sets no =CurrencyType= exports
  none. Twelve of the thirteen corpus files depend on that.
