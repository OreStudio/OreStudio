* Goal

Give =market_data_generation_config= the two orthogonal primitives the
parent story needs: a =scope= column (system/tenant/party, sharing
radius) and a =binding_mode= column (bound/sandboxed, authority), plus
a database-level guard so at most one enabled =bound= config can ever
cover the same scope at once.

* Plan

- Added two hand-written domain enums (=domain::scope=,
  =domain::binding_mode=) in =ores.synthetic.api=, following the
  =domain::asset_class= precedent (=ores.marketdata.api=) -- plain C++
  enum classes, no codegen enum-model facet in use yet for this
  component.
- Extended =ores.synthetic.market_data_generation_config.org=: made
  =party_id= nullable (=std::optional<uuid>=), set
  =:nullable_tenant_id: true= (tenant scope's =tenant_id= can now be
  null for system-scope rows), added =scope= and =binding_mode= as
  =text=/=is_enum= columns with generator blocks (both always generate
  =party=/=bound= -- the per-column generator has no way to coordinate
  =scope= with =party_id='s nullability, so tenant/system-scope rows
  are created explicitly, not via the synthetic generator).
- Regenerated the entity's full supported set via
  =compass codegen entity generate market_data_generation_config=.
- Qt Columns (list model) needed a =formatter= for both new columns --
  the Qt codegen's =string= column type assumes the C++ field actually
  is a =std::string= and calls =QString::fromStdString()= directly on
  it, which doesn't compile against an enum. Added
  =ores.qt/ScopeLabel.hpp= / =BindingModeLabel.hpp= (small hand-written
  formatter functions, mirroring the existing
  =ores.qt/ProcessTypeLabel.hpp= pattern) and wired them via the
  Columns table's =formatter=/=formatter_include= columns.
- The reject-at-activation conflict check is cross-row logic, not a
  per-column FK validation, so it doesn't fit the =Insert trigger /
  Validations= table mechanism. Used the paste-block mechanism instead
  (=:implements d4e8e136-828d-440a-ba59-82ba2b9d3e2e=, the same
  injection point =ores.refdata.business_unit= uses for its
  cross-column level check) to hand-write a symmetric scope-overlap
  predicate directly in the insert trigger, positioned before the
  version-management block so it runs against the still-active prior
  row and can exclude it by =id=.
- Verified live: recreated the DB, inserted an enabled tenant-scope
  bound config, confirmed a conflicting party-scope bound insert for
  the same tenant is rejected with the expected error, and confirmed a
  =sandboxed= config for the same tenant/party inserts cleanly
  (sandbox never participates in the check).

* Notes

* Result

=market_data_generation_config= now carries =scope= (system/tenant/party)
and =binding_mode= (bound/sandboxed) end-to-end -- entity, SQL schema,
domain struct, mapper, generator, Qt list model, and history/diff view
-- with =party_id= and =tenant_id= nullable to match. A database
trigger rejects enabling a =bound= config that conflicts with another
already-enabled =bound= config covering an equal-or-wider scope;
=sandboxed= configs are exempt. A CHECK constraint enforces the
scope/nullability invariant the guard depends on, and the RLS policies
correctly show wider-scope rows to narrower-scope sessions. Covered by
a new pgTAP regression test. Fixed a pre-existing codegen gap along
the way: the history-field-mapper template never rendered =is_enum=
columns.

Review round 1: 5 issues fixed (RLS visibility gap, missing
history/diff fields, missing CHECK constraint, Qt Add-flow party_id
gap, no automated test), 3 declined (see =* Review= table for
reasoning). =compass build= and the =ores.synthetic.*=/=ores.qt.tests=
C++ suites pass; the new pgTAP test and the full =ores.sql/test= suite
run clean (pre-existing unrelated failures need Acme fixture data this
fresh DB doesn't have).
