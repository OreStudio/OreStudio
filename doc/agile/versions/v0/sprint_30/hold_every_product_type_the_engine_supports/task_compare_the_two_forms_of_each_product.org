* Goal

Each product ORE carries in both forms is booked as a twin pair on the same
terms, ORE values both, and a test compares the two values, so a difference
between the native and the scripted implementation is seen and explained.

* Acceptance

- the generator books, for each product with both forms, a native trade and a
  generic ScriptedTrade that state the same economic terms, linked as twins
- an ORE run values both trades of each pair
- a test compares each pair's values: a pair agrees when the difference is
  within a relative tolerance of the larger value, with an absolute floor for
  values near zero; a product that needs a wider tolerance states it on a list,
  with the reason
- a pair that differs beyond its tolerance is on a known list with the reason it
  differs; the list is asserted exactly, so a listed pair that now agrees fails
  the test until its entry is removed
- a page or report shows each pair's two values and their difference

* Plan

The both-forms task already books every pair, and the ORE engine test already
runs ORE over every recorded trade with the Products example's configuration,
which writes =npv.csv=. The comparison reads that run, not a run of its own.

- The engine test runs ORE once for both of its tests. The run is held in
  memory, and its directory is removed when it succeeds.
- Merging the recorded trades renames each by its file, because the recorded
  trades of each asset class share ids. The merge keeps each run id's trade
  type and recorded id.
- A pair is a recorded native trade and the ScriptedTrade whose id
  =twin_id_for= draws from the native's id and type. =twin_id_for= moves to the
  scripted twins header for this.
- The values come from =npv.csv= through ores.ore's =read_metrics_for_file=. A
  trade ORE names =Failed= has no value.
- A pair agrees when both are valued, in the same currency, and differ by no
  more than a millionth of the larger value or by a cent.
- =generated_trades_twin_differences.txt= lists each trade type whose pairs do
  not agree, with the reason. The test fails on a differing type the list does
  not hold, and on a listed type whose pairs now agree.
- =ORES_UPDATE_GENERATED_TRADES=1= writes =generated_trades_twin_values.tsv=:
  each pair's two values, their difference and whether they agree.

* Notes

Depends on [[id:589884B5-1B2C-4044-AAD4-40680C9F3F0C][Generate every product in both of its forms]], which books the
twins, and on the valuation story, because a pair can be compared only when the
engine prices both forms: today several element forms raise an engine
configuration error in the Products example configuration.

** What the comparison found

Every pair whose two trades are both valued agrees to the cent, except the FX
worst-of basket swap, so no product needs a wider tolerance than the default.
Both forms price through ORE's scripted engines on the same market, so equal
terms give equal values.

- *EquityPairwiseVarianceSwap, FxPairwiseVarianceSwap*: the native trade is not
  valued, because the Products example states no pricing engine for either type
  (the known errors list holds the message). The twins price.
- *FxWorstOfBasketSwap*: ORE's class runs a script of its own. The twin reads
  one fixing per period where the class compounds, and pays the initial fixed
  amount on the first period date. The twins differ by 3.2% (-651335.18 against
  -630811.63 USD) and 0.6% (266454.13 against 264880.01 USD).

The planted check: with the worst-of line removed from the known list and an
EquityBasketOption line added, the test fails and names both.

* Result

The ORE engine test now compares each product's two forms. One ORE run over the
recorded trades values both; the test pairs each native trade with its scripted
twin by =twin_id_for=, and requires each pair to agree, or its trade type to be
on a known list with the reason, asserted exactly. Of the 34 pairs, 28 agree to
the cent. The pairwise variance swaps' natives are not valued in the example's
configuration, and the worst-of basket swap's twin differs by a few percent for
reasons the notes state. A recording run writes each pair's two values and their
difference to =generated_trades_twin_values.tsv=.
