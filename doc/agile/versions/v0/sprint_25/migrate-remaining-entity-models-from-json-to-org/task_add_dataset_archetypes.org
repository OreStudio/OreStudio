This page documents a [[id:31C868B9-306E-4282-BA8C-07E647021B34][task]] in the [[id:5FFB587D-D85A-4B51-8C80-0F8D485754A7][Migrate remaining ~100 entity models from JSON to org]] story. It captures the goal, current status, acceptance, and any notes or results.

* Goal

Add the ores.sql.populate archetypes that crypto, flags, ip2country and
FPML need, plus the generator changes those archetypes require, so the
four datasets can move onto the org dataset pipeline.

The nine generic archetypes from [[id:7917CA28-A69D-4FA5-A95B-B0346C73272A][Decommission the legacy ores.codegen
bash scripts]] cover the six-file metadata core of every dataset:
catalog, dataset, dataset_dependency, tag, methodology and the
batch-execute master include. They do not cover the artefacts. Three
archetype families are missing:

1. *Image artefacts* — crypto icons and country flag SVGs. The current
   output comes from =images_generate_sql.py=, which inlines a whole
   SVG document per row.
2. *The ip2country artefact plus its TSV import* — IP geolocation
   ranges loaded from a tab-separated source file.
3. *FPML per-entity refdata* — 22 entities, a dataset plus an artefact
   each, plus the coding schemes they reference.

The archetypes also need a generator change: the payload each dataset
carries comes from =manifest.json=, whose field names do not match what
the archetypes read (=subject_area= vs =subject_area_name=, =catalog=
vs =catalog_name=, =coding_scheme= vs =coding_scheme_code=,
=source_system= vs =source_system_id=, =license= vs =license_info=,
=artefact_type= vs =asset_type=).

This task stops at the archetypes and the generator. Moving the four
datasets themselves is [[id:44B275EC-DC37-4961-80EF-9D79D4C186FB][Migrate FPML, crypto, flags and ip2country onto
the org dataset pipeline]].

The bar is semantic equivalence, not byte-identical output: the same rows
with the same values, however the SQL is written. The user set this bar,
and it is what makes the six metadata-core archetypes usable at all, since
they emit a different SQL shape from the committed files.

* Where an archetype's data comes from

The first cut of the image and ip2country archetypes named
=manifest.json= as their =#+data_source:=, which made a metadata document
double as the artefact payload. The user rejected that: the manifest
describes the dataset, and it must not carry the dataset's rows. It is
also why =source_dir= and =description_template= appeared in the crypto
and flags manifests, duplicating =sources[].data_dir= and putting
presentation in metadata. Both fields are removed.

An archetype's =#+data_source:= now names every payload it reads, and a
dataset's directory holds its model and its payloads together, which the
live =acme_corporation= dataset and the retired =slovaris= one both show.
The manifest is therefore a sibling the archetype can simply name. The
image archetype names =images.json= for its ={"key", "description"}=
entries and =manifest.json= for the dataset identity and the SVG
directory, which it takes from the source's existing =data_dir=. The
ip2country archetype still names only the manifest, because its artefact
data is the TSV and the generated script loads that itself at run time.

Two rules follow for the datasets that move next. Artefact data belongs in
a payload file beside the model, never in the manifest. And a value that
already has a home, such as the upstream directory in =sources[].data_dir=,
does not get a second one.

* Acceptance

- An image-artefact archetype generates the crypto-icon and
  flag-image SQL that =images_generate_sql.py= produces today.
- An ip2country archetype generates the artefact SQL plus its TSV
  import.
- An FPML archetype generates the per-entity dataset and artefact SQL
  for all 22 entities, plus the coding schemes, byte-identical to the
  committed output.
- The generator reads =manifest.json= directly, or the four datasets
  carry a translated payload; either way no hand-written translation
  step remains.
- Each new archetype is an org node in the template library with a
  =#+data_source:=, an =#+output:= pattern, and a tangled mustache.
  (=#+model_types:= belongs to the facet, not to the archetype.)
- =compass build --direct tangle_codegen_templates= produces no drift.
- The codegen test suite passes, with a test per new archetype.

* Plan

1. Read the committed crypto, flags, ip2country and FPML populate SQL
   to fix the exact output each archetype must produce.
2. Write each new archetype as an org node with its mustache source,
   following the shape of the nine generic archetypes.
3. Extend the generator to read =manifest.json=, or add the payload
   translation, and decide which on the evidence.
4. Re-tangle, then diff the generated output against the committed SQL
   until it is byte-identical.
5. Add a test per archetype, following =test_data_scope.py=.

  and =sql_schema_artefact_create.org= are orphan archetype docs left

  =#+data_source:=. They are the closest existing source for the FPML

- Reading, 2026-09-18. What the committed populate SQL says:
  - *Nothing consumes the nine archetypes.* No dataset model carries
    =#+type: ores.codegen.dataset= outside agile docs, and no payload
    JSON (=datasets.json=, =catalogs.json=, =tags.json=,
    =methodologies.json=) exists in the tree. The pipeline is built and
    unexercised.
  - *The archetypes are a redesign, not a reproduction.* They emit a
    bare =select=, a =-- Data Quality {model} ...= banner, a licence
    via ={{{sql_license}}}=, and a =-- Summary= count block. The
    committed crypto, flags and ip2country files emit =DO $$ BEGIN ...
    PERFORM ... END $$;= and no summary. So byte-identical holds for the
    three new families, which can be written to the committed style,
    but not for the six metadata-core archetypes.
  - *Two artefact conventions.* The crypto and flags images use
    PL/pgSQL =DO $$=; the FPML artefacts use psql =\gset=.
  - *Licence headers are inconsistent.* All four master includes carry
    none. FPML carries none on its six metadata-core files either,
    while its 44 per-entity files do. Crypto and flags use (C) 2025 and
    (C) 2026 in the same directory.
  - *=fpml_populate.sql= and =populate_fpml.sql= are byte-identical.*
    =fpml_parser.py:921= writes the latter; the former is the wired
    master include and still credits =generate_fpml_refdata.sh=.
  - *=fpml_coding_schemes_populate.sql= is dead legacy* — =set schema
    'metadata'= and positional =upsert_dq_coding_schemes= calls.
  - *FPML ships no =dataset_tag= file.* Crypto, flags and ip2country do.
  - *ip2country has two scripts for one dataset.* The DQ artefact
    populate writes =ores_dq_ip2country_artefact_tbl=; the import
    writes =ores_geo_ip2country_tbl= with a =:data_file= variable. The
    artefact script is malformed: its =\copy= has no terminating
    semicolon, and it declares the staging temp table twice.
