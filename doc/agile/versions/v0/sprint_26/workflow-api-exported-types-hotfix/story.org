* Goal

The Windows clang-cl build fails at the link step of the workflow core DLL:

#+begin_src text
lld-link: error: undefined symbol: __declspec(dllimport) public: __cdecl
  ores::workflow::service::workflow_registry::workflow_registry(void)
lld-link: error: undefined symbol: __declspec(dllimport) public: __cdecl
  ores::workflow::service::workflow_definition::workflow_definition(void)
#+end_src

=ORES_WORKFLOW_API_EXPORT= is =BOOST_SYMBOL_IMPORT= for a consumer and
=BOOST_SYMBOL_EXPORT= while the library itself is compiled. On the Microsoft
ABI the import arm is =__declspec(dllimport)=, so a consumer that constructs
one of these types references the symbol in the library's import library and
cannot generate it locally.

The export is real only if some translation unit of the library includes the
header. Every =.cpp= under =ores.workflow/api/src= is generated domain or
generator code, and none of them includes these two service headers, so the
library exports nothing for the types while every consumer imports them. They
are the only hand-written headers in the estate in that state.

It surfaced now because until the same afternoon the Windows build stopped
earlier -- at the export attribute on the enum in the same header, which the
previous hotfix removed -- so the link step was never reached.

  a =workflow_definition= compiles to a definition rather than to an import.

* Decisions

- The attribute is removed rather than the library given a translation unit
  that includes the headers. Either works, and =ores.eventing.api= uses the
  second for =event_bus=; but a header-only type needs no DLL attribute on any
  ABI, while a compilation unit would have to be added for every such type and
  relies on the compiler exporting implicitly-declared members.
- The scan checks the *include graph* rather than looking for an out-of-line
  definition. A type whose header reaches a library translation unit is
  exported correctly even when the type is header-only; a type whose header
  reaches none is broken even when it declares out-of-line members that no
  unit defines. Whether the header reaches a unit is the thing that decides.
- The check joins the enum check on the same pull-request workflow. Both are
  source scans with no toolchain, and both exist because Windows is the only
  compiler that reports the defect and it reports it hours late.

- The =event_bus= stub unit in =ores.eventing.api=, which is the same pattern
  and passes the check.
