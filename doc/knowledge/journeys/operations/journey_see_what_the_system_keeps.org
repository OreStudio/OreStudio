This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A system administrator sees every store the installation keeps, what bounds it, how large it is and whether it is growing.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want to know what this installation is keeping, how big each store is, and
whether anything is growing with nothing to stop it." The journey is done when
the administrator can say, for every store the installation keeps, what bounds
it and how large it is — or has found the stores that nothing bounds.

* Actor and trigger

The system administrator: an account holding the =SuperAdmin= role and acting
from the system tenant, in *system administration mode*. The screen belongs to
the *Operations* area beside the services, the grid, the bus and the logs,
because it answers a question about the installation and not about a tenant.

The trigger is a capacity question rather than a fault: a backup that takes
longer each week, a database that crossed a size somebody noticed, an audit
that asks how long the installation keeps its report outputs, or the plain
monthly check that nothing is filling the disk. A tenant cannot ask this
question of itself: the stores are the installation's, and their policies are
held by the system tenant, so a tenant administrator has no screen here.

The journey reads. Nothing on it changes a store, and opening it writes
nothing; the one act that writes is the step that leaves for
[[id:C647D403-BFF0-4910-83E4-4EFEBD4F39C4][Change what is kept, and for
how long]].

* Steps

1. *Open the housekeeping screen.* The administrator opens *Operations* and
   chooses *Housekeeping*. The system shows one screen: every store the
   installation keeps, one row each, with the policy that bounds it, its size,
   its growth and the outcome of its last sweep.
2. *Read the ground first.* The screen opens on a summary that a person can
   take in before reading any row: how many stores there are, how many are
   bounded by an enabled policy, how many are unbounded, and the total size
   under management. Every store that can take one carries a default bound, so
   a store without a policy is the exception: either its bound cannot be
   expressed as an age, or somebody removed the default. A store counts as
   unbounded when no policy names it, when its policy names an action the sweep
   cannot apply, or when the policy is off or its last run failed — the skipped
   action is the dangerous one, because it looks bounded on paper.
3. *Scan the table.* Each row carries the store by the name a person knows it
   by — "Calendar dates", not =ores_refdata_calendar_dates_tbl= — with its
   description a click away, the shape it has (a chunked table, an ordinary
   table, an object-store prefix, a directory on a compute host), whether
   anything bounds it, what bounds it and for how long, the size and the
   growth. The physical target sits beneath the name, because it is what
   the database and the sweep name the store by, and it is not what a person
   reads first. The administrator reads the bound first and the size second,
   because a large bounded store is doing what it was told and a small
   unbounded one is a decision nobody made.
4. *Order by what matters.* The system orders by size, by growth or by whether
   anything bounds the store. Growth is the number that answers the trigger: a
   store that added 400 MB this week is a different problem from one holding 4
   GB that has not moved.
5. *Open one store.* A row opens that store's own page: its code and name, its description, the component that writes it,
   the shape of its target and the target itself, the column a row delete
   would compare, and what measures it. Beneath the record are the size now,
   the plot of its growth, the policy that bounds it, and the latest activity
   that names it — measurements, sweep runs, and the changes a person made.
   The plot is what separates a store that grew once from a store that grows
   every hour; the activity is what says why. A breadcrumb and a back action
   return to the list, which keeps the comparison the person came for.
6. *Follow the store to its runs.* The detail links to the housekeeping log
   filtered to that store, so the administrator can read what the sweep did
   and why it says what it says, in
   [[id:F6622109-4F52-4DE9-9C06-6B0EAA7C8D2E][Read the housekeeping log]].
7. *Find what nothing bounds.* An unbounded store reads as such, with the
   reason: no policy, a disabled policy, a failed run, or an action the sweep
   does not perform. The last is stated in the sweep's own words, so the screen
   reports the platform's behaviour rather than a guess about it. The screen
   states the count at the top and filters the table to those stores, so the
   question "what still nothing bounds" is one action rather than a reading of
   every row; the count is the work left, and it should reach zero. Each row
   also states the cost in bytes: what the store holds now, and what the rate of
   the last twelve weeks comes to over a year.
8. *Leave by changing something.* From a store's detail the administrator
   opens its policy in
   [[id:C647D403-BFF0-4910-83E4-4EFEBD4F39C4][Change what is kept, and for
   how long]], which is where a store stops being unbounded.

* Screens and wireframes

Two screens, in the shape the rest of the application uses. The list page is
composed around the question "what is this installation keeping": a summary
strip states the counts and the total, and the table carries one row per store.
The store page is the record a row opens: the store's own fields, its plot, its
policy and its log, with the way back to the list stated at its head.

The size of a store is not a field of the store: it is a measurement, held as
a series of samples that point at the store, and the screen shows it as such.

* What is missing

The screen was built after this journey was written, and three of the gaps it
stated are closed by one read. What remains is stated here so the screen's own
words match it.

- *A name and a description for a store.* Closed: the catalogue
  (=ores.scheduler.retained_stores_tbl=) holds a code, a display name, a
  sentence about the store, the shape of its target and the component that
  writes it, and =scheduler.v1.store_bounds.list= answers every store with
  them. A policy names a store through =store_code=, so "unbounded" is a store
  no policy names rather than a target string that appears in none.
- *A size of a target.* Closed for the stores the database can see: the sampler
  writes one sample per store per hour, and the same read answers the latest
  one. An object prefix and a folder on a compute host are measured by the
  component that owns them, and that component does not report a size yet, so
  those stores read as not measured rather than as empty.
- *A growth history.* Closed for shape and open for detail: the samples are a
  series, so a store's page plots it, and the runs ledger still records what a
  sweep removed and not the size it found. A step in the plot is therefore the
  sampler's view of a sweep, not the sweep's own statement of it.
- *A read of the runs.* Open. The table exists and the sweep writes it, and no
  wire type reads it; PR #5126 adds one. Until it merges the screen states the
  last run, which the bounds read carries, and names the gap.
- *Which actions the sweep performs.* Closed: the bounds read states the
  mechanism a bound names and whether it applies today, so a policy the sweep
  cannot perform reads as unbounded and says why. The rule is the database's,
  in =ores_scheduler_store_bounds_vw=, and never the client's.
- *The object store's own numbers.* Open, as the size note above states.
