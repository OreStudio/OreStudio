#+description: Every data bundle and package the system defines or needs: what each one is, whether it is a bundle or a package, the relatedness that justifies it or the provenance that gathered it, the components that own its parts, the atomicity it has today with file evidence, the atomicity it requires, and its status.

* Summary

Bundles and packages are heterogeneous but typed, so the set is
enumerable. This page
enumerates it: every candidate found in the code and the models, with the
relatedness that makes it a bundle or the provenance that gathers it into
a package, the number of
owners, the atomicity it has today with a file reference, the atomicity it
requires, and its status. The candidates were read from the code, not
imagined: the =ores.codegen.operation= models, the workflow definitions,
the ORE import and export paths, the seeder and DQ publication, the
approval proposals, tenant provisioning and the compute path.

Three results follow from the table. Most candidates are single-owner,
related sets: they are bundles, and each needs one =unit_of_work=, not the
package transport. A few span owners: they are packages, they need a
workflow, and several already have one. Several
are wrongly shaped today, and the conventions and curve-configuration
documents are the two clearest. The gaps are equally concrete: the
package manifest and part format that
[[id:0BA30CC1-18C8-48CC-8243-8912880F8DEC][Transporting a package]]
specifies exist in no header, and the one implemented manifest carries no
checksum and no =as_of=.

* Detail

** How to read the table

Every row carries evidence or is labelled *inference*. An evidence cell
names a file and a line; a line number is where a call site, a loop or a
write begins, so a reader can open the file and see the claim. *Inference*
marks a judgement the code cannot state: that an atomicity is required
when no caller demands it yet, or that a set is wrongly shaped when it
compiles.

The columns follow
[[id:56AD6F46-99E0-482E-B7B5-C9FDEC8A7641][the data classification
checklist]]: the set, its shape, its invariant or none, the owner count,
the parts by owner and kind, the atomicity today, the atomicity required,
the trigger and the status. Owner count is the number of components that
write rows in the set, and it decides the classification before any shape
is chosen.

The *Shape* column separates the two words this page uses. A *bundle* is a
set of related families, belonging to one owner, applied as one unit: its
families share either an invariant that must hold at one instant, or one
operation whose intent is all-or-nothing, and it is atomic in one
=unit_of_work=. A *package* is an artefact carrying one or more bundles
plus a manifest, moved between systems as bytes; it has no relatedness
constraint, its bundles may belong to different owners, and it is never
atomic as a whole. Relatedness makes a bundle; provenance makes a package.
The rows with one owner and related families are therefore bundles, and the
rows with several owners are packages. A single-owner set whose families
share no invariant is a bundle only if one operation names it; with no such
operation, each family is its own bundle. B1 has the operation, and nothing
applies the set as one.

*uow* is one
=ores::database::repository::unit_of_work=: one connection, one
transaction, committed once. *per owner* means one such transaction in
each owner's database and no transaction across them, per
[[id:D5F77B10-D498-4B56-ADF7-7E5CEFA44FA0][Database per Service]].

** The frontier: three shapes

The table sorts into three shapes, and the sort is what makes the work
decidable once instead of per feature.

*** Single-owner sets that need one =unit_of_work=

B2 to B5, B7, B12 and B13 are written by one component each, and each is a
bundle of related families. None of them
needs the package transport, and none needs a coordinator. They need one
transaction over the tables the document names, opened where the write
begins and committed after the last row. B1 is single-owner as well, and
one operation names its families, but they share no invariant. It is a
bundle by that operation only: the import could apply the set as one, no
operation declares all-or-nothing today, and the finding stays per family.

B7 and B12 already do this, so the pattern is proven in the codebase. B13
shows the cost of not doing it: the batch is saved, and the workunits are
saved one at a time, so a failure leaves a batch whose work is partly
dispatched. B1 to B5 show a second cost: the document reads back with
whatever writes happened to succeed, because each repository call commits
on its own.

B6 is also single-owner, and needs the same one transaction. It has no
operation today, which is why it is absent rather than broken.

*** Sets that span owners and need the workflow

B9, B10, B11, B14, B17, B18, B19, B20 and B21 span several owners, or
carry parts owned by another component, so each is a package. They cannot
be one
transaction, and the code does not try. Several of them already use a
workflow run, and B21 adds a compensation that deletes what the step
wrote.

The shape they need is the one
[[id:0BA30CC1-18C8-48CC-8243-8912880F8DEC][Transporting a package]]
describes: a manifest that names the bundles and their parts, one message
per bundle which is one per owner, and a
declared failure policy. B17 uses the workflow and states =stop=
deliberately, because a provisioning run is resumed rather than undone. B14
uses the workflow and states no policy, which is why its =atomic= flag has
nothing behind it.

B10 and B11 are the same set seen twice. The workflow gathers, the manifest
row records, and the packaging step turns the parts into one file. That is
the package classification implemented without its transport, and it earns
its place because the ORE engine needs every part at one instant: the
bundles are dispatched at one =as_of=, and the package is not atomic
across them.

*** Sets that are wrongly shaped today

B1 to B5 and B8 share one fault: a file's element list became a type. The
conventions document carries one array per convention kind because ORE XML
lists those kinds, not because a zero convention constrains a CDS
convention. The curve document repeats the shape for the curve file's
element list. The analytics and reporting documents repeat the shape at
smaller size, and the ORE import repeats it across messages instead of
inside one struct.

The right shape for each is the one its owner count states. B1 has no
cross-family invariant, so it is one family after another, each with its
lists, converted on its own. B2 to B5 have a header that the children name,
so each is one bundle per document with one transaction. B8 is one bundle
per trade.

B14 is wrongly shaped in a different way: it declares an =atomic= flag on
the request and ignores it. A caller can ask for all-or-nothing and
receive a partial publication that reports success.

** Transaction use: one unit per same-service set

The rule this catalogue supports is short:

- *A set that one service writes is one unit of work.* One connection, one
  transaction, committed once, over every table the set names. The
  classification calls it a bundle, and the mechanism is
  =ores::database::repository::unit_of_work=. B7, B12, B15 and B16 are the
  proof that the mechanism holds: in each, the set is written by one owner
  and a failure leaves nothing.
- *A set that several services write is never one unit of work.* No
  transaction spans two databases, no two-phase commit exists, and the
  =unit_of_work= is function-local to one connection. The sequence is the
  consistency mechanism: a workflow run, a declared failure policy, a
  stated instant, and a sandbox where a person must examine the result.
  B14, B17 and B21 are the proof that the code follows this, and B13 is
  the proof that a set with one owner gains nothing from a workflow.

The rule is not a preference. The table shows it as a fact about the
owners. Every row with one owner either already opens one transaction or
would be fixed by doing so; every row with several owners either already
uses a workflow or has no artefact at all. No row needs a mechanism its
owner count does not allow.

Two corollaries follow. A document that mixes related kinds from one owner
is a bundle, and the fix is a transaction rather than a transport. A
document that mixes kinds from several owners is a package, and the fix is
a manifest and a workflow rather than a bigger struct. A set that is both
in one artefact must be split, because the two halves need different
guarantees.

** Gaps

The gaps are of two kinds, and the two need different answers.

*** Packages and bundles with no artefact

- *B9, the environment export.* The transport page works the example in
  full, and no export operation, manifest or part format exists in any
  header. The package classification has a transport page and no
  implementation.
- *B18, sandbox promotion.* The sandbox exists, the import targets it, and
  the promotion the transport page relies on does not. The compensating
  control the package design assumes is therefore not available.
- *B19, the support package, and B20, the archival export.* Neither is
  modelled. The only archive machinery is a generic tar.gz helper with no
  digest, no manifest and no part boundary, so neither can be built from
  it without the package work.
- *The manifest, part and ledger types.* No =package_format_version=, no
  =bundle_record=, no =part_record=, no part-apply ledger and no =as_of=
  field exists in the
  code. B11's row is the nearest thing, and it carries the storage keys
  and the counts.

*** Sets whose relatedness does not hold

- *B1 and the documents like it are gathered only because a file contains
  them.* The relatedness the classification asks for cannot be written
  without naming ORE XML. They are a package's contents: B1 is a bundle
  only because one operation names it, its families share no invariant,
  and no operation declares the import all-or-nothing, so each family is
  applied on its own. Declare that operation all-or-nothing and the bundle
  is atomic in refdata's =unit_of_work=; until then the finding stands.
- *B14's =atomic= flag.* The request promises a property the workflow
  cannot provide, and no code reads the field. A flag that nothing
  consumes is worse than no flag, because a caller believes it.
- *B8's parts.* A trade is priceable only when its instruments and legs
  exist, and the import writes them across many calls. The invariant is
  real and unenforced, so a failed import leaves a trade whose parts are
  missing. The compensation deletes the trade, which is why the failure is
  survivable and not why it is correct.
- *B13's batch.* "The batch is complete when every workunit has a
  canonical result" is the stated invariant, and the batch row and its
  workunits are written separately. A restart can leave an open batch with
  fewer workunits than the request named.
