* Acceptance

- ores.security compiles on Windows MSVC with /WX and no C4101 warning.
- The catch block still logs and returns false on a malformed scrypt parameter.

* Plan

One-line change: drop the unused name from the catch clause. The block
already logs =param= and returns false, so it never needed the exception
object.

* Notes

Root cause: the catch clause declares =const std::exception& e= but the body
logs =param= instead, so =e= is never referenced. MSVC reports C4101, and =/WX=
promotes the warning to error C2220.

Replacing the name with an unnamed parameter is the established convention in
this codebase: 44 catch clauses already use =catch (const std::exception&)=
for the same reason.

The same C4101 risk was checked across every =catch (const std::exception& e)=
clause in the source tree: 1371 clauses in 394 files. Only
=password_hasher.cpp:127= failed to reference its exception; all others use it
directly or pass it on. No further changes were needed.

Build check: =compass build ores.security.lib= is green, and
=ores.security.tests= passes 127 assertions in 55 test cases.
