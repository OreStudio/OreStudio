* Goal

A system administrator picks last hour, day or week and reads how the grid's load, fleet, throughput and outcomes moved, and which node was busy or quiet when. Both stored sample tables already hold the data. No subject reads a range of either, so the story adds the reads, serves them through the BFF, and draws the panels the Watch the grid journey names. A week of node samples is about half a million rows for 26 nodes, so the reads bucket the rows on the server. The second half reads ORE's runtimes.csv and its memory lines in the wrapper, so each node sample can also state how long the engine ran and how much memory it peaked at.

* Acceptance

- A grid sample range read returns the samples between two times, bucketed to a width the caller asks for, so a week comes back as hundreds of points and not tens of thousands.
- A node sample range read returns one series per node over the same range and buckets, with the tasks done, failed, mean and longest duration and bytes moved.
- Both reads serve the whole installation, are gated by a permission, and say an empty range is empty and not a flat line at zero.
- The BFF serves both reads with the range presets of the other operations screens, and the grid screen draws load, fleet, throughput and outcomes on one shared time axis.
- The grid screen draws the node load heatmap and the node state ribbon from the node series, grouped by machine.
- A node sample carries the engine run time and the peak memory of its jobs, read from runtimes.csv and the memory lines, and the screen can chart them.
