A [[id:A7FCC423-1CA3-4345-BF5B-18D54207B00B][report]] page describes one report in
depth: what decision it feeds, who reads it, how often it runs, what it reads and
produces, the measures it carries, the ORE XML that configures it, the
parameters a definition of it states, and the test that exercises it. The page is
written from the report's definition and its configuration, never from one run of
it. A run is a report instance, and where a run stopped belongs on the task or
the investigation that owns it.

This folder holds the pages for individual reports, as =report_<slug>.org=. It
sits beside [[proj:doc/knowledge/workflows][=doc/knowledge/workflows/=]] for
the same reason: a report page is a durable statement about a report, and it
outlives the sprint that wrote it.

* What belongs here, and what does not

- A page here owns *one report*: its purpose, audience, frequency, inputs,
  outputs, measures, ORE configuration, parameters and test coverage.
- The *pipeline* that runs a report is not this folder's subject. The phases, the
  run configuration, the compute handoff and the substitution mechanism live in
  [[id:61EA2FC7-C112-44FB-8042-9BD7994B71E9][Report Processing]] under
  [[proj:doc/knowledge/architecture][=doc/knowledge/architecture/=]]. A report
  page links that cluster; it never restates it.
- The *business catalogue* of report families, their classification axes and
  their measures lives on
  [[file:../domain/risk_reporting.org][Risk reporting]]. A report page cites
  the axes and the measure definitions rather than copying them.
- A fact about one *run* (where it stopped, what it produced, what failed)
  belongs on the task or the investigation that owns that run.

* Reports

This page is the inventory of the reports the platform documents. Each row names
one report, the code its definitions and seeds refer to, and the page that
describes it; a new report is a new page and a new row.

The folder holds twenty-seven pages. Fourteen describe a report the platform
runs: thirteen catalogued reports, of which three run on both cycles so each has
a close twin beside it, and one smoke test. Thirteen describe the vega and greek
ladder family: ten are seeded and fail at the engine for the reasons their pages
state, and three are documented and not seeded.

The =Cut= column is the kind of cut the seeded definition selects, and it is the
column that says what the report prices from. A report on both cycles is two
definitions and not one: the plain name selects =LIVE= and runs during the day,
and the same name with "(EOD)" selects =EOD= and runs at the close. Headline
Position, Bump and Reprice Spot Greeks and Bump and Reprice Triple Vol Spot Ladder are seeded that way.

The =Frequency= column is the cadence the seeded definition of each report states,
in the words its page uses. The times are the hours the cron expression names, and
the expression is the one the seed states rather than a rounding of it. A report
whose expression can never fire runs only when a person starts it, so the column
reads =on demand=.

half of it by
[[file:../architecture/report_compute_handoff.org][Report compute handoff]].

* The vega and greek ladder family

These thirteen pages describe one family: a report bound to a sensitivity
configuration that bumps one risk factor and reprices the book. The number a
reader sees is a value change, not a derivative, and the bump is a setting of the
document rather than the identity of the report.

Ten of the family are seeded. The product owner overruled the design's decision to
hold them back on 2026-11-04: a definition that produces no figure costs nothing to
hold, and a catalogue that states the family says more about the platform than an
empty page does. Each seeded report binds its party's sensitivity run settings,
which name =sensitivity.xml= and =simulation.xml=, the =Risk Sensitivities=
engines, the six configuration types and the cut its name states. The plain name
selects =LIVE= and the "(EOD)" twin selects =EOD=, so a report on both cycles is two
definitions. What still stops a figure is the same for all of them, and
[[*What is not built][What is not built]] states it.

Three pages describe a ladder the design's list does not seed. The three-pillar is
the surface shift under its other name, so it is a reading of a report that exists
and not a second definition. The Volga and the Vanna wait on a stored shape for a
second-order and a paired figure.

* What is not built

The reports this folder does not yet describe, and the ones it describes that the
platform does not yet run, are two different lists.

- *The ladder family is seeded and cannot price.* Ten of the thirteen pages above
  describe reports a definition now states, on both cycles where the design says
  so. They are definitions like any other: they select a cut, bind their
  configuration and run the pipeline. They produce no figure, and the reasons are
  the ones that stop a sensitivity figure anywhere in the platform, not defects in
  a ladder:
  - *No mapper reads or writes the document.* A =SensitivityAnalysis= document is
    a name in a lookup and a row in the ORE file library, not a modelled entity, so
    a configuration can name it and nothing can read it. The round trip is
    backlogged as [[id:190620B4-2F86-44C0-B4B7-31EE2C07D3F9][Round trip the
    sensitivity configuration]].
  - *No shift size is stated.* The store names the document a ladder binds and
    states no size, so nothing says what a 0.1 bump, a basis point or a per cent
    is. The document holds the shift, and no table holds the document.
  - *No volatility market data and no spot.* The ACME seed's 420 curve quotes are
    all =IR_SWAP/RATE/...=. There is no =FX_OPTION/RATE_LNVOL= quote and no
    volatility surface configuration, so every volatility ladder shifts nothing.
    [[id:3D2A2BD4-4126-4E54-9046-A9E00966D898][Support volatility surfaces]] is the
    work that closes it.
  - *The report inputs are not complete.* The run package carries the four Setup
    documents and no analytic document of its own, so a document that no owner
    exports never reaches the engine. That is the subject of
    [[id:441E3343-F754-49B1-9763-960BBC2D4532][Complete the ACME report inputs and
    prove they run]], and a ladder waits on it with the rest.
- *No volatility market data.* Outside the ladder family this stops the option
  maps and the triple vol ladder, which need a surface to bucket the book by. The
  seed holds curves alone, so a run over an option book records the engine's
  refusal against itself.
- *The matrix reports are not described here.* Rho/Vol, Spot/Vol and Spot/Rho
  state two bumped inputs in one grid, which is a stress configuration rather than
  a sensitivity one. No ACME risk report configuration switches a stress analytic
  on.
- *The remaining catalogued reports have no page.* The catalogue on
  [[file:../domain/risk_reporting.org][Risk reporting]] names Bump and Reprice Spot Ladder, All
  Crosses, Spot Vol Ladder for the base and quote currency, Trade Level Ladder
  for the premium currency, Vol Manipulation and IPV Explain. Each states a scope
  or a measure the seed has no configuration for: a cross of every currency pair,
  a premium currency bump, or an IPV cut whose market data the platform does not
  hold.
- *The generic seed is behind the ACME one.*
  =projects/ores.sql/populate/reporting/reporting_report_definitions_populate.sql=
  seeds the operational reports for the generic provisioning path with no cut
  selection. It is a second statement of the same catalogue, so a tenant
  provisioned through it holds no intraday report; the ACME and Northwind
  datasets carry them.

The intraday reports that *are* seeded price from the live cut. The dataset
holds no volatility market data, so a body whose options need a surface has no
volatility to shift. That is a fact about the data and not about the definition:
the cut mints, the run records it, and the definition states a run whose phases
execute.

* Which entity runs which report

A report definition belongs to one party, and the parties of a group do
not run the same reports. The rules that choose the reports for each
Acme entity are in the Acme Corporation chapter of the user manual, under
"The reports each entity runs". The reason for each choice is in the
investigation [[id:6A1EE441-E132-4230-BCD9-E8BB786D721F][Which reports each ACME party runs]].

The ladder family is the one exception, and it is deliberate. The product owner
asked for it on 2026-11-04, so the family is decided before those rules: every
party holds the ten seeded ladders, the holding company included, and Northwind
holds them through the London rows its catalogue reads. A party that runs no
option book therefore states a volatility ladder it cannot price, which is the
point of the exercise: the reports exist, the list shows them, and the run that
stops says why.

* Adding a report

#+begin_src sh :results verbatim
compass add report \
  --slug <slug> \
  --title "<title>" \
  --description "<one line>" \
  --report-code <code> \
  --tags "report,<topic>"
#+end_src

=--parent-dir= defaults to =doc/knowledge/reports=, so it can be omitted. The
file is =report_<slug>.org=, and =--report-code= defaults to the slug. Fill in
every section the scaffold leaves, then add a row to the table above. The full
contract is on
[[id:4498456E-71DE-4250-8080-727690FAEFE6][Document type: report]].
