* Goal

When the export writes an ORE file, or the run document names one, it looks the name up in the file types table by file type. A parameter that names an input document is resolved through the bindings of the definition: the parameter definition refers to a configuration type, and the export writes the bound document under the well known name of its file type. A parameter that names an output or an intermediate file takes the default of its file type, and a configuration stores a value only to override it. Two analytics that share a file read one name.

* Acceptance

- The file types table classifies every file parameter of the ORE samples and of the official user guide: input or output, input document, data file, intermediate file or output file, its format and, for an XML file, its XSD. It replaces the classification of the parameter definitions that this task first planned, because the table already holds the name, the direction and the writer of each file.
- The export and the run store name every file from the file types table. The names hard coded in the run document builder and in the run store are removed.
- Each parameter that names an input document is filled from the binding of the definition. A definition that binds no document of the type fails the readiness check with a message that names the type.
- The simulation and the analytic that reads its cube agree on the cube file name by construction.
- Every exported ACME run document validates against the ORE schema, and its input files all exist in the exported package.

* Plan

1. Classify every file parameter as an input document, a data file, an intermediate file or an output file, from the ORE samples and the official user guide. Record the classification in the file types table with the direction, the format and the XSD.
2. Mark the files an analytic names by default, and link a file that one analytic reads to the file type of the analytic that writes it.
3. Replace the file names hard coded in the run document builder and in the run store with a lookup in the file types table.
4. Resolve each input document parameter from the bindings of the definition at export. A definition whose bound type no file type names fails with a message that names the type.
5. Make an intermediate file that two analytics share read one name.
6. Validate every exported package, and check that every file a run document names is in the package.

* Notes

The files are of three kinds. Input documents are dumps of domain entities: the export writes them from the database under a well known name, so no parameter needs to store the name. Analytic specific configuration documents, such as the simulation and the sensitivity configuration, are the same kind of thing and are bound as configuration types. Files the engine writes are not in the database, and the platform only needs their names to collect results.

Decisions made while building this.

- The classification lives in the file types table, so the parameter definition is unchanged. The first plan put it on the parameter definition.
- The canonical name of a file is the name the official ORE user guide gives it in its listings. A file the guide does not list takes the most common name in the 416 samples without a date. A name that few samples use for an input document that other analytics name too is not canonical, so the shared name replaces it.
- A file type marked as a default is one that at least half of the samples running the analytic name. The run document names the default files of an analytic unless the configuration states the parameter, and a stated value wins.
- A file one analytic reads and another writes takes the writer's name, including the name the writer's configuration states. The reader is named only when the writer is in the run and switched on.
- The analytic input documents, such as netting.xml and simulation.xml, are in the table with their names, their format and their XSD, but the export does not write the parameter that names them. No entity produces the document yet, so naming it would put a file in the run document that the package does not contain. The tasks that add the entities switch them on.
- The export finds the Setup parameter of a configuration type in the table. Nothing else in the export or the run store holds a file name.

* Result

The export names every file from the file types table. The generator, the run store and the ore service hold no file name. The Setup file of each configuration type, the default output files of each analytic and the files that one analytic reads from another all come from the table.

The table is richer than the first version: every row has a direction (input or output), a format (xml, csv, csv_gz, txt, dat or json), for an XML file the XSD that validates it, and a description of the purpose of the file, built from the official ORE user guide where the guide speaks and worded to claim no more than the guide supports where it does not. The canonical names are the guide's. A name that few samples use for an input document that other analytics name too is replaced by the shared name, and lists of files and name stems are not file types.

All 78 ACME runs export, validate against ore.xsd, name four Setup files each and carry those files in the package. The simulation, pfe and xva runs agree on the cube and scenario data names by construction.

Found on the way: the reporting service never registered the generated file type handlers, so the ore service could not read the table over NATS until the registrar was fixed. The analytic type, configuration type and parameter definition handlers are not registered either, and nothing needs them yet.

Not done: the analytic input documents (netting, collateral balances, simulation, sensitivity, stress and the rest) are in the table with names, formats and XSDs, but the export does not name them, because no entity produces the documents. The tasks that add them switch them on.
