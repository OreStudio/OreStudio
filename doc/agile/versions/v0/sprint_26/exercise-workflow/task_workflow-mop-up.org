* Goal

* Acceptance

- Two engine handlers can no longer lose each other's write on a step row, so a step that reports completion always advances its instance whatever the timing.
- The start path reports whether the engine accepted the run, so an unregistered type or a request with no steps fails at the shell instead of printing an instance id to follow.
- Each configuration has a name and a script that asserts its terminal state, and each script fails when the path it covers does nothing.
- The repeat-instance-id behaviour survives the race fix: supplying an id twice still leaves exactly one run.

* Plan

Three workstreams, in this order, because each is what makes the next one
trustworthy.

** 1. The step-row race

=on_start_workflow= calls =stamp_command_published= after it publishes, and
=on_step_completed= calls =set_step_state= when the answer arrives. Both are a
read-modify-write of the same row under optimistic locking, and the two
subscriptions are not serialised against each other, whatever the engine's own
header claims. The fixture answers in about two milliseconds, so the two
overlap; the three-millisecond window is the whole bug.

Reproduce it against a live fleet before changing anything. What it looks like
when it lands, from =ores.workflow.service='s log on the rebased #2184:

#+begin_example
Publishing step command:  step_index=0 step_name=one step_id=c3f1d1ce-...
Step-completed event received: step=c3f1d1ce-... outcome=completed
Workflow STARTED: step_count=2 first_step=one
ERROR Executing INSERT failed: Version conflict: expected version 1, but current version is 2
ERROR Unhandled exception in NATS message handler for subject '...events.step-completed'
#+end_example

and =workflow wait= then reports =[1/1] one: in_progress= until it times out,
with nothing the shell can report as an error.

The fix is not a mutex bolted on. If a publish can re-enter a handler on the
same thread, a non-recursive =std::mutex= deadlocks and a recursive one hides
the re-entrancy rather than removing it. Establish which of the two it is
first: the timestamps above say the completion is processed inside the start,
which is what a synchronous delivery on one thread would also look like, and
the two want opposite fixes.

** 2. A start that reports acceptance

=workflow start= prints "Dispatched", an instance id and a follow-up command
whatever happens. It did so for an unregistered type, for a request with no
steps, and while every workflow in the product was failing to insert. Three of
the four defects found on #2184 were invisible at the shell for exactly that
reason, and were read out of a log instead.

The reply must report acceptance and not completion. The start is a durable
JetStream publish and callers still poll for the terminal state, so this must
not quietly turn a crash-safe publish into a request/response transaction.
Record that where the reply is defined.

** 3. The configurations

Named, one script each, asserting terminal state rather than printing it. The
set designed on the identity workflow task: =happy_path=, =fan_out=,
=with_warnings=, =fail_fast=, =saga=, =long_running=, =recovery=, =empty= and
=unknown_type=.

=--instance-id= is what makes this one invocation per configuration rather than
two, so a script can start a run under a name it chose and then wait on it.

Each script must fail when the path it covers does nothing. That is the point of
the task, and it is why the race comes first: a configuration written on top of
it would pass whenever it happened to win.

* Notes

The fixture needs no other component's data, so every configuration runs as
=super_admin= in the system tenant. Drive it from =ores.shell=:

#+begin_example
compass shell -l <script>.ores
#+end_example

=--load= runs a script non-interactively and exits. A script cannot read a
command's output back, which is why a run that has to be followed is named by
its caller:

#+begin_example
workflow start identity_workflow '{"steps":[{"name":"one"}]}' --instance-id <uuid>
workflow wait <uuid> --expect-steps 1
#+end_example
