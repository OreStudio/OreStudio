This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A signed-in person compares what the compute nodes have against what a job needs and what is scheduled to arrive soon, and judges whether the grid can absorb it.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want to know whether the grid can take what is coming." The person picks a
horizon and reads one screen: what capacity the nodes have, how much of it the
grid is using, what a job needs to run, and what is scheduled to arrive inside
the horizon. The journey is done when the person can say whether the grid has
headroom for the work that is about to arrive, and which resource is the
constraint.

* Actor and trigger

The actor is what the rows admit, and the session decides the rows. A tenant
sees its own arrivals; the super administrator sees the installation's fleet.
This is one journey: the activity is the same "can the grid take this" at two
visible sets.

The fleet rows are the installation's: the nodes and their capacity describe
machines the installation owns, so they are read whole. The arrivals are a
tenant's, so they narrow to the session's tenant. The allocation by tenant is
not this journey's panel: it moved to the Watch the grid screen's Usage tab,
where the installation reads the usage ledger it keeps about its own operation.
This journey reads the fleet and the arrivals
([[id:5A5D6490-AF64-4AAF-8B3D-48EF3EDAF3D2][Tenant ownership and the
information flow]]).

The trigger is a change to either side: a node was added or drained, a release
needs more memory than the fleet has, or a schedule is about to fire a large
batch. The person opens the capacity screen to compare the two sides. The
journey ends when the headroom question is answered.

This journey writes nothing. It reads the host registry, the app version
requirements, the samples and the scheduler's status. It does not add a node,
change a schedule or stop a job.

* Steps

1. *Open the capacity screen and pick a horizon.* The person opens the screen
   and picks how far ahead to look, for example the next day or the next week.
   The system answers over that horizon and draws the arrivals and the usage
   against one time axis.
2. *Read what the nodes have.* The system states each node's capacity from the
   host registry: =cpu_count=, =ram_mb= and =gpu_type=, with the node's
   =external_id= and =display_name=. This is the grid's ceiling, and it does
   not depend on any sample
   ([[id:0739BC05-3713-4695-8B7B-04D9DBA1AEE0][ores.compute.host]]).
3. *Read the headroom.* The system draws used against total capacity in each
   interval. The total is the host registry's. The usage the grid records is
   coarse: =grid_sample= states how many hosts were online and how many were
   idle, so the headroom is drawn in hosts and not in cores, memory or GPUs.
   The screen must say which unit it is drawing, because a headroom in hosts
   is not a headroom in memory.
4. *Read what a job needs.* The system states the requirements a job carries.
   The app version states a =min_ram_mb=, and its platform row states the
   triplet the package was built for: =code=, =os_family= and =cpu_arch=. A job
   is a =workunit= that names its =app_version_id=, its =priority= and its
   =target_redundancy=
   ([[id:1E563104-6F89-4858-9395-D869A7E817A6][ores.compute.app_version]],
   [[id:256097D3-ED41-40C3-99DC-C61C6B13E80A][ores.compute.platform]]).
5. *Read the requirements matrix.* The system draws the open jobs against the
   nodes that can hold them: memory against =ram_mb=, platform against the
   node's triplet, and a GPU need against =gpu_type=. A job whose
   =min_ram_mb= is above every node's memory, or whose platform no online node
   runs, is a job the grid cannot start, and the matrix is where that shows.
6. *Read the upcoming arrivals.* The system draws a timeline of the scheduled
   runs ahead of now. The scheduler answers with each job's =job_name=, its
   =schedule_expression=, its =next_fire_at=, its =last_run_status= and its
   =running_count=, so the person sees what fires and when
   ([[id:BD750888-6B72-48C1-AE74-DDC535705022][ores.scheduler.job_definition]],
   [[id:3D1E9A64-7C2B-4F58-9E01-6A5D2C4B8E17][ores.scheduler.scheduling_operations]]).
   What each arrival needs is not on the scheduler's answer: a scheduled run
   submits a batch, and the batch's jobs and their requirements exist only after
   submission. The timeline shows when, and the requirements matrix shows what,
   and the two join only for work that has been submitted.
7. *Judge the constraint.* The person compares the three: the ceiling, the
   usage and the arrivals. The answer is a sentence about one resource, for
   example "the grid has memory for tomorrow's batch and no node runs its
   platform".
8. *No capacity data.* No sample is stored for the horizon, or no host row
   describes the fleet. The screen says the capacity is unmeasured and does not
   draw a ceiling from an empty table.
9. *Leave, or go on.* A constraint that is a busy grid continues in
   [[id:32ECF41B-B27B-4A69-B7F0-A4131F993297][Watch the grid]]. A constraint
   that is a release's memory need continues in
   [[id:19A796E3-A594-4C3E-8ACA-646D743BB496][Keep what the grid runs]].

* Screens and wireframes

One screen. The horizon bar, the host capacity table, the headroom chart, the
requirements matrix and the arrivals timeline are panels of that screen,
because the person reads them as one answer. The screen is read-only: it
creates nothing, changes nothing and destroys nothing. The allocation chart
left this screen for the watch screen's Usage tab.

The panels are the charts [[id:0169FDD7-9B88-4766-9AE9-93FE87200700][Compute
journeys]] names for planning capacity:

| Panel | Chart | Answers |
|-------+-------+---------|
| Headroom | *Capacity headroom* | Can the grid take more? |
| Arrivals | *Upcoming arrivals* | What kicks in soon? |
| Matrix | *Requirements matrix* | What does each job need? |

The headroom chart is a stacked area of used against total. The grid does not
measure a node's used cores, memory or GPUs, so the panel can draw only the
part the samples support, in hosts, and it must not draw a used line it cannot
fill.

Every list on the screen pages on the server, per the
[[id:2BF7F03F-6BF4-45FF-8E26-4D3B4E2D943D][Record screen standard]]. The host
capacity table, the requirements matrix and the arrivals timeline each carry
First, Previous, Next, Last, a page size and Load all, with the page and the
page size held in the address. A new search, a new filter, a new order or a new
page size returns to page one, and Load all is offered only when the server's
total is 1000 or less. No list reads with a fixed large limit, and none pages to
the end to show everything.

The host is the only row that states capacity. The node sample states what a
node did, not what it used: it carries task counts, durations and bytes, and no
cores, memory or GPU in use. The requirements matrix therefore compares a job's
stated need against a node's stated capacity, and the headroom chart can report
usage only in the units the samples carry.

* Operations and messages

#+ATTR_HTML: :class hug-leading
| Step | Operation | Subject | Status |
|------+-----------+---------+--------|
| Read what the nodes have | Read the host registry | =compute.v1.hosts.list= | exists |
| Read the headroom | Read the grid samples in the horizon | (no range read) | missing |
| Read the headroom | Read the node samples in the horizon | (no range read) | missing |
| Read what a job needs | Read the app versions and their platform rows | =compute.v1.app_versions.list=, =compute.v1.app_version_platforms.list= | exists |
| Read what a job needs | Read the waiting jobs | =compute.v1.workunits.list=, =compute.v1.batches.list= | exists |
| Read the arrivals | Read the scheduler's job status | =scheduler.v1.status= | exists |
| Read the arrivals | Read what a scheduled run will need | (nothing until it submits) | missing |
| Refresh | Read the horizon again | (the reads above) | missing |

=scheduler.v1.status= carries no request fields and answers with every job the
caller can see, each with its schedule, its last run and its =next_fire_at=.
It is the arrivals read, and it is the scheduler's, not the grid's.

The grid's own reads are the host registry, which is complete, and the sample
range read, which does not exist. The requirements matrix reads two entity
lists that already exist. The allocation chart's reads live with the watch
screen's Usage tab, which owns that chart now.

The browser reads the screen through a hand-written BFF route on the
[[id:6A63AAC7-4869-493A-97E7-55B919874784][journey runtime]]. No route serves
a compute screen yet.

* What is missing

1. *No usage over time.* The headroom chart spans time and the grid read
   answers with the newest sample alone. The poller keeps writing samples that
   no read returns, so the chart has no series to draw
   ([[id:E7035C69-EB6E-4158-B384-825A8CDACA8A][The grid has no usage
   history]]).
2. *No measured usage per resource.* The host states total cores, memory and
   GPU, and no row states how much of any of them a node is using. The node
   sample reports tasks, durations and bytes. The headroom chart cannot draw a
   used line in cores, memory or GPUs today, and the candidate is to carry the
   node's in-use figures on the sample or a new resource sample.
3. *The arrivals have no requirements until they are submitted.* The scheduler
   says when a job fires and nothing about what the run will need. The
   requirements matrix and the arrivals timeline therefore describe different
   sets: submitted jobs on one, scheduled jobs on the other. This is the open
   question the use cases raise, that "what is scheduled to kick in soon" is the
   scheduler's question and the grid's is what it does to the load
   ([[id:0169FDD7-9B88-4766-9AE9-93FE87200700][Compute journeys]]).
4. *The grid serves one tenant's slice.* The grid read filters by the session
   tenant, so a headroom chart drawn from it would report one tenant's hosts as
   the fleet ([[id:3621E2BC-2670-4E59-8721-32F86B640F24][The grid read is
   scoped to the session tenant]]).
5. *A wrapper consumes one tenant's work.* Capacity that is planned per tenant
   must account for the wrapper subscribing to the system tenant's assignment
   subject alone, which leaves another tenant's dispatched work with no node to
   run it. The plan would reserve capacity for work the fleet cannot pick up
   ([[id:0072F772-F879-4DDB-8944-96433843CE17][The wrapper consumes one
   tenant's work]]).
6. *The quotas and the fair share are targets, not rows.* The design for
   thousands of runs gives each tenant a weight and a cap on its assignments in
   flight, and each tenant and party a limit on running runs. Those numbers are
   capacity-test targets, and no table holds them, so the requirements matrix
   cannot state a tenant's own cap
   ([[id:B3165E6F-AE8C-4DBD-8F87-2EC4F276FCF0][Report execution at scale]]).
