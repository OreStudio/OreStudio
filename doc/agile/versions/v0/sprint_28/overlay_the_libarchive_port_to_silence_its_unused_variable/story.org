#+title: Story: Overlay the libarchive port to silence its unused variable

* Decisions

- *An overlay port is the only lever short of touching the submodule.* The
  unused-variable check lives in =vcpkg_cmake_configure= and runs
  unconditionally; there is no global switch, and =MAYBE_UNUSED_VARIABLES= is
  per-call, so it can only be fixed in the portfile. The alternatives are a
  dirty submodule, which the next bump discards, or an overlay.
- *Upstream cannot be bumped to fix it.* The master libarchive portfile still
  passes =CMAKE_REQUIRE_FIND_PACKAGE_MbedTLS= without listing it, so the entry
  is missing at every version rather than at the pinned one.
- *The overlay vendors the pinned port and changes one line.* It copies
  portfile.cmake, vcpkg.json, usage, vcpkg-cmake-wrapper.cmake.in and the two
  patches, and adds the missing variable to MAYBE_UNUSED_VARIABLES. Everything
  except that line and a comment is byte identical, which is what makes the
  copy reviewable. The cost is a re-sync on every vcpkg bump, and the overlay
  must be dropped once upstream lists the variable.
- *boost-system gets no overlay.* That port warns through
  =vcpkg_buildpath_length_warning(37)= when the buildtrees path exceeds 37
  characters, and the warning is correct: our Windows path is about 68
  characters. Deleting the call would hide a real MAX_PATH advisory rather than
  fix it, so the story records the options instead of taking that one.

* Out of scope

- The boost-system build-path warning. It is fixed by a shorter vcpkg root on
  the Windows runner, not by a port.
- Reporting either warning upstream.
