* Acceptance

- A refused completion leaves every leg a draft and writes no member.
- A completed structure has every leg live and unauthorised.
- A second completion answers already_exists.
- The reply carries the structure's internal version.
- A database-backed test proves the rollback.

* Plan

The operation is =trading.v1.ops.complete_structure=, served beside the booking
because it writes the same things a booking does: a trade to live, and now a
structure and its members around it.

Two pieces came first. The execution a leg needs was inside =execute_trade=,
which opened its own transaction; it is now =execute_within=, taking the caller's
context, so a leg goes live inside the completion rather than beside it. And the
structure is written through =structure_service=, not the repository, because that
is what names it: a deal a person reads later carries a reference rather than a
uuid.

The order inside the unit is the order the checks imply: count, then existence,
then every leg, then the structure, then the members, then the executions. A
refusal anywhere before the writes returns before the transaction opens or leaves
it to roll back, so the legs stay drafts and no member is written.

* Result

A structure is completed in one unit: its anchor, its members, and every leg
taken live.

| Piece | Where |
|-------|-------|
| The subject | =trading.v1.ops.complete_structure= |
| The messages | =complete_structure_request= and =complete_structure_response= in [[proj:projects/ores.trading/modeling/ores.trading.trade_operations.org][trade_operations]] |
| The service | =trade_operations_service::complete_structure= |
| The shared execution | =trade_operations_service::execute_within=, which takes the caller's context |
| The reply | the structure's id and the version it is at after the write |

The checks run before any write: the leg count against the list, the structure
against the store, and every leg against the trade, its state and any structure
that already holds it. The structure is then named by its own service, the
members follow, and the legs are executed last, all in the caller's unit of work.

* What the cases prove

- A completed structure holds every leg live and waiting on Operations, and each
  leg is a member of the structure just made.
- A second completion of the same id answers =already_exists=.
- A completion whose list is shorter than its count is refused, and every leg is
  still a draft with no member and no request.
- A completion with a leg that is already live is refused, and the leg beside it
  is still a draft with no member.
