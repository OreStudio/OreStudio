* Acceptance

- A policy naming an ordinary table and a row delete removes the rows past its period, proved on the delivery counts

* Plan
* Plan

** What blocks it, and what the two actions need

The sweep performs =drop_chunks= on a chunked table and records every other
policy as =skipped= with "the sweep applies only a chunk drop today"
(=projects/ores.sql/create/scheduler/scheduler_retention_sweep_create.sql=).
The model states three actions, so two are inert.

- *A row delete needs a time column.* Deleting the rows past a period means
  comparing a column to the cutoff, and the policy does not name one. The
  policy grows a column for it, which is a model change: the entity, the SQL,
  the protocol and the web types are generated from
  =ores.scheduler.retention_policy=. The alternative — a table of known
  (table, column) pairs in the sweep — puts the same fact in code where nobody
  reads it, and makes a new store a deployment.
- *An object expiry needs the object store's own API.* The storage service
  holds the objects, so the sweep asks it to expire a prefix rather than
  reaching past it. The target is the bucket and prefix the policy names, and
  the number the run records is the bytes the service says it removed.
- *The write must refuse what the sweep cannot do.* Reporting a skipped policy
  after the fact is how a store reads as bounded while nothing bounds it. The
  validation belongs on the policy write: an action outside the set the sweep
  performs is refused when it is stated, not discovered at 03:00.

** Then the policies themselves**

With the actions working, the two stores the validation found are declared:
the delivery counts (an ordinary table, about 27,000 rows an hour) and ticks (a
chunked table whose chunks are already cut on the write instant). The policies
are rows of the system tenant, delivered as platform data like the report
outputs' three.

** Verification**

- pgTAP: a delete-rows policy removes the old rows and keeps the recent ones;
  a drop-chunks policy on ticks removes a chunk; an unsupported action is
  refused by the write.
- The sweep's own run on a recreated database, read from the runs ledger.
- The delivery counts stop growing past their period in a measured run.

* Result

The sweep applies both actions a database can perform, and it now reads the
catalogue for the store behind each policy: the shape, the target and the column
a delete compares are stated once, and a policy that has drifted from its store
is reported rather than acted on. A row delete compares the catalogue's column,
checked against the table first, so a store whose column is gone is reported
instead of deleted from by a guess.

The other two actions are not the sweep's to perform. An object prefix lives in
the object store and a job's folder on a node's disk, and SQL reaches neither. The
sweep records them skipped with the owning mechanism named in the detail, and it
no longer pretends to have bounded the store. The bounds view is what a screen
reads: it states, per store, which mechanism bounds it and whether that mechanism
applies today, so a policy that names an unbuilt mechanism reads as unbounded
rather than as bounded on paper.

Two findings came out of the work. The sweep had never run as the service user,
only as an administrator, so its rights had never been tested: it deletes from
tables other components own and calls a TimescaleDB function it was not granted.
It is now a definer function, with the targets taken from platform data and the
column checked, which is the smaller right of the two available. And the ledger
has to be read per tenant, or one tenant's run suppresses another's policy.
