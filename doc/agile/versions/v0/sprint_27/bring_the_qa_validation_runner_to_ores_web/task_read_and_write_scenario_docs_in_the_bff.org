* Goal

* Acceptance

- The store lists every scenario with its state, target, story and task, and tells waiting from done.
- The store reads a scenario's steps, each with its client, status and note, and the ids of its story and task.
- The store finds any doc under the doc root by its :ID: property.
- The store records each step's Result table and the overall State and Results in place, in the format the compass template creates.
- A write that would leave the doc root is refused, and a write names the steps it changes.
- Tests run against copies of real compass-created scenario docs: single client, several clients and an earlier result.
- A test fails when a doc made by the current compass test_scenario template does not parse, so a change to the template shows up here.
- A doc id resolves only to a file inside the doc root, and a path with .. is refused.
- Two saves of one scenario do not merge. The last write wins, and the task states it.
- The doc root is configuration. No code path runs compass.

* Plan

Three layers, each in =projects/ores.web/packages/bff/src/scenarios/=.

1. =scenario-doc.ts= is pure. =parseScenario= reads the text of a scenario doc. =recordRun= returns new text with a run written in. It uses the =@ores/org= outline, so it edits lines in place and leaves every other line alone.
2. =scenario-store.ts= is the interface: =list=, =read=, =readDoc=, =record=. A database store can replace the files later.
3. =file-scenario-store.ts= keeps scenarios as files under a doc root. A scan reads the head of each .org file for its :ID:, and an id lookup finds only a file the scan found. A write goes to a temporary file and is renamed over the doc.

Decisions:

- A client is a level-two heading that has a child other than =Result=. The Clients cell is not trusted, because the template says the cell is blank for one client and old docs disagree.
- A step is named by its client and its title. A save that names a missing step, or a title the doc repeats, refuses the whole save.
- A closed Results status (PASSED or FAILED) outranks the State row, because the Qt runner wrote only the Results table. 89 scenarios in the corpus show PASSED there with State at PENDING.
- A save sets Status and Notes in a Result table and keeps any other row, so a later task can add an image row.
- The doc root is =ORES_WEB_DOC_ROOT=. Unset means the runner is off.

* Notes

- Two saves of one scenario do not merge. Saves to one file run one after the other, and each writes only the steps it names. The last save to name a step wins that step. A step that only the first save named keeps the first save's result.
- A save writes the whole doc back with the doc's own line end and a final line end. A byte order mark is dropped.
- A note goes in one table cell. A line end becomes "; " and a pipe becomes "/", as in the Qt runner.
- The scan does not follow a symbolic link. Before a read or a write, the real path of the file must sit inside the real doc root, else =PathEscapeError=.
- The tests read the two scenario fixtures of the =@ores/org= package. A second copy would repeat their :ID: in the corpus.
- Nothing calls compass. A test renders the current =doc_test_scenario.org.mustache= template and parses it, so a change to the template shows up there.
- A call for the Tests queue reads one index entry per doc and caches each scenario summary by file time and size. The first call after a start scans the tree.

* Result

The BFF has a scenario store in projects/ores.web/packages/bff/src/scenarios. A pure codec, scenario-doc.ts, reads a scenario doc with parseScenario and writes a run into its text with recordRun. The write changes only the Result tables of the steps it names, the Results table and the State row, and every other line stays. The store sits behind the ScenarioStore interface, and the file store keeps its docs under ORES_WEB_DOC_ROOT. It lists scenarios, reads one with its steps, finds any doc by its :ID: and records a run. Nothing calls compass.

A client is a level-two heading that has a child other than Result, and a step is named by its client and its title. A save that names a missing, repeated or doubled step refuses the whole save. A closed Results status outranks the State row, because the Qt runner never updated State: 89 old scenarios show PASSED in Results with State at PENDING. Of the 134 scenarios in the repository, 16 are waiting.

The tests number 47 for the store and 2 for the config, and the BFF suite passes with 456. They use the two real fixtures of @ores/org, the current compass template rendered and parsed, and every scenario doc in the repository, each taking a full run back without losing a step. Removing the root guard, the id check, the shared scan, the retry after a failed scan or the long head read each fails its own test. The review found three real faults in the first scan code, and all three are fixed. A save is a read and a rename, so an editor that saves between the two loses its edit. Last write wins, and task 5 may add a conflict check. Task 3 serves the store and maps its errors to statuses.
