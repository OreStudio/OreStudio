* What

Commit =119efdee23= ("[assets] Apply the generation and clear the superseded
hand-written files") regenerated =projects/ores.sql/create/assets/assets_images_create.sql=
from the assets model. The file had carried a hand-written
=ores_assets_get_template_image_fn=, and the generated replacement does not.
Nothing defines the function anywhere in the tree today.

Three callers still expect it:

- =projects/ores.sql/create/refdata/refdata_publish_from_dq_create.sql:2370=
  calls it in the LEI party publish, to attach the system tenant's template logo
  to a known-LEI counterparty.
- =projects/ores.iam/core/include/ores.iam.core/messaging/tenant_provisioning_handler.hpp:1048=
  selects from it when it copies the template logo.
- =projects/ores.sql/create/iam/iam_service_db_grants_create.sql:148= still grants
  =execute= on it to =iam_service=, so the grant itself outlived the function.

* Why

A freshly recreated database can no longer provision the Acme tenant. The
tenant-aware workflow engine fix let the base bundle publish leave step 0 for
the first time, and it then failed on the missing function. The provisioning
record on the day reads:

=✗ Failed to provision Acme tenant: Query execution failed: ERROR: function
ores_assets_get_template_image_fn(unknown) does not exist=

This is the same class the generation gate exists for: a hand-written SQL object
lived inside a generated file, so regenerating the file deleted it silently.
Either the model must express the function (as the assets publish-from-DQ and
RLS scripts now are), or the function must move to a hand-written file that the
aggregator includes.
