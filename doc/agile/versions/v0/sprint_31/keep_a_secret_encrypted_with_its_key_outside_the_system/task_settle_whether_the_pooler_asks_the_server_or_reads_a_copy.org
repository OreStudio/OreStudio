the server for a client's verifier instead of holding a copy of it. Nothing
called it, so the choice was to wire it or to remove it. This task removes it,

* Acceptance

- The function, its drop script and both entry-point lines are gone, so a fresh
  database holds no mechanism nothing calls.
- Nothing in the tree names =ores_pooler_auth=, =auth_query= or =auth_user=, so
  the pooler's configuration is the path it actually runs.
- The reason the pooler reads verifiers rather than asking the server is written
  where a reader of the pooler looks, so the decision is not re-opened as an
  oversight.

* Plan

The capture left two ways, and one of them had to be taken. This task takes the
second: the function goes and the verifier copies stay.

Wiring the pooler to ask the server costs a database role that the pooler logs
in as. That role may read every verifier in the instance, which is a wider view
than the pooler's own: it serves a named set of accounts, not the deployment.
Wiring also costs a lookup function installed in each database the pooler
fronts.

What wiring buys is a pooler restart saved after a rotation. Each service
resolves its password at start, so a rotation restarts the services, and the
pooler's restart rides along in the same step.

* Result

* Promoted from capture

Captured 2026-11-28 in the product backlog; promoted preserving the UUID.

** What

=ores_utility_pooler_auth_lookup_fn= exists so a transaction pooler can ask the
server for a client's verifier instead of holding a copy of it. Nothing calls it.
Settle it: wire the pooler to ask, or remove the function and keep the copies.

** Why

=start_ci_pooler.sh= writes =auth_type = scram-sha-256= with an =auth_file=, and
the file is filled with verifiers that =compass vault provision= reads from
=pg_shadow= and writes under =build/keys=. No configuration anywhere sets
=auth_query= or =auth_user=, so the function, its drop script and its two
entry-point lines are the whole of its life. A standards review over PR #5220
found that, and the PR merged with it recorded rather than hidden.

Wiring it is the better design: a rotation then needs no pooler restart and no
copy of anything lives under =build/=. It costs a login role for the pooler
itself, which is one more credential in the environment file — the very thing the
register's second phase removed from the services.

Removing it keeps the verifier files, whose cost the register already states: a
verifier is useless without the password, and a rotation needs a pooler restart.

Doing neither is the only wrong answer, because a function nothing calls reads as
a mechanism that exists.
