* Goal

A scheduled report run acts as the tenant and the party of its definition, with
no caller present. The steps of the run read and write the owners' data through
their operations, and row-level security applies as it does for a person.

Today a step calls the owners with its own service identity, which acts for the
system tenant and sees no party rows. This story builds the
[[id:C79B5E4D-71D0-44C2-9D06-444EA2AC1CB7][Scheduled Work Acting as a Tenant]] pattern as [[id:78B82824-0BBB-4442-A9FA-E1F265DF57BD][Run grants and run tokens]] specifies it, and wires it into reporting as
[[id:B3165E6F-AE8C-4DBD-8F87-2EC4F276FCF0][Report execution at scale]] describes. It unblocks the backlog task "Package the run input
through the owners' operations", in the story Complete the ORE report
configuration, which needs a run token to call the owners.

* Acceptance

- IAM stores run grants and serves =iam.v1.run_grants.create=, =revoke=, =get=
  and =exchange=, with the checks and claims the IAM page states.
- A run token carries the grant's tenant and one party, the role's permissions
  intersected with the grantor's, and the =act=, =grant_id= and =run_id= claims;
  every issue is logged.
- Every step service obtains run tokens through one shared cache in
  =ores.service=.
- Reporting creates, revokes and re-creates grants with the schedule, and
  suspends a definition whose grant lapses.
- A live test: a scheduled run's step reads a party's configuration document
  through its owner with a run token, and the same read with the service token
  returns nothing.
