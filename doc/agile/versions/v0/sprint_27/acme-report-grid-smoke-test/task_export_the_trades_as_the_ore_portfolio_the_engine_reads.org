* Relationship to the redesign

This task is the near-term unblock: it maps the trades blob the run gathers
*today* so ORE proceeds past "Build Portfolio". The shape of that blob is
about to change — [[id:004B0E88-1BB6-4323-A579-EEB56C29BA3F][Gather a run's inputs by declared dependency]] replaces the
one export with a trade set's archive at an as-of, and gives the mapping its own
task there ([[id:18FFC5F4-6DEB-4E7F-B0C5-ECC359ED5A82][Map a book's archive into the ORE portfolio]]).

Whichever lands first, the same thing is built underneath both: the reverse of
=trade_mapper= and of the instrument mappers. Build that once. If the redesign
lands first, this task dissolves into it and should be abandoned rather than
carried.

* Acceptance

- The run's portfolio input is ORE-readable, placed at the path the run document
  names, exactly as the market data and the fixings now are.
- The engine proceeds past =Pricing: Build Portfolio= rather than failing with
  =Failed to run analytics PRICING,XVA=.
- Every trade the run gathered appears in the portfolio, carrying the instruments
  and envelopes the engine needs to price it.
- The reverse walk lives beside the forward one, so adding an instrument to the
  import mapper without its export counterpart fails a test rather than losing a
  trade silently. That is the property worth having: the two directions are one
  fact about one schema, and nothing today makes them move together.

* Plan

The chain, and where it broke. =gather_trades= asks
=trading.v1.ops.export_trades_to_storage= for the run's trades, which writes the
=export_portfolio_response= -- the trades and their instrument batch -- as
msgpack. =prepare_ore_package= then downloaded that blob and wrote it at a
hardcoded =trades.msgpack=, so nothing ever put a portfolio where the run
document says one is.

*Correction to the first reading.* The export walk already exists. It is
=ores::ore::xml::exporter::export_portfolio= in
=projects/ores.ore/core/src/xml/exporter.cpp=, with the per-instrument reverse
mappers beside the forward ones in =ores.ore.core/domain/= (=reverse_swap=,
=reverse_bond=, and so on). It reads the response's trades and instrument batch,
rebuilds each trade's instrument from the batch by trade id, reverse-maps it,
and renders the result with =save_data(const portfolio&)=. It was written for
the roundtrip harness and has a production caller in the shell's portfolio
export, so the gap was one unconnected call, not a missing walk.

So the work was one half, not two.

*Placement.* =run_store.hpp= declares =run_data_files::portfolio=, the path the
run document names, and =report_package_handler.cpp= already writes the market
data and the fixings at their declared paths. The trade branch was the odd one
out. It now decodes the gathered blob, calls =export_portfolio=, writes the
result at =places.portfolio=, and refuses the run when the run document names
no portfolio, because ORE requires that name and a package without it cannot
price.

Where the export lives is right as it stands: =ores.ore= owns the ORE schema,
the XML facet owns the rendering, and =ores.ore.core/domain/= owns the
per-instrument walks. The reporting chain asks for a portfolio; it does not
know how one is built.

*Risk.* The redesign ([[id:18FFC5F4-6DEB-4E7F-B0C5-ECC359ED5A82][Map a book's archive into the ORE portfolio]])
needs the same reverse walk against a trade set's archive instead of the run's
one blob. =export_portfolio= is already a function of the rows rather than of
where they came from, so both callers share it. The shape of the stored blob is
the remaining coupling: it is the export response, and
[[id:3653CE61-84B8-4B77-9BBA-8D718A4B2F93][Carry the export's instruments as typed batches]] changed it while this task was
open. The first draft decoded a bare vector of =trade_export_item= and stopped
compiling after that change landed; the rebase moved the decode onto the
response. A future change to the stored shape reaches this call site.

* Result

*The task was mis-sized, and the correction is the substance of this record.*
The premise "no trades-to-ORE-portfolio exporter exists" was false when the
work started. =ores::ore::xml::exporter::export_portfolio= has been on trunk
since PR 2628 and already does the whole reverse walk: it takes the export's
trades and instrument batch, rebuilds each instrument by trade id, reverse-maps
it through the per-instrument mappers, and renders the portfolio with
=save_data(const portfolio&)=. It has a production caller in the shell's
portfolio export and a corpus-wide round-trip suite behind it. What was missing
was one call on the run path. The task's own note said to build the reverse
walk once and to abandon this task if the redesign landed first; neither was
needed, because the walk was already built.

*What changed.* =report_package_handler.cpp= no longer writes the gathered
trades at =trades.msgpack=. It reads the blob as the stored
=export_portfolio_response=, calls =export_portfolio=, and writes the result at
=places.portfolio=, the path the run document names. A run document that names
no portfolio is refused, and so is a stored export marked failed.

*Acceptance, bullet by bullet.*

1. Placed at the declared path -- done in code; the test asserts the path
   =declared_data_files= returns for a real run document.
2. The engine proceeds past "Build Portfolio" -- *not observed*. This needs a
   build and a run, and this environment does neither. It is the hourly
   validation's to confirm.
3. Every gathered trade appears -- the exporter writes a trade it cannot
   reverse-map as its type and envelope rather than dropping it, and
   =xml_exporter_directory_roundtrip_tests.cpp= already asserts that every
   mapped trade in the ORE corpus reaches an output.
4. The reverse walk sits beside the forward one and a one-sided change fails a
   test -- already true on trunk, by that same corpus suite. No new test was
   needed for it.

*What was not done.* No build, no test run, no database recreate -- by the
standing workflow, the agent does not build. The change is inspected
statically: =clang-format= clean on both sources, org links resolve, =compass
lint= clean.

*The rebase.* The first draft decoded a bare =std::vector<trade_export_item>=.
That stopped compiling when [[id:3653CE61-84B8-4B77-9BBA-8D718A4B2F93][Carry the export's instruments as typed batches]]
landed and replaced the instrument payload with a typed batch, and made the
storage export store the whole response. The rebase moved the decode onto
=export_portfolio_response= and passed the batch to =export_portfolio=.

*Kept for later.* The `Failure to run analytics PRICING,XVA` message cannot be
cleared by this change alone. The run also needs its compute packages published
and an ORE engine that accepts the portfolio this renders.
