* Goal

The batch list reads newest first, and the workunit and result lists can be ordered by their recording time, through the generated order field.

* Acceptance

- The batch, workunit and result models declare the recording time sortable and the batch model declares a default order of newest first.
- A list request that names the recording time returns pages in that order, and any other unsorted field is still refused.
- The Jobs routes read the batches newest first and a live check shows the order against the recording times.

* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

1. The recording time is not a model column. It is the audit column
   =valid_from=, and the domain calls it =recorded_at=. A list names a field
   as the wire names it, so the generator needs a field whose wire name and
   stored column differ.
2. Add the flag =:sortable_recorded_at: true= to the entity flags. The
   generator then adds the sortable field =recorded_at=, stored in
   =valid_from=. The default order may name it, as =recorded_at desc=. The
   flag is refused on a current-state entity, which has no =valid_from=.
3. Emit the column lookup in the repository only for an entity that sets the
   flag, so no other component's generated code changes.
4. Set the flag on the batch, workunit and result models. The batch model also
   sets =:default_order: recorded_at desc=. Index the column, because a model
   makes a column sortable only when it is prepared to index it.
5. Regenerate the three repositories and the three table scripts. Test the
   order against the store.
6. Read the batches through the BFF and compare the page with the database.

* Notes

- The key stays the last tie-break. Four batches written in one second show
  the same =recorded_at= on the wire, which has a resolution of one second, and
  the service still orders them by the stored microsecond time.
- The stored time is that of the current version of the row. A batch whose
  status changes is recorded again and moves to the top. The list is therefore
  ordered by the latest change, not by creation. A page that is open while a
  batch changes can show that batch twice or skip one. The story accepts this
  in a decision. A creation time needs a column that the models do not hold.
- A running BFF that still sent =descending: true= read the batches oldest
  first after the service changed. The default order is now descending, so the
  stated direction reverses it. The BFF now sends no direction, and the web
  service was restarted to run that code.
- The workunit and result lists accept =recorded_at=. Neither has a default
  order yet, so they read in key order. A screen that wants the runs in the
  order they were started can state =recorded_at=.
- The result index on =workunit_id= gained =valid_from=, which replaces the
  old index with a longer one. The workunit model gained an index on
  =batch_id=, which it did not have. The three index definitions were built
  inside a rolled-back transaction on the live database. A full database
  recreate was not run for them.
