* Goal

A report definition is ready to run only when every configuration document its report type and analytics need is published and bound. Step one adds the DQ tables that store those documents and the publish that writes them to the owning component. Step two populates ACME's datasets, crafted for the reports each party runs and inspired by the ORE samples, and publishes the bindings, with declared dataset dependencies in the order configurations, then definitions with bindings, then risk configurations. The earlier analysis already says which documents each report reads, and this task builds on it and does not repeat it.

* Acceptance

- Every configuration kind that an ACME report reads has a DQ staging table, an artefact type and a publish function that writes the owning component's tables, party scoped and idempotent. The kinds are the four the risk type requires (pricing engines, today's market, curve configuration, conventions) and the extras the analysis names (simulation, sensitivity, stress test, counterparty information, netting set definitions).
- Each ACME party has a dataset per kind, crafted for the reports that party runs. A dataset declares its dependency on the data it needs.
- After a clean provision every ACME definition has a binding for each configuration type its report type requires, and the extras its analytics need. No ORE import runs.
- The reports that read a kind nothing can store yet are listed with what they wait for, and the report design is reconciled with that list.

* Plan

Two parts, in this order, as the product owner decided on 2026-10-11.

*Part 1. The DQ tables that store the data.*

1. Take the inventory against the current tables. The existing analysis lists
   what each report reads. Check each kind against what the schema holds today
   and mark it as stored, stageable or unstorable. A kind with no owning table
   gets its entity first.
2. For each kind, add the DQ staging table and its artefact type, and the
   publish function that writes the owning component's tables for the party a
   publish names. The codegen flag that generates a staging table from an entity
   model is the route, as the instrument conventions took.
3. Add the publish of the bindings between a definition and its documents, and
   change the risk configuration publish so it reads those bindings and no longer
   assumes an ORE import wrote them.

*Part 2. The ACME datasets.*

4. Craft each party's documents for the reports that party runs, inspired by the
   ORE samples and not copied from them. Start from the analysis of which reports
   read which documents, and from the report design of which party runs which
   report.
5. Register a dataset per party and kind in the party's bundle. Declare the
   dependencies: the configurations before the definitions with their bindings,
   and those before the risk configurations.
6. Prove it on a clean provision: every definition has all its bindings, and a
   readiness query lists nothing missing.

*Part C. The run settings, shared, and the run document built at export.*

The product owner decided on 2026-10-12 that the run settings are shared configurations in DQ,
generated from the domain entity, and that the run document is built at export.

7. Make the risk report configuration a shared, party-owned entity. A definition binds it by name in
   the =risk_report_config= slot, as it binds its pricing engines. The configuration type is seeded,
   and the risk report type requires it. The DQ staging table is generated from the domain entity
   with one extra column that names the scope portfolio. The separate DQ model for the staging entity
   is deleted.
8. Publish the run settings through one function on the shared document publish, and write their
   portfolio scope from the staged name. Craft the settings of each party from the analysis of what
   each report needs: the analytics, the currency and the scope. Declare the dependencies, so that
   the portfolios come first and the definitions last.
9. Bind the conventions and the run settings in the bindings of each definition.
10. Build the run document at export from the settings and the bindings. A stored run document
    overrides the built one.
11. Recreate the database, provision, export the UK "Yield Curves" definition and validate each file
    against its schema.

What this means for the order of work.

- The four kinds every risk run requires are modelled and stored. They need only
  the DQ side, so they are the first deliverable (phase A). With them every
  definition can bind its required documents and the risk configuration can
  publish.
- Simulation and sensitivity have no entity model. The inbox story "Complete the
  ORE report configuration" holds them as its tasks "Round trip the simulation
  configuration" and "Round trip the sensitivity configuration", still BACKLOG. The
  simulation document has 18 entities and the sensitivity document has 58. They
  are the second deliverable (phase B), and they are prerequisites for the
  analytics reports. That story's tasks must move into this work or run first.
- The stress test needs a store, in the task "Store the stress test and credit
  simulation documents", also in that backlog story.
- The counterparty and netting documents are exported from entities that ACME
  already publishes. Step 1 decides whether they need a configuration kind of
  their own or an export from the existing data.
- The historical return and Basel traffic light kinds stay out until the
  blocked reports are reconciled with the report design.

*Found while proving the publish, 2026-10-11.* A definition also needs its run
document, the ORE run document that the export names. Exporting the run
configuration of a published Acme definition fails with "The report definition holds
no run document". The run document is the setup block, the market bindings and the
analytic list, held in the run setup, market binding, analytic and analytic parameter
tables of the reporting component. Nothing publishes them for Acme, so they join the
scope of this task as part C below. The analytic list follows the analytics switches
that the risk report configurations already carry for each report.

*Open points the first step settles.*

- The tables I found for the documents are pricing engines, today's market,
  curve configuration, the instrument conventions, stress test and credit
  simulation. I found no table for the simulation and the sensitivity analysis
  documents, which several reports read. The analysis says savers exist for
  them, so the inventory has to find where they are stored, or add the entities.
- The analysis marks four reports as blocked, because they read a kind that
  nothing stores yet: Stressed VaR and the Intraday Risk Monitor and the Board
  Risk Dashboard read a historical return, and P&L Attribution reads a Basel
  traffic light. The report design decided that Stressed VaR and P&L Attribution
  run at every trading entity (rule D7). Either the two kinds get stored, or the
  design and the blocked list are reconciled. The task must do one of the two.
- Part of the earlier work is done in another environment. The story "Build the
  retire or reset tenant journey" published the risk report configurations as a
  dataset and wrote the function that expands a root portfolio into its books.
  This task changes that publish, so it should tell that environment.
