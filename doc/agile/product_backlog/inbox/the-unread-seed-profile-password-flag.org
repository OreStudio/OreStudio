#+title: The seed profile carries a password flag only the web form reads
#+description: inherits_admin_password is stored, mapped, displayed and settable from the shell, and the provisioning path never reads it. The tenant administrator's password is whatever the caller passes to bootstrap setup, and a dataset's staff take their hash from the dataset. Only the web setup journey reads the flag, as the offer to hand the creator's password to the new tenant's administrator. Retiring it is therefore a journey affordance, not a provisioning rule, and it collides with whoever owns the setup journeys.

* What

Retire =inherits_admin_password= from =ores.iam.seed_profile=: the model
field, its column, everything generated from it, and the hand-written places
listed below. The provisioning path consults it nowhere.

* Why

The flag reads as a provisioning rule and is not one.

- The C++ provisioning path never consults it.
  =tenant_provisioning_service::provision()= takes =admin_password= from its
  caller, and =bootstrap setup= passes =--tenant-admin-password=.
- A dataset's staff take their hash from the dataset:
  =ores_iam_publish_accounts_from_dq_fn= writes =r.password_hash= into the
  credential row. ACME's people sign in on the dataset's hash whatever the
  profile says, which is the whole of why ACME works today.
- The only reader is the web setup journey.
  =journeys/state.ts= sets
  =useMyPassword: profile.inheritsAdminPassword && creatingPassword !== ''=,
  and =journeys/parts.tsx= renders the *Use my password* checkbox from it, so a
  profile that sets the flag offers to hand the creator's password to the new
  tenant's administrator. Standalone first-run holds no password, drops the
  offer, and asks instead.

So the flag is a journey affordance wearing a provisioning name. ACME is a test
database and the dataset is the right home for its passwords, which is what
makes the removal worth doing rather than implementing the flag.

* The decision it forces

Dropping the checkbox means the embedded journey always asks for the new
tenant's administrator password, where a profile that inherits it could offer
to reuse the creator's. Keeping that offer without the flag needs another
source for it. Decide this before starting: it is a change to a journey, not a
column drop.

* Collision risk

The setup journeys are brave hopper's area. Its recent commits there are *Do not
ask a browser that holds the session to sign in* and *Take a bootstrap answer as
it stands while the rail is open*, so =state.ts=, =parts.tsx= and
=newTenantSteps.tsx= are likely to move under this. Land it after that work, or
tell brave hopper to expect the conflict.
