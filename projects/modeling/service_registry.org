#+title: Service registry
#+description: Codegen service-registry model — catalogue of ORE Studio backend services and fleet processes, with two independent aspects per entry: DB access (psql var, IAM role, DDL grant prefixes) and deployment (replicas, enabled, startup dependencies, execution runtime, extra CLI args). Not every entry has both: the DB-access aspect only applies to services with their own NATS-domain-service role, while the deployment aspect applies to every process compass systemd generate needs to know about. Platform-agnostic by design: nothing in the deployment aspect is systemd-specific, so a future Windows-service or macOS-launchd generator can consume the same model.

* ores.web.service
:PROPERTIES:
:description: TypeScript web interface. One process serves the browser bundle and the HTTP API on ORES_WEB_PORT, and reaches the services over NATS.
:display_name: Web Service
:summary:     Serves the web interface and its API, and reaches the services over the message bus on the browser's behalf.
:replicas:    1
:enabled:     true
:depends_on:  ores.iam.service
:runtime:     node
:entry_point: packages/bff/dist/main.js
:END:

It carries no =account_var=, and that is deliberate rather than an omission. The
other services hold an IAM account because they act as themselves: they open a
database connection, and a validator or a permission check resolves who they
are. This one acts for the browser. It reaches the bus over the same mutual-TLS
client certificate every service presents, and the identity a service acts on
is the caller's, which travels with the request. Giving it an account would give
it an identity that nothing reads and nothing can check.

* ores.storage.service
:PROPERTIES:
:psql_var:    storage_service
:env_key:     STORAGE_SERVICE
:iam_role:    StorageService
:description: Object Storage
:display_name: Storage Service
:summary:     Stores and serves files as objects over the message bus.
:email:       storage_service@system.ores
:replicas:    1
:enabled:     true
:depends_on:  ores.iam.service
:END:

Answers put, get, delete and list on the =storage.v1.objects.*= subjects,
over the same storage root the HTTP routes are given, so a caller reaches one
set of objects either way. It holds no tables: the database gives it the
request context the shared runner hands to a handler, and nothing else.

=description:= stays a few words because three templates append "; domain
service" to it for a SQL comment and a service-account label. A paragraph here
reads back as "... and nothing else. domain service".

** Extra args

# The same root the HTTP server is given, because the two processes are two
# front doors onto one set of objects. Without this the service falls back to
# its own default and the two stop seeing each other's writes.

- --storage-dir ../storage
