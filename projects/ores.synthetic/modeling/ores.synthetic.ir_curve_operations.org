The two dry-run previews an IR curve editor asks for before it saves or
starts anything.

=simulate_ir_curve_paths= builds the real short-rate process and steps it, so
a screen can see the configured process behaviour over time.
=preview_ir_curve_shape= derives the rate each Curve Template row implies from
the process's current state, with no ticking, so a screen can see the curve it
would publish.

Both are stateless: nothing is persisted and nothing is published.

The two share one payload type, =parameter_spec=, so they share one model and
one generated header. A payload type is named unqualified inside its own
protocol and is resolved there, so declaring =parameter_spec= in a second model
would either duplicate the C++ struct or leave the TypeScript side naming a
type no module exports.

The batch bounds are not part of this protocol. They are the service's clamp
and a screen's spinner maxima, so they are declared once, in
=simulate_paths_common.hpp=, beside the FX spot bounds two of them share.

#+begin_src cpp :name comment
/**
 * @brief Request a stateless preview of the curve shape (rate per Curve
 * Template entry) implied by the given process parameters and template rows.
 *
 * Derives each row's rate the same way ir_curve_feed does
 * (IYieldCurveProcess::discount_factor() + curve_instrument_pricer, via the
 * shared price_ir_curve_entry()), from the process's current state, with no
 * ticking, so an editor can show "if I save these parameters and this
 * template, here is the curve you would publish" before committing anything.
 * Nothing is persisted or published.
 */
#+end_src
