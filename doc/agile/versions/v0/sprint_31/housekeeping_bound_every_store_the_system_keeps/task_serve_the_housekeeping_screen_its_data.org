* Goal

The housekeeping screen has one read for the list and one for a store's plot. The
first states every store, what bounds it, whether it is bounded now and how large
it is; the second states one store's measurements. Neither is composed from
entities by the browser: whether a store is bounded is a fact the database states,
and a client that inferred it would be a second implementation of the same rule.

* Acceptance

- A read states every store in one answer, with its name, description, owner, target, bound kind, action and period
- The same read states the mechanism that bounds the store and whether it applies today, so a policy naming an unbuilt mechanism reads as unbounded
- The same read states the latest size, the count and when it was measured, and states nothing for a store nothing has measured
- A second read states one store's measurements, oldest first, so a plot has its points in order
- The mapping from a row to the answer is a pure function with its own tests, so the absent values are proved rather than assumed

* Result

Two subjects serve the screen: `scheduler.v1.store_bounds.list` states every store
with its bound, its mechanism and its size, and `scheduler.v1.store_samples.list`
states one store's measurements oldest first. Both read the views and tables the
sweep and the sampler already write, and neither composes anything the database
can state.

The mapping from a text row to the answer is a free function with its own tests,
because the query helper hands back text and the absent values carry the meaning:
a store with no policy has no action and no period, and a store nothing has
measured has no sample rather than a size of zero. Three tests state a bounded
store, an unmeasured one and an unbounded one as the view states them, and read
the answer back.

The read is hand-written rather than generated, because an installation's answer
to "is this store bounded" is a rule the database holds in one view; a generated
read per entity would make the browser assemble it and give the rule a second
implementation.
