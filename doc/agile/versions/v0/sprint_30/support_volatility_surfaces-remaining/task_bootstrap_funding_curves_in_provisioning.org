* Goal

Every provisioned party has its own published funding curves. A curve is derived data, so it belongs to a party and not to the system. A provisioning step creates each operational party's blueprints, bootstraps them from the raw quotes the party subscribes to, and publishes them through marketdata.curve_publish under the tenant's auto-approval. The 20 system-tenant curves are not what a party prices from. Check what else reads them before removing them.

* Acceptance

- Provisioning Acme on a fresh database ends with published funding curves for ACMCOR, ACCOUK, ACCOUS and ACCOHK, with no seed.
- Each publish names the party, the raw quotes used and the rule that closed its approval.
- With the auto-approval switch off, the curves wait for a person.
- A curve that does not bootstrap is reported by party and name, stops the step, and a retry publishes nothing twice.
- After provisioning, a regular user raises and publishes a new curve through maker-checker.
- The task records whether anything still needs the system-tenant curves.
- Each operational party has a published funding curve in all 20 configured currencies.

* Plan

The system tenant already holds 20 curve blueprints: a bootstrap config, its pillars and an output series per currency. The system run publishes them from the system party's Bloomberg series. A new step, =publish_party_curves=, gives each party it names its own copy, after =subscribe_market_data= and inside the auto-approval bracket.

- =plan_party_curves= is a pure function. It maps each system config, pillar and output series to the party's copy. Each pillar reads the party's own series of the same item and provider. Ids derive from the party and the system row, so a second run names the same rows and writes only what is missing. A config whose quotes have not reached the party waits, and the plan names the series it lacks.
- The step reads the system blueprints as the system administrator, and each party's series and configs in the party's session. It waits up to three minutes for the quotes, writes the rows, then previews and publishes each curve the party has not published yet.
- The preview and publish loop moves out of the system step into =publish_curves=, so both steps publish the same way.
- A curve that does not publish fails the step, named with its party.

What reads the system-tenant curves: only the system tenant itself. The curve reader, the reports and the forward ladder read the session's tenant, and the derived FX vol feed reads no curve. The system curves stay as the reference set the system run checks.

* Result

Every operational Acme party now publishes its own 20 funding curves during provisioning. The curves copy the system's blueprints, read the quotes the party's own subscriptions deliver, and close under the tenant's auto-approval. After provisioning, a person publishes through maker-checker as before.

Nothing outside the system tenant reads the system curves. They stay as the reference set the system run checks.

Not run live: a curve that fails to publish, and a second run of the step. The plan's tests cover the second run, and the step skips a curve the party has already published.

The first live run failed because the workflow service also builds the step list, and I had not rebuilt it.
