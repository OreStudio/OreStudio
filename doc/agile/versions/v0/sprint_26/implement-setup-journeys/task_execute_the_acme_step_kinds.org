* Plan

The unit is the three step kinds only the ACME demo card declares, the
executors behind them, and the arguments that card's rows state. The
definition, the run lifecycle and the other three kinds landed in the
task beside this one; this task grows the executed-kind list by three
and gives each new kind its own arguments.

*What a kind acts on.* Every kind reads what it acts on from its own
arguments, so no ACME name stands in code. The profile's rows carry the
values; the kind's parser fixes their shape and refuses a row that omits
one, naming the field.

- =load_staff= names, for each party, the party's legal name and the bundles
  that carry its staff and its organisation. The legal name is what the
  profile's own hierarchy data creates the party with, and it is the key
  the party read resolves: a party's external identifier is guarded by
  party isolation, which a step's own context does not carry, so the
  name is the handle the profile can state and the deployment can honour.
  The kind publishes each bundle scoped to its party, then leaves the
  party ready for its staff: the party becomes active, its onboarding is
  complete, and the run's administrator is associated with it. The entry
  that says so makes that party the administrator's default.
- =attach_photos= names, for each party, the dataset that carries the
  staff's photo keys, and the key of the party logo's template. The kind
  reads each dataset's account rows as that party, copies each account's
  own template image into the tenant, saves it on the account, and
  attaches the logo to the party.
- =start_market_feeds= names the configuration bundles and the theme
  dataset. The kind publishes each configuration bundle against the
  tenant's system party, binds every party the tenant holds to the
  theme, and starts the theme's feeds from the system party's
  collection folder.

*The failure rule.* Every kind throws when its work does not complete,
so the step fails, the instance stops and a retry resumes from that
step. That is the policy the workflow page declares. The synchronous
ACME handler this work is lifted from is deliberately not the model: it
reported no step, so its uneven best-effort behaviour — a slow base
bundle logged and ignored, a missing system party skipped, two
responses never read — is not carried into a step that has an instance
to report to.

*What is lifted.* The three executors call the requests =provision_acme=
calls today — =dq.v1.bundles.publish= with a follower wait,
=refdata.v1.parties.put=, =variability.v1.ops.complete_party_onboarding=,
=iam.v1.account_parties.put_many=, =iam.v1.accounts.set-default-party=,
=assets.v1.images.put=, =iam.v1.accounts.update=,
=marketdata.v1.feed_bindings.put= and
=marketdata.v1.market_feed_configs.start_folder= — so the demo card
provisions end to end against data that exists and no other component
changes. =provision_acme= itself stays until the shell moves to the
generic request at plan step 12, which is where it retires.

*The party's ready state is a step kind's work, not a request's.* The
ACME path activates each party and completes its onboarding inside the
same synchronous handler that publishes its data. The new kinds keep
that pairing, in =load_staff=, because the profile's row is what names
the party: a kind that loads a party's staff is the kind that says the
party is ready to hold them.

*Live proof.* The acceptance is the ACME demo card's own run: a tenant
created by =iam.v1.tenants.provision= with the =acme_demo= profile,
followed to its terminal state, and the tenant's staff, images and
feeds read back from the deployment.

* Notes

- *What a kind reads, and why a party is named by its legal name.* The
  profile's rows state each kind's arguments. A party is named by the legal
  name the hierarchy import created it with, because a party's external
  identifier is guarded by party isolation, which a step's own context does
  not carry: the name is the handle the party read answers and the profile
  can state. The datasets, bundles, template keys and theme are named
  outright, so the executor composes no ACME name of its own.
- *The demo card's rows.* =load_staff= names four parties with the bundles
  that carry their staff, the holding party marked as the administrator's
  default. =attach_photos= names the four accounts datasets and the party
  logo's template key. =start_market_feeds= names the three configuration
  bundles and the theme. All of them live in the seed profile's rows, which
  is what makes the card data rather than code.
- *A feed binding's existence claim.* The first live run stopped in
  =start_market_feeds= because the store's must-not-exist claim for a
  binding is read by the ORE key alone while the binding's natural key is
  the party with the ORE key and the source, so the second party's binding
  for a shared source was refused. The step now states no expectation for
  that write and keeps its own freshness check, which is what lets it bind
  every party; the key defect is captured for the component that owns it.
- *The completing step's warning.* The run's last step reports
  =completed_with_warnings= because the settings write that clears a
  tenant's bootstrap mode is a create over a row the provisioner seeded.
  The tenant's status is active and its data is in place, so the run is
  accepted; the settings defect is captured for the components that own it.

* Result

The executor runs the three step kinds the ACME demo card declares, and the
card's run completes on the live deployment. The run is recorded beside this
task in =evidence/provision_acme_run_completed.txt=: seven steps in thirty
seconds, every step kind reporting completion, and the tenant holds the data
the three kinds produced — its four legal entities active and linked to
their staff, fifty-eight photographed staff accounts, sixty-five feed
bindings, and the observations its running feeds materialise.

Two defects were found by running the card, neither of them this unit's own,
and both are captured in the product backlog's inbox: a feed binding's
existence claim is read by the ORE key alone rather than by the binding's
natural key, which this kind works around with its own freshness check; and
the completing step cannot clear a tenant's bootstrap mode, which is the
run's single warning.
