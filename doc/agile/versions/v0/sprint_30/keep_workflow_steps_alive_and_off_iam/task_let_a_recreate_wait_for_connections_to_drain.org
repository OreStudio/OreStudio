* Acceptance

- compass db recreate -k waits a bounded time for the environment's connections to close before it refuses.
- Stopping the services and recreating the database succeed back to back.

* Plan

1. Widen the drain window in =check_connections(kill=True)=, from the 10
   seconds it waits today to a bounded minute, and keep it bounded: a backend
   that never closes must still fail the recreate rather than hang it. The
   wait reports how many connections remain, so a run that waits says so.
2. Keep the refusal honest without =-k=. Terminating a backend is the
   caller's decision, so a recreate that was not told to kill still refuses at
   once, and the hint stays.
3. Move the deadline into one named constant, so the window the wait uses and
   the window the tests state are the same number.
4. Update =test_compass_db_connections.py=: its deadline case counts the kill
   rounds, so it changes with the window. Add a case that the wait reports the
   connections it is waiting for.
5. Prove it against the real environment: stop the services, then recreate
   back to back, which is the acceptance line the story recorded as failing.

* Notes

- The refusal was a bare =10= second deadline in =check_connections=, in
  =projects/ores.compass/src/compass_db.py=. After it terminates the backends it
  polls every half second until the count is zero or the deadline passes, so
  the algorithm was right and the window was short. A fleet of stopped services
  closes for longer: the story recorded a recreate refusing while 25 stopped
  services' connections drained, for about 15 seconds.
- The change is two named constants and a report. =DRAIN_SECONDS = 60= is the
  window, =DRAIN_POLL_SECONDS= is how often the count is taken, and the wait
  names the count it is waiting for once per change, because a silent wait
  reads as a hang. The window stays bounded: a backend that never closes still
  fails the recreate rather than hanging it.
- The function was already covered: =test_compass_db_connections.py= pins the
  kill path, the deadline path and the refusal without =-k=, through a stand-in
  for =psql=. The deadline case counted kill rounds against a magic number, so
  it now states the window through the constant, and a fourth case holds the
  reporting.
- The acceptance holds on this environment: stopping the 25 services and
  recreating straight after succeeded, in 1m 33s. The wait said nothing during
  that run, which is the honest reading: systemd's stop had already closed the
  backends, so this host did not reproduce the 15 second drain. The case that
  would have exercised it is the one the unit tests pin, where the count stays
  above zero and the window is what ends the wait.
- The review round changed three things. The progress line flushes, because a
  piped run would otherwise stay silent for the minute this wait exists to
  explain. A caller that passed =-k= was told to pass =-k= when the window ran
  out; it now reads that the connections did not close in time, and the hint
  is for the caller without it. The deadline case states how long the wait
  spends instead of counting rounds, so a change to the loop does not fail it.
- Two effects the acceptance does not name. =compass db drop -k= runs the same
  check, so it also waits up to a minute, and the docstring says so. And an
  answer that never came back used to read as "the database may not exist, so
  nothing is connected", which let a recreate go on to the drop: the count is
  cluster-wide, so an absent database answers zero, and an unreadable answer is
  now a refusal that says what it could not read.
- The shell path is unchanged and different: =projects/ores.sql/utility/
  check_db_connections.sh= does not wait at all, it counts and points at
  =kill_db_connections.sh=. =recreate_env.sh= sources it, and the backlog's
  *Consolidate the scripts into compass* work is where the two become one. This
  task is =compass db recreate=, so the shell keeps its behaviour.
