* Goal

Decide what the layer between an ORE XML document and the ORE Studio model
is, and settle it with measurements rather than preference.

The bond review found that a money value cannot be recovered exactly from the
generated binding wherever ORE types the element as a bare =xs:float=. That
was one symptom. The layer has two more problems of the same origin: it builds
an object graph where the guidelines say the document tree is transient, and
it splits one mapping across 122,000 generated lines and 800 KB of
hand-written mapper that cannot be checked against each other.

The story is done when the route is chosen, the evidence is on the page, and
the work that follows is broken into tasks.

* Decisions

- *The document tree is transient.* The
  [[id:BBD43BF2-9FEE-42B0-A667-9468AF759DC2][guidelines]] place ORE
  documents at the boundary, outside the three regimes, and name the entity
  representation as the review target. The design follows that rather than
  the usual shape of an XML library.
- *Three routes were weighed; route C is recommended.* Keep and extend
  =xsdcpp=, adopt a document library, or own a scanner driven by tables
  generated from the schema. The investigation carries the numbers.
- *The mapping becomes data.* A table can be checked against the XSD by
  constructing it. The mechanical part of the mapping moves into the table,
  and the semantic part stays a short function.

* Out of scope

- Extending =xsdcpp=. Route A is described and rejected, not scheduled.
- A general XML library: XPath, run-time schema validation, a DOM.
- The drift on =trade= and =componentSubTrade=. Route C does not touch the
  generated binding, so the drift stops blocking anything.
