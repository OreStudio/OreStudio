* Acceptance

- A signed-in person loads one list from the C++ server while the BFF serves every other screen.
- The list follows its rows: a change in the data reaches the open screen over the change stream.
- Turning the flag off serves the same screen from the BFF.
- The smoke run proves both paths, and the gate stays green.

* Plan

*The browser talks to one origin, and a prefix decides which server answers.* The
transport issues same-origin requests to relative paths, and the dev server already
proxies =/api= to the BFF. So a screen on the new server is a prefix, not an origin:
the proxy routes =/cpp= to the C++ server and strips the prefix, and the one screen's
module asks for =/cpp/api/v1/...= while every other module asks for =/api/v1/...=.
That is the design's own wording, "behind a flag or a prefix", and it needs no change
to the C++ server's routes.

*The flag picks the prefix, and it is read once.* One module resolves the base for
the screen from a build-time or start-up value, so the same bundle serves both
arrangements and turning the flag off returns the screen to the BFF with no rebuild
of the C++ side.

*The cookie's path is the prefix.* The door sets a session cookie, and the BFF sets
one with the same deployment name, so a cookie at =Path=/= from the C++ server and one
from the BFF would overwrite each other. The C++ server must set the cookie's path to
its prefix, which makes the two sessions independent: the screen's calls carry the
C++ cookie and everything else carries the BFF's.

*Slices, each one verifiable.* First the prefix and the proxy, proved with =curl= on
the C++ server's own list route. Then the screen's list on the prefix with the flag
on, proved in a browser. Then sign in on the prefix, so the screen's session is the
C++ one. Then the change stream on the prefix, so the list follows its rows. Sign in
first would make every later slice need a working browser session, and a failure
would have three possible causes instead of one.

*What this needs running.* The prefix slices need only the C++ server and the dev
server. The sign-in slice needs the fleet, because the door asks IAM, and the change
stream slice needs NATS. This checkout's database was reported out of sync with the
tree, so the first browser proof will need =compass services start= and a database
that matches.

* Notes

- The dev server proxies =/api= to =ORES_WEB_PORT= (8080 by default) and the C++
  server listens on =ORES_HTTP_PORT= (21601), so the two are separate origins today
  and the prefix is what puts one screen on the second.
- A cookie at =Path=/= and a second cookie with the same name overwrite each other,
  which is why the prefix is also the cookie's path rather than a cosmetic detail.
  The path is now a server setting, =--web-session-path=, read into the door's
  =cookie_settings=.
- The two sessions cannot yet be one. The BFF keeps the token and hands the browser
  its own cookie; the C++ door keeps its own store. Neither accepts the other's
  credential, so a screen on the prefix carries the C++ session and the rest of the
  application carries the BFF's, and both exist at once because their paths differ.
  Making them one is a decision for the cutover, not for this task.
- Which list is not yet settled. The C++ server answers the generated collections,
  such as =/api/v1/reference-data/currencies=, and the screen that shows currencies
  asks the BFF for =/api/refdata/currencies=, which is the generic router the
  classification retires. The two shapes are not the same, so the first moved list
  needs either an adapter in the screen or the screen rewritten against the
  generated collection. This task takes the second, because an adapter would be the
  BFF's route kept alive under a new name.
