* Analysis

[[id:A898881E-B0A8-4E23-B717-DB7681AB2B18][Hold the calendar dates once, in
the system tenant]] gave the exception its party, and the generator added
=party_id= to =CalendarExceptionWrite=. The hand-written schema in
=packages/bff/src/records.ts= was left as it was, and it is tied to the wire
type by =satisfies z.ZodType<CalendarExceptionWrite>=, so =tsc --build= stopped:
=TS1360, Property 'party_id' is missing=.

The break reached =main= with merge 64020779f1. It was not caught because the
branch's gates were chosen by hand — the format and codegen checks — and the
classifier was not asked. The generated =calendar_exception_protocol.ts= is a
change under =projects/ores.web=, which classifies as =web=, whose check runs
the typecheck that fails.

The field is nullable on the wire, and the screen may omit it, so the schema
takes it as =z.uuid().nullable().default(null)=: the output type stays the
wire's, and a write that names no party still validates as the installation's.

* Result

The BFF's calendar-exception schema names =party_id= again, so the generated
write type and the boundary schema agree and the web build of =main= is green.

The fix is one line: =party_id: z.uuid().nullable().default(null)=, which keeps
the wire's output type and lets a write that names no party through as the
installation's row. It was proved in both directions: =npm run typecheck= fails
with =TS1360, Property 'party_id' is missing= on =main=, and the full web check
passes with the line — install, typecheck, format and tests, in 157.8 seconds.

The gate was there and was not asked: a model change that regenerates a
TypeScript file is a =web= change to the classifier, and the branch ran only the
checks it had chosen by hand. The capture that follows records the structural
gap: nothing checks the 23 =satisfies= schemas short of a full web build.
