* Plan

** What decides a type's shape

The model file is the authority, not the generated header: a model states its
fields, which of them are optional, and which table each belongs to. The
generated header is one projection of it.

The criteria come from [[id:BBD43BF2-9FEE-42B0-A667-9468AF759DC2][Data-Oriented
Design in ORE Studio]] and [[id:56AD6F46-99E0-482E-B7B5-C9FDEC8A7641][The data
classification checklist]]. A type passes when:

- it holds one component: the fields share one invariant that must hold at one
  instant, and one key identifies them;
- every member is read by whoever reads the component. A member read by a
  different screen, job or service, on a different cadence, is a candidate for
  an annex or a component of its own;
- a block of members that always move together is a candidate for a field
  group, and a block that a different owner writes is a component.

A count is a signal of a problem, never the problem. 60 columns can be one
correct component and 12 can be two components badly joined, so every verdict
states its reason and the count alone decides nothing.

** The lever

One script under =build/scripts/= reads every =modeling/*.org= and prints one
row per persistent type: the model path, the field count, the optional count,
the persisted column count, and the column prefixes that recur. It runs from a
clean checkout, takes no arguments, and its output is committed under
=evidence/= beside this page so a reader can re-run it and compare.

The numbers in the report are the script's, and each row names the model it came
from, so a reader can go from a verdict to the fields in one step.

** The verdicts

Three, and only three:

- *keep* — one component, and the fields belong to it.
- *group* — one component, but a block of fields is its own type and belongs
  together: a =field_group= member, not a new table.
- *split* — more than one component. The verdict names each part and the fields
  that go to it.

Every type above the threshold gets a verdict. The threshold is stated in the
report and justified there, not assumed.

** The order

The split task works worst first, so the report ends with the =split= types
ranked: by the number of parts their verdict names, then by persisted column
count. A type with three parts and 60 columns comes before one with two parts
and 20.

* Notes

- The report is [[id:E6C92BB1-8AB4-4580-A318-A5EB2A10BBB1][Inventory of type widths]].

- The count of bindings above is the count the query builder sees, which is the
  persisted column count plus the audit columns; it is a proxy until the script
  exists, and the script's number replaces it.
- MSVC runs out of instantiation depth at 46 bindings for one entity. That is
  where the shape stops compiling, not where it stops being wrong: the model was
  wrong at 20 too, and a split made to reach 45 would be a split made for a
  compiler.

* Result

[[id:E6C92BB1-8AB4-4580-A318-A5EB2A10BBB1][Inventory of type widths]] is the
report. It carries the verdicts, the three shapes they repeat, and the order the
split task works in.

=build/scripts/inventory_entity_columns.py= is the lever, and
=evidence/entity_columns.tsv= its output: one row per persisted type, with the
members the domain struct carries, the columns the table holds, the nullable
count and the distinct groups. The page states the command and the commit.

Nothing outside the script, its output and the report changed. The numbers
released three findings that the split task now depends on:

- the median type carries 6 members, so the model is not wrong everywhere and
  the work is a tail of 24 types;
- three shapes repeat across that tail, and each names its own split;
- the failure that started this was 47 bindings, which is a model with 39
  columns plus the scaffold's eight.
