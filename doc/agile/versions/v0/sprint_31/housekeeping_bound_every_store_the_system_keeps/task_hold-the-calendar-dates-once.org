* Goal

The calendar dates exist once per installation, in the system tenant, and every
tenant reads them there, so adding a tenant adds no copy of a calendar it shares
with every other tenant.

* Acceptance

- The dates are materialised into the system tenant, once, and no tenant holds a
  copy
- A tenant reads them through the shared-reference policy, as it reads the
  calendars and the exceptions
- The recompute path stays, and rebuilding the system tenant's copy is a command
  rather than a migration
- A test covers a tenant reading the installation's dates

* Analysis

The decision is recorded on
[[id:A54B0989-BFCB-45C6-80B7-279BF9843E78][Decide whether calendar dates are
stored or computed]]. In short: a calendar's days follow from its rule and its
exceptions, both of which the platform authors and publishes once, so the days
are the same in every tenant. A per-tenant copy is therefore the same bytes
written twice, and the treatment the classification names for derived reference
data -- recompute, or share one copy -- applies.

What this task does not do: it does not stop materialising. The dates sit on the
pricing path, and moving the computation there would charge every run for work
the installation can do once. It moves the materialisation's target from the
caller's tenant to the system tenant, and makes the copy readable across
tenants.

The read is the part that needs care: =ores_refdata_calendar_dates_tbl= carries
the tenant in its key, and its reads filter on the caller's tenant. A
shared-reference read policy admits the system tenant's rows, and the repository
that reads the dates must ask for them the way its sibling repositories ask for a
shared catalogue.
