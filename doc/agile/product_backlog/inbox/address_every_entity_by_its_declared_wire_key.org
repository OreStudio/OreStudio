#+title: Address every entity by its declared wire key
#+description: The model declares which key identifies an entity on the wire, once; the generated key record currently comes from the primary key instead, so role, tenant and permission have two identities and the web withholds their history and delete routes.
#+type: capture
#+level: cross
#+filetags: :codegen:protocol:keys:
#+created: 2026-09-22
#+updated: 2026-09-22

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Make the key a model declares the key the wire uses, everywhere.

The rule is already written down; the generator does not follow it.
=doc/knowledge/architecture/nats_entity_protocol.org= § "the two are not
interchangeable":

#+begin_quote
Holding a natural key and a surrogate primary key is permitted, and the two are
not interchangeable. Which one identifies the entity on the wire is a
declaration of the model, made once. It is the same key that appears in the
subject's resource's operations and in the HTTP projection's path parameter, so
that a caller never has to translate between an address and a request.
#+end_quote

Today =key_record_fields= (=projects/ores.codegen/src/codegen/org_loader.py=,
~line 2662) builds =<resource>_key= from =primary_key.columns=, while every web
route addresses the entity by the presentation drawer's =key_field=. When the
two disagree the model has two identities, and =_keyed_by_natural_key= detects
it and withholds the delete and history routes:

| Entity           | =key_field= | primary key  | delete/history route |
|------------------+-------------+--------------+----------------------|
| =tenant_type=    | =type=      | =type=       | present              |
| =account_type=   | =type=      | =type=       | present              |
| =tenant_status=  | =status=    | =status=     | present              |
| =role=           | =name=      | =id=         | withheld             |
| =tenant=         | =code=      | =id=         | withheld             |
| =permission=     | =code=      | =id=         | withheld             |

Holding the current rule means every client that knows an entity by its natural
key must translate before it can address one, which the quote above forbids.
That translation is the whole of the "where does username-to-id go?" question.

* Decision

Taken 2026-09-22. Both parts:

- *Accounts declare =username= as their wire identity.* =account_key { username }=.
  The uuid stays a storage detail, which is what it is for: foreign-key
  stability across versions. It is not the identity a caller uses.
- *=<resource>_key= is derived from the declared key*, not from the primary key.
  One declaration, read by the key record, the operations and the HTTP path.

* Work

** 1. Derive the key from the declaration

=key_record_fields= (=org_loader.py=, ~line 2662) reads the presentation
=key_field= when the model declares one, and falls back to the primary key when
it does not -- an entity with no screen has declared no wire key, and its
primary key is the only one there is. The primary key stays in the repository
entity and the DDL, where it belongs.

Three small helpers carry the rule, so the templates read one answer rather than
each deriving it: =declared_key_field=, =declared_key_column= (which searches
the primary key, the natural keys and the plain columns, because which list
holds the declared key is not the caller's concern but its type is) and
=key_is_primary=. Expose the last two on the enriched entity in
=generate_from_model=, beside =domain_entity['messages']= (~core.py:4931).

*Checked before starting:* of every entity model in the repo, exactly two
declare a =key_field= that names none of their columns --
=ores.compute.result= (=modified_by=) and =ores.workspace.workspace= (=name=).
They are outside IAM, and a hard failure would surface them rather than let them
fall back silently.

=_keyed_by_natural_key= (=core.py=, ~line 2114) becomes a load-time validation
rather than a gate. A model whose two keys still disagree should fail to load,
not silently lose routes.

** 2. Read and write by the declared key

Good news from the probe: the handler passes the whole request straight to the
service (=svc.get_tenant(*req)= in =tenant_handler.hpp=), so the key resolution
is concentrated in the service and the repository. The handler and the events
need no change -- events carry the key record, which follows from step 1.

The seams, all in =ores.cpp.service.service_impl.org=:

- =read_one= (~line 71) loops =primary_key.key_columns= to convert a key record
  into the repository's text arguments. It must loop the declared key.
- =key_from= (~line 87) builds a key record back from a domain object, so a
  written row can be read back. Same loop, same change.
- The batch removal (~line 329) builds one text vector per key column from the
  removal records. Same loop, same change.
- =pk['key_columns']= is derived in =core.py= (~line 4119) and carries the
  =is_uuid=/=is_timestamp= flags the conversions branch on. A sibling derivation
  is needed for the declared key. Watch this: those flags are set by the SQL
  shaping loop over =domain_entity['columns']= only (~core.py:2923), so a
  declared key held in =natural_keys= may not carry them yet.

The repository needs a read by the declared key. It has only =read_latest(ctx,
id)= -- the storage key. The precedent is =service_find_by_code=
(=ores.cpp.repository.repository_impl.org= ~lines 282--328, header ~122--139),
which already generates =read_latest_by_code= parameterised by ={{column}}= and
an optional ={{parent_column}}=. Generalise the method name to
=read_latest_by_<declared_key>= and emit it whenever =key_is_primary= is false,
rather than behind a per-model flag -- one declaration, as above.

** 3. Fix the BFF route envelopes

Every generated entity route except =list= predates the canonical protocol. The
shell already sends the canonical shapes, so these are stale, not divergent:

| Verb    | The route sends                | The protocol expects                |
|---------+--------------------------------+-------------------------------------|
| =list=  | ={offset, limit}=              | ={offset, limit, order}= -- order defaults, so this one works |
| =get=   | ={<keyField>: value}=          | ={key: <resource>_key}=              |
| =put=   | ={data}=                       | ={change, intent}=                    |
| =delete= | ={<keysField>: [key]}=         | ={removal, intent}=                   |
| =history= | ={<keyField>: value}=        | ={entity_type, entity_id}=            |

This is why the permission, role and login_info screens list a collection and
then fail on every other action. It has to be fixed whatever else happens here,
and it is the natural place to build the key record. It needs the detail form to
collect a change intent -- a reason code, and the version it read -- which the
web does not gather today.

** 4. Delete the legacy account history

=iam.v1.accounts.history= is keyed by username because username is the account's
real wire identity. It got the addressing right and the payload wrong: a prose
=change_summary= where the generic path carries a structured diff. Once
=entity_id= is the declared key, the generic =iam.v1.history.get= covers accounts
exactly, so the legacy protocol, its four consumers and its two supporting files
are deleted rather than migrated. See the surface list in git history
(=doc/agile/product_backlog/inbox/remove_legacy_account_history_from_iam.org=,
replaced by this capture).

* Note on composite keys

=entity_id= is a single string and =get_entity_history_request= is generic, so it
cannot carry a composite key -- and the specification forbids flattening one.
Deriving the key from the declaration removes that case rather than needing to
solve it: =key_field= names exactly one field, so a declared wire key is always
single-field. Composite keys remain, but only as the storage key.
