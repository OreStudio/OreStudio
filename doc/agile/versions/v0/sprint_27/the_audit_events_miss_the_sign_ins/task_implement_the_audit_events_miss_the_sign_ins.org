* Acceptance

- A party-selecting sign-in writes one =login_success= row, with the party.
- A refusal writes one =login_failure= row, with the reached tenant.
- The read's time bounds compare against =event_time= without error.

* Plan

Two of the three are one edit each; the first is the interesting one.

=select_party= and =switch_party= are deliberate near-duplicates, so the
success record goes in =select_party= only. A re-scope of an already-open
session is not a new sign-in, and recording one there would double-count
every party switch.

=record_auth_event= is private to the auth handler, and =select_party= lives
in =account_operations_handler=, so the new site builds the repository
itself and swallows a recording failure the same way the helper does. A
telemetry write must never refuse a sign-in that already succeeded.

The failure path could not reach the tenant context or the bare username,
because both were resolved inside the =try= whose =catch= records the
event. Hoisting them above the =try= is what makes the refusal recordable;
the two catches (the typed =login_error= and the generic =std::exception=)
share the fix.

The read's cast goes through =nullif= rather than a bare =::timestamptz=,
because the empty string is the filter turned off and =''::timestamptz=
raises instead of yielding null.

* Result

The audit screen has sign-ins to show. A refusal and a party-selecting
sign-in now both record, against the right tenant and the bare username,
and the events read answers for =day= and for =all= on the running
installation.

What made this hard to see is worth keeping: the read failed, the BFF turned
the failure into an empty list, and the screen said there was nothing to
show. An empty list and a broken read are the same picture, and the IAM
service's log was the only place the difference was written down. A read
that cannot run should not be allowed to read as an empty log.

One gap is left, and it is not this task's. The browser's sign-out destroys
the BFF's session and clears the cookie, but never calls the server's logout
subject (=server.ts=, =DELETE /api/session=), so no =logout= event is
recorded and the session row is left open. The server-side recording works;
nothing reaches it. That wants its own story.
