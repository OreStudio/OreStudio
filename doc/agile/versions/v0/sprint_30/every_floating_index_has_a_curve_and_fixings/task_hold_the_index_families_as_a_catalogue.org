* Goal

The index families a synthetic IR curve can name, and the tenors each one
admits, are a catalogue of data. The curve config's insert trigger, the DQ
publish function's projection or discount choice and the web form read it,
so a new family, or a family that gains a term tenor as HIBOR does for HKD,
is a seed row.

* Acceptance

- =ir_curve_index_family= holds every family the config accepted, with
  whether it admits an overnight curve, a term tenor or a dated tenor.
- The config's two hand-written family checks are gone; the insert trigger
  checks the family and the tenor together against the catalogue.
- The publish function no longer lists families, and every seeded curve
  keeps its role.
- The web form lists the families from the catalogue and checks the tenor
  against the family's row.
- =hibor= admits a term tenor, so the task Bootstrap the HKD HIBOR term curves
  can state its curves.

* Plan

1. Model =ores.synthetic.ir_curve_index_family= on the yield curve process
   type, the catalogue of the same shape and scope, and generate it.
2. Wire what the process type wires by hand: the HTTP routes, the shell
   commands, the core and event registrars, the history list, the SQL
   create, drop and RLS scripts, a read permission and the seed.
3. The tenor rule needs two columns, and a validation row passed one. Extend
   the template so a row may name a second column (=with_column=), and write
   the rule as =ores_synthetic_validate_ir_curve_index_family_tenor_fn=. The
   template's source is its org block in
   =ores.sql.schema.domain_entity_create.org=; the =.mustache= is tangled
   from it.
4. Base the publish function's role on the tenor and the catalogue.
5. Make the web form read the catalogue; drop the two lists in =irCurve.ts=.

* Result

The IR curve index families are a catalogue, and the hand-written lists are
gone.

- =ir_curve_index_family= in =ores.synthetic=: 52 generated files and the
  wiring the yield curve process type has, with a seed of 32 families. =hibor=
  admits both an overnight curve (CNH) and a term tenor (HKD); =sofr= keeps
  =FOMC= as its dated tenor.
- Codegen: a validation row may name =with_column=, and the trigger passes it
  as a second argument. No other entity's SQL changed.
- =ores_synthetic_validate_ir_curve_index_family_tenor_fn= replaces the
  config's two checks; the publish function's role reads the tenor and the
  catalogue.
- The web form lists the families from the catalogue and checks the tenor
  against the family's row; =irCurve.ts= keeps the tenor as typed and
  leaves the rule to the server.

Found on the way: =compass generate= does not converge in one run after a
template's org source changes. Codegen renders with the =.mustache= as it was
before tangle rewrites it in the same run, so the first run writes the old
output and =compass-ng check= reports drift; a second run converges. I first
edited the =.mustache= alone, which tangle then reverted, and read the drift
as compass-ng dropping =with_column=; it does not. Reported to compass-85 with
the steps, for v0.0.7.

Not changed: =indexTenorOf= in =irCurve.ts= still maps =FOMC= to the =1D=
series tenor, mirroring the synthetic service's own rule; a family's dated
tenor could feed it, and that is left for when a second dated tenor exists.
