* Goal

Give a person the three acts of a session as resources of their own: sign in with
=POST /api/v1/auth/sessions=, sign out with =DELETE /api/v1/auth/sessions=, and ask
who the caller is with =GET /api/v1/auth/sessions/me=. Signing in answers with the
principal and sets the cookie; the token never appears in the answer.

* Acceptance

- [X] =POST /api/v1/auth/sessions= opens a session, sets the cookie, and answers with
      the principal only.
- [X] =DELETE /api/v1/auth/sessions= closes the session and clears the cookie.
- [X] =GET /api/v1/auth/sessions/me= answers who the caller is, with no token.
- [X] The live round trip is proven against a provisioned tenant, for the tenant
      administrator and for a seeded member of staff.

* Plan

The door delegates identity to IAM and keeps the session itself: the token is held
server side, the cookie carries an opaque identifier, and the principal is projected
from the claims the session already resolved. The live case drives the same code the
server runs, against the running fleet, so it needs no HTTP client of its own.

* Notes

- =me= and signing out are proven without IAM, because neither needs it: =me= reads
  the claims the session already resolved, and signing out closes a session the test
  opened. Both are cases in =ores.http.iam.tests=.
- Signing in has a case of its own and it runs against the fleet. It found a real
  defect on its first run: the sign-in asked for an *authenticated* NATS call with no
  token, and the client refused it before the request left the process. A sign-in
  cannot present a session, so it sends an ordinary request, and it is answered.
- The case then skipped, because the recreated database held no accounts and IAM
  answered =invalid_credentials=. That was a fact about the database and not about the
  door, and it stayed true until the tenant was provisioned.
- Provisioning the tenant made the case's last assertion visible for the first time,
  and it was wrong: it looked for the qualified principal the sign-in form sends
  (=tenant_admin@acme_corporation=) while the answer states the account alone
  (="username":"tenant_admin"=) with the tenant id beside it. The answer is right — it
  reports what the token states, and the BFF's session record has the same shape — so
  the assertion was corrected to name the account exactly and to require a tenant.
- The door was then proven twice: once for the tenant administrator, and once for a
  seeded member of staff, whose password the =acme_demo= profile sets.
- The tenant is still =bootstrapping=, because the profile's last step,
  =generate_trades=, fails on an FX variance swap that violates its own check
  constraint. That is a defect of the generator and not of this door, and it is
  captured separately; the sign-in that this task is about does not wait for it.
- Getting there cost time to two operational traps, both captured: a service binary
  older than its libraries crashed with a stack that named innocent code, and a
  provisioning run that dies cannot be resumed.
- To run the live case: =compass services start=, provision the tenant, then
  =./ores.http.iam.tests "[live]"= from the preset's =publish/bin= with the
  environment file loaded.
- The cookie's name comes from =--web-session-name= and its =Secure= from the
  deployment's TLS flag, so one deployment cannot read another's session.

* Result

The three acts are resources and the door is proven: a person signs in with the
credential the deployment gave them, the answer names them and the tenant, the
cookie carries only an opaque identifier, and the token stays in the gateway's own
store. The live case runs against the fleet, so the next change to IAM's sign-in
answer is measured by a test that talks to IAM.
