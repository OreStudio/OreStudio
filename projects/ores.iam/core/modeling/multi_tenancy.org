* Overview

ORE Studio implements a multi-tenant architecture where each tenant's data is
isolated at the database level using PostgreSQL Row-Level Security (RLS). This
document describes how tenant context flows through the system from user
authentication to database queries. For the party hierarchy, RLS, and data
ownership model see [[id:BAE3AA18-6027-10A4-965B-2C174C237195][Multi-Party Architecture]]. For account-party
rules and the login flow see [[id:AAD74D7C-4789-4E54-8B02-EC60231D78A5][Multi-Party Login Flow]].

Tenant isolation is not the whole model, because not every row belongs to a
tenant. A row belongs to a tenant, to the system tenant, or to the
installation — the deployment's own facts, such as the services roster, the
hosts and wrapper nodes, the grid and node samples, the telemetry logs and the
database row. [[id:5A5D6490-AF64-4AAF-8B3D-48EF3EDAF3D2][Tenant ownership and the information flow]]
names the three owners and the policy each one wants; this page describes the
mechanism they share.

* Core Concepts

** Tenant Identification

Each tenant is identified by a UUID. The =tenant_id= wrapper type provides
type-safe handling of tenant identifiers:

#+begin_src cpp
namespace ores::utility::uuid {

class tenant_id {
public:
    static tenant_id system();  // Returns system tenant (max UUID)
    static std::optional<tenant_id> from_string(const std::string& s);
    static tenant_id generate();

    const boost::uuids::uuid& value() const;
    std::string to_string() const;

    bool operator==(const tenant_id& other) const;
    auto operator<=>(const tenant_id& other) const;

private:
    explicit tenant_id(boost::uuids::uuid id);
    boost::uuids::uuid id_;
};

}
#+end_src

** Tenants Table Structure

The =ores_iam_tenants_tbl= table stores tenant definitions. It has two UUID columns
that serve different purposes:

| Column      | Purpose                                                    |
|-------------+------------------------------------------------------------|
| =id=        | The tenant's unique identifier (used by accounts, etc.)    |
| =tenant_id= | Always system tenant (FFF...) - the record's owner         |

This design follows a key principle: *the tenants table itself is managed by the
system tenant*. All tenant records have =tenant_id = system= because the system
owns and manages the tenant registry.

#+begin_example
┌─────────────────────────────────────────────────────────────────────┐
│                      ores_iam_tenants_tbl                           │
├──────────────────────────────┬──────────────────────────────────────┤
│ id (the tenant's own ID)     │ tenant_id (always system tenant)     │
├──────────────────────────────┼──────────────────────────────────────┤
│ 197fae34-...-cfa4            │ ffffffff-ffff-ffff-ffff-ffffffffffff │
│ (Example Corp)               │ (system owns this record)            │
├──────────────────────────────┼──────────────────────────────────────┤
│ b7b302e6-...-c9a9            │ ffffffff-ffff-ffff-ffff-ffffffffffff │
│ (ACME Corp)                  │ (system owns this record)            │
├──────────────────────────────┼──────────────────────────────────────┤
│ ffffffff-ffff-ffff-ffff-fff  │ ffffffff-ffff-ffff-ffff-ffffffffffff │
│ (System tenant itself)       │ (system owns this record)            │
└──────────────────────────────┴──────────────────────────────────────┘
#+end_example

When an account belongs to "Example Corp", its =tenant_id= column references the
tenant's =id= (not the =tenant_id= column):

#+begin_src sql
-- Accounts reference tenants.id, not tenants.tenant_id
SELECT a.username, t.name as tenant_name
FROM ores_iam_accounts_tbl a
JOIN ores_iam_tenants_tbl t ON a.tenant_id = t.id  -- Note: t.id, not t.tenant_id
WHERE a.valid_to = ores_utility_infinity_timestamp_fn()
  AND t.valid_to = ores_utility_infinity_timestamp_fn();
#+end_src

This pattern applies to all tenant-scoped tables: they reference =tenants.id= to
identify which tenant owns the record.

** System Tenant

The system tenant is defined as the maximum UUID value:

: ffffffff-ffff-ffff-ffff-ffffffffffff

The system tenant is used for:

- System-level operations that span all tenants, by acting inside each one; a
  session in the system tenant does not see them by itself
- SuperAdmin accounts
- Bootstrap and provisioning operations
- Default context when no specific tenant is configured

The max UUID was chosen because:

- It is a valid UUID that will not conflict with randomly generated UUIDs
- It is easily recognizable in logs and debugging
- It avoids issues with nil UUID (all zeros) which some databases treat as NULL

** Tenant Types

Each tenant has a type that determines its operational characteristics, available
features, and the level of controls enforced. Tenant types are stored in the
=ores_iam_tenant_types_tbl= lookup table and validated on tenant creation.

| Type           | Purpose                                          | Controls              |
|----------------+--------------------------------------------------+-----------------------|
| =system=       | Platform administration and shared governance    | Platform-managed      |
| =production=   | Real customer organisations                      | Strict                |
| =evaluation=   | Realistic environments for demos and testing     | Relaxed               |
| =automation=   | Automated test infrastructure                    | None (programmatic)   |

*** =system=

The system tenant (tenant 0, max UUID) is the platform-level tenant that owns
shared governance data such as the tenant registry, system-wide permissions, and
reference datasets in the data librarian. There is exactly one system tenant per
deployment. Users logged into the system tenant are super administrators with
cross-tenant visibility.

*** =production=

Production tenants represent real customer organisations with isolated business
operations. These tenants enforce strict operational controls:

- Four-eyes authorisation for sensitive operations (e.g., counterparty
  onboarding, party modifications).
- KYC-gated counterparty creation with supporting documentation.
- Data librarian operations restricted to safe, auditable actions.
- No bulk import of parties or counterparties from external datasets.

*** =evaluation=

Evaluation tenants provide realistic, production-like environments for
demonstrations, user acceptance testing, QA, and system evaluation. Controls are
relaxed to allow rapid environment setup:

- GLEIF-based tenant onboarding available (importing root party and child
  parties from LEI data).
- Bulk counterparty import from LEI datasets via the data librarian.
- No four-eyes requirement for sensitive operations.
- Clearly labelled in the UI to prevent confusion with production tenants.

Evaluation tenants are suitable for pre-production testing, sales demos, training
environments, and exploratory testing by QA teams.

*** =automation=

Automation tenants are created and destroyed programmatically by test harnesses
for unit, integration, and load testing. They are not intended for human
interaction:

- Created with random UUIDs for isolation between test runs.
- No UI-driven workflows; all operations performed via test fixtures.
- Parallel test execution without interference.
- Ephemeral; typically torn down after test completion.

** Party Types and Multi-Party Architecture

Each tenant contains parties that represent business units. Parties have their
own type taxonomy and RLS-based data isolation. See the companion document
=projects/ores.refdata/modeling/multi_party.org= for the full multi-party
architecture, including party-level RLS, visible party sets, and the login flow
extension.

| Party Type      | Purpose                                    | Auto-created |
|-----------------+--------------------------------------------+--------------|
| =system=        | Administrative party (party 0)             | Yes          |
| =operational=   | Business entity (trades, books, KYC)       | No           |

** Row-Level Security

PostgreSQL RLS policies enforce tenant isolation at the database level. Each
transaction sets a transaction-local variable that RLS policies use to filter
data:

#+begin_src sql
select set_config('app.current_tenant_id', 'tenant-uuid-here', true);
#+end_src

All queries on tenant-scoped tables automatically filter by this value,
preventing cross-tenant data access.

The value comes from the request, not from the service. A request carries an
[[id:4E0D934A-21D4-4609-8B7C-29F6D9A6A52D][Access Token]] whose claims state the
tenant and the party, and every transaction of the request's context sets
the variables from them. A service that calls with its own identity, by
[[id:4B5B6195-F542-4A88-B5B3-9A4561554406][Client Credentials]], therefore has no
party and sees no party rows.

** The three policy shapes

The tenant variable is one mechanism; what a policy does with it is the
decision, and not every row belongs to a tenant. A row belongs to a tenant, to
the system tenant, or to the installation — the deployment's own facts, which
no tenant owns. Three shapes are in use, and only one of them can hand one
tenant's rows to another:

| Shape | Policy body | What it is for |
|-------+--------------+----------------|
| Own tenant | =tenant_id = ores_iam_current_tenant_id_fn()= | The default, and the only shape a tenant's own data may use. |
| System-owned rows for all | =tenant_id = current or tenant_id = system= | A system-owned row every tenant reads: shared reference data, and the installation's own facts. It exposes no tenant's data. |
| A system session sees every tenant | =tenant_id = current or current = system= | The widening. It hands one tenant's rows to a session in another, and =check_rls_system_tenant_widenings.py= fails a new one. |

Naming the row's owner is what decides which shape it may take, and the
difference between the last two is which side of the comparison the *session*
sits on. Read
[[id:5A5D6490-AF64-4AAF-8B3D-48EF3EDAF3D2][Tenant ownership and the information flow]]
before adding a policy.

Reaching a tenant's data from outside it is not a fourth shape: it is a session
inside that tenant, by
[[id:96460BBE-D7BF-4538-B620-AC5FD9F0C9FE][Token Exchange]] or =with_tenant()=.

** The accounts exception: party visibility through membership

*This is a special case. It applies to the accounts table and to no other
table.* Do not copy it to another entity. A party-owned entity takes the
party-isolation shape, which keys on its own =party_id= column and on the
session's visible party set. That shape is the rule, and accounts are the one
reviewed exception to it.

An account has no =party_id= column, because a person works in several
parties. The links in =ores_iam_account_parties_tbl= say which. The party
column shape therefore cannot scope accounts, and the visible party set is the
wrong scope: it holds the party the session acts for and the parties below it,
while an account works in the parties it is linked to. A head of group linked
to several parties would lose the parties it does not act for.

The policy is =accounts_party_visibility_policy= in
=projects/ores.sql/create/iam/iam_rls_policies_create.sql=. It is hand-written,
not generated. It is a restrictive policy on reads. It is ANDed with the
own-tenant policy, so tenant isolation does not change.

| Session | Sees |
|---------+------|
| A person | The accounts linked to a party that the person's own account is linked to, the accounts linked to the system party of the tenant, the person's own account, and the shared accounts of the system tenant |
| A service acting in a tenant | Every account of the tenant and the shared accounts of the system tenant, because a service works in no party |
| A tenant administrator | Every account of the tenant, because its account is linked to every party of the tenant |
| A session with no actor: a service acting as itself, or the sign-in lookup before a session exists | Every account of the tenant, as a session with no party set passes the party policy of other tables |

A person whose account has no party links gets no party set, so they see their
own account and no other. This includes a tenant administrator: the
administrator sees the tenant because its account is linked to every party of
the tenant, and not because the policy names the role. A tenant provisioned
without party links would show its administrator only the administrator's own
account until the links exist.

The function =ores_iam_actor_party_ids_fn()= returns the parties the actor's
account is linked to. The actor is =app.current_actor=, which every user
request sets from the token. The function is =security definer=. It reads the
actor's account to find the links, and without that it would apply the policy to
itself.
The policy wraps its function calls in a =select=, so the planner runs each
once per query and not once per row.

The shared accounts are the second part of the exception. The service accounts and the
super admin belong to the system tenant, and a service writes under its own name into
the history of every tenant. The column =shared= marks the rows that every tenant may
read. The select policy =accounts_select_policy= admits the current tenant and the
system tenant rows with =shared= set. The party rule passes a shared row, because a
shared account works in no party. The insert, update and delete policies admit the
current tenant only, so no tenant writes a shared row. The super admin is a =user=
account that humans sign in with, and it is shared by its flag and not by its type.
The generated repository states =:system_tenant_visible: true=. The standard that
every table read across tenants follows is
[[id:0EAAEDFD-7954-4649-A463-9EE377B023F7][Data read across tenants]].

A record that names an account checks that it exists through
=ores_iam_account_exists_fn(id)=. The party rule hides every account from a service,
because a service works in no party, so a select on the accounts table fails for the
inbox service. The function is security definer and returns yes or no. It takes the
tenant from the session and answers for the current tenant and for the shared accounts
of the system tenant.

What the exception does not do:

- It does not limit writes. A write needs the write code of the operation, and
  the own-tenant policy still bounds it.
- It does not reach the other IAM tables. Credentials, contact information,
  sign-ins and sessions are separate tables. Each has its own policy and its own
  permission code.
- It does not make =iam::accounts:read= a read of the tenant. The permission
  says that a caller may read accounts. The policy says which accounts.
  Member holds the permission for this reason; see
  [[id:804C7048-DBBF-4B39-8737-BFB4949884C4][Authorised reads]].

* Database Context

** =context= Class

A =database::context= names who a statement acts for. It holds the tenant and,
optionally, the party and the parties that party sees, which the row-level
security policies read; the actor, the end user behind the request, which
=modified_by= records; and the service account, the service that performs the
write, which =performed_by= records.

#+begin_src cpp
class context {
public:
    explicit context(pq::connection_options options,
                     utility::uuid::tenant_id tenant_id,
                     std::string actor = "",
                     std::string service_account = "",
                     pq::open_policy policy = {});

    const utility::uuid::tenant_id& tenant_id() const;

    context with_tenant(utility::uuid::tenant_id tenant_id, std::string actor) const;
    context with_party(utility::uuid::tenant_id tenant_id,
                       boost::uuids::uuid party_id,
                       std::vector<boost::uuids::uuid> visible_party_ids,
                       std::string actor) const;

    pq::pool& pq_pool() const;
    pq::session_context pq_session() const;
};
#+end_src

Key properties:

- The tenant ID is mandatory at construction.
- =with_tenant()= and =with_party()= return a light copy for another tenant or
  party. The copy keeps the service account, the roles, the pool and any bound
  unit of work, so narrowing a context never widens what it may do.
- Every copy shares one libpq pool, which the context opens on first use.

** Tenant settings are transaction-local

A pooled connection carries no tenant. Every transaction that a context opens
sends its settings with its first statement, in the same pipeline as =begin=:

#+begin_src sql
select set_config('app.current_tenant_id', $1, true),
       set_config('app.current_party_id', $2, true),
       set_config('app.visible_party_ids', $3, true),
       set_config('app.current_actor', $4, true),
       set_config('app.current_service', $5, true),
       set_config('TimeZone', 'UTC', true);
#+end_src

The third argument, =true=, makes each setting local to the transaction.
PostgreSQL clears them at commit or rollback, so the next transaction on that
connection starts with no tenant and cannot read rows of the previous one. The
settings cost no extra round trip: they travel in the pipeline with =begin= and
the first statement.

A unit of work binds its context to its transaction. Every repository call
made with that context runs on the one transaction, under the one set of
settings.

* Connection Pool Architecture

One pool serves every tenant and party. Each service process holds a few
long-lived connections to pgbouncer, which runs in transaction pooling mode in
front of PostgreSQL:

#+begin_example
  request 1 (tenant AAA)   request 2 (tenant BBB)   request 3 (tenant CCC)
            │                        │                        │
            ▼                        ▼                        ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │ database::context copies (tenant, party, actor; one shared pool) │
  └────────────────────────────────┬─────────────────────────────────┘
                                   │ lease a connection for one transaction
                                   ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │ pq::pool: a few long-lived connections per service               │
  └────────────────────────────────┬─────────────────────────────────┘
                                   ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │ pgbouncer (transaction pooling)                                  │
  └────────────────────────────────┬─────────────────────────────────┘
                                   ▼
  begin; set_config('app.current_tenant_id', 'AAA', true); ...; commit
#+end_example

This architecture provides:

- Efficient use of server connections: pgbouncer bounds them for the whole
  fleet, and no tenant needs a connection of its own.
- Tenant isolation through RLS: each transaction sets its own context.
- Thread safety: each request holds its own immutable context copy, and a
  leased connection serves one transaction at a time.

Transaction pooling is safe because no setting outlives its transaction. A
session-level =SET= would follow the server connection to the next client, so
no code sets one. The PostgreSQL listener is the exception to the pool: =LISTEN=
needs a session that stays on one server connection, so the listener holds a
direct connection to PostgreSQL.

* Request Context

** The bearer token carries the tenant

A request names its caller in a JWT bearer token, in the =Authorization= header
of its NATS message. A downstream service forwards the end user's token in
=X-Delegated-Authorization=. The token's claims carry the tenant, and
optionally the active party, the parties it may see, the username and the
roles.

The tenant is resolved once, at login, and signed into the token. A request
cannot change it, because the service verifies the signature before it reads
any claim.

** Per-Request Context Creation

=ores::service::service::make_request_context()= turns a message into a
=database::context=. It verifies the token, then narrows the service's base
context to the token's tenant, or to its tenant and party:

#+begin_src cpp
if (!claims->party_id || claims->party_id->empty())
    return base_ctx.with_tenant(*tid_result, claims->username.value_or(""))
        .with_roles(claims->roles);

return base_ctx
    .with_party(*tid_result, party_id, std::move(visible_ids),
                claims->username.value_or(""))
    .with_roles(claims->roles);
#+end_src

This ensures:

- Each request operates in the correct tenant context.
- The username becomes the actor, which =modified_by= records.
- The pool is shared: the context copy is light.
- Tenant context is immutable for the request lifetime.
- Party context sets =app.visible_party_ids= in each transaction for RLS.

A token that is absent, expired, unsigned or without a tenant is refused as
unauthorized. A malformed party falls back to tenant scope, because the party
only narrows a context that the tenant already authorises.

* Tenant Resolution

** By Hostname

Tenants can be associated with hostnames. When a principal includes a hostname
(/e.g./, =john@acme.example.com=), the system looks up the tenant by that
hostname:

#+begin_src cpp
tenant_id lookup_by_hostname(const database::context& ctx,
                             const std::string& hostname);
#+end_src

This enables:

- Multi-tenant SaaS deployments where each customer has their own subdomain
- Automatic tenant resolution without explicit tenant selection

** Default Tenant

When no hostname is provided in the principal:

- In production: uses system tenant for administrative operations
- In testing: uses the test fixture's tenant for isolation

* Performance Characteristics

** Per-Request Overhead

A request pays for one context copy: the tenant, the party list, the actor and
a reference to the shared pool. The tenant settings cost no round trip of
their own: =pq::transaction= sends them in the pipeline with =begin= and the
first statement.

** Connection Pool

- One pool per service process, shared by every tenant and party.
- The pool opens its connections at startup and keeps them. No query opens a
  connection.
- pgbouncer bounds the server connections of the whole fleet.
- RLS handles isolation at the query level.

* Tenant Isolation Guarantees

** Data Isolation

- All tenant-scoped tables have RLS policies
- Queries automatically filter by =app.current_tenant_id=
- Cross-tenant data access is impossible at the SQL level *except* through a
  reviewed widening: a policy whose body compares the session to the system
  tenant admits every tenant's rows to that session.
  =check_rls_system_tenant_widenings.py= lists every one and fails a new one,
  and [[id:6C930659-6548-4371-B9EB-1AACE597D0E9][Read each tenant's cache
  partition inside its tenant]] is removing them.

** Token Isolation

- Each token names exactly one tenant.
- The tenant is signed into the token, so a request cannot change it.
- A refused token gives no context, so no statement runs for it.

** Request Isolation

- Each request creates its own tenant context
- Contexts are immutable values.
- Tenant settings are local to a transaction, so concurrent requests, and
  consecutive transactions on one pooled connection, cannot see each other's
  tenant context.

* Configuration

** Production

=context_factory::make_context()= builds a service's base context from its
configuration. The tenant defaults to the system tenant; the service account
names the service and becomes the connection's =application_name=; the open
policy says how often and how long the pool retries opening its connections:

#+begin_src cpp
auto options = to_connection_options(cfg.database_options);
options.application_name = cfg.service_account;

const pq::open_policy policy{.attempts = cfg.num_attempts,
                             .wait = std::chrono::seconds(cfg.wait_time_in_seconds),
                             .shape = ...};

utility::uuid::tenant_id tenant_id = utility::uuid::tenant_id::system();
if (!cfg.database_options.tenant.empty())
    tenant_id = /* parsed from cfg.database_options.tenant */;
#+end_src

Each request then narrows this base context to its token's tenant.

** Testing

In tests, =ores::testing::database_helper= builds the context with the test
tenant that the test environment names, and can switch it to party scope. Each
test run provisions its own tenant, so runs do not interfere.
