* What

Find and fix the cause of the intermittent failure in =projects/ores.sql/test/refdata_conventions_publish_test.sql=. The repeat publish (test 5, line 138) fails with a duplicate key on a =*_conventions_version_uniq_idx= index. The kind and the row change from run to run: =AED-ZERO-TENOR-BASED= (zero), =EUR-RON-XCCY-FIX-FLOAT-CONVENTIONS= (cross currency fix-float) and =BECPIHL= (zero inflation index) were seen. The publish's =not exists= filter did not see a live row, and the version trigger then wrote version 1, which already exists. So between the two publishes a live row was closed, or a row was written with a =valid_from= or =valid_to= that the filter does not match. The version trigger closes with =valid_from < clock_timestamp()=, which is a candidate.

* Why

The test fails the pgTAP gate at random, so a branch can fail for a reason it did not cause. Measured on 2026-10-26 in clever_dijkstra, with =run_tests.sh= and the test alone, on a fresh database: 1 failure in 8 runs with no convention term triggers; 1 in 8 with insert-only triggers; 3 in 16 with =insert or update of= triggers. The rates do not differ beyond the noise of these samples.
