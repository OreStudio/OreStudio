* Goal

A dataset's page gains a Contents view: the tables its artefact type names, each
with its own columns and its own staged count, and the rows of whichever table a
person opens. It answers the question the coverage screen raises but cannot
settle. A member says "512,186 rows staged", and a person who has never seen one
of those rows cannot tell a correct catalogue from a plausible one.

The view is a list of tables rather than one grid, because a dataset does not sit
in one table: its artefact type names a table or a family of them — =conventions=
names thirty-four — and every family carries its own columns. The Qt Data
Librarian never offered either: it read a dataset's own row and its metadata, and
left the staged rows to psql.

* Acceptance

- A read over the bus answers the tables one dataset stages into, in its
  artefact type's own order, each with its own columns and the rows it holds for
  the dataset. The caller names the dataset, never the tables.
- The same read answers one page of one table's rows when a table is named, with
  the columns the rows carry, because every artefact family carries different
  ones and the screen cannot know them in advance.
- The table is checked against the dataset's own artefact type, so one generic
  read serves every family and a caller cannot read another family's rows.
- The rows state neither =dataset_id= nor =tenant_id=: the request already states
  both, and a screen that drew them would report the row's bookkeeping, not its
  content.
- The dataset's page draws the Contents tab as a list of tables, each with its
  columns and staged count, and opening one table draws its rows under the
  columns' own names.
- The rows page like every list in the application: the standard =Pager=, its six
  page sizes, its first–previous–next–last strip and its bounds sentence, with the
  page held in the address as =from= and =size=. The read's own cap is the Load
  all limit, not a number the screen invents.
- The view is a read. Changing a row is
  [[id:88F9E5B4-20FF-4EEC-B8A0-97B35970E120][its own task]].
- A test reads the contents of a seeded dataset and asserts a table, its columns
  and a known row.

* Plan

The shape of the answer was the hard part and the prototype settled it before any
code: a list of the family's tables, then the rows of the one opened. The
prototype and its sign off are in
[[file:doc/prototypes/dq/reference-data-coverage.org][the coverage prototype note]].

1. The store reads. Two functions beside the DQ roster, because that file already
   owns the discovery functions and their grants:
   - =ores_dq_dataset_tables_fn(p_dataset_code)= answers the family's tables with
     =information_schema='s columns, minus the two every family shares, and one
     count per table against the dataset's own id. A family's sum cannot say
     which table is empty, which is the reason the count is per table.
   - =ores_dq_dataset_rows_fn(p_dataset_code, p_table_name, p_limit, p_offset)=
     answers ={columns, rows, total}= as JSON. It resolves the dataset's artefact
     type and refuses any table the family does not name, so the read is one
     generic function rather than thirty-four of them. The rows drop
     =dataset_id= and =tenant_id=.
2. The operation. =dq.v1.ops.dataset_contents= is declared in a model so both
   languages get the request and the response from one statement: tables as
   messages, rows as JSON.
3. The service and the handler. =publish_service::read_dataset_contents= wraps
   both functions and turns the store's ={error}= answer into a failed response;
   =dataset_contents_handler= owns the =dq::datasets:read= gate.
4. The route. =GET /api/v1/dq/dataset_contents= forwards the named dataset, the
   optional table and the page.
5. The screen. A Contents tab between Publications and Dependencies, holding the
   open table in the address so a link reopens the rows and Back returns to the
   list, and paging through the shared =Pager= the record lists already use.
6. Tests: a pgTAP suite for the two functions and their refusals, a handler suite
   through the bus, and the dataset page's tests for both the list and the rows.

* Notes

The hard part is not the read but the shape of the answer. There is one artefact
table per family, and each carries its own columns beside the two every family
shares, =dataset_id= and =tenant_id=. Countries carries =alpha2_code=,
=alpha3_code=, =numeric_code=, =name=, =official_name= and =image_id=; the next
family carries different ones. A screen that must draw any of them reads the
columns with the rows, and the store can state them: the catalogue already
describes every artefact type's table, and =information_schema= describes its
columns. The design decision this task owns is which of the two the answer
carries, and whether the read is one per family or one generic read over a
whitelisted table name.

Two limits worth stating in the design:

- A count and a page are not the same evidence. The count says how much exists;
  the page says whether it is right, and only for the rows it shows.
- A family of half a million rows is the case to design for, not the exception:
  =geo.ip2country= holds 512,186 in the provisioned environment.

The write half is
[[id:88F9E5B4-20FF-4EEC-B8A0-97B35970E120][Read and write an artefact row over
the bus]], which reads one row by key to correct it. This task reads many to look
at them. They share the read path and land in whichever order suits the sprint.

The first cut capped the rows at fifty and stated how many of how many it showed.
Review refused that: a list pages like every other list in the application, through
the same control and the same address parameters, and a cap of its own is a second
paging scheme to learn. The read's cap is the Load all limit so the pager can offer
every size it states.

Asked for on 2026-11-26, after the coverage screens were reviewed. The Data
Librarian drew a lineage graph of a dataset and never its rows, which is the gap
this closes.

* Result

A dataset's page gains a Contents tab: the tables its artefact type names, each with
its own columns and its own staged count, and one table opened to read its rows. The
read is one operation, =dq.v1.ops.dataset_contents=, which answers the family first
because a dataset names one artefact type and the type names a table or a family of
them, and answers a page of rows with the columns they carry because every family
carries different ones. The table is checked against the dataset's own family, so one
read serves thirty-four of them and a caller cannot read another family's rows.

The rows page through the shared =Pager=, not a cap of their own, and the read's own
limit is the Load all limit. A row carries neither =dataset_id=, =tenant_id= nor
=version=: the request states the first two and nobody reads the third.

Two critical findings from the review were fixed before the merge: the page had no
order (=order by 1= is =dataset_id=, constant after the filter, so LIMIT and OFFSET
could repeat or skip a row), and the readers ran as the owner with no tenant
predicate, so a dataset code stated in more than one tenant could return another
tenant's rows. The page now orders by =ctid= and reads invoker-rights, scoped to the
caller's tenant or the system tenant.

Proven with 10 pgTAP assertions, 166 handler assertions in 4 cases, 8 dataset-page
tests, a live read of 34 tables and 1,040 rows over the route, and a 21-of-21 gate.
