* Goal

Produce a written inventory of exactly where the workspace feature
stands today, so the rest of this story (and the dependent Trade
Blotter story) can be scoped from facts rather than assumption:

1. Every table/entity carrying =workspace_id= (cross-reference against
   =projects/ores.workspace/core/modeling/multi_workspace.org='s
   "affected categories" list -- trading, reference data, market data,
   curve config, pricing engine, today's market, reporting).
2. For each: does its Qt widget/dialog actually respect and surface
   workspace scoping (e.g. workspace chip/badge, correct filtering),
   is that support codegen-generated or hand-patched, and is it
   consistent with the entities that already got it right?
3. What hand-crafted C++/Qt code exists purely to bolt workspace
   support onto an entity after the fact -- this is the candidate set
   for a new codegen template flag (the "much like page support"
   pattern the user asked for: pagination is already a flag entities
   opt into and get for free; workspace-awareness should work the same
   way).
4. Cross-check against the three known open codegen follow-ups
   (workspace entity model drift, workspace-cpp safe drift,
   ores.qt.workspace commissioning) -- confirm they cover what the
   audit finds, or surface gaps they don't.
