* Notes

** The includes are read from the contents, not from the catalogue**

A schema states its includes in its own markup, so the route scans the content it
already holds rather than trusting a column: an include is
=<xs:include schemaLocation="…">= and the scan finds it the way the BFF's scanner
did, which is the same order of attributes. A schema is complete only with its
includes, so an include the version does not store is a refusal that names it
rather than an archive that cannot validate a document.

The walk is breadth first and remembers what it has seen, so a schema included
twice travels once and an include of an include is reached.

** The archive is built here, and its bytes are not the BFF's**

The BFF wrote the zip by hand with raw deflate; this writes it with libarchive,
which the storage part already depends on. Both are zips of the same files under
the same names, and neither reader can tell them apart, but the bytes differ, so
a test compares what the archive holds and not the archive.

** The route is the area's one binary answer, and it states no cache**

The answer is =application/zip= with the name =<code>-<version>.zip= and
=cache-control: private, no-store=, because the schema is read from the store per
request and a schema read a version at a time is not a thing to keep.

** The catalogue is read once, whole**

The BFF read the file catalogue twice, once whole to find the schema and once
filtered by the schemas category to map a version's file code to its name. One
whole read answers both, so the route reads it once.

* Result

The ORE schema is served as one archive: the schema the catalogue names at the
engine version asked for, and every schema it includes at once or through
another. A missing include is a refusal that names what is missing and what
includes it, and never a partial archive.

The includes are read from the schema's own markup rather than from a column, and
the walk is breadth first and remembers what it has seen, so a schema included
twice travels once. The archive is written with libarchive, which the storage
part already depends on, so the answer's bytes are not the BFF's hand-written
zip even though every reader sees the same files under the same names.

With this route the reporting area has no BFF route left unpaired: 44 of 44. The
whole inventory stands at 252 of the BFF's 328 routes paired, with 1018 of the
1346 routes answered by the gateway.

The reporting part's suite passes 102 cases and 731 assertions, ten of them for
this route, and half of those for the include walk itself, which is a pure
function and needs no estate.
