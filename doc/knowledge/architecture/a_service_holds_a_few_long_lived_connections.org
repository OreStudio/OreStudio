#+title: A service holds a few long-lived connections and never connects per query
#+description: A process keeps a floor of long-lived connections and may burst above it to the concurrency its work has; no query opens a connection of its own.
#+type: knowledge
#+level: cross
#+filetags: :architecture:database:connections:
#+created: 2026-10-26
#+updated: 2026-11-21

* Summary

A service process holds a floor of long-lived database connections and may open
more when its work needs them, up to a ceiling it states. A connection above the
floor is closed once it has been idle, so a service that is doing nothing holds
only the floor. No query opens a connection of its own: a connection costs a name
lookup, a TCP handshake, a SCRAM login and the session setup, milliseconds of CPU
for a query that runs in a fraction of one.

* Detail

** What the pool holds

Every connection authenticates once, at start or when it replaces a broken
connection. A connection carries no tenant and no party between transactions
([[id:3C334C3B-2760-4278-95B8-B71268E8FD18][A transaction sets its own tenant context, so any connection serves any tenant]]), so any connection serves any request. The pool hands a connection to
one transaction at a time and takes it back when the transaction ends.

** The floor and the ceiling

The floor is what an idle service keeps: enough that a request arriving after a
quiet spell does not wait for a login. The ceiling is the concurrency the
service's work really has, so a burst meets connections rather than a wait. For
a service that runs provisioning steps, that number is its step workers times the
lanes a step runs, plus the handler work beside them
([[id:4DA654B3-7CE6-4637-B4D8-E8E2B4D092B3][Delivery threads enqueue and a bounded pool runs the handlers]]); for one with only
control-plane work it is a handful. A connection above the floor is closed after
an idle period, and a pool at its ceiling fails the caller with the retryable
"no connection came free" error ([[id:E11DB09A-328A-476A-A71B-8E303A68D07D][A store error says whether a retry can succeed]]) rather than growing
without bound.

Two numbers rather than one is what lets a service ask for the burst its work
has without holding it for life. The marketdata service holds the same floor for
its reads, and each tick lane holds one more connection of the writer role,
outside the pool ([[id:BCD7D253-8B1E-4887-B476-EDD3EDE01BE6][Ticks reach the store through sharded binary COPY in bounded batches]]). What the
*instance* carries is a different number: the pooler's cap for each environment,
where a pooler stands ([[id:42930B6A-544A-4F7E-ACF4-9ABC60F2B408][The environments share the database through a transaction pooler]]).

** Changing what a service holds

A service states both numbers in its environment, as
=ORES_<APP>_DB_POOL_MIN=, =ORES_<APP>_DB_POOL_MAX= and
=ORES_<APP>_DB_POOL_IDLE=, which set the floor, the ceiling and the idle period
in seconds. The floor defaults to two, the ceiling to eight, and the idle
period to thirty seconds, so a service that states nothing holds two idle
connections and bursts no wider than eight. A service whose work grows states a
larger ceiling and changes no code; a service asked to hold fewer connections
lowers its floor, which is the number an idle process keeps.

The notification listener is the one connection that can name a different
endpoint from the service's own: =ORES_<APP>_DB_LISTENER_HOST= and
=..._DB_LISTENER_PORT= say where it connects, and both default to the service's
own. An environment that pools its traffic names PostgreSQL's port there, because
a transaction pooler hands a =LISTEN= to somebody else at the next commit, while
the service's requests keep going to the pooler.

** When a connection breaks

The pool replaces a broken connection in the background. The transaction that
was using it ends with a retryable error ([[id:E11DB09A-328A-476A-A71B-8E303A68D07D][A store error says whether a retry can succeed]]), and its caller retries on a
fresh connection.

** One connection path

The generated repositories and the hand-written statements reach the store
through the same pool and the same unit of work ([[id:37D08E01-F99C-4D2D-8ACA-E19E252BBE3D][A repository works inside an open transaction and never holds credentials]]). There is no second
way to reach the database.
