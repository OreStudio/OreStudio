* Summary

The recent work settled the market data pipeline as one path. A producer
publishes a =market_tick= on its own subject, a feed binding routes that tick
to the parties that consume it, and the marketdata ingest loop plans the tick,
writes the series and observation, and republishes onto the per-party stream.
The knowledge graph does not yet mirror that shape. It holds four large notes
that mix the pipeline with its history, plus one architecture note that
predates the binding model it now describes.

This proposal keeps one idea per note, names the code or model each note
documents, and gathers the notes under two hubs. It follows the atomic note
discipline in [[id:E3B70401-5142-4ACC-A61F-1BBF19F8470F][Zettelkasten]], where a note that grows is split rather than
extended, and the structure note discipline, where a hub gists and links and
carries no content its cluster does not. It also follows
[[id:7474935C-95D1-3034-B833-83DCD9FB3A09][Knowledge]], where the index lists the hub of a topic and never the pages
under it.

The proposal deletes two notes, splits three, and merges seven existing notes
into proposed ones. It adds twenty nine notes, each with a path, a symbol or a
table behind it, and it names the hub each one hangs from.

* Decisions taken, 2026-10-06

The owner read this proposal and decided three things. Where a later section
reads differently, these decisions win.

1. *One hub, not two.* The market data pipeline, synthetic generation, the
   operation surface and the vendor side share one structure note with
   ordered sections, so a reader takes one reading order and the shared links
   appear once. The separate reading orders the proposal preferred are
   sections, not hubs.
2. *The vendor producers note is written now.* The =producer_kind= vocabulary,
   the =VENDOR= default and the binding all exist even though no vendor
   producer does, so the note is a contract note that says what a vendor
   producer must be and records that none is in the tree yet.
3. *The binding to generation-config gap is stated, not hidden.* A
   =feed_binding= names only its =source_name=. The link back to the
   =market_data_generation_config= or feed config that produced that source is
   name similarity, not a foreign key. The pipeline hub names this as a gap
   with its consequence, that a binding cannot show which config authored its
   source, so a future reader sees it rather than inferring a relationship
   that the schema does not carry.

* How this grows

The rule is a list of edits a person makes in the same change as the code.
It is not a wish, because each item names a file that a reviewer opens.

**A new feed kind**

1. Add the config table and its codegen model under =projects/ores.synthetic/modeling/=.
2. Add the producer behind =IFeed= and its kind string beside the existing two.
3. Register the builder in =make_default_feed_factory=.
4. Add one note under the synthetic hub, titled for the asset class, in the
   same slot the FX and IR notes occupy, and name its config table and its
   producer file.
5. Add one row to the =Adding an asset class= note if the kind needed an edit
   the note does not list. A row that is never needed is the evidence the seam
   works.

**A new operation**

1. Add the request and response to the protocol model and register the handler.
2. Add or extend the note under Hub C. If the operation is a new verb rather
   than a parameterisation of =preview= or =simulate=, it earns its own note.
3. Add the shell verb to =synthetic_commands.cpp= or its marketdata
   counterpart, and extend the shell surface note in the same change.

**A new asset class that only binds a vendor source**

No producer note is added. The work touches the feed binding note and the
vendor producers note, because the asset class is a new series and a new
binding, not new generation code.

**A new subject or a new tick field**

The change touches the market tick note and the producer subject note, and
the ingest loop note, in the same change. These three are the contract, and a
contract note that lags its code is worse than no note.

**How a reviewer checks the docs moved with the code**

The reviewer opens the diff and asks three questions.

1. Does every new table, struct or subject in the diff have a note that names
   it, or does it belong to a note the diff also edits?
2. Does any edited note now state something the diff made false? The usual
   suspects are the two hub notes and the market tick note.
3. Does the diff add a second copy of something a note already says? If it
   does, the note is the wrong place and the new text belongs beside the code.

A =grep= answer is available today for the third question. Every note in this
proposal names its anchor, so =grep= for the anchor in =doc/knowledge/= returns
the notes that touch a symbol. That check is what makes the rule enforceable
rather than aspirational, and it is worth a script under =scripts/= once the
notes exist.

These are the ones the code cannot answer.

1. Should the two hubs be separate? The pipeline hub and the synthetic hub
   share the market tick, the ingest loop and the binding notes. A reader who
   wants to author a generator does not want the vendor section first, and a
   reader who wants the store does not want the config entities. Keeping two
   hubs duplicates nine links and one boundary statement. One hub with three
   ordered sections removes the duplication and loses the separate reading
   orders. The proposal splits them because the two orders differ and a reader
   who takes the wrong one pays for it in pages read before the useful one.

2. Does the vendor side have a producer to document? The =producer_kind=
   table, the =VENDOR= default and the binding all exist, and the vocabulary
   is settled. No vendor producer exists in the tree. The proposal writes the
   vendor producers note as a contract note, stating what a vendor must
   satisfy and that none exists yet. If a vendor integration is planned in the
   next two quarters the note should be written now; if it is not, the note
   should wait and the contract rule should live in the binding note alone.

3. How much of the approach document survives? Its method-per-asset-class and
   cross-asset constraint sections are the only place the reasoning behind the
   GMM and short-rate choices is written down. Its roadmap section is about to
   be wrong, because the work it sequences has landed. The proposal splits it
   and keeps both halves. The alternative is to retire it whole and let the
   session records carry the reasoning, which loses the reasoning.

4. Does the architecture document's configuration split still hold? It says a
   feed config references the producer's config. =feed_binding= stores only
   =source_name=, so the link from a binding back to a =market_data_generation_config=
   is the source name and nothing else, and the name-similarity rule is what
   keeps them in step. The rewritten hub must describe the implementation or
   the gap, and only the owner can say which.
