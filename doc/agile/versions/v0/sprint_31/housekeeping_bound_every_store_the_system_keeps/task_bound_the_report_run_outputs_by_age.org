* Goal

A run's cashflows, metrics and text values are removed once the run is older than the stated retention period, so the store's size follows the runs a person still compares rather than every run ever made.

* Acceptance

- A retention period is stated for the run output tables, with the reason for the period recorded
- Chunks past the period are dropped by the engine where it runs a job, and by the executor where it does not
- A run inside the period still reads its rows

* Plan

The three tables were chunked on =as_of=, the date the engine stated for the
figure. A chunk drop on that column bounds a store by the date the rows carry:
a run states its figures at every payment date its trades hold, so most of the
rows are dated years ahead and a chunk there ages out only after the projection
has passed. The chunk is therefore cut on =valid_from=, the instant the row was
written, which every row of a run shares because the table is written once with
the run and never edited.

The period is ninety days, stated in the model and in the seeded policy, with
the reason beside it. The model gives the period to the engine, which applies it
where its edition carries a retention job. For the edition that carries none,
three policies are seeded beside one daily job that fires the sweep, and the
sweep drops the same chunks and records what it removed.

Two properties of a TimescaleDB hypertable shape the work. A unique index must
carry the partitioning column, so the natural key index is declared in the model
with =valid_from= rather than generated from the keys. And the partitioning
column is checked for null before any row-level trigger runs, so =valid_from=
needs a default, which the model language cannot state: the reporting chain sets
it in =reporting_run_output_partitions_create.sql=.

The change needs a database rebuild, because a hypertable's partitioning column
is fixed when it is created.

* Notes

- The earlier verification of the sweep recorded =removed = 0= against the ticks
  table and read that as nothing being old enough. It could not have been
  anything else: the target was unqualified, so the count compared two
  different strings and found no chunks either side of the drop. The count is
  fixed, and the policy the seed writes names its table schema qualified.
- A policy is versioned and retiring one closes its row. The sweep read every
  row whose =enabled= flag was set, so a policy a person had turned off kept
  being applied through its closed version. It now reads only the current one.
- A row cannot be moved between chunks by updating the partition column: the
  chunk's own constraint refuses it. The probe rows were written with the
  trigger disabled instead, which is a test technique and not a supported path.
- The model language states no column default, so the default on =valid_from=
  lives in a hand-written script beside the generated ones. A model that could
  state it would delete that script.
- On this cluster the licence reads =apache=, so no table carries an engine
  retention job and the sweep is the only path that drops anything. The model's
  interval still states the period, which is what the licensed edition would
  apply, and both paths name the same ninety days.
- Nothing else schedules the sweep: the seeded job is the only thing that fires
  it, and its cadence is the job's, not the policies'. Each policy records a
  cadence too, which no code reads yet.
- The seed writes 'system' as the actor, as the neighbouring seeds do. On a
  database that has been provisioned, the account validator refuses that name,
  so re-running the populate against a live database fails on these rows as it
  already does on the job definitions.

* Follow-up

The write path, not the trigger, was the gap, and another environment found it
by running =ores.reporting.core.tests=: three of 283 cases failed on a chunk
check constraint, reported 2026-11-25 and fixed in the same area by
=solid_dirac= the same day.

=report_metric_entity= defaulted =valid_from= to =db_timestamp::max()=, so the
insert stated 9999-12-31. The hypertable routed the row to that instant before
the insert trigger ran, the trigger then stamped =current_timestamp=, and the
chunk refused the change. Every row of every run output table would have landed
in the far-future chunk, which is worse than the failure: the failure is what
kept it out of production.

The note above records that a probe row cannot be moved between chunks, and the
tests wrote their probes with the trigger disabled. That technique hid the
cause, because it removed the only step that disagreed with the routing.

The fix makes the column the store's. The model states
=:store_stamps_valid_from: true=, the generated entity binds the column with
=query_builder::store_fills=, which keeps it in reads and leaves it out of the
insert, and the insert trigger stops rewriting it. The column default stamps
the write instant before the row is routed. =ores.reporting.core.tests= passes
283 of 283, =ores.database.tests= 87 of 87, and the pgTAP suite 1022 tests.

* Result

The three run output tables are chunked by the instant their rows were written,
one day at a time, and declare a ninety day retention interval with the reason
recorded beside it. A run's figures are dropped whole once the run is older than
the period, on either edition of the storage engine: the engine's own job where
its licence provides one, and the seeded sweep where it does not. A run inside
the period still reads its rows.

The sweep now counts what it removed, reports a target it cannot resolve instead
of counting nothing, and applies only the current version of each policy.
