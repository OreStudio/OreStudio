* Plan

(Implementation strategy. Written when work starts; key decisions
are distilled into the parent story's =* Decisions= at close, but the
plan itself stays — it is the historical record of what we did.)

Investigated live against a freshly-provisioned Acme tenant:
1. Confirmed CRM topology configs exist in the DB for all three
   offices (majors/exotics/scandies) -- the provisioning-bundle
   premise this task started from was already fixed.
2. User reported the CRM screen was still blank live. Checked the
   marketdata service log and found repeated "JWT verification
   failed: token expired" warnings starting ~35 min after login.
   Traced to CrmCrossRatesMatrixMdiWindow snapshotting the auth token
   once at construction instead of refreshing it per-request, unlike
   ClientManager's proactive refresh timer which keeps the session's
   own token current. Fixed with a small thread-safe token holder
   refreshed on the GUI thread at the top of every reload().
3. Even with a fresh token, CRM was still blank. Found the CRM name
   picker (showMatrix()) queries topology configs across every party
   visible to the caller (server-side RLS, no party filter on
   get_crm_topology_configs_request), while reload() scopes the
   actual rates query to clientManager_->currentPartyId() only. The
   default login party (Acme Corporation Plc, the holding company)
   has zero topology configs of its own -- only the three offices do
   -- so the picker showed real names sourced from other parties that
   then silently resolved to zero rows (a legitimate empty response,
   not a request failure, so nothing surfaced it as an error). Fixed
   by filtering the picker to the current party and showing an
   explicit "no CRM configured for current party" message when empty.
4. That fix, once live, confirmed the diagnosis: the holding company
   genuinely has no CRM/treasury data of its own by current
   provisioning design (acme_bundle_populate.sql scopes
   books/portfolios/CRM to the three offices only). Whether that's
   correct depends on what a real holding company needs -- discussed
   with the user and broken out as its own story rather than decided
   unilaterally here.

* Result

Two real bugs fixed in CrmCrossRatesMatrixMdiWindow/Controller
(projects/ores.qt/marketdata/):
1. Stale JWT snapshot -- crmClient_'s token_provider captured
   currentAuthToken() once at construction; now refreshed on the GUI
   thread at the top of every reload() via a thread-safe token
   holder (safe because ClientManager's session state has no
   internal synchronization of its own).
2. CRM name picker/reload() party-scoping mismatch -- the picker
   queried topology across all visible parties; reload() only ever
   queries the current party. Picker is now filtered to the current
   party, with an explicit message when it has none configured.

The original task premise (a provisioning-bundle gap) was already
fixed on main before this task started. The deeper finding --
Acme's holding company has no CRM/treasury footprint at all, which
may not match what a real holding company needs -- is scoped as its
own story: [[id:C8FA1CE7-F4D7-4D9B-B6A5-1B3A623D7071][Holding company treasury functionality: FX/CRM visibility, Group Treasury book, consolidated reporting]].
