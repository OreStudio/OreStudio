======================================================================
What surprised me
======================================================================

1. The whole file-exporter sub-tree is dead. file_log_exporter,
   hybrid_log_exporter, their log_exporter interface and upload_position_tracker
   have no production consumer and no test: 4 headers and 3 .cpp files. The
   export path that is actually wired is telemetry_sink_backend -> a handler
   supplied by the caller (ores.testing writes to telemetry_repository::create).
   The JSON-lines exporters look like the intended durability layer and are
   never constructed.

2. The whole distributed-tracing API is test-only. telemetry_context, span,
   span_context, span_kind, span_link, span_status_code and both ID generators
   are exercised only by core/tests/telemetry_context_tests.cpp,
   span_id_tests.cpp and trace_id_tests.cpp. No production code calls
   create_root, start_span or start_linked_trace. span_id and trace_id
   themselves survive because the log sinks call from_hex/to_hex for correlation.

3. macros.hpp is broken as well as dead. Nothing includes it and no code uses
   TLOG_SEV, and the macro body names ::ores::logging::trace_context_injector
   while the struct is declared in ores::telemetry::log, so the macro cannot
   compile if anyone ever uses it.

4. application_exception is dead. application.cpp includes the header but never
   throws the class, and no test names it. By contrast the sibling
   parser_exception is load-bearing in parser.cpp and main.cpp.

5. Half of telemetry_repository's public API has no caller: sql, read_by_account,
   read_hourly_stats, read_daily_stats, count_errors, delete_old_logs,
   query_server_samples and query_stream_samples. read_by_session and get_summary
   are test-only. The hourly/daily stats entities and telemetry_stats follow the
   read_hourly_stats/read_daily_stats pair into the dead pile. Only create,
   create_batch, query, count, insert_server_sample, insert_stream_samples,
   insert_service_sample and list_service_samples are wired.

6. fetch of nats_server_samples_query / nats_stream_samples_query: the query
   structs are fields of live protocol messages, but the handler
   nats_server_samples_list ignores the query and replies with an empty sample
   list, so query_server_samples/query_stream_samples are dead while their
   parameter types are still part of a served message.

7. database_sink_utils.hpp in the database part is unreachable: no source and no
   test includes it, so both handler factories are dead. The core part's
   database_sink_utils.hpp survives only because a test and an unbuilt example
   use make_forwarding_handler.

8. database/include has no outermost banner header (no ores.telemetry.database.hpp).
   That is a G08 gap, not a B03 finding, but it is worth a line.

======================================================================
Method and collision notes
======================================================================

- Collisions that inflated the raw counts and were filtered by hand: attributes
  (other components' attribute fields), resource (used as a common noun in many
  services), span (nats/storage/http 'span'), trace_id/to_string (ubiquitous),
  lifecycle_manager (ores.logging owns a different class of the same name),
  application, host, options, parser, parser_exception, registrar (every service
  component declares these), and application_exception (26 hits, all other
  components' own exception classes). ores.testing counts as production: it is a
  library, not a tests/ directory, and it is the component's biggest real consumer.

- Trivial boilerplate was skipped by the standard's own instruction: comparison
  operators, stream operators, constructors and destructors, and interface
  overrides (log_exporter::export_record/flush/shutdown, both sink consume()
  methods). To keep the census bounded, member functions are listed in full only
  for telemetry_repository (the dead-API hotspot) and for the tracing chain; other
  classes are represented by the class row, whose verdict already reflects the
  methods' consumers.

======================================================================
REVIEW CORRECTIONS, 2026-09-26
======================================================================

The task checked the survey's verdicts before acting on them. Three of the
eleven 'dead' files are not dead, and the survey's own note that the whole
census is name-based explains why:

- service/include/ores.telemetry.service/app/application_exception.hpp is
  included by the component's own service/src/app/application.cpp, so it is
  infrastructure. Every service part in the tree keeps a file of this name,
  which is what made the name-based count wrong.
- database/include/ores.telemetry.database/log/database_sink_utils.hpp is
  included by database/tests/database_sink_backend_tests.cpp, so it is
  test-only, not unreached.
- core/examples/database_sink_example.cpp is built by
  core/examples/CMakeLists.txt. An example program is unreferenced by
  definition; it is documentation by example, not dead code.

The remaining eight are dead as stated: the file-JSONL exporter sub-tree
(log_exporter.hpp, file_log_exporter.hpp and .cpp, hybrid_log_exporter.hpp
and .cpp, upload_position_tracker.hpp and .cpp), whose only surviving
mention is a doxygen example block in log/lifecycle_manager.hpp, and
log/macros.hpp, whose TLOG_SEV macro is reached from no file.
