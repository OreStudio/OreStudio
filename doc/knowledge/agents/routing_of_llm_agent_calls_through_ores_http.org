#+title: Routing of LLM agent calls through ores.http
#+description: How an agent's call reaches ORE: through ores.http's MCP endpoint and the person's own permissions, never around them.
#+type: knowledge
#+level: cross
#+filetags: :knowledge:agents:mcp:architecture:
#+created: 2026-11-22
#+updated: 2026-11-22

This page states the target design. It does not describe what is built.

* Summary

An agent, a program that a language model drives, calls ORE only through
=ores.http=, and only as a person who consented to it. The claim of this page
is that the agent needs no access of its own: it borrows a person's, narrowed
by a grant, and every check that guards the person's own calls guards the
agent's. =ores.http= adds three things on the agent's path and nothing else:
the exchange of a key for the person's token, the MCP transport, and the
catalogue through which the agent finds an operation. A write it makes then
waits for further eyes, and every call it makes is recorded as its own.

* Detail

** One door

A model executes nothing itself: every effect passes through the caller that
runs its tool calls, which decides whether to permit it ([[id:0D919421-2B73-4322-9F79-9FDA38A67EA1][Large language models]],
/Tool use/). For an agent acting in ORE, =ores.http= is that caller, and an
agent reaches ORE through the =/mcp= endpoint of =ores.http= and through
no other door: not through NATS, not through the database and not through the
BFF. The rule follows from what an agent is. A person's access is decided by
the roles the person holds and enforced by the services and by row-level
security ([[id:3CAA394F-E84C-3434-331B-6E664F7E84D2][Role-Based Access Control]]); a second door would need a second copy of those
checks, and two copies drift. The prototype that preceded this design held
its own NATS credentials and its own allowlist of subjects, and the lesson
drawn from it is recorded in [[id:039005AD-8319-416C-9F70-6A5477FEE89D][The ores.agent prototype: findings for the target design]].

** The steps of a read

A read passes through five steps, drawn below.

1. The agent sends an MCP request to =/mcp= with its key as a bearer token
   ([[id:5E479832-A0B2-4BC6-B008-BAD505F4E145][Serving the Model Context Protocol from ores.http]]).
2. =ores.http= exchanges the key for a short token that names the person as
   subject and the agent as actor ([[id:1162906F-BB72-486E-9A11-30D567C65F3E][Delegation tokens for LLM agents: subject and actor claims]]); the key is the redeemable
   form of the person's [[id:A7E2942C-66AD-449C-B80B-CA789EBC34FA][Agent grants: delegated consent for LLM agents]].
3. The tool the agent called finds the operation in the catalogue and checks
   that the person may call it ([[id:4C382E8F-9449-4012-A09F-76291373E6F7][Progressive disclosure of the operation catalogue to LLM agents]]).
4. The route serves the request exactly as it serves the person's own: the
   service receives the token and applies the person's permissions.
5. The result returns, cut to a size a model can read.

** What differs from the person's own call

Three things, and each has its own page. The token names the agent, so every
write records it beside the person ([[id:2D36D474-2CF9-4498-AF49-818CEF080B98][Auditing of LLM agent actions]]). A grant can be read only,
so the agent can hold less than the person holds. And an agent's write does
not apply at once: it waits for the person and then for a second approver
([[id:381D87BB-4E2D-47BA-8853-6132CF900305][Six-eyes approval of LLM agent writes]]).
