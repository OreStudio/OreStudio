* Acceptance

- ores.ore declares, for each configuration type it imports, the setup parameter that names its file.
- A test compares that table with external/ore/xsd and with the ORE samples that exercise each parameter.
- The import no longer reads a file type to learn a parameter name.

* Plan

The codec gains =xml/run_document_files.hpp=: one row for each configuration
document a run can name, with the configuration type and the Setup parameter
whose value is its file, and a lookup by type. The service drops its
=document_kinds_of= and the =list_file_types= request it made to reporting, and
iterates the codec's table in both directions.

=ore.xsd= types the Setup parameter list without naming any of its entries, so
the names cannot be read from the schema. They come from the run documents ORE
ships, which is also where the seed generator that filled the table learned
them, and the new test holds the table against that corpus: each declared
parameter must be exercised by at least one sample.

* Notes

The pricing engines export still asks the file types table, at
=pricing_engines_handler.cpp=. That call reads the file's canonical *name*,
which a tenant may override, and not the Setup parameter that names it. The
parameter is a fact of ORE and lives in the codec; the name is a tenant's choice
and stays in the table.

The schema types the Setup list as a repeatable =Parameter= with a free name,
so it cannot say which parameter carries the conventions file. That is why the
knowledge was in a generated table rather than in the schema, and why this
table's check is the corpus ORE ships rather than the schema.

* Result

Merged as #4004. The four Setup parameters a run can name are declared in
=xml/run_document_files.hpp=, and both the import and the export read them
there. The service no longer asks reporting's file types table for a parameter,
so the request is gone from the path.

The test holds the table against the run documents ORE ships: all four declared
parameters are exercised by a sample. The schema cannot be the check, because
=ore.xsd= types the Setup list as a free-named repeatable parameter.

Proven: the service builds, =ores.ore.core.tests= passes (29s) with the new
corpus test, and the component regenerates to exactly what is committed.
