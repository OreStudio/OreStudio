* Goal

A client reads the ticks of a series with one history call, =marketdata.v1.ops.get_series_ticks=, and one live subscription. The call returns every tick of a time range in one reply. The client merges the reply with its live ticks. The design is in [[id:10E479D2-990E-4627-95A2-1DA0FA5D68D5][A chart reads a series with one history call and one live subscription]] and [[id:E1A582A6-9E12-4074-877E-91ACD7E64301][The history call returns every tick of a range in one reply, or refuses the range]].

* Acceptance

- The call returns all ticks of a range in one reply, with the coordinates stated once and the time, coordinate and value as arrays. A test states the reply for a range that holds ticks of two coordinates.
- The call has no pages and no count. A range over the ceiling is refused and the refusal names the ceiling, and a test states it.
- A context with no party is refused, and a test states it.
- A range that only the store holds returns its ticks in one reply, and a test states it. Done.
- A range that the window covers returns its ticks from the window in the same reply, and a test states it. Open: the lane window is not built, so the call answers from the store alone.
- The observation list returns no tick, and its wire comment and the shell help say so.
- The shell and the screens of a live series call the history read.
- The cause of the count of 45 in the reporting environment is found and written in the task.

* Plan

The documents come first, and they are done: the new page, and the changes to the pipeline
page, the series and observation page, the snapshots page and the ingest loop page. The
code follows the page.

1. Model the request and the reply as an operation type, so that the generator writes the
   wire types. Done: =get_series_ticks_request= and =get_series_ticks_response= in the
   operations model, with the TypeScript twin.
2. Add a tick reader to the repository: one probe on series and time, joined to the
   coordinate dictionary, for a range, with an optional coordinate. Done:
   =tick_repository::read_range=.
3. Add the handler. It refuses a context with no party, checks the range and the
   ceiling, and answers from the store. The window joins the answer when the lane window
   is built. Done for the store: =series_tick_reader= and =series_ticks_handler=, and three
   outcomes in the catalogue.
4. Point the shell and the screens of a live series at the call. Open.
5. State in the observation list that it returns no tick. Done in the model of the
   observation. The shell help has no text of its own to change.

* Notes

** Finding

The reported defect is real, and a fresh database shows it in its plain form. The list
and the count of a series read =ores_marketdata_market_observations_tbl= only. Since
c5ca60e3f6 the ingest writes live ticks to =ores_marketdata_ticks_tbl= only, so a live
series lists no point at all.

** Readers that already merge the tick table

=read_latest_for_series=, =read_as_of_records=, =read_as_of_buckets= and =read_instants=
in =market_observation_repository.cpp= read both tables. The as-of reader takes the
latest tick of each coordinate, so it gives one point for each coordinate and not a window
of points.

** Readers that read the observation table only, and keep doing so

- =read_latest_by_series_id= and =get_total_market_observation_count_by_series_id=. The
  =market_observations by-series-id= call and the series list use them.
- =read_latest(ctx, offset, limit, order, filter)= and its count, and =read_latest(ctx, ids)=.

** Readers that already take ticks

=series_snapshot_reader= calls =read_as_of_records=. =series_slice_reader= and
=series_evolution_reader= call =read_instants=. =curve_pillar_reader= and
=curve_republish_service= call =read_as_of=. =ore_export_service= reads both tables
itself. All of them reach the tick table through the repository, and no change to them
is needed. Only the list family above reads the observation table alone, and it keeps
doing so.

** The count of 45

Not explained. The fresh database has no observation row, so it cannot show the number.
The writers that still create observation rows are =import_service=,
=manual_point_service= and =curve_republish_service=. A series that an ORE import or hand
keying fed would keep its rows, and the list would show those and no tick. This is a
guess. The database of the reporting environment, or a query of its series, would settle it.

** What the build found

- Every instant has one wire shape, a text of 27 characters. A text instant for each tick
  would take more than twice the bytes of a gap, so the reply carries the first instant and
  a gap in microseconds for each tick. Page B states it.
- The ceiling is 25,000 ticks. A tick takes about 15 bytes in the three arrays, which is
  about 375 KB for a full reply against the 1 MB cap. The estimate is not measured against
  a real reply yet.
- The unit tests drive the reader against the database with a party session. Each of four
  mutants fails a test: the party check removed, the ceiling test off by one, the
  upper bound made inclusive, and the coordinate filter ignored.
- A codec round trip of the request and the reply passes with the default wire codec.
- A request with no token to the live subject answers =X-Error: unauthorized=, so the
  service serves the subject.
- Five test cases run the handler over real NATS with a minted token. A token with the read
  permission gets the ticks with the right gaps, a token without it gets =forbidden=, a request
  with no token gets =unauthorized=, a token that sees another party gets an empty reply, and a
  token that sees no party gets =party_required=. Three mutants fail a test each: the permission
  check removed, the reply that ignores the reader, and, through it, the no-party outcome.

** Decision

The observation list stays a list of observations. Ticks are a different kind of fact, with
a different key and a different cost, so they get their own read. The backlog task "List
live ticks with the observations of a series" asked for a merged list and is abandoned in
favour of this task. A client makes two calls, one for history and one for new ticks, and
merges them itself. A reply holds the whole range, with no pages.
