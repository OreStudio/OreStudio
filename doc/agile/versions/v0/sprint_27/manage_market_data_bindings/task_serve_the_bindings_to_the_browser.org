* Goal

The record screen standard builds a screen from a record kind declared once: its resource, its write schema, its field table and its columns. The BFF has no record kind for feed bindings. Declare it, with the list searched by source name and series and filtered by kind, the fields Edit offers (the source name and the enabled flag), and the write checked at the boundary with a test that a bad row and a read only write are refused.

* Result

The feed binding is a record kind of the synthetic routes, =feed-bindings=, with the permission namespace =marketdata=. A page is read for the party of the session, searched by source name and ordered by source name or the enabled flag on the server. A write states only the source name and the enabled flag. The BFF adds the session's party and the synthetic kind, keeps the party and kind of a binding that exists, and refuses a write to a binding that a real feed made, which is read only. A delete names the binding by its source name, which is how the server removes it, and it is allowed for a vendor binding. A new route, =GET /api/bindings/activity=, answers what each binding has written. Two things the review of the earlier task suggested were found true here: the bindings and observations are isolated by tenant alone, so the model now makes the party a filter of the list and the BFF always sets it. The model also makes the source name searchable and sortable. Checked live as System Party: the page, the search, the order, one binding by id, the activity read with real series and tick times, and an add, an edit, a refused stale version and a delete of a throwaway binding. The 13 new BFF tests pass, and the BFF suite passes (762).
