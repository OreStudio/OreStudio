This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A market-risk owner or a tenant administrator reads the analytics a report configuration carries, opens the screen that manages them, and reads what the change does and does not reach.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"This report does not produce what I need any more, so I want to add one
analytic, take another away, and know what that does to the runs I already
have." The person owns a report definition for a party and reads its runs. A run
came back with the measures they knew, and without the one they asked for. They
want the missing measure produced by the next run, they want a measure they no
longer read to stop costing a run, and they want one setting inside a measure
adjusted. The journey is done when the definition runs the analytics the person
meant, and the person has read what the change does and does not reach: which
rows now carry what, which configuration moved, which runs keep the
configuration they ran with, and which comparison stops being a comparison.

* Actor and trigger

A market-risk owner or a tenant administrator runs this journey. The owner knows
what the desk reads and asks for the measure; the administrator holds the
definition and makes the change. The person acts inside their own tenant, on a
definition their party owns, and the configurations they can change are the
party's own.

The trigger is a run that came back without the measure the person asked for, or
with a measure nobody reads any more, or with one setting of a measure that is
wrong for the book. The person opens the definition from
[[id:891DE3CB-2374-4FD9-B7FB-D8892F5174A1][See the reports a party runs]], and
the journey ends when the analytics read the way they meant them to.

This journey reaches the analytics of the configuration the definition binds. It
does not write the definition's name, its schedule, its concurrency policy, its
processing phases or its bindings, and it does not run the report. The next run of
the definition carries the change; nothing here makes one.

The journey is a wizard of three panels, titled *What this report runs*: the
definition and the configurations it binds, the analytics the bound configuration
carries, and what a change to that set reaches. The analytics themselves are set
on **Manage the analytics**, one screen that owns them, and step 2 opens it. This
journey is that screen's owner.

* Steps

** Step 1: the definition and the configurations it binds

1. *Read what the definition binds.* The wizard opens on step 1, titled =The
   definition and the configurations it binds=. The panel states the definition's
   =name=, =report_type=, =party_id=, and the configurations it binds. A
   definition binds configurations of exactly five types: =conventions=,
   =pricing_engines=, =todays_market=, =curve_configuration= and
   =risk_report_config=. It reads them through =report_configurations= and
   reads the configurations themselves, all five named on the panel.
2. *See what each configuration supplies.* Each of the five is shown with what it
   puts into a run: conventions supplies the calendars, day-count rules,
   business-day rules and currency pairs every analytic reads; pricing_engines
   says which engine prices which product family; todays_market carries the
   market data of the valuation date; curve_configuration says how each curve is
   built; and risk_report_config carries the analytics, their order and their
   parameters.
3. *Follow each to the screen that holds it, where one exists.* Each of the five
   links to the screen that holds its data. **Only one such screen exists today**:
   conventions is a real route, =PATHS.conventions=, which is
   =/refdata/conventions=. The other four, =pricing_engines=,
   =todays_market=, =curve_configuration= and =risk_report_config=, have no
   screen and no route, so the panel states the link as missing rather than
   drawing one that would not resolve. The panel never invents a route.
4. *Read who else is bound to the analytics.* The configurations in the first four
   slots are the party's own. The one in the fifth, =risk_report_config=, carries
   the analytics, and it is shared: three other definitions bind the same
   configuration in this fixture. The panel names them before offering a change,
   because "change this report" and "change these four reports" are different
   decisions.

** Step 2: the analytics

5. *Read the set the configuration carries.* Step 2, titled =The analytics=,
   states the set of the run settings configuration the definition binds: the
   count that is on, every row with its =display_order= and a one-line statement
   of what that analytic produces, and the rows that are on the configuration and
   off. It reads =reporting.v1.configuration_analytics.list_by_configuration_id=
   and the vocabulary with =reporting.v1.analytic_types.list=. The fourteen types
   are =npv=, =sensitivity=, =cashflow=, =curves=, =simulation=, =saccr=,
   =parametricVar=, =portfolioDetails=, =creditcurves=, =pfe=, =calibration=,
   =pnlExplain=, =historicalSimulationVar= and =xva=. The panel names the codes in
   words, and it keeps three states apart: a type that is on, a type that owns a
   row that is off, and a type the configuration has never carried.
6. *Read what the panel does not draw.* Step 2 is read only. It draws no switch,
   no parameter and no add action, because **the analytics are managed on one
   screen and this is the reading of that screen's result**. A panel that also
   drew the controls would be a second implementation of the same interaction,
   and the two would drift.

*** The shared screen: manage the analytics

7. *Open the screen that manages them.* Step 2 links to Manage the analytics,
   =doc/prototypes/reporting/manage-the-analytics/=. That screen owns the whole
   analytic interaction of a run settings configuration, and
   [[id:891DE3CB-2374-4FD9-B7FB-D8892F5174A1][Create a report]] hands the work
   there too. It opens on a switchboard: every analytic type, one row each, with
   the on/off control, the =display_order= and a one-line summary, and a type the
   configuration carries no row for says so and offers to add it. It then gives
   one step to each analytic that is on, in =display_order=, titled with the
   analytic's name, and it ends on a step that reads the set back.
8. *Read what the analytic is, and set every parameter it takes.* Each analytic
   step carries what the analytic is, how it is calculated in plain words, and
   every parameter it takes with a helpful control, a note on what the parameter
   means and what a normal value is. The control follows the parameter's shape: a
   number field for a count or a size, a select for an enumeration, a toggle for a
   boolean, and a text field for a name. An analytic that takes no parameter says
   so rather than showing an empty list. The fixture carries settings for the
   fourteen types, so almost every analytic that is on opens a step with something
   to set.
9. *Turn one off.* The person sets the row's =active= to false. The row stays.
   **An analytic is turned off by setting =active= false, not by deleting the
   row**, because the history must show that it was turned off: a person who
   reads the configuration later sees the measure, its =display_order= and its
   parameters, and sees that it is off. Deleting the row would erase the fact
   that the report ever produced it. The shared screen asks first, because the
   parameter values leave the rail with the step, and it states the write in
   those words. **No control anywhere on either screen removes a row.**
10. *Turn one on.* Turning an analytic on, or adding one the configuration never
    carried, is the switch on the switchboard, and the switch is the only way to
    add one. It writes the row with the default value of every parameter at the
    next =display_order= and gives the analytic a step of its own, so the person
    is offered the step the switch just created. A row that exists and is off is
    turned back on with the settings it kept.
11. *Read where the editor is deferred.* =simulation= and =pfe= need
    purpose-built editors for the cube, the shift and the time grid. The shared
    screen says so on the parameter itself: these are drawn as plain fields for
    now, each labelled a deferred editor, and the purpose-built editor is a later
    task. The page never presents a plain field as the final design.
12. *Read the set back.* The last step of the shared screen names the rows rather
    than counting them: each active analytic with its =display_order= and its
    number of parameter rows, the rows kept off with their order, every parameter
    value with its position, and the definitions bound to the configuration that
    read the set. It is the final step, so it offers no Back, and it offers the
    way back to the report.

** The rule between analytics

13. *See the incompatibility as a state, not as prose.* =pfe= reads a cube that
     =simulation= writes, so =pfe= on without =simulation= cannot work. Both
     screens show that as a visible state: the rule strip names the rule and
     marks the set as one that cannot run, both rows are marked in red, and on
     the shared screen the toggle that would write either row of the pair is
     refused and its last step refuses to read the set back. The rule lives in
     the ACME seeder, in =generate_risk_config_data.py=, function
     =check_exposure_needs_simulation=, and **no service validates it**. The write
     would be accepted and the run would fail later, so the shared screen refuses
     what the server would not, and says that is what it is doing.

** Step 3: what a change reaches

14. *Review what a change does and does not reach.* Step 3, titled =What a change
     reaches=, states the reach before anything is written. It reaches the next
     run of every definition bound to this configuration, including the three the
     person did not open. It does not reach a run already produced: a run keeps
     the configuration it ran with, and its outputs and its errors are that run's
     own record. It does not reach the definition's scheduling, its processing
     phases, its concurrency policy or its other four configurations.
15. *Read that the comparison stops being a comparison.* A run made after the
     change is not comparable with a run made before it, because the two runs did
     not produce the same measures. The difference between them is then a
     difference of configuration and not a difference of the book, and the
     comparison states a change that did not happen. The panel says so plainly,
     and names the definition's runs from before the write as the runs it makes
     incomparable.
16. *Read where the write happens.* The write is the shared screen's and not this
     wizard's. The set is sent in one call, so a turned-on analytic, a
     turned-off one and a changed parameter land together and a half-written
     configuration is not left behind; one setting alone is written one row at a
     time. Step 3 names the operations, states that this page stages nothing and
     writes nothing, and points at the screen that does. No step anywhere deletes
     a row.
17. *See the version history.* The person reads the definition's version history:
     the versions it has had, and what each one states. This is the record of the
     change, and it is also the only timeline the screen has to place a run
     against. It is not a complete answer. **No operation says which runs were
     made with which configuration version.** The best the screen can do is
     compare a run's own start time with the definition's version history and say
     that a run started before a version, which is an inference and not a fact,
     because the analytics live on the configuration and the configuration's own
     version history is not read here. *What is missing* records all of it.
18. *Leave, or go on.* The person returns to the definition's latest run, or runs
     the report to see the new measures. The run is
     [[id:76431668-8656-4276-9F9B-F292FE45B2CA][Run a report and watch it
     finish]]'s page, and its figures are
     [[id:969C14D2-4280-4D7C-8F51-1D395B521C83][Read what a run produced]]'s.
     This journey changes what the next run produces and nothing else.

* Screens and wireframes

Two screens. The wizard has three panels: step 1 shows the definition header and
the five configurations it binds, each with what it supplies and a link to the
screen that holds its data; step 2 shows the analytics of the bound run settings
configuration as a read-only summary — the count on, the display order, the rows
kept off, and the pair marked when it cannot run — and links to the shared
screen; step 3 shows what a change reaches and the runs it makes incomparable.
The person reads the three as one answer: what this report runs, and what
changing it does.

Manage the analytics is the second screen, and it owns the analytic interaction
for every journey that needs it. It is the standard steps UI: a switchboard of
the fourteen types, one rail step per analytic that is on in =display_order=
carrying that analytic's explanation, calculation and every parameter with a
control chosen for its shape, and a final step that reads the set back and
refuses to read a set that cannot run. The rail is computed from the set, so
turning an analytic on adds a step and turning one off removes it.

The two screens write two things and read eight. They write the analytic rows and
their parameter rows, both from the shared screen. They read the definition, its
bindings, the five configurations, the configuration's analytics, their
parameters, the analytic types, the definition's versions, and the configurations
grouped by type. They run nothing and they schedule nothing.

The wizard keeps four statements beside the summary, because a person who reads
only the wizard must still read them. Turning an analytic off sets =active= to
false and leaves the row. A configuration is shared, so the change can reach
definitions the person did not open. A run keeps the configuration it ran with,
and nothing says which configuration version that was. And a run after the change
is not comparable with a run before it. The wizard draws the incomparable runs by
their start times and says the placement is an inference.

* Prototype

The [[file:../../prototypes/reporting/manage-the-analytics/][manage the analytics
prototype]] owns this journey, and
[[file:../../prototypes/reporting/manage-the-analytics.org][its design note]] says
what it argues, which states it can reach and what is fake. It belongs at
=doc/prototypes/reporting/manage-the-analytics/=.

It is one screen on the standard steps UI, and it draws the whole analytic
interaction: the switchboard with every analytic type as one row, the on/off
control, the =display_order= and a one-line summary; a rail step for each
analytic that is on in =display_order=, titled with its name, carrying what the
analytic is, how it is calculated, and every parameter with a control chosen for
its shape and a note on its meaning and its normal value; and a final step that
reads the set back and offers the way to the report. It must show the =pfe=
incompatibility as a visible state — the rule strip, both rows marked, the toggle
refused and the last step refusing to read the set back — and it must name the
rule and the seeder it lives in. It must state that an analytic is turned off by
setting =active= false and never by deleting the row, and no control on it may
remove a row. It must say that the complex editors for =simulation= and =pfe= are
deferred, and label each as it draws it. It carries =?variant=A|B|C= as three
readings of the per-analytic step, because that layout is the open question. Every
value on the page is a fixture, and the page says so.

The [[file:../../prototypes/reporting/change-what-a-report-runs/][change what a
report runs prototype]] is the same journey's wizard, and
[[file:../../prototypes/reporting/change-what-a-report-runs.org][its design
note]] says what it argues. It belongs at
=doc/prototypes/reporting/change-what-a-report-runs/=. It must draw step 1 with
the definition's five bindings, each with what it supplies and a link that is real
for conventions and stated missing for the other four; step 2 as the read-only
summary of the bound configuration's analytics, with the =active= flag shown, the
display order, the incompatibility as a visible state, and the link to the shared
prototype; and step 3 with what a change reaches and the runs it makes
incomparable, placed by start time against the definition's version history and
marked an inference. It must state the server's silence beside the rule, say that
past runs keep their configuration, that the configuration is shared, and that a
new run is not comparable with an older one. It draws no analytic control, because
the shared prototype owns them.

The rows this journey edits are =configuration_analytic= and
=configuration_analytic_parameter=, and neither belongs to the definition. The
definition reaches them through =report_configuration=, one row per configuration
type, and the configuration in the fifth type, =risk_report_config=, is the one
that carries the analytics. The definition's own fields are shown to the person
but not written here:
=schedule_expression=, =concurrency_policy=, =pre_processing=,
=prepared_input_key=, =post_processing= and =is_official= all stay as they are.

The definition is bitemporal. An edit writes a new version, older versions stay
readable, and a run keeps the configuration it ran with. That is what makes the
change safe to make and hard to read afterwards: nothing is destroyed, and
nothing names the version a run used.

Every entity above carries =party_id= and is party-scoped by row-level security.
The analytic and its parameters carry the tenant as well, because a
configuration's analytics are written by the session that writes the
configuration.

Two operations are this journey's writes, and =configuration_analytics.put_many=
carries the set. A person toggles rows, adds one with the switch, and the shared
screen sends the whole set at once, so added, turned-off and reordered analytics
land together and a half-written configuration is not left behind.
=configuration_analytic_parameters.put= writes one parameter at a time, because
a parameter is one row with one value and the set of parameters a person edits is
not a unit. Both belong to the shared screen; the wizard sends neither.

=report_configurations.put=, =configurations.put= and =report_definitions.put=
exist, and this journey sends none. Reaching into another configuration,
rebinding the definition to a different one, or editing the definition's own
fields is a different change: it would move every analytic at once and leave the
old configuration running for whoever else binds it. A person who wants that has
not asked to change what a report runs; they have asked to change which
configuration it uses, or what the definition says.

No BFF route serves reporting. The shared screen adds one, for example
=GET /api/reporting/configurations/<configuration-id>/analytics= for the read and
=PUT /api/reporting/configurations/<configuration-id>/analytics= for the write,
which calls =configuration_analytics.put_many= and the parameter write behind it.

* What is missing

1. *A route and a screen for reporting.* No BFF route serves reporting, and
   nothing in the web application shows a report today. The wizard, the summary,
   the shared analytics screen and the read-back are new.
2. *No screen exists for four of the five configuration types.* Step 1 names the
   five configurations the definition binds, says what each supplies, and links
   each to the screen that holds its data. **Only conventions has a screen
   today**: =PATHS.conventions= is =/refdata/conventions=, a real route in
   =projects/ores.web/packages/web/src/shell/paths.ts=. The other four,
   =pricing_engines=, =todays_market=, =curve_configuration= and
   =risk_report_config=, have no screen and no route, so step 1 states the link
   as missing rather than drawing one that would not resolve. A person who wants
   to change the engines, the market data or the curves behind a run has nowhere
   to go, and the wizard says so instead of hiding it.
3. *The complex editors for simulation and pfe are deferred.* =simulation= and
   =pfe= each need a purpose-built editor: one for the cube, one for the shift,
   one for the time grid. Manage the analytics draws those settings as plain
   fields, =time_grid= as a select and =exposure_cube= as a text field, and it
   says on the parameter that the purpose-built editor is a later task. A plain
   field is not the design, and the page never pretends it is.
4. *Nothing validates the =pfe= rule.* =pfe= reads a cube that =simulation=
   writes, so =pfe= on without =simulation= cannot work. That rule lives
   in the ACME seeder, in =generate_risk_config_data.py=, function
   =check_exposure_needs_simulation=, and nowhere else. The reporting service
   does not check it when a configuration is written, so
   =reporting.v1.configuration_analytics.put_many= accepts the set and the
   failure arrives in the run. A screen cannot rely on a refusal it does not get,
   so the summary marks the pair, the shared screen refuses the toggle and its
   last step refuses to read the set back, and all three name the rule. That is a
   screen defending itself against a server that does not, and it is the
   second-best answer; a validation on the write is the first.
5. *No operation says which runs used which configuration.* A run keeps the
   configuration it ran with, and nothing reads that configuration back with the
   run. The screen can place a run against the definition's version history by
   the run's own start time, and that is an inference: the analytics live on the
   configuration, and the definition's version history says what the definition
   changed, not what the configuration held. A person who needs "this run predates
   my change" has an inference and no fact, which is why the panel marks it.
6. *No read of a configuration's version history.* A configuration carries a
   version, and no operation in this journey's set returns the versions of one
   configuration or the version a definition bound at a time. The definition's
   history is the only history the screen can read, and it is a history of a
   different row.
7. *The comparison is marked partial for errors and not for a changed set of
   analytics.* The results screen compares a run with a previous run of the same
   definition and marks the comparison partial where either side carried errors.
   It cannot mark it invalid because the analytics changed, because nothing tells
   it that they did. A person reading a comparison across the change is reading
   two different sets of measures side by side, and the screen shows the change
   as a change in the figures.
8. *The allowed values of a parameter are not readable here.* A parameter's kind
   comes from the definition behind it, and the operations in this journey's set
   read the configuration's parameter rows and the analytic types. No operation
   in the set returns the value domain of a parameter, so the shared screen draws
   a select only where the fixture knows the enumeration, and a text field where
   it does not, and cannot tell the person whether a value is one the analytic
   accepts. A run is where a wrong value shows up.
