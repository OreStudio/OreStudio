* Goal

A DSH plugin that shows the sprint as a kanban board inside the DSH web
session. The board reads the agile org tree directly, so it is never stale,
and it surfaces the properties the org files already carry: the environment
working each story and task, the state, the branch, the PR, the owner, the
epic, and the task progress. The work tree the session runs in is
highlighted, and one control filters the board to a single environment.

* Acceptance

- The board renders in a live DSH session and reads the current sprint from
  =doc/agile/versions=, with no build step and no stale index.
- Every card shows the story's environment, state, epic, task progress,
  branch, and PR.
- The session's own work tree is identified and its story is highlighted.
- Filtering by environment answers which story and task a given work tree
  is on.
- Story and task details are reachable from the board without leaving the
  session.

* Plan

The board is a read-only view over the org tree, so the work split three ways
and the seams were frozen before either half was written.

- =CONTRACT.md= names every payload field, the resolution rules, and both client
  seats. The host half was built and measured against it first, and the browser
  half then consumed it. The two halves changed without touching each other.
- The host reads the org tree. =lib/agile.js= is a pure transform from org text
  to the model, so the parser is tested with no server and no filesystem.
  =lib/git.js= owns the only process boundary, answering the work tree list and
  each work tree's journal.
- The browser half is one hand-written file loaded verbatim by the module
  loader, with no build step and no dependencies beyond React from the platform
  module table. That keeps the whole plugin to five files.

The design changed twice under review, both times from the user. The first scope
was a single work-item panel, and it became a board. The second was a board that
could be pointed at any work tree; that came out, because a board showing one
work tree's data inside another work tree's session is the confusing case, and
the fleet strip became a read-only overview instead.

* Result

=projects/ores.dsh_kanban= is a DSH web plugin that renders the session's own
work tree's sprint as a kanban board, read from the org tree on disk. It is
read-only, it has no build step, and it is five files.

What it shows. A five-column board of the sprint's stories, coloured by state,
with the session's own story outlined and scrolled into view. Each card carries
the story's environment, epic, task progress, and age. A read-only fleet strip
lists every work tree and what each is currently on. A header readout names the
current environment, story, and task without opening the board. The detail panel
carries the story's id, state, environment, epic, dates, description, branches,
and pull requests, then every task with its own state, environment, branch, and
PR.

How it resolves the work tree. Three strict rungs: the host session store, then
a directory that must land on a work tree root of this repository, then failure.
There is no fallback to the process working directory, because the shipped unit
starts the server in the user's home and that fallback would answer for a
directory that is not a work tree. =tree.source= reports the rung taken.

Measured. 31 host tests, 87 browser assertions in a real Chrome against a real
instance, exit 0. Payload 470KB. Cold request 0.22s, cached 0.01s. No page
errors.

Packaging. The plugin carries the ORE Studio version, enforced against
=CMakeLists.txt= by =scripts/check-manifest.mjs=, and =scripts/install.mjs=
installs it into a profile as an independent copy extracted from a versioned
tarball rather than as a link into a work tree.

Verification. =scripts/verify.mjs= is the client gate. It binds its own port,
copies the scratch home so it can run beside a served instance, refuses to
continue unless the boot log names the port it bound, asserts the resolution
ladder, drives the board in a real browser, and measures overflow rather than
leaving it to the eye. A workflow runs the manifest check, a parse check on the
browser bundle, and the host tests, because no existing workflow reaches this
component.
