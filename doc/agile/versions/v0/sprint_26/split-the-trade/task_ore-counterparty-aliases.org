* Acceptance

- The ORE scheme is a party identifier scheme with no cardinality limit, and an alias names at most one counterparty per tenant.
- An inventory of the counterparty names in the ORE samples is recorded with the count of each.
- A fresh database publishes the chosen GLEIF banks as counterparties beside ACME's own, and gives each sample name an ORE alias onto one of them.
- The LEI counterparty publish adds the LEIs a tenant lacks instead of skipping a tenant that already has any.
- Build, ctest, pgTAP and the local check set pass.

* Plan

- The owner chose an import alias over a mapping table: an ORE document's
  CounterParty name is an identifier of a real counterparty, under a new =ORE=
  party identifier scheme with no cardinality limit. It mirrors task 4, where
  ORE's =Trade/@id= became a trade identifier scheme, and a later source
  system gets a scheme of its own the same way.
- A unique index on =(tenant_id, id_scheme, id_value)= for current =ORE= rows
  makes a name answer to one counterparty per tenant; other schemes keep the
  per-counterparty key.
- The samples' placeholder names map onto eleven GLEIF banks the owner asked me
  to pick, all active in the small GLEIF dataset. The busiest names take the
  largest dealers; =CPTY_1= to =CPTY_10=, which one example uses together, take
  ten different banks. The inventory is in
  =evidence/ore_sample_counterparties.txt=.
- =ore.sample_counterparties= is an LEI entities dataset in the =ORE= catalog
  whose rows are selected from =gleif.lei_entities.small=, not copied. A
  populate script publishes it into the system tenant, where ACME publishes,
  and adds the 23 aliases.
- The LEI counterparty publish skipped any tenant that already had an LEI
  counterparty, so a second dataset could never publish beside ACME's. It now
  removes the LEIs the tenant already holds and skips only when none is
  left.
