* Goal

The Add dialog lists the synthetic sources the party does not consume, says which series each would write, and refuses a source whose series a running feed already writes. Today no read joins the generation configs to the bindings, and no read says which feed holds a series, so the check would come after the write. Add the reads, so the dialog can say it before.

* Acceptance

- A read lists the synthetic sources with no binding for the party, each with the series it would write.
- A read says which running feed writes a series, and the dialog uses it before the write.
- The reads are in the generated protocol and the BFF contract, with tests.

* Plan

The read splits in two, and only one half can be a server read.

*The sources a party may bind* are its own generation configs, and its
*bindings* belong to the marketdata service. No service user reads the other's
tables: measured across =projects/ores.sql/create/=, marketdata reads no
=ores_synthetic_*= table and synthetic reads no =ores_marketdata_*= table, and no
cross-service function exists in either. The join therefore belongs in the BFF,
which already reads both sides for the bindings screen and the activity route.
That keeps the service-table isolation rule intact rather than widening a grant
for one screen.

*Which running feed holds a series* is the synthetic service's own to answer.
The feed controller holds the running set, its =feeds_conflict()= decides that a
series belongs to one feed at a time, and it already exposes
=running_source_name_for_series()=. The feed overview handler already holds the
controller as =ctrl_=. This is the answer the journey calls missing, and it is
the read that has to be a new subject, because only the running service knows
it.

So the work is:

1. A new synthetic read, =synthetic.v1.ops.resolve_series_owners=: given a list
   of series, the source name of the running feed that holds each, empty where
   none does. Declared in =ores.synthetic.feed_overview.org= beside
   =list_folder_feeds=, so the C++ protocol and the TypeScript protocol are both
   generated from it. Served from the controller through the feed overview
   handler, registered in =registrar.cpp=.
2. A BFF read, =GET /api/bindings/bindable-sources=: for the caller's party, the
   synthetic sources with no binding, each with the series it would write, and
   the running feed that already holds that series where there is one. Composed
   from the feed overview read, the feed bindings read and the new read.
3. Tests at both seams: the handler unit test for the controller answer, and the
   BFF test for the composition, including a source that is already bound and a
   source whose series a running feed holds.

The Add dialog of the next task takes the BFF read. The handler read is what
makes its refusal the controller's answer rather than a guess from the feed
listing.
