#+title: Story: Handle the backlog when the compute path stalls
#+description: The compute path has no backpressure and no cheap way to tell that a downstream store has stopped. On 2026-11-19 pauli's disk filled; JetStream could not store a message, js_PublishMsg waited five seconds for an ack that never came, and batch_workflow_bridge blocked the compute service's only io_context for that whole time. The grid poller shares that thread, so its thirty second cadence slipped to a hundred and seventy seconds and the overview chart lost its samples. Meanwhile the marketdata usage recorder had written 2.3 million delivery count rows, 2.4 GB, one new versioned row per party per thirty second flush. This story makes the path survive a stall: bound the growth, give each cadence its own execution, refuse work the previous run has not finished, and report a full store as a full store.

| [[id:2FDC34EA-1816-4654-BA55-48BD8158252D][Stop the delivery counts from growing without bound]] | STARTED | 2026-11-19 | | The marketdata usage recorder flushes every thirty seconds and writes one new versioned row per party and feed through delivery_count_repository::write, which is an INSERT into a versioned table. On pauli this reached 2.3 million rows, 2.4 GB, one day of a counter that only needs its current value. Make the flush carry the counter forward instead of appending history, or state and enforce a retention, so the table's size follows the number of subscriptions rather than the number of flushes. |
| [[id:BC700C53-DF63-4D2E-9B87-1E7A8F72DAE7][Take the bridge's publishes off the service's only thread]] | DONE | 2026-11-19 | 2026-11-19 | batch_workflow_bridge::poll_once walks every pending link and calls nats_.js_publish synchronously. One link whose ack never arrives blocks the coroutine for the client's five second default, and because the bridge, the grid poller and every request handler share one io_context, the whole service stops with it. Cap the work a single poll may do, publish without blocking the executor, and back off when a publish fails instead of retrying every link in turn. |
| [[id:86DB6342-7255-42F3-9E2A-6E3C121E22C5][Keep the grid poller on its cadence while the service is busy]] | DONE | 2026-11-19 | 2026-11-19 | compute_grid_poller runs poll_once synchronously on the io_context and only arms its steady timer afterwards, so any blocking work elsewhere in the service pushes the sample interval out. In the incident the chart lost every bucket between samples. Sample on a timer that measures from the previous expiry rather than from the end of the work, and run the sampling where a busy executor cannot delay it. |
| [[id:9AE9A146-B379-4E42-8B07-E29AD79454F4][Refuse a report while the previous one is unprocessed]] | DONE | 2026-11-19 | 2026-11-19 | report_submit_handler creates a batch and its workunits for every submit_compute step and never asks whether an earlier batch for the same tenant and party is still open. A stalled engine therefore queues more work behind work that cannot finish. Refuse the step, with a reason the run can report, while an earlier batch for that party is unprocessed, so the queue cannot grow past what the grid is draining. |
| [[id:F2E50639-0C5E-4BB2-AF54-141975BCC252][Report a full store as a full store]] | DONE | 2026-11-19 | 2026-11-19 | When JetStream cannot write, js_PublishMsg waits for an ack that never comes and the caller sees only Timeout, five seconds later, with no cause. Make a failed store surface the server's own error, so a full disk reads as a full disk, and have the compute service and the site show the grid's storage state instead of silently dropping its samples. |
