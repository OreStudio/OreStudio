* Goal

The five refdata journeys that were drawn and written in
[[id:93E2D898-6098-4C1C-9C4E-0E8BFDF4E799][Write the refdata party,
book, convention and tenor journeys]] work in =ores.web=, on the server
changes each one needs. A tenant administrator onboards a counterparty,
keeps a party's details current, shapes the book structure, defines the
conventions for an instrument and defines how tenors resolve, on screens
that match the accepted prototypes.

Each journey document records what the server does not yet provide. The
gaps are the tasks here, grouped by concern rather than by journey where
several journeys need the same thing.

* Acceptance

- Each of the five journeys runs end to end in =ores.web= against the
  live fleet, and matches the prototype the product owner accepted.
- Every gap recorded in the five journey documents is either built or
  recorded as dropped with its reason.

  its coverage table claims, and the tables are corrected where they
  say =missing= and the operation has since been built.

  the catalogue assigns them.

* Decisions

- *The gaps are tasks, and they are grouped by concern.* Several
  journeys need the same thing: a refusal that names the field, a
  field-level diff in a reply, a composite write. One task per gap
  would have produced four tasks saying the same thing, so the tasks
  below group the gaps where a single change closes several.
- *The refusal shape comes first.* Every screen reads a refusal, so the
  shape it reads is settled before the screens are built, not while
  they are.
- *The server tasks precede the screens they block.* A screen is built
  against the operations it needs, so the task order follows the
  dependency, not the journey number.
