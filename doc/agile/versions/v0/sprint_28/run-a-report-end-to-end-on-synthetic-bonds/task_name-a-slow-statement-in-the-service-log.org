* Acceptance

- A read of 250 ms or more logs a warning with its description and duration.
- The executor that opens its own connection logs the connect, session and statement parts.
- A read below the threshold logs at debug level only.

* Plan

The task before this one removed the slow export and inferred its cause from the plan of one statement. This task measures the cause. The two executors that run a read, =execute_read_query= and =execute_parameterized_multi_column_query=, time each read. A read of 250 ms or more logs a warning with its description and duration. The executor that opens its own connection also splits the time into the connection, the session settings and the statement. A read below the threshold logs at debug level.

* Notes

The cause of the 38 seconds is now measured. A statement of the old export took 32 to 73 ms in the database even for one row, because the planner works through every chunk of the observation table, and the table has 163 of them. The executor also opened a connection for each statement, 13 to 16 ms. A statement for each series, three per series, over 306 series, is about 42 seconds. The export took 38.

The chunk count is not ACME's. ACME's rows sit in 13 monthly chunks. 22 other tenants hold 99.6% of the rows, and their dates run from 2016 to 2035. They are the rows the C++ test suites write into this database, with random dates. So the same code on a database without that residue plans over 13 chunks, and the old export would likely have passed. This is an inference and has not been run. The code still did a statement for each series, so the test residue exposed a defect that was already there.

Seen on the way and handed on:

- The usage recorder, the feed ingest loop and the usage planner write =modified_by= as the text =ores.marketdata.service=. After bootstrap the database accepts only the name of an account. The service account is =ores_swift_curie_marketdata_service=, which the service already holds as =db_opts.user=. So the recorder fails every flush, with 19,910 delivery counts waiting.
- =gather_trades= and =gather_market_data= have no =consumes=, so they run side by side. When one fails, the other can already have started, and it logs "cannot move from failed to running". It is by design and harmless, but the log says ERROR.
- The database schema fingerprint differs from the checkout, so the database needs a recreate before the soak.

* Result

A read of 250 ms or more now names itself and its duration in the service log. The executor that opens its own connection says how the time split. A run of the NPV report on the instrumented services completed in 12 s with the export at 214 ms, and no read crossed the threshold. The timing line was seen at debug level in a test, so the warning level is by the same code path but has not been seen to fire.
