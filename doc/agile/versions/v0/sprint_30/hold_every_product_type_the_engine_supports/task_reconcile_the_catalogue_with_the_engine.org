* Goal

A reader can tell, for every product type, what ORE does with it: the trade type it is registered under, the data element it is read from, whether it is a ScriptedTrade subclass or a native class, and whether it is supported at all.

* Acceptance

- each of the 121 catalogue types states its ORE evidence: registered trade type, data element, and the class it is read as
- the types ORE cannot carry are named, with the evidence that shows it
- each type ORE reads through a ScriptedTrade subclass names the library script with the same payoff, where one exists, so the both-forms task has its list
- the evidence is mined by a script from ORE's Engine source and its script library, names the ORE commit it read, and is checked in as a table the checks read
- the note links the task that closes each gap, so the coverage work has one index

* Plan

Ask ORE itself rather than read its registrations as text. A harness,
=trade_catalogue=, calls ORE's =dataBuilders()=, builds every type the trade
factory holds and prints its class and whether it derives from
=ScriptedTrade=. A miner, =mine_trade_types.py=, joins that with ORE's source
(the element =fromXML= reads), the XSD, the Products script library, two
curated lists (the twins and the elements that break ORE's naming
convention) and the catalogue. Twins are graded by comparing the library
script's code with the code ORE's class embeds. The result is checked in
beside the other mined catalogues, and a generator turns it into the coverage
note, with a =--check= mode wired into the local gate.

* Result

Every catalogue type now states what ORE does with it, from ORE itself. The
=trade_catalogue= harness asks ORE's trade factory for each registered type
and the class it builds; =mine_trade_types.py= adds the data element read in
ORE's source, whether the XSD declares it, and the library scripts that carry
the same product, graded by comparing their code with the class's own. The
result is =external/ore/catalogue/trade_types.tsv= at ORE =3d75a6908=, and
[[id:CC7CC29C-9413-4DF3-BC32-D1C8A978D295][Which trade types ORE carries and ORE Studio holds]] renders it with the table that holds each type, whether the generator
books it, and the task that closes each gap. A =trade-type-coverage= check in
the local gate fails when the page drifts from its sources.

What it found: ORE reads 39 types through a =ScriptedTrade= class and the
catalogue states 5 of them so; =CommodityPairwiseVarianceSwap= and the bare
=ForwardVolatilityAgreement= have no builder but are carried by library
scripts; =CommodityWindowBarrierOptionData= is read by ORE and missing from
the XSD; three types read an element other than the convention's; and 35 types
have a library twin, 9 of them in identical code.
