* Analysis

The previous story, [[id:E5A10C2E-E4E6-49C4-A4D0-78A6F0E2CBE2][Filter and search trades through the model]], declared the columns of the trade itself. Four needs remain, and they need three kinds of change.

** What constrains the design

- The state, booking, identifiers, party roles, portfolios and additional fields are separate entities. Each is keyed by =trade_id= and has its own version timeline.
- A filter record covers only the entity's own columns. It has equals, one-of and =search= members. It has no range member and no member that reaches into another entity.
- =subtree= works only where a relation is the entity's own parent. Everywhere else the generated service refuses with =scope_not_supported=.
- A book belongs to a portfolio (=parent_portfolio_id=), and the portfolios form the tree.

** Child tables: no protocol change

- Put =:list_by: true= on =trade_id= in each child model. That gives =list_by_trade_id= for the identifiers, party roles, portfolios, additional fields and instrument parts.
- State and booking are one row per trade, so =get= already reads them. For a page of trades, one =get_many= with the page's trade ids reads their states and bookings.
- Unchecked: the generator may not accept =:list_by:= on a column that is also the primary key. The spike answers it.

** State, book and date: three options

- *A. Join in the client.* The screen lists the bookings for a book, then calls =get_many= on the trades. This breaks the total, the paging, the sort order and any combination with the counterparty filter. Rejected.
- *B. Cross-entity filter members.* A trade column declares "filter through =trade_booking.book_id=", and the repository joins. This puts joins into the generic protocol, and each joined component needs its own as-of handling.
- *C. A read-only entity, =trade_summary=.* A standard entity with =list= and =get=, backed by a SQL view. It carries the trade, its current state and booking, and the identifiers as one searchable text column. Every filter is an ordinary member, and the total and paging stay correct.

Recommendation: C. The cost is a new entity: a registry entry, a permission and a TypeScript twin. Unchecked: whether the generator supports a view-backed read-only entity, and how =as_of= works across the joined tables. The second is the main risk.

** Book filter and portfolio subtree

- Book filtering is =book_id= equals or one-of on the summary.
- A portfolio subtree is not a trade subtree. The client resolves the portfolio to its books, then sends =book_id_one_of=. The limit is 1000 books.

** Identifier search

A trade has several identifiers (UTI, USI, internal, ORE). The summary carries them as one aggregated, searchable text column. A search then matches any scheme, ignoring case and literally, as the trade type search does. The view builds the column at query time, and no index supports a case-insensitive literal scan over it. The summary task measures a large list and decides whether a trigram index is needed.

** Enum filters

The generator takes a filter member's type from the column's C++ type, so an enum column gets an enum-typed member. The repository binding and the TypeScript type are unproven. The spike proves both with =counterparty_scope=. An enum member also rejects invalid values at decode, which a text member would not. The spike checks that the error is the one other invalid filters give.

** Date filters

Equals on a date is useless, and the filter record has no range member. The proposal is =<column>_from= and =<column>_to=, inclusive, on date and timestamp columns that declare =:filterable: true=. A =_to= on a date column includes the whole day. On a timestamp column a =_to= given as a date means the end of that day. This is a specification change, then a generator change, then the TypeScript twin.

* Decisions

Open, to settle before the tasks that depend on them:

- Option C (=trade_summary=) against option B (cross-entity filter members). Recommended: C. The spike and the summary task depend on it.
- The range member for dates. Recommended: =_from= and =_to=, inclusive. The range task depends on it.
- The limit of 1000 books for a portfolio subtree. Above it the client refuses the scope and says why. It never truncates, because a truncated filter returns a wrong total.
- The instant of the trade summary. One read states one =as_of=, and the view takes the state and the booking that were current at that instant, so they never come from different instants.
