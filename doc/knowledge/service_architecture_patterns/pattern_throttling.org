This page defines the [[id:68FAC606-569C-4B9B-932B-3B3A0181AC8B][service architecture pattern]]
Throttling in the [[id:EA249899-6611-407F-A43A-B37019EBD1A7][pattern language]].
A service limits how much one caller or tenant may ask for in a period, so no
single source can exhaust it. In ORE Studio IAM limits token exchanges per
service and per tenant, and reporting caps the runs of each tenant and party.

* Also known as

- /Rate limiting/.
- /Quota/, for a limit on concurrent work rather than a rate.

* Context

A shared service serves many callers. One caller, by fault or by load, can send
more than the service can serve.

* Problem

How does a service protect itself, and its other callers, from one source of
excess load?

* Forces

- Every caller deserves service; none may take all of it.
- Some work can wait; some must be refused.
- A refused caller needs to know when to try again.

* Solution

Count each caller's use over a period, or its work in flight, against a limit.
Over the limit, delay the request, queue it, or refuse it with a reason and a time
to try again. Log every refusal with the caller and the limit.

* Failure handling

#+ATTR_HTML: :class hug-leading
| Concern | What the pattern does |
|---------+-----------------------|
| Errors | A refusal names the limit and, where it can, when to try again. |
| Timeouts | Does not apply: the limit counts use, not time. |
| Retries | A refused caller retries after the stated time, with back-off; see [[id:93737023-4FB7-45CD-9511-9B27DBACB2FC][Retry]]. |
| Idempotency | Does not apply. |
| Observability | Refusals are counted per caller, per tenant and per limit. |

* Pitfalls

- *Limits nobody sees until they bite.* State them, and measure use against them.
- *A limit per replica.* Several replicas each grant the limit, so the real limit multiplies.
- *Retries that ignore the refusal's time.* They arrive at once and are refused again.

* Security

Availability: a faulty or hostile caller cannot exhaust the service. Limits per
tenant keep one tenant's fault from reaching another.

* Resulting context

- Benefits :: The service stays up under excess load, and the cause is named.
- Liabilities :: Legitimate bursts are delayed or refused, and limits need tuning.
