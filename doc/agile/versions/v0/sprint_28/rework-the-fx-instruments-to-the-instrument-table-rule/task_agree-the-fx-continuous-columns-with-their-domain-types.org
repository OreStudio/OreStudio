* Result

=fx_variance_swap_instrument.strike= is =double precision= at rest, matching the
=double= the domain and the entity already carried. A variance strike is a
volatility, so rounding it to twelve decimal places stated a precision the
quantity does not have.

The sweep walked every column of the seven FX models and of
=ores.trading.range_bound= whose C++ type is float or decimal, which is the
population that can hold a continuous value in this family. Its command:

#+begin_src python

for path in paths:
    text = path.read_text()
    for m in re.finditer(r"^\*\* (\w+)\n:PROPERTIES:\n(.*?):END:", text, re.S | re.M):

The columns that already agreed, and why each is money rather than
continuous, by the rule in [[file:../../../../../../doc/knowledge/architecture/exact_numbers_and_economic_change.org][exact numbers and economic change]]:

| Column | Where | Reading |
|--------+-------+---------|
| bought_amount, sold_amount | the forward, vanilla option and barrier option facts | an amount |
| fixing_amount, target_amount, reference_notional, settlement_notional, notional | the accumulator, the Asian forward and the variance swap facts | an amount |
| strike | the accumulator, the Asian forward and the digital option facts | a price level |
| lower_barrier, upper_barrier, knock_out_barrier | the barrier, digital and accumulator facts | a level |
| range_from, range_to, strike, strike_adjustment | =range_bound= | a price level |

Each is =numeric(38, 12)= in the column and an exact decimal in the domain, so
each agreed before the unit. The two continuous quantities are the variance
strike and =range_bound.leverage=, and both now carry =double precision= with a
=double=.

The sweep also found the same quantity typed the other way one family over:
=equity_variance_swap_instrument.variance_strike= was =numeric(38, 12)= with a
decimal in the domain. Both families read the same =varianceSwapData.Strike=,
an =xs:float=, so the column is mirrored to =double precision= here rather than
left to disagree with its twin.

Both columns also gained a check that refuses what a double admits and a
numeric does not: an infinite or not-a-number strike, which no comparison
downstream can use.

Nothing that is money moved to a float. The SQL regenerated from the model, the
generated C++ did not change because the entity and the mapper already read a
=double=, and =check_model_sql_types.py= passes.

* Decisions

- *A variance strike is continuous, not money.* It is a volatility, the same
  kind of quantity as a basket weight, so the exact-numbers rule puts it in the
  binary double direction. The money direction is for amounts, notionals, price
  levels and rates, which is what the other columns hold.
- *Continuous here means a volatility, a weight, a ratio or a count.* The
  canonical page keeps a rate in the money direction, so the task's earlier
  wording, which listed a rate as continuous, was wrong and is corrected here.
- *The equity twin is fixed with the FX column.* Leaving one family's variance
  strike exact and the other's binary would keep the same quantity typed two
  ways, and the money gate now reports the exact form in either family.
- *The money gate learns the column by its entity.* The FX model names the
  volatility =strike=, which the classifier reads as money, so the gate keys the
  column on the entity that states it and reports it in the continuous direction
  when it is typed exact. A revert of this unit now fails the gate, and the
  codegen test asserts that failure.
