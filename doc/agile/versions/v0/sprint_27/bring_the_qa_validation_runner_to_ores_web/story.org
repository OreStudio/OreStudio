* The arc

ores.web gains a module for development and testing. It is a regular module, like
the others, and it does not depend on the developer surface. It joins development
and testing in one place. It will replace =ores.org-js= and =ores.dsh_kanban=, in
story 2. This story is the first step.

| Story | What it adds |
|-------+--------------|
| 1. Test scenarios (this story) | A regular module in ores.web. A Tests tab lists scenarios waiting and scenarios done. The runner opens one: its steps, its story and its task, a PASS or FAIL and a note on each step, and a save that writes the org file. |
| 2. Browse the agile tree | Kanban for the sprint, stories, tasks, the backlog buckets and any doc by link. It reaches parity with =ores.dsh_kanban= and =ores.org-js=, then both go. |
| 3. The test queue as notifications | A scenario waiting for a tester raises an inbox notification. The bell shows it. A tester role and an assignment arrive here. |

* Decisions

- The module is a regular module. It does not use =developerTools=. A trader may run test scenarios without developer tools. How a development mode works, and whether the module runs in production, are open.
- ores.web does not call compass and cannot rely on it. Compass creates scenario docs from its test_scenario template, and ores.web parses those docs and writes results into them. The format the template creates is the contract. The BFF holds a scenario store behind an interface. The first cut is file backed and reads and writes the docs in the work tree the BFF runs in, so a database store can replace it. The compass journal stamp the Qt tool wrote is dropped, because git keeps the history.
- Until the production question is settled, the module reads the work tree the BFF runs in. It never merges work trees, as the =ores.dsh_kanban= contract says.
- The browser cannot capture the screen, so a step takes a pasted or dropped image. The BFF saves it next to the scenario doc.
- =ores.org-js= leaves the public website. The new module needs a running BFF and does not replace the public static view, and there is no static export. Story 2 removes the project and its publishing: the copy into the site in =ores-build-site.el=, the exclude patterns in =ores-build-site.el=, =ores-sync-org-roam.el=, =ores-check-org-links.el= and =compass.py=, and the memory, tag and modeling pages that name it. Story 2 also checks that no page on the site links to the old agile view.
- The runner uses layout B, one step at a time, accepted on 2026-10-10. A Pass moves on and a Fail stays on the step. The queue carries no heading, because the Tests tab names it. The prototype is under =doc/prototypes/testing/=.
- One shared package parses and renders org text. The BFF reads and writes scenario docs with it and the browser renders step text with it. The port from =ores.org-js= is the first step of retiring that project.

* Open questions

- Who may use the module? The first cut allows any signed-in user. A permission and a tester role come with story 3.
- Does the module run in production? A deployed BFF has no work tree, so it has no org files to read or write. The answer decides where scenarios and their results live. Settle it before the module leaves development.
- How does a development mode work? It is open. The module does not assume one.

* Out of scope

- Starting or closing tasks from the browser.
- A tester account, assignment and review. They belong to story 3.
- =ores.dsh_environment=, which this arc does not retire.
- A compass verb to list, show or record scenarios. ores.web does not rely on compass.
