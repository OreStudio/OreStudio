#+title: Transporting a bundle
#+description: How a bundle travels: a content-addressed artefact in object storage with a modelled manifest, a coordinator that reads only the manifest and sends one part reference per owner, a per-owner transaction, sequencing and a sandbox in place of global atomicity, per-part progress and retry, and an as_of instant that makes a stale import detectable.

#+level: cross
#+filetags: :knowledge:architecture:modelling:classification:nats:storage:

#+updated: 2026-10-17

* Summary

A bundle is a set of entities of different kinds that must arrive
together because a genuine cross-type invariant holds at one instant: an
environment export, an archive, a portfolio-wide conversion. The test is
one sentence, completed without naming a file, a screen, a workflow step
or a boundary format: "one member may not be written without the others
because ___ must hold at one instant". If the blank needs a file, a
screen, a step or a format, the set is an artefact's contents or a
display concern, not a data type. If one owner writes every member, the
set is a *family*, not a bundle.

A bundle is carried by three artefacts. The *manifest* is a generated,
modelled operation type naming every part. A *part* is one owner's rows
of one kind, encoded as a msgpack stream. The *bundle archive* is a
content-addressed, zstd-compressed ZIP that holds one entry per (owner,
kind) and embeds the manifest. The bytes live in object storage. The
manifest and the part references are kilobytes; the rows are never on
the wire.

A coordinator reads only the manifest and dispatches one message per
owner. Each message carries the archive URI and that owner's part
records, never the data. Each owner fetches only its own entries,
verifies their checksums, streams and validates the rows, and applies
them atomically in its own =unit_of_work=. Atomicity is per owner by
construction; global atomicity across owners does not exist on this
platform and must not be promised. Consistency comes from sequencing, a
stated =as_of= instant, and a sandbox for examine-before-live. Progress
and retry are per part.

* Detail

** What a bundle is, and the test for one

A bundle is a classification, not a file format and not a large message.
It is sanctioned by
[[id:B2D74E96-0353-4A3D-8CE5-3FC3C30D864C][the bundle classification]]
when a cross-type invariant must hold at one instant and several owners
hold the types. The kinds are open: a portfolio may span every
instrument type the system holds, so no closed set of member types can
name the bundle.

The test is the sentence above. Complete it without naming a file, a
screen, a workflow step or a boundary format:

#+begin_quote
One member may not be written without the others because __________
must hold at one instant.
#+end_quote

- If the blank needs a file, a screen, a step or a format to be true,
  the set is an artefact's contents or a display convenience. Split it.
- If the invariant covers only some members, the set is two or more
  classifications. Split it at the invariant.
- If the invariant covers every member and one owner holds them, the
  set is a *family*, not a bundle. One owner that writes the set is a
  family even when the set is large or spans several tables.
- If the invariant covers every member and several owners hold them, it
  is a bundle, and this page is its transport.

A file's contents are never an invariant. A document lists conventions
because the format lists them; that is a fact about ORE XML, not about
conventions. An export that must be converted to a boundary format is a
bundle only when the conversion needs all the members at one instant;
otherwise it is a set of entity or family reads.

The design constraint is the heterogeneity, not the size. Size makes the
transport worth designing; heterogeneity is why the transport cannot
name the types in one message.

** Anatomy: manifest, part, archive

A bundle has exactly three artefacts. Each one has one writer, one place
to live, and a fixed set of readers.

#+ATTR_HTML: :class hug-leading
| Artefact | What it is | Where it lives | Who may read it |
|----------+------------+----------------+-----------------|
| *Manifest* | A generated operation object: the bundle format version, the producer, the =as_of= instant, the target, and one record per part. It is encoded with the platform wire codec, like any other message. | The object =bundles/{bundle_id}/manifest.msgpack=. The same bytes are the first entry of the archive, named =manifest.msgpack=, so the archive describes itself. | The coordinator, the producer, and a boundary converter such as the ORE XML writer. An owner receives its own part records in its message and does not need the whole manifest. |
| *Part* | One owner's rows of one kind, encoded as a msgpack stream of one generated type. It is a logical member of the archive, not a separate object. | An entry in =bundle.zip.zst= or in the tar container, selected by its entry name or by its byte range. | Its owner, and only its owner, during an apply. A converter may read every part during an export. |
| *Bundle archive* | A content-addressed ZIP whose entries are zstd-compressed, with one entry per (owner, kind) and the manifest embedded. It is the only object that holds rows. | The object =bundles/{bundle_id}/bundle.zip.zst=, or =bundle.tar.zst= when the container is a tar. | An owner reads one entry. A converter reads every entry. The coordinator does not open it. |

The archive is assembled from staging objects written by the owners.
Each owner encodes its own part, compresses that entry with zstd, writes
the compressed entry to a staging object, and returns a part record with
the checksum and both sizes. The producer writes the manifest, then asks
object storage to copy each staging entry into the archive under its
entry name, at ZIP method 93, without recompressing it, and to add the
manifest as the =manifest.msgpack= entry. It never decodes an entry. The
producer deletes the staging objects once the archive's part checksums
have been verified. No component ever encodes or compresses another
owner's rows.

The =bundle_id= is SHA-256 over the canonical manifest bytes with every
=part.uri= set to the empty string, encoded by the same codec in
declaration order. The URI is the only field blanked, because it is
derived from the id. The digest therefore covers =as_of=, the target, the
producer, every part checksum and the compressed layout. A re-encoding
changes the id and therefore the key; the part checksums do not change,
so semantic identity survives at the part level. A key is never reused
for different semantic content.

** Why nothing bulk is on the wire

The manifest and the part references are kilobytes. The data is in
object storage. Efficiency comes from that structure, not from the
encoding: encoding a bundle into a message would still move the same
bytes onto the bus, and would add a decode step before any owner could
start.

The reason a bundle does not travel as a message is validation,
routing, per-part retry and the prohibition on an encoded value in a
message field — not size.

- *Validation.* A message is validated before it is accepted. A bundle's
  rows cannot be validated until they are decoded against the owner's
  model, which is the owner's job at its own boundary.
- *Routing.* One message has one subject and one handler. A bundle has
  one part per owner, and the coordinator must dispatch each part to the
  owner that may write it.
- *Per-part retry.* A failed row must cost one part, not a whole
  bundle. A message that carries the archive forces a re-send of every
  part to retry one.
- *The encoded-value rule.* A message field that holds an encoded value
  has no static type at either end; see
  [[id:C951B5F1-B51C-4274-BA4D-6297AD46A4FB][Polymorphic payloads over NATS]].

A message also has a practical bound, and a bundle does not. That is a
limit on the message, not the reason for the design.

** The manifest

The manifest is a *generated, modelled operation type*. It is declared
in =ores.codegen.operation=, generated with a schema and a codec, and
encoded with the platform wire codec like any other message. It is never
free-form JSON, never a =std::string= field holding JSON, and never
inferred from the payload or from the archive. It is versioned, so a
reader refuses a layout it does not know instead of guessing.

The target is not decoration. An apply bundle with an empty
=target.sandbox= is refused by the coordinator. A bundle aimed at a
sandbox applies inside that sandbox's isolation; the anchor decides who
may open the sandbox and who may then see the result, per
[[id:4AB0BC63-D73A-4FC3-B9AF-16C1BB90653F][Sandbox]].

=parts= is grouped by owner: every part of one owner is contiguous, and
the owners appear in dependency order. The grouping is what lets one
message per owner preserve the global application order. A manifest that
interleaves two owners is refused, because no single message per owner
could deliver the interleaving.

=parts= is O(number of parts), never O(number of rows). A part record
holds a =row_count=, not the rows. That bound is what makes the
manifest validatable before any bytes move: its size is set by the
number of owners and kinds, not by the size of the portfolio, so a
portfolio of a hundred million rows still has a manifest of kilobytes.
A manifest that grew with rows would be the message the bundle exists to
avoid, and the coordinator would have to read the data to validate its
own routing table.

** The container and the encoding

The archive is a ZIP with one zstd-compressed entry per (owner, kind),
named ={owner}/{kind}=, using ZIP compression method 93, plus the
embedded =manifest.msgpack= entry. The ZIP central directory is the
index: it gives every entry's name, compression method, compressed size
and offset. The archive is content-addressed: a key is never reused for a
different semantic content. A put replaces the whole object; a different
compression is a new =bundle_id=. A =tar_zstd= container is allowed only
when it carries a seekable zstd frame index that gives each entry's byte
range; a plain =tar.zst= has no index, cannot give random access, and is
refused.

*Random access is the decisive point.* A container with an index gives
random access to a single part. An owner seeks to its entry, reads that
entry and nothing else. A single large msgpack document cannot do this,
because a msgpack array has no index: to reach the owner's part, a reader
must decode every row of every earlier part. That would force one owner
to read and parse bytes another owner produced, which is exactly what
[[id:D5F77B10-D498-4B56-ADF7-7E5CEFA44FA0][Database per Service]]
forbids. The index is therefore a boundary control, not a performance
detail.

The row encoding has four rules:

1. *One entry, one type, one stream.* An entry is a stream of msgpack
   maps, one map per row, and every map is the owner's generated type
   for that kind. The entry does not hold one array of all rows.
2. *Named fields, never positional arrays.* A row is a map with string
   keys. A later field addition adds a key and does not shift an
   existing value, so an archived bundle still decodes after the type
   gains a field. A positional array binds meaning to position; adding
   a field in the middle silently reinterprets every archived row.
3. *Row-by-row streaming decode with bounded memory.* The owner
   decompresses the entry and decodes one map at a time, validates it
   and writes it inside its transaction. Memory is the size of one row
   plus the transaction state, not the size of the bundle. This is what
   makes a portfolio spanning every instrument type tractable: the
   number of kinds changes the number of parts, not the memory an owner
   needs to apply one of them.
4. *The part format version is independent of the bundle format
   version.* =part.format_version= gates the row encoding;
   =bundle_format_version= gates only the manifest layout and the
   container rules. A version 1 bundle may contain a version 2 part, and
   the owner selects the decoder from the part record. A new row field
   or a new part encoding does not force a new manifest layout.

** Checksums and compression

Every part is checksummed *uncompressed*: SHA-256 over the concatenated
msgpack maps exactly as the owner will decode them. The checksum is
therefore a statement about the data, not about the compressor. A later
zstd version, a different compression level or a re-encoding of the
archive leaves the checksum unchanged, so the part's semantic identity
survives a compressor upgrade. The compressed size is recorded separately
in =part.compressed_size=; it describes the object, not the data. A
re-encoding produces a new =bundle_id=, because the compressed layout is
part of the manifest, and the recomputed checksum still matches.

The owner decompresses the entry, hashes the uncompressed stream, and
compares the digest with the manifest before it applies the first row.
Verification is a first pass over the entry and decoding is a second
pass, so memory stays bounded and no row is applied before the digest
matches. A mismatch is a failure of the part, never a warning.

Compress the archive, not the messages. The wire codec already gzips a
message payload above 4096 bytes, so compressing a manifest or a
part-reference message again is compressing compressed data. Do not wrap
the archive in gzip either: its entries are already zstd-compressed.
Compression belongs to the object-storage layer, where the archive and
its entries live.

** The coordinator

The coordinator is the apply operation's front end. It reads only the
manifest. It validates the version, the target, the required fields,
that every part names a known owner, that every (owner, kind) pair is
unique, and that the part order is the declared sequence. It may HEAD
the archive object to confirm that it exists; it does not GET, decompress
or decode a part, and it does not compute a part checksum. That check
belongs to the owner, which reads the bytes anyway.

The coordinator must never parse another owner's data, or database per
service is broken. It has no schema for another service's rows, so any
parse it performs is a second model that can only drift. The same rule
is recorded in
[[id:8866D24E-D95B-43C6-A65B-546807E049DD][No service reads or writes
another component's tables]] and in
[[id:D5F77B10-D498-4B56-ADF7-7E5CEFA44FA0][Database per Service]].

It dispatches one message per owner, carrying the bundle id, the
correlation id, the archive URI, the manifest's =as_of= and =target=,
and that owner's part records. A reference, never the data. When an
owner holds several parts, the one message carries all of that owner's
records; the message is still O(parts this owner owns), and the owner
applies them in manifest order and reports each part separately. No
message carries rows, a document or an archive.

The part message is a request with a deadline, per
[[id:49F0A1B2-C3D4-4E5F-8A71-8293A4B5C6D7][Bounded Request]]. The
reply names the part and reports applied, rejected or failed, with the
reason and the row count.

** The owner

The owner's step is the only step that writes rows, and it writes only
its own:

1. Fetch only its part, by entry name or byte range, from the archive
   the message names. It does not fetch the whole archive.
2. Decompress the entry and verify the SHA-256 of the uncompressed
   stream against =part.checksum=.
3. Look up the idempotency key (bundle id, owner, kind, checksum). If
   this part already committed, reply applied with its recorded counts
   and stop.
4. Compare =as_of= with the owner's heads. A stale part is refused, as
   *Progress, retry, and staleness* states.
5. Decode the stream with the codec =part.format_version= names, one
   row at a time, and validate each row against the owner's own model:
   required fields, keys, and references the owner holds.
6. Write each validated row through the generated repository for its
   kind, inside one =unit_of_work=, in manifest order when the owner
   holds several parts. Never write a kind's table with a hand-written
   statement in a part handler; see
   [[id:5724BDE2-7FA4-4667-9129-2D9DD7783AB2][Entity-table writes go
   through the repositories]].
7. Commit only after the last row, and only if the decoded count equals
   =part.row_count=. A row that fails validation, a count that differs
   and any write error roll back the whole part. The part is all or
   nothing.
8. Do not read between the writes of the unit of work. In unpatched
   sqlgen a read commits the transaction, so the rule that keeps the
   part atomic is the one in
   [[id:9562C34E-5790-422D-8E31-774691995860][A read inside a unit of
   work commits it]].
9. Stamp the session's tenant and party, never a value from the payload.
10. Reply with the counts and, on failure, the reason.

The transaction is the owner's, so the part is the unit of atomicity. A
failure halfway rolls back that part alone. No other owner sees a
partial write, and no other owner is asked to compensate.

** Atomicity and consistency

- *Global atomicity across owners is not available.* Two services own
  two databases, and no transaction spans both. A two-phase commit would
  couple every owner's availability to the coordinator's, which the
  component boundaries forbid. Do not promise global atomicity to a
  caller, and do not describe a bundle as all-or-nothing across owners.
- *Per-owner atomicity is the guarantee.* Each part is all or nothing,
  and the manifest names exactly which parts exist. A bundle that is
  complete when every part reports applied is a bundle whose parts all
  resolve at the same instant.
- *A bundle that needs global rollback is a modelling error.* If the
  invariant truly needs every owner to commit together, the data belongs
  under one owner or the operation is not a bundle. Split the invariant
  until each part holds locally, or use the sandbox below.
- *Consistency comes from sequencing.* The order in =parts= is the order
  of application, and a part starts only after its predecessor's reply
  where the invariant has a direction. An environment export imports
  reference data before the configuration that names it, and trades
  before the structures that group them. A failed part blocks only its
  successors, which stay pending and are not dispatched; independent
  parts continue. Where no part constrains another, they apply
  independently, and =as_of= is what makes the set coherent rather than
  the sequence.
- *The sandbox is the compensating control.* An import applies into a
  sandbox, so a wrong part is discarded with the whole sandbox rather
  than repaired row by row in live data. Promotion from the sandbox to
  live data is a separate, smaller operation with its own review; it is
  not a retry of the import. See
  [[id:4AB0BC63-D73A-4FC3-B9AF-16C1BB90653F][Sandbox]].

** Progress, retry, and staleness

Progress and retry are per part, never per archive:

- *Progress.* The coordinator records each part as =pending=,
  =dispatched=, =applied=, =rejected=, =failed= or =timed_out=, with its
  row count and reason. The bundle's progress is the set of its parts,
  not a percentage of a blob.
- *Retry.* A retry re-sends the part reference. The archive's content is
  immutable, so the retry reads the same uncompressed bytes. The apply is
  idempotent
  on the key (bundle id, owner, kind, checksum): the owner records that
  key in its own part-apply ledger in the same transaction as the rows,
  and a second delivery of the same part finds the key and replies
  applied without writing again. The coordinator does not re-upload the
  archive and does not restart the whole bundle to fix one part.
- *Rejection.* A rejected part is a finding about the data, not a
  transport failure. It is reported with the row or key that failed, and
  the other parts are not rolled back.
- *Restart.* Restarting the coordinator re-offers the outstanding parts
  only.

=as_of= makes a stale bundle detectable rather than last-writer-wins.
It is the bitemporal instant the bundle is a view of, per
[[id:4AAD3581-CFA7-4B44-A2DD-0236784E939F][Time and Timestamps]]. A
part is *stale* when the owner's heads have moved since that instant:
any row the part would write has a version whose transaction time is
later than =as_of=, or a key the part references in this owner's
database was deleted or replaced after =as_of=. A part whose =as_of= is
later than or equal to every relevant change is not stale, and it
applies.

The owner *refuses* a stale part. It does not rebase it. A rebase is an
explicit new export at a newer =as_of=, which produces a new manifest and
a new =bundle_id=; the producer mints it, and no owner edits the
manifest or silently applies an older part against newer rows.

Refusal is the chosen behaviour for three reasons. A silent rebase would
make each part a different instant, which destroys the one property the
bundle exists to provide. The archived bundle is the evidence of what was
imported and when; a rebase that changed its meaning would destroy that
evidence. And a refusal is detectable: the user sees the stale part and
can ask for a fresh bundle, while a rebase reports success and leaves the
mixture invisible.

** Worked example: a portfolio exported for ORE XML

A portfolio spans currencies, calendars, conventions, curves, trades and
every instrument type the book holds. The export must give the ORE XML
converter one instant, or the document mixes two books.

*The parts.* One part per (owner, kind), in application order:

- =refdata/currency=, =refdata/calendar=, =refdata/day_count= and
  =refdata/convention=;
- =marketdata/curve= and =marketdata/vol_surface=;
- =trading/portfolio=, =trading/book=, =trading/trade= and
  =trading/instrument/*=, one part per instrument kind.

This is exactly the case a closed message type cannot carry: the last
group gains a member whenever the book gains an instrument kind.

*The manifest in outline.*

#+begin_example
bundle_format_version  1
container              zip_zstd
producer               {trading-export, 1.0.0, production}
as_of                  2026-10-17T09:00:00.000000Z
target                 {sandbox: empty (export only),
                        anchor: desk-42, party: portfolio-owner}
parts                  refdata/*, marketdata/*, trading/*
                       one part record per (owner, kind)
#+end_example

*The sequence.*

1. The converter fixes =as_of= and asks the export operation for the
   portfolio. No owner reads outside that instant.
2. Each owner reads its rows in one transaction, encodes and
   zstd-compresses its entry, writes a staging object, and returns a
   part record with the checksum, row count and both sizes.
3. The producer writes the manifest, then asks storage to assemble the
   staging entries into one archive and to add the manifest entry. It
   verifies every part checksum.
4. The converter reads the manifest, then streams each entry into the
   ORE XML writer. It writes to a temporary file and renames it only
   after every part has been read and checked.

*The atomicity actually obtained.* There is no global transaction. Each
owner's part is one consistent read at =as_of=, and the conversion is
all or nothing at its own boundary: if any part is missing or fails its
checksum, the converter writes no ORE XML at all. A failure does not
roll back a read, because there is nothing to roll back; it withholds
the output. That is consistency by the instant plus an atomic output
file, not distributed atomicity.

** Worked example: an environment export imported into development

A developer needs a production defect reproduced from one snapshot of
the environment: identity, reference data, market data and trades
together.

*The parts.* =iam/tenant= and =iam/party=; =refdata/currency=,
=refdata/calendar= and =refdata/convention=; =marketdata/curve=;
=trading/book=, =trading/portfolio=, =trading/trade= and
=trading/instrument/*=. Owners: =ores.iam=, =ores.refdata=,
=ores.marketdata= and =ores.trading=.

*The manifest in outline.*

#+begin_example
bundle_format_version  1
container              zip_zstd
producer               {environment-export, 1.0.0, production}

*The sequence.*

1. The source environment exports the bundle and stores the archive and
   manifest, as in the previous example.
2. The development coordinator reads the manifest, checks that the
   sandbox is open, that its anchor matches =target.anchor=, and that
   every part names a known owner.
3. It sends one message per owner in =parts= order: =ores.iam= first,
   then =ores.refdata=, then =ores.marketdata=, then =ores.trading=.
4. Each owner fetches only its entries, verifies the checksums, streams
   the rows, validates them, and applies them in one =unit_of_work= per
   part.
5. A person examines the sandbox. Promotion to live data is a separate
   operation with its own review.

*The atomicity actually obtained.* Each part is atomic in its owner's
database. If =trading= rejects a trade after =refdata= applied, the
=refdata= rows stay in the sandbox and the =trading= part applied
nothing; the sandbox is then discarded as a whole, and no official row
was touched. The bundle does not provide global rollback, and the
sandbox is what makes that limit safe.

** What a bundle must not become

- *An opaque archive inside a message field.* That is the artefact
  anti-pattern in
  [[id:B2D74E96-0353-4A3D-8CE5-3FC3C30D864C][Data classifications]]:
  the receiver must unpack before it can validate, no owner can be
  routed to, and one failed row costs the whole archive. It also breaks
  the encoded-value rule in
  [[id:C951B5F1-B51C-4274-BA4D-6297AD46A4FB][Polymorphic payloads over
  NATS]].
- *A union of unrelated entities presented as one struct.* That is the
  anti-type in
  [[id:B2D74E96-0353-4A3D-8CE5-3FC3C30D864C][Data classifications]]:
  one typed array per kind, named after a file or a screen, with no
  manifest, no owner boundary and no instant.
- *A payload the coordinator parses.* A coordinator that decodes another
  owner's rows is a second model. It is the composite scope the
  classification page refuses, in
  [[id:B2D74E96-0353-4A3D-8CE5-3FC3C30D864C][Data classifications]],
  and it breaks
  [[id:D5F77B10-D498-4B56-ADF7-7E5CEFA44FA0][Database per Service]].
  The manifest is the only thing the coordinator reads.
- *A substitute for a family when one owner suffices.* If one owner
  writes every member and one transaction can hold the invariant, the
  set is a family; use =ores.codegen.family=, not this transport. The
  classification page owns that decision, in
  [[id:B2D74E96-0353-4A3D-8CE5-3FC3C30D864C][Data classifications]],
  and the checklist records it, in
  [[id:56AD6F46-99E0-482E-B7B5-C9FDEC8A7641][the data classification
  checklist]].
