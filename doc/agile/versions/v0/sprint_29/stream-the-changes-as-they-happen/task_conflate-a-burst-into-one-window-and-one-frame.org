* Goal

too slow to read holds one frame per collection rather than one per window.

* Acceptance

- [X] A change opens the window; a quiet system opens none.
- [X] A burst that starts between ticks is one frame, not two.
- [X] A stream that was not read holds one frame for its collection, the newest.
- [X] Two collections a stream missed are still two frames.

* Plan

Two halves of one property, so they change together.

*The window opens on the first change.* The ticker re-arms a fixed interval
whatever happened, so a burst that starts just after a tick is cut in two: the
screen redraws twice for one import. The coalescer calls a hook when its dirty
set goes from empty to non-empty, the ticker arms its own timer from that call,
and a tick that finds nothing to arm does not pump. A long burst is still a
series of windows, because a window is never extended by what arrives inside it;
what changes is that the burst's first window begins with the burst.

The change arrives on the NATS dispatch thread and the timer belongs to the
server's, so the arm is a post: one allocation per change and no timer touched
from two threads.

*The pending frame for a collection is overwritten.* A slow stream queues every
window it missed, and the bytes it holds are for a collection that has moved
again since. The subscription keeps one pending frame per collection and a new
frame for the same collection replaces it, moved to the back so the ids a client
sees stay ascending. That is a small map of collection to frame plus a list for
the order, not a second queue.

The capacity keeps its meaning as "collections pending", and the drop policy
stays drop-oldest: a stream that is behind loses the frame it is least able to
use.

* Notes

- The arm is a post because the change arrives on the publishing thread and the
  timer belongs to the server's. A change recorded before =run= has started finds
  no executor to post to, so the loop's first pass reads =pending()= and arms the
  window itself; the case that records before the loop runs covers that path.
- The loop's idle sleep is one hour and is not a policy: it only bounds how long
  a quiet server stays asleep, because a change expires the timer as it arms.
- The conflation key is tenant, party and collection joined with a separator the
  parts cannot contain. It is built by the hub, so a publisher states the
  collection its frame is about and nothing more, and a stream that hears two
  tenants cannot have one replaced by the other.
- A replay conflates too: a client that missed three frames of one collection is
  given the newest, which is the same answer it would have reached by refetching.
- The capacity still means collections pending, and the drop policy is still
  drop-oldest.

* Result

A burst is one frame per collection however it falls across the clock, because the
window is armed by the burst's first change and nothing inside it extends the
window. A stream that fell behind holds the newest frame for each collection it
missed, with the ids still ascending, so a client that resumed from the last id it
read is never told to go backwards.
