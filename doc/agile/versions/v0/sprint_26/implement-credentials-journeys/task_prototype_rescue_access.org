* Goal

Answer one question with a throwaway prototype: how does a tenant
administrator get one colleague back into the system, or shut the account
down, on one screen?

[[id:A441DA2E-4B74-49B3-97AD-1861647B7D94][Rescue access]] carries one screen.
It holds the account, its security state, the password form and the actions,
because the administrator thinks of them as one decision. The screen starts
from a support call, so the prototype decides how the screen opens, how it
shows the recommended action, and how it states the actions the server cannot
perform.

* Notes

The journey's gaps, from the * What is missing section of
[[id:A441DA2E-4B74-49B3-97AD-1861647B7D94][Rescue access]]. The screen states
each one, and the prototype decides how.

1. *No forgot-password or self-service recovery.* Nothing lets a member who
   cannot sign in start recovery. The only password subjects are
   =iam.v1.accounts.change-password= and =iam.v1.accounts.reset-password=.
2. *No activate or deactivate.* An account has no active flag. The only state
   an administrator can change is =login_info.locked=.
3. *The reset flag cannot be set over NATS.* =password_reset_required= exists,
   =account_operations_service::set_password_reset_required= implements it, and
   the HTTP route uses it. No NATS subject calls it.
4. *Locking does not end sessions.* =iam.v1.accounts.lock= writes the login
   record only, and an open session stays open until it expires.

The three write subjects exist and each needs its own permission:
=iam.v1.accounts.reset-password= needs =iam::accounts:reset_password=,
=iam.v1.accounts.lock= needs =iam::accounts:lock=, and
=iam.v1.accounts.unlock= needs =iam::accounts:unlock=. A tenant administrator
who holds the role has all three.
