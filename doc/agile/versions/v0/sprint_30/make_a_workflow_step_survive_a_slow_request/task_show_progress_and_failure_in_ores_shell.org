* Goal

A person watching a provisioning run in the shell sees a failure that names the
work, the attempts it took and the reason. The progress lines a running step
reports are already printed; this task keeps them and makes the failure read as
a report.

* Acceptance

- A failed step prints its name, its position, the work that failed, the
  attempts it took and the reason.
- A step that retried and then succeeded prints each attempt and its reason.
- The progress lines a running step reports stay printed as they move, as the
  heartbeat work added them.
- The output stays readable when a step reports many progress lines.

* Plan

- The shell already prints a running step's progress, from the heartbeat work
  that merged as PR #4660, and prints a step's own log beside each status
  change. The failure it prints is the step's error text.
- So the missing half is not in the shell: it is that a retry said nothing on
  the step's own record. Carry each attempt into the step's log, which the
  engine answers and the shell prints.
- Keep the shell unchanged, and verify the three lines a person reads: the
  progress line while the step runs, the attempt lines in its log, and the
  failure line naming the work.
- The failure text itself arrives from the retry helper, so its attempts and
  reason are already in the line the shell prints.

* Result

* Result

The shell needed no change. What was missing was on the run's own record, and
that is now carried there: each transient failure writes one line into the
step's log, and the engine answers that log to every client.

A person watching a run now reads three things from the same source:

#+begin_src text
  [13/15] publish_party_surfaces: in_progress
      progress: ACME: surfaces with their quotes 3 10
  [13/15] publish_party_surfaces: completed
      info: ACME: EUR/USD surface calibration: attempt 1 failed (NATS request timed out: no
      reply from 'marketdata.v1.ops.calibrate_fx_vol_surface' within 120000 ms); asking again
      in 300 ms
#+end_src

A step that gives up reads as the report the retry helper composes:

#+begin_src text
  [13/15] publish_party_surfaces: failed -- ACME: EUR/USD surface calibration failed after 3
  attempts: NATS request timed out: no reply from '...' within 120000 ms
#+end_src

The progress line comes from PR #4660 (`progress_line` and the per-step
`last_progress` map in `workflow_run_commands.cpp`). The attempt line comes from
the step's log, which `print_step_log` prints at each status change. The failure
line is the step's error, which the retry helper composed.

The attempt-report case proves the note reaches the caller once per failed
attempt, naming the work and the reason. The remaining link -- that the engine
stores the step's log and the shell prints it -- is already covered by the
engine and shell behaviour, and the end-to-end run is task 7's check.
