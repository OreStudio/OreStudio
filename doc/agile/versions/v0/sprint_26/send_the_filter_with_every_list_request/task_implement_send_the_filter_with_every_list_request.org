* Result

The web client states the filter in every list request it builds by hand.

- *Cause.* PR #2588 gave almost every generated list request an optional
  =filter= member. The server's decoder requires every member, optional or
  not, so a request that leaves it out is refused as =bad_request=. The web
  routes for accounts, login info, sessions, seed profiles, tenant types,
  tenant statuses and badges built their requests from hand-written schemas
  with no filter, and each answered 502. The web server tests stub the server,
  so none of them saw it; the routes were last read live before #2588.
- *Fix.* Each of the seven hand-written list request schemas sends
  =filter: null=, and so does the client's paged party read.
- *Guard.* Each schema now =satisfies= its generated request type, so a member
  the protocol adds fails the typecheck instead of the live read. Removing the
  filter from the tenant types schema fails the typecheck (TS1360).
- *Verified live.* Signed in as the system administrator against the running
  deployment: =/api/accounts=, =/api/login-info=, =/api/sessions=,
  =/api/seed-profiles=, =/api/tenant-types=, =/api/tenant-statuses= and
  =/api/change-reasons= all answer 200; before the fix all but the last
  answered 502. Web tests: 124 BFF, 229 web, 66 wire protocol, all passing.
