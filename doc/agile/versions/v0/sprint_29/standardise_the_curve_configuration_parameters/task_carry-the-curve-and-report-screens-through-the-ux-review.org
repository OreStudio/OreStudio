* Notes

- *The review is running on the live environment.* Findings arrive against
  =http://localhost:21202=, and each is answered on the branch named for this
  task. Nothing is merged and nothing is rebuilt until the owner says so, because
  the screen is being judged while it changes.
- *A leaf's documentation is read once.* The contract gives a curve leaf a =help=
  and a =description= that are the same guide line, so the row's hint and the
  panel printed it twice. The row now states the label, the required mark and the
  value, and the sentence is read in the panel it is collapsed into, as the leaf
  standard states for a leaf that is read and not changed.
- *A closed list shows the values it accepts.* The panel now states
  =Valid values: ...= from the leaf's value set, so a person who reads "the
  allowable values are given in the guide" sees the values rather than a
  sentence sending them elsewhere. The shared panel carries it, so every screen
  of leaves gains it.
- *The report page reads like the other screens.* Its first tab is *Details*, not
  *Definition*, and the card inside it is headed the same way; the latest-run
  card is gone, because a run is read on the *Runs* tab and the health of the
  latest run stays in Details as a field.
- *The configurations are a tab.* Each binding is a card that names the kind, the
  configuration it binds and links to it, and one sentence that says what that
  kind is for (product pricing, engine run settings, today's market, curve
  configuration, conventions, run settings). A kind the screen does not know
  still gets a sentence, so a new kind reads as one of the report's
  configurations rather than as nothing. The sentence belongs on
  =configuration_type= once that row holds one; until then it is in one place,
  =blurbOf=, in the screen that draws the bindings.
- *A configuration is reached from the area, not only from a report.* The
  reporting area gains a *Curve configurations* card, and with it the list
  screen the area needs: the header rows and their definitions, with the party,
  the sections filled and the curve count of each. The card is gated on
  =refdata::curve_configurations:read=, which is now one of the reads the area's
  door asks for. The other kinds still reach the area through their own screens;
  a kind with no list of its own has no card.
- *Two dead translations were removed.* =fr.ts= and =pt.ts= carried
  =reporting.results.oneRowPer.tradeId= and =.tradeType=, which the English
  source catalogue does not have, so the i18n catalogue test failed for every
  branch. Both were unused and are gone.
- *A person could not start a run.* The report page offers *Start* only to a
  person who holds =reporting::report_instances:write=, and only the =ReportRun=
  service role held it, so the button never rendered. =Operations= now holds it:
  starting a run costs compute, so the role that owns operations has it and a
  reader does not. The screen was right and the seed was wrong.
- *A curve configuration's party is not named in the list.* The parties read the
  list would need is a read the screen is not granted, and the session's parties
  are already what scope the rows, so the column is left out rather than drawn
  empty. It returns when the parties read is granted to the screen.
- *The copies of a report are a party-scope defect, not a display one.* The
  owner's account works in four parties, so the list reads the definitions of
  all four (78 of them) with no party on the row and no party selector on the
  screen, and the four copies of =Exposure= look identical. The party filter is
  a query parameter the list already accepts, so the fix is the list's: offer
  the filter, and name the party on a row when the reader is in more than one.
  It is filed here and not fixed in this change.

- *The history of a refdata entity was never served.* The refdata service
  builds its history registry in =core/src/messaging/registrar.cpp=, and 60 of
  the 167 generated =register_<entity>_history_provider= calls were missing from
  it. So =/api/history= answered =No history provider registered for
  entity_type: ores.refdata.curve_configuration=, and the same for every
  convention kind, every curve section and every curve segment. All 167 calls
  are now present. Nothing caught the gap, because the generated registrar
  compiles into the library and the service starts and serves every other
  subject.
- *The composition is now checked.* =check_history_registrar_composition.py=
  fails when a generated registrar of a checked component is not called from
  that component's registrar, and =--fix= wires the missing ones. It joins
  =compass check= as =history-registrars= and runs in its own workflow, as the
  event-registrar check already does. ores.refdata is the only component in the
  checked list.
- *The same gap is in twelve other components.* ores.trading composes 72 of 96,
  ores.analytics 11 of 27, ores.reporting 0 of 28, ores.reference data's siblings
  and the rest less. Each needs its own story; the check's docstring states the
  census so the next person does not measure it again.
- *A convention's record page had no History tab.* The page now draws *Details*
  and *History*, and the tab reads =ores.refdata.convention=, the central entity
  the page edits. The BFF serves that entity type. The tab keeps =?party=,
  because the convention is read under a party and a tab change must not lose
  it; =useRecordTabs= gained the =keep= parameter for it.
- *The check suite recreated the database.* =compass check= runs a =db= step
  that rebuilds the schema, so the tenant was gone when the run finished. The
  Acme script provisioned it again, and the history reads below were taken on
  that fresh database: a curve configuration answers one version, a convention
  of the caller's party answers two, and a convention held by the system party
  stays hidden by row-level security, which is right.
- *The equity underlying permission codes were not seeded at all.*
  =refdata::equity_underlyings:read/write/delete= were checked by the entity's
  handler and absent from =iam_permissions_populate.sql=, so the history
  provider wired here could never have answered. The three rows are added and
  =handler-permissions= is green.

* Result

The curve page's documentation is read once, in the panel it is collapsed into,
and the panel states the values a closed list accepts. The report page draws
Details, Configurations and Runs: its first tab is named as every other screen
names it, the latest-run card is gone, and each configuration it binds is a card
with the sentence that says what its kind is for.

The reporting area gains the *Curve configurations* card and the list screen
behind it, so a person reaches a curve configuration without a report that binds
it. The list route reads the headers and the definitions and answers the party,
the sections filled and the curve count of each.

The BFF suite passes with 1,088 tests, seven of them for the curve configuration
route and its list, and the browser suite with the ten tests of the curve page
among them. The two dead French and Portuguese translations that failed the i18n
catalogue for every branch are removed.

A refdata record's history now answers. The refdata registrar composes every
one of its 167 generated history providers, a check keeps it that way, and the
conventions record page draws the History tab it never had.

Still open in this round: the party scope of the reports list, which is filed
above and is the reports list's change rather than this page's. The other twelve
components whose generated history providers are not composed are their own
story.
