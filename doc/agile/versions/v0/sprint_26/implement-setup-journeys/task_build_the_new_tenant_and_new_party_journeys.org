- *New tenant* runs in the browser, signing in as an administrator, choosing a
  starting point, describing the tenant, following the run and handing over to
  the new tenant's administrator.
- *New party* runs in the browser: find the legal entity, describe the party,
  review, follow the run, and the next steps.
- Both reuse the runtime and the step library the first run uses, and first run
  inlines those same steps.
- A scripted end-to-end run walks the first-run path against the real server on
  a fresh database, in the shape of
  =projects/ores.web/scripts/verify-login.ts=, and is committed as the proof.

* Result

The *New tenant* journey runs at =/tenants/new=, and it is a route rather than
a gate: the installation is already set up, so a signed-in administrator adds a
tenant beside the ones the deployment has. The rail is the same five steps the
first run inlines, from the same library, so the two journeys cannot describe a
tenant differently; what the new journey does not carry is the administrator to
create and the first sign-in, because both already happened.

Two things differ from the first run and both come from who the person is. The
browser does not hold the signed-in administrator's password, so a starting
point that hands that password to the tenant's administrator asks for one
instead -- the form already warns when it has none to hand on -- and the
hand-over is the journey's end: the person either becomes the new tenant's
administrator, which signs out and back in as them, or passes the account on,
which signs out and stops.

The walk in a headless browser is recorded in
=evidence/new_tenant_journey_live.txt= with a screenshot: the five-step rail,
the three starting points read from the server, the form built from the chosen
profile's settings with the shared password field and the deployment's policy,
and the review summary before anything is created. The run itself was not
walked to its end in the browser, and the file says so.

What this task still owes is the *New party* journey and the scripted browser
proof. The party journey is the larger half: the deployment's search over its
legal entities exists, but nothing in the browser reaches
=iam.v1.parties.provision=, and a party that is not one of the deployment's
legal entities has to be described by hand, so it needs a BFF route and a wire
call of its own before its screens can be honest.
