* Goal

A tenant administrator whose starting point forces a password change is told so at first sign-in and sets a password only they know, and the rules the screen shows are the rules the server enforces. The profile's choice reaches the account the provisioner creates, the login answer carries the flag that account holds, and a read returns the policy the validator enforces.

* Acceptance

- The provisioner marks the administrator's account for a password change when the starting point it runs from says so, and the login answer reports that flag.
- A read returns the password policy the server enforces, and the browser reaches it through its own route and wire-client method.
- A first sign-in by an Empty operational tenant's administrator reports that a change is required.
- No client declares the password rules: the policy a client states is the policy the server answered with.

* Plan

Two things land: the forced change reaches the person it is for, and the rules
the screen shows come from the server.

*The flag has to be carried twice.* The account's own record holds the reset
flag — =login_info.password_reset_required= — and the login answer declares the
same field, but the two are never joined: the login path reads the account's
login record to check it is not locked and then drops the flag, and the reply
is built without it. So the service's login answer carries the flag the record
holds, and the handler copies it into both answers it can give, the one-party
answer and the party-selection answer. One read of the record, one answer.

*The flag has to be set in the first place.* The starting point declares
whether it forces a change — the seed profile carries =force_password_change= —
and the provisioner never reads it, so the administrator of a profile that
forces a change signs in with nothing forcing anything. The tenant provisioner
takes the profile's choice and marks the account it creates, at the point the
account and its login record are made, so the first sign-in of an *Empty
operational* tenant is answered with the flag set.

*The policy is the validator's.* The rules the server enforces live in the
validator: a minimum length, an uppercase letter, a lowercase letter, a digit
and a symbol from its own set. A client that states those rules today copies
them, and a copy drifts. So the validator states its rules as data and enforces
the same data it states, and a read answers with it. The read needs no session,
because the screen that shows the rules is the sign-in and first-run screen and
neither has one yet; the IAM service serves it beside the bootstrap status,
which is the other subject a caller reaches before it has a session.

*Reach.* The browser reaches the read through its own route and wire-client
method, and the sign-in and sign-up screens of plan steps 10 and 11 build their
field from it. No rule is declared in the client, so a rule the server changes
reaches the screen without a client change.

*What this task leaves.* The starting point's other hand-over choice — copying
the caller's password rather than taking a new one — is not part of this unit:
the plan step names the forced change and the policy read, and the profile's
=inherits_admin_password= stays unread, which the notes record.

* Result

The forced change reaches the person it is for and the rules on screen are the
server's. The evidence beside this task records both: the policy read through
the browser's own route, before anybody had signed in, answered the validator's
record; and the Operational card's administrator was answered with
=passwordResetRequired: true= at first sign-in, because the starting point's
choice now reaches the account the provisioner creates.

The join was missing twice. The login path read the account's login record to
check it was not locked and dropped the flag, and the profile's
=force_password_change= was never read, so nothing set the flag either. Both
are closed, and the answer a person receives is the record's own value.

The rules are stated once. The validator carries them as a record and enforces
that record, so a client that reads them states what the server applies; the
read needs no session, because the screen that shows them is the one a person
signs in on.

What this task leaves: the starting point's other hand-over choice, copying the
caller's password rather than taking a new one, stays unread.
