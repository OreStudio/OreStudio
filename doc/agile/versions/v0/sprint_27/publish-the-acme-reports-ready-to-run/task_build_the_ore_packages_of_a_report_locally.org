* Goal

A developer can take a report and get, on disk, every package the compute grid would receive for it, laid out as the ORE samples are (Input and the data files), so the package can be inspected and run in ORE locally. Two commands do this. One builds the packages fresh from a report definition by running a temporary report instance of a new package kind: it runs the real gather and prepare steps, with the definition's own run grant, and stops before the compute grid. The other fetches the packages a past report instance stored.

* Acceptance

- A report instance has a kind, held in a lookup table: production, which prepares, computes and records, and package, which prepares and stops. Every existing instance is production.
- A package instance runs the real gather, package and finalise steps and no compute step, so the packages are the ones the grid would receive. No gather step has a flag that changes its behaviour for a package instance.
- A package instance neither blocks nor waits behind a production instance of the same definition. The scheduler creates production instances only, and a default listing shows production instances.
- The command ore build-packages, given a report definition id and an output folder, runs a package instance, waits for it, then downloads every tarball the instance stored and unpacks each into its own folder under the output folder. It reports the instance it made.
- The command ore fetch-packages, given a report instance id and an output folder, downloads and unpacks every package a past instance stored, and says so clearly when the instance stored none.
- A package built for an ACME report has Input/ore.xml and the documents, the portfolio and the market data where the run document names them, and validates against the ORE schema.
- A command removes package instances and their stored packages older than a given age.

* Plan

1. Model the kind of a report instance. Add a lookup =report_instance_kind= with the codes =production= and =package=, and a column on =report_instance= that refers to it and defaults to =production=. Generate the layers from the models and seed the lookup.
2. Make the kind count where instances are counted. The in-flight check that the concurrency policy uses ignores =package= instances. The scheduler creates =production= instances only. The default instance listing shows =production= instances.
3. Let a trigger name the kind. =trigger_report_instance_request= gains the kind, with =production= as its default, and the response returns the instance it created.
4. Add the package chain to the report execution workflow. A =package= instance gets the steps gather trades, gather market data, assemble bundle, prepare ORE package and finalise. The steps are the real ones and none of them has a flag for a package instance.
5. Add =ore build-packages=. It triggers a =package= instance of a definition, waits until the instance reaches a terminal state, lists the stored packages by the instance's storage prefix, downloads each and unpacks each into its own folder under the output folder. A failed instance reports its output message.
6. Add =ore fetch-packages=. It does the listing, download and unpacking for any instance, and says so when the instance stored none.
7. Add a clean-up command for =package= instances and their stored packages older than a given age.
8. Prove it on the ACME reports: build the packages for each definition, check the layout, and validate =ore.xml= against the ORE schema.

* Notes

The model has no notion of the kind of a run. The closest concepts are at the wrong level. =pre_processing= and =post_processing= are the standing recipe of a definition. =trigger_run_id= says which scheduler trigger created an instance. The FSM states =cancelled= and =skipped= mark runs that never executed. The concurrency policy counts every instance of a definition that has not reached a terminal state, so a temporary instance would block a real run.

The decision is to model the kind on the instance. A package build is a real =report_instance= row with the kind =package=. The gather steps already use the instance id for the run token scope, the storage keys, the state changes and the failure marking, so a =package= instance reuses all of that unchanged and the steps need no flag. The definition's own run grant gives the package the data the real run would see.

A temporary instance is made from a definition, because its data is gathered fresh. It cannot rebuild the exact packages of a past instance, because the market data and the trades have changed since. The tarballs a past instance stored are in storage, and =ore fetch-packages= downloads those.

The packages of one instance are a list, because the submit step takes a list of tarball URIs. Today the prepare step stores one. The commands list the stored objects by prefix, so they take several when a later task splits a run into batches.
