* Acceptance

- The server finds the built bundle from a manifest rather than by joining paths, so
  a request cannot escape the root.
- A hashed asset is answered =immutable=; =index.html= is answered =no-cache=.
- A screen route that is not a file is answered with the bundle's =index.html=.
- The prebuilt brotli file is served when the client offers it.
- The files are streamed from a descriptor, not read whole.

* Plan

1. Read the manifest the build writes, and hold a table from request path to file.
2. Answer a miss that is not an asset with =index.html=, and a miss that names an
   asset with 404 so a broken page is visible.
3. Serve each file through the body source, with the cache headers by name.
4. Test the headers, the fallback, a traversal attempt and the compression choice.

* Notes

- The manifest is read from the directory the build wrote rather than from a file
  the build emits. The build does not write one, and a directory read at start-up
  gives the same property: a request is resolved by lookup and no path is joined to
  the root at request time.
- A path under =api/= is never answered with the shell, including bare =api=, so a
  misspelled endpoint is a 404 and not HTML for a caller expecting JSON.
- Nothing generates the brotli copies yet. The server serves =.br= when it is there
  and =Vary: Accept-Encoding= when the copy exists, so the build only has to start
  writing them.
- The bundle is served from the last route registered, so it answers what nothing
  else claimed. The server logs and skips it when the configured directory is not
  there, rather than serving an empty application.
