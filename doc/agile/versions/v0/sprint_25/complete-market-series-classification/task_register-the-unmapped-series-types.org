dimension and the default point of every series type move from a

* Acceptance

- The key shape of every ORE series type lives in a table, seeded
  from the corpus and managed like any other catalogue: the qualifier
  depth, the point dimension, and the point to record when a key
  carries none.
- The table holds a row for each of OI_FUTURE, SHAPE_PROFILE,
  BOND_OPTION, RATING, INDEX_CDS_TRANCHE, GENERIC-MD, CPR and FIXING.
- Every distinct key of those types decomposes into a qualifier and a
  point, so its observations share one series.
- =ores.ore.core= receives the shape table. It never reads the database
  itself, so its tests run with no database, no NATS and no pipeline.
- An empty table throws, and the message names the table and says it is
  unseeded. A row that claims a point dimension and also carries a
  default point is rejected, both in the constructor and by a table
  constraint.
- =known_series_types()= answers from the supplied rows, so no list of
  type names is compiled into the reader.
- A test asserts that the classifier's type set and the table's type
  set are equal, so the two cannot drift.
- The corpus census of distinct series is materially lower after the
  change, and the drop is recorded.

* Plan

The mechanism changed after the design discussion. The shape of an ORE
key was to stay a compiled table, with eight rows added. It becomes
managed data instead, and this task records that rescope. The outcome
does not change: the eight types must decompose properly.

** Why the shape becomes data

The shape table says how a key splits. That is ORE's grammar, so it
belongs to =ores.ore=, and nothing in the component prevents it. Every
component that owns an entity model owns a schema, and =ores.ore.core=
already links =ores.database.lib=. A compiled table also cannot serve
the case that matters: when ORE adds a type, or a user brings one of
their own, the answer must be an inserted row, not a rebuild.

** Two tables, two owners

The shape table belongs to =ores.ore=, because it describes the ORE
file format, which ORE defines and we only read. The classification
table belongs to =ores.marketdata=, because it maps a type to refdata
asset class codes, which are our taxonomy. The two facts change for
different reasons. This also means the promise "a user can add their
own types" holds only once the classification table is data too, which
is task 219. Until then a new row imports only if both tables carry it,
and the shape row without a classification row makes the classifier
throw and aborts the file. That pulls 219 into this work.

** The reader takes the table

=series_key_registry= stops being free functions over a static map and
becomes a value built from rows.

#+begin_src cpp
class ORES_ORE_CORE_EXPORT series_key_registry final {
public:
    explicit series_key_registry(std::vector<domain::series_key_shape> shapes);
    decomposed_key decompose(const std::string& key) const;
    bool has_point_dimension(const std::string& series_type) const;
    std::string default_point_for(const std::string& series_type) const;
    std::vector<std::string> known_series_types() const;

private:
    std::unordered_map<std::string, domain::series_key_shape> by_type_;
};
#+end_src

The rows are the generated =domain::series_key_shape= rather than a
second struct of four fields. The design sketched a parallel struct,
because it was not obvious that =ores.ore.core= may see the entity
type. It may: =ores.ore.core= already links =ores.ore.api.lib=, and
its generated repositories include that header to return rows. A
second struct would be a second artefact for the same table-shaped
data, which the data oriented design note rules out: the wire shape
is a codegen projection of the entity, not another type. So the
repository's rows feed the constructor with no mapping layer between
them.

=reconstruct_key= stays free. It joins strings and needs no table, so
the serializer does not change.

The constructor throws when the rows are empty, and the message names
the table. It also rejects a row that claims a point dimension and
carries a default point. A table constraint carries the same two
checks, so an illegal state cannot be stored either.

A third check was considered and declined. =qualifier_depth= is an
=integer= in the table, so a negative depth can be stored. It needs no
check, because a negative depth makes the key shorter than its type
expects, and that branch already folds the whole remainder into the
qualifier: the row degrades a key exactly as an uncatalogued type
does, and the key still reconstructs verbatim. Throwing in the
constructor would abort an import over a row the table accepts, which
is the failure this task exists to remove.

** An unknown type still folds

An empty table throws. A type with no row is a different case. Its key
folds into the qualifier and loses nothing, because the key still
reconstructs verbatim. A file carrying a type nobody catalogued must
not take an import down, because ORE adds types over time and this
corpus already carries two that ORE's own catalogue does not document.
The alarm lives in the corpus test instead, which fails whenever the
corpus carries a type with no row.

** How the rows arrive

A repository reads the table once at the start of each import, builds
the registry, and passes it down by const reference. That is one read
per batch rather than per key, and no process-wide cache to invalidate
when a row changes. The component already injects this way, since
=import_service= takes a =context=.

** The call sites are shallow

=decompose_key= has one production caller, =market_data_parser.cpp=.
=default_point_for= has two, in =import_service.cpp= and
=feed_ingest_loop.cpp=. =has_point_dimension= is used only by tests
today. The generated =market_observation.hpp= mentions
=default_point_for= in a comment and does not call it.

** The file name decides which reader a file feeds

The first cut of this test offered every file to the market data reader
and handed each rejection to the fixing reader. That is not what an
import does, and it inflated the fixing census fourteen-fold.

=import_service= takes market data and fixings as two separately named
payloads, =req.market_data_content= and =req.fixings_content=, and
never asks either reader to guess a file's kind. The corpus names its
fixing payloads =fixings*=, so the walk does the same.

Without that rule the fixing reader took 68 files for 2,246 keys, where
the corpus holds 54 files and 158. The excess was not fixing data. The
corpus's exposure reports are =date,EPE,ENE= tables, and
=parse_fixings= checks the date and stores the two fields after it
without reading them, so

#+begin_src
2016-02-05,99230.3007,0.0000
#+end_src

entered the census as a series whose qualifier is =99230.3007=. The six
=xvacg-exposure.csv= files alone supplied 2,033 of the 2,246 keys.
Naming the payload as the corpus and the import both name it is what
keeps them out. A walk that counts them is not measuring fixings, and
its floors would have been set from the inflated figure.

** Unit 5a evidence

The classification table is data. Its rows live in
=ores_marketdata_series_classification_rules_tbl=, one per series type,
and the compiled map it replaces no longer sits on the path an import
takes.

=ores.marketdata.series_classification_rule= is generated from
=projects/ores.marketdata/modeling/ores.marketdata.series_classification_rule.org=,
with the facets the other marketdata catalogues carry: the domain type,
the entity, the mapper, the repository, the service, the history
provider registrar, the event registrar, the presentation field mapper,
the JSON and table IO, the protocol, the generator and the eventing
integration test.

The natural key is =(tenant_id, series_type, metric)=. Two codegen
templates gained what this model needs. The eventing test template now
matches a notification by every key part rather than by the id alone,
because the notify trigger emits one =entity_id= per key column: a test
that matched on the type alone would accept a notification for another
metric of the same type. The schema template now honours
=:skip_empty_check:=, the per-column opt-out from the =<> ''= check,
which =metric= needs because the empty metric is a value this table
gives a meaning to. Both changes are guarded, and the new model is the
only model in the tree that reaches either one, so no generated file
that already existed changes.

The table carries what its siblings carry: the temporal primary key
=(tenant_id, series_type, metric, valid_from, valid_to)=, the exclusion
constraint over the validity range, the version and latest-row indexes,
the insert trigger that manages the version and validates
=asset_class_code= when it is present together with
=series_subclass_code= and =change_reason_code=, the notify trigger, and
the delete rule that closes the active row instead of removing it.

Two columns hold what one class column could not. =asset_class_source=
is =literal= for forty-two of the forty-three rows, and those rows read
their class from =asset_class_code=. The forty-third is =CORRELATION=:
its source is =correlation_operands=, its class column is null, and its
subclass is =correlation=, because a pairwise correlation belongs to the
two classes its operands name and to neither alone. The gating between
the two columns is a table check, so the database refuses a
=correlation_operands= row that names a class and a =literal= row that
names none.

=GENERIC-MD= is the one row keyed by a metric as well as a type. Its
metric is =EQUITY_OPTION=, because the wrapper's metric slot names the
instrument inside it, so this row is the =EQUITY_OPTION= rule reached
by the type route and it takes the class and the subclass that route
gives. Every other row leaves the metric empty and covers every metric
of its type.

The seed is =marketdata_series_classification_rules_populate.sql=. It
holds the forty-three rows grouped by family, each with a description
that says why that type takes its class and its subclass and, where the
choice can be disputed, the corpus evidence behind it. It is idempotent
through =on conflict ... do nothing= against the active row.

The seed reproduces the compiled table it replaces. A row-by-row compare
of the two reports the same forty-two types with the same class and the
same subclass on every one, including the codes that name a catalogue
row outside the fifteen the generator's array carries, such as
=transition_probability= for =RATING= and =prepayment= for =CPR=. So
Unit 5b can read the rows without changing any answer the classifier
gives today, which is what makes the swap verifiable rather than merely
plausible.

A test tenant is provisioned fresh on every run, so
=ores_iam_provision_tenant_fn= copies the classification rows into it,
as it already did for the series key shapes. Without the copy the
tenant's table is empty, and the reader that Unit 5b builds rejects an

** Unit 5b and 5c evidence

The classifier is a value built from rows. =series_classifier= takes
the rule rows in its constructor and holds them by type and then by
metric, and =import_service= reads the table and passes it in. The
compiled map is gone: =classify=, =try_classify= and
=known_series_types= answer from the rows alone, so a type the table
does not carry fails rather than resolving from a list in the binary.
The header says so, and a case in the classifier suite proves it by
asking for a type the fixture does not carry.

The constructor rejects the four states a reader must never accept: an
empty row set, which names the table and says it is unseeded; a row
whose =asset_class_source= is neither =literal= nor
=correlation_operands=; a =literal= row that carries no class code; and
a =correlation_operands= row that also names one, because a reader
would not know which of the two to record. The first is why a fresh
tenant must receive the copy, and the other three are why a bad row
fails the import before any series is written rather than halfway
through it.

The empty metric is the wildcard the column documents. A key whose
metric has no row of its own takes its type's row for the empty metric,
which is the =GENERIC-MD= route, and a row whose type and metric repeat
replaces the earlier one.

=import_service= builds the classifier on the first series that needs
one and keeps it for the request. Both the market data path and the
fixings path create series, so the read belongs to neither branch, and
a request that carries neither payload never pays for it. The read
happens once per request, not once per series.

One piece of the mapping stays compiled, and it is the piece that is
not taxonomy. =operand_asset_class= resolves a correlation operand by
the prefix ORE gives it, =EQ-=, =FX-= and =COMM-=, and by the =-CMS-=
a rates operand carries instead of a prefix. That is a naming rule
about ORE's own keys, which no row of ours can state. Task 235 owns its
documentation.

environment receives. Nine cases cover the value directly, from a

fallback, the metric preference and the empty-metric fallback, the

* Result

The ORE series vocabulary is data. Both facts that describe a key, how
it splits into a series and a point and what it classifies as, are now
rows a user can manage rather than lists compiled into the binary, and
every series type the corpus carries decomposes properly.

The task title names only the smaller half of what shipped. The Plan
records the rescope: the eight missing types were to be added to a
compiled table, and instead the table became managed data, which pulled
the classification table in with it.

** What shipped

- =ores.ore.series_key_shape=, owned by =ores.ore= because the grammar
  it records is ORE's and ORE defines it. Forty-three rows: the
  thirty-five the compiled table carried, reproduced row for row, plus
  the eight the corpus carries and the table did not know.
- =ores.marketdata.series_classification_rule=, owned by
  =ores.marketdata= because it maps a type onto our refdata taxonomy.
  Forty-three rows that reproduce the compiled map, so the swap changes
  no answer the classifier gave before. Two columns carry what a single
  class column could not: =asset_class_source= separates a literal rule
  from a correlation, whose classes are read from the two operands its
  key names, and the key holds the metric as well as the type so
  =GENERIC-MD= is classified by the instrument inside it.
- =series_key_registry= and =series_classifier= are values built from
  rows and passed in by const reference. Neither reaches for the
  database, so both are testable with no database, no NATS and no
  pipeline, which is what the story asked for.
- =ores_iam_provision_tenant_fn= copies both tables into a fresh
  tenant, so a new environment can import.
- The review round found that the two added tables carried no row level
  security and fixed it. The policy is opted into from each model, and
  a catalogue query confirms both tables now report row level security
  on with one policy, matching the sibling table the component already
  trusted.

** Acceptance

Every bullet is met. Two are worth stating precisely rather than
ticking.

The eight types each have a row, and the corpus proves the seven it
carries as market data keys. =GENERIC-MD= is the exception the Notes
explain: the corpus holds it only as the fixing id of four rows, so
=import_service= composes =FIXING/RATE/<id>= for them and the
=GENERIC-MD= shape row is never reached by this corpus. Its
classification rule is still covered, by the catalogue sweep that
classifies every type the classifier names.

The census drop is the acceptance's material change, and it is
measured rather than asserted: 1,612 distinct series before the eight
rows and 1,117 after, a fall of 31 per cent, printed by the test that
runs both ways.

The classifier's type set and the table's type set are equal at
forty-three, asserted in both directions, so a type with a shape row
and no classification row, or the reverse, cannot pass unnoticed.
