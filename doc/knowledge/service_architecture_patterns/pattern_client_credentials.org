This page defines the [[id:68FAC606-569C-4B9B-932B-3B3A0181AC8B][service architecture pattern]]
Client Credentials in the [[id:EA249899-6611-407F-A43A-B37019EBD1A7][pattern language]].
A service authenticates with its own credentials and receives a token for
itself, for work that belongs to the service and to no caller. In ORE Studio
every service logs in to IAM with its database account at startup and renews
the token before it expires.

* Also known as

- /Client credentials grant/, in RFC 6749, section 4.4.
- /Service identity/, /service token/, and =svc_nats=, the names ORE Studio uses.

* Context

A service does work that no person asked for: it loads its caches at startup,
runs a feed, answers a timer, or calls another service for data that is global
or that the service owns. No caller token exists for this work.

* Problem

How does a service authenticate when it acts on its own behalf, with no caller?

* Forces

- The service needs a token every other service accepts.
- The identity must be the service's, so its permissions are the service's and
  an audit row names the service.
- The service has no tenant and no party, so it must not be used to read data
  that row-level security scopes by them.
- A token that expires during the service's life must be renewed without a
  person.

* Solution

Each service has an account in IAM. At startup, after it has subscribed its own
subjects, it logs in with that account and receives a token. A token provider
in the service caches the token and renews it before it expires. Every call the
service makes as itself carries that token in the =Authorization= header.

The provider is a small state machine. It logs in only after the service's own
subjects exist, renews before the token expires, and backs off while IAM is
unreachable. A refused login is final: it means the account or the password is
wrong.

* Failure handling

#+ATTR_HTML: :class hug-leading
| Concern | What the pattern does |
|---------+-----------------------|
| Errors | A login refused by IAM is a configuration error: the account or its password is wrong. The service logs it and does not start the work that needs the token. |
| Timeouts | The login is a request with a timeout. A service that cannot reach IAM at startup retries with back-off. |
| Retries | The provider renews at 80% of the lifetime. A call answered =token_expired= forces a renewal and is retried once. |
| Idempotency | A login is safe to repeat; each one returns a new token. |
| Observability | Each renewal is logged with the new expiry. A refused login is an error with the account name. |

* Pitfalls

- *Tenant data read with the service's identity.* The service has no party, so
  row-level security returns no rows and no error. The result looks like "no
  data". The FX quote check met this, as
  [[id:F3CB17FB-6472-4DEB-BC5B-EC764C1368F8][Detect and correct reversed FX spot quotes]]
  records. Use [[id:EC6FAA96-294C-4547-8C2D-247C708E61C7][Token Relay]] for a
  caller's data.
- *A login before the service's subjects exist.* A service that mints a token
  against its own subjects before it subscribes them waits for a reply nobody
  sends. See [[id:1D02DB5B-1E50-4AA0-9780-A3F1CF237349][Service Bootstrap Phases]].
- *Wide service permissions.* A service account that holds every permission
  turns a compromised service into a compromised platform. Give each account
  only what its own work needs.

* Security

The service's password is a long-lived secret, held in its configuration. Its
token acts for the system tenant, so its permissions must be narrow. A leaked
token is bounded by its lifetime. A leaked password is not bounded, and rotating
it is the remedy.

* Resulting context

- Benefits :: Background work and startup work authenticate like any caller.
  The audit trail names the service.
- Liabilities :: The identity has no tenant and no party. Work that must act in
  a tenant needs another pattern.

* In ORE Studio

- =ores::iam::client::make_service_token_provider= logs in with the service's
  database account and renews the token at the refresh threshold.
- =ores::nats::service::nats_client= wraps it, and the service keeps one
  instance, =svc_nats=, for its own calls.
- The scheduler's trigger of a report uses this identity, as
  [[id:13105F27-9C05-495E-B9A0-2EFC9B5AC811][Scheduling and workflows]] states.
- [[id:8ECCBD02-21F5-455C-B520-193E4631092F][Anatomy of a Service]] shows the
  idiom, and [[id:03FA2F6D-9920-4BA1-A895-F8F796C94789][JWT Token Refresh]] is the
  plan that introduced the renewal.
