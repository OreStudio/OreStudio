* Goal

A body past the limit makes the read fail and the session return, so the caller
sees a closed connection and cannot tell a refusal from a network fault. The
refusal should say what happened, and the one route that legitimately takes a
large body should keep working.

* Acceptance

- An over-limit body is answered 413 with a JSON error and =Connection: close=.
- A chunked body past the limit gets the same answer.
- The storage upload route accepts a body up to the server ceiling.
- A client that sends =Expect: 100-continue= receives =HTTP/1.1 100 Continue=
  before its body.

* Plan

1. Compare the declared =Content-Length= with the limit straight after the
   headers and answer 413 without reading the body, closing the connection
   because the body is now unframed.
2. Catch =http::error::body_limit= during the body read for a chunked body that
   declared no length, and answer the same 413.
3. =domain::http_status= gains =payload_too_large= (413).
4. =storage_routes= takes the largest object it will accept and states it with
   =max_body()=, so the upload route keeps its current size while every other
   route keeps the small default.
5. Honour =Expect: 100-continue=: a client that asks before sending is told to
   proceed, so a refusal costs no upload.

* Result

An over-limit body is answered 413 with a JSON error and =Connection: close=,
for both a declared length and a chunked body, instead of the connection being
closed with no response. =Expect: 100-continue= is honoured, so a client that
asks first is told to proceed and a refusal costs no upload. The storage upload
route states the server ceiling as its own limit, so engine packages still
transfer as before.
