* Goal

The current --source acme path re-implements party activation, onboarding completion, and dataset publishing directly in a single hand-written plpgsql function, bypassing the C++ service/repository layer entirely (and the real counterparty save() path for the Acme Corp logo fixture). This already caused one real bug: the SQL path forgot to activate parties and mark onboarding complete, re-launching the Party Provisioning Wizard on every login. Target state: (1) reuse the real request pipelines a manual holding-group setup exercises, by minting short-lived JWTs server-side for each actor/party context needed and issuing the same NATS requests a client would -- not raw SQL, not in-process service calls -- so the Acme path continuously exercises and validates the exact same code real users run; (2) establish this internal-impersonation (mint scoped JWT, issue request, discard) as a reusable architectural pattern for other multi-actor server-side workflows, not a one-off for Acme; (3) make the holding-group spec (legal entities, LEIs, dataset bundles per entity) data-driven rather than hardcoded in SQL, so Acme is the first consumer of a generic mechanism, not a special case; (4) surface human-readable step-by-step progress to the client as it runs (e.g. "Step 1: Creating holding-group party", "Step 2: Publishing UK business units"), matching what a manual walkthrough would show, instead of raw internal step-codes.

* Acceptance

- A single --source acme (or equivalent) request completes the full four-party Acme Corporation holding-group setup with no manual per-party login, by internally impersonating each actor via short-lived JWTs and driving the real NATS handler pipeline (LEI import, dataset-bundle publish, party activation, onboarding completion, counterparty logo attachment) end to end.
- The internal-impersonation mechanism (mint scoped JWT for actor X, issue request, discard) is a named, reusable component -- not embedded ad hoc in the Acme orchestrator -- documented for reuse by future multi-actor workflows.
- The holding-group spec (legal entities, LEIs, dataset bundles per entity) is data-driven (config/dataset), not hardcoded in a SQL VALUES list or C++ literal.
- The client-visible log shows human-readable, per-step progress (e.g. "Step 1: Creating holding-group party") as the workflow runs, not raw internal step/action codes.
- No hand-written SQL re-implements activation/onboarding/versioned-save logic that already exists correctly in the C++ service/repository layer.
