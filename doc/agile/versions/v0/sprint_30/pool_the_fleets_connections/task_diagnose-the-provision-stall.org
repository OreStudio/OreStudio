* Result

The stall was not the pool, and it was not the transport. Every executable in
the tree was older than the libraries it loads: =ores.shell= and
=ores.dq.service= were linked on 21 November at 14:57, and the libraries they
call were built on 22 November. The dq service took the =system_core= request,
died in the copy its decoder made of it — the core dump names
=publish_bundle_request::publish_bundle_request= copying a string whose data
pointer was =0x5c= — and the step that sent it reported no reply within thirty
seconds. A full build relinked 691 targets, and the decoder, the shell command
that reported =std::bad_alloc= on the same subject, and the provisioning run all
behaved.

Two changes travel with the diagnosis. A step's publish dispatch now asks again
while the failure is transient, inside two minutes and at most six asks, so a
dependency that restarts costs seconds rather than the run; the upsert mode the
request names makes a repeat converge on the first write. Each phase of the
system provisioning is recorded before it starts, so a run that stalls says
which phase it stands in.

The evidence is the scenario this task existed to unblock. The database was
recreated with the fleet stopped, the provisioning recipe ran to all 17 steps,
and the marketdata service's journal holds no acquisition failure.
