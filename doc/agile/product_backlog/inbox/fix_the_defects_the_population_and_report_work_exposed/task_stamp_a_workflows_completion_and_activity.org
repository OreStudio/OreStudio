* Plan

The columns exist, are documented in the model, and are read by the query
path; nothing writes them. The engine reaches the completion at
=set_instance_state= and the step answers at =set_step_state=, so both
timestamps are written at those two funnels rather than at each of their
callers:

- =set_instance_state= moves =last_event_at= on every transition and writes
  =completed_at= on the first transition into a terminal state (completed,
  failed, compensated), leaving it alone afterwards so it names when the run
  finished rather than when its row was last written.
- =note_instance_activity= covers the work between two transitions, so a
  start that dispatches its first steps and a recovery that re-dispatches a
  step both move =last_event_at=.
- =set_step_state= writes =started_at= when a step first goes to work and
  =completed_at= when it first settles (=completed=,
  =completed_with_warnings=, =failed=, =compensated=), and logs the
  transition. The dispatch path writes =started_at= with the row it creates.
- A run the engine cannot reach, such as a test tenant dropped mid-run, is
  left alone rather than failed on a guess: its =last_event_at= stops where
  it stopped, which is how a reader tells it from a live run. This is the
  pattern the capture on the leftover test runs wants, and it does not need
  a hand over the state machine.

The model doc for =last_event_at= said "the most recent step-completed event
processed", which is narrower than what it now records, so the comment was
updated to match the behaviour.

* Notes

=build/stamp-verify/= holds the two scripts the clean check used: the minimal
provisioning script copied from the shipped Acme library script, and the SQL
that reads the properties. Both are untracked build output.

Two things the brief got wrong, both about the tables' shape rather than the
defect. The 50 instance rows are 25 instances, each with two version rows, and
the 828 step rows are 552 steps across versions: write-version tables carry
one row per version, so a count of rows is not a count of runs. And
=workflow_instance.last_event_at= was never going to be moved by a trigger:
the column is the engine's to write, and the engine is where the completion is
known.

* Result

Done on branch =chore/stamp-workflow-completion-and-activity=.

A clean =compass db recreate -y -k=, a fleet restart and one =bootstrap
setup ... --profile acme_demo= left 25 current instances, every one of them
=completed=, every one with =completed_at= and =last_event_at=, and 276
current steps, every one =completed= with =started_at= and =completed_at=.
None of the 50 instance rows or 828 step rows the defect was measured on
carried any of those times; those 50 rows are 25 runs and those 828 rows are
552 steps, because both tables are write-version. The tenant's
=tenant_setup_workflow= finished at =19:28:45.709675+01= by the log and wrote
=completed_at 19:28:45+01=, the second it finished in, while the tenant row
became =active= at =19:28:45.554809+01=, 155 milliseconds before the run's own
last step answered. Neither time is finer than a second in the store as it
stands: the generated mapper writes a whole-second =Timestamp=, so a
microsecond part read back is a round hundred thousand. The engine's writer
and every other writer share that truncation, and no reader can see past it.

Twelve lines carried the run's eight steps from their first dispatch to its
close -- a creation line for each of the four steps the graph is free to start
with and a transition line for each state change -- and each names the step,
the instance, the state it left, the state it entered and the time. The last
two were:

=./compass.sh test run -- -R "ores.workflow"= passed all three suites:
=ores.workflow.api.tests= 10 cases and 32 assertions, =ores.workflow.core.tests=
49 cases and 385 assertions, =ores.workflow.service.tests= 6 cases and 46
assertions.

Left for another task: rows written before this change still carry no times,
including the runs the test suites leave in progress in a tenant they then
drop. Nothing can recover the instant a past run finished, and the newer
capture on those leftovers is the place to decide what to do with them.

Also left, and named rather than fixed here because each is its own defect:

- =workflow_instance_summary=, the message the shell's =workflow list= reads,
  carries =completed_at= but not =last_event_at=, so the abandoned-run answer
  is available on the database and on the entity read but not yet on that
  summary. Adding it means a model change in
  =ores.workflow.workflow_messages.org= and the codegen run that follows it.
  =ores.workflow.workflow_instance= carries both, so a reader that needs the
  activity time has a path today.
- The generated CRUD verbs for both entities treat =completed_at=,
  =last_event_at= and =started_at= as caller-supplied: the write record
  carries them, the shell's =set= commands require them, and the service
  builds the new row from the record alone. So a caller that edits an instance
  without re-stating the times erases them. They are the engine's to own; the
  write record should stop carrying them.
- A compensation step reaches =compensated= while the forward step it undid
  keeps =in_progress=. That is pre-existing behaviour the deadline pass and
  the shell both read, so changing it here would have been a second fix
  wearing this one's clothes.
