* Goal

Every series of a class is derived in one batch that scales, because the platform quotes the whole
term structure rather than one rate: a per-series call with a vector of cells is the wrong shape for
the job it has to do.

* Acceptance

- The batch takes many series and returns flat, contiguous outputs: one array per coordinate axis (a level, a factor, a window, an ATM volatility and the smile's two parameters), one status per cell, and one offset per series, so a caller reads a series' row without walking another. A caller reads results without an allocation per series and without a variant per cell.
- No step shares mutable state between series, so the pass can run one series per task with no lock and the parallel answer equals the serial one.
- The cost is measured over a corpus of every interest rate series the seed carries, with the command and the commit on the task, and the measurement states the corpus size.
- A refused series or pillar costs its own cell and no more: the rest of the batch stands, and the refusal is a status and a reason per cell.
- The pass takes the discipline the FX batched grid already uses: prefix sums where a window slides, and one allocation for the whole output.

* Plan

Two layers, because the first draft put a class in the batch and that is the fault the story exists
to remove: a class-shaped batch invites a second one for the next class.

- =vol_batch=, in the measurement engine, is many level histories over one ladder of pillars. It
  names no class: per cell it holds the returns a window read, the level over that window, and the
  shape of the series' whole sample scaled to the cell's own life, plus a state and a reason. The
  transform is a parameter, because only the class knows whether a level keeps a sign.
- =project_ir_vols= turns a measured batch into the rates class's quotes: the model's factor, the
  ATM normal volatility, and the smile's slope, in arrays keyed by the batch's own layout. An FX
  projection would be the same function with different arithmetic, and no second batch type.
- =make_vol_batch= is the one place the layout is decided. =measure_batch= allocates with it and
  fills the rows in turn; a caller that wants its own threads allocates with it and fills rows
  itself, which is what the parallel test does.
- =measure_row= owns exactly one row. It reads the caller's levels and the settings and writes
  nothing else, which is why the parallel answer equals the serial one and no lock is needed.
- The pass walks the returns once, newest first, summing the first four powers. Because every
  pillar reads a tail, the sum of a window is the sum taken so far: a window costs only the returns
  the previous window did not reach, and no scratch, prefix array or per-cell allocation is needed.
- Refusals are data, not exceptions: a pillar no measurement can read, a series with no return or no
  spread, and a window the sample does not cover each mark their own cells with a state and a
  reason, and the rest of the batch stands. The projection refuses as a whole, because the model is
  one statement about every cell.
- The smile's level is the ATM, so the projection stores the slope alone: a second copy of the ATM
  is a second place the level can be wrong.

* Notes

- The precedent is =derive_grid= in the FX derivation: prefix sums of the first four powers of the returns make a day cost the same whether its window is a week or ten years, and a test holds it cell for cell equal to the day-at-a-time answer.
- The corpus is the currencies and terms the seed configures, so the number is about this platform and not a synthetic benchmark. A measurement without the corpus size is not a measurement.
- The parallel shape is one task per series over immutable inputs. Nothing in the derivation holds a cache, so no series can see another and the result does not depend on the order the tasks finish.
- =moments_from_power_sums= is the engine's moments read from four sums rather than from a sample, and the FX grid now uses it too: the two places that reconstruct moments from sums were the same arithmetic written twice. The FX tests that hold the grid equal to the day-at-a-time answer pass unchanged, which is what makes that fold safe.
- The suite was run with the environment's =.env= loaded, because the synthetic tests read their
  database settings from it and this worktree's services are down: the suites that need a database
  are outside this task's evidence and could not be run here.
- The first draft of this task put the class in the batch: =ir_vol_batch= held the series, the
  factor and the ATM. The review of the arc rejected it for the reason the story exists: a batch
  whose name and fields are a class's invites a second batch for the next class, which is the
  duplication being removed. The measured batch is now the platform's, and a class states its
  quotes as a projection over it.

* Result

=measure_batch= takes many level histories over one pillar ladder and answers in flat arrays: a
state, a window, a level, the shape at the cell's life and the refusals beside them, with an offset
per row. Nothing in it names a class, so the next class derives into the same batch and writes its
own projection over it; =project_ir_vols= is that projection for rates, and =derive_term_matrix=
still answers the same numbers for one series.

=measure_row= fills one row and nothing else, so the batch runs serially or one task per series with
the same answer; a test fills four rows at once and finds the arrays equal to the serial pass.

The pass costs one walk of each series' returns, and a window costs only the returns the previous
one did not reach. Over the seed's 264 rate series and 12 expiries, 3,168 cells take 13.8 ms of processor time
against 54.9 ms for the same corpus one series at a time.

It was proved against the whole system and not only the suite. The environment was rebuilt from
scratch, the whole tree was built, and the fleet ran the rebuilt binaries: 115 of 116 suites pass
against a recreated database, the ticks smoke passes with 0 ticks rejected by any adapter, and the
one failure is the vault custody suite, which inserts a consumer with an empty =modified_by= and so
cannot run on a provisioned system at all.

What this task did not do: the emitter that writes the quotes and the simulator that builds the cube
are separate tasks, and the FX grid is untouched, because it files a day of one pair across expiries
and not many series across a ladder.
