* Goal

A term structure or a surface is identified by its =market_series= row, and that row is named by
its =oresmd_uri=, whose query names each identity field under its own key: the asset class, the
scope such as a currency pair, the object kind, and the party. Nothing today lets a caller ask for
"the FX vol surface for EURUSD" from those fields. The caller builds the URI, or matches on a
string. The free-text =qualifier= column the original capture described is gone, so the
string-matching workaround it named no longer exists.

The outcome this task delivers: a caller names the object by its typed identity and the server
resolves it to a series, so a view can list and pick the composite objects of a scope without
knowing the URI grammar, and without a second source of truth for what the identity means.

* Acceptance

- A caller names a composite object by typed identity fields, the asset class, the scope such as a
  currency pair, the object kind and the party, and the server resolves it to one series with no
  hand-built =oresmd_uri= and no string match.
- The resolution is a repository read, not a client-side scan of every series. It does not parse
  every series: the read filters on the projected identity columns of
  [[id:C3B6A94D-0464-4BD8-AAD4-D1FEAE8398E4][Make a series identity joinable in the database]],
  which the codec wrote, so the narrowing states no grammar of its own.
- The typed fields mean what the URI means, from one source of truth, so the lookup cannot
  disagree with the identity the ticks land under.
- The request and the answer are on the wire, so a view can list the composite objects of a scope
  and pick one, and the shell can do the same.
- At least one production consumer uses it, or the result says why none does.

* Plan

Start from the identity that already exists. A series is named by its =oresmd_uri=, and the codec
already parses every field out of it, so the typed fields do not have to be invented. The capture
leaves one question open, how a caller filters on them. Choose between reading the URI per row,
adding an index over a derived projection of the URI's parts, or carrying typed columns. Then
settle the request shape, the read and the wire, and prove the consumer. Nothing here changes the
points, the observation table or the ingest path.

** The five fields of a series identity, and what they cost

The URI carries the identity in three places, and each one has a different cost to
resolve. A worked example, the FX vol surface for =EURUSD=, as it is stored today:

#+begin_example
oresmd://fx/EUR?type=series&instrument=fx_option&quote=rate_lnvol&ccy=USD
#+end_example

| Identity part | Where the URI holds it | Resolved by |
|---------------+------------------------+-------------|
| asset class   | the authority, =fx=    | a text prefix |
| scope         | the path, =EUR=        | a text prefix |
| object kind   | =instrument=fx_option= | a text match inside the query |
| the party     | a column, =party_id=   | the column, already indexed |
| quote and the type's remaining identity fields | the query | a text match inside the query |

The asset class and the scope both sit in the URI's *path*, so one prefix predicate,
=oresmd_uri LIKE 'oresmd://fx/EUR?type=series&instrument=fx_option%'=, resolves the
first three parts at once, and it can only be satisfied by a row of that asset class and
that scope, which keeps the answer no wider than the request. The column =party_id=
resolves the party. What no prefix reaches is the =ccy= field, which is what the capture's
"USD + USD-SOFR" filter wants, and it is the only part of the identity the prefix leaves
inside the query text.

** Option 1, parse every visible series in C++: rejected

It parses the URI once per row, which the second acceptance bullet forbids. Nothing in
the tree shows that bullet is wrong: =idx_read_latest_by_uri= already resolves a series
identity from the identity text through one equality predicate, so a scan per row buys
nothing over it.

** Option 3, typed columns on market_series: rejected

It stores the oresmd identity a second time, and the model says the URI is the only name
the row carries ([[id:A1B2C3D4-E5F6-7890-A1B2-C3D4E5F67890][market_series]]: "the registry's
=series_type=, =metric= and =qualifier= columns have gone"). This is the decision the
original capture asked for and the oresmd migration reversed.

** The chosen shape: narrow by the fixed prefix in SQL, then let the codec match

Option 2 is the shape the story names, and this is the form of it the task implements. It
is neither the projection nor a per-row parse, and the two facts below are what make it
work.

The typed identity read resolves through =oresmd_uri_codec::write=, which is not a
quote-only writer: =spelling_of= branches on =datum.is_series()= and writes =type=series=,
and =market_datum::make_series= is the checked factory for exactly the key =read= produces
for a stored series. So a typed request holding the row's identity fields, its instrument
type and its quote type composes the identity through the codec the reader uses, and the
repository resolves it through the existing unique index
=market_series_party_id_oresmd_uri_uniq_idx=, whose third key column is =oresmd_uri=. No
second grammar, no codec change, no codegen change, and =quote_type= is required because
the URI grammar makes =quote= a required key of every series URI.

The currency and index filter is the part a projection would normally serve, and the
decision is that it does not need one yet. The =ccy= field's *position* is not fixed
across instrument types, so a pattern match on it would be wrong — but that rules out
matching, not narrowing:

- The URI's *base* is fixed by the grammar and by the schema row: the authority is the
  asset class, the path is the =subject= field's value, and the query always opens
  =type=series&instrument=<kind>&quote=<quote>=. The writer emits it that way for every
  instrument type, so the base is a deterministic prefix, and the party is a column.
- Every field after that base is emitted in the row's schema order, which is why the
  codec, and not SQL, is the authority on what those fields mean.

So the read narrows in SQL with that prefix, over the existing identity index, and then
parses only the surviving rows with =oresmd_uri_codec::read=, filtering the remaining
typed fields such as =ccy= against the parsed datum. A wrong currency is refused by the
codec's own field comparison and never by a pattern, and the type's field names and order
stay in one place. The prefix itself composes through =market_datum::make_series= and the
codec's writer, so no part of the grammar is restated in SQL.

*The projection stays deferred, with its trigger.* A projection of the URI's query parts,
generated from the field specs, with an index over it, is the right answer when a plan or a
row count demands it: when the narrowing's candidate set grows too wide to parse, or when
the planner stops serving the read from an index. At 1707 rows the plan recorded in
* Evidence * shows the index already doing the work, so the projection buys nothing yet.
It remains the only shape that lets SQL itself filter on a query field whose position
varies, which this read answers by parsing after the narrowing instead.

* Notes

The capture's =qualifier= column and the =CurveBuilderWorkbench::selectedIndexQualifier()=
dash-to-slash workaround it describes are both gone from this tree, so this task cannot
reproduce the original bug. What it can do is keep the class of bug from coming back, which
is why the one source of truth for the identity is the deciding constraint and not a
preference.

The =party_id= column is part of the identity's fourth field and is already resolved
through =market_series_party_id_oresmd_uri_uniq_idx=, so the party needs no work of its
own.

The =ccy= field a filter would match is an identity field of some instrument types and a
coordinate of none, but its *position* in the query is not fixed across the schema: it
follows the row's field order, which is why a prefix cannot reach it and why the projection
has to be generated from the specs rather than pattern-matched.

The branch name and the task title both say "strongly typed index and currency filter",
which is the filter half that needs codegen. The task's own acceptance names only the asset
class, the scope, the object kind and the party, which is the identity half that does not.
The two halves are the two reads in the Plan, and the parent should say which one this task
is.

An identity with more than one party resolves to one series per party rather than to one
series. The read reports a list for that reason, and a caller that wants one series states
the party.

* Result

Delivered: a caller names a composite object by typed identity fields and the server
resolves it to a series, with no hand-built URI and no string match.

The design gate below stopped this task once, because the currency filter needed a
projection codegen did not have. The projection story, [[id:C3B6A94D-0464-4BD8-AAD4-D1FEAE8398E4][Make a series identity joinable in the database]],
then built it: the identity is real columns now, written from the codec's own parse. This
task's read therefore filters those columns rather than the prefix it was first built on.

What landed:

- =resolve_series_identity_request= and =resolve_series_identity_response= on
  =marketdata.v1.ops.resolve_series_identity=. The caller states the asset class, the
  scope, the instrument type, the quote type, the party and any remaining identity fields;
  the answer is the series rows that carry them.
- =series_identity_handler=, which checks the read permission, decodes the request, calls
  the read and answers.
- =market_series_identity_reader=, which validates the identity against the codec schema
  and then filters the projection on the columns the identity names. It refuses a
  malformed identity with =std::invalid_argument= rather than letting an invented column
  name reach the store, so the request is what is wrong when one is.
- The read is registered in =registrar.cpp=.

The prefix narrowing this task first chose was abandoned once the projection landed, and
the codec no longer carries =series_prefix=.

Limitations:

- Nothing was compiled and no test was run, by the hourly-build workflow. The build and
  the suites are swift curie's validation.
- The read is two statements: the projection is filtered, then the series rows are read by
  the keys it returned. A caller that wants one query needs a join, which is not written
  here.
- A series with no projection row is not found. The backfill operation repairs that.
- No production consumer calls it yet. The shell and the web client do not, so the read is
  on the wire with no caller. That is the acceptance's "or the result says why none does".
- The =* Plan= and =* Evidence= sections above are the design gate as it stood before the
  projection landed. They are kept as the record of that decision, not as a description of
  the code.

* Promoted from capture

Captured 2026-08-08 in the product backlog; promoted preserving the UUID.

** What

CurveBuilderWorkbench (the IR curve bootstrap builder UI) needs a way to constrain which
=market_series= rows a user can pick as a curve's Source/Output series and as a discount curve's
config, given a chosen currency and index (e.g. "USD" + "USD-SOFR"). Today the only way to do
that is client-side substring matching against =market_series.qualifier= — a free-text column with
no fixed shape. This already produced a real bug: =floating_index_type.code= uses a dash after the
currency (=USD-SOFR=), but =market_series.qualifier= for rates uses a slash instead (=USD/SOFR=,
per =ir_curve_feed.cpp='s own qualifier construction) — the two conventions silently diverged and
the filter matched nothing until a hand-rolled dash→slash translation
(=CurveBuilderWorkbench::selectedIndexQualifier()=) was added as a workaround.

String matching (substring/regex) against a free-text identifier column is not a sustainable way
to express "this series belongs to this currency and this index" — it is fragile to any future
change in qualifier generation, cannot be validated at write time, and cannot be indexed/queried
efficiently. What's needed instead is strongly-typed fields: a currency column and an index
column (soft FKs into =iso.currencies= and =floating_index_type=, following the same soft-FK
convention already used throughout the codebase — e.g. =change_reason_code=) directly on
=market_series= (or reachable from it), so filtering is a normal equality/join predicate, not a
string-matching workaround.

** Why

The dash-vs-slash bug above is a direct symptom of relying on unstructured text to encode
structured identity (currency + index family + tenor). Every future consumer that needs to filter
or group market series by currency/index (not just this workbench — the Rate Curves viewer,
synthetic feed bindings, etc. all currently do their own ad-hoc parsing of the qualifier string)
will hit the same class of bug unless the underlying data model gets typed fields.

This is closely related to, but not identical with, the =oresmd= migration
([[id:CA11A754-C153-42A7-AF8B-FA8447CE50B1][Migrate to oresmd, delete market_series qualifier and ore_key]]): that story's own
=Task: Migrate market_series qualifier/point_id generation onto oresmd= explicitly keeps
=qualifier='s *column shape* as a plain string (just generated deterministically from oresmd
fields instead of free text) — and per the oresmd design doc's own worked examples, the resulting
qualifier shape is still *type-dependent* (a discount-factor quote projects to =qualifier=USD3M=,
a swap-rate quote to =qualifier=USD/2D/3M=, etc.), so oresmd alone does not give callers a stable,
strongly-typed field to filter on either — it standardises *generation*, not *queryability*. This
capture is about whether =market_series= (or a related lookup) should additionally carry
structured, indexable currency/index fields, which is a genuinely open design question the oresmd
work doesn't resolve by itself and needs its own thinking session before implementation.

** Update, 2026-10-04

[[id:92415927-9D6F-4C3D-8C4C-6E282B73FA28][Rewrite the oresmd grammar as a hand-written codec checked against ORE]]
removed the free-text =qualifier= column. A series is now named only by
=market_series.oresmd_uri=, whose query holds each schema field under its own
name, for example
=oresmd://ir/GBP?type=series&instrument=ir_swap&quote=rate&ccy=GBP&...=. The
currency and the index name are therefore separate, typed fields of the
series identity, and =oresmd_uri_codec::read= returns them. The open question
narrows to how a caller filters on them: by reading the URI, or through an
indexed column or a query that the repository offers.
