* Goal

A republish of an app version checks the version of its own row, whichever other versions share its wrapper version.

* Acceptance

- The precondition of an app version reads its own row, by its id.
- Two versions that share a wrapper version republish more than once without a version conflict.

* Plan

The workunit model met the same fault and dropped its =:key_field:=, so its key is the
id. Do the same for the app version: drop =:key_field: wrapper_version=, regenerate
the files the model drives, and add a service test that republishes two versions that
share a wrapper version. A write then reads its own row by id.

* Notes

- The shell commands that took the wrapper version as the key, such as get, delete and
  versions, take the id now. The recipe and its scripts are regenerated.
- The notify trigger of the table states the key as the id, so a database that is not
  rebuilt keeps the old trigger and the eventing test fails until a recreate.

* Result

An app version is keyed by its id, as the workunit is. Two versions of one app that
share a wrapper version each read their own row, so each republishes without a
version conflict. The shell commands that named a version by its wrapper version name
it by its id.
