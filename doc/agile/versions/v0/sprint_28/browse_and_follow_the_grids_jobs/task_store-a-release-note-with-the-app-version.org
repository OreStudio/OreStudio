An app version holds a release note as text, written by the same call that publishes its package, and the generated read returns it.

* Acceptance

- The app_version entity has a release_note text column, and the generated table, protocol and wire type carry it.
- compute publish-package takes the note from a file and stores it with the version.
- A republish without a note keeps the stored note.
- The glossary and the app_version model page name the field.

* Plan

Add =release_note= to the app_version model as a text column that defaults to
the empty string, and regenerate the C++, SQL, TypeScript and shell recipe
files. Add =--release-note-file= to =compute publish-package=. The command reads
the file and writes the note with the version. A republish without the flag
keeps the stored note. Add the glossary entry.

* Notes

- The service reads the version precondition of an app version by =wrapper_version=
  alone, because that is the model's key field. Two versions that share a wrapper
  version, such as the two ORE builds with wrapper 1.0.0, read each other's row. A
  second republish of such a version fails with a version conflict. This is not
  new: the key was already so. The check used wrapper version 2.0.0 for a clean
  row. The task Key the app version by its app, engine and wrapper versions
  records the gap.
