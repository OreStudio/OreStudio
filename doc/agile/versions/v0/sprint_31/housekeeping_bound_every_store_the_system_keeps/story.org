#+title: Story: Housekeeping: bound every store the system keeps
#+description: Every store the system keeps grows without bound, because nothing deletes old data and nothing deletes old artefacts. Measured on the shared cluster on 2026-11-24: environment databases run from 415 MB to 13 GB. In the largest healthy one, ores_reporting_report_cashflows_tbl holds 1777 MB, ores_marketdata_delivery_counts_tbl 1270 MB, calendar dates 612 MB and ticks 72 MB, while report tables other than cashflows are small. The growth is therefore not uniform: cashflows, counters, calendars and compute artefacts each have their own shape and their own fix. Retention is declared on ticks alone and the Apache Timescale edition runs no retention job at all, so even that declaration does nothing. Nothing models a policy, nothing schedules a sweep, and no screen shows a person what the system is keeping. This story inventories every dimension, decides the concepts, models the configuration as data, gives it a screen, and applies it to each dimension.

* Acceptance

- Every dimension that grows without bound is identified, with its current size, its growth rate and the artefact that produces it
- The concepts are named and decided: what a retention policy is, what it attaches to, who runs the sweep, and what happens when the licence forbids the obvious mechanism
- The configuration is data, modelled and stored like any other entity, not hard-coded per table
- A person can see and change the policy of a dimension from a screen
- Every housekeeping run is visible in the system as a scheduled task, with when it last ran, what it freed and whether it is enabled, so a person can tell what housekeeping is running and tune it
- Each dimension has a mechanism that bounds it, or a recorded decision that it is kept indefinitely and why
- An installation ships no store without a default bound that the sweep applies, so a store is unbounded only when a person removed the bound or when its bound cannot be expressed as an age
- A store that is unbounded, whose policy is skipped or failed, or that passes its size budget reaches the administrator who owns it in their inbox, without them opening the housekeeping screen

* Result

Every store the installation keeps now has a catalogue row that states what
bounds it, a policy where a period can bound it, and a mechanism that applies
that policy. The screens read the verdict from one view rather than inferring it,
a pass tells a person about the stores nothing effective bounds and stops telling
them when a bound returns, and the object prefixes expire at the period their
policy states instead of reading as skipped.

Thirty-three tasks delivered it, across the scheduler, the storage service, the
SQL schema and the web. Two stores stay unbounded by decision: the calendar dates
cannot be bounded by a period because they are held once and rebuilt on a
horizon, and a node's scratch folder is released by the node, with the folders of
failed jobs kept as evidence. The screen states both, and the notice for each is
the person's cue rather than a silence.

* Decisions

- Every store ships bounded. The store catalogue declares a default retention
  policy for each store that can take one, and provisioning creates it, so no
  installation starts with a store that grows without a bound. The alternative —
  a screen that nags until somebody works through every store — fails on its own
  success: an alarm that fires on most of the list is wallpaper, and the count
  only means something if it can reach zero. The cost is the opposite risk, that
  a default deletes data nobody decided about, which the periods answer: a
  quarter for run output, a month for counters, a week for job inputs, a day for
  scratch. A store without a policy then means a person removed the default, or
  the bound cannot be expressed as an age, and both are worth a notification.
  The calendar dates are the second case: a policy bounds by age, and a business
  day behind the horizon is not old, it is out of range, so that store needs a
  delete by range and stays unbounded until it has one
  ([[file:../../../../product_backlog/inbox/a_policy_cannot_bound_a_store_by_date_range.org][the capture]]).

- Housekeeping tells the administrator; it does not wait to be asked. The screen
  is pull, and a store fills a disk without anyone opening it, so housekeeping
  raises notifications through =ores.inbox= rather than building a channel of its
  own: a kind per case, an audience by permission in the store's own tenant, and
  a link to the store's page. The message never carries the numbers a person
  needs to act, because acting needs the plot and the policy, and a sweep that
  skips four policies raises one message rather than four. A store the platform
  owns is the system administrator's problem; a store a tenant writes is the
  tenant's.

- The node package cache is keyed by content, not by app version. A machine
  downloads and unpacks a package once per distinct digest, into a directory
  named after the digest, and every node on that host shares it. The wrapper
  already locks per package, verifies the transfer against
  =evt.package_sha256= and renames an extracted tree into place, so the digest
  is in hand and the change is to key on it and to drop the retained tarball.
  The first step is configuration only: pass =--package-dir= to every wrapper
  unit so the sharing the code already implements actually happens.

- A store's chunks are cut on the instant its rows were written, not on a
  business date it carries. A chunk drop bounds a store only by the time the
  chunk is cut on: the run output tables carried the date the engine stated,
  which for a projected measure lies decades ahead, so almost every row sat
  beyond the period and no chunk ever aged out. Cutting on the write instant
  makes a chunk one run's worth of rows, which is the unit a retention period
  can name and a sweep can remove.

- A node releases a job's folder once its output has been uploaded. The folder
  is scratch: its output lives in =compute/output= and its log in
  =compute/logs= by then, so keeping the copy buys nothing and costs about
  3.8 MB per job, forever. A job that fails before its upload keeps its folder,
  because that folder is then the only evidence of what went wrong; those are
  bounded by age once the policy engine exists rather than deleted on the spot.

- The calendar dates are held once, in the system tenant, and rebuilt on demand.
  A calendar's business days follow from its rule and its exceptions, which the
  platform authors and publishes once, so every tenant needs the same bytes:
  486,540 rows and 283 MB for 36 calendars over 37 years, at 610 bytes a row with
  its indexes. A per-tenant copy writes them once per tenant; computing them in
  every pricing run charges the run for work the installation can do once. One
  copy, read through the shared-reference policy, with the materialisation
  service kept as the way the copy is rebuilt, bounds the store by the horizon
  rather than by the number of tenants. The copy is the baseline the platform's
  rules state; a holiday is a party's fact, so the tree holds two levels for an
  exception, the installation's and a party's, and the party's own rows are
  applied over the baseline when it reads them. An HK party and a UK party in one
  installation therefore trade on different dates without either holding a copy
  of the days.

- The screen states boundedness; the client never infers it. Whether a store is
  bounded, and why it is not, is a fact the installation states once, in
  =ores_scheduler_store_bounds_vw=, and two reads answer it: the bounds of every
  store, and one store's measurements. A client that decided boundedness from a
  policy's presence would have to hold its own copy of which actions the sweep
  performs, and that copy goes stale the first time the sweep learns an action —
  which is exactly the state the prototype called the dangerous one, a store that
  reads as bounded while nothing bounds it. A failed last sweep is the same
  argument: the view states the store unbounded, because the mechanism exists and
  did nothing.

- The list is a work list; the store's page is where a bound changes. The
  review that signed off the prototype rejected its two-pane variant as a shape
  and kept its editor: the form opens on the store's own page, where the store,
  the size it holds and the last sweep are already in view, so a period is
  chosen beside the quantity it applies to. The list holds every store and every
  number at once because comparing them is the question it exists to answer, and
  a form in one of its columns would take that comparison away.

- A bound is written from the catalogue, and the form names three numbers. A
  policy holds its store, its target, its action and the words that say why the
  store is kept; the catalogue states all four, and a form that sent them back
  could retarget a bound. So the write takes whether the bound applies, its
  period and its cadence, and the service composes the rest from the catalogue
  row it just read. The version the read answered travels back with the change,
  so a period somebody else moved is refused rather than overwritten, and a
  policy the screen creates is named by its store.

- Housekeeping tells a person, and stops telling them. The screen is pull, so a
  pass of its own reads the bounds view and the run ledger and raises a notice
  per store nothing effective bounds; it also clears the notice of a store that
  comes back under a bound, which is what makes the inbox's count follow the
  count of unbounded stores rather than the number of times anybody looked. The
  audience is the permission the catalogue's own write requires, resolved in the
  tenant that holds the store, and only a person is told: a service account holds
  the component's wildcard and no person signs in as it. A notice names the store
  and links to its page, and carries no size, no rate and no period, because a
  second statement of those numbers would drift from the page that reads them.
  One sweep raises one notice however many policies it leaves unapplied: the
  ledger's instant is the transaction's, so the sweep's own rows share it.

- An object prefix is bounded by an action that reaches the store, not by the
  store's own lifecycle rule. A bucket rule expires by prefix and age without a
  caller and without a ledger, so it cannot be asked what it would remove and it
  states the period outside the installation's own data, where no screen reads
  it and no policy version records it. The sweep cannot do the work either: it
  is SQL, and SQL cannot reach an object store, which is why the two prefixes
  read =skipped= for as long as they did. So the object half of housekeeping is
  an action of its own, =expire_prefix=, which asks the database which object
  policies are due — beside the rule the table sweep uses, so the two cannot
  disagree about when a store is next treated — asks the storage service to
  expire each prefix at its cutoff, and writes one ledger row per policy stating
  what the cutoff held, what was removed and what a limit left. A dry run is the
  same path with nothing removed, so the plan is readable before a sweep acts.

- An expiry is one operation, and it states age to the whole second. A caller
  that lists a page, removes part of it and reports the whole page has stated
  something it did not do, so the storage service selects and removes in one
  request, bounded by a limit whose remainder the reply states. Age is stated to
  the second because the file clock is converted through the clocks' current
  difference: a finer instant differs between two reads of one untouched file,
  and a cutoff a caller derives from a listing would not include the object it
  came from.

* Out of scope

-
