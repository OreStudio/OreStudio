* Notes

** There is no hotspot to split

The largest gap between two step completions in the failing run is 36.9 s
and the median is 1.96 s. The time is spread across all 5422 steps, with a
long tail of 20 to 30 s translation units in =ores.shell/refdata=,
=ores.ore/core=, =ores.reporting/core= and =ores.trading/core=. Splitting
one oversized translation unit therefore buys little.

** The linker is measured out

The build has 53 link steps out of 7187. Link time cannot be a
significant share of a six-hour build, so a faster linker is not the lever.

** The unity build is blocked on symbol hygiene

Merging translation units fails immediately. Four files in
=ores.analytics.quant= each define a file-local =small_kappa_threshold= at
namespace scope, so one unity translation unit redefines it:

=black_karasinski_process.cpp:33=, =ornstein_uhlenbeck_process.cpp:30=,
=quadratic_gaussian_process.cpp:37=, =two_factor_gaussian_process.cpp:29=.

The build stops in 19 s. A unity build therefore needs a sweep first:
every file-local constant and helper becomes =static= or moves into an
anonymous namespace. The sweep's size is unknown, because the build stops
at the first collision.

The collision itself was cleared later, by the separate story that hoisted
=small_kappa_threshold= into one constant of the component. Unity was still not
pursued, because the hotspot measurement below had already removed the reason
to.

** The cache, not the compile work, is the whole story

Run 37097859492 on 2026-10-03 built at an 85.72 % sccache hit rate. Its
=linux-clang-release-ninja= job finished the whole build in about 49
minutes, ran the suites in 340.30 s, and failed only one of 89 tests. The
job took 1h0m1s in total. The same job needs more than six hours at the
3 to 10 per cent hit rate it sees now, which is why it times out. The
tree is not too big to build; the cache is cold.

** Why it cannot recover on its own

A job that hits the six-hour limit is cancelled, so it never reaches
=Save sccache= and the entry is never refreshed. The next run restores
the same stale entry, misses again, and times out again. The cache size
follows the same trap: the clang-release entry is 1.22 GB against its
2.5 GB ceiling, because it takes several completing runs to fill.

** How the deadlock was broken

The deadlock was broken on the cache side, which is where the constraint was,
and each repair landed as its own story in this sprint:

- Save the cache whenever the CTest step ran and the local cache grew, instead
  of gating the save on =!cancelled()=.
- Cap the CTest step below the job limit, so the save has time to run before the
  job is torn down.
- Save under a run-unique key and prune older entries, so a failed save cannot
  destroy the cache and the entries cannot grow past the repository cap.
- Scope the cache keys to each workflow, so the two workflows stop handing each
  other entries built with flags the other cannot use.

The continuous clang jobs now finish inside the six-hour limit: clang-debug in
4h08m39s and clang-release in 2h24m15s.

* Result

The trials are complete and every compile-time lever is recorded as measured
out. No compile-time lever was adopted.

- There is no hotspot to split: the largest gap between build-step completions is
  36.9 s and the median is 1.96 s, so the time is spread across all 7187 steps.
- The linker is measured out: 53 link steps of 7187.
- A whole-tree unity build stops in 19 s on the repeated =small_kappa_threshold=,
  and the hotspot measurement had already removed the reason to pursue it. The
  collision was cleared later by a separate story, so the block is gone even
  though unity was not adopted.
- Precompiled headers were not trialled, because the hotspot measurement removed
  the reason to.

The constraint was the compiler cache, and the repairs landed as separate
stories in this sprint: keeping the save on a cancelled job, giving the save
time to run, pruning older entries, and scoping the keys to each workflow. The
continuous clang jobs now complete inside the six-hour limit, at 4h08m39s and
2h24m15s.

The story is closed with these findings so that the next reader does not re-run
the trials. Its commits carry documents only; no build or workflow file changes
in them.
