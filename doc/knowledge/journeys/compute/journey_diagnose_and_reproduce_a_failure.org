This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A signed-in person reads why a compute job failed, from its app version, package, command, inputs, exit code and stderr, and pulls the node's own logs, so the work can be run again locally.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want to know why this job failed, and I want to run it again on my own
machine." The person opens one failed run and reads one screen: the failure rate
around the run, which nodes and which app versions it clusters with, the job's
full detail, the exact command the wrapper ran, the exit code, the stderr, and
the lines the node recorded. The journey is done when the person can explain the
failure and has the input bundle and the engine package to reproduce it.

* Actor and trigger

The actor is what the rows admit, and the session decides the rows. A member
sees their own run, a tenant administrator sees their tenant's, and the super
administrator sees every run. That part of the journey does not split on the
actor: the job's own detail is rows, and permissions and row-level security
already describe the sets.

One control on the screen is withheld, and this is the one genuine boundary in
the five journeys. A node's own logs are installation logs, and they may carry
another tenant's inputs, so pulling them is a capability the super administrator
holds and another tenant administrator does not. The job's own engine logs are
not withheld: they belong to the job and carry its result id. The control for
the node's logs is disabled for a non-super administrator and the screen says
why. That is one control withheld, on the same screen, and it is not a second
journey
([[id:5A5D6490-AF64-4AAF-8B3D-48EF3EDAF3D2][Tenant ownership and the
information flow]]).

The trigger is a run whose outcome is 3 ClientError or 4 NoReply, or a cluster
of them on the failure charts. The person opens the run's detail and reads it
until the failure is explained. The journey ends when the run is explained and
the person holds what they need to reproduce it.

This journey writes nothing. It reads the failed run, its job, its batch, its
app version, its node and the logs. It does not re-run the job, which the
person does on their own machine with the shell.

* Steps

1. *Find the failure.* The person opens the failure screen from a failed run,
   or from the failure charts. The system answers with the run and its job: the
   run's =outcome=, its =error_message=, the =host_id= it ran on, and the
   =workunit_id= it belongs to.
2. *Read the shape of the failure.* The system draws the failure rate over
   time, so the person sees when it started; the failures by node, so one bad
   machine shows up; and the failures by app version, so one bad release shows
   up. The load heatmap, coloured by failures, places the failures on the grid.
3. *Read the job's full detail.* The system states the job's batch and its
   external reference, the workunit's =app_version_id=, =input_uri= and
   =config_uri=, the run's =server_state=, =outcome=, =error_message= and
   =received_at=, and the node's name.
4. *Read the app version and the package.* The system states the
   =wrapper_version= and =engine_version= the run used, and the per-platform
   package row of that version: its =platform_id=, its =package_uri= and its
   =sha256=. The person can verify the package they will run against the digest
   the grid verified
   ([[id:1E563104-6F89-4858-9395-D869A7E817A6][ores.compute.app_version]],
   [[id:E0010C05-D225-462B-A194-330F12A41B28][ores.compute.app_version_platform]]).
5. *Read the command and the stderr.* The system states the exact command the
   wrapper ran. The wrapper logs the command line and the engine's
   stdout and stderr to =engine.log=, and publishes its lines to the telemetry
   logs tagged with the run's result id, so the person reads what the engine
   said and with which arguments
   ([[id:1805BAFC-7E43-4D9C-822F-17C3455C6E00][Compute job lifecycle]]).
6. *Read the exit code.* The system states the engine's exit code. The result
   carries no exit-code field; the wrapper writes it into =error_message= as
   "Engine exited with code N", followed by the tail of =Output/log.txt=. The
   screen reads it from there and says so.
7. *Read the node's logs.* The person presses the node logs control. A super
   administrator gets the lines the node recorded around the run. A non-super
   administrator finds the control withheld, and the screen says why: the
   node's logs are installation logs and may carry another tenant's inputs.
   This is the one control the actor dimension withholds.
8. *Reproduce it locally.* The person downloads the job's input bundle with
   =compute download-input= and the engine package from its =package_uri=,
   checks the package against =sha256=, extracts both, and runs the engine with
   the command from step 5 in the job directory. That is what the wrapper did
   ([[id:A6E676BD-E907-4F29-8D55-07174C846AA9][How do I download a compute job
   input from the shell?]]).
9. *Nothing to explain.* The run succeeded, the range holds no failures, or the
   failure belongs to another tenant. The screen says so and offers the way
   back. It does not present a flat failure line at zero as a quiet grid.
10. *Leave, or go on.* A failure explained by a build continues in
    [[id:19A796E3-A594-4C3E-8ACA-646D743BB496][Keep what the grid runs]]. A
    failure explained by a busy or a lost node continues in
    [[id:32ECF41B-B27B-4A69-B7F0-A4131F993297][Watch the grid]]. A failure the
    logs explain continues in
    [[id:57C4B9A6-DA79-403E-984E-50D2561352B3][Read the telemetry logs]].

* Screens and wireframes

One screen. The failure charts, the job detail, the command and stderr panel,
the node logs control and the reproduce panel are panels of that screen, because
the person reads them as one answer. The screen is read-only: it creates
nothing, changes nothing and destroys nothing, and the one control it withholds
is a read and not a write.

The panels are the charts [[id:0169FDD7-9B88-4766-9AE9-93FE87200700][Compute
journeys]] names for diagnosing a failure:

| Panel | Chart | Answers |
|-------+-------+---------|
| Rate line | *Failure rate over time* | When did it start? |
| Node bars | *Failures by node* | Is one node bad? |
| Version bars | *Failures by app version* | Is one release bad? |
| Node grid | *The load heatmap, on failures* | Where is it failing? |

The node grid is the same chart as the load journey's heatmap with a different
metric, which is why the two journeys share it.

The wireframe is not drawn yet. This journey is written before the prototype,
and the prototype must draw these charts from mock series at the sizes the real
screen gives them.

* Prototype

None. This journey is not built and has no clickable prototype. Its design
record is the use-case analysis on
[[id:0169FDD7-9B88-4766-9AE9-93FE87200700][Compute journeys]].

The job's engine logs are found by their tag. The wrapper publishes both
=engine.log= and ORE's =Output/log.txt= to the telemetry logs with the run's
=result_id= as the =tag=, so the log read takes a tag filter and no host is
involved. The node's own logs carry no host id at all, which is why step 7 is
both withheld and, today, not directly answerable.

* Operations and messages

#+ATTR_HTML: :class hug-leading
| Step | Operation | Subject | Status |
|------+-----------+---------+--------|
| Before the screen: the wrapper runs the engine and submits the outcome | Submit one result | =compute.v1.results.submit= | exists |
| Before the screen: the wrapper publishes the engine's lines | Publish a batch of log entries | =telemetry.v1.logs.publish= | exists |
| Find the failure | Read one run | =compute.v1.results.get= | exists |
| Find the failure | Read the runs of the job | =compute.v1.results.list_by_workunit_id= | exists |
| Read the job's detail | Read one job | =compute.v1.workunits.get= | exists |
| Read the app version and the package | Read the app versions and their platform rows | =compute.v1.app_versions.list=, =compute.v1.app_version_platforms.list= | exists |
| Read the node | Read one host | =compute.v1.hosts.get= | exists |
| Read the command, the stderr and the engine's lines | Read the log entries whose tag is the run's result id | =telemetry.v1.logs.list= | exists |
| Read the node's own logs | Read the log entries of one node | (the entry carries no host id) | missing |
| Withhold the node's own logs | Check the caller's permission for a node's logs | (no dedicated permission) | missing |
| Read the failure charts | Read the failures by node and by app version over a range | (no aggregate subject) | missing |
| Read the failure charts | Read the grid samples in the range, coloured by failures | (no range read) | missing |
| Reproduce it locally | Download the job's input bundle | =compute download-input= | exists |
| Reproduce it locally | Download the engine package | (no shell verb; storage HTTP only) | missing |

=telemetry.v1.logs.list= takes an optional tag, source, source name, component,
level, range, session and account, and its filters combine with AND. The job's
lines are read with =tag= set to the run's result id, which is what the wrapper
published them under.

=compute.v1.results.submit= is the trusted machine channel: a node holds no
user JWT, so the submit carries the =result_id=, =host_id=, =output_uri=,
=outcome= and =error_message=, and the service records them on the run.

The browser reads the screen through a hand-written BFF route on the
[[id:6A63AAC7-4869-493A-97E7-55B919874784][journey runtime]]. No route serves
a compute screen yet.

* What is missing

1. *The exit code is prose, not a field.* The result carries no exit-code
   column. The wrapper writes "Engine exited with code N" into =error_message=,
   so the screen reads a number out of a sentence. A dedicated field is the
   clean shape, and the tail of =Output/log.txt= belongs beside it.
2. *A node's logs cannot be pulled by node.* The log entry carries a source, a
   source name, a component and a tag, and no host id. The job's own line
   stream is reachable by tag, and a node's wide line stream is not. A host id
   on the ingested entry, written by the publishing wrapper, is what the
   control needs. The same missing field is the permission boundary: the lines
   that would answer the question are the lines that may carry another tenant's
   inputs.
3. *No permission guards the node logs.* =telemetry::logs:read= exists in the
   seed, and the logs read checks no permission. Withholding one node's logs
   from a non-super administrator needs a code that names the node scope, and
   the read must check it
   ([[id:CCB1D9D1-B5F8-43D5-B5E5-A6A3A5BDC9E7][Nothing gates a hand-written
   operation handler]]).
4. *The failure charts have no read.* The failure rate, the failures by node
   and the failures by app version are aggregates over a time range. A result
   carries =host_id= and =outcome=, and a workunit carries =app_version_id=, so
   the rows the charts need exist, and no subject returns them over a range.
   The heatmap on failures needs the same range read as the load journey
   ([[id:E7035C69-EB6E-4158-B384-825A8CDACA8A][The grid has no usage
   history]]).
5. *No package download verb.* The wrapper downloads the engine package from
   =package_uri= and verifies it against =sha256=, and a person reproducing a
   failure has no shell verb for either. The input has =compute download-input=
   and the output has =compute download-output=; the package has neither. The
   storage HTTP path works, and the journey must not pretend a verb exists.
6. *A failed run writes no output archive.* On a non-zero exit the wrapper
   uploads nothing, so =output_uri= stays empty and there is no =Output/= to
   inspect beyond the lines. The screen must say the archive is absent and not
   present an empty field as a missing file.
7. *The node summary drops the failure fields.* =node_sample= carries
   =tasks_failed= and =max_task_duration_ms=, and =node_stats_summary= carries
   neither, so the failures by node chart cannot be driven from the summary read
   ([[id:8C1D6E61-3661-49F2-90BB-00ED7C4F113C][The node summary drops the
   failure fields]]).
8. *One tenant's work is dispatched to nobody.* A wrapper subscribes to the
   system tenant's assignment subject while the dispatcher routes to the owning
   tenant's, so a job can sit =Unsent= with no failure and no result. A failure
   screen that only reads results would show nothing for it
   ([[id:0072F772-F879-4DDB-8944-96433843CE17][The wrapper consumes one
   tenant's work]]).
