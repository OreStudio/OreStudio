* What the Windows job says first

The task's premise is that the MSVC build fails on C1202 in the reflected
aggregate. On 2026-10-28 it does not: the nightly run
[[https://github.com/OreStudio/OreStudio/actions/runs/40643890504][40643890504]]
contains no C1202 at all, because the build stops earlier:

#+begin_example
real_environment_provider.cpp(28): error C2220: the following warning is
treated as an error
clang-cl: error: 'getenv' is deprecated [-Wdeprecated-declarations]
#+end_example

That is a unity-build effect: the file defined _CRT_SECURE_NO_WARNINGS, which
arrives after the CRT has already been included by an earlier file in the same
unity unit, so it suppressed nothing. Fixed by reading the environment with
_dupenv_s on Windows and dropping the define.

The same sweep found the rule broken in four test files, eighteen calls in all,
one of which suppressed the warning with the same macro and one of which used
=setenv=, =unsetenv= and =tzset= with no platform guard at all -- a Windows
build break waiting behind this one. They read through =ores.platform= now, and
the timezone calls have a portable shim. No warning is suppressed anywhere in
the tree; the only native =getenv= left is the provider's own POSIX branch,
which is where the project's memory says it belongs.

The consequence for this task is an order, not a change of goal: the C1202
cannot be observed, let alone measured, until the build gets past the errors in
front of it. The Windows job also reports =nats-server did not become ready
within 30s=, which is its own problem and does not stop the compile.

* What the Windows job says next

With the environment read fixed, the 2026-10-28 run
[[https://github.com/OreStudio/OreStudio/actions/runs/40722677906][40722677906]]
gets past it and stops somewhere else, in each of its two compilers.

MSVC stops on a unity-build name clash in this project's own header:

#+begin_example
ores.nats/service/retry.hpp(56): warning C4459: declaration of 'logger_name'
hides global declaration  -> error C2220
note: see declaration of 'ores::nats::service::`anonymous-namespace'::logger_name
#+end_example

The local in =retry_with_backoff= is now named for the retry, so it hides
nothing.

clang-cl stops inside third-party headers, on a preprocessor error rather than
on anything this project wrote:

#+begin_example
vcpkg_installed/x64-windows/include/rfl/Literal.hpp:413:75: error: too few
arguments provided to function-like macro invocation
(same in rfl/Variant.hpp:31 and rfl/Generic.hpp:211)
#+end_example

That is a separate failure with a separate owner: it is an =rfl=/clang-cl
interaction, it appears in headers the project does not own, and nothing in the
configuration document is involved. It is recorded here so the split is not
blamed for it, and it wants its own task before the clang-cl job can prove
anything about this one.

* What the split actually is

The measurement first: =curve_configuration_document= holds **33 typed vectors**
plus its configuration object, in one reflected struct. The C1202 limit is a
per-struct count, so a file split -- moving the same struct into more headers --
cannot lower it. The task's original instruction ("split the header and the
handler") was written before that was measured, and on its own it would not have
worked.

The mechanism that does work is already in this tree: field groups.
=projects/ores.codegen/library/templates/ores.cpp.field-group.field_group_header.org=
states it in its own words --

#+begin_quote
By composing the parent struct via =rfl::Flatten<SubStruct>= each sub-struct is
reflected independently, keeping the per-struct field count low while preserving
the original flat JSON wire format.
#+end_quote

So the split is: the document's families become field groups, the document
composes them with =rfl::Flatten=, and each family is reflected on its own. The
wire stays flat, which is what the acceptance asks for, and no subject or
handler changes.
