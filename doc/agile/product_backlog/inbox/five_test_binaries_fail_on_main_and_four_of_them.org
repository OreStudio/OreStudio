What the run establishes: the tests write one entity, poll up to ten
seconds for its notification, and, when none arrives, re-drive the write
with the same version-0 object. The re-drive is a create against a row
the first write left live, which the store refuses with 'Row already
exists: a create cannot replace it'. Before =4d36229a81= that duplicate
replaced the row and the tests passed.

What the run does not establish is which of the two is cause and which is
effect. The capture above reads the missing event as a consequence of the
refused write; the test's own retry comment reads the refused write as a
consequence of a missing event, and the retry window is an order of
magnitude longer than the chain it waits on, so a lost notification is
not the obvious explanation either. Whoever takes this decides between
the two, and the decision is one for all ten assertions rather than per
file: either the tests write version-aware, or the notification chain is
what needs the work.
