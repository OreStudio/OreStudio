* Acceptance

- A quote's value is read from the element that holds it, not from a column named after an ORE child element.
- A segment's quotes are drawn under that segment, in the order the document writes them.
- A composite quote's rate and spread show, and so does the list a quote belongs to.
- A quote that states no words of its own, such as a composite quote, shows its rate and spread rather than an empty row.
- The page names a quote's parts in its own words, because the contract documents the `Quotes` element and not its parts.

* Plan

Three facts decided the shape.

A quote is not a leaf. It is the text of a `Quote` element, and the element has no
name of its own: the contract documents `Quotes`, an element, and carries no row
for what is inside it. Forcing a quote into the leaf shape would have meant a
leaf whose xpath no document holds, which is the defect the columns already fix
for the other way round. So a quote is read as its own shape: its list, its text,
its optional flag, and the rate and spread pair a composite quote states.

Quotes belong to a segment, not to the curve. The collection rule says which
column joins a quote to a row, so a segment's quotes are the rows that name it,
in the position order the document writes them.

What is not drawn: the quotes a section attaches to the curve itself rather than
to a segment, such as an equity curve's. Those are rows of the same table with no
segment, and they want the entry's own card.

* Notes

- *The contract documents the list, not what is in it.* No contract row names a
  `Quote`, a `RateQuote` or a `SpreadQuote`, so a quote has no leaf to join and no
  words to read. The page names its parts itself, which is the one place this
  screen departs from the leaf standard, and the deviation is the contract's.
- *A quote is a row, not a leaf.* The element has no name of its own: the text is
  the element's text. Reading it as a leaf would have meant an xpath no document
  holds, which is the defect the columns already fixed for the other direction.
- *The corpus is plain quotes.* All 420 quotes a provisioned document holds carry
  a text and no list, no rate and no spread. The composite and named-list paths
  are therefore covered only by the fixtures, which state a quote with a
  =BasisQuotes= list and a =RateQuote=/=SpreadQuote= pair.
- *The list is never filled.* No caller of the projection's =import_quotes= passes
  a list name, so =quote_list= is null for every row the system writes today; the
  screen draws the field, and the projection owes it a value.

* Result

A person reading a curve sees, under each segment, the quotes it bootstraps from:
the text of each quote, the list it sits in, and a mark on the ones ORE may leave
out, in the order the document writes them.

The BFF reads a segment's quotes by the column the collection rule states, so a
quote arrives with the segment that holds it and never with another. The page
draws them under the segment's leaves.

Seen on a provisioned environment, in a browser as well as through the route: the
walk in =evidence/curve_screens.mjs= signs in, chooses the party, opens the UK
configuration and reads the Curves tab, and =evidence/curve-segments-and-quotes.png=
is what it saw — the Segments card holding one row of kind Simple, its two leaves,
its twelve quotes, and the block badges below it for the elements it does not draw.

Through the route the page reads: every yield
curve of the UK configuration reports one `Segments` row of kind `Simple`, two
leaves and twelve quotes, the first being `IR_SWAP/RATE/GBP/0D/1D/1M`. The whole
configuration counts 221 of 238 parameters documented.

Two things that only the live run showed, both fixed or filed: the row's recorded
instant was drawn as a leaf, and a segment's conventions arrive as a gap because
the contract holds no row for them (task 3D1208F2, "Record the leaves a segment inherits").
