* Goal

The context header no longer includes pq/pool.hpp or pq/transaction.hpp, but the second path into pq/connection.hpp is still open: pool.hpp and statement.hpp each reach it. This task closes that path so the cut is not undone by another includer.

* Plan

This plan was written before the work started. Two things it says were
corrected by measuring: a fourth path into the connection header turned up
(the listener service, see =* Notes=), and the numbers it guessed are the
analysis's 365 rather than the 279 this tree measured.

The previous task cut =pq/pool.hpp= and =pq/transaction.hpp= from
=domain/context.hpp=, and the cut holds: the context header now names
=pq::pool= through a =unique_ptr= and =pq::session_context= through a
declaration. But five hundred objects still read =pq/connection.hpp=,
and one of them is =domain/database_options.hpp=, which every service's
=app/application.hpp= and =config/options.hpp= include. So the cut is
undone one level further out: a service's application header parses
=libpq-fe.h= to hold a database configuration it never connects with.

Three paths reach the connection header. Each is cut at its own cause.

1. =domain/database_options.hpp= includes =pq/connection.hpp= for one
   declaration, =pq::connection_options=, which has lived in
   =pq/options.hpp= since the context task. The include is a leftover,
   and it is emitted by the =cpp_options_header.hpp.mustache= archetype
   from the model's =* Includes= block, so the fix is the model and then
   =regenerate --address ores.cpp.field-group=. Editing the generated
   header alone would be undone by the next regeneration.
2. =pq/pool.hpp= includes =pq/connection.hpp= because it holds
   =std::vector<std::unique_ptr<pq::connection>>=, and a =unique_ptr=
   member with an implicit destructor needs the complete type where it
   is destroyed. It takes a forward declaration instead, and =~pool()=
   moves out of line, where =connection= is complete. This is the idiom
   the context task used for =pq_slot=.
3. =pq/statement.hpp= and =pq/transaction.hpp= reach the header through
   =pq/codec.hpp=, which includes it for =result=. =result= is the one
   type in =connection.hpp= that the statement layer uses in full: a
   =PGresult= handle with six declared accessors. =class result= moves
   to =pq/result.hpp=, so the statement layer takes the type it uses and
   not the connection, its closer or =check()=.

=pq/connection_fwd.hpp= carries =class connection;= for =pq/pool.hpp=
and =pq/transaction.hpp=, which name it in a =unique_ptr= member and a
reference member and never touch it. The tree already has this shape in
=domain/context_fwd.hpp=, and the forward-declaration check reads it.

What this does not claim: the objects that read =connection.hpp= today
read =result.hpp= tomorrow, and there are as many of them. The saving is
that the header which changes — the libpq wrapper, its prepared-statement
bookkeeping and its reset — rebuilds eight objects instead of five
hundred, and that the header which does not change, =result.hpp=, is the
one five hundred objects depend on. The one cut that removes objects
outright is path 1, because every service header that holds database
options stops reaching the pq layer at all.

=pq/unit_of_work.hpp= keeps its two definition includes. It is still the
forward-declaration check's one offender, and it needs the header split
its own task carries; this task does not move it.

* Notes

The analysis named two paths into =pq/connection.hpp=, the pool and the
statement layer. There were four. The two it did not name are the ones that
mattered:

- =domain/database_options.hpp=, which every service's =app/application.hpp=
  and =config/options.hpp= include, still included the connection header for
  =pq::connection_options=. That type moved to =pq/options.hpp= in the context
  task; the include was a leftover, and the archetype emitted it from the
  model.
- =service/postgres_listener_service.hpp=, which =ores.eventing.core= includes
  through =postgres_event_source.hpp=. Because every service includes the
  eventing core, this one header held 101 objects. It was cut the same day the
  other three were, because without it the task's own claim — that the
  connection header stops reaching the tree — would have been false: 101
  objects would still have rebuilt whenever a connection changed.

Nothing here lowers the count for the pq family itself: =pool.hpp=,
=codec.hpp=, =statement.hpp= and =transaction.hpp= each still reach 185
objects, because the unit of work and the repositories include them. That is
the next task's work, the split of the unit of work header.

=connection.hpp= now reaches 2 objects: the database library's unity object,
which compiles =connection.cpp=, =pool.cpp=, =transaction.cpp= and the
listener, and the database test binary that connects to a real server. Both
are places that open a connection.

* Where this departs from the analysis

The analysis's decision table says *Keep* for =connection= and =result=, and
for =pq/codec.hpp= and =pq/statement.hpp=: "each has one includer that only
names it, and both need libpq to name PGconn, so they stay in this header".
The measurement disagrees on the second half. The statement layer does not
only name a result: =read_rows= calls =r.rows()= and =read<T>= calls
=r.value()=, so it uses the type in full. A forward declaration cannot cut
that edge, and splitting the header is the only cut that leaves the
statement layer with what it uses and the connection header with the
=PGconn= half. The analysis was right that libpq stays under 185 objects
either way; what it missed is that =connection.hpp= and =result.hpp= have
very different change rates, and that 94 objects were reaching libpq through
=database_options.hpp= and the listener with no need for either.

The story's acceptance asks for the rebuild time after the header is
touched, before and after, at named commits. This task records reach
instead: the same 930 objects, the same compiler and the same flags, so the
number of objects that rebuild is what the reach number says. Timing a touch
would take two full builds of about two and a half hours each and would
measure the machine more than the change, which is the same trade the
forward-declaration tasks in this arc made.

The local gate fails eight checks and none of them is this change:
=xml-benchmark-recorded=, =route-inventory=, =ore-parameters-seed=,
=ore-parameter-value-sets=, =parameter-value-sets-only=,
=convention-kind-terms=, =ore-element-map= and =conventions-dataset=. Each was
run in a worktree at this branch's base commit =735c13adfe=, with this branch
absent, and each fails there too. They are main's generated artefacts drifting
behind main's models, and they are left to whoever owns those generators.
=cmake-sources= failed earlier in the same run for a reason that was this
task's: the two new headers belong in =component_files.cmake='s HEADERS set.
It is regenerated into the change and passes now.

* Result

Four headers stopped including the connection header: the database options
model, the pool, the statement layer's codec, and the Postgres listener
service. =class result= is its own header, so the statement layer takes the one
type it uses in full. The pool and the listener take a forward declaration,
and =~pool()= moves out of line where a connection is complete; the listener's
destructor was already there. The transaction names a connection in a
reference member.

On the built tree =pq/connection.hpp= goes from 279 objects to 2 and
=libpq-fe.h= from 279 to 185, with 94 objects that stop reading libpq-fe.h.
