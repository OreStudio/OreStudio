This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A system administrator reads the tenants a deployment holds: their code, name, hostname, type and status.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want to know what tenants this deployment holds." The system administrator
reads one screen and gets one row per tenant. The journey is done when every
row answers five questions: what code names the tenant, what name it shows, what
hostname serves it, what type it is, and whether it is in service.

* Actor and trigger

The system administrator: an account that holds the =SuperAdmin= role and acts
from the system tenant. The shell calls this context *system administration
mode*: the session's tenant is the system tenant, so every request it sends is
scoped to the deployment and not to a customer. A tenant administrator is
signed in inside their own tenant, and the shell offers them no *Tenants* area,
so they cannot reach this screen.

The trigger is a question about the deployment: which tenants exist, or which
one to act on next. The administrator opens the *Tenants* area in the system
administration context, and the journey ends when they have read what they came
for.

This journey writes nothing. The roster is now its own journey, and
[[id:00179132-3463-45E9-A6FC-75B0F3EBCC8E][Retire or reset a tenant]] picks
its tenant from it, so the destructive journey no longer has to be opened to
find out what exists.

* Steps

1. *Open the roster.* The administrator opens the *Tenants* area in the system
   administration context. The system shows one screen: a read-only table with
   one row per tenant. The administrator expects to find every tenant the
   deployment holds.
2. *Read the tenants.* The system lists the tenants and gives each row five
   columns. The code is the tenant's stable name in a request. The name is what
   a person reads. The hostname is the address that routes to the tenant. The
   type is the kind of tenant it is. The status is its place in the lifecycle.
   The type and the status are painted with the badge their rows name, and the
   words are the rows' own.
3. *An installation with none.* The deployment is provisioned but holds no
   tenant of its own yet. This is the state right after the system
   administrator is created. The roster answers an empty table and says that no
   tenant exists, rather than showing a failure. The way out is
   [[id:4C062ECC-D6D4-4BA4-8F96-10E141663D9C][New tenant]].
4. *A tenant that is not active.* The status column reads one of four codes.
   =bootstrapping= means the provisioning has not finished. =active= means the
   tenant is in service. =suspended= means sign-in is refused. =terminated=
   means the data is still there and the tenant is unusable. The roster states
   the status; it does not act on it.
5. *Find one among many.* The administrator pages through the roster with the
   offset and the page size, and reads the total. A search field narrows the
   roster over the code, the name and the hostname, so a large deployment does
   not need many pages of reading. Two filters keep one tenant type and one
   status, from the deployment's own type and status rows.
6. *Leave test tenants out.* Tenants of the type =automation= are test
   infrastructure: the type table describes them so, and the test fixtures
   write them. The roster hides them by default and says how many it hid; a
   *Show test tenants* toggle shows them, and asking for that type by name shows
   them too. The server leaves them out, so the page and its total agree.
7. *Leave, or go on.* The administrator leaves the roster, or picks a tenant
   and goes on to another operation on it: retiring or resetting it, or adding
   a party to it. The roster carries the chosen row into that operation.

The roster does not show the system tenant. The tenant registry is
system-scoped: the table's own check requires every row to carry the system
tenant in =tenant_id=, so that column names the owner of the registry and never
the tenant a row describes. A row's identity is its =id=, and the deployment's
own bookkeeping is the row whose =id= is
=ffffffff-ffff-ffff-ffff-ffffffffffff=. That row is not a tenant somebody set
up, so the roster leaves it out. A reader who filters on =tenant_id= instead of
=id= asks the wrong question and gets an empty list for a deployment full of
tenants. The rule is the one
=projects/ores.iam/core/include/ores.iam.core/service/tenant_presence.hpp=
states in =has_tenant_of_its_own()=.

One screen. The roster table, the search field, the paging controls and the
empty state are panels of that screen, because the administrator reads them as
one answer. The screen is read-only: it creates nothing, changes nothing and
destroys nothing.

* Entities composed

#+ATTR_HTML: :class hug-leading
| Entity | What it contributes | Model |
|--------+---------------------+-------|
| =tenant= | Code, name, hostname, type and status, read-only here; the row's identity is its =id= | [[id:11ED9447-461D-4074-9663-E83190BA7371][ores.iam.tenant]] |
| =tenant_type= | The codes that classify tenants | [[id:0B64E03F-1EDE-43E9-BEDA-96CDF9822B3F][ores.iam.tenant_type]] |
| =tenant_status= | The four lifecycle codes the status column reads | [[id:22C2020E-E745-4D7B-B2BF-C17659DFCE6E][ores.iam.tenant_status]] |

The row the server returns carries more than the five columns. It also carries
=version=, =id=, =description=, =is_registration_default=, =modified_by=,
=performed_by=, =change_reason_code=, =change_commentary= and =recorded_at=.
The roster shows five of them and drops the audit columns, because a roster
names each tenant and says what state it is in, and nothing on it is about who
last edited the row.

* Operations and messages

#+ATTR_HTML: :class hug-leading
| Step | Operation | Subject | Status |
|------+-----------+---------+--------|
| Open the roster | List the tenants the deployment holds | =iam.v1.tenants.search= | exists |
| Read the tenants | Read the row's code, name, hostname, type and status | carried by =iam.v1.tenants.search= | exists |
| An installation with none | Answer an empty page | carried by =iam.v1.tenants.search= | exists |
| A tenant that is not active | Read the lifecycle status | carried by =iam.v1.tenants.search= | exists |
| Find one among many | Page, search and filter the roster | =iam.v1.tenants.search= | exists |
| Leave test tenants out | Hide the automation type unless asked | =iam.v1.tenants.search= | exists |
| Leave, or go on | Read the chosen tenant for the next operation | =iam.v1.tenants.get= | exists |

=iam.v1.tenants.search= is declared in the operation model
=ores.iam.tenant_roster_messages=, requires a session and checks
=iam::tenants:read=. Its request carries a search, a type filter, a status
filter, a type to leave out, an offset and a limit; its response carries one
page of tenants and the total that match. The system tenant is never in the
answer.

The browser reads it through the BFF route =GET /api/tenants=, which hides the
automation type unless asked and reports how many tenants that hid, and the
type and status rows through =GET /api/tenant-types= and
=GET /api/tenant-statuses=.
=iam.v1.tenants.get= is the read the next operation uses to take up the tenant
the roster chose.

* What is missing

1. *Closed: search, filters and paging.* =iam.v1.tenants.search= searches the
   code, the name and the hostname, filters by type and status, leaves a type
   out, pages and counts every match
   ([[id:4A15EFC1-447A-4573-9BF1-5B9E69A9C7D7][Search and page the tenant roster]],
   [[id:49E680DA-EC29-42A7-89BD-0D40481539A5][Filter the tenant roster by type and status]]).
2. *Closed: the system tenant is left out by the server.* The search function
   leaves it out beside the registry, so a caller of the search cannot see it
   and the BFF no longer corrects the page. The generic list subject still
   answers it.
3. *The generic list read checks no permission.* The search checks
   =iam::tenants:read=; =iam.v1.tenants.list= still checks none, so the BFF's
   refusal of a session outside system administration remains the boundary for
   that subject.
4. *The roster cannot show the tenant's administrator.* The tenant row carries
   no administrator, and no read joins a tenant to the account that runs it.
   So "who runs this tenant" is not answerable from the roster, and a review
   has to open each tenant in turn. The candidate is an administrator column on
   the row, or a joined read.
5. *Nothing reaches the system tenant row.* The roster excludes the system
   tenant by design, and no other screen offers it, so the deployment's own row
   cannot be read from the web at all. That is intended for a roster of the
   tenants somebody set up. The open question is whether the system tenant
   should be readable anywhere, for example to confirm its status, given that
   the generic delete path can still terminate it. See
   [[id:00179132-3463-45E9-A6FC-75B0F3EBCC8E][Retire or reset a tenant]].
