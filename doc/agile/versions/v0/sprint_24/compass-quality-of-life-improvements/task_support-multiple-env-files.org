#+title: Task: Support multiple named .env files, e.g. per remote host
#+description: Every compass command that needs environment or DB config (db recreate, services start, etc.) reads a single hardcoded .env at the repo root, with no way to point at a different target. Surfaced while deploying the containerized service runtime to Newton: compass db recreate had to be run against Newton's Postgres by temporarily editing the repo's own .env in place (ORES_DB_HOST, PGPORT), then restoring it afterward -- fragile and easy to forget to revert. Add support for named environment files, e.g. .env.newton alongside the default .env, and a way to select one per invocation (an --env-file flag or similar), so targeting a remote host's DB or services never requires mutating the working .env.

* Goal

Let compass commands that read environment/DB config (~db recreate~,
~services start/stop~, ~nats init~, etc.) target a named environment
file other than the repo-root ~.env~, e.g. ~.env.newton~ for a remote
deploy host. Today every one of these hardcodes ~project_root / ".env"~
(~compass_db.py load_env()~ and equivalents elsewhere), so the only way
to point at a different Postgres/NATS/host is to edit the working
~.env~ in place and remember to revert it -- exactly what this
session's Newton deploy-and-verify task had to do by hand.

* Acceptance

- Environment-reading compass commands accept a way to select a named
  env file (e.g. ~--env-file .env.newton~ or ~--env newton~ resolving
  to ~.env.newton~), defaulting to the current ~.env~ when omitted --
  fully backwards compatible.
- At minimum ~compass db recreate~ and ~compass services
  start/stop/status~ support it, since those are the two operations
  this session needed against Newton.
- Documented via a recipe under ~doc/recipes/~.
- The working ~.env~ is never mutated as a side effect of targeting a
  different host.
