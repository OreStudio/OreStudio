* Acceptance

- ores.http gains a dq part that answers the reads the coverage screen needs: datasets, dataset bundles, bundle members by bundle code, and artefact types.
- One web API module, api/dq.ts, sends every call to ores.http.
- A route test on the generated part proves each read answers, and the module's unit test proves the screen reads what the route returns.

* Plan

1. Scaffold =projects/ores.http/dq= by copying a part of the same shape, and add
   it to the http tree's CMake.
2. Turn on =:ores.cpp.http-route.enabled: true= on the DQ models the screens read:
   =ores.dq.dataset=, =ores.dq.dataset_bundle=,
   =ores.dq.dataset_bundle_member_junction=, =ores.dq.artefact_type=.
3. Generate, and check the part renders into =projects/ores.http/dq/= with a test.
4. Register the part's aggregate in the server's application, and build.
5. Add =api/dq.ts= to ores.web with the reads typed, and a unit test.

The BFF is not in the plan: it is being decommissioned.

* Notes

The C++ server has HTTP parts for analytics, assets, compute, core, iam,
marketdata, refdata, reporting, synthetic, trading and workflow, and none for
dq: the reads the screens need are served by nobody.

The BFF is deliberately not served, because it is being decommissioned. Writing
a route there would be work for a component on its way out; the screens are
built against =ores.http=.

Most of the route code is generated: a DQ entity model that opts into
=:ores.cpp.http-route.enabled: true= renders its route header, implementation and
tests into =projects/ores.http/dq/=, so this task is the part's scaffold, the
facet on the right models, the aggregate registration and the build.
