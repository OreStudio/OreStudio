This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A system administrator sees whether each public provider's fixings are arriving, accepts or declines its terms, pauses or resumes it, asks for a backfill, and reads where each synthetic feed started.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want to know whether the rates we use are actually arriving, and to do
something about it when they are not — accept a publisher's terms, pause one
that costs too much, fetch a range we missed — without asking someone to run a
command." The journey is done when the person has read the state of every
public provider, has acted on each one that needed it, and knows which feeds
started from which published value.

* Actor and trigger

The actor is the system administrator, because every public provider is system
data and a person accepts its terms on the system's behalf. Reading the
providers and the fixings needs =marketdata::providers:read= and
=marketdata::market_fixings:read=. Accepting or declining terms needs
=marketdata::providers:accept_terms=. Pausing, resuming and starting a backfill
need a permission the server does not define yet, and deleting a provider's
fixings needs a delete permission the server does not define yet.

The trigger is one of four events. A publisher's terms change, and the person
must accept them again or stop using its data. A fixing a desk needs is late,
and the person looks for the cause. A pair or a provider is new, and the person
checks that its data arrives before anyone builds on it. A bill or a coverage
review says a provider is not worth its cost, and the person pauses it.

The journey starts at *Market data*, then *Public rates*, and ends when the
person leaves the screen. A person who came from a synthetic feed's page
returns there, because that page carries the value a run started from.

* Steps

The screen is the record screen shape of the [[id:2BF7F03F-6BF4-45FF-8E26-4D3B4E2D943D][Record screen standard]]: a list of
providers, one provider's page with its fixings, and a pair comparison. This
journey adds the operational facts the screen already has data for and the two
acts the architecture can carry.

1. *Read the providers.* The person opens *Market data* and then *Official
   rates*. The system lists every public provider that has terms: its name, the
   kind of source it is, whether its terms are accepted at the version shown,
   the items it serves, and its freshness. The route that reaches it, Frankfurter
   or later another, is on the adapter's health, not on the row.
2. *Read the freshness.* For each provider the row states the last fixing's
   date, the time it was received, and whether the next expected publication is
   late. A provider that has never had a fixing says so in words rather than
   showing a blank cell.
3. *Tell the three failures apart.* An adapter that is not serving, a provider
   whose next publication is late, and a provider that has never had a fixing
   read as three different states, each with the sentence that says what to do.
   The adapter's state, heartbeat and the ids it refuses come from the adapter
   status read the marketdata service already answers.
4. *Accept or decline terms.* The person opens a provider whose terms are not
   accepted, reads the terms page and the credit it asks for, and accepts them
   at the version shown or declines. The service refuses an acceptance of a
   version that changed since the person read it, and the screen reloads and
   says so. The service fetches a provider only after someone accepts its terms.
5. *Read a provider's fixings.* The person opens the provider and reads its
   series as a table and a chart over a window, one item at a time. Each value
   keeps the publisher's own id of the item and the time it was received.
6. *Compare a pair.* The person compares one pair across every provider, as
   published, inverted, or crossed through the provider's base, and the screen
   names the route of each value.
7. *Pause and resume.* The person pauses a provider that is not worth its cost,
   and the system stops demanding its items. The fixings the provider already
   published stay, and a feed that started from one keeps its start. Resume
   restores the demand. Each act is audited with an actor and a reason.
8. *Force a fetch.* The person opens the Fetch tab, picks today, yesterday or a
   range, all providers or one, one pair or every pair, and asks for it. The
   service asks the adapters for exactly that, and the screen says the fetch is
   running and names the days it has fetched. A range that overlaps what the
   store holds adds nothing, because the store skips a fixing it already has.
9. *Delete the fixings of a provider whose terms withdrew storage.* When a new
   terms version withdraws permission to store, the person deletes that
   provider's fixings. The deletion records who did it and when, and the screen
   says which feeds started from a value that is now gone.
10. *See where a feed started.* From a synthetic feed's page the person reads
    the provider, the item, the value as published and the time it was received
    of the fixing the run started from. The screen links back to this one.
11. *See who changed it.* The person opens the provider's history: terms
    acceptances and declines, pauses and resumes, backfills and deletions, each
    with its actor and its reason.
12. *Read the availability of one underlying.* The person opens the Availability
    tab and picks a pair. The system lists each publisher that fixes the pair,
    with the first and last date it holds, the count, and the gaps. A publisher
    whose terms are not accepted shows as a row with no data and the reason.
13. *Compare the publishers.* The person opens the Compare tab for the same
    pair. The system draws each publisher's fixing over the window on one axis,
    the difference of each against the others in basis points, and the largest
    disagreement. It names the publisher whose value is furthest from the rest.
14. *Read one publisher's history for one underlying.* The person opens the
    publisher and picks the pair. The system shows the fixings over the window,
    the corrections, the days with no value, and the synthetic feeds that started
    from a value, with the value each took.
15. *Read a provider's configuration.* The person opens the provider's record
    page. The Details tab shows its name, kind, terms page, credit, credential
    reference and whether storage is allowed. The History tab is the shared
    timeline: every version and every acceptance, with the person and the time.
16. *Leave.* The person returns to *Market data*.

* The screen is five surfaces, not one

The review of this journey and the prototype it produced made one thing clear:
the screen carries several jobs, and each deserves its own surface. A person
moves between them without losing the provider they were reading.

#+ATTR_HTML: :class hug-leading
| Surface | The question it answers | Where it sits |
|---------+-------------------------+---------------|
| Providers | Which publishers are there, what are their terms, and is their data arriving? | The Public rates list, the home of the journey |
| Publisher | What did this one publisher publish for this pair, over time, and where did a feed start from it? | A provider's page |
| Availability | For one underlying, what does each publisher hold, and what gaps does it have? | A tab, read by underlying first |
| Compare | For one underlying, how far apart are the publishers' values, and which one is off? | A tab, read by underlying first |
| Fetch | Ask for data now: a day or a range, one publisher or all, one pair or every pair | A tab, the only place a person starts a fetch |
| Configuration | What does this publisher's record say, and who changed it? | The provider's record page, Details and History |

The hierarchy the words must follow is three levels deep. An *access route* is
how the platform reaches a publisher, such as Frankfurter. A *publisher* is the
central bank or public body whose terms apply, such as the ECB. An *item*, or
underlying, is one pair from one publisher, such as =FX-ECB-EUR-CAD=. The
provider entity is the publisher, and Frankfurter is a route, not a provider; the
screen groups publishers by route only to show the adapter's health.

The schedule is not this screen's. The platform's scheduler runs a job that asks
the adapters to refresh on each publisher's publication rhythm. The Fetch tab
sends the same request on demand, so one request serves the schedule and the
person, and the screen owns neither the poll nor the interval.

publisher over time, availability across publishers for one underlying, the
compare view with the distance between them, the fetch scope and its progress,
and a provider's configuration with its history. It is a static page: no build,
no server, no session.

* What is missing

- *Pause and resume a provider.* The download follows demand, so the act is
  either a demand change or a new provider state. The decision is
  [[id:EFAC2D06-56C6-41FD-856E-2B2AB415A947][Decide how a provider is
  paused]]. Until it exists the screen states that a provider is fetched
  because the system party subscribes to it, and names the subscription.
- *A fetch on demand and on a schedule.* The adapter contract carries announce,
  demand, tick and heartbeat, and no fetch request. One request must serve the
  scheduler's job and the screen's Fetch tab, and the design is
  [[id:B9BCE538-9616-4C0F-A56F-BBE981CB2043][Design the refresh request the
  scheduler and the screen share]]. Until it exists the screen offers only the
  window the service fetches on its own.
- *Deleting a provider's fixings.* The durable table is never deleted today,
  because the terms in force when a value was stored keep it. A terms version
  that withdraws storage needs an act with an actor, which
  [[id:EFAC2D06-56C6-41FD-856E-2B2AB415A947][Decide how a provider is
  paused]] carries alongside the pause.
- *Freshness in one read.* The fixings read answers one item at a time, so the
  screen reads the latest fixing of every item a provider serves. A single read
  that answers the last fixing of each series would make the row cheap; until
  then the screen reads the provider's best item and says which one it read.
  The row and the three states are
  [[id:3003F16C-C239-4C5C-A36A-29A2D376EEE1][Show each provider's freshness
  and its adapter's health]].
