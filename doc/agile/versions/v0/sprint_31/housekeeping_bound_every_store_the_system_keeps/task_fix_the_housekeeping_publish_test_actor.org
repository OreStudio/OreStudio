* Analysis

[[id:A71D89B6-2A44-4826-BF30-25E6E3AF631E][Deliver housekeeping as platform data]]
introduced the test with two inserts that wrote =modified_by = 'system'=, as a
stand-in for the person who restates a policy's period or a job's schedule.

The store accepts any actor until the installation holds a person: the validator
allows any name while the current tenant has no account of a type other than
=service=, and after that it demands a username the accounts table holds, in any
tenant. A freshly created database holds service accounts and no person, so the
suite passed where it was written and fails where the corpus is provisioned and
somebody has signed up.

The fixture now takes its actor from the accounts table, with the bootstrap case
as the fallback, so the suite reads the same in both states.

* Result

The housekeeping publish test now runs on a provisioned installation. The
fixture takes the person who restates a policy's period and a job's schedule
from =ores_iam_accounts_tbl=, and keeps ='system'= only as the bootstrap-state
fallback, so the same fifteen assertions pass whether or not the installation
holds a person.

Proved in both states: 15 of 15 on a database that holds only service accounts,
and 15 of 15 after one account of type =user= was added to the system tenant,
where the test failed at line 106 with "planned 15 tests but ran 1" before the
change. No schema, model or code changed; the store's actor rule is untouched.
