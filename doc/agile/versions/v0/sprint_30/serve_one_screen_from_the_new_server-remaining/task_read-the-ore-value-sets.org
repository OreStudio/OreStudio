* Goal

The gateway has no reader of the ORE value sets. Add the C++ form of the BFF's
=readValueSets=, and serve the one route that needs nothing else:
=GET /api/reporting/engine-settings/documentation=. The route states, for each
group of settings, what each setting means and which values it accepts, so a
person editing a document reads the engine's own answer and not a second
statement of it.

* Plan

Branch =feature/serve-the-ore-value-sets=.

The reader goes in =projects/ores.http/core/=, under =routes/=, beside
=history_routes= and =change_routes=. The reporting part and the reference data
part both read value sets, and the reporting part already links
=ores.refdata.api=, so a reader in the reporting part would close a cycle
between two part libraries.

The reader answers the same seven fields the BFF's does: the set's code, its
kind, the catalogue it draws on, its choices, its minimum, its maximum and its
pattern. It takes the four tables as the service returned them, so it needs no
entity type from the reporting part and the shared part gains no new link. It
answers a fixed list of catalogue relations, and a set that names another one is
a seed error that is refused rather than drawn empty.

The documentation route is the reader's first consumer and its proof. It joins
three reads: the groups of settings, the settings of each group, and the
=ore.xsd= / =Setup= parameters. It states each setting's documentation from the
parameter and its fields from the value set. It lives in the reporting part, in
an =engine_settings_rows= unit that the reads task extends.

* Notes

** The reader's home

The design note and this task's predecessor said the value set reader lives in
the reporting part. It does not. The reference data part answers convention and
curve routes and reads value sets too, and the reporting part already links
=ores.refdata.api=, so a reader in the reporting part would close a cycle
between two part libraries. The reader is at
=projects/ores.http/core/include/ores.http.core/routes/ore_value_sets.hpp=.

The reader takes the four tables as rows, so the shared part gains no link to
the reporting part. The catalogue relations are the caller's: a relation names a
view in another component, so the part that serves a screen states which
relations it reads. The reporting part reads the three the value set data names
(tenors, currencies and sensitivity templates) and refuses any other with a
sentence that names it.

** The routes the earlier families left unpaired

The three families before this one added their routes to the inventory but never
added them to =build/scripts/route_pairing.py=, which is the table the coverage
is counted from. The coverage table therefore stated 9 of 44 reporting routes
paired where 26 were served. This task adds those seventeen pairs, so the
coverage is now counted and not claimed.

** A seed this build cannot read

The BFF threw from the handler, and the browser read a 500 with the sentence.
The gateway does the same: the reader raises =value_set_error= and the route
refuses with 500 and the reader's sentence. Every other failure keeps the
house answer, which logs the detail and tells the browser the service could not
answer.

** The relation the page does not need

The documentation page reads the =Setup= scope, whose settings name no catalogue
relation. The reader still resolves the relations the data names, because a set
that names one must not be drawn as an empty list; a relation is read only when
a setting that draws on it is asked for.

* Result

The gateway reads the ORE value sets and answers
=GET /api/reporting/engine-settings/documentation= at the BFF's path, in the
BFF's shape.

- The reader is in =ores.http.core=, and the reporting and reference data parts
  both reach it. It answers the same seven fields the BFF's does.
- The documentation page answers the groups the data states, each setting's
  documentation from the =ore.xsd= / =Setup= parameters, and its allowed values
  from the value set of its ORE parameter. Nothing is derived that a service
  states.
- A set whose kind this build does not know is a 500 that names the set and the
  word, as the BFF's own throw was, and not a control that checks nothing.
- The seventeen routes the three earlier families served but never paired are
  paired. The coverage table states 27 of 44 reporting routes where it stated 9.
- The reader's eight cases and the route's two cases pass. The gateway core's
  suite is 100 cases and 100590 assertions; the reporting part's is 44 cases and
  447 assertions.
- The gate is 45 of 45.
