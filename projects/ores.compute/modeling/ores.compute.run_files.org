#+title: ores.compute.run_files
#+description: Codegen operation model for the files one report run holds: the run's batch, its workunits and the packages each of them read and wrote.
#+type: ores.codegen.operation
#+component: compute
#+subcomponent: api
#+entity_singular: run_files
#+namespace: ores::compute::messaging
#+brief: The files of a compute batch.
#+filetags: :model:operation:compute:
#+created: 2026-11-13
#+updated: 2026-11-13

A screen that shows a run's files asks a question whose answer is spread
over four of this service's own rows: the batch, its workunits, each
workunit's input package, and each workunit's accepted result with the
package that result wrote. Every link but the first is a row here, and the
batch states the run in its external reference, so the join belongs in this
service and not in its callers.

The read states what an archive *is*, not what it holds. The bytes of a
package are the storage service's, and so is the walk through them, so each
archive travels as its object path and its packed size. A caller that wants
the files inside asks storage, in one call, for every key this reply names.

There is no page: a run has as many workunits as a report has parts, and a
listing that could stop in the middle would draw half a tree.
