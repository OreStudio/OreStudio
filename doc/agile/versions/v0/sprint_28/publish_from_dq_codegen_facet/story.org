This page documents a [[id:699A8D45-B67E-4D3E-9206-24FA17C51ADA][story]] in [[id:3CEE598D-47C8-4EC0-9E01-19CE79CCA4CD][Sprint 28]]. It captures the goal, current status, acceptance criteria, and the tasks that compose it.

* Goal

Generate the mechanical part of the DQ publish-from-dq pattern from the
entity's own codegen model, and stop hand-writing it. The pattern is the
=SECURITY DEFINER= =ores_<component>_publish_<plural>_from_dq_fn= that reads
an artefact table and writes the owning service's tables.
[[id:F19A6B98-1CAD-4206-913B-A4EAAED2DEAF][DQ artefacts]] states its contract;
[[id:F05B779F-769B-49D5-B369-D2AAC029B36D][DQ Bundle Publication Pipeline]] has
the end-to-end walkthrough and the codegen value assessment this story acts on.

The scope is narrower than this story first claimed. The measurements below are
the reason, and two things follow from them:

- *Generate the functions that are genuinely the same.* About 29 of the 57 are
  one plain per-row upsert into one target table, honouring =mode=, matched on
  the entity's natural key. That family is a template.
- *Do not generate the handlers.* The eight =publish_from_dq_handler= files are
  already one generic handler per service, not one per entity. Fifty-seven
  generated handlers would be fifty-seven copies of something that is not
  copied. They should be unified instead.

* Acceptance

- The declaration unit is decided and recorded, and it expresses the real
  relation: 122 models opt into an artefact table and 57 functions publish
  them, so one function covers many artefact tables.
- Enabling the facet on an entity model generates its publish function for the
  plain one-table per-row upsert family, with no hand-written SQL beyond the
  declaration.
- Regenerating one existing hand-written instance produces a semantic zero-diff
  against the hand-written version, which is then deleted. Use =asset_classes=
  or =countries=; =report_definitions= is a helper-delegating set-based
  document and is the wrong first instance.
- The functions that do not fit the family are named and recorded as
  deliberately hand-written, with the reason, so the facet's boundary is a
  statement rather than an omission.
- The eight =publish_from_dq_handler= files are unified, or the reason they
  cannot be is recorded. Generating 57 handlers is explicitly not the answer.
- =dq_artefact_types_populate.sql=, =entity_table_writes_baseline.json= and the
  pgTAP publish tests are updated for whatever moves.

* Decisions

- *The declaration unit is not decided, and it is the first task.* A publish
  function does not correspond to one entity: =curve_configuration= publishes
  31 artefact tables and analytics' today's market publishes 5, while 122
  models opt into staging. The facet has to express "these artefact tables are
  published together by this function" before anything else can be cut.
- *The C++ half is unification, not generation.* =subject_to_fn= is already
  generic in every handler, and synthetic's validates against an allow-list.
  What differs is the subject spelling and the allow-list, not the handler.
- *This story no longer retires the =lookup_entity= shadow models.* The DQ
  artefact migration already did: no =#+type: ores.codegen.lookup_entity= model
  is left, and the =sql_schema_artefact_create= template is deleted.
- *The =model_type == 'schema'= enrichment bug is moot.* It was raised as a
  prerequisite for rendering from a =lookup_entity= model. That path is gone.
- *Subject constants are partly modelled already.* =ores.codegen.operation=
  renders C++ protocol from =ores.analytics.publish_operations.org=,
  =ores.iam.account_messages.org= and =ores.reporting.operations.org=; refdata,
  assets, dq and marketdata still hand-spell subjects in =registrar.cpp=. A
  facet should use the operation models where they exist rather than add a
  fourth way to name a subject.

* Out of scope

- The artefact table itself. That half is done
  ([[id:5B8F3C2A-6E1D-4A9F-8C3B-1D7A9E2F4B6C][ores.sql.schema.domain_entity_artefact_create]]).
- The bundle and dataset registration rows, which are one-liners.
- The ~28 functions that are genuinely bespoke: helper-delegating documents,
  multi-table publishes, and party-scoped publishes with their own =p_params=
  contract.
