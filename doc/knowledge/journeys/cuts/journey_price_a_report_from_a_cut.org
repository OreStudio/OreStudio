This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A market-risk owner binds the run settings to a cut, picks it by kind and timepoint with its state, is refused a cut that is not authorised, and runs the report, whose record names the cut it priced from and whether it reproduced.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

The decision behind it is
[[id:F6362451-D569-4609-97A3-F1C785AAAF02][The cut is the body a run prices
from]], which supplies the second binding the
[[id:FB8F701C-E56A-49A9-AA90-1B6BD0B02092][report binding decision]] records as
missing: the binding names the curve, and the cut names the body. This journey is
the person's side of the second binding.

* Goal

"A report told me a number and I cannot say what body of data it priced from. I
want to say which cut this report prices from, see what the cut holds and who
signed it before I run anything, be refused plainly when the cut I picked cannot
be priced from, and have the run's own record name the cut — so that when somebody
asks me next year how the number was produced, I can rerun the same cut and get the
same answer."

The journey is done when the run's record names one cut, the cut is authorised,
and the run prices from that cut's body rather than from whatever the store holds
at the moment the run starts.

* Actor and trigger

A market-risk owner runs this journey, or a tenant administrator acting for the
party. Both act inside their own tenant, on a run settings configuration their
party owns, and bind a cut their party took.

The permissions are the ones the binding decision already names, with one added.
Reading and changing the run settings is
=reporting::configurations:read= and =reporting::configurations:write=. The picker
over cuts reads =reporting::cuts:read=. Running the report is
=reporting::report_instances:write=, through
=reporting.v1.ops.trigger_report_instance=. An action the person may not take is
not drawn, as the
[[id:2BF7F03F-6BF4-45FF-8E26-4D3B4E2D943D][Record screen standard]] requires.

The trigger is a result nobody can account for. A run completed, the report shows
a number, and the question is which deal population and which market data produced
it. The answer available today is a valuation date, and the store answers that date
differently a week later. The person opens the report, then the run settings
configuration it binds, and the journey ends on the run's page with the cut named.

This journey does not take a cut: that is
[[id:E840111E-AA2F-4746-8D49-A1D73742925E][Take a cut]]. It does not bind a
market role to a published curve, which is
[[id:3FCDF005-AE5B-42AF-A053-BFEBAEDAD6AD][Bind a report to a published curve]],
and it does not read what the run produced, which is
[[id:969C14D2-4280-4D7C-8F51-1D395B521C83][Read what a run produced]].

* Steps

** Step 1: reach the cut a report prices from

1. *Open the report and read what it prices from.* The report's page carries the
   *Market and pricing* tab, which the binding decision settles. Above the market
   roles the tab now names the cut the configuration prices from: its label, its
   kind, its timepoint, its state and its authoriser, with a link to the cut.
2. *Open the run settings configuration.* The cut is a row of that configuration,
   beside the market role bindings, because it is shared by every report bound to
   it exactly as the roles are. The tab that holds it is *The cut it prices from*,
   and the trail is Home, Reporting, Run settings, the configuration's name, then
   the tab.
3. *Read what the tab decides.* One sentence stands above the fields: it decides
   which fixed body each run of this configuration values; it does not decide which
   published set each market role resolves to, which is the *Market bindings* tab,
   nor the valuation date, which the cut fixes.

** Step 2: pick the cut

4. *Change the cut.* *Change* opens the picker over cuts, which is the record
   standard's =RecordPicker= applied to a cut: a search, a kind select, a state
   select, a table and a pager. It reads a read that does not exist yet, and the
   parties offered are the configuration's own.

   | Column | What it holds |
   |--------+---------------|
   | Cut | The derived label, monospace, and the scope under it |
   | Kind | The occasion |
   | Timepoint | The instant, exact, with its timezone |
   | State | Authorised, Superseded, Taken, Draft, Incomplete or Refused |
   | Taker | The account that took it |
   | Authoriser | The account that decided it, and a dash where nobody has |
   | Holdings | The deal count and the number of market data values the body fixed, right-aligned |
   | Runs | How many runs have priced from it, right-aligned |

5. *Pick the day's cut.* The person picks the row whose state is *Authorised*, and
   the dialog states what the configuration will name: the label, the kind, the
   timepoint, the scope, the counts of the body, the taker, the authoriser and the
   authorisation request. The authorisation is drawn as a fact and not as a link a
   report can move.
6. *Read the superseded cut, and why it is still offered.* A cut that a later one
   replaced is offered, drawn *Superseded*, with the sentence that says what that
   means: a rerun reproduces an earlier result from it, and a new run of a report
   should normally name the cut in use. The pinned-as-of rule the binding decision
   makes for an ended curve does not apply here, because a cut is a record of an
   instant and not a value in use.

** Step 3: the refusal, when the cut cannot be priced from

7. *A cut that is not authorised is refused.* The picker refuses it at the row and
   in the dialog's footer, and *Save* is not drawn while a refused row is selected.

   | The cut's state | What the screen says |
   |-----------------+---------------------|
   | Taken | That the body is fixed and nobody has signed it, that no run may price from it, and that the request waits on the named part. It names the account the request waits on |
   | Draft, or Incomplete | That the body is not fixed, or is not complete, and that the gaps are on the cut's page. It names the part each gap belongs to |
   | Refused | That the authorisation was refused, the reason, and that the remedy is a new take rather than a second decision |
   | A cut of another scope or another party | That a run of this configuration values this party's books, so another body cannot be named |

8. *Read the flash cut's indicative mark.* A flash cut is offered while its
   authorisation reads pending, because its occasion precedes the authorisation,
   and the row says *Indicative* in the same column as *Authorised* says
   *Authorised*. A configuration bound to one is drawn with the mark wherever the
   cut is named, and every result it prices is marked indicative.
9. *Read the refused run.* A run asked for while the configuration names a cut that
   is not consumable does not start. It is refused before the engine is reached, in
   the words the tab uses, and the run's output message carries the same sentence,
   so a scheduled run nobody watched still says why it did not price.

** Step 4: run the report, and read what the run priced from

10. *Run the report.* *Run now* on the report's page is
    [[id:76431668-8656-4276-9F9B-F292FE45B2CA][Run a report and watch it
    finish]]'s press. The dialog names the cut before the press: the label, the
    kind, the timepoint, the authoriser and the counts of the body.
11. *Let the run read the cut.* The gathering steps read the cut's body instead of
    the store's current state. The deal step reads the population the cut fixed, and
    the market data step reads the fixed snapshot the cut names, refusing a cut that
    is not consumable in the same sentence the screen uses. A run that reads a cut
    reads one body and not two halves at two instants.
12. *Read the run's card.* The run's page gains one card: *The cut it priced from*.
    It names the label, the kind, the timepoint, the scope, the taker, the
    authoriser and the authorisation instant, the deal count, the market data values
    read, the engine version and the publish record of each market role in the
    body. It is read from the run and not from the configuration, because the
    configuration can move after the run.

** Step 5: read whether the run reproduced

13. *Read the reproduction state.* The run's card carries one of three verdicts,
    and the verdict is the answer to the question the cut exists for.

    | Verdict | What holds | What the card says |
    |---------+------------+-------------------|
    | Reproduced | The same cut and the same engine version as the run it is compared with, and every figure equal | That the two runs are one result computed twice, and the instant of each |
    | Differs | The same cut, and one or more figures differ | That the body and the engine are the same and the result moved, which is a defect in the engine or in the code. It names the first figure that differs and both values |
    | Cannot be compared | The engine version differs, a part of the body is unavailable, or the run priced from a body that was retaken | That the two runs are not one result computed twice, and which of the three reasons holds |

14. *Read what makes reproduction impossible.* The third verdict is the one a
    person must act on, so the card names the reason: a run whose engine version
    differs says which versions and that the software is not the same software; a
    cut whose fixed snapshot can no longer be read says which series is gone, which
    means the body was recorded and one of its parts is not served; and a comparison
    across a retake names the two cuts, because a retaken body is a different body.

** The audit of the consumption**

15. *Read the cut's consumers.* The cut's *Runs* tab lists every run that priced
    from it, newest first, with its report, its instant, its engine version and its
    result. That is the question a person asks before a cut is superseded — *what
    still rests on this body?* — and it is the same fact the run states from its own
    side.
16. *Read the configuration's history.* The row that names the cut is a row of the
    configuration, so its versions merge into the configuration's *History* tab as
    the [[id:E69C008D-7092-4855-98EC-47A75F422F61][Configuration screen standard]]
    states it: the cut before and after, the account, the instant and the reason.

* Screens and wireframes

Three surfaces, and each is the binding decision's, extended by one object. The
*Market and pricing* tab of the report names the cut above the roles. The *cut it
prices from* tab of the run settings holds the choice, with the picker and the two
refusals. The run's page carries the card that names the cut and the verdict on
reproduction.

* Prototype

The [[file:../../prototypes/cuts/the-cut/][the cut prototype]] draws this
journey on two of its surfaces: the picker over cuts, and the run that names one.
Its [[file:../../prototypes/cuts/the-cut.org][design note]] records the
states and what is fake.

It must draw a configuration that names no cut, one that names an authorised cut,
one whose cut is a draft, one whose cut is taken and unauthorised, one whose cut
was refused, one that names the flash cut and is marked indicative, one that names
a superseded cut, a run refused before the engine, a run whose card names the cut,
and a rerun that reproduces and one that cannot be compared. Every value is a
fixture.

The write that names the cut is one row of the configuration, saved with the
document as a collection is saved. The run's reference to the cut is written by
the run and never by the screen, for the reason the binding decision gives: a run
names what it used, and the configuration may move afterwards.

* What is missing

1. *No cut exists to name.* Everything this journey draws waits on the entity the
   decision note describes. Until it exists the picker has nothing to pick and the
   card has nothing to name.
2. *The run records a date and not a body.* =record_run_pricing= carries =priced_at=
   and =price_note=, and it was built because the packaging step knows both dates.
   A cut is the answer that survives a correction to the store, and the run needs
   the field.
3. *The gathering steps re-read the store.* Neither step reads a fixed body, so a
   run of a cut would price from whatever the store holds when the step runs. The
   [[id:19630B5D-A163-42B5-B9C4-61A87BAE8F5F][Trade cut]] page states the defect
   in the population and the
   [[id:DD59B04C-DAD2-458C-B35E-3F6B0B3D6DC6][Market data cut]] page states it in
   the market data.
4. *No comparison of two runs exists.* The reproduction verdict is the point of the
   whole cluster, and nothing compares two runs' figures, so the card would state a
   verdict it cannot compute. The first slice can state only what it knows: the cut
   and the engine version, and whether the two agree.
5. *No picker over a filtered read.* As the binding decision found for published
   sets, the shared =RecordPicker= reads its whole kind once and draws no state. A
   cut is filtered on the server and carries a derived state, so the screen needs
   its own picker or the shared one needs a filtered form.
6. *No market card that reads through the cut.* The binding decision's card reads
   the publish record the run recorded. Read through a cut it reads the cut's
   market data half, and the two must not disagree: the run records the cut, and
   the card reads the sets from it.
7. *No route and no screen for reporting.* The report page, the run settings
   screen and its tabs still do not exist, so this journey's surfaces are new with
   the binding's.
8. *The indicative mark has no badge.* A flash cut's result is indicative, and no
   code domain holds the word. The badge seed needs it, or the screen draws the
   label the seed's rule gives for an unmapped code.
