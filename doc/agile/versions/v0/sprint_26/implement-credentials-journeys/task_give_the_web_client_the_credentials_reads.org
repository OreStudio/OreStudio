* Goal

Give the browser's own client the reads the three credentials screens make, over
the BFF routes that now serve them. The client is where the shapes a screen
renders are checked at the network boundary, so it is the link between the
routes and the screens rather than part of either.

* Acceptance

- The client answers the account page, one account, one login record, the
  login-record page, the session page and the active sessions.
- Each answer is parsed with the schema the browser and the wire share, so a
  shape the server stops sending is a failure at the boundary rather than a
  screen rendering nothing.
- An absent account and an absent login record are values, not failures.

* Result

Done 2026-10-01.

The browser's client can ask for the six credentials reads: the account page,
one account, one login record, the login-record page, the session page and the
active sessions. Each is parsed with the schema the browser and the wire share,
and an absent account or login record comes back as nothing rather than as a
failure, because both are states a screen shows.

Verification: 334 tests green in three packages (bff 97 in 20 files, web 186 in
17, wire-protocol 51 in 7), typecheck clean, Prettier clean. Nothing in this
slice decides anything on its own: the reads are the ones the routes already
answer, and the screens follow.
