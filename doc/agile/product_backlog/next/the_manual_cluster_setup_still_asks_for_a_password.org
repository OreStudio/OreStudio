#+title: The one-shot script that sets up a new cluster still asks for a service password
#+description: setup_user.sql guards every service on a password variable that format 39 removed, while recreate creates the role without one.

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

=projects/ores.sql/setup_user.sql= is the one-shot script that sets up a new
cluster by hand. It guards every service with an =\\if :{?x_service_password}=
check and creates each role with that value, and environment format 39 no
longer writes one, so the script stops at its first guard. =compass db recreate=
took the opposite route: it creates each service role without a password, keeps
a fixture login beside it, and leaves =compass vault provision= to write the
password. The recipe for adding a domain service points a reader at the manual
script, so the two paths now disagree about how a service role gets a password.

* Why

A person who follows the recipe for adding a domain service finds a script that
refuses to run on a current environment, and the reason is not in the script:
the variable it wants was removed because the vault holds the value now.

The two paths also disagree about the fixture login, which a cluster set up by
hand would not get, so a suite that acts as a service would fail on such a
cluster while =compass db recreate= makes it work.

Either route settles it: give the script the treatment recreate got, or delete
the manual path and point the recipe at =compass db recreate=.
