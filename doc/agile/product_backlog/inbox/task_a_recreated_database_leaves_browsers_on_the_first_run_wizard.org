* Notes
Seen on 2026-10-24 on brave_hopper after `compass db recreate -y -k` with the services up.

A session minted before the recreate names accounts the recreate replaced with new ids. Its token
can no longer be refreshed, so every read through it is refused. The setup gate reads the
onboarding flag through the session, a failed read yields false, and a signed-in account in
`system-administration` mode is then held on the first-run wizard. The wizard's first screen reads
the starting points through the same session, is refused, and reports "The starting points could
not be read… You do not have access to this." beside its own Bare system card — a card that is not
a server starting point at all.

A fresh sign-in proves the deployment: `/api/bootstrap` returns `isInBootstrapMode: false`,
`hasTenant: true`, `onboardingComplete: true`, and `/api/seed-profiles` returns the four profiles.
`compass open-as … --fresh` clears the persona cookie and fixes the browser.

Three things to decide:

1. The gate should treat a session it cannot read through as signed out, not as an installation
   that still needs setting up. A dead session must not be able to open the wizard.
2. `compass db recreate` should invalidate sessions: the BFF could drop every session when the
   database fingerprint or creation time it reports changes.
3. The wizard's fallback card should not stand in for a read that failed. When the starting points
   cannot be read, say so and stop; a card that creates no tenant is not an answer to a refusal.
