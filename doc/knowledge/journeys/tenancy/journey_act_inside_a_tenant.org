This page documents a [[id:F44766FA-1E9C-416F-849A-E131101B2ECA][user journey]]: A system administrator enters one tenant on purpose, sees on every screen that they act in it, reads its data through the ordinary reads, and leaves.

A user journey describes what one person is trying to do, before anything is
built. It is a design document that outlives any sprint, so it names the
screens, the entity fields each screen shows, and the operations and messages
each step needs.

* Goal

"I want to look inside this tenant the way its own people see it, and know that
I am doing so." The system administrator enters one tenant on purpose, reads
its data through the same screens and reads its members use, and leaves. The
journey is done when the administrator is back in system administration, and
the tenant's audit trail says who entered, when, and when they left.

* Actor and trigger

The system administrator: an account that holds the =SuperAdmin= role in the
system tenant, with the permission =iam::tenants:impersonate=. The trigger is a
question that only the tenant's own data answers: which parties it holds, who
has access, what its members signed in to. The journey starts on the tenant's
screen in [[id:9A77690B-8190-4237-94F1-D8111F3FB0B9][See one tenant]] and ends
when the administrator leaves the tenant.

The rule behind the journey: a tenant's data is read from inside the tenant.
The session's token names the tenant, row-level security scopes every read from
it, and no read takes a tenant as a parameter. So the administrator does not
get a second, cross-tenant way to read; they get a session in the tenant, and
the ordinary reads do the rest.

* Steps

1. *Enter the tenant.* On the tenant's screen, which the roster row's *Open*
   leads to, the administrator chooses *Act in this tenant*. The system checks the
   permission, refuses the system tenant, and issues a session scoped to the
   tenant. The session acts as the tenant's system party, which sees every
   party of the tenant. The system records the entry in the tenant's audit
   trail, with the administrator's account, so the tenant's own trail says who
   looked inside it.
2. *See that I am inside.* Every screen shows a banner: *Acting in Acme
   Corporation as admin*, with *Leave*. The session's mode is tenant
   administration, so the menus are the ones a tenant's administrator sees, and
   the system administration screens are not offered.
3. *Read the tenant.* The administrator lands on the tenant's *Parties*
   screen, which lists its parties with =refdata.v1.parties.list=, a page at a
   time with the server's total. *Who has access*, *Rescue access* and *Audit* read the
   tenant's accounts, sessions and sign-ins. Every read is the ordinary one,
   scoped by the session's token.
4. *Leave.* The administrator chooses *Leave*. The system ends the tenant
   session, records the exit in the tenant's audit trail, and returns the browser to
   the administrator's own system session, on the tenant's screen. The
   administrator does not sign in again.
5. *The session runs out.* The tenant session lives for one access lifetime and
   is not refreshed. When it expires, the system returns the browser to the
   system session and says the time in the tenant ended. The administrator can
   enter again.
6. *Refused.* An account without =iam::tenants:impersonate=, a session that is
   not in system administration, a session already inside a tenant, the system
   tenant, or a tenant no row names is refused with a reason, and the browser
   stays where it was. A suspended or terminated tenant can be entered: its
   data is still there, and reading it is how an administrator decides what to
   do with it.

Entering writes only the audit records. Inside a tenant, data is read only, and
two things hold it so. The token carries the administrator's own read
permissions, resolved from their roles in the system tenant and filtered to the
=:read= codes, so every service refuses a write that checks its permission. The
BFF also refuses every change while the session is in a tenant, before the
route runs, so a route that checks no permission cannot write either. The token
names the tenant the administrator acts from in the claim
=acting_from_tenant_id=, refresh refuses a token that carries it, and entering
refuses it, so a session inside one tenant cannot enter another.
A system administrator changes a tenant in one way only: by deleting the whole
tenant, from system administration, in
[[id:00179132-3463-45E9-A6FC-75B0F3EBCC8E][Retire or reset a tenant]].

* Operations and messages

#+ATTR_HTML: :class hug-leading
| Step | Operation | Subject | Status |
|------+-----------+---------+--------|
| Enter the tenant | Issue a session scoped to one tenant, record the entry | =iam.v1.ops.enter_tenant= | exists |
| Read the tenant | List the tenant's parties, paged | =refdata.v1.parties.list= | exists |
| Read the tenant | The tenant's accounts, sessions and sign-ins | the reads behind Who has access, Rescue access and Audit | exists |
| Leave | End the tenant session, record the exit | =iam.v1.ops.leave_tenant= | exists |

=iam.v1.ops.enter_tenant= is a domain operation, because it acts on a session
and not on an entity. Its request names the tenant by id. Its reply is the
token, the tenant's name and code, the party the session acts as, and the
access lifetime. The token carries the tenant, the tenant's system party, every
party of the tenant as visible, the administrator as subject and actor, and a
claim that names the tenant the administrator acts from, so audit columns and
the banner can say who is really acting.

The browser reaches both operations through the BFF: =POST /api/session/tenant=
enters and =DELETE /api/session/tenant= leaves. The BFF's client for the
browser session holds the system token beside the tenant token while the
administrator is inside, so leaving needs no sign-in. Leaving does not revoke
the tenant token, because no token is revoked in this system: the client
discards it, and it lasts at most one access lifetime. If the system session
itself ends while the administrator is inside, the browser signs in again, as
it would from any screen.

* What is missing

1. *Closed: a session scoped to another tenant.* =iam.v1.ops.enter_tenant=
   and =iam.v1.ops.leave_tenant=, in the operation model
   =ores.iam.tenant_session_messages=, issue and end it. The entry checks
   =iam::tenants:impersonate= against the database, because a person's token
   carries no permissions.
2. *Closed: a claim that says who is really acting.* The token carries
   =acting_from_tenant_id=, and refresh refuses a token that carries it.
3. *Closed: the cross-tenant party read.* =refdata.v1.parties.list-of-tenant=
   is removed; the parties are read inside the tenant.
4. *A person's token carries no permissions.* Login issues none, and the
   token check passes an empty list, so every permission check a handler makes
   against the token passes for a person. The tenant session is safe from this
   because it carries an explicit read-only list, but the gap is wider than
   this journey; the capture
   [[id:31644F1D-5A51-4742-BF6B-1E72F4697229][A token with no permissions passes every permission check]]
   tracks it.
