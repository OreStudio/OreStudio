* Plan

Phase 1 closes the grants first, because a read no person role may call is not a
read. The grants go to =Member=, the role every person account holds: the
journey's three actors all hold it, and a functional role adds nothing to a
shared screen. Each grant is one line in
=projects/ores.sql/populate/iam/iam_roles_populate.sql=, beside the section that
already classifies the same kind of read.

The latest-run read follows the codebase's own shape. The filter on
=definition_id= is the model's own =:filterable:= knob, so the filter record,
the repository condition and the TypeScript twin are generated rather than
hand-written. The latest-run read is a custom message on the run entity: one
request carrying the definition ids, one reply carrying one run per definition,
a custom repository method, and a custom handler method and subscription. The
generated files carry the paste points for all three, so nothing under
=projects/ores.reporting= is hand-edited.

* Notes

** What the tests call, and what they assert

Both tests live in
=projects/ores.reporting/core/tests/service_report_instance_listing_tests.cpp=
and call the read through the service, which is the entry its NATS users reach.

- =a list of runs answers only the definitions it is asked for= writes one run
  of each of two definitions, then asks the list for the first definition and
  for both definitions. It asserts the reply holds the runs asked for, and only
  those.
- =two definitions and three runs read as two rows, each the latest run= writes
  two runs of one definition and one run of another, asks the latest-run read
  for all three definitions, and asserts the reply has two rows: the newer run
  of the first definition and the only run of the second, with no entry for the
  definition that never ran.

** Phase 1, gap by gap

- *G6, G7, G8 and G9.* Five reads are granted to =Member= in
  =projects/ores.sql/populate/iam/iam_roles_populate.sql=:
  =reporting::report_definitions:read=, =reporting::report_instances:read=,
  =reporting::report_error_events:read=, =dq::fsm_states:read= and
  =scheduler::job_instances:read=. =Member= is the role every person account
  holds, which is what reaches all three actors of the journey. No wildcard and
  no write code is granted. The classification is stated in
  [[id:3CAA394F-E84C-3434-331B-6E664F7E84D2][Role-Based Access Control]].
- *G1.* One read answers for every definition named:
  =reporting.v1.report_instances.get_latest_by_definition=, declared in
  =ores.reporting.report_instance.org= under =* Messages= and carried through
  the custom paste points of the repository, the service, the handler and the
  sub-registrar. The store reduces, so the cost is one row per definition.
  Party scope is the row-level security on the table; the request names no
  party.
- *G2.* =definition_id= is =:filterable: true= on the run entity, so the list
  filter carries =definition_id= and =definition_id_one_of=, the repository
  builds the condition, and the TypeScript twin states them. The model, not a
  generated file, is the file that changed.

The shape chosen for G1 is two reads, not one join: the definitions read, then
one latest-run read keyed by the ids that read returned. Neither the definition
nor the run has to grow a composite message, and each read stays the codegen's
own artefact. The screen is one call per table, not the three reads and the BFF
reduction the specification records.
