* Plan

=ores-deploy-web-app= and =ores-inject-site-nav= already do the whole job:
copy a directory into the site tree, then patch its =index.html= with the
site chrome. The graph and agile apps deploy through them. So this task
adds no machinery. It does three things.

1. *Relocate the deploy destination.* The call for the trade entry prototype
   becomes =doc/prototypes/trade-entry=, so the app lands beside the org page
   that describes it. [[id:EDA1C2B2-C029-4BFC-8DEF-A15E8B369B4A][Build the booking screen prototype]]
   planned that path in the first place; the earlier call deployed to
   =prototypes/trade-entry= instead.

   The relocation also removes a trap. =ores-build-page.el= hardcodes the
   =site:pages= project, and =site:pages= publishes =doc/X.org= to
   =doc/X.html=. A page under a different publish project would go to a
   different place under =compass site page= than under a full build. Keeping
   the gallery inside =doc/= means the incremental publisher and the full
   build agree, and no second publish project is needed.

2. *Add the gallery.* =doc/prototypes/index.org=, scaffolded with
   =compass add knowledge=. One row per prototype, linking the app and the
   page that describes it. The link is relative (=file:trade-entry/=), so it
   resolves on the local preview and on the published site alike. A root
   relative link is not usable: org exports =[[/OreStudio/...]]= as
   =file:///OreStudio/...=, which is dead.

3. *Link it from the nav.* One top-level anchor in =site-html-preamble=,
   beside Home and Downloads, so the gallery is visible without opening a
   dropdown.

** The nav change needs the publish cache cleared

The site chrome — the nav and the stylesheet tag — is applied when a page is
published, and no source file's timestamp moves when it changes. So
=org-publish= keeps serving the old chrome from
=build/output/org-timestamps/site:pages.cache=, and a nav edit reaches only
the pages that were edited for some other reason.

=ores-build-page.el= states the intended cure for a rendering-only change:
name the pages on the command line, since a named page is published whether
or not its timestamp moved. That is the right tool for a handful of pages.
For a whole-site chrome change it is not practical, so delete the cache
instead and let a full build republish every page:

#+begin_src sh
rm build/output/org-timestamps/site:pages.cache
compass build site
#+end_src

=build/output/= is gitignored, so CI is always cold and always publishes
every page. The trap is local to a warm worktree.
