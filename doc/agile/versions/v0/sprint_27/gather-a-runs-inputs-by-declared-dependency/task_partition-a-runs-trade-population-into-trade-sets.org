* Goal

Nothing in =ores.trading= groups trades. The run resolves its scope once,
inside =gather_trades=, and treats it as one bag of books: the handler asks the
risk report configuration for its books and hands the whole list to one export.
A report covers hundreds to thousands of books, and each needs its own trades
archive, its own market data and its own portfolio XML.

Give =ores.trading= a batcher: a subsystem that partitions a report's trade
population into **trade sets**, driven by a **strategy**. The sets are what the
rest of the run reads.

* Acceptance

- A batcher partitions a report's trade population into trade sets, and a
  strategy decides how it partitions.
- "Batch by book" is the first strategy, and it is one implementation behind an
  interface rather than a special case in the caller.
- A trade set carries a name and an as-of date. The name is the **batch key**,
  a plain string of the form =REPORT_NAME:BOOK_ID:ASOF= for the book strategy,
  and nothing downstream parses it beyond using it as the artifact key.
- The batcher records the sets it created against the run, so the run knows its
  fan-out width before any producer starts.
- A later strategy can partition differently — by grid behaviour, by size —
  without a producer or the package step changing.

* Requirements the strategy machinery must carry

Recorded here while the batching subsystem's own documentation is pending (it
arrives with Merry Newton's trade-set work). These are requirements, not a
design; the design lands with the subsystem's docs.

- *A strategy is associated with a report.* Which batching a report uses is the
  report's to state, not a global setting.
- *Strategies compose.* "Simple report batching" is =batch by book= *and* =at
  most 1000 trades= — a composite over two strategies, not a third strategy
  that reimplements both. The simplest strategy is still the only leaf at the
  start, but the composition must already be expressible.
- *A strategy's parameters are configured in tables,* so a parameter is data
  and changing it is not a deploy. What a strategy reads must therefore be
  declared the same way its behaviour is.
- *A strategy may be marked default,* for a report that states none.
- *The leaf set starts at one.* =batch by book= ships first; the machinery
  around it ships with it rather than after it, because retrofitting composition
  onto a hard-coded first strategy is the thing this task exists to avoid.

* Plan

*The set is the unit, not the book.* A book is one way to slice trades and it is
the first way, not the shape of the system. Everything downstream addresses a
*trade set by its batch key*, so a strategy that groups by desk, by counterparty
or by whatever the grid is doing next needs no subscriber to change.

*The dependency is real and it is not ours.* Trade sets do not exist yet:
they are being built in =ores.trading= by Merry Newton. This task is blocked on
that landing, and the batcher is the second thing to be built rather than the
first. What the batcher needs from the set is small and worth stating so the
two efforts agree early: a name, an as-of, and the trades in it.

*Why the strategy is an interface and not a switch.* Grid behaviour is the
stated reason for wanting more than one strategy — how work is best split
depends on what the grid is doing — and that is a thing that changes while the
system runs. A switch in the caller would put grid knowledge in the report
path; a strategy boundary keeps it in trading where the population is known.

*The batch key is opaque downstream.* =REPORT_NAME:BOOK_ID:ASOF= is a
convention, not a grammar. Nothing downstream splits it: the key names an
artifact and the as-of travels on the set, so a future strategy may use any
string without a producer being able to tell.
