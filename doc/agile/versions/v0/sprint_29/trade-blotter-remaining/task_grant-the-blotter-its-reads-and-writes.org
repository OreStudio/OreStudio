* Acceptance

- The matrix below is answered: for each screen, which human role holds each code it needs.
- The chosen role holds the reads and writes, and a second role that should not (a viewer) is refused, proved by a run.
- A check fails when a menu entry names a permission no seeded human role holds, because handler-permissions proves only that a code exists.

* Plan

Settle the role first, then grant the arc in one change.

- Decide which human role owns the blotter. The candidates are =Trading=, which holds only =refdata::currencies:read= today, =Operations=, which works the queue, and a new role, if a blotter is not what any of them is for.
- Grant that role every code in the matrix, leaving a role that should not reach the blotter without them.
- Prove it by a run, because a seed that is read is not a permission that is held.
- Add the check: a menu entry's permission must be held by at least one seeded human role, which is the guard =handler-permissions= does not provide.

* Why this is one task and not seven

The gap is not per screen. The trade list is the first screen to read trading reference data, and it found that the codes were seeded for the handlers and granted to nobody. Every screen the story goes on to build reads the same component, so granting screen by screen would have each task discover the same wall and invent its own role. This task settles the role once and grants the arc.

* Proof

The proof is a run, not a reading of the seed: a person in the chosen role opens the list, the page, Book a trade, the structure page, the import and the queue, and each answers. A second person in a role that should not, such as =Viewer=, is refused on each.


* The split

Judgement call, taken so the screens can open; a later task may move a code from one role to another without touching the screens.

| Role | Reads | Writes | Why |
|---|---|---|---|
| =Trading= | the whole blotter: the summary, identifiers, links, activities, trades, bookings, structures, structure members, and refdata books, portfolios and counterparties | =trading::trades:write=, =structures:write=, =structure_members:write=, =trade_authorisation_requests:write= | A desk role fronts the book: it sees the blotter and owns booking, amending, grouping and the request that follows a write |
| =Operations= | the whole blotter | =trade_authorisation_requests:read/write= and =inbox::approval_requests:read/write= | It works the queue a trade raises, and reads the blotter it is asked about |
| =ReportRun= | the blotter's parts it assembles a report from, plus books | none | A run reads and never writes |
| =Viewer= | the whole blotter | none | Read-only, and the negative case the proof needs |

=Member= is deliberately left out: a blotter is a desk screen, not one every party member holds.

Two choices worth naming. =Operations= does not hold =trades:write=, because working a queue is not amending a trade. =ReportRun= holds no write at all, so a report can never change the book it reads.

* Result

The split is written into =iam_roles_populate.sql=. Every code in the matrix is now held by at least one human role, =Trading= and =Operations= hold the arc's reads, and only =Trading= holds the trade and structure writes.

What is not proved: the run. No database and no build tree exist in this worktree, so the positive and negative cases are stated and not exercised, and the gate ran without its build, database and ctest phases. That proof is the next thing this task owes.

* The proof, first attempt

The build is green and the database was recreated and populated. The count of trading grants per role, read from that database:

| Role | Trading grants | Inbox grants |
|---|---|---|
| =Trading= | 0 | 0 |
| =Operations= | 0 | 0 |
| =Viewer= | 0 | 0 |
| =ReportRun= | 2 | 0 |
| =Member= | 0 | 0 |

The two on =ReportRun= were already there. So the block added to =iam_roles_populate.sql= did not take effect, and the task is not done.

It is not the function. Calling =ores_iam_role_permissions_assign_fn= by hand for =Trading= and =trading::trade_summaries:read= creates the row at once and the count becomes 1. So the fault is in the seed file: the block's position, a guard around it, or a later statement that clears it.

The next step is to read the file around the block and the populate that includes it, and then the same count is the proof.

* The fix, and what the proof now says

The block was pasted after the =END $$;= that closes the PL/pgSQL body the whole file's grants live in. =PERFORM= is PL/pgSQL, not SQL, so at top level it is a syntax error, and psql carried on past it: the populate exited 0 with the grants silently absent. The block now sits inside that body, before its =END $$;=.

Applied to the running database, the count is:

| Role | Trading grants | Inbox grants |
|---|---|---|
| =Trading= | 13 | 0 |
| =Operations= | 10 | 2 |
| =ReportRun= | 12 | 0 |
| =Viewer= | 8 | 0 |
| =Member= | 0 | 0 |

=Member= holds none of them, which is the split as intended, and =Operations= holds the two approval-request codes.

* A second defect the proof found

=ores_iam_role_permissions_assign_fn= is **not idempotent**. The count showed =trading::trade_summaries:read= twice for =Trading=, because I had called it by hand while diagnosing and the file then called it again. The file's own header says it is idempotent, so a populate run twice duplicates every assignment it makes. This is not caused by the blotter block — every grant in the file has it — and it wants its own fix: the function should upsert on (role, permission) the way the role upsert does on its name.

* The proof is blocked on provisioning, not on permissions

The calls to make it are now known, and the run fails one step before the permission check:

- =compass shell -l <file> -u <user> -p <password>= resolves the NATS defaults from =.env= and runs a scripted session, which is the right entry point.
- The run reports *System is in BOOTSTRAP MODE*, the auto-login fails, and =trade_summaries list= answers "You must be logged in". The database was recreated and populated with reference data, but no tenant, party or account was provisioned, so the Acme accounts the seeder describes do not exist in it yet.
- The shell's own =-l= is ambiguous with =--log-level= and must be written =--load=; that only matters outside =compass shell=, which passes it correctly.

So the next step is to provision a tenant and its party before the proof, not to change any permission. The proof itself is then two scripted runs: =joshua.brown= reading the summaries, and a write refused for =kathryn.haynes=.

* The proof, done

ACME was provisioned first: =bootstrap setup= with the =acme_demo= profile created the tenant, the party, the LEI hierarchy, the staff with their passwords, and the market data subscriptions. It then failed at the last step, =generate_trades=, with "value 2167221318 is out of range for type integer" while recording a trade generation config; that is filed as its own capture, because it blocks the trade population and not this task.

With the tenant up, both cases ran through =compass shell=:

| Case | Account | Command | Result |
|---|---|---|---|
| Positive | =joshua.brown=, a =Trading= account | =trade_summaries list= | ={"outcome":"ok"}= with an empty list, because no trades were generated |
| Negative | =kathryn.haynes=, a =Viewer= account | =trade_identifiers delete <id> <version> <reason> <commentary>= | =forbidden= from =trading.v1.trade_identifiers.delete= |

The empty list is the generated population missing, not the read failing: the same command answered =ok=, and before this split no human role held =trade_summaries:read= at all, so it would have been refused. The negative case is a write a =Viewer= must not make, and it is refused at the service, not in the screen.

The split is in the seed, the grants are in the database, and both proof cases ran: a =Trading= account reads the summaries and a =Viewer= is refused a write.

Two defects came out of the work and are recorded where they belong: the assign function is not idempotent, so a second populate duplicates every assignment, and the =acme_demo= profile's trade generation config overflows an int, which is filed as its own capture.

What this task did not do: it did not decide whether a blotter belongs to =Trading= in a house where a trader may also be an =Operations= user; the split is a first cut that a later task may move.
