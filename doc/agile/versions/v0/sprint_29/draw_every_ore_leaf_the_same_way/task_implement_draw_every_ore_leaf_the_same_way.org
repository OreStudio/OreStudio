* Goal

Write the one standard for how a screen draws a leaf of an ORE document and the element type it belongs to, with the exact words, and the Allium specification of its state rules. Review it against the two built screens, product pricing and engine run settings, and record where each one, and conventions, conforms. Conventions are the first screen to apply it, in the tasks that follow.

* Plan

1. Compare the product pricing and convention data and screens, to find what a product and a convention share. The answer: the leaf and its documentation are the same; identity, ownership, reach and selection differ.
2. Take the words from the translations the built screens use, not from memory, and pick one where two screens differ.
3. Write the page, review it against the two built screens rule by rule, and take into the standard what the built screens do better.
4. Write the Allium specification of the state rules, leaving the words and the layout to the harness, as the record screen specification does.
5. Link the page into the graph with the relation of each link, and back-link it from every page it names.

* Result

The standard is [[id:852207A6-6785-43E6-A5D6-2D5C2C374101][ORE element and leaf screen standard]], and its specification is =doc/llm/specs/ore-leaf-behaviour.allium=.

- A product parameter, an engine run setting and a convention term are leaves. The page states how a leaf and its element type are drawn, with the exact words in one =oreParameter= namespace; four words are marked new and wait for the owner.
- The review against the built screens moved five rules from the engine run settings page into the standard and added two from the gaps of product pricing. Engine run settings fails mostly on its own copies of words and parts; product pricing shares the parts, but its data cannot yet answer three rules, because a parameter is held only when set.
- Conventions draw no leaf on any screen, so every rule is a gap there. The three tasks that follow apply the standard to conventions.
- The page is linked from the UX hub, the knowledge index and the screen review checklist, which has twelve lines for it, and back-linked from every page it names, with the relation of each link.
