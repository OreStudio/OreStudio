* Goal

The application's dark theme is the GitHub-dark palette the project site uses, and the landing-page review argued a different one: a blue-black surface ramp on slate neutrals, an indigo accent reserved for interaction, and a sky hue for content that is not built yet. The reviewed screens also lean on tokens the theme does not carry — accent tints, a tinted elevation glow, a radius scale, and a micro-label size — so every screen that wants them hard-codes a value instead. Move the theme onto the reviewed scheme and add the missing roles, from the one block every screen reads.

* Result

The application wears the scheme the landing-page review argued, from the one
block every screen reads: a blue-black surface ramp on the slate neutrals,
indigo for interaction, and sky for content that is not built yet.

The review's accent did not survive being measured. Indigo at 500 fails AA as
text on the raised surface and for the inverse ink on a filled button, where
400 clears both, so the hue is the review's and the lightness is a floor a
mock screen cannot show. Five of the roles that changed improved their
contrast; only the accent and its bright step got worse, both still inside AA.

The roles the reviewed screens reach for and the theme lacked are declared
with the palette: accent tints, a tinted elevation, a radius scale, the
micro-label size, and a hue for future content so a card that is not built
yet is never mistaken for a live control.

Two follow-ups are recorded rather than taken. =ink-faint= stays below AA on
175 secondary lines, because a palette move is the wrong place to change one.
And the prototypes still carry the old tokens by hand; refreshing them, or
checking the copies against the source, is its own change.

The palette no longer matches the project site, which the stylesheet header
now says.
