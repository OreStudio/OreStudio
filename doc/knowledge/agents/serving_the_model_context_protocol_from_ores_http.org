#+title: Serving the Model Context Protocol from ores.http
#+description: ores.http serves MCP's Streamable HTTP transport itself, on its own server, sessions and JSON codec.

This page states the target design. It does not describe what is built.

* Summary

=ores.http= serves the Streamable HTTP transport of the Model Context Protocol
at =/mcp=, on its own Boost.Beast server, sessions and JSON codec, with the
library boost.taar as the reference implementation rather than a dependency.
The claim of this page is that the transport is small and the server already
holds most of it, so writing it in =ores.http= costs less than adapting a
library whose tools are compile-time functions and whose JSON is a second
stack ([[id:FC0847D1-9F09-42EF-A4BD-D5E3C34398EA][How ores.http serves MCP]]).

* Detail

** What it serves

One endpoint answers three methods (Model Context Protocol, 2025a). =POST=
carries one JSON-RPC 2.0 message and is answered with JSON; =GET= is answered
with 405, which the transport permits of a server that sends nothing unasked;
=DELETE= ends a session. =initialize= issues an =Mcp-Session-Id=, which every
later request carries; a request without one, other than =initialize=, is
answered with 400, and one for an ended session with 404. A session is bound
to the person and agent that opened it, so an identifier another agent learns
names no session for it. The methods served are =initialize=,
=notifications/initialized=, =ping=, =tools/list= and =tools/call=; resources,
prompts and the other optional capabilities wait until a client needs them.

The routes at =/mcp= are declared to the catalogue as a transport: they change
nothing themselves, so the gateway holds no write against =/mcp=, and each
call a tool makes is held and recorded as the route it reaches. A request that
names an =Origin= other than this machine's, or one the deployment lists, is
refused, which the transport requires against DNS rebinding (Model Context
Protocol, 2025a).

** What it reuses

| Need | Already in ores.http |
|------+----------------------|
| An HTTP server with coroutine handlers | =http_server=, =http_session=, =router= |
| A streamed response | =awaitable_body_source=, which already serves =text/event-stream= |
| Sessions and authentication | the session store, and the bearer token every route reads |
| JSON | ORE's codec in =ores.utility/codec= |
| Tools | the route registry, through [[id:4C382E8F-9449-4012-A09F-76291373E6F7][Progressive disclosure of the operation catalogue to LLM agents]] |

** Authentication

An MCP client, Claude Code or a small local model's agent, sends a fixed
bearer header on every request, so every request carries the agent's key as a bearer token, as MCP's
authorization asks of every request in a session (Model Context Protocol,
2025b); a missing or invalid key is answered with 401. An MCP session id is a
transport identifier, not a credential, and grants nothing on its own. The key
is exchanged as [[id:1162906F-BB72-486E-9A11-30D567C65F3E][Delegation tokens for LLM agents: subject and actor claims]] describes; when OAuth is added, the endpoint also
publishes protected resource metadata and names it in its 401 answers, and
nothing else on the path changes.
