* Goal

Every hand-written caller that can send a put-many or delete-many of more than 1,000 elements sends it in parts of at most 1,000, sized from one named constant, so the refusal the next task adds breaks no caller.

* Acceptance

- The bound is one named constant, and the get-many refusal in the service template reads it.
- The variance calibration points, the synthetic counterparty and trade-type scope, the iam provisioning plans and the ORE import rollback send their batches in parts of at most 1,000.
- A test proves the split: each part holds at most 1,000 elements, the parts keep the order, and together they hold every element.

* Plan

1. Name the bound once. =ores::utility::domain::max_batch_size= in
   =protocol.hpp= holds 1,000, and =batches_of= splits a vector into spans of at
   most that size, in order. The service template's three get-many and one-of
   refusals read the constant instead of the literal.
2. Find the callers. A scan of every hand-written file that names a
   =put_many_*_request= or =delete_many_*_request= found six C++ files and five
   web files. Generated handlers only decode and dispatch, and the shell and
   HTTP surfaces pass a caller's request through.
3. Split each caller that can exceed the bound. Each split caller sends
   changes or removals that are safe to repeat: they claim =any=, or claim
   absence over rows the step skips once recorded.
4. Leave the callers that cannot exceed the bound. The web screens send a
   screen's rows, the GMM components are a mixture's few components, and the
   derived source already writes 1,000 at a time.

* Result

=ores::utility::domain::max_batch_size= names the protocol's 1,000-element
bound, and =batches_of= splits a vector into spans of at most that size, in
order. The rvalue overload is deleted, so a part cannot view a set that is gone.
Four tests prove the split: each part is bounded, the parts keep the order and
together hold every element, an exact-size set is one part, and an empty set has
none.

The service template's get-many and one-of refusals read the constant, and
every generated service is regenerated.

These callers now send in parts: the variance calibration input points, the
synthetic trade-type and counterparty scope, the seven iam provisioning curve
and surface plan writes, and the ORE import rollback's four delete-many calls.
The derived FX volatility source sizes its writes from the constant.

Verification: the whole tree builds. The utility protocol tests pass (4 of 4).
The iam core (305), ORE service (10), marketdata core (413) and dq core (126)
suites pass. The synthetic service suite passes 78 of 79. The one failure is an
adapter test that expects no answer to its announce, and this environment's
marketdata service answers it. With that service stopped, the 20 adapter tests
pass. The light local checks pass, 46 of 46.
