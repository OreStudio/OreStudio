* What

A tenant provisioning run is a workflow whose steps publish bundles, import a
registry hierarchy, create parties and load staff. If it dies part way — a service
it needs is down, a step fails — nothing picks it up again. `provision tenant`
refuses with "A tenant with the code 'acme_corporation' already exists", and
`compass db reset-tenant` re-arms the *browser's* wizard rather than a headless
run. The only headless way forward is `compass db recreate`, which throws away
every other tenant in the database to finish one.

* Why

The work a tenant provisioning run does is worth minutes, not seconds, and a
database worth recreating holds other tenants, sessions and runs. A run that fails
at step 8 of 8 leaves a tenant in `bootstrapping` with its accounts loaded — a
state no command can move forward and no command can cleanly restart.

Measured on 2026-10-31 in this worktree:

| Step | Outcome |
|------+---------|
| `bootstrap setup … --profile acme_demo` | reached `generate_trades` (step 8 of 8), then failed |
| tenant status | `bootstrapping`, 294 accounts loaded |
| `provision tenant --tenant-code acme_corporation` | refused: code already exists |
| `compass db reset-tenant -t acme_corporation -y` | reset done; its message says the *wizard* fires on next login |
| `reset-tenant` then `provision tenant` | still refused: the tenant row is preserved by design |

Two shapes would fix it. A `provision tenant --resume` that starts the profile's
remaining steps on a tenant in `bootstrapping`, or a `compass db reset-tenant
--delete` that removes the tenant row and its provisioned data so the ordinary
command can run again. The first is the better one: the run already records which
steps completed, so the information needed to resume is on hand.
