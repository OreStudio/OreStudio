* Goal

The rate engine holds current state and answers rate() and rates() for now. A volatility derivation needs ten years of daily levels. Step the same engine day by day through a publisher's fixing series, reading every pair after each day, and return the levels as a history. The streaming path is untouched: this is a second way to drive the same engine, not a second engine.

* Result

=replay_fixings= steps the same =rate_engine= the live path uses through a
publisher's fixings: each day's quotes go in through =update()= and every pair is
read through =rate()= at that day's close, so a caller gets one level per day with
no second triangulation and no change to the streaming path.

Four decisions the tests pin:

- The replay stamps every quote with its day's close, whatever clock the caller
  set, because a fixing is known when its day ends.
- Days may arrive in any order and are stepped oldest first.
- A day a pair could not be read keeps its row, carrying =fresh=, =stale=,
  =disconnected= or =unavailable=, so a gap reads as a gap rather than as a
  shorter series.
- The pairs are resolved against the topology before anything is stepped, so a
  pair nobody quotes is refused by name instead of returning a history quietly
  short of one series.

Measured: =ores.analytics.quant.tests= passes in 16.19 seconds. The six new cases
state the cross read from each day's own drivers (150/0.90, 151/0.91, 152/0.92),
out-of-order days stepped correctly, a day without the yen tick keeping its row
and ageing to =stale= under a one-hour tolerance, an unknown pair refused naming
it, an empty pair list refused, and no days being an empty history rather than a
failure. Both changed files were compiled with the build's own flags before the
build ran, and clang-format is clean.
