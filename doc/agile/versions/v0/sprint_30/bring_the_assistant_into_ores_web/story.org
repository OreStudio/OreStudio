* Goal

A person signed in to ores.web asks the assistant, in a panel of ores.web,
to do anything they can do themselves: find and read records, run
reports, explain results, and book or change records. The assistant works
through the same operations the screens use, with the person's own
permissions, and every operation it performs is recorded as the
assistant's, done for that person, so nobody can mistake it for the
person's own action.

The prototype in =projects/ores.agent= (PRs #4498, #4534 and #4752) shows
that this works. Its architecture does not fit ORE's:

- It is a separate Node process with its own chat UI, outside ores.web.
- It calls NATS through a hand-kept subject map, =backend.ts= and
  =backend-contract.json=, pinned to one revision, instead of the
  generated wire protocol, so it drifts when a subject changes.
- Its tools are written by hand, one per question, so it can do only what
  someone wrote a tool for.
- It starts and owns a llama.cpp process, so the model is not a service
  the rest of the system can run, watch or scale.
- Its documents call it read-only, but it books trades through
  =trading.v1.ops.book_trade=.
- No ORE gate covers it: =compass check= and compass-ng do not read it.

This story designs the target architecture first, then builds it, and
retires the prototype once ores.web does what it does.

* Context

- The browser is moving off the BFF onto ores.http. This story adds
  nothing to the BFF. See [[id:21323568-8E87-4858-98E1-77451E123965][Serve what the BFF serves, then retire it]].
- ORE already has two patterns for one service calling another, and one
  for a service acting as a user: [[id:3E20C1A0-7BA1-4F31-8C34-1E5F13558890][Service-to-service auth]] and [[id:AAC60D20-8696-4455-9292-E8FAE1389CBC][Internal actor impersonation]]. The machine operation

* Acceptance

- The assistant runs in ores.web and reaches the server only through
  ores.http and the services behind it. Nothing is added to the BFF.
- The model runs on an inference server that the analysis chooses: plain
  llama.cpp, deployed and run beside ORE, or an ORE service that wraps
  it. Either way, ORE's tooling starts and stops it, a person can see
  whether it is healthy, and its model files are pinned.
- The model can call any operation the signed-in person may call, from a
  catalogue derived from the generated protocol, not from hand-written
  tools.
- Every operation the assistant performs is distinguishable from the
  person's own, in the audit trail and wherever ORE shows who did what.
- An operation that changes data runs only after the person confirms it.
- Asked about something the knowledge base covers, the assistant answers from
  its pages and links each page it used, which ores.web shows as a page.
- The gates cover the new code, and the prototype is retired or reduced
  to what the new design keeps.

* Decisions

- *ores.http only* (2026-11-21). The BFF-to-ores.http migration is nearly done,
  so the assistant's server side is ores.http and the services behind it, and
  nothing goes through the BFF. Taken over from solid_dirac the same day.
- *ores.http speaks MCP itself, with boost.taar as the reference*
  (2026-11-21). Context: no C++ MCP library is both mature and a fit; boost.taar
  is the only one on Beast and in vcpkg, but its tools are compile-time C++
  functions and its JSON is Boost.JSON. Decision: implement MCP's Streamable
  HTTP transport in ores.http as an improvement of its own server, reading
  boost.taar for how each part of the protocol is handled. Consequences: no new
  dependency; the catalogue comes from ores.http's route registry; conformance
  is tested against the official MCP conformance runner. See [[id:FC0847D1-9F09-42EF-A4BD-D5E3C34398EA][How ores.http serves MCP]].
- *Split into three stories* (2026-11-21). The knowledge base is a feature
  without any model, and MCP is useful without the assistant. So they are their
  own stories: [[id:05FE6068-3CBD-4B93-B6AE-47A5689F1FCB][Search the knowledge base from ores.web]],
  [[id:008127D7-B897-4CF7-854B-6DDFB89AC7F4][Serve ORE's API to LLM agents over MCP]], and, when both are done,
  [[id:70A4D585-8A56-475D-BE32-803D08A5D0CF][Answer from the knowledge base over MCP]]. This story keeps the
  chat in ores.web, the agent loop, the inference server, the confirmation of
  changes in the chat, and the prototype, and builds on the three.

* Out of scope

- New BFF routes or BFF changes for the assistant.
- Hosted model providers. The model runs in ORE's own service; whether to
  add a hosted provider later is a separate decision.
- Training or fine-tuning a model.
