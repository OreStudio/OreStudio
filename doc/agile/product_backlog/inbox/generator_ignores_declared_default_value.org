#+title: The synthetic generator ignores a column's default_value unless the column also carries a generator block
#+description: cpp_domain_type_generator.cpp.mustache honours a column's declared default_value only when the model also supplies a generator block; with no block it assigns a random faker value, silently discarding the default. Fixed for assets by restating the literal in a generator block; the template fix would touch all 53 models that declare default_value.

This page is a [[id:671F18E4-E09C-4B3B-BD24-D33DF8AE38A6][capture]] in the *inbox* bucket of the product backlog — a pre-sprint idea, not yet pulled into a sprint as a story.

* What

Make the C++ domain generator honour a column's =default_value= when the column declares no generator block, instead of inventing a random value.

* Why

The generated domain type carries the declared default: =image.hpp= says =std::string mime_type = "image/svg+xml";= and the SQL column default is the same string. The synthetic generator disagrees. In =cpp_domain_type_generator.cpp.mustache= the text-column branch is ={{#generator_expr}}= ... ={{{generator_expr}}}= ... ={{/generator_expr}}{{^generator_expr}}= =r.<column> = std::string(faker::word::noun());=, so =default_value= is consulted only when a generator block also exists. The result was that every synthetic image was written with a random noun as its media type.

The assets story fixed its own instance by restating the literal in a =generator= block on =ores.assets.image.mime_type=, which is duplication and a standing invitation to let the two drift apart. A template-level fix is the root-cause one: when a column has =default_value= and no =generator_expr=, use the default. The reason it was not done here is cost — =default_value= appears in 53 model files across the tree, so changing the template changes generated output for every component at once and needs a tree-wide regeneration and a drift check on a committed tree, the same shape of change as the notify-trigger defect.
