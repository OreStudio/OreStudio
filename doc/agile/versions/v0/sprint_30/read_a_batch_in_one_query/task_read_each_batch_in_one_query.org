* Goal

The generated get-many, put-many and delete-many paths read their rows with one query per batch, and put-many answers from one read of the rows it wrote.

* Acceptance

- The service template reads the current rows of each batch path with one query.
- A put-many still refuses the whole batch when one row fails its precondition, and writes nothing.
- The regenerated services build and pass their suites, and the codegen drift gate is clean.
- A 1,000-row put of market observations is measured before and after, with the command, on the same environment.

* Plan

- Add one helper, =<entity>_read_many=, beside =<entity>_read_one= in
  =ores.cpp.service.service_impl.org=. It returns one entry per key, in the
  order of the keys, and each entry holds what =_read_one= holds for that key.
  Every bulk path calls it, so the call sites do not depend on the key shape.
- When the declared key is the storage key, the helper calls the repository's
  batch =read_latest= in chunks of 1,000 keys. It joins the rows back to the
  keys by the text form of each key column (=key_text= and =row_text=), which
  is the same conversion the compound-key filter already uses.
- When the declared key is not the storage key, the helper loops over
  =_read_one=. A batch finder by declared key is a separate task.
- =prepare_change= takes the current rows as a parameter. Put-many reads all
  current rows once before the loop. The single put reads its one row.
- Put-many reads back the written rows with the keys it read before the
  write. A write keeps the key its change states.
- Delete-many uses the helper on the gated path and on the declared-key path.
- Remove =:service_batch_reads_by_trade_id:=. The general path covers its
  seven trade-id entities, so the flag has no use.
- Out of scope: the junction service variant (24 services). Its repository
  has no batch read.

* Notes

- The trade-id get-many refused more than 1,000 keys with
  =filter_too_large=, because one statement carried every key. The helper
  reads in chunks, so that reason is gone and the refusal is removed. No test
  asserted it.
- =:has_batch_read:= is set on seven trading models, but no template reads it.
  Every repository declares the batch =read_latest=.

** What limits the put after this task

The repository's batch write checks each row's claim with its own read:
=apply_claim= calls =read_latest= once per row. Before this task a 1,000-row
put made about 3,000 single-row reads (2,000 in the service, 1,000 in the
repository); after it, about 1,000. Both sides cost about 5.5 ms a read
(16.52 s / 3,000 and 5.89 s / 1,000), which is what a read-bound path gives.
This is inferred from the counts, not profiled. The repository's claim check is
the next task of the story.

** What the benchmark leaves out

The benchmark calls the service in process, so it leaves out the NATS round
trip, one message each way per batch on both sides. The end-to-end number is
the derived source's first history, measured at the end of the story.

** Not in this task

- Services whose declared key is not the storage key read each key on its own,
  through the same helper. Their repository has no batch read by that key.
- The 24 junction services and the 4 convention services come from other
  templates.

* Result

The generated get-many, put-many and delete-many paths read their rows through
one helper, =<entity>_read_many=, which reads a storage-keyed batch with one
query per chunk of 1,000 keys. Put-many reads the current rows once before it
checks the changes, and reads the written rows once to answer.

- Acceptance 1 holds for every service keyed by its storage key: 528 entity
  services call the helper. Services keyed by another declared key still read
  each key on their own, through the same helper.
- Acceptance 2 holds: a refused row refuses the whole set and nothing is
  written. =service_market_observation_batch_tests.cpp= proves it, and fails
  when the service passes no current row to the check.
- Acceptance 3 holds: the 14 touched core libraries build, the dq, trading and
  marketdata core suites pass, and the drift gate flags only a protocol file
  that main already drifts on.
- Acceptance 4 holds: a 1,000-row put went from a median of 16.52 s to 5.89 s.
  The repository's per-row claim read is what remains, and is the next task.
