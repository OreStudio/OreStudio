SQL file has a recorded reason to be hand-written. What codegen can own, it

* Plan

No single method fits. The census is an investigation, the CI gate is a
feature, and generating the aggregates would be a refactoring whose evidence is
an unchanged recreate. This plan sequences them.

| Phase | Produces | Check |
|-------+----------+-------|
| 1. Census | every SQL file under =create=, =drop= and =populate=, labelled entity codegen, other generator, or hand-written | the labels sum to the tree's file count; every file codegen renders exists in the tree |
| 2. Reasons | for each hand-written file, why no generator produces it | every file lands in exactly one class; one file per class is read to confirm |
| 3. Aggregates | whether a component's create and drop order can be derived from its models | a derived order for one component satisfies every dependency the hand order encodes, or the gap is named |
| 4. Gates | the parser fails CI on a warning; generated drop files carry a marker | the parser passes =--strict= on main; drift is clean after the template change |
| 5. Decisions | a decision per class, an evidence file, and follow-up tasks | each class has generate, keep with a reason, or delete |

The census uses the drift checker's own rendering, not file markers: it
renders every catalogue component into a scratch root, and a file is entity
codegen output exactly when that root contains it.

*Stop and ask before* generating any aggregate or moving a hand-written file
to codegen. Phase 5 decides, and the operator approves, before that work
starts. Stop phase 3 at a recommendation if the hand order encodes dependencies
the models do not hold.

* Notes

Found while reviewing PR #2500 (today's market round trip). Adding five
entities passed the build, the model drift check and every test, and the
entities still did not reach the database until two aggregate files were edited
by hand.

**The aggregates are hand-written in every component.** All 22
=create/<component>/<component>_create.sql= files and their drop twins are
written by hand. They hold the =\ir= includes in dependency order, with prose
per block. This is a project-wide convention, not something PR #2500 started.

**A check exists and does not fail.** =validate_component_wiring= in
=projects/ores.codegen/src/plantuml_er_parse_sql.py= reports rule =WIRE_001= for
any create or drop file the root script does not reach. The
=codegen-drift.yml= step runs the parser with =--warn= and without =--strict=,
so the report only prints. With the five today's market =RLS_001= warnings
fixed, the tree has zero warnings, so =--strict= costs nothing today.

**Generation looks possible for the aggregates.** The models already hold the
foreign keys, so a dependency order can be computed by a topological sort. The
open questions:
- where the prose per block goes;
- how hand-written files (functions, RLS, service bundles) sit in the same order;
- whether one generated fragment per component is better than generating the
  whole aggregate.

**Generated drop files carry no marker.** For example,
=drop/analytics/analytics_todays_market_configs_drop.sql= is generated but has
no "generated" line. So the drop count below cannot tell generated from
hand-written.

* Result

The hand-written SQL is measured, every class has a decision, and the checks
that let two defects reach main are now gates.

**The census.** Of 1800 SQL files, 1119 are entity codegen output, 164 come
from other generators and 517 are hand-written. The method renders the
generator's own output rather than trusting markers. Every class, its reason
and its decision are in the
[[file:evidence/hand_written_sql_census.md][evidence file]], with the scripts.

**Decisions.**

| Class | Decision | Owner |
|-------+----------+-------|
| Component create and drop aggregates | Generate the entity part per component; hand-written files stay listed by hand | [[id:3460236B-747A-4081-B3E6-9CE98CCE709D][Generate the entity part of each component's SQL aggregates]] |
| FpML coded-scheme tables, artefacts and triggers (44 + 15) | Model them so codegen owns them | [[id:08B98A2C-5123-45B0-B536-8421AB99EC0E][Model the FpML coded-scheme tables so codegen owns them]] |
| Hand-written RLS policies (251) | Generate from model flags into a late per-component file | [[id:AE86A142-B734-44F1-9647-0F37A551DA83][Generate the hand-written RLS policies from model flags]] |
| Tables with no model (25) | Model those a codegen shape covers | [[id:F59B6C8F-B487-4C8C-82FF-E6DB21EFF6F1][Model the hand-written tables that have a codegen shape]] |
| Procedural code, views, =alter= scripts, uncatalogued components, populate seed data, data generators | Keep; each reason is in the evidence | — |
| Dead legacy triggers (15), broken FpML populate (1) | Deleted | this task |

**Why aggregates can be generated.** Soft foreign keys impose no creation
order: 88 tables are already created before the parent their trigger checks,
and every recreate succeeds. Only a table before its trigger, functions from
earlier components and hand files that name tables at creation need order.

**Gates.** The schema parser fails CI on any warning. =WIRE_001= now covers
every =.sql= file in the three trees, reached from their roots and from the
bootstrap scripts, which found fifteen dead files and two populate scripts that
never ran. The five real drop gaps are wired and the full drop script runs
clean. The census is committed as a tool.

**Recorded, not fixed here.** Three captures: =ores_iam_auth_events_tbl= has a
=tenant_id= and no RLS policy despite an ignore reason calling it tenant-scoped;
two populate scripts were never wired, and wiring them changes what a recreate
seeds; the drop script leaves 115 functions behind.

**One operational note.** The first recreate hung for minutes in =DROP
DATABASE= on =ProcSignalBarrier=, with this environment's services still
reconnecting. Stopping the services, cancelling the drop and retrying worked.
