* Goal

A system administrator configures a supplier session once, with its endpoint,
environment, credential and settings, and adds the publisher feeds that come off
it. The adapter runs with those values instead of command-line flags, so a test
session and a production session of one supplier differ without a redeploy.

* Acceptance

- A supplier has sessions; a session names one adapter, one environment, one
  endpoint, one credential reference and the adapter schema's settings.
- A feed names one publisher, one session, one service, a provider key, a scope
  and a schedule. No item belongs to two feeds of one publisher.
- The adapter reads the session transport and reports the values it uses; no
  endpoint or interval comes from a service flag.
- A secret is a reference. A read never returns its value, and a write sets or
  rotates it.
- A party routes one feed for each publisher and asset class.
- The prototype shows the supplier → session → feed tree, with the adapter
  catalogue behind it.

* Decisions

- The content owner is the *publisher*. The delivery party is the *supplier*.
  They are different: Frankfurter delivers the ECB's data; Bloomberg is both the
  supplier for a session and the publisher of its own data.
- An *adapter* is code, installed by the release. An *instance* is now a
  *session*: one configured adapter at a supplier, with an environment.
- A *service* is what a session offers, and it decides the feed's shape:
  =real_time= is demand driven, =end_of_day= is scheduled, =historical= is a
  backfill.
- A *feed* is the binding: publisher + session + service + provider key + scope
  + schedule. It replaces the code's "source".
- A party routes one feed for each publisher and asset class. The route key
  changes accordingly.
- Transport and credentials live on the session. The publisher keeps its terms
  and credit; the supplier carries the contract.
- The endpoint is entered once per session, not once per feed.
- An adapter is a class whose metadata names its code, version, process, asset
  classes, services and configuration. The catalogue holds the definitions the
  release ships; an installation claims a module only when that module
  announces itself, so a module this installation never runs is not installed
  here. The release defines two: =frankfurter= and =synthetic=.

* Terms compared

The story had to choose a name for the configured instance of a provider. This
table records the candidates and the reason the story uses the fourth.

#+ATTR_HTML: :class hug-leading
| Candidate | What it would name | Why the story does not use it | Word used instead |
|-----------+--------------------+-------------------------------+-------------------|
| Provider | The content owner and the delivery party at once | The two are different, and the contract, the credentials and the support belong to the delivery party. | Publisher and Supplier |
| Source | The configured adapter | It hid the supplier's session and made every feed repeat the endpoint. | Session and Feed |
| Instance | The configured adapter | The code already used it ad hoc; the real-world word for a configured connection is a session. | Session |
| Service | — | It is not a candidate; it is needed, because real-time, end-of-day and historical feeds behave differently. | Service |

The story uses *provider*, *source*, *adapter*, *kind*, *route*, *item* and
*vendor instrument*, with the meanings in the table above and the examples in
the prototype.
