* Plan

The session is a codegen entity, like the adapters and suppliers it names. The
code is the key as well as the label a feed will use, so it is the primary key:
=frankfurter-eu= names one session as clearly as an id would, and a feed's
=session_code= stays readable in a query.

The session carries the supplier and the adapter by code, the environment, the
endpoint, the credential reference, the settings and the enabled flag. The two
codes are validated against the system-tenant catalogues, so a session cannot
name an adapter or supplier the release does not define. The environment is a
check constraint over =production=, =test=, =dr= and =simulated=.

The settings are the one field whose validity depends on another row: the
adapter's =configuration_schema=. A hand-written trigger validates them, because
the codegen insert trigger carries only per-column validations. It refuses a key
the schema does not state, a missing required key, a value of the wrong type,
and a settings value that is not a JSON object.

The system tenant owns the rows, as it does for the catalogues: one set of
adapter processes serves the installation, not one per tenant. The session has
its own event registrar, history provider and handlers, and no shell unit: the
shell's =sessions= menu belongs to IAM logins, and the Connectivity screen is
where a person configures a session.

The acceptance's =a read returns a session and its feeds= waits for the feed
entity (task A3). The read returns the session's own row today.
