* Acceptance

- After switch-party, a batch added in the same session carries the chosen party.
- The soak sends each wave in a random party of the sender's tenant.

* Plan

=select-party= and =switch-party= printed the new token and kept the old one, so every later command of the session ran in the party the login opened in. A script could not change party, and neither could a person in the shell. The commands are generated, so the fix is in the generator.

- A message in an operation model may state =:shell_adopts_token_for: <request field>=. The field names the party the token is scoped to.
- The loader reads it, refuses a field the request does not have, and projects it as =adopts_token_field=.
- The shell command template emits a block for such a command. On success it stores the token as the session's token, with the party as the default party.
- Both party messages of the iam model state it, and the shell commands are regenerated.
- The grid soak reads the parties of the sender's tenant, other than its system party, when it starts. Each wave then switches to one at random. =--no-spread-parties= keeps the login party.

* Result

The shell keeps the token that a party switch returns, so later commands run in the chosen party. The soak spreads its waves across the parties of the sender's tenant. A script that switched to the UK and then the US party added a batch in each. A 70 second soak put batches in all four Acme parties. The compute work of a tenant can now be seen split by party.
