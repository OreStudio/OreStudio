*This page is a proposal under review. The use cases are complete; the journey
list is the set proposed to write and prototype. Nothing here is an accepted
journey yet.*

* Overview

The compute grid is not one screen. It is a set of things a person wants to
find out and do, and the [[id:5E970C7F-68EA-42BF-B73E-997C4A003762][Operations journeys]]
give exactly one of them a journey: the fleet survey. Everything about the
*work* the grid does — how much is in flight, how busy it is, where the time
goes, why a job failed, what is about to arrive, what capacity it needs — has
no journey at all.

This page states those use cases, decides how few journeys can carry them, and
is the input to prototyping them.

* The rule: a journey splits only for security

A journey fragments only when the *activity itself* cannot be the same for two
people, and narrowing the rows cannot make it the same. Everything else is one
journey whose rows the session decides.

Two forces push against fragmenting, and both are stronger than they look.

- *The common deployment is one tenant.* In it the tenant administrator and
  the super administrator are the same person. Forcing them into a mode to see
  their own grid is friction bought for nothing.
- *Row scoping already exists.* A member, their tenant administrator and the
  super administrator asking "where is this job" are one activity over three
  visible sets, which permissions and row-level security already describe. Two
  journeys would duplicate every step, every screen and every model to express
  one difference the database already knows.

So the burden of proof sits on the fragment: name the data that would leak, and
show that narrowing cannot withhold it. Where a boundary is real, the first
answer is still one journey with one control withheld — a whole second journey
is the last resort, not the first.

* The use cases

** 1. Is the grid healthy right now?

How many nodes, are they reporting, which is behind, what the wrappers are
doing, how much work is in flight, and how that load moved over the last day
and week.

*Security:* the fleet is the installation's and carries no tenant's data, so
everyone the permission admits may read it whole. The work counts are
cross-tenant aggregates and are the only part with a real question — answered
by a permission on a panel, not by a second journey.

** 2. Where is one job?

One job end to end: its state, its node, its timings, its inputs and outputs,
and where its time went.

*Security:* rows. A member sees their own job, a tenant administrator their
tenant's, the super administrator all of them. One journey.

** 3. Why did it fail, and can I run it again?

A job's full detail — its app version, package, command, inputs, exit code and
stderr — plus the node's own logs, so the work can be reproduced locally.

*Security:* this is the one genuine boundary, and it is a capability rather
than a journey. The job's own detail is rows and narrows as in use case 2. A
*node's* logs are installation logs and may carry another tenant's inputs, so
pulling them is a capability the super administrator holds and another tenant
administrator does not. Same screen, one control withheld.

** 4. What is coming, and can the grid take it?

What capacity the nodes have, what a job needs, what is scheduled to kick in
soon, and whether the grid can absorb it.

*Security:* rows again. A tenant sees its own arrivals and its own share; the
installation's totals are the installation's.

** 5. What may the grid run, and how much at once?

The apps, their versions and packages, and the concurrency policy that caps
how many of a thing run together.

*Security:* writing the catalogue is the super administrator's; reading it is
everyone's, because a tenant needs to know what it may submit. A permission on
the write, one journey.

** 6. Keep the grid running

Drain a node for maintenance, requeue stuck work, stop a runaway.

*Deferred.* This is control, not observation, and the Operations area's mode
is reading. It may belong with the scheduler journeys.

* The journeys proposed

1. *Watch the grid* — the fleet, the load, and how it moved.
2. *Follow a job* — one job end to end, and where its time went.
3. *Diagnose and reproduce a failure* — a job's full detail, its node's logs,
   and enough to run it again locally.
4. *Plan the grid's capacity* — what the nodes have, what a job needs, and
   what is arriving.
5. *Keep what the grid runs* — apps, versions, packages and concurrency.

Five to write, one deferred. Not nine: the actor split I first proposed was not
a security boundary, and expressing it as journeys would have duplicated five
screens to say what the session already says.

* Where the actor dimension actually bites

| Use case | Single-tenant deployment | Multi-tenant deployment | Fragment? |
|----------+---------------------------+--------------------------+-----------|
| Watch the grid | The operator sees it whole | The super administrator sees it whole; a tenant administrator sees the fleet and no other tenant's counts | No — one journey, a gated panel |
| Follow a job | Everyone sees every job | Rows: own, tenant's, all | No — rows |
| Diagnose a failure | The operator sees everything | The job's detail narrows; the node's logs are withheld | No — one control withheld |
| Plan capacity | The operator sees it whole | Own arrivals and own share; totals are the installation's | No — rows |
| Keep what the grid runs | The operator reads and writes | Everyone reads; the super administrator writes | No — a permission on the write |
| Keep the grid running | The operator acts | Super administrator only | Deferred |

Every "fragment" column is empty, which is the finding: the grid has use cases,
not actor-segregated screens.

* Open questions

- *Jobs versus the scheduler.* "What is scheduled to kick in soon" is the
  scheduler's question, answered by =ores.scheduler=; the grid's is what those
  arrivals do to the load. The two journeys must not both own it.
- *Jobs versus reports.* A report run submits a batch of workunits; the
  [[id:1805BAFC-7E43-4D9C-822F-17C3455C6E00][Compute job lifecycle]] is the
  flow between them. Each journey must say which end it starts from.
- *Where does the mode boundary belong?* The Operations area is offered in
  system administration mode alone. If the common deployment is one tenant,
  that boundary is itself a fragmentation the journeys did not ask for, and
  the area's reach is worth re-deciding separately from the journeys.

* How the use cases are reached today

| Use case | Journey today |
|----------+---------------|
| Watch the grid | [[id:7B820710-161C-4926-B5AA-5EF2772A3652][Watch the compute grid]] — the summary, the node table and the wrappers; the load and its history are absent |
| The rest | None. [[id:E7035C69-EB6E-4158-B384-825A8CDACA8A][The grid has no usage history]] records one of the gaps, and [[id:57C4B9A6-DA79-403E-984E-50D2561352B3][Read the telemetry logs]] searches the installation's logs rather than pulling one node's |

** The legacy surface agrees.** The retired =ores.qt/compute= client carried
=HostMdiWindow=, =BatchMdiWindow=, =WorkunitMdiWindow=, =ResultMdiWindow=,
=QueueMonitorMdiWindow=, =QueueChartWindow=, =ComputeConsoleWindow=,
=ComputeDashboardMdiWindow=, =ConcurrencyPolicyController=, =AppMdiWindow=,
=AppVersionMdiWindow=, =TransferProgressDelegate= and the =Report*= family.
Not one of them has a journey behind it. The legacy client is not the target —
the journeys are — but its breadth measures what is missing.
