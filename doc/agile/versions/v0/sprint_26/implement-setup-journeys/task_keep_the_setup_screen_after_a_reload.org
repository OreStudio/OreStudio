* Acceptance

- The bootstrap status read answers whether the deployment has a tenant of its own, the system tenant aside.
- The route table keeps every path on the setup journey while the deployment has no administrator or no tenant, and releases it when it has both.
- A journey that opens on a deployment which already has its administrator asks for that account rather than creating a second one.
- The password typed there is what a profile that shares the administrator's password hands to the tenant's administrator.
- A policy tightened since the password was set does not lock the administrator out of the installation they own.

* Plan

*The gate answers the deployment.* An installation is set up when it has
an administrator and a tenant of its own, and the setup screen is the only
screen until it has both. The gate read only the administrator question,
which created the hole: creating the administrator closed bootstrap mode,
so a browser that reloaded before it had finished was sent to the ordinary
sign-in screen with no path back to the work. The status read now answers
the tenant question beside it, counting the system tenant out, because the
system tenant is the deployment's own bookkeeping.

*The rail opens where the deployment is.* A position on the rail is memory
and does not survive a reload, which the journey already says of itself. So
the journey opens at the step that signs in as the administrator the
deployment already has, rather than at the welcome: the welcome describes
work that is partly done, and the account exists, so it cannot be created
again. That password is kept for the journey's length, because a profile
may hand the creating administrator's password to the tenant's
administrator, and it is not measured against the policy a second time: a
rule tightened since it was set must not lock somebody out of the
installation they own.

*The gate releases on the fact the journey produces.* The tenant is what
ends the setup, and the answer is stale by then, so the journey asks again
when it finishes. Without that the browser would sit on a journey that has
nothing left to do.

* Notes

- The live deployment answers ={"isInBootstrapMode":false,"hasTenant":false}=
  after the change, which is the state the report described: an
  administrator exists, the installation has no tenant, and a reload now
  lands on the setup rail rather than on the sign-in screen.
- *What this leaves.* A reload after the tenant is created but before the
  hand-over finishes still drops the rail, because the tenant is the
  deployment fact the gate reads and the run is then server-side: the
  progress read can follow the run by instance id, but nothing in the
  browser remembers which run it was. The *New tenant* journey is where a
  person starts one again from the application, and it is the place to
  carry that.
