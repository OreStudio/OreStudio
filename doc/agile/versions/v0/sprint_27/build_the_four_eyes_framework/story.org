* Goal

A gated write cannot take effect until every function the policy names has approved it, the person who asked cannot decide, and every kind of request shares one queue, one request page and one review panel.

* Acceptance

- A request can name several deciding parts, each answered by a person holding that part's permission, in order where the policy says so.
- A request holds its proposed writes, applies them in one transaction on the last approval, and records a failed apply.
- A gated write refuses with approval_required unless it comes from an approved request.
- One review panel, one request page, one queue and one story draw every kind through a kind descriptor.
- The book structure, counterparty, party, convention and tenor screens raise requests instead of writing.

* Decisions

- *A line holds its proposed write as a typed row.* The product owner ruled that the data design allows no untyped or weakly typed data, and the role request already keeps a typed table keyed by the request. Each gated entity therefore gets a generated pending table with its own columns. The earlier recommendation of one lines table with a serialised write is withdrawn.
