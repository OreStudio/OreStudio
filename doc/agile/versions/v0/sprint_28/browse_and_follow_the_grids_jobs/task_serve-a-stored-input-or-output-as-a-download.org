* Acceptance

- A caller who may read the record and holds the storage read code downloads the file, and a large file streams. A party member lacks that code, and the task Let a party member download its own files carries that case.
- A caller who may not read the record is refused before any byte of the file is read.

* Plan

Two BFF routes stream a stored file, and the screens link to them.

- =GET .../workunits/:id/input= and =GET .../results/:id/output= read the owning record on
  the session's own client first. A denied or missing record answers 403 or 404 before the
  storage service is asked for any byte.
- The route then asks the storage service for the object path the row states, with the
  session's own token, and streams the body on under the file's own name. A path that is not
  a plain object path under the storage prefix is never asked for.
- The Jobs tab details and the job page Files panel show the stored address as a link to the
  route for a person who holds =storage::objects:read=, and as text for anyone else.
- The HTTP server read no request whose headers passed 8 KB, and the access token of a person
  who acts for many parties does. The server now accepts up to 64 KB of headers.

* Notes

- The first member download failed with 500 and then 502 because the HTTP server closed
  the connection: the member's token was larger than 8 KB. The header limit option fixes it.
  The storage service then refused the member with 403, because the Member role does not hold
  =storage::objects:read=.
- Granting that code to the Member role would let any member read any stored object through
  the storage service, since the code states no record. The task does not grant it.
- The storage service is reached at the base address the HTTP info subject states, so the BFF
  keeps no address of its own.

* Result

A person who holds the storage read code downloads the stored input of a workunit and the stored
output of a run from the Jobs tab and the job page. The BFF reads the owning record first and streams
the file on. A party member lacks the code and sees the address as text, which a follow-up task carries.
The HTTP server accepts larger headers, so the token of a person who acts for many parties is read.
