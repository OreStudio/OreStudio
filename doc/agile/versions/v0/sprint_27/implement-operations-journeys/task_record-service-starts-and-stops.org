* Goal

The roster can tell a graceful stop from a crash, and it can count restarts.
Heartbeats alone answer only whether an instance went quiet. Every process
announces two lifecycle events through the shared service lifecycle in
=ores.service=: =started= when it becomes ready, and =stopped= in its shutdown
hook, before =nats.drain()= flushes it. The messages and the table belong to
telemetry, which already stores every heartbeat: the events are modelled in
=ores.telemetry= and stored in =ores_telemetry_service_events_tbl=, and no
service writes the table itself. The roster then states four things:
*running* (started, heartbeats fresh), *stopped* (the last event was a graceful
stop), *lost* (started, never stopped, heartbeats quiet) and *missing* (no
instance ever filled the slot), with each instance's start time and its
service's restart count.

* Acceptance

- The telemetry model carries the =started= and =stopped= event messages, and
  telemetry stores them in =ores_telemetry_service_events_tbl=.
- The shared lifecycle in =ores.service= publishes =started= on readiness and
  =stopped= on a graceful shutdown, and owns the heartbeat the services start
  one by one today, so no service wires either by hand.
- =ores.storage.service= and the =ores.web= BFF publish heartbeats and both
  events; today neither sends a heartbeat, so the roster shows both missing.
- The roster states running, stopped, lost and missing, each instance's start
  time, and each service's restart count over a stated window; a restart whose
  previous instance never stopped is marked as one.
- A test proves each state, and a graceful =systemctl stop= of a live service
  reads as stopped rather than lost.

* Notes

Settled with the operator on 2026-10-06, after comparing the decommissioned
controller (definitions, instances with =pid=, =phase= and =restart_count=, and
events). The roster needs a small subset of it: what should run, which comes
from the registry through the expected-services table; and what each instance
said about itself, which comes from these events and the heartbeats.
Supervision stays systemd's job, as it would be Kubernetes' in a real
deployment, so =pid=, stderr and restart policy are not modelled.

A service cannot write the table itself: =ores.service= owns no SQL, and the
compute wrapper, the http server and the web BFF have no database. Telemetry
is the one writer, as it is for heartbeats.

When the telemetry service itself stops, its own =stopped= event may be lost,
because it is draining the subscription that would store it, so it can read
as lost. That limit is documented rather than solved.
