* Acceptance

- The menu page names the Trades area, its screens, its addresses and where each screen belongs.
- The entity screen specification covers the trade page, booking, the structure and package screens, and the entity protocol.
- Booking is one page in tabs, with a combo box for the trade type and a tab for each part of the instrument.
- The trade list filters through the standard filter record, and the prototypes show the request.

* Plan

Read the menu page, the entity specification and the NATS entity protocol. Add the Trades area to the menu page. Add the trade, the structure and the package, and the entity protocol, to the entity specification. Change the prototypes: Book a trade becomes the Add button, the trade type a combo box, booking one page in tabs with a tab for each part of the instrument, and the list a standard filter record. Remove authorisation from the prototypes and the journeys.

* Result

The menu page now names the Trades area, its screens, its addresses and where each screen belongs. The entity screen specification covers the trade page, booking, the structure and package screens, and the entity protocol the screens read and write through. The prototypes follow both. Authorisation is out of scope and is drawn nowhere. Its capture waits in the backlog.

The reading of the NATS entity protocol showed that the trade list needs model changes and no new operation: a search member, and filterable columns for the counterparty, the trade type and the state. The trades of a book are the standard scoped read =list_by_book_id= with the subtree scope.
