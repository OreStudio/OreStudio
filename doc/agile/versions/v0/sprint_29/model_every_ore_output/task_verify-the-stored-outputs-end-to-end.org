* Plan

1. Fix the defect that failed every run: a central convention keeps its party
   inside =identity=, so the run configuration read its party from there too.
2. Write the first scenario: one report, four families stored, one skipped,
   one misspelt.
3. Make the run screens fit to test with, as the tester asked on first sight:
   - The runs of a report are a standard record table: a state badge, a
     duration column, and a row that opens the run.
   - A run has one page, under reporting, with four tabs: Details, Results,
     Errors and Downloads. The operations page of a run is gone, and its old
     address sends the reader to the new page.
   - The errors are one row each, with the columns Severity, Scope, Subject and
     Message, and a filter by severity.
   - Downloads lists every file the run read and wrote: the input package and
     each file inside it, the output archive and each file its manifest names,
     with size, digest, family and the job. The BFF builds the list from
     compute's records and serves each file by its id in that list.
   - A run with no results says so, and points at the Errors tab.
4. Grant select on views to the service roles. The results view was never
   granted, so every results read failed with "The results could not be read."
5. Read the run's figures from the key the service replies with. Commit
   804a0dad50 moved the read to =reporting.v1.run_results.list= but kept the
   old reply key =rows=. The reply names them =results=, so every run showed no
   results while its figures were stored. Run 9f2a5329 has 36 rows in the view.
6. Give the run screens what a tester asked for on second sight: an overview
   and a list of the errors, with a trade subject linking to its trade; the
   results tables as standard record tables; the files in a tree of the run,
   its batch, each job and its input package and output, on the blotter's rail
   moved into a shared TreeRail.
7. Name every file of a run as the ORE user guide names it. A new reporting
   entity, the ORE file, is keyed by the guide's name: market_data, npv_cube,
   npv_report. It has a category, a configuration type, a guide section, an
   origin, a format, a typical name and the regex of every name a run gives it,
   and a description written by hand. Fourteen categories group the 148 files,
   following the guide's chapters for what a run is given and its data flow
   for what ORE writes, with one for ORE Studio's packaging and one for the
   schemas. File types name their ORE file by code; the output catalogue keys
   each family by it, so stress.csv is the stress test report's other name.
8. Store the schemas: each XML schema ORE ships is an ORE file, an xml file
   names its schema by a self join, and ore_file_version holds the contents of
   a file at one engine version, seeded from external/ore/xsd after checking
   its manifest's digest. A file's page offers its schema for the engine that
   ran the job, as a zip with every schema it includes.
9. Send every member of a request the generated codec now requires. The run
   trigger, the booking and its instrument batch were refused with "Missing
   member"; the bodies are now typed with the generated requests.
10. Keep the tests to what they mean: the SQL tests read the moved columns
    through the ORE file, and a test that counted every live feed counts the
    seeded ones, since the integration tests write into the same database.

* Notes

** Why a file is an entity of its own

A file type is a parameter that names a file: npv.outputFileName,
simulation.cubeFile. Many parameters name one file, the cube is written by one
analytic and read by two, and some files no parameter names at all: ore.xml,
the log, the outputs the engine names itself. So the file is the parent and the
parameter points at it. Direction and kind stay on the file type, because the
cube is an output of the simulation and an input of xva: they belong to the
parameter. The format and the schema belong to the file.

** Why the includes are read from the contents

A schema is complete only with the schemas it includes, and input.xsd includes
22. The stored contents state the includes, so the download reads them there; a
table of includes would state the same fact twice and could disagree with it.

** Why the schema check orders paths as sort does

The vendoring script's tree digest orders the paths with sort, which follows the
locale, so the seed check orders them the same way. A machine whose locale sorts
differently would compute another digest; the fix belongs in the vendoring
script.

** Why the errors were all combined at the bottom

The old operations run page grouped errors by curve. It made one card for each
curve-scoped error and hung the trade errors that named the same curve under it.
Every other scope, Analytics, Report and Configuration, and every row whose
scope did not match a curve, fell into one catch-all card, "Analytic and report
failures". That card dropped the scope and the subject, so a person could not
tell which trade or analytic each line was about. The new list shows one row per
error, with its scope and its subject.
