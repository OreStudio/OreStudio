* Acceptance

- The job starts a pooler in transaction mode against the test database, with the
  configuration the shared-fleet task states, and runs the affected suite through
  it.
- The job runs wherever this repository validates a change - the push to main or
  the scheduled build - because no workflow here triggers on a pull request. It
  is not optional.
- It fails when the prepared-statement decision is violated: with named statements
  and a pooler below the floor, or with unnamed statements configured as named.
- The default path stays direct: a developer runs the suite with no pooler
  installed, and CI's ordinary job still does too.
- The job's own cost is recorded, because a check nobody waits for is a check
  nobody runs.

* Plan

** What the measurement changed

Two things this plan assumed are wrong, both found by running the suites through
a pooler on the development host.

First, the tests do not read their database from the shell. Each suite's
environment is baked into =CTestTestfile.cmake= as one =ENVIRONMENT= property,
generated from =.env= when CMake configures. Redirecting a suite to a pooler is
therefore a *configure* step, not an exported variable: the port must be the
pooler's before =cmake --preset= runs, or the property still names 5432.

Second, the suite this task names is not the one that proves the statements.
=ores.marketdata.service.tests= through a pooler ran 307 of 328 cases; the 12
failures were the harness, not the pooler - no NATS settings and no service
database user, because the binary was run outside ctest. =ores.database.tests=
is the suite that exercises the statements directly, and through a pooler it
runs 71 of 75 with the same four connection-level cases review named on
[[id:5C2A4734-FE8D-4097-9720-31515FA03CA5][Settle the statement question]].

** The shape the job takes

1. PostgreSQL from =build/scripts/start_ci_postgres.sh=, as every other job does.
2. =pgbouncer= installed by the job's own step. Ubuntu 24.04 carries 1.21, which
   is the floor the statement task decided, so the job tests the floor and not a
   comfortable margin.
3. One configuration, generated by a script beside =start_ci_postgres.sh=, so the
   unit and the job share it rather than each writing its own: transaction mode,
   =max_prepared_statements= at its default, a stated =max_db_connections=, and a
   credential file built from the environment's own database users.
4. The suite runs with the environment configured against the pooler's port.
5. The direct path stays the default: the ordinary job runs the same suite with no
   pooler, and nothing about this job changes a developer's machine.

** What this task cannot claim yet

The acceptance asks for a job on every pull request. This repository has no
workflow that triggers on a pull request - the =no-pr-triggers= gate forbids it -
so the job can run where the change is validated instead: on the push to main,
in the =compass check= gate, or in the scheduled build. The acceptance line is
amended below rather than quietly satisfied by a job that never runs.

* Notes

** Measured, 2026-11-21

- =ores.database.tests= through a transaction pooler with
  =max_prepared_statements = 0=: the first prepare fails, "prepared statement
  ores_pq_set_context already exists".
- The same suite with the default 200: 71 of 75 cases pass. The four failures are
  the listener (which the story keeps direct) and three connection-level cases in
  =pq_layer_tests.cpp=.
- =ores.marketdata.service.tests= through the same pooler: 307 of 328, the
  failures being the harness's own missing environment, not the pooler.
