* Notes

- Every generated repository defines helpers such as =list_order= in an anonymous
  namespace, so files merged into one unity source redefine them. A unity build
  needs the generator to put each file's helpers in a namespace of its own, which
  CMake supports with =UNITY_BUILD_UNIQUE_ID=. Measure after that change.
- Only two names collided in =ores.dq.core=: =queue_group= in the 21 message
  registrars and =list_order= in 20 repositories. =unity_fix.py= renamed them to
  =<file stem>_<name>= to measure; the generator's registrar and repository
  templates need the same change, which is two template edits.
- Batch size 16 beats 32 on wall time: 173 files make about 6 batches of 32, too
  few to keep three jobs busy. The precompiled header adds little on top of a unity
  build, because each batch already parses its headers once.
- Peak memory rises from 1.8 to 4.0 GiB across three jobs, because a job compiles
  16 files at once. It stays within the build slot.

* Result

A unity build of 16 is the largest single lever found. On =ores.dq.core= it cut
the wall time by 74% and the CPU by 75%. Peak memory rose from 1.8 to 4.0 GiB
across three jobs, which stays inside the build slot. Batch 16 beats 32 on wall
time, because a component of about 170 files makes too few batches of 32 to keep
three jobs busy.

A unity build needs file-local names that do not collide. The generator now
prefixes each file-local helper with the entity name (commit =6b80472c6b=), so
no generated file collides with another. The remaining collisions are in
hand-written code, such as =lg= and test helpers. A full unity build of the
tree, in =build/output/unity-16=, is renaming those now. The full-build
measurement against the baseline needs a quiet machine, and it is not done.
