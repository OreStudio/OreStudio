* Goal

Decide what the layer between an ORE XML document and the ORE Studio model
is, and settle it with measurements rather than preference.

The bond review found that a money value cannot be recovered exactly from the
generated binding wherever ORE types the element as a bare =xs:float=. That
was one symptom. The layer has two more problems of the same origin: it builds
an object graph where the guidelines say the document tree is transient, and
it splits one mapping across 122,000 generated lines and 800 KB of
hand-written mapper that cannot be checked against each other.

The story is done when the route is chosen, the evidence is on the page, and
the work that follows is broken into tasks.

* Acceptance

- One investigation page states the design, the alternatives and the decision.
- One prototype demonstrates the design on a real ORE document and reports
  time, allocations and fidelity against the current path.
- The prototype's output agrees record for record with the production path on
  the document it covers.
- The follow-on work is expressed as tasks with sizes, or the route is
  declined with the reason recorded.
- Numeric accuracy is stated as an invariant, not a hope: money is a decimal
  taken from the document's digits, continuous quantities stay binary, and the
  writer emits a form that reads back to the same value.
- Round trip is defined as the values surviving and the output validating
  against =input.xsd=, not as the document being reproduced.
- Every corpus root element is either on a table and proved by the harness, or
  named by the census as still migrating because product code reads it, or
  deleted because nothing does. No family is silently left behind.
- Every XML document in the repository parses with the new scanner, and the
  check that proves it fails the build when one does not.
- The write direction is specified, including the one place where shortest
  round-trip formatting is wrong.

* Decisions

- *A family nobody reads is deleted, not mapped.* Seven of the twenty corpus
  root elements have no product consumer, so a table for them would prove a
  capability no feature has. They are deleted with xsdcpp, and a table is added
  if a feature needs one. The census in
  =build/scripts/check_xml_family_coverage.py= names the state of every family
  and fails when the tree disagrees with it.

- *The document tree is transient.* The
  [[id:BBD43BF2-9FEE-42B0-A667-9468AF759DC2][guidelines]] place ORE
  documents at the boundary, outside the three regimes, and name the entity
  representation as the review target. The design follows that rather than
  the usual shape of an XML library.
- *Three routes were weighed; route C is recommended.* Keep and extend
  =xsdcpp=, adopt a document library, or own a scanner driven by tables
  generated from the schema. The investigation carries the numbers.
- *The mapping becomes data.* A table can be checked against the XSD by
  constructing it. The mechanical part of the mapping moves into the table,
  and the semantic part stays a short function.

* Out of scope

- Extending =xsdcpp=. Route A is described and rejected, not scheduled.
- Reproducing a document byte for byte: comments, indentation, attribute
  order and the original spelling of a number are out of contract.
- A general XML library: XPath, run-time schema validation, a DOM.
- The drift on =trade= and =componentSubTrade=. Route C does not touch the
  generated binding, so the drift stops blocking anything.
- Removing =xsdcpp= before every root element has a codec. It is the last
  task, not an early one.
